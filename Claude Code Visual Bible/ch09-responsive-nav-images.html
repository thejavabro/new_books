Responsive Design, Navigation and Images

Make the layout rearrange instead of shrink, connect the three pages with navigation anyone can use, and add images that are lawful, light and described.

1

Responsive means rearranging, not shrinking

A responsive page rearranges its content to fit the screen. It does not just scale everything down until text is too small to read and buttons too small to tap. If things are shrinking rather than rearranging, you need a breakpoint, not a smaller font. Drag the width and compare the two approaches.

2

Start from the smallest screen

Design for a narrow phone first and add complexity as space allows; pages built that way age better than ones designed wide and hoped to shrink. Ask Claude to walk the page at phone width before touching wider layouts, then add breakpoints (CSS media queries) only where the design genuinely needs to change: a handful of well-chosen ones beats dozens of tweaks.

Assume this page is viewed on a phone about 375 pixels wide. Walk through the hero and features sections and list anything cramped, cut off or too small to tap. Don't change anything yet.

Add breakpoints so the features grid shows one column on narrow screens, two on medium and three on wide screens.

Use your browser's responsive preview mode to test, not just a slightly narrower desktop window: real phones are much narrower than a resized laptop browser.

3

Navigation anyone can use, including by keyboard

Navigation must work for someone using a keyboard or a screen reader. Click into the demo below, then press Tab to move between links and Enter to follow one. You should always see where focus is. Then switch off the focus outline to feel what it's like when a site removes it.

Current page: Home. The underlined link is the active state.

Every page should carry the same navigation: same labels, same order, same active-state style. A visitor shouldn't have to relearn it page by page, even on a three-page site. Which of these pages breaks the pattern?

4

Fill Support and Privacy with real, specific content

Support works well as three or four real questions with answers. Privacy has exactly one job: let a cautious visitor check what data HabitTrail collects, why, and how to get it deleted. Vague reassurance fails that job, and so does pasted boilerplate that doesn't describe your app. If you can't state specifically what's collected, decide that before writing the page.

Would a cautious visitor learn anything?

5

Use images that are legally yours

An image you didn't make isn't automatically yours to use. Stick to your own work, assets explicitly licensed for free use, or ones you've paid to license, and note each source and licence the moment you add it (one line per image in your project notes is enough). A small-business owner in the book almost published a striking photo found through a search engine before a friend asked about the licence.

6

Responsive images and alt text that helps

Images should scale with the layout, and every meaningful image needs alt text: a short description a screen reader announces and that shows if the image fails to load. Ask what the image adds. If it matters, describe what it shows and why it's there, as you would to someone on the phone. If it's purely decorative, give it empty alt text so screen readers skip it. Never just the filename or "image". Decide for each picture and write alt text where needed.

7

Testimonials, FAQ and a download panel

A few familiar sections make the home page feel finished and help visitors trust and act. Because HabitTrail is a book example, any testimonials must be clearly fictional examples, never something that could pass as a real review. Structure each new section like the others: a meaningful heading, readable text, a layout that responds across widths.
