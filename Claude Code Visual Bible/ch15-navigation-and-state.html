Navigation, Props and State

Wire the three screens together with Expo Router, then make them respond: props carry data in, state changes on a tap, a streak is calculated not stored, and one shared list feeds every screen.

1

Three screens as real routes

Save your Chapter 3.1 brief as BRIEF.md in the app project so Claude can build from it. Expo Router turns files in the app folder into screens, the file's location giving the screen's address. Ask for three routes from the brief: Habits as the main screen, Add Habit, and a Habit Detail route that takes an identifier. Confirm each file exists and loads without errors in the terminal; you won't be able to reach them on the phone until navigation is wired up, which is expected.

2

Tabs for destinations, a stack for drilling in

Tab navigation shows a few top-level destinations, usually along the bottom, that you switch between directly: here Habits and Add Habit. Stack navigation pushes a new screen on top of the current one, with a way back: tapping a habit opens its detail. Test it with placeholder content first; a broken back button is far easier to spot on a screen that just says "Habit Detail". Try this one, including a deliberately bad identifier.

Navigation stack

Pass an id, then check itThe detail screen learns which habit to show from an identifier passed in the route. A screen that assumes the id is always valid can crash or show a confusing blank if it's ever missing or wrong. Confirm Claude added a check and a friendly fallback, and test it with nonsense yourself.
3

Props flow down, events flow up, state changes

A prop is data handed into a component by whatever uses it, like handing someone a document instead of expecting them to have it already. HabitCard receives the habit's name and whether it's done as props, which is what lets one component show any habit. State is data that can change over time, such as whether a habit is done today. A tap sends an event up; the screen updates its state; the screen redraws with the new value. Tap the cards.


  






  
4
Calculate the streak; don't store it

  
It's tempting to keep a separate streak number and add one each time a habit is marked done. It drifts. A reader in the book found his displayed streak disagreeing with the record once he could edit past days. Instead, derive the streak fresh from the completed days every time it's shown: correct by construction. Mark days, then "edit history" by unticking a past day, and compare.

  

    

    

    
0derived streak (counted from the days)
0stored counter (+1 on "Mark today done" only)

    

  

  
The general rule: for any number the app shows, ask whether it could be calculated from data you already store.






  
5
One shared list for every screen

  
All three screens need the same habits: one created on Add Habit must appear on the list; one marked done on the list must show as done in its detail. If each screen keeps a private copy, they drift apart. React Context makes one piece of data available to any screen that needs it, held by a component called a Provider: a shared shelf every screen can reach instead of a copy in each drawer. Add a habit both ways.

  

    

    

    

  

  
In plain language, explain what you just created: what a Provider is, where it sits in the app, and how each of the three screens reads and updates the habit list.
