Behaviour with JavaScript and a Contact Form

JavaScript follows one small pattern: find an element, wait for an event, change a value, update the screen. The same pattern powers a menu, an FAQ, a theme toggle and a contact form that fails gracefully.

1

Select, listen, change, update

JavaScript makes a page respond. Nearly every interaction follows one four-step shape: select an element (by the same id or class your CSS uses), listen for an event such as a click or key press, change a value, and update what the visitor sees. You won't write this yourself, but you should be able to read Claude's explanation and confirm it matches what you want. Press the button and watch the four steps fire.

2. Listenwait for a "click" event
3. Changeadd 1 to the count
4. Updateshow the new count on screen

const btn = document.querySelector('#like');   // 1 select
btn.addEventListener('click', () => {          // 2 listen
  likes = likes + 1;                             // 3 change
  label.textContent = likes + ' likes';          // 4 update
});

Explain in plain language what happens, step by step, when a visitor clicks the iOS download button: how it's found in the HTML, what the code listens for, and what changes on screen.

3

A contact form that fails gracefully

The Support page gets a form. Three rules make it trustworthy. Every field has a real label connected to it (placeholder text can show an example, never replace the label). Validation checks the constraints that matter before submitting: name and message not empty, email looks like an email. Keep rules sensible; over-strict rules frustrate more than they protect. And errors must keep everything typed and point at the exact field with a message you can act on. Try it with a deliberate mistake first.

A student in the book lost a whole paragraph of feedback to one missing @ under the "bad" behaviour. Switch modes and submit the mistake to feel the difference.

4

Or skip the form: a mailto link

The form posts data to a server, which suits a site that must collect every submission in one place (Netlify can do this, see the next chapter). A lighter option is a mailto link: it opens the visitor's own email app with a draft addressed to you. No server at all, so it even works on GitHub Pages. But it sends nothing by itself, and on a device without an email app it may do nothing useful. Label it honestly, like "Email us".
