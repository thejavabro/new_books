Plan the Website and Structure It with HTML

HabitTrail needs a three-page site. Plan it around who visits and what they need, then create the project, run a local preview and give the home page meaningful structure.

1

Plan around visitors and the one action each needs

Book 2 builds the public website for HabitTrail, a habit tracker you'll build as an app in Book 3. The app needn't exist yet; you only need to describe it honestly: it helps someone build a small daily habit and see their progress. A product site serves several kinds of visitor, each wanting one thing. A page that tries to do all three jobs usually does none well. Match each visitor to the page that serves them.

Which page is for them?

2

Sketch the site map, then write it in words

Three pages: Home introduces the app and links to Support and Privacy; both link back to Home. A small map isn't a limitation, it keeps every page focused. A sketch helps you think, but you'll also want a written version you can paste to Claude Code: a plain text outline or a Mermaid flowchart (text that compatible tools draw as boxes and arrows). Toggle links and watch both versions, and the trap checker, update.

3
Content and a success criterion for every page

  
For each page, a sentence or two of required content and one criterion you could actually check: these are the website's acceptance criteria. For Home: introduce HabitTrail, list its main features, give a clear next step; success is a first-time visitor explaining in one sentence what it does. Support: answer likely questions; success is finding an answer without leaving the page. Privacy: what data is collected, why, and how to have it deleted; success is finding this without searching.

  
Usable as a success criterion?

  
A real nonprofit in the book started with fourteen pages. Naming one action per page cut it to five; the other nine became sections.






  
4
Create the project and a local preview

  
Plain HTML, CSS and JavaScript, no build tools, so the structure stays small enough to understand. Ask Claude Code for one minimal file per page (just a title and a heading for now) plus folders for shared styles, scripts and images, using the exact names from your site map. A reader in the book let Claude invent about.html instead of support.html; asking for the exact structure avoids that drift. Tap the tree.

  
I'm building a three-page site for a habit-tracking app called HabitTrail: Home, Support and Privacy. Suggest and create a simple folder structure with one minimal HTML file per page (title and one heading each) and shared, empty CSS and JavaScript files.

  

    

    

  

  

    

    
A local preview (often an address like http://localhost:8000) shows the site in your browser and refreshes as files change. It exists only on your computer while the preview runs; nobody else can open it. Check all three starter pages load before adding content, then initialise Git and make a first commit.

  






  
5
Meaningful regions: header, nav, main, footer

  
Semantic HTML uses tags that say what a region is for. Screen readers let people jump between these regions; with generic <div>s everywhere there is nothing to jump to, and no visual polish fixes that. Tap a tag, or switch to "div soup".

  

    

    

      
<header> HabitTrail name + navigation
<nav> Home · Support · Privacy
<main>
<section> Features
<section> Try HabitTrail
<footer> © and contact

      

    

  






  
6
Check the document outline before styling

  
Headings should nest in order: one top heading for the page, smaller ones for each section, never a level chosen because it "looks the right size". That is CSS's job in the next chapter. Ask Claude to list the headings with their levels, or set them yourself below and read the verdict.

  

  
Then the call to action: a specific link like "Try HabitTrail", not "Click here". Upload your brief and ask Claude to build the home page's main content from it.
