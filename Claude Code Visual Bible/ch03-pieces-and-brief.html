Software Pieces and the Build Brief

Recognise what software is made of so you can follow along, then turn a rough idea into a short brief with a user, a smallest useful version, acceptance criteria and non-goals.

1

Interface, logic, data and services

You won't write these pieces, but recognising them lets you follow along, ask sensible questions and spot something out of place. Nearly all software, from one page to a big app, is built from four kinds of part. Tap each layer.

Which kind of piece?

The tiny page from the last chapter was almost all interface. The following books add logic, data and services one at a time.

2

Recognise a language by its shape

HTML gives a page structure, CSS makes it look a certain way, JavaScript adds behaviour, and TypeScript is JavaScript with extra mistake-catching (you'll meet it in Book 3). Around them sit HTTP (how browsers request things from servers), JSON and XML (structured data) and SQL (querying data). You don't need their rules, just the ability to tell one from another, the way you can tell a recipe from a shopping list. Glancing at the file extension first (.html, .css, .js, .ts/.tsx) usually settles it.

Name that snippet

3

Packages, frameworks and APIs

Claude Code chooses and installs most of these for you. Your job is to ask, in plain words, what a package does before relying on it. Unfamiliar words are never a reason to stop asking questions.

4

Start the brief with a person and a problem

A build brief gives Claude Code a clear target and gives you something to check the result against later. It starts with who it's for and what problem they have right now, before any solution. "A tool for renaming files" is a start; "a tool that renames a folder of holiday photos by the date taken, for someone who imports hundreds and can never find one later" is something to aim at.

Build for yourself, not for a market

The author's warning: Claude Code can make a working tool in under an hour, but finding users, earning their trust and supporting them is as hard as ever. Each time a creative tool got easier (home recording, photo editing, website builders, the early App Store), the number of makers exploded while attention stayed the same. Drag the slider.

So aim your first briefs at yourself or someone you know. If your "user" reads "anyone who…" or "small business owners who…", you've written a product for a market. Park that idea somewhere outside the brief.

5

Choose the smallest useful version

Plan the smallest version that is still useful, not the polished finished one. A brief with ten must-haves is a wish list. Sort a study-timer idea into "first version" and "later"; the book's rule of thumb is three or four must-haves at most.

6

Acceptance criteria you could hand to a stranger

Acceptance criteria are specific, checkable statements of what "works" means. A good test: could someone else check your result without asking what you meant? Non-goals are things you are deliberately not building yet, written down so you and Claude both know they were a choice. Without them Claude can happily build a sprawl of features you never wanted.

Checkable or vague?

7

Write your brief in Markdown

Save the brief as BRIEF.md. Markdown is plain text that stays readable before formatting: # starts a heading (## a smaller one), - starts a bullet, *italic* and **bold** add emphasis, backticks mark `code`, and blank lines separate blocks. A missing blank line above a list is the usual reason a preview looks wrong. In VS Code, create the file in the Explorer and open the preview with Ctrl/Cmd+Shift+V.
