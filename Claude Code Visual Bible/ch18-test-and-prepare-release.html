Test on a Real Device and Prepare for Release

Test like a stranger would, including offline and with a screen reader. Then give the app its permanent identity and the assets and policies the stores expect.

1

From quick checks to a deliberate test pass

Most testing so far happened in small checks after each feature. This chapter adds two deliberate layers on a real device: a full walkthrough as a genuinely new user would do it, and a real accessibility check. The aim is a short list of issues found on purpose, fixed with Book 1's reproduce, inspect, hypothesise, fix, verify loop.

2

Walk the edges, including airplane mode

The easy path rarely breaks. Bugs hide in long names, repeated toggling, being offline, and deleting the last item. One reader found his Add Habit button did nothing in airplane mode: it had been wired to check for a connection the offline-first app never needed. Reproduce his bug below, then fix it.

3

Read the logs Expo prints

The development server prints logs you can read in the terminal. As in Book 1, most of a log is context and one line usually points at the cause. Paste the steps, the relevant log lines, and what you expected when asking Claude for a hypothesis. Which line matters here?

4

Hear the app the way a screen reader user does

Turn on VoiceOver (iOS) or TalkBack (Android) and move through the Habits list and Add Habit form using only its cues. Reading about accessibility and experiencing it are different things. A control announced only as "button" is a specific, fixable problem. Step through the screen below, then add labels and hear the difference. Check touch-target size and text contrast in the same pass.

5

Choose the app's permanent identity

An app has a display name people see and a unique identifier the stores use behind the scenes, usually in reverse-domain form such as com.yourname.habittrail. The identifier effectively can't change after your first submission: changing it means starting over as a new listing. Choose it deliberately now.

6

Icon, splash, screenshots and honest listing copy

Both stores need an icon at several sizes, a splash screen shown while the app loads, screenshots, and listing copy. Take screenshots on your own phone of the real app, nothing staged. Write the copy from your Chapter 3.1 brief, describing what the app actually does. Set an initial version such as 1.0.0 and increase it with every update you submit.

Check current requirementsIcon sizes, screenshot dimensions, listing fields and store policies are set by Apple and Google, differ between them, and change periodically. The book deliberately doesn't print a fixed list; check each store's current developer documentation before finalising assets.

7

Does the privacy page match the app?

Both stores require a privacy policy and a support contact. HabitTrail already has both: the Privacy and Support pages you published in Book 2. But they must describe the app as it is now. A reader noticed, only while writing his listing, that his privacy page never mentioned the notification permission he'd since added. Compare.
