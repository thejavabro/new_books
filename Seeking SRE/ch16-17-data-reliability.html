Database Reliability Engineering

1

From DBA silo to database reliability engineer

Traditional DBAs built silos and snowflakes: different tools, hardware and languages from everyone else. The database tier has the least tolerance for risk, which makes it the biggest opportunity for reliability culture. Campbell's guiding principles reduce the cognitive load of daily decisions and, added up, form a culture.

2

A recovery strategy, not a backup strategy

Backups are a means; recovery within your SLO parameters is the end. "Is the database backed up?" should be answered "yes, in multiple ways, depending on the scenario." Pick a scenario and see which storage tier and tool serve it.

Replication is not a backup. Neither is RAID.Replication is blind: it faithfully copies user errors, application bugs and corruption to every replica. RAID protects against a disk, not against a bad DELETE. Both are tools for availability and data movement, not recovery artifacts.
3

From gatekeeper to enabler

The old DBA reviewed every migration, object and query and hand-shepherded changes into production. That gatekeeper becomes a bottleneck and burns out. The DBRE instead educates developers, publishes living architecture and data-model knowledge, gives them tools (benchmarks, consistency checkers, templates), pairs with them, and builds safe migration pipelines.

How many nines does replication buy?

  
Most companies survive downtime; few survive losing a big fraction of user data. Replication is table stakes, and a simple Markov model estimates what it buys. Each of n disks fails at rate λ = 1/MTTF; each failed disk is re-replicated at rate μ = 1/MTTR; data is lost if more than m disks in a group fail. The loss rate works out to

  
R(loss) ≈ n! / (m! (n−m−1)!) · λm+1 / μm

Only an upper boundTwenty-four nines is an MTTF longer than the age of the universe. These numbers model routine disk failure, which is easy to protect against. What actually loses data are the things you didn't see coming: a truck into the data center, an intern let loose on production, a bug that writes garbage everywhere.

The operator wasn't to blame: if a simple mistake can take down production, the process failed. Dropbox added access controls against rebooting live database hosts, changed the tool's syntax to resist typos, rejected commands spanning multiple isolation domains, and above all automated the job so nobody runs such scripts by hand. "Don't hate the player, hate the game."






  
6
You will mess up: detect it

  
Is your storage system correct, 100%? Most aren't: dangling references from an old bug, rows on the wrong shard, a background trickle of 404s everyone has learned to ignore. Dropbox aims for the power of zero: no unexplained errors, so any non-zero is a real signal. Building the verifiers took more effort than building the storage system. 7
Automation shrinks the window of vulnerability

  
MTTR defines the window in which a second (and third) failure turns into data loss. A RAID array waits days for someone to drive in and swap a disk; a distributed system re-replicates automatically in hours. Automation also fights operator fatigue (Cowling has seen people pipe yes into a tool that asked hundreds of confirmation questions) and is simply more reliable than a person at a keyboard.
