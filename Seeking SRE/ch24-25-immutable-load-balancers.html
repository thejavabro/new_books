Chapter 24

Immutable Infrastructure and SRE

Jonah Horowitz (Stripe): never change a running server; replace it with a freshly built one.
1

Patch in place or replace?

In mutable infrastructure, long-lived servers are updated in place by hand or by configuration management. Over months, each machine accumulates a slightly different history (a hotfix here, a failed package install there) until no two are alike and nobody can say what state a server is really in. Immutable infrastructure starts every server from a base image, bakes each release into a new image, and never patches running instances: to change anything, you deploy new instances and destroy the old ones.

2

What immutability buys an SRE team

At Netflix, as the chapter recounts, baking images (tools like Aminator; today Packer is common) cut the time to bring a new service into production from days to about an hour, and later to minutes.

3

The release-engineering pipeline

Commit→CI build + tests→Bake image (base + app + config)→Canary instances→Red/black: new group takes traffic→Old group kept briefly, then destroyed
Where it hurtsStateful data stores are the hard case: you can't throw away a database node's disk every release. Teams keep data on separate volumes, or (as with Cassandra) roll replacements through a cluster one node at a time, letting replication stream data to each new node. Image builds also add minutes to every change, and you need good tooling to debug instances you never log into.
Chapter 25

Scriptable Load Balancers

Emil Stolarsky (Shopify): putting code in the load-balancer tier (Lua in NGINX/OpenResty) lets SREs solve problems at the edge.
4

What a programmable edge can do

Load balancers sit in front of everything, see every request, and are run by the infrastructure team, which makes them a powerful place for logic that would be painful to add to every application. Click a use for the gist.

5

Pausing requests for a zero-downtime move

Moving a shop's data between database shards normally needs a maintenance window. With scriptable LBs, the edge can hold incoming requests for a few seconds while the cut-over happens, then release them to the new location: users see a slow request instead of an error.

6

Flash-sale checkout queue with a feedback controller

During flash sales, Shopify throttles checkout at the edge: excess users wait in a queue page and are admitted at a rate the backends can sustain. Each load balancer runs its own throttle without coordinating with the others, and a PID-style controller adjusts the admit rate from backend health. Users carry a signed timestamp cookie, so the earliest arrivals are admitted first and state lives in the client, not in a shared store.

The catch: SLA inversionEvery service now depends on the shared LB tier. Its reliability must exceed the best SLO of anything behind it, so edge scripts need the same rigor (tests, staged rollout, kill switches) as any critical service.
