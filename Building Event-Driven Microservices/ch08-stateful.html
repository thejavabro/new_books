Partitions, assignments and copartitioning

Every event-driven service does three things: react to an event, process it, produce results. Doing that with state across many instances means deciding which instance owns which partitions. In Kafka the first client in a group acts as leader and assigns partitions; in Pulsar the broker does it. Work pauses briefly during a rebalance so no partition is processed twice, and any state built for a moved partition must move too.

Repartitioning (new key, partition count or partitioner) and copartitioning (matching another stream's count and partitioner) make joins possible. Repartitioning can reorder events, and it doesn't raise throughput beyond the input stream's. Below, a service reads stream A (4 partitions) and joins copartitioned streams B and C (3 partitions each). Partitions with the same number from B and C must stay together.

Internal or external state store?

The book's example: a packaging service that materializes Orders and Inventory to decide what can ship now. Where should that state live?

Events in a partition are processed one at a time, in order, so each state lookup's latency caps throughput for that thread. Feel the cost of the network.

3

Changelogs: state backed by a stream

Internal stores are volatile. A changelog stream records every change to the store (the stream side of stream-table duality), usually compacted, and readable only by its own application. A new instance restores by loading the changelog, with no business logic triggered, instead of reprocessing all input. Kafka Streams provides this built in; basic clients don't.

Global (broadcast) stateA global store materializes all partitions of a stream on every instance, rather than just assigned ones. Use it for small, popular, rarely changing lookup data, like letting every packaging instance check inventory before bothering warehouse staff. It typically serves lookups, not event-driven logic.
4

Hot replicas for zero-downtime failover

Normally a failed instance's partitions move elsewhere and wait while state reloads from the changelog. A hot replica keeps a standby copy of each partition's state on another instance (a single setting in Kafka Streams), so failover is near-instant. The cost: extra disk and upkeep.

5

External state: recovery and rebuilding

Recovering from a snapshot is common for external stores. The catch is lining up consumer offsets with the snapshot. Drag the offset you resume from.

New requirements, like international shipping needing a customer's country, change the store's model. Don't migrate data; rebuild.

Never share state directlyA shared database platform is fine; a shared data set is not. Every service materializes its own copy. And each team manages its own external stores, helped by a list of approved services with guides for scaling, backup and restore, rather than handing them to a separate team.
6

Effectively-once processing

An inventory accounting service adds and subtracts stock events and orders more when stock gets low. Every event must count exactly once in the state. Crash it right after it has updated state and produced, but before committing its offsets, and compare the guarantees.

Effectively once means each event's effect on state and output is applied once. The logic may still run twice, so external side effects (emails, third-party calls) can still repeat. That's why "exactly once" is a misnomer.

7

Deduplication without broker transactions

Duplicates appear when a producer retries after a lost acknowledgement (idempotent production filters these) or crashes before committing offsets and redoes work (new offsets and timestamps make them look new). Without broker help, give each event a dedupe ID built from high-cardinality fields (account, amount and time for a transfer; an order ID) and keep a bounded store of recent IDs per partition.
