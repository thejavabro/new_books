Schemas and Data Contracts

Events are an API. Schemas say what an event contains, data contracts say what it means and who stands behind it, and a registry keeps both honest as they change.

1

Serialize, send, deserialize

A schema explicitly declares a data structure: names, types, defaults and limits. To publish, a producer serializes an in-memory object into bytes following the schema; the consumer uses the schema to deserialize the bytes back into its own objects. If a value doesn't fit, serialization fails, which is exactly what you want. Try to publish a bad Person.

Waiting…

Try a height of "six feet", a fractional id, or the country "Canada" instead of a three-letter code. Note what a schema can't catch: 66 typed as inches still passes as an integer.

2

Without a schema, every consumer guesses

Leave out the schema and interpretation falls to each consumer, in their own language and database. Important data has many consumers, so misreadings multiply and results stop matching.

Evolving a schema without breaking anyone

  
Schemas change as the business does. Compatibility modes let a converter translate events between versions so consumers don't write if version == 2 code. Two rules drive everything: a reader can fill a missing field only if the reader's schema gives it a default, and defaults apply at read time, only when the field is absent. Build version 2 and see which guarantees survive.

Start at full-transitiveEvery version convertible to and from every other version is the strongest guarantee: consumers change code only when the business changes, never because a schema broke. You can loosen the level later; tightening it again is extremely hard. Note that Protobuf v3 dropped custom defaults, which makes evolution trickier; Protobuf Editions lets you choose these behaviours.






  
5
A data contract: the promise about a stream

  
A service contract describes a service. A data contract describes the guarantees of the data in a stream: the compact between its producer and every consumer, past, present and future. Tap each clause.

  

  
Not every stream needs one. A stream used only inside a tightly coupled, single-team workflow can skip it.






  
6
Negotiating a breaking change

  
Breaking changes usually come from shifting domain boundaries. In the book's example a User's single address string must become separate home and work address objects. There's no clean way to convert old events, because nobody knows whether an old address was home or work. Borrow the API playbook: run old and new side by side, deprecate, then remove.

  






  
7
The schema registry

  
Shipping the full schema inside every event wastes network, storage and consumer effort. A registry stores schemas once and the event carries a short ID instead (Confluent's registry uses a 5-byte prefix). The producer registers or looks up the schema, swaps it for the ID and produces; the consumer reads, looks up the ID, then deserializes.

  

    

    

    

  

  






  
8
Field-level encryption

  
Encrypt only the sensitive fields, and give decryption keys only to consumers that need them. One stream can then serve both the settlement service and the analytics team, instead of a separate stream per security level. Format-preserving encryption keeps the same characters and length, so even an existing schema still describes the data.

  

    

    

  

  
Data catalogsA catalog goes beyond the registry: one place to browse, search and publish data sets with owners, evolution rules, sample data and tags such as PII. They used to cover only data at rest; most now cover event streams too (examples named include AWS Glue, Azure Data Catalog, Google Dataplex, Apache Atlas, OpenMetadata and DataHub).
