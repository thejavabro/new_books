Integrating Event-Driven Architectures with Existing Systems

Your existing databases hold the data everyone needs. Data liberation gets it into event streams reliably, without the dual-write trap.

1

What is data liberation?

Existing systems, often monolithic databases, hold data many other domains need: products, prices, stock, payments. Data liberation means identifying those cross-domain data sets and publishing them to event streams, which become the new single source of truth. Point-to-point dependencies show you what to liberate first.

2

The dual-write antipattern

The tempting shortcut: write to your database, then write to the event stream. The two are independent, so there's no single transaction around them. Retries help with blips but not with an invalid schema, a moved service or a long outage. Eventually you give up, and the two copies have diverged for good. Two-phase commit could help, but many databases and brokers don't support it (Kafka's support was still in progress at publication).

3

Three ways to liberate data

All three must capture the entire data set and keep up with inserts, updates and deletes. All should produce in timestamp order, putting the source record's last-updated time in the event header so the stream reflects when things happened, not when they were published. Frameworks like Kafka Connect, Debezium and Apache NiFi provide ready-made connectors for each.

Change-data capture and the snapshot problem

Databases write every change to a durable log first (MySQL's binlog, PostgreSQL's write-ahead log) so they can recover from crashes. CDC tails that log and turns each change into an event. Debezium is the de facto leader. It checkpoints its log position, so delivery is at-least-once, which is harmless for entity data because upserts are idempotent.

But the log only holds a short window, so you first need a snapshot of everything. A classic snapshot locks the table for hours. Netflix's DBLog approach, adopted by Debezium, interleaves chunked table selects with live log events using watermarks, without locks. Step through the merge.

CDC strengthsTracks deletes (as tombstones), minimal impact on log-based stores, low latency, and non-blocking snapshots.
CDC weaknessesExposes the internal model; produces normalized streams that consumers must join (Chapter 7); valid table changes can break the event schema.
5

Polling: what the query never sees

Query-based liberation runs a bulk load, then repeatedly selects rows changed since the last high-water mark (an updated_at timestamp or incrementing ID). Kafka Connect's JDBC connector offers incrementing, timestamp, and timestamp+incrementing modes. Now poll a busy row.

6

The transactional outbox

Inside the same database transaction, update your internal tables and insert the public version of the data into an outbox table. A connector later reads the outbox, publishes, and deletes what it sent. The database's own atomicity replaces the impossible dual write.

-- sketch: one transaction, two inserts
BEGIN;
UPDATE item SET price = 1299.99, cost_basis = 811.20 WHERE id = 4291;
INSERT INTO item_outbox (id, name, price)      -- public fields only
  SELECT id, name, price FROM item WHERE id = 4291;
COMMIT;
7

Triggers, and changing tables under capture

Older databases can capture changes with AFTER triggers that write to an audit table. They're widely supported and fine for small, stable legacy tables, but the author advises avoiding them where possible: they run inline (cost), scale linearly with tables, are easily forgotten when tables change, and usually validate schemas only after the fact.

Whatever the mechanism, you are bridging two independent schemas, usually across a team boundary. Columns get added, renamed and retyped. Protect the stream:

Watch pull requestsSubscribe to changes touching the captured data stores.
Integration testsCompare the stream's schema with the table's during development.
Deployment gatesBlock deploys that fail schema validation unless explicitly overridden.

The outbox's big advantage here: its code lives in the application repo, so breaking changes fail compilation and tests before production.

8

Stream first, or keep the legacy store?

The ideal: the application writes to the stream first, then materializes its own state from it, so it shares one source of truth with every consumer and recovers by replaying. The compromise: keep the legacy store and liberate one way, so the stream is eventually consistent with it.

9

Sinking events, and the cultural trap

Sinking is the reverse: a connector or small service consumes streams and writes into a data store for systems that can't read streams, replacing point-to-point links between legacy systems or landing data in S3, Azure Blob or Google Cloud Storage and table formats like Iceberg and Delta Lake for batch analytics.

A central connector platform gets you started fast, but watch two traps: a cross-team dependency (the source team's schema changes break connectors that another team runs), and complacency (teams never move beyond connectors). CDC is a bootstrap, not the destination. Where is a team on the spectrum?
