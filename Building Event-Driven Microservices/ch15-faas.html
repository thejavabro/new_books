Microservices Using Functions as a Service

Functions spin up when there is work and vanish when there is not. They fit event-driven work well once you understand triggers, offsets and their limits.

1

Why functions as a service?

A function is code that starts when a trigger fires, runs to completion and stops. The framework handles compute, scaling and monitoring. A useful way to think of it is a basic consumer/producer that reliably crashes every few minutes but keeps its data in an external store, so it can pick up where it left off. The appeal is serverless: write the code, say when it runs, deploy.

Functions suit simple and stateless topologies, very wide queue-style work and spiky volumes. Once determinism across several streams matters, you need event scheduling, just as with a plain producer/consumer.

The four parts of a function-based service

Every setup needs the function, its input stream(s), triggering logic and policies and metadata. The framework usually keeps the wiring in a hidden function-trigger map like this one:

Each function-based microservice gets its own consumer group, just like any other service. The function receives a batch of events (key, value, timestamp, offset, partition) and a context object (its name, stream, remaining lifetime).

Cold starts, warm starts and shutdown

A cold start loads code and opens connections to the broker and stores. A warm start revives a hibernating instance whose connections are still open. Instances run for a limited lifespan, typically 5–10 minutes, then hibernate, and may later be evicted. Drive one:

Clean up on exit?A suspended consumer can keep its partitions until a timeout, which stalls those partitions. If the function is almost always busy, it will be back in moments, so keeping connections open is fine. If it runs only now and then, close connections and give up its partitions. When in doubt, clean up.
4

Choosing a provider

The big cloud providers dominate FaaS because teams already use their other services, integrations are deep, and the legal questions about running code and storing data are already settled. Open-source options exist (OpenWhisk and OpenFaaS are still available; Kubeless is archived) but haven't displaced them. A welcome change: cloud functions can now trigger straight from open-source brokers like Kafka. Before, you had to use the provider's own broker, with its retention cap, or run a connector in between.

Maximum retention of provider-specific brokers when the book was written, in days. An open-source broker log can be kept indefinitely.

What starts a function

Batch size vs. batch window

Listener triggers wait to collect a batch so the start-up cost is shared across many events. Each batch is dispatched when it fills up or when the window runs out, whichever comes first. The input here is 20 events per second.

Synchronous triggering waits for each invocation to finish before sending the next batch, which keeps order (parallelism is capped by the partition count). Asynchronous triggering fans out freely and loses order.

Scaling without thrashing, and where state lives

When functions manage their own broker connections, every instance that joins or leaves forces a consumer-group rebalance. Short-lived functions, small batches and a twitchy scaling policy can trap the group in endless rebalancing. Compare policies on the same bursty lag:

State is externalProviders want to run any function on any node, so local state from an earlier run is never guaranteed. Read and write state explicitly in an external store, and lock it down to your bounded context.
Durable functionsSome frameworks (for example Azure Durable Functions) persist local variables for you, so a function can be suspended and revived without hand-written save and load code.

Functions calling functions

Functions can talk through events (each one consumes, works and produces, committing its own offsets; failures just mean reprocessing), or by direct calls, either fire-and-forget (choreography) or wait-for-the-result (orchestration). Order of B's completions:

def orchestrate(batch, ctx):
    for e in batch:                 # strictly one event at a time
        a = call("A", e)               # wait
        b = call("B", e, a)            # wait
        produce("out", combine(a, b))
    ctx.success()                       # offsets committed only now

When functions fail

The safety net is the stream itself: you can always reprocess from the last committed offset. Because retries repeat side effects, make processing idempotent. Common failures:

Batch halving

Some listener triggers halve the batch after each timeout until it fits. Here one event takes 0.5 s and the lifespan is 60 s.

Functions that consume for themselves can also commit offsets partway through a batch. Functions handed a batch can't.

Durable function orchestration

If a plain orchestrator function crashes, the results its workers returned are lost, and rerunning the batch repeats every call and side effect. Durable function orchestrators (cloud products such as AWS Step Functions, Google Cloud Workflows and Azure Durable Functions) record each step in a durable log and resume after the last one that completed. Step through a stock-trade workflow that fails twice:

Workflow as a documentSteps, choices and loops are written in a JSON or YAML state language, separate from the function code. Clear separation, but verbose and harder to read.
Workflow as codeThe orchestrator is ordinary code that calls activities and awaits their results. You use the same tools and editor as for the functions, at the price of framework-specific notation.

In practice, few organizations change cloud just for this, so you'll likely use the one your provider offers.
