Lightweight Framework Microservices

Lightweight frameworks give you stream processing as a library inside an ordinary app, leaning on the event broker for repartitioning and state durability.

1

No cluster of its own

A lightweight framework offers much of what a heavyweight one does: declarative topologies, materialized tables, primary- and foreign-key joins, grouping, windowing and aggregation. The difference is that it needs no separate processing cluster. It is a library inside your app, and it leans on the event broker (for shuffles, state durability and offsets) and the CMS (for instances). Compare who does each job:

Kafka Streams is effectively the one lightweight framework still in wide use, because it ships inside the Apache Kafka project. Others such as Apache Samza and Python's Faust have faded. Building a durable, scalable framework is hard, and keeping enough contributors when off-the-shelf options exist is harder.

2

Example: enrich products with brand data

Connectors stream the product and brand tables out of a shop database. Each product holds a brandId foreign key. The service materializes both streams as tables and joins them, so every product is published with its brand name and logo. Change data and watch what gets emitted.

brand table (from brand-topic)

enriched-product-topic (newest first)

// sketch of a table-to-table foreign-key join
products = builder.table("product-topic")
brands   = builder.table("brand-topic")
products.join(brands, p -> p.brandId,
              (p, b) -> enriched(p, b.name, b.logo))
        .toStream().to("enriched-product-topic")

Serdes (serializer/deserializers) turn broker bytes into typed objects and back. Note that a single brand change fans out to every product that refers to it.

3

Shuffling through internal event streams

Key-based work (joins, groupByKey, aggregations) needs all events for a key on one instance. A lightweight framework repartitions by writing events to an internal stream on the broker, keyed the new way, and reading it back. Each repartition stage gets its own internal stream.

Private by designInternal streams belong to one application. Never let another service consume them, or you couple the two services to an implementation detail.
4

State lives locally, and the broker backs it up

The default state store is a local in-memory or on-disk key-value store, matching the key/value API. Every write also goes to a changelog stream on the broker. On a restore:

Operator state<partition, offset> for input and internal streams, kept by the consumer group.
Key state<key, value> pairs, kept in each store's changelog.

Because each app is independent, one can ask for fast local SSDs and another for huge, slow disks. You can also plug in your own store (for example a cloud key-value database) by implementing the framework's store interface.

5

Scaling and failure are the same move

Adding an instance (to scale or to replace a failed one) and removing one (deliberately or by crash) both mean reassigning partitions and the state that goes with them. No restart is required, but there may be a pause. Choose a mode and add an instance.

Hot replicas are standby copies materialized from the changelog. When an instance dies, ownership can move to a replica and processing continues without a rebuild. They cost extra disk and CPU. Warming a new instance before it takes ownership was still under development for Kafka Streams when the book was written.
