Fundamentals of Events and Event Streams

An event is a recorded fact; an event stream is an ordered, durable, replayable log of them. Everything else in the book is built on these two ideas.

1

An event is a recorded business fact

An event is anything that happened that matters to the business: an invoice received, a meeting room booked, a coffee ordered, a hire made. Like an application log, it records what happened. Unlike a log, it is also the single source of truth, so it must hold everything needed to describe what happened. Events are immutable: once published, you can't edit one. If something was wrong, you publish a new event with the correction.

An event stream is a durable, append-only log

Producers append records to the tail; consumers start wherever they like (often the head) and read at their own pace. A stream is a timestamped sequence of facts about one domain, and it is:

immutablepartitionedindexed by offsetordered within a partitiondurable and replayablestorable indefinitely

Three partitions. Instance 0 reads partition 0; instance 1 reads partitions 1 and 2. A freshly added consumer has to catch up through all history.

The stream lives on an event broker such as Apache Kafka, the de facto standard, which calls a stream a topic and handles replication, rebalancing, client connections and access control.

5
Keys give data locality

  
The producer hashes the key to pick a partition, so all events with the same key land in the same partition. That guarantee, data locality, lets consumers split work by partition: anything you compute per key needs to read only one partition. Type a licence plate and watch where it goes.

  

    

    
Partitions:

    

    

  

  

    
RepartitioningA service reads a stream and rewrites it with a different key, partitioner or partition count, for example to key camera events by plate. It is what makes joins and grouping possible across mismatched streams, and it can introduce out-of-order data.

    
CopartitioningTwo streams are copartitioned when they share key, partitioner and partition count. Then partition n of each holds the same keys, so one instance can join or aggregate them locally. Required for primary-key joins, aggregations and reduces.

  






  
6
Turning streams into state

  
An aggregation combines many events into one result, such as total fines per plate. A materialization projects an entity stream into a table by upserting each event in order, so the table holds the latest value per key. The reverse also works: publish every table change and you have a stream. This is stream-table duality, and it is how services share state without calling each other.

7
Kappa: the stream is the whole story

  
In kappa (Jay Kreps, 2014), the event stream is the only record of both history and the present. A consumer reads from the start and catches up. It became practical once brokers stopped forcing short retention and cloud storage got cheap. The cost is hydration time for big streams, softened by snapshots and backups that frameworks such as Kafka Streams, Flink and Spark provide.

  
Lambda keeps history in a separate store and only recent data in the stream. The book includes it for history, not as a recommendation. Try a failure in the middle of a dual write.

8
The broker, and how to choose one

  
Enterprise brokers run as a cluster for scalability (add nodes), durability (replicate data), high availability (clients fail over) and high performance (hundreds of thousands of reads and writes per second). Schemas (Chapter 4) give producers and consumers a shared definition, like an API contract. When choosing a broker, weigh these. Tick what your candidate offers.
