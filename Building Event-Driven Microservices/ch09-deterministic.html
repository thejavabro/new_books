Deterministic Stream Processing

Run the same events through the same code and you should get the same answer, whether live or replaying a year of history. Time is what makes that hard.

1

Same input, same output, live or replayed

A service is either processing in near real time or catching up on history (new or under-scaled services). Rewind its offsets to the beginning and run it again: does it produce the same output? That's deterministic processing. It matters because bugs, errors and new business logic all force reprocessing.

Perfect determinism needs no latency, no failures and no network blips, so in practice it's best effort, built from consistent timestamps, good keys, partition assignment, event scheduling and a plan for late events. Some logic is deliberately nondeterministic: anything using the wall clock, or calling an external service whose answer depends on when you ask.

2

Four kinds of time

An offset says where an event is in one partition; a timestamp says when it happened relative to events everywhere else. Tap each point on the timeline.

Two machines can never share exactly the same clock. NTP gets close: a few milliseconds of drift after 15 minutes on a LAN (sub-millisecond with frequent syncs), but around ±100 ms across the open internet. Cloud providers offer satellite- and atomic-clock-backed time. Good enough for most business needs; minor disorder still happens.

3

Event scheduling: which event next?

The bank keeps deposits and withdrawals in two copartitioned streams and charges an overdraft fee when a balance drops below $0. Offsets order events only within a partition, so across streams the consumer must choose. Compare a naive round-robin consumer with the common scheduler: always dispatch the event with the oldest timestamp across all assigned partitions.

Stream-processing frameworks schedule this way; basic consumers usually don't. Custom schedulers (Samza's MessageChooser, for example) are possible but easily nondeterministic. Prefer event time from the producer; fall back to broker ingestion time if producer clocks can't be trusted. A timestamp extractor on the consumer reads it from the key, value or metadata.

4

Watermarks carry event time through a topology

Spark, Flink, Samza and Beam inject special watermark events at the source. Watermark(t) tells each downstream node: everything at time t or earlier has been processed. A node with several inputs takes the minimum of its inputs' times. Events older than a node's watermark are considered late. Step through.

Heavyweight frameworks shuffle data between nodes over their own cluster network, not through the broker.

5

Stream time (the Kafka Streams way)

Stream time is the highest event timestamp a processing node has seen. The consumer buffers events from its partitions, schedules the oldest, processes it all the way through the (sub)topology, and bumps stream time if it's higher. Anything below stream time is out of order. Kafka Streams holds window results open for a grace period so late data still counts. Repartition topics split a topology into subtopologies, each with its own stream time.

6

How events end up out of order

An event is out of order if its timestamp is lower than one ahead of it in the stream. Within one partition you still process by offset. Batch jobs over bounded data barely notice disorder, at the price of a day's latency. Unbounded streams force a business choice between latency and determinism. Causes:

"Late" is in the eye of the consumerWith watermarks, t′ is late if it arrives after W(t) where t′ < t. With stream time, it's late if stream time already passed t′. One service may call any out-of-order event late; another may wait hours.
7

Windows, and what to do with late events

Windowing groups events by time. Pick a window type, then send a late event into an already-closed window and pick a strategy.

Decide with the business first: How likely are late events? How long must you guard? What does dropping them cost, and what does waiting gain? How much state does waiting need? A financial transaction must count however late; a stale temperature reading can be dropped.

8

Reprocessing, and the outage that hides

Reprocessing (rewinding offsets) works for services that use event time, not wall-clock windows. Tick off the five steps for a safe replay.

One subtle trap: a producer loses its broker connection while events keep happening. The consumer sees stream B go quiet, keeps advancing time from stream A, and when B's events finally arrive in correct time order, they're late in real time but perfectly on time during a later replay. Live and replayed results differ.
