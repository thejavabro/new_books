Heavyweight Framework Microservices

Heavyweight frameworks run your processing on a dedicated cluster with built-in state, checkpoints and windowing, at the price of operating that cluster.

1

What makes a framework heavyweight

Streaming frameworks give you joins (on primary and foreign keys), aggregations, windows and time-based operations over data sets far larger than one machine can handle. This chapter covers the heavyweight kind, using Apache Spark, Apache Flink and the Apache Beam model as examples. Three traits earn them the name. Tap each card.

A fourth trait: they can also run batch jobs, because that's where they came from.

2006Hadoop bundles parallel processing, recovery and durable storage on cheap commodity hardware.
MapReduce eraThe dominant way to process huge batches. Data grows from gigabytes to petabytes.
SparkStarts as a faster replacement for MapReduce in batch work. Streaming arrives later.
FlinkBuilt for streams from the start. Many teams first try streaming by converting batch jobs.
2

Example: session windows of clicks and ad views

An ad reseller bills customers per session: a run of user activity with no gap longer than 30 minutes, measured in event time. Two streams feed in, AdView (ad shown for a product) and Click (user clicked that product). Within each session, an ad view followed by a click on the same product is an engagement. Move the gap slider and watch the sessions split or merge.

A sketch of the job in a chained, MapReduce-style API (illustrative, not any framework's exact signatures):

clicks.union(views)
  .keyBy(e -> e.userId)                       // forces a shuffle
  .window(SessionWindows.gap(30 min))       // event time, not wall clock
  .process(matchViewsToClicks)            // emits userId -> [adId, ...]
  .sinkTo("AdEngagements");

4

Inside a heavyweight cluster

A cluster has two roles. Resource managers schedule and track work, with standbys ready to take over. Workers (executors) run the tasks, which are generated from your job's topology and connect straight to the event broker. A coordination service such as ZooKeeper decides which resource manager leads. Newer setups may use something else, but some form of distributed consensus is always there. Break things and watch the recovery.

"Job" is batch-era vocabulary. A streaming job is simply an application that runs forever, like any other microservice.

5

Benefits and limitations

Where they shineETL into new stores; session and window analysis; spotting abnormal behaviour; stream aggregation with state; any stateless transform. Mature, widely used and well documented.
Where they pinch(1) They weren't designed for microservice-style deployment and need a dedicated cluster. (2) Language support is mostly Java, Scala and Python. (3) Not all of them can materialize an entity stream into an indefinitely retained table out of the box, which rules out table joins and long-running aggregations.
The acid testAsk how a framework handles joins, both between streams and between materialized tables. If it can't do them, it probably hasn't solved the hard problems yet. The leading frameworks offer a "global window" that keeps a table indefinitely.
6

Cluster setup and application submission

Who runs the cluster, and how do applications get onto it?

Driver modeA small local driver coordinates the app, while the work runs on cluster resources. Kill the driver and the app stops, so you can deploy the driver with the CMS like any other microservice.
Cluster modeThe whole app is handed to the cluster, which returns a unique ID. Every later command (stop, inspect) goes through the cluster's API, which may not suit your normal deployment pipeline.
7

State and checkpoints

Heavyweight frameworks prefer internal state: kept in memory, spilled to local disk. A checkpoint is a snapshot of that state written to durable storage outside the workers (HDFS once; now usually cloud object storage). It must record two things atomically together: the operator state (partition → offset) and the key state (key → aggregate). Try it: process events, checkpoint, process more, then crash.

If the offsets and the key state didn't match, a restore would either skip events or count them twice. A task can't process new data until its state is fully loaded.

8

Scaling: by restart, or while running

Parallelism is capped by the input partition count. User-driven load is usually cyclical, high by day and low at night, so scaling saves real money. Stateless apps just join or leave the consumer group. Stateful apps must move state and keep it matched to partitions, and shuffles make that harder: remove an instance in mid-shuffle and its downstream readers lose their source.

Other routes exist too: Spark's shuffle tracking and shuffle-block decommissioning, and Flink's adaptive scheduler. Autoscaling wires a metric (latency, consumer lag, CPU, memory) to one of these mechanisms. Some engines include it; with others you build it yourself.

9

Failures and multitenancy

A failed worker's tasks move to another worker and reload their state from the latest checkpoint. A failed resource manager shouldn't disturb running apps, though you may be unable to deploy until a standby leads. Monitor both. The bigger everyday risk is a shared cluster: a new app replaying from the start of its topics can grab most of the free resources and push its neighbours past their SLOs.

10

Choosing, and checking yourself

Choosing is like choosing a CMS or a broker: how much operational overhead (monitoring, scaling, debugging, cost allocation) will your organization fund? Managed offerings are fewer than for brokers. Popularity matters too: Flink has grown strongly, Spark Structured Streaming is widely used, and Beam is mostly used to run on Google's Dataflow. And make sure a heavyweight framework actually fits the problem.
