Integrating Event-Driven and Request-Response Microservices

The outside world speaks request-response. This chapter shows how to turn requests into events, serve state back out, and build user interfaces on event-driven back ends.

Where request-response still belongs

Event streams can't do everything. You'll still need request-response (one service calling another's API, synchronously or with a callback) to collect metrics from phones and IoT devices, talk to third-party services, serve web and mobile users in real time, and answer requests that depend on live context such as location or weather. This chapter covers turning requests into events, calling third-party APIs, serving state, and micro frontends.

Turning requests into events

Option one is a dedicated endpoint: clients send data to a backend you own, which writes events. It gives high throughput and load isolation. Where does serialization happen?

Option two is a shared REST proxy: an HTTP API to the broker for listing, creating, producing to and consuming from streams. Send records with a schema and the proxy checks it against the registry, refusing anything incompatible. Try it:

Consuming through a proxy takes several calls: create a durable consumer, subscribe, fetch, commit offsets, delete the consumer. Proxies aren't fast. Moderate loads may need several instances, so consider native clients for heavy traffic.

Calling third-party APIs from an event-driven service

A service can call an outside API for each event and wait for the answer. If it reads a stream, that wait is head-of-line blocking: nothing else moves until the call returns or times out. Consume as a queue if order doesn't matter. Wrapping the output and the offset commit in one transaction keeps them atomic. Serving data over request-response

From internal, sharded state

With internal state spread over instances, a request for a key must reach the instance that holds it. Two facts make that findable: a key maps to exactly one partition, and a partition belongs to exactly one consumer instance. Hashing the key gives the partition, and the consumer group's assignments give the owner. With a round-robin load balancer, the first try hits the right instance only 1 in N times.

A smart load balancer is best effort. Rebalances create races, so every instance must still be able to forward a request. It also ties the balancer to your topology and store names, so deploy and test it with the service.

From an external store

Every instance can read all the state, rebalances don't rebuild anything, and request capacity scales separately from storage. Clients must still go through the service's API, never straight to its database.

5

Handle the request now, or as an event?

Event first gives you a durable audit and replay record, and lets the service hold the reply until it has processed every earlier-timestamped event. The cost is latency and complexity, so the UI must be asynchronous: confirm the request was sent, discourage repeat clicks (think "booking, please wait"), and decide when results are worth pushing. Ask how much harm a stale view could do, and how expensive an update is. Network retries can cause duplicates, so stay idempotent.

6

Example: approving a newspaper layout

Designers lay out articles and ads in a GUI. The editor must approve, and then the major advertisers check their ad placement (a toy maker may refuse a spot beside a story about a missing child). Either can reject. Step through the event-driven version, then the later split into separate editor and advertiser services.

The designer's clicks aren't events. That service can be an ordinary request-response app that only produces the final candidate (use an outbox or CDC so the stream stays in step with its database). Large PDFs live in a file store, and events carry their URI.

Micro frontends

A micro frontend is a microservice that owns one business concern all the way up to the UI. Compare how teams and code are organized:

Example. Version 1 of an experiences app had one service for search and reviews, backed by a simple key-value store. Version 2 splits out reviews, moves search onto a store that supports text and geolocation search (and uses the user-profile stream for personalization), and adds a product frontend that stitches them together without holding their business logic. Reviews were always written to a stream first, so nothing needed migrating: the new services replayed the same streams.
