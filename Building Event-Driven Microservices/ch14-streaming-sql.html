A query that never ends: streaming SQL lets you filter, join and aggregate event streams declaratively, and the results update as new events arrive.

A query that never finishes

Streaming SQL lets you say what you want and leaves the how to an engine underneath. Flink SQL and Spark SQL sit on top of their frameworks' lower-level APIs. There is no standard yet: each engine speaks its own dialect, though the dialects are close. The key difference from a database query is time. A database query reads what exists and ends. A streaming query runs forever and handles every new event as it arrives.

SELECT * FROM readings WHERE value > 5

2

First, declare a table over the stream

SQL works on tables, so the first step is to declare a table over a stream. Engines offer up to three kinds. Feed the same events into each and compare. Your engine should support at least upsert and append-only tables; append-only alone is very limiting.

3

Example: enrich photos with photographer names

Two upsert tables are declared over the Photographs and Photographers topics, a third over the output topic, and an INSERT INTO … SELECT … JOIN keeps the output filled. The key is marked not enforced because this job doesn't own the data; the producer does. Table metadata goes into a catalog (Hive or a Hive-compatible one in production) so other jobs can find the tables. A schema registry can supply the Avro schema for decoding.

CREATE TABLE photos (
  id BIGINT, shooter_id BIGINT, url STRING,
  PRIMARY KEY (id) NOT ENFORCED
) WITH ('connector'='upsert-kafka', 'topic'='photos', ...);

INSERT INTO photos_enriched
SELECT p.id, p.url, s.first_name, s.last_name
FROM photos p JOIN shooters s ON p.shooter_id = s.id;

Both inputs stay in the job's state indefinitely, mirroring the source topics' key space.
