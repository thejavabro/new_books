Building Workflows with Microservices

Business processes span many services. You can let services react to each other (choreography) or put one in charge (orchestration), and you need a plan for when a step fails.

1

Workflows across services

A workflow is the set of actions, branches and compensations that make up a business process. It usually spans several microservices. Three questions decide how to build one: how do you change it without breaking work in progress, how do you monitor it (finished? stuck? healthy?), and how do you make several actions happen together or not at all?

2

Choreography and orchestration

In choreography, like dancers who each know their part, services react to events independently; producers don't know their consumers. In orchestration, like a conductor, one service holds the workflow logic, sends commands and awaits results. Now the business wants C's step to happen before B's.

3

Monitoring a choreographed workflow

Define the workflow, define success (order paid and fulfilled? car assembled?), then build a monitor that materializes the relevant streams into its own store, plus health checks on the services. For a 100-step workflow, watch just the 5 or 6 most critical steps. Expect break-fix work, since independently owned services change.

4

Inside an orchestrator

The orchestrator materializes every command it sent and every response it got. It knows exactly where each input event is. It says what to do (bill this order), never how: if payment needs three attempts, that's the payment service's business. Avoid the "God service" commanding weak minions.

// orchestrator loop, sketched
for (e : consumer.poll(input, aResp, bResp, cResp)) {
  switch (e.source) {
    case input -> { state.start(e);  send("A-command", e); }
    case aResp -> { state.record(e); send("B-command", e); }
    case bResp -> { state.record(e); send("C-command", e); }
    case cResp -> { state.finish(e); send("output", state.result(e)); }
  }
}
consumer.commit();
Event-driven orchestrationSame lag-based scaling and tooling as other services; others can read its streams; the broker isolates each side from the other's failures; retries are built in, since nothing moves until a response exists. Queues suit the workers well.
Request-response orchestrationLower latency, and the only way to reach SaaS and legacy APIs with no events. Needs request-response plumbing (routing, failover). Mixing both is common.
5

Distributed transactions: the saga

A saga spans several independent data stores: each service commits its part and knows how to reverse it, idempotently. The book warns: avoid them unless truly necessary. Choose where to fail.

    Orchestrated sagas can also abort on timeouts or a human "cancel" through a REST API. The worst case, a step that can neither complete nor roll back, should halt processing and be handled as an incident. Each service, not the orchestrator, is responsible for being consistent after its own rollback.

    6

    Compensate forward instead of undoing

    The warehouse can't find an item the system says is in stock: misplaced, stolen, miscounted, or a race with another order. The customer has paid and received a confirmation. What now?

    Strict saga rollbackRefund, cancel the order, fix stock, notify the customer.Technically correct, but what about the rest of their order? Cancel everything? Partial refund?
    Compensation workflowDecide the desirable outcome from the current bad state, and build a path to it.Reorder stock, tell the customer about the delay with a discount code, let them choose to wait or cancel. Humans can be part of the workflow.

    Any system mapping the digital world onto the physical one will meet mismatches, sometimes discovered weeks later, when undoing is impossible anyway.

    7

    Durable execution engines

    A durable execution engine (Cadence, Temporal, Restate and Resonate are named) records each step, its parameters, return values and promises in an append-only log, essentially event sourcing for your code. After a crash the code is replayed, completed steps are skipped, and execution resumes. Crash this workflow midway.
