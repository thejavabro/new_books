Handling Bad Data in Event Streams

Bad events are forever in an immutable log, so prevention beats cure. When prevention fails, good event design decides how painful the fix is.

Three strategiesEight typesPreventionEvent designLast resortQuiz
1

Bad data meets an immutable log

Bad data is anything that doesn't match expectations: an email with no @, an expiry date in the wrong order, or plain garbage. In a database you'd just fix the row. An event stream is an immutable log (apart from expiry and compaction), so you need strategies, in this order of preference:

1. Prevention: schemas, validation and tests. Fail fast and gracefully. Cheapest by far.
2. Event design: state events let you overwrite mistakes.
3. Rewind, rebuild, retry: last resort.

The recurring cause: producers writing without a strict schema, quality rules or tests.

3

Prevention: schemas, quality rules, tests

Types 1–5: use a real schema format (Avro, Protobuf or JSON Schema) with a registry, and validate evolution in CI/CD. Plain JSON enforces no types, required fields, defaults or evolution rules, and tribal knowledge isn't a contract. Type 6: schemas check types, not meaning, so add producer unit tests and data quality rules that run at serialization time. Types 7 and 8: unit and integration tests for serializers, rules and business logic. An idempotent producer fences out retry duplicates, but not logically distinct duplicates.

// a write-time rule attached to the schema (illustrative)
rule "taxIdLength": on write require len(msg.taxId) == 9 && digitsOnly(msg.taxId)

Careful with dead-letter queuesA DLQ just postpones the problem: someone still has to repair and resend the data. It works when events are independent and order doesn't matter. Otherwise consumers see a stream that looks error-free but is incomplete. Keep DLQs as a last-ditch measure.
4

Event design decides how fixable you are

A bad price reached the stream, and a consumer keeps a running inventory value. Fix it with each event model:

State: fix once, at the sourcePublish the corrected record. Every consumer picks it up and compaction eventually removes the bad one. With CDC you just fix the source row. Downstream services re-emit their corrected state in turn. Consumers must still undo any decisions they already made from the bad value.
Deltas: build forwardThey can't be compacted, and each depends on the one before. You must write undo or compensating deltas that land every consumer exactly back on the right state, never past it. There's one correct state and endless wrong ones, and some are terminal (a shipped parcel can't be unshipped). This is realistic only when one team owns both producer and consumer. Deltas also give you no way to purge personal data for GDPR erasure requests.

For partners who drop XML files on FTP, a triggered function can convert each file into keyed state events. Push partners toward a basic schema, even if you have to give them tooling.
