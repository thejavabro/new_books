Agentic Runtime Architecture

The runtime is the engine that keeps an agent working until a goal is met: durable state, governed tools, memory, coordination and the frameworks that provide them.

1

What runtime means for agents

Every application you have built follows the same shape: a request arrives, code runs, a response leaves. An agent instead keeps working until a goal is finished, across many steps, tools, waits and people. The runtime is the engine that makes that safe. Its reference loop:

Design the kernel from identity, not capabilityDo not start with which tools the agent can call. Start with what it is: its role, its authority, what it must never do. The agent kernel then manages runs, steps, state and policy around that identity.
2

Runs, steps, checkpoints and continuations

Execution semantics are the runtime's rules of motion. A run is one attempt at a goal; it is made of steps, each checkpointed. When a process crashes or waits days for a human, the run resumes from its last checkpoint without redoing completed work. Without idempotency, a retried step after a lost reply can send a second email, file a second claim or make a second payment. Drive the run.

3

Concurrency: parallelize what is safe

Real work does not arrive in a tidy line. Start with parallel tool calls, but be disciplined: parallel is usually safe for read-only and independent operations; writes that touch the same record need ordering. In an auto claim you can fetch coverage, prior claims, a repair estimate and a fraud check at the same time.

4

Memory and prompt assembly

The model is rarely the limit; the context is. Before each step the runtime assembles the agent's entire world view for that moment. Memory is separated by purpose, like a claims adjuster's working notes, case file, reference library and policy checklist. Pick what goes into an 8,000-token window and watch what gets squeezed.

Temporal truth

Knowledge changes: coverage can change between opening and settling a claim; guidance gets superseded. Retrieval must respect effective dates. Choose the claim's loss date.

5

Tools, actions and actuation control

Reasoning happens inside; impact begins when the agent calls an API. The tool execution layer makes every call safe, authorized, idempotent and well-reported. Actuation control sits between the agent's decision and the enterprise system and sorts actions into three tiers. Sort the claims actions.

Secrets stay outside the agentCredentials live in the tool layer or a vault and are injected per call. The model never sees them, so no malicious document and no long run can leak them.
6

Transactions in agents: sagas and compensation

Microservices gave you rollback or compensation. Agents need the same guarantees across multi-step work: a saga pairs every step with a compensating action. Choose where it fails.

7

Multi-agent architecture

Enterprise problems are rarely one straight line, so split the work by expertise (a fraud agent does not price) and by independence (tasks that need not wait for each other run in parallel). Then pick a topology.

A delegation contract

delegate:
  to:        fraud-screening-agent
  goal:      "Assess fraud indicators for claim CLM-2093"
  inputs:    [claim_summary, photos_ref, prior_claims]
  done_when: "score 0–1 with top 3 reasons and evidence refs"
  deadline:  90s
  escalate:  "score > 0.8 or evidence missing → SIU queue"
  on_fail:   "return partial + reason; never guess"

Agents and microservices on one claim

The chapter's worked example: a customer is rear-ended and submits a first notice of loss (FNOL) in the insurer's app. One tap for the customer; a coordinated run behind it, with tools as the bridge between agents and microservices.
