1

Why agents need a new development mindset

Conventional software is deterministic: engineers write the rules, workflows and exception paths. The early generative wave was prompting: a person asks, the model answers. Agents go further: they pursue goals across steps, tools and systems, so their behaviour must be designed, bounded and verified rather than just coded. Compare what "done" means.

2

From idea to agent design: the BOUND principle

Development begins before models or frameworks: frame the problem, use DDD to find real agentic use cases (Chapter 6), then define goals, boundaries and success criteria. The chapter's mnemonic is BOUND. Fill it in for a sample agent and the spec builds itself.

Reliable workflows: start constrained

The author's advice: do not start with maximum autonomy. Open-ended agents impress in demos and disappoint in production. Pick a constrained pattern.

Resilience: retries with exponential backoff and jitter

max 4 attempts, then fallback or escalate
Validate every critical outputCheck outputs against an explicit schema or typed contract before anything downstream uses them. Externalize state so the workflow never relies on the context window to remember what already happened. Never let an agent run raw queries against core databases: go through governed APIs and tools.
5

Low-code, pro-code and building an MCP server

Low-code tools (n8n, Flowise, Dify and similar) are fast and accessible for experiments. Pro-code frameworks (LangGraph, Semantic Kernel, the OpenAI Agents SDK, CrewAI and others) give control, testing and composition. Most enterprises use both. Here is how a tool travels: the server advertises it, the agent decides to call it, the server validates, enforces policy and executes. A minimal illustrative server:

// illustrative MCP-style tool server (not production code)
server.tool("get_claim_status",
  { claim_id: z.string().regex(/^CLM-\d+$/) },     // typed input schema
  async ({ claim_id }, ctx) => {
    await policy.check(ctx.user, "claims:read", claim_id); // authorize on behalf of the user
    const c = await claimsApi.get(claim_id);               // governed API, not raw SQL
    audit.log({ tool: "get_claim_status", claim_id, user: ctx.user });
    return { status: c.status, updated: c.updatedAt };     // minimal, structured result
  });

Security from the start: no unrestricted file or database access, authenticated remote transport, scoped permissions, and logging on every call. Servers can also expose prompt templates for common workflows.

6

CI/CD for agentic systems

An agent can change without a line of code changing: a prompt edit shifts tool selection, a memory schema drifts, a policy bundle update silently alters approvals. So the pipeline gates behaviour, not just builds. Toggle which gates exist and push a risky change through.

Approvals and segregation of dutiesThe person who changes a policy bundle or a high-risk prompt should not be the one who approves its release. Infrastructure is code too, deployed through the same pipeline.
7

Deployment is a business capability rollout

Deploying code makes it available. Deploying an agent releases decision-making behaviour into a business process, including the point where it must stop and hand control back to a human. Deployments rarely fail because the model stops working; they fail in context, integration or governance. Click each failure.

8

Scaling without letting cost run away

Adding workers without controlling how often they call the model makes cost grow faster than value. Give every agent an explicit token budget, per request, hour or day.

Illustrative blended price of 5 per million tokens; change the shape, not the exact figure.

9

Version everything that shapes behaviour

The principle: everything that shapes agent behaviour is versioned: agents, prompts, tools, workflows and policies. Semantic versioning tells consumers what a change means. Classify each change.

Patch, minor or major?

10

Rings, canaries, flags and kill switches

The safest pattern for enterprise agents is a ring rollout: internal users, pilot group, limited availability, then general availability. Promotion depends on operational signals, not the calendar. Feature flags control behaviour inside a runtime; blue/green and canary handle runtime and MCP-server changes. Simulate a release.
