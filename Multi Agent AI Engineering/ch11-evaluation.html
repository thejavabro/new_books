Evaluating the Performance and Behaviors of Multi-Agent Systems

If you cannot measure quality you have a demo, not a system. Evaluating agent teams means judging trajectories, coordination and cost, not just final answers.

1

Without measurement you have a demo

The chapter's opening line puts it bluntly: if you cannot measure quality, you have a demo, not a system. Normal software is built and then tested. With agents the order flips, because the behaviours you need (sound reasoning, faithful handoffs, recovery from errors) cannot be specified without being measured.

3

Which evals at which stage

Software has its development life cycle with unit, integration and acceptance tests in their places. The chapter draws an agent version (ADLC). Step through it.

The two life cycles match closely until production. There, classic software is checked against a spec the team wrote; an agent is checked against how a model it does not control actually behaves. That is why agent testing is never finished.

4

Every instrument has holes

No single check catches everything. The chapter borrows the Swiss Cheese Model from safety engineering: line up several imperfect layers and few failures get through all of them. Turn layers on and fire 200 failures at the stack. Each layer's catch rate here is made up for illustration.

The layers also feed each other. Production traces become new eval cases, user complaints become rubric lines, and human reviews keep the LLM judge honest.

5

Code, model, or human

Separate from when you grade is how. The three graders form a cost ladder: code checks are almost free, LLM judges cost per call, and human review is the scarcest resource. Use the cheapest grader that can honestly score each dimension.

6

Four places where reality diverges

Every agent runs a loop: interpret the task, reason about it, act, then perceive the result. Each named failure mode is a gap between what is true and what the agent believes at one of those steps. Classify the cases.

More agents do not create new kinds of failure. They multiply the places where each kind can happen, since every agent runs its own loop and every message is another chance to lose a constraint.

7

A good eval suite is SHARP

The chapter's six-step recipe builds one: define the task mix and coverage (edge and adversarial cases in separate panels, each scored on its own); write gold outputs or rubrics; make scenarios reproducible (fixed tools, seeds and even container resources); instrument everything; run enough trials; and analyse trajectories.

Read paths, but gate on outcomes. Trajectories are where you learn why something failed. Do not fail a run just because it took a different route. Do gate on path rules that are real requirements, such as "authorisation happens before every write".
8

Size the run to the decision

Models vary even at temperature 0. The chapter cites up to 15% accuracy swings across ten "deterministic" runs. So a single run proves nothing. To detect a regression of size δ when paired differences have spread σ (5% two-sided test, 80% power), you need about ((1.96 + 0.84) × σ / δ)² cases.

46 paired cases needed

Rare harms need a different approach. If you see zero harmful outputs in n independent trials, the 95% upper bound on the true rate is roughly 3/n (the "rule of three").

Two consistency numbers. pass@k is the chance at least one of k tries succeeds, which suits retry-until-green work. pass^k is the chance all k succeed, which suits an agent that runs once for real.

9

Humans and LLM judges apply the same rubric

A rubric names each quality dimension, its scale, and an anchor description for every level. Good multi-agent rubrics score the artifact (factual accuracy) and the process (coordination quality), with partial credit for multi-step work. Measure how consistently humans apply it (Cohen's or Fleiss' kappa) before you hand it to a model.

Then calibrate the judge one dimension at a time against held-out human labels, and set acceptance criteria in advance. Known judge biases include favouring the first option shown, preferring longer answers and preferring their own model family. Agents can also learn to talk a judge into a pass. A calibrated judge goes stale, so recheck it after every model upgrade or rubric change, and keep collecting cases where humans and the judge disagree.

10

Measuring how the team worked

Four coordination diagnostics are reported separately, never blended into one weighted score: redundancy ratio, workload concentration (a Gini coefficient over each agent's share), handoff retention (do the sender's constraints still govern what the receiver does?) and convergence speed for loops. Move the token shares to see the Gini change.

Whether a role earns its place is a counterfactual question, answered by ablation: remove or merge the role, hold everything else fixed, and compare. Cost works the same way. Report cost per successful outcome, because a pipeline that is a third cheaper per run but succeeds half as often costs more per result.

11

Five levels of evaluation maturity

Production evaluation records then feed development. Each live trace goes to one of two sides: measure (it becomes an eval case) or shape (it becomes a prompt example, memory entry or training pair). Never both. A trace that shaped the system can no longer test it fairly.

Recap

  • Evaluate five dimensions: correctness, coordination, resource efficiency, robustness, safety. Rank them per context, and write them down in a versioned spec.
  • Stack imperfect instruments (suite, benchmarks, observability, A/B tests, feedback, case studies, human review).
  • Failures come from interpretation, reasoning, action or perception. More agents multiply each.
  • A SHARP suite is sensitive, holistic, adaptive, representative and probabilistic. Size trials to the decision.
  • Calibrate LLM judges per dimension against humans, and recheck them often.
  • Report coordination diagnostics separately. Judge cost per successful outcome.
