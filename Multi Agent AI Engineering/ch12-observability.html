Observability for Agentic AI

Observability explains what each run actually did. For agents that means traces that follow decisions across agents, tools and models, with cost and quality attached.

1

You cannot fix what you cannot see

Institutions keep minutes, censuses and case law so they can see themselves. A multi-agent system needs the same: a record of who did what, why and at what cost. Chapter 11 judged whether behaviour is good enough. Observability supplies the evidence from production, and the two form one loop that later feeds self-evolution (Chapter 13).

Ordinary monitoring tools still apply, but agents change their assumptions along five axes. Pick one.

Agentic system

One thing does not change. Agents run on, and call into, ordinary systems, so their telemetry must join up with the telemetry of the queues, databases and services underneath.

2

OpenTelemetry is the common language

The chapter builds on OpenTelemetry (OTel). OTel is more than a library. It is a specification, SDKs, a wire protocol (OTLP), a Collector that receives and routes data, and semantic conventions for attribute names. It graduated at the CNCF in 2026, which is why the authors treat it as a long-term bet. (One author works at Splunk; the chapter says so.)

The model maps neatly: a workflow is a trace, each agent's work is a span, and model calls, tool calls and handoffs are child spans. Tap a span to see the kind of attributes the gen_ai.* conventions give it.

Tap a span.
# my sketch of wrapping one agent step in a span
with tracer.start_as_current_span("invoke_agent research_agent") as span:
    span.set_attribute("gen_ai.operation.name", "invoke_agent")
    span.set_attribute("gen_ai.agent.name", "research_agent")
    result = await agent.run(task)
    span.set_attribute("mas.handoff.bytes", len(result.payload))

Attribute names marked mas.* are the book's own extensions where the standard has nothing yet. Many frameworks emit OTel natively now, but coverage varies by version, so check exactly what yours exports.

3

Behaviour, performance, cost, quality

Telemetry costs storage, processing and attention, so collect what answers questions you will actually ask. The chapter sorts signals into four dimensions. Each has a different audience.

Judge on live traffic. Run the calibrated LLM judge from Chapter 11 on a sample of production runs, and track judge-human agreement as a service-level indicator. If agreement drops, every quality number is suspect.
4

Keep the runs you will need

Head sampling decides at the start of a run, before anything interesting has happened. Tail sampling waits until the run ends, so it can keep every error and slow or expensive run. Try 10,000 runs with 2% failures.

5

Price every call, attribute every token

Price each model call from its usage record and a versioned rate card, then reconcile the total against the provider's bill. Count tokens you could not price as a separate metric, so a missing price never shows up as a free call. Try it with an example rate of $3 per million input and $15 per million output tokens.

Then ask what the money bought. The chapter splits spend by purpose (task work, coordination, verification and so on, one purpose per call) and by composition inside each call (system prompt, history, tool results, output), and adds a rework flag for work that was thrown away. Keep the axes separate or you will double-count.

Beneath the agents, the model gateway sees two things agents cannot: rate-limit headroom and failover. When a fallback fires, a different model answers the same request, so record both the requested model and the model that actually responded.

6

Privacy is decided where data is emitted

Traces of agents are full of user text, retrieved documents and reasoning. The default the chapter recommends: record structure (operation, version, status, timing, tokens) always, and store sensitive payloads only for a declared purpose in a short-lived encrypted vault, with telemetry carrying a reference. Redaction happens in layers: application code first, then the Collector before data fans out to any backend. Run the pipeline.

Hiding data only at display time is a UI feature, not privacy. Each redaction stage should emit evidence that it ran (rule, count, policy version), never a hash of the value. That evidence shows the rule ran, not that every secret was found. Multi-tenant stores need a tenant ID that comes from somewhere the agent cannot write.

8

Classify first, then attribute

The chapter's six categories tell you which spans to open first. Classification is not attribution: knowing it was a coordination failure still leaves "which agent, which step?", which is harder and mostly done by a human with tool help. Sort these.

9

Layered dashboards, alerts on symptoms

Four dashboard layers move from overview to detail: system health (success rate, latency, cost rate), agent performance (per-agent latency, errors, tokens, tool success), workflow analysis (latency by phase, coordination overhead, retry rates) and anomaly detection (deviation from a 7-day baseline).

Page on symptoms users feel, not on causes. Use burn rate: how fast you are spending the error budget. With a 99% success SLO, a 3% failure rate burns the budget at 3×. Requiring a fast and a slow window to agree avoids paging on blips.

Recap

  • Instrument from day one. A trace per workflow, a span per agent step, child spans for model calls, tools and handoffs.
  • Use OpenTelemetry and its gen_ai.* conventions; add your own names only where the standard is silent.
  • Observe four dimensions (behaviour, performance, cost, quality) and tail-sample so failures are kept.
  • Price every call, count unpriced tokens, and record which model actually answered.
  • Capture structure by default, put payloads in a vault, and redact before the backend.
  • Classify failures into six types, then attribute. Alert on symptoms with multi-window burn rates.
