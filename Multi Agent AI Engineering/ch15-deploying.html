Deploying and Scaling Multi-Agent Systems

A system that only runs on your laptop is a prototype. Production adds queues, rate limits, cost budgets, canaries and rollback, and every one of them shapes the agents.

1

Mostly ordinary work, with a few sharp differences

Most of deploying a multi-agent system is ordinary distributed-systems engineering. The value of this chapter is in the handful of places where standard defaults break. Pick one.

Usual default

Multi-agent workflow

Readiness is a set of properties, not an infrastructure stage. A container or a Kubernetes cluster supplies some of them. What the system does (recoverable work, external effects, shared quotas, shared tenants, regulated data) decides which controls it needs. Local, serverless, containers, Kubernetes and hybrid setups each fit a stage. Run your own models only when data residency, measured economics or a custom model require it, and compute the break-even on your real workload.

2

Scale on the queue, not the CPU

Workers that call hosted models spend most of their time waiting. CPU stays low while the queue grows. Scale on queue age and depth, in-flight model calls and rate-limit headroom, with explicit caps. Adding workers past the provider's quota only turns waiting into 429 errors.

Hand the work to a durable queue with worker pools. Long runs need durable execution underneath (checkpoints and leases) so a crashed worker's job resumes elsewhere. Keep state outside the workers, and coordinate the provider's rate limit across the whole fleet, not per pod.

Cancellation has three parts. When a user closes the tab or sends a correction: future steps stop at a safe boundary; committed effects (a sent email, a merged PR) do not un-happen and need a compensating action or an explicit decision to keep them; and effects whose outcome is unknown are held until they are reconciled.
3

Why token cost grows faster than you expect

A multi-agent run uses roughly an order of magnitude more tokens than a chat, because each sub-agent carries its own context. Within one agent, re-reading a growing history makes input tokens grow roughly with the square of the number of steps. And an autonomous loop has no human slowing it down. Play with it. The price is an illustrative mid-tier rate of $3 in and $15 out per million tokens.

Prompt caching is the biggest single lever. Agents resend the same system prompt, tool definitions and examples on every call. Major providers bill cached input at a discount of about 90%, and it also cuts time to first token. Keep the stable part of the prompt first and identical.

Level 1 · agent engineer

Route each call to the cheapest model that meets its quality bar. Use slower, cheaper service tiers for batch and evaluation work.

Level 2 · workflow owner

Budgets per task with a circuit breaker that stops or degrades a run before it overspends.

Level 3 · platform / finance

Fleet and tenant budgets, attribution per customer, and reconciliation with the bill.

On build versus buy, the chapter's default is to buy first. Managed agent platforms handle deployment, scaling, queue durability and much of the rest. The self-built stack in the chapter is a teaching scaffold that shows the mechanics. It is not a recommended day-one investment for a team without a platform group.

4

Fingerprint every release

An agent system has much more release state than a code commit: code, prompts, an exact model snapshot, tool and schema versions, the retrieval index, the memory schema, policy settings, pricing settings, runtime settings and the eval-set version. Hash them into one fingerprint and attach it to every span. Then "what changed?" has an answer.

# my sketch
manifest = {"code": "a41f9", "prompts": "p-2026-11-02", "model": "provider/model@snapshot",
            "index": "idx-0412", "policy": "v7", "pricing": "rc-14", "evals": "suite-v9"}
fingerprint = sha256(json.dumps(manifest, sort_keys=True)).hexdigest()[:12]
span.set_attribute("release.fingerprint", fingerprint)   # keep the manifest too

Canary on more than errors. The dangerous new versions are correct but twice as expensive, or faster but worse. Neither moves the error rate. Compare the canary with the baseline.

Catch runaways early. Alert on token burn rate before the daily cap trips, and watch trace shape: many near-identical tool or model spans under one agent are the signature of a loop.

5

Rollback is a state transition, not a command

Rolling back a workflow system touches compute, queues, caches, effects, memory and schemas. Step through what each needs.

Then break it on purpose in staging: kill a worker that holds a lease, deploy mid-run, make the client disappear, fail a call after the side effect commits. No unit test reaches these seams.

6

Promise only what you can measure

Two kinds of indicator behave very differently. Counted ones (availability, latency, completion without error, cost per successful task) arrive with every run, for free, and can page someone. Judged ones (task quality) arrive hours later from a sampled judge or a human, and are only as good as that judge's agreement with people. A promise like "99% of tasks succeed" that does not say which kind it is cannot be checked.

Recap

  • Name the deltas first: long stateful runs, fan-out, quota-bound scaling and economic failures.
  • Scale on queue and quota signals with caps. Use durable execution and externalised state.
  • Token cost compounds. Cache stable prefixes, route to the cheapest adequate model, and budget at three levels.
  • Buy a managed runtime first unless you have a platform team.
  • Fingerprint the whole release; canary on cost and quality as well as errors.
  • Plan rollback across queues, caches, effects and memory. Make SLOs say whether they are counted or judged.
