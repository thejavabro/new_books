Choosing a framework is an architecture decision

Chapter 3 gave a way to look at frameworks: four categories and a five-layer stack. This chapter uses that lens on nine real frameworks plus Microsoft's Azure stack, as they stood in the authors' late-2026 snapshot. The chapter is honest that the snapshot will age, and it notes that one author founded AG2. The lasting value is in the questions, not the scorecard.

The core warning: moving from one framework to another usually means rewriting the agent definitions, the orchestration logic, the memory layer and the observability hooks. A migration can eat most of a quarter. So the choice deserves the care you would give a database.

Six dimensions run through every comparison: agent model, orchestration, tools and MCP, memory and state, production readiness and model dependence. The chapter adds exit cost on top as a seventh thing to weigh.

2

Two axes place every framework

Two questions separate the field. First, is the workflow shape emergent (agents talk until they finish) or prescribed (you draw the steps)? Second, who owns orchestration: does your application compose the calls, or does the framework run the loop for you? Tap a dot. 8

A five-step selection process

1. Classify the orchestration need. Conversational, pipeline, role-based, handoff, or a mix.
2. Check the ecosystem. Cloud, model provider and existing tools rule out more than features do.
3. List production must-haves. Checkpointing, tracing, guardrails, permissions.
4. Look at the team. What they can read, debug and keep running at 3 a.m.
5. Plan for evolution. Where will this be in 12 to 18 months, and what does leaving cost?

A good habit for step 5: keep your own domain logic (prompts, tool code, schemas, evaluation sets) in plain modules, and let the framework only wire them together. Then a migration rewrites the wiring, not the product.

9

Mixing frameworks, carefully

Large systems often use more than one framework. The chapter's examples: an AG2 conversational front end that hands settled requests to a LangGraph back end for the auditable part, or Strands using swarm mode to explore and graph mode to execute. The rule is to join frameworks at service boundaries (a protocol such as A2A or MCP, a queue, an API), never by calling one framework's internals from inside another's loop.

10

Five ways teams choose badly

The chapter's longer view: frameworks are converging. MCP for tools and A2A for agents are becoming common ground, and graph-style execution is showing up nearly everywhere. Framework syntax will change, but the ideas from Part 2 (orchestration models, collaboration patterns, memory designs) carry across.

Recap

  • Select by context: workflow shape, ecosystem, production needs, team and exit cost. There is no overall winner.
  • Emergent versus prescribed workflow, and app-owned versus framework-owned orchestration, place most frameworks.
  • Hard constraints (cloud, checkpointing, guardrails, multimodal) shrink the list faster than feature tours do.
  • Compose frameworks at service boundaries, and keep domain logic outside any framework.
  • Demos, star counts and today's problem are poor guides. Price the migration before you commit.
