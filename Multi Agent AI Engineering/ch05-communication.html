Failures start where work changes hands

Inside one process, two agents share a machine, a clock and a call stack, so a lot never has to be said. Across a boundary, all of it does. A human lead splits "how big is the humanoid-robot market?" into three briefs for three readers and checks back two hours later. Reveal what came back.

Analyst reports"Pull the latest market-size forecasts"
Industry press"Sweep last quarter's funding news"
Makers' filings"Aggregate what makers disclose"

In one failure taxonomy of multi-agent runs (MAST), about a third of observed failures were inter-agent misalignment, and the biggest members were handoff failures.

A handoff is a contract, not a packet

Every meaningful transfer of work (one after which the sender depends on someone else) should state seven things. Untick an element and see what the receiver is left to guess, quickly and confidently.

Fields don't enforce themselvesA permissions list is a request, not a grant. The receiving runtime authenticates the sender, checks the deadline against its own clock, and intersects requested permissions with the grants it actually holds.
3

The envelope: identity and lineage

Keep the contract (what's asked, on what terms) apart from the envelope (what delivery needs to route, deduplicate, expire and stitch messages back together). Three IDs do different jobs; click a message to trace its lineage.

@dataclass(frozen=True)          # an illustrative envelope
class Envelope:
    message_id: str          # unique; doubles as the idempotency key
    conversation_id: str     # groups one user request
    causation_id: str | None # the message this answers; None only for a new task
    message_type: str        # task | ack | result | status | control
    schema_version: str      # reject unknown shapes before parsing
    expires_at: float        # an instant, not a duration
    trace: dict              # telemetry context, NOT the conversation id
    payload: dict            # the contract lives here

How much structure a message needs

Format runs from free text to a fully typed schema. The rule isn't system size: structure should rise with boundary risk. Tick what's true for your boundary.

5

Direct, topic and broadcast

Direct addressing names the receiver: lowest latency, but the sender must know the roster. Topic addressing lets the set of interested agents change at runtime. Broadcast is just a topic everyone subscribes to, which makes its cost visible: every subscriber pays to read every message.

Bounded inboxes turn overload into backpressure

A slow consumer drains one message every 1.5 s.

6

Synchronous or asynchronous?

Synchronous chains are linear and easy to debug, but one slow agent stalls everything and latency compounds. Asynchronous flows (fire-and-forget with callback, fan-out/fan-in, event pipelines) gain the most when subtasks are independent. Make one reader slow.

Acknowledgment is not completionAn ack says "received, understood, accepted". Completion carries the result. Treat an ack as done and you report success on work that hasn't started; wait only for completion and you can't tell a thinking receiver from a deaf one.
7

The lifecycle of a communicated task

Once ack and completion are separate, a task has states both sides agree on. Only one terminal state carries a result. Click the terminal states: the sender's right response differs for each.

8

Deadlines that survive the trip

A deadline written as a duration resets at every hop; that's how a 60-second run spends four minutes. An absolute instant doesn't reset. Inside a process use a monotonic clock; across processes send a UTC instant on the envelope.

With a deadline, two honest behaviors follow: at the deadline, synthesize from partial results and record the gap; when a late answer arrives, don't silently splice it into a result that already shipped.

9

Duplicates, idempotency and staleness

At-least-once delivery is normal, so the same message will arrive twice: a retry after a timeout that actually succeeded, a redelivery after a crash. The stable message_id doubles as an idempotency key. Try retrying a paid lookup.

Staleness is the mirror problemA verdict can be perfectly valid and still judge a claim that was revised meanwhile. Carry the artifact version out in the provenance, carry it back in the result, and refuse a result whose version no longer matches.
10

What this layer owns, and what it doesn't

Message historyThe ordered record of what was said, by conversation_id. Owned by the communication layer as an audit trail.
Task stateProgress of the work itself. The orchestrator decides retries, breakers and persistence (chapter 8).
KnowledgeWhat agents remember beyond the exchange. Memory's job (chapter 7).

Nothing here depends on a transport. The same contract and envelope ride an in-process queue, HTTP, a broker or a standard protocol (chapter 9). A tiny protocol can be enough if it's explicit: the book's example of a personal two-bot fleet coordinates through one shared chat channel with a few rules: act only on structured mentions, acknowledge before overlapping work, and keep ack separate from completion.

Contract tests that run without a model

  • Malformed message is rejected at the door.
  • Expired message is not worked on.
  • Duplicate returns the recorded result and the work ran exactly once.
  • Stale verdict (wrong claim version) is refused by the sender.
  • Unauthorized permission request is cut to the server-side grant.
