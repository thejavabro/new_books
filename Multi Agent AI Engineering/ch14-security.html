Security and Privacy for Multi-Agent Systems

An agent team's attack surface is its own autonomy. Security is an authority architecture built into the shape of the system, not a filter bolted on at the end.

1

Security is about authority, not filters

Agent security incidents rarely look like a clever prompt slipping past a filter. They look like an agent with too much authority doing something real: deleting data, sending mail, changing records. So the chapter treats security as an authority architecture: who or what may act, on whose behalf, with which permissions, and how that is checked at every boundary.

Threats rise through three tiers, named for the capability each one adds. Higher tiers re-stage lower-tier attacks in new places, so the old defences remain necessary even when they stop being enough. Tap a tier.

The OWASP Top 10 for agentic applications (goal hijack, tool misuse, identity and privilege abuse, unexpected code execution, insecure inter-agent communication, and more) works as a coverage map: each category points to the mitigations below.

2

Three attack stories, and where they break

An attacker needs only one permitted path to an effect. Pick a story, switch controls on, and see which step stops it.

Trust boundary vs authority boundary. A trust boundary marks which input is untrusted. An authority boundary marks who may act or change state. Filtering untrusted input never fully works; limiting authority bounds the damage when it fails.
3

The minimum viable baseline

Seven controls form the chapter's floor: capability-scoped tools, input and output validation, authentication between agents, memory provenance, an audit trail, human approval for irreversible actions, and sandboxed execution for untrusted content. If you only have a week, the chapter's order is:

1. Every tool call checks a capability token, issued to a short-lived, attested agent identity. No inherited long-lived credentials. This limits the blast radius of everything else.
2. Any path that ingests outside content (web, attachments, third-party MCP servers) runs in a sandboxed untrusted region behind a dual-LLM boundary. This closes the main route for indirect prompt injection.
3. Sign messages between agents, and have the memory store stamp provenance on every write, with reads filtered by authorisation.
4

Seven architectural mitigations

The chapter's "spine" is seven design-level controls, AM1 to AM7. Each has a runtime enforcement point (RG1 to RG3) or works alongside standalone filters (RG4 to RG7). Tap one.

Tap a mitigation.

A capability grant in my own simplified form. In production the issuer signs it or stores it server-side and hands out an opaque reference:

grant = {
  "grant_id": "g-7c1", "issued_to": "summarizer@run-42",
  "allow": ["docs.read"],            # no email, no memory.write
  "audience": "doc-tool", "expires": "+10m",
  "parent_grant_id": "g-19a"        # lineage, so revocation can cascade
}
# the mediator checks issuer, audience, expiry, replay, revocation, then the effect
5

Keep the planner away from untrusted text

Indirect prompt injection works because the same model that plans also reads attacker-controlled text. The dual-LLM pattern (Simon Willison, 2023; made rigorous by DeepMind's CaMeL in 2025) splits the roles. Toggle it.

Plan-then-Execute (AM4) is the same idea applied over time. Untrusted observations may not rewrite safety invariants, permissions or approval points. Steps may adapt at a typed checkpoint, but the new segment is re-authorised before effects resume.

6

Red-team continuously, triage by surface

Use attack harnesses (the chapter uses PyRIT for multi-turn attacks) and benchmarks as calibration, not as proof. Replay the public incident canon every quarter. Then route each finding to the right owner. Response time differs a lot by surface.

Containing a live compromise. The order matters: the first steps stop damage, and the later ones would overwrite evidence if done first.

The chapter also recounts an incident in which agents in an evaluation escaped their sandbox and coordinated through a package registry. Its lesson for builders: a group of agents can be the attacker, and any shared service can become their channel.

7

Privacy is about where information flows

The chapter adopts Helen Nissenbaum's contextual integrity: privacy holds when information flows match the norms of the context where it was shared. A symptom told to a doctor is fine in the clinic and a violation when it reaches an employer, with no access rule broken. Models are poor at this. Benchmarks the chapter cites found leaks in roughly a quarter to well over a third of cases, even when models were told to protect privacy. Try some flows.

Multi-agent structure makes it worse: each handoff moves information into a new context, and shared memory carries it across users. Design for minimisation, purpose-bound stores, per-tenant isolation and redaction at handoffs.

Recap

  • Three tiers: generation, effects, collaboration. Lower-tier defences remain necessary.
  • Separate trust boundaries (untrusted input) from authority boundaries (who may act).
  • First week: capability tokens on short-lived identities; sandbox plus dual-LLM for outside content; signed messages and memory provenance.
  • Seven mitigations (AM1 to AM7) form the spine; runtime guardrails (RG1 to RG7) enforce and supplement them.
  • Triage red-team findings into architectural, runtime and policy fixes. Contain compromises in a fixed order.
  • Privacy means appropriate flows, not just access control.
