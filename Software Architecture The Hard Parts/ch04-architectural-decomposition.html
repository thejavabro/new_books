Which way to break it apart?

The Sysops Squad has its funding. Now: how? Two common approaches exist. Component-based decomposition refines and extracts components step by step. Tactical forking clones the whole app and chips away what each team doesn't need, the way a sculptor removes marble. The choice hinges on how well structured the existing code is. Walk the decision tree.

2

Is the codebase decomposable at all?

Brian Foote named the Big Ball of Mud in 1999: a system with no discernible internal structure, for instance UI event handlers calling the database directly. Without governance, many systems drift this way. No single number says whether code is salvageable, but coupling metrics give an architect the macro picture. Click a component to measure it.

Afferent and efferentYourdon and Constantine (1979): afferent coupling counts incoming connections to an artifact, efferent counts outgoing ones. When a monolith comes apart, a shared class like Address with dozens of incoming references is exactly what you need to find first.
3

Abstractness, instability and the main sequence

Robert Martin derived two ratios that work in any object-oriented language. Abstractness A is abstract elements (interfaces, abstract classes) over all elements. Instability I is Ce / (Ce + Ca): near 1, the component breaks easily when its dependencies change. Near 0 it is either stable (mostly abstract) or rigid (mostly concrete), so read them together. The ideal line A + I = 1 is the main sequence; D = |A + I − 1| measures how far a component strays from it.

// the three derived metrics, written out
A = abstractTypes / (abstractTypes + concreteTypes)
I = Ce / (Ce + Ca)
D = |A + I - 1|          // 0 = on the main sequence, 1 = as far away as possible
Why it matters for a migrationMoving a building with a bad foundation is risky; so is moving code. If most components sit deep in the zone of pain or of uselessness, shoring up the structure enough to decompose it may not be worth the time. If most sit near the line, decomposition is feasible.
4

Component-based decomposition

In the authors' experience, most of the pain of moving to microservices comes from poorly defined components. A component has a clear role, a defined set of operations, and shows up as a namespace or directory. The leaf directory holds the source files; the path is the namespace. Tap a folder.

Build services from components, not classesThe six patterns in the next chapter refactor a monolith into well-defined components, which then become services.

Those patterns naturally lead to a service-based architecture: a handful of coarse-grained, separately deployed domain services over one shared database. It is a fine destination, or a stepping stone to microservices.

5

Tactical forking: delete instead of extract

Named by Fausto De La Torre for codebases that really are mud. Extracting a piece from tangled code means pulling on strands of coupling until half the monolith comes with it. Deleting what you don't need leaves the dependencies intact; the compiler and tests tell you what is safe to remove. Two teams want two services: one for the hexagon and square domains, one for the circle domain.

Benefits

  • Teams start almost immediately with little up-front analysis.
  • Deleting is easier than extracting in tangled code; compilation and simple tests verify it.

Shortcomings

  • Services keep lots of latent code left over from the monolith.
  • Code quality is no better than before; there is just less of it.
  • Shared code drifts and gets named inconsistently, so commonality is hard to spot.
6

Sysops Squad: choosing an approach

The architects plot the Sysops Squad components: most fall near the main sequence, a few outliers. It is decomposable. Austen fancies the sculptor's approach; Addison worries about duplicating shared logging, security and persistence code across services, when maintainability, testability and reliability are the very problems. Weigh it yourself.

ADR

Migration using the component-based decomposition approach

Decision

Components already have good boundaries; this avoids duplicated code in each service; service boundaries can emerge from component grouping instead of being fixed up front; and an incremental, controlled migration suits the reliability and availability problems.

Consequences

It will take longer than tactical forking. In return the whole team collaborates on shared functionality and domain boundaries, instead of splitting into separate fork teams that must coordinate.
