What Happens When There Are No "Best Practices"?

Most of an architect's hard problems have never been solved before by anyone, so there is nothing to look up. The job is to weigh trade-offs, write the decision down, and guard it automatically.

1

There is no best design, only the least worst

Developers can usually search their way to an answer: someone has configured the same tool before. Architects rarely get that luxury. Their problems are tangled up with one organization's systems, people and politics, so the exact situation has often never been met by anyone. The authors' tongue-in-cheek rule: stop hunting for the best design and look for the least worst combination of trade-offs.

"Best" would mean every competing characteristic is maximized at once. That never happens. Try it: three candidate designs, each strong at something. Change what the business cares about and watch the winner change.

No silver bullet, stillFred Brooks argued in 1986 that no single technique delivers a tenfold gain. The authors take the same line: the real skill is objectively weighing the trade-offs on each side of a consequential decision, then documenting the choice.
2

Hard means difficult, and hard means solid

The title does double duty. Hard as in difficult: decisions with long-term consequences, made amid people and politics, that no one has faced in quite this form. And hard as in hardware: the foundational, structural parts that change slowly while the "soft" design on top changes often. One cheeky definition of architecture is "the stuff that's hard to change later". That stuff is what the book covers.

Because the ecosystem keeps replacing itself, the book avoids tool recipes and focuses on how to decide. Step through how one capability unlocked the next and toppled a dominant style.

3

Data outlives the systems around it

Early distributed systems still kept all their data in one relational database, so data stayed out of the architecture conversation. Microservices and Domain-Driven Design's bounded context changed that: each service now hides its own data, so data and transactions became architectural concerns. Many of the hard parts in this book come from the tension between data and architecture.

The book distinguishes two kinds of data throughout. Sort these examples.

Operational or analytical?

Operational (OLTP)What the company runs on: sales, orders, inventory. Inserts, updates and deletes all day. If it stops, the business stops soon after.
AnalyticalWhat the company steers by: trends, predictions, business intelligence. Often not transactional, often not relational, and not needed minute to minute.
4

Write every decision down: the ADR

An Architectural Decision Record is a short text file, usually a page or two, that captures one decision. Michael Nygard popularized them; they live happily next to the code in Markdown or AsciiDoc. The book uses a lean three-part format and records a decision this way at the end of almost every Sysops Squad episode. Draft one and see it rendered.

Fitness functions: governance that runs on every build

Writing a decision down does not make developers follow it. Code reviews and review boards catch problems late and miss details. The DevOps lesson applies: automate the expensive manual check. An architecture fitness function is any mechanism that performs an objective integrity assessment of an architecture characteristic, or a combination of them.

A classic example: component cycles. IDEs offer to auto-import any class you mention, developers click yes by reflex, and soon every component depends on every other one, the road to a Big Ball of Mud. Draw dependencies below and let the fitness function judge.

Tap one component, then another, to add a dependency arrow. Tap an arrow to remove it.
// illustrative only: a build step that fails on any package cycle
test("no cycles between components", () => {
  const graph = analyzeImports("src/");   // package -> packages it imports
  expect(findCycles(graph)).toEqual([]);
});
test("only the service layer may touch persistence", () => {
  expect(importersOf("app.persistence", graph))
    .toBeSubsetOf(["app.service"]);
});

Real tools in this space include JDepend and ArchUnit for Java and NetArchTest for .NET; code hygiene tools such as SonarQube ship many checks ready-made.

6

Unit test or fitness function?

The scoping rule is a single question: does running this check need any domain knowledge? If yes, it is a unit, functional or acceptance test. If no, it is a fitness function. Elasticity checks don't care whether the site sells shoes or hosts a game; validating a mailing address does.

Which is it?

Objective, not necessarily staticSome fitness functions return pass/fail or a fixed threshold. Others are dynamic, for example allowing per-user response time to slip a little as concurrent users rise, but not fall off a cliff. Some are manual, like a lawyer reviewing changes to a legal module, and run as a manual stage in the pipeline.
7

A security slot in every pipeline

In 2017 a widely used Java web framework had a published vulnerability and a patch, yet a major credit agency took months to find and patch every affected system with manual scans, and suffered a huge breach. Imagine instead that every team's deployment pipeline gives the security team a slot for fitness functions. Play the scenario.

An executable checklistLike surgeons' and pilots' checklists, fitness functions protect things that are important but never urgent, the stuff that otherwise becomes "we'll fix it later". Don't overdo it, though: an ivory-tower web of rules that only frustrates teams is its own anti-pattern.

Simple, verging on simplistic, definitions

The book stays on the architecture side of the architecture and design line: why one option has better trade-offs before how to build it. It uses deliberately simple definitions. Open each card.

Meet the Sysops Squad

Every chapter grounds its ideas in one running story. Penultimate Electronics sells electronics with optional support plans; when something breaks, a Sysops Squad expert visits the customer. Four kinds of user rely on its ticketing system: administrators, customers, experts and managers. Step through the ticket lifecycle.

A bad scenarioThe ticketing system is an old monolith. Tickets get lost, the wrong expert shows up, the app freezes for minutes or hours at a time, and every change breaks something else. If nothing improves, the company will drop the support business and everyone on it, architects included.
