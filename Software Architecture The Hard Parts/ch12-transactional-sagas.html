Eight sagas from three switches

"Saga" first meant a way to keep long database transactions from holding locks forever. In microservices it usually means one thing: an orchestrator calls services in turn and, if a call fails, sends compensating updates to undo the earlier ones. That is only one of eight combinations of the three forces from Chapter 2. The authors gave each a playful name plus a code: s/a for sync or async, a/e for atomic or eventual, o/c for orchestrated or choreographed. Flip the switches.

3

Compensating updates, step by step

An Epic saga in Sysops Squad: an expert taps "complete" on a ticket. The orchestrator asks Ticket to mark it complete, which also queues analytics; then it asks Survey to email the customer. This time Survey is down.

Compensation gives

  • Everything restored to how it was
  • A chance to retry or restart the whole request

Compensation costs

  • No isolation: others acted on data that is now being undone
  • Undoing can have side effects of its own
  • The compensating update itself can fail
  • The user waits, then gets an error
4

Or: record the state and fix it later

Ask a blunt question: why should the expert care whether the survey went out? With state management and eventual consistency, the orchestrator does not undo the ticket. It records that the saga is in a "fixed, but no survey yet" state, tells the expert they are done, and keeps retrying the survey behind the scenes. This is how a Fairy Tale or Parallel saga would handle the same failure.

Gregor Hohpe's essay about coffee-shop ordering makes the same point: most of the real world runs on "carry on and reconcile later", not on everyone freezing until a value is agreed.

Making sagas visible in code

No framework hands you distributed transactions; you design and maintain them. One cheap help: mark each service's entry point with the sagas it takes part in, using a Java annotation, C# attribute or similar. The marker does nothing at runtime, but it is a searchable record. Here is my own minimal version:

public enum SagaId { OPEN_TICKET, CLOSE_TICKET, ENROL_CUSTOMER, CANCEL_PLAN }

@Retention(RUNTIME) @Target(TYPE)
public @interface TakesPartIn { SagaId[] value(); }

// on each service's entry class
@TakesPartIn({SagaId.OPEN_TICKET, SagaId.CLOSE_TICKET})
public class TicketApi { /* ... */ }

A small script can then walk the repository and answer "which services does this saga touch?", which is exactly the testing scope for a change. Try it:

Sysops Squad: rethinking ticket completion

Sysops SquadLogan walks the team through ticket completion as an Epic saga and lists what can go wrong: Analytics already used the "completed" data before it was rolled back, the rollback itself might fail, and the expert is stuck waiting for an error about a survey they do not care about. Austen asks whether this is not exactly what the old monolith did. It was, inside a single database transaction, which is precisely what the new architecture no longer has. Logan's suggestion: look at Fairy Tale or Parallel sagas, which use state management and eventual consistency, and only reach for atomic patterns if atomicity is truly required.
