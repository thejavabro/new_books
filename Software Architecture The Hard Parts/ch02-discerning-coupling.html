Discerning Coupling in Software Architecture

Before you can pull a system apart you need a way to see what holds it together. The architecture quantum and three dimensions of dynamic coupling give you that lens.

1

The dose makes the poison

Everyone says "decouple". Follow that to the end and nothing talks to anything, and you have no system. Coupling is like Paracelsus's poison: harmful or necessary depending on the dose. The book uses the plainest definition: two parts are coupled if a change in one might cause a change in the other.

Why did distributed systems get so much harder with microservices, when queues and events are decades old? Earlier distributed systems usually shared one relational database that handled integrity and transactions. Bounded contexts moved the database inside each service, and transactionality became an architecture problem. Problems now come braided together, so the method starts by separating the strands.

The running questionHow do architects decide the size and communication style of microservices? Too small and you drown in transactions and orchestration; too big and you hit scale and distribution problems. The rest of the book untangles this one question.
2

The architecture quantum

The authors borrow quantum (plural quanta, like datum and data) from its Latin root meaning "how much". An architecture quantum is an independently deployable artifact with high functional cohesion, high static coupling and synchronous dynamic coupling. A well-formed microservice in a workflow is the usual example. Open each part.

Why not just say "bounded context"?The two overlap: cohesion and independent deployment match a service built around a bounded context. But that term has a precise Domain-Driven Design meaning. The quantum adds what the architect needs: the kinds of coupling, and so the scope over which characteristics like scale or reliability apply.
3

Count the quanta

Static coupling is the wiring a thing needs to bootstrap: OS, frameworks, libraries, database, broker. Any coupling point the whole system needs to run pulls everything around it into one quantum. Pick an architecture and see where the quantum boundaries fall.

4

Static wiring versus dynamic calls

Static coupling is how things are wired; dynamic coupling is how they call each other at runtime. A useful test: "if I had to bring this service up from nothing, would I need this?" The presence of a message broker is static. Sending a request through it to another service is dynamic. Sort these.

Scalability is not elasticityScalability is supporting many concurrent users. Elasticity is absorbing a burst of requests in a short time. Static decoupling sets the scope over which each service can be elastic; a synchronous call temporarily collapses two scopes into one.
6

Dynamic coupling has three dimensions

How quanta talk to each other is a three-way decision, and each choice pulls on the others. Transactions are easier with synchronous, orchestrated calls; the highest scale comes from asynchronous, eventually consistent, choreographed ones.
