Managing Distributed Workflows

Who coordinates a workflow that spans services? A central orchestrator or the services themselves? The answer moves complexity around; it never removes it.

1

Coordination: the third force

Chapter 2 named three forces that shape how services interact: communication (sync or async), consistency (atomic or eventual) and coordination. This chapter is about the last one: how several services are combined into one piece of domain work. There are two basic shapes. Orchestration puts a conductor in the middle, an orchestrator (or mediator) that holds the workflow's state, optional steps, error handling and notifications, and owns no domain behavior of its own. Choreography has no conductor: each service does its part and passes the baton, like dancers who know the routine.

Not the same as an API gatewayIn microservices, each workflow gets its own orchestrator. A single global one would couple everything. A gateway that only routes requests is not an orchestrator.
2

Order placement: happy path, then reality

A shop's order workflow: record the order, take payment, fulfil, email the customer. On the happy path choreography looks simpler: no extra service, just a chain. Now try the two failures. Watch the message count and, more importantly, the red links: communication paths that did not exist on the happy path.

Links are counted by direction between domain services: a reply that flows backwards is a new dependency. Orchestrator links are two-way by nature.

In the orchestrated version, even the nastiest error reuses the lines that were already there; the orchestrator just sends different messages along them. In the choreographed version, each error grows new paths between domain services, and those services must learn more about the workflow to know whom to tell. A back order deep in the chain means every earlier step has to be undone by messages fanning backwards.

3

You can't make the domain simpler, only the code worse

Every workflow carries semantic coupling: the steps the problem itself demands. A ticket must be submitted, assigned, routed, fixed and closed, whatever you build. No architecture can remove that coupling; a poor fit can multiply it. Compare where one domain workflow, "checkout", lives in a technically layered monolith versus a domain-partitioned modular monolith.

The lesson of the last decadeMake the implementation follow the shape of the workflow as closely as you can. Sometimes a technical split is worth it, for example layering for shared connection pooling, but then it is a deliberate trade, not a default.
4

Complexity tips the balance

The more steps and error paths a workflow has, the more an orchestrator pays for itself. Choreography's sweet spot is high throughput with few, or rare, error cases. Describe your workflow.

Orchestration gives you

  • One owner for state and behavior as complexity grows
  • Easier error handling
  • Retries and recovery when a service blips
  • Workflow state you can query

Orchestration costs you

  • A throughput bottleneck: everything passes through it
  • A single point of failure unless made redundant
  • Less parallelism, so less scale
  • Tighter coupling between orchestrator and domain services

Sysops Squad: the primary ticket workflow

Sysops SquadAusten offers to write an ADR declaring "choreography everywhere". Logan suggests modeling the real ticket workflow both ways first: submit a ticket, assign an expert, route it to their phone, notify the customer, mark complete, then send a survey. Messages get lost, experts get reassigned, phones drop offline. Decide each row yourself, then compare with the team.

ADR

Use orchestration for the primary ticket workflow

Decision

The workflow must make lost or mis-routed tickets easy to spot, handle errors well, and let anyone check a ticket's status. An orchestrator does all three.

Consequences

The single orchestrator could limit scalability. Revisit the decision if scale requirements change.
