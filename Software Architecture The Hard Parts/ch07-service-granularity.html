Service Granularity

How big should a service be? Six forces push services apart and four pull them back together. The right size is wherever those forces balance for your system.

1

Modularity is about parts; granularity is about their size

The dictionary definitions blur together, but the book separates them: modularity is breaking a system into parts (Chapter 3); granularity is how big those parts are. Most trouble in distributed systems comes from granularity, not modularity. Size isn't classes or lines of code but what a service does. Two rough metrics help: the number of statements and the number of public operations a service exposes.

Two forces decide size. Granularity disintegrators ask "when should I break this service apart?" Granularity integrators ask "when should I put services back together?" The classic mistake is listening only to the first.

2

Lab: should Notification be split?

One Notification Service sends SMS, email and postal letters. All three relate to "notify the customer", so cohesion alone doesn't justify splitting. "Single purpose" is in the eye of the beholder. Measurements settle it. Turn on the evidence you have.

Check the leftoversIf email crashes and you pull it out alone, what do you call what remains? "Other Notification"? "SMS-Letter"? If a service is hard to name, its cohesion is weak. Whenever you split for one reason, make sure the leftover functionality still forms a strong, nameable service.
3

Security and extensibility

Security: protect the access path, not only the storage

Card data may sit in a locked-down schema, yet if the same Customer Profile service also maintains card numbers, anyone calling it for a name is one endpoint away from the cards. A separate single-purpose card service restricts access at the service level.

Extensibility: only if growth is expected

A payment service that keeps adding methods (gift cards, rewards points, new wallets) has to retest and redeploy every method each time. Separate services per method make additions cheap. But notification channels rarely grow; payment methods often do. Don't guess: apply this driver only when expansion is known or normal for the domain.

4

What pulls services back together

Workflow and choreography. Split one customer service into five and a single screen now needs five hops. At an assumed 300 ms of network and security latency per hop, the cost adds up. Fault tolerance gained by splitting also vanishes if services depend on each other synchronously.

Database transactions and reliability. Registering a customer across separate services means separate commits. Watch one fail.

Shared code. Logging, security and monitoring shared by everyone are no reason to merge. Shared domain code is different: if it is a large share of the codebase, changes often, or carries defects that can't be versioned, consider merging.

Data relationships. Map which function writes (owns) and which only reads each table, then split. If services keep reading tables owned by each other, they will chatter forever.

Turn the drivers into a question for the business

Architects shouldn't settle these alone. Pair a disintegrator with an integrator, phrase it as a trade-off in business terms, and ask the product owner which matters more. Build one.

6

Sysops Squad: two granularity calls

Predict what the team decided, then read why.

Your call

ADR

Consolidated service for ticket assignment and routing

Decision

Tickets are routed the moment they are assigned, so the operations are tightly bound. Both scale the same; neither is fault tolerant without the other; splitting would add workflow, latency and reliability risk.

Consequences

Frequent changes to the assignment algorithm mean retesting and redeploying routing too: bigger test scope and deployment risk.

Customer registrationProfile, card, password and products: one service, four, or two (sensitive versus not)? Austen facilitates rather than dictates, with the product owner and security expert. Registration must be all-or-nothing, and security can be handled through design (a dedicated encryption library, access controls) rather than architecture (separate deployment units). Result: one consolidated customer service, with the security measures written into the consequences.
