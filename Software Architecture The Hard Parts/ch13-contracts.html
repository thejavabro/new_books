Contracts

Every time two pieces of software meet, there is a contract. How strict it is decides how much they can change without breaking each other.

Contracts cut across everything

Chapters 2 and 12 treated communication, consistency and coordination as three axes. Contracts are different: they cut across all three, like a texture laid over the whole space. The book uses a deliberately broad definition: a contract is whatever format one part of an architecture uses to pass information or dependencies to another. That covers REST payloads and gRPC calls, but also library dependencies, caches and anything else that wires the system together.

Contracts sit on a spectrum from strict (names, types, order, all fixed) to loose (just names and values). Pick a point to see a sample contract for the same order message.

What breaks when the provider changes?

  
Strict contracts behave like method calls, which feels safe, but every change to the agreement is a change for both sides. Loose contracts let each side keep its own internal model and survive more changes, but nothing checks that the right fields actually arrive. Choose a change and see which consumer styles break.

  

    

    

    

  

  
Strict: good for
  • Guaranteed fidelity, checked by schema
  • Explicit versions for gradual change
  • Build-time verification
  • Self-documenting parameters and types
Strict: costs
  • Tight coupling: change one side, change both
  • Versioning that sprawls without a deprecation plan

  
Loose: good for
  • Highly decoupled services, each with its own model of "customer"
  • Easier evolution of everything except semantics
Loose: costs
  • Contract management: missing or misspelled fields
  • Needs fitness functions to stay honest

Consumer-driven contracts: loose wire, strict tests

  
Normally the provider decides what to send and pushes it at consumers. A consumer-driven contract flips that: each consumer writes tests stating exactly what it needs, and hands them to the provider, who runs them in its build pipeline. The wire format stays loose; the tests make it as strict as each consumer wants. Try removing fields from the provider's message.

Two simple mechanisms instead of one clever oneLoose payloads plus consumer tests often beat an elaborate schema toolchain. Tests can also check what schemas cannot, such as the allowed range of a number. The catch: it only works with engineering discipline. If teams ignore red builds, broken integrations go unnoticed.

Stamp coupling: sending the whole stamp for one detail

  
Stamp coupling means passing a large structure when each receiver uses only a small part of it. Sometimes it is legitimate, as with industry-standard XML documents that many parties fill in. More often it is accidental: Wishlist needs a customer's name, but the contract is the entire profile "in case it needs more later". Now any profile change can break Wishlist, and the payload eats bandwidth. Bandwidth is not infinite, a classic fallacy of distributed computing.

The good use: carrying workflow state

  
Chapter 11 left choreography with a question: without an orchestrator, where does the workflow's state live? One answer is to put it in the contract. Each service updates its part and the workflow section, then passes the whole thing on. The last receiver can read success, failure and error messages straight from the message. Step through it.

  

  
Yes, this couples services more than strictly necessary. But the semantic coupling of a complex workflow has to live somewhere, and this keeps choreography's scale without adding an orchestrator. The trade: bigger messages, which matters at high volume.

Decision
The app ships through a public app store whose review can take a long time, so contract changes cannot be rolled out quickly. Use name-value pairs between the orchestrator and the app, plus an extension mechanism for short-term additions.
