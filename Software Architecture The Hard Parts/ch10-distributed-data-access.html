Distributed Data Access

A service needs data it does not own. Ask the owner each time, keep a copy, share a cache, or share the tables: four patterns with very different trade-offs.

1

Reading data you no longer own

In a monolith, a join is free. After Chapter 9 every table has one owner, and a service that needs someone else's data can no longer just query it. The example: the Wishlist service shows each saved item with its description, but descriptions live in the Catalog service's bounded context. Four patterns answer "how does Wishlist get item_desc?" Pick one to see the shape and the scorecard.

The scorecard condenses the trade-off lists in the chapter into good, mixed and poor. It is a reading aid, not a measurement.

2

Just ask the owner

The most common pattern, and the simplest: Wishlist sends a list of item IDs to Catalog and gets descriptions back. Nothing is duplicated and data volume is irrelevant. The costs are three kinds of latency, plus coupling: if Catalog is down or slow, so is Wishlist, and Catalog must scale whenever Wishlist does. Try your own numbers.

Three latencies, namedNetwork: getting packets there and back. Security: extra authorization at the endpoint, which can easily add tens to hundreds of milliseconds. Data: the owner makes its own database call to answer you, so one logical read becomes two.
3

Copy the column across

Add an item_desc column to the Wishlist table. Reads are now local, fast, and immune to Catalog outages. The price is keeping copies in step: every time Catalog adds, removes or renames a product it has to tell every service holding a copy, usually asynchronously. And since the copy sits in someone else's table, nothing technically stops them from editing it. Watch drift build up.

The authors are wary of this for wish-list style lookups. It earns its place in aggregation and reporting, or where volume, responsiveness or fault-tolerance demands rule out everything else.

4

Three caching models, only one fits

Caching is usually sold as speed. Here it is used for sharing. Compare the three models when Catalog updates a description, and when Catalog or the cache server goes away.

5

Where replicated caching runs out

Catalog owns the cache and is the only writer; Wishlist holds a read-only replica that the caching product keeps current. Access is in-memory, there are no calls, and Catalog can go down without hurting Wishlist. So what is the trade-off? Four of them. The first two are arithmetic.

Startup dependencyThe first Wishlist instance needs Catalog running to fill its cache. Later instances can copy from a peer.
Data volumeEvery instance holds the full copy. Past roughly half a gigabyte, memory bills climb fast.
Update rateVery volatile data, such as stock counts, may change faster than replication can keep up.
ConfigurationPeers find each other by network broadcast and lookup, which is fiddly in cloud and container setups with shifting IP addresses.
6

Share the schema, on purpose

The same move Chapter 9 used for joint writes. Put Catalog's product table and Wishlist's table in one shared schema, and Wishlist reads with an ordinary join. No calls, no copies, no sync, and foreign keys work again. The catch: the schema itself becomes the contract. There is no API in front to absorb changes, so a column rename can break both services. And Wishlist can now see everything in that schema, which may include data it should not.

-- inside the shared product_domain schema
SELECT w.item_id, p.description
FROM   wishlist_item w
JOIN   product p ON p.item_id = w.item_id
WHERE  w.customer_id = :customer;
7

Choosing by elimination

The chapter reaches the data domain pattern by ruling the others out one by one. Do the same: tick what is true for your situation.

8

Sysops Squad: expert profiles for ticket assignment

Sysops SquadTicket Assignment reads the expert profile table constantly, and that table now belongs to User Management. Asking over the network on every assignment is too slow and fragile. A shared schema is out because Ticket Assignment already uses the ticketing data domain and the two are different domains. Nobody can find a serious drawback to a replicated cache, so the team checks it against the deployment environment and builds a proof of concept.
ADR

In-memory replicated cache for expert profile data

Decision

Replicate expert profiles from User Management into Ticket Assignment. User Management is the only writer. This fixes the speed and fault-tolerance issues of remote calls without merging schemas across domains.

Consequences

At least one User Management instance must be up when the first Ticket Assignment instance starts. The caching product carries a licence cost.
