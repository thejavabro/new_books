Component-Based Decomposition Patterns

Six repeatable steps turn a tangled monolith into well-sized components, grouped by domain, and finally into domain services, with a fitness function guarding each step.

1

Six patterns, in order

Component-based decomposition works when the code is at least somewhat organized into namespaces or directories. The authors capture it as six patterns, applied in sequence during the migration and then individually as maintenance continues on the monolith. Each comes with fitness functions so the codebase doesn't drift back while the migration is under way. Tap a step.

Architecture storiesEach refactoring is recorded as an architecture story, not a user story and not a tech-debt ticket: "As an architect, I need to decouple the payment service to support better extensibility when adding payment types." It changes structure for a business driver, and it needs doing now, not "later".
2

Identify and size components

Services are built from components, so get the components right first. Lines of code and file counts vary too much by style; the authors size components by number of statements. Sizes should be fairly even, within one or two standard deviations of the mean. Below is the Sysops Squad inventory (about 83,000 statements). Set the threshold and run the fitness functions.

Other signals: a "simple" component with 12,000 statements is more complex than it looks; one with 18,000 statements in 2 files needs smaller classes; a vague name like "Ticket Manager" should be renamed. Large components are split by subdomain, if a clear one exists.

# fitness function: size outliers (illustrative)
sizes = statements_per_component(src)
mean, sd = avg(sizes), stdev(sizes)
for c, n in sizes:
  if n / total(sizes) > MAX_PCT or abs(n - mean) / sd > 3:
    alert(c)
3

Gather common domain components

Shared domain logic (notification, formatting, validation; used by some processes) differs from shared infrastructure (logging, metrics, security; used by all). Duplicated domain logic turns into duplicate services. Clues: a class like SMTPConnection used from five namespaces, or namespaces that end the same way. Spot the duplicates.

Leaf-name fitness function

The scan alerts when two or more components share a final namespace node. An exclusion list suppresses known false positives like .validate.

The Sysops Squad has three notification components. Consolidating them looks good, but check what it does to coupling first.

4

Flatten components

A component is a leaf node of the namespace that contains source code. Once ss.survey is extended by ss.survey.templates, it becomes a root namespace (a subdomain), and any classes left inside it are orphaned classes belonging to no component. Stacked components form "hills". Flatten them one of two ways.

5

Determine component dependencies

Three questions come before any migration: is it feasible, roughly how big is it, and is it a refactor or a rewrite? A CIO once asked one of the authors simply: golf ball, basketball or airliner? A component dependency diagram answers it. Only dependencies between components count; a mess inside a component doesn't matter here.

Splitting a component can cut its coupling

Component A has 20 incoming dependencies, but 14 callers only use one small feature. Split it.

Governance: a fitness function caps total coupling (Ca + Ce, say 15) per component, and rules such as "Ticket Maintenance must not access Expert Profile" can be enforced with a tool like ArchUnit, one rule per restriction.

6

Create component domains

Services and components are usually one-to-many. Group components into domains and express them in the namespace: ss.customer.billing.payment reads as domain, subdomain, component. Older code written before Domain-Driven Design rarely lines up, so namespaces get refactored. Place each Sysops Squad component in a domain, as the architects and product owner did.

Domains: Ticket, Customer, Reporting, Admin, Shared

A component that fits nowhere is a signal to go back to the business stakeholders. A fitness function can then restrict all namespaces to the approved domains.

7

Create domain services

Finally, move each domain into a separately deployed, coarse-grained domain service: a service-based architecture with a UI calling domain services over one shared database. Only start after every domain is identified and refactored, or you'll be moving components between already-extracted services.

Don't start too fine-grainedTeams that jump straight to microservices take on data decomposition, distributed workflows and transactions, containers and operational automation before they know whether they need them. Learn from domain services first, then split only those that need it.
