Reuse Patterns

Distributed systems still need shared code. Copy it, package it, deploy it as a service or hang it on a sidecar: each choice trades a different kind of coupling.

1

Reuse is abuse? Not quite

In a monolith, reuse is an import statement. In a distributed system every shared piece raises a question: where does it live, how does it change, and who breaks when it does? Some microservices folk answer "share nothing" or swap DRY (don't repeat yourself) for WET (write everything twice). But formatters, validators, security and logging still have to come from somewhere. The book compares four techniques.

2

Code replication

Copy the shared code into every service's repository. It became popular in early microservices, when "bounded context" was misread as "share nothing", and mostly fell apart. It still suits simple static code that will never change, like a marker annotation saying "this class is the service entry point". It also works as a migration trick: copy a utility class everywhere and let each service trim it, a bit like tactical forking. Then a bug turns up.

A defect is found in the replicated DateUtils. Tap each copy to patch it.

// a good candidate for replication: pure marker, no behaviour to go wrong
@Retention(RUNTIME) @Target(TYPE)
public @interface ApiEntryPoint { String domain() default ""; }
3

Shared libraries: granularity and versioning

A JAR, DLL or gem bound in at compile time. The tension is dependency management versus change control. One coarse SharedStuff.jar is easy to depend on, but any change eventually forces every service to retest and redeploy. Many fine-grained libraries isolate change but turn the dependency matrix into a distributed big ball of mud. Change one class and compare.

The authors favor change control: smaller, functionally partitioned libraries, especially carving off static code like formatters and security. And always version. Then choose how many old versions to keep supporting.

Versioning is not simpleThe authors half-jokingly call "versioning is simple" a ninth fallacy of distributed computing. Who hears that Validation.jar is now 1.5, and what changed? A per-library deprecation policy beats one global rule, a serious defect overrides any policy, and depending on LATEST will bite you during an emergency hot fix.
4

Shared services: runtime reuse

Put the shared functionality in its own deployed service (which means reuse by composition, not inheritance). Change it once and everyone gets it, with no redeploys. That convenience is a double-edged sword. Compare it with a library on the same scenarios.

# endpoint versioning: each change gets a URI...
GET /v1.0/discount?order=123
GET /v1.1/discount?order=123
GET /v1.2/discount?order=123   # ...and every caller must be repointed. Does a new error message count?

Shared service: good for

  • Code that changes often
  • Polyglot estates: no duplicate implementations per language
  • Preserving the bounded context; no static code sharing

Costs

  • Runtime changes can break everything at once
  • Network and security latency (gRPC or async messaging help)
  • Must scale with its busiest caller
  • Its outage is every caller's outage
5

Sidecars and the service mesh

"Duplication is preferable to coupling" works for domain concepts like each service's own Customer. But monitoring, logging, service discovery, authentication and circuit breakers benefit from being identical everywhere, and leaving them to each team descends into chaos. The answer descends from Alistair Cockburn's hexagonal (ports and adapters) architecture: separate the domain from the technical plumbing, and put the plumbing in a sidecar.

Orthogonal couplingTwo concerns that are independent but must intersect, like monitoring and checkout, are orthogonally coupled. Services are cut along domain lines; operational concerns cut across them at right angles. The sidecar isolates that cross-cut, much as the Decorator pattern adds behavior without touching the object. Downsides: one sidecar implementation per platform, and a sidecar that can grow large. Never put domain classes in it.
6

Reuse comes from abstraction, value from slow change

Orchestration-era SOA chased reuse above all. An insurer noticed every division had a notion of "customer" and built one enterprise Customer service. It became too complex for simple uses and so brittle that any change rippled across every division. We happily reuse operating systems and open source frameworks because they change slowly and predictably. Place each candidate; tap it to cycle its rate of change.

Abstraction makes reuse possible; slow change makes it worth itHence the current fashion for platforms: each domain capability behind a well-designed, loosely coupled API, so the implementation can change fast while the contract changes slowly (Chapter 13).

Sysops Squad: two reuse decisions

Who writes the logs?Teams consolidating code into shared libraries start getting double log entries: the Message Dispatch library logs and so does the service. Logging, monitoring, discovery and circuit breakers are operational coupling. Decision: a sidecar plus service mesh, owned by the shared infrastructure team, with service teams as its customers. No domain classes allowed in it.

Later, ticketing splits into Ticket Creation, Ticket Assignment and Ticket Completion, all using the same database logic. Taylen wants a shared data service; Skyler wants a shared DLL. Addison proposes testing the hypothesis "a shared data service is best" against the trade-offs. Judge each claim.

For the service or the library?

ADR

Use a shared library for common ticketing database logic

Decision

Better performance, scalability and fault tolerance for the customer-facing Ticket Creation service; the code is stable (repository history showed few changes); versioning covers the rare change; fewer runtime dependencies and less network traffic.

Consequences

Changes to the library mean retesting and redeploying the ticketing services; each service instance manages its own connection pool.
