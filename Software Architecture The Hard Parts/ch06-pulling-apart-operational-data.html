Pulling Apart Operational Data

Splitting the code is the easy half. Data has its own forces for and against breaking apart, a careful five-step migration, and a whole menu of database types to land in.

1

Data is harder to split than code

The Sysops Squad now runs as domain services, all on one database. Addison starts on the data, and immediately learns the first lesson: bring the data architect and DBAs in from day one. Data is usually the company's most important asset, so the risk is higher, and data is tightly coupled to functionality, so seams are harder to find. Microservices insist on splitting it; service-based architecture lets services share it. Luckily, the code techniques translate.

2

Disintegrators versus integrators

Six data disintegrators argue for breaking data apart; two data integrators argue for keeping it together. Getting data granularity right means balancing them for your system. Switch on the forces that apply to you.

3

Change control and the forgotten service

Adding a table or column rarely breaks anything. Dropping or renaming a column, or changing its type, is a breaking change: every service whose SQL touches it must be changed, tested and deployed with the database. The real danger is the service nobody remembered. Try a change on a shared database.

A bounded context fixes this: the service that owns (writes) the data is the only one touching its tables; everyone else asks it through a contract. Because the contract is not the schema, the owner can absorb a breaking change.

-- owner's private table
CREATE TABLE wishlist (
  customer_id  VARCHAR(10),
  item_id      VARCHAR(20),
  qty          INT,
  expires_on   DATE
);
// contract other services see
{ "custId": "C123",
  "itemId": "SKU-9",
  "quantity": 2,
  "expiresAt": 1767139200000 }
4

Connection management and scalability

In a monolith, the app server owns one connection pool. In a distributed system, every instance of every service brings its own pool. Slide the numbers to see why a shared database runs out.

One remedy while still sharing: a connection quota per service, kept in external configuration. Start with even quotas, measure with fitness functions, then rebalance. Five services share 100 connections; move capacity until nobody waits.

5

Fault tolerance, quanta and database type

A shared database is a single point of failure and, as Chapter 2 showed, forces every service into one architecture quantum. Splitting the data lets two services with different needs form their own quantum, and lets some data move to a better-suited database type, for example key-value reference data like country codes.

6

What holds data together

Foreign keys, views, triggers and stored procedures exist for integrity. Telling your DBA that every cross-domain one must go is a hard conversation, and yet a database-per-service demands it. And when one business action writes to tables in two databases, there is no single ACID transaction any more. Step through what is lost.

Sysops SquadDana, the data architect, is skeptical. Addison shows logs: reporting queries run in parallel threads, grab every connection, and ticket creation times out waiting. Devon shows the projected services and instances, each with its own pool. Connection management, scalability and fault tolerance win the argument.
7

The five-step process

An evolutionary, iterative way to go from one database to many, using the data domain as the vehicle. Picture the database as a soccer ball: each white hexagon a data domain. Relationships inside a hexagon stay; the ones crossing seams must be cut.

Data sovereignty per service: benefits

  • Change a schema without affecting other domains.
  • Each service can choose the best database type.

Shortcomings

  • Slow when a service needs large volumes of others' data.
  • No referential integrity across domains: data quality risk.
  • Stored procedures that span domains must move into services.

9

Choosing a database type

Since around 2005 the database world has exploded, a real paradox of choice. The authors compare types on learning curve, ease of modeling, scalability, availability and partition tolerance, consistency, ecosystem maturity, and read or write priority. Explore the families.

Aggregates and "schema-less"NoSQL stores are aggregate-oriented: a ticket and everything that belongs to it travels as one unit, which spreads easily across a cluster and avoids joins, but aggregate boundaries are hard to change and cross-aggregate analysis is hard. And "schema-less" is misleading: the schema is still there, just implicit, and the application must cope with several versions of it.
