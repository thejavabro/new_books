Data Ownership and Distributed Transactions

Once data is split, someone has to own each table. And when one business action writes to several services, atomic transactions give way to eventual consistency.

1

Whoever writes, owns

Splitting the database (Chapter 6) is only half the work. The pieces must be stitched back together: someone has to own each table, multi-table updates have to survive the network, and services need a way to read data they no longer own. This chapter covers the first two. The starting rule of thumb is simple: the service that writes to a table owns it. Readers do not count. The rule is easy when one service writes and gets messy when several do.

The running example has three services and three tables. Tap a table to see who writes to it and what kind of ownership problem that creates.

Single ownershipExactly one service writes. Give it the table, draw the bounded context around both, and move on. Do these first to clear the board.
Common ownershipMost or all services write (audit logs, configuration). Nobody is the obvious owner.
Joint ownershipA couple of services in the same domain write to the same table. The most frequent and the hardest case.
2

Common ownership: appoint a keeper

Dropping the Audit table into a shared schema brings back every problem from Chapter 6: change control, connection starvation, scaling and fault tolerance. Instead, create one service whose only job is to own that table. Everyone else hands it data. If callers need nothing back, a persisted queue with fire-and-forget messages keeps them from waiting. If they need an answer (a generated key, a confirmation number) they must call synchronously, by REST, gRPC or request-reply messaging.

If other services need to read audit data they do not own, that is a data access question, answered in Chapter 10.

3

Joint ownership: four ways out

Catalog writes product details; Inventory writes stock counts. Both write the Product table. There are four ways to untangle that. Pick one to redraw the picture and see what you trade.

Here is a table split written as plain DDL (my own sketch, not the book's listing). Create the new table, copy the column across, then drop it from the old one. The hard part is not the SQL; it is keeping the two tables in step afterwards.

-- 1. new table owned by the Inventory service
CREATE TABLE stock_level (sku VARCHAR(12) PRIMARY KEY, on_hand INT NOT NULL);
-- 2. seed it from the shared table
INSERT INTO stock_level (sku, on_hand) SELECT sku, on_hand FROM product;
-- 3. Catalog's table loses the column it never really owned
ALTER TABLE product DROP COLUMN on_hand;
Two questions every split raisesWhen Catalog adds a product, does it need confirmation that the stock row exists (synchronous, consistent, slower) or can it fire and forget (fast, eventually consistent)? And what does it do if Inventory is down: refuse the new product (consistency) or accept it and catch up later (availability)?

Which service becomes the delegate?

The authors usually lean to domain priority and fix the speed problem with a replicated in-memory or distributed cache, because making Inventory handle product maintenance gives it a job outside its domain. Either way the non-owner pays: network latency, no atomic write, and an outage whenever the owner is down. That is why the delegate technique tends to come last among the four.

BASE: what a distributed transaction offers instead

Spread the same registration over a Profile, a Contract and a Billing service and none of the four ACID properties hold across the whole request. Each service still commits its own rows atomically; the business request is no longer atomic. The opposite of an acid is a base, and so the industry named the replacement BASE.

Three ways to become consistent eventually

Customer 123 unsubscribes. The Profile service deletes them and tells the customer they will no longer be billed, but their rows still sit in the Contract and Billing tables. How do those get cleaned up? Pick a pattern, optionally break Billing, and run the clock.

Durable subscribers and dead lettersEvent-based consistency only works if no event is lost. Topic-based brokers need durable subscribers; streaming platforms must keep the message long enough. When a consumer keeps failing, the broker parks the event in a dead letter queue, where an automated fixer, or a person, deals with it.

Sysops Squad: who owns the survey table?

Sysops SquadThe developers and the database team realise ownership cannot be settled by either side alone. A blanket ADR goes first: single-writer tables belong to that writer, and other bounded contexts may not reach into its schema. Then the survey: Ticket Completion writes the finish time and expert; Survey writes when the survey was sent and the answers. Joint ownership.

Pick a technique for the Survey table

ADR

Survey Service owns the Survey table

Decision

Use the delegate technique. Ticket Completion already sends an event when a ticket closes; it adds the fields the survey needs to that payload, and only Survey writes the table.

Consequences

Everything Ticket Completion used to insert now travels in the message. Creating the survey record becomes its own step instead of part of closing the ticket.
