Queues vs. topics, live

A queue is point-to-point, like a group text: the sender picks each recipient and needs one queue per consumer. A topic is a broadcast, like posting to your social feed: the sender posts once and anyone subscribed gets it. Send some trades, then try the two twists.

The first law

First Law of Software Architecture

Everything in software architecture is a trade-off.

Corollary: if you think you found a decision with no trade-off, you haven't looked hard enough.

Your job is twofold: know the upsides and downsides of every option, then choose the one that best serves the characteristics that matter most. When someone praises a shiny tool, the right response is: "What are the trade-offs?"

Every upside has a shadow. Tap to flip.

About formal methods. ATAM walks stakeholders through scenarios to validate an architecture. CBAM focuses on the cost of each "-ility". Both are useful, but the goal matters more than the process: an architecture that fits the business, revisited as you learn.

What makes a decision architectural?

Mostly, it affects the structure. But a decision is also architectural when it protects a key characteristic (like "all trade traffic stays on internal queues for security"). Michael Nygard's checklist says a decision is architectural if it affects any of five things. Pick an example to see which it touches.

The second law

Second Law of Software Architecture

Why is more important than how.

A newcomer can read the code and see how you built something. They cannot see why. Without the why, they may waste weeks re-testing an option you already rejected, or undo a decision that was protecting something important.

Good titles make good file names

Titles start with a three-digit number (001 to 999, never reused) and a short, noun-heavy description, like a headline. Store ADRs as Markdown in their own repository (or a wiki that tracks changes) and use the title as the file name: lowercase, hyphens for spaces. Sorting by name then gives you the order of decisions.

10

Consequences and governance

Consequences list the good and the bad, so everyone can judge whether the upside is worth it. Ask: how does this affect the team, the infrastructure, cross-cutting concerns like security and observability? Governance says how you'll make sure people keep following the decision: code reviews, pairing, or automated tests (fitness functions) that fail the build when someone breaks the rule.

Consequences of "use queues"

+Each consumer gets exactly the data it needs
+Only known services can read trades
+Queues scale and are monitored separately
−Adding Compliance means changing the trading service
−New infrastructure that must itself be highly available
