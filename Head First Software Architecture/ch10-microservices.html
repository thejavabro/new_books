Microservices Architecture: Bit by Bit

Small, single-purpose services that each own their data. Microservices buy agility, scale and fault tolerance, and you pay for them in complexity. Here's how to size them, share code between them and coordinate them.

1

MonitorMe: watching patients' vital signs

A medical-equipment company is replacing its hospital monitoring software. The new system reads eight vital signs per patient (heart rate, blood pressure, oxygen, blood sugar, breathing, ECG, temperature and sleep), keeps five minutes of history, and alerts a nurse or doctor the way they prefer when a reading crosses a threshold. Up to 500 patients per hospital, with a full copy of the system in each one. And if one input fails, the other seven must keep working.

Which characteristics matter most? Pick five.

One reasonable top five: fault tolerance (one failed input must not stop the rest), responsiveness (alerts are life and death), data integrity (no lost readings), scalability (hundreds of patients streaming data) and testability (medical software must be thoroughly tested). Different picks are fine if you can tie them to a requirement.
Careful: jumping straight to "it's obviously microservices" is a trap. Learn the style and its trade-offs first, then decide.

What makes a service "micro"?

A service is anything deployed separately. Micro is about purpose, not size: a microservice does one thing and does it well. "Monitor heart rate" is a microservice; "monitor all vital signs" is just a service.

It's my data, not yours

Each microservice is the only one allowed to touch its data. Together they form a physical bounded context. Anyone else who needs that data has to ask the owner. Change the sleep data's structure and see who breaks.

4

How micro is micro?

Monitoring blood pressure involves four jobs: capture the reading, record it, analyse it, alert someone. You could build one, two or four services. Switch between them to compare.

5

Disintegrators vs integrators

Granularity isn't guesswork. Disintegrators push you to split a service; integrators push you to merge. Toggle the forces that apply to "monitor basic vital signs" (blood pressure, temperature, heart rate) and watch the rope.

Merge it (integrators)

Rule of thumb: start coarse-grained, then split as you learn where the real pressures are. Bring big trade-offs to the business stakeholders.
6

Sharing code: library or service?

Every vital-sign service needs the same "alert a nurse" code. Copying it is only safe for code that never changes. The real options are a shared service called over the network, or a shared library compiled into each service. Try each scenario.

Shared serviceShared library
Changing itDeploy once, everyone gets itEvery service retests and redeploys (versioning helps)
Mixed languagesAny language can call itOne build per platform
PerformanceNetwork hop every callIn-process call
Fault toleranceIf it's down, every caller suffersAlways there
ScalabilityMust scale with all callersScales with each service

For MonitorMe's alerts, where speed and reliability save lives, the library's operational strengths usually win.

7

Workflows: conductor or dancers?

A nurse asks "how is this patient doing?" That one request needs the temperature, blood-pressure and heart-rate services. Coordinating several services for one request is a workflow, and there are two ways to run it.

Orchestration (conductor)

+ whole workflow in one place, knows the state, handles errors, easy to change
− slower, a bottleneck, tightly coupled, a single point of failure unless you run several copies

Choreography (dancers)

+ faster, loosely coupled, each service scales alone
− errors handled everywhere, hard to know the state or where to restart. Don't let one dancer quietly become the conductor.
