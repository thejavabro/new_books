Starting layered and refactoring into a modular monolith as the app grows is very common. Choosing layered first was not a mistake. It got the shop online.
2

Take a vertical bite

Nobody eats a burger one layer at a time: top bun, then cheese, then patty. You bite straight down through everything. A modular monolith slices the same way. Each module is a vertical slice for one subdomain, owned by one cross-functional team.

3

Inside a module (yes, there may be layers)

A module still needs an entry point, business logic and data access, so it may have layers inside. That's an implementation detail. At the architecture level, the system is partitioned by domain. In code, each module is a namespace in one codebase.

5

Keeping modules modular

Ordering needs to know if there are mushrooms in stock, so modules must talk. In one codebase it is dangerously easy (thanks, IDE auto-import) to reach straight into another module's internals. Do that enough and you're back to a ball of mud. Treat each module like a service with a public API.

7

Take modularity to the database

Modular code over a tangled database just moves the mud. The rule: each module touches only its own tables, ideally in its own schema. It's fine to store another module's IDs, but never join across schemas or use a foreign key. Ask the other module's API instead. (Do this once the team is comfortable with modular code; it can evolve.)
