Layered Architecture: Separating Concerns

The simplest architecture that still gives you real structure. Split by technical layer, deploy as one unit, and you can build fast. The catch: business changes cut through every layer.

1

Naan & Pop needs a website, fast

A small Indian-inspired restaurant selling flatbread sandwiches and sodas wants online ordering. It's a startup with a small budget.

Time to marketThe restaurant is already open. Every week offline is lost money. Keep it simple.
Separation of responsibilitiesPart-time specialists: UI designers, database admins. Keep their work apart.
Simple, yet extensibleLater: a mobile app, delivery-service integrations, maybe more menu items.

Characteristics: feasibility, simplicity, specialisation, some extensibility. That points to a layered monolith.

2

From MVC to layers

Developers know the Model-View-Controller design pattern: the view is the UI, the controller runs the workflow, the model holds business entities. A design pattern is a logical solution. Architecture must also deal with real things like browsers and databases. Map one onto the other.

Which came first? Probably layers. Layered systems existed long before the pattern was named. Patterns are harvested from things people keep doing.
3

A request's trip through the layers

Every request starts at the top and travels down through each layer, to the database and back. Follow one order. Layers are just packages or namespaces, like com.naanpop.orderapp.presentation.

The domain gets sliced across layers

  
Logical components describe the business (Place Order, Menu, Payment). Layers describe technical jobs. So each business component is cut into pieces that live in different layers. Tap a component to see where its pieces end up.

Two kinds of change

  
This is the key trade-off of the style. Try both changes and count the layers you touch.

  

    

    

    

  

  
Rule of thumb
Layered architectures make technical changes easy and domain changes hard.






  
6
Same layers, different physical shapes

  
The layered monolith is a logical design. It can be deployed several ways. Pick one.

  

    

    

    

  






  
7
Adding a layer

  
You add a layer when every request needs a new kind of handling. Naan & Pop wants delivery services to place orders too, so the team adds an integration layer (a services layer for business-to-business access works the same way).

Recap on one page

  

    
Technical + monolithicLayers by technical role, deployed as one unit with its database.

    
Typical layersPresentation, workflow (business rules), persistence. Add more when every request needs it.

    
Cousin of MVCFamiliar, so quick to understand and build.

    
Easy technical changeNew UI or database touches one layer.

    
Hard domain changeThe domain is smeared across all layers.

    
Physical formsTwo-tier, three-tier, embedded/mobile.

    
Keep it leanGrows into a ball of mud and hits resource limits if overused.
