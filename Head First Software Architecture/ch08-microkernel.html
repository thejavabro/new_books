Microkernel Architecture: Crafting Customizations

A small, stable core plus as many plugins as you need. The champion style for customisation, and once you know it you'll see it everywhere.

1

Going Green buys your old gadgets

A startup buys old phones, music players and other small electronics, then resells or recycles them. Its system has three parts with different needs. The interesting one is device assessment, which works out what each gadget is worth. New models arrive constantly, and the faster the company can assess a new model, the more money it makes. So this service needs to change quickly without breaking the models it already handles.

2

A core with sockets

The name comes from operating systems, where a tiny kernel offers only the basics. The core here knows the general assessment steps (age, condition, model number). For each kind of device it hands off to a plugin with that device's valuation rules. Plug some in, then assess a device.

3

The spectrum of "microkern-ality"

Lots of software supports plugins: browsers, IDEs, build tools. Supporting plugins doesn't make something a microkernel. Ask two questions: how useful is the core with no plugins? and how often does the core change? The less the bare core can do, the more microkernel it is. (Microkernel and microservices are unrelated despite the name.)

4

Monolithic or distributed plugins?

Microkernel sits between the two deployment models. Plugins can be components in the same deployable (JARs, DLLs, gems) or separate services called over the network, synchronously or asynchronously.

Monolithic pluginsDistributed plugins
PerformanceIn-process callsNetwork latency
Adding a pluginRedeploy or restart the serviceDeploy just the plugin, no downtime
ScalabilityScale everything togetherScale busy plugins alone
Language choiceSame stack as the coreAny language reachable over the network
SimplicityOne unitMore moving parts
Going Green's decision: distributed plugins (new devices without restarts, better availability and scalability, freedom to use other languages later), called synchronously because the service is already responsive enough. They accept the performance cost.
5

Contracts instead of switch statements

The core talks to plugins through a contract (an interface). Every device plugin implements the same DeviceInterface. Compare that to the alternative: one giant switch that grows forever.

// without plugins: edit the core for every device
function assess(device) {
  switch (device.model) {
    case "PhoneX 8":  ...  break;
    case "PhoneX 9":  ...  break;
    case "Tablet 2":  ...  break;
    // + 300 more cases, all in the core
  }
}
// with plugins: the core never changes
interface DeviceInterface {
  supports(model): boolean
  value(device): Money
}

function assess(device) {
  const p = plugins.find(p => p.supports(device.model));
  return p ? p.value(device) : notSupported();
}

The same trick powers A/B tests (old behaviour in plugin A, new in plugin B), integration hubs and many UI patterns. It's an architectural cousin of the Decorator design pattern.

6

Should plugins talk to each other?

They can, through the core. But it brings versioned contracts between plugins and runtime dependencies (plugin X won't work unless plugin Y is installed). Tools that allow it pay with complexity. Try changing plugin Y.

7

Keep the core boring

The core should change rarely; the plugins absorb change. If the core keeps changing, you've probably made the wrong things into plugins, or picked the wrong style.
