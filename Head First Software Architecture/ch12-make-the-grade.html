The brief

Students take a timed, two-hour multiple-choice test in their homeroom, supervised by their teacher. They can skip questions but never go back. Each answer is graded automatically and stored in a central relational database. Flip each requirement to hear what an architect hears.

The crunch: 200,000 students, 300 connections

The hardest problem hides in two numbers. Up to 200,000 students may submit answers at the same moment, but the database allows only 300 connections. Try writing directly, then put a persistent queue in between.

Step 4: The decision record

One reasonable choice is microservices, with async pieces where they help. Here it is as an ADR, paraphrased. Tap each consequence to see why it follows.

ADR 11: Use microservices for Make the Grade

Status: Proposed

Context:
Test-taking, grading, admin and reporting need different
characteristics (responsiveness, elasticity, fault tolerance,
data integrity), so the system should be distributed.
The options are microservices and event-driven architecture.

Decision:
Microservices, for fault tolerance, elasticity and scalability.
 · Keep calls between services to a minimum and cache student
   lists, questions and answer keys in memory for speed.
 · Send answers to grading asynchronously through a persistent
   queue; grading acknowledges a message only after the answer
   is saved, so nothing is lost if it crashes.
 · Test admin (scheduling, tests, students) is one service.
   Reporting is one service.
