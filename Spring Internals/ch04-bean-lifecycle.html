The Bean Lifecycle

A bean goes through a fixed sequence of steps between "the class exists" and "you can use it". Most of Spring's magic, including the proxies behind @Transactional, is plugged into one of those steps.

    Two kinds of post-processor, two different moments

    The names are confusingly close, and they are a favourite question. One works on recipes once at startup; the other works on every bean instance as it is born.

    // A tiny BeanPostProcessor: wrap every bean annotated @Timed in a proxy.
@Component
class TimingPostProcessor implements BeanPostProcessor {
  @Override
  public Object postProcessAfterInitialization(Object bean, String name) {
    if (!bean.getClass().isAnnotationPresent(Timed.class)) return bean;
    ProxyFactory pf = new ProxyFactory(bean);
!!    pf.addAdvice((MethodInterceptor) inv -> {
      long t = System.nanoTime();
      try { return inv.proceed(); }
      finally { log(name + "." + inv.getMethod().getName() + " " + (System.nanoTime() - t)); }
    });
!!    return pf.getProxy();   // the container stores THIS, not the bean
  }
}

    That is, in miniature, exactly what Spring's own AbstractAutoProxyCreator does for @Transactional, @Cacheable, @Async and your @Aspects. Pages 5 to 7 open that proxy up.
