Comparing Algorithms

An app that flies on 100 items can crawl on 10,000. That is rarely a coding problem; it is an algorithm problem. This chapter sets up the question the whole book asks: which strategy keeps up as the input grows?

1

Two searches at the Micro-Storage warehouse

The book opens in a tidy warehouse where every item has its own numbered box, and the boxes are listed alphabetically by item. Your predecessor left two search functions. The first, linear search, opens boxes one at a time from the start. The second, binary search, opens the middle box, sees whether the target comes before or after it alphabetically, and throws away the half that can't contain it.

Linear search0 boxes opened
Binary search0 boxes opened

Pick an item and step. Faded boxes are ones the search has ruled out.

Both functions are correct: each finds the item if it is there. The difference is how many boxes they open. Linear search can only rule out one box per look; binary search rules out half of what is left.

2

An algorithm is a recipe, only stricter

A recipe is a fair first picture: ordered steps that turn inputs into a result. But a recipe leans on a cook who can improvise ("spread some jam"). A computer never improvises. If a step is vague, the program crashes, gives a wrong answer silently, or runs forever. Donald Knuth's five criteria raise the bar for what we will study as a formal algorithm. Pick a candidate and see which tests it passes.

The five testsFinite: it always stops. Precise: every step is unambiguous. Input: it has something to work on. Output: it produces a result. Effective: it gets the right answer using reasonable time and resources.
3

Correct first, then efficient

Passing Knuth's tests only gets an algorithm through the door. Among correct algorithms we want good ones, and the book puts efficiency first: how much time (steps) and space (memory) the algorithm needs. The classics in this book are already proven correct, so most of the effort goes into how they perform and scale. Other qualities still matter; open the cards.

4

Count steps, not seconds

Timing code with a stopwatch is misleading. The result depends on the machine, what else is running, and above all on the input size you happened to test. Time complexity asks a cleaner question: as the input grows, how does the number of steps grow? Drag the slider to grow the warehouse.

Linear timeSteps grow in proportion to the input. Double the data, double the work. Simple and predictable; fine for small inputs.
Logarithmic timeEach step halves what is left. Double the data, add one step. A billion sorted boxes need only about 30 looks.
5

log₂ n: how many times can you halve it?

The worst case for binary search is the number of times you can cut n in half before one box is left. Going the other way, it is the power you must raise 2 to in order to reach at least n. That number is log₂ n, which computer scientists usually just write log n. Type any n.

Halving
Doubling from 1

You never need to compute logs by hand. You need the intuition: log n grows so slowly that it barely moves even when n explodes.

Play: guess the number from 1 to 100

A friend picks a number from 1 to 100 and only says "higher" or "lower". Competitor A guesses 1, 2, 3 and so on. Competitor B always guesses the middle of what remains. Play it yourself, then compare.

7

Everyday searches: linear or logarithmic?

The pattern shows up away from computers too. If the things you are searching are in order and you can jump around, you can halve. If they are in no useful order for your question, you must look at each one.

8

Binary search was standing on a sorted list

Binary search looks brilliant, but half its work was done before it started: the list was already sorted. Shuffle the same boxes and try again. This is why the book studies algorithms and data structures together. The algorithm is the plan; the data structure is the layout that makes the plan possible.
