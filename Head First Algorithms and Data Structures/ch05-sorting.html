Sorting

Sorted data is what makes binary search, de-duplication and fast lookups possible. Here are the classic ways to get there, from the simple O(n²) sorts to the O(n log n) workhorses.

Someone has to do the sorting

Binary search gave us O(log n) lookups, but only on a sorted array, and arrays don't sort themselves. This chapter meets four classic ways to sort, a new growth class (O(n log n)), a speed limit for sorting, and the hybrid sorts your language actually uses. Bubble sort: swap neighbors until nothing moves

Walk the array comparing neighbors and swap any pair that's out of order. Each pass carries the largest remaining value to the right end, like a bubble rising, so the unsorted part shrinks by one. Stop when a whole pass makes no swaps. It is simple and in-place, but in the worst case (reverse order) almost every comparison is a swap: about n²/2 comparisons, so O(n²).

def bubble_sort(a):
    for end in range(len(a) - 1, 0, -1):
        swapped = False
        for i in range(end):          # inner loop shrinks each pass
            if a[i] > a[i + 1]:
                a[i], a[i + 1] = a[i + 1], a[i]
                swapped = True
        if not swapped: break          # already sorted: stop early
3

Insertion sort: like sorting cards in your hand

Keep a sorted section on the left. Take the next item (the key), slide it left past every bigger item, and drop it in place. On reversed data each key slides all the way: O(n²). On data that is already nearly sorted each key barely moves, so it approaches O(n). That makes insertion sort a favorite for small or nearly sorted inputs. Step through one run.

4

Merge sort: split in half, merge in order

Merge sort is divide and conquer. Split the list in half, and keep splitting until every piece has one item (one item is already sorted). Then merge pairs of sorted pieces by repeatedly taking the smaller front item. Splitting does no comparisons; all the work is in the merges.

Where O(n log n) comes fromHalving gives log n levels (7 items need 3 levels; 9 need 4). Each level of merging touches all n items once. log n levels × n work per level = O(n log n), in the best, average and worst case alike. The cost is memory: temporary arrays for merging (O(n)) plus O(log n) stack frames, so O(n) extra space.
5

Quicksort: let a pivot do the dividing

Quicksort skips perfect halves. Pick any item as the pivot; everything smaller goes to a "before" pile and everything bigger to an "after" pile. Sort each pile the same way, then join before + pivot + after. Good pivots split near the middle and give O(n log n). Bad pivots (say, always the first item on already-sorted data) peel off one item at a time and degrade to O(n²). Try pivot rules on sorted input.

Stability: do ties keep their order?

A stable sort keeps items with equal keys in their original order. That enables multi-level sorting: sort students by name, then by grade, and each grade group stays alphabetical. Bubble, insertion and merge sort are stable; quicksort's partitioning can reorder equal items.

      The sorting speed limit

      Can a sort that works by comparing items beat O(n log n)? No. There are n! possible orderings of the input, and each yes/no comparison can at best halve the possibilities, so any comparison sort needs at least log₂(n!) comparisons in the worst case, which grows like n log n. Merge sort already runs at that limit.

      What your language really uses: Timsort and friends

      Built-in sorts are engineered hybrids. Python's sorted and list.sort use Timsort: it finds runs that are already in order, extends short runs with insertion sort, then merges runs merge-sort style. Real data often contains such runs, so Timsort can approach O(n). Java uses a quicksort variant for primitive arrays and Timsort for objects.
