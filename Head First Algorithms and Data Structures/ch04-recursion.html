Thinking Recursively

A recursive function solves a problem by handing a smaller copy of the same problem to itself. Get the base case right and the call stack does the bookkeeping for you.

1

Stacking scoops: meet factorial

Ten new ice cream flavors, all stacked on one cone, and the order matters. How many different cones are there? Any of the 10 can go on the bottom, then any of the remaining 9, then 8... so 10 × 9 × ... × 1 = 3,628,800. That product is the factorial, written n!: the number of orderings (permutations) of n things.

2

A definition that uses itself, safely

Mathematicians define factorial in two lines: 0! = 1, and n! = n × (n−1)!. That looks circular but isn't. A circular definition sends you around forever; a recursive definition always has a base case that stops the process, and a recursive case that moves toward it. Russian nesting dolls work the same way: if the doll won't open, you're done; otherwise open it and repeat on the smaller doll inside.

def factorial(n):
    if n == 0:          # base case
        return 1
    return n * factorial(n - 1)  # recursive case
Two rules for every recursive function1. A base case that answers directly. 2. A recursive case that calls itself on a smaller problem, so it eventually reaches the base case. Miss either and you get an infinite loop of calls.
3

How recursion runs: the call stack

Every function call, recursive or not, pushes a stack frame holding its arguments, local variables and where to return. When it returns, the frame is popped. Recursion just uses the stack heavily: calls pile up while winding down to the base case, then results flow back up as frames pop. Step through factorial(4).

Fibonacci and the exploding call tree

Fibonacci numbers start 0, 1 and each later one is the sum of the two before: 0, 1, 1, 2, 3, 5, 8, 13... The recursive definition is short: fib(0) = 0, fib(1) = 1, fib(n) = fib(n−1) + fib(n−2). But each call makes two calls, and the tree of calls doubles at nearly every level. Hover or tap a node to highlight every other call computing the same value.

When the stack runs out

The stack is a limited slice of memory. Python, for example, stops at about 1,000 nested calls by default. Every recursive call must stay on the stack until its own calls finish, so deep recursion can crash with a recursion-depth error or stack overflow. And plain Fibonacci also burns time recomputing the same subtrees. Drag n to see both problems.

6

Memoization: give the function a notebook

The fix the team lands on: keep a dictionary of answers already worked out. Before computing fib(k), check the notebook; after computing it, write it down. Each value from 0 to n is now computed once, and each costs one addition, so the time drops from about O(2ⁿ) to O(n). The price is O(n) memory for the notebook. That trade of space for time is the seed of dynamic programming in chapter 9.

memo = {}
def fib(n):
    if n in memo:       # already solved?
        return memo[n]
    if n < 2:
        return n
    memo[n] = fib(n-1) + fib(n-2)
    return memo[n]
Notebook after fib(10)
Not always worth itMemoization only helps when the same subproblems recur. When memory is tight or there is little overlap, the notebook costs more than it saves. And recursion's real value is often clarity: trees, mazes and divide-and-conquer read naturally in recursive form.
7

Same word, two meanings

"Factorial time", O(n!), is one of the worst growth classes: algorithms that try every ordering. Computing the value n! is cheap: n multiplications, so O(n). Keep the two apart.

8

Bonus: Fibonacci and the golden ratio

Divide each Fibonacci number by the one before it and the ratios settle on about 1.618, the golden ratio, the proportion seen in shell spirals and sunflower heads.
