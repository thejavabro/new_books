Micro-Storage's route problem

Micro-Storage now has many facilities, and a driver must visit every one exactly once and return home along the shortest total route. It looks like a Dijkstra job, but it isn't: this is not "best path from A to B", it's "best ordering of everything". Every choice reshapes the rest of the route. With n stops there are (n−1)!/2 distinct round trips. Tap cities to build your own route, or let the computer try.

Hard to find, easy to check

Then the team notices something odd. If someone hands you a route and claims "under 8,000 miles", checking it is trivial: add up n distances. Finding the best route is astronomically hard; verifying a proposed one is easy. The same gap shows up in subset sum: from these dishes, can you pick some that total exactly $100? Try it. Checking your pick is one addition per dish.

P, NP and NP-complete

P is the class of problems solvable in polynomial time (O(n), O(n log n), O(n³)...): everything earlier in this book. NP is the class whose proposed solutions can be verified in polynomial time. Every P problem is in NP. The open question, does P = NP?, asks whether everything easy to check is also easy to solve. The hardest problems in NP are NP-complete: Cook (1971) showed satisfiability (SAT) can encode any NP problem, and Karp (1972) linked 21 classic problems by reductions. A fast algorithm for any one of them would give fast algorithms for all. Tap a problem.

Proving P = NP or P ≠ NP carries a million-dollar prize. If P = NP, much of today's cryptography, which relies on some problems being hard, would be in trouble.

4

Beyond slow: problems no program can solve

NP-complete problems are slow, but an algorithm exists. Undecidable problems are different: the question is precise, the answer exists, and yet no algorithm can always find it. Not with infinite time, not with a planet-sized computer. The first one, proven by Alan Turing in 1936, is the halting problem: will a given program, on a given input, ever stop?

Some cases are easy to spot. Others are not. This loop halves even numbers and turns odd n into 3n + 1. Does it reach 1 for every starting number? It has for every number anyone has tried, but nobody has proved it does for all.

Why a perfect halt-checker can't exist

Turing's argument is a proof by contradiction. Step through it.


  
Everything that requires perfectly predicting program behavior inherits the wall: detecting every infinite loop, proving two programs always behave the same, catching every bug or every virus. In general: impossible. In practice, tools solve the easy cases and flag the rest. Your editor's "infinite loop" warning is a partial halt-checker.
