Atomic Variables and Nonblocking Synchronization

Locks make a thread wait. Compare-and-swap lets it try, fail and retry instead. Atomic variables and the nonblocking algorithms built on them are where much of java.util.concurrent gets its speed.

1

The trouble with locks

Much of java.util.concurrent's speed comes not from locks but from atomic variables and nonblocking algorithms. Locks have real downsides under contention:

Suspension is expensiveA thread that loses the race for a lock may be suspended and later resumed: context switches and scheduling delay, often far longer than the work the lock protected.
Waiting threads do nothingWhile one thread holds the lock, others can't make progress. If the holder is delayed (page fault, preemption), everyone is delayed.
Priority inversionA high-priority thread blocked on a lock held by a low-priority one effectively runs at the lower priority.
Too heavy for tiny operationsFor incrementing a counter, a lock is a sledgehammer. volatile is lighter but can't make count++ atomic.
2

Compare-and-swap

Modern processors have an instruction for atomic read-modify-write. Most offer compare-and-swap (CAS): given a memory location V, an expected old value A and a new value B, it sets V to B only if V currently holds A, and reports what V held either way. It is optimistic: proceed hoping nobody interfered, and detect it if they did. A thread that loses a CAS isn't suspended; it learns it lost and can retry, back off or give up.

Try: both read, then both CAS. One wins; the other sees a value it didn't expect and must re-read. No updates lost, nobody blocked.

class CasCounter {
  private final AtomicInteger value = new AtomicInteger();
  int increment() {
    int v;
    do {
      v = value.get();
!!    } while (!value.compareAndSet(v, v + 1));   // retry on interference
    return v + 1;
  }
}

Under low to moderate contention, a CAS-based counter beats a lock-based one handily: an uncontended CAS costs a handful of cycles, and the fast path needs no OS involvement. Java 5 exposed CAS through the atomic classes; the JVM compiles them to the best instruction the hardware has.

3

Atomic variables as better volatiles

There are twelve atomic classes in four groups: scalars (AtomicInteger, AtomicLong, AtomicBoolean, AtomicReference), field updaters, arrays (with volatile semantics per element) and compound ones (AtomicStampedReference, AtomicMarkableReference). Think of them as "better volatiles": same visibility, plus atomic conditional updates.

Remember the NumberRange from chapter 4, whose two AtomicInteger bounds could end up inverted? Put both bounds in one immutable pair and swap it with a single CAS on an AtomicReference:

private final AtomicReference<IntPair> values = new AtomicReference<>(new IntPair(0, 0));

void setLower(int i) {
  while (true) {
    IntPair old = values.get();
    if (i > old.upper) throw new IllegalArgumentException();
    IntPair next = new IntPair(i, old.upper);
!!    if (values.compareAndSet(old, next)) return;   // both bounds, one atomic step
  }
}
4

Performance: locks versus atomics

The book benchmarks a pseudo-random number generator implemented with a ReentrantLock and with an AtomicInteger. At extreme contention (threads do nothing but hammer the shared value) the lock version wins: losers get suspended, which acts as a throttle, while atomics keep retrying and generate more traffic. At realistic contention (threads do some local work between accesses) atomics win clearly. And a version that shares nothing (ThreadLocal seeds) beats both, a reminder that eliminating sharing beats any synchronization. Slide the amount of work between accesses.

Nonblocking algorithms: the Treiber stack

An algorithm is nonblocking if the failure or suspension of any thread can't cause another to fail or stall; it is lock-free if, at each step, some thread makes progress. Nonblocking algorithms are immune to deadlock and priority inversion (though starvation and livelock are possible). The key is to confine each atomic change to a single variable. A stack is the easiest: the only shared state is the top pointer.

void push(E item) {
  Node<E> n = new Node<>(item);
  Node<E> old;
  do {
    old = top.get();
    n.next = old;
!!  } while (!top.compareAndSet(old, n));
}

A nonblocking linked queue

A queue is harder: an insert must update two pointers, the old last node's next and the tail. The Michael-Scott algorithm (used by ConcurrentLinkedQueue) makes the in-between state recognisable and lets any thread finish another's half-done operation. If a thread finds the tail's next isn't null, some insert is midway: it advances the tail for them, then retries its own.

Creating one AtomicReference per node is costly, so ConcurrentLinkedQueue uses atomic field updaters: a reflection-based view that performs CAS on an ordinary volatile field of existing objects.

7

The ABA problem

CAS asks "is V still A?". But what if V changed from A to B and back to A while you weren't looking? For plain numbers it usually doesn't matter. For node pointers in a linked structure with node reuse, it can: the "same" node may now sit in a different place. The fix is to compare a version stamp too. AtomicStampedReference updates a reference and an integer stamp together; AtomicMarkableReference pairs a reference with a boolean (used to mark nodes as deleted).
