Introduction

Threads let one program do many things at once and use every core. They also let two parts of a program trip over the same data. This chapter sets out the deal: benefits, risks, and why you can't avoid threads anyway.

1

From one program to many threads

Early computers ran one program at a time, start to finish. Operating systems then learned to run several processes at once, for three reasons the book names: resource utilization (do something useful while waiting for I/O), fairness (let users and programs share the machine in small time slices) and convenience (several small programs are easier to write than one that does everything).

The same three reasons gave us threads: several streams of control inside one process. Think of making breakfast. You could stand and watch the kettle, or you could start the toast while it boils. Toggle the two styles and watch how long breakfast takes.

2

What a thread owns, and what it shares

Threads are sometimes called lightweight processes, and modern operating systems schedule threads, not processes. Threads in a process share its memory and file handles, so they can exchange data cheaply. That same sharing is the root of every problem in this book. Tap a box to see whether it is private to each thread or shared by all of them.

3

Four benefits of threads

Used well, threads make programs both faster and simpler. The book gives four reasons.

The first one gets more pressing every year. A single-threaded program can run on at most one processor at a time. Slide the core count and see how much of the machine it leaves idle.

4

Risk 1: safety, when value++ is three steps

Here is the book's first warning. A tiny sequence generator hands out the next number with return value++;. It looks like one action. It is really three: read the value, add one, write it back. Two threads can do those steps interleaved and both walk away with the same number.

class Sequence {
  private int value;
  // NOT thread-safe
!!  int next() { return value++; }
}
class SafeSequence {
  private int value;
  // one thread at a time
!!  synchronized int next() { return value++; }
}

5

Safety, liveness, performance

The book sorts everything that can go wrong into three groups. Safety means nothing bad ever happens. Liveness means something good eventually happens. Performance asks whether it happens soon enough. Sort each symptom.

Which hazard is it?

Threads cost something even when correctEvery context switch saves and restores state, spoils CPU caches and spends time in the scheduler instead of your code. Synchronization blocks compiler optimizations and flushes caches. Threads pay for themselves only when the work they enable outweighs these costs.
6

Threads are everywhere, even if you never start one

You can't opt out. The JVM starts threads for garbage collection and finalization, and frameworks call your code from threads you never created. Once a framework calls you from its threads, anything your code touches can be touched from several threads at once. Concurrency spreads: it is rarely possible to confine it to the framework code. Tap each framework to see which thread calls you.

If your code is called from a framework's threads, every piece of state it reaches must be thread-safe.
