Cancellation and Shutdown

Starting threads is easy; stopping them cleanly is not. Java offers no safe way to force a thread to stop, only interruption: a polite request that well-written code agrees to honour.

1

Why stopping is hard

Activities get cancelled for many reasons: the user clicks Cancel, a time limit passes, one of several parallel searches finds the answer, an error occurs, or the application shuts down. Java has no safe way to force a thread to stop. The old Thread.stop and suspend were deprecated because they could leave shared state corrupted. What Java offers is cooperation: code asks, and the task checks and agrees to stop at a safe point.

The simplest approach is a volatile boolean cancelled flag that the task polls. It works for a loop that only computes. But if the task can block, it may never get round to checking the flag. Compare a task that just computes with one that puts results into a full BlockingQueue.

Interruption: the standard cancellation mechanism

Each thread has a boolean interrupted status. Calling interrupt() sets it. That doesn't stop anything by itself; it's a message saying "please stop when convenient". Blocking library methods like sleep, wait and BlockingQueue.put check it, and when set they clear it and throw InterruptedException. Try the calls on a thread.

interrupted = falsethread is running normal code
Careful with the static oneThread.interrupted() returns and clears the current thread's status. If you call it and get true, you must act on it or re-raise it, or the request is lost.

Interruption is usually the most sensible way to implement cancellation. A well-behaved thread has an interruption policy: what it does when interrupted. Tasks don't own the thread they run in (the pool does), so a task should preserve the interrupted status for the owner. That's why library code should either propagate InterruptedException or restore the status with Thread.currentThread().interrupt(). Only code that implements the thread's policy may swallow it. A task that can't be cancelled but calls interruptible methods should save the interruption and restore it just before returning, not right away (that would make it spin).

Because each thread has its own interruption policy, you should not interrupt a thread unless you know what interruption means to that thread.
3

Timed runs and cancelling via Future

Want to run a task for at most N seconds? Don't schedule an interrupt against a borrowed thread. Submit it to an executor and use its Future:

Future<?> task = exec.submit(r);
try {
  task.get(timeout, unit);
} catch (TimeoutException e) {
  // fall through to finally
} catch (ExecutionException e) {
  throw launderThrowable(e.getCause());  // rethrow the real cause
} finally {
!!  task.cancel(true);   // harmless if already done
}

cancel(true) interrupts the task if it is running; cancel(false) only prevents it starting. Standard executor threads have a policy that lets tasks be cancelled by interrupt, so cancel(true) is safe for tasks submitted to them.

4

Blocking that ignores interrupts

Not everything responds to interruption. A thread stuck in classic socket I/O or waiting for an intrinsic lock just sets its status and keeps waiting. To unblock it you need to know why it's blocked. Match each case to its remedy.

How do you unblock it?

You can wrap such nonstandard cancellation in a thread subclass that overrides interrupt() to also close its socket, or, for tasks in a pool, override newTaskFor so that Future.cancel runs your custom cancel logic.

5

Stopping a thread-based service

An application owns a service; the service owns its worker threads. So the service, not the app, should offer lifecycle methods to stop them. The book's example is a logging service: callers put messages on a queue and a background thread writes them out. How do you shut it down without losing messages or leaving callers blocked forever?

A poison pill is another clean way: a special object put on the queue meaning "stop when you get here". Consumers finish everything ahead of it in FIFO order. It only works when the number of producers and consumers is known: each producer sends one pill per consumer, or the consumer waits for one pill per producer.

shutdownNow returns tasks that never started but can't tell you which running tasks were interrupted midway. The book's TrackingExecutor records tasks cancelled after starting, so a web crawler can save its unfinished pages and resume later.

6

Handling abnormal thread termination

When a thread dies from an uncaught exception, the default is to print a stack trace to the console that nobody reads. In a pool, one dead worker can quietly shrink capacity, or in a GUI app freeze everything. Threads that call unknown code (like a pool worker running tasks) should catch RuntimeException in a try/finally and report the failure.

Also set an UncaughtExceptionHandler, through a ThreadFactory for pool threads, to log failures properly. One subtlety: exceptions from tasks run with execute reach the handler; tasks run with submit have their exception captured in the Future and rethrown (wrapped in ExecutionException) by get.

7

JVM shutdown, hooks and daemon threads

The JVM shuts down in an orderly way when the last normal (non-daemon) thread ends, when System.exit is called, or on Ctrl-C. Then it runs registered shutdown hooks concurrently: they must be thread-safe, quick and not depend on services other hooks may already have stopped (the book suggests one hook that shuts things down in order). Abrupt shutdown (Runtime.halt, kill -9) runs nothing.

Daemon threads don't keep the JVM alive. When only daemons are left, the JVM just stops: no finally blocks, no stack unwinding. Fine for housekeeping like expiring cache entries, dangerous for anything doing I/O. Tap a thread to end it and see when the JVM exits.

Avoid finalizersFinalizers run in a JVM-managed thread at an unpredictable time, may never run, cost performance and are hard to write correctly. Use finally blocks and explicit close methods instead.
