Sharing Objects

Locks don't only stop threads colliding; they also make one thread's writes visible to another. Without them, a reader can see stale values, half-built objects, or nothing at all.

1

Visibility: will the other thread ever see it?

Chapter 2 used locks to stop threads colliding. This chapter shows their second, quieter job: making one thread's writes visible to others. Without synchronization there is no guarantee that a reader sees a writer's update in a timely way, or ever. Values can sit in a CPU cache or register, and the compiler and hardware may reorder writes that look independent.

static boolean ready;   // plain fields, no synchronization
static int number;

// reader thread
while (!ready) Thread.yield();
System.out.println(number);

// main thread
number = 42;
ready = true;

This tiny program might print 42. It might print 0, because the write to ready became visible before the write to number. Or it might loop forever, because the reader never sees ready change. Pick a scenario and step through it.

Whenever data is shared across threads, use proper synchronization. Don't try to reason about the order in which memory actions "must" happen.
2

Stale data and torn longs

A reader without synchronization may see stale data: an out-of-date value, and possibly fresh values for some fields and stale ones for others. Java does promise out-of-thin-air safety: a stale value was at least written by someone at some point. Except for one case. Reads and writes of non-volatile long and double may be split into two 32-bit halves, so a reader can see the high half of one write glued to the low half of another.

The fix is the same as for everything else. Locking guarantees that whatever thread A did before releasing a lock is visible to thread B after B takes the same lock. That's why reads need the lock too.

3

Volatile variables: visibility without locking

Marking a field volatile tells the compiler and runtime it is shared: no caching in registers, no reordering with other memory operations around it. A volatile read always sees the most recent write by any thread. Writing a volatile is like leaving a synchronized block; reading one is like entering it. But volatile gives visibility only, not atomicity: count++ on a volatile is still a race.

The typical use is a flag for completion, interruption or status, such as volatile boolean asleep. Tick what's true of your variable to see whether volatile is enough.

4

Publication and escape

Publishing an object makes it available outside its current scope: storing it in a public or static field, returning it, or passing it to a foreign method. An object that is published when it shouldn't be has escaped. Publishing internal state breaks encapsulation; publishing an object before it is fully built can let other threads see it half-made.

A sneaky case is letting this escape from a constructor. Registering a listener built from an inner class, or starting a thread, from the constructor hands out a reference to an object that doesn't exist properly yet. The fix: construct privately, then publish, for example with a factory method.

class Sensor {
  Sensor(EventBus bus) {
    // inner class holds Sensor.this
!!    bus.register(e -> onEvent(e));
    threshold = 10;  // not set yet!
  }
}
class Sensor {
  private Sensor() { threshold = 10; }
  static Sensor create(EventBus bus) {
    Sensor s = new Sensor();
!!    bus.register(e -> s.onEvent(e));
    return s;
  }
}

5

Thread confinement: don't share at all

If only one thread ever touches the data, no synchronization is needed. Swing confines UI objects to the event thread; JDBC pools hand each connection to one thread at a time. The book describes three flavours.

A ThreadLocal is a variable with one value per thread. Ask for it from different threads and each gets its own copy, so a non-thread-safe object such as a date formatter or a connection can be used freely. Press a thread to make it call get() and then mutate its value.

Same ThreadLocal object, three independent values. Treat them like hidden globals: handy, but they add coupling.

Immutable objects can still be used to model changing state: you replace the whole object instead of editing it. That gives a neat fix for chapter 2's cache, where a number and its factors had to change together. Put them in one immutable holder and swap the reference through a volatile field. Every reader sees an old pair or a new pair, never a mix.

final class CacheEntry {
  private final BigInteger n;
  private final BigInteger[] factors;
  // constructor copies the array
  BigInteger[] factorsFor(BigInteger i) {
    return n.equals(i) ? copy(factors) : null;
  }
}
!!private volatile CacheEntry cache;
Make fields final unless they need to be mutable. Final fields guarantee initialization safety and cut down the states you must reason about.

8

Four ways to share an object safely

Whenever you hand out a reference, you need to know what the recipient may do with it. The book ends Part I's sharing rules with four policies; document which one each shared object follows.

Thread-confinedOwned by one thread; only it may read or change the object.
Shared read-onlyAny thread may read without locks, nobody may change it. Immutable and effectively immutable objects.
Shared thread-safeThe object synchronizes internally; use its public interface freely.
GuardedAccess only while holding a specific lock. Includes objects encapsulated inside thread-safe objects.
