Explicit Locks

ReentrantLock is not a replacement for synchronized; it is an alternative for the cases where intrinsic locks are too blunt: timeouts, interruptible waits, fairness and non-nested locking.

1

Lock and ReentrantLock

Java 5 added the Lock interface. ReentrantLock implements it with the same mutual exclusion and memory-visibility guarantees as synchronized, and the same reentrancy. What it adds is flexibility for the cases where intrinsic locking is too limited. The price: you must release it yourself, always in a finally block.

Lock lock = new ReentrantLock();
...
lock.lock();
try {
  // update state, keep invariants
!!} finally {
!!  lock.unlock();   // forget this and it's a ticking bomb
}
Why the finally mattersIf an exception escapes between lock and unlock, an intrinsic lock is released automatically. An explicit lock stays held forever, and the failure shows up far away, when some other thread blocks. That is why ReentrantLock is more dangerous than synchronized.
2

Polled and timed lock acquisition

tryLock() grabs the lock only if it's free; tryLock(timeout, unit) waits at most that long. That gives you a way out of lock-ordering deadlock: if you can't get both locks, release the one you have, back off for a random interval, and try again. Timed locks also fit activities with a time budget: if the lock can't be had in time, fail fast instead of being late. And lockInterruptibly() lets a thread waiting for a lock respond to interruption, which an intrinsic lock wait never does.

3

Non-block-structured locking

Intrinsic locks are released in the same block they were acquired in. Explicit locks needn't be. That enables hand-over-hand locking (lock coupling) on a linked list: hold the lock on the current node, acquire the next node's lock, then release the current one. Different threads can work on different parts of the list at once instead of locking the whole thing.

4

Performance: a moving target

In Java 5, ReentrantLock scaled far better than intrinsic locks under contention. In Java 6 the intrinsic lock implementation borrowed the same algorithm, and the gap almost closed. The lesson the book draws: performance is a moving target. Yesterday's benchmark showing X is faster than Y may already be out of date, so don't pick ReentrantLock for speed alone.

5

Fair and nonfair locks

ReentrantLock can be fair (threads get the lock in the order they asked) or nonfair, the default, which allows barging: a thread that requests the lock just as it becomes free may jump the queue. Why would unfairness be the default? Because waking a suspended thread takes time. In that gap, a running thread can grab the lock, do its work and release it before the woken thread is even ready.

Under heavy contention, the book measured fair locks running roughly two orders of magnitude slower than nonfair ones. Use fairness only when your algorithm needs it. Intrinsic locks give no fairness guarantee either, and that's fine for almost everything.

6

Choosing between synchronized and ReentrantLock

ReentrantLock is an advanced tool for when you need timed, polled or interruptible acquisition, fair queueing, or non-block-structured locking. Otherwise, prefer synchronized.

Intrinsic locks are simpler, impossible to forget to release, familiar, and (in Java 5) showed up in thread dumps with lock details while explicit locks didn't. Future JVM optimizations, such as lock elision, are more likely to target synchronized as well.

Read-write locks

Mutual exclusion is often more than you need. If data is read far more often than written, readers don't interfere with each other at all. A ReadWriteLock has two locks: many threads can hold the read lock at once, or one thread can hold the write lock, never both. Try readers and writers against each kind of lock.

Read-write locks pay off only for read-mostly data on multiprocessors; their bookkeeping makes them slower than a plain lock otherwise. The book wraps a Map with one to build a read-mostly cache, and measures it well ahead of a plain ReentrantLock, though ConcurrentHashMap is usually still the simpler choice for maps.
