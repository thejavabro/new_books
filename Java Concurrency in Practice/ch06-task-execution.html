Task Execution

Most concurrent programs are a stream of independent tasks. The Executor framework separates deciding what to run from deciding how to run it, so the threading policy can change without touching the tasks.

Tasks and their boundaries

Most concurrent applications are organized around tasks: abstract, discrete units of work. Good task boundaries make tasks independent, not depending on each other's state, results or side effects, so they can run in parallel. For servers, the natural boundary is one client request. A web server, a mail server or a file server each handles requests that are mostly unrelated.

2

The Executor framework

The primary abstraction for task execution in Java is not Thread but Executor: a single method, execute(Runnable). It separates task submission from task execution. Code that submits work doesn't care which thread runs it, when, or how many at a time. That decision is the execution policy, chosen in one place and changeable without touching the tasks.

Executor exec = Executors.newFixedThreadPool(100);

while (true) {
  Socket conn = server.accept();
!!  exec.execute(() -> handleRequest(conn));
}
An execution policy answers…In what thread will tasks run? In what order (FIFO, LIFO, priority)? How many concurrently? How many may queue? Which task is rejected under overload, and how is the submitter told? What runs before and after each task?
Whenever you see new Thread(runnable).start() and might want a more flexible execution policy later, use an Executor instead.

The Executors class offers ready-made policies. Pick one and submit tasks.

3

Executor lifecycle and shutdown

An executor's threads keep the JVM alive, so it must be shut down. ExecutorService adds lifecycle methods and three states. shutdown() is graceful: no new tasks, but queued ones finish. shutdownNow() is abrupt: it tries to cancel running tasks and returns the ones never started. After either, submitting throws RejectedExecutionException. awaitTermination waits for the end.

4

Delayed and periodic tasks: drop Timer

Timer runs all its tasks in one thread, so a long task throws off the timing of the others. Worse, if a TimerTask throws an unchecked exception, the Timer thread dies and isn't replaced: later tasks silently never run (thread leakage). Use ScheduledThreadPoolExecutor instead. Finding exploitable parallelism: a page renderer

Within a single request there's often more parallelism to find. A browser renders a page with text and images. The book's renderer goes through three versions. Callable is a task that returns a value or throws; Future represents its lifecycle and lets you get() the result, check it or cancel it.

The limits of heterogeneous tasksSplitting work into two different kinds of task helps only as much as their sizes allow. If rendering text takes 10× less time than downloading images, two threads give at best about 9% speedup. Real gains come from many independent, homogeneous tasks, like one download per image.

CompletionService combines an Executor with a BlockingQueue: submit Callables, then take() Futures in the order they complete. Each image is drawn the moment it arrives.

6

Placing time limits on tasks

Sometimes a late answer is worthless. An ad server or a travel portal must answer within a budget. Future.get(timeout, unit) returns when the result is ready or throws TimeoutException; then you cancel the task and use a default. For many tasks at once, invokeAll(tasks, timeout, unit) returns all the Futures when every task is done or the time is up, cancelling the stragglers. Set the budget for gathering travel quotes.
