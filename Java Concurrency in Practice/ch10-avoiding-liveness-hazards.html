Avoiding Liveness Hazards

Locks keep programs safe, but used carelessly they stop programs moving. Java does not recover from deadlock, so the design has to make it impossible.

1

Deadlock: the dining philosophers

Five philosophers sit at a round table with five chopsticks, one between each pair. To eat, a philosopher needs both neighbouring chopsticks. If each grabs the left one and then waits for the right, all five can end up holding one chopstick and waiting forever. That is deadlock: a cycle of threads, each holding a lock another one needs.

Databases detect deadlock and pick a victim to abort. The JVM does not. Deadlocked Java threads are stuck for good, and whatever they hold is gone with them. Run the table with two strategies.

2

Lock-ordering deadlocks

Two threads that acquire locks A and B in opposite orders can deadlock. The cure is a global rule: if every thread acquires the locks it needs in the same fixed order, there can be no lock-ordering deadlock. Verifying that takes a global view of how locks are used.

Sometimes the order depends on arguments. Transferring money locks the from account and then the to account. If one thread transfers A→B while another transfers B→A, they lock in opposite orders.

Cooperating objects and open calls

  
Lock ordering gets harder when locks are acquired in different classes. The book's example: a Taxi whose synchronized setLocation calls the Dispatcher's synchronized notifyAvailable, while the dispatcher's synchronized getImage calls each taxi's synchronized getLocation. Neither method looks like it takes two locks. Together they deadlock.

  
Calling an alien method while holding a lock is asking for liveness trouble: that method might acquire other locks, or block for a long time.

  
An open call is a call made with no locks held. Shrink synchronized blocks so they guard only the shared state, then make the outward call after leaving them. Programs built with open calls are far easier to analyse for deadlock.

  

    

    

    

  

  
One catch: making a method's call open may make an operation that used to be atomic no longer atomic. Sometimes that's fine; sometimes you need another protocol (for example, marking an object "shutting down" under the lock, then doing the work outside it).






  
4
Resource deadlocks

  
Threads can deadlock on resources as well as locks. If task 1 holds a connection from database pool D1 and waits for one from D2, while task 2 holds D2's last connection and waits for D1's, both wait forever. Bigger pools make it rarer, not impossible. Thread-starvation deadlock from chapter 8 is the same idea: a task waits for a result that needs a thread from the full pool it's sitting in.






  
5
Avoiding and diagnosing deadlocks

  

    
Use few locks at a timeA program that never takes more than one lock at once can't have lock-ordering deadlock. Otherwise, document a lock order and audit for it.

    
Prefer open callsThey reduce the places where multiple locks are held, and make those places obvious.

    
Timed lock attemptsExplicit Lock.tryLock(timeout) (chapter 13) lets you give up, back off, log the near-miss and retry, instead of waiting forever. Intrinsic locks can't do this.

    
Thread dumpsThe JVM can print every thread's stack and the locks it holds and wants (Ctrl-\ on Unix, Ctrl-Break on Windows). HotSpot even detects and reports deadlock cycles.

6
Starvation, poor responsiveness and livelock

  

  
Livelock is a thread that isn't blocked but can't make progress, because it keeps retrying something that keeps failing. It's two polite people in a corridor who both step aside the same way, again and again. The cure is randomness in the retry: Ethernet collision back-off works this way.
