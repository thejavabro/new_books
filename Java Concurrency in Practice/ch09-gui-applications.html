GUI Applications

Every mainstream GUI toolkit is single-threaded on purpose. The trick is to keep all UI work on the event thread and all slow work off it, and to hand results across cleanly.

1

Why GUIs are single-threaded

Nearly every GUI toolkit (Swing, SWT, AWT, the Windows and macOS toolkits) is built as a single-threaded subsystem: all UI work happens on one event dispatch thread (EDT). People tried multithreaded toolkits many times and kept giving up. Two forces doom them:

User input "bubbles up" from the operating system to widgets to application code, while application actions "bubble down" from the app to widgets to the OS. Locks taken in opposite orders are a recipe for deadlock (chapter 10). Model-view-controller makes it worse: controller calls model calls view, while view calls back into model. Confining everything to one thread side-steps all of it, at the price that any slow handler freezes the whole UI.

2

Sequential event processing, felt for real

Events are processed one at a time, in order, each one finishing before the next starts. That makes handlers easy to write, but a long handler blocks everything behind it, including repaints and the Cancel button. A web page's main thread works exactly like Swing's EDT, so this demo is not a simulation: the slow button really blocks this page for two seconds. Click it, then try clicking the counter while it's busy.

Code on the event thread must be short. Anything long-running (computation, I/O, network) belongs in another thread.
3

Thread confinement in Swing

Swing components and data models are not thread-safe; they are confined to the EDT. Code running elsewhere must not touch them. A handful of methods are exceptions and safe from any thread:

SwingUtilities.isEventDispatchThreadAm I on the EDT?
SwingUtilities.invokeLaterSchedule a Runnable to run on the EDT, return at once. Works like a single-thread executor.
invokeAndWaitSame, but block until it has run. Only call it from a non-GUI thread.
repaint, revalidateQueue a repaint or layout request.
Listener add/removeSafe from any thread, though listeners are always called on the EDT.

Short tasks can run entirely on the EDT: a button's action listener updates a model, the model fires events, the view repaints, all in one thread with no synchronization. That's the happy case.

Long-running tasks: off and back again

For a slow task, the handler hands the work to a background executor and returns. When the work finishes, the background thread uses invokeLater to post a completion task back to the EDT, which updates the UI. Cancellation rides on the Future returned by submit: the Cancel button calls future.cancel(true), and the task polls its interrupted status.

The book wraps this in a BackgroundTask class built on FutureTask: subclasses implement compute() in the background, call setProgress, and get onCompletion and onProgress callbacks on the EDT. Java 6's SwingWorker provides the same: doInBackground, publish/process and done.

new SwingWorker<Report, Integer>() {
  protected Report doInBackground() {   // background thread
    for (int i = 0; i < 100; i++) { work(i); setProgress(i); }
    return build();
  }
  protected void done() {               // event thread
    label.setText(get().summary());
  }
}.execute();
5

Shared data models

Data models such as a TableModel are confined to the EDT too. But what if the data lives elsewhere, say a large tree loaded lazily from a remote file system, or updated by a feed? Two approaches:

Thread-safe data modelIf the data structure is thread-safe and not too contended (a ConcurrentHashMap, a copy-on-write list), background threads update it and the EDT reads it. Versioned structures with copy-on-write can serve consistent snapshots.
Split data modelKeep a presentation model confined to the EDT and a separate thread-safe shared model. The shared model registers listeners and pushes either full snapshots or incremental updates to the presentation model via invokeLater.

Consider a split data model when a model must be shared by more than one thread and making it thread-safe is too complex or costly.

Other single-threaded subsystems. The same idea helps whenever a resource is unsafe for concurrent use, like a native library that requires all calls from one thread. Confine it to a dedicated single-thread executor and have everyone else submit tasks to it, getting results through Futures.
