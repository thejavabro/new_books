Composing Objects

You rarely want to reason about every field access in a whole program. This chapter shows how to build thread-safe classes out of smaller pieces so that safety can be checked one class at a time.

1

Designing a thread-safe class

Proving a whole program thread-safe by checking every field access is hopeless. Encapsulation lets you check one class at a time. Designing a thread-safe class comes down to three steps:

1. Find the state variablesThe object's fields, plus the state of objects it owns through those fields. A LinkedList field means the list's nodes are part of your state too.
2. Find the invariantsWhich combinations of values are valid, and which transitions are allowed from one state to the next.
3. Set a synchronization policyDecide how immutability, confinement and locking combine to protect the state, and which lock guards which variables. Then write it down.

Invariants and postconditions shrink the space of valid states. The smaller the space, the easier the reasoning. Take a range with lower and upper bounds and the invariant lower ≤ upper. Drag the bounds.

Because the invariant ties two variables together, they can't be updated independently. Both must be guarded by one lock, and changed in one atomic step. Operations with state-based preconditions (you can't remove from an empty queue) are state-dependent; chapter 5 and 14 show how to make them wait rather than fail.

2

Instance confinement and the Java monitor pattern

A non-thread-safe object can still be used safely if it is encapsulated inside another object, and every path to it holds the outer object's lock. For example, a class can keep people in a private, plain HashSet and expose only synchronized add and contains. The set never escapes, so its own lack of thread safety doesn't matter. Confinement makes it easy to analyse a class without looking at the whole program.

The simplest policy is the Java monitor pattern: encapsulate all mutable state and guard it with the object's own intrinsic lock. Vector and Hashtable work this way. A variation uses a private lock object instead of this.

Delegating thread safety, and when it fails

  
Often a class can hand its thread safety to fields that are already thread-safe. A counter backed by an AtomicLong is thread-safe because its only state is the atomic. A component that keeps keyboard listeners and mouse listeners in two CopyOnWriteArrayLists is thread-safe too: the two lists are independent, with no invariant linking them.

  
Delegation breaks as soon as there is an invariant across the delegated variables. Build the range from two AtomicIntegers, each setter checking the invariant first. Step through two threads updating it at once.

  
class NumberRange {  // NOT thread-safe
  private final AtomicInteger lower = new AtomicInteger(0);
  private final AtomicInteger upper = new AtomicInteger(10);
  void setLower(int i) {
!!    if (i > upper.get()) throw new IllegalArgumentException();
    lower.set(i);
  }
  void setUpper(int i) {
!!    if (i < lower.get()) throw new IllegalArgumentException();
    upper.set(i);
  }
}

If a class has independent thread-safe state variables and no invalid state transitions, it can delegate thread safety to them. Otherwise it needs its own lock.

  
A delegated variable can even be published (made accessible to clients) if it is thread-safe, takes part in no invariants, and has no forbidden transitions. A tracker that stores mutable but thread-safe SafePoints can let callers move a vehicle directly.

Document your synchronization policy

  
Documentation is one of the strongest tools for managing thread safety, and one of the most neglected. Users need to know what thread-safety guarantees they get; maintainers need to know which lock guards which state. Many JDK classes say nothing, leaving people to guess. Is SimpleDateFormat thread-safe? (No, and the docs said so only from JDK 1.4.) Is a JDBC DataSource? The book suggests reading specs from the implementer's point of view, but better still: write it down. Annotations such as @ThreadSafe, @NotThreadSafe and @GuardedBy are a cheap start (see the appendix page).

  

    
@ThreadSafe
public class Inventory {
  @GuardedBy("this")
  private final Map<String,Integer> stock = new HashMap<>();
  // Policy: all access holds this.
  // Clients may lock on an Inventory to
  // make compound actions atomic.
}

    
What to recordWhether the class is thread-safe; which lock guards each mutable field; whether callers may (or must) use client-side locking; whether callbacks occur while a lock is held.
