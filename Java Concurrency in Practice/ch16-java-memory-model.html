The Java Memory Model

Underneath every rule in the book sits the memory model: a contract saying when one thread's writes must be visible to another. Without happens-before, the hardware and compiler may reorder almost anything.

1

What is a memory model, and why care?

When one thread writes x = 3, when will another thread see 3? Without synchronization, possibly late, possibly never. Compilers may keep values in registers or reorder instructions; processors may execute out of order; caches may delay when writes reach main memory. Each processor architecture has its own memory model saying what guarantees you get, and they differ: some are strong, most are weaker, and all provide memory barriers to force ordering.

The Java Memory Model (JMM) papers over the differences. It says exactly when the JVM must make one thread's actions visible to another, and leaves it free to optimize everywhere else. That freedom is why single-threaded Java is fast, and why unsynchronized multithreaded Java is strange.

2

Reordering: the (0, 0) surprise

Two threads, two shared variables, all starting at 0. Thread 1 does a = 1; x = b;. Thread 2 does b = 1; y = a;. Every interleaving of these four statements gives x or y (or both) equal to 1. Yet without synchronization, (0, 0) is allowed: each thread's two actions don't depend on each other, so they can be reordered, or the writes can sit in a buffer the other CPU doesn't see yet.

Reasoning about orderings is hardEven this four-line program has outcomes nobody would predict from the code. That's why the book's advice is to use synchronization correctly and stop reasoning about orderings at all.
3

Happens-before in 500 words or less

The JMM is defined in terms of actions (reads and writes, locks and unlocks, thread start and join) and a partial order over them called happens-before. If action A happens-before B, then B is guaranteed to see A's effects. If two actions on the same variable aren't ordered by happens-before and one is a write, you have a data race, and a program with data races has no useful guarantees. A program without them is correctly synchronized and behaves as if executed in some sequential interleaving.

The monitor rule in action: everything thread A did before releasing lock M is visible to thread B after it acquires M. Step through.

Is the read guaranteed to see the write?

Piggybacking. Because happens-before is transitive, you can sometimes borrow ordering from another synchronization action rather than adding your own. FutureTask does: it writes the result, then does a volatile write of its state; get() reads the state first, so the result is visible. The library uses this too: putting an object into a thread-safe collection happens-before another thread takes it out.

4

Unsafe and safe publication

Unsafe publication is what happens when a reference to a new object becomes visible before the object's fields do. Constructing an object is several writes (fields, then the reference). Without happens-before, another thread may see the reference first, and so see default values in the fields of a "constructed" object.

With the exception of immutable objects, it is not safe to use an object initialized by another thread unless the publication happens-before the consuming thread uses it.

Why double-checked locking breaks

  
Double-checked locking (DCL) tried to avoid synchronizing on every getInstance() call: check without the lock, and only lock if the instance is null. Its flaw: the unsynchronized first check can see a non-null reference to a partly constructed object.

6
Initialization safety and final fields

  
The JMM gives final fields a special guarantee. For a properly constructed object (no this escape), every thread sees the correct values of its final fields, and of anything reachable through them as of the end of construction, however the reference was published, even through a data race. That's what makes immutable objects shareable without synchronization. Non-final fields get no such promise.
