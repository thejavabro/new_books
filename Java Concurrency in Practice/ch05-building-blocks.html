Synchronized collections and their traps

The old synchronized collections, Vector, Hashtable and the Collections.synchronizedXxx wrappers, make each method atomic by locking the whole collection. That is not enough for compound actions like iteration, navigation or put-if-absent. Two methods that look harmless together:

static Object getLast(Vector list) {
  int last = list.size() - 1;
  return list.get(last);
}
static void deleteLast(Vector list) {
  int last = list.size() - 1;
  list.remove(last);
}

Iteration has the same problem. The collections' iterators are fail-fast: if the collection changes during iteration they throw ConcurrentModificationException, on a best-effort basis. Locking the collection for the whole loop fixes it, but blocks everyone else for as long as the loop runs; cloning first costs a copy. Watch out for hidden iterators: toString, hashCode, equals, containsAll, removeAll and copying constructors all iterate. Even logging a set with string concatenation does.

2

Concurrent collections: built for sharing

Java 5 added collections designed for concurrent access. Replacing synchronized collections with concurrent ones can bring dramatic scalability gains at little risk. ConcurrentHashMap doesn't use one lock for the whole map: (in the book's era) it used lock striping, 16 locks each guarding a slice of the buckets, so many readers and a number of writers proceed at once. Its iterators are weakly consistent: they never throw ConcurrentModificationException and may or may not show changes made after they were created. The trade-off: size and isEmpty are only estimates, and you can't lock the whole map for exclusive access.

Since you can't lock it from outside, the compound actions you'd want are built in: putIfAbsent, remove(key, value), replace(key, old, new). For read-heavy lists, CopyOnWriteArrayList copies the backing array on every write, so iteration needs no locking at all. Ideal for event-listener lists: many traversals, few changes.

Blocking queues and producer-consumer

A BlockingQueue adds put, which blocks while the queue is full, and take, which blocks while it's empty. That makes the producer-consumer pattern almost free: producers don't need to know about consumers, and a bounded queue applies back-pressure automatically when consumers fall behind. Unbounded queues just move the problem to your memory. Try it.

producer
consumer

Queues also enable serial thread confinement: a mutable object can be handed from producer to consumer through the queue, and as long as the producer forgets it after handing it over, only one thread owns it at a time. Java 6's Deque supports work stealing: each consumer has its own deque, and an idle one takes work from the tail of someone else's, which keeps contention low.

4

Blocking methods and InterruptedException

A method that throws InterruptedException is a blocking method: it may wait for something (a lock, a sleep, a queue) and will try to stop early if the thread is interrupted. Interruption is cooperative: one thread asks another to stop what it is doing. When your code calls one of these methods, you can't just ignore the exception. You have two good options:

Propagate itDeclare throws InterruptedException and let the caller deal with it, possibly after some cleanup.
Restore the interruptIf you can't throw it (say, inside a Runnable), catch it and call Thread.currentThread().interrupt() so code higher up still sees the request.

Part I in one screen

  
Part I ends with a cheat sheet. Its headline: it's the mutable state, stupid. All concurrency issues come down to coordinating access to mutable state; the less of it, the easier.

  

    
Make fields finalunless they need to change.

    
Immutable is automatically safeShare freely without locks or copies.

    
EncapsulateData within objects keeps invariants local; synchronization within objects keeps the policy local.

    
Guard every mutable variablewith a lock, and all variables in an invariant with the same lock. Hold it for compound actions.

    
No sync, no correctnessA program that touches a shared mutable variable without synchronization is broken. Don't be clever about why it isn't.

    
Design it in, write it downPlan for thread safety, or document that a class isn't safe. Document the synchronization policy.
