State-dependent operations

Some operations have state-based preconditions: you can't take from an empty queue or get the result of an unfinished task. In a single-threaded program, a false precondition is a bug. In a concurrent one, it may become true later, thanks to another thread, so the operation might wait. The best plan is usually to build on a library class (Semaphore, BlockingQueue, CountDownLatch). This chapter is for when none fits.

The book tries three versions of a bounded buffer's take. Compare how they treat a consumer waiting for an item.

Condition queues and the canonical wait

  
A condition queue is a set of threads waiting for some condition to become true. Every object has one, used through wait, notify and notifyAll, and it's tied to the object's intrinsic lock: you must hold the lock to call them. wait() atomically releases the lock and suspends the thread, then reacquires the lock before returning.

  
The thing you wait for is the condition predicate, like "buffer not empty". There's a three-way relationship: the predicate involves state, the state is guarded by a lock, and the lock is the one whose condition queue you wait on.

  

    
// the canonical form of a state-dependent method
void stateDependentMethod() throws InterruptedException {
  synchronized (lock) {           // lock guarding the state
!!    while (!conditionPredicate())  // test, in a loop
      lock.wait();                 // release, sleep, reacquire
    // predicate is true and the lock is held: act
  }
}

    

  

  
Why a while, not an if? Because waking up doesn't mean the predicate is true. One condition queue may serve several predicates; notifyAll wakes everyone; another thread may get the lock first and change the state; and wait may even return spuriously. Step through.

Checklist for condition waitsAlways have a condition predicate. Always test it before calling wait and again after returning. Always wait in a loop. Make sure the predicate's state is guarded by the queue's lock. Hold that lock when calling wait, notify or notifyAll. Don't release the lock between checking the predicate and acting on it.

Missed signals, hijacked signals, notify vs notifyAll

  
A missed signal happens when a thread waits for something that already happened, because it didn't check the predicate first. Notification isn't sticky: a notify with nobody waiting is simply lost. The book's analogy: the toaster pops while you're outside fetching the paper, and you sit down to wait for a bell that already rang.

  
A hijacked signal is subtler. A bounded buffer uses one condition queue for two predicates, "not full" and "not empty". Use single notify, and the JVM may wake a thread waiting for the wrong predicate, which checks, goes back to sleep, and the right thread is never told. Play with a buffer of capacity 1.

Use single notify only when waiters are uniform (one predicate, same logic after waking) and each notification lets at most one thread proceed. Otherwise, notifyAll.

  
notifyAll can be inefficient (a herd of threads wakes, most go back to sleep), so the book also shows conditional notification: only notify when a put moves the buffer from empty to not-empty. It's an optimization: make it work first.






  
4
A recloseable gate, subclass safety and encapsulation

  
A latch can't reopen. The book builds a ThresholdGate with open, close and await. The trick is a generation counter: if the gate opens and quickly closes again, a waiter's predicate ("is it open?") may be false by the time it runs, so the waiter instead checks "is it open, or has the generation changed since I started waiting?"

  
State-dependent classes complicate inheritance: a subclass that changes the state transitions may need to add notifications the base class doesn't know about. Either document the waiting and notification protocol for subclassers, or forbid subclassing (make the class final, or hide the condition queue). Better still, encapsulate the condition queue in a private lock object, so outside code can't wait or notify on it. Think in terms of entry and exit protocols: for each state-dependent operation, what must hold on entry, and what must you notify on exit.






  
5
Explicit Condition objects

  
Intrinsic condition queues have a big flaw: one per lock, so a buffer's "not full" and "not empty" waiters share it. A Lock can create any number of Conditions via newCondition(), each a separate wait set. Their methods are await, signal and signalAll (beware: a Condition is also an Object, so it has wait and notify too, which are the wrong ones). With one predicate per condition, the uniform-waiters rule holds, so signal is safe and efficient.

  
final Lock lock = new ReentrantLock();
final Condition notFull  = lock.newCondition();
final Condition notEmpty = lock.newCondition();

T take() throws InterruptedException {
  lock.lock();
  try {
!!    while (count == 0) notEmpty.await();
    T x = items[head]; /* advance head, count-- */
!!    notFull.signal();          // only producers wake
    return x;
  } finally { lock.unlock(); }
}

  
Conditions also offer fair or nonfair queueing (inherited from the lock), interruptible and uninterruptible waits, and deadline-based waits.

Anatomy of a synchronizer: AbstractQueuedSynchronizer

  
ReentrantLock and Semaphore look alike: both act as gates that let a limited number of threads through. In fact either can be built from the other. Both are built on a common base, AbstractQueuedSynchronizer (AQS), as are CountDownLatch, ReentrantReadWriteLock, SynchronousQueue and FutureTask. AQS handles the hard part, queueing and blocking threads; a synchronizer only defines what its single integer state means and when acquire and release succeed.

  

    
class OneShotLatch {
  private final Sync sync = new Sync();
  public void signal() { sync.releaseShared(0); }
  public void await() throws InterruptedException {
    sync.acquireSharedInterruptibly(0);
  }
  private class Sync extends AbstractQueuedSynchronizer {
    protected int tryAcquireShared(int ignored) {
!!      return getState() == 1 ? 1 : -1;  // open? succeed
    }
    protected boolean tryReleaseShared(int ignored) {
!!      setState(1);                      // open the latch
      return true;                        // let others try
    }
  }
}
