Performance and Scalability

Threads are meant to make things faster. Whether they do depends on how much of the work must run one-at-a-time, and in Java that serial part is usually a lock.

1

Performance is two questions

Threads are meant to make programs faster by using more of the machine. But performance has two sides. How fast is service time and latency for one unit of work. How much is throughput and capacity. Scalability is how throughput grows as you add resources like CPUs. For servers, how much usually matters more than how fast, and the two pull in different directions: a design tuned for single-thread speed (doing everything in one pass) often can't be split up, while a scalable design pays coordination overhead that makes one request slower.

Every performance decision is a trade-off, usually against complexity and safety. The book's advice before optimizing: know what "faster" means for you, under what conditions, with measurements, and whether you're trading away safety for it.

Make it right, then make it fast, and only if your measurements say you must. Measure, don't guess.

Amdahl's law

Some fraction F of almost every computation must run serially (taking a task off a shared queue, combining results). Amdahl's law caps the speedup on N processors:

Speedup ≤ 1 / (F + (1 − F) / N)As N grows without limit, speedup approaches 1/F. Ten percent serial means at most 10×, however many CPUs you buy.

What threads cost

Contention is what hurts. Uncontended synchronization is cheap and getting cheaper: the JVM can remove locks on objects that never escape a thread (escape analysis), merge adjacent locks (lock coarsening), and skip locks it can prove are thread-local. Don't worry much about uncontended synchronization. Worry about contended locks, which serialize threads and make them block.

Reducing lock contention

The main threat to scalability in concurrent Java code is the exclusive resource lock. Contention depends on two things: how often the lock is requested and how long it is held. There are three ways to reduce it: hold locks for less time, request them less often, or replace exclusive locks with something that allows more concurrency. Pick a technique and see how throughput scales in a simple model.


    

    

  

  
Avoid hot fieldsA cached element count looks like a nice optimization for a single-threaded map. In a concurrent one, every insert and remove must update it, making it a hot field that serializes everything again. ConcurrentHashMap instead keeps a count per stripe and adds them up when asked.

Just say no to object pooling

  
In early JVMs, allocation was slow, so people pooled objects. Today, allocation is extremely fast (roughly ten instructions on the common path) and garbage collection of short-lived objects is cheap. In concurrent code, pooling is worse than useless: the pool itself needs synchronization, which creates contention that's far more expensive than an allocation. Allocating is usually cheaper than synchronizing. Only very expensive objects (threads, connections) are worth pooling.

Example: comparing map performance

  
The book benchmarks a read-mostly workload: single-threaded, ConcurrentHashMap and a synchronizedMap perform about the same. As soon as several threads compete, the synchronized map's throughput collapses (each operation takes the single lock, and contended locks cost context switches), while the concurrent map's throughput keeps rising with the thread count. Reducing context switches. Many tasks block briefly for I/O or locks, and each block costs a context switch. Moving the blocking into one dedicated thread helps: a logger that writes to disk from every request thread causes contention on the output stream; a logger that queues messages for one background writer keeps request threads running. Fewer switches, shorter service time.
