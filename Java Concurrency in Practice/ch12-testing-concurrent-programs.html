Testing Concurrent Programs

Concurrency bugs are rare, timing-dependent and shy: the test harness itself can hide them. This chapter shows how to write tests that actually shake them out and benchmarks that measure what you think.

1

Two kinds of property, two kinds of test

Concurrent programs have a degree of nondeterminism sequential ones don't, so the space of things that can go wrong is much bigger, and failures are rare, timing-dependent and hard to reproduce. Tests fall into the same two groups as the hazards: safety ("nothing bad ever happens", usually checked as invariants) and liveness ("something good eventually happens": progress, plus performance properties like throughput, responsiveness and scalability).

The book's running example is a BoundedBuffer built from two semaphores: one counts free slots, one counts items. Start with the boring tests (a new buffer is empty, a buffer filled to capacity is full). They catch the easy bugs, so later failures can be blamed on concurrency.

The test can hide the bugAny synchronization or timing a test adds can mask the very race it is looking for. Test code should add as little coordination as possible, and what it adds should be justified.
2

Testing that something blocks

How do you test that take() on an empty buffer blocks? Success means the method doesn't return. The book's recipe uses interruption: start a thread that calls take() (which should block), wait a bit, interrupt it, and check that it ended with InterruptedException in a timely way.

void testTakeBlocksWhenEmpty() throws Exception {
  BoundedBuffer<Integer> bb = new BoundedBuffer<>(10);
  Thread taker = new Thread(() -> {
    try {
      bb.take();
!!      fail("take returned on an empty buffer");
    } catch (InterruptedException ok) { }
  });
  taker.start();
  Thread.sleep(LOCKUP_DETECT_TIMEOUT);
  taker.interrupt();
  taker.join(LOCKUP_DETECT_TIMEOUT);
!!  assertFalse(taker.isAlive());
}

Testing safety under load

To catch races you need many threads doing many operations, then a check that doesn't itself need heavy synchronization. The book's PutTakeTest: producers put random numbers in, consumers take them out, and each side keeps a checksum (sum) in thread-local variables, combined only at the end. If the buffer drops or duplicates an element, the sums won't match. The random numbers come from a cheap generator computed in-thread, so the test doesn't serialize on a shared Random.

Two more tricks make such tests effective. Use a start gate (a latch or CyclicBarrier) so threads begin at the same instant instead of the first finishing before the last is even created. And run more active threads than CPUs, so that the scheduler interleaves them at more places.

4

Generating more interleavings

A race window may be a few instructions wide; a test might pass millions of times. Ways to tilt the odds: run on a multiprocessor (and with more threads than CPUs), run on several kinds of hardware and JVM, and add Thread.yield() or short sleeps in critical spots during testing to provoke context switches there. The book suggests guarding these hooks so they cost nothing in production.

Testing resource management and callbacks. Heap snapshots before and after a test reveal leaks such as a buffer that keeps references to taken elements. Callbacks are natural test hooks: a ThreadFactory that counts the threads it makes lets you test that a pool grows to its maximum and no further.

5

Testing performance

Performance tests measure end-to-end throughput or latency under realistic use. Extending PutTakeTest with a barrier action that records the time when all threads arrive gives a timer that doesn't distort the test. Plotting throughput against thread count and buffer size, and comparing LinkedBlockingQueue, ArrayBlockingQueue and the semaphore buffer, shows how much tuning matters. For responsiveness, look at the variance of service time, not just the mean: a fair lock or semaphore gives lower variance but much lower throughput.

6

Why Java microbenchmarks lie

A naive timing loop in Java can measure the wrong thing entirely. Toggle each pitfall on and watch a pretend timing graph change.

Unrealistic code pathsThe JIT optimizes for what it has seen. A test that exercises only one path may get code that is faster than real runs, or deoptimized code when you switch.
Unrealistic contentionReal tasks do work between accessing shared data. A test that does nothing but take locks measures maximal contention, which may or may not resemble production.
7

Code review, static analysis and tools

No amount of testing finds all concurrency bugs. Combine tests with code review by someone who knows concurrency, static analysis (the book praises FindBugs, which flags patterns like inconsistent synchronization, calling Thread.run, unreleased locks, empty synchronized blocks, double-checked locking, starting threads in constructors, notify mistakes, waiting outside a loop, sleeping while holding a lock, and spin loops), aspect-oriented instrumentation, and profilers that show lock contention and thread states.
