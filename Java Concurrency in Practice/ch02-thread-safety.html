Thread Safety

Thread safety is not about threads, it is about state: shared, mutable state. A class is thread-safe when it stays correct no matter how threads interleave, with no extra effort from callers.

1

Thread safety is about state

Writing thread-safe code is, at its core, about managing access to state, and in particular to shared, mutable state. An object's state is the data in its fields (and in the objects those fields point to). Shared means more than one thread can reach it. Mutable means it can change. Take away either word and the problem disappears.

If several threads use the same mutable variable without proper synchronization, the program is broken, even if it has passed every test for years. The book lists exactly three ways out. Tap each.


    

  

  
It is far easier to design a class to be thread-safe than to retrofit it later. Encapsulation, immutability and clearly stated invariants are your best friends.






  
2
What does thread-safe mean?

  
Most definitions found online are circular ("safe to use from many threads"). The book anchors it in correctness: a class is correct if it keeps its invariants (rules about valid states) and meets its postconditions (what each operation promises). Then:

  
Thread-safe classOne that keeps behaving correctly when used from several threads, whatever the scheduling or interleaving, and without callers adding their own synchronization.

  
The simplest thread-safe object has no state at all. A servlet that reads a number from the request, factors it into local variables and writes the answer back shares nothing between requests: each thread's locals live on its own stack. Stateless objects are always thread-safe.

Race conditions: getting the right answer by luck

  
A race condition happens when correctness depends on the relative timing of threads. The book names two common shapes:

  

    
Read-modify-write
Read a value, compute a new one from it, write it back. Another thread can change the value in between, as with count++.

    
Check-then-act
Observe something ("file doesn't exist", "instance is null"), then act on that observation. The observation can go stale before you act.

  

  
Lazy initialization is the classic check-then-act. Two threads can both see null and both build an instance; callers who expected one shared object get two.

  
class LazyHolder {
  private Expensive instance = null;
  Expensive get() {
!!    if (instance == null)            // check
!!      instance = new Expensive();    // then act
    return instance;
  }
}

Compound actions and atomic variables

  
An action is atomic if, to every other thread, it has either happened completely or not at all. Check-then-act and read-modify-write are compound actions: to be safe they must run atomically. For one counter, java.util.concurrent.atomic does it for you: AtomicLong.incrementAndGet() is a single atomic step.

  
class CountingService {
  private final AtomicLong count = new AtomicLong();
  void handle(Request r) {
    // ... do the work ...
!!    count.incrementAndGet();
  }
}

  
But atomic pieces don't add up to an atomic whole. Suppose a service caches the last number and its factors in two AtomicReferences. Each set is atomic, yet the pair is supposed to agree: the factors must belong to the number. Step through what a reader can see.

Intrinsic locks and reentrancy

  
Every Java object can act as a lock. A synchronized block names a lock object and a body; a synchronized method uses this (or the Class object, for static methods). These intrinsic locks (or monitor locks) are mutexes: at most one thread holds one at a time. A thread acquires the lock on entry and releases it on exit, even if the block throws.

  

    

    

  

  
Intrinsic locks are reentrant: a thread that already holds a lock can acquire it again. The JVM keeps an owner and a hold count. Without reentrancy, a subclass whose synchronized method calls super's synchronized method would deadlock on itself.

  

    
class Widget {
  synchronized void doWork() { ... }
}
class LoggingWidget extends Widget {
  synchronized void doWork() {
    log("calling doWork");
!!    super.doWork(); // same lock: this
  }
}

Guarding state with locks

  
A lock only protects data if every access to that data, reads included, holds the same lock. Synchronizing the writes and leaving reads bare protects nothing. There is no magic link between an object's lock and its fields; it is purely a convention you must follow everywhere.

  

    
One variable, one lockFor each mutable variable reached by more than one thread, all accesses must hold the same lock. That variable is then guarded by that lock.

    
One invariant, one lockWhen several variables take part in an invariant, all of them must be guarded by the same lock.

    
Say who guards whatMake it clear to maintainers which lock guards each field, for example with @GuardedBy("this").

    
Not a cure-allMaking every method synchronized doesn't make compound actions like if (!v.contains(x)) v.add(x) atomic.

  






  
7
Liveness and performance: lock as little as you can

  
The quickest fix for a caching factorizer is to make its whole service method synchronized. That's safe, but now only one request can be factored at a time, however many CPUs you have. Better: keep the slow factoring outside the lock and synchronize only the short sections that touch shared fields. Compare the two with six requests on four cores.

  

    

    

    

  

  
Two cautionsDon't split blocks so finely that a compound action is broken up. And never hold a lock during lengthy computation or anything that might block, such as network or console I/O. Simplicity comes first: resist trading safety for speed you haven't measured.
