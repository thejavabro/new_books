Greedy Iterative Pretty Printing

How does an editor decide where to break your long line of code? A doc tree of text, line breaks and groups, plus a greedy "does it fit?" rule, produces tidy layouts in linear time.

1

Turning a parse tree back into pretty text

C-family languages don't care about whitespace, so teams agree on one automatic formatter and never reformat files for any other reason. How do those pretty printers decide where to break lines? After a lexer and parser produce a parse tree, the printer must turn the tree back into text, balancing three goals, usually in this order:

1. Stay within the widthNo line beyond 80 or 100 characters unless unavoidable.
2. Show structureIndentation helps the reader see what belongs to what.
3. Save vertical spaceUse as few line breaks as possible.

Real languages add misery: end-of-line comments in the middle of an expression, or which token a /* comment */ sticks to when a line splits (a real problem on the C# compiler and IDE). The chapter simplifies: no comments, spaces and line breaks only, indentation fixed at four spaces, and no required line breaks, so it formats expressions.

2

Greedy: locally best, usually good enough

A greedy algorithm makes the best choice for each small piece and never reconsiders. Making change is the classic case: hand back the biggest coin that fits, repeat. With US coins it is always optimal… until the till runs out of nickels. Compare with the true optimum (found here by dynamic programming; chapter 8's backtracking would also do).

Greedy
Optimal

A pretty printer runs as you type in an IDE, so a fast, greedy "fit as much on this line as you can" beats a slow optimal layout that wouldn't look noticeably better. The algorithm here is a simplified form of Christian Lindig's Strictly Pretty (2000), from Philip Wadler's A Prettier Printer (1998), going back to Derek Oppen (1980); Wadler was also inspired by John Hughes, of Hughes-list fame.

3

Phase 1's output: a doc

Phase 1 turns the parse tree into a doc: an immutable graph that states formatting wishes. Phase 2 turns the doc into text. Five node kinds are enough:

// Foo.Bar(xx + yy * zz) with these rules: may break before ".", after "(";
// operators keep company with their left operand; never break before ")"
BinOp(l, op, r) = Group(Indent(Group(l + Space + op) + Space + r))
member  = Group(Foo + Indent(Group(OptBreak + "." + Bar)))
args    = Group(Indent("(" + OptBreak + BinOp(xx, "+", BinOp(yy, "*", zz)) + ")"))
call    = Group(member + args)
The design lesson"The most important thing I know about software design": build a small library whose programs read like the concepts of the domain. A handful of factory methods and an overloaded + make formatting rules short, readable and easy to experiment with.
4

Docs are deep, so avoid recursion

Groups and indents have one child each, so docs grow deep, not wide: the 21-character example above is 17 levels deep. Format a big file recursively and you risk a stack overflow on a fixed-size call stack. So both phase-2 methods use an explicit Stack of work items instead. 5

Fits(width) with a work stack

"Would this doc fit in width characters if none of its breaks became newlines?" Pop a doc: text and optional breaks add their length; groups and indents push their child; a concat pushes right then left (so left is processed first). Stop as soon as the count exceeds the width, or the stack empties. The stack can never hold more items than there are concats. Step through Fits(13) on the argument group.

6

Pretty(width): try it live

Pretty keeps a stack of (fits?, indent, doc) triples. A group asks Fits(width − used) of its contents and passes the answer down; every optional break directly governed by a group that didn't fit becomes a newline plus the current indentation; indent nodes add four spaces for their descendants. Wrap the whole doc in a group first so every break has one. Type an expression (identifiers, ., calls, parentheses, + and *) and drag the width.

Why the last line can overflowWith Foo.Bar(xx + yy * zz) at width 15, the last line comes out 16 wide. Not a bug: "yy * zz" fit in the space left, the greedy printer took it, and the rule "never break before )" left the parenthesis nowhere else to go. Good enough is good enough. The whole pass is about O(n) in the size of the doc.
7

Phase 1: the visitor pattern

Where should "parse tree → doc" code live? A virtual ToDoc() on every node class means the editor team edits the compiler team's code (Conway's law), every new style (Alice's, Bob's) adds yet more methods, and so does every other analysis: coloring, linting, type checking, code generation. The visitor pattern puts each concern in its own class. Each node gets one boilerplate method, Accept(visitor) => visitor.Visit(this), and that's the only change ever made to the tree.
