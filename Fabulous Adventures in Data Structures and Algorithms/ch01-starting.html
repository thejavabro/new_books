Starting a Fabulous Adventure

An algorithm is a way to solve a problem and a data structure is a way to organize data. This opening chapter sets up the vocabulary of complexity and warms up with the humblest structure of all: an immutable linked list.

What this book is after

Undergraduate courses already cover balancing trees, sorting arrays and building priority queues, and class libraries already ship them. This book goes off the beaten path: structures and algorithms the author had to learn on the job, usually from research papers, because no ready-made solution existed. The picks are the ones that are counterintuitive, look like magic, push a language to its limits, or change how you think.

Data structure, algorithm, complexity

Data structureA way to store information in an organized form: arrays, classes, records and interfaces arranged so the operations you need are cheap.
AlgorithmA finite sequence of steps that solves a problem. It may flip coins, and need not run on a computer. (The word honours the 9th-century mathematician al-Khwarizmi.)
ComplexityHow the cost of solving a problem grows with its size. Cost can be time, memory or any other resource you care about.

The usual language for complexity is big O notation. Pick a class below, then drag the slider to grow the problem and watch how quickly each curve runs away.

The doubling test

A handy way to feel the difference: what happens to the cost when the problem doubles? Logarithmic algorithms barely notice, linear ones double, quadratic ones quadruple, and exponential ones square their cost. Press the button a few times.

Bars are on a log scale so all of them fit; the numbers are the actual relative costs.

Cost is not only timeMemory, handles and other resources count too, and there are many kinds of time: best case, average case and worst case can tell very different stories. A good analysis names which cost it is talking about, and which size: some tree algorithms are linear in the height, not the node count.
4

Better asymptotics is not always better

As an intern, the author spotted a string-search routine with an O(n²) worst case and asked why it didn't use a known linear method. The answer: its users searched for commas in short strings, and on those the simple loop is blazingly fast. Asymptotic growth only matters when problems get big. Adjust the constant factors and see where the curves cross.

5

An immutable linked list

The warmup: a linked list is either empty, or a value followed by a tail list. Make it immutable, so "pushing" never changes an existing list; it makes a new node pointing at the old one. Every old version is still valid and shares its nodes with the new ones.

sealed record Node<T>(T Value, Node<T>? Tail);
// push is O(1): one new node, the old list is untouched
var a = new Node<int>(10, null);
var b = new Node<int>(20, a);   // 20 → 10
var c = new Node<int>(30, a);   // 30 → 10, shares node a with b

Design choices hiding in a few linesRepresenting "empty" as a null reference is awkward in an object-oriented language: you want an empty list to be a real object you can call methods on. The chapter's first draft uses a special node with a null value and tail, which still lets you build malformed lists. Chapter 2 fixes this with a separate empty class.

Hidden costs in innocent code

Even tiny types hide performance traps, especially in code the compiler writes for you.

Accidentally quadratic ToString

characters copied

Appending to an immutable string copies everything so far. Build an n-item string the naive way and the copies add up to roughly n²/2 items; a string builder copies each item about once.

7

Reversing an immutable list

The famous interview question, "reverse a linked list", becomes almost trivial when the list is immutable: walk the list and push each value onto a new, initially empty list. The original is never touched, so nothing can go wrong for anyone else holding it. O(n) time and O(n) extra memory.

static Node<T>? Reverse<T>(Node<T>? list) {
  Node<T>? result = null;
  for (var n = list; n != null; n = n.Tail)
    result = new Node<T>(n.Value, result);   // push
  return result;
}
The interview that went sidewaysThe preface tells how the author answered this question in 1996 with an immutable list in four lines, and was told he was wrong: the interviewer expected in-place pointer surgery in C. Same words, different question. The lesson: what is in your toolbox shapes which problems look easy.
