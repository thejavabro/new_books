Immutable Stacks and Queues

Data that never changes sounds like a limitation. It turns out to be a superpower: correctness, free history, cheap sharing, painless undo, and one very strange list that holds no data at all.

1

Why prefer data that cannot change?

If two structures do the same job but one cannot be modified, why choose the one with fewer features? Because the restriction buys a lot. The deepest reason: any fact you deduce about an immutable object stays true forever. On the C# compiler team, a common bug class was caching a fact, mutating the program tree so the fact went stale, then trusting it later. The Roslyn rewrite leaned on immutable structures and whole classes of such bugs disappeared.

2

A security story: time of check, time of use

Low-trust code hands a resource name to high-trust code, which checks permission and then uses the name. If the name object is mutable, a second hostile thread can flip it between a permitted and a forbidden name, and sooner or later the flip lands between the check and the use. An immutable stack, designed properly

Start from the abstract data type, not the mechanism: what can users do with a stack? Create one, push, peek, pop, ask if it is empty, and enumerate it. Only push and pop mutate a normal stack, so in the immutable version those two return a new stack instead.

interface IImStack<T> : IEnumerable<T> {
  IImStack<T> Push(T item);
  T Peek();
  IImStack<T> Pop();
  bool IsEmpty { get; }
}

Two classes, one interface. A singleton Empty stack that throws on Peek and Pop, and a non-empty node holding an item and a tail. Constructors are private: the only way to get a stack is to start from Empty and push. No null anywhere, so nothing to dereference by mistake (the null object pattern).

O(1)Push, Peek, Pop, IsEmpty
O(n)enumerating n items, with O(1) extra memory
Sharedstacks with the same tail share it; nothing is copied
4

Immutability makes covariance safe

A giraffe is an animal, but is a list of tigers a list of animals? If it were, you could add a giraffe to it through the animal-typed reference, and a tiger variable could end up holding a giraffe. Mutability prevents covariance. Read-only sequences are safe. An immutable stack ought to be safe too, except Push(T) takes T as input. The trick: move Push out of the interface into an extension method, mark the interface out T, and pushing a giraffe onto a stack of tigers simply yields a stack of animals.

A queue made from two stacks

A stack is cheap at one end; a queue needs two cheap ends. So use two stacks: enqueue pushes onto the back stack, dequeue pops from the front stack, and when the front stack runs dry, reverse the back stack to become the new front. One invariant keeps the code small: a non-empty queue always has a non-empty front stack. Try it, and watch the cost of each operation.

Amortized O(1)Follow one item: pushed onto the back stack, popped off it during a reversal, pushed onto the front stack, popped by dequeue. Four constant-time steps per item, so the average cost is constant even though one dequeue after a million enqueues does a million steps. Whether that occasional pause is acceptable depends on the user.

Undo and redo for free

Undo for a queue is surprisingly awkward: dequeuing does not undo an enqueue. The book weighs three designs.

The third design is a mutable wrapper over an immutable value: a class with one private field pointing at the current immutable queue. Every operation replaces the field. Undo and redo stacks simply hold old queue values, and persistence means each snapshot costs O(1) extra memory on average.

Each box in the undo and redo stacks is a whole queue value. They share nodes, so this is cheap.

The flaw in the amortization argumentEnqueue 100 items, dequeue (reversing 99), undo, dequeue again, undo… Each dequeue repeats the expensive reversal, so the cost is never spread out. Options: don't worry if it never happens in practice, use a structure with a better worst case (chapter 3), or memoize the reversal (chapter 4). A nice bonus the other way round: redo of an expensive operation is free, because the result is already stored.
7

Currying, and a very odd way to store a number

Any two-argument function can be split into a function that takes the first argument and returns a function waiting for the second. That is currying; fixing the first argument is partial application. Off-label use: add(n) "stores" n, and calling the result with 0 gets n back out.

Func<int, Func<int, int>> add = x => y => x + y;
var box = add(123);   // a function that "holds" 123
box(0);                // 123: zero is the "give it back" argument

The Hughes list does exactly this with stacks: a list is stored as "the function that concatenates me onto whatever you pass", and the empty stack plays the role of zero.

8

The Hughes list: build it cheap, pay later

John Hughes' difference list holds a single field: a delegate stack ⇒ myItems ++ stack. Empty is the identity function. Push, Append and Concatenate just build a new delegate that calls the old ones, so they are all O(1) no matter how big the list. The bill arrives when you Peek or Pop: you must call the delegate with the empty stack, which runs every deferred concatenation, O(n).

Empty        = s => s
Single(x)    = s => s.Push(x)
Concat(a, b) = s => a(b(s))        // O(1) to build
ToStack()    = this(ImStack.Empty) // O(n) to run

Where is the data?In the closures. When a lambda captures a and b, the compiler generates a class with fields for them, so every Concat delegate is secretly a binary tree node with left and right children, and Single delegates are leaves holding one item. The drawing above is that hidden tree. Running it is a recursive traversal, which also means a list built from thousands of pushes can overflow the call stack.
