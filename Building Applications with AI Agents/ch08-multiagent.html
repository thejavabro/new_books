From One Agent to Many

One agent with fifty tools gets confused. Several focused agents need a way to divide work, talk to each other and agree. This chapter weighs the trade.

1

Start with one agent; split when tools pile up

Begin simple and add complexity only when it improves results. A single agent is easier to build and run, cheaper and faster. The book's supply-chain agent shows the limit: with 16 tools in one prompt, the model has to weigh every option on every request and starts choosing poorly. Grouping tools under specialists fixes that. Drag the tool count (illustrative curves).

2

A supervisor routes to specialists

The multiagent version keeps the same tools but gives them to three specialists: inventory, transportation and supplier. A supervisor reads each request and routes it, without the overhead of full consensus. Each specialist sees only its own handful of tools.

What you gainFocused prompts, specialization, parallel work, and adaptability: a disruption such as a storm can be rerouted to the specialist who handles it.
What it costsCoordination logic, more model calls and tokens, harder debugging, and new failure modes such as a misrouted request.
3

Swarms: simple rules, emergent behavior

Swarms borrow from flocks, schools and ant colonies: many simple agents follow local rules, with no central controller, and useful collective behavior emerges. They scale to thousands, have no single point of failure and adapt on the fly. The price is predictability and observability. Each dot below only looks at its neighbors.

Rules: steer toward nearby agents, match their direction, avoid crowding. Remove agents and the flock carries on.

Actor-critic: generate until the critic approves

An actor drafts; a critic scores the draft against a clear rubric and sends back feedback; the loop repeats until the score clears a threshold or a retry cap. It works best when judging is easier than generating. Here the actor drafts a supplier email.

7

Letting agents design agents

Automated Design of Agentic Systems treats agent designs as code that a meta-agent writes. Its search loop keeps an archive of prior agents, proposes a new design, implements it as a function, evaluates it on tasks and adds it to the archive. Designs found this way tended to transfer well to new domains and models. The book notes that running generated code demands sandboxing and ethical care.

8

Agent-to-Agent protocol

In one process, agents talk by function calls or in-memory queues. Across services they need a protocol. A2A has each agent publish an Agent Card, a JSON description of identity, skills, endpoint and auth, often at a well-known URL. Others discover it through a registry, check compatibility, then delegate tasks. It is promising and young: security and the spec are still evolving.

9

Message brokers decouple agents

Point-to-point calls get brittle as systems grow. A message broker lets the supervisor publish events to topics; specialists consume them when ready. You get loose coupling, scaling by adding consumers, logging and replay of missed messages, at the price of eventual consistency. Kafka suits high throughput; Redis Streams and RabbitMQ are lighter; NATS is a low-latency cloud-native option.

10

Actors and durable workflows

Actor frameworks (Ray, Orleans, Akka) bundle each agent's state and message handling into one addressable unit that processes messages one at a time, scales out and recovers. Worth the infrastructure once you have more than a few agents or per-session memory. Workflow engines (Temporal, Airflow, Dagger) add durable sequencing, retries and dependency tracking for flows that call unreliable models, APIs or humans and may run for hours.
