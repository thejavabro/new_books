Validation and Measurement

You cannot improve what you cannot measure. Build a test set of realistic tasks, score the final answer and the path taken, and run it on every change.

1

Measurement is the keystone

Building agents has never been easier; knowing whether they work is the hard part. The chapter follows one support agent through one case (a customer reports a cracked coffee mug and wants a refund) and builds a measurement practice around it. First lesson: for language, exact match is the wrong metric, because correct answers come in many forms. Pick an agent reply.

Reference reply: "I've issued a full refund of $19.99 to your original payment method."

2

Anatomy of an evaluation case

A good case defines the input state and the expected outcome, so scoring can be automatic. One case tests several things at once: did the agent ask for evidence, call the right tool, use the right parameters, say the right things? Click the highlighted parts.

Collections of such cases become a living specification: what the agent must handle, versioned and rerun on every change, so regressions show up before users see them.

3

Unit-test the parts: tools, planning, memory, learning

Tools get ordinary automated tests: deterministic outputs for the same inputs, edge cases, the full suite rerun after every change. Planning is scored by comparing the calls the agent made against the expected ones. Toggle what the agent actually called for the mug case and watch the three planning metrics.

4

Same input, many runs

Models are probabilistic, so one good run proves little. Consistency testing reruns the same case and checks the outcome stays aligned: the mug refund should always go to the right order for the right amount. Raise the randomness of this simulated agent and rerun.

5

Unexpected and hostile inputs

Real users send typos, empty messages, emoji, other languages and attacks. Integration tests should cover deliberate edge cases as well as random fuzzing. Pick an input to see what a robust agent should do.

6

Quality gates before deployment

Set explicit release criteria, for example at least 95% tool recall on refund and cancellation cases, and enforce them automatically: a candidate that misses a gate does not ship. Then roll out gradually, watch for regressions and keep rollback ready. Adjust the gates and see whether version 2.3 ships.
