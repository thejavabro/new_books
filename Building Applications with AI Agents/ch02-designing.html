1

Start with one narrow, boring job

The chapter opens without a grand design document. It picks a real, repetitive job: a support team reads emails asking to refund a broken mug, cancel an unshipped order or change an address, looks the order up, calls the right backend API and types a confirmation. Two minutes each, hundreds a day. The agent gets the message plus the order record, chooses one of a few tools, fills in the arguments and writes the confirmation.

The shape of the code is small. Here is a framework-free sketch of the same idea (the book builds it with LangGraph):

TOOLS = {"cancel_order": cancel_order, "issue_refund": issue_refund}

def handle(ticket, order):
    msgs = [system("You are a support agent. Use a tool if needed."),
            user(ticket), context(order)]
    first = model(msgs, tools=TOOLS)          # pass 1: tool call or reply
    if first.tool_call:
        result = TOOLS[first.tool_call.name](**first.tool_call.args)
        msgs += [first, tool_result(result)]
        return model(msgs)                    # pass 2: confirmation text
    return first
Why a narrow slice worksConcrete inputs, structured outputs, and a tight feedback loop. You can see exactly what the agent did, and test it.
2

Ask three questions of every run

Running is not the same as working. For the cancel-order agent, check: did it call the right tool? With the right parameters? Did it send a clear confirmation? Because tool calls are structured, these checks are plain assertions, and they add up to metrics like tool recall and parameter accuracy. Inject a bug and watch the scores.

3

The four core components

Every agent system combines a model that reasons, tools that act, memory that keeps context, and orchestration that strings actions into a plan. Click a box to see its job.

4

Model choice is price per performance

Selection starts with task complexity: open-ended reasoning wants a large model; narrow, repetitive work (classification, extraction) often runs fine on a small one. Then come modality, openness (open weights you can host and tune versus hosted APIs), domain specificity, and above all cost and latency. The book's table of large models makes the point: quality varies a little, price varies a lot.

Data points are the MMLU scores and relative prices listed in the book at publication; they change quickly. The lesson does not: measure on your task and pick the best value, and revisit the choice as models evolve. Small open-weight models (8 to 14 billion parameters) fit on a single gaming GPU and get you moderate performance at a fraction of the cost.

5

Three kinds of tools

Tools are the capabilities an agent can use. They are designed around the job, and kept modular so each can be built, tested and replaced on its own.

6

Short-term and long-term memory

Short-term memory holds the current conversation, usually as a rolling window: new turns push old ones out. Long-term memory lives outside the model, in databases, knowledge graphs or fine-tuned weights, and is retrieved when relevant. Add turns and watch the window.

7

Orchestration ties it together

Orchestration composes, schedules and supervises skills so each action feeds the next. Real conditions change: a resource disappears, priorities shift. A good orchestrator watches progress, pauses or reroutes, and makes sure skills do not work at cross-purposes. Chapter 5 is all about it.

9

One agent or several?

A single agent is simplest and fits well-defined, narrow tasks. Multiagent systems shine for complex, distributed or specialized work, at a price. Chapter 8 goes deep; here is the summary.

Multiagent gains

  • Specialization: each agent masters one area.
  • Parallelism: subtasks run at once.
  • Scalability: add agents as load grows.
  • Redundancy: one failure need not stop all.

Multiagent costs

  • Coordination: messages, conflicts, consistency.
  • Complexity: harder to design, debug and maintain.
  • Efficiency: often many more tokens per task.
10

Iterate, evaluate, test in the real world

The chapter ends with practices that carry through the book: build a minimal version quickly, test it with real users, refine, repeat. Evaluate correctness, edge cases and domain metrics; check generalization; collect satisfaction scores, completion rates, explicit thumbs and implicit signals. Then roll out in phases.
