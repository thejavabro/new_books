Monitoring in Production

Offline tests never cover everything users will do. Production monitoring tells you what the agent actually did, how much it cost and where it broke.

1

Monitoring is how you learn

Agents behave probabilistically, and their failures are subtle: a tool call succeeds but sets off a cascade, a fluent answer misleads, a plan half-works. The book's stance: failures are test cases. Monitoring finds them and feeds them back. The first skill is telling a true failure from acceptable variation. Sort these.

Failure, or fine?
Watch the privacy lineTraces and logs often hold user messages and personal data. Redact, restrict access and set retention, so observability does not become a compliance problem. And use the same pipeline as the rest of production; agents are not a side project.

Traces and spans: what the agent actually did

Instrument each graph node with an OpenTelemetry span: start it when the node starts, attach metadata (model, tokens, tool, arguments, outcome), record events such as retries and fallbacks, and nest spans for downstream calls. Spans flow to a trace backend (Tempo), logs to Loki, and Grafana shows both. Compare two sessions and click a span.

with tracer.start_as_current_span("tool.issue_refund") as span:
    span.set_attribute("order_id", order_id)
    span.set_attribute("agent.version", "2.3")
    try:
        result = issue_refund(order_id, amount)
    except TimeoutError:
        span.add_event("retry", {"attempt": 1})   # visible in the trace
        raise

5

Dashboards and alerts

Dashboards should show the agent's semantics, not just CPU: token use per agent, P95 latency of tools and planning, success rate by prompt version, fallback frequency, drift. Alerts fire when nobody is watching, using rules like the book's examples. Inject an incident.

7

Catching distribution shift

Users change: new products, new slang, a seasonal spike in returns. Slow drift quietly degrades an agent. Compare the current mix of tool usage against a baseline with the population stability index (alarm above about 0.25) or KL divergence (the book's example alarms above 0.5). A Kolmogorov-Smirnov test does the same for continuous values such as embedding distances.

Other warning signs from the chapter: accuracy dropping 5 to 10% over a rolling day, task abandonment above 15%, retries in more than 20% of sessions.

8

Who owns which metric

An agent's response is the product, so no single team can own its telemetry. Latency, for example, is shaped by prompts and models (ML), infrastructure (SRE) and user tolerance (product). The book offers a RACI template: Responsible, Accountable, Consulted, Informed. Pick a metric.
