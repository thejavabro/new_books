The parts of a database

There is no single blueprint for a database, and real codebases blur component boundaries for the sake of performance. Still, most systems share the same broad shape: a client/server design where a query enters through a transport layer, gets parsed and planned, and is finally executed against a storage engine that owns the bytes on disk. Two kinds of integrityThe transaction manager and lock manager together form concurrency control. One protects logical integrity (no transaction sees a half-done state), the other physical integrity (two threads never scribble on the same page at once). Chapter 5 covers both.
2

Memory-based versus disk-based

An in-memory database keeps its data in RAM and uses disk only for logging and recovery. A disk-based database keeps most data on disk and uses RAM as a cache. Memory is orders of magnitude faster and far easier to program: you allocate and free chunks and follow pointers. On disk you manage layouts, references, fragmentation and serialization yourself. What holds RAM back is cost and volatility.

An in-memory store still needs durability. Before an operation counts as done it is appended to a sequential log. To avoid replaying the whole log after a crash, the store keeps a sorted on-disk backup and folds log records into it in batches. Each batch leaves a snapshot that is current up to some point, so the log before that point can be thrown away. That is checkpointing.

Not just a big page cacheA disk database with all its pages cached is still slower than a true in-memory store: it keeps its disk-oriented page layout and serialization costs. In-memory systems can pick data structures (pointer-rich trees, hash tables) that would be painful on disk.
3

Row-oriented versus column-oriented layout

A table can be split horizontally (all fields of one row stored together) or vertically (all values of one column stored together). Disks hand over whole blocks, so whatever shares a block with the value you want is read too. Pick a layout and a query and watch which blocks get read and how much of each one is wasted.

To put a row back together, a column store must know which values belong to the same row. Storing the key next to every value duplicates data, so many column stores use virtual IDs: the value's position in the column is its row number.

4

Wide column stores are not column stores

Bigtable and HBase are often called "column" databases, but they are something else: a multidimensional sorted map. A row key leads to column families, each family holds columns named by qualifier, and each cell keeps several timestamped versions. Families are stored apart from each other, yet inside a family data is stored row by row. The classic example is a web table keyed by reversed URL. Expand the map.

5

Data files and index files

Databases do use files, but not one file per record. They build their own formats inside files to be efficient in storage (little overhead per record), access (few steps to find a record) and updates (few on-disk changes per write). Files are cut into pages of one or more disk blocks. Most modern engines don't erase data in place: a delete writes a tombstone, and garbage collection later copies live records elsewhere and drops shadowed ones.

6

Point at the record, or at its primary key?

A secondary index can store the record's physical location (one hop on read, but every index must be rewritten whenever the record moves) or its primary key (an extra primary-index lookup on every read, but moves only touch one index). MySQL's InnoDB takes the second route. Add secondary indexes, then run a workload.

A hybrid stores both: try the cached offset first, fall back to the primary key if the record moved, then fix the offset.

7

Buffering, immutability and ordering

Nearly every storage structure in this book can be described by three choices. Buffering: does it deliberately collect data in memory before writing? Immutability: does it append or write elsewhere instead of updating in place? Ordering: are records kept in key order on disk, so range scans are cheap?
