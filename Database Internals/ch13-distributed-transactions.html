Distributed Transactions

A transaction that touches several machines must commit everywhere or nowhere. This chapter walks through the protocols that try to guarantee it, from the classic two-phase commit to the designs behind Spanner and Calvin.

1

Making several nodes agree to commit

Moving money between accounts on two different partitions must change both or neither. Single-node concurrency control (Chapter 5) can't do that alone: we need an atomic commitment protocol. Participants can only vote yes or no on a transaction the coordinator proposes; a single "no" aborts it. Because it needs unanimity, it can't tolerate Byzantine participants that lie about their vote. Each node still decides locally what "ready to commit", "commit" and "roll back" mean.

2

Two-phase commit (2PC)

Phase 1 (prepare): the coordinator sends the transaction to every cohort; each executes it up to the point of no return, logs its vote durably and replies. A "yes" is a promise: the cohort will not change its mind. Phase 2 (commit/abort): if every vote is yes, the coordinator logs and sends Commit; otherwise Abort. Pick a scenario and play it.

Why 2PC is "blocking"Once a cohort has voted yes, it may not decide alone. If the coordinator dies before telling anyone the outcome, cohorts wait, holding locks, until it recovers or a replacement re-collects votes. If any cohort already got the decision, the others can safely copy it, because the decision is unanimous. Still, MySQL, PostgreSQL, MongoDB and Kafka use 2PC: it is simple, cheap in messages, and well understood. Backup coordinators help.
3

Three-phase commit (3PC)

3PC inserts a prepare round between voting and commit, and gives cohorts timeouts. Before the prepare round, a timeout means abort; after everyone acknowledged prepare, a timeout means commit, because all participants now know the vote passed. That removes blocking on coordinator failure, assuming a synchronous network. Partitions break it.

4

Calvin: agree on the order first

Instead of coordinating while executing, Calvin agrees on the input up front. A sequencer collects transactions into short epochs (about 10 ms), replicates each batch via Paxos, and hands it to schedulers. Every replica runs the same batch in the same deterministic order, so they all reach the same state without talking during execution, and a crashed node can just replay. The cost: each transaction's read and write sets must be known before it runs. FaunaDB is built on this idea.

5

Spanner: 2PC over Paxos groups, ordered by TrueTime

Spanner (and CockroachDB, YugabyteDB) takes the other road. Data is split into shards, each replicated by a Paxos group with a long-lived leader. Cross-shard writes run 2PC between group leaders; since each cohort is a whole group, one machine failing doesn't block 2PC. Leaders use two-phase locking for isolation. Ordering comes from TrueTime, a clock API returning an interval [earliest, latest] guaranteed to contain real time. A transaction picks commit timestamp s ≥ latest, then waits until earliest > s before revealing results. Then any transaction starting later gets a bigger timestamp: external consistency, a transactional version of linearizability.

6

Partitioning and consistent hashing

Both systems rely on partitioning: each replica set owns part of the key space. Range partitioning keeps neighbors together (great for scans, risky for hot ranges); hashing the key spreads neighbors apart. The naive mapping hash(k) mod N reshuffles almost everything when N changes. Consistent hashing places nodes and keys on a ring; each key belongs to the next node clockwise, so adding a node only takes keys from one neighbor: about K/n keys move.

7

Snapshot isolation

Snapshot isolation lets each transaction read from a frozen snapshot as of its start time; if two concurrent transactions write the same cell, the first committer wins and the other aborts. It stops read skew without read locks. It is not serializable: write skew is still possible when two transactions write disjoint cells based on overlapping reads.

Invariant: x + y = 100. T1 reads x, then T2 moves money, then T1 reads y.
8

Percolator: transactions on top of Bigtable

Google's Percolator adds snapshot-isolated transactions to Bigtable using only single-row atomic read-modify-write. Each cell has three columns: data (versioned values), lock, and write (which data version is committed). A timestamp oracle hands out increasing timestamps for start and commit. The client drives a 2PC. TiDB follows this model. Here: move 30 from Account B to Account A.

9

Coordination avoidance and RAMP

Sometimes coordination can be skipped entirely. If operations are invariant-confluent (any two valid diverged states can be merged into a valid state), replicas can run transactions locally and merge later without ever breaking the invariant. Decide for each case.

Can this run without coordination?

RAMP (Read Atomic Multi-Partition) transactions provide read atomic isolation: you see all of another transaction's writes or none, never a fractured read. Writes go through prepare (stored, invisible) and commit (visible). Each written version carries metadata listing the transaction's other keys, so a reader that sees a newer version on one partition knows to fetch the matching version from the other, without locks.
