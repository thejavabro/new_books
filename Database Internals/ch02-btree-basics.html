B-Tree Basics

Binary search trees are fine in memory and terrible on disk. B-Trees fix that with one idea: make every node wide, so the tree stays shallow and each disk read brings back hundreds of keys.

1

Binary search trees and why balance matters

A binary search tree keeps smaller keys to the left and larger keys to the right, so each comparison halves what is left to search: about log2 N steps. That only holds while the tree is balanced. Insert keys in sorted order and it degenerates into a linked list with O(N) lookups. Balanced trees fix this with rotations after inserts and deletes: a middle node is promoted and its parent becomes its child.

2

Why binary trees fail on disk

On disk two things hurt. Locality: nodes are created in random order, so a child can live in a different page from its parent and every pointer hop may be a seek. Height: with a fanout of two, a lookup crosses log2 N levels. Constant rebalancing also means relocating nodes and rewriting pointers. A disk-friendly tree needs the opposite: high fanout and low height, which go hand in hand.

3

What the hardware wants

Spinning disks

The expensive part is moving the head and waiting for the platter. Once positioned, reading contiguous bytes is cheap, hence the obsession with sequential I/O. The smallest transfer is a sector, 512 bytes to 4 KB.

Solid state drives

No moving parts. Cells form strings, then arrays, pages (2 to 16 KB), blocks (64 to 512 pages), planes and dies. You read and write pages, but you can only write to erased cells, and the smallest erasable unit is a whole block. The Flash Translation Layer maps logical pages to physical ones and garbage-collects blocks.

Play the flash translation layer

Both are block devicesThe OS exposes both as block devices: read one word, get the whole block. On-disk structures should therefore pack useful data into each block, keep out-of-page pointers few, and prefer full-block writes. Random versus sequential matters less on SSDs, but random, unaligned writes still trigger more garbage collection.
4

The B-Tree hierarchy

A B-Tree is like a library card catalogue: pick the cabinet, then the shelf, then the drawer, then flip through cards. Each node holds up to N keys and N + 1 child pointers. Nodes are the root, internal nodes and leaves. The book, like most literature, uses "B-Tree" for what is strictly a B+-Tree: values live only in leaves and internal nodes hold separator keys. 5

Lookup: seeks versus comparisons

A lookup starts at the root, binary-searches the node for the first separator greater than the search key, follows the pointer to the left of it (or the last pointer), and repeats until it reaches a leaf. Count two things: pages read (one per level, logN M) and comparisons (log2 M in total, because each node is binary-searched). Finding one key among four billion takes about 32 comparisons but only a handful of page reads.

6

Insert, split, delete, merge

B-Trees grow from the bottom up. An insert goes to the right leaf. If the leaf overflows, it splits: half the keys move to a new sibling, and the first key of the new node is copied to the parent as a separator (in an internal node the middle key is moved up instead). If the parent overflows too, the split propagates. Only a root split makes the tree taller. Deletes do the reverse: when a node underflows and fits together with a neighbour, the two merge and a separator leaves the parent; otherwise a key is borrowed. This tree holds at most 3 keys per node so you can watch it happen.

// Leaf split in a B+-Tree (sketch)
function splitLeaf(leaf, parent, slot) {
  const mid = Math.ceil(leaf.keys.length / 2);
  const right = { leaf: true, keys: leaf.keys.slice(mid) };
  leaf.keys = leaf.keys.slice(0, mid);
  parent.keys.splice(slot, 0, right.keys[0]);   // copy up
  parent.kids.splice(slot + 1, 0, right);
  // if parent now overflows, split it too (move middle key up)
}
