Buffer Management and Recovery

Transactions need two things from the storage engine below them: a cache that keeps hot pages in memory, and a log that lets the database put everything back together after a crash.

1

What a transaction promises

A transaction is an indivisible unit of work: several reads and writes that behave as one step. The guarantees are summed up as ACID. Inside a single node, they come from four cooperating parts: the transaction manager schedules and tracks transactions, the lock manager guards resources, the page cache stages changes in memory, and the log manager records history so it can be replayed or undone. This page covers the cache and the log; the next covers concurrency.

2

The page cache

Databases keep a two-level hierarchy: slow disk, fast RAM. The page cache (or buffer pool) holds copies of disk pages. A requested page is returned from memory if present, otherwise paged in. A modified page is dirty until flushed. A page in use is referenced and can't be evicted; a page the engine wants to keep around can be pinned. Because each B-Tree level has far fewer nodes than the one below, the top levels are cheap to keep in memory permanently, so a lookup only touches disk for the lower levels.

3

CLOCK: LRU's cheaper cousin

Relinking a list on every access is expensive under concurrency. CLOCK keeps pages in a circular buffer with an access bit each. Accessing a page sets its bit. To evict, the hand sweeps: a bit of 1 gets a second chance (reset to 0, move on); a bit of 0 means evict. Referenced pages are skipped. The hand and bits can be updated with compare-and-swap, no lock needed. Linux uses a variant.

Bypassing the kernelThe OS has its own page cache. Many databases open files with O_DIRECT to skip it and manage memory themselves, which some kernel developers dislike. fadvise only offers hints, and mmap saves syscalls but surrenders control over caching.
4

The write-ahead log

Dirty pages in the cache are lost on a crash. The write-ahead log (WAL, or commit log) is an append-only, immutable file that records every change before the page is modified. Each record gets a monotonically increasing log sequence number (LSN). Records collect in a log buffer and are forced to disk in LSN order; a transaction counts as committed only once the log is forced past its commit record. A checkpoint marks the point up to which pages are safely on disk so the log before it can be trimmed. Real systems use fuzzy checkpoints: write begin_checkpoint, flush the listed dirty pages in the background, write end_checkpoint, then advance last_checkpoint.

Even fsync can liePostgreSQL's checkpointer relied on fsync() reporting errors. On Linux, a failed flush could clear the dirty flag anyway, and errors only reach descriptors that were open at the time. The checkpointer could believe data was on disk when it wasn't. Recovery code must assume every layer below can fail in surprising ways.
5

Physical, logical, and shadow paging

Any change can be described as a before-image and after-image, or as a redo and an undo operation. A physical log stores page images or byte diffs; a logical log stores operations like "insert X under key Y" with an inverse "remove Y". Many systems use logical undo (good for concurrency) and physical redo (fast recovery). System R used shadow paging instead: write changes to an unpublished copy of the page and make them visible with a single pointer flip.

6

Steal and force policies

Two questions decide what recovery must do. Steal: may the cache flush a page with uncommitted changes (to make room)? Force: must every page a transaction touched be flushed before it commits? Pick a cell.

7

ARIES recovery, step by step

ARIES is a steal / no-force algorithm: flexible for the cache, so recovery must both redo and undo. It uses LSNs, a dirty page table, physical redo, logical undo and fuzzy checkpoints. After a crash it runs three phases: analysis, redo (repeat history exactly, even for losers), and undo (roll back in-flight transactions in reverse order, writing compensation log records so that a crash during recovery never undoes the same thing twice).
