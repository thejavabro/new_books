Log-Structured Storage

Instead of editing data where it lives, write everything to new places and clean up later. That one decision gives you fast writes, simple concurrency and a background job called compaction you have to live with forever.

1

The LSM Tree, hands on

A log-structured merge tree never updates data in place. Writes go to the write-ahead log and to a sorted in-memory memtable. When the memtable is big enough it is flushed as an immutable, sorted disk table. Deletes are writes too: a tombstone that shadows older values (some engines also support range tombstones). A read must check the memtable and then every table from newest to oldest until it finds the key. The number of tables keeps growing, so a background compaction merges them, dropping shadowed records. Try it; the memtable flushes at 4 entries.

2

Merge-iteration and reconciliation

Reads over ranges, flushes and compactions all need the same primitive: merge several sorted iterators into one sorted stream. A priority queue (min-heap) holds the head of each iterator; pop the smallest, output it, refill from the iterator it came from. When several sources hold the same key, reconciliation keeps the record with the newest timestamp, and a tombstone wins over the values it shadows.

3

Leveled versus size-tiered compaction

Leveled compaction (RocksDB): level 0 holds freshly flushed tables whose ranges may overlap; from level 1 on, tables on a level have disjoint key ranges and each level is exponentially larger than the previous one. When a level exceeds its target, tables are merged into the next level's overlapping tables. Size-tiered compaction (Cassandra's classic strategy) groups tables of similar size and merges a group into one bigger table. Leveled rewrites data more often; size-tiered leaves more tables to check per read. Flush tables and compare.

Size-tiered

Simplified model: every flush is one unit of data with no overwrites; L1 holds 4 units, each next level 4× more.

Tombstones and starvationA tombstone can only be dropped once no older value it shadows could still exist. RocksDB keeps tombstones until they reach the bottommost level; Cassandra keeps them for a GC grace period so replicas see them. Drop one too early and deleted data is resurrected. In size-tiered compaction, merged tables can stay small (lots of data deleted), so bigger tiers starve and their tombstones are never applied; compaction has to be forced. Cassandra's time window strategy can drop whole expired files without rewriting them.
4

Read, write and space amplification; the RUM conjecture

Immutable storage trades three costs. Read amplification: several tables per lookup. Write amplification: data rewritten again and again by compaction. Space amplification: multiple versions of a key kept until compaction. Compact eagerly and you write more; compact lazily and you read and store more. Note that B-Trees and LSM Trees amplify writes for different reasons (page writeback versus file-to-file migration), so comparing raw numbers can mislead. The RUM conjecture generalises this: of Read, Update and Memory overheads, improving two worsens the third. Click a structure.

5

Sorted String Tables

Disk tables are usually SSTables: an index file (often a B-Tree or a sorted list of keys and offsets) and a data file of key-sorted records, written sequentially and never modified. Sorted order makes merge-iteration simple and range scans sequential. Cassandra's SSTable-Attached Secondary Indexes (SASI) go further: each table carries its own secondary index, built when the memtable is flushed and merged along with it during compaction.

6

Bloom filters

Most tables don't hold the key you want. A Bloom filter per table answers "definitely not here" or "maybe here" from memory. It is a bit array with k hash functions: adding a key sets k bits; a lookup checks those k bits, and any zero proves absence. All ones may be a false positive, never a false negative. The false-positive rate is roughly (1 − e−kn/m)k for n keys in m bits.

7

Skiplists for memtables

Memtables need a sorted structure that is cheap to insert into concurrently. A skiplist is a sorted linked list with extra "express lanes": each node gets a random height (each level with probability ½), and a search starts at the top lane, moves right while the next key is smaller, then drops down. Expected O(log n), no rebalancing, and inserts only touch nearby pointers, which keeps them concurrency-friendly. Some engines also use them in WiredTiger update buffers (chapter 6).

8

Unordered storage: Bitcask and WiscKey

Drop the "ordering" knob and writes get even cheaper. Bitcask (Riak) appends records to log files in write order and keeps an in-memory hash table, the keydir, mapping each key to its latest record. Point lookups take one seek; compaction copies live records and drops shadowed ones. The costs: every key in RAM, a keydir rebuild on startup, and no range scans. WiscKey keeps keys (small) sorted in an LSM Tree and values (large) in an append-only vLog, so compaction moves only keys. Range scans become random reads, eased by SSD parallelism; vLog garbage collection must consult the key tree to know what is live.

9

Concurrency: switching table views

LSM concurrency is mostly about changing the table view (the set of memtables and disk tables a reader sees) atomically, and coordinating that with the log. Cassandra uses operation-order barriers so the flush knows every accepted write has landed.

10

Log stacking

Log-structured storage is everywhere: the SSD's flash translation layer remaps pages, batches small writes, garbage-collects erase blocks and spreads wear (wear leveling); many filesystems log too; then the database adds its own WAL and LSM Tree. Stacked logs each keep their own bookkeeping and GC, duplicate work, and misaligned segments fragment the layer below. Interleaved write streams that are each sequential may not be sequential on the device. Align partitions and writes to hardware page sizes, or cut out layers.

Every structure in Part I can be placed by the three properties from chapter 1. Buffering always helps write amplification; immutability shifts work to garbage collection or compaction; ordering buys range scans at the cost of sorting effort.
