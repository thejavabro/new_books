B-Tree Variants

Classic B-Trees update pages in place and pay for it in write amplification and latches. The variants in this chapter keep the shape of a B-Tree while borrowing buffering and immutability to avoid those costs.

1

What's wrong with the classic B-Tree?

The original B-Tree was designed for spinning disks. On modern hardware three costs stand out. Write amplification: changing a few bytes rewrites a whole page. Space amplification: pages keep free space for future inserts, and that empty space is read and written along with the data. Concurrency complexity: latches, crabbing and their bugs. The variants in this chapter attack these with the knobs from chapter 1: buffering and immutability.

2

Copy-on-write B-Trees (LMDB)

Never modify a page: copy it, change the copy, and copy every ancestor up to a new root, reusing all untouched subtrees. Then swap the root pointer atomically. Readers hold an old root and see a consistent, immutable tree without any latches; a crash can never leave a half-written page because the old root is still valid. LMDB (used by OpenLDAP) is built this way and needs no page cache, no WAL, no checkpoints and no compaction. It keeps just two roots and, being append-only, has no sibling pointers.

3

Lazy B-Trees: WiredTiger and LA-Trees

Another approach: keep the on-disk page as is and buffer changes in memory. A node can live in memory as raw bytes behind pointers, as language-native objects, or behind a wrapper over the buffer; separating the in-memory form from the on-disk page is what makes buffering possible. WiredTiger (MongoDB's default engine) gives each dirty page an update buffer, implemented as a skiplist. Reads merge the buffer with the page image; on flush, reconciliation writes the merged page, splitting it if it grew too large. Splits and merges happen in a background thread.

The Lazy-Adaptive Tree (LA-Tree) attaches buffers to subtrees instead. Inserts go to the root's buffer; when it fills, its contents cascade down to the buffers of the children responsible for those keys, and so on until a batch reaches the leaves and is applied in one go, with splits propagating up in batches too.

4

FD-Trees: a small head tree and sorted runs

Why update nodes at all? The FD-Tree (Flash Disk Tree) confines random writes to a small mutable head tree. When it fills, it is written out as an immutable sorted run. Runs grow by a factor k from level to level; when a level overflows it is merged into the next, much like LSM compaction. Deletes are filter entries (tombstones) that disappear once they reach the bottom.

Searching several sorted arrays would cost a binary search per level. Fractional cascading fixes that: copy every N-th element of each lower level up into the level above as a bridge (a "fence") pointing at its position below. One binary search at the top, then each level only needs to look at a small window. Search below.

5

Bw-Trees: delta chains and compare-and-swap

The Bw-Tree tackles write amplification, space amplification and latching at once. A node is a logical entity: a base node plus a chain of delta nodes (insert, update, delete), newest first. Nothing is ever rewritten in place, and no space is reserved. Parents point at logical IDs; an in-memory mapping table translates each ID to the head of its chain. Installing a delta is a single compare-and-swap on the mapping table: if two threads race, exactly one wins and the other retries. No latches at all.

6

Cache-oblivious B-Trees

B-Trees are cache-aware: tuned to one block size for one two-level hierarchy. Cache-oblivious structures perform within a constant factor of optimal for any block size, so they work across CPU caches, RAM and disk without tuning. The static part uses the van Emde Boas layout: cut the tree at its middle level, store the top subtree contiguously, then each bottom subtree contiguously, recursively. Any subtree small enough to fit in a block sits in one block. Below, the highlighted cells are a root-to-leaf path in memory order. Change the block size.

Dynamic versions add a packed array with gaps for future inserts at the bottom. As of the book's writing, no nonacademic implementations were known.
