File Formats

A B-Tree node on disk is just a page of bytes. This chapter is about how to lay those bytes out so that variable-size records fit, keys stay sorted and nothing has to be shuffled more than necessary.

1

Why storage formats are hard

In memory you call malloc, follow pointers and let the allocator worry about fragmentation. On disk there is no allocator and no garbage collector: you get a file of bytes, accessed block by block, and you decide where every field goes. A storage format has to be compact, easy to traverse and cheap to update. Everything starts with encoding primitive values, then grows into a hierarchy: fields → cells → pages → files.

2

Integers and byte order

Fixed-size integers take 1, 2, 4 or 8 bytes. Which byte comes first is the byte order: big-endian writes the most significant byte (MSB) first, little-endian writes the least significant first. Encoder and decoder must agree, so formats pick one and convert explicitly. Type a number.

Floats, strings and variable-size data

Floating-point numbers follow IEEE 754: a sign bit, an exponent and a fraction. A 32-bit float has 1 + 8 + 23 bits, and most decimals can only be approximated. Strings and byte arrays have variable size, so the usual trick is to write the length first, then the bytes (a "Pascal string"). The reader knows exactly how far to slice without scanning for a terminator.

Purple: a 2-byte length prefix, then UTF-8 bytes. To skip this field, read the size and jump.

4

Booleans, enums and flags

A boolean only needs one bit, so formats pack eight of them into a byte. Enums become small integers (a node type: root, internal, leaf). Flags are non-exclusive booleans, each owning one bit, set with |, cleared with & ~ and tested with &. Toggle the flags of a page header.

Fixed fields first, variable fields after

  
With a fixed schema there is no need to store field names: position identifies the field. A practical layout puts all fixed-size fields first (they sit at precomputed offsets), followed by the variable-size ones. To find a variable field, you add up the lengths stored in the fixed part. 6
Slotted pages

  
The original B-Tree paper stored fixed-size key/value/pointer triplets back to back. That breaks with variable-size records: inserting in the middle shifts everything, and freed holes rarely match new records. The slotted page (used by PostgreSQL, SQLite and many others) splits the page in two: a pointer array grows from the left after the header, cells grow from the right. Cells are appended in arrival order; only the small pointers are kept sorted, so binary search still works. Outside the page, records are referred to by slot ID, so cells can move inside without breaking anything.

7
Versioning and checksums

  
Formats change, and a new engine must still read old files. The version can live in the file name (Cassandra prefixes data files, e.g. na-1-big-Data.db), in a separate file (PostgreSQL's PG_VERSION) or in the file header, possibly as a magic number. Disks and software also corrupt data, so each page carries a checksum in its header: compute on write, recompute on read, refuse to use the page on mismatch. A plain additive checksum is the weakest; a CRC catches burst errors where several neighbouring bits flip. Neither protects against deliberate tampering: that needs a cryptographic hash.

PrimitivesFixed-width integers with an agreed byte order; IEEE 754 floats; length-prefixed strings.

    
BitsPack booleans, enums and flags; set with OR, clear with AND NOT, test with AND.

    
LayoutHeader, pages, optional trailer. Fixed fields first, variable fields after.

    
Slotted pagesPointers sorted on the left, cells appended on the right, slots referenced by ID.
