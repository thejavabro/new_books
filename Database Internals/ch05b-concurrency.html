Concurrency Control

Running transactions one at a time is safe and slow. Running them at once is fast and dangerous. Concurrency control is the set of rules that lets a database do the second while looking like it does the first.

Schedules and serializability

A schedule is the sequence of reads, writes, commits and aborts the database actually executes. A serial schedule runs transactions one after another: easy to reason about, slow. A serializable schedule interleaves them but produces the same result as some serial order. Build your own schedule: T1 transfers 50 from A to B, T2 adds 10% interest to both. 2

Read and write anomalies

The SQL standard names three read anomalies: dirty, nonrepeatable and phantom reads. There are write anomalies too: lost update, dirty write and write skew. Pick one and step through it.

3

Isolation levels

Isolation costs coordination, so databases offer levels. Read uncommitted allows dirty reads. Read committed forbids them. Repeatable read also forbids nonrepeatable reads. Serializable forbids everything: outcomes equal some serial order. Snapshot isolation reads from a snapshot taken at start and commits only if nobody else changed the values it wrote, which stops lost updates but still allows write skew. Click a level.

Serializability is not linearizabilitySerializability is about groups of operations (transactions) appearing in some serial order. Linearizability, from chapter 11, is about single operations respecting real time. "I" in ACID means serializability.
4

Optimistic concurrency control

OCC bets that conflicts are rare. Each transaction runs a read phase in a private workspace, collecting its read set and write set. Then a validation phase checks for conflicts with concurrent transactions; on conflict, the workspace is cleared and the transaction restarts. If clear, the write phase publishes the writes. Validation and write form a short critical section. Below, T1 committed while T2 was still reading (backward validation). Pick their sets.

5

Multiversion concurrency control

MVCC keeps several timestamped versions of each record. Writers add a new version instead of overwriting; readers pick the newest version committed as of their snapshot, so reads never block writes. There is at most one uncommitted version at a time. Snapshot isolation is the classic use. Drag the reader's snapshot.

6

Pessimistic without locks: timestamp ordering

Each transaction gets a timestamp; each value tracks max_read_ts and max_write_ts. A read older than max_write_ts aborts (a newer value already exists). A write older than max_read_ts aborts (someone newer already read the old value). A write older than max_write_ts is simply skipped: the Thomas write rule, since its value would be overwritten anyway. Aborted transactions restart with a new timestamp. Predict each outcome.

Value V: max_read_ts = 20, max_write_ts = 15 at the start of each row

7

Two-phase locking and deadlocks

Two-phase locking: a growing phase acquires locks, a shrinking phase releases them; once you release any lock you may not take another. (Nothing to do with two-phase commit.) Waiting for locks invites deadlock: T1 holds L1 and wants L2, T2 holds L2 and wants L1. Systems either use timeouts, acquire everything up front (conservative 2PL), detect cycles in a waits-for graph, or avoid them with timestamps.

Locks versus latches

Two mechanisms, two kinds of integrity. Locks protect logical data: keys or key ranges, held for the whole transaction, managed by the lock manager outside the tree. Latches protect physical structure: a page while it is read or modified, held as briefly as possible. Even "lock-free" concurrency control still needs latches. Most latches are readers-writer latches: any number of readers, or exactly one writer.

9

Latch crabbing and B-link trees

Latching every node from root to leaf is safe and a bottleneck. Latch crabbing (latch coupling) moves like a crab: latch the child, then release the parent as soon as it's clear the operation can't affect it. Readers release the parent immediately. Writers release it once the child is not full (insert) or not near empty (delete), because then no split or merge can propagate up. A further trick: latch shared on the way down and upgrade only where a split happens.

Blink-Trees remove the need to hold the parent during a split. Every node has a high key and a sibling link. A split first publishes the new right node through the sibling link (a half-split), then lazily adds the separator to the parent. A reader that lands on the left node and finds its key above the high key just follows the link right. Locks held during a structural change drop to a constant, and readers never wait on splits.
