Replication and Consistency

Copies make data survive failures and serve more readers. They also mean different nodes can disagree. Consistency models are the contracts that say how much disagreement clients are allowed to see.

1

Why replicate, and what availability means

Replication keeps copies of data on several nodes so the system survives failures and serves more readers. Availability is usually quoted in nines; each extra nine cuts allowed downtime tenfold. But copies can disagree, and keeping them in sync costs coordination. The rest of the chapter is about that trade-off.

2

CAP: consistency or availability during a partition

Brewer's CAP conjecture (proved by Gilbert and Lynch): with a network partition, you can't have both consistency (here: linearizability) and availability (every non-failing node answers). A CP system refuses requests it can't serve consistently, like a consensus group that needs a majority. An AP system answers anyway and may return stale or conflicting data. Partition tolerance isn't a knob: partitions happen. PACELC adds that else, with no partition, you still trade latency against consistency. Note CAP's C is not ACID's C, and CAP's availability has no latency bound.

3

Harvest and yield

CAP talks only about the extremes. Fox and Brewer's softer metrics: yield, the fraction of requests that complete, and harvest, how complete each answer is. When some shards are down, a search can fail outright (protect harvest) or answer from the shards that are up (protect yield).

4

Shared memory and registers

To reason about replicated data, model it as registers supporting read and write. Each operation takes time: an invocation and a completion. What may a read that overlaps a write return? Safe: anything in the register's range (the old value, the new one, or garbage). Regular: the old value or the new one. Atomic: old or new too, but once any read returns the new value, no later read may return the old one: the write appears to happen at a single instant. That is linearizability.

Write(1) is in progress over a register holding 0. A read overlaps it.

5

Linearizability

A history is linearizable if every operation can be given a single linearization point somewhere between its invocation and completion, such that the resulting sequence is a legal single-copy history. Real-time order is respected: if A finished before B started, A comes first. Move the reads and choose what they returned.

The costLinearizability needs coordination on every operation: real systems use consensus or a single leader. Even a CPU's memory isn't linearizable by default; it takes fences or atomic instructions. Building it from scratch is hard, so systems often lean on reusable infrastructure such as a consensus service or compare-and-swap on a linearizable store.

7

Vector clocks

Causal consistency needs to know which events could have influenced which. A vector clock holds one counter per process. A process increments its own entry on each event and attaches the vector to messages; a receiver takes the element-wise maximum, then increments its own entry. Event a happened before b if a's vector is ≤ b's everywhere and smaller somewhere; if neither is ≤ the other, they are concurrent and may conflict. Dynamo and Riak use them to detect divergent versions and hand both to the application to reconcile.

8

Session (client-centric) models

Sometimes a global guarantee is overkill and what matters is that one client's view makes sense. Session models describe what a single client sees, often by pinning it to a replica or tracking the versions it has seen. Monotonic reads + monotonic writes + read-own-writes together give PRAM (FIFO) consistency.

9

Eventual and tunable consistency

Eventual consistency only promises that replicas converge if writes stop; conflicts are resolved by last-write-wins or vector clocks. Dynamo-style stores make it tunable: with N replicas, a write waits for W acks and a read queries R replicas. If R + W > N, every read set overlaps every write set, so a read sees the latest acknowledged write. Even then, reads during an in-flight write can alternate between old and new unless reads also repair replicas.

Witness replicas

Three replicas: two full copies (1c, 2c) and one witness (3w) that normally stores only "a write happened". Quorums of two still work, at two-thirds of the storage.

10

Strong eventual consistency and CRDTs

Conflict-free replicated data types are designed so that merges are commutative, associative and idempotent: replicas can accept updates independently, exchange state in any order, and are guaranteed to converge. That is strong eventual consistency. A G-Counter keeps one slot per node; each node increments only its own slot; merging takes the element-wise maximum; the value is the sum. Try to break it.
