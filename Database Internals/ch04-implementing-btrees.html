Implementing B-Trees

The textbook algorithm leaves out everything that makes a B-Tree work in production: what goes in the page header, how to find your way back up the tree, what to do with huge values, and how to clean up after deletes.

1

The page header and magic numbers

Every page starts with a small fixed header that the engine reads before anything else: flags describing the layout, the number of cells, the lower and upper offsets bounding free space, and whatever else the implementation needs. PostgreSQL keeps page size and layout version there; InnoDB keeps the number of heap records and the tree level; SQLite keeps the cell count and the rightmost pointer. Click a field.

A magic number is a constant multi-byte value written into the header, for example 50 41 47 45, ASCII for "PAGE". On read, compare the first four bytes. Random bytes almost never match, so a match means the page was loaded from the right, aligned offset. Try reading at different offsets.

2

Sibling links versus climbing the tree

To reach the next leaf during a range scan, a tree without sibling links must go back up to a parent, and if the node is the parent's last child, keep climbing until it can turn right, then come back down. Storing forward and backward links in each header makes it one hop. The price: splits and merges must also update a neighbour's header, which may need extra locking. Pick a leaf.

3

Rightmost pointers and high keys

A node with N keys has N + 1 pointers, so one pointer has no key to pair with. Implementations either store that rightmost pointer separately (SQLite keeps it in the header and has to reassign it when the rightmost child splits) or add a high key: an upper bound for everything in the node. With a high key every pointer gets a partner cell, there are fewer edge cases, and each node knows its own key range. PostgreSQL does this, following the Blink-Tree design (more in chapter 5).

4

Overflow pages for oversized records

Node size is fixed, but values aren't. A node can be "not full" by key count yet out of bytes. Rather than resizing pages, engines cap how many payload bytes live in the node, max_payload = page_size / fanout, and spill the rest to linked overflow pages. The first overflow page ID goes in the primary page header; further ones are chained. Keys are usually distinctive enough that the prefix kept in the primary page settles most comparisons.

5

Binary search through indirection pointers

Cells sit in insertion order; only the pointer array is sorted. Binary search therefore probes the middle pointer, follows it to the cell, compares the key, and halves the range. On an internal node we rarely expect an exact hit: we want the insertion point, the first key greater than the search key, which tells us which child to follow. Step through a search.

6

Breadcrumbs: remembering the way up

A split may have to propagate to the parent, grandparent and so on. Nodes could store parent pointers, but those must be updated every time a separator moves between nodes. The alternative is to remember the descent: push each visited node and the child index followed onto a stack (PostgreSQL calls it BTStack). If the leaf splits, pop to find the parent and the slot where the promoted key goes; repeat until a level absorbs the change.

7

Rebalancing, right-only appends and bulk loading

Splits leave two half-empty nodes. Three tricks push occupancy up. Rebalancing moves keys to a less full sibling (updating the parent separator) instead of splitting; B*-Trees wait until two siblings are full and split two nodes into three, each two-thirds full (SQLite does this). Right-only appends exploit auto-increment keys: PostgreSQL's fastpath inserts straight into the cached rightmost leaf, and SQLite's quickbalance starts a new, nearly empty rightmost page rather than splitting in half, since it will fill soon anyway. Insert 60 keys and compare.

Bulk loading takes this to the limit. Given presorted data, write full leaves left to right, push each leaf's first key into the parent level, and build the upper levels the same way. No splits, no merges, only the current right edge in memory. An immutable tree can fill every page completely.

8

Compression granularity

Compressing the whole file gives the best ratio but means decompressing a lot to reach one page. Page-wise compression couples nicely with loading and flushing, but a compressed page rarely fills whole disk blocks, so reads drag in bytes belonging to neighbours. Compressing rows or columns instead decouples compression from page management. Libraries such as Snappy, zlib and LZ4 trade ratio against CPU and memory.

9

Fragmentation and vacuum

Deletes only remove a cell's pointer. Splits only trim the pointer array. Updates may leave older versions of a cell behind (MVCC even relies on them for a while). The bytes stay: they are garbage, no longer addressable from the root. The page ends up with enough free space in total but not enough contiguous space. Vacuum (also called compaction or maintenance) rewrites pages, puts cells back in key order and records freed page IDs in a persistent free list.
