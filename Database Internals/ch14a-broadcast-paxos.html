Consensus: Broadcast and Paxos

Consensus lets a group of unreliable machines agree on one value and never take it back. It starts with broadcast and ends with Paxos and its many descendants.

1

What consensus guarantees

Consensus lets a group of processes agree on one value even if some crash. Three properties define it: agreement (all correct processes decide the same), validity (the value was actually proposed by someone) and termination (all correct processes eventually decide). FLP says no deterministic algorithm can guarantee all three in a fully asynchronous system, so real algorithms keep safety always and rely on failure detectors and timeouts for liveness. For each broken "algorithm" below, which property fails?

2

Best-effort and reliable broadcast

A best-effort broadcast makes the sender responsible for reaching everyone; if it crashes halfway, some nodes got the message and some never will. A naive reliable broadcast fixes that by having every receiver forward the message to everyone else once it suspects the sender failed. Everyone ends up with it, at the cost of about N² messages.

3

Atomic broadcast and virtual synchrony

Reliable broadcast agrees on which messages arrive, not their order. Atomic broadcast (total order multicast) adds that every node delivers them in the same order. It is equivalent to consensus. Two clients broadcast at once:

Virtual synchronyExtends atomic delivery to groups whose membership changes. Messages belong to a view (a group membership). A message is received when a member gets it and delivered only once every member of that view has it. A view change acts as a barrier: nothing sent in an old view is delivered in a new one. Elegant, but little used commercially.
4

ZooKeeper Atomic Broadcast (ZAB)

ZooKeeper orders all writes through one leader per epoch. Any election method can pick a prospective leader; safety comes from the three phases that follow. Followers only accept proposals from the established leader of the current epoch.

5

Paxos, hands on

Roles: proposers drive rounds, acceptors vote, learners record the outcome (one process often plays all three). Phase 1: a proposer sends Prepare(n). An acceptor that hasn't promised a higher number promises to ignore anything lower and reports any value it already accepted. Phase 2: with promises from a majority, the proposer sends Accept(n, v), where v must be the highest-numbered value reported, or its own if none. A value is chosen once a majority accepts the same proposal. Choose which acceptors each proposer can reach, then run phases, or load a scenario.

Liveness needs helpTwo proposers can keep preempting each other's Prepare forever (try Duelling). Implementations add random backoff or a stable leader. Safety never depends on timing: any two majorities share an acceptor, and that acceptor carries the earlier value forward.
6

Quorums and Flexible Paxos

With 2f + 1 acceptors, majorities of f + 1 tolerate f failures, and any two majorities overlap. But only phase 1 and phase 2 quorums must overlap: Q₁ + Q₂ > N (Flexible Paxos). Since phase 2 runs for every value and phase 1 only on leader change, you can shrink Q₂ and enlarge Q₁. Steady-state replication then survives N − Q₂ failures, but electing a new leader needs Q₁ nodes up.

7

Multi-Paxos: a replicated log

Single-decree Paxos fills one write-once slot. Multi-Paxos keeps a stable leader that ran phase 1 once and then only runs phase 2 for each new log slot, halving the round trips. The log is applied to a state machine and truncated after snapshots. Reads from the leader need care: a newer leader may exist. Leases (followers promise not to back another leader for a while) allow local reads, but rely on bounded clock drift.

8

Fast Paxos

Clients normally go through the leader. Fast Paxos lets proposers send values straight to acceptors after the coordinator issues an Any message, saving a hop. The price: 3f + 1 acceptors and fast quorums of 2f + 1, and collisions when proposers race; then the coordinator must run a recovery round. Under contention it can be slower than classic Paxos.

f = 1: four acceptors, fast quorum of three.

9

Egalitarian Paxos

A single leader is a bottleneck and an outage risk. EPaxos has no fixed leader: any replica leads its own command. It attaches dependencies (interfering commands it knows of) and a sequence number. Two commands interfere only if their order changes the result. If a fast quorum agrees on the dependencies, it commits in one round trip (fast path); otherwise it merges the dependency lists and runs an extra Accept round on a majority (slow path). Execution follows the dependency graph.

10

A generalized view of consensus

Heidi Howard and Richard Mortier recast single-decree Paxos as clients writing write-once registers on servers. Registers with the same index across servers form a set; each quorum of a set is in one of four states. Clients may only write a value they were given or have read, and may never contradict an earlier register set's possible decision. Phase 1 checks a register is unwritten (and seals lower ones with nil); phase 2 writes the value.
