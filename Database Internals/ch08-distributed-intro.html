Introduction and Overview

The moment a database runs on more than one machine, it stops being able to trust the network, the clock or even the silence of a peer. This chapter sets out what can go wrong and the vocabulary for talking about it.

Concurrent execution and shared state

Even on one machine, two threads touching the same variable without coordination give different answers depending on how their steps interleave. In a distributed system the "threads" are processes on different machines, there is no shared memory, and messages take an unknown amount of time. Here x starts at 2; process A adds 1, process B doubles it. Each does read → compute → write. Run them in different orders.

Consistency modelsBecause a distributed system can't pretend there is one copy updated in one order, it needs a consistency model: a contract describing which outcomes clients may observe. Chapter 11 is entirely about them. Concurrent means overlapping in time; parallel means literally at the same instant on different processors. Distributed systems care about the former.
2

The fallacies of distributed computing

Peter Deutsch's 1994 list names the assumptions that hurt newcomers: the network is reliable, latency is zero, bandwidth is infinite, the network is secure, topology doesn't change, there is one administrator, transport cost is zero, the network is homogeneous. The book adds a few of its own: processing is instantaneous, clocks agree, and state is consistent. Tap each card for why it fails.

Processing isn't instantaneous: queues and backpressure

3

Clocks and time

Every node has its own clock, and clocks drift. Synchronisation (NTP) narrows the gap but never closes it. If you order events by local timestamps, a later event on a fast-clocked node can look earlier than an event that actually came first. Time is still useful (timeouts, leases), just not as an exact ordering tool. Increase the skew.

4

Partitions, partial failures and cascades

A single machine is mostly either up or down. A distributed system is usually partially failed: some nodes up, some down, some unreachable from some peers but not others. A network partition splits nodes into groups that can't talk; from inside, a partition looks exactly like a crash. Failures also cascade: a recovering node gets hammered with catch-up traffic, or clients retrying in a tight loop overload the very thing they wait for. Defences: circuit breakers, exponential backoff and jitter. Simulate a 10-second outage with 200 clients.

5

From fair-loss links to perfect links

Algorithms are built on abstract links. A fair-loss link may lose, delay or reorder messages but won't invent them, and a message sent infinitely often is eventually delivered. Add acknowledgments and resend until acked and you get a stubborn link, which delivers duplicates. Number messages and have the receiver drop duplicates (and reorder by sequence number) and you get a perfect link: reliable delivery, no duplication, no creation. TCP is this pattern.

Exactly once?Exactly-once delivery over a lossy network is impossible: the sender can't distinguish a lost message from a lost ack. What systems build is exactly-once processing: at-least-once delivery plus deduplication or idempotent operations (running twice has the same effect as running once). Charging a credit card is not idempotent; "set status = shipped" is.
6

The Two Generals' Problem

Two armies must attack together or not at all. Their generals talk only through messengers who may be captured. Agreement over an unreliable link, with no timing assumptions, is impossible: every message needs an acknowledgment, which needs an acknowledgment... Step through and see who is ever sure.

7

FLP impossibility and system synchrony

Consensus means every process starts with a value and they all decide on one. A correct protocol needs agreement (all decide the same), validity (the value was proposed by someone, not invented or a fixed default) and termination (everyone eventually decides). Fischer, Lynch and Paterson proved that in a fully asynchronous system, where a crashed process is indistinguishable from a slow one, no deterministic protocol can guarantee consensus in bounded time if even one process may crash. That doesn't make consensus impossible in practice; it means the algorithm needs some timing assumption.

Failure models

Algorithms state which failures they tolerate. Click a model. Each outer class includes the ones inside it.

Most algorithms in Part II assume crash faults and mask them with redundancy: groups of processes, so one failing goes unnoticed. Byzantine tolerance (chapter 14b) is far more expensive.
