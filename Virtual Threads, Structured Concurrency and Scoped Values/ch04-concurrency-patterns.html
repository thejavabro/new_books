Concurrency Patterns

With threads this cheap, the unit of design becomes the task. This chapter shows how to reason in tasks, how to move an existing application across, and how frameworks switch request handling to virtual threads.

1

Think in tasks, not threads

A million threads means a million lifetimes to keep track of. The book's answer is to stop thinking about threads at all and think about tasks: self-contained units of work that carry everything they need, ideally independent of other tasks. A web request is the model example. Give each task its own virtual thread, start it, and let it end. This thread-per-task model was always the simplest design; it used to be unaffordable. Tap the cards for what it buys you.

A burst of requests: pool vs thread per task

Each request waits 100 ms on a remote call and needs almost no CPU. A pool works through the burst in waves of pool-size requests; with a virtual thread per request every one can wait at the same time. Numbers are a model, not a benchmark.

2

Before you switch an existing application

Measure first. Record CPU and memory use, requests per second and response times, so you know where a change would matter and can tell whether it helped. Then remember the memory chart from chapter 1: with fewer than about a thousand concurrent threads, the switch may not be worth it. Tick what is true for your application.

3

Replace pools-as-limits with a semaphore

The quickest migration is swapping an executor for Executors.newVirtualThreadPerTaskExecutor(). That breaks one thing: some code uses a small fixed pool on purpose, for example five threads so there are never more than five database connections. With a thread per task the cap disappears. Put it back explicitly with a Semaphore: every task gets a thread, but only five hold a permit at once. Compare the two runs of ten one-second tasks.

talking to the databasewaitingdone
0.0 selapsed

try (var pool = Executors.newFixedThreadPool(5)) {   // the pool IS the limit
    for (int i = 0; i < 10; i++) pool.submit(() -> save(msg));
}
Semaphore db = new Semaphore(5);                      // the limit, made explicit
try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 10; i++) exec.submit(() -> {
        db.acquire();                                  // parks the virtual thread
        try { save(msg); } finally { db.release(); }   // always give it back
        return null;
    });
}

Same throughput, same cap. The difference is that the limit now guards the resource rather than the threads, so it can't be accidentally removed by changing the executor, and other work is never stuck behind it.

Virtual threads in Spring Boot and Quarkus

You usually don't create request threads yourself; the framework does. Both major frameworks can hand each request to a virtual thread, with a different philosophy. Switch between them and turn the feature on.


    

    

  

  
Libraries caught upSpring Boot's spring.threads.virtual.enabled needs Boot 3.2 or later and Java 21. Since JDK 24 removed pinning on synchronized, older drivers and libraries that lock with monitors around I/O no longer quietly stall carrier threads, which removes the biggest practical caveat from the book's era.

CompletableFuture on virtual threads

  
If your code already uses CompletableFuture, the minimal change is to pass a virtual-thread executor to supplyAsync or runAsync; otherwise they run on the common ForkJoinPool. It works, but the authors find it hard to read. Often you can drop the future entirely. Compare three versions that print the same line.

  

    

    
var exec = Executors.newVirtualThreadPerTaskExecutor();
CompletableFuture
    .supplyAsync(() -> greeting(), exec)
    .thenAccept(s -> System.out.println("Says: " + s))
    .join();
exec.shutdown();                       // easy to forget
Keeps the async pipeline style. Useful when you genuinely need to chain stages; otherwise ceremony.

    
try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    Future<String> f = exec.submit(() -> "Says: " + greeting());
    System.out.println(f.get());       // blocking is fine on a virtual thread
}
When you need a value back. try-with-resources closes the executor for you.

    
Thread t = Thread.startVirtualThread(
    () -> System.out.println("Says: " + greeting()));
t.join();
When you don't need a value at all. Short, and says exactly what it does.

  

  
Blocking is no longer the enemyFutures and callbacks existed largely to avoid blocking scarce threads. On a virtual thread, calling get() or join() just parks it, so straightforward blocking code is often the clearest option. For several related calls, reach for structured concurrency from chapter 2.

Measure before and afterCPU, memory, throughput and response times. Under ~1,000 threads, gains may be small.

    
Semaphores, not small poolsLimit the resource with permits; let every task have its own thread.
