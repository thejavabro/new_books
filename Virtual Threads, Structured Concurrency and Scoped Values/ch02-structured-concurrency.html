Structured Concurrency

Forking threads used to mean losing track of them. Structured concurrency ties every subtask to a code block: they start inside it, and by the time the block ends they have all finished or been cancelled.

Unstructured vs structured

Structured programming gave us blocks: a variable declared inside an if can't escape it. Structured concurrency applies the same rule to threads. Work is split into subtasks at a clear point, joined at a clear point, and no subtask outlives the block that started it. The result is a tree of tasks whose shape matches the shape of the code.

Compare that with submitting three requests to an ExecutorService and calling get() on each future. The futures know nothing about each other. If one fails, the others keep running, and if the caller gives up, nothing cancels them. Make a subtask fail and watch both styles.

The shape of every scope

Whatever the API version, a structured scope follows the same six beats. Step through them. The code shown is the book's Java 21 form; the amber box below shows the same thing in today's API.


      

    

    

  

  
The API was redesigned in JDK 25Structured concurrency is still a preview feature (JEP 505 in JDK 25, JEP 525 in JDK 26; compile with --enable-preview). The constructors and subclasses are gone. You open a scope with a static factory, pass a Joiner that decides when the scope is done, and join() returns the outcome or throws FailedException.

  

    

    
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    Supplier<Current>  now  = scope.fork(this::current);
    Supplier<Forecast> next = scope.fork(this::forecast);
    scope.join();            // wait for both, or the first failure
    scope.throwIfFailed();   // rethrow it as ExecutionException
    return new Weather(now.get(), next.get());
}

    
try (var scope = StructuredTaskScope.open()) {   // default: all must succeed
    Subtask<Current>  now  = scope.fork(this::current);
    Subtask<Forecast> next = scope.fork(this::forecast);
    scope.join();            // throws FailedException on the first failure
    return new Weather(now.get(), next.get());
}

A Subtask is a handle with a state

  
fork() hands back a Subtask. It is a sealed interface with a single private implementation, which keeps the door open for more implementations later without breaking anyone. It extends Supplier, so you can read the result with get(). Internally the implementation wraps your Callable in a Runnable that records either the result or the exception. Each subtask is in one of three states. Pick one to see what the accessors do.

  

    

    
CallOutcome

  

  
Subtasks run on virtual threads by default. The Java 21 API took a ThreadFactory in a constructor if you really wanted platform threads; in JDK 25 you pass it through the configuration, as in open(joiner, cf -> cf.withThreadFactory(factory)). The authors advise sticking with the default unless you have a compelling reason.






  
4
Putting a deadline on the whole scope

  
Plain join() waits as long as it takes. Usually you would rather fail fast. In the book's API you call joinUntil(Instant deadline), which throws TimeoutException if the deadline passes first. Drag the deadline across the three subtasks.

  

    
    

    

  

  

    

    
scope.joinUntil(Instant.now().plusMillis(550));   // TimeoutException

    
try (var scope = StructuredTaskScope.open(
        Joiner.awaitAllSuccessfulOrThrow(),
        cf -> cf.withTimeout(Duration.ofMillis(550)))) {
    // ... fork ...
    scope.join();   // cancels the scope and throws TimeoutException
}

  






  
5
Invoke all, invoke any

  
The two built-in policies are old patterns with clearer rules. Invoke all (ShutdownOnFailure) needs every result: the first failure shuts the scope down and cancels the rest. Use it for screens assembled from several related sources, such as a customer page with address, orders and balance. Invoke any (ShutdownOnSuccess) is a race: the first successful result wins and the rest are cancelled, as when asking two map providers for a route and taking whichever answers first. A failing racer is simply ignored while others can still win; only if all fail does result() throw.

Latencies are random each run.

  

  

    

    
try (var scope = new StructuredTaskScope.ShutdownOnSuccess<Route>()) {
    scope.fork(() -> mapsA.route(from, to));
    scope.fork(() -> mapsB.route(from, to));
    scope.join();
    return scope.result();     // first success; ExecutionException if none
}

    
try (var scope = StructuredTaskScope.open(
        Joiner.<Route>anySuccessfulResultOrThrow())) {
    scope.fork(() -> mapsA.route(from, to));
    scope.fork(() -> mapsB.route(from, to));
    return scope.join();       // first success; FailedException if none
}

  

  
Under the hood, both Java 21 policies are subclasses that override the protected handleComplete(Subtask) hook: on-failure records the first exception and calls shutdown(), on-success records the first result and calls shutdown(). Shutdown interrupts the subtasks still running and lets join() return.

  
Joiners replace the policy subclassesShutdownOnFailure became Joiner.awaitAllSuccessfulOrThrow() (the default) or allSuccessfulOrThrow(), which also returns the results; ShutdownOnSuccess became anySuccessfulResultOrThrow(). There are also awaitAll() and allUntil(predicate). JDK 26 is refining names and adding a timeout hook, so check the javadoc of the JDK you run.

Your own policy: the ski-trip scope

  
When neither pattern fits, write your own. The book's example plans a ski trip: ask a weather API about several towns at once, keep only the answers that came back successfully, and pick the ones reporting snow. A failed lookup for one town shouldn't sink the whole query, so this policy never shuts down early; it just collects successes. Choose towns and run the query.

  

    

    
Weather and failures are random.

    

  

  

    

    
class SuccessesOnly<T> extends StructuredTaskScope<T> {
    private final Queue<T> ok = new ConcurrentLinkedQueue<>();
    @Override
    protected void handleComplete(Subtask<? extends T> s) {
        if (s.state() == Subtask.State.SUCCESS) ok.add(s.get());
    }
    List<T> results() { ensureOwnerAndJoined(); return List.copyOf(ok); }
}

    
class SuccessesOnly<T> implements Joiner<T, List<T>> {
    private final Queue<T> ok = new ConcurrentLinkedQueue<>();
    @Override
    public boolean onComplete(Subtask<? extends T> s) {
        if (s.state() == Subtask.State.SUCCESS) ok.add(s.get());
        return false;                  // never cancel the scope early
    }
    @Override
    public List<T> result() { return List.copyOf(ok); }
}
// List<Report> all = scope.join();  with open(new SuccessesOnly<>())

  

  
The book's own listing builds the request URL with a string template (STR."..."). String templates were a preview in JDK 21 and 22 and were withdrawn in JDK 23, so use ordinary concatenation or formatted() instead.

Alternatives: futures and reactive streams

  
Structured concurrency doesn't try to replace java.util.concurrent. The two common alternatives each have a place. Tap a card.

  

  

    

    
var a = CompletableFuture.supplyAsync(this::current);
var b = CompletableFuture.supplyAsync(this::forecast);
Weather w = a.thenCombine(b, Weather::new).join();
// if a fails, b still runs to the end

    
Mono.zip(Mono.fromCallable(this::current).subscribeOn(boundedElastic()),
         Mono.fromCallable(this::forecast).subscribeOn(boundedElastic()))
    .map(t -> new Weather(t.getT1(), t.getT2()))
    .subscribe(this::show);   // a different mental model: nothing runs until subscribed

    
try (var scope = StructuredTaskScope.open()) {
    var a = scope.fork(this::current);
    var b = scope.fork(this::forecast);
    scope.join();                       // a failure cancels the other
    return new Weather(a.get(), b.get());
}

  

  
Early drafts of the API returned a Future from fork(). It was changed to Subtask because a future is most useful while it is still pending and can be chained, whereas a subtask is only read after join(), when its value is already final.

Recap on one page

  

    
Subtasks can't escapeWhen the scope's block ends, every subtask has completed or been cancelled.

    
Unstructured leaksIndependent futures don't cancel each other, and nothing cancels them when the caller gives up.

    
Fork, join, read, closeThe owner thread forks, waits in join, handles errors and closes the scope with try-with-resources.

    
Three subtask statesUNAVAILABLE, SUCCESS and FAILED decide whether get() or exception() is legal.

    
All or anyFail fast when every part is needed; race when any answer will do.

    
Custom policiesOverride handleComplete (JDK 21) or implement a Joiner (JDK 25+).

    
Still a previewRedesigned in JDK 25 and refined in JDK 26. Expect small API changes.
