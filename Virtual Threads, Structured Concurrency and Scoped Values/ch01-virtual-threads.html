Virtual Threads

Java threads used to be thin wrappers around expensive operating-system threads. Virtual threads are cheap objects on the heap that borrow a real thread only while they have work to do, so you can have millions of them.

1

A Java thread used to be an OS thread

Before Java 21 there was one kind of thread. new Thread(task).start() asks the operating system for a kernel thread, and the Java object is only a thin wrapper around it. That request is a system call, and the OS sets aside a fixed block of stack memory for the thread up front, often around 1 MB by default. The JVM can't shrink it later because it has no idea how deep the thread's call stack will go.

The book now calls these platform threads, because the platform (the OS) manages them. They haven't gone anywhere. Virtual threads are a second implementation of the same Thread class.

The model assumes about 1 MB of reserved stack per platform thread and about 1 KB of heap per shallow virtual thread; real numbers depend on the OS, JVM flags and stack depth. The authors measured with native memory tracking and saw almost no difference at 1, 10 or 100 threads, a widening gap from 1,000, and an out-of-memory error for platform threads at 100,000.

2

Pools reuse threads, and their leftovers

Creating and throwing away a platform thread per task wastes all that setup. Since Java 5 the advice has been an ExecutorService: a pool of threads that pull tasks from a queue. It helps, but two problems remain. A pooled thread that blocks on I/O just sits there instead of picking up other work, so with many small blocking tasks you run out of threads (and memory) long before the CPU is busy. And because threads are reused, anything a task leaves behind in a ThreadLocal is visible to the next task on that thread.

try (var pool = Executors.newFixedThreadPool(1)) {
    pool.submit(() -> CTX.set("tenant-A"));          // never removed
!!    pool.submit(() -> System.out.println(CTX.get())); // prints tenant-A
}
try-with-resources on executorsExecutorService has implemented AutoCloseable since JDK 19 (the book introduces it alongside Java 21). close() waits for every submitted task to finish, which is why the examples can rely on the block's end as a join point.
3

Async code scales but reads badly

Asynchronous frameworks get around the thread limit by never blocking: you register a callback and the thread moves on. Resource use is excellent and the CPU saturates before memory does. The price is code that nests callbacks inside callbacks, splits one logical flow into fragments, and loses the stack trace that Java debuggers and profilers are built around.

createUser(req, user -> {
    if (user.failed()) { reply(500); return; }
    placeOrder(user.result(), order -> {
        if (order.failed()) { reply(500); return; }
        sendMail(order.result(), mail -> {
            reply(mail.succeeded() ? 200 : 500);
        });
    });
});
try {
    User user   = createUser(req);      // blocks; the carrier is freed
    Order order = placeOrder(user);     // blocks; the carrier is freed
    sendMail(order);
    reply(200);
} catch (Exception e) {
    reply(500);                         // one place for errors, real stack trace
}

Virtual threads aim for the best of both: write plain sequential blocking code, and let the runtime do the "move on while waiting" part underneath.

4

Five ways to start a virtual thread

Virtual threads are not an OS concept at all. Creating one makes no system call and allocates no fixed stack. The stack frames live in ordinary heap objects that grow and shrink as needed, which is why one costs a few hundred bytes rather than a megabyte. Pick an API to see how it is used.


    

  

  
Not faster, just more of themA virtual thread runs its code on a platform thread, so a single one is never quicker than a platform thread. The win is throughput: many more tasks can be waiting at once without tying up real threads.






  
5
Carrier threads and the scheduler

  
Virtual threads run on carrier threads: ordinary platform threads in a dedicated ForkJoinPool, one per CPU core by default. New or unblocked virtual threads wait in a queue and get a carrier in roughly first-in, first-out order. A virtual thread keeps its carrier until it hits a blocking call; then it unmounts, its frames move to the heap, and the carrier takes the next one. What mounting actually moves

  
Mounting and unmounting is the trick that keeps the expensive resource, the carrier, busy. Step through one round trip. A task that never blocks never unmounts, so it behaves like a platform thread with a bit of extra overhead.

  

    

    

  






  
7
Pinned virtual threads

  
Some code makes it impossible to lift a virtual thread off its carrier. When that code blocks, the virtual thread is pinned: it and its carrier both sit idle. In Java 21 the main causes were blocking inside a synchronized block or method, Object.wait(), and native code reached through JNI. Short pins are harmless; long or frequent ones starve the scheduler, as the pinned mode above shows.

  
For a few cases, such as Object.wait() and many file-system calls, the JDK temporarily adds extra carriers to compensate, up to jdk.virtualThreadScheduler.maxPoolSize (256 by default). A plain blocking call inside synchronized on Java 21 got no such help, which is why replacing synchronized with ReentrantLock around blocking code was the standard advice.

  
synchronized no longer pins (JDK 24)JEP 491 reworked object monitors so a virtual thread can unmount while it holds or waits for a monitor, including inside Object.wait(). On JDK 24 and later, there is no need to rewrite synchronized code for virtual threads. Pinning remains for native frames (JNI and Foreign Function calls) and for blocking inside a class initializer. The jdk.tracePinnedThreads flag the book uses was removed in JDK 24; use the JFR event jdk.VirtualThreadPinned instead, which now reports every pinning reason.

8
When not to use virtual threads

  
Virtual threads are a tool for tasks that spend most of their time waiting. The book's warnings: never pool them (they are meant to be created and thrown away), don't use a small pool as a stand-in for a lock (use a Semaphore; chapter 4 shows how), and be careful with tasks that barely block or block very often for very short times, since each mount and unmount has a small cost. When in doubt, benchmark with JMH. Sort these situations.

Recap on one page

  

    
Platform threads are costlyOne OS thread each, with a fixed stack reserved up front. Thousands are fine; hundreds of thousands are not.

    
Pools trade one problem for othersReuse saves setup but blocked threads idle, and ThreadLocal values leak between tasks.

    
Virtual threads live on the heapNo system call, a growable stack, millions possible. Create one per task.

    
Carriers do the runningA ForkJoinPool with one carrier per core by default; virtual threads queue for them.

    
Blocking means unmountingFrames go to the heap and the carrier picks up other work. Waiting becomes cheap.

    
Pinning blocks the carrierJNI and class initializers still pin. synchronized stopped pinning in JDK 24.

    
Not a silver bulletCPU-bound or rarely blocking work gains nothing. Don't pool them; measure.
