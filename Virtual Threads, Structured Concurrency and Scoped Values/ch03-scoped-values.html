Scoped Values

ThreadLocal variables carry context such as the current user without passing parameters, but they are mutable, leak easily and get copied into every child thread. Scoped values keep the convenience and drop the problems.

1

ThreadLocal: a hidden parameter

A ThreadLocal holds one value per thread. Two threads reading the same variable each see their own copy, and neither can see the other's. In effect it is a hidden parameter that every method on the thread can read without anyone passing it.

The classic use is request context. A web request arrives, a thread picks it up, and somewhere deep in the call chain an audit log needs the user id. Threading it through every method signature is noisy, and adding a second value later (say, an audit comment) means editing every signature again. Try it.

2

Where the per-thread value really lives

The value is not stored in the ThreadLocal. Every Thread object has a field holding a ThreadLocalMap, a purpose-built hash map keyed by the ThreadLocal instance. Oddly, the map is managed by ThreadLocal's code, not by Thread: set() looks up the current thread's map, creates it if missing, and stores the entry. If you override initialValue(), the first get() on each thread fills it in. Below, a counter hands out 101, 102, 103 to each new thread.

Shared counter: 100
3

Three problems, made worse by virtual threads

Thread locals have real drawbacks, and virtual threads amplify them, because you might now have a million threads instead of two hundred.

Any code that can see the variable can call set(), and these variables are usually public static, so that is everywhere. It is global mutable state with extra steps. Click methods to let them "helpfully" overwrite the API key, then ask: which one set the value the database call used?

Pooled threads live a long time. A value that isn't removed stays reachable from the thread for as long as the thread lives, even though the map uses weak keys, and the next task on that thread can read it (chapter 1 has an animation). The fix is a disciplined finally with remove(), or an afterExecute hook on ThreadPoolExecutor. Studies of large codebases show people forget.

API_KEY.set(key);
try {
    callService();
} finally {
!!    API_KEY.remove();    // easy to forget; nothing forces you
}

With InheritableThreadLocal, each child thread gets its own copy of the parent's inheritable entries when it is created, because a mutable value may change later and the child must not see that. That is fine for a few hundred platform threads and costly for a million virtual threads. Scoped values are immutable, so children can share one reference.

Toy model: about 64 bytes of map overhead plus 48 bytes per copied entry for each child, against one shared snapshot for scoped values. The shape matters, not the exact bytes.

4

Scoped values: bind, run, unbind

A ScopedValue is declared once, with no value. You bind a value for the duration of one call with ScopedValue.where(KEY, value).run(...) (or .call(...) to return a result). Everything that call reaches, directly or indirectly, can read it with get(). When the call returns, normally or by throwing, the binding is gone. There is no set().

static final ScopedValue<String> USER = ScopedValue.newInstance();

void handle(Request r) {
!!    ScopedValue.where(USER, r.user()).run(this::process);
}
void process() { audit(); }
void audit()   { log("changed by " + USER.get()); }   // no parameter needed

Step through the book's binding example, including a rebinding: a method that already sees a value can bind a different one for the code it calls, and the outer value comes back afterwards. Scopes nest like blocks.

Several values bind by chaining: ScopedValue.where(USER, u).where(TENANT, t).run(task). Keep the number small; a long chain is the same smell as a long parameter list.

5

When nothing is bound

Calling get() outside any binding throws NoSuchElementException. Code that may run without a binding should check. Choose a situation and an accessor.

How the three problems go away

  

    
ProblemThreadLocalScopedValue

    
      
Mutable stateAnyone can set() at any time.Immutable once bound. Code can only rebind for its own callees, and the outer value returns afterwards.

      
LeaksLives until remove() or the thread dies.Unbound automatically when the call ends, even on an exception.

Bindings flow into structured subtasks

    

    
ScopedValue.where(USER, "Duke").run(() -> {
    try (var scope = StructuredTaskScope.open()) {
        scope.fork(() -> audit());     // sees USER = "Duke"
        scope.fork(() -> notify());    // sees USER = "Duke"
        scope.join();
    }
});

    
Subtasks forked in a scope inherit the owner's bindings without copying. This is safe because the scope guarantees the subtasks end before the binding does.

  

  
Final in JDK 25, with a slimmer APIThe book expected scoped values to be final in Java 23; it took until JDK 25 (JEP 506). Along the way the shortcut methods the book shows, ScopedValue.runWhere(...) and callWhere(...), were removed in JDK 24: write ScopedValue.where(K, v).run(...) or .call(...). call now takes a ScopedValue.CallableOp, which lets the lambda throw a specific checked exception, and orElse(null) is no longer allowed. No --enable-preview is needed from JDK 25 on. Thread locals are not going away; scoped values are the better default for new code that shares immutable context one way.
