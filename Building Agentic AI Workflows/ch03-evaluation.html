AI Evaluation Plus Experimentation

A demo that looks good is not evidence. This chapter turns "seems better" into numbers you can defend: the right metric for each task, and experiments that change one thing at a time.

1

Bucket the task before you pick a metric

Evaluation means systematically checking that a system meets its task's requirements: accuracy, reliability, cost, scalability. There's no single best way. What helps is sorting the work into task types, because each type has its own natural metrics.

Generative tasks

Multiple choice: reason over a fixed set of options. Easy to score.
Free text response: unbounded output (SQL, summaries, answers). Hardest to score.

Understanding tasks

Embedding: turn data into vectors for search, clustering, recommendations.
Classification: map inputs to predefined labels, via a fine-tuned head or the language-model itself.

Then make sure you have at least one of three ingredients. Without any of them you're guessing, not evaluating.

The Chapter 2 text-to-SQL workflow contains two task types: retrieving evidence is an embedding task, and writing SQL is a free response task. Each gets its own experiments below.

2

Experiment 1: which LLM should write the SQL?

The metric is SQL Query Accuracy (SQA): the share of generated queries whose result table matches the known-correct result. Six models from four providers ran the same deliberately basic prompt (the shortlist was limited to models that support structured output). Accuracy, latency, cost, and the rate of SQL that at least ran, were logged side by side.

Experiment 2: which examples, how many, and reason first?

Most people pick few-shot examples at random or write a fixed set. 4

Precision, recall and MRR, by hand

To test retrieval in isolation, run each test question through the retriever and compare what comes back with what should come back. Three metrics, each exposing a different failure. Tap results to mark them relevant, and slide k.

Precision@k: of what we fetched, how much was useful?
Recall@k: of what exists, how much did we get?
Reciprocal rank: how soon was the first useful one?

MRR is the mean of the reciprocal rank over all test queries.

5

Comparing embedders, and finding the hard domains

Seven embedders from four providers (three OpenAI, two Cohere, plus open-source Jina v3 and all-MiniLM-L6-v2) each got their own vector database holding the same evidence. Cohere's Embed V4 led on precision, recall and MRR at most k. It's the first use of autoencoding models in the book: the open ones definitely are.

Averages hide things. A Recall@10 heatmap per database exposes which domains are hard and where a different embedder wins.

Schematic: patterns follow the book (financial and formula_1 hard for everyone; european_football_2 easy despite the biggest schema; debit_card poor with open models; Cohere V3 slightly ahead of V4 on formula_1). Cell values are illustrative.

Why a domain is hardMany evidence strings overlap ("lap time", "race id") so near-misses crowd out the right one. And some evidence simply doesn't resemble the question: a question about a driver's best race paired with "full name means forename + surname" has little semantic overlap to match on.
Fixes to testFine-tune an embedder on the domain (Chapter 9). Rewrite evidence so it matches likely questions. Add an LLM gate, a multiple-choice prompt that predicts the database first, then route to the best embedder per database.
6

Case study 2: how good is a summary?

"Summarize this podcast transcript" is easy to prompt and hard to grade. No reference summaries exist, and humans reading both don't scale. The book's working definition: a summary is good if each part of the source is represented in it. Split the transcript into ten 10% chunks, embed them and the summary's chunks, and for each source chunk keep its best cosine match. The average of those ten is the score.

On long transcripts a single-shot summary scored lowest in the middle: the lost-in-the-middle problem again. The fix tried was a prompt chain: summarise each chunk separately, then either concatenate the pieces or ask for one final summary of the summaries.

Say exactly what you showedNot "model X is the best summariser", but "for this dataset, this embedder, these models and these chunking choices, model X with chunked summaries scored highest". And note what you didn't measure: here, cost and latency, both higher for chains.

Recap on one page

Bucket tasksMultiple choice, free text, embedding, classification: each has fitting metrics.
Three ingredientsGround truth, rules/rubric, or a target. Without one you are guessing.
Choose with dataLog accuracy, latency and cost side by side before picking a model.
Prompting paysSemantic few-shot plus CoT lifted SQL accuracy by roughly a third.
Retrieval is multi-sidedPrecision, recall and MRR catch different failures; slice by domain.
ReproducibleScripted experiments, fixed seeds, versioned prompts, so you can rerun as models change.
