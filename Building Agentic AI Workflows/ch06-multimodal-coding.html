Moving Beyond Natural Language: Multimodal and Coding AI

Text is only one way in or out. Models that share an embedding space across images and words, that caption and answer questions about pictures, and that write and run code open up a much wider set of workflows.

1

Five ways to build a multimodal system

Most of the internet and the world isn't text: images, video, audio, code. Multimodal systems understand, combine or generate two or more data types. The book sorts the ways to build them into five strategies. They aren't exclusive; strong systems mix several. Tap each.

2

CLIP: images and text in one vector space

Old multimodal systems glued together encoders trained separately (CNNs for images, RNNs for text) that knew nothing of each other. CLIP (OpenAI, 2021, a year before ChatGPT) trains an image encoder and a text encoder together on image–caption pairs so both land in the same space. The training is contrastive: in each batch every image is compared with every caption; matching pairs are pulled together and all the mismatches pushed apart. Press train.

CLIP's image side popularised the Vision Transformer (Google Brain, 2020): cut the image into fixed-size patches, treat each patch like a token, and run the sequence through a standard Transformer encoder, usually ordered left to right, top to bottom.

An image is worth 16 × 16 words.
CLIP → SigLIPCLIP's text encoder was GPT-2-like, reading in one direction only, and weak on long or complex captions. Google's SigLIP swapped in a bidirectional, BERT-style text encoder and beats CLIP on many retrieval and zero-shot tasks.
3

Mapping modes: generate by denoising

Text-to-image and text-to-video systems (DALL-E, Sora and the like) mostly use diffusion: start from pure noise and repeatedly apply a learned denoising step, with the prompt steering each step, until a clean picture emerges. Drag through the steps.

4

Ground in text, fuse jointly, or keep apart

Grounding converts everything into one primary modality, usually text, so a strong LLM can do the work: OCR for scans, captions for images, transcription for audio. Voice bots feel multimodal, but most do speech-to-text, run a text agent, then text-to-speech. All the reasoning and policy checks happen in text.

Joint modelling feeds both modalities through one shared Transformer so words and pixels interact directly: ViLT (an autoencoding, non-generative model) and generative VQA models such as LLaVA and Moondream. It's richer, but harder to build and hungrier for data: the model must handle text-only, image-only and mixed tasks.

Handling modalities separately fakes it: an agent calls an image generator, then later a captioner, and the models never share anything. Fast to prototype with best-in-class parts, at the cost of real cross-modal understanding.

5

Case study: searching a camera roll with CLIP, then re-ranking

The author's 3,383 personal photos become the documents. Retrieval works like RAG with an extra stage. CLIP embeds the query and each image separately (a bi-encoder: fast, each side in a vacuum) and returns the top k by cosine. ViLT then cross-encodes each query–image pair together, looking back and forth between both. That's slower but sharper. Results are re-sorted by the ViLT score, which can go negative for unrelated pairs.

      6

      Case study: visual Q&A with Moondream

      Moondream is a small open visual question-answering model: a SigLIP vision encoder, Microsoft's Phi-1.5 text decoder (1.42B parameters, despite the name), and a projection that turns image patches into embeddings concatenated with the text tokens. Phi alone can't see; the combination can. It runs on edge devices. It is not a chat model: one image, one question, no system prompt or message roles. Try its four abilities on a drawn scene.

      
  
      

      


      
  
      7
      Case study: a coding agent that draws and sees
      
  
      A coding agent's action is executable code, not a JSON tool call. One code block can call several tools, loop, use libraries and handle errors. The book's version is a two-node LangGraph loop that looks just like ReAct: generate (the LLM may emit code in a custom <<PYTHON_CODE>> tag, chosen because models use backticks when merely explaining code) and execute (run it with the tools pre-imported, feed the output or traceback back as a message, and if it failed, ask "what went wrong, and how will you fix it?").
      
  
      
    
      Task: "Get the weather in Istanbul and make an image on my desktop showing it."

      Tools are described in the prompt as function signatures with examples, not bound via a tool API, and there are no tool messages. So any chat model that can write Python works, including ones with no tool calling. The book uses Inception's Mercury, a diffusion LLM that drafts many tokens in parallel and refines them. At the time of writing its reported throughput was about 620 tokens/s against roughly 62 for GPT-4.1 and 121 for GPT-4.1-Nano, though its coding benchmarks were weaker.
      
  
      
  
      Tools: get_weather (wttr.in), image_generator (FLUX.1-dev via a Hugging Face Space, fine for demos, rate-limited for production) and Moondream captioning, so the agent can "see" by asking another model. "Find every photo with a black cat and make a collage" becomes one loop over files calling Moondream on each.
      
  
      

      


      
  
      8
      Towards any-to-any models
      
  
      Beyond text, image, audio and video lie music, PDFs, tables and sensor feeds, each with its own encoding quirks. The frontier is any-to-any: one model that takes any mix of inputs and produces any mix of outputs, with per-modality tokenizers and encoders feeding a shared core. That needs robust tokenization, dynamic fusion and reasoning over unseen combinations. Current frontier models are moving that way; we aren't fully there.
