Retrieval Augmented Generation in three parts

The model doesn't know your data, and stuffing all of it into the prompt is slow, expensive and (Chapter 1's needle problem) unreliable. RAG answers questions by looking things up first. It has three parts: an indexer that turns raw text into vectors stored in a database, a retriever that fetches the closest matches for a query, and a generator, an LLM that reasons over the query plus what was retrieved. You'll find it in support, sales and any team that lives off FAQs and knowledge bases.

2

Case study: a text-to-SQL workflow

Instead of plain Q&A, the first case study asks an LLM to write SQL for a given database schema, a very common need in companies with big, messy databases. The data is the public BIRD-SQL benchmark: more than 12,000 question–SQL pairs over 95 databases (33 GB+). The book uses 11 of those databases. Each item has four parts. Tap them (the example below is made up in BIRD's style).

Three things stand out in the data: the databases differ in how hard their questions are; their schemas differ a lot in size (more tables, fields and foreign keys to describe to the model); and there's no single right SQL. Two different queries can return the same table, so you grade by comparing results, not query text.

-- expected
SELECT name FROM drivers
ORDER BY dob DESC LIMIT 1;
-- generated
SELECT name FROM drivers
WHERE dob = (SELECT MAX(dob) FROM drivers);
Different text. Same answer?
3

The workflow, node by node

The pipeline: a user asks about a specific database; the query pulls evidence by embedding similarity; an LLM writes SQL from the query, the evidence and the schema description; a DB node runs it; if it runs, the user sees the result, otherwise a canned reply. Two simplifications for now: retrieval always happens, even for "hello", and the prompt is deliberately plain. Chapter 3 tests better ones. Everything is wired together with LangGraph, an open-source library for graph-shaped workflows and agents.

The LangGraph contractEvery node takes the shared state as its only input and returns a dictionary of updates. LangGraph merges them before the next node runs. Keep the returned keys identical to the state's field names, so you can tell at a glance what each node changes.
class State(BaseModel):
    query: str = ""
    db_id: str = ""
    k: int = 5
    context: str = ""
    sql_query: str = ""

def retrieve(state: State) -> dict:
    docs = store.search(state.query, k=state.k, filter={"db_id": state.db_id})
    return {"context": "\n".join(d.text for d in docs)}   # an update, not a new state
4

Indexing and retrieving evidence

The benchmark's "evidence" strings (hints such as "free rate = free meals / enrollment") are treated as the documents. Each is run through an embedding model and stored in a vector database (Chroma here) with four things: the vector, the raw text for the LLM to read, the database id so retrieval can filter to the right database, and any other metadata.

At query time, embed the question with the same embedder (non-negotiable) and return the k closest pieces. Drag the query below; pick a database filter; change k.

    Cosine similarity and its cousins

    Embedders are trained so similar texts land near each other. The usual comparison is cosine similarity: the smaller the angle between two vectors, the closer to 1. The hidden surprise: when every vector has length 1, cosine and the much cheaper dot product give the identical number, which is why most embedding models quietly return unit-length vectors.

    6

    Generate the SQL, then run it

    The generation node sends three things to the model: the question, the retrieved context and the schema description. It asks for a structured output with two fields, reasoning (a built-in chain of thought) then sql_query, and sets temperature to 0 so the same input gives roughly the same SQL. The DB node executes the SQL against SQLite, formats up to ten rows for the user, and on any exception returns the error text instead of crashing.

    class SQLOutput(BaseModel):
    reasoning: str = Field(description="Think step by step first")   # order matters: reason before answering
    sql_query: str = Field(description="Executable SQL")

llm = ChatModel(model="small-model", temperature=0).with_structured_output(SQLOutput)
    That's the R, the A and the GRetrieval: the evidence lookup. Augmented: a simple prompt that adds the evidence and schema. Generation: an LLM with structured outputs. On the sample school-meals question, the first run returned the correct value.
    7

    Stateless versus stateful

    The first version forgets everything between invocations: ask "who was the youngest driver?" then "what about the oldest?" and the second question arrives in a vacuum. The fix: an ask_for_user_input node that uses LangGraph's interrupt to pause for the next message, a conditional edge that ends on "exit"/"bye", and a MemorySaver checkpoint that saves the thread while it waits, however long the user takes. The SQL prompt can stay separate from the longer-running conversation.

    Recap on one page

    IndexEmbed each evidence string; store vector, text, db id and metadata.
    StateOne shared object; nodes read it and return updates with matching keys.
    RetrieveSame embedder for queries; cosine similarity; filter by metadata; top k.
    GenerateStructured output with reasoning first, temperature 0.
