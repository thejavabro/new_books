1

Case study: a policy-following support agent

Front-line support over a knowledge base is probably the most common agent job today. This case study builds a ReAct agent with one tool, a search over policy documents, and asks how well it actually uses them. There's no ready-made benchmark this time, so the first job is building a test set from unstructured documents.

Generator: go bigWriting coherent, nuanced scenarios is harder than grading against a rubric, and this dataset will be reused (including for fine-tuning in Chapter 8). Use an upper-tier model to generate.
Then check itThe author spot-checked about 5% and could trace every solution back to its article. Not proof, but a sanity check, and the set is public for others to inspect.
2

BM25: old-school keyword search still works

Instead of embeddings, the policy tool uses BM25 (Best Matching 25), the keyword ranking function that powered search for decades. It ignores meaning. It scores documents with three ingredients: term frequency with diminishing returns, inverse document frequency (rare words count more), and length normalisation so long documents don't win just by having more words. It's fast, and it handles industry jargon that general embedders blur. Edit the query or the two knobs.

A head-to-head of BM25 against several embedders and a hybrid of both is the obvious experiment here; the book leaves it as homework.

3

Experiment: what one sentence in the prompt is worth

Three agents, each on two models (GPT-4.1 and GPT-4.1-Nano), graded by a rubric (3 = correct) on the synthetic scenarios:

  1. no_db_agent: no tools; a baseline, since big models have surely read about the company online.
  2. db_agent_no_prompt: the BM25 tool, nothing said about it.
  3. db_agent_with_prompt: the same plus one sentence: always use the search tool before answering.

From the book: GPT-4.1 scored 44.4%, 47.8% and 70.7% on the three variants; Nano gained even more from the sentence. Nano used the tool 31/232 times unprompted and still skipped it 45/232 times when told to. For Nano, Chapter 8 reports 12% without tools and 23% with them; the middle Nano bar is illustrative.

A calibration problemThe bigger model was "smug": handed a tool, it essentially never used it, answering from (probably outdated) memory. It doesn't know what it doesn't know. The smaller model treated "ALWAYS" as a suggestion: weaker instructional alignment. Either way, presenting tools isn't enough; you have to say when to use them, or move that step into a workflow.

One blind spot the author flags: the test assumes every scenario is answerable. To see whether the agent will admit it lacks information, add questions no policy covers.

4

An agentic workflow for deep research

An agentic workflow is a rigid workflow where some steps are agents. Deep research (multi-step web research that ends in a cited report) is a good fit. It leans on discursive reasoning (Aristotle's step-by-step kind, as opposed to intuitive), induced with two components: planning (plan first with a strong model, then let cheaper models execute, since planning is the harder part) and reflection/re-planning (after each step, check whether the plan still holds, or critique a draft answer before the user sees it).

5

Three ways to connect agents

The deciding questionDo the agents actually need each other to solve one task? If not (the lead qualifier doesn't care what the emailer is doing), a supervisor or plain workflow handing out to-do items is enough. If they do, you need networking and shared context.
6

Handoffs in a two-agent network

The book's deliberately awkward example: Agent 1 has a calculator, Agent 2 has a weather tool, and Agent 1 is the entry point (someone has to be). Each gets a "hand off to the other agent" tool; in LangGraph a Command object says which node runs next and which messages to pass along.

The answer was right, but the ping-pong was wasteful. The obvious fixes (a router agent, or let Agent 2 go first) assume you know in advance what will be asked. In practice you design for the tasks you expect and keep updating as real traffic arrives.

7

The SDR team gets a supervisor

Chapter 4's three SDR agents had nothing tying them together. A fourth agent, woken daily by a cron job, follows simple rules: if fewer than three leads await qualification, ask the generator for more; qualify anything unqualified; email any qualified lead not yet contacted. It delegates asynchronously and moves on; it doesn't chat. The rules are hard enough to be a workflow, but a supervisor stays steerable by prompt. Run some days.

8

Experiment: does the agent pick the right tool?

An MCP server with 15 tools; 80 questions written to map to specific tools; five models from 3B to frontier size; each question asked repeatedly with a fresh thread and the tool order shuffled each time. Larger models were more accurate, as expected. Per-tool precision and recall told the more interesting story.

The suspicious zero: what would you do?

The email tool needs to, subject and body. Given vague requests, strong models asked the user for details instead of calling it, arguably the right behaviour, which the setup scored as a miss.

Positional bias in tool choice

selected − correct, percentage points (schematic)

Averaged over the five models, tools listed first were picked slightly more often than they were correct (e.g. about 20.35% selected vs 20.13% correct for positions 0–2), and the last tools slightly less. Small, but always there, whatever the descriptions say. Reasoning first (CoT, reasoning models) is the usual counter.
