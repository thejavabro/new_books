Turning the SQL workflow into an agent

An agent is an LLM, a prompt describing how to behave, tools that touch an environment, and some notion of conversation and memory. ChatGPT is one: an LLM plus a prompt (knowledge cutoff and so on) plus tools for web search and remembering things about you.

The first agent case study rebuilds the Chapter 2 text-to-SQL pipeline as an agent. The striking difference is how little code it takes. No nodes, edges or conditions: a goal, tools, and the model's trained-in drive to solve tasks. LangGraph's prebuilt ReAct agent is just two nodes in a loop, and one line (a checkpointer) makes it remember the thread, replacing dozens of lines from Chapter 2.

agent = create_react_agent(
    model=llm,
    tools=[look_up_evidence, run_sql, get_schema],
    checkpointer=MemorySaver(),        # one line of memory
    prompt="You are a helpful SQL assistant...")
What makes it an agentNot the tool-calling API. You can build agents with prompting alone (the author has a package that does exactly that). What matters is a system that notices the model asking for a tool, runs it, and passes the result back, and a model that is allowed to decide not to call a tool.
2

Three tools, and what the agent actually did

Three tools, each with arguments the model must write correctly: look_up_evidence(query, database, k) searches the vector store; run_sql_against_database(sql, database) executes and returns raw rows; get_database_schema(database) returns the tables, fields and keys. Pick a run to replay.

Across the benchmark, the agent fetched the schema in only about 80% of conversations; sometimes the evidence was enough for it to guess a working query. Occasionally it wrote SQL without saying which database to run it on, or a tool hit an exception. A tool runs independently of the model, so always catch errors and return them as text so the agent knows what happened.

Judging free-text answers with an LLM rubric

The workflow returned SQL rows you could compare exactly. The agent replies in prose. So the book grades with a rubric: a prompt for a separate LLM containing the question, the agent's answer, the ground truth and scoring rules, returning structured output (reasoning first, then a score 0–3). Try being the grader.

Question: How many races were held in 2009? Ground truth: 17.

4

Agent versus workflow: the scoreboard

Same model (a cost-effective small model), same questions. The workflow was judged by exact SQL result matching, the agent by a rubric score of 3. Accuracy came out close. The agent was slower and more expensive, because it had to spend calls fetching what the workflow simply handed over. That's why two chapters went into the workflow: the only way to know is to build both and test them on the same data.

Schematic relative values; the direction of each gap is what the book reports.

Agent evaluation looks at three things: the path (right tools, right order, how many calls), the final answer, and cost and speed, which track the number of tool calls. Some runs used zero tools and answered from memory. Most were wrong, though two chemistry questions happened to come out right.

5

The extended mind: give the agent a notebook

In 1998 philosophers Andy Clark and David Chalmers argued that memory can extend beyond the brain. Their example: Otto, who has Alzheimer's, keeps everything in a notebook, and for him the notebook works as part of his memory. For an agent, that's a tool that writes its own findings to the vector store (non-parametric memory) for later.

The experiment: empty the evidence store, give the agent a log_evidence tool, and run it over a stream of questions. Once on a slice of the plain benchmark, and once on a version where each question has synthetic paraphrases ("Where is X's hometown?" / "In which place did X grow up?").

With no starting evidence, accuracy began around 36% (versus about 51% with evidence earlier), which shows how much retrieval matters. On the plain benchmark the notes never paid off. That's actually good news for BIRD: its questions don't repeat. With rephrasings mixed in, accuracy climbed from 37.7% to 67.2%, slowly at first, once the notebook filled up. That agent also logged more and fetched the schema less, and the author is candid that he doesn't know exactly why.

Case study: a (nearly) end-to-end sales development rep

An SDR finds potential customers, qualifies them and makes first contact. The case study splits the job across three agents working on real systems: HubSpot (CRM), Resend (email), Google search via SerpApi, and Firecrawl (web crawling). The target: lecturers who might use the author's book in a course. Step through a lead's journey.

Spend where false positives hurtThe generator only points and says "they look right"; a cheap, fast model is fine because a second agent will double-check. The qualifier reads syllabi and CVs and makes the call that leads to a stranger's inbox: use a larger model there. Same tools, different context (a short rule list vs. one person plus a long requirement list).
8

MCP: tools you can plug in

Anthropic's Model Context Protocol (November 2024) standardises how tools reach models. An MCP server is an API server, in any language, that lists its tools and executes them. On start-up the agent asks each server it was given what tools it offers; after that, to the LLM, they're tools like any other. A developer in one country can publish a server that a developer elsewhere just plugs in.

A server needs three parts: a route to list tools (names, descriptions, input schemas), a route to call one, and the code that does the work. The author wrote the research server and (with an AI agent's help, using the first as an example) the five-tool HubSpot server; the TypeScript email server came from Resend itself. The caveat: an agent now meets tools of unknown quality, and one bad description can send it down the wrong path.

Why three agents instead of one?

One agent with a long prompt could do the whole thing, and you could run a hundred of them. Splitting buys control:

Think microservicesChange one agent in isolation, as long as you know how it fits the bigger picture. With one giant agent, every prompt tweak risks a regression somewhere else. (A fair counterpoint: the emailer has so little agency it could be a workflow. Chapter 5 tests assumptions like that.)

Four lenses for evaluating agents, plus tracing

Tool-efficient or token-efficient?

Agent B calls five tools with no thinking in between. Toy cost model: each tool call adds a round trip of overhead; each reasoning token costs output time. Neither is simply "more efficient".

For auditing, don't reinvent the wheel. LangSmith (from the LangGraph team) records every input, output, tool call and LLM step once a few environment variables are set, and lets you split traces by project and share links to failed runs. It's free to start and a good baseline for what any observability platform should offer.

LANGSMITH_TRACING=true
LANGSMITH_API_KEY=...
LANGSMITH_PROJECT=ai-agent
