First law: everything is a trade-off

The book revisits the first law with a common question: shared code between services, as a library or as a service? Click a row for the reasoning.

A library is tied to one language; a service can be called from any.

Library calls are in-process; service calls cross the network.

A shared service can scale on its own.

If the shared service goes down, every caller suffers.

A library version is adopted when each team is ready; a service change hits everyone at once.

Library versions multiply in every consumer; a service can version its API centrally.

Corollary 1If you think you've found something with no trade-off, you just haven't found it yet.
Corollary 2You can't do trade-off analysis once and reuse it everywhere. Context changes the answer.

Parting advice

How do we get great designers? Great designers design, of course.

The authors close by quoting Fred Brooks. Practice: katas, side projects, reviewing real systems. Analyse trade-offs every time; never stop asking why.

First lawEverything is a trade-off, and you can't do the analysis just once.
Second lawWhy is more important than how: record context and reasoning.
Third lawDecisions sit on a spectrum between extremes.
Keep practisingArchitecture skill comes from repeated design and reflection.
