Component-Based Thinking

Logical components are the building blocks of every architecture. This chapter shows how to find them, how to avoid the entity trap, and how to manage the coupling between them.

Logical versus physical architecture

Logical components are the functional building blocks: what the system does. The physical architecture is how they are deployed: services, databases, messaging. Architects must design the logical view first; many teams skip it and get lost. Toggle.

A component is usually a namespace or directory, like app/order/placement. It contains the source code for that behaviour.

The same behaviour mapped onto runtime pieces. The style chosen later decides this mapping.

3

The entity trap

A tempting shortcut: one component per database table, each called a Manager. The result is a CRUD layer, not an architecture: workflows smear across every manager. Compare.

Each component mirrors a table. Placing an order calls four managers. Business logic has nowhere to live, so it leaks everywhere. This is really an ORM, not architecture.

Components are named after what they do. Cohesion is about behaviour, so changes to one workflow stay inside one component.

4

Coupling and the Law of Demeter

Afferent and efferent coupling apply to components too. The Law of Demeter (principle of least knowledge) says a component should know as little as possible about others. Moving knowledge reduces one component's coupling, but someone else now carries it.

Order Placement checks stock, and when it is low, it orders more from the supplier itself. Efferent coupling: 4.

Inventory decides on reordering. Order Placement drops to 3 dependencies. Note: total coupling in the system did not change, only who holds it. That is still a trade-off.
