Service-Based Architecture Style

A pragmatic distributed style: a handful of coarse domain services, usually sharing a database. Many of the benefits of distribution with far less pain.

Topology: a few coarse domain services

Service-based architecture is a pragmatic distributed style: a separately deployed UI, roughly 4 to 12 coarse-grained domain services, and usually one shared database. The book uses the Going Green electronics recycler. Toggle the variants.

The classic form. Services are independent deployments but share data, so you keep SQL joins and ACID transactions inside a service.

An API layer or gateway can handle cross-cutting concerns such as security and metrics, and hide the services from the outside.

Data can be split into domain-scoped databases when services don't share tables. More isolation, less coupling to schema changes.

2

Coarse services keep transactions simple

Because each service is a whole domain, a business workflow usually happens inside one service with a local ACID transaction. Split the same domain into fine-grained services and you need distributed transactions. Step through.

3

UI options

The UI can be a single monolithic front end, one UI per domain, or one per service. Click each.

Simplest. One deployment for all screens.

Going Green might have a customer-facing UI (quoting) and an internal one (receiving, assessment, accounting).

Maximum independence and scalability per area, at the cost of consistency and more deployments.

4

Characteristics ratings

Service-based: characteristics scorecard

Stars follow our reading of the book's scorecard: 1 means poorly supported, 5 means a core strength. Check the book's figure for the authors' exact ratings.

No five-star ratings, but four stars in many vital areas: deployability, fault tolerance, modularity, testability, reliability. Scalability is three stars because services are coarse; elasticity two. It is one of the most pragmatic styles in the book.

5

When to use it

Use whenDomain-driven teams; you want independent deployments and better fault tolerance without microservices complexity; data needs ACID inside a domain.
Watch out forShared-database schema changes ripple across services; services that talk to each other a lot; the style creeping toward too many services.
