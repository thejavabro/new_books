Space-Based Architecture Style

Built for extreme and unpredictable load: replicated in-memory data grids replace the central database in the request path.

1

Topology: take the database out of the path

Most systems scale their web servers fine and then choke on the database. Space-based architecture removes the database from synchronous processing: data lives in replicated in-memory grids inside each processing unit, and updates flow to the database asynchronously. Click each part.

Processing unit

App code plus an in-memory data grid. Many copies run; each holds the data it needs in memory, replicated between instances.

Messaging grid

Routes incoming requests to an available processing unit, like a smart load balancer that also manages sessions.

Data grid

The replicated cache inside every processing unit. The heart of the style: no central database in the request path.

Processing grid

Optional orchestrator when one request needs several processing-unit types.

Deployment manager

Starts and stops processing units as load changes: the source of elasticity.

Data pumps

Asynchronously send cache updates to the database, usually via a queue.

Data writers / readers

Writers persist pumped updates; readers load data into caches on startup or after a crash.

2

Elasticity: scale with the crowd

The deployment manager adds processing units as load rises and removes them as it falls. Because no unit waits on a database, the system can absorb sudden spikes, like concert tickets going on sale. Drag the load.

3

Data collisions: calculate the risk

With replicated caches, two units can update the same row before replication finishes. Both caches end up wrong. Inventory 500 → A sells 10 (490), B sells 5 (495) → replication overwrites each with the other: both wrong, should be 485. The book gives a formula: collisions = N × (UR² / S) × RL. Play with it.

4

Replicated or distributed cache?

Extremely fast (local memory), fault tolerant, but limited by memory per unit and prone to collisions with high update rates. Good for small, read-heavy data.

One external cache: consistent and handles large volumes, but slower (remote calls) and a fault-tolerance concern. Good for large, frequently updated data.

A near-cache hybrid (local front cache + distributed backing) is possible but the book cautions about inconsistent front caches across units.

5

Characteristics ratings

Space-based: characteristics scorecard

Stars follow our reading of the book's scorecard: 1 means poorly supported, 5 means a core strength. Check the book's figure for the authors' exact ratings.

Elasticity, scalability and performance are all five stars: the reason the style exists. Simplicity and testability are its worst: simulating 100,000 concurrent users in test is hard and expensive, and caching plus async persistence is complex.

6

Where it fits

Concert ticketingHuge spikes the moment sales open; seat counts in memory; elasticity is everything.
Online auctionsBursty bidding near the end; bid data in memory; async write to the database.
