Modularity is not granularity

Modularity is about breaking a system into logical parts: grouping related code. Granularity is about the size of those parts. You can be well modularised and still have the wrong granularity. Toggle the views.

Three logical groupings. Each module holds related classes and hides its internals. This is the logical, organisational view.

The same system split into nine deployable pieces. Granularity asks: how big should each be? Too fine, and you pay in communication and coordination.

2

Cohesion: how well the parts belong together

Cohesion measures how related the parts inside a module are. The book lists seven kinds from best to worst. Click each bar.

Functional cohesion

Every part relates to the others and the module contains everything needed to function. Best.

Sequential cohesion

Output of one part is input to the next.

Communicational cohesion

Parts form a chain operating on the same data, like writing a record then emailing it.

Procedural cohesion

Parts must run in a particular order.

Temporal cohesion

Parts are grouped by timing, like startup tasks.

Logical cohesion

Related logically but not functionally, like a StringUtils class.

Coincidental cohesion

Elements are in the same module only by accident. Worst.

LCOM (Lack of Cohesion in Methods) is the structural metric: it counts sets of methods that share no fields. A class whose methods split into separate islands is really two or three classes wearing one name.

See LCOM in action

A class with three fields and four methods. Lines show which method uses which field. Switch versions and watch the islands appear and disappear.

Three islands: m1 and m2 share a, m3 uses only b, m4 only c. High lack of cohesion. This class could be three classes.

Two islands: m2 bridges a and b, but m4 still stands alone with c. Better, but m4 probably belongs elsewhere.

One island: every method connects to the others through shared fields. Low LCOM, a cohesive class.

Coupling, abstractness and instability

Afferent coupling (Ca) counts incoming dependencies; efferent coupling (Ce) counts outgoing ones. From these come instability I = Ce / (Ca + Ce) and abstractness A = abstract types / all types. Plot a module against the main sequence, the line A + I = 1. Use the sliders.

5

Connascence: a finer language for coupling

Two components are connascent if changing one forces a change in the other to keep things correct. Static forms are visible in the source code; dynamic forms only appear at runtime. Weaker forms are easier to refactor. Click a bar.

Connascence of Name static

Components agree on the name of something. Renaming breaks callers, but IDEs fix it.

Connascence of Type static

Components agree on a type.

Connascence of Meaning static

Components agree on what a value means, e.g. true = 1. Replace magic values with named constants.

Connascence of Position static

Components agree on parameter order: update(street, city) vs update(city, street).

Connascence of Algorithm static

Components agree on an algorithm, like the same hash on client and server.

Connascence of Execution dynamic

Order of execution matters: set the recipient before calling send().

Connascence of Timing dynamic

Timing matters, as in a race condition between two threads.

Connascence of Values dynamic

Several values must change together, as in a distributed transaction.

Connascence of Identity dynamic

Components must reference the same instance, like two parts sharing one queue object.

StrengthRefactor towards weaker forms: turn position into name with named parameters, meaning into a named constant.
LocalityStrong connascence is acceptable inside one module; across modules it is dangerous.
DegreeHow many things are affected. Connascence touching two classes is far less risky than touching two hundred.
