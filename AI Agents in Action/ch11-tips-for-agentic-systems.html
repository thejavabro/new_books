Tips for Building Agentic Systems

Field-tested advice, organised by the five layers, then applied to three systems people actually build: a customer support agent, a RAG system and a deep research agent. Use this page as a checklist for your own agent.

1

Audit your agent, layer by layer

Optimise each layer independently, then integrate. Pick a layer, tick what your agent already does, and watch the stack fill in.

2

Write the persona as an API contract

Not prose: a clear role, explicit boundaries, a defined output, and an "I don't know" off-ramp. Inject dynamic facts (date, organisation, user) at runtime so they never go stale. Keep the scope narrow.

same tricky question: "Can I get a refund on a 2019 order and also, what's the weather?"

  






  
3
Tools the model can use well

  
The model learns your tools from their schemas: name, docstring, typed parameters. Make each tool do one thing. Control when tools run (tool choice, parallel calls) and stop early when one call suffices. Plan for failure: timeouts, retries, graceful error payloads, fallbacks.

  

    

    

  






  
4
Blueprint: a customer support agent

  
A real support agent is several cooperating agents: triage → retrieval → grounding → action with guardrails → answer. Narrow the charter first (orders, returns, status), check identity before touching account data, and always offer escalate_to_human. Send a request through.

  

    

    

    

  






  
5
Blueprint: a RAG agent system

  
Modular roles: router/triage → retriever → answerer, optionally a critic for corrective retrieval (CRAG). Use an agentic orchestrator only when one-shot RAG is not enough. Toggle the retrieval optimisations the chapter lists and see the trade-offs (illustrative).

  

    

    

    

    

  






  
6
Blueprint: a deep research agent

  
Two-tier orchestration: a planner (the brain) delegates to stateless workers (the hands) for search, extraction, analysis and writing. No claim without a cited source; a critic fact-checks before the final report; partial findings stream to the user; caches dedupe repeated queries and budgets cap tokens and calls.

Recap on one page

  

    
PersonaContract, not prose; narrow scope; typed outputs; dynamic instructions; "don't know" off-ramp.

    
ToolsSingle-purpose, crisp names and docstrings, typed params; control tool choice; plan for failure.

    
ReasoningReAct or CoT; plan then execute; cap iterations; quick self-review.

    
KnowledgeRAG as a tool; session vs long-term memory; hybrid search; ground strictly; fresh, partitioned data.

    
EvaluationTrace everything; automated evals per change; HITL; guardrails at input, tool and output; AIOps.

    
Production-readyTight personas, scoped tools, explicit reasoning, grounded knowledge, continuous evaluation.
