Managing Transactions with Sagas

When each service owns its own database, one business transaction becomes many local ones. A saga strings them together with messages and undoes completed steps with compensating transactions when something fails.

1

Why distributed transactions don't fit

In the monolith, createOrder() runs in one ACID transaction. Now the data it touches lives in the Order, Consumer, Kitchen and Accounting services, each with a private database. The textbook answer is a distributed transaction: the X/Open XA standard and two-phase commit (2PC). The book rejects it for three reasons.

Participants in the 2PC transaction

With 2PC, every participant must be up for the transaction to commit, so availability is the product of all of them. Eric Brewer's CAP theorem says that under a network partition you choose consistency or availability; modern architects usually choose availability.

2

A saga: local transactions plus compensations

The Saga pattern maintains data consistency across services with a sequence of local transactions, each in one service, each triggered by the completion of the previous one via a message. Every step commits immediately, so a saga can't simply roll back: if a later step fails, earlier steps are undone by compensating transactions, run in reverse order. Here is the Create Order Saga. Steps that are only checks (verify consumer, authorize card) or that come after the last possible failure need no compensation. Only createOrder and createTicket have undo actions: rejectOrder and rejectTicket.

3

Coordinating a saga: choreography or orchestration

Someone has to decide which step runs next. With choreography there is no central coordinator: each participant subscribes to the others' events and reacts. With orchestration a saga orchestrator object sends command messages to participants and reacts to their replies. Compare the happy path of the same saga.

ChoreographyOrchestration
GoodSimple for small sagas; loose coupling, since participants only subscribe to events.Simpler dependencies (no cycles); less coupling between participants; business logic of the saga lives in one place; can be modeled as a state machine.
BadHard to understand: the logic is spread across services. Risk of cyclic dependencies. Each participant must subscribe to everything that affects it.Risk of centralizing too much business logic in the orchestrator, leaving dumb services. Keep it to sequencing.
The book's adviceUse choreography for simple sagas, orchestration for anything complex. And publish events or send commands reliably: the participant must update its database and send the message atomically (the transactional outbox from chapter 3).
4

Orchestrators as state machines

An orchestrator is naturally a state machine: states plus transitions triggered by replies from participants. That makes it easy to design, implement and test. Click a reply to fire a transition.

5

ACD, not ACID: the lack of isolation

A saga is atomic (all steps run or all are compensated), consistent and durable, but not isolated: other sagas see its intermediate results. That causes the classic anomalies. Watch a lost update.

6

Countermeasures, and the anatomy of a saga

Lars Frank and Torben Zahle's 1998 paper names countermeasures that reduce or remove anomalies. To apply them, first classify each saga step. Compensatable transactions can be rolled back. The pivot transaction is the go/no-go point: once it commits, the saga runs to completion. Retriable transactions follow the pivot and are guaranteed to succeed eventually. 7

Inside the Order Service

The book builds the Create Order Saga with the Eventuate Tram Saga framework. The OrderService creates the Order and the saga instance in one transaction. The CreateOrderSaga is a singleton that defines the state machine with a small DSL; per-run state lives in a CreateOrderSagaState object persisted by the framework. Proxy classes such as KitchenServiceProxy describe each participant's command channel. OrderCommandHandlers handle the commands that the saga sends to Order Service itself. Here is the idea, in pseudo-Java of our own.

// a saga definition reads like the steps table
saga = step()
    .withCompensation(order.reject)                       // 1 createOrder() happened in OrderService
  .step()
    .invokeParticipant(consumer.validate)                 // 2
  .step()
    .invokeParticipant(kitchen.createTicket)              // 3
    .onReply(TicketCreated, state::rememberTicketId)
    .withCompensation(kitchen.rejectTicket)
  .step()
    .invokeParticipant(accounting.authorize)              // 4 pivot
  .step()
    .invokeParticipant(kitchen.approveTicket)             // 5 retriable
  .step()
    .invokeParticipant(order.approve)                     // 6 retriable
  .build();
