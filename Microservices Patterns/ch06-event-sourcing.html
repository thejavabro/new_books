Event Sourcing

Instead of saving the current state of an aggregate, save every change as an event, and rebuild the state by replaying them. You get an audit log and reliable event publishing for free, at the price of a new way of thinking.

1

The trouble with storing only current state

Traditional persistence maps classes to tables and rows to objects: an ORDERS row holds the order as it is right now. That works, but it has drawbacks: an object-relational impedance mismatch, no history (an update overwrites the past), audit logging you must bolt on and keep in sync, and event publishing that is an afterthought, which is easy to get wrong.

Pattern: Event sourcingPersist an aggregate as a sequence of domain events that represent state changes. Rebuild the current state by loading the events and replaying them.
2

Rebuild state by replaying events

Instead of an ORDERS table, there is an EVENTS table: one row per event, with the aggregate's type and ID, the event type and the event data. Send commands to an order, then drag the replay slider back in time. The current state is just a fold over the events.

EVENTS for Order 7

Two kinds of method

class Order {
  // process(command): validate, decide, return events. Never mutates state.
  process(CancelOrder cmd) {
    if (state != APPROVED) throw new UnsupportedStateTransition();
    return [ new OrderCancelled() ];
  }
  // apply(event): update state. Never fails; used for new and replayed events.
  apply(OrderCancelled e) { state = CANCELLED; }
}

A command method no longer changes fields directly. To handle a command: load the events, replay them with apply(), call process() to get new events, apply those too, and append them to the event store. Creation works the same way: process(CreateOrder) returns OrderCreated.

3

Concurrent updates: optimistic locking

Two requests can update the same aggregate at once. The event store uses the aggregate's version (the number of events applied) as an optimistic lock: an append succeeds only if the version is still what the writer read.

Stored version: 3

Publishing comes almost for free: the event store is the outbox. A relay polls the EVENTS table for unpublished rows, or tails the transaction log, and pushes events to the broker. Consumers still have to be idempotent; with an RDBMS-based event store they record processed message IDs in the same transaction, and with a NoSQL store the message ID can be stored with the events the handler generates.

4

Snapshots for long-lived aggregates

A long-lived aggregate, such as an Account, may have thousands of events. Loading it means replaying them all. A snapshot stores the aggregate's state every N events; to load, read the latest snapshot and replay only the events after it.

5

Evolving domain events: upcasting

Events are stored forever, but their schema changes. Adding a field is backward compatible; renaming or removing one is not. Rather than rewriting history, an event-sourced app upcasts: when old events are loaded from the store, a transformer converts them to the latest version before the application sees them.

Benefits and drawbacks

  

  
Deleting data is a special headache: the GDPR "right to be forgotten" meets an append-only log. One technique is to encrypt each user's data with a per-user key and delete the key; another is pseudonymization, replacing identifying data with tokens. Try the first.

Implementing an event store

  
An event store is a hybrid of a database and a message broker. Options include purpose-built ones (Greg Young\'s .NET Event Store, Lightbend\'s Lagom, the Axon framework) or the author's Eventuate: Eventuate SaaS, and Eventuate Local, built on MySQL plus Apache Kafka. Tap a part of Eventuate Local.

  

    

    

  

  
The Eventuate client framework gives you a base class for aggregates (ReflectiveMutableCommandProcessingAggregate, which dispatches process() and apply() by reflection), an AggregateRepository with save/find/update, and annotations for event subscribers.






  
8
Sagas with event sourcing

  
Choreography is natural with event sourcing: aggregates emit events when they change, and participants subscribe. One wrinkle: an event handler must also record events for things like "card not authorized" even when no state changes, because events are the only way to say something. Orchestration needs care. Step through creating an orchestrator atomically.

  

    

  

  
Orchestrators can be event-sourced tooPersist the orchestrator as events (SagaOrchestratorCreated, SagaOrchestratorUpdated). Sending a command becomes a two-step trick: first save a SagaReplyRequested-style pseudo event, then a handler for that event sends the command. Participants must reply even when processing a duplicate, which they handle with the same pseudo-event approach. The result: an application that uses only an event store.
