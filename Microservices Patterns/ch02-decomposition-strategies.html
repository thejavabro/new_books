Decomposition Strategies

Microservices are an architectural style about maintainability, testability and deployability. The hard part is finding the services. This chapter gives a repeatable process: find the system operations, pick the services, then define their APIs.

1

What software architecture is, and why it matters

Architecture is the decomposition of a system into parts and the relationships between them. Philippe Kruchten's 4+1 view model describes it from four angles, each with its own elements and relations, tied together by scenarios. Tap a view.

Why bother?An application has functional requirements (what it does) and quality requirements, the -ilities: maintainability, extensibility, testability, deployability, scalability, reliability. You can meet the functional ones with almost any architecture, even a big ball of mud. The architecture is what decides the -ilities, and those decide how fast you can develop.
2

Architectural styles, and microservices as one

An architectural style is a family of architectures: a vocabulary of element types and constraints on how to combine them. Two you meet in every Java shop are the layered style and the hexagonal style. Toggle between them, then look at what the microservice style constrains.

3

A three-step process for defining the architecture

There is no mechanical algorithm, but there is a repeatable process. It starts from requirements (user stories and scenarios) and works in three steps. In practice you iterate: decisions in later steps send you back to earlier ones.

4

Step 1: find the system operations

First, sketch a high-level domain model from the nouns in the user stories (Consumer, Order, Restaurant, Courier, MenuItem, Address...). Then turn each request the application must handle into a system operation. Operations come in two kinds: commands create, update or delete data; queries read it. Each command gets a spec of parameters, return value, preconditions and post-conditions written in terms of the domain model. Classify these FTGO operations.

Step 2a: decompose by business capability

A business capability is something a business does to generate value: what it does, not how. "Deposit a check" stayed the same while the how moved from teller to ATM to phone camera. That stability makes capabilities a good basis for services. Organize FTGO's capabilities into a hierarchy, then map them, at whatever level fits, onto services. Tap a capability to see which service owns it.

Step 2b: decompose by subdomain (DDD)

Domain-driven design takes a different route to a similar result. Rather than one enterprise-wide model, which never gets agreed, DDD gives each subdomain its own domain model, and the scope of each model is a bounded context. In a microservice architecture each bounded context becomes a service or a small set of services. The same word can mean different things in different contexts. Pick a context to see what "order" means there.

Two principles to steer bySingle Responsibility Principle: a class, and a service, should have one reason to change. Common Closure Principle: things that change together for the same reason belong together. Packaged into one service, a change in a business rule then touches one team's code, not five.
7

Obstacles, and the god class

Decomposition looks simple on a whiteboard. Five obstacles get in the way: network latency (chatty services; batch APIs or merging services help), reduced availability from synchronous calls (chapter 3), data consistency across services (sagas, chapter 4), a consistent view of data across databases, and god classes.

A god class is a bloated class used everywhere. FTGO's Order has fields for ordering, kitchen preparation, delivery and payment. Every service seems to need it. The DDD answer: give each service its own model with its own version of the concept. Tap a field to see where it ends up.

8

Step 3: define the service APIs

Assign each system operation to the service that owns its data, then work out which collaborations each operation needs. createOrder() lands in the Order Service, but it must verify the consumer, validate the order with the restaurant, create a kitchen ticket and authorize the card. Each collaboration adds an operation to another service's API. Step through.

At this stage the API is abstract: operations and events, not yet REST or messaging. Chapter 3 picks the IPC technology; chapter 4 turns this collaboration into a saga.
