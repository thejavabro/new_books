Implementing Queries

Data is private to each service, so a screen that shows an order with its ticket, delivery and bill has to gather it from several places. Two patterns do the job: compose API calls, or keep a dedicated read model up to date with events.

1

Queries across private databases

Chapter 4 handled updates that span services. Queries have the same problem. FTGO's findOrder(orderId) powers the order-status screen of the mobile app: it needs the order (Order Service), the kitchen ticket status (Kitchen Service), the delivery status and courier location (Delivery Service), and the payment status (Accounting Service). No service has it all, and no one may join across their databases.

2

The API composition pattern

An API composer calls the provider services that own the data and combines the results in memory. Step through, and compare calling the providers one after another with calling them in parallel.

A composer should call independent providers concurrently, typically with a reactive style (CompletableFuture, RxJava, Project Reactor). Sometimes one call depends on another's result, which forces some sequencing.

3

When composition hurts

API composition is simple and should be your default. But it has drawbacks: increased overhead (many requests and database queries per query), reduced availability (every provider must answer) and no transactional consistency (providers answer at slightly different moments). For availability, a composer can return cached data or a partial result. Take a service down.

The worst case is a query that filters on data owned by several services. findOrderHistory(consumerId, filter) lets a consumer search past orders by keyword, and the keyword may match a menu item (Order Service) or the restaurant name (Restaurant Service). The composer must pull everything and do an in-memory join.

4

Command query responsibility segregation

CQRS splits the persistent model in two. The command side handles create, update and delete with its own database and publishes domain events. The query side keeps one or more views, read-only databases shaped for particular queries and kept up to date by subscribing to events. A query side can live inside the service, or be a separate query-only service, such as an Order History Service that subscribes to events from several services. Run the flow.

5

Living with eventual consistency

The view always trails the command side a little. A client that updates and then immediately reads may not see its own change. Two remedies from the book: the command returns a token (for example, the ID of the published event), and the client polls the view until the view has caught up to that token; or the client updates its own local model optimistically from the command's response, and refreshes later.

Adding a new view, or changing one, means building it from scratch by replaying events. Brokers don't keep messages forever, so older events come from an archive (for example, in S3) processed with a big data tool such as Spark, combined with snapshots, then the view catches up with live events.

7

Example: an order history view in DynamoDB

The book implements findOrderHistory() in an Order History Service that stores a view in AWS DynamoDB. OrderHistoryEventHandlers subscribe to events and call OrderHistoryDao. The table ftgo-order-history has one item per order, keyed by orderId. A global secondary index keyed by consumerId with creation time as the sort key serves the query, newest first, with pagination and a filter expression for keywords and status. Updates are conditional so duplicate or old events are ignored. Query it.
