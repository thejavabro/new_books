Interprocess Communication

Services are separate processes, so every collaboration goes over the network. This chapter compares interaction styles, synchronous RPC and asynchronous messaging, and the techniques that make each reliable.

1

Interaction styles

In a monolith, modules call each other with method calls. In a microservice architecture, services are separate processes, so they must use interprocess communication (IPC). Before picking a technology, pick an interaction style. Two dimensions: is it one-to-one or one-to-many, and is it synchronous (the client waits, and may even block) or asynchronous?

2

Defining and evolving APIs

Whatever the IPC, a service's API is a contract. The book recommends API-first design: write the interface definition (OpenAPI for REST, a .proto file for gRPC, channels and message types for messaging) and review it with client developers before you write code.

APIs change, and in a microservice architecture you can't update all clients in lockstep. Use semantic versioning: MAJOR for incompatible changes, MINOR for backward-compatible additions, PATCH for compatible fixes. Make clients and servers follow the robustness principle: be conservative in what you send, liberal in what you accept, so additions don't break anyone. Message formatsText formats (JSON, XML) are self-describing and readable, and a consumer can ignore fields it doesn't know. They are verbose and slow to parse. Binary formats (Protocol Buffers, Avro) are compact and typed via a schema, which makes compatibility easier to check, but you need tooling. Avro readers need the writer's schema; Protocol Buffers uses tagged fields.
3

Synchronous RPI: REST and gRPC

In the Remote procedure invocation pattern, the client's business logic calls a proxy interface; a proxy adapter sends the request, and a server adapter calls the service's business logic. REST models the API as resources addressed by URLs and manipulated with HTTP verbs. Leonard Richardson's maturity model rates how RESTful an API is. Climb the levels.

// gRPC: the API is a protocol-buffers IDL, compiled into client and server stubs
service OrderService {
  rpc createOrder(CreateOrderRequest) returns (CreateOrderReply);
  rpc cancelOrder(CancelOrderRequest) returns (CancelOrderReply);
}
message CreateOrderRequest { int64 consumerId = 1; repeated LineItem items = 2; }

gRPC is a binary, HTTP/2-based framework with compact messages, efficient streaming in both directions, and a natural place for operations that don't fit CRUD. On the downside, JavaScript clients and older firewalls may struggle with it.

4

Partial failure and the circuit breaker

A remote service can be down or, worse, slow. If the Order Service keeps waiting on an unresponsive dependency, its threads pile up and it fails too: a cascading failure. The book's recipe: network timeouts, a limit on outstanding requests, and the Circuit breaker pattern, which stops calling a service once its error rate crosses a threshold and tries again after a cool-off. Service discovery

Service instances come and go, with addresses assigned dynamically. Clients need a service registry: a database of available instances. There are two families. Toggle them.

6

Asynchronous messaging

With the Messaging pattern, services exchange messages over channels. A message has a header (an ID, maybe a return address) and a body. There are three kinds: a document (just data, such as a reply), a command (please do X) and an event (X happened). Channels are either point-to-point (one consumer gets each message: good for commands) or publish-subscribe (every subscriber gets a copy: good for events).

7

Scaling consumers without losing order, and handling duplicates

To scale, you run several instances of a consumer as competing receivers. But then two updates to the same order can be processed out of order. The fix, used by Kafka and Kinesis, is a sharded (partitioned) channel: the sender puts a shard key such as the order ID on each message, all messages with that key go to the same shard, and each shard is read by one consumer instance at a time. Send some events.

Most brokers promise at-least-once delivery, so a crash can redeliver a message. Either write idempotent handlers, or record the IDs of processed messages in the same database transaction as the business update and discard repeats.

8

Transactional messaging: the outbox

A service usually needs to update its database and send a message, atomically. If it commits and then crashes before sending, the message is lost; if it sends first and then the transaction rolls back, it has announced something that never happened. Distributed transactions across the database and broker are not an option for most modern brokers. The Transactional outbox writes the message into an OUTBOX table in the same local transaction, and a separate message relay publishes it. Step through.

Frameworks such as the author's Eventuate Tram package these patterns (plus duplicate detection and command and reply channels) behind simple APIs, so you don't use a raw broker client directly.
