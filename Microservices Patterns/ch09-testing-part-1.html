Testing Microservices, Part 1

Automated tests are what let you change a service quickly and safely. This chapter sets up the strategy: the test pyramid, stubs and mocks, a deployment pipeline, and unit tests for each kind of class in a service.

1

What a test is, and test doubles

Microservices only pay off if you can change a service quickly and safely, and that requires automated tests. A test verifies the behavior of a system under test (SUT), which may be a class, a cluster of classes, a service or the whole application. Each test has four phases.

1 SetupBuild the fixture: the SUT and its dependencies, in the right state.
2 ExerciseInvoke the SUT.
3 VerifyAssert on the result and the SUT's new state.
4 TeardownClean up, e.g. roll back a database transaction.

Dependencies make tests slow and complicated, so we replace them with test doubles. A stub returns values to the SUT. A mock lets the test verify that the SUT called the dependency correctly (and is often a stub as well). Toggle to see the difference on an OrderController test.

The test quadrant and the test pyramid

Tests differ in scope: unit (a class), integration (a service with its infrastructure or another service), component (acceptance tests for one service) and end-to-end (the whole application). Brian Marick's test quadrant sorts tests by two other axes. Tap a quadrant.

Mike Cohn's test pyramid says how many of each to write. Higher tests are slower, more complex and more brittle, so write lots of unit tests and very few end-to-end tests. Drag the mix and see what a test run costs.

3

The challenge: testing interactions without everything running

Most bugs in a microservice app hide in the interactions: REST calls, published events, commands and replies. End-to-end tests catch them but are slow and fragile. The answer is consumer-driven contract testing: the consumer team writes contracts, example request/response or message pairs, and they are used twice. Step through it for the API gateway (consumer) and Order Service (provider).

// a contract, sketched in plain JSON (Spring Cloud Contract uses a Groovy DSL; Pact is the other popular family)
{ "request":  { "method": "GET", "url": "/orders/99" },
  "response": { "status": 200,
                "body": { "orderId": 99, "state": "APPROVED" } } }
Tests, not documentationA contract test checks that the provider's API matches what the consumer expects: the shape of requests and responses. It doesn't test the provider's business logic. Contracts also exist for messaging: an event-publishing contract is an example event; a command contract is an example command and reply.
4

The deployment pipeline

Every service gets its own deployment pipeline: the automated route from a commit to production, run by a CI server such as Jenkins. Fast tests run first for quick feedback; slower ones later. Push a commit.
