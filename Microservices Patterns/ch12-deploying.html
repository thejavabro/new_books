Deploying Microservices

Deployment has moved from copying a WAR file onto a hand-built server to declaring what should run and letting a platform make it so. This chapter walks the four main patterns and the trade-offs between them.

1

Four ways to deploy a service

Deployment combines a process (the steps people and automation take to get code into production) and an architecture (the environment it runs in). Both changed enormously: from hand-copying WAR files to hand-tended servers, to declaring what should run and letting a platform keep it running. A production environment must provide a service management interface, runtime service management (keeping instances running), monitoring, and request routing. The book covers four patterns. Compare them.

The book's rule of thumbChoose the most lightweight pattern that meets the service's needs, evaluating in this order: serverless, then containers, then VMs, then language-specific packages.
2

Language-specific packages and virtual machines

Pack services onto a machine and see what each pattern isolates. In the language-specific package pattern, a JVM may even host several WARs, so a runaway service can starve its neighbors. With a service per VM, each instance is a VM image (an AWS AMI built with tools such as Netflix Aminator or Packer, or deployed with Elastic Beanstalk): fully isolated, but heavy.

3

Service as a container, with Docker

A container is OS-level virtualization: an isolated sandbox with its own process, network and file-system view, sharing the host's kernel. You can limit its CPU and memory. Build, push, run. Step through.


  

  






  
4
Kubernetes: a Docker orchestration framework

  
Running containers on one machine is easy; running hundreds across a cluster isn't. Kubernetes turns a set of machines into one pool of resources, schedules containers onto them, restarts failed ones, and routes requests to them. Tap a part.

  

    

    

  

  
# a Deployment, in spirit (abridged, our own example)
kind: Deployment
metadata: { name: restaurant-service }
spec:
  replicas: 2
  template:
    spec:
      containers:
      - image: ftgo/restaurant-service:1.1
        env: [ { name: DB_URL, valueFrom: { secretKeyRef: ... } } ]
        readinessProbe: { httpGet: { path: /actuator/health, port: 8080 } }
        livenessProbe:  { httpGet: { path: /actuator/health, port: 8080 } }

  
A Service object gives the pods a stable DNS name and IP and load-balances across them (server-side discovery from chapter 3). To expose the API gateway outside the cluster, use a Service of type NodePort (a port on every node) or LoadBalancer (a cloud load balancer). Configuration and credentials come from ConfigMaps and Secrets.






  
5
Zero-downtime rolling updates

  
Change the image tag and reapply the Deployment, and Kubernetes performs a rolling update: it starts a new pod, waits for its readiness probe to pass, then terminates an old one, and repeats. If the new version never becomes ready, the rollout stalls without hurting traffic, and kubectl rollout undo puts the old version back.

  

    

    

    

  






  
6
Separate deployment from release with a service mesh

  
A rolling update still sends real users to the new code the moment a pod is ready. A service mesh such as Istio lets you deploy without releasing. Each pod gets an Envoy proxy as a sidecar; all traffic goes through it. The control plane (Pilot configures the proxies with routing rules; Mixer handles policy and telemetry) lets you route by header or by percentage. Try it.

  

    

    
    

    

  






  
7
Serverless deployment with AWS Lambda

  
With serverless deployment you upload code (for Java, a ZIP or JAR) and the cloud runs it as many times as needed, in response to requests or events. You never see a server, an OS or a runtime. A lambda can be invoked by HTTP requests via the AWS API Gateway, by events from AWS services (S3, DynamoDB, Kinesis, SQS), on a schedule, or directly by an API call. The book deploys a REST version of Restaurant Service as lambdas with the Serverless framework. Compare cost and latency against an always-on container.
