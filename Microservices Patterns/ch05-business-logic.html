Designing Business Logic

Inside a service, the business logic is still the heart of the system. Aggregates give the domain model hard boundaries that fit a microservice world, and domain events let them tell everyone else what happened.

Transaction script or domain model?

A service is still mostly business logic, wrapped in inbound adapters (REST controllers, message handlers) and outbound adapters (repositories, message publishers). The first choice is how to organize that logic. Toggle the two patterns.

The problem with fuzzy boundaries

  
A traditional domain model is a web of interconnected classes. Where does an "order" end? Without a clear boundary, invariants are hard to enforce. FTGO has an order minimum; in this demo, $20. Two people edit the same order concurrently, each checking the minimum on what they read. Try it with and without an aggregate boundary.

Aggregates have explicit boundaries

  
A DDD aggregate is a cluster of domain objects within a boundary that can be treated as a unit: a root entity plus entities and value objects. Operations act on the whole aggregate, which is loaded whole and updated as a unit, usually with optimistic locking on the root, so invariants hold. Three rules make aggregates fit microservices. How big should an aggregate be?

  
Because a transaction updates one aggregate, bigger aggregates let you update more atomically. But they serialize concurrent work and make it harder to split a service later. Drag from small to large.

  

    
    

    

    

  






  
5
Publishing domain events

  
When an aggregate is created or changes in a significant way, it publishes a domain event: a class named with a past-tense verb (OrderCreated, OrderCancelled) carrying the data about what happened, plus metadata such as an event ID and timestamp. Uses include choreographed sagas, keeping replicas and CQRS views up to date, notifying users, WebSocket updates to browsers, and analytics.

The Order and Ticket aggregates

  
In the Kitchen Service, the Ticket aggregate is the restaurant kitchen's view of an order: it tracks preparation and pickup, with states such as AWAITING_ACCEPTANCE, ACCEPTED, PREPARING, READY_FOR_PICKUP and PICKED_UP. In the Order Service, the Order aggregate holds line items, delivery and payment info, and a state machine driven by sagas. Operations that need a saga move the order into a *_PENDING state, a semantic lock. Drive the order.

  

    

    

    

  

  
Service + aggregate + repositoryThe OrderService class is a thin domain service: it loads aggregates from a repository, calls a method on them, saves them, publishes the events they returned, and creates sagas when needed. The interesting rules live inside the aggregate.
