Testing Microservices, Part 2

Above unit tests sit tests that check a service against its database, its collaborators and its requirements, without dragging the whole application into every run. Contracts are the trick that keeps these tests fast and honest.

Integration testsComponent testsStubbingEnd-to-end testsWhere tests liveQuick check
1

Integration tests: test the adapters, use contracts

A service talks to infrastructure (its database, the broker) and to other services. Launching everything to test that is end-to-end testing: slow and brittle. The book's two tricks: test each adapter on its own (the repository, the event publisher, the proxy), and use contracts for interactions with other services. The shape of the contract depends on the interaction style. Pick one.

2

Component tests: one service, all of it, alone

A component test verifies a whole service in isolation, through its API, with stubs for the services it depends on. Its scenarios are the service's acceptance tests, written from the consumer's point of view, commonly in Gherkin (Given / When / Then) and executed by Cucumber, which maps each step to code. Run the scenario.

3

Stubbing dependencies in an out-of-process test

An out-of-process test runs the real service (for example its Docker image, started with Docker Compose alongside a real database and broker) and must fake its collaborators. For REST dependencies, a tool such as WireMock plays the other service. For messaging, the test itself subscribes to command channels and sends canned replies. For Order Service: when it sends a command to Accounting Service, the stub replies "authorized"... unless the scenario says the card has expired.

4

End-to-end tests: few, and shaped like user journeys

End-to-end tests deploy many services and drive the application through its public API. They give confidence, but they are slow, brittle and expensive to write. Keep them few. The book's trick is the user journey test: instead of one test per feature, one test that walks through a user's journey, so setup costs are paid once. Compare.

Run them in their own pipelineEnd-to-end tests need the whole application deployed, including infrastructure. They can run in their own pipeline against an environment built with Docker Compose, or against a staging environment, after a service passes its own pipeline.
