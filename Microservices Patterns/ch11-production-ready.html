Developing Production-Ready Services

Working business logic is only half of a service. It also has to be secure, configurable for any environment, and observable when things go wrong. A microservice chassis or service mesh takes most of that weight off each team.

1

Security: who are you, and may you do that?

Much of security (encryption in transit, secure credentials, protecting against injection) is the same in any architecture. What changes is authentication and authorization. A monolith keeps an in-memory session with the logged-in user and checks roles before each operation. Services can't share an in-memory session, so the identity must travel with each request. The book's recipe: the API gateway authenticates the client, then passes an access token to each service, which uses it to authorize. Step through a login using OAuth 2.0.

The token is usually a JWT (JSON Web Token): a transparent token whose payload carries the user's identity and roles, signed so nobody can forge or alter it. Services verify the signature locally, with no call to a security service. Tamper with it.

The catch with self-contained tokensA JWT can't be revoked: a service accepts it until it expires. So issue short-lived access tokens, and let the gateway use the OAuth 2.0 refresh token to get new ones without the user logging in again.
2

Externalized configuration

The same build of a service runs in development, test and production, with different database URLs, broker addresses and credentials. Hard-coding them, or building per-environment artifacts, is a recipe for mistakes. The Externalized configuration pattern supplies them at runtime. Choose a model and an environment.

3

Observability 1: the health check API

Observability is a shared job: operations runs the infrastructure (log servers, metrics, tracing); developers make each service observable. The first pattern is a health check API, such as GET /health, which reports whether the instance can handle requests, including whether its database and broker connections work. The deployment platform or load balancer calls it and routes around, or restarts, sick instances. Break something.

4

Observability 2: log aggregation and distributed tracing

With dozens of services, logs are scattered across many machines. Log aggregation ships every service's logs to a central server that supports search and alerts, such as the ELK stack (Elasticsearch, Logstash, Kibana). Each request gets a unique ID that every service logs. Search the aggregated logs.

Logs tell you what happened; distributed tracing tells you where the time went. A trace is the tree of spans for one external request: each span is one unit of work, with a start, an end and a parent. An instrumentation library (Spring Cloud Sleuth, in the book) propagates trace and span IDs in headers and reports spans to a tracing server such as Open Zipkin. Make a service slow.

5

Observability 3: metrics, exceptions, audit

Application metrics: services report counters, gauges and timings (requests, orders placed, latency) at the application level, and infrastructure metrics come from the platform. Metrics are aggregated, visualized (e.g. Grafana) and alerted on. Delivery to the metrics service is either push (the service sends them, as with AWS CloudWatch) or pull (the metrics service scrapes an endpoint, as with Prometheus). Watch a dashboard while you fire an incident.

alert threshold: p95 > 400 ms

Exception tracking: rather than burying stack traces in logs, report them to a service (Honeybadger, Sentry.io) that de-duplicates them, alerts developers and tracks resolution.

6

Microservice chassis, then service mesh

All of these concerns, plus service discovery and circuit breakers, are needed in every service. Rebuilding them per service would waste weeks. A microservice chassis is a framework that handles them so developers write business logic: Spring Boot plus Spring Cloud in Java, Go Kit or Micro in Go. Its weakness: you need one per language. A service mesh moves the networking concerns (circuit breakers, discovery, load balancing, tracing headers, TLS) out of the process into infrastructure, e.g. Istio, Linkerd or Conduit.
