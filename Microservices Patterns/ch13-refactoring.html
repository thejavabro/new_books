Refactoring to Microservices

Almost nobody gets to start with microservices; they start with a monolith. The safe route out is incremental: grow a strangler application around the monolith, one valuable service at a time.

Why and howThree strategiesExtracting a capabilityIntegration glueSagas with the monolithFTGO examplesQuick check
1

Strangle the monolith, don't rewrite it

Before migrating, make sure the problem is really the architecture. Slow delivery may come from a slow process (manual testing, manual deployment); fix that first. If the monolith genuinely holds you back, avoid the big bang rewrite: years of building a replacement while the old system keeps changing underneath, with nothing delivered until the end. Instead, grow a strangler application, named after the strangler fig that grows around a tree until the tree is gone: new services around the monolith, taking over its functionality bit by bit. Drag through time.

Demonstrate value early and oftenThe business pays for the migration only if it sees results. Each service you extract or build should speed up some real development work, so the strangler approach delivers value long before the monolith is gone, and you may never need to finish.
2

Three strategies

Not every module is worth extracting. Prioritize the ones that give the most benefit: functionality under active development, parts with scalability or performance problems, or parts that would let you swap out an obsolete technology. Score some FTGO candidates.

3

Extracting a business capability

Extracting a service is more than moving classes. The service gets its own slice of the domain model and its own database. That means splitting the domain model (replacing object references with primary keys, splitting classes like Order into Order and Delivery) and refactoring the database. Changing every monolith reference to moved fields could take forever. A trick borrowed from Refactoring Databases: keep the old columns for a transition period as read-only replicas, kept up to date from the new service, and only change the monolith code that writes them. Step through extracting Delivery.

4

Integration glue and the anti-corruption layer

A new service almost always needs the monolith's data and functionality, and the monolith often needs the service's. That collaboration is the integration glue: inbound and outbound adapters on both sides, over REST or messaging. For queries, the service can call the monolith's API, or keep a replica fed by domain events. For commands, it invokes the monolith or publishes events that the monolith handles. A legacy monolith doesn't publish events, so you may need to retrofit it, e.g. by tailing its database's transaction log or with triggers. Choose a need.

The monolith's model is usually messy, and its names differ from the service's. Don't let it leak in. An anti-corruption layer (ACL), a DDD pattern, translates between the two models at the boundary. See it translate a monolith record.


    

  






  
5
Data consistency: order the extractions

  
Once data is split between the monolith and services, updates that span them need sagas. Retrofitting compensating transactions into a legacy monolith is painful. The book's way out: sequence the extractions so that the monolith's step in each saga is always the pivot or a retriable transaction, never compensatable. Pick how far the migration has gone.

  

    

    

    

  

  
Authentication across bothThe monolith uses session cookies; services expect a token. The book's bridge: the monolith's login handler also sets a USERINFO cookie containing a JWT with the user's identity and roles. The API gateway passes it to services, which validate it, so users log in once.
