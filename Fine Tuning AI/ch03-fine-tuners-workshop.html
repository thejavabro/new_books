Training is a memory problem

Inference is light work: weights sit in memory and data flows through. Fine-tuning changes the weights, so on top of the weights you must hold a gradient for each trainable parameter, the optimizer's state (Adam keeps a running mean and variance for each one) and the activations saved for the backward pass. That is why the same GPU that chatted happily yesterday throws "CUDA out of memory" today.

The second trap is software: PyTorch, CUDA, Hugging Face and quantization libraries all pin versions. A mismatch often fails silently: the code runs, on the CPU, very slowly. The book warns that an AI coding assistant will try to "fix" code that was never broken when the real fault is the environment.

CPU vs. GPU on a matrix multiply

A CPU has a handful of fast cores built for branching logic. A GPU has thousands of simpler ones (an A100 almost 7,000, an H100 over 15,000) that do the same operation on many numbers at once, exactly what matrix multiplication needs.

2

VRAM: one number to rule them all

VRAM is the GPU's own memory. If your training footprint does not fit in it, training either crawls (swapping over the card's bus) or crashes. The author's rule: if it does not fit, pick a smaller model. Precision sets the bytes per weight: FP32 4, FP16 and BF16 2 (modern NVIDIA prefers BF16 for its wider range), INT8 1, INT4 half a byte.

Picking a GPU

The free optionA Colab T4 with about 15 GB of usable VRAM costs a few cents an hour on paid units, or nothing on the free tier (which can queue you behind paying users). It is enough for QLoRA on models up to about 7B, which is every example in the book.
4

When one GPU is not enough

Two ways to pool GPUs. Data parallelism copies the whole model to every GPU and splits each batch; faster, but the model and optimizer must fit on each card. Model parallelism (tensor or pipeline) splits the model itself across cards so huge models fit, at the price of lots of communication. Techniques like ZeRO reduce the duplication, and Hugging Face Accelerate hides most of it behind accelerate config and accelerate launch train.py. The book sticks to one modest GPU.

5

The software stack

Linux (Ubuntu LTS) is the path of least resistance with first-class CUDA support. Windows works well through WSL2 with CUDA passthrough. macOS on Apple Silicon has huge unified memory but a thinner ecosystem: PyTorch's MPS backend misses some operations, MLX is the native option, and bitsandbytes (so QLoRA) is not supported. Use Python, inside a virtual environment: Conda if you want it to manage CUDA too, venv if CUDA is installed system-wide.

7

Local or cloud?

Colab and Kaggle give notebook GPUs (Kaggle around 30 free hours a week); Lambda gives you a full Linux box over SSH; RunPod and Vast.ai are marketplaces with cheap but interruptible machines; AMD-based clouds exist too. Most people settle on a hybrid: iterate locally or on free Colab with a small model and a slice of data, then rent a big GPU for the final run.
