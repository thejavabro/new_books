A model only ever sees token IDs. This chapter turns rows of examples into exactly the token sequences, masks and splits a trainer expects.

1

Models read templates, not text

A model is trained on tokens arranged in a template it was built to consume. Present your carefully curated data in the wrong shape and the model either treats it as noise or learns to produce malformed output, spending the training budget fixing format instead of learning the task. Many disappointing fine-tunes look fine on paper and fail right here.

Two paradigms

2

Chat templates: messages to one string

A chat template (a small Jinja2 program shipped with the tokenizer) loops over the messages and stitches them into one string wrapped in special tokens. Each marker is a single token the model learned during pretraining and instruction tuning, so you must use the template of your base model. Use the wrong one and you get valid-looking text with unpredictable behavior. Pick a family:

In practice, never hand-write these: tokenizer.apply_chat_template(messages, tokenize=False) renders the exact string so you can eyeball it, and tokenize=True returns IDs. Set add_generation_prompt=True at inference (open the model's turn and let it write) and False for training (the answer is already there).

3

Store simple, convert late

The book keeps data in an easy-to-read Alpaca-style record (instruction, input, output) and converts it to the messages format just before training, adding one consistent physician system prompt. Templates and APIs change; a neutral source format makes switching cheap. (Alpaca variants are not standardized, so pick one and stick to it.) The most common error after conversion: an assistant message that is empty once whitespace is stripped, a teacher failure that slipped through filtering.

Alpaca-style source
{"instruction": "Is my headache a sign of high blood pressure?",
 "input": "",
 "output": "Usually not. Blood pressure ..."}
Messages (TRL, OpenAI style)
{"messages": [
 {"role": "system", "content": "You are a physician..."},
 {"role": "user", "content": "Is my headache..."},
 {"role": "assistant", "content": "Usually not..."}]}

Gemma calls the answering role "model", but the template maps "assistant" for you.

4

Loss masking: learn the answer, not the question

Train on the whole conversation and the model is also graded on reproducing the user's question and the system prompt. With long patient questions and shorter answers, most of the learning signal is wasted. Loss masking sets the labels of non-answer tokens to -100, PyTorch's "ignore" value: the model still reads them as context, but gradients come only from the answer. A data collator does this at batch time by finding the response marker.

6

Train, validation and test splits

The validation set is checked during training to watch for overfitting; the test set is held back until the end for an honest score. About 85/10/5 suits the medical set. Shuffle with a fixed seed (the book uses 42) for reproducibility. But random splits can leak: if "asthma treatment" questions land in both train and test, you measure recall of near-copies. Splitting by category keeps whole topics out of training.

Letters are topics (A = asthma, D = diabetes...). Colors: train, validation, test. A test cell whose topic also appears in train counts as leaked.

7

Validate before you train

The filter is cheap; retraining is not. The book's Gemma checks: the record has messages (or instruction and output), the list is non-empty, there is a user turn, the last turn is the model's, no message is empty, the template renders without error, and the result fits your token limit. Then look at the length distribution: a big gap between p90 and p99 means a few monsters.
