A foundation, not a finish line

The book has walked from Linux and Git through infrastructure as code, configuration management, cloud, containers, Kubernetes, Go, databases and CI/CD. Knowing these tools doesn't make anyone a DevOps expert by itself. DevOps is a mindset and a habit of continuous learning. Underneath the tools, a few ideas keep coming back, and they'll outlast whatever tools you use next. Pick a milestone and see which ideas it was really teaching.

2

Same title, different jobs

"DevOps engineer" means different things in different organisations. Some roles are mostly cloud and infrastructure automation, some lean towards application delivery, some towards reliability, some towards building platforms. The constant is the need to adapt: people who understand principles move between these more easily than people who memorised one tool. Compare the emphasis (our own rough sketch).

DevSecOps: security as pipeline stages

Chapter 11 made security part of the pipeline: scoped credentials, scans, careful PR triggers. The next step is security testing as its own automated stages. Static analysis (SAST) reads your source for risky patterns. Dependency scanning checks the libraries and images you pull in against known vulnerabilities. Dynamic scanning (DAST) attacks the running app from outside, as an attacker would. None of them replaces human review, but together they catch a lot before a person has to look. Generative AI in the delivery process

AI is turning up in pipelines too: reviewing pull requests for likely bugs and security problems, suggesting test cases, summarising a huge unfamiliar diff before a reviewer opens it. Treat it like every tool in this book. It's good at taking away repetitive, mechanical work. It doesn't replace understanding what the pipeline does, or the human judgement applied to what it suggests. Sort each use.

6

Multi-cloud and hybrid: usually a constraint, not a bargain hunt

The book used Azure to learn on, but real estates often span several providers or mix cloud with on-premises. That's rarely about chasing the cheapest price for each service. Tick the reasons that actually hold up.

The individual skills don't change: the same Terraform, Kubernetes concepts and CI/CD principles apply. Deciding where workloads should run becomes its own discipline as an organisation grows.

7

Platform engineering: the golden path

Not every app team should need the full depth of Kubernetes, Terraform and CI/CD. A platform engineering team builds an internal developer platform on top of them, a self-service way to deploy and run apps along a golden path. That doesn't replace the skills in this book; it packages them, built by people who know this material well enough to hide it from everyone else. Ship a new service both ways. Platforms such as Red Hat OpenShift similarly add operational layers on top of Kubernetes.

8

Containers aren't the end of the story

Docker Swarm, plain virtual machines and serverless functions all remain sensible choices somewhere. Knowing when and why is part of growing. Describe a workload and see what fits; the rules are our own simplification.

9

Logs, metrics and traces

As systems grow, you need to see inside them. Metrics are numbers over time: is something wrong, and how much? Logs are timestamped events: what exactly happened? Traces follow one request across services: where did the time go? Checkout has become slow. Ask each signal.

10

SRE: reliability as a number you can spend

Site reliability engineering gives DevOps a structured way to manage risk. You set a target for, say, availability (a service level objective, SLO). Whatever the target leaves over is the error budget: downtime you may "spend" on releases and experiments. Budget left means ship; budget gone means slow down and fix reliability. The mechanics here are a general illustration of ours; the book only names the idea.

AIOps applies machine learning to the logs, metrics and traces you already collect, to surface trends and anomalies, and sometimes to tie them to the deploy or config change that happened at the same time. Build experience, and learn from failure

Hands-on practice still teaches the most: personal projects, open-source contributions, lab environments you're allowed to break. Incidents and broken deployments teach a lot if you approach them with curiosity rather than blame. Compare two reviews of the same outage.
