Cloud Fundamentals

The cloud is someone else's data centre, rented by the minute and driven by an API. The chapter tours the four building blocks every cloud shares, using Azure as the lab.

1

Someone else's computer, fully programmable

Before public cloud, servers were ordered, racked and configured by hand; environments lived for years and change was risky, so experimentation was rare. Public clouds made infrastructure available on demand through APIs: environments can be recreated rather than repaired, and costs became variable instead of fixed. That is exactly what DevOps automation needs. The provider takes over the hardware and data centres; your responsibility for architecture, security and operations doesn't disappear, it changes shape. The chapter uses Azure, but the patterns apply to every major cloud.

2

Who runs which layer? The shared-responsibility model

Service models are a trade between control and convenience. IaaS (Azure Virtual Machines, Virtual Network) gives you VMs to patch and networks to configure. PaaS (Azure App Service, Azure SQL Database) runs the OS, patching, scaling and availability for you; you bring the app and data. SaaS (Microsoft 365 replacing the Exchange box under the stairs, Salesforce, Google Workspace) runs everything; you still own identity, access, integrations and data. It's a spectrum, and one company uses all three.

Identity is the perimeter: groups, roles and scope

Cloud security starts with identity rather than network walls. In Azure, Azure AD authenticates users, groups and service principals; role-based access control authorises them. Everything lives in a subscription (the billing and access boundary), grouped into resource groups (containers that share a lifecycle) in a region. A role assigned at a scope flows down to everything beneath it, including things created later. Assign roles to groups, at the smallest scope that works. Try it.

Beyond accessMicrosoft Defender for Cloud gathers security recommendations and alerts into one dashboard. Azure Policy audits or blocks non-compliant resources, for example denying any storage account with public access or flagging resources without a cost-centre tag.

5

Compute: design for failure, not for a perfect machine

VMs give full control of the OS and runtime. Don't count on any one machine being reliable: place a pair in an availability set (spread across separate hardware, power and network switches within a data centre: different fault and update domains) or across availability zones (physically separate data centres in one region). And pick the size deliberately: a small burstable Standard_B1s is plenty for learning, at a fraction of the default's cost. Break something.

6

Storage: redundancy, performance and access tiers

Apps come and go; data lives longer. Azure storage accounts offer blob storage (unstructured data), file shares (lift-and-shift) and queues and tables. The account name must be globally unique and lowercase (say st90daysofdevops). Three separate choices: redundancy (how many copies, where), performance (Standard or lower-latency Premium), and blob access tier (hot, cool, archive: how often you read it). High durability still isn't a backup.

Managed Disks for VMs are billed by provisioned size, not use, so over-provisioning costs money quietly. Control access through the same Azure AD group instead of shared keys.

7

Networking: VNets, subnets and security rules

A virtual network (vnet-90days, 10.0.0.0/16) is an isolated address space, split into subnets that often mirror the app's tiers. Network Security Groups filter traffic: rules are checked by priority, lowest number first, and the first match decides. Application Security Groups let rules say "WebServers" or "DbServers" instead of IP addresses that change. Send a packet and watch which rule catches it.

8

Portal, CLI, Cloud Shell, PowerShell

The portal is discoverable, but every click is just an API call, and clicks can't be reviewed or replayed. The Azure CLI (az ...) runs anywhere and can be scripted and committed to Git. Cloud Shell is a pre-authenticated browser shell with Bash or PowerShell (temporary machine, files kept in a small share, 20-minute idle timeout). Azure PowerShell does the same jobs as cmdlets (New-AzVM vs az vm create); pick whichever matches your team's scripting. Check the Pricing Calculator before creating anything you're unsure of.

9

From clicks to code: Git, IaC and CI/CD

Everything built here could be a Terraform configuration using the azurerm provider, which calls the same Azure Resource Manager API as the portal and CLI. Put it in Git and a teammate can read what exists; add a pipeline that plans on every PR and applies on merge. Azure's native alternatives are ARM templates (JSON) and Bicep (a friendlier language that compiles to ARM).
