Version Control with Git

Git is the shared memory of a team: every change recorded, every experiment on its own branch, every contribution reviewed. It is also where all later automation starts.

1

From final_v2_REALLY to a real history

Before version control, people copied a file before a risky edit and renamed it backup, old or final, or left dead code commented out "just in case". That collapses as soon as a project grows or a second person joins. Version control records every change as a snapshot with an author, a time and a message, which buys three things straight away: traceability (who changed this firewall rule, and why?), collaboration without overwriting each other, and safe experimentation. It is not a backup, though: you still need one for laptops and remotes.

2

Distributed: every clone holds the whole history

Older systems such as Subversion keep the one true repository on a central server; if it's down, so is your work. A Git clone copies everything: files, every commit, every branch and tag. Logs, diffs and commits happen locally, so they are fast, work offline, and history survives in many places. Knock the server out and compare.

First-time setupInstall with the Windows installer (tick Git Bash for a Unix-like shell) or sudo apt-get install git, then tell Git who you are: git config --global user.name and user.email. Settings exist at system, global and local (per-repo) levels. Stuck? git add -h for short help, --help for the manual.
3

Three areas: working directory, staging, history

Git keeps your work in three places. The working directory is the files you're editing. The staging area (or index) is where you pick exactly which changes go into the next commit. The repository history holds committed snapshots. Staging is the deliberate middle step that lets one commit equal one logical change. Run the commands and watch files move.

4

Branches, merges and rebases

A branch is a movable pointer to a commit: a separate line of work you can break without hurting main. Create one with git switch -c feature/new-feature (or git checkout -b). When the work is done you either merge it, which joins the lines and may add a merge commit, or rebase it, which replays your commits on top of the latest main for a straight line. Build some history and try both.


    

  






  
5
Resolving a merge conflict

  
If both branches changed the same line differently, Git stops and writes both versions into the file between markers. Everything from <<<<<<< HEAD to ======= is your current branch; from there to >>>>>>> is the incoming branch. Edit to what you want, delete the markers, then git add and git commit (or git rebase --continue mid-rebase). --abort backs out entirely.

  

    

    

    

  






  
6
Merge or rebase? A rule of thumb

  
Both integrate one branch into another; they differ in the shape of history. The golden rule: never rebase commits other people already have. Decide for each scenario.

7
Remotes: fetch, pull and push

  
A remote is a named reference to another copy of the repository, usually on GitHub, GitLab or Bitbucket; cloning creates one called origin. fetch downloads new history into remote-tracking branches like origin/main without touching your work (the safe default). pull is fetch plus a merge or rebase. push uploads your commits; a "non-fast-forward" rejection means the remote has commits you don't, so fetch or pull first.

  

    

    

    

  






  
8
Fork, clone, change, pull request

  
You usually can't push to a project you don't control. Open source (and many companies, using branches) solve this with forks and pull requests: propose changes, let people review them, let automation check them, then merge.

  

    

    

  






  
9
Git as the trigger for everything else

  
When application code, infrastructure, configuration and pipelines all live in Git, it becomes the single source of truth and change becomes a controlled, repeatable process. A push can kick off tests, builds, image builds, security scans and deploys. A tag (git tag v1.0.0, git push origin v1.0.0) is a fixed pointer to one commit that never moves, which makes it the natural trigger for a release pipeline.
