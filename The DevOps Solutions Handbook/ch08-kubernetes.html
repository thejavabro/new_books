Kubernetes

Running one container is easy. Running hundreds, keeping them healthy, reachable and up to date, is the job Kubernetes takes on, by constantly steering reality toward what you declared.

1

From one host to a cluster

Compose stopped at the edge of one machine: no load balancing across replicas, no rescheduling when the host dies, no automatic limits or health-driven replacement. Container orchestration is that missing layer, and Kubernetes is its dominant implementation (Docker Swarm and Nomad also exist). It takes images, containers and declarative configuration and stretches them across a cluster. Open each capability.

2

The control loop: you declare, Kubernetes reconciles

You don't start five instances. You say "I want five", and controllers keep comparing actual state with desired state and fixing any difference, forever. That's the same declarative idea as Terraform and Ansible, but running continuously. Change the replica count, kill Pods, or take down a whole node.

3

What a cluster is made of

A cluster is a set of nodes in two roles. The control plane decides what should run and where; worker nodes run it. Don't memorise components; follow the flow: you declare state through the API server, the scheduler and kubelets carry it out, and the controller manager's loops reconcile. Even single-node Minikube has all these roles, just on one machine. Step through what happens on kubectl create -f nginx.yaml.

4

Choosing where the cluster runs

Kubernetes is a specification with many implementations. The question is mostly who operates the cluster. The skills transfer: they all expose the same APIs.

5

Deploying nginx: namespace, Deployment, Service

Applications are YAML manifests describing desired state. The Pod (one or more containers sharing network and storage) is the smallest unit, but you rarely create one directly. A Deployment declares how many replicas and handles rollouts and rollbacks; it creates a ReplicaSet that actually keeps the count right. A Service gives them a stable address. The chapter's example puts a Namespace, Deployment and Service in one file separated by ---. Drive it.


    

    
Short names: po pods, svc services, deploy, ns, pv/pvc. Change things by editing the manifest and reapplying, never by tinkering inside running containers.

  






  
6
Labels tie it together; Services find Pods by label

  
Pods come and go with new IPs each time, so nothing points at a Pod directly. Objects are loosely coupled through labels: the Deployment's selector says which Pods it owns, the Service routes to whatever Pods match app: nginx right now. Click a Pod to relabel it and watch the Service, and the ReplicaSet, react.

8
StatefulSets and persistent volumes: the Pac-Man test

  
A database needs a stable identity and storage that outlives its Pod. A StatefulSet gives Pods predictable names (mongo-0, mongo-1) and each its own storage; Deployment Pods are interchangeable with random names. Storage comes from a PersistentVolume (real storage, usually set up by cluster admins), requested through a PersistentVolumeClaim (made by whoever deploys the app), with a StorageClass creating volumes on demand. The chapter proves it with a Pac-Man game whose high scores live in MongoDB. Play, then delete mongo-0.

9
Ingress: one front door for HTTP

  
A LoadBalancer per Service gets expensive and messy. An Ingress resource, implemented by an ingress controller such as ingress-nginx, routes external HTTP and HTTPS through one entry point by host or path, and handles TLS. On Minikube: minikube addons enable ingress, apply the Ingress, then minikube tunnel. Send requests.
