Configuration Management

Terraform gives you machines; something still has to make them useful and keep them that way. Ansible describes the desired configuration and applies it, safely, as many times as you like.

1

Drift turns troubleshooting into archaeology

Terraform gives you machines. Then someone must install packages, manage config files, enable services, harden settings and deploy apps, and keep doing it for the machine's whole life. Done by hand, "identical" servers drift apart: a memory limit raised on one at 2 a.m., a logging module disabled on another, a test tweak never written down. Configuration management keeps systems in a known, desired state, with the configuration itself as code in Git. The rule of thumb: Terraform provisions, Ansible configures.

2

How Ansible reaches a host: SSH, Python, done

Ansible is agentless: nothing to install on managed hosts. It runs from a control node (your laptop, a jump box, a CI runner or a platform), connects over SSH (WinRM for Windows), copies small Python programs, the modules, to the host, runs them and reads back the result. That's why every target needs Python; some minimal images don't ship it and Ansible fails with a clear error until you install it.

3

Inventory, ansible.cfg and the first ping

The inventory is the source of truth for which hosts exist and how they are grouped. Friendly names map to IPs with ansible_host, so playbooks don't care when addresses change. A project-level ansible.cfg pins the inventory, remote user and SSH options so everyone gets the same behaviour. Then prove connectivity with ad-hoc commands. Break db01 and compare the two kinds of failure.

[webservers]
web01 ansible_host=192.168.56.11
web02 ansible_host=192.168.56.12

[loadbalancer]
lb01 ansible_host=192.168.56.10

[database]
db01 ansible_host=192.168.56.13

Playbooks and idempotency: the second run says ok

A playbook holds plays; a play maps hosts to tasks; each task calls a module that checks current state before acting. So the first run reports changed, and a second run with nothing new reports ok: safe to rerun. Use become: yes to escalate to root. A handler (for example "Restart Apache") runs only when a task that notify-s it actually changed something. Lean on shell commands instead of real modules and you lose all of this: Ansible is not "SSH with YAML".


    

  

  
YAML in three rulesSpaces, never tabs. A line starting with - is a list item. key: value needs that space after the colon. Name every task specifically: it's the first thing you read when a run fails. A failed task stops that host only; the others carry on.

Roles: the unit of reuse

  
One giant playbook becomes unreadable fast. ansible-galaxy init roles/apache scaffolds a role: tasks/, handlers/, templates/, defaults/ (easy to override) and vars/ (hard to override), plus files/, meta/ and tests/. The same tool installs community roles and collections from Ansible Galaxy. site.yml then just says which roles apply to which groups. Click a role.

Web servers behind a load balancer, generated from inventory

  
The nginx role's template loops over groups['webservers'] to build its upstream pool, so scaling the web tier is an inventory change, not a template change. Each web server's index page prints its own hostname, which makes it easy to see the load balancer alternating. Add a third server (the chapter's Exercise 2) and send requests.

Variables, tags and separate environments

  
Move values like http_port and html_welcome_msg out of roles into group_vars/ and host_vars/; then the same roles serve dev and prod from separate inventory folders. Tags run just part of a playbook, but can hide dependencies. Facts (gathered automatically) are variables too, at a time cost on big fleets.

8
Running safely at scale: forks, serial, check and diff

  
Writing tasks is easy; running them safely on a big fleet is the hard part. forks sets how many hosts are worked on in parallel; serial rolls a change through in batches to limit the blast radius if it goes wrong. --check --diff previews what would change. Set a batch size and roll out a bad change.

  

    
    

    

  






  
9
Governed runs and encrypted secrets

  
In larger organisations, playbooks run through AWX (the upstream project) or Ansible Automation Controller (the supported product): a web UI and API with schedules, audit trails, role-based access and central credentials. They wrap your playbooks, not replace them. Secrets get Ansible Vault: ansible-vault create group_vars/database/vault.yml, run with --ask-vault-pass or a tightly permissioned --vault-password-file, or encrypt one value with encrypt_string.
