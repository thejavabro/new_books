Infrastructure as Code

If a server can only be rebuilt by the person who built it, it is a liability. Infrastructure as Code turns machines into text you can review, version, test and recreate on demand.

1

What if you lost everything today?

Ask the uncomfortable question: if every server, VM, network rule and managed service vanished today, how long would rebuilding take, and would it come back the same? With manual build steps and runbooks that drift, the honest answer is "a long time, and no". Infrastructure as Code (IaC) describes the environment in files kept in Git, reviewed like any code, and applied by automation. The code is the blueprint: it doesn't replace backups, but it changes what recovery looks like. It is also where the pets vs. cattle idea comes from.

2

Provisioning, configuration, deployment

"IaC" covers three layers, and tools specialise. Provisioning creates servers, networks, load balancers, firewalls and managed services. Configuration installs packages and manages files inside machines. Application deployment releases, scales and operates the app. Terraform is provisioning-focused; it can bootstrap a machine with user data, but long-lived configuration fits Ansible, Chef or Puppet better. Making one tool do everything is a classic mistake. Sort each task.

Which layer?

3

Declarative desired state: say what, not how

A procedural approach lists steps: create a server, install packages, edit a file, restart. A declarative one states the end result, "three servers", and the tool works out the steps by comparing what exists with what you asked for. Terraform is declarative. Together with immutable infrastructure (replace rather than modify in place) this makes rebuilds routine. Set the desired count, plan, and apply. Then simulate drift.

Anatomy of a Terraform configuration

  
Terraform is a CLI that reads .tf files and uses providers to call platform APIs, whether a public cloud, a SaaS product or on-prem kit; the workflow stays the same whatever the target. A small project often has main.tf, variables.tf, outputs.tf and terraform.tfvars; larger ones are compositions of reusable modules. Click a block to see what it does.

  

    

  






  
5
State: Terraform's memory, and why it needs a lock

  
The state file maps each resource in your code to the real object on the platform; without it Terraform cannot compute a plan. It may hold IDs, IP addresses and even secrets, so protect and back it up. Local state breaks down in teams: two people applying at once can corrupt it. Remote backends (Terraform Cloud, or S3 with DynamoDB locking on AWS) store it centrally and lock it so only one apply runs at a time. Run two applies together.

  

    

    

    

  

  
Workspaces let one directory hold several state files; handy for demos, but many teams prefer separate directories or backends per environment for clarity.

Variables, precedence and outputs

  
Hardcoded values are fine for a demo. Reusable code takes variables, which can come from many places. When several set the same variable, the later sources in this list win, so a value passed at run time overrides files and defaults. That is what lets one configuration serve dev, test and prod. Toggle the sources for vm_memory.

  

    

    

  

  

    
Sensitive isn't secretsensitive = true hides a value from plan and apply output. It does not remove it from state, so inject secrets safely and secure the backend.

    
Outputs are integration pointsOutput an IP, DNS name or ID and hand it to the next tool or pipeline stage: no copy and paste.

  






  
7
Treat plan as your safety net

  
In real teams Terraform rarely runs from a laptop. A pull request triggers formatting and validation, a plan is posted for reviewers, and after approval a pipeline (or a tool such as Atlantis) applies it with a service identity. Saving the plan (plan -out=tfplan, then apply tfplan) guarantees the plan reviewed is the plan applied, and leaves an audit trail.

  

    

    

  






  
8
Code rot, and the layers of defence

  
Infrastructure code is often written once, used, and left alone while the world moves on. It rots through out-of-band console changes, unpinned provider versions, deprecated arguments and APIs, and unapplied changes piling up as drift. The first defence is discipline: the code is the source of truth. The second is automation. Switch on defences and see which problems they catch.
