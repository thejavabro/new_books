Why databases are not like the rest of the stack

Most of this book treats servers as cattle: if a web container misbehaves, throw it away and start another. A database breaks that habit because it is the state. Its whole job is to remember what happened, so replacing it carelessly means forgetting. Flat files and spreadsheets work until several users and processes write at once; a database engine adds concurrency control, constraints, recovery and querying on top. That is why Kubernetes runs databases as StatefulSets with persistent volumes rather than as ordinary Deployments (Chapter 8). Try replacing each kind of instance.

Relational and non-relational models

Relational databases (PostgreSQL, MySQL, SQL Server, Oracle) keep data in tables of rows and columns. A foreign key in one table points at the primary key of another, so related records are joined when you ask rather than copied everywhere. Non-relational (NoSQL) stores loosen some rules for scale or flexibility: documents (MongoDB), key-value and in-memory (Redis), graphs (Neo4j). Same customer, two shapes:


    

  

  
Neither family is "better". A reporting system with complex queries over structured records is usually a relational fit; millisecond lookups at huge scale where a slightly stale read is fine often lean NoSQL. DevOps engineers rarely pick the engine alone; we make sure whatever the app team chose is deployed, secured, backed up and watched properly.

ACID: what a transaction promises

  
Relational engines guarantee four things about a transaction (a group of changes treated as one): Atomicity (all of it or none of it), Consistency (rules like foreign keys are never broken), Isolation (concurrent transactions don't see each other's half-done work) and Durability (once confirmed, it survives a crash right after). Atomicity is easiest to feel with money. Move 50 from Ana to Ben, and pull the plug halfway.

CAP: pick two when the network splits

  
Once data lives on several machines, the CAP theorem says you can't fully guarantee all three of Consistency (every read sees the latest write), Availability (every request gets an answer) and Partition tolerance (keep working when nodes can't reach each other). Networks do split, so the real choice is what happens during a split: refuse, or answer with possibly old data. Relational systems usually lean towards consistency; many NoSQL systems trade some of it for availability. Cut the link and write to node A.

Querying: say what you want, not how

  
SQL is declarative, like Terraform or a Kubernetes manifest: you describe the result and the engine works out how to get it. For a DevOps engineer, queries are mostly for checking things: is the migration applied, did automation create the expected rows, is the app seeing what we think it sees? This pretend psql session holds a small users table. Writes really change it; type reset to start over.

Indexes and execution plans

  
An index works like the index at the back of a book: jump to the page instead of reading from the start. EXPLAIN shows the execution plan the planner chose. On a tiny table, reading every row (a sequential scan) really is cheaper, so the planner may ignore your index; that's a decision, not a bug. Grow the table and see when the index starts to pay. Backups are really a recovery process

  
Disks die, software has bugs, people type the wrong thing. A backup no one has restored is an untested assumption. Two numbers decide the design: RPO (recovery point objective), how much data you may lose, counted back from the failure; and RTO (recovery time objective), how long until service is back, counted forward. Set the targets, pick a strategy, then trigger a failure.

11
High availability, disaster recovery and replication

  
High availability deals with routine failures, like one server in a cluster dying. Disaster recovery deals with losing a whole site or region. Both rely on replication, configured differently. Synchronous: the primary waits for a replica to confirm each commit, so nothing is lost on failover but every write is as slow as the slowest replica. Asynchronous (common for a warm DR standby): the primary doesn't wait, so writes stay fast but the replica lags, and that lag is your RPO.

Replication is not a backupA replica copies a bad DELETE or a corrupting migration just as faithfully, and just as fast, as a good write. Backups protect against mistakes; replicas protect against hardware.

Performance in three layers, plus a cache

  
Slow databases rarely have one cause. Work down the layers and measure before changing anything: server (CPU, memory, storage latency; in containers, sensible requests and limits), engine settings (cache memory: too little hurts, too much starves the OS) and queries (plans, missing indexes, stale statistics after a bulk load). The cheapest query is the one that never reaches the database. Put a cache such as Redis in front and tune the time-to-live (TTL).

Monitoring that people still read

  
Watch latency, throughput, connection counts, disk I/O and above all free disk space: running out stops the service at once, with no gradual warning. A database is often where someone else's problem shows up first. But page on everything and you get alert fatigue: the important page is ignored with the rest. Choose which alerts wake a person up.
