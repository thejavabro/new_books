The problem CI/CD actually solves

Everything so far (infrastructure as code, configuration management, containers, Kubernetes) leaves one question open: how does a change get from a laptop into production safely and repeatedly? Continuous integration (CI) merges changes into the shared repository often, each one triggering automatic builds and tests. Continuous delivery (CD) takes what passed and gets it ready to release, often all the way out. The point is the feedback loop: how quickly you learn whether a change is safe. Before CI, teams integrated in big batches, sometimes overnight or only before a release. See what batch size does.

The numbers come from our own simple model, not from the book. The shape is the point: the longer work sits unmerged, the worse merges get and the further a bug is from its cause. A shortcut merged today is cheap to unwind today; buried under months of work, it isn't.

2

From commit to production

A commit on its own does nothing; something has to be watching the repository. The pipeline tool (Jenkins, GitHub Actions…) builds an artifact (binary, container image, package), tests it, gives it a version and publishes it to a registry, then deploys to staging and, after a gate, to production. Run it, or break a stage and run again.

3

Testing layers, and failing fast

The "test" box hides several layers: lint/format checks catch trivial slips; unit tests check single functions in isolation; integration tests check parts working together with realistic dependencies; validation tests check the software does what it's for, not merely that it runs. They run on every push, which matters when contributors commit from different time zones: a manual gate would either bottleneck or get skipped. Order them so the cheapest checks run first. A typo in a YAML file is pushed; reorder the stages to get feedback sooner.

Jenkins: a controller and its agents

Jenkins is an open-source automation server, still common where teams have invested in it or need heavily customised pipelines; plugins connect it to almost anything. The controller holds configuration, schedules runs, serves the UI and tracks state. It does not run the build steps: agents do. Agents can be long-lived machines or, on Kubernetes, Pods created for one run and deleted after, so they never pile up drift. Queue some builds and compare.

The #90DaysOfDevOps labs install Jenkins into a local cluster with Helm. That works for learning; production also needs persistent storage for config and history, a service account allowed to create agent Pods, and credentials for the registry, Git host or cloud, the same concerns as any stateful workload in Chapter 8.

The pipeline is a security boundary

  
A pipeline usually holds credentials to push images, deploy to production and sometimes change infrastructure. That makes it a privileged system. An outside contributor opens a pull request on your public repository whose test script quietly tries to steal tokens and ship a vulnerable base image. Turn on the defences.

  

    

      
      
      
      
    

    

    

  

  
That is what DevSecOps means here: not a security gate bolted on at the end, but checks built into the same pipeline that already builds, tests and deploys.

GitHub Actions: CI next to the code

  
GitHub Actions has no server for you to run. Any YAML file in .github/workflows/ is a workflow. An event under on: starts it; it holds jobs (parallel by default) made of steps, each either a run: command or a reusable action via uses:. Every job gets a fresh runner (GitHub-hosted Linux, Windows or macOS, or self-hosted). Click a line.

Argo CD: the cluster pulls from Git

  
With GitOps, Git is the single source of truth for what should run. Instead of the CI pipeline pushing into the cluster, a controller inside it, Argo CD, watches a repository of manifests or Helm charts, compares them with the live cluster and reconciles. CI builds and tests artifacts; delivery belongs to the controller. Rollback is a git revert.

11
Observing and troubleshooting pipelines

  
A pipeline that fails silently, or in a way nobody can diagnose, defeats its purpose. Read the failing step's log in full first. Over time, watch duration (three minutes creeping to twenty), failure rate by stage (one stage failing far more often usually means a flaky test or shaky dependency) and queue time (long waits before starting mean too few agents, a capacity problem). Pick a metric.

  

    

    

    

  

  
A failure that disappears when you re-run the exact same commit is flaky, and deserves its own investigation. Try it.

The book's exercises build one small app through all three tools: a Jenkinsfile read from SCM (then deliberately broken), the same checks as a GitHub Actions workflow triggered by pushing it, and Argo CD on Minikube syncing a manifest repository, first with a replica change in Git and then with drift made by hand. Afterwards the CI pipeline's job shrinks to producing a versioned artifact and updating the manifest that points to it.
