Containers

A container packages an application with exactly what it needs, so "works on my machine" becomes "works on every machine". Docker made that easy enough to change how teams ship.

1

One box for every kind of software

Running any software means answering the same questions: where do I get it and can I trust it, what licence, what does it depend on, how do I configure, start, restart, update and remove it? Before containers, each app answered them differently on each server, and servers drifted. Containers don't make the questions disappear; they answer them once, the same way for everything. An image packages the app with everything it needs; running an image gives you a container. Like the steel shipping container, the win is the standard box: the thing you tested is, byte for byte, the thing you run.

2

Containers and VMs: different jobs, not rivals

A VM virtualises hardware: each one boots a full guest OS on a hypervisor. A container virtualises the operating system: isolated processes sharing the host's kernel. So containers are megabytes not gigabytes and start in seconds, while VMs give stronger isolation and can run different operating systems. In practice containers usually run on VMs; that's what a cloud's managed container service is doing underneath.

3

Docker, and what happens on docker run hello-world

Docker standardised the tooling and image format that made containers mainstream. "Docker" means several things: the Engine (a long-running daemon, dockerd, that builds images and runs containers), the CLI (docker, which instructs the Engine) and Docker Desktop (both plus a GUI and a small Linux VM for Windows and macOS). The Open Container Initiative standardises images and runtimes, so these skills transfer to Podman, containerd and CRI-O.

4

Images, containers and their lifecycle

Images are read-only and immutable: to change something you build a new image and replace the container, never patch a running one. They come from registries: Docker Hub (official images for nginx, PostgreSQL, Redis... and many unofficial ones whose trust must be earned) and, for your own images, usually a private registry. Containers are ephemeral; docker ps -a shows stopped ones too. Play with a pretend engine, including the classic errors.

5

Dockerfiles, layers and the build cache

A Dockerfile is a text recipe; each instruction (FROM, WORKDIR, RUN, COPY, ADD, ENTRYPOINT, CMD, EXPOSE, LABEL) adds a layer. Docker caches layers, but once one layer changes, every layer above it rebuilds. So put rarely changing steps first and your frequently edited code last. 6

Docker Compose, and where a single host stops

Real apps are several containers. Compose declares them in one YAML file (services, ports, environment, volumes, depends_on for start order, restart: always for a taste of self-healing) and docker compose up -d starts the lot on a shared network. Use docker compose with a space; the hyphenated tool is retired. Then try --scale wordpress=3 and poke at the result.

services:
  db:
    image: mysql:5.7
    volumes: [db_data:/var/lib/mysql]
    restart: always
    environment:
      MYSQL_DATABASE: wordpress
      MYSQL_USER: wordpress
      MYSQL_PASSWORD: # from a secret, not Git
  wordpress:
    depends_on: [db]
    image: wordpress:6.6
    ports: ["8000:80"]
    restart: always
    environment:
      WORDPRESS_DB_HOST: db
volumes:
  db_data: {}

7

Stateless containers, stateful data: volumes

Anything a container writes to its own filesystem dies with it: perfect for a web server, fatal for a database. A named volume is Docker-managed storage that outlives containers (db_data:/var/lib/mysql). A bind mount maps a host folder in, handy for live-editing source code in development. Write a blog post, then tear down.

8

Bridge networks, published ports and least privilege

Compose creates a user-defined bridge network. Containers on it find each other by service name through Docker's embedded DNS, and stay invisible from outside unless you publish a port (8080:80 maps host 8080 to container 80). docker network ls shows bridge, host and none. Containers give isolation, not immunity: publish only what's needed, keep images small, run as non-root, never bake secrets in. Click a connection to test it.

9

Beyond Docker, and the bridge to Kubernetes

Everything so far lived on one host. Compose could run three replicas, but nothing balanced traffic between them, nothing moved them when the host died, nothing set resource limits or acted on health checks. That gap is what orchestration fills, and the next chapter's Kubernetes Pods still run these same images.
