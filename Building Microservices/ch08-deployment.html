From one logical service to many running instances

On a diagram, Catalog is one box. In production it is several instances behind a load balancer, ideally spread across data centers (availability zones), plus a database that may itself be a primary with read replicas. Two services can share database infrastructure while keeping logically separate databases; just remember that a shared database server is a shared point of failure. Try losing a data center.

The same logical service also changes shape between environments: perhaps one process on a laptop, a single instance in test, and four instances over two data centers in production. Environments near the developer are tuned for fast feedback; those near production for realism. Keeping the differences manageable is a job for good tooling.

3

Desired state management and GitOps

Declare what you want ("four instances of Catalog") and let the platform make it so, relaunching instances when they die. With GitOps (from Weaveworks, tools such as Flux) the desired state lives in source control, and the platform reconciles to whatever the repository says. Kill some instances.

GotchaDesired state can surprise you. Turn an instance off for debugging and the platform will dutifully start another. Know that it's there.

A simplified view of Kubernetes

With containers, Dockerfiles took over much of what Puppet and Chef used to do inside the host. You then need something to run containers across many machines: a container orchestrator, of which Kubernetes is now dominant. A cluster has a control plane and nodes that run workloads. Click each concept.

8

Separate deployment from release

Deployment installs a version into an environment. Release makes it available to users. Separate them and you can check software works in production before anyone relies on it. The Accelerate research shows speed and stability go together, and these techniques are part of why. James Governor named the family progressive delivery: control who sees what, and roll out gradually.
