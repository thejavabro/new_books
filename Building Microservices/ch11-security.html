Core principles

The author is clear he isn't a security specialist; the chapter covers what every developer on a microservice system should know. Microservices cut both ways: more data on the network and more moving parts, but also more chances for defense in depth. Lock down the basics before buying a pick-proof front door while the back window is open.

3

Credentials and secrets

User credentials (follow current advice from NIST and the UK's NCSC, summarized well by Troy Hunt: use password managers, drop complex password rules and forced regular changes, and add multifactor authentication) and secrets: TLS certificates, SSH keys, API key pairs, database passwords. Each secret has a life cycle: creation, distribution, storage, monitoring, rotation. Kubernetes has basic built-in secrets; HashiCorp Vault is far more capable, and can issue short-lived credentials; clouds offer their own managers.

Implicit trust, zero trust, and the spectrum between

Implicit trust: anything inside the perimeter is assumed friendly. The most common model, often not a conscious choice, and an attacker inside gets everything. Zero trust: assume you're already compromised; every call must authenticate and be authorized, and data in transit is protected. Done properly, it lets you do counterintuitive things, like putting services on the public internet. It's a mindset, not a product. Most organizations sit in between, varying by data sensitivity. 7

Authentication and single sign-on

Authentication establishes who a principal (person or thing) is; authorization decides what they may do. Services can authenticate each other with mutual TLS. For humans, use single sign-on with an identity provider via OpenID Connect (the author's preference over the complex SOAP-based SAML). Rather than every service handling the handshake, a single sign-on gateway at the edge does it and passes principal information downstream, but don't let it lull you into trusting everything behind it. Gateways can make coarse decisions (only staff reach the helpdesk); fine-grained decisions belong in the services, with coarse roles modeled on how the organization works.

8

The confused deputy problem

A customer logs in to the web shop and views an order. The Web Shop asks Order service for order 42. Order trusts Web Shop, because it's an internal caller. What if the customer edits the URL to ask for someone else's order?

Centralized upstream authorization implies implicit trust and spreads knowledge of what Order owns into other services. Better to push the decision into the service that holds the data, which needs the principal's identity and claims to travel with the request.

9

JSON Web Tokens

A JWT carries signed claims about a principal in one string: header, payload and signature, each Base64-encoded and joined with dots. The gateway (or identity provider) issues one; downstream services verify the signature with a public key and read the claims, with no callback. Edit the payload (this is a made-up example).
