What the ideal technology does

Let the problem pick the technology, not the other way around. Whatever you choose should help with five things.

2

RPC, REST, GraphQL and message brokers

Rather than survey every option, the book looks at four popular families. Pick what you need and see which fit best.

RPC's trapsSome RPC stacks (Java RMI) bind client and server to one platform. All of them make remote calls look local, which tempts you to forget the network is unreliable ("the network is reliable" is the first fallacy of distributed computing). And binary-serialized objects tend to be expand-only: remove an unused field and every client needs new stubs. Modern options such as gRPC (on HTTP/2, protocol buffers) are excellent if you keep these in mind.
3

REST, HTTP and hypermedia

REST is about resources (a Customer, an Album) and how they're represented; the representation you send isn't tied to how it's stored. Over HTTP you get verbs, status codes, caching proxies, load balancers and monitoring tools for free. Hypermedia (HATEOAS) goes further: responses contain links, and clients follow links by their meaning rather than hardcoding URIs, as people follow a "basket" icon even when the site moves it. Change the server's URI scheme and see which client survives.

The author likes the idea but has seen little evidence that full HATEOAS pays off between microservices; it costs extra round trips. REST over HTTP is a sensible default for synchronous request-response, and great at the perimeter. OpenAPI now provides schemas and client generation.

Message brokers: queues and topics

  
Brokers sit between services and handle asynchronous messages. A queue is point to point: each message goes to one consumer in a group (good for work distribution and async request-response). A topic broadcasts: every consumer group gets its own copy (good for events). Publish a message.

Formats, schemas and two kinds of breakage

  
Text formats (JSON, XML) are readable and interoperable; binary ones (protocol buffers, Avro) are compact and fast. Either way, the author favors explicit schemas: they make the contract visible and let tools catch accidental breaks. The question isn't schema or no schema; a consumer always assumes some structure. It's whether that structure is written down.

  
Tools can catch structural breaks (a field removed or retyped). Semantic breaks (same shape, different meaning) need tests. Sort these changes.

Five ways to avoid breaking changes

  
The second most common question after "how big?" is "how do you handle change?" First, avoid breaking changes: make expansion changes (add, don't remove), be a tolerant reader, choose tech that tolerates change, keep the interface explicit, and catch breaks early with schema comparison or contract tests.

Semantic versioning in three numbers

  
MAJOR.MINOR.PATCH: major for incompatible changes, minor for backward-compatible additions, patch for compatible bug fixes. A client built against 1.2.0 can use 1.3.0 but not 2.0.0. Make a change and watch the version.

When a breaking change can't be avoided

  
Three options: lockstep deployment (change the service and all consumers together, giving up independent deployability), coexisting versions (run old and new services side by side: twice the fixes, routing logic, and shared state to reconcile), or emulating the old interface in the new service. The author prefers emulation: it is the expand and contract pattern. Step through it.

  

    

    

  

  

    
The social contractAgree up front how changes are raised, how consumers and producers collaborate, and who does the upgrade work. Track which consumers still call the old endpoint (logs, client IDs) so you know when it's safe to remove.

    
Extreme measuresOne company deprecating an old library added a sleep to it, logging why, and kept increasing it until the lagging teams moved. Not a first resort.

  






  
9
DRY across services, and client libraries

  
Don't-repeat-yourself is about duplicated behavior and knowledge. Within a service, apply it freely. Across services, shared code is coupling: you can't upgrade every user of a library at once, so expect many versions in production. Shared libraries for cross-cutting concerns (logging) are fine; shared domain objects that leak over the boundary are not.

  
Client libraries can help, but if the team that builds the server also writes the client, server logic tends to leak into it. The model the author likes is AWS: the underlying API is usable directly, and SDKs on top are written by others or by a separate team. Let clients decide when to upgrade.

Finding services

  
Discovery systems do two things: instances register, and others look them up. Pick a mechanism to see how it handles a new instance.

  

    

    

  

  
Don't forget the humans. Developers need to find out what APIs exist, too, which is where documentation and registries come in.






  
11
API gateways and service meshes

  
North-south traffic enters from outside; east-west flows between services. An API gateway sits at the perimeter and handles the former: routing external requests, API keys, logging, rate limits. A service mesh handles the latter: a local proxy (often Envoy) next to each instance, managed by a control plane, providing mutual TLS, correlation IDs, discovery, load balancing.

  

    

    

    

  

  
Aren't meshes smart pipes?What goes in the mesh must be generic, not specific to any one service. Business logic stays in services. Advice on adopting a mesh used to be "if you can wait six months, wait"; the space has matured since, and Monzo credits its mesh as essential at its scale. You may still not need one with only a few services.






  
12
Documenting services

  
Explicit schemas help, but people need more. OpenAPI covers HTTP APIs and AsyncAPI covers event-based ones. Beyond that, a humane registry (Martin Fowler's term) gathers what's known about each service: owner, docs, health, dependencies. Start with a wiki page; the Financial Times built Biz Ops, which even scores each service's operability, and Spotify's Backstage is an open source option.
