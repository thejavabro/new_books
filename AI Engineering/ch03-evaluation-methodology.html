Evaluation Methodology

Open-ended outputs have no single right answer, which makes evaluation the hardest part of AI engineering. This chapter is the toolbox: language-model metrics, exact checks, similarity scores, AI judges and head-to-head rankings.

Why foundation models are hard to evaluate

2

Entropy, cross entropy and perplexity

Language-model metrics come from information theory. Entropy is how much information a token carries, or how hard the next token is to predict. Picture describing a position inside a square. A language with two tokens (top, bottom) needs 1 bit per token; one with four tokens (each quadrant) carries 2 bits per token: more information, harder to predict.

Positions in a square

Cross entropy of a model on data is the data's own entropy plus how far the model's learned distribution diverges from it (KL divergence). Training minimises it. Perplexity is its exponential: the number of equally likely options the model is effectively choosing between. Units matter: bits use base 2, nats (PyTorch, TensorFlow) use base e. Bits per byte normalise across tokenizers.

Bits per byte
Compression

Perplexity = 2H for bits or eH for nats. Bits per byte = bits per token ÷ bytes per token; a BPB of 3.43 means each 8-bit byte compresses to 3.43 bits.

Lower is expected when…

Data is structured (HTML is more predictable than prose), the vocabulary is small, and the context is long.

Useful for

A proxy for capability; spotting contamination (suspiciously low perplexity on a benchmark); filtering odd or gibberish text (very high perplexity); deduplicating training data.

Careful

Post-training (SFT, RLHF) narrows a model toward preferred answers, which usually raises perplexity. It is a weaker proxy for chat models, and many APIs don't expose the logprobs you need.

Exact evaluation: does it work?

Exact evaluation gives a judgment without ambiguity. The best kind is functional correctness: does the output do what it should? Code can be run against tests (HumanEval, MBPP); a game bot's score can be counted; a scheduling plan can be checked for energy saved. Pick a candidate for has_close_elements(nums, threshold) and run the tests.

Similarity against reference data

When you can't test behaviour, compare the output with reference answers. Options, from strict to loose: exact match, lexical similarity (overlapping words, n-grams or edit distance, as in BLEU and ROUGE), and semantic similarity (closeness of embeddings, as in BERTScore). Edit the texts.

Semantic score here uses a tiny hand-made concept table, purely illustrative. Real systems use learned embeddings.

Weak spotsReferences are costly and never complete, so a correct answer can score low; references can even be wrong. Higher overlap doesn't always mean better: on code, BLEU barely separates correct and incorrect solutions. "Contains the reference" is risky too: asked for Anne Frank's birth year (1929), an output of "September 12, 1929" contains the right year but states a wrong date.
Same tools, other jobsSimilarity also powers retrieval and search, ranking, clustering, anomaly detection and deduplication. Expect to meet it again in RAG (chapter 6) and data processing (chapter 8).

A quick introduction to embeddings

An embedding is a vector meant to capture the meaning of data. Good embeddings put similar things close together. Models built for this include BERT, CLIP and Sentence Transformers; APIs offer them too (OpenAI's text-embedding-3 small is 1,536 numbers, large is 3,072). CLIP learns a joint space for text and images from (image, caption) pairs, so a caption lands near its picture. Click a point to find its nearest neighbours.

A 2D sketch; real embeddings have hundreds or thousands of dimensions and are compared with cosine similarity.

AI as a judge

Which models can judge?

  
A stronger judge seems natural (it can grade a cheaper production model, perhaps on samples), but the strongest model then has no judge. Self-evaluation sounds like cheating, yet asking a model "is this answer correct?" often catches its own mistakes. Can a weaker judge work? Judging is arguably easier than generating, and specialised small judges are common:

  

    
Reward model
(prompt, response) → score. Used in RLHF and to rank outputs.

    
Reference-based judge
(prompt, response, reference) → similarity or quality score.

    
Preference model
(prompt, response 1, response 2) → which one users prefer. Cheap preference data for finetuning.

  






  
8
Ranking models by comparing them

  
Often you want a ranking, not a score. Comparative evaluation shows two models' answers to the same prompt and asks which is better, the way chess players are rated by games, not exams. Chatbot Arena uses it, adapting rating algorithms such as Elo and Bradley–Terry. A ranking is correct if higher-ranked models tend to win future matches.
