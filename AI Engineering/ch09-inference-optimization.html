Inference Optimization

A brilliant model that is slow and expensive will not be used. Measure what matters, understand why decoding is memory-bound, and apply the model-level and service-level techniques that make inference faster and cheaper.

1

Better, cheaper, faster

Models come and go; making them faster and cheaper stays relevant. A slow model loses users or makes its predictions useless (an outdated forecast), and an expensive one may not be worth running. Optimization happens at three levels: the model (make it smaller or more efficient), the hardware (better chips), and the service (use the hardware well for many requests). If you use a model API, the provider does most of this, but the ideas still help you choose between APIs and self-hosting.

2

Compute-bound or bandwidth-bound?

Optimizing means finding the bottleneck. A workload is compute-bound when the arithmetic limits it, and memory bandwidth-bound when moving data between memory and the processor limits it. ("Memory-bound" sometimes means running out of memory capacity instead; that's a different problem.) The roofline model shows which: an operation's arithmetic intensity (FLOPs per byte moved) decides whether it hits the bandwidth slope or the compute ceiling.

Roofline explorer

chip: ~312 TFLOP/s (16-bit), 2 TB/s

Prefill: compute-boundAll input tokens go through the model in parallel. Limited by how many operations the hardware can do. Sets time to first token.
Decode: bandwidth-boundOne token at a time, and each step loads large weight matrices into the compute units. Limited by memory bandwidth. Sets time per output token.

Because the two phases stress different resources, production systems often run them on separate machines (see Service optimization below). Image generators like Stable Diffusion are usually compute-bound, while language model decoding is usually bandwidth-bound.

Online APIs

Optimize latency: handle each request on arrival (perhaps batched briefly). For customer-facing apps like chatbots and coding assistants. Streaming sends tokens as they're produced so users wait less, at the cost of not checking the full response before showing it.

Batch APIs

Optimize cost: as of writing, Google Gemini and OpenAI offered batch APIs at 50% off, with turnaround in hours. Good for synthetic data, periodic reports, document processing, migrations, evaluation runs. (Unlike traditional ML "batch inference", these don't precompute answers before requests arrive.)

Performance metrics

Latency = TTFT + TPOT × (number of output tokens). Time to first token covers prefill (plus queueing); time per output token covers each decode step. A very fast reader takes about 120 ms per token, so a TPOT around 120 ms (6–8 tokens/s) is usually enough when streaming. Users may see a longer TTFT than the model does: if the model plans and calls tools before writing the visible answer, the user's "first token" comes late.

Goodput: throughput that meets your SLO

Utilization: MFU and MBU

not the same as "GPU utilization"

NVIDIA's "GPU utilization" only says the GPU was busy, not how much of its capacity was used. MFU (model FLOP/s utilization) compares achieved FLOP/s to the chip's peak. MBU (model bandwidth utilization) compares bandwidth used, parameters × bytes per parameter × tokens/s, to the chip's peak bandwidth.

Defaults: 7B in FP16 at 100 tokens/s on an A100 (2 TB/s) uses 700 GB/s, an MBU of 70%. Fewer bytes per parameter (quantization) means fewer bytes to move per token. Training tends to reach higher MFU than inference; PaLM reported 46.2% MFU in training.

4

AI accelerators

CPUs have a few powerful cores (up to about 64 on high-end consumer machines) built for sequential, general work. GPUs have thousands of small cores built for parallel work like matrix multiplication. Many other accelerators now exist, including chips specialized for inference (lower precision, faster memory access) and for transformers. Chips also differ in their compute primitives: scalar, vector and tensor (matrix) units.

Compute depends on precision (H100 SXM, with sparsity)

Fewer bits, more operations per second. TF32 is a 19-bit format.

The memory hierarchy

GPU on-chip SRAM>10 TB/s · ≤40 MB

CPU memory (DRAM)25–50 GB/s · up to TBs

Faster means smaller and more expensive. Much of GPU optimization is about keeping data in the fast tiers. Reference numbers only.

PowerAn H100 at peak for a year uses about 7,000 kWh; an average US household uses about 10,000 kWh a year. Electricity is a real limit on scaling compute. Chips list maximum power draw or TDP (thermal design power, a cooling proxy).

Choosing accelerators comes down to three questions: can it run my workload, how long will it take, and what does it cost? FLOP/s, memory size and bandwidth answer the first two; price and power answer the third.

5

Model-level optimization

Ideally optimization doesn't change quality, but many techniques do, which is one reason the same open model can behave differently on different providers. Transformer language models are resource-hungry because they're big, autoregressive and attention-based; each has a family of fixes.

Beating the one-token-at-a-time bottleneck

At 100 ms a token, 100 tokens take 10 s. Output tokens cost two to four times input tokens across providers, and Anyscale found one output token can affect latency as much as 100 input tokens.

Speculative decoding

A fast draft model proposes K tokens; the big target model checks them all in one parallel pass, keeps the longest correct prefix, and adds one token of its own. The output is exactly what the target alone would produce.

Estimated speed-up

Expected tokens per round = (1 − aK+1) / (1 − a). Speed-up assumes verifying costs one target step and drafting costs 1.8 ms vs 14.1 ms per token, the ratio DeepMind reported for a 4B draft model and Chinchilla-70B (which more than halved latency). Structured text like code tends to have higher acceptance.

Inference with reference

Answers often repeat parts of the input (quoting a document, editing code). Instead of a draft model, copy a matching span from the context as the draft and let the model verify it. No extra model, but it only helps when outputs overlap the input.

Parallel decoding

Generate several future tokens at once, then verify and fix them. Lookahead decoding uses the same decoder (with Jacobi iteration); Medusa adds extra decoding heads, each guessing a later position, and picks the best combination with tree attention. Promising, but harder to implement.

Attention and the KV cache

Each new token attends to the key and value vectors of all earlier tokens. Rather than recompute them, keep them in a KV cache (inference only). It grows with sequence length and batch size: a 500B+ model with multi-head attention, batch 512 and context 2,048 needs a 3 TB cache, three times the model's weights.

Kernels and compilers

Kernels are code tuned for specific hardware, written in CUDA, Triton or ROCm. Writing them used to be a dark art; it's increasingly part of AI engineering. Compilers (torch.compile, XLA, TensorRT, Apache TVM, MLIR) "lower" model code into kernels for a target chip.

Service-level optimization

Given fixed resources and a stream of requests, allocate them well. These techniques don't change the model, so quality stays the same.

Batching simulator

Decouple prefill and decode

Prefill is compute-bound and decode bandwidth-bound; on one machine they fight. DistServe and "Inference Without Interference" showed separate instances raise the requests a system can serve within latency targets; moving intermediate state between them is cheap on fast links like NVLink. With long inputs and a TTFT priority, prefill-to-decode instance ratios of 2:1 to 4:1 are common.

Parallelism

Replica: more copies, more requests. Tensor (intra-operator): split each matrix multiplication across devices; serves bigger models and cuts latency, with communication overhead. Pipeline: split layers into stages on different devices with micro-batches; serves big models but adds latency, so it's more common in training. Also context (split the input sequence) and sequence parallelism (split operators).
