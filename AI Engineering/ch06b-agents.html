Agents: Tools, Planning and Memory

Give a model tools and let it decide what to do next, and you have an agent. More power, more autonomy and many more ways to fail.

1

An agent is a model that acts

An agent perceives its environment and acts on it. It is defined by its environment (a game, the internet, a codebase, a company database), the actions it can take, mostly through tools, and a planner, the AI model that decides what to do. The environment decides which tools make sense: a chess agent can only move pieces; a coding agent like SWE-agent navigates, searches and edits files in a terminal. Even the RAG system with a SQL tool from the previous page is a simple agent.

2

Why agents need strong models

Agents take many steps, and errors compound: if each step is right 95% of the time, ten steps succeed only about 60% of the time, and a hundred steps about 0.6%. Stakes are also higher: tools let agents do real things, so mistakes cost more. Multi-step tasks take time and money, which is worth it only if they save more human time.

3

Tools: perceive and act

Tools that read let the agent perceive; tools that write change the world. The set of tools is the agent's tool inventory. Three categories are worth considering:

Knowledge augmentation

Know more

Retrievers, SQL, internal APIs (inventory, customer records), web search and news APIs. Keeps answers current, but the open web brings unreliable sources and injected prompts.

Capability extension

Do what models are bad at

Calculators, calendars, unit and time-zone converters, translators, code interpreters, image generators and transcribers that make a text model effectively multimodal. Chameleon gave GPT-4 13 tools and beat the best published few-shot result on ScienceQA by 11.37%, and gained 17% on a tabular math benchmark.

Write actions

Change things

Send email, update a database, place an order, transfer money. They enable full automation, and the risk the book compares to giving an intern write access to production. Add safeguards, approvals and auditing.

4

Planning: decide before doing

A task has a goal and constraints. A plan is the roadmap of steps. Plans differ in cost: to find companies with no revenue that raised at least $1 billion, filtering first by the $1 billion is far cheaper than filtering first by "no revenue", because far fewer companies match. Executing a bad plan wastes time and API calls (or worse), so separate planning from execution: generate a plan, validate it, and only then execute.

Can foundation models plan?Debated. Planning is search: explore paths, predict outcomes, backtrack. Some argue autoregressive models can't backtrack; but a model can revise a path once it sees it fails. Models may also plan poorly because they lack information about what actions do: a plan should predict each action's resulting state. A model can be one part of a planner with search and state tracking around it.
Intent firstAn intent classifier tells the agent what kind of task it is (billing? troubleshooting?) so it picks the right tools, and can flag IRRELEVANT requests to decline politely instead of burning compute. Humans can approve plans, especially risky ones.

RL agents and foundation-model agents share the same frame (environment, actions); the difference is how the planner is built: an RL planner is trained by reinforcement learning, an FM planner is a model prompted or finetuned to plan. The two may merge.

Function calling

Model APIs expose tool use as function calling: you declare a tool inventory (names, parameters, descriptions), the model decides which function to call with which arguments, and your code runs it. You can usually force a tool (required), forbid tools (none) or let the model decide (auto). Pick a request:


    

  

  
Always log the argumentsBoth the function and its parameters are generated, so both can be hallucinated: a tool that doesn't exist, the wrong number of arguments, or a plausible but wrong value. Plan granularity and control flow

  
Plans written as exact function names are easy to execute but break when the tool inventory changes (rename a function and a finetuned planner is out of date). Plans in natural language ("get last week's best seller") survive changes but need a translator into commands. That's the planning/execution trade-off. 7
Reflection and error correction

  
Reflection isn't strictly required, but it helps a lot. Check whether a request is feasible, whether the plan makes sense, whether each step went well, and whether the task is done. ReAct interleaves reasoning and acting: Thought, Action, Observation, repeat. Reflexion adds an evaluator and a self-reflection module that explains failures and feeds the lesson into the next attempt. Cost: more tokens and latency.

  






  
8
Choosing the tools

  
Agent papers range from 5 tools (Toolformer) to 13 (Chameleon) to 1,645 APIs (Gorilla). More tools mean more capability but are harder to use well, and their descriptions eat context. Experiment: compare tool sets, run ablations (remove a tool and see what breaks), drop tools the agent misuses, and plot which tools get called. Different models and tasks prefer different tools; ScienceQA leaned on knowledge retrieval far more than tabular math did. Agents can even build tools: Voyager stores new skills as code in a skill library for reuse.

Failure modes and how to evaluate agents

  
Evaluation means finding failures and measuring how often each happens. Planning failures: invalid tool, valid tool with invalid parameters, valid tool with wrong values, failing the goal or its constraints (including time), and false belief that the task is done. Tool failures: the right tool returns wrong output, a translation step mangles the action, or the needed tool is missing. Efficiency: steps, cost and time per task, compared with a baseline (another agent or a human, remembering they work differently). Classify these:

10
Memory

  
Both RAG and agents juggle more information than fits in context. A model has three kinds of memory: internal knowledge (its weights), short-term memory (the context window) and long-term memory (external stores reached by retrieval). Put essentials for every task in the weights, frequently needed but changing info in context, rarely needed info in long-term storage. Memory lets an agent manage overflow within a session, persist knowledge across sessions (a coach that remembers you; consistent answers to repeated subjective questions), and keep structured data intact.
