Building up an AI application, one step at a time

The earlier chapters covered techniques one at a time. This chapter puts them together: a common architecture, grown step by step as needs appear, and then the user feedback that keeps improving it. The simplest app sends a query to a model and returns the response. Everything else is added when a real need shows up, and each addition brings new ways to fail.

Monitoring and observability run across all of it, and orchestration ties the pieces together. Both get their own sections below.

2

Step 1: enhance context

Context construction is feature engineering for foundation models: retrieval of text, images and tabular data (Chapter 6), plus tools such as web search and other APIs (agents, Chapter 6). Model providers differ in what they support (how many files you can upload, which tools, which retrievers), so compare them as you'd compare models.

3

Step 2: put in guardrails

Input guardrails guard against two risks: leaking private data to outside APIs (an employee pastes a secret into a prompt; a tool pulls in sensitive data) and executing bad prompts (Chapter 5). There's no airtight fix for leaks with third-party APIs, but you can detect sensitive data (IDs, phone numbers, faces, specific keywords, IP) and block it or mask it.

The response uses placeholders like [PHONE_1]; your system swaps the real values back before showing it. This toy detector only spots emails, phone numbers and two-word capitalised names after "I'm"; real tools often use AI to detect sensitive data.

Output guardrails catch failures and set a policy for each. Quality failures: malformed output, factual inconsistency, generally bad responses. Security failures: toxicity, private data, remote code or tool execution, brand-risk content. Track false refusals as well as failures. A system that blocks everything is safe but useless.

Guardrail trade-offsGuardrails add latency, and some teams skip them for that reason. Output guardrails also clash with streaming: tokens reach the user before the full response can be checked. Third-party APIs ship many guardrails, so you need fewer of your own; self-hosting means you can send sensitive data without it leaving your systems, but you build the guardrails yourself. Model providers, API providers and app developers can all add them.

Step 3: add a model router and gateway

A router, usually an intent classifier, sends each query to the right solution: a cheap model for simple requests, a specialist for technical ones, a human for billing disputes, a polite refusal for out-of-scope topics, and a clarifying question for ambiguous ones. Next-action predictors play the same role inside agents. Routers should be small and fast (GPT-2, BERT, Llama 7B, or smaller custom classifiers). Queries may also need trimming to fit the chosen model's context.

A model gateway gives your organization one interface to many models, self-hosted or commercial. Code changes in one place when an API changes, keys are managed centrally (no keys handed to every team), and it's a natural home for access control, cost limits, fallbacks, load balancing, logging and analytics. Off-the-shelf options exist (Portkey, MLflow AI Gateway, Kong, Cloudflare's AI Gateway and others). The core idea, sketched in my own minimal form:

PROVIDERS = {"fast": call_small_model, "smart": call_big_model}
FALLBACK = {"smart": "fast"}

def gateway(req):
    check_quota(req.team)              # access + cost control
    name = req.model
    for _ in range(2):
        try:
            out = PROVIDERS[name](req.prompt, req.max_tokens)
            log_usage(req.team, name, out.tokens)
            return out
        except (RateLimited, Unavailable):
            name = FALLBACK.get(name, name)   # degrade, don't fail
    raise ServiceDown()

Step 4: reduce latency with caches

KV and prompt caches live inside inference (Chapter 9). At the system level there are two more. Exact caching reuses a result only for an identical request: summaries of the same product, repeated vector searches, expensive multi-step answers. Store it in memory, Redis or a database, and evict with a policy such as LRU or LFU. Don't cache user-specific or time-sensitive queries ("What's the weather?"). Careless caching can leak data: a cached answer to "What's my return policy?" built from one user's membership details could be shown to another.

Semantic cache playground

Semantic caching embeds each query, searches for similar cached queries, and reuses the answer above a threshold. Value is dubious: it needs good embeddings, a vector search on every query, a well-tuned threshold, and a high hit rate to pay off. Set the threshold too low and the wrong country's capital comes back. (Similarity here is word overlap, standing in for embeddings.)

Step 5: add agent patterns and write actions

So far each query flows straight through. Agent patterns add loops: the output can go back in for another retrieval, a tool call or a reflection step, and parallel branches can run at once. Letting the system take write actions (send an email, place an order, start a bank transfer) makes it much more capable, and much riskier. Put strong guardrails and, often, human approval in front of them. By now the architecture is complex: more components, more ways to fail, and observability is what makes it debuggable.

Monitoring and observability

Observability should be designed in, not added later. Monitoring and evaluation share the same goal: reduce risk and find opportunities. Three DevOps metrics grade how good your observability is:

MTTDdetectMean time to detection: how long until you notice something broke?
MTTRrespondMean time to response: how long from detection to fix?
CFRchangeChange failure rate: what share of deployments need a fix or rollback? If you don't know it, rethink your platform.

Monitoring tracks a system's outputs to infer that something's wrong; observability assumes you can figure out what from those outputs, without shipping new code. The book uses "monitoring" for the act and "observability" for the whole practice.

Metrics: start from failure modes

Format failures (invalid JSON) are easiest to track. Then quality (factual consistency, conciseness, relevance), safety (toxicity, PII, guardrail triggers, refusal rate, unusual queries), conversational signals (how often users stop generations, turns per conversation), length, per-component metrics (retrieval context relevance and precision), latency (TTFT, TPOT, total, per user) and cost (queries, tokens, requests per second for rate limits). Use spot checks or exhaustive checks, and break everything down by user, release, prompt version, prompt type and time. Check which metrics correlate with business north-star metrics like DAU, session length or subscriptions.

Logs, traces and drift

Metrics say something went wrong five minutes ago; logs say what. Log everything: configs, the user query, the final prompt, outputs, intermediate outputs, tool calls and their results, start and end times, crashes, tagged with IDs so you can find them. Look at production data every day. Traces link related events into the path of one request. Watch for drift: system prompts changed without you knowing (a template update, a coworker's typo fix), users changing behaviour as they learn the system, and the model behind an API changing silently.

AI pipeline orchestration

An orchestrator lets you define components (models, retrievers, tools, evaluators, with easy swaps) and chain them, passing data between steps and alerting when one fails. It's different from a general workflow orchestrator like Airflow or Metaflow. Run steps in parallel where you can: routing and PII removal, for example, can happen together.

A typical chain

Start without oneLangChain, LlamaIndex, Flowise, Langflow, Haystack and others exist, and many RAG and agent frameworks double as orchestrators. Build without one first; external tools add abstraction that can hide bugs and bloat. When you do pick one, check integration and extensibility (does it support your models and databases, and can you add your own?), support for complex pipelines (branching, parallel steps, error handling) and ease of use, performance and scalability (no hidden API calls adding latency).

User feedback

Feedback tells you how the app performs and shows you what to build next, and in AI apps it is also training data, possibly a proprietary edge (a data flywheel). It's user data, so treat it with the same privacy care. Feedback is explicit (thumbs, stars, "did we solve your problem?") or implicit (inferred from actions). Conversational interfaces make implicit feedback richer, because users react in natural language.

Designing for feedback

When to ask

At the start, to calibrate (face ID scans, preferred style), with a neutral default if users skip it. When something goes wrong (hallucination, wrongful block, slowness): let users downvote, regenerate, switch models, or fix the output themselves, as inpainting does for images. When the model is unsure: show two options (full responses side by side, or partial ones to expand), or ask "is this the same person?" as a photo app might. When something good happens, an optional thumbs up still helps, as long as it doesn't clutter or annoy.

How to ask

Fit feedback into the workflow. Midjourney's four images, each with upscale, variation or regenerate actions, yields preference signals as a side effect of normal use; Copilot's grey suggestions are accepted with a single key. Standalone chat apps see less, since they don't see what users do next. Explain how feedback is used. Don't ask for the impossible (comparing two math proofs at a glance). Make options unambiguous. Luma once put an angry emoji where five stars should be. Decide whether feedback is public or private, since visibility changes behaviour.

Feedback isn't a free lunch

Degenerate feedback loop

Six answers styles with similar true quality. Users only rate what they're shown, and the top slot gets most attention. Each round, the system re-ranks by accumulated likes.

Feedback can teach a model to flatterSeveral studies find models trained on human feedback drift toward sycophancy: telling users what they want to hear, agreeing more, not being more correct. Feedback is crucial, but used blindly it amplifies biases and can turn a product into something its builders didn't intend.
