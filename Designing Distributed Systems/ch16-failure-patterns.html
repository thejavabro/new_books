Common Failure Patterns

The same mistakes recur in system after system. Knowing their shape is the cheapest way to avoid them.

1

The thundering herd

A slow page; you hit reload. Congratulations, you are the herd. When a service is overloaded by some amount X, the failed requests are retried while new ones keep arriving, so next minute it faces 2X, then more. Chained services with their own retries multiply it further. The cures, in rising strength: exponential backoff, plus jitter (machines, unlike people, all retry at the same instant), plus a circuit breaker that stops traffic for a while, and a gradual ramp when letting it back in. Capacity drops for a minute at t = 20 s. Choose the clients' behaviour.

2

The absence of errors is an error

Healthy distributed systems always have a trickle of errors, absorbed by retries. So zero errors is suspicious. The book's example: a pipeline that adds subtitles to uploaded movies. The uploader loses its storage permissions. Nothing is uploaded, nothing is processed, nothing fails: error rate 0%. An alert on "errors > 10%" never fires. Alert on too few requests (or too few errors) as well.

Beware the "not my problem" bucket

Errors caused by bad client requests shouldn't count against your reliability. But that bucket becomes a convenient hiding place. One user failing authorization is their problem; every user failing it is your broken auth code. The fix: alongside real traffic, send synthetic requests you control end to end. For those, no error is ever "the client's fault".

4

Versioning: keep three representations apart

If changing your API means updating every client at the same moment, you haven't built a decoupled system. It is tempting to make the external API, the in-memory object and the stored record identical. Keep them separate, with translation between them: then several client versions can talk to one internal version, fields can be renamed or merged without clients noticing, and storage can be migrated or rolled back on its own schedule. Pick a client version.

The myth of the optional component

  
A cache is added as a nice-to-have: if it vanishes, read from the source of truth. Then traffic grows, and quietly the system can no longer meet its goals without it, yet nobody upgraded the cache's reliability to match. Local in-memory caches are especially sneaky: easy to add, many per app, growing with the system, hard to see. Choose when the cache dies.

  

    
    

    

  






  
6
Oops, we cleaned up everything

  
A photo service has a user database, a user API, photo storage, and a garbage collector that deletes photos whose owner no longer exists (for privacy law and to stop storage leaking). One day the database is unreachable, and the user API returns 404 Not Found instead of 500. To the collector, every user has vanished. Try the safeguards the book recommends.

  

    

    

    

    

  

  
Blame the system, not the personDifferent teams owned the user API and the collector; nobody holds a whole distributed system in their head. People will always make mistakes. The fix is technical: normal deletion runs at about 1% of users a day, so a 100× spike should be throttled and then stop the collector until a human resets it.






  
7
"Compiler" problems: 100% broken for a few users

  
Rare races look like flakiness, and users just reload. Worse are bugs that hit specific inputs every time: with a huge input space, someone eventually sends a valid input that crashes you, like the programmer who finds a compiler bug. Fuzzers (and the old SQL injection attacks) do it on purpose. Two defences: replay a representative sample of real inputs (from every region and every time of day), and fuzz with random but valid data, which LLMs can now help generate. Choose your test data and see which bugs you'd catch.

  

    

    

    

  






  
8
Processing work nobody is waiting for

  
The opposite of the herd: after an outage is fixed, the backlog remains. If the system normally runs near capacity, it crawls through old requests whose users have long since hit reload, while new requests wait behind them. Ten minutes down can mean hours of slowness. The book's three remedies can be combined. Toggle them.

  

    

    

    

  






  
9
The second-system trap

  
Seeing all these flaws, you want to start over: a new system built alongside the old, switched on "when it is ready". It rarely is. Business-critical features and fixes keep landing in the old system, so the new one chases a moving target; and when it hits production bugs it gets switched off, so it never earns the mileage it needs. Better: improve one microservice at a time, and put abstractions (say, around storage) between business logic and the parts you expect to replace, so old and new can run side by side.

  

    
    

    

  






  
10
Conclusion: a new beginning

  
Every company is becoming a digital company, so the number of reliable, agile distributed systems needed has jumped by an order of magnitude, far faster than the supply of people who can build them. Software has been here before: compilers, then object-oriented languages and managed code, each distilled expert practice into tools and patterns a much larger group could use. Containers and orchestrators are the new tools; sidecars, ambassadors, sharded services, functions, work queues and the rest are the patterns. The book's closing hope: stop building from scratch alone and share reusable implementations of these canonical patterns.
