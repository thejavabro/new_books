AI Inference and Serving

Large models are now a building block of distributed systems. Serving them brings new constraints: GPUs, huge files, retrieval and testing outputs that are never the same twice.

1

Models, training, fine-tuning, inference

The book treats AI as one more function a distributed system serves. A model is a large set of numeric weights (trillions, in big LLMs) that maps inputs to outputs. Unlike ordinary code it is trained: feed in an example input, compare the output to the expected one, push the error back through the weights, repeat a very large number of times on dedicated hardware. 2

The prompt wraps the question

When you chat with an LLM, your words are rarely sent alone. The application wraps them in a prompt with instructions and context (location, preferences, rules for the answer). Shaping that wrapper is prompt engineering, and it largely decides answer quality. Type a question.

3

Hosting: latency, GPUs and small models

Start with pretrained models before investing in training: not every application suits today's AI. For interactive use, latency rules: people notice around 250 ms and drift off after a few seconds. Big LLMs need expensive, sometimes scarce, GPUs and cannot run on a phone. Small language models (billions of weights, not trillions, trained on focused data, such as Microsoft's Phi family) score lower on benchmarks but are far cheaper and faster, and can run on the device, which keeps user data off the cloud. 4

Distributing models: formats, hubs, caches, rollouts

Each framework has its own file format, but an open one, ONNX, works across them and across model hubs. Hubs such as Hugging Face are to models what Docker Hub is to images: download a popular model with a line of Python. Models are big, though. If every replica downloads its copy at startup, every restart and rollout waits minutes. Cache the model once in a shared file system or in-memory store.

Assumes 1 Gbit/s shared download from the hub versus 10 Gbit/s per node from a local cache. Illustrative.

Treat a new model like new code: progressive exposure. A model change can shift quality in surprising ways, so start with a small percentage of users or one region and widen as confidence grows.

5

Don't pay for the big model while building the UI

Every inference is expensive. When you're working on the interface or other non-AI parts, a full model is wasted money. Put inference behind your own REST API with a parameter, or a Kubernetes Service, choosing the model per environment: a cheap SLM in dev and CI, the full model in production. Evaluate on the full model only when quality is what you're testing.

6

Retrieval-augmented generation

A model is frozen at training time and knows nothing about you. Ask "who is the closest friend to my current location?" and it cannot know your friends or where you are. RAG runs ordinary queries first (your contacts from a database, your position from the phone) and folds the results into the prompt. Nothing personal is baked into the model's weights, so it cannot leak to other users; it travels only with the request of someone allowed to see it.

7

Testing: from 'correct' to 'good enough on average'

assertEquals(expected, actual) doesn't work when outputs vary and a prompt tweak can help one input and hurt ten others. Test statistically: score a large set of prompts before and after a change, and pass it only if average quality doesn't drop. Who scores? Humans are too expensive, so ask a model whether each answer is good: "letting the inmates run the asylum", the book admits, but it works well in many cases. Try two candidate prompt changes on 200 test prompts.

And during rollout, watch user feedback (thumbs up/down, retries, abandonment) alongside errors and latency: a release can be fast and error-free and still make answers worse.
