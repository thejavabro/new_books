The Sidecar Pattern

A sidecar is a helper container that sits next to your application in the same pod and adds a capability, like HTTPS, configuration reloads or a debugging UI, without changing the application itself.

1

Why split one machine into several containers?

Part II looks at groups of containers that always run together on one machine. Why split them at all? Containers draw three boundaries: resources (this part gets two cores and 8 GB), ownership (this team owns this image) and concerns (this image does one thing). The resource boundary is easiest to see. Below, a user-facing server and a background config loader share a machine. Let the loader leak memory and watch who pays.

All patterns in this part assume the containers are co-scheduled onto one machine and can share volumes, the network namespace and memory. Kubernetes calls this group a pod.

2

The shape of a sidecar

A sidecar pattern has exactly two parts. The application container holds the core logic; without it there is no application. The sidecar augments it, often without the application knowing. Because they live in one pod they share the hostname, the network, parts of the filesystem and more. Toggle what is shared to see what each enables.

3

Example: HTTPS for a service you cannot rebuild

A legacy service speaks only plain HTTP. Security now requires HTTPS, and the old build system no longer works. Rather than resurrect the build, the team binds the legacy server to 127.0.0.1 and adds an nginx sidecar that terminates HTTPS on the pod's external address and proxies over loopback. Unencrypted bytes never leave the pod. Send a request through each setup.

The same trick adds certificate rotation, or authentication and authorization, to applications that are hard to change.

4

Example: pushing configuration to an app that reads a file

Older apps read a config file at startup. Cloud environments prefer a configuration API (Kubernetes has ConfigMaps) so changes can be pushed, audited and rolled back. A config manager sidecar bridges the two through a shared directory.

5

Sidecars as reusable modules: topz

Sidecars are not only for legacy code. Suppose every service should expose a /topz page listing its processes and their resource use. You could ask every team to link a library, then write that library in every language you use, and keep the versions aligned. Or you could ship one topz sidecar that shares the app's PID namespace, and have the orchestrator inject it everywhere.

Library in each appTailored and possibly faster. Every team must opt in; behaviour drifts between languages; new languages start with nothing.
Sidecar containerOne implementation, one UI everywhere, any language. Slightly less tailored. The book likens it to buying off the rack instead of bespoke: right for most, not for extreme performance needs.
# start any app, then attach topz to its process table
docker run -d my-app            # prints a container id → APP_ID
docker run --pid=container:$APP_ID -p 8080:8080 topz-image
# now browse http://localhost:8080/topz

Building a git-push PaaS from two containers

Sidecars can carry real application logic too. Pair a Node.js server run under nodemon (which restarts on file changes) with a sidecar that loops git pull; sleep 10 into a shared volume. Push code and it goes live, with no deploy pipeline written. Push a few commits and watch the timeline.

Time runs at 10× speed. The sidecar pulls every 10 s.
