Monitoring and Observability

You cannot run what you cannot see. Logs, metrics, alerts and traces each answer a different question about a running distributed system.

Four pillarsLoggingMetricsRequest monitoringAlertingTracingAggregationQuick check
1

Notice it before the customer does

Distributed systems are services: always on, for users in every time zone. To be reliable you must notice a problem before the customer does, and then understand it. The book builds observability from four parts. Click one to see what it captures from the same burst of traffic.

2

Logging: leveled, contextual, conditional

Every system logs, even if only with printf. The first thing you notice in a distributed system is the sheer volume. A logging library adds what raw prints lack: timestamps so you know the order, context (request ID, user, thread) so you can pull one request out of many identical lines, and levels so the detail stays in the code but out of the stream. Debug logging can even be switched on conditionally for one component on a live server; carefully, since it adds latency. Play with the viewer.

What to logEvery error or exception, and anything weird: a request that was slow, and which part was slow. Not the play-by-play "function foo called". The old joke: you learn what to log by what you wished you had logged last time. Better: imagine the hardest bug in this code and log what you'd need to solve it.
3

Metrics: counts, values, histograms

Metrics summarize many requests over time as time series. The book uses Prometheus, the de facto standard, often feeding a cloud monitoring service. Three kinds of data matter.

A raw count is dull; its rate (count now minus count a window ago) is what you graph. Window too small and the rate flickers between 0 and 1; average over a longer window to see the real shape.

Pull for services, push for batchPrometheus scrapes (pulls) metrics from running apps. A batch job may finish before the next scrape, so it pushes its metrics to the Prometheus push gateway, which is scraped instead.
4

Monitoring requests: labels and latency

Start with the request count, labeled with the HTTP status code so you can graph 2xx versus 5xx. Labels must be a small set of discrete values, though. Latency can't be a label: it's a separate histogram metric (which can itself carry the code label). Customer ID can't be a label either: there are too many. That kind of question goes to log search, which is slower but richer. Pick labels and watch the number of time series.

Alerting: thresholds, SLOs and anomalies

Nobody watches dashboards all day, and finding out from a customer complaint (a "CRI") is the worst way. Alerts are rules over metrics or logs that page a human. Your alert thresholds effectively are your SLO: whatever you don't alert on, you won't notice. But too many alerts burn people out, and false alarms teach them to ignore the pager. Tune the threshold on a week of p90 latency containing three real incidents.

Static thresholds assume every user sees the same thing. Suppose a bug takes 1% of customers completely offline: the global error rate reads 1%, right at a typical threshold, and nothing fires. Anomaly detection (a form of AI) spots that customer A is 100% down while B is fine. As systems grow, it becomes essential.

6

Tracing: one request across many services

Per-service views show all requests at once, but not the path of one. Tracing rebuilds it. Give every incoming request a unique correlation ID (a big random number, or better a hash of things like path and source IP), pass it along in a header such as x-my-app-correlation-id, and attach it to every log line and metric. Then group by it. In practice, use OpenTelemetry, which has SDKs for most languages and plugs into many backends. Click a span.

7

Aggregating, downsampling and cold storage

Observability data piles up fast. First you want to search across replicas: tools like ktail merge logs from many pods; a search index like Elasticsearch lets you query them like the web. Running such an index well is hard, so the book recommends a logging or metrics service. To cut cost, downsample old data (per-second metrics become per-minute averages after a week; keep only errors from old logs), or keep full fidelity in cheap, slow cold storage for compliance.
