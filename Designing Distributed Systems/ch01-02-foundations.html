From one machine to many

The book opens with a short history. Computers started as single-purpose calculators, became general-purpose, learned to time-share, and then were wired together. Each step made programs more powerful and harder to reason about. Step through the eras to see where the complexity moved.

The bargain of distributionSpread across many machines, a system can survive the loss of any one of them, and the teams who build it can split up along the same lines. The price is a system that is much harder to design, build and debug. Containers and orchestrators are what make that price affordable.
2

Why a book of patterns?

Software has been through this kind of shift before. Knuth's volumes taught algorithms independent of any one machine. The "gang of four" gave object-oriented programmers names for recurring designs, which then became reusable libraries. Open source showed that this is community work. Burns argues containers can do the same for distributed systems: a pattern here is a general blueprint, not a recipe for one product or stack.

APIs, RPCs and the synchronous trap

A distributed system is held together by APIs called over the network: remote procedure calls. HTTP plus JSON (REST) dominates because everything speaks it, though gRPC and others exist. A synchronous API answers only when the work is done. An asynchronous one accepts the job, returns an operation ID, and lets the caller poll. Anything that takes minutes belongs in the second camp, because network calls time out.

Two more ideas from this section: generate client libraries from an interface description (OpenAPI and similar) rather than making everyone hand-roll HTTP calls, and publish SLOs, service level objectives for latency, reliability and throughput, so callers know what they can build on.

What counts as an error?

Reliability sounds easy: successful requests divided by all requests. But almost every HTTP request "succeeds" at the protocol level; the trouble hides in the status code. 2xx is success and 5xx is failure. 3xx is usually fine. The 4xx range is the gray zone: a 404 could be a client typo or your service looking in the wrong place; a 403 could be a bad password or your auth service being down. Why the average lies

Averages mislead in two ways. A small group of very fast (or very slow) requests drags the mean away from what most people feel. Worse, a user's experience is usually many requests that all have to succeed. If one in a hundred requests is slow, a page that makes forty requests is slow for most visitors. Idempotency: safe to say twice

Designing distributed systems is mostly anticipating failure, and the first tool is idempotency: doing an operation once or ten times gives the same result. x = 5 is idempotent; x = x + 1 is not. If an operation is idempotent, the cure for "did it work?" is simply to try again. It is the same idea as declarative versus imperative configuration.

7

At least once, at most once, never exactly once

When retries are not harmless, you have to choose what failure looks like. At-least-once delivery guarantees the message arrives but maybe several times. At-most-once guarantees no duplicates, but a message can vanish, so someone must notice and try again; think of charging a credit card. True exactly-once is so hard to achieve that the book advises designing for one of the other two.

8

Relational integrity, strong and eventual consistency

Relational integrity asks whether data spread across several stores agrees: for every user in the balances table, is there a row in the addresses table? Guaranteeing that takes distributed transactions and locks, which cost speed. Roughly, SQL databases pay that cost for you; NoSQL key-value stores hand the problem to your code.

Data consistency asks how fast a replicated write becomes visible everywhere. A strongly consistent write waits for every data center; an eventually consistent write returns after one and replicates in the background. Try both, then try reading your own write.

CAP, read gentlyConsistency, availability and partition tolerance: you cannot guarantee all three. The book's reading is practical rather than absolute. Optimizing one always trades against the others, and "good enough" availability (say 99%) can buy the consistency you need. Choose early: the storage model spreads through all your code and is very hard to change later.

Orchestrators, liveness and readiness

An orchestrator such as Kubernetes takes a desired state ("three frontends, five backends") and keeps reality matching it. To do that it needs to know how each piece feels. Liveness: is the process still working, or should it be killed and restarted? Readiness: should it receive traffic yet? A container that is warming a large cache is alive but not ready.
