Adapters

Different applications emit metrics, logs and health in different shapes. An adapter container translates them into one standard interface so shared tools can manage them all.

Many shapes in, one shape out

The third single-node pattern points the other way. Real systems are a mix: code you wrote, code a vendor sent, open source binaries you never compile. Each logs, reports metrics and signals health its own way. An adapter container sits next to an application and reshapes its interface into the one standard the rest of your tooling expects. Toggle the adapters to see what your monitoring system sees.

Adapter #1: make anything scrapeable by Prometheus

Monitoring standards abound (syslog, Windows ETW, Java's JMX...) and differ in both protocol and style: some push, some get pulled. Prometheus pulls: it scrapes a metrics endpoint from every container into one time-series database you can query and chart. Redis does not speak that format, but an off-the-shelf exporter container does the translation. Two existing images, zero custom code.

→

    
left: what Redis reports when asked · right: what the adapter serves on /metrics

  

  

    
kind: Pod
spec:
  containers:
  - name: redis
    image: redis
  # the adapter: translates to
  # the Prometheus format
  - name: adapter
    image: a-redis-exporter

    
  • Ship a new Redis without touching the exporter, and vice versa.
  • The monitoring team can supply the adapter; app teams just add it.
  • Separate CPU and memory limits: a misbehaving exporter cannot starve the user-facing server.

Adapter #2: normalize the logs

  
Containers are expected to log to stdout, because that is what kubectl logs shows. Many programs instead write per-level files, and every logging library formats timestamps and levels differently. You do not care about the differences; you want every line to arrive structured and timestamped. A logging adapter (the book uses fluentd and its plug-ins) tails the files and rewrites the lines.

  

    

    
four apps, four formats

    

  

  
Turning commands into historySome data only exists while someone is asking. Redis's SLOWLOG lists slow queries only on demand, and Apache Storm exposes stats only through a REST API. A fluentd adapter pointed at localhost polls them and writes a time series of logs, so the evidence is already there when you investigate a problem at 3 a.m.

  
# fluentd adapter source block (shape only)
<source>
  type  redis_slowlog
  host  localhost      # shared network namespace
  port  6379
  tag   redis.slowlog
</source>

Why not just change the application?

  
If you own the application, changing it to speak the standard is fine. But most of the time the image belongs to someone else. Forking it means you now rebuild, patch and rebase your copy every time upstream ships. An adapter runs alongside their image untouched, and can be shared with everyone else who runs it.

Adapter #3: a richer health check

  
An orchestrator can check that a process runs and a port is open. That says little about whether a database can actually answer queries. Kubernetes can run a script or call an HTTP endpoint as a health check, so put a small program in an adapter container that runs a representative query against MySQL on localhost and returns 200 or 500. The MySQL image stays stock. Pick a situation and compare the two checks.

  

    

    
Port check"is something listening on 3306?"
Query adapter"does SELECT ... FROM orders succeed?"

    

  

  
// the adapter, in spirit (Go-like pseudocode)
db := open("localhost:3306", user, password)
http.HandleFunc("/healthz", func(w, r) {
  if err := db.Exec(testQuery); err != nil {
    w.WriteHeader(500); return    // orchestrator restarts mysql
  }
  w.WriteHeader(200)
})

  
The point the book stresses: a shared MySQL health adapter lets people who don't know how to health-check MySQL benefit from someone who does. Patterns build communities, not just systems.
