Work Queue Systems

A work queue takes a pile of independent tasks and spreads them over a pool of workers. Split it into reusable containers and you get a batch system you can assemble from parts.

Batch work, and the simplest batch pattern

Part IV turns from servers that run forever to batch jobs that run, finish and stop: rolling up telemetry, weekly sales reports, transcoding video. Batch is about pushing a lot of data through quickly using parallelism. MapReduce is the famous example; the work queue is the simplest. Every item is independent, a pool of workers chews through them, and the pool grows or shrinks so each item finishes in reasonable time.

The insight of this chapter: almost all of a work queue is generic. Only two small pieces are specific to your job. Click the boxes.

2

The source container: an ambassador for work

The queue manager needs a list of work. Where that list lives varies: files on a network share, objects in a cloud bucket, messages in Kafka or Redis. So the manager talks to a source container in its pod over a tiny HTTP API on localhost. That makes the source an ambassador, and there can be one reusable source per kind of storage. Pick a backend and call the API; the answers have the same shape whatever the backend.


  

  
  • Note the v1. Versioning an API on day one costs almost nothing; retrofitting it later is expensive.
  • There is no "mark as done" call. Tracking progress is the manager's job, which keeps each source trivially simple.






  
3
The worker container: a file, not a web server

  
The worker is different. It runs once per item in its own pod, started through the orchestrator, so the manager must hand work across the network. An HTTP endpoint would be overkill (workers are often a shell script around a command-line tool) and a security risk (anyone in the cluster could inject work). So the interface is a file: the manager writes the item's data into a ConfigMap, mounts it, and sets WORK_ITEM_FILE to its path.

  

    
#!/bin/sh
# a complete worker: thumbnail one video
IN=$(jq -r .path "$WORK_ITEM_FILE")
ffmpeg -i "$IN" -vf fps=1/10 thumb%03d.png
cp thumb*.png /output/$(basename "$IN")/

    
The book's video-thumbnailer needs just two user containers: a source that lists *.mp4 files on a shared disk, and a worker that runs ffmpeg. Generic workers exist too: "download a file, run the script you pass me, upload the result" covers many queues with no new image at all.

The shared manager: a loop over Kubernetes Jobs

  
The reusable manager is a short loop. Kubernetes does the heavy lifting: a Job runs a container until it succeeds, even if a machine dies; and labels and annotations on Jobs record which item each one handles. So the manager needs no storage of its own: the list of Jobs is its state. Run it.

  

    
every 10 s in real life

    

    

  

  
while True:
    items = get("http://localhost:8000/api/v1/items")["items"]
    jobs  = {j.metadata.name for j in k8s.list_jobs(namespace)}
    for item in items:
        if item not in jobs:          # the diff is the whole algorithm
            k8s.create_job(job_for(item))
    sleep(10)

Keeping up: interarrival time vs. processing time

  
Spawning a Job per item as fast as items arrive creates feast-or-famine load on the cluster. Capping parallelism smooths it, but then items wait. The rule is simple: the effective processing time (time per item ÷ parallelism) must be less than the interarrival time of new items. Otherwise the backlog grows without limit. Tune the system, or let the autoscaler do it.

Scaling down is trickier than scaling up; keep a safety margin. Rather than writing your own scaler, the book points to KEDA (Kubernetes Event-Driven Autoscaling), which can scale on queue length in many pub/sub systems, files on disk and more.

The multiworker: compose workers from parts
