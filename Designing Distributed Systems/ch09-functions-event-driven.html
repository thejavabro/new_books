Functions and Event-Driven Processing

Functions-as-a-service run your code only when an event arrives. That makes some jobs trivially simple and others painfully expensive. Here is where the line sits.

Event-driven is not the same as serverless

Missing from the source PDF: Chapters 7 (Sharded Services) and 8 (Scatter/Gather) come before this one in the book but are absent (a placeholder page) in the copy used here, so they are skipped.

Everything so far has been long-running servers. Some work only needs to exist for one request or one event. Functions-as-a-service (FaaS) runs your code when an event arrives and bills per request. People call it "serverless", but the book separates two ideas: event-driven (code triggered by events) and serverless (you never see the machines). You can have either without the other. 2

Benefits for developers, headaches for operators

FaaS shrinks the distance from code to running service: no image to build, automatic scaling and restarts, and a building block even finer than a container. The same radical decoupling is its weakness. Functions share no memory, so all state lives in storage; and nobody holds a map of who calls whom. The book's cautionary example: A calls B, B calls C, C calls A. Start a request and watch.

Invocations: 0Bill: $0.00

The loop ends only when a timeout hits, or your budget does. Lesson: FaaS demands rigorous monitoring and alerting, which eats into its simplicity.

Pattern: the decorator

FaaS shines at small, stateless transformations of a request or response on its way to or from a service, much like a Python decorator wraps a function. Example: defaults. JSON makes "missing" look like null, which reads as false, so a field that should default to true is awkward. Rather than mixing defaulting into the API server, a function fills in the gaps and forwards the call. Edit the request.

def add_defaults(ctx):
    req = ctx.json
    req.setdefault("color", "blue")
    if req.get("name") is None:
        req["name"] = random_name()
    return forward_to_api(req)   # the real service

  
Why not an adapter container?You could. But an adapter in the API's pod scales with the API. Defaulting is cheap and needs far fewer instances. A function also makes it easy to try several decorators (validation, defaulting) before baking the winner into the service.






  
5
Pattern: event handlers (two-factor login)

  
The book draws a line between requests, which belong to a session of interactions, and events, which are one-off and asynchronous: a user signed up, a file was uploaded, a machine is about to reboot. Events are independent and bursty: a natural fit for functions. Example: after a correct password, send a one-time code by text. Doing it inline makes the login page wait on the SMS provider; firing an async webhook does not.

Pattern: event pipelines

  
Some workflows read like an old flowchart: a directed graph where each node is a function or webhook and each edge a network call. Unlike a microservice mesh of long-running servers, a pipeline is event-driven and can include very slow, very different steps, even a human closing a ticket.
