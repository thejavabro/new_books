From one node to many: monoliths and microservices

Part III leaves the single machine. Multinode patterns are loosely coupled: components talk over the network, often in parallel, and coordinate loosely. The popular word for this is microservices: many small services with defined APIs, as opposed to a monolith that does everything in one tightly coordinated program.

2

Why even a tiny service needs two replicas

The simplest multinode pattern: identical stateless servers behind a load balancer. Stateless means no saved state is needed, so any replica can answer any request. Replication buys scale, but first it buys availability. Play with the numbers to see how fast a single instance must be redeployed to hit its target.

Load balancing, scaling out and readiness

Add replicas to handle more users: horizontal scaling. The load balancer also gives the service one stable name, independent of any replica. But it must only send traffic to replicas that are ready: many apps are alive for a while before they can serve (connecting to databases, downloading files). The book's dictionary server, for instance, starts at once but only reports ready after downloading its 8 MB dictionary. Add a replica, kill one, and toggle the readiness probe.

4

Sticky sessions, and how they break

Sometimes a user should keep hitting the same replica, because their data is cached there or the interaction keeps state between requests. A session tracked service hashes the source and destination IP to pick a replica (ideally with consistent hashing, so scaling moves few users). Inside a cluster that works. Two things break it.

5

A caching tier: few and fat beats many and thin

Stateless code can still be expensive: database queries, rendering. A caching web proxy (the book uses Varnish) keeps responses in memory, so the second request for the same page never reaches your servers. You could run the cache as a sidecar beside every web server, but then each page is stored once per replica. With a fixed memory budget, more copies means fewer distinct pages and a lower hit rate. Slide to see it.

Model: 20,000 pages with a typical skewed popularity (a few pages get most traffic); each GB holds 1,000 pages; every replica sees all pages. Numbers are illustrative.

So: a separate cache tierPut two big caches above many small web servers (Node.js uses one core, so many small replicas suit it). Two catches: IP-based session affinity now sees only the cache's IP, so use a cookie or header instead; and the cache gives you a natural place for two more jobs.
6

Rate limiting at the edge

Denial of service is usually an accident: a misconfigured client, or a load test pointed at production. The caching layer is a good place to throttle, by IP, path or login. The advice: a small limit for anonymous callers and a bigger one for logged-in users, which also tells you who caused the load. Over the limit, return 429, and tell callers how much they have left in a header such as X-RateLimit-Remaining. Fire some requests.

For a real, determined attacker, the book recommends adding a cloud provider's DDoS protection: edge throttling alone will not hold.

7

SSL termination and the complete serving stack

Varnish cannot terminate SSL, so a third replicated tier of nginx handles HTTPS and forwards to the caches. Use a different certificate at the edge than inside, and ideally one per internal service, so each layer can roll out independently. Three Deployments, three Services. Follow one request.
