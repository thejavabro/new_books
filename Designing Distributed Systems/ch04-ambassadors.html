Ambassadors

An ambassador is a container that stands between your application and the rest of the world. The app talks to localhost; the ambassador handles sharding, service discovery and experiments.

The patternShardingService brokeringExperimentsQuick check
1

An ambassador speaks for your app

A sidecar adds something to your application. An ambassador stands between your application and the outside world and brokers every conversation with it. The app connects to what looks like a simple local service on localhost; the ambassador knows the messy reality behind it. As with every single-node pattern, the two containers share a pod, and the ambassador is a modular piece written once and reused by many apps.

2

Ambassador #1: talk to a sharded store as if it were one

When the data no longer fits on one machine, you shard: split it into disjoint pieces on separate machines. Now every request needs routing to the right shard, and old code expects one backend. Worse, development usually has one shard and production many. A sharding ambassador hides all of it: the app talks to localhost:6379, and the proxy hashes each key to a shard. Type a key to route it.

How the proxy hashes matters when you add a shard. Naive hash(key) % N reshuffles nearly every key, which empties a cache all at once. The book's twemproxy example uses ketama, a consistent-hashing ring, so only a slice of keys moves. Compare:

# ambassador config (twemproxy style)
listen: 127.0.0.1:6379   # app sees "redis"
hash: fnv1a_64
distribution: ketama      # consistent ring
auto_eject_hosts: true    # drop dead shards
servers:
  - shard-0.redis:6379:1
  - shard-1.redis:6379:1
  - shard-2.redis:6379:1

A StatefulSet gives each Redis replica a stable name, a headless Service turns those into DNS entries (shard-0.redis ...), and a ConfigMap mounts this file into the proxy container. Then any app container can be dropped into the pod beside it.

Client side or server side?You can also put a stateless routing tier in front of the shards: an "ambassador as a service". Clients stay simple, the sharded service gets harder to deploy. Which is better depends on where team lines fall and whether you are writing code or deploying off-the-shelf software.
3

Ambassador #2: find the right database anywhere

A portable app has to find its dependencies wherever it lands. MySQL might be a managed cloud service, a VM in a private data center or a container on a laptop. Discovering and wiring that up is service discovery, done by a service broker. Put the broker in an ambassador and the app always just opens localhost:3306. Pick an environment.

4

Ambassador #3: split traffic for experiments

Request splitting sends some fraction of traffic to a different implementation, usually a beta, to check it is reliable and fast enough. The book's nginx ambassador gives production a weight of 9 and the experiment a weight of 1: a 10% experiment. It also hashes on the client's IP so each user sticks to one side instead of flip-flopping between versions. Send a few rounds of requests from 30 users.

# the heart of the ambassador's nginx.conf
upstream backend {
  ip_hash;                 # same user → same side
  server web        weight=9;
  server experiment weight=1;
}
server { listen localhost:80; location / { proxy_pass http://backend; } }
