Event-Driven Batch Processing

Chain work queues together and the output of one stage becomes the input of the next. A handful of plumbing patterns cover almost every workflow.

1

Chaining queues into workflows

A single work queue turns one input into one output. Real batch jobs need several steps, or several outputs from one input. So queues get linked: the completion of one stage is the event that feeds the next. The result is a workflow, a directed acyclic graph of stages. Like a web of functions, it is hard to understand without a blueprint, and error handling quickly complicates it. A small vocabulary of linking patterns keeps it readable.

2

Copier, filter, splitter, sharder, merger

Plain chaining (one queue feeds the next) needs no name. These five describe everything else. Pick one and press play: each coloured token is a work item.

3

Copying to buy reliability and speed

A copier can also trade compute for reliability. Run every item twice and keep whichever finishes first: a 1% crash rate becomes 0.01%, and a rare 60× slowdown almost vanishes. The book is clear that fixing the worker is the better long-term answer; doubling is a stopgap when you can't.

4

Sharding for blast radius and spread

A sharder splits one queue evenly across several. Two payoffs. A bad worker release can be rolled out shard by shard, so a crash hits a quarter of users, not all. And shards can sit in different regions to even out load and survive a region failure. When a shard is unhealthy, the sharding function spills its work onto the healthy ones. Break some shards.

6

The plumbing: publish/subscribe

Stages could pass files through a shared directory, but that ties you to one node or a network file system. The usual answer is a pub/sub service: publishers write messages to named topics, the service stores them reliably, and subscribers receive them. Clouds offer managed ones; Kafka is the popular open source choice, easy to install on Kubernetes with Helm. Typically each stage's output is a topic, so a three-way sharder writes to photos-1, photos-2, photos-3. Two settings matter when creating a topic.

7

Uneven work and work stealing

Real work items are not identical: a longer movie, a deep directory tree your code handles badly. Usually it averages out, until all the slow items land in one queue, like a grocery checkout lane stuck behind a full trolley. Work stealing: a worker with an empty queue takes items from the back of the longest other queue (the back, because nobody is about to start on those). Run both.

8

Crashes, poison items and the retry queue

Queues usually hide a message while a worker processes it and delete it only on a "completed" acknowledgment. If the ack does not come in time, the message reappears for someone else. That rescues work from crashed workers, but a merely slow worker means two workers on one item, so assume duplicates and make work idempotent. Then there is the poison item that crashes every worker that touches it: count its attempts and back off exponentially until it is set aside.

Last trap: after a stall (say a downstream dependency was returning garbage), the backlog of old retries sits in front of fresh work, though the fresh work is often what users still care about. Keep two queues, fresh and retry, and serve them with priority.
