The State of Things

An object whose behavior depends on its mode tends to grow nested if-statements everywhere. State turns each mode into a class, so the object appears to change its class as it changes state.

1

Start with a state diagram

A streaming audio player can be Stopped, Playing, Paused or Buffering. The user (and the network) trigger actions: play, pause, stop, data-runs-out, data-arrives. Each action means something different depending on the current state, and some actions mean nothing at all. Drive the player; the diagram follows.

2

The conditional version

The first implementation keeps the state in an int and gives every action method an if/else over all states. It works, until the product team asks for ads. Toggle the change request and see how much of the existing code you must reopen.


    

  

  
SmellsNot closed for modification: every new state touches every action. Transitions are buried in conditionals. Nothing object-oriented about it. And the next change is likely to introduce bugs in working code.






  
3
One class per state

  
Instead: define a PlayerState interface with one method per action. Write one class per state that implements what each action means in that state. The player (the context) holds a reference to its current state object and delegates every action to it. A transition is just the state telling the context which state object comes next.

  
interface PlayerState { void play(); void pause(); void stop(); void starve(); void refill(); }

class Paused implements PlayerState {
  private final Player player;
  public void play()  { player.resumeAudio(); player.setState(player.playing); }
  public void pause() { /* already paused: ignore */ }
  public void stop()  { player.rewind(); player.setState(player.stopped); }
  // starve(), refill(): nothing to do while paused
}

class Player {                      // the context
  PlayerState state = stopped;
  public void play()  { state.play(); }   // delegate, no conditionals
  public void pause() { state.pause(); }
}

  

  
The State Pattern
Allows an object to alter its behavior when its internal state changes. The object will appear to change its class.






  
4
Same diagram as Strategy, different intent

  
The class diagrams of State and Strategy are practically identical: a context delegating to an interchangeable object. The difference is who changes that object and why.

  

    
StateStrategy

    
Who swaps the objectUsually the states or the context, automatically, as things happenThe client, deliberately

    
Client awarenessClients barely know states existClients often choose the strategy

    
Changes how oftenConstantly, as part of normal operationRarely; often once at setup

    
Think of it asAn alternative to lots of conditionals in the contextA flexible alternative to subclassing
