Encapsulating Invocation

Turn a request into an object and you can store it, pass it around, queue it, log it and undo it. The thing that asks no longer needs to know the thing that does.

1

Turning a request into an object

A keyboard shortcut, a menu item and a toolbar button can all trigger "make this bold". If each one calls the document directly, the UI is welded to every operation the app can perform, and adding undo means touching every button. The Command Pattern puts each request in an object with one method, execute(). The button only knows it holds some command. Step through who does what.

The Command Pattern

Encapsulates a request as an object, thereby letting you parameterize other objects with different requests, queue or log requests, and support undoable operations.

2

Programmable shortcut keys

Here is an invoker: four shortcut slots. The client (you) loads each slot with a command object. The receiver is a tiny text document. Assign commands, press keys, and use Undo. Slots start out holding a NoCommand, a null object that does nothing, so the invoker never has to check for null.

Undo stack (top = next undo)
Redo stack
interface Command { void execute(); void undo(); }

class AppendText implements Command {
  private final Document doc; private final String text;    // receiver + parameters
  public void execute() { doc.append(text); }
  public void undo()    { doc.deleteLast(text.length()); }   // knows how to reverse itself
}
class Uppercase implements Command {
  private String before;                                       // state saved for undo
  public void execute() { before = doc.text(); doc.set(before.toUpperCase()); }
  public void undo()    { doc.set(before); }
}
3

Macro commands

A MacroCommand is itself a command that holds a list of commands. Execute runs them in order; undo runs their undos in reverse. Record a few key presses below, save them as a macro, and the macro can go into a slot like any other command.

While recording, press the shortcut keys above. Each press is executed and also added to the macro.

4

Queuing requests

Because a command is a package of receiver + action + parameters, it can be created in one place and run later somewhere else. A job queue accepts commands from anywhere; worker threads take the next one and call execute() without knowing whether it's resizing an image or sending an invoice.

5

Logging requests for recovery

Add store() and load() to commands and you can write each one to disk as it runs. After a crash, reload the log and re-execute the commands in order to get back to where you were. That is how many systems recover big data structures without saving the whole structure on every change: checkpoint now and then, log commands in between.

6

Commands as lambdas

If a command interface has a single abstract method, a Java lambda (or a method reference) can be the command. No class per action needed. You lose undo unless the interface grows a second method, so use lambdas for simple fire-and-forget commands.

shortcuts.set('B', () -> doc.toggleBold());
shortcuts.set('S', doc::save);               // method reference
button.addActionListener(e -> doc.print());  // GUI listeners are commands too
