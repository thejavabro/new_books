Two collections, two loops

A music app merges two catalogs. One team stored its tracks in a fixed-size array; the other used a linked list. A third, newer catalog uses a hash map keyed by track ID. The player that shows "everything" now has three loops, each tied to an internal data structure it should never have needed to know about.

for (int i = 0; i < indieCount; i++) show(indieTracks[i]);         // array
for (Node n = jazzHead; n != null; n = n.next) show(n.track);    // linked list
for (String id : liveTracks.keySet()) show(liveTracks.get(id));     // map
The thing that variesThe iteration. It differs for each collection type, and the client is coded to concrete implementations. Encapsulate it.
2

One interface to walk them all

Each collection hands out an iterator: an object with hasNext() and next() that knows how to walk that particular structure. The client uses the same two calls no matter what. Pick a collection and step through it; watch the client code stay the same.

Iterator<Track> it = catalog.createIterator();
while (it.hasNext()) {
  show(it.next());     // identical for all three
}
The Iterator Pattern

Provides a way to access the elements of an aggregate object sequentially without exposing its underlying representation.

3

One reason to change

Design principleA class should have only one reason to change.

Why not let the collection iterate itself? Because then it has two jobs, managing the collection and traversing it, and two reasons to change. Each reason to change is a chance for a bug. Classes that do one thing are highly cohesive. Sort these responsibilities of a Catalog class.

4

Playlists inside playlists

Now users want folders: a playlist can contain tracks and other playlists, to any depth. We need a tree, and we want clients to treat a single track and a whole folder the same way: ask either one for its duration, or tell it to print. Click nodes to select, add children, and compute duration() from any node.

abstract class MediaItem {                 // the component: one type for leaves and composites
  int duration() { throw new UnsupportedOperationException(); }
  void add(MediaItem m) { throw new UnsupportedOperationException(); }
}
class Track extends MediaItem { int secs; int duration() { return secs; } }      // leaf
class Playlist extends MediaItem {                                         // composite
  List<MediaItem> children = new ArrayList<>();
  void add(MediaItem m) { children.add(m); }
  int duration() { return children.stream().mapToInt(MediaItem::duration).sum(); }  // recursion
}
The Composite Pattern

Allows you to compose objects into tree structures to represent part-whole hierarchies. Composite lets clients treat individual objects and compositions of objects uniformly.

5

Transparency versus safety

Putting add() on the shared component type means a leaf has a method that makes no sense for it. That breaks the Single Responsibility Principle a little, deliberately, in exchange for transparency: the client never needs to know whether it holds a leaf or a composite. The alternative is safety: put child management only on the composite, and make clients check types. Flip between them.

Iterating over a composite

  
Iterator and Composite combine well: an iterator that walks the whole tree (using a stack of child iterators) lets a client filter every track, however deep, without recursion of its own. Find every track under the root that matches a genre.
