Being Adaptive

Two wrapping patterns with different jobs: an Adapter makes one interface look like another, and a Facade puts one simple interface in front of a whole subsystem.

1

Adapters all around us

Travel with a laptop and you meet the problem: the plug has one shape, the socket another. An adapter sits in the middle and changes the interface without changing either side. In software, an adapter lets a class with the "wrong" interface work with a client that expects a different one. Plug things in.

2

Adapting a legacy sensor

A new climate dashboard works with TemperatureSensor objects that report celsius(). A warehouse already has hundreds of old sensors whose vendor class is LegacyThermo with readFahrenheitX10() (tenths of a degree). You can't change the vendor class, and you don't want to change the dashboard. Write an adapter, then run the client.

class ThermoAdapter implements TemperatureSensor {  // target
  private final LegacyThermo adaptee;              // composed
  ThermoAdapter(LegacyThermo t) { adaptee = t; }
  public double celsius() {
    double f = adaptee.readFahrenheitX10() / 10.0;
    return (f - 32) * 5 / 9;
  }
}
The Adapter Pattern

Converts the interface of a class into another interface the clients expect. Adapter lets classes work together that couldn't otherwise because of incompatible interfaces.

3

Object adapters and class adapters

The adapter above uses composition: an object adapter. The GoF also describe a class adapter, which subclasses both target and adaptee using multiple inheritance. Java can't do that with classes, so object adapters are the norm. Compare.

Real world: Enumeration to IteratorOld Java collections handed out Enumeration (hasMoreElements, nextElement); newer code expects Iterator (hasNext, next, remove). An adapter maps the first two directly. Enumeration has no remove, so the adapter throws UnsupportedOperationException. Adapters aren't always perfect matches, and the client has to be ready for that.
4

Facade: one door into a subsystem

Publishing a blog post on a homemade platform takes a dozen calls across six classes, in the right order. A facade gives clients one simple method that makes all those calls. The subsystem classes stay public and untouched, so power users can still reach them. Try publishing by hand, then through the facade.

The Facade Pattern

Provides a unified interface to a set of interfaces in a subsystem. Facade defines a higher-level interface that makes the subsystem easier to use.

Intent is what separates themAdapter converts an interface to one a client expects. Facade simplifies an interface. Decorator adds behavior without changing the interface. An adapter can wrap several classes and a facade can wrap one; the difference is purpose, not the number of objects.
5

Principle of Least Knowledge

Design principleTalk only to your immediate friends.

Also known as the Law of Demeter. Inside a method, only call methods on: the object itself, objects passed in as parameters, objects the method creates, and the object's own components (fields). Calling a method on something returned by another call means you depend on that stranger too. Judge each line inside Checkout.total(Cart cart).

Friend or stranger?

The cost: more small "wrapper" methods that just forward calls. Like every principle, it's a guideline that trades some complexity for less coupling.
