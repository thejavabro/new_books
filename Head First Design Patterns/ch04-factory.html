Baking with OO Goodness

Every new ties your code to a concrete class. Factories gather that creation code in one place, so the rest of the system can depend on abstractions.

What's wrong with new?

Nothing, as such: you need new to make objects. The trouble is that new names a concrete class, so the code around it is tied to that class. When the choice of class depends on conditions, the same if/else chain gets copied wherever objects are made, and every new type means editing all of them. Here a notification service picks a channel. Add a channel and count the edits.


  

  
Find what varies, againThe creation code is the part that changes. The code that uses the object (format, send, log) does not. So pull the creation out.






  
2
Simple Factory: a warm-up

  
Move the conditional into one class whose only job is creating notifiers. Clients ask the factory and get back a Notifier supertype. There is now exactly one place to edit when a type is added. The book calls this a programming idiom more than a true pattern, but it's used constantly.

  

    

    

  

  
class NotifierFactory {
  Notifier create(String type) {
    switch (type) {                      // the only place that knows concrete classes
      case "email": return new EmailNotifier();
      case "sms":   return new SmsNotifier();
      default:      return new PushNotifier();
    }
  }
}






  
3
Factory Method: let subclasses decide

  
Now suppose a report tool exports in many formats. The steps of exporting are fixed and should stay under quality control: open a writer, write the header, write rows, close. Only which writer varies. So the base class calls an abstract createWriter(), the factory method, and each subclass decides what to create. Pick a subclass and run the same export().

  

    

    

      

      

    

  

  
The Factory Method Pattern
Defines an interface for creating an object, but lets subclasses decide which class to instantiate. Factory Method lets a class defer instantiation to subclasses.

  






  
4
Depend upon abstractions

  
Design principleDepend upon abstractions. Do not depend upon concrete classes.

  
This is stronger than "program to an interface". It says high-level components (the exporter) should not depend on low-level components (each concrete writer); both should depend on an abstraction. The "inversion" is that the arrows from the low-level classes now point up to the abstraction. Flip the switch.

  

    

    

  

  

  
These are guidelines to strive for, not laws. Instantiating a stable class like String is fine; worry about classes that are likely to change.






  
5
Abstract Factory: families of products

  
Sometimes you create not one object but a set that must match: a button, a checkbox and a tooltip that all belong to the same visual theme. An abstract factory is an interface with one creation method per product. Each concrete factory makes a consistent family, and the client code never names a concrete widget. Switch factories, or turn the factory off and let the client mix by hand.

  

    

    

    

  

  
The Abstract Factory Pattern
Provides an interface for creating families of related or dependent objects without specifying their concrete classes.
