Keeping Your Objects in the Know

One object changes, and a crowd of others need to hear about it. Observer lets a subject broadcast to any number of listeners without knowing anything about them except that they listen.

1

A feed that many screens depend on

Picture a live match-score service for a sports app. Every time a goal is scored the service gets new data: the score, the minute, who scored. Several parts of the app need that data: a scoreboard widget, a push-notification sender, a stats tracker. Next season the product team will add more. The first, obvious design calls each of them directly.

void onGoal() {
  int home = getHome(); int away = getAway(); String scorer = getScorer();
  scoreboard.update(home, away);        // coding to concrete classes
  pushSender.update(home, away, scorer); // adding a display = editing this method
  stats.update(scorer);
}
What's wrong with itThe feed knows every consumer by name. Adding or removing a consumer means changing the feed, at runtime nothing can join or leave, and the part that changes (the list of consumers) is not encapsulated. The shape of the calls even hints at a fix: they all look like update(...).
2

Publishers + subscribers = Observer

Think of a newsletter: the publisher sends each issue to whoever is on the list right now. People subscribe and unsubscribe whenever they like; the publisher never needs to know who they are. In Observer the publisher is the subject and the subscribers are observers. Toggle subscriptions and score a goal.

3

The Observer Pattern defined

The Observer Pattern

Defines a one-to-many dependency between objects so that when one object changes state, all of its dependents are notified and updated automatically.

The subject owns the state and is the single source of truth. Observers depend on it, and they hear about changes instead of polling. Step through the class diagram.

4

The power of loose coupling

Design principleStrive for loosely coupled designs between objects that interact.

The subject knows only one thing about each observer: it implements the Observer interface. That's all. So you can add new observer types without touching the subject, reuse either side on its own, and change one side without breaking the other. Try making changes and see which classes you would have to edit in each design.

5

Push or pull the data?

In the first version the subject pushes all its data into update(home, away, scorer). Add a new field (say, possession percentage) and every observer's signature changes. In the pull version the subject just says "something changed", and each observer calls getters for what it needs. The book's weather example ends up with pull, which is usually the better default.


    

  






  
6
Observer in the wild

  
Observer is everywhere you see "listeners", "subscribers" or "callbacks": GUI event listeners (a button notifying every registered listener when clicked), JavaBeans property-change listeners, reactive streams and the publisher/subscriber types in Java's Flow API. Java once shipped built-in Observable and Observer classes; they're deprecated, and rolling your own small interfaces is easy and more flexible.

  

  
Don't depend on notification orderObservers are notified in whatever order the subject's list holds them. If your code only works when the scoreboard hears before the push sender, your observers are coupled after all.
