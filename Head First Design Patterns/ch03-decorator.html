Decorating Objects

Subclassing every combination of features explodes into hundreds of classes. Decorators wrap an object in layers, each adding one responsibility, so new behavior arrives without touching old code.

When subclasses multiply

Say you sell phone plans. There's a basic plan and some add-ons: extra data, roaming, a music bundle, insurance. If every combination is its own subclass (BasicWithRoamingAndInsurance...), the class count doubles with each new add-on. Change the price of roaming and you hunt through dozens of classes. Slide the number of add-ons.

Booleans in the superclass don't save youThe next idea is one base class with hasRoaming, hasInsurance flags and a big cost(). Fewer classes, but every new add-on means editing that base class, and every plan inherits add-ons that may make no sense for it.
2

Open for extension, closed for modification

Design principleClasses should be open for extension, but closed for modification.

The goal is to add new behavior by writing new code, not by editing code that is already tested and working. That sounds contradictory, but Observer already did it: new observers extend the subject's behavior without touching it. Don't apply it everywhere, though. It adds abstraction and complexity, so use it in the parts of a design most likely to change.

3

Wrapping objects in layers

A decorator has the same supertype as the object it wraps, so it can stand in for it anywhere. It holds a reference to the wrapped object, does its own bit before or after delegating, and returns the result. Wrap as many times as you like. Here the component is a text stream: build a stack of decorators around a source and call read().

abstract class TextDecorator implements TextSource {   // same supertype
  protected final TextSource inner;                     // HAS-A the wrapped object
  TextDecorator(TextSource inner) { this.inner = inner; }
}
class Upper extends TextDecorator {
  Upper(TextSource s) { super(s); }
  public String read() { return inner.read().toUpperCase(); } // delegate, then add
}
TextSource s = new Upper(new Trim(new FileSource("notes.txt")));

The Decorator Pattern defined

The Decorator Pattern

Attaches additional responsibilities to an object dynamically. Decorators provide a flexible alternative to subclassing for extending functionality.

Wait, decorators do extend a class. True, but they inherit to get the right type, not to get behavior. Behavior comes from composing decorators at runtime. Step through it with the phone-plan example.

5

Real decorators: java.io

The java.io package is a decorator showcase. InputStream is the abstract component. FileInputStream and ByteArrayInputStream are concrete components. FilterInputStream is the abstract decorator, and BufferedInputStream, DataInputStream and ZipInputStream are concrete decorators. Writing your own is a few lines: extend FilterInputStream and override read().

The downsidesLots of small classes that confuse newcomers. Code that checks for a specific concrete type breaks once that object is wrapped. And creating a deeply wrapped object by hand is wordy. Factories (chapter 4) and Builder (appendix) tidy that up.
