Leftover Patterns

Nine more patterns from the original catalog that did not get a chapter, each with a short explanation, a sketch of the structure and a small demo.

1

Bridge

Use Bridge to vary not only your implementations but also your abstractions. A remote-control app supports several devices (TV, soundbar, projector) and several kinds of remote (basic, advanced, voice). With inheritance alone you'd need a class for every pair. Bridge splits the two hierarchies: the remote has a device implementation, and both sides extend independently.

Benefits
Decouples an implementation so it isn't bound permanently to an interface. Abstraction and implementation extend independently; changes to concrete implementors don't affect clients.
Uses and drawbacks
Handy for graphics and windowing systems that must run on several platforms, or any time you change an interface and its implementation in different ways. Adds complexity.
2

Builder

Use Builder to encapsulate the construction of a product and allow it to be constructed in steps. An HTTP request has a URL plus many optional parts. Instead of a constructor with twelve parameters, a builder collects steps and produces the finished, often immutable, object at the end.


  

  
Benefits
Encapsulates how a complex object is built; allows multistep and varying construction (unlike one-step factories); hides the product's internal representation; implementations can be swapped because clients see only an abstract interface.
Uses and drawbacks
Often used for composite structures. Building objects requires more domain knowledge of the client than a Factory does.






  
3
Chain of Responsibility

  
Use Chain of Responsibility when you want to give more than one object a chance to handle a request. Expense claims go to a chain of approvers. Each one either handles the claim or passes it to its successor. The sender doesn't know who will end up approving it.

  

    
    

    

  

  
Benefits
Decouples the sender from its receivers; simplifies objects because they don't know the chain's structure or keep direct references to its members; responsibilities can be added or removed by changing the chain at runtime.
Uses and drawbacks
Common in windowing systems for mouse clicks and key events. A request isn't guaranteed to be handled (it can fall off the end), and the runtime path can be hard to observe and debug.






  
4
Flyweight

  
Use Flyweight when one instance of a class can be used to provide many "virtual instances". A text editor shows a document of thousands of characters. Making a full object per character (font, glyph outline, size) wastes memory. A flyweight shares one object per distinct glyph; the varying, extrinsic state (position) is kept outside and passed in when drawing.

  

    
    

    
Model: a full glyph object ≈ 2 KB; a flyweight document stores 96 shared glyphs plus 8 bytes of position and glyph index per character.

  

  
Benefits
Cuts the number of object instances at runtime, saving memory; centralizes the state of many "virtual" objects in one place.
Uses and drawbacks
Use when a class has many instances that can all be controlled identically. Once implemented, single logical instances can't behave independently of the others.






  
5
Interpreter

  
Use Interpreter to build an interpreter for a language. Each grammar rule becomes a class with an interpret(context) method; a sentence is a tree of these expression objects. Here is a tiny robot language: F moves forward, L/R turn, and repeat n [ ... ] loops.

  

    
    

  

  
Benefits
Each rule is a class, so the language is easy to implement and to change or extend; adding methods to the classes adds behaviors beyond interpretation, like pretty printing or validation.
Uses and drawbacks
Good for simple languages, scripting and rule engines where simplicity beats efficiency. Becomes unwieldy as the grammar grows; then a parser generator or compiler fits better.






  
6
Mediator

  
Use Mediator to centralize complex communications and control between related objects. A control tower is the classic: aircraft don't negotiate with each other, they all talk to the tower, which applies the rules. Without it, every object must know every other. Add planes.

  

    

    

    

  

  
Benefits
Increases reusability of the objects the mediator supports by decoupling them; centralizing control logic simplifies maintenance; simplifies and reduces the messages between objects.
Uses and drawbacks
Common for coordinating related GUI components. Without careful design, the mediator itself can become overly complex.






  
7
Memento

  
Use Memento when you need to be able to return an object to one of its previous states. A game character saves a checkpoint. The memento is an object holding the character's state that the outside world (the save manager, or caretaker) keeps but can't look inside. Only the character (the originator) can restore from it.

  

    

    

    

  

  
Benefits
Keeps the saved state outside the key object, which helps cohesion; keeps that object's internals encapsulated; provides an easy-to-implement recovery capability.
Uses and drawbacks
Used to save state. Saving and restoring can be time-consuming. In Java, consider serialization to save a system's state.






  
8
Prototype

  
Use Prototype when creating an instance of a class is either expensive or complicated. A level editor places monsters. Configuring one from scratch means loading models and stats; cloning a ready-made prototype from a registry is cheap, and the client doesn't even need to know the concrete class.

  

    

    

  

  
Benefits
Hides the complexity of making new instances from the client; lets the client generate objects whose type isn't known; copying can be more efficient than creating.
Uses and drawbacks
Consider it when a system must create new objects of many types in a complex class hierarchy. Making a copy can be complicated (deep vs. shallow copies).






  
9
Visitor

  
Use Visitor when you want to add capabilities to a composite of objects and encapsulation isn't important. A drawing contains circles, rectangles and triangles. Rather than adding area(), toSvg() and toJson() to every shape class, each shape just accept(visitor)s, and each operation lives in its own visitor class. Pick a visitor and send it through the drawing.

  

    

    

  

  
Benefits
Adds operations to a structure without changing it; adding new operations is relatively easy; the code for each operation is centralized.
Uses and drawbacks
Encapsulation of the element classes is broken (visitors need their internals), and changing the structure (a new shape class) means changing every visitor.
