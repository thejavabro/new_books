Controlling Object Access

A proxy stands in for another object and controls access to it: across a network, until something expensive is ready, or only for callers who are allowed.

1

A stand-in that controls access

A proxy implements the same interface as the real object (the real subject), so clients can't tell them apart. Every request goes through the proxy first, and the proxy decides what to do: forward it across a network, hold it until an expensive object is ready, or refuse it. Same structure, three common jobs.

The Proxy Pattern

Provides a surrogate or placeholder for another object to control access to it.

2

Remote proxy: a local representative

A warehouse dashboard wants to ask stock-counting services in three cities for their numbers. Those objects live in other JVMs. A remote proxy on the client side (the stub) looks like the service but packs each call into bytes and ships it over the network. On the server, a skeleton (in modern RMI, built in) unpacks it and calls the real object. Send a call and follow it.

3

Virtual proxy: stand in until it's ready

A photo gallery shows dozens of large images. Loading them all before showing the page would freeze it. A virtual proxy for each image answers immediately with a placeholder size and a "loading" message, starts the real load in the background, and once the real image exists, delegates everything to it. Compare with eager loading.

class ImageProxy implements Picture {
  private volatile RealImage real;            // null until loaded
  public void paint(Canvas c) {
    if (real != null) { real.paint(c); return; }  // delegate once ready
    c.drawText("Loading…");
    if (!started) { started = true; pool.submit(() -> { real = RealImage.fetch(url); c.repaint(); }); }
  }
  public int width() { return real != null ? real.width() : 600; }  // placeholder size
}

Want to let callers know where it's at? The book's design puzzle suggests splitting the proxy's two modes into State classes (chapter 10).

4

Protection proxy with Java's dynamic proxies

A document-sharing service has a SharedDoc interface. The owner may edit and change sharing; viewers may read and comment but not edit; nobody may delete someone else's comment. Java can build a proxy class for you at runtime (java.lang.reflect.Proxy). You supply an InvocationHandler: every call on the proxy arrives at its invoke() method, which decides whether to forward it to the real object. Choose a caller and call methods.

class ViewerHandler implements InvocationHandler {
  private final SharedDoc doc;
  public Object invoke(Object proxy, Method m, Object[] args) throws Throwable {
    String n = m.getName();
    if (n.startsWith("get") || n.equals("addComment")) return m.invoke(doc, args);  // allowed
    throw new IllegalAccessException(n + " not allowed for viewers");       // everything else
  }
}
SharedDoc forViewer = (SharedDoc) Proxy.newProxyInstance(
    doc.getClass().getClassLoader(), doc.getClass().getInterfaces(), new ViewerHandler(doc));
5

The proxy zoo

Remote, virtual and protection are the big three, but the same structure turns up with many other jobs.

Proxy vs DecoratorBoth wrap an object behind the same interface. A decorator adds behavior; a proxy controls access. A proxy often creates or locates its real subject itself, while decorators are handed their component. And clients typically get a proxy from a factory, so they never know whether they're holding the real thing.
