When inheritance goes wrong

Imagine a small game with a Character base class. Knights, archers and mages all extend it, and every shared behavior lives in the superclass, so each subclass gets it for free. That feels like reuse. Then the designers ask for something new, and a single change to the base class shows up in places nobody wanted it.

tap a request

A local change, a non-local side effectInheritance shares everything with every subclass. Each time behavior varies between subclasses you have to override it, sometimes with a method that does nothing. Those empty overrides are a smell: the class hierarchy is fighting the way the requirements actually change.
2

Interfaces alone just move the mess

The obvious fix is to pull attack() out into an Attacker interface that only fighting characters implement. That stops the training dummy from swinging a sword, but now every class that implements the interface writes its own copy of the attack code. Change how sword attacks work and you edit every swordsman. Slide the number of character types and compare how many places you would touch to change one behavior.

Rough model: about half the types fight with a sword. "Places to edit" counts the classes whose code changes when sword behavior changes.

3

Principle 1: find what varies and encapsulate it

Design principleIdentify the aspects of your application that vary and separate them from what stays the same.

The one constant in software is change. So look for the parts that change from one subclass to the next, or from one release to the next, and pull them out into their own objects. Then a change to them can't ripple through code that was fine. Sort these parts of the game: which ones vary between characters and which stay the same?

Principle 2: program to a supertype

Design principleProgram to an interface, not an implementation.

"Interface" here means a supertype, not only the Java keyword. The point is that the variable's declared type should be an abstraction, so the real object behind it can be swapped without the caller noticing. Flip between the three versions.

Building characters from behaviors

  
Move and attack now live in their own families of classes. A character has a move behavior and an attack behavior and delegates to them. Because the character holds them through supertypes, you can even swap them while the game runs. Pick a character, give it behaviors and press Play turn.

  

    

      

        
        
        
        

      

      

    

    

  

  
abstract class Character {
  MoveBehavior move;        // held as supertypes
  AttackBehavior attack;
  void performMove()   { move.move(); }     // delegate, don't do it yourself
  void performAttack() { attack.attack(); }
  void setMove(MoveBehavior m) { move = m; }  // swap at runtime
}
class Knight extends Character {
  Knight() { move = new Walk(); attack = new SwordSwing(); }
}






  
6
Principle 3: favor composition

  
Design principleFavor composition over inheritance.

  
Inheritance is an IS-A link fixed at compile time. Composition is a HAS-A link you can rewire at runtime. Composing behaviors gives you families of algorithms you can mix freely, and new behaviors (a Teleport, say) can be added without touching any character class. Step through the finished design.

  

    

  

  
The Strategy Pattern
Defines a family of algorithms, encapsulates each one, and makes them interchangeable. Strategy lets the algorithm vary independently from the clients that use it.






  
7
Patterns are a shared vocabulary

  
Patterns don't come in a library you import. They live in your head and in your team's language. Naming a pattern carries a whole design, its trade-offs and its consequences in one word, which keeps design conversations at the level of ideas instead of fields and loops.
