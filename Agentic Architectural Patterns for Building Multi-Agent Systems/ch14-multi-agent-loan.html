Use Case: A Multi-Agent System for Loan Processing

The same loan pipeline, rebuilt as a team: a supervisor that plans and delegates, four single-purpose specialists behind a standard tool interface, and production guardrails around them. The agent stops being a doer and becomes a manager.

From one brilliant generalist to a team of specialists

The monolith from the last chapter had three limits: an overloaded prompt, a single point of failure, and no real specialisation. Toggle between the two designs.

Agent Delegates to Agent: wrapping a specialist as a tool

The key adapter: a whole agent (its own model, instructions and tool) is wrapped behind a standard tool interface, so the supervisor calls it like any function. Step through the wrapping.

3

The orchestrator as a semantic data mapper

There is no shared Python dictionary here. The "state" is the history of JSON results in the orchestrator's context, and its prompt says which fields to pass to whom. Step through the hand-offs.

Run the team: four scenarios

  
The happy path, a denial, a specialist failure, and a burst of 429 errors from the model provider. The orchestrator follows its failure policy: reflect, resolve, then escalate.

  

    

    

    

    

  






  
5
Heterogeneous model selection

  
Decoupled specialists can each use a different model: a fast, cheap model for extraction, a stronger reasoner for nuanced policy. Choose per agent and compare cost and latency for one application.

  

    

    

    
Numbers are illustrative relative units. Mixing models can introduce subtle behaviour differences, so strict tool schemas matter more, and specialists that must be deterministic run at temperature 0.

The cost of abstraction: delegation depth

  
Every extra layer (supervisor → manager → specialist → sub-specialist) adds its own model calls. Increase the depth.
