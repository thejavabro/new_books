What is a Web Crawler?

A web crawler is a program that browses the web in a methodical, automated way. It starts from a list of pages called the seed set. It downloads each page, finds the links inside it, and follows them to new pages. It repeats this loop until it has collected the documents it needs.

Search engines are the biggest users of crawlers. They download pages to build an index, a data structure that makes search fast. The index is the reason a search over billions of pages answers in under a second.

Crawlers have other uses too:

  • Testing web pages and links for valid syntax and structure.
  • Monitoring sites to see when their structure or contents change.
  • Maintaining mirror sites, meaning copies of popular websites.
  • Searching for copyright infringements.
  • Building a special-purpose index, like one over the content of multimedia files.

Step 1: Clarify the Requirements

💡 Always clarify requirements at the beginning of the interview. Ask questions until you know the exact scope of the system the interviewer has in mind.

"Crawl the web" can mean many different systems. A crawler for one news site and a crawler for a search engine share almost no design. So spend the first minutes of this interview narrowing the scope. Let's assume we need to crawl the whole web.

Functional requirements

  1. Given a set of seed URLs, download every page the crawler can reach from them.
  2. Extract the links from each downloaded page and follow them.
  3. Store each downloaded page, with some metadata, for later processing like indexing.

Non-functional requirements

  1. Scalability. The service must be able to crawl the entire web and fetch tens of billions of web documents.
  2. Extensibility. The design must be modular. Newer document types will need to be downloaded and processed in the future. Adding support for one should not require redesigning the system.
  3. Politeness. The crawler must not overload any web server it visits. Step 6 shows how to enforce this.

Scope questions. Four questions change this design, so ask them before drawing anything.

Is this a crawler for HTML pages only? Or should it also fetch media like images, videos, and sound files? The answer changes the design. A general-purpose crawler needs a separate parsing module for each media type. One module extracts what matters from HTML, another from images, another from videos. Let's assume our crawler handles HTML only. The design stays modular, so adding new media types later is easy.

Which protocols? We assume HTTP. Extending the design to FTP and other protocols later should not be hard.

How many pages will we crawl? Let's assume we need to crawl one billion websites. A website can contain many URLs, so assume an upper bound of 15 billion different pages.

What about robots exclusion? Courteous crawlers implement the Robots Exclusion Protocol. A webmaster writes a file called robots.txt that declares which parts of the site are off limits to crawlers. Before downloading any real content from a site, the crawler must fetch this file and obey it.

Step 2: Estimate the Scale

Every other estimate follows from two numbers: 15 billion pages, crawled within four weeks.

How many pages per second do we need to fetch?

15B / (4 weeks x 7 days x 86,400 seconds)   = ~6,200 pages per second

What about storage? Page sizes vary a lot. Since we deal with HTML text only, assume an average page size of 100KB. We also store 500 bytes of metadata with each page.

15B x (100KB + 500 bytes)                   = ~1.5 petabytes

Never plan to fill a storage system completely. Assume a 70 percent capacity model: we never want to use more than 70 percent of the storage we own.

1.5 petabytes / 0.7                         = ~2.14 petabytes

What about bandwidth? The fetch rate and the page size together set the network requirement, and it is the figure that usually surprises people.

6,200 pages per second x 100KB              = ~620 MB per second

That is about 5 gigabits per second of sustained inbound traffic, held for four weeks without a pause.

All three results point the same way. 6,200 pages per second is too much for one machine. 620 MB per second is too much for one network card. 2.14 petabytes is too much for one disk array. This is a distributed system from the first sketch.

Step 3: Define the API

💡 Defining the API early forces you to be concrete about what the system actually does, and it usually exposes a requirement nobody has stated yet.

A crawler is unusual among these case studies: it has no end users. It is an internal system, and its customers are other programs, like an indexing pipeline. Say that in the interview, because it explains why this step is short.

A small operator API is still worth defining:

POST /seeds
  body: { urls }
  202:  accepted for crawling

GET /status
  200:  { pages_crawled, pages_queued, crawl_rate }

The first call gives the crawler its starting URLs. The second reports progress, which matters for a job that runs for weeks. The interesting interfaces are internal, between the crawler's own modules. Step 6 describes them.

Step 4: Define the Data Model

The crawler manages three small datasets and one large one.

  1. URLs to visit. This is the waiting list of the crawl, called the URL frontier. A crawl of 15 billion pages discovers links faster than it fetches them, so the waiting list runs into the billions of URLs. That is far too large for memory, so it must live on disk.
  2. Checksums of URLs already seen. A checksum is a short, fixed-size number computed from a piece of data. Two identical inputs always produce the same checksum, so checksums are a cheap way to detect repeats. We store an 8-byte checksum per URL, not the URL text itself.
  3. Checksums of downloaded documents. Also 8 bytes each. These detect the same content reached through different URLs.
  4. The downloaded pages themselves, with their metadata, in the datastore. This is the large one: the 2.14 petabytes from step 2.

Storing checksums instead of full URLs is a real saving. A URL can be hundreds of bytes long, and its length varies. A checksum is always 8 bytes, so 15 billion of them need a small, predictable space. Step 6 does that math.

Eight bytes is 64 bits, and 15 billion of them is enough to expect collisions. The arithmetic gives about six colliding pairs across the whole crawl. Each one costs a page: a genuinely new URL matches an old checksum and is dropped, so it is never fetched. Six pages in 15 billion is a loss a crawler can accept, and saying so is better than not having checked. A system where a single miss matters would need a wider checksum.

The schema below shows these four records and where each one lives:

URL frontier records are the simplest: each entry is one URL, stored as plain text. URLs leave the frontier in the order they arrived: first in, first out. Downloading a frontier URL adds at most one page to the datastore. Step 6 splits the frontier into per-hostname queues and puts memory buffers in front of the disk.

URL store holds one 8-byte checksum for every URL the crawler has ever seen. The checksum is the key, and there is no other field. Every extracted link is checked against this store before it can join the frontier. A match means the URL is already queued or already downloaded, so the link is dropped. This is what stops the crawler from fetching the same URL twice. The store lives in a database, behind a small in-memory cache of popular URLs. At 15 billion URLs it needs about 120 GB.

Document checksum store holds one 8-byte checksum per distinct page content, computed after download. Many URLs can serve the same content, because popular pages are copied onto many sites. The URL store cannot detect that, since each of those URLs is genuinely new. This store detects it: a matching checksum means the content was already processed under another URL. The crawler then ignores the duplicate. So the relationship is many to one: many URLs can map to one stored page. Step 6 sizes this store and shows where to keep it.

Datastore records are the downloaded pages themselves. Each record holds the page contents plus about 500 bytes of metadata, such as the page's URL. The crawler writes this store; the indexing pipeline reads it later. Pages average 100KB, so this is bulk storage on disk, never rows in a database. It is the 2.14 petabytes from step 2, and by far the largest piece of the system.

Step 6 adds several caches in front of these records. Caches hold derived data: the crawler can rebuild them at any time, so they are not part of the data model. Step 6 also distributes the data. Each hostname is assigned to one server, and that server keeps all three small sets for its own URLs.

Step 5: Draw the High-Level Design

Every web crawler runs the same basic loop. It takes a list of seed URLs as input and repeats these steps:

  1. Pick a URL from the unvisited URL list.
  2. Resolve the URL's hostname to an IP address.
  3. Connect to the host and download the document.
  4. Parse the document contents to find new URLs.
  5. Add the new URLs to the unvisited list.
  6. Process the downloaded document, for example store it or index its contents.
  7. Go back to step 1.

Breadth-first or depth-first? The crawl must visit pages in some order, and Breadth First Search (BFS) is the usual choice. It explores the pages closest to the seeds first, level by level. Depth First Search (DFS) is used in some situations. If the crawler has already opened a connection to a website, it can DFS through all the URLs on that site. That reuses the open connection and saves the handshaking overhead. (A handshake is the exchange of setup messages that starts a new connection.)

Path-ascending crawling. A path-ascending crawler also visits every parent path of each URL it intends to crawl. Given the seed http://foo.com/a/b/page.html, it will also try /a/b/, /a/, and /. This discovers isolated resources: pages that no inbound link would ever have revealed.

Why is crawling hard? Two characteristics of the web make crawling a difficult task.

  1. The large volume of pages. The crawler can only ever download a fraction of the web at any time. So it must be smart about which pages to download first.
  2. The rate of change. Web pages change very frequently. By the time the crawler downloads the last page from a site, earlier pages may have changed, and new pages may have appeared. The design must never assume the web is static.

A bare-minimum crawler needs at least five components:

  1. URL frontier: stores the list of URLs to download and prioritizes which URLs to crawl first.
  2. HTML fetcher: retrieves a web page from its server.
  3. Extractor: extracts links from HTML documents.
  4. Duplicate eliminator: makes sure the same content is not extracted twice.
  5. Datastore: stores the retrieved pages, URLs, and metadata.

Step 6: Go Deep

How one worker processes one URL

Start with a single server, because the loop is easiest to see there. Assume the crawler runs on one server with multiple worker threads. Each worker thread performs, in a loop, all the steps needed to download and process one document.

The first step of the loop removes an absolute URL from the shared URL frontier. An absolute URL begins with a scheme, like "HTTP", which names the network protocol to use. The worker calls the protocol module matching that scheme to download the document. Protocol modules are separate pieces, so supporting a new protocol later means adding one module.

The downloaded document goes into a Document Input Stream, or DIS. A DIS caches the document's contents. Later modules can then re-read the document without downloading it again.

Next, the worker runs the document dedupe test. This checks whether the same content has already been seen under a different URL. If it has, the worker stops processing this document and removes the next URL from the frontier.

If the document is new, the worker processes it. Every document has a MIME type, a label like HTML page, image, or video. Each MIME type has its own set of processing modules. The worker invokes the process method of every module registered for the document's type. This modular scheme is what makes the crawler extensible. Supporting a new document type means adding a processing module, nothing more.

The HTML processing module extracts all links from the page. Each link is converted into an absolute URL. It is then tested against a user-supplied URL filter, which decides whether it should be downloaded at all. Each URL that passes the filter goes through the URL-seen test. Is it already in the frontier, or already downloaded? Only new URLs are added to the frontier.

The loop above ran on one server. Now let's discuss the main components one by one, and see how each is distributed across many machines.

The URL frontier

The URL frontier is the data structure that contains all the URLs remaining to be downloaded. A FIFO queue implements it naturally. (FIFO means first in, first out.) Removing URLs from a FIFO queue, starting from the seed set, produces exactly a breadth-first traversal of the web.

The frontier is far too big for one machine, so we distribute it across servers. A hash function maps each URL to the server responsible for crawling it. Each server runs many worker threads.

Now politeness becomes concrete. The distributed frontier must respect two rules:

  1. The crawler should not overload a server by downloading a lot of pages from it.
  2. We should not have multiple machines connecting to the same web server.

To enforce both, each server keeps a collection of distinct FIFO sub-queues. Each worker thread has its own sub-queue and removes URLs only from it. A new URL is placed into a sub-queue chosen by its canonical hostname. (Canonical means the hostname is first reduced to one standard written form.) Our hash function maps each hostname to one thread number. Together, these choices mean at most one worker thread ever downloads from a given web server.

That solves half of politeness. It bounds the crawler to one connection per host, which is rule 2. It does not bound the rate, which is rule 1. A thread working through a queue as fast as the host answers will send twenty requests a second to a host that replies in fifty milliseconds, and for a small site that is an overload.

So politeness also needs a delay. Record the time of the last request to each host, and make a URL eligible only once a minimum gap has passed. Derive that gap from the host's own response time, which asks slow hosts for less, and honor the Crawl-delay line in robots.txt where a site states its own limit. In practice each thread keeps its hosts in a priority queue ordered by next-eligible time, and takes whichever host is ready first instead of draining one queue to the end. That also stops one enormous site from starving every other host mapped to the same thread.

How big will the frontier be? It holds billions of URLs, so it must be stored on disk. Give each queue two buffers. The enqueue buffer collects new URLs and is dumped to disk once it fills. The dequeue buffer keeps a cache of URLs to visit next, and periodically refills itself from disk.

The fetcher

The fetcher downloads the document for a given URL, using the appropriate protocol like HTTP. It also enforces robots exclusion. Fetching a host's robots.txt again for every request would waste traffic. Instead, the HTTP module keeps a fixed-size cache mapping hostnames to their robots exclusion rules. The rules for a host are fetched once, then reused.

The document input stream

Several processing modules may need to read the same document. Downloading it once per module would waste bandwidth. The Document Input Stream (DIS) prevents that. It is an input stream that caches the entire contents of a document read from the internet, and it provides methods to re-read it.

The DIS keeps small documents entirely in memory, and writes larger ones to a temporary backing file. Pick that threshold against step 2, where the average page is 100 KB. A 64 KB threshold would send most pages to disk and defeat the purpose of the stream. Set it around 1 MB instead, so the ordinary page stays in memory and only genuinely large documents spill. Each worker thread has one DIS, which it reuses from document to document. After taking a URL from the frontier, the worker passes it to the matching protocol module. That module initializes the DIS from the network connection. The worker then hands the same DIS to every relevant processing module.

The document dedupe test

Many documents on the web are available under multiple different URLs. Documents are also mirrored, meaning copied, on many servers. Both effects would make any crawler download the same content many times.

The document dedupe test prevents this. Calculate a checksum of every processed document and store it in a database. MD5 and SHA are the usual hash functions, and neither produces 64 bits: MD5 gives 128 and SHA-256 gives 256. So take the first 64 bits of the digest, which is what the 8-byte figure below assumes. Keeping the full digest removes the collision concern from step 4 at twice the storage. Compare each new document's checksum against the stored set. A match means the content has been seen before. The worker then ignores the document and moves to the next URL.

How big is the checksum store? One checksum per distinct page:

15B x 8 bytes                               = 120 GB

That 120 GB is the total across the whole crawl, not the load on one machine. Step 7 assigns each hostname to a crawling server, and each server keeps the checksums for its own URLs, so one server in a fleet of a hundred holds a little over a gigabyte. That sits in memory comfortably. Treat the single-server reading as a sanity check on the total, and keep a smaller LRU cache in front of persistent storage on each server. (LRU, least recently used, evicts the entry that has gone unused the longest.) The test first checks the cache, then the backing storage. If the checksum is found in either place, the document is ignored. Otherwise the checksum is added to the cache and the backing storage, and the document is processed.

URL filters

The URL filter is a customizable way to control which URLs are downloaded. Filters can restrict URLs by domain, by prefix, or by protocol type. This is how we block websites the crawler should ignore. The worker consults the filter before adding any URL to the frontier.

Domain name resolution

Before contacting a web server, the crawler must use the Domain Name Service (DNS) to map the hostname to an IP address. Given the huge number of URLs, DNS resolution becomes a big bottleneck. To avoid repeated external requests, build a local DNS server that caches results. Most lookups then resolve inside our own datacenter.

The URL dedupe test

While extracting links, the crawler meets multiple links to the same document again and again. Links like a site's home page appear on almost every page of that site. So a URL dedupe test runs on each extracted link before it is added to the frontier.

To perform the test, store every URL the crawler has seen, in canonical form, in a database. Storing the full text of each URL would waste space. So we store a fixed-size checksum of each URL instead.

Popular URLs justify one more optimization. Because some links appear extremely often, keep an in-memory cache of popular URLs on each host, shared by all threads. The hit rate on those common links is high, so the cache answers most tests without a database operation.

How much storage does the URL store need?

15B x 8 bytes                               = 120 GB

Can we use a Bloom filter?

A Bloom filter is a probabilistic data structure for testing set membership. It can produce false positives, but never false negatives. The set is represented as a large bit vector. Adding an element computes n hash functions of it and sets the matching bits. An element is judged "possibly in the set" if the bits at all n of its hash locations are set. Other elements may have set those same bits, and that is what causes a false positive.

For the URL-seen test, a false positive is costly. It makes the filter claim a new URL has already been seen. That URL is never added to the frontier, so its page is never downloaded. Making the bit vector larger reduces the chance of a false positive. The stronger fix is to treat every "possibly" as an instruction to check the real URL store. The Bloom Filters lesson describes this pattern, and it does remove the risk of losing a page.

But notice what it saves, because the usual claim is backwards here. A Bloom filter answers a definite no on its own, and sends every possible yes to the store. So it saves a lookup only for URLs the crawler has never seen. This test is mostly the opposite case: links to a site's home page appear on nearly every page of that site, so most extracted links have been seen already, and each one still costs a lookup. A filter helps a workload of mostly new URLs. For a workload of mostly repeats, the in-memory cache of popular URLs above is the better tool, because it answers exactly the frequent repeats that the filter cannot.

Checkpointing

A crawl of the entire web takes weeks to complete. Over a period that long, server failures are certain. So the crawler writes regular snapshots of its state to disk. This is called checkpointing. An interrupted or aborted crawl can restart from the latest checkpoint, instead of from the beginning.

Step 7: Bottlenecks and Failure Points

The interviewer does not expect this design to be limitless. They expect you to know where it ends.

A crawling server dies. Distribute URLs among crawling servers with consistent hashing. Consistent hashing does two jobs here. It spreads load evenly among the crawling servers. And when a host dies, it remaps that host's URLs to the remaining servers with minimal disruption. Pick one recovery path rather than both. Either remap the dead server's hosts onto the survivors, which spreads the work but gives up the checkpoint, or bring up a replacement that loads the dead server's last snapshot and keeps its hosts. The second preserves politeness, because a host stays with one server and its record of last-request times survives.

Where the data lives. The crawler coordinates three kinds of data: URLs to visit, URL checksums, and document checksums. We distribute URLs by hostname, so each host stores all three sets for its own URLs. That keeps every dedupe test local to the host that needs it. Each host performs checkpointing periodically and dumps a snapshot of its data onto a remote server. If a host dies, its replacement takes the data from the last snapshot.

Crawler traps. A crawler trap is a URL, or a set of URLs, that causes a crawler to crawl indefinitely. Some traps are unintentional. A symbolic link within a file system can create a cycle. Other traps are intentional. Some sites dynamically generate an infinite web of documents. The motivations vary. Anti-spam traps catch the crawlers spammers use to collect email addresses. Other sites trap search engine crawlers to boost their search ratings. The URL filter is the defense: once a trap site is identified, block its domain there.

Where AI Fits in This Design

After the main design, interviewers often ask one more question: where would AI fit in this system?

There are two fits, and both extend mechanisms this lesson already built.

The first is the frontier. A FIFO queue treats every URL as equally worth fetching, and the web is not like that. A scoring model can predict a page's value before the page is fetched. The signals are the host's history, how often pages on that host change, and how many other pages link to this one. High-value URLs are dequeued sooner. The sub-queue structure and the politeness rules stay exactly as they are. The model only changes the order in which a thread works through its own queue.

The second is the dedupe test. The document checksum catches exact copies and nothing else. Mirrored pages differ by a date stamp or an advertisement, and every one of them passes the checksum test as new. An embedding of the page's content, a list of numbers capturing what the page says, catches these near-copies. A lookup for close neighbors finds a match where the checksum finds none. Run it as a second filter, after the cheap exact test.

That is the pattern to name in the interview: AI extends an existing mechanism instead of replacing it. The exact test stays cheap and certain, and the model covers what the exact test cannot see.

💡 In the interview: spend your time on the URL frontier and the two dedupe tests. That is where this design differs from the other case studies. State the politeness rule precisely, in both halves: each hostname maps to exactly one worker thread, so no web server is ever crawled by two machines, and a minimum gap between requests to one host caps the rate as well as the concurrency. Give the scale numbers early. 15 billion pages in four weeks is about 6,200 pages per second, and that single figure justifies every distributed choice you make. The most likely follow-up is the Bloom filter question. Know both halves of the answer. A false positive would silently skip a page forever. Checking every "possibly" against the real URL store removes that risk.

Key takeaway: a web crawler is a simple loop run at an enormous scale. Fetch a page, extract its links, add the new ones to the URL frontier, and repeat, about 6,200 times per second. The frontier lives on disk, because billions of waiting URLs do not fit in memory. Politeness takes two mechanisms, not one. Each hostname hashes to one worker thread's sub-queue, so no web server is ever contacted by two crawler threads at once, and a minimum gap between consecutive requests to the same host keeps the crawler from overloading it. Two dedupe tests protect the crawl. URL checksums stop repeated downloads, and document checksums stop repeated processing of mirrored content. Each set of checksums needs only 120 GB. Cache DNS results locally, cache robots.txt rules per host, and checkpoint regularly, because a crawl that runs for weeks must survive failures.
