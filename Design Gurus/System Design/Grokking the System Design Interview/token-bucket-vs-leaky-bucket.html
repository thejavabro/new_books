Practice Questions

An API allows each client 100 requests per minute. One client sends all 100 requests in the first second of the minute, and then sends nothing.

Did the client break the limit? Over the whole minute, no. But during that first second, it sent requests at 60 times its average rate. The two classic rate limiting algorithms differ mainly in whether that sudden burst of requests is acceptable.

This lesson explains the token bucket and the leaky bucket. It shows how each one handles the same burst, and how to run a rate limiter on many servers.

What a Rate Limiter Does

A rate limiter is the component that enforces a limit on how many requests a client can send. When a client goes over the limit, the API usually answers with 429 Too Many Requests. This is the HTTP status code for a request rejected by a rate limit.

The two algorithms treat bursts differently:

  • Token bucket allows bursts, up to a chosen size.
  • Leaky bucket enforces a constant output rate, so bursts are smoothed out.

Token Bucket

Imagine a bucket that holds tokens.

  • The bucket has a capacity, for example 5 tokens. It never holds more than that.
  • New tokens are added at a fixed refill rate, for example 2 tokens per second.
  • Every request must take one token to pass.
  • If a token is available, the request passes immediately.
  • If the bucket is empty, the request is rejected immediately with 429.

The two numbers control two different things:

  • Capacity is the largest burst you allow. A client that has been idle collects tokens, up to the capacity. It can then spend all of them at once.
  • Refill rate is the long-term rate. Once the saved tokens are used up, the client can send only one request for each new token.

A token bucket does not need a timer that adds tokens every second. It only stores two values for each client: the token count and the time of the last refill. When a request arrives, it calculates how many tokens were earned since then:

now = current time in seconds
tokens = min(capacity, tokens + (now - last_refill) x refill_rate)
last_refill = now
if tokens >= 1:
    tokens = tokens - 1
    allow the request
else:
    reject the request with 429

A token bucket fits public APIs well, because normal clients send harmless bursts. For example, a web page loads and sends eight requests at once, and then sends nothing for a minute. A token bucket lets those eight requests through, but it still limits long-term usage. Many commercial APIs, including AWS API Gateway, use token bucket rate limiting.

What Token Bucket Gives You

  • Normal bursts succeed instead of failing.
  • Rejection is immediate, so a client learns at once and can slow down.
  • Very little state: one token count and one timestamp for each client.

What Token Bucket Costs You

  • Traffic that passes can still be bursty. The systems behind the limiter must handle the largest burst you allow.
  • Two numbers to tune. If the capacity is too high, the limit does not protect much.

Leaky Bucket

Now imagine a bucket with a small hole in the bottom.

  • Requests arrive at any speed and wait inside the bucket. So the bucket is a queue, which is a waiting line for requests.
  • Requests leave through the hole at one constant drain rate, and never faster.
  • When the bucket is full, new requests are dropped.

The key property is the output. However uneven the incoming traffic is, the outgoing traffic never goes above the drain rate, and it is a steady stream whenever requests are waiting. Changing the timing of traffic, not only its amount, is called traffic shaping.

Traffic shaping is useful when the system behind the limiter cannot handle a sudden spike. Common examples are an old system that crashes under load, and a partner API with a strict limit per second. Another is a device that processes messages at a fixed speed.

What Leaky Bucket Gives You

  • Smooth, predictable output, which protects the system behind it.
  • A spike becomes waiting, instead of failures, as long as the queue has room.

What Leaky Bucket Costs You

  • Added latency. A queued request waits, and the caller does not know why the response is slow. For user-facing APIs, a fast rejection is usually better than a hidden delay.
  • No burst allowance. A client that was idle for an hour still gets the same constant rate.
  • Dropped requests. When the queue is full, new requests are dropped.

One Name, Two Versions

The name "leaky bucket" is used for two different designs:

  • As a queue, the version described above. Requests wait inside and leave at a constant rate. This version shapes traffic and adds delay.
  • As a meter, a counter that drains over time. A request is rejected if it would overflow the counter, and nothing waits. This version behaves much like a token bucket counted in the opposite direction.

When people compare the two buckets, they usually mean the queue version, because that is the version that behaves differently.

The Same Burst Through Both

Suppose eight requests arrive at the same moment.

  • The token bucket holds 5 tokens and refills at 2 tokens per second.
  • The leaky bucket drains 2 requests per second, and its queue can hold 8 requests.

Here is what happens:

  • Token bucket: 5 requests pass immediately, and 3 are rejected with 429. After one second, 2 new tokens are available, so the client can retry.
  • Leaky bucket: all 8 requests are accepted into the queue. One request leaves every 0.5 seconds, so the last request leaves after about 3.5 seconds.

The input is the same, but the promises are different. Token bucket promises a fast answer, which may be "no". Leaky bucket promises smooth output, and the price is waiting.

Running a Rate Limiter on Many Servers

The algorithm is only a small part of the design. The harder question is where the counts are stored.

Suppose the limit is 100 requests per minute for each user, and there are 10 limiter servers. If each server keeps its own counter, a user's requests can be spread across all 10 servers. Each server allows 100 requests, so the user gets up to 1,000 requests per minute, which is 10 times the limit.

So the counters must be stored in one shared place. Redis, an in-memory data store, is the usual choice, with one key for each client.

Be ready for two details:

  • Race conditions. A race condition happens when two servers read and update the same value at the same moment, and one update is lost. The fix is to make the check and the update one atomic operation, which runs as a single step. In Redis, a small Lua script can read the token count, add the new tokens, and take one token, all in one step.
  • Lookup cost. Every request now makes a network call to Redis. One common solution is to check the limit once at the API gateway, so only the gateway tier calls Redis instead of every service. The gateway still runs several instances sharing those counters, so the call does not disappear. Another option is to give each server a small local allowance it can spend without asking Redis every time. Another is to give each server a small local allowance, which it can use without asking Redis every time.

Also choose the key carefully. The key decides whose requests are counted together:

  • User ID fits APIs where users log in.
  • IP address is the fallback for anonymous traffic. But everyone behind one shared address, like a school or an office, shares one limit.
  • API key fits traffic from partners.

Many systems apply several limits at the same time.

Finally, tell the client what happened. Return 429 with a Retry-After header, which says how long the client should wait before trying again. The Designing an API Rate Limiter case study covers the full design.

Choosing Between Them

  • A public, user-facing API: use a token bucket. Let harmless bursts pass, and limit the long-term rate.
  • Traffic into a fragile system that cannot handle spikes: use a leaky bucket, because smooth output is exactly what it provides.
  • A user is waiting for the response: prefer a fast rejection over a hidden queue.
  • Many limiter servers: keep the counters in a shared store like Redis, and update them atomically.
  • Always: return 429 with Retry-After, so well-behaved clients wait instead of retrying immediately.

Using This in an Interview

For a general API rate limiter, choose a token bucket. Give the reason in one sentence: "Real clients send bursts, so I allow a burst up to the bucket size, and limit the long-term rate."

Then move to the part interviewers usually care about most: shared state. Keep the counters in Redis, keyed by user ID, and update them atomically, so parallel servers do not allow extra requests. Return 429 with Retry-After.

A common follow-up question is: "When would you use a leaky bucket instead?" Answer: when a system behind the limiter cannot handle a spike, so smooth output is worth the extra waiting.

Key Takeaways

  • A rate limiter enforces a request limit, and usually rejects extra requests with 429.
  • A token bucket allows bursts up to its capacity, limits the long-term rate to its refill rate, and rejects immediately when it is empty.
  • A leaky bucket queues requests and releases them at a constant rate. Its output is smooth, but requests wait, and requests are dropped when the queue is full.
  • The main difference: token bucket allows bursts, while leaky bucket enforces a constant output rate.
  • Use a token bucket for user-facing APIs, and a leaky bucket in front of systems that cannot handle spikes.
  • On many servers, keep the counters in a shared store like Redis, and update them atomically.

A rate limiter decides who gets served and when. The next lesson, Stateful vs Stateless Architecture, explains why servers that keep no user data are easier to scale.

Practice Questions

Try each question first, then open the answer.

1. A token bucket has a capacity of 10 tokens and refills at 1 token per second. A client has been idle for a long time, and then sends 15 requests at once. What happens?

Show answer

10 requests pass, and 5 are rejected with 429. The idle client collected tokens up to the capacity of 10, so the first 10 requests each take a token. The bucket is then empty, so the other 5 are rejected. After that, the client earns 1 new token per second, so it can send about 1 request per second.

2. Eight requests arrive at once. A token bucket holds 5 tokens. A leaky bucket drains 2 requests per second, and its queue can hold 8 requests. What does each algorithm do?

Show answer

The token bucket passes 5 at once and rejects 3. The leaky bucket passes all 8, at 2 per second. The token bucket has only 5 tokens, so 3 requests get 429. The leaky bucket queues all 8 and releases one every 0.5 seconds, so the last request leaves after about 3.5 seconds.

3. An old billing system can process at most 20 requests per second, and it crashes when traffic spikes above that. Which algorithm should protect it, and what is the cost?

Show answer

A leaky bucket with a drain rate of 20 requests per second. However uneven the incoming traffic is, the billing system never receives more than 20 requests per second, so spikes cannot crash it. The cost is waiting. During a spike, requests queue up and responses are slower. If the queue fills up, new requests are dropped.

4. The limit is 100 requests per minute per user. There are 10 limiter servers, and each keeps its own counter. A user's requests are spread evenly across all 10 servers. How many requests per minute can the user send, and how do you fix it?

Show answer

Up to 1,000 requests per minute. Each server sees only its own share and allows up to 100, so 10 servers allow 10 x 100 = 1,000. The fix is to keep one counter per user in a shared store like Redis. The check and the update must be one atomic operation, so two servers cannot both use the same last token.

5. An API limits anonymous traffic to 60 requests per minute per IP address. A school has 300 students, and all of them reach the internet through one shared IP address. What problem does this cause?

Show answer

All 300 students share one limit of 60 requests per minute. That is only 0.2 requests per minute per student on average, so most of their requests are rejected with 429. A better key is the user ID, once students log in. For anonymous traffic, the team can set a higher limit for known shared addresses.
