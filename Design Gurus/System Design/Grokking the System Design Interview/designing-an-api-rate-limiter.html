What is a Rate Limiter?

Imagine a service that receives a huge number of requests but can only serve so many per second. To stay healthy, it needs a way to refuse the extra requests. That mechanism is called rate limiting, or throttling.

A rate limiter caps how many events an entity can perform in a time window. The entity can be a user, a device, or an IP address. Once the cap is reached, the limiter blocks further requests from that sender until the window ends. For example:

  • A user can send only one message per second.
  • A user is allowed only three failed credit card transactions per day.
  • A single IP address can only create twenty accounts per day.

Why do we need rate limiting?

Rate limiting protects a service from abuse at the application layer: Denial-of-Service (DoS) floods, brute-force password attempts, and brute-force credit card attempts. These attacks send huge numbers of HTTP requests that look like they come from real users. They are usually generated by bots, so they are hard to detect.

Rate limiting also helps in ordinary operation:

  • Misbehaving clients and scripts. Some clients send far too many requests, on purpose or by mistake. A limit also keeps low-priority traffic away from critical traffic. A user pulling lots of analytics data should not slow down other users' transactions.
  • Security. Limit how often a user may try a wrong password or a wrong second-factor code.
  • Cost and resource control. Services are built for normal human behavior, like one post per minute. A computer can push thousands of requests per second through the same API. A limit caps that load and its cost.
  • Revenue. Offer a default limit for every account, and sell higher limits to paying customers.
  • Reducing traffic spikes. Capping every sender helps keep the service up for everyone else.

Try it yourself

Before reading the solution, try designing it. Aim to produce four things: the requirements, a rough load estimate, the API, and a first drawing of the components.

Step 1: Clarify the Requirements

💡 Always clarify requirements at the beginning of the interview. Ask questions until you know the exact scope of the system the interviewer has in mind.

Functional requirements

  1. Limit the number of requests an entity can send to an API within a time window, for example 15 requests per second.
  2. The API runs on a cluster of servers, so the limit must apply across all of them. The user gets an error once the threshold is crossed, whether one server or many received the requests.

Non-functional requirements

  1. High availability. The limiter protects the service from attacks, so it must always work.
  2. Low latency. The check runs on every request before the API answers. It must not add a delay the user can notice.

Which kind of throttling? Throttling is the act of enforcing the limit. Agree on the rule, because there are three common versions:

  • Hard throttling. The number of requests cannot exceed the limit.
  • Soft throttling. Requests may exceed the limit by a set percentage. With a limit of 100 messages a minute and a 10 percent exceed-limit, the limiter allows up to 110 messages a minute.
  • Elastic or dynamic throttling. Requests may go beyond the limit when the system has free resources. A user allowed 100 messages a minute can send more while capacity is spare.

We design for hard throttling. When a client crosses the limit, the server returns HTTP status 429 Too Many Requests.

Fixed window or rolling window? "15 requests per second" can be measured two ways, and they give different answers.

A fixed window runs from the start of a time unit to its end. For a one-second limit, the windows are 0 to 1 second, 1 to 2 seconds, and so on. It does not matter when inside a window a request arrives. In the diagram below, two messages arrive between 0 and 1 second, and three arrive between 1 and 2 seconds. With a limit of two messages a second, a fixed window throttles only m5.

A rolling window starts at the moment a request arrives and lasts one window length. Suppose two messages arrive at the 300th and 400th millisecond of a second. They count from that 300th millisecond until the 300th millisecond of the next second. Look at the same diagram with a limit of two messages a second. A rolling window throttles m3 and m4.

The rolling window is stricter and fairer, but it must remember when each request happened. That difference decides the memory cost, and step 6 works it out for each algorithm.

Step 2: Estimate the Scale

Ask the interviewer for two numbers: how many entities are active at any time, and how large their limit is. Assume one million active users and a limit of 10 requests per second per user.

Load. In the worst case, every user sends at their limit.

1M users x 10 requests per second   = up to 10 million checks per second

That is an upper bound, and most users send far less. Still, the check runs on every request the API receives, so the limiter needs many machines however small its data is.

Memory. This depends on what each algorithm stores per user. Step 6 works it out, and the answers range from about 32 MB to about 12 GB for one million users. That range is the main reason we compare algorithms at all.

Step 3: Define the API

The limiter has one caller: the web server, or the API gateway in front of the API servers. It makes one call per request.

is_allowed(entity_id, api_name)
  allowed:   { allowed: true, remaining }
  throttled: { allowed: false, retry_after_seconds }

entity_id is the user id, or the IP address for anonymous traffic. api_name names the endpoint, so different endpoints can have different limits. When the answer is throttled, the web server returns 429 Too Many Requests to the client with a Retry-After header. The limits themselves, per API and per account tier, are configuration.

Step 4: Define the Data Model

The data has one simple shape: one small record per entity, always looked up by the entity's key.

The key is the UserID, or the IP address. The value is whatever the algorithm needs to decide. For a simple counter, that is a Count and a StartTime. Other algorithms store a list of timestamps or a set of small counters. Step 6 shows how each algorithm uses its record.

One more record sits beside the per-user data: the rule. A rule stores the limit itself, for example three requests per minute. Step 3 said the limits are configuration, per API and per account tier. The rule is what the check compares a user's record against.

The diagram below shows the rule and the three per-user record shapes:

Rate limit rule. One rule exists per API and per account tier, and it covers every user on that tier. APIName and AccountTier identify the rule. Limit and Window state the cap, like 500 requests per hour. Rules are few and rarely change, because they are configuration, not per-user state.

Fixed window counter. One record per user. Count holds how many requests the user has made in the current window. StartTime holds when that window began, and only its minute and second parts are stored. Step 6 adds an optional lock field to this record, because many servers may update it at once.

Sliding window. One record per user. The value is a sorted set: every request's timestamp, kept in time order. This shape is exact, and it is the most expensive one to store.

Sliding window with counters. One record per user. The value is a hash, a small map from each minute to a counter. An hourly limit needs at most 60 counters.

A fourth algorithm in step 6, the token bucket, stores only a count and a timestamp, like the fixed window record.

Small records read by key is the workload of an in-memory key-value store like Redis or Memcached. There are no relationships to join, so a relational database has nothing to offer here. The sorted set and the hash are native Redis value types. These records are also the limiter's only storage; no other database sits behind them.

The record shape decides the memory estimate from step 2, about 32 MB to about 12 GB for one million users. The byte sizes in the diagram come from step 6, which turns them into those totals.

Step 5: Draw the High-Level Design

The rate limiter decides which requests reach the API servers and which are declined. When a request arrives, the web server first asks the rate limiter. If the request is not throttled, the web server passes it to the API servers. Otherwise it returns 429 at once.

Read the diagram as a check placed in front of the API servers, never behind them. The order is client, web server, rate limiter, then API servers.

Read the limiter box as a logical step, not a separate network hop. Step 1 asked for a delay the user cannot notice, and two extra round trips per request would not deliver that. So the limiter runs as a library inside the web server or the API gateway process. The only remote call it makes is to the counter store, and step 7 names even that one as a cost. The limiter reads and writes only its own store of counters. It never touches the application's database. That is what makes a rejected request cheap: the API servers do no work for it.

Step 6: Go Deep

Fixed window with a counter

Suppose we limit the number of requests per user. For each user we keep two values: how many requests they have made, and when the current window started. Store them in a hash-table. The key is the UserID. The value is a structure with an integer Count and an integer epoch time for the window start:

Assume the limit is three requests per minute per user. When a new request arrives, the limiter runs these steps:

  1. If the UserID is not in the hash-table, insert it. Set Count to 1 and StartTime to the current time, normalized to the minute. Allow the request.
  2. Otherwise, find the user's record. If CurrentTime - StartTime >= 1 minute, the window has ended. Set StartTime to the start of the current minute, set Count to 1, and allow the request.
  3. If CurrentTime - StartTime < 1 minute, the request is inside the current window:
    • If Count < 3, increment Count and allow the request.
    • If Count >= 3, reject the request.

Normalized to the minute matters. StartTime is always the start of a clock minute, with the seconds set to zero. It is never the exact moment a request arrived. If we stored the request time instead, each window would begin whenever a user's first request came in. That is a rolling window, and it behaves differently. A fixed window is aligned to the clock, so every user's windows start at the same moments.

What are the problems with this algorithm? There are two.

  1. The window edge. This is a fixed window, because the count resets at the start of every minute. So it can allow twice the limit in a short burst. Suppose Kristie sends three requests in the last second of a minute. She can then send three more in the first second of the next minute. That is six requests in about two seconds, against a limit of three per minute. The sliding window algorithm below fixes this.
  1. Atomicity. In a distributed setup, many limiter servers update the same record. Each server reads the count and then writes it back. That "read-and-then-write" pattern creates a race condition (two operations that overlap and produce a wrong result). Suppose Kristie's Count is 2 and she sends two more requests. Two servers read the count at the same time, before either has updated it. Each server sees 2, decides she has one request left, and allows its request. She gets four requests in the window instead of three.

If we store the records in Redis, one solution is a Redis lock held for the whole read-update operation. Only one server can change a record at a time. The cost is that concurrent requests from the same user wait for each other, and we add another layer of complexity. Memcached has comparable complications.

The more common fix is to make the check and the update one atomic operation, so there is nothing to lock. A Redis INCR command with an expiry, or a small Lua script that runs inside Redis, does this. The Token Bucket vs Leaky Bucket lesson covers this shared-counter problem in more depth. With a simple in-process hash-table, a custom lock on each record does the same job.

How much memory do we need for all the user data? Assume the simple case where everything sits in a hash-table. The UserID takes 8 bytes. A 2-byte Count can count up to about 65,000, which is enough. An epoch time normally needs 4 bytes, but the minute and second parts alone fit in 2 bytes. So one user's data is 12 bytes:

8 + 2 + 2 = 12 bytes

Assume the hash-table adds 20 bytes of overhead per record. To track one million users at any time, we need 32 MB:

(12 + 20) bytes x 1 million = 32 MB

If we add a 4-byte lock to each record to solve the atomicity problem, the total is 36 MB.

One caution comes with that 2-byte timestamp. Keeping only the minute and second means the value repeats every hour. A record last touched at 10:05 looks only thirty seconds old to a request arriving at 11:05, so a stale count would be reused as though the window were still open. This is safe only because each record expires at the end of its window, which is what the Redis expiry below does. Store the full 4-byte epoch time if the records have no expiry.

That fits on a single server. But recall step 2: with a limit of 10 requests per second, the limiter may face 10 million QPS. That is far too much for one machine, and the reason is the request rate rather than the data. One Redis node serves on the order of 100,000 operations per second, so 10 million checks per second needs about 100 nodes. The 36 MB of data spread over them is almost nothing. Sharding here buys throughput, not space. In practice we run Redis or Memcached as a distributed store. All the data lives on the remote Redis servers, and every limiter server reads and updates them before it serves or throttles a request.

Sliding window

We can keep a sliding window if we track every request per user. Store the timestamp of each request in a Redis Sorted Set, which becomes the value in our hash-table:

Assume again that the limit is three requests per minute per user. When a new request arrives, the limiter runs these steps:

  1. Remove every timestamp from the sorted set that is older than CurrentTime - 1 minute.
  2. Count the elements left in the sorted set. If the count is 3 or more, reject the request and insert nothing.
  3. Otherwise, insert the current time into the sorted set and accept the request.

The check in step 2 is "3 or more", not "more than 3". Three timestamps inside the last minute means the allowance is used up. Accepting a fourth request would put four requests in one minute.

How much memory does the sliding window need? Assume the UserID takes 8 bytes and each epoch time takes 4 bytes. Suppose the limit is 500 requests per hour. Assume 20 bytes of overhead for the hash-table and 20 bytes of overhead per element in the sorted set. At most, one user's data takes about 12 KB:

8 + (4 + 20 (sorted set overhead)) x 500 + 20 (hash-table overhead) = ~12 KB

Why 20 bytes per element? A sorted set needs at least two pointers per element to keep the order, one to the previous element and one to the next. On a 64-bit machine each pointer is 8 bytes, so 16 bytes, plus about 4 more bytes of bookkeeping.

To track one million users at any time, we need about 12 GB:

12 KB x 1 million = ~12 GB

The sliding window is exact, but it costs far more memory than the fixed window's 32 MB. It stores one entry per request instead of one counter per user. Can we combine the two algorithms and use less memory?

Sliding window with counters

Instead of one timestamp per request, keep several small fixed windows per user, each about 1/60th of the limit's time window. For an hourly limit, keep one counter per minute. When a request arrives, add up the counters from the past hour and compare the sum with the limit.

Take an example: 500 requests per hour, plus a second limit of 10 requests per minute. When the sum of the counters from the past hour passes 500, Kristie has reached the hourly limit. She also cannot send more than ten requests in any one minute. Real users rarely send that fast, and a retry succeeds when the minute resets.

Store the counters in a Redis Hash, which is very compact for fewer than 100 fields. Each request increments one counter in the hash and also sets the hash to expire an hour later. We normalize each timestamp to the minute.

The bound of 60 entries per user holds only if the old minutes go away. Resetting the expiry on every request keeps the whole hash alive for an active user, including minutes that have left the window. So each update also deletes the fields older than an hour, or the sum step skips them and the hash grows without limit. Deleting them is better, because it keeps the record at the size the memory estimate below assumes:

How much memory does the sliding window with counters need? Assume the UserID takes 8 bytes. Each epoch time takes 4 bytes, and each counter takes 2 bytes. Keep the limit of 500 requests per hour. Assume 20 bytes of overhead for the hash-table and 20 bytes for the Redis hash. With one counter per minute, a user has at most 60 entries. One user's data takes about 1.6 KB:

8 + (4 + 2 + 20 (Redis hash overhead)) x 60 + 20 (hash-table overhead) = ~1.6 KB

Why 20 bytes per hash entry? The same bookkeeping argument as the sorted set: in its general representation, each entry carries pointers and header bytes for the structure around the field and value. Redis actually stores small hashes in a compact packed encoding that costs only a few bytes per entry, so 20 bytes is a deliberately safe allowance, not an exact figure. The estimate errs on the high side, and the conclusion survives either way: about 1.6 GB against 12 GB.

To track one million users at any time, we need about 1.6 GB:

1.6 KB x 1 million = ~1.6 GB

So the sliding window with counters uses about 86 percent less memory than the plain sliding window. It is a little less exact, because the oldest minute counter may include a few requests from just outside the hour. That error is small, and it is still far more accurate than a single fixed window.

Token bucket

The most common interview answer to this question is a fourth algorithm, the token bucket. Each user has a bucket that holds tokens up to a fixed capacity. Tokens are added at a fixed refill rate. Every request takes one token. If the bucket is empty, the request is rejected with 429.

The state per user is tiny: one token count and one timestamp of the last refill. That is about the same 12 bytes as the fixed window counter, yet there is no window edge to exploit. An idle user can send a burst up to the capacity, and after that gets exactly the refill rate. Real clients are bursty in harmless ways, so this fits public APIs well.

The Token Bucket vs Leaky Bucket lesson covers the algorithm, the leaky bucket, and how to choose between them. Do not repeat that lesson in the interview. Say which algorithm you pick and why, in one or two sentences, then spend your time on the shared state.

Which algorithm should you pick? For a public API, pick the token bucket. It stores as little as the fixed window and behaves better. Pick the sliding window with counters when the rule is "no more than N in any hour" and you must enforce it closely. Reserve the plain sliding window for small limits like failed logins, where the counts are tiny.

Sharding and caching

Shard the data by UserID to spread it across machines. Use consistent hashing for fault tolerance and replication, so a node joining or leaving moves only a small share of the keys. If different APIs need different limits, shard per user per API. In the URL shortener, for example, createURL() and deleteURL() can each have their own limiter per user or IP. If an API is itself partitioned, each partition can also run a smaller limiter of its own. An example is three new short URLs per minute on top of 100 per hour.

Caching recent active users helps a lot, but be careful what the cache sits in front of. Step 4 said the counters are the limiter's only storage, with no database behind them. So there is no permanent store to write back to. The useful cache here is a local one inside each limiter process, in front of the remote Redis shard.

That local cache changes the guarantee, which is the part to say out loud. If a process counts in its own memory and syncs to Redis at intervals, the global limit becomes approximate, because other processes cannot see those counts yet. The usual compromise is to give each process a small slice of the allowance to spend locally, and to go to Redis for the rest. A read-only check is the one case that caches cleanly: once a user is known to be at their limit, every further check is a read with no update, and the local cache answers it until the window ends.

Be careful with eviction here, because it is not an ordinary cache. Dropping a user's record erases their count, and the next request starts a fresh allowance. An attacker who floods the limiter with many different keys can push their own record out and reset their limit, which turns the eviction policy into a way around the limit.

So the right mechanism is expiry, not eviction. Each record carries a time to live equal to its window, and Redis removes it when the window ends. A record that is still inside its window is never a candidate for removal. Keep LRU (evict the least recently used entry) only as a safety valve for memory pressure, know that it fails open, and cap the number of tracked keys so the pressure is rare.

Rate limit by IP or by user?

By IP. Throttling per IP address is not good at telling good actors from bad ones, but it is far better than no limit. The biggest problem is a shared public IP, like an internet cafe or phones behind one carrier gateway. One bad user gets everyone behind that address throttled. IPv6 adds a second problem. One computer can use a huge number of IPv6 addresses, and an attacker cycling through them can make the limiter run out of memory.

By user. Once a user is authenticated, they get a token and send it with every request. Limiting by that token targets the right entity. But what about the login API itself, where there is no token yet? If we limit failed logins per account, an attacker can enter wrong passwords for a victim's account until the limit is reached. The real user is then locked out. That is a denial of service against one person.

The way out is to keep two counters and respond to them differently. Count failures per source address and reject hard, because that is the attacker. Count failures per account and respond by asking for more proof, such as a CAPTCHA or a second factor, rather than by closing the account. The victim is slowed down and never locked out.

Hybrid. The right approach is to limit both per IP and per user, because each has weaknesses alone. The cost is more cache entries with more detail per entry, so more memory and storage.

Step 7: Bottlenecks and Failure Points

The interviewer does not expect this design to be limitless. They expect you to know where it ends.

  • The counter store is on the path of every request. If Redis is slow, every API call is slow. If Redis is down, decide in advance whether the limiter fails open (allows everything) or fails closed (rejects everything). Failing open is usually right for a public API.
  • One network round trip per request. Enforcing limits at the API gateway, or giving each server a small local allowance, cuts that cost.
  • Memory growth from anonymous traffic. Per-IP records, especially IPv6, can grow without limit under attack. Cap the number of tracked keys, and let records expire with their windows. Reach for LRU eviction only above that cap, remembering that evicting a record resets the limit it was holding.

Where AI Fits in This Design

After the main design, interviewers often ask one more question: where would AI fit in this system?

A rate limiter looks like a place for a smart model, and that instinct is worth resisting. The limiter runs on every request, so its decision must be fast and explainable, and its check-and-update must be one atomic operation. A client that gets rejected deserves a reason: which rule, which window, when to retry. A model that decides each request adds latency to every API call and can explain nothing.

So keep the enforcement exactly as designed: rules in configuration, counters in Redis, one atomic check per request.

AI works one level up, on the rules themselves. The limiter's logs are a complete record of who asked for what, and how often. An anomaly detector, a model that learns normal traffic and flags departures from it, reads those logs offline. It finds what fixed rules miss: an attacker rotating through addresses, a scripted client staying under every limit, a stolen key behaving unlike its owner. Its output is a proposal: tighten this rule, add a rule for that API, review this account. A person, or an automated process with safeguards, changes the configuration. The enforcement path never changes.

That division is the teaching point: AI advises, rules enforce.

💡 In the interview: spend your time on the algorithm choice and on where the counters live. State the throttling rule and the window type early. Then pick an algorithm and give the reason in one sentence; token bucket is the usual answer for a public API. The moment the interviewer is listening for is the shared state. The counters live in Redis, sharded by user, and each check-and-update must be one atomic operation. Have the memory numbers ready, 32 MB against 12 GB against 1.6 GB, because they show why the algorithm matters. If asked what breaks first, name the Redis round trip on every request.

Key takeaway: a rate limiter is a small record per entity, read and updated on every request, and shared across a cluster. Put the check in front of the API servers, so rejected requests cost nothing, and return 429 with Retry-After. A fixed window counter is 12 bytes of data per user, 32 bytes once the hash-table overhead is counted, but it allows double the limit at the window edge. A sliding window of timestamps is exact but costs about 12 GB for a million users. Sliding window with counters cuts that to about 1.6 GB. Token bucket keeps the state as small as the fixed window with no edge problem. Whatever the algorithm, the counters live in Redis: sharded by user with consistent hashing, updated atomically, and expiring with their own windows rather than evicted, because evicting a record resets the limit it holds. Limit by user and by IP together, because each is weak alone.
