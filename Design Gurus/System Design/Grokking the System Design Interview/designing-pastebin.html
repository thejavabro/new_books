What is Pastebin?

Pastebin lets users store a block of plain text and get a unique URL for it. Anyone who has the URL can read the text. People use it to share source code, configuration files, and log snippets. Sending a short link is easier than pasting a wall of text into a chat or an email.

If you haven't used pastebin.com before, please try creating a new "Paste" there. Spend some time going through the different options their service offers. This will help you a lot in understanding this chapter.

This design overlaps heavily with Designing a URL Shortening Service like TinyURL. Both systems hand out short, unique keys that must not be guessable. The new part is the paste contents. A URL row is a few hundred bytes, but a paste can be megabytes. Deciding where those contents live is the main design decision this lesson adds.

Try it yourself

Before reading the solution, try designing it. Aim to produce four things: the requirements, a rough load estimate, the API, and a first drawing of the components.

Step 1: Clarify the Requirements

💡 Always clarify requirements at the beginning of the interview. Ask questions until you know the exact scope of the system the interviewer has in mind.

Functional requirements

  1. Users can paste text and get a unique URL to access it.
  2. Uploads are text only.
  3. Pastes expire after a default period. Users can also set their own expiry time.
  4. Users can optionally pick a custom alias for their paste.

One design limit is worth agreeing on early: a paste can be at most 10 MB. The limit stops abuse of the service, and the estimates below depend on it.

Non-functional requirements

  1. High durability. Once a paste is stored successfully, it must never be lost. This is the requirement TinyURL did not have. A short link points at a page that exists somewhere else, but a paste is often the only copy of the user's data.
  2. High availability. If the service is down, no shared paste link works.
  3. Low latency on reads. A paste should load with minimum delay.
  4. Keys must not be guessable. Somebody should not be able to type random characters and reach other people's pastes.

Extended requirements

  1. Analytics: how many times a paste was accessed.
  2. The service is also accessible to other programs through a REST API.
  3. A paste can be private, readable only by the users its owner permits.

Step 2: Estimate the Scale

Ask the interviewer for two numbers: new pastes per day, and the ratio of reads to writes. Pastebin traffic is nowhere near Twitter or Facebook. Assume one million new pastes a day and a 5:1 ratio between reads and writes, so five million reads a day.

Load.

1M / (24 hours x 3600 seconds)   = ~12 new pastes per second
5M / (24 hours x 3600 seconds)   = ~58 reads per second

Storage. The limit is 10 MB, but most pastes are small. Source code, configs, and logs are usually a few kilobytes. Assume 10 KB per paste on average.

1M x 10KB                        = 10 GB per day
10 GB x 365 days x 10 years      = ~36 TB

We also store a seven-character key for each paste. Ten years of pastes is 3.6 billion keys.

1M x 365 days x 10 years         = 3.6 billion pastes
3.6B x 7 bytes                   = ~25 GB

25 GB is negligible next to 36 TB. To keep a safety margin, assume a 70 percent capacity model: we never want to use more than 70 percent of the storage we own. That raises the ten-year target to about 51.4 TB.

36 TB / 0.7                      = ~51.4 TB

Bandwidth.

12 writes x 10KB                 = ~120 KB per second in
58 reads x 10KB                  = ~0.6 MB per second out

Cache. If 20 percent of pastes produce 80 percent of the traffic, we want those pastes in memory. Size this on distinct pastes rather than on reads. Five million reads a day do not open five million different pastes, and multiplying reads by a paste size mixes the two.

Assume a day touches one million distinct pastes, most of them recent:

20% x 1M distinct pastes x 10KB  = ~2 GB

That distinct count is an assumption, so say it out loud. Measure the hit rate once the service runs and resize from that.

Two of these numbers change the design. The rest are just reassurance:

  • 36 TB of paste contents. Too big to treat as database rows. The contents need their own store.
  • 5 reads per write. Read-heavy, so a cache helps. But the skew is far milder than TinyURL's 100:1.
  • 12 writes and 58 reads per second. Small. A handful of application servers can carry this.

Step 3: Define the API

Three endpoints cover the whole product, and every authenticated call carries a developer key.

POST /pastes
  Authorization: Bearer <api_dev_key>
  body: { paste_data, custom_alias?, expires_at? }
  201:  { paste_url, paste_key, expires_at }

GET /{paste_key}
  Authorization: Bearer <api_dev_key>   only for private pastes
  200:  the paste text
  401:  sign-in is required for this private paste
  403:  the caller may not read this paste
  404:  no paste has this key
  410:  the paste has expired

DELETE /pastes/{paste_key}
  Authorization: Bearer <api_dev_key>
  204:  no content

api_dev_key is the API developer key of a registered account. It identifies who is calling. We use it to throttle each account to its allocated quota, which protects the key pool and the storage.

Two details about the key are worth saying in an interview. First, it travels in the Authorization header, not in the request body. Keeping credentials out of the payload lets the API gateway reject a missing or invalid key before the request reaches any service. Second, the key is a randomly generated secret, issued at registration and stored hashed, like a password. It is never the account's UserID. Database ids follow predictable patterns, and a guessable credential would let one caller act against another account's quota.

The same endpoints serve the website and other programs. That answers the extended requirement about a REST API.

Step 4: Define the Data Model

The data has one unusual property: a record's metadata and its contents have very different sizes.

  1. Billions of records.
  2. Each metadata row is small, under one kilobyte.
  3. Each paste's contents can be big, up to 10 MB.
  4. One relationship: a paste belongs to the user who created it.
  5. One read pattern that matters: look up a paste by its key.

Point 3 is the one that decides the storage. Metadata (the key, the expiry, the owner) goes into a database table. The contents go into a store built for large objects, which step 5 shows. Two tables cover the metadata:

URLHash is the short key of the paste, the same idea as the short key in TinyURL. It is varchar(16) rather than a fixed seven characters because the same column must also hold custom aliases. UserID links a paste to the user who created it. ContentKey is a pointer: it names the object in external storage that holds the actual text. The row never contains the paste itself.

Paste also carries the two dates. CreationDate records when the paste was made. ExpirationDate records when it should stop resolving, either the default period or the time the user picked. Step 6's cleanup service reads this column to remove dead pastes.

Access counts, the analytics item on the extended list, stay off this row. A counter column would make every read write the row, and a popular paste would become a write hotspot. TinyURL keeps click counts out of the URL row for the same reason. Counts belong in a separate analytics store.

User holds one row per account, and UserID on a paste points at it. It holds the name, the email, and the account dates. This table grows only when someone registers, so it stays small beside Paste.

Which database for the metadata? The workload has the same shape as TinyURL's: billions of small rows, looked up by primary key. A key-value or wide-column store like DynamoDB or Cassandra fits well. A relational database like MySQL also works, because 12 writes per second is a light load.

Where do the contents go? Into object storage, like Amazon S3. Object storage is built for exactly this pattern: write a blob once, read it many times, never edit it in place. It also replicates every object across machines on its own, which is what the durability requirement demands. When contents grow, we add capacity without touching the metadata database.

Only Paste grows without limit. It gains a million metadata rows a day, and its contents add 10 GB a day to object storage, by step 2's numbers. Splitting that data across machines is a step 6 decision, covered in its partitioning section.

Step 5: Draw the High-Level Design

At a high level, we need one application layer and two stores. The application servers handle every read and write. They keep paste metadata in one store and paste contents in the other.

The split is the point of this diagram. Metadata and contents have different sizes, different growth rates, and different access patterns. Separate stores let each one scale on its own.

Step 6: Go Deep

Generating the key

The key question carries over from TinyURL, so run the same checks at this system's scale.

How long should the key be? We will store 3.6 billion pastes over ten years. Six base62 characters give about 56.8 billion possible keys. That sounds like plenty, but 3.6 billion of those keys would point at a real paste. A random guess would find someone's paste about once in 16 tries. Pastes often hold private data, so that breaks the guessability requirement. Seven characters raises the keyspace to 3.5 trillion. A random guess then works about once in 1,000 tries, and rate limiting covers the rest of the risk.

Which alphabet? Base62, meaning A-Z, a-z, and 0-9. The TinyURL lesson explains why base64's extra characters cause trouble inside a URL.

Where do keys come from? The same two answers as TinyURL. The simple answer: the application server generates a random seven-character key and inserts the row. If the key is already taken, it generates another and tries again. That collision loop runs on the request path while the user waits. For a custom alias the check is unavoidable, because the user chose the value. Insert it, and return an error if it is taken. The 16-character limit on aliases keeps storage predictable.

The better answer: a standalone Key Generation Service (KGS) generates random keys ahead of time and stores them in its own database (call it key-DB). Creating a paste then just takes a key from the pool. No collision check, no retry, nobody waiting.

KGS keeps two tables: keys not yet used, and keys already used. As soon as KGS hands keys to an application server, or loads them into its own memory, it moves them to the used table. This way, two servers can never receive the same key. If a server dies holding unused keys, those keys are lost. That is acceptable, because the keyspace has trillions of keys to spare.

Is KGS a single point of failure? Yes. Run a standby replica of KGS; it takes over when the primary dies. Application servers also cache a batch of keys in memory, so writes continue during the failover.

For that failover to be safe, both tables must live in a replicated store, and a key must reach the used table durably before it leaves KGS. A standby that takes over without those writes can hand out keys the old primary already gave away, and two pastes end up sharing a key. Losing keys to a crash is fine. Handing the same key out twice is not.

Handling a write

Order the steps so a failure cannot leave broken data. The server takes a key, writes the contents to object storage first, and then inserts the metadata row. If the contents upload fails, no row exists, so nothing points at missing data. Only after both writes succeed does the user get their URL.

The opposite failure leaves rubbish rather than breakage. If the upload succeeds and the metadata insert does not, the object sits in storage with nothing pointing at it. Nobody can read it, and the cleanup service will never find it, because that service works from metadata rows. Give every uploaded object a short time to live that a successful commit clears, so an object nobody committed removes itself.

Handling a read

The server looks up the key in the metadata database. If the key does not exist, it returns an error. If the paste has expired, the server treats it as gone and queues the paste for removal, the row and its object together. Dropping the row on its own would strand the contents in object storage. Otherwise, it fetches the contents from object storage using ContentKey and returns them to the user.

Read the diagram in three parts. The request path runs from clients through the load balancers to the application servers. Below it, the Key Generation Service feeds blocks of keys from key-DB to the application servers. On the right sit the two stores, each with a cache in front, and the cleanup service.

Caching and load balancing

There are two caches because there are two kinds of data. A metadata cache holds hot rows, so a lookup can skip the database. A block cache holds the contents of hot pastes, so a read can skip object storage. Size the content cache at the 2 GB we estimated. LRU (evict the least recently used entry) is the right policy here. The reason is the same as in TinyURL: a paste is read most when it is new.

Caching the contents is safe for the same reason it was safe in TinyURL: a paste's text never changes after creation, so a write cannot race a cached copy. The metadata cache needs more care, because a metadata row does change. A deletion must drop the cached row, and so must a change of visibility. The scanner described at the end of this lesson works by flipping that flag, and a stale cached row would go on serving a paste that was just taken down. The TinyURL caching section covers the rest, including caching missing keys.

Expiry and cleanup

Same policy as TinyURL: never scan constantly, clean up lazily.

  • When a request arrives for an expired paste, treat it as gone and delete it then.
  • A separate cleanup service runs during off-peak hours. It removes expired pastes from the metadata database and their contents from object storage.

Some designs move expired keys back into the key pool. Do not do that. A recycled key makes an old link point at somebody else's paste. That is the same security problem TinyURL names, and with trillions of keys there is nothing worth recovering.

Partitioning, replication, and durability

Partition the metadata by the key, exactly as TinyURL partitions its table. Hash the key and map it to a partition. Use consistent hashing, so adding or removing a machine moves only a small part of the data. Randomly generated keys spread evenly on their own.

Durability comes from copies. The metadata database replicates every partition to at least two other machines. Object storage replicates every object by itself, which is a large part of why we chose it. Losing one machine loses no paste.

Security and permissions

Store a visibility flag on each paste's metadata row. For private pastes, also store the set of user ids permitted to read it. The check runs on the read path, before the contents are fetched. That is why the permission data belongs in the metadata store, not in a separate service. Abuse is handled where it enters: api_dev_key throttles paste creation per account, and rate limiting on reads makes brute-force guessing of keys impractical.

Step 7: Bottlenecks and Failure Points

The interviewer does not expect this design to be limitless. They expect you to know where it ends.

  • The read path depends on the metadata store, the object store, and the caches in front of them. That is one more dependency than TinyURL's redirect path had. When object storage is slow, every uncached read is slow.
  • KGS and the cleanup service can both be down without stopping the product. Writes keep working on the keys the application servers hold in memory, and expired pastes are simply cleaned later.
  • The 10 MB limit protects every estimate above. Without it, a few abusive uploads would make the storage and bandwidth numbers meaningless.

Where AI Fits in This Design

After the main design, interviewers often ask one more question: where would AI fit in this system?

For Pastebin, the fit is scanning what people paste. Developers paste configuration and logs, and those often carry secrets: passwords, private keys, tokens that unlock other systems. A paste is public by default, so a leaked key stays visible to everyone until someone notices. A detector scans each new paste after it is stored, off the write path. Simple patterns catch known key formats, and a model catches secret-shaped text that the patterns miss.

The interesting question is what to do when the detector finds something, and it is a question about errors. A false positive hides a harmless paste until a review clears it. The cost is one annoyed user. A false negative leaves a working key public. That harms whoever the key belongs to, not just the user who pasted it. The two mistakes have very different prices, so an unsure detector should flag. Note that this is the reverse of the URL shortener, where the false positive was the expensive error.

The mechanism already exists. Each paste's metadata row carries a visibility flag, checked on the read path. The scanner only has to set it, and the paste stops being served until a person responds.

Key generation, the stores, and the caches need no AI.

💡 In the interview: spend your time on the two things Pastebin adds: the metadata-versus-contents split, and durability. Say early that key generation carries over from the URL shortener, run the guessability check at this scale, and move on. The moment the interviewer is listening for is when you explain why the contents belong in object storage rather than in database rows. If you are asked what breaks first, name the uncached read that has to touch object storage.

Key takeaway: Pastebin is TinyURL plus a payload. Reuse the key design: seven base62 characters, pre-generated by a KGS, moved to a used table before they are handed out. Store small metadata rows in a partitioned database, and store the paste contents in replicated object storage. A 10 KB average with a 10 MB limit does not belong in database rows. Split the caches the same way: one for hot metadata, one for hot contents. Durability is the requirement TinyURL did not have, and object storage's replication is how this design meets it.

The second clause is specifically a durability requirement:

  • Availability → the system is reachable and able to serve requests.
  • Reliability → broader umbrella idea: the system consistently behaves correctly over time despite failures.
  • Fault tolerance → the system can continue operating when components fail.

using durability is more accurate and clearer. The current sentence conflates reliability with durability.
