Usage Metering and Billing APIs

On This Page

Key Takeaways

A customer has three features: document summaries, support-answer drafts, and product-description generation.

At the end of the month, they see one total. They cannot tell which feature consumed it, which calls were retried, or whether a failed stream was billed.

A metered API needs more than a monthly total. Provide usage with each result, a collection for reconciliation, an estimate before generation, and clear behavior when the spending limit is reached.

1. Name the Unit Before Naming the Price

"The API charges per call" is not enough when calls differ by thousands of times in size.

This chapter meters inference in tokens. A token is a model-specific unit used to measure processed input and generated output, and the caller should not assume that one token equals one word or one character.

Input and output are counted separately, for four reasons. They may carry different prices. The caller controls the size of each in different ways. Output size is unknown until generation ends. And a customer trying to reduce cost needs to know which side dominates.

If cached input, image units, audio duration, or tool execution becomes billable later, each receives its own named quantity. Do not silently fold a new unit into input_tokens and change what an old field means.

The contract has to state five things:

  • which text contributes to input tokens;
  • whether tool schemas and system instructions count;
  • whether output that was generated and then filtered counts;
  • how failed and cancelled calls are handled; and
  • which tokenizer belongs to the selected model.

The service owns the authoritative count. A local estimate helps a caller plan, and it never replaces the billed number.

2. Read Prices From the Model Resource

Do not publish one current price in prose and expect it to remain true. The caller reads GET /models/model_text_general, whose representation includes:

{
  "pricing": {
    "id": "price_81M",
    "currency": "USD",
    "scale": 6,
    "input": { "amount": 250000, "per_tokens": 1000000 },
    "output": { "amount": 750000, "per_tokens": 1000000 }
  }
}

Each amount is an integer measured in the named currency at the declared scale. With scale 6, one unit is one millionth of that currency. per_tokens states how many tokens that amount prices. Publish rounding and aggregation rules because individual token charges can be smaller than one stored monetary unit.

AI calls can cost less than the smallest ordinary currency unit, which is the explicit-scale financial case Chapter 2 allowed. The API fixes scale for the version, so callers do not receive one scale in one response and another elsewhere.

pricing.id identifies the exact price schedule. If prices change, new calls refer to a new pricing id, while historical usage continues to name the price that applied when work was admitted. Without that identity, a customer replaying last month's arithmetic against today's model resource may calculate a different bill.

3. Report Usage With the Call

The caller should not make a second request merely to learn how much one completed call consumed, so the non-streaming response carries a usage object alongside its output:

{
  "usage": {
    "input_tokens": 200,
    "output_tokens": 100,
    "total_tokens": 300,
    "billable_input_tokens": 200,
    "billable_output_tokens": 100,
    "pricing_id": "price_81M",
    "estimated_cost": { "amount": 125, "currency": "USD", "scale": 6 },
    "final": false
  }
}

For a stream, the same object appears in response.completed or response.failed.

Why can token counts be complete while final is false? The inference service knows what it processed, but the billing pipeline may still apply an account rule, credit, or adjustment, and the durable usage record has not yet completed reconciliation. The immediate cost is an estimate under the price accepted at admission; the later usage record becomes the billing authority.

The caller can attach bounded metadata such as {"feature": "document_summary", "job_id": "job_812"}, which the service echoes into the usage record. Publish limits such as at most 10 keys, 40 characters per key, and 100 per value, and reject unknown or oversized structures with 400 rather than accepting an unlimited object that becomes a hidden log store. Metadata supports attribution; it must not be trusted for authorization, pricing, or tenant identity.

4. Usage Is a Normal Paged Resource

GET /usage?recorded_at_start=<RFC 3339 UTC>&recorded_at_end=<RFC 3339 UTC>&limit=20

The default page size is 20, the maximum is 100, and the cursor is opaque. Each record carries:

  • its own id, plus source_type and source_id;
  • model_id and pricing_id;
  • the four token counts;
  • an integer cost with its currency and scale;
  • the metadata the caller attached;
  • a final marker; and
  • three timestamps.

Order the collection by recorded_at and id, descending. recorded_at is when the record entered the collection; occurred_at is when work happened. A record added after traversal starts appears before the current cursor, so callers must poll the newest range with overlap and deduplicate by id. A descending cursor alone does not discover new records or later finalization changes.

Supported filters are published and refused when unknown: the recorded-at range, model_id, source_type, source_id, and selected metadata keys explicitly approved for filtering. Each filter is a performance promise, so do not expose arbitrary JSON-path filtering over metadata.

5. Publish How Late Usage Can Be

The contract explicitly allows finalized_at to be null only while final is false. A customer dashboard may show preliminary usage, while an invoice or accounting export waits for final: true.

A preliminary record keeps its id during reconciliation. After finalization, represent corrections as linked adjustment records rather than silently changing an already reconciled amount. Provide a way to discover those updates.

Immediate estimates can differ from final billing. The benefit is that customers can inspect and reconcile the difference.

6. Estimate Before Spending

A caller should not have to submit expensive generation merely to learn that its input was too large or its budget insufficient, so provide a counting operation:

POST /token-counts

It returns 200, because it calculates and returns a result rather than creating an addressable durable resource:

{
  "model_id": "model_text_general",
  "input_tokens": 200,
  "reserved_output_tokens": 400,
  "maximum_billable_tokens": 600,
  "pricing_id": "price_81M",
  "estimated_maximum_cost": { "amount": 350, "currency": "USD", "scale": 6 }
}

The maximum estimate uses all requested output tokens, so actual output may end sooner and actual cost may be lower. The estimate is valid only for the returned pricing_id and unchanged input, and the actual POST /responses performs its own count and admission check, because the caller could modify the body after estimating.

7. A Spend Cap Is Not a Rate Limit

Before admitting a response, the server reserves enough budget for input tokens plus maximum_output_tokens. If that reservation would exceed the cap:

{
  "error": {
    "code": "spend_cap_exceeded",
    "message": "The request would exceed the tenant's current spend cap. Reduce the request, raise the cap through an authorized workflow, or wait for the next billing period.",
    "spend_cap": { "amount": 50000000, "currency": "USD", "scale": 6 },
    "request_id": "req_91P"
  }
}

This course uses 429 for temporary rate limits and 403 for spend-cap refusal. These are API conventions. The important distinction is the next action: a short wait may restore rate capacity, while a spending cap needs a lower-cost request, an authorized cap change, or a period reset.

After generation ends, settle the reservation against recorded usage and release the unused amount. Concurrent admission must account for all outstanding reservations so simultaneous requests cannot exceed the cap.

8. Threshold Alerts Reuse Webhooks

A customer may want warning before the cap is reached, so use the Chapter 3 webhook contract with an event such as usage.spend_threshold_reached carrying the threshold percent, the current spend, and the cap.

Delivery keeps every property from that contract:

  • signed over the body plus a timestamp;
  • retried on the published growing schedule;
  • at least once, so the receiver deduplicates by event id;
  • visible in the failed-delivery list; and
  • redeliverable on demand.

Do not make webhook delivery part of admission. A slow customer endpoint must not delay an inference response.

9. One Logical Response Produces One Charge

POST /responses requires an idempotency key, and the service stores the caller and operation scope, the key, the request fingerprint, the admission result, the response outcome, and the linked usage identity for 24 hours.

If a caller times out and repeats the same key and body, the service returns the original result or the in-progress refusal. It does not start another generation and does not write a second usage record. If the caller uses a new key, it has requested new logical work, and the new generation is billed.

This is especially important for batch workers that automatically retry network failures. A retry policy without stable idempotency keys can turn one intended job into several charges.

Failed and cancelled generations still write one usage record for the billable work defined in Lesson 2, and the record's source_id lets the customer connect charge, response, and application job.

10. The Interview Answer

"I treat usage as part of the API contract. Input and output tokens are counted separately, and live prices come from the selected model resource with an immutable pricing id. Final token counts and an estimated cost are returned in the response or final stream event, while a cursor-paged /usage collection becomes visible within five minutes and final within 24 hours. The caller can attach bounded feature metadata for attribution and can call /token-counts to estimate maximum cost before generation. Admission reserves against input plus maximum output. A reached spend cap is 403, not 429, and threshold alerts use signed at-least-once webhooks. The response idempotency key ensures a network retry does not create a second generation or charge."

Key Takeaways

  • Tokens are the metered unit, and input and output counts remain separate.
  • Current prices and limits come from the read-only model resource, and an immutable pricing id connects historical usage to the price that actually applied.
  • Responses and terminal stream events report immediate usage; /usage provides durable reconciliation.
  • Usage becomes visible within 5 minutes and final within 24 hours, with an explicit final marker.
  • POST /token-counts estimates maximum work before spending.
  • A spend cap is policy, so exhaustion returns 403; temporary traffic exhaustion returns 429.
  • Threshold alerts reuse signed, at-least-once webhooks, and never delay admission.
  • A 24-hour idempotency record ensures one logical response produces one usage record and one charge.

The next lesson protects the compute itself. It combines request, token, and concurrency limits, then decides whether an admitted caller is refused immediately or held in a short published queue.
