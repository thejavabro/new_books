Model Serving

  1. TL;DR

1. The Incident

The store deploys a self-hosted 7B-parameter support model for privacy and serves requests one at a time on a GPU, following a conventional web-service design. Response latency meets the requirement, but the resulting capacity calculation reveals a cost problem.

Do the arithmetic with them. One A100-class GPU (about 35,000/year) generates about 50 tokens/second serving a single request. An average reply is 400 tokens. That is 8 seconds of GPU per request, so one GPU sustains about 0.125 requests/second; the assistant needs 20 requests/second at peak. That is 160 GPUs: $5.6 million a year, for a feature whose business case assumed a tenth of that.

Profiling shows that each GPU uses only about 8% of its compute capacity because one request supplies too little work. At batch size one, an LLM forward pass, which runs the model to produce one token, is memory-bandwidth-bound. Data movement from memory limits performance rather than arithmetic speed. Every token step transfers tens of gigabytes of model weights from GPU memory through the compute units, regardless of request count. The arithmetic for one request is small compared with that transfer, leaving most compute units idle.

2. The Obvious Fixes, and Why They Fail

"More GPUs": adding capacity would produce 160 GPUs that each remain 8% utilized. The bottleneck rule requires addressing the limiting resource, which is work performed per weight transfer rather than GPU count.

"A smaller model": distillation, which trains a small model to imitate a large one, and quantization, which stores weights in fewer bits, reduce the weights streamed during inference. This option changes the quality-cost trade-off without resolving utilization. A smaller model served one request at a time still remains mostly idle, so consider it after fixing batching and only when quality requirements allow.

"Queue everything and run hourly batches." For offline work, exactly right. Providers sell it at about 50% off: the queue lesson's permission-to-be-slow, productized, but the assistant is interactive. A customer is waiting, so the staleness budget is seconds. What is needed is batching without the hour: forming batches in milliseconds.

3. The Pattern

Hold incoming requests for a few milliseconds, form a batch, and run them through the model together. The weights stream once per step regardless of how many requests ride along. So a batch of 32 costs barely more time than a batch of 1, and delivers roughly 20-30x the throughput; for LLMs, go further. Continuous batching admits and releases requests at token granularity, so short replies exit without waiting for long ones.

The mechanics, in the order the field learned them:

Dynamic batching is the general form, for any model. The server holds requests up to a tiny window (say 5-10 ms) or a max batch size, whichever comes first. Leave when full, or when the timer expires. Latency pays the window (+5 ms); throughput multiplies; for fixed-shape work (embeddings, image classification), where every request costs the same, this is the whole pattern, and it is clean.

The LLM complication is Constant 1: work variance. In a static batch, every request waits until the longest generation finishes. A 10-token reply grouped with a 2,000-token essay therefore waits for the essay. This is the convoy effect, where short work waits behind long work, and utilization declines as completed requests leave idle slots.

Continuous (in-flight) batching: schedule work at each token step rather than once per request. The engine processes one token for every active request during each step. Finished requests exit immediately, while waiting requests enter the active batch. Requests therefore enter and leave continuously, keeping utilization high despite 100x variance without reserving slots for completed work.

KV-cache memory management: each active request's KV cache (its conversation-so-far working memory) lives in GPU memory. Naive allocation fragments it, capping how many requests fit. Paged allocation reclaims the fragmentation. This is PagedAttention: virtual memory's page tables, rediscovered for attention; the result is 2-4x more concurrent requests in the same GPU. Old OS ideas, new hardware.

The surrounding stack: replicas sit behind a load balancer that routes by queue depth and outstanding tokens. Connection counts are inaccurate when request work varies by 100x. Sticky routing keeps a conversation on the replica containing its existing KV cache. Advanced systems also separate prefill and decode: prefill, which reads the prompt, is compute-bound, while decode, which generates the reply, is bandwidth-bound. Specialized pools can optimize these two workloads independently.

4. Walkthrough with Numbers

Now serve the support assistant with continuous batching through a vLLM-class engine.

Throughput per GPU: aggregate generation at batch size around 32 reaches about 2,500-3,000 tokens/second, versus 50 single-stream; per request, 400 tokens still takes a few seconds of wall clock. But the GPU is serving 6-7 requests/second at the same time.

The fleet: 20 req/s divided by about 6 per GPU is about 3.3, requiring 4 GPUs plus one for capacity headroom, or 5 total instead of 160. Annual cost falls from 175K, a 30x reduction produced by scheduling alone. The model and output quality remain unchanged. Batching therefore determines whether the service is financially viable rather than merely optimizing an existing design.

What latency paid: tTFT gains about 20-30 ms from batching windows and scheduling: invisible under the SSE stream. Per-token pace is roughly unchanged. The customer notices nothing; the CFO notices everything.

Utilization. 8% becomes about 70%.

And the bulk work moved out entirely: the nightly product-description job (10M items) goes to the provider's batch API at half price. It is bulkheaded away from the interactive fleet, exactly as the caching capstone separated display from decision.

5. Trade-offs

You gain:

  • 10-30x throughput per dollar: the economics that make self-hosted inference exist at all.
  • Variance tamed: continuous batching keeps utilization high while requests differ 100x.
  • A serving tier that composes with everything downstream: autoscaling has fewer, fuller GPUs to manage.

You pay:

A small latency floor: the batching window and scheduling overhead add milliseconds to TTFT. This delay is small but still matters for hard-real-time workloads.

Shared resource contention: batch members use the same memory and compute, so one enormous prompt can dominate scheduling, as Q3 shows. An engine-level failure also interrupts every request in the batch.

A genuinely complex serving layer: token schedulers, paged memory, preemption. This is why the ecosystem's answer is: do not build it. vLLM, TGI, and Triton are the pattern as products. Hand-writing a scheduler today is a mistake, not a strength.

Tuning per workload: batch caps, window sizes, and memory budgets differ between chat, embeddings, and long-document work.

6. When Not to Use It

Hard real-time, single-digit-millisecond inference (voice frames, some ranking). Batching windows may be unaffordable; use dedicated small-batch or specialized runtimes instead.

Tiny traffic: a dev environment or a 0.1 req/s internal tool gains nothing. Batch-of-one is correct when one is all there is.

Offline bulk: do not route it through the interactive fleet at all. Batch APIs and offline jobs are cheaper by half and far more patient.

The classic misuse is the reverse of the incident: interactive and bulk traffic sharing one fleet. The 10M-item nightly job delays customer chats, and that is the bulkhead lesson's success-shaped starvation, GPU edition.

7. Dynamic vs. Continuous Batching

Dynamic (request-level)Continuous (token-level)
Batch membershipFixed at launch: all wait for the last to finishFluid: exit on completion, join mid-flight
100x output varianceThe convoy effect: short waits for longAbsorbed: capacity reclaimed per token
FitsFixed-shape work: embeddings, vision, rankersLLM generation: the variance is the workload
ImplementationSimple window + max sizeThe engine's whole scheduler (buy it: vLLM)

The routing sentence: uniform work batches by request; variable work batches by token. LLM generation is variance (Constant 1), so continuous batching is the LLM default. Dynamic batching serves the fixed-shape fleet beside it: your embedding endpoint, which the semantic cache will soon be calling.

8. Real-World Examples

vLLM implements continuous batching and paged KV memory as open-source software. These mechanisms reduced inference cost enough to make self-hosted LLM serving practical for more workloads.

NVIDIA Triton is dynamic batching as general-purpose infrastructure: every model type, one server.

TGI, TensorRT-LLM, SGLang are the engine ecosystem, all variations on this lesson.

Provider batch APIs from Anthropic and OpenAI apply this pattern to offline work at about a 50% discount. Providers schedule delay-tolerant requests during spare fleet capacity, using the same batching economics.

9. In the Interview

"Design LLM inference serving" is the fastest-growing system design question, and the batching economics are its center. The probe question is "why does batching help so much on GPUs?" It separates candidates who have operated inference from those who have only called APIs.

The 30-second answer: "At batch size one, LLM inference is limited by memory bandwidth. Every token step streams the complete weights through the chip while performing little computation, producing eight percent utilization and a fleet costing millions. Batching distributes that transfer across requests. Thirty-two requests share one weight pass, increasing throughput by twenty to thirty times for milliseconds of additional first-token latency that streaming can conceal. LLMs require continuous batching with token-level entry and exit because output lengths vary a hundredfold, and request-level batches make short replies wait for long ones. Paged KV-cache memory provides two to four times the concurrency. Route on queue depth and outstanding tokens rather than connections, and keep conversations sticky for warm caches. Use an established vLLM-class engine because its scheduler implements these mechanisms. Send bulk work to batch APIs at half price rather than this interactive fleet."

Likely follow-ups:

"Why is batch-32 barely slower than batch-1?" The step's cost is dominated by streaming weights from GPU memory, and that cost is identical regardless of batch size. The per-request compute rides along nearly free; adding requests is nearly free until the batch is large enough to saturate the compute units.

"A user pastes a 50-page document and everyone's latency spikes. Why, and what do you do?" Prefill (reading in a huge prompt) is a compute-heavy burst that can monopolize token steps. That is the batch's shared fate (Q3 works it fully). Mitigations: chunked prefill (interleave the giant prompt's ingestion with everyone's decode steps), input-size caps and tiering, and at scale, prefill/decode disaggregation. The largest requests get their own pool (bulkhead, as always).

Mistakes that fail candidates: costing one-request-at-a-time serving and seeing nothing wrong, request-level batching proposed for chat (the convoy effect, unrecognized), or hand-writing the token scheduler.

10. Check Yourself

Q1 (recall): explain, mechanically, why a batch of 32 costs approximately the same wall-clock time per token step as a batch of 1; where does that stop being true?

Q2 (trade-off): three workloads: (a) the embeddings endpoint (uniform 50 ms jobs), (b) customer chat (100x output variance), (c) nightly summarization of 10M product pages. Assign each its serving strategy.

Q3 (scenario): the assistant's p99 TTFT (the first-token latency of the slowest 1% of requests) is normally 200 ms. Support reports it spiking to 4+ seconds, intermittently, for all users at once. The spikes correlate with sessions where users paste entire contracts; diagnose the mechanism, and layer the fixes.

Answers

A1: each generation step must stream the model's full weights from GPU memory through the compute units. That is a fixed, dominant cost independent of batch size. The per-request math is small enough to ride along nearly free. So requests add at almost no marginal cost until the batch's aggregate compute finally exceeds the streaming time, or KV-cache memory runs out. At that point the workload turns compute-bound and each additional request costs real time; batching is free until the GPU saturates. Then it is a second GPU (autoscaling's cue).

A2. (a) Dynamic request-level batching (Triton-style). Uniform work has no convoy risk: simple window, large batches, done. (b) Continuous batching (vLLM-class) with paged KV. The variance is the workload. (c) Neither fleet. The provider's batch API or a dedicated offline run at off-peak: half the price, zero interactive impact; add a bulkhead rule ensuring bulk can never route to the interactive pool.

A3: the pasted contract triggers a large prefill operation. Ingesting tens of thousands of prompt tokens is compute-bound and competes with every active decode for token-step scheduling. This one request increases TTFT across the batch, applying Constant 1 to input computation instead of output length. Combine these repairs:

  1. Chunked prefill: the engine interleaves the giant prompt's ingestion across many steps, capping its per-step share. Most engines expose this: turn it on.
  2. Input tiering: documents past a threshold route to a long-context pool or an async flow. The bulkhead, again: the largest requests get their own lane.
  3. Product-level caps with honest UX ("large document: processing may take longer") rather than silent delays.
  4. Prefill/decode disaggregation, at serious scale. Separate pools for the two phases, each provisioned for its own physics.

The meta-lesson: the module's Constant 1 (100x variance) shows up in inputs too; every fix is an old pattern (interleaving, bulkheads, tiering) pointed at new hardware.

11. Related Patterns

  • Load Balancing: queue-depth and outstanding-token routing: the inference twist, now with its full context.
  • GPU Auto-Scaling: next lesson: fewer, fuller GPUs, and the hard question of adding more when full.
  • Message Queue: the offline half: bulk work goes through batch queues, at half price, away from the interactive fleet.
  • Semantic Caching: the best batch is the request that never reaches the GPU: two lessons ahead.

12. TL;DR

ProblemOne-at-a-time LLM serving runs GPUs at about 8% utilization (memory-bandwidth-bound weight streaming with almost no work aboard), turning a 20 req/s feature into a $5.6M/year fleet.
MechanismBatch the requests: dynamic batching amortizes the weight-stream across ~32 requests for milliseconds of TTFT; LLMs need continuous token-level batching (exit on finish, join mid-flight) against 100x variance, plus paged KV memory for 2-4x concurrency: bought as vLLM-class engines, never hand-rolled.
CostsA small TTFT floor, shared fate within the batch (giant prompts dominate: chunked prefill, tiering, disaggregation), a genuinely complex engine layer, and per-workload tuning.
Skip it whenHard real-time milliseconds, trivial traffic, or bulk offline work: which belongs on batch APIs at half price, bulkheaded away from the interactive fleet entirely.
30-second answerWeights stream once per step whether one request rides or thirty-two, so fill the batch: continuously, at token granularity, with paged memory: and the fleet math collapses 30x. Buy the engine, route by queue depth, and keep bulk work off the interactive fleet.
