Event Sourcing

  1. TL;DR

1. The Incident

Three questions arrive at your team in the same week. Your database cannot answer any of them.

Monday, a dispute. A customer insists they cancelled order 7f3a before it shipped. They want a refund for the return postage; support pulls up the order: status = shipped. That is the current state; was it ever cancelled? For a minute, at 14:02, before the shipping job overwrote it? The row has one status column, and every UPDATE wrote over the last one; the history is not hidden. It is destroyed.

Wednesday, a bug. A pricing bug deployed two weeks earlier miscalculated some order totals and was later fixed without preserving evidence. Finance asks which of the roughly 90,000 orders from that period were affected. Because incorrect totals were updated in place and only some received manual corrections, the later fix removed the evidence.

Friday, product. "How often do customers add an item to the cart and remove it before checkout? We want to understand hesitation." Nobody ever thought to record cart removals; the data was not lost; it was never kept.

Three different questions, one root cause: your database stores the present, and UPDATE is a destructive operation; now recall what the last lesson revealed. Underneath your tables, the database already keeps an append-only log of every change, for its own survival. It just does not share it, and its log records row-diffs (which column changed to which value), not business language.

Which suggests a thought. What if the application kept a log like that, in words the business understands, and treated it as the truth?

2. The Obvious Fixes, and Why They Fail

"Add an audit table." Triggers or app code copy every change into an order_history table. This is the standard move, and it half-works, but the audit table is an afterthought copy. Some code path always forgets to write it, and backfills skip it; the day it disagrees with the orders table (that day comes), which one is true? An audit log kept beside the truth is only as reliable as its least careful writer, and it still records diffs ("status: shipped"), not intent ("customer clicked cancel").

"Add columns: updated_at, previous_status..." Schema clutter that captures one step of history. It answers Monday's question by luck, and Wednesday's and Friday's not at all.

"We have point-in-time backups." True, from the WAL lesson, but restoring a 2-week-old copy of the database to answer one question is slow and awkward, and it shows you that a row changed, never why. No backup contains the fact "the customer cancelled": only the indirect trace of it.

All three try to attach history to a design whose source of truth forgets. The pattern reverses the relationship.

3. The Pattern

Store what happened, not what is. Every change is appended as an immutable event with a business meaning (OrderPlaced, ItemRemoved, OrderCancelled). Immutable means it is never changed after it is written. The current state is whatever you get by replaying an entity's events from the beginning. The log is not a record of the truth. The log is the truth.

Your bank already works this way; it does not store your balance and update it. It stores the transactions, and your balance is the running total. Ask the bank "why is my balance $412?" and it can answer, line by line, forever; nobody can overwrite a transaction that happened. A mistake is fixed by adding a correcting entry; accountants have worked this way for five hundred years, for exactly the reasons in section 1.

  Event stream for order 7f3a (append-only, immutable):

  1. OrderPlaced      {items: [A], total: $49}     Mon 13:41
  2. ItemAdded        {item: B, total: $89}        Mon 13:44
  3. ItemRemoved      {item: A, total: $40}        Mon 13:46
  4. CheckedOut       {total: $40}                 Mon 13:51
  5. OrderCancelled   {by: customer}               Mon 14:02
  6. ShipmentDispatched {carrier: UPS}             Mon 14:07   <- the bug!

  replay 1..6  ->  current state: shipped-but-cancelled (a conflict
                   the old design silently overwrote, now visible)

The working parts:

The event store. An append-only home for events, organized into one stream per entity (order 7f3a's events, in order). Appending is the only write operation; this should sound familiar; you are building the write-ahead log, one level up, with business verbs instead of row-diffs.

Current state = replay. Load order 7f3a's 6 events and apply them in order: start empty, place, add, remove, check out, cancel, ship. The state is the result; for streams that grow long, a snapshot every N events caches the state, so replay only covers the tail. That is the checkpoint idea, making its third appearance in this module.

Projections: the query problem, solved separately. You cannot ask an event log "all orders over $100 this month". That would mean replaying everything, so you maintain projections: ordinary read-optimized tables, like a current_orders table or a daily-revenue table. Each is built by consuming the event stream and updating itself; if this sounds exactly like the local views from the Event-Driven Architecture lesson, it should. It is the same mechanism, applied internally; projections are derived, disposable, and rebuildable from the log; remember the word disposable; it appears in the self-check.

Mistakes get corrected, never erased. The pricing bug's fix is not an UPDATE; it is a new OrderTotalCorrected event, with a reason attached. The error and the correction are both permanently visible, which is precisely what finance and auditors want; immutability is not a limitation to work around; it is the feature.

4. Walkthrough with Numbers

The week's three unanswerable questions, replayed against the event store:

The dispute. Load stream 7f3a; event 5: OrderCancelled at 14:02; event 6: ShipmentDispatched at 14:07. The customer is right, and the refund is issued in minutes. As a bonus you have discovered a real race condition, where two steps ran without checking each other. The shipping job does not check for cancellations; the evidence of the bug is the data.

The pricing bug. Scan two weeks of events for CheckedOut where the replayed total matches the buggy formula's output. That gives an exact list of affected orders, in one query; it is followed by an auditable stream of OrderTotalCorrected events; finance gets a spreadsheet and a complete record.

The product question. Count ItemRemoved events that follow an ItemAdded for the same item across all streams. A question nobody thought to instrument, answered later, because everything is kept; this is the pattern's most underrated property: your history can answer questions you have not asked yet.

The bill. An average order stream is about 12 events x 300 bytes = 4 KB, versus a 400-byte row. Storage runs 10-15x the current-state design; that is real, and small compared with the questions it answers. Replaying one order takes microseconds; rebuilding a projection over 100 million orders takes hours. That is the number that actually constrains you; it is why projections are maintained continuously rather than computed on demand.

5. Trade-offs

You gain:

  • A complete, trustworthy history by construction, not by discipline: audit is not a feature you add, it is the storage model.
  • Debugging with full history: the state of anything, at any moment, plus the exact sequence that led there.
  • Retroactive analytics: new questions answered from old data.
  • A natural fit with Module 2. The events you would want to publish anyway already exist, so the log doubles as the outbox, the store of events waiting to be sent.

You pay:

Queries need projections. The log answers "what happened to this order?" perfectly and "which orders exceed $100?" terribly; you will maintain read models. Keeping the write side this shape while the read side wants another is the exact tension the next lesson resolves.

Events remain permanent, including their old formats. Code written much later may replay today's OrderPlaced event, so event schemas require versioning from their first release. Use additive changes and upgrade-on-read logic for older formats, applying the pub/sub schema contract permanently.

Eventual consistency, again. Projections lag the log by a moment; that is eventual consistency: a read model catches up shortly after the write. Everything the EDA lesson taught about reading your own writes applies here.

The cost of the model. Uniqueness rules ("this email can only register once") are awkward across append-only streams. Teams unfamiliar with the model move slowly at first, and deletion regulations meet an immutable log. The answer is crypto-shredding: encrypt each person's event fields with their own key, and destroy the key to erase them everywhere; that is exactly what the EDA lesson prescribed.

6. When Not to Use It

This is the most direct "when not" in this course: the default answer to event sourcing is no. Most applications manage current state (profiles, settings, content pages); history genuinely does not matter for them. A plain table with an audit log covers the rare "who changed this?" Use event sourcing where the domain is a ledger:

  1. Money. Balances, payments, wallets: the bank statement is not an analogy here, it is the requirement.
  2. Inventory and orders. Contested, audited, and dispute-prone: exactly section 1's world.
  3. Anything compliance-audited, where "show me the complete history, provably untampered" is a legal requirement.

Skip it for high-volume current-value data, like sensor readings where only the latest matters. Skip it for CRUD-shaped admin tools (create, read, update, delete), and skip it for any system where the team's unfamiliarity costs more than the history is worth. If you need history but not the model, the comparison below has a cheaper option.

Two common misuses.

Ideological event sourcing. Converting the whole company because the payments team loved it.

CRUD disguised as events. An event log full of OrderUpdated {field: status, new_value: shipped}; those are row-diffs with event names; real events are business verbs (OrderCancelled, PaymentCaptured). If your events read like database operations, you have paid the pattern's full price for none of its meaning.

7. Event Sourcing vs. Change Data Capture

If you need history, an alternative can provide it without restructuring the application. Change data capture reads the database's own WAL, described in the previous lesson, and publishes each row change as an event. A later lesson covers it fully, but the comparison matters here:

Event sourcingCDC-based history
Source of truthThe event log itselfYour existing tables (unchanged)
What is capturedBusiness intent: OrderCancelled, by customerRow diffs: status: 'active' to 'cancelled'
Adoption costRestructure the write pathAdded on: no app changes
Can it miss changes?No: events are the writesNo: the WAL sees everything (unlike audit tables)
Friday's question ("why?")Answerable: intent is recordedPartly: you see what changed, and infer why

The honest routing: CDC when you need history; event sourcing when the events are the product. CDC gives you a complete, cannot-miss change history for the cost of a connector; for analytics, caches, and search indexes, it is the right answer and the mainstream one. Event sourcing is worth its cost only where the business meaning of each change must itself be stored: money, disputes, audits; state that routing instead of picking a side.

8. Real-World Examples

  • Banking and accounting are the five-century-old original: double-entry ledgers are event sourcing on paper.
  • Git is the version you already use daily. Commits are immutable events, your working directory is a projection, and git log is the audit trail. If you have ever rebuilt state by replaying commits, you understand this pattern.
  • Kafka-centric architectures treat the topic as the durable log and every database as a projection of it: event sourcing at company scale.
  • EventStoreDB, Axon, Marten: purpose-built event stores for teams adopting the pattern directly.

For AI engineers: agents are event-sourced whether you meant it or not. A conversation is an append-only stream of messages, tool calls, and results; the agent's "state" at any point is a replay of that stream. That is exactly why you can re-run an eval from history, debug by replaying a session, and audit what an agent did and why. Store agent traces as event streams in their own right (not just logs) and you get full-history debugging over agent behavior. The same idea powers point-in-time correctness in feature stores; training a model "as of March 1st" requires replaying feature history to that moment. That only works if history was stored as events rather than overwritten in place.

9. In the Interview

"Design a banking ledger or digital wallet" is the question most directly associated with this pattern. Explain that balances are derived while transactions are authoritative. Other questions may require a complete audit history or ask how to determine what happened to one order.

The 30-second answer: "For domains that are really ledgers (money, orders, inventory), I store events, not state. Each entity gets an append-only stream of business facts, like OrderPlaced and OrderCancelled. Current state is a replay of the stream, with snapshots so replays stay short. Queries run against projections: read tables maintained from the events, disposable and rebuildable by replay. Mistakes get compensating events, never edits, so the audit trail is the storage model itself. The costs I manage: projections are eventually consistent, event schemas must evolve additively because old events replay forever, and deletion requests get crypto-shredding. And I only pay this cost where history is the product. For plain history needs, CDC on a normal database is cheaper."

Likely follow-ups:

  1. "Current balance for an account with 2 million events: you replay all of them?" Snapshots: persist the state every N events, and replay only the tail since the last one. Same technique as database checkpoints. For frequently read accounts, a continuously maintained projection means zero replay at request time.
  2. "Legal says delete this user. Your log is immutable." Crypto-shredding: personal fields in events are encrypted with a per-user key from day one. Destroying the key makes every copy unreadable: log, snapshots, projections, backups. Immutable structure, erasable content. Answering this without being prompted about backups marks a senior candidate.

A mistake that fails candidates: proposing event sourcing for everything, events that are row-diffs with event names (OrderUpdated), or no projection story. "We'll replay on every request" collapses at the first entity with a long history.

10. Check Yourself

Q1 (recall). Where does truth live in an event-sourced system? How is current state obtained? And what happens when a past event turns out to be wrong?

Q2 (trade-off). Four systems: a digital wallet, user profile settings, warehouse inventory, and a marketing CMS. Which two deserve event sourcing, and what do the other two deserve instead?

Q3 (scenario). The revenue dashboard (a projection) says today's total is 48,950. Which number is right, what likely happened, and what is the fix? What does your answer reveal about the pattern?

Answers

A1. Truth is the append-only event log; everything else (current-state tables, dashboards, caches) is a projection derived from it. Current state is obtained by replaying an entity's events in order, shortcut by snapshots for long streams. A wrong past event is never edited or deleted. A compensating event (for example, OrderTotalCorrected, with a reason) is appended, so both the mistake and its correction remain permanently visible: the accountant's rule.

A2. The wallet and the inventory; both are ledgers by nature, contested and audited. For both, "how did we get to this number?" is a business-critical question; profile settings and the CMS are current-state domains. Nobody disputes the history of a notification preference, so they deserve plain tables, plus an audit log or CDC if "who changed this?" occasionally matters. Paying the cost of event sourcing there gains nothing.

A3. The event store is right because it is authoritative, while the projection is a derived copy. The projection consumer may have crashed and missed events, applied a redelivery twice without idempotency, or processed events incorrectly. Fix the consumer, then rebuild the disposable dashboard table by replaying the log. A large store may require hours, but derived data can always be regenerated instead of remaining permanently corrupted.

11. Related Patterns

  • Write-Ahead Log: the same technique, one level down; event sourcing is the WAL promoted to your application's data model, with business verbs.
  • Publish-Subscribe: the events you would want to announce already exist; the log doubles as the outbox.
  • CQRS: the next lesson: what happens when you let the write side stay event-shaped and give the read side entirely different storage.
  • Change Data Capture: the less expensive alternative for plain history needs: complete change streams from a normal database, no restructuring required.

12. TL;DR

ProblemUPDATE destroys history: disputes cannot be settled, a bug's blast radius cannot be reconstructed, and yesterday's unasked questions cannot be answered, because the database only stores the present.
MechanismAppend immutable business events (one stream per entity) as the source of truth; derive current state by replay (with snapshots); serve queries from disposable, rebuildable projections; correct mistakes with compensating events.
CostsProjections and their lag, ~10-15x storage, event schemas that must evolve additively forever, crypto-shredding for deletion, awkward uniqueness rules, and a real learning cost for the team.
Skip it whenThe domain is current-state CRUD: which is most domains. Default to no; use CDC or an audit log for plain history; reserve this for ledger-shaped domains: money, orders, inventory, compliance.
30-second answerStore what happened, not what is: append-only business events as truth, state by replay, queries from rebuildable projections, corrections as new events. The bank statement, generalized: and only worth its cost where the domain really is a ledger.
