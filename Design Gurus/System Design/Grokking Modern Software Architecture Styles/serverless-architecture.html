Key Takeaways

The word serverless is a misleading name.

Servers absolutely exist. Your code runs on them.

What disappears is your relationship with them: you do not provision them, patch them, size them, scale them, or pay for them while they sit idle. You hand the platform a unit of code and a description of when to run it, and the platform handles everything between "an event happened" and "your code executed."

This shifts the engineering problem. In a server-based system, a large part of the work is capacity planning and operations: how many instances, what size, how to autoscale, how to deploy without downtime.

In a serverless system, the platform answers most of those questions, and a different set takes their place. How do you design for statelessness and tolerate cold starts? How do you keep thousands of concurrent function instances from overwhelming a database, and how do you control a cost model that charges per invocation?

Serverless is best understood as a spectrum of trade-offs rather than a single technology.

At one end, it gives you extraordinary elasticity and near-zero operational burden for bursty and event-driven work.

At the other end it imposes execution limits, vendor coupling, and cost curves that can surprise teams running steady, high-volume workloads. This lesson covers the mechanisms behind both ends.

Know the Vocabulary

This lesson uses the terms below repeatedly. Read them once now and return here when a later section needs one.

  • Functions as a Service (FaaS): The compute half of serverless, in which the platform runs small functions on demand, such as AWS Lambda.
  • Backend as a Service (BaaS): The managed-services half of serverless, in which the application calls fully managed components, such as databases, through an API.
  • Execution environment: The isolated, short-lived sandbox in which the platform loads and runs a function's code.
  • Cold start: The extra latency when the platform must create a new execution environment before it runs a function. A warm start reuses an existing one.
  • Handler: The function that the platform calls with the event on each invocation. Code outside it runs once per execution environment.
  • Concurrency: The number of execution environments that run a function at the same moment, each handling one request at a time.
  • Reserved concurrency: A setting that sets aside part of the account's concurrency limit for one function, which both guarantees and caps its capacity.
  • Provisioned concurrency: A paid setting that keeps a fixed number of environments initialized, so requests that reach them have no cold start.
  • Event source: The service, such as a gateway or a queue, whose events trigger a function. Its type makes the invocation synchronous, asynchronous or poll-based.
  • Dead-letter destination: A separate queue, database table or file that holds records that failed processing, for later investigation or reprocessing. A queue used this way is a dead-letter queue.
  • Choreography: A way to coordinate a multi-step process in which each service reacts to the events of other services, with no central coordinator.
  • Orchestration: A way to coordinate a multi-step process in which one central coordinator, the orchestrator, sends each service a command and decides the next step from each outcome.
  • Connection pool: A set of open database connections that a server keeps and reuses, instead of opening a new connection for every query.
  • At-least-once delivery: A delivery guarantee in which a message is never lost but may arrive more than once.
  • Idempotency: The property that processing the same message twice produces the same result as processing it once. An idempotency key, such as the event ID stored in the database, lets a consumer detect and skip a repeat.

Part 1: What Serverless Means

The Defining Properties

A system is serverless when it has four properties.

  • No server management. You do not provision or maintain machines, operating systems, or runtime patching. The provider owns the fleet.

  • Automatic, fine-grained scaling. Capacity follows demand without configuration, from zero instances to thousands, and back down. You do not define an autoscaling policy; scaling is intrinsic to the platform.

  • Pay for use, not for capacity. Billing is based on actual consumption, such as invocations and execution time measured in milliseconds, rather than on reserved instance hours. When nothing runs, you pay nothing for compute.

  • Event-driven execution. Code runs in response to events: an HTTP request, a file landing in object storage, a message on a queue, a database change, a timer. There is no long-running process waiting for work.

The scale-to-zero property is the one that most distinguishes serverless from merely managed infrastructure. A managed container service takes care of orchestration, but you still pay for the running containers. A serverless function costs nothing when idle.

The Two Models

Serverless covers two related ideas, and conflating them causes confusion.

Functions as a Service (FaaS) is the compute half. You write small functions, and the platform runs them on demand. AWS Lambda, Google Cloud Run functions (formerly Cloud Functions), Azure Functions, and Cloudflare Workers are FaaS. Your code is the unit of deployment, and each invocation is independent.

Backend as a Service (BaaS) is the managed-services half. Instead of building and running a backend component, you consume a fully managed one through an API: authentication (Auth0, Cognito, Firebase Auth), databases (DynamoDB, Firestore, Aurora Serverless), storage (S3), messaging (SQS, SNS, EventBridge), and API routing (API Gateway). You write no server code for these capabilities, and they scale and bill on their own.

A real serverless application is usually a composition of both: managed services provide the building blocks, and functions provide the custom logic that connects them.

A common mature view is that the less code you write yourself, the more serverless your architecture is, because every managed service you use is infrastructure you do not operate.

Part 2: How a Function Actually Executes

The Execution Environment

When an event triggers a function and no suitable environment exists, the platform has to create one.

In AWS Lambda terms, this means allocating a lightweight virtual machine, downloading your code package or container image, starting the language runtime, and running your initialization code. Lambda's virtual machines are microVMs built on Firecracker, the open-source microVM manager that AWS wrote for Lambda. Only then does it invoke your handler with the event.

This sequence is the cold start. Its cost varies with the runtime and package. Lightweight runtimes like Node.js, Python, and Go typically add tens to a few hundred milliseconds. Java and .NET without optimization can add multiple seconds, because of heavier runtime startup and class loading. Larger deployment packages, more dependencies, and attachment to a private cloud network (a VPC, or virtual private cloud) in older configurations all add time.

After the invocation finishes, the platform does not destroy the environment immediately. It keeps it warm for a period, so a following request can reuse it and skip initialization.

This is a warm start. The platform may keep an environment for minutes, but it makes no guarantee, and it may recycle environments at any time.

Why This Shapes the Code You Write

Because environments are reused, code outside the handler runs once per environment, and code inside the handler runs once per invocation.

This is the most important practical idiom in serverless programming: expensive setup belongs outside the handler so warm invocations skip its cost.

Creating the client outside the handler means its connection setup and credential resolution are paid once, not on every request.

The converse rule matters as much: never assume the environment will persist or that two invocations will share one.

Any state kept in memory between invocations is a cache at best, never a source of truth.

Concurrency and the Scaling Model

Each execution environment handles one request at a time in the standard FaaS model.

If ten requests arrive simultaneously, the platform runs ten environments. If ten thousand arrive, it tries to run ten thousand. This is concurrency, and it is how serverless scales: horizontally, by adding environments, with one request per environment.

At a steady load, the number of environments a function needs is the request rate multiplied by the average duration. For example, 5,000 requests per second that each take 200 milliseconds need about 5,000 × 0.2 = 1,000 concurrent environments. If each environment opens its own database connection, the database sees 1,000 connections, which is the problem described in Part 4.

This model has several consequences worth knowing.

  • Burst limits. Platforms cap how quickly concurrency can grow and how high it can go. Each account has a regional concurrency limit, and there is a limit on how fast new environments are added. A sudden spike can therefore be throttled even though the platform is nominally elastic. Reserved concurrency lets you guarantee capacity for critical functions, and also cap a function to protect a downstream dependency.

  • Provisioned concurrency. To avoid cold starts on latency-sensitive paths, you can pay to keep a set number of environments initialized and ready. This trades the pure pay-per-use property for predictable latency, and it is the standard fix for cold-start-sensitive APIs.

  • One request per environment, not per process. Because concurrency is expressed as separate environments, a function does not need to be thread-safe in the way a long-running server does, which simplifies code. Some platforms, such as Cloud Run and newer function offerings, allow multiple concurrent requests per instance, which reduces cold starts and cost for I/O-bound workloads.

Execution Limits

Functions are bounded.

Typical constraints include a maximum execution time (15 minutes on AWS Lambda at the time of writing), a cap on memory, limits on request and response payload size, and limited ephemeral disk. A function also cannot accept inbound connections other than through its event source. On Lambda, the memory setting also determines CPU allocation, because CPU scales with memory.

These limits are the reason serverless is a poor fit for long-running jobs, large in-memory processing, and persistent connections, covered below.

Part 3: Event Sources and Composition

Triggers

Every function is attached to one or more event sources, and the nature of the source determines the invocation semantics, which matters more than most people expect.

  • Synchronous invocation. An API Gateway request, an application load balancer call, or a direct invoke waits for the function's response. Here the gateway is only the HTTP event source that turns a request into an invocation. Its wider role as the single entry point for client traffic is covered in Microservices Architecture. The caller sees errors and latency directly, and retries are the caller's responsibility.

  • Asynchronous invocation. Object storage events, SNS notifications, and EventBridge rules hand the event to a platform-managed queue, and the caller does not wait. The platform retries failed invocations automatically (twice by default in Lambda) and can route persistent failures to a dead-letter queue or a failure destination. A failure destination is a target, such as a queue or event bus, that receives a record of each failed event.

  • Poll-based invocation. For queues (SQS), streams (Kinesis, DynamoDB Streams), and Kafka, the platform runs pollers that read batches from the source and invoke your function with the batch. Scaling is tied to the number of shards (the partitions of a stream) or the queue depth, and error handling interacts with the source. A poison message, one that fails every time it is processed, can block a stream shard until it is handled. Retry limits, batch bisection (splitting a failed batch in half to isolate the bad record), and failure destinations prevent that.

Knowing which category a trigger belongs to determines what failure behavior you inherit, so it is one of the first things to check when designing a flow.

Composition: Choreography and Orchestration

A single function rarely does a whole job. Real workflows chain functions together. The two ways to coordinate them, choreography through events and orchestration through a central coordinator, are explained in Event-driven Architecture. What changes in serverless is who plays each role.

In choreography, the event sources connect the functions. A function writes a file to object storage, which triggers a second function, which publishes a message, which triggers a third. No function knows the whole flow, so debugging a failed flow means tracing events across triggers.

In orchestration, a managed workflow service such as AWS Step Functions, Azure Durable Functions, or Google Workflows is the coordinator. It defines steps, branches, parallel fan-out, retries with backoff, timeouts, and compensation on failure, and it holds the state of the process, which stateless functions cannot hold themselves. This is the right tool for multi-step business processes, long waits, and anything needing visible, auditable progress.

A key principle: do not chain functions by having one function synchronously call another and wait. While the second function runs, the first one waits idle and is still billed, so you pay for both functions during that wait. Synchronous chaining also compounds latency and failure, and it hides the dependency.

Use events or an orchestrator instead.

Part 4: State, Data, and Connections

Statelessness Is Mandatory

Because environments are ephemeral and concurrent invocations run in separate environments, a function cannot rely on local memory or disk for durable state.

All persistent state lives in external services: a database, object storage, a cache, or a workflow engine.

This is the same principle that makes any horizontally scaled service easy to run, enforced here by the platform rather than by convention.

The Connection Exhaustion Problem

This is the most common serious failure in serverless systems that use relational databases.

A traditional server keeps a pool of, say, 20 database connections shared by all its requests.

A serverless function scaled to 2,000 concurrent environments may each open its own connection, producing 2,000 connections against a database that supports a few hundred.

The database runs out of connection slots and starts refusing requests, even though the functions themselves are healthy.

There are standard remedies.

A connection pooler or proxy, such as Amazon RDS Proxy or PgBouncer, sits between the functions and the database and multiplexes many function connections onto a small number of real ones.

Databases built for this access pattern, such as DynamoDB, Firestore, and Aurora Serverless with its Data API, use HTTP-style request APIs rather than long-lived connections, so the problem does not arise. And reserved concurrency can cap how many environments of a function run at once, limiting the pressure on the database at the cost of throttling.

Data Tier Choices

Serverless pairs naturally with databases that scale the same way.

DynamoDB scales throughput on demand with no connection management.

Aurora Serverless scales compute capacity with load.

Object storage is effectively unlimited. Relational databases can be used, but they demand the pooling mitigation above and careful attention to concurrency.

Edge Functions

A growing variant runs functions at the network edge, as in Cloudflare Workers, CloudFront Functions, and Vercel and Deno edge runtimes. These run close to users in lightweight sandboxes rather than separate virtual machines. Most of them, such as Cloudflare Workers, use isolates, which are lightweight sandboxes inside one shared runtime process. They start in milliseconds, which largely eliminates the cold start concern, but they impose tighter limits on runtime, libraries, and execution time. They also sit far from a central database, so data access latency becomes the dominant design issue. Lambda@Edge is a different case. It runs standard Lambda execution environments in regional edge locations, so it still has normal cold starts.

Part 5: The Cost Model

What You Pay For

FaaS pricing is built from two meters: a charge per request and a charge for compute, measured as memory allocation multiplied by execution duration, typically in GB-seconds (one gigabyte of memory held for one second), billed in millisecond increments.

Managed services add their own meters: API Gateway per request, DynamoDB per read and write unit, Step Functions Standard workflows per state transition (Express workflows bill per request and duration), and data transfer.

The consequence is that cost tracks usage almost linearly, and tiny or intermittent workloads are nearly free.

The monthly bill for one function follows a simple formula:

Monthly cost = requests × price per request + requests × duration in seconds × memory in GB × price per GB-second

The prices in this lesson are illustrative, in the style of AWS Lambda pricing, which changes over time and varies by region. They are 0.0000167 per GB-second, before any free tier. A function called 1,000,000 times a month, running 100 milliseconds each with 0.5 GB of memory, uses 1,000,000 × 0.1 × 0.5 = 50,000 GB-seconds. That is about 0.20 for requests, roughly $1 a month. This is why serverless is an excellent default for prototypes, internal tools, webhooks, cron jobs, and low-traffic APIs.

The Crossover Point

The same linearity becomes a disadvantage at scale.

A steady, high-throughput workload keeps compute busy around the clock, and in that situation the per-millisecond premium of FaaS exceeds the cost of owning reserved capacity.

The same illustrative prices show where this happens. One environment with 1 GB of memory that stays busy for a 30-day month uses 30 × 86,400 × 1 = 2,592,000 GB-seconds, about 5.20 in request charges, for a total near $48.50 a month.

FaaS bills each concurrent environment separately, so a steady 200 requests per second at the same duration needs 20 environments and costs about 20 × 970 a month. A container or instance serves many concurrent requests on one bill. When requests are I/O-bound, meaning they spend most of their time waiting on a database or another service, one small always-on instance can often handle dozens of them at once. The break-even point is the load at which the monthly FaaS cost from the formula equals the monthly cost of the always-on capacity that serves the same load.

As a general tendency rather than a fixed law, a continuously busy workload is often several times cheaper on provisioned containers or instances than on functions. The exact crossover depends on the workload, but the principle is stable: serverless is cheapest when utilization is low or spiky, and most expensive when utilization is high and constant.

Teams also get surprised by secondary costs.

API Gateway can cost more than the functions behind it. Step Functions Standard workflows charge per state transition, so a loop with many iterations is expensive.

A recursive bug or an unbounded retry loop can generate a large bill very quickly, because the platform scales faulty code as readily as correct code. On AWS Lambda, recursive loop detection is on by default. It stops a loop through supported services, such as a function that writes back to the S3 bucket or SQS queue that triggers it, after about 16 invocations. Loops that pass through other services, such as a DynamoDB table, are not detected. This is why budgets, alarms, and concurrency caps are part of a responsible serverless design.

Memory as the Tuning Knob

On Lambda, the memory setting also controls CPU share.

A CPU-bound function given more memory usually runs faster. A higher-memory configuration costs the same when its run time falls in proportion to the added memory, and less when the run time falls even faster. Measuring across memory settings, rather than defaulting to the minimum, is a standard optimization.

Part 6: Reliability, Idempotency, and Observability

Retries Mean At-Least-Once Execution

Asynchronous and poll-based invocations are retried by the platform on failure, and event sources can deliver the same event more than once. This is the at-least-once delivery model, and Event-driven Architecture explains why a consumer must be idempotent under it. What serverless adds is that the retry is not code you write; the platform performs it. Any function behind an asynchronous or poll-based trigger must therefore produce the same outcome when it runs twice for one logical event.

The usual technique is an idempotency key. Derive a stable identifier from the event (a message ID, an order ID plus an action), and record it in a datastore with a conditional write the first time it is processed. Skip the work only when the key shows that an earlier run completed it.

Failure Handling Toolkit

Dead-letter queues and failure destinations capture events that exhaust the platform's retries on asynchronous and poll-based invocations, so they are not lost and can be inspected and replayed.

Timeouts must be set deliberately, with a function timeout shorter than the upstream caller's, to avoid wasted work.

Partial batch response lets a function report which records in a batch failed, so the platform does not retry the whole batch. On a queue, only the failed records are retried. On a stream, processing resumes from the first failed record. And circuit breaking and backoff protect downstream services from the retry storms that elastic scaling can produce.

Observability

A request may touch a gateway, three functions, a queue, and a database, and no single log file tells the story. The general remedy, a trace ID carried through every hop and stitched together by distributed tracing, is covered in Microservices Architecture. Serverless changes two things. There is no server to log into, so structured logs and traces are the only view you get, and they must be designed in from the start. The platform also exposes metrics that have no equivalent on a server, such as throttles, concurrency, queue age, and dead-letter depth, and each of them needs an alarm.

Part 7: Advantages and Limitations

Advantages

  • Minimal operational burden. No servers to patch, size, or scale, which lets small teams run large systems and focus on product logic.

  • Elastic scaling including scale to zero. Capacity tracks demand automatically, and idle systems cost essentially nothing.

  • Cost efficiency for variable workloads. Pay-per-use fits spiky, intermittent, and unpredictable traffic better than provisioned capacity.

  • Fast delivery. Managed building blocks and small deployable units shorten the path from idea to production.

  • Built-in availability. Major platforms, such as Lambda, run functions across multiple availability zones by default.

Limitations

  • Cold starts. Added latency on the first request to a new environment, which matters for latency-sensitive paths and can be mitigated by provisioned concurrency, smaller packages, and faster runtimes at extra cost or effort.

  • Execution limits. Time, memory, payload size, and no inbound connections rule out long-running jobs, large in-memory processing, and persistent connections such as WebSocket servers without help from managed gateway services.

  • Vendor coupling. Triggers, permissions, and event formats are provider-specific, so portability is limited, even though business logic itself can be kept portable with good structure.

  • Cost at sustained scale. High, constant throughput is often cheaper on provisioned infrastructure.

  • Harder local development and testing. Emulating cloud event sources, permissions, and managed services locally is imperfect, so teams rely on testing in real cloud environments.

  • Complex debugging of distributed flows. Event chains spread across many small components require disciplined tracing and correlation.

  • Downstream pressure. Unbounded concurrency can overwhelm databases and third-party APIs that cannot scale as quickly.

Part 8: When to Use It

Serverless is a strong fit for event-driven processing such as image resizing on upload, file ingestion, and stream processing. Strong fits also include APIs with variable or low traffic, scheduled jobs and automation, webhook receivers and integrations, backends of mobile and web apps with spiky load, and integration logic between managed services. It also suits prototypes and early-stage products, where avoiding operational work is worth more than optimizing unit cost.

It is a weak fit for steady, high-throughput services where provisioned capacity is cheaper, and for latency-critical paths that cannot tolerate cold starts without paying for provisioned concurrency. It is also a weak fit for long-running or heavy compute jobs beyond execution limits, for applications needing persistent connections or in-process state, and for systems whose strict portability requirements outweigh operational savings.

Many mature systems are hybrid: containers or instances for the steady core, with serverless handling bursty work, asynchronous processing, and integration logic.

This split is usually the right design, because it assigns each workload to the model whose cost and operational profile fits.

FAQs

Q: What is a cold start and how do you reduce it?

A cold start is the extra latency when a platform has to create a new execution environment for a function: allocating it, loading code, starting the runtime, and running initialization before handling the request. Ways to reduce it include using fast-starting runtimes such as Node.js, Python, or Go, keeping deployment packages small and trimming dependencies, and doing expensive initialization once outside the handler. On Lambda, SnapStart starts new environments from a saved snapshot of an already initialized one, and it supports recent Java, Python, and .NET runtimes. Provisioned concurrency keeps environments pre-warmed for latency-sensitive endpoints. Scheduled warming pings are a weaker, older workaround. Cold starts matter most on user-facing synchronous paths, and little for most asynchronous background work.

Q: What is the difference between serverless and containers?

Containers package your application and its dependencies, and you run them on infrastructure you or a managed service controls, usually paying for the running capacity whether or not it is busy. Serverless functions abstract the runtime entirely and charge per execution. Containers give you more control over runtime, long-running processes, networking, and portability. Serverless gives you less to manage and scale-to-zero billing, within platform limits. The categories blur. Cloud Run can scale containers to zero, so it meets the definition in Part 1, and Lambda supports container images. AWS Fargate removes server management but bills for running tasks, so it remains a managed container service.

Q: How do you handle long-running tasks in serverless?

Do not try to fit them inside one function. Break the work into smaller steps coordinated by an orchestrator such as Step Functions, with each step staying within the time limit and state held by the workflow engine. For naturally long compute, such as video transcoding or large batch jobs, hand the work to a service designed for it, such as AWS Batch, Fargate tasks, or a managed transcoding service, triggered by a function. For work that waits on humans or external systems, workflow engines support waiting for callbacks for days without consuming compute.

Q: How do you manage database connections from functions?

Avoid one connection per concurrent function. Use a connection pooling proxy like RDS Proxy or PgBouncer to multiplex many function connections onto a small database pool, choose databases with HTTP-based APIs and no connection limits such as DynamoDB, and use reserved concurrency to cap concurrent environments. Creating clients outside the handler lets warm environments reuse them, which cuts connection churn but does not lower the count, because each concurrent environment still holds its own connection. Connection exhaustion is the classic production incident of serverless plus relational databases.

Q: Is serverless always cheaper?

No. It is cheapest for low, intermittent, or spiky usage because you pay nothing while idle. For sustained high utilization, the premium per unit of compute makes provisioned instances or containers cheaper, sometimes by several times. Hidden costs also matter: API gateway fees, orchestration transition charges, data transfer, and observability volume. The right approach is to model the real request pattern, compare the crossover point, and revisit as traffic grows. Starting on serverless and moving a stable hot path to containers later is a common and sensible trajectory.

Q: How do you test and develop serverless applications locally?

Structure code so business logic lives in plain functions or classes with the handler as a thin adapter, then unit test the logic without any cloud dependency. Use local emulation tools such as AWS SAM, the Serverless Framework, or LocalStack for integration-style tests, while accepting that their fidelity is imperfect. For confidence in permissions, event shapes, and managed-service behavior, run tests against ephemeral real environments in the cloud, using infrastructure as code to create and tear them down. Treat the cloud as part of the test environment rather than trying to fully simulate it.

Q: Does serverless cause vendor lock-in?

To a degree. The business logic can be portable, but the surrounding triggers, identity and access management (IAM) permissions, event formats, and managed services are provider-specific, and rewriting those to move clouds is real work. Teams limit the exposure by keeping handlers thin and logic portable, using infrastructure as code, and accepting that deep use of managed services is the point of serverless and implies coupling. The honest framing is that lock-in is a trade you make in exchange for less operational work, and it should be a conscious decision weighed against the realistic likelihood and cost of migrating.

Q: How would you explain serverless in a system design interview?

Describe it as event-driven compute and managed services with no server management, automatic scaling to zero, and pay-per-use billing. Then show you understand the mechanics: functions run in short-lived, isolated environments that each handle one request at a time, cold starts add latency on new environments, and state must live outside the function. Name the pitfalls proactively: connection exhaustion on relational databases, idempotency under at-least-once delivery, execution time limits, and the cost crossover at sustained load. Finish with a judgment about fit: serverless for bursty, event-driven, and integration workloads, and containers or instances for steady, heavy, or latency-critical cores. That combination of mechanism and trade-off reasoning is what distinguishes a strong answer.

Key Takeaways

  • Serverless removes server management, not servers. The platform owns provisioning, scaling, and patching, and you pay for execution rather than capacity, with scale to zero as the defining property.

  • FaaS and BaaS together make a serverless application. Functions provide custom logic, and managed services provide authentication, data, storage, messaging, and routing without servers to operate.

  • Execution environments are ephemeral, isolated, and handle one request at a time. Cold starts occur when new environments are created, so put expensive initialization outside the handler and never rely on in-memory state surviving.

  • Trigger type determines failure semantics. Synchronous callers handle retries, asynchronous invocations are retried by the platform with dead-letter handling, and poll-based sources interact with batches and poison messages.

  • Coordinate through events or an orchestrator, do not chain. Use events for loose coupling and a workflow engine for multi-step processes, and never have one function synchronously wait on another.

  • Connection exhaustion is the classic failure. Thousands of concurrent environments can overwhelm a relational database, so use pooling proxies, connectionless databases, and concurrency caps.

  • Design for at-least-once execution. Retries and duplicate deliveries mean every side-effecting function must be idempotent, usually through an idempotency key claimed with a conditional write.

  • Cost grows linearly with use. Spiky and idle workloads are very cheap, while sustained high throughput is often cheaper on provisioned capacity, and runaway loops can scale a mistake into a large bill.

  • Observability must be designed in. Correlation IDs, distributed tracing, and alarms on queue age and dead-letter depth replace the ability to log into a server.

  • Hybrid is usually the mature answer. Keep the steady, latency-critical core on containers or instances, and use serverless for bursty work, asynchronous processing, and integration logic.

  • Evaluate serverless in a fixed order. Define the model, explain the execution mechanics, name the pitfalls, and close with a clear judgment on where it fits and where it does not.
