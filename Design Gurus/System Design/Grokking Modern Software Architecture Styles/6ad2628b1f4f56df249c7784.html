Key Takeaways

Know the Vocabulary

This lesson uses the terms below repeatedly. Read them once now and return here when a later section needs one.

  • Layer: A horizontal slice of the code with one technical job, such as handling HTTP or talking to the database.
  • Tier: A part of the system that runs on its own machines and talks to the other parts over the network. Which parts count as tiers is partly a convention, but a load balancer that only forwards requests between tiers is usually not counted as one.
  • Deployment topology: The map of which components run on which machines and which network paths connect them.
  • Presentation tier: The user interface the user interacts with, such as a browser, mobile app or desktop app, plus the web server that serves it. It is not the presentation layer, which is code inside the application tier.
  • Application tier: The application servers that run all of the business logic. It is the only tier allowed to connect to the data tier.
  • Data tier: The servers that store and manage persistent data, such as the database, the cache and the search index.
  • Thick client: A client application that runs business rules on the user's machine. A thin client, such as a web browser, only renders what the server sends.
  • Load balancer: A server that receives incoming requests and spreads them across several copies of an application.
  • TLS termination: Decrypting incoming HTTPS connections at one server, such as the load balancer, so that the servers behind it do not have to.
  • Stateless server: A server that keeps no user data in its own memory between requests, so any instance can handle any request.
  • Horizontal scaling: Adding more copies of an application on more machines; vertical scaling instead gives one machine more CPU or memory.
  • Connection pool: A set of open database connections that a server keeps and reuses, instead of opening a new connection for every query.
  • Security group: A set of cloud firewall rules that states which ports on a server accept traffic and from which sources.
  • Health check: An HTTP endpoint that the load balancer calls regularly to decide whether an instance should receive traffic.
  • Read replica: A copy of the database that streams every change from the primary and answers read queries.

Part 1: The Core Distinction Between N-Layer and N-Tier

Logical vs Physical Separation

N-Layer architecture is about code organization. The presentation layer, business logic layer, and data access layer are separated by code boundaries within one deployable artifact. Layers are a logical grouping of code. They are usually deployed together in one process, but the layer concept itself says nothing about deployment.

N-Tier architecture is about deployment topology. The presentation tier, application tier, and data tier are separated by network boundaries. Each tier usually runs on its own machines (at minimum, in its own process) and communicates with the other tiers over the network.

A system can have both.

A three-tier deployment (web server, app server, database server) where the app server is built with layered architecture internally uses both patterns simultaneously. The tier describes the deployment topology. The layer describes the code organization within each tier.

The two vocabularies share the word "presentation", so the table below states where each layer from the Layered (N-Layer) Architecture lesson runs.

Layer (code organization)Tier where it runs
Presentation layer (HTTP controllers, request parsing, authentication, response formatting)Application tier
Business logic layer (domain rules and services)Application tier
Data access layer (repositories and queries)Application tier
The database engine itself (PostgreSQL, Redis)Data tier
The user interface the user sees (browser, mobile app, or desktop app) and the web server that serves itPresentation tier

The presentation tier is therefore not the presentation layer. The layer is code inside the application tier; the tier is the user interface on the user's device, plus the web server that delivers it.

Why the Physical Separation Matters

Physical separation across machines creates properties that logical separation within one machine cannot provide.

  • Independent scaling. When the application tier is CPU-bound from business logic computation, add more application servers. The web tier is unaffected, but each new application server opens more connections and sends more queries to the data tier. When the data tier is I/O-bound from query volume, scale the database independently (read replicas, connection pooling). Each tier scales to its specific bottleneck.

  • Independent failure domains. A crash in the application tier does not crash the web tier or the data tier. The web tier can return a service unavailable response while the application tier recovers. An application crash does not corrupt the data already committed in the data tier, although a bug in the application tier can still write incorrect data.

  • Independent technology choices. The web tier runs Nginx. The application tier runs a Python Flask application. The data tier runs PostgreSQL. Each tier uses the technology best suited to its specific role.

  • Network-enforced security boundaries. The data tier can be placed in a private network segment with no public internet access. Only the application tier can reach it, and only on the specific database port. Physical network separation provides security boundaries that logical layer separation cannot enforce.

These properties have a cost. Every tier boundary adds a network round trip, plus the work of converting each request and response to bytes and parsing them on the other side. As a rough guide, one round trip inside a data center takes 0.5 to 1 millisecond. A request that goes from the load balancer to the application tier and then makes 5 database queries pays 6 round trips, about 3 to 6 milliseconds, in addition to the time the business logic itself takes. Inside one process, a call from one layer to the next is a function call that takes nanoseconds.

The Two Variants

Thick client (fat client): The client tier contains significant application logic. A desktop application (a Point of Sale system, an accounting application, an inventory management client) runs business rules on the user's machine and communicates with a server tier that primarily handles data storage and retrieval. The server tier is essentially a database server with some data management logic.

Thin client: The client tier contains minimal logic (a web browser rendering HTML). All business logic and data management happens on the server tier. The server tier combines the application logic and data access in one deployment. The client sends requests and renders responses.

Where Two-Tier Is Used

Two-tier architecture is appropriate for internal enterprise applications with a controlled user base: accounting software used by 50 employees, a legacy ERP system, a manufacturing floor management application, a medical records system in a single clinic. The user base is known, the network is controlled, and the deployment can tolerate the limitations of two-tier.

The limitations of two-tier:

When business logic runs on the client (thick client), updating the logic requires deploying updated software to every client machine. A change to a tax calculation rule means updating the application on 200 employee workstations. This is operationally expensive and creates version inconsistency during the rollout window.

When business logic runs on the server (thin client two-tier), the server tier becomes a combined application-plus-database tier that cannot scale its application logic independently from its database.

Both limitations are addressed by moving to three-tier. The client stays as tier 1, now called the presentation tier, and the server splits into an application tier and a data tier.

Part 3: The Three-Tier Model

What It Is

The three-tier model is the most common N-Tier configuration in production systems. It physically separates three distinct tiers: the presentation tier (the user's browser, mobile app, or desktop app, plus the web server that serves it), the application tier (app server), and the data tier (database server). A server that accepts requests on behalf of the application servers and forwards them to one of them (a load balancer or reverse proxy, such as Nginx or HAProxy) usually sits between the presentation tier and the application tier. It is infrastructure in front of the application tier, not a tier of its own.

Tier 1: The Presentation Tier

The presentation tier is the user interface: the browser, mobile app, or desktop app the user interacts with, plus the web server that serves it. Together with the load balancer described below, it is the publicly accessible entry point and handles everything that happens before a request reaches business logic.

Primary responsibilities:

  • User interface rendering. The browser or app displays pages, collects input, and sends requests toward the application tier. The web server delivers the HTML, CSS, and JavaScript that the browser renders.

  • Static asset serving. HTML, CSS, JavaScript, images, and fonts are served directly by the web server without reaching the application tier. Nginx serves static files at tens of thousands of requests per second from disk or memory. Sending these requests to the application tier would waste application server CPU on file I/O that the web server handles orders of magnitude more efficiently.

  • Connection management. HTTP keep-alive connections, connection pooling toward the application servers, and connection limits are all managed at the web server.

Infrastructure in front of the application tier:

Between the presentation tier and the application tier sits a load balancer and reverse proxy (Nginx, HAProxy, AWS ALB), often with a CDN ahead of it. This infrastructure is not a tier of its own: it holds no user interface and no business logic. The same Nginx process often serves the presentation tier's static assets and proxies dynamic requests to the application tier. That is why many diagrams draw it on the boundary between the two.

  • TLS termination. The load balancer decrypts incoming HTTPS connections. Traffic from the load balancer to the application tier travels over the internal network, which may or may not be encrypted, depending on the security requirements of the deployment.

  • Request routing. The load balancer distributes incoming requests across multiple application tier instances. It uses a routing algorithm (round-robin, least connections, IP hash) to select which application server instance handles each request.

  • Rate limiting and DDoS protection. A web application firewall (WAF), rate limiting by IP address, and bot detection happen at the load balancer or CDN before requests reach the application tier. A distributed denial-of-service (DDoS) attack floods a service with traffic from many machines at once, and a WAF filters out malicious HTTP requests, such as SQL injection attempts.

What the presentation tier does not do:

Execute business logic. Rendering a user's profile page is presentation tier work. Deciding what the user is allowed to see on their profile page is application tier work.

Query the database. The presentation tier has no database connection, and neither does the load balancer in front of the application tier. Neither can directly access the data tier.

Tier 2: The Application Tier

The application tier is where all business logic executes. It is the tier that changes most frequently as the product evolves. It reads from and writes to the data tier, calls external services, applies business rules, and returns results to the presentation tier.

Primary responsibilities:

  • Business logic execution. The application tier validates inputs against business rules, enforces domain constraints, orchestrates multi-step operations, and applies security rules (authorization, not just authentication).

  • Session management. User sessions are typically maintained by the application tier. Session data is stored in the data tier (a shared Redis instance or a database table) rather than in the application server's memory, so any application server instance can handle any request from any user.

  • External service integration. Calls to payment processors, email services, SMS providers, third-party APIs, and other external systems originate from the application tier.

  • Data transformation. The application tier transforms raw database records into domain objects that the business rules operate on, and transforms those objects into the format it returns to the presentation tier.

Horizontal scaling of the application tier:

Because session data lives in the shared data tier rather than in individual application server memory, all application server instances are stateless. Any instance can handle any request. The load balancer distributes freely, with no need for sticky sessions (routing every request from one user to the same server). Sticky sessions can spread load unevenly, and when sessions live in server memory, a server failure logs out every user pinned to that server. Adding an application server instance immediately increases capacity.

Tier 3: The Data Tier

The data tier stores, retrieves, and manages all persistent data. It is the most critical tier for durability and consistency. A failure in the presentation or application tier is recoverable without data loss. A failure in the data tier can mean data loss.

Primary responsibilities:

  • Persistent storage. All data that must survive a server restart lives in the data tier: user accounts, order records, product catalogs, transaction histories.

  • Query execution. The database server executes queries, uses indexes, manages query plans, and returns result sets to the application tier.

  • Transaction management. ACID transactions are enforced by the data tier. ACID stands for atomicity (all steps apply or none do), consistency (every constraint still holds afterward), isolation (concurrent transactions do not see each other's partial work), and durability (committed data survives a crash). A multi-step operation that must be atomic (debit account A and credit account B together or not at all) is wrapped in a database transaction.

  • Data integrity enforcement. Foreign key constraints, unique constraints, check constraints, and not-null constraints are enforced by the database server regardless of what the application tier sends.

The data tier is typically multiple components:

A relational database (PostgreSQL, MySQL) for structured transactional data.

A cache (Redis, Memcached) for frequently accessed data that does not need to be read from the relational database on every request.

A search index (Elasticsearch, OpenSearch) for full-text search and complex faceted queries.

A blob store (S3, Google Cloud Storage) for binary files (images, documents, videos).

Each of these is a separate component of the data tier, each running on its own infrastructure.

Part 4: The Four-Tier Model

What the Fourth Tier Adds

A CDN is not normally counted as a tier, but some teams treat it as a fourth tier, which they call the delivery tier. In this four-tier model, the delivery tier sits between the user's browser or app and the load balancer. The delivery tier handles global traffic distribution, CDN caching, and edge-level processing before requests reach the load balancer and web servers.

The delivery tier serves cached content (static assets, cacheable API responses) directly from edge nodes geographically close to the user without reaching the web servers or the application tier. A user in Tokyo accessing a US-based application receives cached static assets from a Tokyo edge node rather than waiting for a round trip across the Pacific.

For content that cannot be cached (dynamic, user-specific responses), the delivery tier routes the request to the nearest load balancer and acts as a reverse proxy.

Five-Tier and Beyond

Applications with complex microservices architectures sometimes add an API gateway between the presentation tier and the application tier, and some teams count it as a fifth tier. Unlike the load balancer, which spreads requests across copies of the same application, the gateway checks each caller and chooses which service handles each request. It holds no business logic, but it handles cross-cutting concerns (authentication, rate limiting, request routing to specific microservices, response aggregation) as a separate physical deployment. A service mesh is not a tier. It usually runs as small proxies next to each service instance inside the application tier and handles the traffic between services.

The number of tiers in practice is determined by the specific concerns that need to be isolated for independent scaling, independent operation, or security boundary enforcement.

Part 5: Inter-Tier Communication

From the Presentation Tier to the Load Balancer

Traffic from the user's browser or app travels over HTTPS (HTTP over TLS) to the load balancer, which terminates the TLS connection. All traffic between the user's device and the data center is encrypted.

From the Load Balancer to the Application Tier

Traffic from the load balancer to the application tier travels over the internal network. The protocol depends on the application:

HTTP or HTTPS for web applications where the application tier exposes HTTP endpoints.

gRPC over HTTP/2 for high-performance internal communication, common in microservices deployments where the application tier exposes multiple services.

The internal network traffic may or may not be encrypted depending on the deployment's security requirements. On cloud platforms, internal traffic within a VPC (virtual private cloud, a private network that the provider isolates for one customer) typically travels on the private network and may not be encrypted between tiers. Zero-trust security models, which trust no network by default, encrypt all traffic regardless of network location.

From Application Tier to Data Tier

Traffic from the application tier to the data tier uses database-specific protocols over TCP:

PostgreSQL wire protocol (port 5432) for PostgreSQL.

MySQL wire protocol (port 3306) for MySQL.

Redis Serialization Protocol (RESP) over TCP (port 6379) for Redis.

The data tier must be on a private network segment that is not accessible from the internet. Only the application tier should be able to reach the data tier. This is enforced at the network level through security groups, firewall rules, or VPC configuration.

Part 6: Scaling Each Tier

Scaling the Presentation Tier

The user interface runs on each user's own device, so the server-side part of the presentation tier is the web servers. The web servers and the load balancer in front of the application tier are both stateless (they only serve static files and route and proxy requests) and scale horizontally with no coordination required. Add more web server instances behind a DNS load balancer or an anycast IP (one IP address announced from many locations, so each user reaches the nearest one). A cloud-managed load balancer (AWS ALB, Google Cloud Load Balancing) handles health checks and traffic distribution automatically.

Auto-scaling: when CPU utilization on the web servers exceeds a threshold (unusual, since Nginx uses very little CPU for proxying, except for TLS handshakes), add instances. The trigger for scaling the web servers is typically connection count or request rate, not CPU.

Scaling the Application Tier

The application tier is the primary scaling target for most production systems. Adding application server instances increases request processing capacity roughly linearly (assuming the data tier is not the bottleneck).

The application tier is stateless by design (session data in the data tier). Any instance can handle any request. Auto-scaling groups add instances during peak traffic and remove them during low traffic. A health check endpoint (a simple HTTP endpoint that returns 200 if the instance is healthy) allows the load balancer to route traffic only to healthy instances.

Scaling the Data Tier

The data tier is the hardest tier to scale because it is stateful. Scaling strategies:

Read replicas. Add PostgreSQL replicas that stream changes from the primary. Route read queries (SELECT) to replicas and write queries (INSERT, UPDATE, DELETE) to the primary. Read capacity scales roughly linearly with replica count, until write volume or replication lag limits it, because every replica must also apply every write from the primary.

Connection pooling. PgBouncer between the application tier and PostgreSQL multiplexes many application connections onto fewer database connections. This scales the number of application instances that can connect to the database without exhausting the database's connection limit.

Caching. Redis caches frequently read data. Application tier instances read from Redis before querying the database. A high cache hit rate dramatically reduces database read load.

Vertical scaling. The database server gets larger hardware (more CPU, more RAM, faster storage). This has a ceiling but is the simplest scaling step for moderate traffic growth.

Sharding. Distribute data across multiple database instances based on a shard key. Each shard handles a subset of the data and therefore a subset of the queries. Sharding adds significant operational complexity.

Part 7: Fault Tolerance in N-Tier Architecture

Presentation Tier Failure

If one web server instance fails, the load balancer detects the failure through health checks and stops routing traffic to it. Other instances absorb the traffic. Two web server instances behind health-checked load balancing survive one instance failure with little user-visible impact, as long as the remaining instance can carry the full load. Only the requests in flight on the failed instance, or sent to it before the health check notices, fail.

Running the load balancer as a managed service (AWS ALB, Google Cloud Load Balancing) makes it inherently redundant. The cloud provider operates the load balancer infrastructure with multiple availability zones.

Application Tier Failure

If one application server instance fails, the load balancer (in front of the application tier) detects the failure and routes around it. Other instances continue processing requests. Auto-scaling replaces the failed instance.

A failed application tier instance does not affect the data tier. The database continues accepting connections from healthy application instances.

Data Tier Failure

A primary database failure is the most serious failure in an N-Tier system. All application tier instances lose their database connection and cannot process requests that require data persistence.

Mitigation: run the database primary with a hot standby in a different availability zone. When the primary fails, automatic failover promotes the standby to primary. Managed database services (AWS RDS Multi-AZ, Google Cloud SQL HA) handle this automatically. AWS documents RDS Multi-AZ failover as typically taking one to two minutes. Treat that figure as a rough guide, since the actual time depends on the provider, the database engine, and the workload.

A Redis cache failure is less critical if the application tier is designed to read from the database whenever the cache misses or does not respond. The database must then absorb the full read load that the cache was serving. Unless the database has capacity for that load, the cache outage turns into a database overload.

Sessions are a different case. When session data lives in Redis, as in the application tier handler in Part 3, a Redis failure makes every request that needs a session fail. A session store therefore needs replication and automatic failover, like the database, or the sessions can be kept in a database table instead.

Part 9: When to Use N-Tier Architecture

Use It When

  • The application serves public internet traffic. Any application accessible from the internet benefits from the security boundary enforcement that tier separation provides. The database must not be directly accessible from the internet. N-Tier architecture enforces this separation.

  • Components have different scaling requirements. If the application tier is consistently CPU-bound while the web servers are idle, tier separation allows scaling only the application tier. A single-tier deployment scales everything together.

  • Independent deployment of tiers is valuable. Updating the application tier's business logic without restarting the web servers (the presentation tier continues serving cached static assets during app tier deployments) is simplest with physical tier separation. A single-tier deployment can still update without downtime through a rolling deployment, which replaces instances one at a time behind the load balancer.

  • Compliance or security requirements mandate separation. PCI DSS, the card payment industry's security standard, requires that systems storing card data are not directly reachable from the internet. HIPAA and SOC 2 do not prescribe tiers, but network isolation is a common way to meet their controls. N-Tier architecture with the data tier on a private network segment meets the PCI DSS requirement and supports the other two.

  • The team has the operational capacity to manage multiple deployments. Each additional tier is a separate deployment with its own monitoring, logging, scaling configuration, and failure modes. A two-engineer startup may not have the capacity to operate three separate tiers well.

Avoid It When

  • The application is a prototype or early-stage product. A single-server deployment usually handles the traffic of an early-stage product. The operational overhead of three separately managed tiers is not justified by the scale. Even so, a prototype that serves internet traffic should keep the database off that server from the start, in a managed database service on a private subnet.

  • The development team is very small. Two or three engineers often cannot effectively monitor, scale, and operate three separately deployed tiers while simultaneously building product features. A well-configured single server with logical layer separation serves until scale demands physical separation.

  • All components scale identically. If adding capacity always means adding capacity to all components simultaneously, tier separation provides no scaling benefit over a single-tier deployment with multiple instances.

FAQs

Q: What is the difference between N-Tier architecture and N-Layer architecture?

The distinction is physical versus logical separation. N-Layer architecture organizes code into logical layers within one deployable unit. The layers are usually deployed together in one process, but the layer concept itself says nothing about deployment. Changing a layer means changing code; the deployment topology stays the same. N-Tier architecture physically separates components onto different machines or processes that communicate over a network. Each tier is independently deployed, independently scaled, and independently maintained. A three-tier system has three separate deployments. A three-layer system has one deployment. Most production applications use both: an N-Tier deployment topology where each tier is internally organized using N-Layer code structure.

Q: How many tiers should an application have?

The right number of tiers is the number that matches the application's specific requirements for security isolation, independent scaling, and operational separation. Three tiers (presentation, application, data) is the most common configuration and the right starting point for most web applications. Add a delivery tier (CDN) when geographic distribution or caching at the edge reduces latency or cost. Add additional tiers when specific components have fundamentally different scaling requirements, technology choices, or security isolation needs. More tiers mean more operational complexity. Add tiers because specific requirements demand the separation, not because more tiers sound more scalable.

Q: Can the web server and the application server run on the same machine?

Yes, and this is a common starting point for applications that are not yet at the scale where separate servers are justified. Running Nginx and a Python application server on the same machine puts the server side of three tiers onto two machines. Nginx handles TLS termination and static files. The Python application handles business logic. The database is on a separate server. This configuration is operationally simpler than full three-tier separation while still providing the most important separation: the database on a private server not accessible from the internet. As traffic grows and the application tier's CPU becomes the bottleneck, the application tier can be moved to dedicated servers without changing the architecture. Nginx stays on the original server as the load balancer; the application tier scales horizontally onto new servers.

Q: How does N-Tier architecture handle database connection limits?

Each application tier instance maintains a connection pool to the database. The pool holds a configurable number of open connections. With many application tier instances, the total number of open connections grows with the number of instances. A database server has a maximum connection limit (PostgreSQL defaults to 100). With 20 application server instances each holding a pool of 20 connections, the total is 400 connections, which exceeds PostgreSQL's default. The solution is a connection pooler (PgBouncer) deployed as a component of the data tier. Application tier instances connect to PgBouncer. PgBouncer maintains a smaller number of actual connections to PostgreSQL and multiplexes many application connections onto them. In transaction pooling mode, PgBouncer assigns a database connection to an application connection only for the duration of one transaction. 1,000 application connections can share 50 actual database connections with minimal latency overhead.

Q: How do you handle database schema migrations in an N-Tier system with multiple running application instances?

Use the expand, migrate, contract pattern, so that the schema stays compatible with both the old and the new application code at every step of the rollout. The Monolith Architecture lesson walks through the pattern step by step.

Q: Is N-Tier architecture compatible with microservices?

Yes. Microservices change how the application tier is split, not the tiers around it. The application tier holds many services, the API gateway from Part 4 routes requests to them, and each service keeps its own database in the data tier. The Microservices Architecture lesson covers that decomposition.

Q: How does N-Tier architecture relate to the OSI model?

The OSI model splits network communication into seven protocol layers: physical, data link, network, transport, session, presentation, and application. N-Tier architecture describes which machines run which parts of an application. The confusion comes from the shared names. The OSI presentation layer handles data formats and encryption, and the OSI application layer holds the protocols that programs use directly, such as HTTP. Neither is the presentation tier or the application tier. Every tier sends and receives data through the full OSI stack, so an HTTP call from the load balancer to the application tier passes through all seven layers on both machines.

Q: What is the security advantage of N-Tier architecture over a single-tier deployment?

The primary security advantage is network-level isolation of the data tier. In a single-tier deployment (all components on one server), a vulnerability in the web-facing code potentially gives an attacker access to the database. In a three-tier deployment, the database is on a separate server in a private network that the internet cannot reach directly. An attacker who exploits a web-facing vulnerability gains access to the web server or load balancer but cannot directly connect to the database. They must also compromise the application tier, which is behind a security group that only allows connections from the load balancer. This defense in depth, where an attacker must break through several barriers in turn, is why PCI DSS requires that systems storing card data are not directly reachable from the internet. HIPAA and SOC 2 do not prescribe tiers, but network isolation is a common way to meet their controls. Logical layer separation within a single server does not provide this protection. The operating system isolates processes from each other, but an attacker who compromises the server can read its files and credentials, including the database password.

Key Takeaways

  • N-Tier architecture physically separates components onto different machines or processes connected by a network. N-Layer architecture logically separates code within one deployed unit. Both patterns are often used together: N-Tier deployment topology with N-Layer internal code organization.

  • The three-tier model (presentation tier, application tier, data tier) is the most common configuration in production web applications. It provides independent scaling, failure isolation, and security boundary enforcement between tiers.

  • The presentation tier is the user interface (browser, mobile app, or desktop app) plus the web server that serves it. The load balancer and reverse proxy in front of the application tier handle TLS termination, load balancing, and request routing. Neither executes business logic, and neither has a database connection.

  • The application tier executes all business logic and is the primary scaling target. It is stateless by design (session data in the data tier) so any instance can handle any request and instances can be added or removed freely.

  • The data tier stores all persistent state. It is the hardest tier to scale and the most critical for durability. Physical network isolation of the data tier from the internet is the primary security benefit of N-Tier architecture.

  • Each tier is independently scalable. The application tier scales horizontally by adding stateless instances behind the load balancer. The data tier scales through read replicas, connection pooling, and caching. Each tier scales separately to its own bottleneck, but scaling one tier changes the load on the tier behind it.

  • Inter-tier communication must have explicit timeouts. Every call across a tier boundary is a network call that can fail or be slow. Timeouts prevent slow downstream tiers from cascading failures upstream by holding connections open indefinitely.

  • The data tier must be on a private network. Only the application tier should be able to reach the data tier. This network-level isolation is enforced through security groups and firewall rules. It is the primary security advantage of N-Tier architecture over single-tier deployments.

  • N-Tier and microservices are compatible and frequently combined. The N-Tier topology describes the macro deployment structure. Microservices describes how the application tier is internally decomposed. A production system commonly uses both simultaneously.

  • In a system design interview, describe the tier boundaries and explain what each tier is forbidden from doing (presentation tier has no database connection, data tier has no internet access). Then name the communication protocol between each pair of tiers, explain how each tier is independently scaled, and describe the failure mode and recovery mechanism for each tier. That level of specificity demonstrates operational understanding beyond naming the pattern.
