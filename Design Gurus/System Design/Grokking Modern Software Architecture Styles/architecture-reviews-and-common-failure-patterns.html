Key Takeaways

Know the Vocabulary

This lesson uses the terms below repeatedly, so read them once now and return here when a later section needs one.

  • Architecture review: A structured examination that compares a running system's structure with its requirements and produces a ranked list of findings.
  • Main requirement: The one measurable target a review is run to protect, such as a checkout p95 under 800 ms at the dinner peak.
  • Finding: One problem a review records, with its evidence, its effect on the main requirement and its cost to fix.
  • Change coupling: The tendency of two files or modules to be changed in the same commits again and again.
  • Change lead time: The time from a code change being committed to that change running in production.
  • Tangled responsibilities: A module, class or function that does several unrelated jobs, or a piece of another module's job, so changes made for different reasons edit the same code.
  • Dependency cycle: A chain of dependencies that leads back to its starting part, such as Orders and Payments each importing the other.
  • Controller: A function or class in the presentation layer that handles one kind of request, such as creating an order.
  • Cross-boundary write: A write by one module to data that another module owns, which skips the owner's rules.
  • Chatty interaction: An exchange that needs many small calls or queries to complete one operation, where one larger call would do.
  • Coordinated release: A release in which two or more parts must be deployed together, or in a fixed order.
  • Unnecessary abstraction: An interface, class or layer with one implementation, no planned second one and no test that replaces it.
  • Architecture test: An automated test that fails when the code breaks an accepted architecture decision.

The food-delivery app now has 14 engineers, and next quarter the company launches in two new cities. Each city needs its own delivery-fee rules, which sounds like a small request. Over the last ten fee changes, however, the median change took 9 days and touched 7 files in 4 modules. Six of the ten also needed two releases in a fixed order.

The head of engineering asks for an architecture review before anyone proposes a redesign. The question is which problems slow down fee changes, what each costs to fix, and which smallest change brings a fee change down to 2 days.

Part 1: Planning a Review Around One Main Requirement

An architecture review compares the structure of a running system with the requirements it must meet. Its output is a ranked list of findings and one recommendation. Without a stated requirement, a review tends to return 30 or 40 complaints with no way to weigh them.

The diagram below shows the six steps of a review and what each step produces. This Part covers step 1, Part 2 covers steps 2 to 4, and Part 3 covers steps 5 and 6.

Step 1 names the target, and it has three parts. The first is to write down the main requirement, the one measurable target that the review protects.

In the fee review, a change to one city's fee rules must reach production within 2 working days, with one backend release and no app release. That statement names a quantity, a scope and a condition that anyone can check later. The Quality Attributes lesson explains how to turn a quality into a target like this one.

The second part is to limit the scope to the workflows the requirement touches: the fee calculation, checkout and the Customer app's fee estimate. For a system of this size, one reviewer with 2 to 4 hours from each module owner can finish in 3 to 5 working days (illustrative).

The third part is to agree on what counts as a finding. A finding is one problem, with its evidence, its effect on the main requirement and its cost to fix. A problem without evidence is an opinion, and the report leaves it out.

Part 2: Collecting Evidence: What to Read, Measure and Ask

Evidence comes from three sources: the documents and code, measurements, and the people who change the system.

What to Read

Start with the diagrams and decision records, because they state the intended structure. Then read which tables each module owns, and finally the code of each workflow in scope.

Note every place where the code differs from that structure. In the fee review, the fee formula sits in the place-order handler instead of in the Orders business logic. A second copy sits in the handler for phone orders that support agents enter in an internal tool, a third runs inside the Customer app, and Menu computes a surcharge for large items.

What to Measure

The Coupling, Cohesion, and Dependencies lesson names three checks for coupling: imports between modules, files that change together, and cycles in the import graph. A review turns those checks, and a few more, into numbers. The table below lists each signal, its source and the fee review's value (illustrative figures).

Change coupling is usually the most useful signal for a changeability requirement, because it measures what past changes actually cost. A short script over the output of git log --name-only counts module pairs over 6 months of commits.

What to Ask

Interviews find what code and numbers hide. Ask about recent, specific events, because people remember those more accurately than their general habits. Five questions cover most of it:

  1. When you last changed a fee rule, which files did you edit, and why?
  2. Which of your last five releases waited for another release?
  3. Which code do you avoid changing, and what happened the last time?
  4. Which other module's tables does your code read or write?
  5. Which rule exists in more than one place, and do the copies agree?

Each answer should lead to evidence, such as a commit or a line of code.

Part 3: Ranking Findings by Effect and Cost to Fix

Each finding gets two scores: its effect on the main requirement and its cost to fix. The effect is how much of the gap between today's value and the target the finding explains: 0 for none, 1 for under a quarter, 2 for a quarter to a half, and 3 for more than half. The cost is the engineer-days for the smallest fix, including any coordinated release.

The ranking rule has three parts. First, order the findings with an effect above 0 by effect, with the cheaper fix first when two effects are equal. Second, recommend the shortest list from the top that is expected to meet the target. Third, list the findings with an effect of 0 below them, ordered by their own risk, such as wrong charges before slow pages. An effect-0 finding never enters the recommendation, however serious it is.

The table below ranks the fee review's findings (illustrative estimates). The last row is a module owner's proposal from the interviews.

The estimated lead time is then about 1.5 days, including the half day that the cycle adds, so finding 3 is not needed. The next three fee changes test that estimate.

Part 4: Failure Patterns Inside the Code

Parts 4 and 5 cover seven failure patterns: structural problems that reviews find in many codebases. The four patterns in this Part are visible in the source code alone: in one module, in one handler, or in the imports between two modules.

Tangled Responsibilities

What it looks like. The Coupling, Cohesion, and Dependencies lesson showed both forms of low cohesion: the common module with four unrelated jobs, and a fee rule split across Orders, Menu and the Customer app. A review usually meets the second form as a part that has taken over a piece of another part's job. In the fee review, Menu computes the large-item surcharge, so Menu publishes dishes and also prices deliveries.

How to detect it. Apply that lesson's cohesion test as a count: sort a module's recent commits by the business area they served. Of Menu's last 40 commits, 31 changed dishes, prices or hours, and 9 changed the surcharge.

What it costs. A change to one job edits the same code as changes to an unrelated job, so it needs both teams' reviewers and both test suites. In the fee review, 70 percent of fee commits also touched Menu.

The smallest fix. Move only the piece that the main requirement touches into the module that owns its job. The surcharge moves to orders/pricing.py, and Menu keeps publishing each dish's size. Other tangled code, such as common, stays where it is, because moving it would not bring the fee target closer.

Cyclic Modules

What it looks like. The Coupling, Cohesion, and Dependencies lesson showed how a cycle between Orders and Payments forms and what it costs. Here, Payments imports Orders to read an order's fee when it computes a refund, while Orders imports Payments to charge the card.

How to detect it. Draw the import graph with a tool such as pydeps and list every cycle. A second signal is a Payments test that needs Orders fixtures.

What it costs. Every fee change runs the Payments tests and needs a Payments reviewer, adding about half a day.

The smallest fix. Remove one import with one of that lesson's three methods. For refunds, Orders passes the fee amount to Payments, so Payments no longer imports Orders. Then add an architecture test, such as an import-linter contract that forbids payments from importing orders, so the cycle cannot return unnoticed.

How to detect it. Search the handlers for business constants such as 199 and 50 and for arithmetic on money, and count the hits per handler. The same constant in two handlers usually means two copies of one rule.

What it costs. Copies of a rule tend to stop agreeing over time. The phone-order handler charges for the exact distance instead of every started kilometer. A 3.2 km order therefore costs 3.59 dollars by phone and 3.99 dollars in the app. Each new entry point copies the rule again.

The smallest fix. Move the rule into Orders and make every handler call it. With one entry per city, a new city becomes one line in FEE_RULES, which is what the main requirement needs. The code below shows the rule in its own module and the handler calling it.

How to detect it. Count the implementations of each interface, including test fakes; one implementation and no fake marks a candidate. Then count the files touched per change in the module.

What it costs. Each change edits more files: adding a calorie count to dishes touched 6 files in Menu. The layers also hide cost, because a call to menu_manager.get_dish() does not show that it runs a query.

The smallest fix. Remove the forwarding layers and keep a plain class with its dependencies passed in. Keep an interface where a second implementation or a test fake exists, such as the payment gateway in the Coupling, Cohesion, and Dependencies lesson.

Part 5: Failure Patterns at Boundaries and in Releases

The three patterns in this Part live between modules or between deployables, so their cost appears only when one part uses or releases with another.

Cross-Boundary Writes

What it looks like. The Coupling, Cohesion, and Dependencies lesson showed Dispatch reading the orders table. Writing to it is worse, because a write skips the rules that the owner applies to its data. Here, Dispatch sets an order's status to courier_assigned with its own SQL.

How to detect it. List which module owns which tables, then search for INSERT, UPDATE and DELETE statements on each table. In PostgreSQL, a database role per module with write grants only on its own tables turns each such write into an error.

What it costs. Orders allows courier_assigned only after ready, and Dispatch's statement skips that check. In the month before the review, Dispatch assigned couriers to 4 canceled orders (illustrative). Orders also cannot change that table without breaking Dispatch.

The smallest fix. The owner offers a command that applies its rule, and the writer calls it. The code below shows the direct write, the command Orders adds, and Dispatch's new call.

// dispatch/Matching.java (before): one Accounts query per candidate courier
static Candidate pickCourier(AccountsClient accounts, List<Candidate> candidates, boolean needsCar) {
    List<Candidate> eligible = new ArrayList<>();
    for (Candidate candidate : candidates) {

        if (courier.isActive() && (courier.hasCar() || !needsCar)) {

        }

}
// dispatch/Matching.java (after): one call that takes the whole list
static Candidate pickCourier(AccountsClient accounts, List<Candidate> candidates, boolean needsCar) {
    List<String> ids = candidates.stream().map(Candidate::courierId).toList();
    Map<String, Courier> couriers = accounts.getCouriers(ids);  // one query, returns a map keyed by id
    List<Candidate> eligible = new ArrayList<>();
    for (Candidate candidate : candidates) {
        Courier courier = couriers.get(candidate.courierId());
        if (courier.isActive() && (courier.hasCar() || !needsCar)) {
            eligible.add(candidate);
        }
    }
    return nearest(eligible);
. . . .

How to detect it. Count the queries or calls per request in traces, and compare the count with the number of items the request handles. A count that grows with the items means a call inside a loop.

What it costs. Dispatch makes about 120 matches per minute at the dinner peak, one for each new order, so the loop sends about 6,000 Accounts queries per minute (120 times 50) where 120 would do. Each query also takes a database connection from the pool, and between separate services each call adds network time and a chance of failure.

The smallest fix. Add one operation that takes a list and returns everything the caller needs, as get_couriers does above.

Coordinated Releases

What it looks like. In the food-delivery app, coordinated releases appear between the backend and the apps. Because the Customer app computes its own fee estimate, a change to the fee formula needs a backend release and then an app release. App store review usually adds 1 to 2 days.

How to detect it. Count the changes in the release log that touched more than one deployable. In the fee review, 6 of the last 10 fee changes needed both releases.

What it costs. The change lead time becomes the slowest part's lead time plus the wait between releases. Old app versions stay on phones for months, as the What Software Architecture Is lesson noted, so their users see wrong estimates. Between services, this pattern becomes the distributed monolith that the Microservices Architecture lesson describes.

The smallest fix. Remove the reason the parts change together. The backend offers a fee estimate endpoint and the app calls it, so one last app release ends the coupling. When a data contract must change, add the new field first. Remove the old one only when under 2 percent of requests come from app versions that read it.

Part 6: Practice Review: Slow Checkout at the Dinner Peak

Several months later, the checkout screen has become slow. The request that loads it prices the cart and fetches the customer's saved cards from the payment provider, before the customer taps Place Order. Its p95 latency between 6 and 9 in the evening has reached 2.4 seconds, and about 1 in 8 customers leave without paying (illustrative). The main requirement for this review is a checkout p95 under 800 ms at the dinner peak within 4 weeks, with no change to how customers pay.

The reviewer's notes list six observations:

  1. Checkout calls menu_manager.get_dish() and is_available() for each cart item and get_option_price() for each option. In a trace of one checkout at the p95, the cart has 6 items with 3 options each, which makes 30 queries (6 dishes, 6 availability checks and 18 option prices). They take 1,800 ms, about 60 ms each, because each waits for a free database connection. The call that fetches saved cards from the payment provider takes 420 ms, and everything else 180 ms.
  2. Every Menu call passes through MenuManager, MenuServiceInterface and MenuServiceImpl, and no test replaces the interface.
  3. Orders and Payments still import each other, the cycle that the fee review recorded.
  4. The rule that rejects orders shortly before a restaurant closes uses 15 minutes in the checkout handler and 10 minutes in the place-order workflow.
  5. Dispatch's 6 direct writes to the orders table, recorded by the fee review, are still there.
  6. Each change to the order status values needs the backend and two apps released in a fixed order. This happened in 3 of the last 8 releases.

Your task. Name the pattern behind each observation, score its effect from 0 to 3, and estimate its cost to fix. Then rank the six, choose the smallest change that meets the target, and list the alternatives you would reject. Spend 15 to 20 minutes on it before reading the answer.

The Answer

Only observation 1 affects checkout latency, and it explains 1,800 of the 2,400 ms. It is the excessive-calls pattern. In-process imports and forwarding classes cost microseconds, the copied closing rule is a correctness defect, and Dispatch and the app releases run outside checkout. The table below gives the ranking, with the effect-0 findings ordered by their own risk, as Part 3 describes (illustrative estimates).

RankObservationPatternEffectEngineer-daysDecision
130 Menu queries per checkoutExcessive calls32Fix now
2Closing rule at 15 and 10 minutesBusiness rules in controllers02Report as a defect; fix next
3Dispatch writes ordersCross-boundary writes03Fix before the next Dispatch change
4Status changes need three releasesCoordinated releases05Plan with the next status change
5Menu forwarding layersUnnecessary abstractions01Remove in a separate change
6Orders and Payments cycleCyclic modules02Fix when Payments next changes

The smallest change is one Menu operation that takes all the dish and option IDs of a cart and answers with one query. If the larger query also takes about 60 ms, most of it spent waiting for a connection, Menu time falls from 1,800 ms to about 60 ms. The same checkout then takes about 660 ms (60 plus 420 plus 180), under the 800 ms target. Each checkout also asks the pool for a connection once instead of 30 times, which shortens waits for other requests; the estimate does not count that gain.

The diagram below compares the trace before the change with the estimate after it.

Four larger alternatives lose to the batched call.

  • A cache in front of Menu adds a server and a rule for clearing entries when a price changes. A stale entry charges the old price, and checkout still makes 30 calls, now to the cache.
  • A larger database or connection pool costs more every month and keeps the 30 round trips.
  • Moving Menu into its own service takes weeks and turns 30 queries into 30 network calls.
  • Fixing all six findings at once costs about 15 engineer-days and hides which change moved the p95.

Observation 2 explains why nobody saw the loop, and it makes the new operation an edit to three classes, a cost the team accepts to keep the change narrow. The team ships the batched call, measures the p95 over the next three dinner peaks, and opens a separate change for the closing-time defect.

FAQs

Q: How often should a team run an architecture review?

Run one when a main requirement is at risk, and before a large change such as a service extraction. Between reviews, architecture tests check the most important rules on every build.

Q: What if no finding explains the gap?

Then the gap is probably not structural, such as the 420 ms payment provider call in the practice review, and the report should say so. The cause may be capacity, a slow external system or an algorithm inside one module, which is detailed design.

Q: What does the review report contain?

It states the main requirement, the ranked findings with their evidence and scores, and the recommendation with its expected result. It also lists the effect-0 findings with their risks, and an ADR records any recommendation that changes the architecture.

Q: Who should run the review?

An engineer who does not own the modules in scope, so that no finding defends one team's code. That reviewer still needs 2 to 4 hours from each module owner for the code walk and the interview.

Key Takeaways

  • An architecture review checks a running system against one measurable main requirement and produces ranked findings and one recommendation.
  • Collect evidence from the code, from measurements such as change coupling and queries per request, and from interviews about recent events.
  • Rank findings by effect on the main requirement first and cost to fix second, and recommend the shortest list from the top that meets the target. Findings with no effect go into the report, not the change.
  • Four failure patterns live inside the code and three live at boundaries, and each has a signal you can count, such as commits per business area or calls per request.
  • The smallest fix usually moves one piece of code to its owner, adds one operation that takes a list, or removes one import or one layer.
  • Add an architecture test for each fixed finding that a test can check, such as a forbidden import, so the same problem fails the build if it returns.
