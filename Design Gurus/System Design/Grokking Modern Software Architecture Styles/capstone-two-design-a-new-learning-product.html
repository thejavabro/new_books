Key Takeaways

Know the Vocabulary

This capstone relies on the terms below, each defined in an earlier lesson and repeated here with the same wording.

  • Modular monolith: One deployable application whose code is split into modules by business capability, each with its own interface and its own data.
  • Constraint: A limit on how a system may be built that is set outside the design team, such as a budget, a deadline, a law or an existing system that must keep working.
  • Architecture decision record (ADR): A short document that records one architecture decision with its title, status, context, decision and consequences.
  • Idempotency: The property that processing the same message twice produces the same result as processing it once. An idempotency key, such as the event ID stored in the database, lets a consumer detect and skip a repeat.
  • Exponential backoff: A retry rule that doubles the wait before each new attempt, for example 1, 2 and then 4 seconds.
  • Dead-letter destination: A separate queue, database table or file that holds records that failed processing, for later investigation or reprocessing. A queue used this way is a dead-letter queue.
  • Percentile (p50, p95, p99): The latency that a given share of requests stay at or under; a p99 of 800 ms means 99 percent of requests finish in 800 ms or less.
  • Health check: An HTTP endpoint that the load balancer calls regularly to decide whether an instance should receive traffic.
  • Cold start: The extra latency when the platform must create a new execution environment before it runs a function. A warm start reuses an existing one.
  • Container: In C4, a separately runnable or deployable unit that the system needs running, such as a web application, a mobile app or a database. It is not a Docker container.

The founders of a small education company have booked a launch campaign for a date 16 weeks away. On that day, about 5,000 learners will be able to buy a course, watch its lessons and download a certificate when they pass. Four engineers will build the product, and no design exists yet.

This capstone asks you to produce that design. The result is what a team reviews before it writes code: module boundaries, contracts, data ownership, request flows, background jobs, failure plans and a deployment choice, written as diagrams, tables, decision records and a 16-week plan.

The Scenario

A small company is building an online learning platform. Learners browse a catalog and buy a single course or a monthly subscription that opens every published course. They watch video lessons, take quizzes, and receive a PDF certificate when they pass a course's final assessment. Instructors create and publish courses, and company staff read reports on enrollments, completions and revenue. External services host the videos, take the payments and deliver the email.

The driving requirement is a fixed date with a small team. Four engineers must build the platform in 16 weeks and then operate it themselves. It must also handle money and certificates correctly from the first day. A learner who pays and gets no access, or passes and gets no certificate, becomes a support ticket and often a refund.

Your Task

Design the first version of the platform so that four engineers can build it in 16 weeks, run it with modest effort and change it later. Use the module names Accounts, Catalog, Enrollment, Learning, Assessments, Certificates, Billing, Reporting and Notifications exactly. Write each decision so that an engineer who joins in week 10 could build from it.

Deliverables

Items 1, 2, 6 and 10 hold the four required diagrams. Items 2, 7 and 10 hold the three required ADRs, in the chapter's ADR template.

  1. Context view: a C4 context diagram of the platform, its users and its external systems.
  2. Overall style: a comparison with at least two alternatives, an ADR, and a C4 container diagram.
  3. Module boundaries: each module's responsibility and the modules it calls.
  4. Contracts: the operations each module exposes, as markdown tables.
  5. Data ownership: which module owns which tables, and how others read that data.
  6. Request flows: enroll and pay, complete a lesson, and pass the final assessment and receive a certificate, with at least one runtime trace diagram.
  7. Synchronous and background work: what runs in the request, the worker's job list, and an ADR.
  8. Failure handling: for the payment provider, the video service, the email service and the worker.
  9. Test strategy: the kinds of tests, what each checks, and when each runs.
  10. Deployment choice: at least three of a single virtual machine, a managed container platform, serverless functions and Kubernetes, compared with numbers on cost, operations effort and the 16-week date, plus an ADR and a deployment diagram.
  11. Launch plan: the weeks from first commit to launch, the checks that end each stage, and the rollback rule.

Complete the task before you read the reference solution, and expect it to take four to six hours. Write every deliverable down, because a design that exists only in your head cannot be compared with the one below.

Reference Solution

The steps below follow the deliverables in order. Each gives the answer, the reasoning and the alternatives rejected, so compare your reasoning first.

Step 1: Context View

Start with the system as one box. A C4 context view shows the system as a single box, with the people who use it and the external systems it depends on. Every relationship is a one-way line labeled with what the source does and the technology it uses. The Architecture Diagrams and Decision Records lesson in this chapter explains the C4 views.

The diagram below shows three kinds of people and three external systems. Learners and instructors use the platform in a browser, company staff read reports, and the platform calls all three services. All three also call back with webhooks, so each webhook is its own line, drawn in the opposite direction.

Two facts in this view shape every later step. First, card numbers go to the provider's hosted checkout page and never reach the platform. That shrinks the part of the platform covered by PCI DSS, the card security standard described in Constraints and Trade-offs, although the company keeps some obligations. Second, video travels from the video service straight to the browser. The 30 requests per second at peak are therefore small JSON requests, not video streams.

Step 2: The Overall Style

Compare three styles before choosing one. The table below compares a layered monolith with no module boundaries, a modular monolith, and about five microservices that group the nine capabilities, using this team's estimates.

AspectLayered monolith, no modulesModular monolith with a workerAbout five microservices
Extra setup before launchNoneAbout 1 engineer-weekAbout 6 engineer-weeks
Things to deploy11 image, 2 process types5 services and their workers
Operations per weekAbout 1.5 hoursAbout 1.5 hoursAbout 10 hours
Access after paymentOne transactionOne transactionA saga across two services
A change to three featuresAnywhere in shared codeThree modules, one pull requestThree services, coordinated releases
Separating Billing laterDraw boundaries firstExtract one module and schemaAlready separate

Microservices fail on the constraints. Their benefits are independent releases and scaling, and four engineers at 30 requests per second need neither. Their costs start before launch: 6 engineer-weeks of setup, and 10 hours of operations per week at the 2 engineer-hours per service per week that Quality Attributes uses as its example. They also need a saga, a sequence of local transactions in separate services where each step has a compensating action that undoes it on failure, described in Microservices Architecture, just to grant access after a payment.

The layered monolith fails in the other direction. Nothing stops Billing code from writing the enrollment table, so every later change costs more. It also offers no clean way to separate Billing, a likely early request because payment code changes on the provider's schedule. The modular monolith costs one engineer-week and keeps both the single transaction and a path to extract a module.

ADR 0041: Build the platform as a modular monolith with one PostgreSQL database

Status: Accepted.

Context: Four engineers must launch in 16 weeks. Traffic peaks at about 30 requests per second for 5,000 learners. The first year may bring 50,000 learners and about 300 requests per second if the peak grows with them. A confirmed payment must grant access within 1 minute and must never be lost. Nobody on the team has operated several services in production.

Options Considered: (1) A layered monolith: no setup cost, but no data ownership and no way to separate a capability. (2) A modular monolith with a worker: 1 engineer-week of setup and one transaction for payment and access, but every release ships every module. (3) About five microservices: independent releases, but 6 extra engineer-weeks, 10 hours of operations per week and a saga.

Decision: We will build the nine modules in one Python codebase, packaged as one container image and run as two process types, api and worker. One PostgreSQL database holds one schema per module, and a module writes only to its own schema. A module calls another only through that module's api package, and a build check fails on any other import. Reporting reads other modules' data only through published views.

Consequences: Payment and access change in one transaction, and the team runs one pipeline. Every release ships all nine modules, so a Billing change waits for the shared release. The database is a shared point of failure, and the boundaries are enforced by a build check, not by the network.

Assumptions: Peak traffic stays under about 300 requests per second in the first year. One PostgreSQL server with 2 to 4 vCPUs (virtual processor cores) handles it. The team stays under 10 engineers.

Revisit When: Billing releases wait for the shared release more than twice in a month. One module uses over half of the api or database CPU at peak. More than one pull request in four changes three or more modules. The team passes 10 engineers.

The container view shows the decision as running parts. A C4 container view opens the system box and shows each container, its technology and how the containers communicate. The diagram below shows five containers. The api application and the worker run the same image with different start commands.

To stay readable, the view leaves out two minor relationships: the worker's status checks with the video service and the email service's bounce webhooks. The web application is a single-page application, which loads once in the browser and then calls the API for data. It is served as static files from a CDN (content delivery network), a set of servers that cache files close to users. Object storage, a managed file store that serves files through signed links, holds the certificate PDFs.

Step 3: Module Boundaries

Each module owns one business capability. The table below gives each module's responsibility and the modules it calls. The calls always point from a module that runs a business process to a module that holds data or provides a service the process needs.

ModuleResponsibilityCalls
AccountsSign-up, login, sessions, rolesNotifications
CatalogCourses, sections, lessons, publishing, the video service integrationNone
EnrollmentWho may access which course, from a purchase or a subscriptionNone
LearningLesson positions, lesson completion, course progressEnrollment, Catalog
AssessmentsQuizzes, final assessments, attempts, scoring, pass rulesEnrollment, Learning, Catalog, Certificates
CertificatesCertificate records, PDF rendering, verification codesAccounts, Catalog, Notifications
BillingPrices, checkout, payments, subscriptions, refunds, webhooksAccounts, Enrollment, Notifications

NotificationsEmail templates, sending, delivery status, unsubscribesNone

The calls form no cycle, and three choices keep it that way. Enrollment does not know about Billing: Billing grants access and Enrollment records it, so a free course could later use the same operation. Notifications receives an address and a name from its caller, so it never calls Accounts. Assessments asks Learning about progress, and Learning never calls Assessments. Coupling, Cohesion, and Dependencies explains why cycles stop modules from changing alone.

Two merges were rejected. Merging Enrollment into Billing would make every lesson request depend on payment code, which changes whenever the provider's API does. Merging Certificates into Assessments would mix scoring rules with PDF layout and file storage, which change for other reasons and run in another process.

Every operation that a retry can repeat is idempotent. Webhooks arrive twice, and a worker can repeat a job after a crash. So grant_access, request_certificate and queue_email each take a key and return the first result when it repeats. The contract says so, and a caller can retry without reading the module's code.

Step 5: Data Ownership

Every table has one owning module, and only that module writes to it. Each module keeps its tables in its own PostgreSQL schema, a named group of tables inside one database. The table below gives every table's owner and the views each module publishes for Reporting.

Modules read each other's data through operations, and Reporting is the one exception. A report that scans 30 days of enrollments through function calls would load every row into memory. Reporting therefore reads views, stored queries that look like tables. The source module owns each view and keeps its columns stable when its tables change, so a view is a contract too.

Accounts publishes no view, so no report can show a learner's name or email. The platform schema is not a business module. It holds the jobs table, and modules add jobs only through the job runner's enqueue function.

A build step checks the rule. Each module has its own migration folder, and the build fails when SQL in one module's folder names another module's schema, unless it reads one of that module's published views. Both processes use one database user, so the database does not enforce the rule. That gap is accepted at launch, and one database user per module would close it later.

Step 6: The Three Request Flows

Enroll and pay. The diagram below traces a course purchase. The browser never tells the platform that a payment succeeded. Only the provider's signed webhook, or a job that asks the provider directly, can grant access.

  1. The browser sends POST /checkout. Billing checks has_access and stores a pending checkout session.
  2. Billing asks the provider for a checkout page, with the session ID as the idempotency key, and returns its address. The learner pays on that page.
  3. The provider sends a payment.succeeded webhook, and Billing checks its signature. In one transaction, Billing stores the event ID, marks the payment paid, calls grant_access with the payment ID, and calls queue_email for the receipt. After the commit it answers with a success status.
  4. The return page polls GET /checkout/{id} every 2 seconds and opens the course once access exists. The worker sends the receipt.

The transaction spans four schemas, but every write stays with its owner. grant_access is Enrollment's own code writing Enrollment's tables, and queue_email is Notifications code writing its message row and adding a job through the job runner. Both run on the database connection that Billing opened, so all the writes commit or roll back together. That is the shared transaction that the Monolith Architecture lesson describes.

Repeated, failed and out-of-order webhooks are safe. The event ID has a unique key, so a repeated event fails its insert, and Billing answers with a success status and does nothing else. If any step fails, the whole transaction rolls back, including the event ID, so the provider's next retry processes the event again. Each payment and subscription row also stores the time of the last event applied to it. Billing ignores an older event, such as a payment.succeeded that arrives after the refund of that payment.

A lost webhook is caught by reconciliation. Every 15 minutes, billing.reconcile_checkouts asks the provider about each session pending for over 10 minutes. It handles a paid session with the same function as the webhook, keyed by the payment ID, so whichever arrives second changes nothing. It closes sessions that the provider reports as expired. A lost webhook therefore delays access by at most 25 minutes: 10 minutes of waiting plus up to 15 minutes until the next run.

A subscription follows the same path. Its first webhook grants access to all courses until the end of the paid period. Each renewal calls grant_access with the renewal's payment ID and the new period end that the provider reports, so a repeated renewal cannot add a second month.

Complete a lesson. This is the busiest flow, because the player reports the position every 30 seconds. With 600 learners watching at once, those reports alone are 20 requests per second, two thirds of the launch peak.

  1. The browser sends GET /lessons/{id}. Learning calls has_access, get_lesson and create_playback_token, then returns the lesson, the token and the saved position.
  2. The player streams from the video service, which accepts the token.
  3. Every 30 seconds, Learning saves the position with an upsert, an insert that updates the row if it already exists.
  4. Once the position passes 90 percent of the duration, Learning marks the lesson complete and updates course progress in the same transaction.

Pass the final assessment and receive a certificate. The diagram below traces this flow. The learner gets an answer in about 150 ms, and the slow part runs in the worker.

  1. The browser submits the answers. Assessments checks access, checks that progress is 100 percent, and checks the limit of 3 attempts in 24 hours.
  2. The pass mark is 70 percent. In one transaction, Assessments stores the passed attempt and calls request_certificate, which stores a pending certificate in its own table and adds a render job through the job runner, the same pattern as grant_access.
  3. The response says the learner passed and the certificate is being prepared.
  4. The worker claims the job, reads the name and course title, renders the PDF, and stores it in object storage. It then marks the certificate ready and queues the email.
  5. The worker sends the email. The dashboard shows a download link, and a public page at /verify/{code} confirms the certificate.

Step 7: Synchronous and Background Work

A step runs in the request only when the learner needs its result and it makes no slow external call. Scoring, granting access and saving a position meet that rule. A PDF takes about 3 seconds to render (illustrative), and an email changes nothing on screen, so both go to the worker. Starting a checkout is the one external call kept in a learner's request, because the learner needs the provider's page. It has a 5-second timeout.

The worker reads jobs from a table in PostgreSQL. A module adds a job in the same transaction as the change that causes it, so a certificate never exists without its render job. A scheduler inside the worker adds the timed jobs. The table below lists every job at launch.

Two lanes keep a slow report from delaying a certificate. The default lane runs 3 jobs at a time and the reports lane runs 1. Each worker polls every second with FOR UPDATE SKIP LOCKED, a PostgreSQL clause that lets several workers take different rows without blocking each other. A claimed job gets a lease, a 5-minute limit after which another worker may take it. A failed job retries after 2, 4, 8 and so on up to 128 minutes, so the 7 waits between 8 attempts add up to about 4 hours. After the last attempt the job is marked dead, and dead rows are the dead-letter destination.

ADR 0043: Run slow and external work in a worker that reads a PostgreSQL jobs table

Status: Accepted.

Context: A certificate PDF takes about 3 seconds to render, and email depends on an external service that can be slow or down. The API target is a p95 of 300 ms, and a certificate must be ready within 5 minutes for 95 percent of learners. Launch volume is about 100 certificates and 1,500 emails per day, far under one job per second.

Options Considered: (1) Work inside the request: nothing new, but a 3-second PDF breaks the latency target and an email outage breaks checkout. (2) A worker reading a PostgreSQL jobs table: jobs join the business transaction and no new component is needed, but polling adds some database load. (3) A worker reading a managed message queue: higher throughput, but a new component and the outbox pattern from Event-driven Architecture to keep database and queue consistent.

Decision: We will run a worker process from the api image that claims jobs from platform.jobs with FOR UPDATE SKIP LOCKED. It runs two lanes, default with 3 slots and reports with 1, under a 5-minute lease. A failed job retries with exponential backoff up to 8 attempts and is then marked dead. Every job is idempotent by the key in its row.

Consequences: No request waits for a PDF or an email, and an email outage delays mail without failing a request. The team runs no new component. Polling adds about one query per second per worker, and the database limits job volume.

Assumptions: Jobs stay under 50 per second. One worker task, one running copy of the image, renders about 20 PDFs per minute (illustrative, to be measured in week 12).

Revisit When: Jobs exceed 50 per second for an hour. Polling uses over 10 percent of database CPU. The oldest waiting certificate job passes 5 minutes on more than 3 days in a month.

Step 8: Failure Handling

For each dependency, state what fails, what the learner sees, how the team finds out and how the system recovers. The table below covers the three services and the worker. Each failure stays inside one feature: if the payment provider is down, learners who already have access keep learning.

One case needs a closer look. If a worker crashes after sending an email but before marking the job done, the email goes out again. The message ID lets the email service drop most repeats. The team accepts the rare duplicate receipt instead of building exactly-once delivery.

The database is the largest single point of failure. Managed PostgreSQL fails over to its standby in a second zone in 1 to 2 minutes, while the api returns HTTP 503. Point-in-time recovery restores any minute of the last 7 days after a mistake such as a bad migration.

The date decides most of the comparison. Four engineers have 64 engineer-weeks in 16 weeks. The features need about 42 of them, and the launch work of weeks 11 to 15 (load and failure tests, the restore test, the security review, the beta and its fixes) about 12. That leaves 10 for setup and contingency, and the modular monolith's setup takes 1. The container platform takes 1 more and leaves 8 weeks of contingency. Kubernetes would take 5 and leave 4, and the team would learn to run a cluster while customers depended on it.

Serverless functions were the closest alternative. They are the cheapest and grow without effort, and the whole monolith could run as one function. However, the worker would still need a queue and a function per job, and the database would need a connection proxy, a server that shares a few database connections among many functions. A Python function with a PDF library also has cold starts that threaten the 300 ms target in quiet hours. Those 4 weeks of setup, spent on skills nobody on the team has, would cut the contingency from 8 weeks to 5. The single machine takes 2 engineer-weeks to set up, 1 more than the container platform, and one rebuild of 1 to 2 hours uses 28 to 56 percent of the month's allowed downtime.

ADR 0042: Deploy on a managed container platform

Status: Accepted.

Context: The platform is one image run as api and worker (ADR 0041). It needs 99.5 percent availability, launch in 16 weeks and infrastructure under $1,500 per month. Of 64 engineer-weeks, about 10 remain for setup and contingency after the features (42) and the launch work (12). One engineer has used a managed container platform, and nobody has run Kubernetes or serverless functions in production.

Options Considered: Prices are illustrative. (1) A single virtual machine: 550 per month, 1 week of setup and 1.5 hours of operations per week, but less control and a higher price per vCPU. (3) Serverless functions: about $470 per month and automatic growth, but 4 weeks of setup, new skills and cold starts. Kubernetes scored lowest, 200 of 500.

Decision: The api service runs at least 2 and at most 10 tasks of 1 vCPU and 2 GB across two zones, behind a managed load balancer. It scales out when average CPU passes 60 percent. The worker service runs at least 1 and at most 3 tasks of the same size from the same image. It scales out when over 100 default jobs wait for 5 minutes. The database is managed PostgreSQL with 2 vCPUs, 8 GB and a standby in the second zone. Staging has the same shape with 1 api task, 1 worker task and no standby. All of it lives in infrastructure as code, configuration files in the repository that describe the cloud resources.

Consequences: Setup costs about 1 engineer-week, and deploys replace tasks one at a time with no downtime. Production infrastructure costs about 250, well under the $1,500 budget. The team depends on one cloud provider's container service. Moving means rewriting the infrastructure files, not the code.

Assumptions: One api task serves about 40 requests per second within the latency target (illustrative, to be measured in week 12). The platform restarts a failed task in about 1 minute.

Revisit When: The api needs more than 10 tasks at peak. Compute passes $1,000 per month. Traffic is idle more than 70 percent of the day for a month, which favors serverless functions. The team hires an engineer with production Kubernetes experience and runs more than five services.

Deploy to production in week 2 and every week after, so launch day is not the first deploy. A rollback is a redeploy of the previous image, which takes about 5 minutes. It works only if the previous image runs against the current schema. Every migration therefore adds before it removes: a new column arrives in one release, and the old one is dropped in a later release once no code uses it. A problem on launch day is undone by turning the flag off, which takes seconds.

Common Mistakes

  • Designing for traffic that does not exist. Thirty requests per second fit on two small tasks. Microservices or Kubernetes spend the 16 weeks on load that will not arrive before the next review.
  • Trusting the browser's return from the payment page. A learner can close the tab, and a return address is easy to forge. Only the signed webhook or a check with the provider can grant access.
  • Rendering PDFs or sending email inside the request. The learner waits 3 seconds, and an email outage makes passing fail. Add a job in the same transaction instead.
  • Comparing deployment options on the cloud bill alone. Compute differs by about 1,100 and setup by up to 4 engineer-weeks.
  • Writing revisit conditions nobody can check. "When the platform grows" never triggers a review, but "more than 10 api tasks at peak" can be read from a dashboard.

Key Takeaways

  • The constraints chose the style: four engineers, 16 weeks and 30 requests per second point to a modular monolith with one database, one schema per module and one worker.
  • Contracts state errors and idempotency, because webhooks and jobs repeat and callers must know a retry is safe.
  • Give every table one writer, and give reports their own contract through published views.
  • Keep a step in the request only when the learner needs its result, and add every other job in the same transaction as its cause.
  • Price deployment options with engineer time and setup weeks. For a small team with a fixed date, those numbers outweigh the cloud bill.
