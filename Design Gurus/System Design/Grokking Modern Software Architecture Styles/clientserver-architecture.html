Key Takeaways

Know the Vocabulary

This lesson uses the terms below repeatedly. Read them once now and return here when a later section needs one.

  • Request-response model: An exchange in which the client sends one request and the server returns one response. The server never sends data first.
  • Peer-to-peer: A design in which every participant is both a client and a server to the others.
  • HTTP status code: The three-digit number in every HTTP response that states the outcome, such as 200 for success or 404 for a missing resource.
  • Stateless server: A server that keeps no user data in its own memory between requests, so any instance can handle any request.
  • Load balancer: A server that receives incoming requests and spreads them across several copies of an application.
  • Horizontal scaling: Adding more copies of an application on more machines; vertical scaling instead gives one machine more CPU or memory.
  • Sticky sessions: A load balancer setting that sends every request from one client to the same server instance, which holds that client's state in memory.
  • Cookie: A small value that the browser stores and sends with every request to one site. In a cookie-based session, it holds only a session identifier, and the session data stays in an external store such as Redis.
  • JSON Web Token (JWT): A signed token that carries the user's identity and permissions, so a server can verify it without a database lookup.
  • Tier: A part of the system that runs on its own machines and talks to the other parts over the network.
  • Connection pool: A set of open database connections that a server keeps and reuses, instead of opening a new connection for every query.
  • WebSocket: A persistent connection, opened with one HTTP handshake, over which the client and the server can each send messages at any time.
  • Single point of failure: A component whose failure stops the whole system, such as a central server that every client depends on.
  • Health check: An HTTP endpoint that the load balancer calls regularly to decide whether an instance should receive traffic.
  • Exponential backoff: A retry rule that doubles the wait before each new attempt, for example 1, 2 and then 4 seconds.

Part 1: The Foundation

Almost every application an engineer builds is a client-server system. A browser loading a web page, a mobile app calling an API, and one backend service calling another all follow the same pattern. The examples in this lesson come from one small online store API, with users, orders, products, and search.

What Client-Server Architecture Is

Client-server architecture is a distributed computing model that divides functionality between two roles: clients that request services and servers that provide them. Every interaction in a client-server system follows the same pattern: a client initiates a request, a server processes the request and returns a response.

The defining properties of the pattern:

  • Role separation. The client and server each have a primary job. The client is responsible for presenting information to the user and collecting user input. The server is responsible for processing requests, enforcing business rules, managing data, and returning results. A client may still validate input or run some rules locally, as a thick client does (Part 4), but the server remains the authority for shared data and business rules.

  • Client-initiated communication. The client always initiates the communication. A server in the classic client-server model does not send data to a client unless the client has made a request. This is the request-response model. Variants like WebSocket and Server-Sent Events extend or modify this constraint, but the base model is client-initiates, server-responds.

  • Network separation. Client and server run as separate processes and communicate over a network. The network may be the public internet, a corporate intranet, a local area network, or the loopback interface on a single machine. What matters is that the communication uses a network protocol rather than direct memory access or function calls.

  • Many-to-one relationship. Many clients connect to one server (or a cluster of servers acting as one). A peer-to-peer network also has many participants, so the count alone does not define the pattern. What distinguishes client-server from peer-to-peer is that the roles are fixed and asymmetric. In peer-to-peer, every participant is both a client and a server at the same time.

Why Client-Server Architecture Was Invented

Before client-server architecture, the dominant computing model was the mainframe with dumb terminals.

A mainframe was a powerful central computer.

Terminals were input-output devices with no processing capability of their own. Users typed commands into terminals, the commands were transmitted to the mainframe, the mainframe processed everything, and the results were sent back to the terminal for display.

The mainframe model had a fundamental limitation: the mainframe was a single point of both processing and data management.

As organizations grew and the number of terminals increased, mainframe capacity became a bottleneck. Adding capacity meant upgrading or adding mainframes, which was extremely expensive.

The arrival of personal computers created a new possibility: workstations with local processing capability connected to shared servers.

Instead of the mainframe doing all the work, the workstation could handle user interaction, data presentation, and local processing, while the server focused on shared data management and business logic execution. Work was distributed between the two sides of the connection in proportion to each side's capabilities.

This distribution produced the client-server architecture.

The client took on the responsibilities that benefited from local execution: UI rendering, input handling, immediate response.

The server took on the responsibilities that required centralization: shared data, business rule enforcement, multi-user coordination.

The Role of Each Participant

The client:

The client is any process that initiates requests to a server.

Clients are typically the user-facing side of the system: web browsers, mobile applications, desktop applications, command-line tools.

Clients are also services: a payment service calling a fraud detection API is acting as a client, even though it also acts as a server to other callers.

Responsibilities of the client:

  • Initiating requests based on user actions or internal logic
  • Presenting results to the user or consuming results programmatically
  • Handling user input and translating it into requests
  • Managing local state (what the user sees, their current navigation, form input)
  • Handling errors returned by the server gracefully

The server:

The server is any process that listens for requests and returns responses.

Servers are the centralized side of the system: web servers, API servers, database servers, authentication servers.

A server handles requests from many clients simultaneously.

Responsibilities of the server:

  • Listening for incoming connections on a specific port
  • Parsing and validating incoming requests
  • Authenticating and authorizing the caller
  • Executing the requested operation (business logic, data retrieval, data modification)
  • Returning a well-formed response including a status indicator and result data
  • Managing shared resources (databases, files, connections to other systems)

Part 2: The Request-Response Cycle

How a Request Travels From Client to Server

The request-response cycle is the fundamental unit of interaction in client-server architecture. Understanding it at the mechanism level reveals why certain design decisions exist.

When a user clicks a button in a web application, the following sequence occurs:

Step 1: The client constructs the request. The client-side code translates the user action into a structured request. For HTTP, this means assembling an HTTP request object with a method (GET, POST, PUT, DELETE), a URL identifying the resource, headers carrying metadata (content type, authentication token, accepted response formats), and optionally a body containing request data.

Step 2: The client establishes a connection. The client first resolves the server's host name to an IP address through DNS (the Domain Name System). It then opens a TCP connection to that IP address and port. For HTTPS, the two sides then perform a TLS handshake: an exchange in which the server proves its identity with a certificate and both sides agree on a key that encrypts the rest of the connection. In HTTP/1.0, each request typically opened a new connection. HTTP/1.1 keeps the connection open by default and reuses it for later requests. In HTTP/2, a single connection carries many requests at the same time (a multiplexed connection).

TLS authenticates the server to the client, but not the client to the server. The server learns who the client is only from the credentials in the request, such as a session cookie or a JWT (Part 3). When both sides are services and each must prove its identity, mutual TLS (mTLS) has the client present a certificate as well.

Step 3: The client sends the request. The serialized request is transmitted over the network. The data travels as packets through routers and switches from the client to the server. The time this takes is the network latency component of the total request time.

Step 4: The server receives and processes the request. The server's listening process accepts the connection, reads the incoming data, parses the request, routes it to the appropriate handler based on the URL and method, executes the handler logic, and produces a response.

Step 5: The server sends the response. The server serializes the response into a structured HTTP response with a status code, headers, and a body, and transmits it back over the same connection.

Step 6: The client receives and processes the response. The client reads the response, checks the status code to determine whether the request succeeded or failed, parses the response body, and updates its state based on the result.

HTTP Status Codes as the Response Protocol

The server communicates the outcome of every request through an HTTP status code.

Status codes are three-digit numbers organized into five classes. Every server implementation must use them correctly because clients depend on them to determine how to handle the response.

The five classes and their meanings:

  1. 1xx (Informational): The request was received and the server is continuing to process it. Rarely used in application code. 100 Continue signals that the client should proceed to send the request body.

  2. 2xx (Success): The request was received, understood, and accepted successfully. 200 OK is the standard success response for GET requests. 201 Created is the correct response when a POST request creates a new resource. 204 No Content is the correct response when an operation succeeds but there is no response body to return (DELETE operations commonly return 204).

  3. 3xx (Redirection): The client must take additional action to complete the request. 301 Moved Permanently and 302 Found redirect the client to a different URL. 304 Not Modified tells the client its cached version is still current.

  4. 4xx (Client Error): The request contains bad syntax or cannot be fulfilled. 400 Bad Request for malformed input. 401 Unauthorized when authentication is required. 403 Forbidden when the authenticated user lacks permission. 404 Not Found when the resource does not exist. 409 Conflict when the request conflicts with current server state. 422 Unprocessable Entity when the request is well-formed but fails business validation. 429 Too Many Requests when rate limits are exceeded.

  5. 5xx (Server Error): The server failed to fulfill a valid request. 500 Internal Server Error for unexpected failures. 502 Bad Gateway when a proxy receives an invalid response from the upstream server or cannot connect to it. 503 Service Unavailable when the server is temporarily overloaded or down for maintenance. 504 Gateway Timeout when the upstream server did not respond in time.

Part 3: Stateless Servers and Session Management

The Stateless Server Principle

HTTP is a stateless protocol. Each request is independent. The server processes each request based solely on the information in that request. It does not remember previous requests from the same client. When a client sends request number 100 to the server, the server has no inherent knowledge of requests 1 through 99.

Statelessness is not a limitation. It is a deliberate design property with profound operational consequences.

A stateless server can handle any request from any client because it does not depend on any client-specific state that was set up in a previous request. This means any server instance in a horizontally scaled cluster can handle any incoming request. The load balancer can route to whichever server is least loaded without worrying about routing the client back to the same server.

A server instance can crash and be replaced without any client losing their session state.

If the server were stateful (if it held client-specific state in memory between requests), a client would need to be routed back to the same server instance every time. This is called sticky sessions. Sticky sessions still allow more instances to be added, but they make the load uneven and tie each user's session to one instance. If that instance crashes, its users lose their sessions and must log in again. With four instances, for example, one crash logs out roughly a quarter of the active users.

Statelessness does not mean the application has no state. It means application state is stored externally (in a database or a cache) rather than in the server process's memory. The server reconstructs the state it needs for each request by reading from the external store.

Because every instance reads and writes the same store, two requests can update the same row at the same moment. The database settles the conflict. With pessimistic locking, a query such as SELECT ... FOR UPDATE locks the row, and other transactions cannot modify or lock it until the first one commits or rolls back. In PostgreSQL and MySQL, plain reads of that row still proceed. With optimistic locking, the update includes the version number that was read, for example WHERE version = 7, and a conflict shows up when that condition matches zero rows.

Session State Without Stateful Servers

Users need persistent sessions: once they log in, they should not need to log in again on every request. But the server is stateless and does not remember the login between requests. How are these two requirements reconciled?

The solution is a token that the client stores and sends with every request. The token is either a reference to session data in a shared store (a session cookie) or the session data itself, signed by the server (a JWT). The server reads and validates the token on each request, so no server instance needs to remember anything between requests.

Cookie-based sessions: The server generates a session identifier on login, stores the session data in a database or Redis keyed by the identifier, and sends the identifier to the client as a cookie. On every subsequent request, the client's browser automatically includes the cookie. The server reads the session ID from the cookie, fetches the session data from the external store, and has access to the session for that request.

Part 4: Client-Server Variants

Two-Tier and Three-Tier

Client-server systems are grouped by the number of physically separated tiers, and the client counts as one of them. In a two-tier system, the client talks directly to one server that holds the data and whatever application logic does not run on the client. In a three-tier system, an application server sits between the client and the database, and the client never reaches the database directly.

A two-tier client is either a thin client, which holds little logic and renders what the server returns, or a thick client, which runs business rules on the user's machine. The thin and thick variants, the limits of two-tier, connection pooling, and the move to three-tier are covered in the N-Tier Architecture lesson.

Communication Models Between Client and Server

The base pattern is request-response: the client sends one request and the server returns one response. The server stays silent until the next request arrives. Several variants exist for the cases where the server has new data before the client asks for it.

  • Request-response. The client asks, the server answers, and the exchange ends. Every HTTP call in this lesson follows this model. It fits almost every read and write that a user triggers directly.

  • Polling. The client repeats the same request on a fixed interval, for example every 5 seconds, to check for changes. Most of those requests return nothing new, so the model wastes server capacity. It fits infrequent updates where a delay of a few seconds is acceptable, such as a job status page.

  • Long polling. The client sends a request and the server holds it open until new data arrives or a timeout passes. The client then sends the next request immediately, so updates arrive quickly without a new protocol. It fits chat-style updates in environments where WebSocket is not available.

  • WebSocket. After one HTTP handshake, the connection is upgraded to a persistent channel over which both sides send messages at any time (a WebSocket). The server can push data without a pending request. It fits two-way, high-frequency traffic such as multiplayer games, trading screens, and collaborative editors.

  • Server-sent events. The client opens one HTTP connection and the server streams a sequence of text events over it (server-sent events, or SSE). Traffic flows one way, from server to client, and the browser reconnects on its own after a drop. It fits one-way feeds such as notifications, live scores, and progress updates.

In all five models the client still opens the connection, so the client-initiated property from Part 1 holds. What changes is who is allowed to speak once the connection is open.

Trade-offs and When Not to Use Client-Server

The central server is both the strength and the weakness of the pattern. One place holds the data and enforces the rules, so the system is simple to secure, update, and reason about. That same place is also the bottleneck: every request passes through it, and its capacity sets the limit for the whole system.

The server is also a component whose failure stops everything (a single point of failure). If the server, or the cluster acting as one, goes down, every client stops working, because clients hold nothing useful on their own. Horizontal scaling and health checks (Part 5) reduce the risk but do not remove it.

The server carries the cost. The operator pays for enough capacity to serve every client at peak load, and that cost grows with the number of clients, while the clients contribute nothing to the shared work.

Every action also depends on the network. A client with no connection cannot read shared data or save changes, and each request pays a network round trip, often tens of milliseconds and more on a mobile network. Applications that must work offline keep a copy of the data on the device and synchronize it with the server when the connection returns (a local-first design).

Two other patterns fit better when these costs dominate. When participants can share load and storage among themselves, and no single party should control the system, a peer-to-peer design is the better choice; file sharing and some messaging networks work this way. The Peer-to-Peer Architecture lesson covers that trade-off in detail. When components react to things that happen rather than answer direct questions, and the producer should not wait for the consumer, an event-driven design is the better choice; order processing pipelines and notification fan-out are typical cases. The Event-driven Architecture lesson covers that model.

Part 5: Scaling Client-Server Systems

Scaling starts inside one server instance, which must already serve many clients at once. It does so with one of three concurrency models. A thread pool assigns each request to one of a fixed set of threads, as Tomcat and the Apache worker MPM do. An event loop is a single thread that switches to another connection whenever the current one waits for I/O, using calls that return at once instead of waiting (non-blocking I/O); Node.js and Python's asyncio work this way. A process pool, as in Gunicorn with its default sync workers, runs a fixed number of worker processes that each handle one request at a time.

Every process holds its own memory, and every thread reserves its own stack of up to several megabytes. An event loop can therefore hold tens of thousands of mostly idle connections on one thread, while a thread pool or process pool serves at most as many requests as it has workers. Production servers often combine the two: an event loop handles the network I/O, and a thread pool runs code that blocks, such as calls through a synchronous database driver.

Horizontal Scaling

Horizontal scaling adds more server instances to handle increased load. The stateless server design makes horizontal scaling straightforward: because no client-specific state is in server memory, any server instance can handle any request.

A load balancer distributes incoming requests across server instances.

The load balancer monitors instance health through health check endpoints and stops routing to instances that fail health checks.

Rate Limiting

Rate limiting protects the server from clients that make too many requests, whether through bugs, abuse, or attack. Without rate limiting, a single misbehaving client can consume all server capacity and degrade service for all other clients.

The code below keeps a sliding window log: a sorted set of request timestamps per client, stored in Redis. A request is recorded only after it is allowed. A client that keeps retrying is therefore not blocked forever. The count and the record run in one Lua script, which Redis executes as a single step, so two concurrent requests cannot both take the last free slot. Each window is keyed by the user ID that authentication set. A client can put any value in the X-Forwarded-For or X-Api-Key header. A window keyed by an unchecked value from either header would let the client bypass its limit.

FAQs

Q: What is the difference between client-server architecture and peer-to-peer architecture?

In client-server architecture, roles are fixed and asymmetric. Clients always request and servers always provide. A server does not make requests to clients. The relationship is hierarchical: one server handles many clients. In peer-to-peer architecture, every participant is simultaneously a client and a server. A peer both requests resources from other peers and provides resources to them. BitTorrent is a peer-to-peer system where every downloader is simultaneously an uploader. The distinction matters operationally: client-server systems have a clear single point of control and a clear scaling target (the server). Peer-to-peer systems distribute both load and control across all participants but sacrifice centralized management.

Q: What does stateless mean and why does it matter for scaling?

Stateless means the server does not retain any information about past requests from a client between requests. Each request is fully self-contained: it carries all the information the server needs to process it. The server processes the request, returns a response, and forgets everything about the interaction.

Statelessness matters for scaling because it eliminates sticky session requirements. When a server holds client-specific state in memory (stateful), a client must always be routed back to the same server instance because only that instance has their state. This binding limits how freely a load balancer can distribute requests and means a server crash loses every session that server held.

When the server is stateless (session state is in Redis, JWTs carry identity), any server instance can handle any request from any client. The load balancer has complete freedom to route to whichever instance is least loaded. Instances can be added or removed without affecting any client's session. This is the foundation of horizontal scaling.

Q: When should you use cookies vs JWTs for authentication?

Cookies with server-side sessions are preferable when immediate invalidation is required. If a user's account is compromised and you need to revoke their session, you delete the session record from Redis and the next request with that session ID fails authentication immediately. JWTs cannot be revoked before expiry without maintaining a token blocklist, which partially negates the statelessness benefit.

JWTs are preferable when multiple services need to authenticate the same user without sharing a session store. A JWT signed by the authentication service can be validated by any other service that has the public key without a network call to a central session store. This makes JWTs well-suited for microservices architectures where a request passes through multiple services that each need to verify the caller's identity.

The decision also involves security properties. A cookie with the HttpOnly flag is not accessible to JavaScript, and the Secure flag sends it only over HTTPS. HttpOnly limits the damage of cross-site scripting (XSS), an attack in which an attacker's script is injected into the page. The script cannot read the session credential and send it away. It can still send requests as the user while the page is open, because the browser attaches the cookie to them. JWTs stored in localStorage are accessible to JavaScript and can be stolen by XSS. JWTs stored in HttpOnly cookies have the same protection against theft as session cookies, but, like session cookies, they are vulnerable to cross-site request forgery (CSRF) if the SameSite attribute is not set correctly. In a CSRF attack, another site makes the browser send a request that carries the cookie automatically.

Q: What is the difference between synchronous and asynchronous communication in client-server systems?

Synchronous communication means the client sends a request and blocks until the server responds. The client does nothing else while waiting. A basic blocking HTTP call is synchronous: the client sends a request, and the thread or process that sent it waits for the response.

Asynchronous communication means the client sends a request and continues doing other work without waiting for the response. The response arrives later and the client handles it when it arrives. JavaScript's fetch API is asynchronous by design: the call returns a Promise immediately and the callback executes when the response arrives. In Python, the httpx library used with asyncio sends asynchronous HTTP requests, so other work can proceed while the program waits for network responses.

From the server's perspective, synchronous and asynchronous communication are usually identical: the server receives a request, processes it, and returns a response. The asynchronous aspect is a client-side concern about whether the calling thread blocks.

A third model is message-based asynchronous communication: the client sends a request to a message queue and returns immediately. A background worker picks up the request from the queue and processes it. The client later polls for the result or receives a callback. This model is appropriate for long-running operations where blocking the client for the duration of the operation is not acceptable.

Q: How do you handle server errors gracefully on the client side?

Client-side error handling has three components.

Appropriate retry behavior: transient errors (network timeouts, 502 Bad Gateway, 503 Service Unavailable) are retried with exponential backoff plus a small random delay (jitter), so that many clients do not retry at the same moment. Permanent errors (400, 403, 404) are never retried because the request itself is wrong. A 429 response is retryable too, but only after the wait given in its Retry-After header. Retrying a POST that timed out is risky, because the first request may have succeeded and the retry can create a second order. The client therefore sends an idempotency key, a unique ID for the operation that lets the server recognize a repeat and return the first result. The Microservices Architecture lesson covers retries with backoff and jitter as part of its fault-tolerance patterns.

Meaningful user feedback: error responses should be translated into actionable information for the user. A 401 response means the user needs to log in again. A 409 response on an order creation means the item is out of stock. A 500 response means something went wrong on the server and the user should try again. Generic "something went wrong" messages are the minimum. Specific messages like "the item you tried to order is out of stock" are better.

Circuit breaking: when a downstream server keeps failing, the client stops calling it for a cooldown period and fails fast instead of waiting for each request to time out. The pattern, with its closed, open, and half-open states, is covered in the Microservices Architecture lesson.

Q: What is the difference between REST and client-server architecture?

Client-server architecture is an architectural pattern describing the relationship between two communicating parties. REST (Representational State Transfer) is an architectural style that describes how client-server communication should be designed, and it is almost always applied over HTTP.

REST is a specific way to implement client-server communication over HTTP. It prescribes that resources be identified by URLs and that HTTP methods carry semantic meaning (GET for retrieval, POST for creation, PUT for replacement, DELETE for deletion). It also requires stateless communication and responses that include enough information for the client to navigate the API.

A client-server system can use REST, gRPC, GraphQL, SOAP, WebSocket, or any other communication style or protocol. REST is a widely used style for building client-server HTTP APIs but it is not synonymous with client-server architecture. Every REST API is a client-server system, but not every client-server system is a REST API.

Key Takeaways

  • Client-server architecture divides functionality into two fixed roles. Clients request, servers provide. The client initiates every interaction. The server processes requests and returns responses. Each role has a primary job, and the server remains the authority for shared data and rules.

  • HTTP status codes are the server's communication protocol for outcomes. 2xx means success. 4xx means the client made an error. 5xx means the server encountered an error. Using status codes correctly allows clients to handle responses programmatically without parsing response bodies.

  • Stateless servers are the foundation of horizontal scaling. A server that holds no client-specific state in memory can be replaced, added to, or removed from a cluster without affecting any client session. Session state lives in external stores (Redis, databases) or in a signed token (JWT), not in server process memory.

  • Cookie-based sessions and JWTs are the two main approaches to session management. Cookies with server-side sessions allow immediate revocation. JWTs are self-contained and require no session store lookup, making them well-suited for distributed systems where multiple services validate the same identity.

  • Three-tier architecture solves the security and connection scaling problems of two-tier. The application server sits between the client and database, keeping the database off the internet and multiplexing thousands of client connections onto a small pool of database connections.

  • Rate limiting protects the server from overload. A sliding window log in Redis enforces per-client request limits at the API layer. Rate limit headers tell well-behaved clients how many requests they have left and, after a 429, how long to wait.

  • Health check endpoints enable load balancer-managed server pools. A server that fails its health check is removed from rotation. A server that recovers and passes health checks is returned to rotation. Together with rolling deployments and connection draining (letting in-flight requests finish before an instance stops), health checks make zero-downtime deployments and automatic recovery from instance failures possible.

  • Transient errors should be retried with exponential backoff. Permanent errors should never be retried. A circuit breaker stops calling consistently failing servers immediately rather than waiting for each request to time out.

  • TLS encrypts the channel and authenticates the server. Application-level authentication (JWT, session cookie) authenticates the client. Both are required for a secure client-server interaction, unless mutual TLS authenticates the client with a certificate. Standard TLS without application authentication means the channel is secure but anyone who can reach the API can call it. Application authentication without TLS means credentials are sent in plaintext and can be intercepted.
