Key Takeaways

The pipe-and-filter pattern is the architecture behind Unix shell pipelines, compiler toolchains, data pipelines that extract, transform and load records between systems (ETL), machine learning feature engineering, log processing infrastructure, and network packet filtering.

It is one of the oldest documented software architecture patterns. Doug McIlroy proposed pipes for Unix, and Mary Shaw and David Garlan later described the pattern formally in their book Software Architecture: Perspectives on an Emerging Discipline.

Six commands, and each does exactly one thing. Each reads from standard input and writes to standard output.

The output of one is the input of the next.

The pipeline transforms raw log data into a ranked list of the ten most common error endpoints without any command knowing what the others do.

This is the pipe-and-filter pattern in its simplest form: a linear sequence of independent, single-responsibility processing stages connected by data channels, where each stage transforms its input and passes the result to the next stage.

Understanding the pattern in depth means understanding why independent stages are more valuable than a monolithic transformation function and how the pattern enables parallelism that a single function cannot. It also means knowing the failure modes and how to handle them, and where the pattern appears in modern production systems in forms that are less obvious than the Unix pipeline.

Know the Vocabulary

This lesson uses the terms below repeatedly. Read them once now and return here when a later section needs one.

  • Filter: A self-contained processing stage with one responsibility and defined input and output types, which knows nothing about the filters around it.
  • Pipe: The channel that carries one filter's output to the next filter's input, such as a function call, a queue or a network connection. The kind of pipe decides whether the pipeline runs sequentially or concurrently.
  • Pipeline assembler: The code that chooses the filters and their order, from the source filter where data enters to the sink filter where it exits.
  • Type contract: The agreement that one filter's output type matches the next filter's input type, so filters can be replaced or inserted without changing each other.
  • Transformer: A filter that changes the form or representation of the data without adding new facts, such as parsing JSON text into an object.
  • Tester: A filter that passes each record through unchanged or discards it, based on a condition such as a validation rule.
  • Enricher: A filter that adds information the record did not have, such as customer details or a computed risk score.
  • Splitter and merger: Filters that change the number of records (the cardinality). A splitter turns one record into many, and a merger combines many records into one.
  • Sentinel: A marker object placed in a queue to mean end of stream. A worker that reads it stops.
  • Bounded queue: A queue with a fixed maximum size. A stage that writes to a full bounded queue waits until a slot frees up.
  • Backpressure: Slowing a fast upstream stage to the rate of a slower downstream stage, here through a full bounded queue, so memory use stays limited.
  • Bottleneck stage: The stage that processes the fewest records per second (the lowest throughput), which limits the whole pipeline.
  • Dead-letter destination: A separate queue, database table or file that holds records that failed processing, for later investigation or reprocessing. A queue used this way is a dead-letter queue.
  • Directed acyclic graph (DAG): Stages connected in one direction with no loops, where a stage can send output to several stages or receive input from several. A filter graph is the pipe-and-filter form of a DAG.

Part 1: The Core Concepts

What a Filter Is

A filter is a self-contained processing component that transforms data. Every filter has exactly three properties.

  1. A single, well-defined responsibility. A filter does one thing. It validates, it transforms, it enriches, it routes, it aggregates, or it splits. It does not do multiple unrelated things. A filter that validates and enriches and routes is not a filter. It is a multi-step pipeline compressed into one component, which gives up the benefits of the pattern.

  2. Independence from other filters. A filter does not know which filter comes before it or after it in the pipeline. It reads its input, applies its transformation, and writes its output. The pipeline is the concern of the pipeline assembler, not the filter. A filter that calls another filter directly is tightly coupled and loses the composability that makes filters valuable.

  3. Defined input and output types. A filter accepts a specific data type as input and produces a specific data type as output. The output type of one filter must be compatible with the input type of the next filter in the pipeline. This type contract is what allows filters to be assembled into pipelines without knowing about each other.

What Is a Pipe

A pipe is the channel that connects the output of one filter to the input of the next.

The pipe is responsible for buffering and transmitting data between filters. It does not change the data, because transformation is the job of the filters.

In the simplest implementation, a pipe is a function call: filter A returns a value and that value is passed directly to filter B.

In more sophisticated implementations, pipes are queues (the output of one filter is placed in a queue that the next filter reads from) or streams (continuous data flows from one filter to the next). Pipes can also be network channels, where filters run on different machines and pipes are network connections.

The pipe defines the concurrency model. When the pipe is a direct function call, the pipeline is sequential: filter A completes, then filter B begins. When the pipe is a queue and each filter runs in its own thread or process, the pipeline is concurrent: filter A can be processing the next record while filter B is still processing the current one.

The Pipeline

A pipeline is an ordered sequence of filters connected by pipes. Data enters the pipeline at the source filter, passes through each filter in sequence, and exits at the sink filter. Each filter sees only its direct input and produces only its direct output.

The pipeline's overall transformation is the composition of all its filters' individual transformations.

A linear pipeline is the simplest form of the pattern. In general, the filters can form a graph, where one filter sends output to several filters or receives input from several. The FAQ on DAGs at the end of this lesson returns to this graph form.

The power of this structure is composability. Any filter can be replaced with a different filter that accepts the same input type and produces the same output type. A filter whose input and output types are the same, such as a tester, can be removed and the remaining filters still form a valid pipeline. New filters can be inserted between any two existing filters as long as the type contracts are satisfied.

The pipeline can be tested one filter at a time.

Part 2: The Four Filter Types

Every pipeline starts at a source filter (a producer), which reads data from outside the pipeline, and ends at a sink filter (a consumer), which writes the result out. Most filters between them fall into four types, grouped by what they do to their input.

The names come from two sources. Mark Richards and Neal Ford, in Fundamentals of Software Architecture, list producer, transformer, tester and consumer. Enricher, splitter and aggregator, a kind of merger, come from Enterprise Integration Patterns by Gregor Hohpe and Bobby Woolf.

Type 1: Transformer

A transformer converts input data from one representation or structure to another. It changes the form of the data and adds no new facts about it.

The record describes the same thing after transformation; its form is different. Some conversions keep every detail, such as Base64 encoding, while others drop some, such as converting a color image to grayscale.

Examples: deserializing JSON to a domain object, converting temperature from Celsius to Fahrenheit, mapping database column names to domain property names, converting a bitmap image to grayscale, encoding a string as Base64.

Batch-Sequential Versus Streaming

Pipelines differ in how much data a stage takes in before it passes anything on. In a batch-sequential system, each stage processes the whole input and finishes before the next stage starts. Many traditional compilers work this way, and so does scikit-learn, whose steps each receive the complete data matrix.

In a streaming pipeline, data moves through in small pieces, so a later stage starts on the first record while an earlier stage is still reading. The Pipeline class above streams, because its generators hand each record onward as soon as it is ready. Streaming keeps memory use low and returns the first results sooner. Batch processing suits steps that need all the data at once, such as computing a median.

The Concurrent Pipeline

The sequential pipeline processes one record at a time through all stages. For high-throughput systems, this is inefficient.

When Stage 2 is processing record N, Stage 1 is idle waiting for Stage 2 to finish before it can process record N+1.

A concurrent pipeline uses queues between stages.

Each stage runs in its own thread or process.

Stage 1 processes record 1 and puts the result in the queue for Stage 2.

While Stage 2 processes record 1, Stage 1 immediately begins processing record 2.

All stages are active at the same time, each working on a different record. With Python threads, the stages truly overlap only while they wait on I/O or run library code that releases the interpreter lock, as the notes on worker counts below explain.

The code below is one stage of the concurrent pipeline. Each worker stops when it reads the SENTINEL, a marker object that means end of stream, and only the last worker to stop passes the marker on, sending one copy per downstream worker. A worker also catches any error from its filter, logs it and moves on to the next record. A worker thread that ended on an uncaught error would never forward the marker, so the collector could wait forever.

Backpressure in Pipelines

When one stage is slower than the stage before it, the queue between them fills up.

Without backpressure, the faster upstream stage keeps producing records that accumulate in the queue until memory is exhausted.

Backpressure prevents this by making the queue bounded. When the queue is full, the upstream stage blocks until the downstream stage has processed a record and freed a slot.

The pipeline automatically throttles to the rate of its slowest stage.

As an illustration, take three stages that need 2 ms, 50 ms and 5 ms per record. With one worker each, they can handle 500, 20 and 200 records per second, so the pipeline delivers 20 records per second. Four workers on the 50 ms stage, which waits on I/O, raise the pipeline to 80 records per second. At ten workers that stage reaches 200 per second, and more workers no longer help, because the 5 ms stage cannot go above 200.

The bounded queue.Queue(maxsize=500) in the concurrent pipeline above implements this. When a stage's output queue is full, that stage blocks on output_queue.put(result) until the downstream stage reads from the queue and frees a slot.

Part 4: Error Handling in Pipelines

The Three Error Strategies

Every pipeline must define what happens when a filter raises an error.

Three strategies cover the common cases.

  1. Discard and continue. The record that caused the error is discarded. The error is logged. The pipeline continues processing subsequent records. This is appropriate when each record is independent and a bad record should not stop processing of good records.

  2. Dead-letter routing. The record that caused the error is routed to a dead-letter destination (a separate queue, a database table, or a file) rather than being discarded silently. The dead-letter destination holds records that failed processing for later investigation, reprocessing, or alerting.

  3. Stop and retry. The pipeline pauses and retries the failed record. Appropriate when failures are expected to be transient (network timeouts, temporary service unavailability) and the record must not be lost. Each retry waits longer than the one before (exponential backoff), and a record that still fails after a set number of attempts goes to the dead-letter destination.

Part 5: Where Pipe-and-Filter Appears in Production

Compilers

A compiler is the canonical pipe-and-filter system.

Source text passes through six stages. A lexer splits it into tokens, and a parser builds an abstract syntax tree (AST) from those tokens. A semantic analyzer checks types and resolves names. The next stage translates the checked tree into a simpler, machine-independent form of the program (intermediate representation, or IR). An optimizer rewrites the IR for speed, and a code generator turns it into target code, such as machine code or bytecode.

Each stage is a filter. The lexer knows nothing about semantic analysis. The optimizer knows nothing about tokenization. Each stage has a well-defined input type (source text, token stream, AST, checked AST, IR) and a well-defined output type.

Machine Learning Feature Pipelines

Feature engineering in machine learning is a classic pipe-and-filter application. Raw data passes through: a data loader, a missing value imputer, a categorical encoder, a numerical scaler, a feature selector, and a feature transformer. Each step is independent.

The pipeline can be unit tested one step at a time. Steps can be replaced when better techniques are found.

Scikit-learn's Pipeline class directly implements the pipe-and-filter pattern. Each step implements fit() and transform(), the pipe connects them, and the pipeline can be cross-validated and serialized as a unit.

Log Processing Systems

Log aggregation pipelines, such as Logstash (the L in the ELK stack of Elasticsearch, Logstash and Kibana) and Fluentd, are pipe-and-filter systems. Raw log lines pass through five filters. A parser extracts structured fields from text, a filter removes low-value entries, and an enricher adds host metadata and GeoIP, a lookup of the geographic location behind an IP address. A transformer normalizes timestamps and standardizes field names, and a router sends different log types to different destinations.

Logstash's configuration language directly expresses this as a pipeline of input, filter, and output stages.

Network Packet Processing

Firewalls, intrusion detection systems, and network proxies process packets through filter chains. Each rule in a firewall is a tester filter. Network Address Translation is a transformer filter. Deep packet inspection reads the packet contents to classify the traffic, and it acts as an enricher when it attaches that classification for later rules to use.

The packet passes through the rules in order until one of them accepts or rejects it, and some rules transform it as it passes.

Part 6: Trade-offs

Pipe-and-filter suits a transformation with several distinct steps that are worth testing, measuring or reusing on their own. It also suits pipelines whose steps change over time, and work where slow steps gain from running concurrently.

A single function is the better choice when the transformation is simple enough that stages would add overhead without adding value. The same holds when the stages would never be reused or recombined, or when the cost of queuing between stages is too high for the latency budget.

The pattern also fits poorly in four other situations.

  1. Interactive request and response flows. A filter passes data one way and never returns an answer to its caller. A user request that needs a reply suits a call-and-return style better.
  2. Shared mutable state or transactions across stages. Filters share nothing, so a rule that must update the data of several stages together, or roll all of them back, works against the pattern.
  3. Per-stage conversion cost. When filters run as separate processes or services, each pipe writes the data out and reads it back in. For small, fast steps, this conversion (serialization) can cost more than the work itself.
  4. One data format for every stage. Every filter must read the format its neighbor writes. Unix tools exchange plain text lines, so each tool parses the text again, and richer structure is lost between stages.

The one-way flow is also what separates this pattern from Layered (N-Layer) Architecture. A layer calls the layer below it and waits for a response, while a filter hands its output onward and is done.

FAQs

Q: What is the difference between pipe-and-filter and a simple function chain?

A simple function chain calls functions in sequence: result = f3(f2(f1(input))). This achieves the same transformation but with important differences in structure and capabilities.

Both forms fix the order in code, since build_order_pipeline above is as hardcoded as the chain. The difference is that every filter shares one interface, and the pipe can change from a call to a queue or a network link without changing any filter.

In a pipe-and-filter system, the pipeline is assembled separately from the filters. Each filter is an independent component. The pipeline assembler decides the sequence. New steps are added to the pipeline definition without modifying any filter. A filter can be used in multiple different pipelines without modification. The pipeline can be tested as a unit, and each filter can be tested independently by passing test input directly.

Additionally, pipe-and-filter enables concurrent execution (each filter runs in its own thread reading from a queue) which a function chain cannot easily achieve.

Q: How do you handle errors when a filter fails midway through a pipeline?

Three strategies cover the common cases. Discard and continue: the failed record is logged and skipped, and the pipeline continues with subsequent records. This is appropriate when records are independent and a bad record should not stop the pipeline. Dead-letter routing: the failed record is saved to a separate location (a queue, a database table) for later investigation or reprocessing, without stopping the pipeline. Stop and retry: the pipeline pauses and retries the failed record, appropriate for transient failures like network timeouts.

The choice depends on whether the record must not be lost (use dead-letter routing), whether failures are transient (use retry with exponential backoff), or whether occasional data loss is acceptable in exchange for throughput (use discard and continue).

In production systems where records must not be lost, dead-letter routing combined with alerting on dead-letter queue depth is the common default. Records are never silently lost, but pipeline throughput is not affected by individual record failures.

Q: How do you find the bottleneck stage in a pipeline?

The bottleneck stage is the one with the lowest throughput. In a concurrent pipeline with queues between stages, the bottleneck stage's input queue is consistently full (upstream stages are blocked waiting to write to it) and its output queue is consistently empty (downstream stages are starved waiting for output).

Instrument each stage with counters: records processed per second, average processing time per record, queue depth before and after the stage. The stage with the fewest records processed per second is the bottleneck, and it usually also has the deepest input queue. Its time per record alone can mislead, because a stage with more workers handles several records at the same time.

Bottleneck resolution has three options. Add more worker threads to the bottleneck stage (effective for I/O-bound stages where parallelism helps). Optimize the bottleneck stage's processing logic or run it in several processes (effective for CPU-bound stages, which Python threads usually do not speed up). Split the bottleneck stage into two simpler stages (if it is doing multiple things that can be parallelized).

Q: What is the difference between a pipeline and a directed acyclic graph (DAG) of tasks?

A pipeline is a linear sequence of stages. Data flows in one direction from source to sink. Each stage has exactly one predecessor and one successor (except the source and sink).

A DAG allows branching and merging. A stage can produce output that goes to multiple downstream stages simultaneously. Multiple upstream stages can produce output that merges into one downstream stage. This is more expressive than a pipeline but more complex to implement.

Apache Airflow, Luigi, and Apache Spark's job graphs are DAGs rather than linear pipelines. Where data flows along their edges, they still fit the pipe-and-filter pattern, which Shaw and Garlan describe in general as a network of filters. A linear pipeline is the special case, and it is the better choice whenever the data needs no branching, because it is simpler to build and to reason about.

Q: How does backpressure work in a concurrent pipeline?

Backpressure prevents a fast upstream stage from overwhelming a slow downstream stage by making the queue between them bounded. When the queue is full, the upstream stage blocks on its write attempt until the downstream stage reads from the queue and frees a slot.

The practical consequence: the pipeline's throughput is determined by its slowest stage. All other stages implicitly throttle to the rate of the slowest stage through queue-full blocking. This prevents unbounded memory growth (the queue cannot grow beyond its maximum size) and throttles fast stages (they wait while slow stages catch up).

In systems where blocking is not acceptable (reactive systems, async frameworks), backpressure is signaled differently: the downstream stage signals its capacity, and the upstream stage only produces as much as the downstream stage can consume. RxJava and Project Reactor implement this through the Reactive Streams specification, a standard interface in which each consumer requests a set number of items from its producer.

Key Takeaways

  • A filter is a self-contained processing stage with a single responsibility, independence from other filters, and defined input and output types. A filter that knows about other filters is not a filter.

  • A pipe is the channel between filters. When pipes are direct function calls, the pipeline is sequential. When pipes are queues and each stage has its own worker, the pipeline is concurrent and each stage works on a different record at the same time.

  • The four filter types are transformer (changes form), tester (passes or discards), enricher (adds information), and splitter/merger (changes cardinality). Most filters between the source and the sink are one of these four types.

  • Independent filters enable independent testing. Each filter can be unit tested by passing test input directly without running the complete pipeline. This is the primary testability advantage of the pattern.

  • The concurrent pipeline's throughput is limited by its slowest stage. Adding worker threads to an I/O-bound bottleneck stage increases throughput, while a CPU-bound stage in pure Python code needs processes. Bounded queues implement backpressure that prevents fast stages from overwhelming slow ones.

  • Dead-letter routing is the common default for production pipelines whose records must not be lost. Failed records are saved for investigation without stopping the pipeline's processing of subsequent records.

  • Pipe-and-filter appears throughout production systems as compilers (lexer through code generator), ML feature pipelines (data loader through feature transformer), log processing systems (parser through router), and network packet filters (each firewall rule is a tester filter).

  • The general pattern is a graph of filters. A linear pipeline is its simplest case, and splitters, mergers and routing filters let data branch and join again, as ColumnTransformer does in the scikit-learn example.

  • Pipe-and-filter fits one-way data flows. It fits poorly with request and response flows, transactions across stages, and small steps whose conversion cost exceeds their work.

  • In a system design interview, describe the pipeline stages, name each stage's filter type and single responsibility, and explain how stages are independent and testable in isolation. Then describe the concurrency model (sequential vs queue-based), and name the bottleneck stage and how you would resolve it. That specificity demonstrates pattern knowledge and operational reasoning.
