Key Takeaways

Know the Vocabulary

This lesson uses the terms below repeatedly. Read them once now and return here when a later section needs one.

  • Event: An immutable record of something that happened in the past, such as OrderPlaced. It names what happened and carries some data about it, from a single ID to the full details.
  • Command: A request for something to happen, addressed to one recipient, such as ReserveInventory. Unlike an event, the recipient can reject it.
  • Message broker: A server, such as RabbitMQ or Kafka, that receives messages from producers and delivers them to consumers.
  • Message queue: A channel in a broker that hands each message to one of the consumers reading it, and deletes the message once that consumer acknowledges it.
  • Offset: A consumer's position in the ordered log of an event streaming platform, such as Kafka. Events stay in the log after they are read.
  • At-least-once delivery: A delivery guarantee in which a message is never lost but may arrive more than once.
  • Idempotency: The property that processing the same message twice produces the same result as processing it once. An idempotency key, such as the event ID stored in the database, lets a consumer detect and skip a repeat.
  • Transaction: A group of database writes that either all succeed or all roll back together (atomicity).
  • Dual write: Writing to the database and publishing to the broker as two separate steps, so that a failed publish loses the event.
  • Outbox pattern: Writing each event to an outbox table in the same transaction as the business data. A relay process then publishes the stored events to the broker and retries until the broker acknowledges them.
  • Choreography: A way to coordinate a multi-step process in which each service reacts to the events of other services, with no central coordinator.
  • Orchestration: A way to coordinate a multi-step process in which one central coordinator, the orchestrator, sends each service a command and decides the next step from each outcome.
  • Saga pattern: A sequence of local transactions in separate services, where each step has a compensating action that undoes it on failure.
  • Event store: An append-only log of every event for each aggregate, the object whose state those events describe. Replaying the events in order rebuilds the current state (event sourcing).

Part 1: The Core Concepts

The Definition

Event-driven architecture is a style in which components communicate by publishing events instead of calling each other directly. A producer announces that something happened, and every interested consumer reacts in its own time. The producer does not know who the consumers are and does not wait for them.

The Problem It Solves

In a synchronous design, the order service calls the inventory, payment, and email services one after another before it answers the user. The request is then as slow as the slowest call, and it fails if any one of those services is down. This dependence on every downstream service being available at the same moment is called temporal coupling.

With events, the order service saves the order, publishes OrderPlaced, and responds to the user immediately. Each downstream service processes the event when it can. A new consumer can be added later without any change to the producer.

What an Event Is

An event is an immutable record of something that happened in the past. Three properties define an event precisely.

  1. It happened. An event describes a fact about the past, not a request for the future. "OrderPlaced" describes something that already occurred. "PlaceOrder" is a command, a request for something to happen. The distinction matters: a command can be rejected, modified, or redirected. An event cannot be undone. It happened. Systems can react to it but they cannot change it.

  2. It is immutable. Once an event is recorded, it is never modified. The record of what happened does not change. If the state changes later, a new event describes the new state change. The history of what happened is an append-only log of immutable events.

  3. It identifies what happened. A production event usually carries its type, a unique ID, the time it occurred, and the ID of the entity it concerns. Some short examples in this lesson leave out the fields that their point does not need. How much more data it carries is a design choice, described under Three Styles of Event Use below. An OrderPlaced event can carry the full order, or only the order ID.

Three Styles of Event Use

Martin Fowler describes four patterns that teams call event-driven. Three of them, listed below, are ways that systems use events, and the fourth, CQRS, is covered in the FAQs. Each is a standard choice with its own costs, and one system can use all three.

  • Event notification: The event is thin. It carries the event type and an ID, such as the order ID, and a consumer that needs details calls the producer back. Events stay small, and consumers always read current data. The cost is extra calls, and the producer must be available when consumers call back.
  • Event-carried state transfer: The event is fat. It carries the data that consumers need, as OrderPlacedEvent does above. Consumers need no callback and can keep a local copy of that data. The cost is tighter coupling to the event schema, and personal data such as customer_email and shipping_address is copied into a retained log.
  • Event sourcing: The stored events are the record of state. The current state of an entity is rebuilt by replaying its events in order. Part 5 covers this pattern.

The thin OrderCreated event in the code above is therefore not an error. It is event notification, and it suits consumers that need little data or must always see the latest state.

Events vs Commands vs Messages

Event-driven systems use three related but distinct concepts. Confusing them produces incorrect designs.

  • Events describe things that happened. They are facts. They are broadcast to anyone who cares. The producer does not know who will consume the event and does not expect a response. Multiple consumers can process the same event independently.

  • Commands are requests for something to happen. They are addressed to a specific recipient. The sender usually expects confirmation. A command can be rejected. "Reserve inventory for order 123" is a command. "Inventory was reserved for order 123" is the resulting event.

  • Message is the general term for any data unit sent between components. Events and commands are both messages, but with different semantics. A message broker carries both events and commands as messages, but the application code treats them differently based on their semantic intent.

The Core Components

Most distributed event-driven systems have four core components: producers, consumers, the event channel (broker or bus), and the event schema. An in-process bus often has no formal schema at all.

  • Producers are services that publish events when something happens in their domain. An order service publishes OrderPlaced events. A payment service publishes PaymentProcessed events. Producers know nothing about who will consume their events.

  • Consumers are services that subscribe to event types and react when matching events arrive. The notification service subscribes to OrderPlaced events and sends confirmation emails. The analytics service subscribes to every event type and records them. Consumers know what events they care about but do not know who produces them.

  • The event channel is the infrastructure that receives events from producers and delivers them to consumers. The channel may be a simple in-process event bus, a message queue (RabbitMQ, SQS), or a distributed event streaming platform (Kafka, Kinesis, Pulsar). The channel is responsible for routing, buffering, and delivery guarantees.

  • The event schema defines the structure of each event type. Schemas serve as the contract between producers and consumers. A schema registry stores schemas centrally and checks each new schema version for compatibility when that version is registered. In the common setup, the serializer in each producer and consumer client validates events against the registered schema. The broker itself usually does not check them.

Part 2: The Event Channel

In-Process Event Bus

The simplest event channel is an in-process event bus. Events are published and consumed within the same process. This is appropriate for a modular monolith, a single deployable application divided into modules with clear boundaries, where modules communicate through events. There is no network overhead. There is also no durability and no retry. If a handler fails, or the process stops after the database commit, the event is gone and nothing delivers it again.

Message Queue vs Event Streaming

When event-driven architecture crosses service boundaries, the channel must be a durable, networked system. Two fundamentally different models exist.

Message queues (RabbitMQ, Amazon SQS, Azure Service Bus) treat each message as a task to be processed once and then removed. A message sits in the queue until a consumer retrieves it, processes it, and acknowledges it. After acknowledgment, the message is deleted. If multiple consumers read from the same queue, each message goes to exactly one of them. This is the competing consumers pattern. Queue brokers can still broadcast. A RabbitMQ fanout exchange, or Amazon SNS feeding several SQS queues, copies each message into one queue per subscriber.

Message queues are appropriate when each event represents work to be done once: send one email, process one payment, run one background job. The queue is a work distribution mechanism.

Event streaming platforms (Apache Kafka, Amazon Kinesis, Apache Pulsar) retain events in a durable, ordered log for a configured retention period. Consumers read from the log at their own pace by tracking their current position (offset). Multiple independent consumers can read the same events simultaneously, each at their own offset. Events are not deleted when consumed. They remain in the log until the retention period expires.

Event streaming is appropriate when events are facts that multiple independent systems need, when historical replay is required (a new service needs to process all past events), and when events for the same key must stay in order. Kafka keeps order only within one partition, not across a whole topic, so events that must stay in order share a partition key, as the producer code below shows. The deeper difference between the two models is retention and replay. A queue deletes a message once it is processed, while a stream keeps it for any consumer to read again.

Part 3: Delivery Guarantees

At-Most-Once Delivery

At-most-once delivery means a message is delivered zero or one times. It is never delivered twice but may be lost. The producer sends the message and does not retry on failure. The consumer acknowledges the message (commits the offset) before it processes it. If the consumer crashes after the acknowledgment and before processing finishes, the broker treats the message as done, and the message is lost.

This is the appropriate model when duplicate processing is harmful and message loss is acceptable: metrics and telemetry aggregation, real-time dashboards where a missing data point is acceptable, fire-and-forget logging.

At-Least-Once Delivery

At-least-once delivery means a message is delivered one or more times. It is never lost but may be delivered more than once.

The producer retries if it does not receive an acknowledgment.

The consumer acknowledges only after successful processing, so a crash before acknowledgment causes redelivery.

This is the most common model in production event-driven systems. The consumer must be idempotent: processing the same message twice must produce the same result as processing it once.

A short timeline shows why. The payment consumer reads the event at offset 41 and charges the card. It crashes before it commits offset 42. On restart it reads offset 41 again and charges the card a second time. An idempotency key, such as the event ID, lets the second attempt detect the first and skip the charge. The consumer stores the key with the payment and also sends it to the payment provider, which returns the first result instead of charging again. The provider check matters because the crash can also fall between the charge and the database commit.

The code below records the event id and runs the side effect inside one database transaction. A crash before the commit removes both, so the redelivered event is processed. A duplicate finds the stored id and is skipped. A rollback undoes only database writes, so a side effect outside the database, such as a card charge, must also pass the event id to the payment provider as its idempotency key.

Exactly-Once Processing

Exactly-once processing means the effect of each message is applied exactly one time, with no loss and no duplication. A network cannot guarantee that a message is delivered only once. Systems therefore build this guarantee from at-least-once delivery plus idempotent processing or transactions, so a redelivered message does not change the result a second time. This is the hardest guarantee to provide, and it holds only within defined boundaries.

Kafka's exactly-once semantics (introduced in Kafka 0.11) combine idempotent producers (preventing duplicate writes from producer retries) with Kafka transactions (atomically committing both the output records and the input offset). This guarantees exactly-once processing for Kafka-to-Kafka pipelines. The consumers that read the output must also set isolation.level=read_committed, so that they skip records from aborted transactions.

For Kafka-to-external-system pipelines (Kafka consumer writing to a database), exactly-once requires that the database operation and the offset commit be atomic, which typically requires using the database itself to store the offset and committing both in one database transaction.

The code below stores the last processed offset in the same transaction as the business write. The database transaction rolls both back on any error. On startup, resume seeks the consumer to the offset the database holds, because nothing is ever committed to Kafka.

Part 5: Event Sourcing

What Event Sourcing Is

Event sourcing is an architectural pattern where the state of a domain object is derived by replaying all events that have ever occurred to it, rather than storing the current state directly.

In a traditional system, the database stores the current state of each entity. When state changes, the current state is overwritten. History is lost.

In an event-sourced system, the event store stores every event that has ever occurred. The current state is derived by reading all events for an entity and replaying them in order. No state is ever overwritten or lost.

Because the history is kept, replaying events only up to a chosen time rebuilds the state as it was at that time. This is called a temporal query.

Event sourcing is a persistence pattern, not a required part of event-driven architecture. A single service can store its state as events without publishing them to anyone, and most event-driven systems store current state in ordinary tables. The pattern has two main costs. Stored events are kept indefinitely, so every new version of an event's schema must still be able to read the old events. Replaying a long history is slow, so event stores keep snapshots, saved copies of the state at a given version, and replay only the events after them.

Trade-offs and When Not to Use Event-Driven Architecture

Event-driven architecture removes temporal coupling, but it adds costs that a synchronous design does not have.

  • Eventual consistency: Consumers update their data after the producer commits. A user who places an order may not see it in a read model for a short time.
  • Harder debugging: No single call stack shows the whole flow. Tracing a failure needs correlation IDs and distributed tracing, described in the FAQs below.
  • Schema evolution: Every change to an event must keep working for consumers that the producer team may not know about.
  • Operational cost: A durable broker such as Kafka is another cluster to run, monitor, and upgrade.
  • Duplicate and late events: Consumers must be idempotent, and they must handle events that arrive after related ones.

Avoid event-driven architecture when the caller needs an immediate answer, such as a login check, a price quote, or an account balance. Request-response is simpler for those cases. Events also add little to a small application with one team and a simple flow, where a direct function call is easier to follow.

FAQs

Q: What is the difference between event-driven architecture and message-driven architecture?

The terms are often used interchangeably but have a meaningful distinction. Message-driven architecture is the broader category: any system where components communicate by sending messages rather than making direct calls. Event-driven architecture is a specific form where the messages are events: records of things that happened.

In a purely message-driven system, messages can be commands (requests for action), queries (requests for data), or events (records of facts). Event-driven architecture specifically emphasizes events as the primary communication mechanism. The distinction produces different designs: in EDA, the producer publishes a fact and does not expect a response. In a message-driven command system, the sender issues a request and expects a result.

Q: When should you use choreography vs orchestration?

Use choreography when services should be truly independent, when new consumers should be addable without changing existing services, and when each service's reaction to an event is self-contained. Choreography is better for loose coupling and extensibility.

Use orchestration when the process has complex decision logic that depends on outcomes from multiple steps, or when compensating transactions must be coordinated centrally. Orchestration also fits when the complete process flow needs to be visible and debuggable in one place, and when the process has strict ordering requirements. Orchestration is better for visibility and complex coordination.

Many systems use both: choreography for the main flow between independent services, orchestration for specific multi-step processes that require central coordination.

Q: What is the outbox pattern and why is it critical in event-driven systems?

The outbox pattern solves the dual-write problem. An application that writes to a database and then publishes to a broker cannot do both atomically, so a failed publish loses the event. The pattern writes the event to an outbox table in the same transaction as the business data, as the place_order code in Part 4 shows.

A separate relay process reads the outbox table and publishes each event, retrying until the broker acknowledges it. A common relay uses change data capture (CDC), which reads new outbox rows from the database log, with a tool such as Debezium. The relay can publish an event twice if it crashes after publishing and before marking the row as sent, so consumers still need idempotency.

Q: How do you handle event schema evolution without breaking consumers?

Schema evolution is one of the most practically challenging aspects of event-driven architecture. Producers and consumers are independently deployed, so a schema change in a producer can break consumers running the old schema.

The safe evolution strategies are additive: add new optional fields to events without removing existing fields. Consumers that do not know about the new fields ignore them. Consumers that need the new fields can be updated at their own pace.

Breaking changes (removing fields, renaming fields, changing field types) require versioning the event type. Publish the new event as a different event type (order.placed.v2) while continuing to publish the old event type until all consumers have migrated. The schema registry (Confluent Schema Registry, AWS Glue Schema Registry) enforces compatibility rules when a new schema version is registered, which stops an incompatible version from being used.

Q: How does event-driven architecture handle failures and ensure events are not lost?

Events are not lost when three conditions hold. The message broker is durable: events are replicated to multiple brokers before being acknowledged, as with acks=all and min.insync.replicas of at least 2. The producer uses synchronous publishing with acknowledgment: it waits for the broker to confirm the event was received before returning. The consumer commits offsets only after successful processing.

This combination provides at-least-once delivery: events are never lost but may be redelivered on consumer failure. Consumer idempotency handles duplicate deliveries. An idempotency key stored in the database stops a repeated event from repeating a database write. For an operation in an outside system, such as a card charge, the consumer must also send the key to that system. A database rollback cannot undo a call that has already happened. The payment provider then returns the first result instead of charging again.

Q: What is CQRS and how does it relate to event-driven architecture?

CQRS (Command Query Responsibility Segregation) separates the write model from the read model. Commands modify state through the write model. Queries read from a separate read model that is optimized for queries. CQRS does not require events, but in an event-driven system the commands produce events, and consuming those events updates the read model.

Event-driven architecture and CQRS combine naturally. The write side processes commands, updates the write store, and publishes domain events. Projections consume the domain events and update read models that are optimized for specific query patterns. A user dashboard that needs data from five different services maintains a local read model updated by consuming events from all five services. Queries hit the local read model (fast, single database query) rather than calling five services (slow, multiple network calls).

The main cost is lag. The read model changes only after the events are consumed, so a user who has just placed an order may not see it on the dashboard for a short time. The interface must allow for that delay, for example by showing the new order from the write response.

Q: How do you debug an event-driven system when something goes wrong?

Debugging event-driven systems requires distributed tracing. Every event should carry a correlation ID that links it to the original request that caused it. When order placement triggers inventory reservation, payment processing, and email sending, all three downstream events carry the same correlation ID as the original OrderPlaced event.

Filtering all events by correlation ID in a centralized log aggregation system (Elasticsearch, Splunk) shows the complete chain of events that resulted from one user action. A distributed tracing system (Jaeger, Zipkin, Honeycomb) visualizes the chain as a trace with timing information showing exactly how long each step took.

Dead-letter queues capture events that could not be processed after all retry attempts. Monitoring the dead-letter queue size and content reveals systematic processing failures before they cause visible user impact.

Q: What is an event store and how is it different from a regular database?

A regular database stores the current state of entities. When state changes, the old state is overwritten. History is lost by default.

An event store is an append-only log that stores every event that has ever occurred. Events are never updated or deleted. The current state is derived by replaying events in order. The full history of what happened is always available.

Event stores optimize for append-only writes (very fast) and sequential reads of all events for a specific aggregate. They support event streams per aggregate, subscriptions to event streams (for projecting read models), snapshots (periodic state captures to avoid replaying thousands of events on every load), and concurrency control through optimistic locking on the aggregate version.

Apache Kafka is sometimes used as an event store with unlimited retention, but it has two gaps. It cannot efficiently read the events of one aggregate, and it cannot reject an append that conflicts with the expected version. Many teams therefore keep the system of record elsewhere. KurrentDB, formerly EventStoreDB, is a purpose-built event store. PostgreSQL can be used as an event store by using an append-only events table with appropriate indexing.

Key Takeaways

  • Events are immutable records of things that happened. They are facts, not requests. They are named in the past tense. A thin event carries only an ID, and a fat event carries the data that consumers need. Both are valid choices.

  • Producers and consumers are decoupled. Producers publish events without knowing who consumes them. Consumers subscribe to event types without knowing who produces them. Adding consumers requires no change to producers.

  • In-process event buses serve single-application modular monoliths. Message queues serve work distribution where each task is done once. Event streaming platforms serve durable, replayable event logs where multiple independent consumers need the same events.

  • At-least-once delivery is the standard guarantee in production systems. It means events are never lost but may be delivered more than once. Consumer idempotency handles duplicates.

  • Choreography distributes coordination through events. Each service reacts independently. Loose coupling, extensible, but harder to understand and debug.

  • Orchestration centralizes coordination in one place. The complete flow is visible and debuggable, but the orchestrator is coupled to every service it sends commands to.

  • The outbox pattern solves the dual-write problem. Write the event to a database outbox table in the same transaction as business data. A relay process publishes from the outbox to the broker. Events are never lost even if the broker is temporarily unavailable.

  • Event sourcing stores events instead of state. The current state is derived by replaying events. The full history is always available. Replaying events up to a chosen time rebuilds past state (a temporal query). The write model is an append-only log.

  • CQRS and event-driven architecture combine naturally. Commands produce events. Projections consume events and build query-optimized read models. Queries hit the read model rather than the write model.

  • In a system design interview, name the specific event-driven pattern (choreography vs orchestration), connect it to the specific coupling or scalability requirement it addresses, name the delivery guarantee required and why, and name the failure mode each choice introduces. That reasoning demonstrates architectural depth beyond naming the pattern.
