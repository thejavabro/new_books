Key Takeaways

In 2005, Alistair Cockburn published an article on his website describing an architectural pattern he had been thinking about for years. He called it hexagonal architecture.

Cockburn said the number six has no meaning. The hexagon simply gave him room to draw many ports around the edge of the application, and it broke the habit of drawing an application as a vertical stack of layers.

The idea in the post was this: stop thinking about software as a stack with a top and a bottom. Stop thinking about the database as the foundation and the UI as the surface. Start thinking about the application as having an inside and an outside. The inside contains the business logic.

The outside contains everything the business logic communicates with: databases, UIs, APIs, message queues, file systems, external services. The business logic defines what it needs from the outside.

The outside provides it. The business logic never knows which specific outside implementation it is talking to.

Cockburn named the interfaces the inside uses to communicate with the outside "ports" and named the outside implementations "adapters," which is why the pattern is also called ports and adapters. The name hexagonal architecture comes from the shape of that first diagram.

The main consequence of this design is that the entire business logic of the application can be executed and tested without any running database, web server, message queue, or external service.

Tests of the business rules then run in memory, so a suite of hundreds of them can finish in seconds rather than minutes. Part 7 shows how.

Know the Vocabulary

This lesson uses the terms below repeatedly. Read them once now and return here when a later section needs one.

  • Domain: The inside of the hexagon, which holds every business rule, domain object and use case and imports no infrastructure library.
  • Port: An interface that the domain defines and owns, which states in business terms what the domain offers or needs. It contains no implementation and names no technology.
  • Adapter: A class outside the domain that translates between one technology, such as PostgreSQL or HTTP, and a port. It holds no business logic.
  • Repository: The class that reads and writes one kind of database record on behalf of the business logic.
  • Dependency inversion principle: A rule where the higher-level module owns the abstraction and the lower-level module implements it. Here, the domain owns the driven ports and the adapters implement them.
  • Domain entity: An object with an identity that stays the same while its state changes, such as an Order. Its methods enforce the rules about its own state.
  • Value object: An immutable object defined only by its values, such as Money, which rejects an invalid value when it is created.
  • Use case: A domain class, also called an application service, that carries out one business operation by coordinating entities and driven ports. Use cases implement the driving port.
  • Driving port: A port through which the outside world calls the domain, also called a primary or inbound port, such as OrderUseCases.
  • Driven port: A port through which the domain calls the outside world, also called a secondary or outbound port, such as OrderRepository.
  • Driving adapter: An adapter that turns external input, such as an HTTP request or a queue message, into a call on a driving port. A test can act as one.
  • Driven adapter: An adapter that implements a driven port with one technology, such as a Stripe payment gateway. The domain never knows which one it received.
  • In-memory adapter: A driven adapter that keeps its data in a dictionary or a list. Tests and local development use it in place of real infrastructure.
  • Composition root: The one place where the application creates its objects and connects them, usually at or near its entry point (a function in a startup file).

Part 1: The Problem Hexagonal Architecture Solves

The Two Problems With Traditional Layered Architecture

Traditional three-layer architecture (presentation, business logic, data access) solves the separation of concerns problem.

Business logic does not appear in controllers and database queries do not appear in service classes. This is a real improvement over no architecture at all.

The Layered (N-Layer) Architecture lesson ended with a design where the business layer defines its own interfaces, such as the repositories and the payment gateway, and the data access and integration layers implement them (dependency inversion). Its business logic tests already run with fakes and no database. Two problems remain, and hexagonal architecture addresses both.

Problem 1: The layered picture still has a bottom layer.

The Layered lesson drew the layers as a stack: presentation on top, business logic in the middle, data access at the bottom. The business layer owned its repository, unit of work, payment gateway, and event bus interfaces, so its dependencies on the data access and integration layers were already inverted.

Nothing in the structure, however, stops persistence types from moving upward. ORM entities, query objects, session scopes, and transaction code leak into the business layer through small shortcuts, and many real layered codebases end up this way. The interface is declared, but in practice the business layer still depends on the shape of the database.

The question is not whether interfaces exist. It is who owns them, and whether the structure enforces that ownership.

Problem 2: The stack treats its two sides differently.

In the Layered lesson's design, the data access and integration sides get interfaces that the business layer owns. The presentation side gets no such treatment: the presentation layer sits on top as the only entry point, and the service API is often shaped around the controllers that call it.

If you want to drive the application from a different source (a CLI command, a batch job, a message queue consumer, a test), the service methods you call may have been designed around the web controllers, not around your caller. The asymmetry is built into the picture.

Hexagonal architecture removes the top and the bottom. Every external actor, on both sides, is an adapter plugged into a port that the domain owns, and everything depends on the domain.

The domain depends on nothing external. The folder structure makes this rule easy to check: any import in the domain that points at an adapter or an infrastructure library is a violation, which code review or an import-checking tool can catch on every change.

Part 2: The Three Zones

Zone 1: The Domain (The Inside)

The domain is the inside of the hexagon. It contains all business logic, all domain objects, all domain rules, and all use cases. The domain is the reason the application exists.

The domain has one absolute rule: it imports no infrastructure code. It may use the language's standard library and small infrastructure-free libraries, such as a decimal type, but nothing else from outside the domain. No database libraries. No HTTP frameworks. No message queue clients. No cloud SDKs. No file system utilities. The domain contains pure business logic expressed in pure language constructs.

This rule is not a guideline. It is a structural constraint. If a file in the domain folder imports SQLAlchemy, psycopg2, Flask, or boto3, the domain is not hexagonal.

The value of hexagonal architecture is precisely the guarantee that the domain is infrastructure-free.

The moment an infrastructure import enters the domain, that guarantee is broken and the testability advantage disappears.

The domain contains three kinds of things:

  1. Domain entities and value objects. The objects that represent the core business concepts. An Order, a Customer, a Payment, a Product. These objects contain business logic as methods. An Order knows whether it can be canceled. A Payment knows whether it was successful. The logic that governs the state of these objects lives on the objects themselves.

  2. Domain services. Business operations that span multiple entities or require coordination that does not belong on any single entity. A PricingService that calculates order totals based on customer tier, applied promotions, and regional tax rules. A FraudDetectionService that evaluates whether a transaction looks suspicious based on multiple signals.

  3. Use cases (application services). The orchestration layer that implements specific business operations by coordinating domain entities, domain services, and the ports. A CreateOrderUseCase that validates the order, checks inventory through a port, charges payment through a port, persists the order through a port, and sends a notification through a port. Use cases are the domain's entry points.

Cockburn called the whole inside "the application" and did not divide it further. This lesson splits it into entities, domain services, and use cases, and the Clean Architecture/Onion Architecture lesson shows how Clean Architecture turns that split into separate rings.

Zone 2: The Ports (The Boundary)

Ports are interfaces defined by the domain that specify how the domain communicates with the outside world. They are the domain's declared dependencies: what it needs from the infrastructure and what it offers to the outside.

Ports are pure interfaces. No implementation code. No infrastructure knowledge.

A port named OrderRepository defines methods such as save and find_by_id. It does not say anything about SQL, MongoDB, files, or any other storage mechanism.

The domain owns the port definition. Infrastructure provides the implementation.

There are two kinds of ports, and the distinction is critical.

  1. Driving ports (primary ports, inbound ports). These are the interfaces through which the outside world drives the domain. They define what the application can do: the use cases and operations that the application exposes. An HTTP API controller calls the domain through a driving port. A CLI command calls the domain through a driving port. A message queue consumer calls the domain through a driving port. The domain defines these interfaces so that any driving mechanism can use them.

  2. Driven ports (secondary ports, outbound ports). These are the interfaces through which the domain drives the outside world. They define what the domain needs from infrastructure: data storage, external services, notifications, message publishing. The domain defines these interfaces because the domain knows what it needs. Infrastructure provides implementations that the domain does not know about.

The naming is from the perspective of the domain. Driving ports: the outside drives the domain through these. Driven ports: the domain drives the outside through these.

Zone 3: The Adapters (The Outside)

Adapters are the implementations of ports.

They live outside the domain. They translate between the domain's language (expressed in ports) and the infrastructure's language (expressed in database clients, HTTP requests, message formats).

A PostgreSQL adapter implements the OrderRepository port by translating the domain's repository methods into SQL queries.

A REST adapter calls the driving port: it accepts HTTP requests, parses them, and calls the corresponding use case, which implements that port.

A Kafka adapter implements the EventPublisher port by serializing domain events and publishing them to Kafka topics.

Adapters have one direction of coupling: they depend on the domain.

The domain never depends on adapters. This is the dependency inversion: the domain defines what it needs, and adapters provide it, but the domain does not know which adapter is providing it.

Part 3: Implementing the Domain

Why Domain Implementation Matters Before Anything Else

The domain is built first, completely independent of infrastructure concerns. This sequence is deliberate and important.

When you build the domain first without any infrastructure imports, you are forced to think purely about the business problem.

There is no database schema to anchor your thinking, no HTTP framework shaping your methods, and no ORM dictating your object structure. You model the business as it actually is, not as the database represents it.

The domain consists of entities (objects with identity that change over time), value objects (immutable objects defined by their values), and domain services (logic that spans multiple entities).

Every rule about what is allowed and what is not allowed in the business lives here.

In the example below, notice what is not present: no SQLAlchemy model, no Flask route, no Kafka import.

The Order class knows nothing about how it is stored or how a request reached it. It only knows the business rules that govern orders. This purity is what makes the domain independently testable and independently understandable.

The Money value object is particularly worth examining. It is immutable (a frozen dataclass in Python), and it enforces the rules that must always hold for a valid value, called invariants (negative amounts are rejected, invalid currency codes are rejected). It also defines its own arithmetic (adding two Money values requires matching currencies). This is business logic expressed directly in the type system.

Any code that tries to create an Order with a negative total will be caught by the Money type before it even gets to order validation.

Part 4: Defining the Ports

What Good Port Design Looks Like

Ports are the boundary of the domain. They express what the domain needs and what it offers, entirely in the domain's language. Designing them well requires resisting two common mistakes.

The first mistake is leaking infrastructure concepts into port definitions.

A repository port that accepts a SQL WHERE clause, an event publisher port that requires a Kafka topic name, or a notification port that accepts an SMTP server address has broken the abstraction.

The domain should express intent, not implementation details. "Find orders by customer ID" is domain language. "Execute this SELECT statement" is infrastructure language. The former belongs in a port. The latter does not.

The second mistake is making ports too specific to one implementation.

Consider a payment port designed specifically around Stripe's API. It accepts Stripe's format for idempotency keys (the unique request values that stop a retried charge from running twice) and returns Stripe's error codes. Such a port cannot be implemented by any other payment provider without awkward mapping. Ports should express the domain's needs in terms that any reasonable implementation can satisfy.

  • Driven port design. Each driven port answers one question: what does the domain need from the outside world to do its job? The OrderRepository port answers "the domain needs to save and retrieve orders." The PaymentGateway port answers "the domain needs to charge and refund payments." The NotificationService port answers "the domain needs to inform customers about order events." Each interface is minimal: only the methods the domain actually calls.

  • Driving port design. Each driving port answers a different question: what does the domain offer to the outside world? The OrderUseCases port defines every operation the application supports. HTTP controllers, CLI tools, and message consumers all call the domain through this interface. Because the driving port is an interface, the same use case implementation can be called from any driving mechanism without the use case knowing which one is calling it.

The result of this separation is that the domain is simultaneously callable from a test, an HTTP controller, a CLI command, and a Kafka consumer, all without modification. The test wires in-memory adapters into the use case and builds the command directly. The HTTP controller receives a JSON request and constructs a command. The Kafka consumer deserializes a message and constructs the same command. All three call the same use case through the same driving port.

Part 5: Implementing Use Cases

The Use Case as Pure Orchestration

The use case is the most important file to understand in hexagonal architecture, because it demonstrates the pattern's core claim. You can implement a complete, real business operation (create an order, charge a payment, reserve inventory, send a notification) without a single import from any infrastructure library.

The use case depends on the driving port interface it implements (OrderUseCases) and the driven port interfaces it calls (OrderRepository, ProductCatalog, PaymentGateway, InventoryService, NotificationService, EventPublisher).

All of these are abstractions defined in the domain, with no infrastructure behind them.

The use case receives concrete implementations through its constructor at runtime, but it never knows which specific implementations it is working with.

This matters in a way that extends beyond testing.

Consider what it means for the business logic to have no infrastructure dependencies. The logic that decides whether an order can be confirmed, whether inventory is sufficient, whether a payment should be attempted, and in what order these steps happen is entirely readable as business logic.

A product manager or a domain expert who can read simple code can read the use case and understand the order creation process. They do not need to parse around ORM decorators, HTTP routing logic, or Kafka producer configuration. The business process is expressed directly.

The create_order use case below implements a ten-step business process. Every step either changes a domain object or calls a driven port.

Step 1 creates the Order entity. Step 2 looks up each product through the ProductCatalog port and adds it to the order. Step 3 checks stock through the InventoryService port. Step 4 moves the order to pending payment and reserves the stock.

Step 5 charges the card through the PaymentGateway port. If the charge fails, step 6 releases the reservation. Steps 7 and 8 confirm the order and persist it through the OrderRepository port, and steps 9 and 10 call the NotificationService and EventPublisher ports.

Undoing an earlier step when a later step fails is called compensation. This use case writes its compensation by hand in domain terms, with no distributed transaction framework and no database-specific transaction code.

The hand-written compensation covers only the failures it handles. If step 10 fails to publish the event after the order is saved, the order exists and is paid, but no event goes out and the caller receives an error. Closing that gap needs the outbox pattern, which the Event-driven Architecture lesson covers.

                .orElseThrow(() -> new OrderException("Order " + command.orderId() + " not found"));
        if (!order.getCustomerId().equals(command.requestingCustomerId())) {
            throw new AccessDeniedException("Cannot cancel another customer's order");
        }
        boolean wasPaid = order.getStatus() == OrderStatus.CONFIRMED;
        order.cancel(command.reason());      // the entity itself rejects a shipped order
        orders.save(order);
        inventory.releaseReservation(order.getOrderId());
        if (wasPaid) {
            // A confirmed order was charged, so canceling it must refund the stored transaction
            PaymentResult refund = payments.refund(order.getTransactionId(), order.getTotal().orElseThrow(),
                                                   command.reason());
            if (!refund.success()) {
                // The order is already canceled, so a failed refund must reach the caller, not vanish
                throw new IllegalStateException("Refund failed for order " + order.getOrderId() + ": "
                                                + refund.failureReason());
            }
        }
    }

Part 6: Implementing Adapters

How Adapters Translate Between the Domain and Infrastructure

Adapters are the infrastructure side of the pattern. Each adapter translates between the domain's language and a specific infrastructure technology.

This translation is the adapter's entire job. It should contain no business logic.

It should not decide whether an order can be canceled or whether a payment should be retried.

It converts formats, makes network calls, executes queries, and returns results in the types the domain port defined.

Driven adapters (outbound) implement the interfaces the domain defined. The PostgreSQL adapter receives a domain Order object, extracts the data the database needs, executes SQL, and handles the mapping between domain types (like Money and OrderStatus) and database column types. When the domain calls find_by_id, the adapter executes the appropriate SQL and reconstructs an Order domain object from the returned rows. This reconstruction is called re-hydration: the adapter rebuilds the domain object from its stored state.

The re-hydration method in the PostgreSQL repository deserves particular attention. It does not set the Order's private fields itself. It calls Order.restore, a class method that the domain defines to build an Order from stored values under a descriptive name (a named factory).

A named factory is safer than reaching into private fields from the adapter. If a developer renames a field inside Order, they update restore in the same file, and every repository adapter keeps working. An adapter that set private fields directly would break silently, and the error would appear only when an order was loaded at runtime.

Driving adapters (inbound) receive external input, validate its format, translate it into a command or query object, and call the appropriate use case method. The HTTP adapter does not apply business rules. It applies presentation rules: is the JSON well-formed, are the required fields present, is the authentication header present. After format validation, it delegates entirely to the use case.

The HTTP adapter also handles the reverse translation: taking the use case result (a CreateOrderResult with domain-typed fields) and converting it to an HTTP response with appropriate status codes.

The adapter owns the mapping between domain errors and HTTP status codes. The domain does not know what a 409 or 422 response is, and it should not. That is HTTP's concern, and HTTP is the adapter's concern.

Part 7: The Testing Advantage

Why Testing Justifies the Extra Structure

Every architectural pattern introduces complexity.

Hexagonal architecture introduces more structural complexity than layered architecture: more files, more interfaces, more indirection.

The question every engineering team should ask before adopting any architectural pattern is: what does this complexity buy?

Hexagonal architecture's primary payoff is in testing.

Specifically, it protects a category of tests that layered codebases often fail to keep: complete business logic tests that run without any infrastructure, execute in milliseconds, are fully deterministic, and can cover every branch of every business rule.

The Layered lesson ran such tests with fakes behind interfaces that the business layer owned. Nothing in the layered structure keeps them that way. Once an ORM entity or a transaction scope leaks into a service, a test for the order creation flow needs a database again. A payment call that bypasses an interface needs a test Stripe account or a mock HTTP server. Setting up these dependencies for each test is slow, fragile, and requires environment configuration that varies between developers and CI pipelines.

Tests that depend on external systems are slow to start (database connection time), slow to run (network round trips), and fragile (external service outages break the test suite).

In hexagonal architecture, every external dependency is behind a port.

In tests, in-memory implementations replace real implementations. The InMemoryOrderRepository stores orders in a dictionary or a map. The InMemoryPaymentGateway returns a configurable result without making any HTTP call. The InMemoryInventoryService returns whatever availability the test needs.

The result is a test suite where each test is a plain function that creates in-memory adapters, wires them into the use case, calls the use case with test input, and asserts on the output.

No database. No network. No external services. Each test typically runs in under one millisecond.

A comprehensive test suite with hundreds of test cases runs in seconds.

This is not just a speed improvement. It is a qualitative change in what tests are practical to write.

As a rough illustration, when a test takes 50ms to run (due to database setup), writing 200 tests feels expensive.

When a test takes 0.5ms to run, writing 2,000 tests feels practical.

More tests mean more coverage, which means more confidence, which means faster development with fewer regressions.

Part 8: The Composition Root

The One Place That Knows Everything

In hexagonal architecture, the entire codebase is organized to keep layers ignorant of each other. The domain does not know about adapters.

Adapters do not know about each other.

The HTTP adapter does not know about the Kafka adapter. Only one place needs to know how the pieces connect.

That place is the composition root, the same idea the Layered (N-Layer) Architecture lesson introduced as the only place where all layers are visible at once. It sits at or near the application's entry point, in a startup file, and it is the application's only place of global awareness. It creates database connections, instantiates adapters with those connections, injects adapters into use cases, and wires use cases into driving adapters.

After the composition root finishes its work, the application is fully assembled and every dependency has been injected without any component needing to know which specific dependency it received.

The composition root is also the place where you switch implementations.

To run the entire application against in-memory adapters for local development (no database setup required), set APP_ENV to development so that the composition root calls its development wiring function instead of the production one.

Every other file in the application is unchanged. The domain, the use cases, and the HTTP adapter are identical between the in-memory development build and the PostgreSQL production build.

This substitutability at the composition root is what makes hexagonal architecture practical for teams.

A new developer joining the team can run the full application locally without installing PostgreSQL, without configuring Stripe, and without setting up Kafka. They start the application with the development wiring function and have a fully functional application backed by in-memory adapters. The same in-memory adapters they use for development are the adapters used in tests, which means local development and the tests run against the same driven adapters.

Part 9: Advantages, Limitations, and When Not to Use It

Hexagonal architecture gives three main advantages. The business rules can be tested with in-memory adapters and no running infrastructure. A new driving mechanism, such as a CLI command or a queue consumer, is one new adapter class rather than a change to the domain. A database or payment provider can be replaced by writing one new driven adapter.

The cost is more structure. Every external dependency needs a port, at least one adapter, and a line in the composition root, so a feature touches more files than it would in a layered codebase. The team also has to keep the rule that the domain imports no infrastructure code, usually through code review or an import-checking tool.

The pattern adds cost without benefit when there are few business rules to protect. Three common examples:

  • A CRUD admin panel. Each screen reads or writes one table with little logic in between, so the ports would only forward calls to the database.
  • A thin proxy service. A service that authenticates a request and forwards it to another service has almost no domain to isolate.
  • A data pipeline. A job that extracts, transforms, and loads records is mostly infrastructure orchestration, and its few rules are easier to test as plain functions.

The pattern fits best when the business logic is complex enough that fast, thorough testing matters, when several driving mechanisms call the same operations, or when infrastructure choices are expected to change.

FAQs

Q: What is the difference between driving and driven ports?

Driving ports (also called primary or inbound ports) are the interfaces through which the outside world drives the application. HTTP controllers, CLI commands, and message consumers call the application through driving ports. The domain defines what the driving port accepts (commands and queries), and any adapter that can produce those inputs can drive the application.

Driven ports (also called secondary or outbound ports) are the interfaces through which the application drives the outside world. The domain needs to store data, charge payments, and send notifications. It defines driven ports for each need. Adapters implement these ports with specific infrastructure.

The naming describes the direction of initiation: external drivers initiate action by calling the application through driving ports. The application initiates calls to driven adapters; they are driven by the application.

Q: Where does validation belong in hexagonal architecture?

Two categories of validation exist and they belong in different places.

Format validation (is the HTTP request body valid JSON, are required fields present, are values the right types) belongs in the driving adapter. The HTTP adapter validates that the request is structurally correct before constructing a command.

Business rule validation (can this order be canceled in its current status, is the quantity positive, does the customer have permission to perform this action) belongs in the domain. Domain entities enforce invariants in their methods. Use cases enforce preconditions before acting.

The distinction: the adapter validates that input is structurally correct. The domain validates that input is semantically correct according to business rules.

Q: How does hexagonal architecture handle database transactions?

The domain never imports a database driver or calls a transaction API directly, because both are infrastructure. When one use case must write several records that succeed or fail together, a common approach is an object that groups those writes into one transaction (a unit of work), reached through a port. The port is an interface owned by the domain, with methods such as commit and rollback and no database types in their signatures.

The use case calls commit on the port after its writes succeed. The PostgreSQL adapter implements the port with a real database transaction, and the in-memory adapter implements it as methods that do nothing.

The repository in this lesson commits inside save because create_order makes only one save call. Once a use case adopts a unit of work port, the repository stops committing, so that the unit of work alone decides when the writes become permanent.

Q: What is the difference between hexagonal architecture and clean architecture?

Both keep every dependency pointing inward, so the domain depends on nothing external and can be tested without infrastructure. Hexagonal architecture describes only the inside, the ports, and the adapters, while Clean Architecture splits the inside into separate rings for entities and use cases. The Clean Architecture/Onion Architecture lesson covers that structure in detail.

Key Takeaways

  • All dependencies point inward. The domain depends on no adapter and no infrastructure. Adapters depend on the domain. The Layered lesson already pointed its data access and integration dependencies at interfaces the business layer owns, but kept the presentation layer on top. Hexagonal architecture gives the domain a port on both sides, so every adapter depends on the domain.

  • Ports are the boundary, and their names describe the direction of initiation. Driving ports define what the application offers, and external systems initiate calls through them. Driven ports define what the application needs, and the application initiates calls through them. The domain owns and defines both. Driving adapters call through driving ports, and driven adapters implement driven ports.

  • Adapters translate between the domain and one technology. PostgreSQL adapters translate domain objects to SQL and back. HTTP adapters translate HTTP requests to commands and results to responses. In-memory adapters simulate infrastructure for tests.

  • The primary payoff is fast, reliable, comprehensive business logic testing. In-memory adapters replace real infrastructure in tests. No database. No network. No external services. Hundreds of tests run in seconds.

  • The composition root is the only place with global awareness. It wires concrete adapters into use cases. Switching from production to development means calling a different wiring function in the startup file. Nothing else changes.

  • The pattern is justified by complexity. For simple CRUD applications, a lighter structure, such as a thin presentation layer that calls the ORM directly, is more appropriate. For systems with complex domain logic, multiple driving mechanisms, or infrastructure independence requirements, hexagonal architecture provides measurable benefits in testability, maintainability, and flexibility.

  • In a system design interview, describe the three zones, explain the dependency direction, distinguish driving from driven ports, explain how in-memory adapters enable fast business logic testing, and name the composition root as the single point of full awareness. That reasoning demonstrates architectural depth beyond naming the pattern.
