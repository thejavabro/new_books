Know the Vocabulary

This lesson uses the terms below repeatedly. Read them once now and return here when a later section needs one.

  • Message broker: A server, such as Kafka, RabbitMQ or SQS, that receives messages from producers and delivers them to consumers.
  • Database per service: The rule that each service owns its database, which other services reach only through that service's API.
  • Bounded context: In domain-driven design (DDD), one business area with its own vocabulary and rules, such as inventory or billing.
  • Service discovery: Finding a healthy instance of a service through a registry of network addresses, which instances join at startup and leave at shutdown. Callers query the registry directly, or a load balancer queries it for them.
  • Exponential backoff: A retry rule that doubles the wait before each new attempt, for example 1, 2 and then 4 seconds.
  • Jitter: A random extra delay added to each retry wait, so that many clients do not retry at the same instant.
  • Circuit breaker: A component that fails every call to a downstream service immediately (open) once its failures pass a threshold. After a cooldown, it allows a few trial calls (half-open) and resumes normal calls (closed) if they succeed.
  • Fallback: A reduced but usable response, such as an empty list or a cached copy, used when a dependency is down.
  • Bulkhead: A separate pool of threads or connections for each dependency, so one slow dependency cannot use up the resources that other calls need.
  • Eventual consistency: A state where copies of the same data in different services disagree for a short time and then converge, once every service has processed the latest change.
  • Saga pattern: A sequence of local transactions in separate services, where each step has a compensating action that undoes it on failure.
  • CQRS (Command Query Responsibility Segregation): Separating the model that handles writes from a read model that answers queries, here one table pre-joined from several services' events.
  • API gateway: The single entry point for all client traffic, which validates tokens, applies rate limits and routes each request to the service that owns it. It holds no business logic.
  • Distributed tracing: Tagging each request with a trace ID that every service forwards in outbound calls and writes to its logs, so the request forms one trace.
  • Distributed monolith: A system split into services that must still be changed and deployed together, because they share data or depend on chains of synchronous calls.

Part 1: What Is Microservices Architecture

The Definition

Microservices architecture decomposes an application into a collection of independently deployable services. Each service:

  • Runs in its own process
  • Owns its own data (in its own database or schema, which no other service directly accesses)
  • Communicates with other services over a network (HTTP, gRPC, or a message broker)
  • Can be deployed independently without requiring other services to be deployed simultaneously
  • Is owned by one team that is responsible for its development, deployment, and operation

The "micro" in microservices refers not to the size of the service (there is no rule that says a service must be small) but to the scope of its responsibility. Each service is responsible for one clearly defined domain capability.

The style grew out of large web companies, such as Amazon and Netflix, where many teams shared one deployable application and every release needed coordination across all of them. Splitting the application into services let each team deploy on its own schedule. James Lewis and Martin Fowler popularized the name in an article that described the traits these systems shared.

Those benefits come with a real operational cost. Part 9 lists the cases where one deployable application remains the better choice, starting with a small team.

The Core Principles

  • Single Responsibility. Each service is responsible for one business capability. The order service handles orders. The payment service handles payments. The user service handles user identity and profiles. No service is responsible for more than one business domain.

  • Database per Service. Each service owns its data. No service directly queries another service's database. Cross-service data access happens through the owning service's API. This is the hardest discipline to maintain and the most important one. A microservices architecture where services share a database has the operational complexity of microservices with none of the data independence benefits.

  • Independent Deployability. Any service can be deployed without requiring other services to be deployed simultaneously. This requires backward-compatible API changes: new fields must be optional, old fields must be maintained during transition periods, and breaking changes require versioning.

  • Decentralized Governance. Different services can use different technology stacks, programming languages, databases, and frameworks. The team owning the payment service can choose Go for performance. The team owning the recommendation service can choose Python for its ML libraries. Each team makes the technology decision that best serves their service's requirements.

  • Design for Failure. Every network call can fail. Every service can be unavailable. A microservices architecture must handle partial failures gracefully: when the recommendation service is down, the rest of the application continues working without recommendations, rather than failing entirely.

Part 2: Service Boundaries and Decomposition

Domain-Driven Design as the Decomposition Tool

The most common and most effective tool for defining service boundaries is Domain-Driven Design (DDD), specifically the concept of bounded contexts.

A bounded context is a part of the domain where a particular domain model applies consistently. The term "order" in the order bounded context means something specific: a collection of line items with a shipping address and a payment status. The term "order" in the fulfillment bounded context means something different: a shipment to be assembled, packed, and dispatched.

These two contexts have different models for the same real-world concept. Forcing them to share one model (and one database table) creates a model that serves neither context well. Separating them into distinct services allows each context to own its model independently.

The Three Decomposition Strategies

Decompose by Business Capability. Identify the business capabilities the application provides: user management, order management, payment processing, inventory tracking, fulfillment, notifications, reporting. Each capability becomes a service. This is the most natural decomposition for most business applications.

Decompose by Subdomain. Apply DDD's subdomain analysis, which sorts the business into three kinds of subdomain. A core subdomain is the business's competitive advantage, such as the recommendation engine at Amazon. A supporting subdomain is specific to this business but does not set it apart from competitors, such as seller onboarding. A generic subdomain is a problem that many businesses share and that is already solved, such as user authentication or email sending. Core subdomains get the most engineering investment, and supporting subdomains are built in-house with a simpler design. Generic subdomains are usually bought or reused rather than built, for example Auth0 or Amazon Cognito for authentication.

Decompose by Team Structure. Conway's Law observes that systems reflect the communication structure of the organizations that built them. Designing service boundaries that match team boundaries (and team boundaries that match service boundaries) produces architectures that teams can own cleanly. As a common rule of thumb, a team of 5 to 8 engineers is the right size to own a microservice.

What Makes a Good Service Boundary

A good service boundary has these properties:

High cohesion. Everything inside the service belongs together. The data the service stores, the operations it exposes, and the business rules it enforces all relate to one clearly defined concept.

Loose coupling. The service can be developed, deployed, and scaled independently. Changing the service's internal implementation does not require changes to other services. Other services depend on the service's public API, not its internal structure.

Stable API. The service's API changes infrequently. Frequent API changes force coordinated updates across multiple services, defeating the independence that microservices provide.

Single team ownership. One team owns the service end to end: development, deployment, monitoring, and on-call. Shared ownership creates coordination overhead that negates the autonomy benefit.

Part 3: Service Communication

Synchronous Communication

Synchronous communication means the calling service sends a request and waits for a response before continuing. The call is blocking: the caller's thread is occupied until the response arrives.

REST over HTTP is the most widely used synchronous protocol for inter-service communication. Services expose HTTP endpoints. Other services call those endpoints using HTTP clients. JSON is the most common request and response format.

When to Use Synchronous vs Asynchronous

Use synchronous communication when the calling service needs the result before it can continue. The checkout service needs to know whether payment succeeded before confirming the order.

Use asynchronous communication when the operation can happen after the response is returned. Sending a confirmation email, updating the activity feed, syncing to the analytics system, and notifying the fulfillment service are all operations that can happen after the order is confirmed. Moving them to async reduces the latency of the synchronous response path and decouples the order service from the availability of downstream services.

Part 4: Service Discovery

The Problem

In a monolith, a function call to the payment module uses the function's memory address. There is no network to traverse and no address to look up. In a microservices architecture, the payment service is a separate process running on a separate machine. The order service needs to know the network address (IP and port) of the payment service to call it.

In dynamic cloud environments, service instances start and stop frequently: auto-scaling adds and removes instances, deployments replace instances, failures restart instances. IP addresses change constantly. Hardcoding IP addresses in service configurations is impractical.

Service discovery solves this: a registry maintains the current list of healthy service instances. Services register themselves when they start and deregister when they stop. Callers query the registry to find available instances.

With client-side discovery, the calling service queries the service registry directly and uses the result to make the network call itself. The caller implements load balancing (choosing which instance to call from the list of available instances).

Server-Side Discovery

With server-side discovery, the caller sends requests to a fixed address (a load balancer or API gateway). The load balancer queries the service registry and forwards the request to an available instance. The caller does not implement load balancing or service discovery logic.

This is the model used by Kubernetes services. The Kubernetes service object provides a stable DNS name (payment-service.default.svc.cluster.local) that resolves to the service's cluster IP, a stable virtual address inside the cluster. Kube-proxy, a network component on every node, routes traffic from the cluster IP to healthy pods (the units in which Kubernetes runs a service's containers). The calling service uses the DNS name and Kubernetes handles discovery transparently.

The code below has no discovery logic at all. The client calls one stable DNS name, and Kubernetes routes each new connection to a healthy instance.

Part 5: Fault Tolerance Patterns

Why Fault Tolerance Is Critical

In a monolith, a function call either succeeds or raises an exception. The exception propagates up the call stack and is handled. In a microservices architecture, a service call is a network call that can fail in many additional ways: network timeout, connection refused, partial response, slow response, temporary unavailability, or cascading overload.

Without explicit fault tolerance, a slow downstream service causes the calling service's threads to accumulate (each thread waiting for the slow response), eventually exhausting the thread pool and causing the calling service to stop serving its own clients. One slow service can cause every service that depends on it to fail.

Timeouts

Retries with Exponential Backoff

Transient failures, such as brief network errors and temporary service restarts, are often resolved by retrying. Retries must use exponential backoff with jitter, so that a recovering service does not receive a burst of simultaneous retries.

Retry only calls that are idempotent (safe to repeat). A read is safe to repeat. A write that timed out, such as a card charge, may already have succeeded, so it is retried only when it carries an idempotency key, a unique request ID that the service uses to detect and ignore repeats.

The code below retries only transient failures: timeouts, 408 (Request Timeout), 429 (Too Many Requests) and the server errors 500, 502, 503 and 504. Any other error status, such as 400, 404 or 501, is treated as permanent and raised at once, because sending the same request again will not change the answer. The delay doubles on every attempt and gets a random extra wait (jitter), so many clients do not retry at the same instant.

Bulkheads

Timeouts limit how long one call waits, but many slow calls to one dependency can still fill a shared thread pool. Each downstream dependency can instead get its own pool of threads or connections (a bulkhead), so one slow dependency cannot exhaust the resources that every other call needs. For example, a product page service can give review calls 10 threads and product calls a separate 20, so a slow review service never blocks product calls. Use bulkheads when one service calls several dependencies and a slow, non-critical one must not block the critical ones.

Eventual Consistency

Without a shared database, operations that span multiple services cannot use a single database transaction. The answer is eventual consistency: the system eventually reaches a consistent state through asynchronous event propagation, rather than being immediately consistent through a synchronous transaction.

When an order is created, the order service commits to its own database and publishes an OrderCreated event. The notification service consumes the event and sends the confirmation email. The order dashboard read model, described under CQRS below, adds a row for the order. These all happen asynchronously.

For a brief window after the order is created, the dashboard view does not list the new order yet. The system is temporarily inconsistent. It becomes eventually consistent when all services have processed the event.

Inventory does not follow this event flow. Stock must be reserved before the customer is charged, so the saga below reserves it as one of its steps.

The Saga Pattern

Operations that must span multiple services and maintain consistency require the saga pattern. A saga is a sequence of local transactions, each in a separate service, with compensating transactions to undo completed steps on failure. A saga gives no isolation: while it runs, other requests can read its intermediate states, such as an order that exists before its payment has succeeded.

Why Observability Is Harder in Microservices

In a monolith, a slow request produces one stack trace in one log file.

Part 9: When Microservices Are and Are Not Justified

Justified When

  1. Multiple teams need to deploy independently. The primary organizational benefit of microservices is that different teams can deploy their services without coordinating with other teams. This benefit only materializes when the teams are large enough and independent enough to justify the operational overhead.

  2. Specific components have genuinely different scaling requirements. The search service needs 10x more CPU than the user profile service, and the media processing service needs GPU instances. Hardware alone does not require a split, because worker processes built from the same artifact can run on machines of their own, including machines with GPUs. A separate service is justified when the component also needs a release schedule of its own, or when its large dependencies, such as GPU libraries, would otherwise be carried into every other process.

  3. Different components genuinely benefit from different technology stacks. The ML inference service needs Python. The real-time event processing service benefits from Go. The team has the platform maturity to support polyglot services.

  4. The organization has platform engineering capacity. Running microservices requires service discovery, distributed tracing, centralized logging, a deployment pipeline per service, container orchestration (Kubernetes), secrets management, and on-call coverage per service. Without a platform team to provide this infrastructure, each product team builds it themselves, which is expensive and inconsistent.

Not Justified When

  1. The team is small. As a rule of thumb, with fewer than 15 to 20 engineers, the coordination overhead of microservices usually outweighs the benefit. Each service needs its own deployment pipeline, monitoring, and on-call coverage. A team of 8 cannot maintain 12 services at production quality.

  2. The domain is not yet stable. Microservice boundaries that seemed correct during initial design often turn out to be wrong once the product is in use. Refactoring a boundary between two microservices requires changing two APIs, two databases, and two deployment configurations. Refactoring a boundary between two modules in a monolith is a code organization change.

  3. The organization lacks platform maturity. Adopting microservices without service discovery, distributed tracing, centralized logging, and automated deployment pipelines leaves the team with the operational complexity of microservices and no infrastructure to manage it.

The result to avoid in every one of these cases is a distributed monolith. A distributed monolith is a system split into services that must still be changed and deployed together, because they are coupled through shared data or synchronous call chains. It carries the operational cost of microservices and provides none of the independent deployability that justifies them.

FAQs

Q: How do microservices handle distributed transactions?

They avoid them where possible and use the saga pattern from Part 6 instead: a sequence of local transactions in each service, with compensating transactions that undo completed steps on failure. A saga is coordinated either by a central orchestrator or by choreography, where each service reacts to the events of the others, and the Event-driven Architecture lesson covers that choice in depth.

Q: How do you handle authentication across services?

Two common patterns. First, validate the JWT at the API gateway. The gateway adds the user identity as a trusted header (X-User-Id, X-User-Role) before forwarding to downstream services. Downstream services trust the gateway's header without re-validating the JWT. Second, each service validates the JWT independently using the identity provider's public key (fetched from its JWKS endpoint, a URL where the provider publishes its public signing keys). The second pattern is more secure (no dependency on gateway correctly validating tokens) but adds JWT validation overhead to every service.

Q: How do you test microservices?

Three testing layers. Unit tests test each service's business logic in isolation with mocked dependencies. Integration tests test each service against its real database and external dependencies. Contract tests (using tools like Pact) verify that a service's API matches what its consumers expect, without requiring all services to be running simultaneously. Contract tests are the critical layer, because they show that two services are incompatible before deployment rather than after it.

Q: What is a service mesh and when do you need one?

A service mesh (Istio, Linkerd, Cilium) handles service-to-service communication at the infrastructure level rather than the application level. It provides mutual TLS (encrypting and authenticating all inter-service traffic), traffic management (retries, circuit breaking, traffic splitting), and observability (metrics and traces for every service call) without requiring application code changes.

A service mesh is justified when the number of services grows beyond what can be managed by per-service library implementations of these concerns. At 20 services with 5 teams, implementing retries, circuit breaking, and mTLS in each service's code is manageable. At 200 services with 50 teams, a service mesh provides consistent behavior without each team implementing it independently.

Q: How do you version microservice APIs?

URL versioning (/v1/users, /v2/users) is the most visible approach. Header versioning (API-Version: 2) keeps URLs clean. The critical discipline is backward compatibility: new fields must be optional, old fields must be maintained during the transition period, and clients that do not send new optional fields must receive correct behavior. Breaking changes require a new version endpoint. Old version endpoints must be maintained until all consumers have migrated. A Deprecation response header marks an endpoint as deprecated, and a Sunset header gives the date when it will be removed.

Q: Should you start with microservices or migrate from a monolith?

Start with a modular monolith and design clear domain boundaries inside it. When a module has a compelling reason for independence (team ownership, scaling requirements, or technology choices), extract it with the strangler fig pattern, in which a new service takes over one slice of the monolith at a time. The Monolith Architecture lesson explains it step by step.

Q: How many microservices is too many?

There is no fixed number. The right number is determined by the number of distinct business capabilities the application provides and the number of teams available to own them. A useful heuristic: each service should be owned by one team of 5 to 8 engineers. If a team owns more than 3 to 4 services, the per-service operational overhead limits the time available for feature development. If a service has no full-time owner, its reliability, security, and evolution will be neglected. The number of services should be proportional to the number of teams that can fully own them.

Q: What is the difference between microservices and a service-oriented architecture (SOA)?

The two main differences are reuse scope and governance. SOA services are built for reuse across the whole enterprise, so one customer service serves every application in the organization. A microservice is owned by one product team and reused only within that product. SOA is governed by a central architecture team, while each microservices team chooses its own technology stack and release schedule. The Service-Oriented Architecture (SOA) lesson compares the two styles in one table.

Key Takeaways

  • Microservices decompose applications into independently deployable services, each owning one business capability and its own data store. The organizational benefit (team autonomy) is as important as the technical benefit (independent scaling).

  • Each service's data is private to it. It may live in its own database or its own schema, but no other service reads or writes it directly. Data independence is what makes microservices genuinely independent.

  • Synchronous communication (REST, gRPC) is appropriate when the caller needs the result before continuing. Asynchronous communication (Kafka, message queues) is appropriate for operations that can happen after the response is returned.

  • Fault tolerance patterns (timeouts, retries with backoff, circuit breakers, bulkheads and fallbacks) protect inter-service calls. Every call needs a timeout, retries suit only calls that are safe to repeat, and the other patterns are added where a slow or failed dependency would otherwise spread its failure. A microservices system without fault tolerance is fragile in ways that monoliths are not.

  • The saga pattern handles cross-service operations that must maintain consistency, using local transactions and compensating transactions rather than distributed database transactions.

  • Distributed tracing is essential once requests cross several services. Without trace IDs propagated across all services and a tracing backend (Jaeger, Zipkin, Honeycomb), finding the source of latency means matching logs from every service by hand.

  • Start with a modular monolith. Design clean domain boundaries. Extract services when specific modules have compelling, concrete reasons for independence. Do not design microservice boundaries for a domain you do not yet fully understand.

  • The operational overhead is real. Service discovery, centralized logging, distributed tracing, per-service deployment pipelines, container orchestration, and on-call coverage per service are all prerequisites. Without platform investment, microservices create more problems than they solve.

  • In a system design interview, choose microservices when the problem explicitly involves multiple teams needing independent deployment, when components have genuinely different scaling needs, or when the scale of the system justifies the operational complexity. Justify the choice with specific requirements rather than treating microservices as the default for any large system.
