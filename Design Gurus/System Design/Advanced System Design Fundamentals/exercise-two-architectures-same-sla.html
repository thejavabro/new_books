Exercise: Two Architectures, Same SLA

On This Page

  1. The Brief
  1. The First Move Is to Cancel
  1. The Two Columns
  1. The Line That Decides It Is Not the One You Were Comparing
  1. The Crossover, Which Is the Real Answer
  1. What a Strong Answer Looks Like

1. The Brief

A mobile product has an API that serves 300 million requests a month. Traffic follows a daily cycle, with a peak about four times the daily mean. Responses average 8 KB. Each request makes two reads against a managed database. The service is stateless.

The availability target is 99.9 percent, and p99 latency has to stay under 200 ms. Two designs meet both.

Architecture A, a container fleet. Containers behind a load balancer, spread across three availability zones, autoscaled between three and six instances. Each instance handles about 150 requests per second. Instances sit in private subnets and reach the database and object storage through a gateway in each zone.

Architecture B, functions. One function per route behind a managed API gateway. No instances, no load balancer, no gateway in the subnet. Each invocation runs about 100 ms at 512 MB.

Assume this rate card, which is close to published pricing and is the card you should use rather than looking anything up.

instance                $0.10 / hour
committed instance      60% off, one year term
load balancer           $30 / month all in
subnet gateway          $0.045 / hour per zone, plus per GB processed
function requests       $0.20 / million
function duration       $0.0000166667 / GB-second
API gateway (HTTP)      $1.00 / million calls
API gateway (REST)      $3.50 / million calls
egress to internet      $0.09 / GB

Pick the cheaper one. Prove it with numbers, then say whether the number should decide it.

2. The First Move Is to Cancel

The instinct is to compute the full bill for each design and compare the totals. That is twice the work and it hides the answer.

Three lines are identical in both architectures.

  • Egress to the internet. 300 million requests at 8 KB is about 2,400 GB, or roughly $216 a month. The same bytes leave in both designs.
  • The database. Same engine, same two reads per request, same instance.
  • Object storage. Same objects, same requests against them.

Compute the differences, not the totals. A line that appears identically in both columns cannot change the decision, however large it is.

This matters more than it sounds, because egress is the line the previous lessons told you to watch and here it is decision-irrelevant. Two hundred and sixteen dollars is three quarters of the entire monthly difference between these designs, and spending your analysis on it produces a number that cannot move the answer either way.

What remains is the part that actually differs: how compute is bought, and what sits in front of it.

3. The Two Columns

Start with the capacity arithmetic for A, because every other line in that column depends on it.

mean rate = 300M / 2.6M seconds  = about 116 req/sec
peak rate = 4 x 116              = about 463 req/sec
instances at peak = 463 / 150    = 3.1, so 4, plus one for failure = 5,
                                   rounded to 6 for an even spread over 3 zones
floor = 3 (one per zone)
average over the day = (6 + 3) / 2 = about 4.5

Architecture A. Commit to the floor of three instances on a one year term, and buy the variable part on demand.

committed baseline   3 x $0.10 x 730 x 0.40  = $88
on-demand variable   1.5 x $0.10 x 730       = $110
load balancer                                 = $30
subnet gateways      $0.045 x 730 x 3 zones   = $99
                                        total = $326 / month

Architecture B. Per-request pricing, with no floor and nothing idle.

function requests    300 x $0.20              = $60
function duration    300M x 0.1s x 0.5GB
                     = 15M GB-s x $0.0000167  = $250
API gateway (HTTP)   300 x $1.00              = $300
                                        total = $610 / month

Architecture A is cheaper, by about $284 a month. At this volume, with this load shape, the always-on fleet costs a little over half of the per-request design.

That result surprises most people, because the serverless pitch is that you stop paying for idle. You do. It is simply not where the money was.

4. The Line That Decides It Is Not the One You Were Comparing

Two lines in those columns deserve more attention than the compute, and both are the kind of charge the egress lesson described as attached to something that does not look like a purchase.

The API gateway is half of column B. Three hundred dollars for the HTTP flavor. Had the design specified the REST flavor at 1,050, and column B would total 310 either way.

That is the finding worth stating out loud: the gateway flavor changes the answer by more than the architecture choice does. A candidate who compares containers against functions and never prices the thing in front of the functions has compared the smaller of the two decisions.

The subnet gateways are thirty percent of column A. Ninety-nine dollars a month in hourly charges alone, before a single GB of processing, for the privilege of letting private instances reach a database and an object store in the same region. Architecture B has no equivalent line.

And that one is reducible. Private endpoints for the object store and the other managed services remove the processing charge for that traffic, which does not appear in the table above because the brief did not give a volume. If internal traffic to those services is in the tens of terabytes, that omitted line is larger than the difference between the two architectures.

Both of these are worth more than the headline comparison, and both are invisible in a diagram that shows a box labeled compute.

5. The Crossover, Which Is the Real Answer

A single volume gives you one answer. The shape of the two cost curves gives you the answer for every volume, and that is what makes the analysis reusable.

  • Column B is linear with no floor. Function requests, duration and gateway calls together come to about $2.03 per million requests, from the first request. Half the volume is half the bill.
  • Column A has a floor and then steps. Three instances, a load balancer and three gateways cost about $216 a month at any volume, including zero. Above that it rises in whole instances.

Setting them equal gives the crossover.

$216 floor + steps   vs   $2.03 per million

below ~106M requests/month   B is cheaper
above ~106M requests/month   A is cheaper
Requests / monthAB
25M$216$51
100M$216$203
300M$326$610
600M$435$1,220

At a tenth of this traffic the recommendation reverses completely, and B costs a quarter of A. The brief put the product at roughly three times the crossover, which is why A wins, and the margin widens as the product grows.

The useful output is not "A is cheaper." It is "A is cheaper above about a hundred million requests a month, and we are at three hundred million."

The second statement survives the product changing. The first one does not.

6. What a Strong Answer Looks Like

The arithmetic above is most of the exercise, and the last step is the one that separates the strongest answers.

Two hundred and eighty-four dollars a month is not a decision. It is about three and a half thousand dollars a year, which is a few days of one engineer. Having proved that A is cheaper, the honest conclusion is that cost does not decide this, and something else should.

That turns the remaining question into the right one. On the stated SLA, the things that differ are not financial.

  • Cold starts against the p99 target. Column B's compute is only correct if invocations are warm enough to stay under 200 ms at the 99th percentile. If they are not, the fix is provisioned concurrency, which removes B's no-idle property and changes the arithmetic.
  • Operating cost. A needs autoscaling configuration, instance patching, image updates and capacity review. B needs very little of that. In engineer-time, which is the currency from the build-versus-buy lesson, B is plausibly the cheaper option while being the more expensive line item.
  • Where this is heading. A is cheaper now and the gap widens with growth. If the product is expected to grow an order of magnitude, that matters more than today's total.

So the complete answer is layered.

  1. Cancel the identical lines and say why, because that is what makes the comparison manageable.
  2. Compute both columns and name the capacity arithmetic behind A, since the instance count is the only assumption doing real work.
  3. Report A as cheaper by $284, with the gateway flavor and the subnet gateways flagged as the two lines larger than the headline difference.
  4. Give the crossover, because it is the result that survives a change in traffic.
  5. Say that the gap is too small to decide on, and name cold starts and operating cost as what should decide instead.

A candidate who stops at step three has answered the question asked. A candidate who reaches step five has answered the question behind it, which is whether they can tell the difference between a number and a decision.

What the interviewer is scoring: the first thing watched is whether you cancel the shared lines before computing anything, because candidates who price both full bills spend their time on egress and arrive at the same answer more slowly. Showing the capacity arithmetic for the fleet is what makes the comparison checkable, and the peak-to-average ratio is the input that does the work. The gateway flavor is the trap: pricing the functions and forgetting what sits in front of them is the most common way to get this backwards, and noticing that it swings the result harder than the architecture does is a strong signal. The subnet gateway line is the second trap, in the opposite column. Producing a crossover rather than a single number is what makes the analysis reusable, and the finish that lands best is concluding that a $284 difference is too small to decide an architecture, then naming cold starts against the p99 target and operating cost as the things that should.
