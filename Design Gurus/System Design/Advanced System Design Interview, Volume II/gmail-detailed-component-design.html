Step 7: Detailed Component Design

The high-level design named the parts. This step looks inside four of them: the cache, threading, security, and search indexing. The diagram below shows how they connect.

Caching Layer

Common reads should not hit the database every time, so we add a cache.

Recently read emails and mailbox summaries stay in memory. When a user opens the inbox, we cache the newest N message headers. A refresh, or a second device asking for the same inbox, is served from the cache instead of the database. A distributed cache like Memcached or Redis works well here.

New mail, or mail that is moved or deleted, makes the cached copy wrong. We handle that in one of two ways. We remove the stale entry, or give it a short TTL. A TTL, time to live, is how long an entry may stay in the cache before it expires. Either way needs care. The rule is simple to state: the cache holds fresh data, or we detect the stale copy and fetch a fresh one.

Threading (Conversation) Implementation

A conversation view groups a message with all its replies. To support it, we give related emails the same ThreadID.

Replies usually carry an In-Reply-To header, or a References header. That header names the message ID the reply answers, and we use it to find the thread. A brand new email is not a reply, so it starts a new thread, and its ThreadID can simply be its own message ID. A reply looks up the ThreadID of the message it answers, and reuses it.

The metadata store keeps a mapping from ThreadID to its list of MessageIDs. Or we skip the mapping and query all messages with that ThreadID instead. To show a conversation, the system fetches every email in the thread, which can include many participants.

Some email chains run to dozens of replies. We set limits, so a very long thread does not cost too much to load. In practice, most threads are small enough.

Trade-off. Not every email service offers threading, because storing and fetching grouped messages adds work. But threading is a key part of the user experience. Gmail made it popular, as noted on Gmail on Wikipedia, so the extra work is worth it.

Security and Privacy Measures

Encryption in transit. Every client connection uses TLS. That means HTTPS for web and mobile, and SMTPS, IMAPS, and POP3S for mail protocols. When we send mail to another provider's server, we also use TLS if that server supports it, an approach called opportunistic encryption, done through STARTTLS. It stops anyone on the network from reading the mail as it passes. Traffic between our own services inside a data center should also be encrypted, or at least kept on a private network. Email content is sensitive.

Encryption at rest. Emails are stored encrypted on disk, either at the disk level or in the application. Google, for example, encrypts data at rest on its storage systems, with keys per disk or per service.

True per-user encryption is different: even the provider cannot read the content without the user's key. Gmail does not do that by default, apart from its secure email programs, because search and spam filtering both need to read the content. Our goal is narrower: if someone gets hold of the raw storage, they must not see plain text.

Rate limiting. A rate limit caps how many actions a client may take in a period, and it stops abuse. We limit three things:

  • Incoming SMTP connections per IP address, to slow down spam attacks.
  • Outgoing sends per user, so a hijacked account cannot send thousands of emails and damage our IP reputation.
  • API calls per client, so nobody can overload the search API or another API and deny service to others.

Monitoring and anomaly detection. Anomaly detection means watching for patterns that do not match normal behavior. A sudden spike in outgoing mail from one account may be spam, and a sudden drop in traffic may be an outage. Security teams can use it to lock accounts that look compromised, for example a login from a new country followed by mass emailing.

Indexing Strategies for Fast Search

Inverted indexes. An inverted index maps each keyword to the list of messages that contain it, so search looks up the word instead of scanning every email. The search service likely keeps several indexes: one for bodies, one for headers, and maybe one for senders and recipients. A query combines them as needed.

Prefix indexes. A prefix index matches the start of a value, which is useful for email addresses, so auto-complete and search by sender stay fast.

Where the index lives. With Lucene or Elasticsearch, index files sit on the search servers' local disks, or on attached storage. Each index shard needs a replica on another server, so one failure does not lose it.

Updating the index. Indexing every email inside the delivery path would slow delivery down, so indexing runs on asynchronous workers after the email is stored. If the indexing backlog grows, we need enough capacity to catch up, or we shed some load.

Query optimization. Frequent searches can be cached, though email queries vary a lot, so the gain is limited. But some common filters, like unread or by label, can be answered from metadata instead of the full-text index.

Putting it together: data management. Every part must agree on the same data. Delivering one email causes several writes: to the blob store, the metadata database, the search index, and the notification system.

One ACID transaction across all of them is not feasible at this scale. ACID means all the writes succeed or fail together. Instead we accept eventual consistency, meaning the copies agree after a short delay, not at once, and handle each failure on its own. Each write is designed to be idempotent, so running it twice has the same effect as once.

  • If storage succeeds but indexing fails, we retry indexing later. The email is safe, and search is just incomplete for a while.
  • If the write to primary storage fails, the email must not vanish. The SMTP service retries against a secondary storage node, or logs it for a later retry.
  • A message queue between parts buffers surges, so a slow search index does not slow down mail receipt.

Backups matter too. We take regular backups of the metadata, and may keep live copies in several regions, which makes disaster recovery smooth. Step 9 covers it.

With the data design and the parts settled, the next question is scale: how does this system stay fast under heavy load?
