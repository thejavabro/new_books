Step 6: Detailed Component Design

6.1 Scheduling Algorithm and Reminder Execution Pipeline

The Scheduler Service turns a stored reminder into a message at the right time. It is a distributed cron engine, a program that runs jobs at set times. It is built on the data model from Step 5. Here is how it works.

Scheduler instances and coordination. We run several Scheduler instances to handle the volume. No two of them may ever pick up the same reminder. So we split the work using the keys from Step 5: the time bucket and the segment.

One approach is a primary coordinator for the schedulers. It assigns each instance a set of segments. With 8 workers and segments 1 to 8, each worker gets one segment. With fewer workers than segments, some workers get more than one.

The coordinator also watches heartbeats, short "I am alive" messages that each worker sends every few seconds. When a worker dies, the coordinator hands its segments to another worker, so no due reminder is missed. This reassignment is what gives us fault tolerance.

A simpler option skips the coordinator: each instance knows its own index and takes segment = index mod N. That only works while the set of instances stays stable. The explicit coordinator is more flexible, because it keeps working as instances scale up, scale down, or fail.

Time-based scanning. Each instance runs a loop that scans its own segments for due reminders. The scan runs often, because our timing target is a few seconds. Every second, or every few seconds, it reads the Schedule table for the current time bucket and its own segments.

At 12:00:00, for example, the instance for segment 3 runs SELECT * FROM ScheduleTable WHERE ExecutionMinute = <current minute, in epoch> AND Segment = 3. This reads exactly one partition, so it is cheap. It returns every reminder due in that minute for that segment. With second-level keys, the query matches an exact second instead of a minute.

In practice we fetch a small range up to now, not an exact match, so anything slightly overdue is picked up too. No other instance owns segment 3, so nothing is ever processed twice.

Processing due reminders. For each due reminder, the Scheduler runs six steps:

  1. Fetch and verify the reminder. The schedule entry may hold only the ReminderID, or it may hold the message and channels too. Either way, the user may have edited the reminder since it was scheduled. So the Scheduler reads the row from the Reminders table by UserID plus ReminderID. That is a primary-key read on one partition, so it is fast. It costs one extra read, and it guarantees the latest message and channels.
  2. Compute the target notifications. Work out which channels to send to, and find the addresses. If channels = [Email, Push], fetch the email address and the device push token. These come from the reminder itself, from a user or device service, or from a cache. Then build the payload for each channel, like the email subject and body or the SMS text. Templates can help here.
  3. Enqueue the notifications. Push a message to the Notification Queue for each channel. With one shared queue, the message carries a channel field, and each processor ignores the other types. With one queue per channel, which is simpler, push one message to each relevant queue. Each message holds at least the reminder ID, the user ID, the message content, and the target contact. The queue stores it durably and delivers it to a consumer. If the enqueue fails, we retry, and in the worst case we mark the reminder as not sent. These queue systems are usually highly available.
  4. Schedule the next occurrence. Reminders here are recurring, so we compute the next time after this one. The rule depends on the pattern:
    • Hourly: add the interval in UTC. Every 4 hours means next = now + 4 hours. Schedule times are stored in UTC, so this is plain addition.
    • Daily: add one day in the user's local calendar. This is where the stored TimeZone is used. Read the current execution time in that zone, add one day, then convert back to UTC. A day that crosses a DST change, a Daylight Saving Time shift, is 23 or 25 hours long in UTC, and this method handles it. Say it fired at 9:00 AM PDT on June 1. The next local 9:00 AM is usually 24 hours later in UTC. Across a DST change it is 23 or 25 hours later instead. In Java, ZoneId and ZonedDateTime for the user's zone, then .plusDays(1), adjust for the jump on their own.
    • Monthly: same day of the month each time. If the user set the 15th at 10:00, do that. Some months are shorter. If a reminder is on the 31st and the next month has 30 days, one policy is the last day of that month. Another option is the 1st of the following month. The last day of the shorter month is the common choice.
    • Then update the Schedule Table. Remove the old entry, or mark it done. Insert a new entry with the new NextExecutionTime in UTC, the same ReminderID, and a new random Segment. Random assignment on each insert keeps the load balanced over time, though keeping the same segment would also work. This is one simple write, and the entry is picked up when its time comes. A one-time reminder would just skip the insert. Ours are recurring, so we keep going until the user deletes it.
  5. Acknowledge completion. Update LastSentTime in the Reminders table for record-keeping. Add a history log entry now too, like "reminder X ran at time Y, enqueued to channels Z."
  6. Handle errors. A database update or a queue push can fail. The Scheduler retries a few times, or moves on and lets a later tick pick the reminder up. A reminder must never get stuck, and it must never be enqueued twice. To stop a failover node from processing the same reminder, we can mark it as in progress with an atomic update. A lightweight transaction, a compare-and-set write that only succeeds if the row still holds the value we expect, does this. If our coordination is solid, we may not need it. We also make sends idempotent: doing the same thing twice has the same result as doing it once. If two nodes ever process the same reminder, ReminderID plus timestamp serves as the idempotency key. Channel services check that key and skip a repeat. We design so this does not happen, and keep the check as a second line of protection.

Frequency of checks. Each check is one partition read per segment, so checking every second or every few seconds is cheap. Say there are up to 50k tasks per minute, under 1,000 tasks per second in total. Split across segments, each segment sees a few hundred per second. The Scheduler processes a partition's tasks as one batch.

With minute-level partitions, the Scheduler might run every 10 to 15 seconds and fetch the current minute. Or it fetches a minute a little early and then sleeps. It could even pre-fetch the next minute into memory and dispatch each task on an internal timer at the exact second. That tightens accuracy, but it adds complexity.

A simpler approach uses second precision in the database plus frequent queries. Querying every second makes many tiny queries. Querying every 5 seconds for the next 5-second window is a compromise. Either way, the target is a tolerance of a few seconds, and the tick interval can be tuned.

Scaling the Scheduler. The segment partitioning is what lets us scale horizontally. Say one instance can process 1,000 tasks per second, and peak load needs 10,000. We deploy 10 instances and set the number of segments to match. Each instance queries only its own segments, so they run in parallel safely. Two instances never hit the same partition at the same time.

If an instance goes down, its segments go unqueried until they are reassigned. The coordinator sees the missed heartbeat and moves those segments to other instances or a standby. This has to happen quickly. The new owner may find tasks whose time has already passed, and it processes them anyway, a little late. So delivery stays at-least-once even during a failure. A few notifications may run seconds late, or up to a minute late during a failover.

Avoiding skew and hot spots. A hot spot is one partition or machine that gets far more traffic than the rest. A popular time like exactly 9:00:00 can carry a huge number of reminders, but segments spread that load across many machines. Random segment assignment on insert spreads reminders roughly evenly. If one user has 500 reminders due at 9:00, they scatter across random segments from 1 to N, never all on one segment.

Choose N to be at least the largest number of scheduler instances we may ever run. If we expect up to 20 instances, N=32 leaves spare room, so we can always hand out segments without running out. The coordinator gives each instance a roughly equal count. Some get one more than others when N does not divide evenly.

Example flow. Suppose Alice creates a daily 9:00 AM reminder in PST (UTC-8 in standard time, UTC-7 in DST), at 1 PM on Jan 1. The Reminder Service computes the first occurrence. 9 AM on Jan 1 has already passed, so the next is Jan 2 at 9:00 AM PST, which is Jan 2 at 17:00 UTC. It stores an entry with NextExecutionTime = Jan 2 17:00 UTC.

On Jan 2, as the clock nears 17:00 UTC, the scheduler for that slot picks up the entry. It may query at 16:59:55 for anything due up to 17:00:00, and find Alice's reminder. It fetches the details, message "Daily Stand-up meeting" and channel "push notification," and enqueues them. The Push Notification service sends to Alice's device.

Meanwhile the Scheduler computes the next occurrence: Jan 3 at 9:00 AM PST, which is Jan 3 at 17:00 UTC. It inserts a new schedule entry. In March, when DST starts, 9:00 local moves one hour earlier in UTC, and the Scheduler works that out through the timezone rules. Alice notices nothing. Her reminder always arrives at 9:00 local.

6.2 Notification Delivery per Channel

Once the Scheduler has enqueued the notification events, the Channel Processors deliver them. Each channel service must scale, and each must be reliable.

Email service. This is a cluster of workers that pull email messages from the queue. For each message it builds an email, usually from a template. The subject might be "Reminder: {Reminder Text}." Then it sends through an SMTP server or an email API.

At web scale, direct SMTP is slow, because each send opens a connection. So we use a provider like Amazon SES or SendGrid, which run the email infrastructure for us. We call their API, possibly in batches.

The service handles the result. The API may accept the message, or it may return an error. On a transient error, one that is temporary, like a network problem or a provider outage, the service retries a few times. If it still fails, it logs the failure. It may also push the task to a dead-letter queue, a holding queue for messages that could not be delivered. Or it marks the task in the database for a later retry.

Quotas matter too. A user with 500 daily reminders at the same time sends 500 emails at once. We can rely on the provider's limits, or add our own rate limiting. The user asked for these emails, so we send them. We might stagger them by a few seconds, so they do not look like spam.

Bounces and invalid addresses go onto a "do not send" list. That is more an email system concern than ours. The main point is that this service sends reliably and scales horizontally. We run many instances pulling from the email queue. With Kafka, a consumer group splits the queue's partitions across instances, and each message goes to exactly one consumer.

SMS service. This works like email. It reads SMS events and calls an SMS gateway API like Twilio with a phone number and a message. The phone number is stored in the user profile, keyed by UserID. If it is not in the message, the service does a quick lookup.

Each send returns success or failure. Gateways have rate limits, like a number of messages per second per phone number or per account. We may need to throttle, or buy more capacity. Many SMS instances can send at the same time. The gateway and the telecom networks queue on their side too.

The service retries on failure, like a network timeout or a gateway error. If a phone is invalid or the user opted out, the gateway tells us. We respect that, and we can mark that user's SMS channel invalid. SMS costs money, so we send only what is needed. If the user chose both SMS and another channel, they wanted both, so we send both. Long content is truncated or split across messages.

Push notification service. This handles push for mobile and web. For mobile apps we use Apple APNs and Google FCM. We need device tokens from the user's devices. Assume a separate Device Service holds them. The Push service asks it for all active tokens for the UserID. A user may have a phone and a tablet.

For each device it builds a payload with a title and body. Then it connects to APNs or FCM, usually over HTTP/2 or their APIs, and sends. These services scale well, but they have rate limits and need auth keys and certificates. The Push service manages those.

It also handles responses. If a token is invalid, because the user uninstalled the app, APNs or FCM returns an error. We remove that token from our device database.

Push is fire-and-forget: we hand the message to APNs or FCM, and we do not wait for the device. They deliver to the device when it is online, and they handle their own retries. Our job is to reach their servers. We retry a limited number of times if we cannot. This service scales horizontally too. With Kafka, we can partition by user or device ID to keep ordering per device.

In-app notification service. The user may be in the app now, or may open it later. So the strategy has two parts.

If the user is online, with a WebSocket connection to the server or by polling, we push in real time. A WebSocket server or push gateway that the app is connected to does this. We might reuse an existing real-time system, like Socket.io or a pub-sub for live updates. The In-App service publishes the reminder event to that user's channel.

Also, or if the user is offline, we store the notification durably. This can be the log table, or a separate "notifications inbox" table keyed by user. The next time the user opens the app, it fetches unseen notifications. Many apps have a notification center in-app, and we populate it.

In practice the In-App service receives the event and writes a record to a UserNotifications table. That table is partitioned by UserID, and it holds the notifications and unread flags. Then it pings the real-time system to notify the user right away if possible.

Even if the real-time push fails because the user is offline, the record is saved. The user does not miss it. This service is mostly internal data handling, plus the real-time channel. It scales by partitioning by user. Many app frameworks do this inside the main app. We show it as a service for clarity.

Unified processing. Each channel service runs on its own, but we want some consistency. If a reminder has several channels, they should go out at about the same time. Pulling from the queue, they generally do. Small differences are fine. We just make sure none is badly delayed.

Logging and acknowledgment. After a send, the channel service logs the outcome. A success updates the Notification Log with a delivered status. A failure gets a failed status, and repeated failures can raise an alert. If a message fails after all retries, we could tell the user through another channel. An in-app alert, for example, could report that the email reminder failed. That is an edge case. It may not be needed if they already see it in-app. The logs also feed stats like delivery latency and success rate per channel for monitoring.

Idempotency. The same message ID could be processed twice, from a rare bug or a retry. To guard against duplicate deliveries, each channel service can use an idempotency key. The key is ReminderID plus the scheduled timestamp. The service keeps a cache of recently sent keys and drops a repeat.

Another option is to configure the Notification Queue for exactly-once processing, for example Kafka with careful consumer management. Exactly-once at scale is hard, and at-least-once is more common. Our design uses at-least-once, and it makes operations idempotent. That is simpler.

6.3 Time Zone and Daylight Saving Time Handling

Correct time zone handling is what makes "recurring at 9:00 AM local time" possible. Here is how we handle it.

Storage of time zone. Each reminder carries a TimeZone attribute. It is an IANA time zone string, like America/New_York. The client provides it, since most apps know the user's locale. If not, we default to the user's account timezone. It is stored in the Reminders table.

We keep the original timezone and local time. We never convert to a fixed offset, because offsets change with DST. For example, we store "Every day at 09:00 in America/Los_Angeles."

Normalization to UTC for scheduling. The Schedule table stores NextExecutionTime in UTC. When we schedule the next occurrence, we compute the exact UTC moment using the timezone rules. If local 9:00 AM on that date is 16:00 UTC, we store 16:00 UTC. That is the value the scheduler queries against. This separates the scan from time zone math at runtime. The hard work happens when we compute the next time, not when we query.

Calculating the next occurrence with DST. We rely on standard libraries or algorithms for recurrences.

We can use a library like rrule, the iCalendar recurrence format, or plain date-time arithmetic in the user's zone. For daily and weekly reminders the pattern is the same. Take the last execution's local date and time. Add the interval, 1 day or 7 days, in calendar terms in that timezone. Then convert to UTC for storage. This handles DST shifts by itself. For example:

DST spring forward. Suppose a daily 2:30 AM reminder in a region where clocks jump from 2:00 AM to 3:00 AM, on March 14. On March 13 it fired at 2:30 AM. On March 14, 2:30 AM local time does not exist. The clock skips from 1:59 to 3:00. What does calendar addition do? Most libraries roll such a time forward by the DST gap, so it moves to 3:00 AM, or to the next valid time. We must pick a policy: skip that occurrence, or fire at 3:00 AM. Calendar apps usually fire at 3:00 AM. The user still gets the reminder, 30 minutes late on that one day.

DST fall back. When clocks repeat an hour, a daily 1:30 AM would happen twice. We want one trigger. Most systems fire at the first 1:30, and they do not fire again in the repeated hour. We can get this from library behavior, or store a flag that DST changed. For our scope, assume the timezone rules in a library give an acceptable result. We can document that reminders adjust across DST with, at most, a small one-time shift.

Hourly intervals. An "every 4 hours" reminder can mean fixed increments in absolute time, or clock-time increments. Usually "hourly" means every X hours regardless of DST. So we add 3600*1000 ms per hour to the last UTC time. DST does not change the interval. The pattern relative to local time shifts by an hour during a DST transition, which is acceptable. If a user wanted :00 of each hour in local time, that is a different reading, and less likely. We assume hourly means a fixed period.

Monthly. Month lengths differ. A reminder on the 30th has no date in February. We send it on the last day of February that month. This is an internal rule. Libraries like RRULE can express "last weekday of the month" and more, but we keep our rule simpler. Our rule: if the next date does not exist, use the last day of the month.

A consistent approach. Creating the reminder sets the pattern. Recurring tasks are often stored as a recurrence rule, like an RRULE or a cron expression plus a timezone. For example, "RRULE:FREQ=DAILY;INTERVAL=1;BYHOUR=9;BYMINUTE=0;TZID=America/Los_Angeles" captures it fully. Then each trigger asks a rule library for "the next occurrence after X," instead of doing plain addition. That is more precise, and it handles cases like the DST duplicate hour cleanly. Full RRULE support may be more than we need. The simple custom logic above is fine for typical patterns.

Time zone database updates. Time zone rules change. Countries change their DST laws. Our system must use the latest tz database, the table of time zone rules the libraries rely on. If a zone's offset changes by law and we do not update, reminders in that zone shift. This is rare, and it is beyond what we handle dynamically. It is worth saying that we keep the libraries updated.

User timezone changes. A user may travel, or change their preferred timezone in settings. What happens to existing reminders? They could stay in the original zone. If you set 9 AM in PST and move to EST, maybe you still want PST. Or the user may expect 9 AM in the new zone. This is a product decision. For simplicity, a reminder is bound to the timezone chosen at creation, likely the user's home zone. If the user changes it, we store the new zone and recompute the future times.

Testing DST. We test scenarios at DST boundaries, so nothing double-sends or drops. Take a daily 1:30 AM reminder when the clock goes back, and 1:30 happens twice. We must send once. The scheduler can store the last execution time, and check that the next computed time is not less than or equal to it. Time must never move backwards. Since we compute from the last execution, the next time moves to the next day anyway, so duplicates are avoided.

In summary, storing timezone info and converting correctly keeps scheduled times matched to what users expect. The system works internally in absolute time, UTC, for coordination. Every next-time calculation goes through the user's local calendar.

6.4 Failure Handling and Reliability

A robust system expects failures, and it has an answer for each one:

Scheduler failover and no single point of failure. As described in 6.1, a crashed scheduler instance misses its heartbeat, and the coordinator reassigns its segments. The new instance finds tasks that are already due, maybe a minute past, and processes them anyway. Late is better than lost. Heartbeats every few seconds keep the delay short. The schedule lives in the database, so any instance can pick up any task. Nothing is lost, except the tasks being processed at that moment.

We avoid single points of failure everywhere. The database is a Cassandra cluster with replication. The queue is a Kafka cluster. Load balancers have failover. Each channel service also runs several instances. If one email sender crashes, the others continue, and the queue holds messages until they are consumed.

Exactly-once vs at-least-once delivery. Our design leans toward at-least-once delivery. In rare cases, like a crash at the wrong moment, a reminder may be sent twice. We prefer that over missing it. Say a scheduler enqueues a message and then crashes before it updates the next execution time. Another scheduler retries that task and sends again. We limit duplicates two ways:

  • Use the idempotency key from 6.2: ReminderID plus the scheduled timestamp, unique for each occurrence. Channel services, or even the external providers, can filter repeats of the same key. Or the Notification Queue can de-duplicate, through Kafka exactly-once processing or a de-dup layer.
  • The scheduler can mark an item as being processed, with a status flag in the schedule table, in one atomic operation. Then another node will not process it. This is tricky in Cassandra, where lightweight transactions exist but are costly. The segment approach already stops two nodes from processing the same partition, but it does not cover a crash mid-way. So we accept at-least-once and a rare duplicate, like two emails instead of one. We say so in the non-functional requirements, and we handle duplicates in logic.

Database failures. If Cassandra goes down, or a partition becomes unavailable, the scheduler cannot fetch due tasks or update times. Cassandra is built for high availability. With proper replication, one node down does not make data unreachable. The scheduler retries transient query failures after a short delay.

A multi-node outage is worse. We might temporarily not send some reminders, which is serious. That is why multi-region or multi-cluster replication is worth considering. A standby cluster in another data center could take over if the primary fails. It adds complexity, like keeping two active clusters from double-sending. Within one region we use a replication factor of 3, meaning every row is stored on three nodes, so data stays durable.

Queue failures. If the message queue, Kafka or RabbitMQ, is down, the scheduler cannot enqueue. So the queue must be a reliable cluster too. Kafka survives broker failures when partitions have replicas. If the whole queue is down, the system cannot deliver.

The scheduler could buffer in memory, but memory could overflow. Better to mark the task in the database and try later. If an enqueue fails, we can leave the schedule entry as still due, so the next scan picks it up. Or we move it to a "stuck" state. Either way we alert on it. A highly available queue, or a cloud managed queue with a good SLA, lowers this risk.

Channel failures. If an external email or SMS provider is down or returns errors, the channel service catches it. We use retry policies with exponential backoff, waiting longer after each failed try, up to a limit.

We must also not lose messages. If a channel service crashes while processing a batch, the at-least-once queue redelivers the message, possibly to another instance. So processing must be idempotent. Say the Email service crashes after sending, but before acknowledging the queue. The queue redelivers, and without a check we send a duplicate email. An idempotency key, or a "sent" status in a temporary store, prevents that. Email cannot easily be de-duplicated by content, so we accept a rare duplicate.

Ensuring no notification is lost. Every piece is durable. The schedule is in the database. The queue is persistent, so once the scheduler enqueues, the message is stored until delivered. Each channel attempt either succeeds, or it is logged for retry. If all retries fail, we log the failure. We could alert an admin, or notify the user another way: "We couldn't deliver your reminder via SMS. Please check your phone or settings." That could go by email or in-app. It is optional.

Data consistency on updates. A user may update or delete a reminder just before it fires. That is a race. Our rule is to always check the latest data at execution time.

Take a delete at 10:00 for a reminder due at 10:01. If the delete removes the schedule entry before 10:01, the scheduler does not find it, and nothing sends. Good. If the scheduler had already fetched it just before the delete, we need a safeguard. We mark the reminder as deleted in the main table, and the scheduler re-checks that status before sending. If it sees the deleted flag, it skips. No notification goes out after a delete.

Updates, like a changed time or channels, write to the database too. If the scheduler picked the reminder up seconds earlier with the old info, it might send the old message. This is a narrow window. One fix is a short lock: set a flag while a change is in progress. Another is to update the schedule entry immediately. We could also say that changes to a reminder due in the next minute do not take effect at once, but that is poor UX.

Ideally, an update writes the schedule table atomically. Then even a reminder due in seconds shows the new time, and the scheduler never picks the old one. Lightweight transactions, or a careful order of operations (delete the old schedule entry, then update the main table), get us there.

With these failure cases planned for, the system handles errors without stopping. No single failure stops reminders. At worst some are delayed, and they still go out. Our design aims for high reliability. It uses the same techniques as large-scale systems: redundancy, idempotent processing, partitioning so one failure touches only a slice, and thorough monitoring.
