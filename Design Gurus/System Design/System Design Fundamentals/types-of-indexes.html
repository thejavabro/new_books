Quick Reference

Conclusion

All indexes do the same job: they help the database find rows without reading the whole table. They differ in what they promise, what goes into them, and which queries they can serve.

It helps to hold three groups in mind:

  • What the database promises. Primary and unique indexes.
  • What goes into the index and where it sits. Clustered, non-clustered, composite, covering and partial indexes.
  • A different structure entirely, because a B-tree cannot answer the question. Full-text, hash, bitmap and geospatial indexes.

Everything in the first two groups is a B-tree underneath, so read How a B-Tree Index Works first if you have not.

One warning before the list. Index syntax is not standard across databases, so every example below says which one it belongs to.

1. Primary Index

A primary key is the column, or set of columns, that uniquely identifies a row. A primary index is the index built on that key.

You almost never create it yourself. Declare a primary key and the database builds the index for you, because it needs one to enforce uniqueness.

Worth knowing: "primary index" is a textbook name rather than something you type. In a real database the primary key is backed by a unique index, and in some engines that index is also the clustered index of section 3. If a colleague says primary index, they mean one of those two.

What it gives you. The fastest possible lookup by identity. The database can stop searching the moment it finds a match, since it knows there is only one. Joins that follow a foreign key back to a primary key are fast for the same reason.

What it costs. Almost nothing extra. Every table needs a primary key anyway, and primary key values rarely change.

Use it for the main identifier of a table: a user id, an order id, an account number.

-- Standard SQL, works everywhere
CREATE TABLE Customers (
  CustomerID INT PRIMARY KEY,
  Name       VARCHAR(100),
  Address    VARCHAR(200)
);

The database builds a primary index on CustomerID, so SELECT * FROM Customers WHERE CustomerID = 123 goes straight to the row.

2. Unique Index

A unique index speeds up lookups like any other index, and adds one rule: no two rows may hold the same value in the indexed column.

A primary key is unique by definition, so its index is a unique index. What makes this type worth naming is that you can have several of them on one table, on columns that are not the primary key.

What it gives you. Correctness and speed at once. The index blocks duplicates, and the database knows at most one row can match.

What it costs. A small check on every insert and on every update to the indexed column. The database looks in the index first to confirm the value is not already there.

The detail that bites people is NULL. A primary key column cannot hold NULL at all. A unique index usually can, and in most databases, including PostgreSQL, MySQL and Oracle, two NULLs are not considered equal, so a unique column can hold many rows with NULL in it. SQL Server is the exception and allows only one. If "at most one row per customer may be active" has to hold, do not rely on NULL to express it.

Use it for any column that must not repeat: an email address, a username, an account number, a national identifier.

-- Standard SQL: prevent two users from sharing an email address
CREATE UNIQUE INDEX idx_users_email ON Users(Email);

After this, SELECT * FROM Users WHERE Email = 'alice@example.com' uses the index, and an insert with an existing email is rejected.

3. Clustered Index

A clustered index decides the order in which the rows are physically stored. The index does not point at the data. The index is the data: its leaf nodes hold the actual rows.

Because rows can only be laid out one way on disk, a table can have at most one clustered index. In MySQL's InnoDB and in SQL Server, the primary key is the clustered index unless you say otherwise. InnoDB goes further. If you do not declare a primary key, it uses the first unique NOT NULL column instead. If there is not one, it creates a hidden key of its own. There is always a clustering key.

PostgreSQL is the odd one out and has no clustered index at all. Its CLUSTER command reorders a table on disk once, and rows inserted afterwards go wherever there is room, so the ordering decays.

What it gives you. Range queries and sorted reads become cheap. If a log table is clustered on its timestamp, then "give me everything from the last hour" is one continuous block of disk, read in order. There is no sorting step, because the rows are already sorted.

What it costs. Inserts that land in the middle of the order are expensive. The database may have to split a page to make room. This is why so many tables cluster on an auto incrementing id: new rows always append at the end.

Use it for the column you most often scan a range of, or sort by. A timestamp on a history table. A customer id on an orders table. If nothing stands out, leave it on the primary key.

-- SQL Server only: store the Customers rows in alphabetical order
CREATE CLUSTERED INDEX idx_cust_name ON Customers(LastName ASC, FirstName ASC);

In InnoDB there is no such statement. The clustering key is whatever you declared as the primary key, so you choose it when you design the table.

4. Non-Clustered Index

A non-clustered index is a separate structure that holds the indexed values and a pointer to each matching row. The rows themselves stay where they are. This is the ordinary index, and it is also called a secondary index.

The book analogy fits exactly. The chapters are printed in the author's order, and the index at the back lists keywords with the page numbers where they appear.

What it gives you. Many of them. A table can carry several non-clustered indexes on different columns, so you can support several different queries.

What it costs. Two things. Every index adds work to every write. And when a query uses a non-clustered index, the database has to follow each pointer back to the table to fetch the columns the index does not hold. That extra hop is cheap for ten rows and expensive for a hundred thousand.

The second lookup, and why it exists

Here is the part worth slowing down on, because it explains a lot of real query behavior.

On a table that has a clustered index, a non-clustered index does not store a raw disk address. It stores the clustered key value, and uses that key to find the row.

Why not a physical address? Because rows move. A page split relocates half the rows on a page, a row migration moves a row that grew too large, and a table rebuild moves everything. If secondary indexes held physical addresses, every one of them would have to be corrected each time a row shifted. Storing the clustered key means the pointer is still correct after the row moves.

The cost is a second descent. Looking up an employee by last name on an InnoDB table works like this:

  1. Search the LastName index. This is a B-tree walk, so a few page reads.
  2. It gives you the clustered key, for example EmployeeID = 4271903.
  3. Search the clustered index for that id. Another B-tree walk.
  4. Now you have the row.

Two tree traversals, not one. SQL Server calls step 3 a bookmark lookup or key lookup, and it is the single most common reason a query that "has an index" is still slow. Every matching row pays for it, so an index that matches 100,000 rows performs 100,000 second lookups. Past some threshold the planner decides a full scan would be cheaper, and ignores your index entirely.

The fix is section 6.

Use it for columns that appear in WHERE clauses, join conditions, and ORDER BY, when the filter is selective enough to return a small slice of the table.

-- Standard SQL
CREATE INDEX idx_emp_lastname ON Employees(LastName);

5. Composite Index

A composite index covers two or more columns at once, and treats them as a single sorted key. An index on (LastName, FirstName) sorts by last name, then breaks ties by first name.

What it gives you. One index lookup for a query that filters on several columns, instead of combining results from two separate indexes. It can also cover the query outright, and it saves the storage and write cost of maintaining two indexes.

What it costs. Column order matters, and getting it wrong makes the index useless. Databases follow the leftmost prefix rule: the index serves a query that filters on the first column, or on the first and second, and so on from the left. A query that filters only on the second column cannot use it.

Use it for column pairs that are queried together. Orders by customer and date. Addresses by state and city.

-- Standard SQL
CREATE INDEX idx_orders_cust_date ON Orders(CustomerID, OrderDate);

This index serves WHERE CustomerID = 42 AND OrderDate >= ?, and it serves WHERE CustomerID = 42 on its own. It does not serve WHERE OrderDate >= ? on its own, because OrderDate is not the leftmost column.

Some databases can partly work around this with a skip scan, where the planner loops over the few distinct values of the leading column and does one search per value. It only pays off when the leading column has very few distinct values, and support for it varies, so design the column order properly rather than relying on it.

The practical ordering rule: put the columns you filter with = first, the column you filter with a range last, and the columns you only sort by after those.

6. Covering Index

A covering index is not a different structure. It is any index that already holds every column a query needs, so the database answers from the index and never reads the table at all. Reading only the index is called an index-only scan.

This is the direct fix for the second lookup in section 4. No trip back to the row means no bookmark lookup, however many rows match.

Take SELECT OrderDate, Status FROM Orders WHERE CustomerID = 42.

  • With an index on (CustomerID), the database finds the matching entries and then fetches every row to read OrderDate and Status.
  • With an index on (CustomerID, OrderDate, Status), everything the query asked for is already in the index. The table is never touched.

Some databases let you attach extra columns to an index without making them part of the sorted key, which keeps the key narrow while still covering the query:

-- SQL Server and PostgreSQL
CREATE INDEX idx_orders_cust ON Orders(CustomerID) INCLUDE (OrderDate, Status);

What it costs. Width. Every extra column is copied into the index, so the index takes more space, a scan reads more pages, and an update to any included column now updates the index too. Covering two or three columns for one important query is good practice. Covering fifteen because they might be useful is how an index ends up larger than the table it indexes.

One database-specific catch: in PostgreSQL an index-only scan also needs the table's visibility map to say the pages are all-visible, otherwise it still visits the table. That is one more reason routine vacuuming matters there.

7. Partial Index

A partial index, called a filtered index in SQL Server, indexes only the rows that match a condition. The rest of the table is not in it at all. PostgreSQL, SQL Server and MongoDB support it. MySQL does not, so there you would keep the hot rows in a separate table instead.

Most tables have a query that only ever looks at a small slice. Orders still pending. Users not yet deleted. Jobs waiting in a queue. Indexing all 200 million rows to serve a query that always adds WHERE status = 'pending' spends space and write effort on rows that will never be returned.

-- PostgreSQL
CREATE INDEX idx_orders_pending ON Orders(CreatedAt) WHERE Status = 'pending';

If pending orders are a thousandth of the table, this index is roughly a thousandth of the size. It fits in memory, it is quick to scan, and rows in any other status cost nothing to maintain in it.

A partial unique index is the clean way to express a rule that a plain unique index cannot. "Each user may have at most one active session" becomes a unique index on UserID limited to rows where the session is active.

What it costs. Two rules to respect. The query has to carry a condition the planner can prove implies the index condition, or the index simply will not be used. And a row that stops matching is deleted from the index, which is an ordinary index write, so this makes the index smaller rather than making writes free.

8. Bitmap Index

A bitmap index stores, for each distinct value in a column, a string of bits with one bit per row: 1 if that row holds the value, 0 if it does not.

A Status column with three possible values gives three bit strings. Answering WHERE Status = 'shipped' AND Region = 'EMEA' is then a bitwise AND of two bit strings, which a processor does extremely fast across millions of rows.

This is the one index type that wants the opposite of the usual advice. What are Indexes? says not to put a B-tree on a column with three distinct values. That is right: such an index points at a third of the table, and the planner ignores it. A bitmap on the same column is small and fast, because a bit string over a low-cardinality column compresses very well.

What it costs. Writes. Changing one row's value means rewriting parts of the bitmaps, and the locking involved can block a wide range of rows at once. Bitmap indexes belong in data warehouses and analytical systems that load in batches and then mostly read, not in systems taking constant single-row updates.

Support varies. Oracle offers them directly. PostgreSQL has no bitmap index you can create, but its planner builds bitmaps on the fly to combine several B-tree indexes within one query, which is the same idea applied at query time. Analytical column stores use the technique under other names.

Use it for low-cardinality columns in an analytical system: status, region, category, yes or no flags.

9. Full-Text Index

A normal index treats a whole column value as one entry, so it can find WHERE Title = 'System Design' but not "every article that mentions the word database somewhere in the body". A full-text index solves the second problem by breaking text into individual words and indexing those.

The structure it builds is called an inverted index: instead of mapping a row to its words, it maps each word to the list of rows that contain it. This is the structure search engines are built on, and it is what Lucene, Elasticsearch and OpenSearch maintain.

What it gives you. Fast keyword search over large text, plus four features a B-tree cannot offer. Phrase search. Ranking results by relevance. Ignoring common words like "the". And matching different forms of the same word, so that a search for "run" also finds "running".

What it costs. Building the index is heavy work, since every document has to be parsed and split. Updates are heavy too, so many systems refresh full-text indexes in the background rather than on every write. The index also needs its own query syntax, such as MATCH ... AGAINST in MySQL or CONTAINS in SQL Server.

Use it for large blocks of free text: article bodies, product descriptions, support tickets, comments.

-- MySQL
CREATE FULLTEXT INDEX idx_articles_content ON Articles(Content);

What a search box actually needs

A search box asks three different questions, and they need three different answers.

Typing the start of something is a prefix match. LIKE 'sys%' is a range scan and an ordinary B-tree already serves it, which is why autocomplete on a name or a product code needs nothing special.

Looking for a word inside a body of text is the full-text case above. The inverted index finds it, and it ranks the results too.

Looking for an arbitrary substring, or tolerating a typo, needs a trigram index. It cuts every value into overlapping three character pieces and indexes those, so a search for %esig% becomes a lookup for the pieces "esi" and "sig" rather than a scan. PostgreSQL provides this through the pg_trgm extension, and the same index also powers similarity ranking, so a search for "desgin" can still find "design".

-- PostgreSQL: this is what makes LIKE '%design%' indexable
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_articles_title_trgm ON Articles USING GIN (Title gin_trgm_ops);

There is also one narrow trick worth knowing. If you only ever need a suffix match, index the reversed column. An index on reverse(Email) turns LIKE '%example.com' into a prefix match on the reversed value, which a B-tree serves normally.

Once search becomes a product feature rather than a query, most teams move it out of the database entirely into a dedicated search cluster. Indexes in Distributed Systems covers how that is wired up.

10. Hash Index

A hash index stores entries in a hash table instead of a tree. The database runs the key through a hash function, and the result tells it which bucket holds the pointer to the row.

What it gives you. Exact match lookups in constant time, on average. There is no tree to walk down, just one hash computation and one jump. For a workload that is purely key lookups, this beats a B-tree.

What it costs. All ordering. A hash scatters keys on purpose, so neighboring values land nowhere near each other. That means no range scans, no ORDER BY, no BETWEEN, and no prefix matching. A hash index on a name column is useless for WHERE Name > 'M'.

The "on average" is doing real work in that sentence. Two different keys can hash to the same bucket, which is a collision, and a lookup then has to check a few extra entries in that bucket before it finds the right one. And as the table fills up, collisions become common enough that the index has to be rehashed into a larger table, which is an expensive operation that touches every entry.

Support also varies by database. PostgreSQL offers hash indexes explicitly. MySQL's Memory engine uses them by default for in-memory tables, while InnoDB does not let you create one and uses B-trees instead.

Use it for columns you only ever compare with =, in systems that support it.

-- PostgreSQL
CREATE INDEX idx_customer_code_hash ON Customers USING HASH(CustomerCode);

11. Geospatial Index

Latitude and longitude are two numbers, and a B-tree sorts on one dimension at a time. A composite index on (Latitude, Longitude) finds a band of latitude and then filters the rest by hand, which is close to useless for "everything within five kilometres of me". Points that sit next to each other on a map are not next to each other in that sort order.

A geospatial index, also called a spatial index, is any structure that keeps points which are close on the map close together in the index. Three constructions cover almost everything you will meet.

Geohash. Interleave the bits of latitude and longitude and encode the result as a short string. Nearby points share a prefix, so a proximity search becomes a prefix match, which an ordinary B-tree can serve. The catch is that two points can be metres apart and still fall either side of a cell boundary, so a correct search also checks the neighboring cells. Redis stores locations this way, as geohash values in a sorted set. Google's S2 and Uber's H3 refine the same idea, S2 with a space-filling curve over a sphere and H3 with hexagonal cells.

Quadtree. Split the map into four quadrants, then keep splitting any quadrant that holds more than some number of points. Dense cities end up with deep, small cells and empty ocean stays one large cell, so cell size follows density automatically. This is the structure most often drawn when someone is asked to design a proximity service.

R-tree. Group nearby shapes into bounding rectangles, group those rectangles into larger ones, and continue up to a root. Unlike the first two it indexes shapes rather than only points, so it can answer "which delivery zone contains this address". PostGIS uses a variant of it, and it is the standard answer for polygons.

What it costs. The usual index write cost, plus a query engine that understands distance, plus one thing that catches people out: the index result is approximate. It narrows candidates to a region. Computing exact distances and sorting by them still runs over that candidate set, so a proximity query is a cheap index step followed by a real filter.

Use it for proximity search, ride matching, delivery zones, geofencing, and anything that asks what is near a point.

-- PostgreSQL with the PostGIS extension
CREATE INDEX idx_stores_location ON Stores USING GIST (Location);

💡 Interviewers rarely ask you to name index types for their own sake. They ask a query question and listen for the right structure. "This screen filters by customer and sorts by date, so I would use a composite index on customer id and order date, in that order." Or: "That is a substring search across article text, and a B-tree cannot serve it, so this needs a full-text index." Or: "That is a proximity search, and latitude and longitude in a B-tree will not do it, so I would use a geohash or a quadtree." Naming the structure that fits the access pattern is the answer.

Conclusion

Choosing an index is choosing which queries deserve to be fast. Start from the queries your system actually runs, pick the smallest set of indexes that serves them, and remember that every index you add is paid for on every write.
