Key Takeaways

Check Your Understanding

Know the Vocabulary

This lesson uses the terms below many times. Read them once now, and come back here when a later section needs one.

  • Large language model (LLM): A model that reads text and writes text. Chat assistants and agents are built on LLMs.
  • Token: A short word or a piece of a longer word. Models read and write text as tokens, and providers charge by the token.
  • Tool: A function the model may ask the system to run, such as looking up an order. The model only asks, and ordinary code runs the function.
  • Workflow: A system whose steps are fixed in code at design time. A model may fill in some steps, but it never picks the next step.
  • Agent: A system in which the model chooses the next step at runtime, within limits that code enforces.
  • The loop: The cycle an agent runs: reason, act, observe, and then repeat. It continues until the task is done or a limit stops it.
  • Trajectory: The full path a task takes: every step, every tool call, and every result, in order.
  • Autonomy: How much the system may do without a human in the loop. A human in the loop is a person who must approve or check a step.
  • Budget: A hard limit on one resource for one task, such as steps, tokens, or time.
  • Blast radius: The amount of damage one runaway task could do before anyone notices.
  • Escalation: Handing a task to a person, together with everything the system has found and done so far.
  • Thrashing: Taking step after step without making progress, such as calling the same tool again and again.
  • Frontier model: One of the largest and most capable models a provider offers. It is usually slower and more expensive per token than smaller models.
  • Routing: Sending each piece of work to the model that fits it, such as a cheap model for an easy step.
  • Action space: The full set of actions an agent may choose from. In practice, it is mostly the agent's list of tools.

Part 1: Two Features, One Test

The Problem

The food-delivery company from Module 1's capstone has a support team. In the same week, the team lead asks for two AI features.

The first feature handles support phone calls. After each call, it should write a short summary and a list of follow-up tasks for the ticket.

The second feature handles chat messages. A customer writes, "My order came without the drinks, and the food was cold." The lead's request for this feature is short: "Resolve this customer's issue."

Both features call an LLM, and both call it more than once. Many teams would call both of them agents. This lesson shows why only the second one is an agent. It also shows why that difference changes almost every design decision that follows.

The Definition

The call-summary feature runs three steps in a fixed order. It transcribes the recording, summarizes the transcript, and extracts the action items. A developer wrote that order in code. The model writes the summary and the action items, but it never decides what happens next. The steps are fixed, and the model fills slots in a path that someone else designed.

That is a workflow: a system whose path is fixed at design time.

The chat feature cannot work that way. Nobody knows the right steps until the system looks. Maybe the restaurant forgot the drinks, or maybe the courier was late, which would explain the cold food. Maybe this customer has reported missing items many times this month. Each finding changes what the system should do next. So the model must choose the next step after it sees each result.

That is an agent: a system in which the model chooses the next step at runtime.

This gives one test that separates the two. Ask who chooses the next step, and when. If code chose it at design time, the system is a workflow. If the model chooses it at runtime, the system is an agent.

The diagram below shows the two shapes, one above the other.

Notice that the workflow is a straight line, and the agent is a cycle. A line has a known length, but a cycle has no natural end. So the design must give the cycle an end, as Part 5 shows.

What an Agent Is Not

An agent is not any system that calls an LLM more than once. The call-summary feature makes several calls and is still a workflow.

An agent is not any system that calls tools. A workflow can call a tool at a fixed step, such as "look up the order, then write the reply."

An agent is not defined by human review. A workflow can end with a person who approves the result. An agent can run with no review at all. Review changes how much the system does alone, not its shape.

An agent is not a better or more advanced workflow. It is a different shape with different costs. Part 7 shows when each one fits.

Part 2: The Loop and the Trajectory

Reason, Act, Observe, Repeat

An agent runs the loop, and each pass through the loop is one step. Each step has three parts.

  1. Reason. The model reads everything in its context and decides what to do next. The context is all the text the model receives on this call: the instructions, the tool list, the task, and every earlier step.

  2. Act. The model asks for a tool call, such as "look up order 47110023." The runtime checks the request and runs the tool. The runtime is the ordinary code that hosts the model and runs its tools.

  3. Observe. The tool's result is added to the context as text. The model reads it in the next step.

Then the loop repeats until one of three things happens. The task is done and its result is checked, a budget runs out, or the system hands the task to a person.

Notice that the model proposes each action, but the runtime decides whether it runs. Tool Use and Function Calling explains this split in detail.

Follow One Issue

The steps below follow the cold-food message through the loop. The times and details are illustrative.

Step 1: The model reads the task. At 7:15 PM, the message arrives with the customer's account. The model decides that it needs the order first.

Step 2: It looks up the order. It calls get_customer_orders, and the result shows two drinks on the bill. It also shows that the delivery arrived 35 minutes later than promised.

Step 3: It checks the delivery. The delay may explain the cold food, so it calls get_courier_timeline. The result shows that the food waited 18 minutes at the restaurant before pickup.

Step 4: It checks the policy. It calls search_policies for missing items and late deliveries. The policy allows a refund for missing items. It also allows a credit when an order arrives more than 30 minutes late.

Step 5: It checks the account. It calls get_risk_signals, a tool that reports signs of refund abuse. This customer has no recent claims, so nothing looks unusual.

Step 6: It proposes the fix. It proposes a refund for the two drinks and a credit for the delay. The runtime checks both in code, against the limits inside the tools, and applies them.

Step 7: It writes the reply. The model tells the customer what was refunded and credited, and why. It asks for no tool, so the loop ends.

Nothing in that path was written in advance. If the order had shown the drinks delivered, Step 3 would have looked different. If the account had shown many recent claims, Step 6 would have been an escalation to a person.

The Trajectory

The full record of those seven steps is the task's trajectory: every step, every tool call, and every result, in order. The final reply is only its last line. The stored record of a trajectory is called a trace.

The trajectory matters because two tasks can end with the same reply and still differ a great deal. One task may take 7 steps, while another takes 30 steps, calls the wrong tool twice, and costs five times as much. Only the trajectory shows that difference. Evaluating Agent Trajectories builds its tests on this idea.

Part 3: Autonomy Is a Ladder

Workflow or agent is a question about shape. Autonomy is a second, separate question: it is how much the system may do without a human in the loop.

The two questions combine into the autonomy ladder, a ladder with four rungs. Each rung lets the system do more on its own. The table uses one more term. A write is any action that changes something, such as a refund or a sent message, while a read only looks something up.

RungWho chooses the stepsWhen a person takes partExample
1. Fixed workflowCode chooses every stepOptional, at the endThe call-summary pipeline
2. Model-chosen branchThe model picks one branch from a short list in the codeOptional, at the endA classifier sends a chat to the order-status path or the refund-policy path
3. Agent with human-approved writesThe model chooses each stepBefore every writeThe agent reads freely, but a person approves each refund
4. Bounded agent, reviewed afterThe model chooses and acts within budgetsAfter the fact, on samples and auditsThe agent applies small credits itself, and staff review a sample each day

Rung 2 sits between the two shapes. By the test, the model does choose a next step. But it chooses once, from branches a developer wrote, and each branch is a fixed path. So it behaves almost like a workflow.

Most production agents sit in the middle of this ladder. They run on rung 3, or on rung 4 for low-risk actions only. Saying so in an interview is not a weakness. It shows an honest read of where real systems sit, instead of a hype claim from marketing material. A candidate who places a design on a named rung, and explains why, sounds like someone who has run one.

One system can also sit on different rungs for different actions. The support agent may add case notes on rung 4 and still need approval for large refunds on rung 3. Evaluating and Controlling Agents shows how a system moves up one action type at a time, as evidence builds. That lesson uses the name autonomy ladder for the stages of that climb: suggest, approve, bounded auto, and audited auto. This lesson's rungs say where a design sits today, and those stages say how one action type earns its way up.

Part 4: Errors Compound

The Arithmetic

Suppose each step of an agent is right 95 percent of the time, which sounds reliable. Now suppose a task needs 10 steps, every step must be right, and nothing catches a mistake. The chance that all 10 steps are right is 0.95 multiplied by itself 10 times, which is about 0.60.

So the task completes correctly only about 60 percent of the time. Small errors at each step compound: they multiply across the steps of a trajectory.

The table shows how fast this happens. It assumes that every step must succeed and that nothing recovers from an error.

StepsReliability per stepChance the whole task is right
595 percentAbout 77 percent
1095 percentAbout 60 percent
2095 percentAbout 36 percent
1099 percentAbout 90 percent

Real steps are not fully independent, and good designs catch some errors. So treat these numbers as a direction, not a forecast. The direction is clear: more steps mean more chances to fail.

Why Agents Compound and Chat Does Not

A chat model also makes mistakes, but each chat answer stands mostly on its own. A wrong answer to one question does not change the answer to the next question.

An agent's steps are chained, because each result becomes part of the next step's context. Suppose Step 2 reads the wrong order. Then Step 3 checks the wrong courier, and Step 4 applies a policy to the wrong facts. Nothing between the steps checks the error, so it flows forward unchecked.

Confused Agents Fail Quietly

A confused agent rarely fails loudly. It does not throw an error or stop to ask for help. Instead, it keeps going: it calls another tool, rewords its search, or tries the same call again. Each of those steps reads the whole context again, so each one spends tokens.

So an agent cannot be trusted to notice its own trouble. Its limits must be enforced by the runtime, in code. Asking the model to stop in the prompt is not enough.

Is a Bigger Model the Fix?

A stronger model helps, because it raises the reliability of each step, and every step in the chain gains. But no model reaches 100 percent, and even at 99 percent per step, a 10-step task still fails about one time in ten.

So the architecture must bound the error as well. Three moves do most of the work.

  • Use fewer steps. Give the agent tools that each do one whole job, so a task needs fewer calls.
  • Check between steps. Validate tool requests and results in code, so an error is caught before the next step reads it.
  • Bound the loop. Cap the steps, the cost, the time, and the possible damage, as Part 5 explains.

Part 5: Every Loop Ships With Budgets

The Four Budgets

This lesson's first design law is short: every loop ships with budgets. Each budget is a hard limit on one resource for one task. The runtime enforces it, and the model cannot change it.

Four budgets cover most designs. The example values below fit a support agent, and they are illustrative assumptions.

  1. Max steps. A cap such as 12 steps stops a loop that keeps going without progress.

  2. Max tokens or cost. A cap such as $0.50 of model spend per task stops a task that grows too expensive.

  3. A wall-clock timeout. Wall-clock time is the real time that passes. A timeout such as 90 seconds stops a task that waits too long on slow tools while a customer waits.

  4. Spend and blast-radius caps. Caps such as one refund and three actions that move money or change an order limit what the task can do to the world.

The first three budgets limit what the task uses. The fourth limits what the task can change. It controls the blast radius: the amount of damage one runaway task could do before anyone notices. A loop with a refund tool and no cap could issue refunds until someone reads the logs. With a cap of one refund, the worst case is one refund.

When a Budget Runs Out

Decide in advance what happens when any budget runs out. The plan has three parts: stop, summarize progress, and escalate with state intact.

  • Stop. The runtime ends the loop, and it does not give the model one more try.
  • Summarize progress. The system records what it found and what it already did. For example: "Order 47110023 is missing two drinks. Delivery was 35 minutes late. No refund was issued."
  • Escalate with state intact. A person receives the task with that summary and the full trajectory. They continue from where the agent stopped, instead of starting over.

An escalation is not a failure of the design. It is the planned exit for work the agent should not finish alone. Agent Memory and Context shows how to store task state so that work can resume safely.

The diagram below shows the loop with its four budgets and its two exits.

Notice that the budget check sits in the runtime, outside the model. The model never decides whether it may take one more step.

Thrashing: A Signal to Act On

Budgets also turn a quiet failure into a visible one. Suppose a research agent has a cap of 60 steps, and its tasks usually take about 8. One task's trace shows it on step 40.

That agent is most likely thrashing: taking step after step without progress. It may be repeating a search that finds nothing, or retrying a tool that keeps failing. A longer trajectory here does not mean more careful work. The right response is to snapshot the state and escalate to a person, not to let the task run to step 60. A snapshot is a saved copy of everything the task has found and done so far.

The example also shows how to set a step cap. Start from the normal step count and add some room. A cap far above the normal count lets a thrashing task waste many steps before it stops.

The Same Mistake as an Unbounded Retry Loop

Engineers know this mistake from classic system design, where it is called the unbounded retry loop. A client that retries a failed call with no limit adds load to a service that is already struggling. When many clients retry at once, they create a retry storm, also called a stampede. It is a burst of requests that keeps the service from recovering. Model Serving Basics gives the standard fix, a small and fixed retry limit.

An unbounded agent loop is the same mistake in a new form. It repeats work with no limit and spends resources while it does. The fix is also the same: a hard cap, enforced in code, and a planned exit.

Part 6: What an Agent Task Costs

One Inference Versus Many

A chat answer is one inference, which is one call to the model. An agent task is many inferences, one per step. And each step reads a larger context than the step before it.

The reason is that the model keeps no memory between calls. So on every step, the runtime sends the whole history again: the instructions, the tool list, the task, and every earlier request and result. Each step re-reads the whole history so far, and that history grows by one step each time. So the cost of each step climbs as the task goes on. Agent Memory and Context shows how to keep that history smaller, but it still grows.

A Worked Example

The prices below are the example prices from Inference Economics. A frontier model costs 12 per million output tokens. Check current prices before you rely on them.

Step 1: Price one chat answer. Assume 3,000 input tokens and 300 output tokens. The input costs 0.0036. One chat answer costs about $0.0126, or about 1.3 cents.

Step 2: Size the agent's first step. Assume the first step reads 4,000 tokens: the instructions, the tool list, and the task. Assume each step writes about 200 output tokens.

Step 3: Add the growth. Assume each step adds about 1,500 tokens to the history: the model's tool request plus the tool's result. So the second step reads 5,500 tokens, the third reads 7,000, and the fifteenth reads 25,000.

Step 4: Add up 15 steps. The input across all 15 steps comes to about 217,500 tokens, which costs about 0.04, so the whole task costs about $0.69.

Step 5: Compare. $0.69 is about 55 times the cost of one chat answer. If each step added 3,000 tokens instead, the task would cost about 90 times as much. So in this example, a 15-step agent task costs roughly 50 to 100 times a single chat answer.

Notice where that multiple comes from: fifteen calls with no growing history would cost about 17 times a chat answer. The growing history more than triples that.

The support agent's example budgets fit this math. Under the same assumptions, a task that uses all 12 of its steps costs about 0.50 cost cap, and about 37 times a chat answer. So the cap is a ceiling sized for the longest allowed task. Shorter tasks, and tasks that keep their context small, cost far less.

Many providers offer prompt caching, which Serving Optimizations explains. It bills the repeated start of the history at a discount. That lowers the cost, but the history still grows with every step.

Routing Inside the Loop

Not every step needs the strongest model. Some steps are mechanical, such as pulling an order number out of a message or shortening a long tool result. Other steps need judgment, such as planning the next step or deciding whether the issue is really solved.

Routing inside the loop sends each kind of step to the right model. Cheap models handle the mechanical steps, and a frontier model handles the planning. In the course's examples, a small model costs about a tenth of the frontier price. Test the cheap path on real tasks, so the saving does not cost quality. Serving Optimizations covers routing in detail.

Put the Cost Near the Top

Because the cost multiplies this way, it is a design input, not a detail. In an interview, "What does one task cost?" belongs near the top of your opening. It should not arrive at the end as an afterthought. The cost per task shapes the budgets, the routing, and whether an agent is affordable at all.

Part 7: Workflow, Agent, or Both

The Decision Rule

The earlier parts showed what an agent costs. Its errors compound, its loop needs budgets, and each task takes many inferences. The decision rule says when those costs are worth paying.

  • Choose a workflow when the path is knowable. If you can list the steps up front, write them in code. The result is cheaper, faster, easier to test, and easier to explain.
  • Choose an agent when the path depends on what gets discovered along the way. If each next step depends on the last result, and the possible paths are too many to list, a workflow cannot cover them.

The table sorts some common tasks by this rule.

TaskShapeWhy
Call summary: transcribe, summarize, extract action itemsWorkflowThe steps are fixed, and the model fills slots
Draft-then-approve email: the model drafts, a person approves, the system sendsWorkflowThe steps are fixed, even though a person reviews
Document processing: read each restaurant menu, extract the dishes, validate, storeWorkflowEvery document follows the same steps
Support issue diagnosis: "resolve this customer's issue"AgentThe next check depends on what the last check found
Live debugging: find why a service is failing right nowAgentEach finding decides where to look next
Open-ended research: compare refund rules across many sourcesAgentThe next source to read depends on what earlier sources say

Notice that the number of steps does not decide the shape. The call summary has three steps and is a workflow. A simple support issue may take only two steps. It is still an agent if the model chose them.

The Hybrid: An Agent Core Inside a Workflow

Real systems rarely use one shape for everything. The production norm is a hybrid: an agent core for the open part of the task, wrapped by a workflow.

The support chat shows the pattern. A workflow handles the parts with a known path. First, it identifies the customer and classifies the message. A simple policy question then takes a fixed path to an answer from retrieval, with no agent. Only an active order problem enters the agent core. When the core proposes an action, a fixed step checks it: the action gate. The action gate is a checkpoint in the runtime that reviews every proposed action before the system carries it out. An action that passes the gate is applied, and an action that fails it is sent to a person.

The diagram below shows the hybrid.

Notice that the agent core has a small action space. It gets a few tools that read orders, policies, and risk signals, and a few capped tools for credits and refunds. It does not get every tool in the company. The action space is narrowed by design, because complexity must earn its place. Each extra tool is another way to choose wrong, another thing to test, and more tokens in every step's context.

Capstone: A Customer-Support Agent designs this hybrid in full.

Part 8: Using This in an Interview

The 30-second answer (to "resolve this customer's issue"): "First, the test: the next step depends on what we find in the order, the delivery, and the account. So the open part needs an agent, and intake and policy questions stay in a workflow around it. Next, the bounds: the loop gets 12 steps, 90 seconds, $0.50 of model spend, one refund, and three money or order changes in total. When a budget runs out, it stops, summarizes, and escalates with state intact. Then the cost: every step re-reads a growing history, so one task costs dozens of chat answers. I route mechanical steps to a cheap model."

That opening states the test, then the loop's bounds, then the cost, all up front. Before you draw a single box, the interviewer knows that you can tell an agent from a workflow. They also know you plan for how it fails and what it costs.

Likely follow-ups:

  1. "Isn't a bigger model the fix for compounding errors?" It helps, because it raises reliability at every step. But it never reaches 100 percent, and 10 steps at 99 percent still fail about one time in ten. The architecture still has to bound the error with fewer steps, checks between steps, and budgets.
  2. "Why not make it fully autonomous?" Most production agents sit in the middle of the autonomy ladder. I would let this agent read freely and apply small, capped credits. A person would still approve large refunds. It earns more autonomy one action type at a time, with evidence.
  3. "A task that usually takes 8 steps is on step 40. What is happening?" It is most likely thrashing, and more steps here do not mean more thorough work. The system should snapshot the state and escalate to a person. The step cap should also sit much closer to 8.

Common Mistakes

Mistake 1: Calling Every LLM Feature an Agent

Several model calls, a tool call, or a review step do not make an agent. Apply the test, and ask who chooses the next step, and when.

Mistake 2: Building an Agent for a Knowable Path

If the steps can be listed up front, a workflow is cheaper, faster, and easier to test. Save the agent for the part where discovery decides the path.

Mistake 3: Shipping a Loop Without Budgets

A loop with no limits fails quietly and expensively. Set max steps, max tokens or cost, a timeout, and action caps, and plan the escalation.

Mistake 4: Pricing an Agent Like a Chat Answer

An agent task is many inferences over a growing history. Estimate the cost per task early, and route mechanical steps to cheaper models.

Mistake 5: Promising Full Autonomy

Production systems rarely run with unbounded autonomy. Place the design on a rung of the ladder, and say what evidence would move it up.

FAQs

Q: Is a system that calls tools always an agent?

No. A workflow can call a tool at a fixed step. It becomes an agent only when the model chooses the next step, at runtime.

Q: Does a human approval step turn an agent into a workflow?

No. Approval changes autonomy, not shape. An agent whose writes need approval is still an agent, on rung 3 of the ladder.

Q: Can a step budget stop a task the agent could have finished?

Yes. That is a trade, and it is usually the right one. Set the cap from the normal step count, with room to spare, and measure how often tasks hit it. A task that hits the cap goes to a person with its state intact, so the work is not lost.

Q: Should every agent use as few steps as possible?

Yes, within reason. Fewer steps leave fewer chances for errors to compound. But do not remove steps the task really needs, such as checking the policy before a refund.

Q: Should the planning steps always use the frontier model?

No, not always. Start with a strong model for planning, because a planning error flows into every later step. Then test cheaper models on real tasks, and switch only where the quality holds.

Key Takeaways

  • One test separates a workflow from an agent. Ask who chooses the next step: code at design time means a workflow, and the model at runtime means an agent.
  • An agent runs a loop of reason, act, and observe. The full path of steps, calls, and results, in order, is the trajectory.
  • Autonomy is a ladder. It runs from a fixed workflow, to a model-chosen branch, to an agent with human-approved writes, to a bounded agent reviewed after. Most production agents sit in the middle.
  • Errors compound across steps. At 95 percent per step, a 10-step task is right only about 60 percent of the time.
  • Every loop ships with budgets. Cap the steps, the tokens or cost, the time, and the actions. When a budget runs out, stop, summarize progress, and escalate with state intact.
  • An agent task costs many inferences over a growing history. In this lesson's example, 15 steps cost roughly 50 to 100 times a chat answer.
  • The production norm is a hybrid. An agent core handles the open part, and a workflow wraps it.
  • In a system design interview, open with the test, then the loop's bounds, then the cost per task. Place the design on a rung of the autonomy ladder, and say why.

Check Your Understanding

1. A pipeline reads each restaurant menu, extracts the dishes, translates them, and stores them, with three LLM calls. Is it an agent?

Show answer

No, it is a workflow. Code fixed the order of the steps at design time. The model fills in the extracted dishes and the translations, but it never chooses the next step.

2. Each step of an agent is right 95 percent of the time. Why can a 20-step task be right only about a third of the time?

Show answer

Because errors compound across the steps. If every step must be right and nothing catches errors, the chances multiply: 0.95 multiplied by itself 20 times is about 0.36. Each step's result also feeds the next step's context, so one error flows forward unchecked.

3. An agent's cost budget runs out halfway through a refund case. What should the system do?

Show answer

Stop, summarize progress, and escalate with state intact. The runtime ends the loop and records what the agent found and did. A person then continues from that point instead of starting over.

4. Why does the fifteenth step of an agent task cost more than the first step?

Show answer

Because each step re-reads the whole history so far. The model keeps no memory between calls, so every step sends the instructions, the task, and all earlier requests and results again. In the lesson's example, the first step reads 4,000 tokens and the fifteenth reads 25,000.
