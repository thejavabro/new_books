Check Your Understanding

Know the Vocabulary

This lesson uses the terms below many times. Read them once now, and come back here when a later section needs one.

  • Model server: A service that loads a trained model and returns its predictions over the network.
  • Stateless service: A service that keeps no memory of past requests between calls. Each answer depends only on the current request and the data it reads.
  • Replica: One running copy of a service. A load balancer spreads requests across many replicas.
  • Latency budget: The most time a request may take, split into a share for each stage of the work.
  • p99 latency: The time that 99% of requests beat. Only the slowest 1% take longer.
  • Batching: Scoring several requests together in one model run, instead of one at a time.
  • Model compression: Making a model smaller and faster. Distillation, quantization, and pruning are the three common methods.
  • Model registry: A store that keeps every approved model version, with its quality results and the data and code that produced it.
  • Shadow deployment: Running a new model on live requests while only the old model answers users. The new model's results are logged, never shown. Running this way is also called shadow mode.
  • Canary release: Sending a new model to a small share of users first, then to more users in steps.
  • Sticky assignment: Sending the same user to the same model version every time.
  • Rollback: Pointing serving back at the previous model version when a new one causes harm.
  • Fallback: The answer the system gives when the model is slow or down, such as a cached value or a simple average.
  • Fail open and fail closed: Two choices for when a safety check cannot run. Fail open lets the action through. Fail closed blocks it.

Part 1: What It Means to Serve a Model

Training vs Serving split the system into two planes. The offline plane trains a model and stores it in the model registry. This lesson is about the other side: how that stored model answers live requests.

The running example is the food-delivery company's delivery-time model. When a customer opens checkout, the app asks for an estimate of the delivery time (ETA). The model is a gradient-boosted tree, which is a model built from many small decision trees. Each tree corrects the mistakes of the trees before it. The estimate must appear within about 100 milliseconds (ms).

The Model Server

A trained model is a file that holds what training learned, and a little code that turns inputs into a prediction. For a neural network, the learned values are numbers called weights. For a tree model, they are the split rules and the values in each tree. A file alone answers nothing. Something must load it and expose it to callers.

A model server does that job. It starts, reads one model version from the registry, and loads it into memory. Then it waits for requests. For each request, it receives the features, runs the model, and returns the prediction.

Stateless by Design

A good model server is a stateless service. It keeps no memory of past requests between calls. The model file is loaded once at startup, and it does not change while the server runs. Everything else arrives with the request or comes from the feature store.

Statelessness gives three benefits:

  • Any replica can answer any request. The load balancer does not need to send a customer back to the same machine.
  • Scaling is simple. More traffic means more replicas, and quiet hours mean fewer.
  • Failures are cheap. A crashed replica is replaced by a new one, and no data is lost.

A new replica should not take traffic the moment it starts. It loads the model, runs a few test predictions, and then reports that it is ready. This step is called a readiness check. It keeps slow first requests away from real users.

What a Model Server Is Not

A model server is not a training job. It never changes the model while it runs. A new model means a new version from the registry.

A model server is not a database. It does not keep past predictions; it sends them to a log, and other systems store them.

A model server is not always a GPU machine. A tree model like the ETA model runs well on ordinary CPUs.

Two Ways to Package the Model

There are two common ways to place the model. The table compares them.

Separate model serviceModel inside the application
How it runsIts own service; the application calls it over the networkLoaded inside the application's own code
LatencyOne extra network hop, often a few msNo network hop
DeploysA new model ships without an application releaseA new model ships only with a new application release
ScalingThe model scales on its ownThe model scales only with the application

Notice the trade. Putting the model inside the application removes a network hop. But it couples the two deploys, and it blocks independent scaling. Most teams start with a separate model service. They embed the model only when it is tiny and every millisecond counts.

Part 2: The Latency Budget

A predictive serving path usually owes its caller somewhere between 10 and 100 ms, end to end. That total is not one number to hope for. It is a budget, and a good design splits it by stage.

Averages Hide the Slow Requests

Latency targets are usually set on p99, not on the average. A p99 of 80 ms means 99% of requests finish in under 80 ms. The average can look fine while 1 in 100 customers waits far longer. At thousands of requests per minute, that 1% is many real people.

The Budget, Stage by Stage

The table below splits one ETA request into its stages. The ranges are illustrative assumptions, not measurements.

StageWhat happensExample range
Routing and checksThe request reaches a replica; login and input are checked1 to 5 ms
Feature fetchStored features are read from the online feature store5 to 20 ms
Request-time featuresValues that exist only now are computed, such as route distance0 to 15 ms
Model inferenceThe model runs on the features1 to 10 ms
ResponseThe estimate is adjusted and returned1 to 2 ms
LoggingThe prediction is written with its features and model versionNot on the critical path

Notice which stage is largest. The feature fetch is the usual bottleneck. It may read several stores, and each read adds network time. Request-time features can cost up to 15 ms here, because the route distance may need another service. Model inference, at 1 to 10 ms, is often one of the smaller lines.

The table lists the stages in order, but they do not all have to wait for each other. The feature fetch and the route call need nothing from each other, so they can run at the same time. The request then waits only for the slower of the two. Features and Feature Stores explains where each kind of feature comes from.

Notice the last row too. The critical path is the chain of steps the user waits for. Logging is kept off it. The service hands the log record to a background writer and returns the estimate at once. A slow log store then cannot slow down checkout. Monitor how many log records are lost, though, because those records become future training data.

The diagram below shows the same request as a chain of stages, with the logging step off to the side.

Every Call Needs a Timeout

A budget only works if each stage stops when its share runs out. A timeout is the limit on how long the service waits for one call. If the route service has not answered within its share, the service stops waiting. It uses an approximate value instead, such as straight-line distance.

Retries need care too, because a retry repeats a failed call. One quick retry can help. Many retries on a slow service add load and make it slower. So set a small, fixed retry limit, and never retry past the budget.

Part 3: Making Serving Faster and Cheaper

Measure each stage before you change anything. The fix depends on which line of the budget is too large. Three tools cover most cases.

Tool 1: Feature Caching

Feature caching keeps recent feature values in the service's memory. It speeds up reads for hot entities. A hot entity is one that many requests ask about, such as a popular restaurant during dinner or a trending video. Many checkouts in the same minute may need the same popular restaurant's features. The service reads them once and reuses them.

Each cached value expires after a short time, such as a few seconds. Use a cache only where the feature's freshness target allows that delay.

This cache does not break statelessness. It is a copy of data from the feature store, not a memory of past requests. A replica that loses its cache gives the same answers, only more slowly.

Tool 2: Batching

Batching scores several requests in one model run. It helps throughput, which is the number of requests served per second. For many models, a GPU can score 100 requests in barely more time than one. A CPU also gains, though usually less.

Live requests arrive one at a time, so the server waits a moment to collect them. This is called micro-batching. The server waits a few milliseconds, then scores whatever has arrived. A request may wait up to that long before its model run starts. So the maximum wait must be small and must fit inside the budget.

Tool 3: A Smaller Model

Model compression makes a model smaller, so it runs faster and needs less memory. There are three common methods:

  • Distillation trains a small model to imitate a large one. The large model is called the teacher. The small model, called the student, learns to copy the teacher's outputs.
  • Quantization stores the weights in fewer bits. For example, each weight may use 8 bits instead of 32. Memory use drops, and speed often rises, usually with a small loss in quality.
  • Pruning removes weights that add little to the output. It is less common in practice than the other two. The speed gain often depends on special hardware or software support.

Each method can cost some quality, so evaluate the smaller model the same way you evaluated the original.

CPU or GPU?

A GPU is a chip that runs many simple calculations at the same time. It is fast for large neural networks and costly to keep running. Reach for a GPU only when the model is a deep network so large that CPU latency breaks the budget.

Most classic models do not meet that test. The ETA model and many fraud models are tree models on tabular data, which means data in rows and columns. They run well on CPU replicas.

A useful rule is to compress before you change hardware. A distilled model on CPUs can be faster and cheaper than the original model on GPUs. Try that first, and buy GPUs only if no smaller model meets both the quality target and the latency budget.

What the Serving Fleet Costs

Here is a rough estimate for the ETA model. Every number is an assumption for illustration.

Step 1: Estimate the peak. Assume about 500,000 orders a day. Many customers open checkout more than once, and some leave without ordering. So assume about 1.5 million estimates a day. That is about 17 requests per second on average, and perhaps 70 at the dinner peak.

Step 2: Measure one replica. Suppose a load test shows that one CPU replica serves 150 requests per second within the budget.

Step 3: Add room for failure. One replica could carry the peak alone. But if it fails, nothing answers. Run four, two in each of two data centers. If one data center fails, the other two replicas still carry the peak with room to spare.

Notice that failure, not load, sets the replica count here. That is common for a small model with modest traffic.

Four small CPU machines are a modest bill. The feature pipelines and the route service often cost more than the model itself. That is typical for a small model, and the opposite of the large language models later in the course.

Part 4: Shipping a New Version Safely

A new ETA model has just been registered. It got into the registry because it already passed offline evaluation. That means it beat the current model on held-out past data. Offline Evaluation: Choosing the Metric covers how that comparison works.

That win earns the model the right to be tested. It does not prove the model is better for users. Live traffic brings slow features, missing values, and real behavior that past data cannot show. So the rollout climbs a ladder, one step at a time. Each step can stop the climb.

Step 1: Offline evaluation. This step is already done. A model that fails it never reaches the registry.

Step 2: Shadow deployment. The new model receives a copy of live requests and scores them next to the current model. Its predictions are logged but never used to answer a real user. Engineers compare the two models on the same requests. They also check the new model's latency, errors, and memory use. Shadow mode has a cost: it doubles the inference cost on the shadowed traffic. To limit it, shadow only a sample of requests.

Step 3: Canary release. The new model now answers a small share of users, such as 1%. The split is by user, and it is sticky. A hash is a fixed calculation that turns an ID into a number. A hash of the user ID picks the version, so the same user always lands on the same model version.

Step 4: Ramp up. If the canary stays healthy, the share grows in steps, such as 5%, 25%, 50%, and then 100%. Each step lasts long enough to collect useful data.

Why the Canary Split Is Sticky

Splitting by request would send each request to a random version. The same customer could see 32 minutes, refresh, and see 41 minutes. That is confusing, and it damages trust.

It also spoils the measurement. A customer who saw both models cannot show which model changed their behavior. A sticky split by user keeps each person's experience consistent, and it keeps the two groups cleanly apart.

Rollback Triggers, Named in Advance

Before the canary starts, write down what will stop it. A good trigger names a metric and a threshold. For the ETA model, a trigger might be: "Roll back if checkout conversion drops 2% or p99 exceeds 100 ms." Checkout conversion is the share of checkouts that become orders. The drop is measured against the users who still get the current model.

When a trigger fires, rollback means repointing serving at the previous registry version. Nothing is retrained, and nothing is deleted. Keep the previous version loaded and warm during the rollout. Rollback then takes seconds instead of a full deploy.

Some models need a matching file from the same training run. A retrieval model needs an item index built by the same model version, as Embeddings and Two-Tower Retrieval shows. Promote the model and its index together, in one step, and roll them back together. Serving then never mixes two versions.

Canary or A/B Test?

A canary and an A/B test can use the same router, but they ask different questions. A canary asks whether anything is broken. An A/B test asks whether the new model is better on the business metric.

Running an A/B test between two models is cheap to set up. Use the same service with two loaded versions. The router splits users between them, sticky by user. No second cluster is needed.

The expensive part is time. An A/B test must wait for statistical significance, which means enough data to trust that the difference is real and not chance. That can take days or weeks of traffic. This is why shadow mode runs first. It filters out weak candidates before they cost you an experiment.

Remember one rule: offline metrics earn a model the right to be tested. The online experiment is the real evaluation. Online Experiments and A/B Testing explains how to run that experiment well.

Part 5: When the Model Fails

Every model server will sometimes be slow or down. A replica crashes, a feature store lags, or a new version has a bug. Decide in advance what the user sees instead.

The Fallback Ladder

A fallback ladder lists the answers to use when the model cannot answer, from best to worst. The system takes the highest rung that works.

  1. The previous model version, kept warm and ready. It is almost as good as the current model, and it is already loaded.

  2. A cached recent prediction for this exact entity. For example, the estimate this customer got for this restaurant a minute ago, before a refresh.

  3. A simple heuristic. For example, the population average ETA, or this restaurant's average delivery time.

  4. A product-level default. For example, a wide standard window such as "40 to 55 minutes." For a recommendation shelf, it might be an unpersonalized shelf of popular items.

Each rung down gives a worse answer, but any answer arrives in time. Test every rung before it is needed, and count how often each one is used. A rising fallback rate is an early warning that something is wrong.

The diagram below shows the ladder for the ETA model.

Fail Open or Fail Closed

Some models guard an action instead of showing a number. A fraud model decides whether a payment may go through. When it times out, the system has two choices:

  • Fail open: let the payment through. Customers are not blocked, but some fraud may pass.
  • Fail closed: block or hold the payment. Fraud is stopped, but honest customers are turned away.

This is a product and policy call, not a pure engineering decision. The answer depends on the cost of fraud, the cost of a lost sale, and the rules the business must follow. Many systems mix the two. For example, small payments may pass, and large ones may be declined or sent to an extra check. Design Fraud Detection works through that policy in detail. Engineers must still build the chosen behavior, test it, and alert when it runs.

Queued Work and the Dead-Letter Queue

Not all inference answers a waiting user. Some work comes from a queue, such as scoring each new restaurant photo. Here, one bad input can crash the worker that picks it up. If the job is put back on the queue, it can crash the next worker too.

A dead-letter queue stops that chain. It is a separate queue for jobs that keep failing. A common rule: a job that crashes a worker twice is set aside there, and an engineer is alerted. The other jobs keep flowing while someone studies the bad one.

Required Writes and Optional Writes

Some writes must succeed before the system answers, such as saving the order. Others are optional for the answer, such as the prediction log. Do the required writes first. Send the optional ones to a background writer, so a slow log store never fails a request.

Part 6: Using This in an Interview

The 30-second answer (to "how would you deploy and serve this model?"): "The model runs as a stateless service, with several CPU replicas behind a load balancer. Each replica loads one version from the registry at startup. The request path has a latency budget split by stage, and feature fetch usually costs the most. A new version runs in shadow first, then as a sticky canary by user. I'd roll back if a named metric crosses its threshold, such as p99 above 100 ms. If the model is down, a fallback ladder starts with the previous version."

Likely follow-ups:

  1. "Do you need GPUs for this fraud model?" No, if it is a gradient-boosted tree. Say that CPU replicas are enough and that they keep cost low. For example, assume CPU replicas serve the same traffic at about half the cost of a GPU cluster. The real saving depends on the model and the traffic. Mention a GPU only if a deep network breaks the latency budget on CPUs.
  2. "How would you decide when to roll back?" Name the metric and the threshold before the canary starts. For a feed, one example is: "Roll back if session click-through rate drops 2% or p99 exceeds 150 ms." Click-through rate is the share of shown items that users click.
  3. "How would you A/B test two models cheaply?" Load both versions in the same service, and let the router split users sticky by user. Then say that waiting for a significant result is the real cost, which is why shadow mode filters candidates first.

Common Mistakes

Mistake 1: Reaching for a GPU Cluster by Reflex

A tree model on tabular data usually runs well on CPUs. Saying "GPU cluster" for it adds cost and shows that the budget was not checked. Compress the model first, and choose hardware from measured latency.

Mistake 2: Shipping Straight to All Users

A model that wins offline can still fail on live traffic. Skipping shadow and canary means every user meets the bug at once. Climb the ladder, even when the offline result looks strong.

Mistake 3: Splitting the Canary by Request

A split by request shows one user two different models. Their experience becomes inconsistent, and their behavior cannot be traced to one version. Split by user, and keep it sticky.

Mistake 4: Promising to "Watch the Dashboards"

A vague promise is not a rollback plan. Name a specific metric and a threshold before the rollout starts, and name the version you return to.

Mistake 5: Putting Logging on the Critical Path

If the response waits for the log write, a slow log store slows every request. Write logs in the background, and monitor how many are lost.

FAQs

Q: Is the model the slowest part of the request?

No. For small models, inference often takes only 1 to 10 ms. The feature fetch is usually the larger cost, so measure it first.

Q: Does every new model need an A/B test?

No. Every new model needs offline evaluation and a careful rollout. An A/B test is the strongest check when the traffic and the time allow it. A small fix, such as retraining the same model on fresh data, may only need shadow and canary steps.

Q: Does shadow mode affect users?

No. Users see only the current model's answers. Shadow mode does cost extra compute, though. If the model can take actions, those actions must be turned off in shadow mode.

Key Takeaways

  • A model server is a stateless service. It loads one registry version at startup and keeps no memory of past requests, so replicas can be added or replaced freely.
  • The latency budget is split by stage. A predictive path usually owes its caller 10 to 100 ms, and the feature fetch is the usual bottleneck. Set targets on p99, not the average.
  • Speed comes from caching, batching, and smaller models. Compress before changing hardware. Use a GPU only when a deep network breaks the budget on CPUs.
  • New versions climb a ladder. Offline evaluation, then shadow, then a sticky canary, then a ramp, with rollback triggers named in advance. Rollback repoints serving at the previous version.
  • Failure behavior is designed, not improvised. The fallback ladder starts with the previous version, and fail open or fail closed is a product and policy call.
  • In a system design interview, describe stateless replicas, an itemized budget, the rollout ladder with one named rollback metric, and the fallback.

The next lesson, Offline Evaluation: Choosing the Metric, looks at the first rung of the ladder: which number shows that a model deserves a live test.

1. A model server crashes in the middle of the dinner peak. Why is this a small problem if the server is stateless?

Show answer

Because no request depends on that one replica. The server kept no memory of past requests, so nothing is lost. The load balancer sends traffic to the other replicas, and a new replica loads the same model version and joins.

2. The ETA service misses its 100 ms target at p99. Which stage would you measure first, and why?

Show answer

The feature fetch. It is the usual bottleneck, because it may read several stores over the network. Model inference for a small tree model often takes only 1 to 10 ms. Caching hot entities, such as popular restaurants, is one common fix.

3. A teammate wants to split canary traffic by request, because it is simpler. What do you tell them?

Show answer

Split by user, and keep it sticky. A split by request can show one customer two different estimates on two refreshes. It also mixes both models in one user's behavior, so the measurement is no longer clean.

4. During a canary, p99 latency rises above the trigger you set. What does rollback do?

Show answer

It repoints serving at the previous registry version. Nothing is retrained or deleted. If the previous version was kept loaded and warm, the switch takes seconds.
