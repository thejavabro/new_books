Key Takeaways

Check Your Understanding

Know the Vocabulary

This lesson uses the terms below many times. Read them once now, and come back here when a later section needs one.

  • Chunk: A focused passage cut from a document. It is the unit that retrieval works with.
  • Embedding: A list of numbers that encodes the meaning of a piece of text. Texts with similar meanings get similar numbers.
  • Semantic search: Finding chunks whose meaning is close to the question's meaning. It runs an approximate nearest neighbor (ANN) search over embeddings.
  • Lexical search: Finding chunks that contain the question's exact words. It is also called keyword search.
  • Exact token: A word or code that must match letter for letter, such as an error code or a ticket number.
  • Inverted index: A lookup table that maps each word to every document that contains it.
  • BM25: A common formula for lexical search. It ranks documents by exact matches with the query's words, and it gives rare words more weight.
  • Hybrid retrieval: Running lexical search and semantic search in parallel, then merging their results into one list.
  • Reciprocal rank fusion (RRF): A way to merge ranked lists that adds up scores based on each result's rank position, not its raw score.
  • Bi-encoder: A setup where the query and each chunk are encoded separately, and then their two embeddings are compared.
  • Cross-encoder: A model that reads the query and one chunk together, in one pass, and returns one relevance score for the pair.
  • Reranker: A slower, more careful model that reorders a short list of candidates. A cross-encoder is the usual choice.
  • Metadata filter: A rule on facts stored with each chunk, such as its status or its date. Only chunks that pass the rule can be returned.
  • Recall: The share of the right chunks that retrieval finds anywhere in its candidate list.
  • Precision: The share of the chosen chunks that are actually relevant to the question.
  • Golden set: A fixed set of test questions, each with its known right chunks or right answer. Every change is measured against it.

Part 1: Where Search by Meaning Fails

Embeddings and Vector Databases built semantic search for the food-delivery company. Its retrieval service holds 10 million chunks of help articles, policy pages, and internal pages. It serves the customer support assistant and the tools that support agents use.

That search turns the question into one embedding. Then an ANN index finds the stored chunk embeddings closest to it. HNSW, a graph with several layers, is a common type of ANN index. In other words, semantic search runs an approximate nearest neighbor search over embeddings, and it never compares the actual words.

That design worked well when a customer typed "I'm locked out of my account" into the assistant. Semantic search found the chunk "How do I reset my password?" even though the two share almost no words.

Now a customer types "what does error E4022 mean?" after a failed payment. The help center has a chunk with the heading "Payment error E4022" that answers it exactly. The chunk explains that the customer's bank did not confirm the payment. You might expect semantic search to find it easily. It often does not.

Why an Error Code Has No Meaning to Place

You can picture the space of embeddings as a map of meaning. Each part of the picture matches something real:

  • A point on the map is the embedding of one chunk.
  • The distance between two points is how different their meanings are.
  • A neighborhood on the map is a topic, such as payments or refunds.

An embedding model places each text on this map by what it means. Identifiers like error codes carry no real meaning to place on the map. The model never learned what E4022 means, so it only sees text that looks like a payment error code. It places E4022 close to E4021, E4220, and every other payment error. To the embedding, chunks about those codes sit almost on top of each other.

The search then returns chunks about payment errors in general. The E4022 chunk may rank fifth, or fifteenth, or not appear at all. The customer gets an answer about the wrong error, and no error message reports the failure.

Exact Tokens Need Exact Matching

E4022 is an exact token, because it must match letter for letter. Exact tokens are common in real questions, as the company's own tools show:

  • Error codes, such as E4022, and ticket numbers, as in "summarize ticket SUP-8871."
  • Order numbers, promo codes, and restaurant names.
  • Rare internal words, such as the name of a new policy.

A close match is not good enough for any of them. Ticket SUP-8872 is a different customer's problem. So semantic search needs a partner that matches words exactly, and that partner is lexical search.

Part 2: Lexical Search and BM25

The Inverted Index

Lexical search starts with an inverted index. An inverted index is a lookup table that maps each word to every document that contains it. Ingestion is the background pipeline that turns documents into chunks and indexes them. During ingestion, the pipeline lists the words in each chunk, and the index records which chunks contain each word.

The table below shows a few entries, with illustrative counts.

WordHow many chunks contain it
e40223
payment41,000
error95,000
mean260,000

When a question arrives, the system splits it into words. The index returns the chunks for each word at once, so nothing has to scan all 10 million chunks.

How BM25 Scores a Match

The index finds the chunks that contain the words, and BM25 decides their order. BM25 is a long-standing scoring formula from the field of search, built on three ideas.

  1. Matches count. A chunk scores higher when it contains more of the question's words.

  2. Rare words count more. A word found in few chunks tells you more than a common one. "E4022" is in 3 chunks out of 10 million, so a match on it carries great weight. "Mean" is in 260,000 chunks, so a match on it carries little.

  3. Repeats and length are kept in check. A word that appears many times raises the score, but each extra repeat adds less. A long chunk gets a small penalty, so it cannot win just by containing more words.

So for the E4022 question, BM25 puts the "Payment error E4022" chunk at or near the top. The rare code decides the ranking, as it should.

BM25 needs no training, and it is fast. Mature engines such as Elasticsearch and OpenSearch run it. Design Search Ranking used the same method to find a model number in a product catalog.

Where Lexical Search Fails

Lexical search has the opposite weakness. It fails on vocabulary mismatch, when the user and the document describe the same thing with different words. "I'm locked out of my account" shares almost no words with "How do I reset my password?" so BM25 cannot connect them.

The table below compares the two searches on the company's questions.

QuestionSemantic searchLexical search with BM25
"I'm locked out of my account"Finds the password chunkMisses it, because no words are shared
"What does error E4022 mean?"Returns payment errors in generalFinds the E4022 chunk
"Summarize ticket SUP-8871"May return a similar ticketFinds the exact ticket
"My food arrived cold. What can I get back?"Finds the refund policy for cold foodFinds it only if the policy uses the same words

Notice that each search fails where the other one succeeds. That is the reason to use both.

Part 3: Hybrid Retrieval

The Definition

Hybrid retrieval runs lexical search and semantic search in parallel, then merges their results into one list. Each search returns its own ranked candidates, for example its top 50. A merge step combines the two lists, and chunks that both searches found move toward the top.

In parallel means the two searches start at the same moment, so the total time is the slower of the two. For example, BM25 may take about 10 milliseconds (ms). Embedding the question and running the ANN search may take about 15 ms. Together, they finish in about 15 to 20 ms, not 25.

What Hybrid Retrieval Is Not

Hybrid retrieval is not semantic search run twice, such as once with the raw question and once with a rewritten one. That is still one kind of search, with one weakness.

Hybrid retrieval is not two vector databases that hold copies of the same chunks. Copies help reliability, but they add no second way to match.

Hybrid retrieval is not reranking either. The merge step only combines two lists, and reranking is a separate, later stage that Part 4 covers.

Why You Cannot Simply Add the Scores

The obvious merge is to add each chunk's two scores. That does not work, because the scores sit on different scales. A BM25 score has no fixed upper limit, so it might top out at 4 for one question and at 30 for another. Vector search scores with cosine similarity, which measures how closely two embeddings point in the same direction. For text embeddings, a cosine score usually falls between 0 and 1.

Suppose you add them anyway. On a question with a rare word, BM25 scores reach 30, and the cosine scores barely count. On a question with only common words, BM25 scores stay low, and cosine decides. The balance changes from question to question, and nobody chose it. Averaging the raw scores has the same problem. Rescaling each list to the range 0 to 1 helps only partly. The top result in each list becomes 1, even when that list found nothing useful.

Reciprocal Rank Fusion

Reciprocal rank fusion (RRF) avoids this problem by ignoring the raw scores and using only rank positions. Each chunk gets points from each list it appears in:

RRF score = 1 / (60 + rank in the BM25 list) + 1 / (60 + rank in the vector list)

A chunk that is missing from a list gets nothing from that list. The constant 60 is a common default that keeps the gap between first and second place small. So one list cannot overrule the other with a single top result.

Rank 1 is rank 1, whatever the raw score was, so RRF needs no score normalization. That is its real virtue: BM25 and cosine scores sit on scales that cannot be compared, and ranks sidestep that problem.

The table works through the E4022 question. To keep it short, each search returned only its top 3 chunks.

ChunkBM25 rankVector rankRRF score
"Payment error E4022"121/61 + 1/62 = 0.0325
"Why was my payment declined?"not found11/61 = 0.0164
"Payment error E4021"2not found1/62 = 0.0161
A ticket that mentions E40223not found1/63 = 0.0159
"Add a new card"not found31/63 = 0.0159

The ticket contains the rare code, yet it ranks below the E4021 chunk in the BM25 list. It mentions E4022 once in a long thread, so BM25's length penalty lowers its score. The E4021 chunk does not contain E4022 at all. It is short, and it repeats the question's words "error" and "mean" several times.

Notice the first row of the table. The E4022 chunk was near the top of both lists. That gives it about twice the score of any chunk that only one list found. Agreement between the two searches is the strongest signal RRF has.

The diagram below shows the two lists merging into one.

Should You Weight the Two Lists?

Weighted RRF multiplies each list's points by a weight. For example, BM25 points might count twice as much as vector points.

Start with RRF's default of equal weights and the constant 60. Fit weights only if the golden set proves they are necessary. Weighted variants make sense for corpora where one signal genuinely should dominate the other. A corpus is the full collection of chunks that retrieval searches. A corpus of log messages and error codes may need BM25 to count more. A corpus of chat conversations, full of paraphrase, may need vectors to count more. Any new weight is tuned on the golden set and checked again when the corpus changes.

Part 4: Reranking

The Problem Hybrid Retrieval Leaves

Hybrid retrieval improves recall, so the right chunk is now usually somewhere in the candidate list. But the model that writes the answer does not read the whole list. Only the top few chunks, for example the top 5, go into its context. The context is the text the model reads before it writes.

Here is an example. A customer writes "My order came 40 minutes late, so can I get a refund?" in the chat. The merged list ranks tracking chunks first, with the chunk "Why is my order late?" at rank 1. These chunks match the words "order" and "late," and they match the topic too. The policy chunk about refunds for late deliveries sits at rank 14.

The question asks about refund rules, not tracking, and the first-stage searches cannot see that difference well. So the right chunk was retrieved but not chosen. Recall is fine, but precision is not, and fixing that needs a different kind of model.

Bi-Encoders: Fast Because They Work Apart

Semantic search uses a bi-encoder. The query and each chunk are encoded separately, and each becomes its own embedding. Then the two embeddings are compared with one fast score, such as cosine similarity.

Because the two sides work apart, the document side never has to wait for the query to show up. Every chunk embedding can be computed ahead of time, in a batch job. At request time, only the question needs to be embedded. Then the ANN index compares it with millions of stored embeddings in a few milliseconds.

The price of this speed is detail. Each chunk is compressed into one embedding before any question exists. That embedding cannot know which part of the chunk a future question will care about.

Cross-Encoders: Careful Because They Read Together

A cross-encoder reads the query and the chunk together, token by token, in one pass. Here, a token is the unit a model reads: a short word or a piece of a longer word. Inside the model, every token of the question can be compared with every token of the chunk. So the model can notice that "can I get a refund?" asks about eligibility, and that the policy chunk answers exactly that. It returns one relevance score for the pair.

That care is expensive. Nothing can be computed ahead of time, because the score depends on both texts together. Each candidate needs its own full model pass, and reading every token pair jointly is expensive at any real scale.

Count the work for one question. Scoring all 10 million chunks would take 10 million model passes. Even a few thousand passes would usually take too long for a waiting user. So a cross-encoder only handles a short list, from a few dozen to about a hundred candidates.

The table below compares the two setups.

Bi-encoderCross-encoder
How it readsQuery and chunk separatelyQuery and chunk together, in one pass
What is computed ahead of timeEvery chunk embeddingNothing
Work for each questionOne question embedding and one ANN searchOne model pass for each candidate
How many chunks it can coverMillions, through the ANN indexA few dozen to about a hundred
Its job in the pipelineFirst-stage retrievalReranking

In short, bi-encoders do first-stage retrieval, and cross-encoders do reranking. The diagram below shows the same difference.

The Reranking Stage

A reranker is a slower, more careful model that reorders a short list. The usual reranker is a cross-encoder. Some teams use a large language model (LLM) instead, often a small one, at a higher cost for each request.

The arithmetic is simple, and the numbers are illustrative, not a guarantee. The first stage retrieves 50 to 100 candidates fast, in about 10 to 50 ms. The reranker then scores each candidate with the question. On a GPU, that takes about 50 to 100 ms for the whole list. Finally, it keeps the best 3 to 8 chunks for the context.

For the late-order question, the reranker reads all the merged candidates and scores the refund policy for late deliveries highest. So that chunk moves from rank 14 to rank 1, and the tracking chunks fall below it.

The Same Funnel as Module 3

This shape is not new in the course. Design a Recommendation System used a retrieval-then-ranking funnel. A funnel is a series of stages that each keep fewer items and spend more effort on each one. Hybrid search with reranking is Module 3's funnel again, this time inside retrieval-augmented generation (RAG).

Recommendation funnelRAG retrieval funnel
Cheap first stageCandidate generation: about 500 of 50 million videosHybrid retrieval: 50 to 100 of 10 million chunks
The first stage is judged onRecallRecall
Careful second stageRankerCross-encoder reranker
The second stage is judged onPrecision at the topPrecision at the top

The funnel's rule carries over as well. A chunk that the first stage misses can never come back, because the reranker can only reorder what it receives. So the first stage is tuned for recall, and the reranker is tuned for precision.

Why Precision Helps the Answer

Fewer, better chunks also help the model that writes the answer. The RAG Pipeline describes a pattern called lost in the middle. Some models use evidence less reliably when it sits in the middle of a long context.

Ten noisy chunks dilute the context, and the right fact may land in the middle, among unrelated text. Five precise chunks keep the evidence short and easy for the model to use. They also cost fewer tokens.

When to Add a Reranker

Teams usually add a reranker once evals show that recall is fine but precision is not. Evals are the tests the team runs on the golden set. In plain terms, the right chunk appears in the candidate list, but not in the top few that reach the model.

If the right chunk is missing from the candidates entirely, a reranker cannot help, so fix the first stage instead.

Part 5: Filters and Structured Questions

Metadata Filters for Facts

Some questions are about more than meaning or words. A support lead types "open tickets about billing errors filed since March" into an internal tool. This question has three parts, and each needs a different tool:

  • "About billing errors" is a topic, which words and meaning can match.
  • "Open" is a status. A ticket is either open or not.
  • "Filed since March" is a date. A ticket's date either falls in the range or not.

Embedding the whole sentence blurs all three. A closed ticket from February about billing errors would still sit close on the map. A status and a date are not meanings to compare, because they are facts with exact answers.

So the hybrid answer splits the work. Metadata filters handle the status and the date: the status is open, and the filed date is on or after March 1. Hybrid text search handles the topic, billing errors, among the chunks that pass the filters.

Both searches apply the same filters before RRF merges their lists. So the merged list holds only open tickets from the right dates. Embeddings and Vector Databases explains why a filter should run during the search, not after it. The filters only work if ingestion stored those facts with each chunk, as Chunking and Indexing describes.

Routing to Structured Sources

Some questions are not about documents at all. "How many refunds did we issue last week?" asks for a count. No chunk contains that number, because the answer sits in a database table.

Routing to structured sources means sending such a question to SQL generation instead of document retrieval. A model writes a database query. The system checks that the query only reads data, then runs it with the user's own permissions. The result becomes the evidence for the answer. Tool Use and Function Calling covers how a model calls tools like this safely.

The query-processing stage decides which path a question takes:

Question shapeExamplePath
Meaning or exact words"What does error E4022 mean?"Hybrid retrieval, then reranking
A topic plus facts"Open tickets about billing errors filed since March"Metadata filters, plus hybrid text search
A count or a total"How many refunds did we issue last week?"Routing to a structured source

Part 6: Follow One Question

The steps below follow the E4022 question through the full retrieval path. The times are illustrative.

Step 1: The question arrives. At 7:15 PM, a customer types "what does error E4022 mean?" after a failed payment. The service sets one filter, which is that the audience is customers.

Step 2: Two searches start at once. The BM25 search sends the question's words to the inverted index. At the same time, the question is embedded with the corpus's model, and the ANN search runs. Both searches apply the customer filter, and each returns its top 50 chunks within about 20 ms.

Step 3: RRF merges the lists. About 20 chunks appear in both lists, so the merged list holds about 80 different candidates. The merge takes about 1 ms, and the E4022 chunk comes first.

Step 4: The reranker reads each pair. The cross-encoder scores the question together with each of the 80 candidates. It runs them in batches on a GPU in about 70 ms, and it keeps the best 5 chunks.

Step 5: The chunks move on. The 5 chunks go to context assembly and then to the model that writes the answer. The RAG Pipeline covers those stages.

The diagram below shows the same steps, with the number of chunks at each stage.

Notice where the time went. The two searches took about 20 ms, but reranking took about 70 ms. The reranker is the slowest step in this retrieval path, so its gain must be measured against that time.

Notice also what ran ahead of time. The inverted index and every chunk embedding were built during ingestion, and the request only processed the question. Retrieval is judged on recall, and reranking is judged on precision.

Part 7: Choosing the Right Shape

Match the Fix to the Failure

Each tool in this lesson fixes one kind of failure. Read the golden set results first, then choose. Four lines map each failure to its fix:

  1. Exact tokens are missed. Add BM25, and make retrieval hybrid.

  2. Paraphrased questions are missed. Add semantic search, and make retrieval hybrid.

  3. The right chunk was retrieved but not chosen. Add a reranker, because this is the failure a reranker is built to fix.

  4. Questions about status, dates, or counts fail. Add metadata filters, or route to a structured source.

When One Search Is Enough

Hybrid retrieval is a strong default, not a rule for every system.

Vector-only retrieval, which skips hybrid, is a reasonable choice in three cases. The first is a conversational corpus with few identifiers, where questions are mostly paraphrases. The second is a small scale, where a second index adds more work than value. The third is early simplicity, such as a first version that the team will measure before it grows.

Keyword-only retrieval fits best in three other cases. The first is identifier-dominated lookup, such as log search for exact error strings and request IDs. The second is a strict latency floor, meaning a hard time limit that leaves no room for embedding the question. The third is a tiny corpus, where exact words already find the right page.

In every case, measure on the golden set. Add the second search when the evals show the kind of question you are missing.

Is the Reranker Worth Its Time?

The reranker adds about 50 to 100 ms and some GPU cost to every request. Measure the trade on the golden set rather than assume it. Run the golden set with and without the reranker. Compare how often the right chunk reaches the top 5, and how often the final answer is correct. Then weigh that gain against the added time and cost.

The length of the candidate list is a second setting to measure. The RAG Pipeline suggested starting with 10 to 20 candidates. A longer list, such as 50 to 100, gives the right chunk more chances to appear, so recall rises. It also adds reranking time, because each candidate needs its own pass. Run the golden set at a few list lengths. Choose the shortest list beyond which recall stops improving.

A latency-critical path can also skip the reranker conditionally. Suppose both searches rank the same chunk first, such as an exact match on a rare error code. Then the order is rarely in doubt, and reranking seldom changes it. Suppose instead that the top candidates score close together. Then the order is uncertain, and that is where the reranker helps most. Test any skip rule on the golden set before you trust it.

Part 8: Using This in an Interview

The 30-second answer (to "is vector search enough for this RAG system?"): "Not on its own. Semantic search misses exact tokens, such as error codes and ticket numbers, because they carry little meaning for an embedding. So I would run BM25 over an inverted index and an ANN vector search in parallel. Both apply the same metadata filters, and reciprocal rank fusion merges the two lists. RRF uses ranks, so the two score scales never need to match. Then a cross-encoder reranks the top 50 to 100 candidates and keeps the best 3 to 8. I would add the reranker when the golden set shows the right chunk retrieved but not chosen, and I would measure its latency cost."

Likely follow-ups:

  1. "Why not average the two scores?" BM25 scores have no fixed range, and cosine scores usually sit between 0 and 1. The balance would change with every question. RRF uses rank positions, so the scales never need to match.
  2. "Why not run the cross-encoder on the whole corpus?" It needs a full model pass for each chunk, with nothing computed ahead of time. Over 10 million chunks, that is far too slow, so it reranks only the short list that the fast first stage found.
  3. "How do you handle 'open tickets about billing errors filed since March'?" Metadata filters handle the status and the date. Hybrid text search handles the topic. A question that asks for a count goes to a structured source instead.

Common Mistakes

Mistake 1: Trusting Vector Search With Identifiers

Error codes, ticket numbers, and product names carry little meaning for an embedding, so semantic search returns near misses for them. Add BM25 when your questions contain exact tokens.

Mistake 2: Adding Raw Scores

BM25 and cosine scores sit on different scales, so their sum gives a balance that nobody chose. Merge the lists by rank with RRF instead.

Mistake 3: Adding a Reranker to Fix Missing Chunks

A reranker only reorders what the first stage found. If the right chunk is not among the candidates, fix retrieval first.

Mistake 4: Embedding Dates and Statuses

A status or a date is a fact with an exact answer, not a meaning to compare. Store it as metadata and filter on it.

Mistake 5: Tuning Weights Before Measuring the Default

Start with plain RRF, and fit weights only when the golden set proves that one signal should dominate.

Mistake 6: Treating the Reranker as Free

A cross-encoder may add 50 to 100 ms to every request. Measure its gain on the golden set, and weigh it against that time and its GPU cost.

FAQs

Q: Is BM25 out of date now that embeddings exist?

No. BM25 is still a cheap and reliable way to match exact tokens. Production systems often keep it next to semantic search, because each one catches what the other misses.

Q: Does hybrid retrieval replace query rewriting?

No. Query rewriting first turns a question like "does that cover my spouse?" into a complete question. Hybrid retrieval then searches with the rewritten question, so the two solve different problems.

Q: Can a reranker find a chunk that retrieval missed?

No. A reranker only reorders the candidates it receives, so a chunk lost in the first stage is lost for good.

Q: Can an LLM act as the reranker?

Yes. A small LLM can judge whether each chunk answers the question. It usually costs more time and money than a cross-encoder, so compare both on the golden set.

Q: Do both searches need the permission filter?

Yes. Each search must apply the same filters, including who may read each chunk. Otherwise, one list could bring a forbidden chunk into the merged result.

Key Takeaways

  • Semantic search misses exact tokens. Error codes and ticket numbers carry little meaning to place, so embeddings return near misses.
  • BM25 matches exact words and favors rare ones. It uses an inverted index, a lookup table from each word to the chunks that contain it.
  • Hybrid retrieval runs both searches in parallel and merges them. Reciprocal rank fusion adds points by rank, so the two score scales never need to match. Start with its default before fitting weights.
  • A cross-encoder reranks a short list. A bi-encoder is fast because chunks are embedded ahead of time. A cross-encoder is careful because it reads the question and chunk together. So it handles only a short list, up to about a hundred candidates.
  • This is Module 3's funnel inside RAG. The first stage retrieves 50 to 100 candidates for recall, and the reranker keeps the best 3 to 8 for precision.
  • Facts go to filters, and counts go to structured sources. Status and dates become metadata filters, and questions that need a count go to SQL generation.
  • In a system design interview, name both searches and RRF. Then say when you would add a reranker, and how you would measure its cost on the golden set.

Check Your Understanding

1. A customer asks about error E4022, and semantic search returns chunks about other payment errors. Why?

Show answer

Because the error code carries no real meaning for the embedding. The model places E4022 close to every similar code, so the search returns near misses. BM25 matches the exact token and finds the right chunk.

2. Chunk A is rank 2 in the BM25 list and rank 3 in the vector list. Chunk B is rank 1 in the vector list only. Which one does RRF place higher?

Show answer

Chunk A. Its score is 1/62 + 1/63, which is about 0.0320. Chunk B scores 1/61, which is about 0.0164. Appearing near the top of both lists beats leading only one.

3. The golden set shows the right chunk in the top 100 candidates for most questions, but rarely in the top 5. What should the team add?

Show answer

A reranker. Recall is fine, but precision is not. A cross-encoder can read each candidate with the question and move the right chunk into the top few. The team should measure its gain and its latency on the golden set.

4. Why can a cross-encoder not do first-stage retrieval over 10 million chunks?

Show answer

Because nothing can be computed ahead of time. It must read the question and each chunk together, in its own model pass. Ten million passes for one question would take far too long, so it only reranks a short list.
