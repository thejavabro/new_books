Check Your Understanding

Know the Vocabulary

This lesson uses the terms below many times. Read them once now, and come back here when a later section needs one.

  • Feature: One input value the model uses, such as a restaurant's average prep time or the distance to the customer.
  • Raw signal: A fact the business records, such as an order event, a price, or a user id. It often must be changed into a number before a model can use it.
  • Entity: One thing the system keeps data about, such as a restaurant, a courier, a customer, or a dish.
  • Window: A stretch of recent time used to compute a number, such as "the last 30 minutes" or "the last 7 days."
  • Aggregate: A number computed from many events, such as a count, an average, or a median.
  • Embedding: A list of numbers that captures what an item or a user is about. Items the model treats as similar get similar numbers.
  • Freshness: How old a feature value is when the model reads it. A value computed 5 seconds ago is fresher than one computed last night.
  • Batch path: Scheduled jobs that compute features from large amounts of stored data, for example once a night.
  • Streaming path: Jobs that read events as they happen and update features within seconds.
  • Request-time feature: A feature computed while the request is being answered, because its value exists only at that moment.
  • Feature store: A system that keeps feature values, with a full history for training and the latest values for fast lookups during serving.
  • Offline store: The part of the feature store that keeps every past value of every feature, for training.
  • Online store: The part of the feature store that keeps only the latest value of each feature, for fast lookups during serving.
  • Point-in-time correctness: Building each training example only from feature values that existed at the moment of the prediction.
  • Training-serving skew: A difference between the features a model saw in training and the features it sees in serving.

Part 1: What a Feature Is

The Module 2 introduction followed one delivery-time prediction through the system. At 6:02 PM, a customer opened checkout. The model predicted 32 minutes. To do that, it read a few input values. Among them were the restaurant's average prep time, the number of orders in its kitchen, and the route distance.

Those input values are features. This lesson explains how to choose them, how to turn them into numbers, and how to keep them correct and fresh. The same food-delivery company runs through every part. Its delivery-time model is called the ETA model, where ETA stands for estimated time of arrival.

The Definition

A feature is one input value that a model uses to make a prediction. Each feature describes something the model can know at the moment it predicts. A model does not read the raw database. It reads a short list of values built for one request. This list is called a feature vector.

For the ETA model, one feature vector might hold the values below. The numbers are illustrative.

FeatureExample value
Restaurant's average prep time14 minutes
Orders waiting in the restaurant's kitchen now9
Route distance from the restaurant to the customer2.1 miles
Time of day6:02 PM
Courier's vehicle typebicycle

Notice that the values come from different places and change at different speeds. The average prep time changes slowly. The kitchen queue changes every minute. The route distance exists only for this one order. Most of this lesson follows from that fact.

What a Feature Is Not

A feature is not a raw table row. An order event is a raw signal. "Orders in the last 30 minutes" is a feature computed from many such events.

A feature is not the label. The label is the answer the model should learn, such as the 38 minutes the delivery really took. A feature must never contain that answer. Otherwise the model learns from information it will not have in production.

A feature is not free. Each one needs code to compute it, storage to keep it, and time to fetch it. Add a feature only if the model is clearly better with it.

Part 2: Finding Features

Start From Five Signal Sources

In an interview, you need a good feature list in about a minute. Listing features as they come to mind is slow and misses whole groups. A faster method is to walk through five signal sources. A signal source is a kind of place where useful facts come from.

  1. Content: what the request is about. For the ETA model, that is the cart: which dishes, how many items, and how long they take to cook.
  2. Actor: who is involved. Here there are three actors: the customer, the restaurant, and the courier.
  3. Behavioral: what those actors did recently. An example is how many orders the restaurant received in the last 30 minutes.
  4. Graph: how the actors are connected. For example, this courier has picked up from this restaurant 40 times before.
  5. Context: the conditions at the moment of the request. Examples are the time of day, the weather, and whether a sports final is on TV.

Name two features for each source, and you have about ten useful features in under a minute. The same five sources work for other designs, such as fraud scores or video recommendations.

Sort Them Into Four Buckets

Once you have a list, sort each feature into one of four buckets. Each bucket is a kind of feature. The bucket tells you how often the feature changes, and so how it should be computed.

  1. Entity features are slowly changing properties of one thing. Examples are a restaurant's average prep time over several months and a courier's vehicle type. They change over days or weeks.
  2. Behavioral aggregates are numbers computed over a recent window of activity. Examples are orders in the last 30 minutes and the median prep time for this dish over 7 days. The median is the middle value when all the values are sorted.
  3. Contextual features describe the request moment itself. Examples are the time of day, the weather, and whether a sports final is on TV.
  4. Cross features combine two entities and describe how they interact. An example is this courier's past delivery times from this restaurant. Neither the courier alone nor the restaurant alone gives you that number.

The diagram below shows the four buckets with examples from the ETA model.

Why Behavioral Aggregates Are the Hard Bucket

Most of the hard engineering in a feature system comes from bucket 2. Many aggregates are useful only when they are fresh. A count of "orders in the last 30 minutes" from last night says nothing about the dinner rush right now. So these features need a streaming compute path that updates them within seconds. Streaming jobs are harder to build, run, and test than nightly jobs.

The other buckets are easier. A nightly job can recompute entity features, and contextual features are mostly simple reads, such as the clock. Cross features can be large, with one value for each pair of entities, but many change slowly.

One boundary needs care. The restaurant's long-run average prep time is an entity feature. The median prep time for one dish over 7 days is a behavioral aggregate. Both measure prep time, and the difference is the window. A value computed over several months behaves like a fixed property of the restaurant. A value computed over a recent window follows what the kitchen is doing now.

Part 3: Turning Raw Signals Into Model Inputs

A model needs numbers. Many raw signals are not numbers, or they are numbers in a form the model handles badly. Each kind of raw signal has a standard recipe. The table below lists the three kinds you will meet most often.

Raw signalExamplesHow it becomes a model input
Numeric valuescounts, prices, distancesLog-scaling for heavy tails, bucketing, or normalization
Low-cardinality categoriesdevice, country, vehicle typeOne-hot encoding or small embeddings; either works at this size
Sparse idsuser id, restaurant id, dish idA learned embedding, kept in an embedding table

Each recipe needs a short explanation.

Numeric values. Many counts have a heavy tail: most values are small, and a few are very large. For example, most restaurants may get 5 orders an hour, while a few get 500. Log-scaling replaces each value with its logarithm, which moves the large values closer together. Bucketing replaces a value with a range, such as 0 to 10 orders. Both methods keep a few very large values from controlling the model. Normalization rescales values to a small common range, such as 0 to 1. It puts features on similar scales, which helps many models train. With a heavy tail, apply it after log-scaling.

Low-cardinality categories. Cardinality is the number of different values a field can take. A vehicle type might have only three: bicycle, scooter, or car. One-hot encoding turns it into three yes-or-no inputs, with exactly one set to yes. A small embedding, a short list of learned numbers for each value, also works. With so few values, either choice is fine.

Sparse ids. An id field can have millions of values, such as one per user. One-hot encoding would need millions of inputs, almost all of them zero. That is what "sparse" means here. Instead, the model learns an embedding for each id. The embeddings live in an embedding table, with one row per id. Training adjusts the rows, so ids that behave alike get similar numbers. Some systems first hash each id into a fixed number of rows. A hash is a fixed calculation that turns an id into a number, here a row number. This step, called the hashing trick, keeps the table at a known size. The cost is that two ids can share a row, which loses a little accuracy.

Part 4: Where Features Are Computed

Three Places to Compute a Feature

A feature can be computed in one of three places. The choice depends on how fresh the feature must be and how much it costs to compute.

  1. The batch path runs scheduled jobs over stored data. A typical example is a nightly Spark or SQL job. Spark is a tool that processes very large datasets across many machines. The batch path suits slow features, such as entity features. It has the lowest cost per value, but its values are only as fresh as the last run.
  2. The streaming path reads events as they happen. The events come from an event log such as Kafka, which stores events in order so that other jobs can read them. A stream processor such as Flink keeps windowed aggregates up to date. A windowed aggregate is an aggregate over a moving window, such as orders in the last 30 minutes. Its value updates within seconds of each new event. This path costs more to run and is harder to operate.
  3. Request-time computation happens inside the prediction service. It runs while the user waits. It is only for features whose values exist at that moment, such as the exact route distance for this order. Part 6 covers this path.

The Lambda Shape

The batch path and the streaming path run side by side. Both start from the same events, and both write into the feature store. On a diagram, they form two arms that meet at the store. This design is often called a lambda architecture, so this lesson calls it lambda-shaped.

Each arm trades cost against freshness in a different way. The batch arm is cheap, and its values are hours old. The streaming arm is fresh within seconds, and it costs more. A good design puts each feature on the cheapest arm that still meets its freshness need. Restaurant averages go on the batch arm. The kitchen queue goes on the streaming arm.

Each arm writes to both parts of the store. After the nightly job computes the restaurant averages, it loads them into the online store, so serving can read them. It also keeps their history for training. The streaming arm does the same for the kitchen queue.

The diagram below shows the two arms, the feature store they write to, and the request-time features.

Notice that training reads only the offline store. Serving reads the online store and the request-time features. Part 5 explains why the two stores must agree.

Part 5: The Feature Store

The Definition

A feature store is a system that keeps feature values, with a full history for training and the latest values for fast lookups during serving. It has two sides, often called its two faces.

  1. The offline store keeps the full history. It records every value each feature has had, with the time each value was written. Training reads it through point-in-time-correct joins, which this part explains below. It is usually a data warehouse or files in low-cost storage, and it is read in large scans.
  2. The online store keeps only the latest value. It holds one value per feature per entity. It is built for low-latency lookup: one read by key returns the latest feature vector for a restaurant. An example target is under 10 ms, not a guarantee. It is usually a key-value store, which is a database that finds a value by its id.

The main idea is that one feature definition feeds both faces. The same job that computes "orders in the last 30 minutes" writes each new value to the online store. It also adds the value, with its timestamp, to the offline store. So the model trains on the same numbers that serving will give it later.

Why One Definition Matters

Training-serving skew is a difference between the features a model saw in training and the features it sees in serving. A common cause is two codepaths for one feature. A codepath is the code that computes a value.

Here is a concrete case. A team streams "orders in the last 30 minutes" through Flink for serving. A separate nightly Spark job recomputes the same aggregate for training. The Spark job counts canceled orders, and the Flink job does not. So training sees larger numbers than serving. The model learns from one feature and meets a slightly different one in production. Quality drops, and no error appears.

The deepest problem here is not speed or cost. The problem is that two codepaths compute the same feature and have drifted apart. One shared definition should feed both faces. That is how a feature store cures skew: the same feature definitions and jobs write both the offline store and the online store.

A shared definition is the main cure, but it is not the whole cure. Defaults for missing values, rounding, and time zones can still differ. Tests that compare logged serving features with training features catch what remains.

Point-in-Time Correctness

A training example pairs a past prediction with its label. Its features must be the values that existed when that prediction was made. Point-in-time correctness guarantees this. Take an example from 6:02 PM on a given day. The join returns each feature value exactly as it was at that moment. A join is the step that matches each training example with its feature values.

Follow one example through the join.

Step 1: The example is chosen. The training job picks the 6:02 PM order from Part 1. Its label is 38 minutes.

Step 2: The history is read. The offline store holds several values of "orders in the kitchen" for that restaurant. The values are 6 orders at 5:55 PM, 9 orders at 6:01 PM, and 14 orders at 6:05 PM.

Step 3: The right value is picked. The join takes the latest value written at or before 6:02 PM. That value is 9 orders, the same value serving saw.

Step 4: The later value is skipped. The value from 6:05 PM is ignored. At 6:02 PM, nobody knew it yet.

The diagram below shows this join on a timeline.

Notice what goes wrong without this rule. A join that ignores time could give the model 14, or even today's value. The model would learn from information that did not exist at prediction time. Its offline results would look better than its results in production. This mistake is called leakage, and Training vs Serving covers it in more detail.

Many teams also log the exact features the service used for each prediction. Once a feature has been served for a while, training can read those logs directly. A brand-new feature has no logs yet, so its history must come from a point-in-time join.

One Registry, Many Teams

A feature store has one more job. It keeps a registry of feature definitions. Each entry records the feature's name, its code, its owner, and its freshness. Teams search the registry and reuse a feature instead of building it again.

This matters for correctness, not only for saved effort. Suppose the fraud team also needs "orders in the last 30 minutes" for each restaurant. If it writes its own version, that version may differ slightly, such as in how it treats canceled orders. That recreates the same skew risk, now between two teams. Reusing the registered definition avoids it.

What a Feature Store Is Not

A feature store is not required in every system. A small model with a few nightly features can read them from an ordinary table. A feature store is worth its cost when there are many features, several models, or fresh streaming values.

A feature store is not a place for raw events. It holds computed features. The raw events stay in the event log and the data warehouse.

Part 6: Request-Time Features

Features That Exist Only Now

Some features cannot live in either store. Request-time features are knowable only at the exact moment of the request. The exact route distance depends on this customer's address and this restaurant, right now. The cart size depends on what the customer chose. No job could have computed these values ahead of time.

So the prediction service computes them inline, while the user waits. Every millisecond spent here comes out of the latency budget. A latency budget is the total time a request may take, divided among its steps.

A common interview trap is to put an expensive call here with no stated latency plan. For example, a candidate says "we call the routing service for the exact route" and moves on. The interviewer then asks how long that call takes, and what happens when it is slow.

When One Feature Uses Most of the Budget

Suppose the full request must finish within 100 ms. Suppose also that the routing service is slow, and its call alone needs 80 ms. That leaves 20 ms for everything else, which is not enough. There are three good options.

  1. Cache it. Keep recent results and reuse them. For example, store route distances and times between delivery zones, and refresh them every few minutes. A cache read can take about a millisecond.
  2. Approximate it. Use a cheaper estimate instead. A straight-line distance, scaled up by a typical ratio for city streets, takes almost no time. It is often close enough.
  3. Default it. Give the call a strict timeout. If it does not answer in time, feed the model a missing-value default instead.

The third option works only if the model learned what the default means. So during training, replace the feature with the default in some examples. Also add a yes-or-no input that says the value is missing. This is called a trained-in missing default. Without the feature, the model then makes a reasonable prediction instead of a wrong one.

State which option you choose and why. A strong answer also says how you will measure the accuracy you lose.

Why Not Compute Everything at Request Time?

Request-time values are always fresh, so why precompute anything? The answer is latency and cost. A restaurant's six-month average prep time would mean reading every order it had in that period. Courier supply across a city could mean scanning millions of events per request. At peak dinner traffic, that work repeats many times each second. The request would be too slow, and the compute cost would be very large. Precomputing does the work once, and each request pays only for one fast lookup.

Part 7: Freshness and Staleness

Stale Features Fail Silently

A stale feature is one whose value is older than it should be. Suppose the streaming pipeline falls 20 minutes behind. Perhaps a stream job crashed, or events arrived faster than it could process them. The online store does not know this. It keeps returning the last value it has, and the model keeps predicting. No request fails, and no error appears. The kitchen queue reads 3 orders while 15 are waiting, so the ETA comes out too short.

This is why freshness needs its own monitored metric. For each important feature, track how old its latest value is. Alert when the age passes a limit. Set the limit for each feature separately. A courier's vehicle type can be days old. The kitchen queue may need to be less than a minute old. Monitoring, Drift, and Retraining shows where freshness checks fit among the other checks on a running model.

Let the Model See the Age

There is a second defense. Add the age of a feature as one more input. For example, next to the kitchen queue, also pass the number of seconds since that value was updated. Train the model with this input, using the real ages from the logs. Include some examples with old values, so the model sees what stale data looks like.

The model can then learn to trust old values less. When a value is stale, it relies more on other features, such as the long-run average prep time. Quality drops a little instead of a lot. This is called graceful degradation: a small, controlled loss instead of a sudden failure.

Part 8: Using This in an Interview

The 30-Second Answer

The 30-second answer (to "what features would you use, and how would you serve them?"): "I'll walk through five signal sources: content, actor, behavioral, graph, and context. Then I'll sort the features into entity features, behavioral aggregates, contextual features, and cross features. Slow features come from a nightly batch job. Fresh aggregates come from a streaming job. Both write one shared definition into a feature store. Its offline store gives point-in-time-correct history for training. Its online store gives the latest values in a few milliseconds. Each request-time feature gets a latency budget, with a cache or a trained-in default. Finally, I'll monitor the freshness of each feature."

Likely Follow-Ups

"Why not compute every feature at request time?" Latency and cost. Long-window aggregates would mean scanning millions of events on every request. Compute them once ahead of time, and look them up in milliseconds.

"Your streaming pipeline falls 20 minutes behind. What happens?" Nothing fails, and predictions quietly get worse. A freshness alert should fire. A model trained with feature age as an input also loses less accuracy.

"The fraud team wants your 'orders in the last 30 minutes' feature. Should they build their own?" No. They should reuse the registered definition. A second version that differs slightly would bring back skew, now between two teams.

Part 9: Common Mistakes

Mistake 1: Listing Features With No Plan

A list of feature names is not a design. For each important feature, say which bucket it is in, where it is computed, and how fresh it must be.

Mistake 2: Two Codepaths for One Feature

Computing a feature in Spark for training and in Flink for serving invites skew. Write one definition, and let it feed both stores.

Mistake 3: Joining Today's Values to Old Examples

A training join that reads current values leaks the future into training. Offline results look strong, and production results disappoint. Use point-in-time-correct joins.

Mistake 4: An Expensive Request-Time Call With No Budget

Name the latency of every request-time call. Give each one a timeout and a fallback, and train the model with that fallback.

FAQs

Q: Does every ML design need a feature store?

No. A small system with a few slow features can read them from an ordinary table. A feature store is worth its cost when there are many features, several models, or fresh streaming values. In an interview, add one when the design needs those things.

Q: Is a feature store just a cache in front of a database?

No. The online store works much like a cache. But the offline store keeps the full history for point-in-time training joins. The registry also keeps the shared definitions. A cache does neither of these jobs.

Q: Can the batch path and the streaming path both compute the same feature?

Yes, but only from one shared definition. For example, a team may compute a value by streaming for serving, then fill in its past history with a batch job. Both must run the same logic, or skew returns.

Key Takeaways

  • A feature is an input value the model can know at prediction time. Each one costs code, storage, and time during the request.
  • Five signal sources find features quickly, and four buckets sort them. Walk through content, actor, behavioral, graph, and context. Then sort into entity features, behavioral aggregates, contextual features, and cross features.
  • Each raw signal needs the right recipe. Scale or bucket numeric values, one-hot encode small categories, and learn embeddings for sparse ids.
  • Two arms compute stored features. The batch arm is cheap and slow, and the streaming arm is fresh and costly. Put each feature on the cheapest arm that meets its need.
  • One definition feeds both faces of the feature store. The offline store gives point-in-time-correct history, and the online store gives the latest values fast. Reusing registered definitions also prevents skew between teams.
  • Request-time features need a budget, and stored features need a freshness monitor. Cache, approximate, or default a slow feature, and train the model for the default.
  • In a system design interview, list features by source and bucket, and say where each one is computed. Draw the two faces of the feature store, and give every request-time feature a latency plan.

The next lesson, Batch vs Online Inference, asks the same question about the prediction itself. Should it be computed ahead of time, or when the request arrives?

Check Your Understanding

1. A feature counts the orders a restaurant received in the last 30 minutes. Which bucket is it in, and which path should compute it?

Show answer

It is a behavioral aggregate, computed on the streaming path. It is a number over a recent window, and it is useful only when fresh. A nightly job would leave it hours old during the dinner rush.

2. A training example comes from 6:02 PM. The offline store has values from 5:55 PM, 6:01 PM, and 6:05 PM. Which value should the join use?

Show answer

The value from 6:01 PM. It is the latest value written at or before 6:02 PM, so it is the value serving saw. The value from 6:05 PM did not exist yet. Using it would leak the future into training.

3. Computing the exact route distance takes 80 ms of a 100 ms budget. What are three ways to fix this?

Show answer

Cache it, approximate it, or default it. You can cache route times between zones, use a straight-line estimate, or time out and feed a missing-value default. If you use a default, train the model with it, so the model knows what it means.

4. The streaming job falls behind, but no errors appear. Why not, and how would you notice?

Show answer

Because the online store keeps serving its last values. Nothing fails, so error monitoring sees nothing. A freshness metric for each feature, with an alert, shows the problem. Training with feature age as an input also limits the damage.
