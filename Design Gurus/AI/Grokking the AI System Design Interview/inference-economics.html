Check Your Understanding

Know the Vocabulary

This lesson uses the terms below many times. Read them once now, and come back here when a later section needs one.

  • Inference: Running a trained model on an input to get an output. For a large language model (LLM), the output is generated text.
  • Token: The unit of text an LLM reads, writes, and is billed in. In English, one token is about three quarters of a word.
  • Input tokens: The tokens you send to the model: instructions, conversation history, documents, and the new question.
  • Output tokens: The tokens the model writes back as its answer.
  • Frontier model: One of the largest and most capable models a provider offers. It is usually also the most expensive per token.
  • Small model: A model with far fewer learned numbers inside it, which costs much less per token and handles many simpler tasks well.
  • Prefill: The first phase of a request, in which the model reads all the input tokens together, in parallel.
  • Decode: The second phase, in which the model writes the answer one token at a time. Each new token needs its own step.
  • Time to first token (TTFT): How long the user waits before the first word of the answer appears.
  • GPU: A chip that runs many simple calculations at the same time. LLMs are usually served on GPUs.
  • Weights: The learned numbers inside a model, also called parameters. They must sit in GPU memory while the model runs.
  • KV cache: The working state a GPU keeps for each request while it writes the answer. It holds the model's processed form of every earlier token in that request.
  • Batching: Packing many requests onto one GPU, so their decode steps run together.
  • Utilization: The share of a GPU fleet's capacity that is doing useful work.
  • Quantization: Storing the weights with fewer bits per number, such as 8 bits instead of 16.
  • Hosted API: A model you call over the network from a provider, paying for each token.
  • Self-hosting: Running a model on GPUs that you rent or own, paying for each GPU hour.
  • Breakeven point: The volume at which two options cost the same. Above it one option is cheaper, and below it the other is.
  • Rate limit: The most requests or tokens a hosted API accepts from you in a time window, such as one minute.

Part 1: Two Meters Run on Every Request

Model Serving Basics served the food-delivery company's delivery-time model on four small CPU machines. That model took a few milliseconds per prediction. Its feature pipelines often cost more than the model itself.

An LLM changes that picture, because each answer takes seconds, not milliseconds. Each answer also has a price that grows with its length. For a generative AI design, two meters run on every request.

  1. The latency meter measures time, meaning how long the user waits. For a chat answer, it has two readings: the time to first token, and the time until the whole answer is done. LLMs at Interview Altitude explains where each reading comes from.

  2. The cost meter measures money, and it counts in tokens, not in requests. A short question with a short answer costs little. A long conversation with a long answer can cost many times more, even though both are one request.

Why the Meters Are Tracked Separately

The two meters do not always move together. A design choice can improve one and leave the other unchanged, or even make it worse. So a design states a target for each meter, and it checks both after every change.

The table below shows four common changes and how each one typically moves the two meters, with no guarantee.

ChangeLatency meterCost meter
Stream the answer word by wordThe first words appear soonerNo change: the same tokens are produced
Send easy questions to a small modelOften fasterMuch lower
Put more requests in each GPU batchEach request can get slowerLower per token on your own GPUs
Ask for shorter answersFaster to finishLower

Notice the first and third rows. Streaming helps the user and saves no money, while a larger batch saves money and can slow each user down. One combined number would hide both of these effects.

Part 2: How Tokens Are Priced

The Price List

Providers quote prices per million tokens, with one price for input and another for output. This lesson uses example frontier prices of 12 per million output tokens. These are assumptions for arithmetic, not current quotes. Real prices change often, so say that you would check the current price list.

Notice the gap: output costs four times as much as input here. For frontier models, output tokens commonly cost roughly 3 to 5 times as much as input tokens. A small model often costs about a tenth of the frontier price, or less.

Why Output Costs More

The reason lies in the two phases of a request.

  • Prefill reads the input in parallel. All the input tokens go through the model together, which keeps the GPU's many cores busy. So each input token costs little GPU time.
  • Decode writes the output one token at a time. Each output token needs its own decode step, because each new token depends on the tokens before it. Every step reads all of the model's weights from GPU memory again.

So one output token takes far more GPU time than one input token, and providers price output higher to match.

What the Cost Meter Is Not

The cost meter is not a flat fee per request. Two requests to the same model can differ in cost by a factor of ten or more. The bill follows the tokens: how much you send, and how much the model writes.

The cost meter is also not only the model. Retrieval, safety checks, storage, and logging have costs too. This lesson focuses on the model, because for many LLM features it is the largest line.

One Number Worth Remembering

A typical chat turn sends a few thousand tokens and gets a few hundred back. For example, take 3,000 input tokens and 300 output tokens at the example prices:

  • Input: 3,000 x 0.009
  • Output: 300 x 0.0036
  • Total: about $0.013

So a typical chat turn costs around a cent on a frontier model. On a small model, it costs a tenth of that or less. This one anchor lets you estimate many designs quickly.

Part 3: Price One Conversation First

The Unit-Economics Habit

A daily bill is hard to reason about on its own. So first price the thing a user sees, such as one conversation, one summarized document, or one answered question. Then multiply by the volume. This is the unit-economics habit: compute the cost per conversation or per document, then multiply by how many there are.

The habit gives the total, and it also shows which part of one unit drives the cost. That second result tells you where to optimize.

The Running Example

The food-delivery company's support assistant answers customers in chat. In the Module 1 capstone, it expected about 40,000 conversations a day. To keep the arithmetic round, this lesson prices a larger support bot that handles 100,000 conversations a day. All numbers are illustrative assumptions.

Step 1: Describe one conversation. A conversation has 10 turns. In each turn, the customer writes about 200 tokens, and the bot answers with about 300 tokens. Every request also carries the bot's fixed instructions, about 550 tokens.

Step 2: Count the input tokens. The model keeps no memory between requests, so each turn must resend the whole conversation so far. Some providers can store the history for you, but they still bill it as input tokens on every turn. Turn 1 sends the instructions and the first message, about 750 tokens. Each later turn adds the previous question and answer, about 500 more tokens. By turn 10, one request sends about 5,250 input tokens.

Across the ten turns, the input averages about 3,000 tokens per turn, so the conversation sends about 30,000 input tokens.

Step 3: Count the output tokens. Ten answers of 300 tokens each make 3,000 output tokens, so the conversation uses about 33,000 tokens in total.

Step 4: Price the conversation. Input: 30,000 x 0.09. Output: 3,000 x 0.036. The total is about 0.13 per conversation.

Step 5: Multiply by volume. 100,000 conversations x 12,600, or roughly 400K per month**.

The diagram below shows the same chain, from one turn up to the monthly bill.

Notice where the tokens went. Output was only 3,000 of the 33,000 tokens, and most of the input was old history, sent again and again. Turn 10 alone sends seven times as much input as turn 1.

Compare It With the Human Cost

Assume a human-handled support ticket costs about 0.13 per conversation looks like a bargain, even if the bot resolves only part of the conversations.

There is a caveat, though. A conversation the bot cannot resolve still goes to a human, so it costs 4. Compare the total support cost per correctly resolved issue, not one bot conversation against one human ticket.

Three Levers the Example Points To

The unit price shows where the money goes, and three levers follow from it.

  1. Summarize the history. Later turns send a short summary of the earlier turns instead of the full text. This shrinks the input tokens each later turn has to resend. In this example, it could cut the 30,000 input tokens by about half. The summary itself costs some tokens, and it can drop details, so test it.

  2. Route easy turns to a cheaper model. Many turns are simple, such as a customer asking where an order is. A small model at a tenth of the price may answer them well, but measure the quality before you move them.

  3. Cache what repeats. The 550 tokens of fixed instructions are the same in every request. Some providers and serving engines can reuse that shared start of each request, which costs less than processing it again. The resent history also repeats the start of the previous request, so it can sometimes be reused the same way. Common questions may also reuse a stored answer, when that is safe.

Serving Optimizations covers these techniques and their risks in detail.

Part 4: What a GPU Runs Out Of

A hosted API hides the hardware. If you self-host, you pay for GPU hours, so you must know what limits one GPU. Often, the first thing to run out is memory.

The Weights Must Fit

At 16-bit precision, each parameter takes 2 bytes, so a model's weights need about 2 bytes times its parameter count.

For example, a 70-billion-parameter (70B) model needs about 140 GB for its weights alone. A large data-center GPU often has 80 GB of memory. So this model needs more than one GPU just to load.

The KV Cache Takes the Rest

During decode, the model reuses its work on every earlier token. It keeps that work in the KV cache, so it does not redo it at each step. Every active request has its own KV cache, which grows as the input and the answer get longer.

For a large model, one long conversation can need a gigabyte or more of KV cache. So the memory left after the weights limits how many requests fit at once. Often, this leftover memory caps how many requests one GPU can serve at the same time, not its raw compute.

Quantization Frees Memory

Quantization stores the weights with fewer bits per number. Moving from 16-bit to 8-bit roughly halves the memory the weights use, so the same 70B model then needs about 70 GB.

Quantization can also raise the number of requests a GPU serves at once, because the freed memory can hold more KV caches. The diagram below compares the 70B model on two 80 GB GPUs, at 16 bits and at 8 bits, with rounded sizes.

Notice the size of the change. At 16 bits, only about 20 GB is left for KV caches and runtime buffers, the working memory the serving software needs. So only a few long conversations fit. At 8 bits, about 90 GB is left for them.

The KV caches themselves do not get smaller here, because only the weights were quantized. The gain comes from the memory the weights give back. A team could instead run the 8-bit model on one GPU. That halves the GPU cost, but it leaves only about 10 GB for KV caches. Either way, lower precision can reduce quality, so test the quantized model on your own tasks.

Batching: Why One Request Wastes a GPU

Small-batch decode is limited by memory bandwidth, which is the speed at which data moves from memory to the GPU's cores. Each decode step reads every weight from memory into the cores. With one request, that work produces only one token. The cores spend most of the step waiting for data, so most of the compute you pay for sits idle.

Batching fixes this by packing many requests onto one GPU, so their decode steps run together. One pass over the weights now produces one token for every request in the batch, and the cost per token drops sharply.

This is why the KV cache matters so much. More free memory means more requests in each batch, and more requests in each batch means more tokens per GPU hour.

Utilization

Utilization is the share of the fleet's capacity that is doing useful work. A GPU costs the same per hour whether it is busy or idle, so low utilization raises the real cost of every token you serve.

The answer is not to aim for 100 percent. A fleet that runs full has no room for a traffic spike, so requests queue and latency jumps. A common target is roughly 60 to 80 percent utilization at peak. The rest is headroom, meaning spare capacity for spikes and failed machines.

Part 5: Size and Price a Fleet

Use one more example, with illustrative numbers, to size a self-hosted fleet. A high-volume feature runs on a small open model, which is a model whose weights you can download and run yourself. Each serving node is one GPU, and the model fits on it.

Step 1: Find the output rate at peak. Traffic peaks at 50 requests per second, and each answer averages 500 output tokens. So the fleet must write 50 x 500 = 25,000 output tokens per second.

Step 2: Divide by what one node sustains. Suppose a load test on this workload shows one node sustains about 2,500 output tokens per second within the latency target. Then 25,000 / 2,500 = 10 nodes by the math.

Step 3: Add headroom. Ten nodes would run at full load during the peak, so provision 14 nodes instead. At peak, the fleet then runs at about 70 percent utilization, inside the 60 to 80 percent target. It can also lose a node and keep serving.

Step 4: Price the fleet. Assume each GPU costs 4 per hour, and one year has about 8,760 hours.

  • Low end: 14 x 245K per year
  • High end: 14 x 490K per year

So the fleet costs roughly 490K per year for the GPUs alone. Networking, storage, monitoring, and the engineers who run it come on top.

Part 6: Hosted API or Self-Host

The Decision Table

Neither option always wins, so the table below compares them on six factors.

FactorFavors a hosted APIFavors self-hosting
VolumeLow or spiky volume: you pay only for tokens usedHigh and steady volume: the fixed fleet cost is spread over many tokens
QualityYou need the strongest frontier modelA smaller open model meets the quality target
Data rulesThe provider's data terms meet your privacy needsData must stay inside your own systems
EngineeringThe team has no one to run GPUsThe team can run, update, and monitor a fleet
Latency controlShared provider latency is good enoughYou need tight control over latency and batching
RiskYou accept rate limits and provider outagesYou accept GPU failures and capacity planning

Notice the volume row. A fleet costs the same each hour, busy or idle. When volume is high and steady, that fixed cost is spread across many tokens, so each token gets cheap. When volume is low or spiky, the fleet sits idle much of the time, and you still pay for every idle hour.

The Breakeven Is a Calculation

Whether the hosted API or self-hosting wins is not a matter of team preference. It is a breakeven you can calculate from sustained volume.

Here is the comparison for the fleet in Part 5, where again every price is an assumption.

Step 1: Price one request on the API. Suppose a provider hosts the same small model at a tenth of the frontier price. That is 1.20 per million output tokens. Each request sends 1,000 input tokens and gets 500 output tokens back, so it costs 0.0006 = $0.0009.

Step 2: Price one day of the fleet. At a middle price of 3 x 24 = about $1,008 per day.

Step 3: Find the breakeven. 0.0009 = about 1.1 million requests per day. That is about 13 requests per second, sustained all day.

Step 4: Compare with the real traffic. Suppose the feature averages 20 requests per second, about 1.73 million requests per day. The API would cost about 1,008 per day.

So the fleet saves about 200K per year, before people costs. Whether that pays for the engineers who run the fleet depends on the team. An interviewer wants to see this calculation, with that last condition stated.

The End State Is Usually a Mix

Most real systems use both options, so the end state is usually a mix. The frontier API serves the hard, lower-volume paths, where quality matters most. Cheaper models, hosted or self-hosted, serve the high-volume paths. For the support bot, that could mean a frontier model for refund disputes and a small model for order-status questions. A router, which is a small component that picks the model for each turn, makes that choice.

Design for Rate Limits and Outages

A hosted API has rate limits, and providers sometimes fail. A production design plans for both with three parts:

  • Client-side budgeting. Your own service tracks its token use against the limit. Each feature gets a share, so one busy feature cannot use up the whole limit.
  • Backpressure. When usage nears the limit, the service slows down new work or queues it. It does not keep sending requests that will be rejected.
  • Graceful degradation. When the limit is reached or the provider is down, users still get something useful. That may be a smaller model, a shorter answer, or a handoff to a human agent.

A blind retry loop is not a plan. Resending failed requests adds load at the worst moment. Retry a few times with growing waits, then degrade.

Part 7: Using This in an Interview

The 30-second answer (to "what will this cost to run?"): "I track two meters separately: latency and cost. Cost is metered in tokens. I'll price one conversation first: about 30K input and 3K output tokens, roughly 13 cents at frontier prices. At 100,000 conversations a day, that's about $13K per day. Most of it is resent history, so I'd summarize history, route easy turns to a small model, and cache the fixed instructions. If volume is high and steady, I'd price a GPU fleet and compare the breakeven. These are orders of magnitude, and I'd verify current prices."

Likely follow-ups:

  1. "Why does output cost more than input?" Each output token needs its own decode step, one after another. Input tokens are read together in parallel during prefill. So output uses more GPU time per token, and the price reflects that.
  2. "When would you self-host?" Self-host when volume is high and steady and a smaller open model meets the quality bar. The team must also be able to run a fleet. Show the breakeven: fleet cost per day divided by API cost per request. Then state the people costs that the hardware number leaves out.
  3. "What happens when you hit the provider's rate limit?" Client-side budgets keep each feature inside its share. Backpressure slows or queues new work near the limit. Graceful degradation serves a smaller model, a shorter answer, or a human handoff.

Common Mistakes

Mistake 1: Pricing Per Request

A flat price per request hides the real driver. Count input and output tokens, and price them separately.

Mistake 2: Multiplying One Turn by the Number of Turns

Later turns resend the earlier history, so they cost more than early turns. A 10-turn conversation costs far more than 10 times the first turn.

Mistake 3: Starting From the Daily Total

A total alone does not show what to fix. Price one unit first, then multiply. The unit shows which tokens drive the bill.

Mistake 4: Sizing GPUs by Weights Alone

A model that just fits in memory leaves no room for KV caches. It can serve only a few requests at once, so each token becomes expensive. Plan memory for the KV cache too.

Mistake 5: Choosing Self-Hosting by Preference

"We have a strong infrastructure team" is not a cost argument. Calculate the breakeven, and include the people who run the fleet.

Mistake 6: Aiming for Full Utilization

A fleet at 100 percent has no room for spikes or failures. Target roughly 60 to 80 percent at peak.

FAQs

Q: Are the prices in this lesson current?

No. They are round examples for practice, and real prices change often. In an interview, say that you would check the current price list, and focus on the relationships between the numbers.

Q: Does streaming reduce cost?

No. Streaming shows the answer as it is written, so the user sees the first words sooner. The model still writes the same tokens, so the cost meter does not change.

Q: Does quantization always help?

No. It saves memory and often allows more requests per GPU. But it can lower quality, so test it on your own tasks before you ship it.

Q: Is self-hosting always cheaper at large scale?

No. It wins only when volume is high and steady and a smaller model meets the quality target. The savings must also pay for the team that runs the fleet, so calculate the breakeven each time.

Key Takeaways

  • Two meters run on every request. The latency meter tracks time, and the cost meter tracks money in tokens. Track them separately, because one change can move them in opposite directions.
  • Output tokens cost more than input tokens. Frontier output often costs roughly 3 to 5 times as much as input, because each output token needs its own decode step.
  • Price one unit first, then multiply. A chat turn costs around a cent on a frontier model. The support bot costs about 13K per day, and $400K per month.
  • GPU memory often runs out before compute. Weights take 2 bytes per parameter at 16 bits, and the KV cache takes the rest. Quantization and batching let one GPU serve more requests.
  • API or self-host is a calculated breakeven. High, steady volume favors self-hosting. The usual end state is a mix of a frontier API and cheaper models.
  • In a system design interview, name both meters, price one conversation in tokens out loud, and name the levers it points to. Then size a fleet only when the volume justifies it.

Check Your Understanding

1. Two requests go to the same model, and one costs ten times as much as the other. How is that possible?

Show answer

The cost meter counts tokens, not requests. The expensive request sent more input tokens, wrote more output tokens, or both. A long conversation history alone can make one request cost many times more than another.

2. A conversation has 10 turns of about the same size. Why does it use far more than 10 times the tokens of the first turn?

Show answer

Because each later turn resends the earlier history. The model keeps no memory between requests, so every turn carries the whole conversation so far. Summarizing that history shrinks the input each later turn sends.

3. A 70B model runs on two 80 GB GPUs at 16 bits. The team quantizes it to 8 bits. Why might the GPUs now serve more requests at once?

Show answer

The freed memory can hold more KV caches. The weights drop from about 140 GB to about 70 GB. Concurrency is often capped by the memory left for KV caches, not by raw compute, so more requests fit in each batch.

4. A fleet of 10 nodes exactly covers the peak load. Why would you provision 14 nodes instead?

Show answer

To leave headroom for spikes and failures. At 14 nodes, the peak runs at about 70 percent utilization, inside the 60 to 80 percent target. The fleet can absorb a traffic spike or lose a node and keep serving.
