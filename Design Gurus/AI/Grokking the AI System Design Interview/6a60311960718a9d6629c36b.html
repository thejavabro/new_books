Key Takeaways

Check Your Understanding

Know the Vocabulary

This lesson uses the terms below many times. Read them once now, and come back here when a later section needs one.

  • ID: A code that names one user or one item, such as user_84302915. It tells you which one, but it carries no meaning by itself.
  • Vector: A list of numbers, such as (0.9, 0.1, 0.4).
  • Embedding: A short vector of learned numbers that stands for one user or one item. Users and items that behave alike get similar numbers.
  • Dot product: A score for how well two vectors match. Multiply the numbers in matching positions and add the results. A higher score means a closer match.
  • One-hot encoding: A way to turn an ID into numbers. The vector has one position for every possible ID, with a 1 in that ID's position and a 0 everywhere else.
  • Tower: A neural network that turns everything known about one user or one item into a single vector.
  • Two-tower model: A model with two separate towers. The user tower turns a user into a vector, and the item tower turns an item into a vector.
  • Positive pair: A user and an item that the user engaged with, such as a product they clicked or bought.
  • Negative pair: A user and an item that training treats as a non-match.
  • Retrieval: The first stage of a recommendation system. It narrows a huge catalog to a few hundred candidates.
  • Ranking: The stage after retrieval, where a richer model scores the candidates and puts them in order.
  • ANN index: An approximate nearest neighbor index. It finds the stored vectors closest to a query vector without checking every vector, and its results are nearly right rather than exact.
  • Cold start: The problem of a new user or a new item that has no history yet.
  • Version skew: Two parts of a system running from model versions that were not built to work together.

Part 1: 100 Million Items, a Few Milliseconds

Picture a large online store with 100 million products. When a shopper opens the app, the home page shows about 20 products chosen for that shopper. The page must load within a few hundred milliseconds. These numbers are illustrative assumptions, not a description of a real store.

The obvious plan is to score every product for this shopper and show the best ones. At this size, that plan fails. Even if a model needed only one microsecond per product, scoring 100 million products would take 100 seconds for one page.

So large systems split the work into stages, which together are called a funnel. Each stage handles fewer items and spends more effort on each one.

  1. Retrieval comes first. It narrows 100 million products to a few hundred candidates, for example 500. It looks at the whole catalog, so its cost per item must be tiny.

  2. Ranking comes next. A richer model scores the 500 candidates and puts them in order.

  3. Rules come last. Business rules remove repeats, add variety, and choose the final 20.

This lesson is about stage one. Retrieval does not need the perfect order, only the good products somewhere in the 500. This goal is measured as recall, the share of the truly good items that reach the candidate list. For a list of 500, it is often written as Recall@500. A product that retrieval misses is lost, because no later stage sees it.

Two ideas make stage one possible. Embeddings turn users and items into vectors that a model can compare. A two-tower model and an ANN index then make the search fast enough. Design a Recommendation System builds the full funnel around them.

Part 2: Why IDs Need Embeddings

An ID Means Nothing to a Model

The store knows that user_84302915 bought hiking boots last week. Yet the model cannot use the ID user_84302915 directly, because the ID is a name, not a measurement. The number 84302915 is not larger or better than 84302914 in any useful way. Two users with nearby IDs are not similar users.

So the ID must become a learned vector, which is a vector whose numbers come from training rather than from a person.

One-Hot Encoding Does Not Work at This Size

The textbook way to turn an ID into numbers is one-hot encoding. Every product gets its own position, so product number 7 becomes a vector with a 1 in position 7 and a 0 everywhere else.

With 100 million products, every one-hot vector has 100 million positions. That is enormous, and it also says nothing about which IDs are similar. Two hiking boots share no position that holds a 1, and neither do a boot and a toaster. Every pair of products looks equally different. So the encoding itself tells the model nothing about how one product relates to another.

An Embedding Is a Learned Vector

An embedding fixes both problems. Each ID gets a short vector, for example 64 or 128 numbers. The numbers start out random, and training adjusts them until IDs that behave alike get similar vectors. Two boots that the same shoppers buy end up close together, while a toaster ends up far away.

The vectors are kept in an embedding table, with one row per ID that the model looks up. The table is large, but each row is short and carries what the model learned.

Here is a tiny example with three numbers per vector. The table shows one shopper and three products, with the dot product of each product and the shopper.

VectorNumbersDot product with the shopper
Shopper(1.0, 0.0, 0.5)
Hiking boot A(0.9, 0.1, 0.4)0.9 + 0.0 + 0.2 = 1.1
Hiking boot B(0.8, 0.2, 0.5)0.8 + 0.0 + 0.25 = 1.05
Toaster(0.1, 0.9, 0.0)0.1 + 0.0 + 0.0 = 0.1

Notice that both boots score high and the toaster scores low. Nobody told the model what the three numbers mean, because training chose them. Real embeddings have many more numbers, and a single number rarely has a clear meaning on its own.

What an Embedding Is Not

An embedding is not needed for every input. Price and distance are already meaningful numbers on their own. A price of 20, and the model can use that fact directly. Embeddings are for inputs whose raw form has no useful size or order, such as IDs, categories, text, and images.

An embedding is not a fixed fact about an item. It depends on the model and the data that trained it, so a vector from one model version means nothing to another version. Part 7 shows why that matters.

An embedding is not an explanation. "These two vectors are close" does not say why they are close. Part 8 returns to this point.

Part 3: Four Ways to Train Embeddings

Every embedding is learned from some signal, and the signal decides the training method. There are four common routes.

1) Matrix factorization. Picture a huge table with one row per user and one column per item, where a mark shows which user engaged with which item. Matrix factorization learns one vector per user and one per item, so that each dot product predicts the mark. In its basic form, it uses only IDs and needs a lot of interaction history.

2) Two-tower contrastive training. Two neural networks, the towers, turn users and items into vectors. Training pulls matching pairs together and pushes non-matching pairs apart. It is called contrastive training because the model learns from the contrast between matches and non-matches. The towers can read many features besides the ID. This route is a common choice for very large catalogs, and Part 4 explains it.

3) Graph embeddings. Some data forms a graph, which is a set of things joined by links called edges. Users follow other users, users save items, and items belong to lists. Graph embeddings learn vectors from these edges. Users and items that are linked to many of the same things get similar vectors. This route fits when relationships are the main signal. An example is a social app that knows who follows whom but has little click history.

4) Pretrained content encoders. A content encoder is a model that turns text or an image into a vector. Pretrained means it was already trained on large amounts of general data. It can embed a product's title, description, or photo with no click history at all. That makes it the cold-start bridge, because a new item gets a useful vector before anyone has clicked it.

RouteWhat it learns fromNeeds click history?Good fit
Matrix factorizationWhich users engaged with which itemsYes, a lotCatalogs with rich interaction logs
Two-tower contrastiveEngaged pairs, plus user and item featuresYesRetrieval from very large catalogs
Graph embeddingsShared edges, such as follows and savesNo, it needs edgesSocial apps and follow graphs
Pretrained content encodersTitles, descriptions, and imagesNoNew items and cold start

The routes are often combined. A common design feeds content-encoder vectors into the item tower of a two-tower model, and Part 5 shows how that helps new items.

Part 4: The Two-Tower Model

Two Towers, One Score

Each tower reads only one side of the match.

  • The user tower reads what is known about the shopper. That includes the user ID's embedding, the products viewed in this session, and the time of day. It outputs one user vector.
  • The item tower reads what is known about a product. That includes the product ID's embedding, its category, and its price. It also reads content-encoder vectors for the title and the photo. It outputs one item vector of the same length.

The score is the dot product of the user vector and the item vector. The diagram below shows the two towers side by side.

Notice the gap between the towers. The user tower never sees the item's features, and the item tower never sees the user's features. The towers meet only at the dot product. This one choice makes the serving plan in Part 5 possible.

How Training Shapes the Vectors

Training learns both towers from logged pairs. The four steps below repeat over many millions of examples.

Step 1: Collect positive pairs. Each time a shopper clicked or bought a product, the logs give a positive pair.

Step 2: Add negative pairs. The logs show what a shopper clicked, but they do not list the millions of products the shopper would never click. So the negative pairs must be manufactured.

Step 3: Score every pair. The towers compute the vectors, and the dot product scores each pair.

Step 4: Adjust the towers. Training changes the numbers inside both towers. Vectors from a positive pair are pushed together, so their dot product scores high. Vectors from a negative pair are pushed apart, so their dot product scores low.

Where the Negative Pairs Come From

Three sources are usually combined, and Where Training Data Comes From covers them in more detail.

  • In-batch negatives are the usual default. Training handles pairs in groups called batches. For each shopper, the products that other shoppers in the same batch engaged with serve as negatives. Their item vectors are already computed, so these negatives are cheap.
  • Popularity correction fixes a bias. Popular products appear in many batches, so they become negatives far too often. Without a correction, the model learns to score popular products low just because they are popular. The fix adjusts for how often each product is sampled.
  • A few hard negatives sharpen the model. These are near misses, such as products that were shown but not clicked. They teach fine differences, but too many can hurt, because some are products the shopper would have liked.

Part 5: Serving: Split the Towers

The towers never see each other, so they can run at different times.

The item tower runs nightly. A batch job pushes all 100 million products through the item tower. It stores one vector per product and builds an ANN index from those vectors. This is batch inference: running a model ahead of time in a background job and storing the results, as described in Batch vs Online Inference.

The user tower runs per request. When a shopper opens the app, the user tower turns the shopper's current features into one vector. The ANN index then finds the item vectors with the highest dot product.

The steps below follow one request, and the times are illustrative.

Step 1: The shopper opens the app. At 8:15 PM, user_84302915 opens the app after viewing two tents earlier in the same session.

Step 2: The user tower runs. It reads the shopper's features, including the two tents, and outputs one user vector in about 5 ms.

Step 3: The ANN index searches. In about 10 ms, it returns 500 products whose vectors score among the highest against the user vector.

Step 4: The ranker takes over. The 500 candidates go to the ranking model, which scores them with richer features.

The diagram below shows the nightly half and the per-request half.

Notice what did not happen at request time. No neural network scored the 100 million products one by one, because all the item vectors were ready before the shopper arrived.

What the ANN Index Does

An exact search would compute a dot product with all 100 million item vectors on every request. An ANN index organizes the vectors ahead of time, so a search checks only a small part of the catalog. It is fast and nearly right, which means it may miss a few of the true best matches. Teams measure that loss as recall and tune the index until the loss is acceptable. A common index type is HNSW, which links each vector to a few of its near neighbors in a layered graph. Embeddings and Vector Databases explains how it searches.

The index also needs memory, and a quick estimate helps. Suppose each vector has 128 numbers of 4 bytes each. Then 100 million vectors take about 51.2 GB, and the index structure and extra copies for reliability add more.

Fresh Where It Matters

The two towers need different freshness.

  • Item vectors can be a day old. A product's identity changes slowly, and a hiking boot is still a hiking boot tomorrow. A nightly rebuild is usually fresh enough, and new products can be added to the index during the day.
  • User vectors must be fresh. A shopper's intent can change within one session, as when a shopper who came for boots starts looking at tents. So the user vector is computed on every request, from fresh session features. Features and Feature Stores explains how such features stay fresh.

Cold Start Through Content

A new product has no clicks, so its ID embedding has learned nothing yet. But the item tower also reads the product's content features, such as the title and the image. So the new product still gets a sensible vector on its first day. It usually lands near similar products, and retrieval can find it.

A new shopper has no history either. In that case, the user tower can still use session features, such as the products viewed in the last few minutes.

Part 6: Why Not One Network That Sees Both?

A model that reads the user and the item together is often more accurate. It can learn crossed features, which combine one user fact with one item fact, such as "this shopper likes this brand." This lesson calls such a model a cross network.

But a cross network cannot be precomputed, because its output depends on the user and the item together. Its score for a product cannot be computed before the shopper arrives. To retrieve from 100 million products, it would have to run 100 million times per request, which is far too slow.

So the cross network has a different job at the ranking stage. There, it scores only the few hundred products that survived retrieval. At that size, it can afford rich features and a precise score.

Two-tower modelCross network
Sees the user and the item togetherNo, they meet only at the dot productYes
Item side computed ahead of timeYes, every nightNo
Work per requestOne user-tower run and one index searchOne run per candidate
Where it fitsRetrieval: 100 million down to about 500Ranking: the few hundred survivors

Part 7: Version Skew: The Silent Outage

How It Happens

The two towers are trained together. Their vectors share one space, and their dot products mean something only because of that shared training. A user vector from one training run does not match item vectors from another run.

Now follow a bad deploy. The team trains version 2 of both towers and deploys the new user tower on Tuesday. But the catalog has not been re-embedded yet, so the index still holds version 1 item vectors.

This is version skew: a new user tower querying an outdated item index. Every request still returns 500 products. Latency is normal, the error rate is zero, and every dashboard looks clean. But the candidates are wrong, because the dot products no longer measure a real match. Engagement drops quietly over the next day, which is why version skew is a silent outage.

The diagram below compares the unsafe deploy with the safe upgrade.

The Safe Upgrade

Treat the user tower and the item index as one paired unit.

Step 1: Re-embed the catalog. Run all 100 million products through the new item tower.

Step 2: Rebuild the index. Build a new ANN index from the new vectors, next to the old index.

Step 3: Test the pair. Check the new user tower against the new index before any user sees it, for example by measuring recall on recent logs.

Step 4: Promote both atomically. Switch the user tower and the index in one step. Atomically means both switch at the same moment, or neither switches. Keep the old pair ready for a rollback.

A simple guard adds safety. Tag the user tower and the index with their version, and have the service check on every query that the two tags match.

Budget for the Re-Embed

Step 1 is not free, because pushing the full catalog through a new tower costs real compute and real hours. For example, suppose one machine embeds 20,000 products per second. Then 100 million products take about 83 minutes, and reading the data, writing the vectors, and building the index add more. So plan for hours, and treat each upgrade as a scheduled job. The new pair then follows the safe release steps in Model Serving Basics.

Part 8: When Not to Use Embeddings

A small catalog. Think of the food-delivery company from the module introduction, and suppose one smaller city has about 2,000 restaurants. Scoring all 2,000 exactly with a good ranking model is affordable. Approximation is unnecessary, so the team can skip embeddings and the ANN index entirely.

Inputs that are already numbers. As Part 2 showed, price, distance, and preparation time are meaningful numbers on their own, so they need no embedding.

Decisions that must be explained. A bank that declines a loan may need to explain the reason to a regulator. "Three late payments in the last year" is a reason that a person can check. A distance between two learned vectors cannot be explained to a regulator in that way. So such teams often prefer features with clear meanings for those decisions.

Part 9: The Same Idea for Text

Later in the course, Embeddings and Vector Databases uses embeddings to find text passages that answer a question. The geometry is the same: turn things into vectors, then search for the nearest ones with an ANN index. What differs is where the vectors come from. Here, IDs and behavior become vectors, trained on your own logs of what users did. There, text becomes vectors, usually through a pretrained text model. The version rule carries over: a new model means new stored vectors and a new index.

Part 10: Using This in an Interview

The 30-second answer (to "how do you find candidates in 100 million items?"): "I would use a two-tower model for retrieval. The item tower embeds the whole catalog every night, and an ANN index stores the vectors. On each request, the user tower turns fresh session features into one vector, and the index returns about 500 nearest items in milliseconds. A richer ranker then orders them. New items get vectors from content features, such as the title and the image. When the towers change, I re-embed the catalog, rebuild the index, and promote both together."

Likely follow-ups:

  1. "Why not one model that reads the user and the item together?" It cannot be precomputed, so it would run 100 million times per request. It belongs at the ranking stage, on the few hundred survivors.
  2. "A new product has no clicks. How does it get recommended?" The item tower reads its title and image, so it gets a sensible vector on day one.
  3. "Engagement dropped a day after a tower deploy, but the dashboards are clean. What happened?" Most likely version skew: the new user tower is querying an index built by the old item tower. Roll back to the matching pair, then promote the new pair together.

Common Mistakes

Mistake 1: Scoring the Whole Catalog With the Ranker

A rich model cannot score 100 million products per request. Put cheap retrieval first, and give the ranker only the few hundred candidates.

Mistake 2: Using Only Hard Negatives

Hard negatives teach fine differences, but some of them are items the user would have liked. Start from in-batch negatives, correct for popularity, and add a tested share of hard ones.

Mistake 3: Deploying One Tower at a Time

A new user tower against an old item index fails silently. Re-embed the catalog, rebuild the index, and promote the pair together.

Mistake 4: Using Embeddings Where Simpler Inputs Work

Small catalogs can be scored exactly, and numeric features need no embedding. Decisions that must be explained may need features with clear meanings.

FAQs

Q: Do the user vector and the item vector need the same length?

Yes. A dot product multiplies the numbers in matching positions, so both vectors need the same number of positions.

Q: Is a two-tower model always the right retrieval method?

No. It is a common choice for very large catalogs. Matrix factorization, graph embeddings, and simple lists of popular items also work in the right setting. Many systems run several retrieval sources in parallel and merge their candidates.

Q: Can I add new products to the index without retraining the towers?

Yes. Run the current item tower on the new products and add their vectors. The tower did not change, so the new vectors share the same space as the old ones.

Q: Does the ANN index return the exact best matches?

No. It returns nearly the best matches, much faster than an exact search, and teams tune it until the loss in recall is acceptable.

Key Takeaways

  • Retrieval is the first stage of the funnel. It narrows 100 million items to a few hundred candidates, and it is judged on recall.
  • IDs need learned embeddings. A raw ID carries no meaning, and one-hot vectors are huge and show no similarity.
  • There are four training routes. Matrix factorization, two-tower contrastive training, graph embeddings, and pretrained content encoders each fit a different signal.
  • The two towers meet only at the dot product. So the item tower can run nightly over the catalog while the user tower runs on each request.
  • Training pushes positive pairs together and negative pairs apart. The negatives are manufactured: in-batch by default, corrected for popularity, with a few hard ones.
  • Version skew is a silent outage. Re-embed the catalog, rebuild the index, and promote the tower and the index together.
  • In a system design interview, draw the nightly item side and the per-request user side. Then explain cold start through content features, place the cross network at the ranking stage, and describe the paired upgrade.

The next lesson, Model Serving Basics, shows how a trained model runs as a service and how its new versions reach users safely.

Check Your Understanding

1. Why can the store not score all 100 million products with its best model on every request?

Show answer

Because it would take far too long. Even at one microsecond per product, one page would need 100 seconds. Retrieval first narrows the catalog to a few hundred candidates, and the best model scores only those.

2. Which tower runs nightly, which runs per request, and why can they be split?

Show answer

The item tower runs nightly, and the user tower runs per request. They can be split because the towers never see each other. They meet only at the dot product, so item vectors can be computed ahead of time and searched later.

3. A team deploys a new user tower, but the index still holds vectors from the old item tower. What happens?

Show answer

Version skew causes a silent outage. Requests still return candidates with normal latency and no errors, but the candidates are wrong, because vectors from different training runs do not match. The fix is to re-embed the catalog, rebuild the index, and promote both together.

4. A food-delivery app shows about 2,000 restaurants in one city. Does it need two-tower retrieval with an ANN index?

Show answer

No. Scoring all 2,000 restaurants exactly is affordable, so approximate search solves a problem this catalog does not have.
