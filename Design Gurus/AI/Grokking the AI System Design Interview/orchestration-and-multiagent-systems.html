Key Takeaways

Check Your Understanding

Know the Vocabulary

This lesson uses the terms below many times. Read them once now, and come back here when a later section needs one.

  • Agent: A system in which a model chooses some of its next steps while it runs. It calls tools in a loop, within limits that the application enforces.
  • Tool: A function the model may ask to call, such as a web search or an order lookup. Ordinary code runs it, not the model.
  • Context: All the text the model reads in one call. It holds the instructions, the task, and the history so far.
  • Trajectory: The full path one task takes. It is every reasoning step, tool call, and result, in order.
  • Multi-agent system: A design in which more than one agent works on the same task. Each agent has its own context and its own loop.
  • Orchestrator: The lead agent in a multi-agent system. It splits the task into subtasks, hands each one out, combines the results, and owns the final outcome. Some teams call it a coordinator.
  • Worker: An agent that receives one subtask, works on it, and reports back. Some teams call it a sub-agent.
  • Handoff: The moment one agent passes work to another, together with everything it passes along.
  • Report schema: A fixed format that a worker must use when it reports back. It has named fields instead of free text.
  • Budget: A hard limit on what one task may use, such as steps, tokens, money, or time.
  • Token: A short word or a piece of a longer word. Models read and write text as tokens, and providers charge by the token.
  • Frontier model: One of the largest and most capable models a provider offers. It is usually slower and more expensive per token than smaller models.
  • Failure surface: The number of places where things can go wrong in a system.
  • Task state store: A database outside the agents. It records a task's progress, its saved results, and the budget it has spent.

Part 1: One Agent Is the Default

The Problem

The food-delivery company's strategy team wants a research assistant. A manager types one request: "Compare our delivery fee, membership plan, and restaurant commission with our five largest competitors." The answer should be a short report. It needs a comparison table and a source for every number.

Many candidates hear this and draw five agents, one per competitor, plus a manager agent. That design may be right here. But it should be a conclusion, not a starting point. This lesson shows how to reach that conclusion, and how to say no when it is wrong.

The Default

Default to one competent agent, with good tools and a bounded context. Each part of that sentence has a meaning.

  • A competent agent is one capable model running the bounded loop from What an Agent Actually Is. The loop has limits on steps, cost, and time.
  • Good tools are a few task-shaped tools, as Tool Use and Function Calling describes. Each tool does one whole job.
  • A bounded context means the model reads only what the current step needs.

Most agent problems are solved by one well-equipped agent like this, not by a crowd of agents.

Why be so strict? Every agent you add on top of the first one multiplies three things.

  1. Cost. Each new agent reads its own instructions and its own context, and you pay for those tokens again.

  2. Latency. Each new agent adds model calls. Planning before the work and combining after it run one after another, so they add waiting time.

  3. Failure surface. Each agent can misread its task, call the wrong tool, or report something false. Each handoff between agents is one more place for a mistake.

So a second agent must justify its cost, and Part 2 names the only three cases where it can.

What a Multi-Agent System Is

A multi-agent system is a design in which more than one agent works on one task. Each agent runs its own loop with its own context. One lead agent, or plain code, decides who does what. It also combines the results.

What a Multi-Agent System Is Not

A multi-agent system is not a team of experts that is smarter than one agent. The workers often run the same model that a single agent would run. What changes is what each one reads.

It is not a group chat. In the designs that work in production, agents do not talk freely to each other. They pass work through fixed handoffs.

It is not free, because the total bill grows with every agent, even when workers run at the same time.

Part 2: Three Cases That Earn a Second Agent

Only three cases justify a multi-agent design: context isolation, parallelism, and specialization by configuration. In an interview, name the case that applies. If none applies, use one agent.

Case 1: Context Isolation

Context isolation means giving a subtask to a fresh agent whose context holds only that subtask.

The problem it solves is clutter. On a long task, one agent's history keeps growing. It holds every page the agent read, every tool result, and every failed attempt. That accumulated history clutters the model's judgment, because old details compete with the details the current step needs. It also wastes tokens, because the model reads the whole history again at every step.

Take the research request. A single agent would read the pricing pages of all five competitors in one context. By the fifth competitor, its context holds four other companies' fees. A mix-up about whose fee is whose becomes more likely.

A worker that researches only Competitor C starts with a clean, minimal context. That context holds its task, its tools, and nothing else. Nothing unrelated competes for its attention, so its judgment stays focused on its one subtask.

This is the strongest argument for sub-agents. Notice that the argument is not about raw intelligence. The worker is no smarter than one agent would be. It simply reads less, and everything it reads is relevant.

Case 2: Parallelism

Parallelism means running independent subtasks at the same time, and it has two halves.

  • Fan-out splits the work across several workers.
  • Fan-in collects their results in one place.

This is scatter-gather, the pattern that Design Search Ranking uses for its index. Scatter-gather sends one request to many parts at once, then merges their answers. In search, the parts are shards, which are slices of the index. Here, the parts are workers. The pattern is the same, but the workers spend tokens instead of searching shards.

Parallelism is only real when the subtasks are independent. Researching Competitor A needs nothing from the research on Competitor B, so the five subtasks can run at once.

Parallel workers must buy one of two things: real wall-clock time saved, or real context freshness. Wall-clock time is the time the user actually waits. Context freshness means each worker starts with a clean context. If parallel workers buy neither, they only make the bill bigger.

Case 3: Specialization by Configuration

Specialization by configuration means giving different subtasks different settings. A subtask can get a different prompt, a different tool menu, or a different model tier.

In production, "a different agent" often just means a different configuration of the same loop, not a new architecture.

In the research example, the orchestrator plans the work and combines the results. That needs careful reasoning, so it runs on a frontier model. The workers mostly read pages and summarize them, so they run on a cheaper model. The tools differ too, since workers get search and page-fetch tools. The orchestrator needs no web tools, because it reads only the workers' reports.

This is the routing idea from Serving Optimizations, applied to each subtask. A cheap model handles summarizing, and a frontier model handles planning.

The table below sums up the three cases.

CaseWhat it buysQuestion to ask
Context isolationA clean, minimal context for each subtaskWould one agent's history get cluttered?
ParallelismLess wall-clock timeAre the subtasks truly independent?
Specialization by configurationThe right prompt, tools, and model tier per subtaskDo the subtasks need different settings?

The research request clearly fits parallelism, because its five subtasks are independent. It also gains context isolation, since each worker reads one competitor only.

Part 3: Two Shapes That Work in Production

Shape 1: Orchestrator-Workers

In the orchestrator-workers shape, one lead agent manages several workers. The orchestrator has four jobs.

  1. It decomposes the task. It breaks the request into subtasks.

  2. It hands out each subtask with a defined scope. The scope says what the worker must do, and what it must not touch.

  3. It integrates the results. It combines the workers' reports into one answer.

  4. It owns the final outcome. When a worker fails, the orchestrator decides what happens next.

Workers stay mostly stateless and bounded. Stateless means a worker keeps no memory from one subtask to the next, so each subtask starts fresh. Bounded means each worker runs under its own strict budget for that subtask.

Workers report back in a structured format, not free prose. A good report has three main parts.

  • Findings: each claim, with an evidence pointer. An evidence pointer names the page and the quote the claim came from.
  • Confidence: how sure the worker is about each finding, such as high, medium, or low.
  • Artifacts: pointers to saved material, such as notes or copies of pages.

Why so strict? Free-prose reports are where integration quality is lost. Prose can hide ambiguity, because "Delivery is free" may mean free for members only. A field named "condition" forces the worker to state that. The orchestrator then combines fields it can check, not paragraphs it must interpret.

Notice that the workers never talk to each other. Each worker receives its work from the orchestrator and reports only to the orchestrator.

Shape 2: A Pipeline With Agentic Stages

A pipeline with agentic stages is a workflow whose individual steps are themselves small, bounded agents. A workflow is a series of steps whose order an engineer fixed in advance. Code fixes the order of the stages, and inside each stage an agent makes choices while the task runs.

A support system for the food-delivery company could use three stages.

  1. A triage agent reads the ticket, looks up the order, and decides what kind of problem it is.

  2. A resolution agent works on that problem with its own small set of tools, such as a credit or a reschedule.

  3. A QA-check agent reviews the proposed resolution against policy before the reply is sent. QA stands for quality assurance.

If the QA-check agent rejects a resolution, the resolution agent revises it. This happens at most twice, and after that the ticket goes to a person on the support team.

This shape keeps the readability of a workflow. Anyone can read the order of the stages in the code. It also adds runtime judgment inside each stage, where judgment is needed.

Most Production Systems Look Like This

Most production "multi-agent" systems are shaped like sequential handoffs. One agent finishes, and the next one starts. They are a pipeline with agentic stages, or an orchestrator with workers. They are not a society of agents that debate each other.

When Two Agents Talk Directly

One case of direct talk is defensible: a producer-reviewer pair. One agent drafts, and a second agent critiques the draft. Then the first agent revises it. This repeats for a bounded number of rounds, such as two.

The resolution agent and the QA-check agent above form this kind of pair. Even this pair is really a pipeline with a loop of two in it. It is not open-ended negotiation.

Part 4: Handoffs Are Contracts

A handoff is the moment one agent passes work to another. In a reliable design, handoffs are contracts. Each delegation carries five things.

  1. A task: one clear goal, with a definition of done.

  2. Scoped context: only the facts this subtask needs.

  3. Tools: the smallest tool menu that can do the job.

  4. A budget: the steps, tokens, and time this subtask may use.

  5. A report schema: the exact format of the reply.

An API is the agreed interface that one component uses to call another. A handoff is an API boundary between two agents, so engineer it like one. You would not let one service call another with an unstated input format. The same rule applies to agents.

Here is the contract for the worker that researches Competitor C.

task:     Find Competitor C's delivery fee, membership price,
          and restaurant commission in the US market.
          Done when each field is filled or marked "not found".
context:  The three field definitions and the target market only.
tools:    web_search, fetch_page, save_note
budget:   20 steps, 60,000 tokens, 5 minutes
report:   findings (value, condition, evidence pointer),
          confidence, artifacts, gaps, status

Notice what the contract leaves out. The worker does not see the other four competitors, the manager's full request, or the orchestrator's history. That is context isolation, written down.

Notice also the fields "gaps" and "status". A worker may not find everything. Commission rates are often not public. The report must say so plainly, instead of filling the field with a guess.

The tool menu follows least privilege, which means giving only the permissions the job needs. This worker can search, read pages, and save notes to the task's own store. It cannot send email or change any business record.

Part 5: State and Budgets Live Outside the Agents

Task State Lives in a Store

Task state lives outside the agents. It sits in a task state store that the orchestrator owns. The store records three things.

  • Task progress: which subtasks are done, running, or failed.
  • Artifacts: the notes, saved pages, and reports that each worker produced.
  • Spent budgets: how much each worker, and the whole task, has used.

Why outside? Agents run as processes, and processes crash. If a worker's progress lived only in its own context, a crash would lose it. With the state in a store, a crashed worker is retryable. The orchestrator starts a fresh worker with the same contract and the artifacts already saved. The whole task stays resumable, so the work done so far survives.

This works because workers are stateless. A fresh worker with the same contract can do the job of the one that crashed.

One caution applies here. The research workers change nothing outside the task's own store, so a retry cannot repeat an outside side effect. At worst, it saves a note twice. A worker with write tools, such as a refund tool, also needs the idempotency keys from Tool Use and Function Calling. An idempotency key makes a repeated write take effect only once.

Budgets Are Hierarchical

Budgets work hierarchically across an orchestrator and its workers. One top-level budget covers the whole task. The orchestrator splits it downward into worker allocations.

For the research task, the example numbers are below. They are illustrative, not a guarantee.

  • Top-level budget: 400,000 tokens and 15 minutes.
  • Orchestrator: 80,000 tokens, for planning and for the integration step.
  • Five workers: 60,000 tokens and 5 minutes each, so 300,000 tokens in total.
  • Reserve: 20,000 tokens for one retry.

Notice that the orchestrator's own budget includes the integration step. A common mistake is to give the whole budget to the workers. Then nothing is left to combine their reports.

When a worker runs out of budget, it stops. It does not keep going, and it does not fail silently. It reports back partial results, with its status set to "partial". The runtime stops the worker's search a little before the limit, so enough tokens remain to write that report. The orchestrator integrates what the worker did complete, and it marks the rest as a gap.

This is the same shape as the latency budget in classic serving. In Model Serving Basics, a request's time limit is split into a share for each stage. Here, a task's tokens and time are split into a share for each agent. In both cases, each part must stay within its share, or the whole request misses its limit.

Part 6: Follow One Research Task

The steps below follow the research request through the orchestrator-workers shape. The times and token counts are illustrative.

Step 1: The request arrives. At 10:00 AM, the manager sends the comparison request. The orchestrator records a new task in the task state store, with a budget of 400,000 tokens.

Step 2: The orchestrator plans. It splits the request into five subtasks, one per competitor. It writes five contracts, each with a scope, tools, a budget, and a report schema. Planning uses about 15,000 tokens on the frontier model.

Step 3: Five workers fan out. At 10:01 AM, five workers start at the same time on a cheaper model. Each worker sees only its own contract.

Step 4: One worker crashes. At 10:03 AM, the worker for Competitor B crashes after saving two notes. The store shows its subtask as stalled. The orchestrator starts a fresh worker with the same task, tools, and report schema, plus the two saved notes. The store shows how much of the first worker's 60,000 tokens is already spent. The fresh worker gets what is left, and the reserve covers the work that must be redone.

Step 5: One worker runs out of budget. The worker for Competitor E finds the delivery fee and the membership price. It cannot find a public commission rate before its 60,000 tokens run out. It reports back with status "partial" and lists the commission as a gap.

Step 6: Fan-in and integration. By 10:07 AM, all five reports are in. The orchestrator builds the comparison table from the report fields. Then a verification pass checks every number in the table against its evidence pointer.

Step 7: The report is delivered. At 10:09 AM, the manager receives the table with a source for every number. One plain note says, "Competitor E's commission rate was not found."

What the Extra Agents Cost

The whole run used about 280,000 tokens. The cost comes from three places.

  1. The orchestrator's context, for planning and for integration.

  2. Each worker's own context. Every worker reads its own instructions, tool menu, and pages. No two workers share those tokens.

  3. The integration pass, which reads all the reports at once.

Now compare that with one agent doing the same research. It would read the same pages. It would skip the plan, the five copies of the instructions and tool menu, and the separate integration pass. But its history would grow to hold all five competitors. As What an Agent Actually Is showed, the model rereads that history at every step, so a long history costs tokens too.

So a multi-agent run usually costs more in total than one agent on the same work, but not simply five times more. One team that runs a multi-agent research system has published its numbers. Its multi-agent runs used roughly four times the tokens of its single-agent runs. The exact multiple depends on the number of workers, how much each one reads, and how long one agent's history would grow. So estimate it for your own design, measure it on real tasks, and treat any multiple as an example, not a rule.

Now look at what the extra cost bought. One agent working through the five competitors one by one might take about 25 minutes in this example. The five workers finished the same work in about 9 minutes. Each worker also read only one competitor's pages. That is real wall-clock time saved and real context freshness. Without them, the extra cost would buy nothing.

Part 7: What Goes Wrong Across Agents

Compounding Errors Move Up a Level

What an Agent Actually Is showed that errors compound along one agent's trajectory. A wrong lookup early on becomes the premise for every later step. If ten steps each succeed 95 percent of the time with no recovery, the task succeeds only about 60 percent of the time.

Across agents, this arithmetic gets worse, not better. A bad worker report becomes a false premise that the orchestrator builds on. The same dynamic from a single agent's loop now runs one level up, through the handoff itself.

The same holds when the orchestrator misreads a correct report. That one misreading corrupts everything downstream of that point in the trajectory. Every comparison and conclusion built on it carries the mistake.

Here is a simple example. Suppose each of the five workers returns a fully correct report 95 percent of the time. Assume the workers fail independently. All five reports are correct only about 77 percent of the time. The integration step adds its own chance of error on top. These numbers are illustrative, but they show the direction: each extra agent adds one more chance to be wrong.

Debugging Gets Harder

A trace is the recorded log of every step, tool call, and result in a task. Debugging a five-agent trajectory is much harder than debugging a single-agent one, for two reasons.

  • There is more to read. Five agents mean roughly five times the trace.
  • There is no determinism. A deterministic system returns the same result for the same input every time. Agent runs are not deterministic, because the same request can take a different path next time. So a failure may not repeat when you try it again.

So record every handoff: the contract sent and the report returned. Then a bad final answer can be traced back to the report or the step that caused it. Evaluating Agent Trajectories shows how to test whole trajectories before release.

A Worked Diagnosis

Suppose an early version of this design let workers report in loose prose. The final report says, "Competitor C charges no delivery fee." That claim is wrong. The trace shows that the worker's report was correct. In a prose note, the worker wrote that delivery is free for members and $3.99 for everyone else. The integration step dropped the condition.

So the worker was right, and the integration step drew a wrong conclusion. Three fixes help, in this order.

  1. Tighten the report schemas. Every claim must carry an evidence pointer and its conditions, not loose prose. A field named "condition" cannot be skipped the way a clause in a sentence can.

  2. Add a verification pass on the integration step. It checks each claim in the final report against the worker finding and the evidence that it cites.

  3. Check for overlapping worker coverage. Two workers may cover the same thing, such as a membership plan that two brands share. They may report different numbers for it. The orchestrator must reconcile them, not pick one without saying so.

Notice that none of these fixes is "use a bigger model." The defect was at the handoff, so the fix is at the handoff.

Patterns to Reject

Three patterns often appear in demos. In an interview, reject them by name.

  • Free-form agent debate: several agents argue about an answer until they agree.
  • Emergent negotiation: agents bargain over who does what, with no plan fixed in advance.
  • Agent chat as coordination: agents coordinate by sending each other open messages in a shared chat.

These are demos, not designs. They can be impressive to watch. But no fixed rule limits how many rounds they take, so their cost has no upper bound. There is also little evidence that they work reliably in production at scale. A bounded producer-reviewer pair is the one form of direct talk worth defending.

Part 8: Using This in an Interview

An interviewer may ask, "Would you use multiple agents here?" That question tests one skill: can you say no, with real reasons, and say yes only where a multi-agent design is earned? Reaching for more agents by habit is the weaker answer.

The 30-second answer (to "design a research assistant that investigates five competitors and writes a comparison"): "I'd start from one agent and ask what a second agent would buy. The five competitors are independent, so parallelism is earned here. Each worker also gets a clean context with one competitor only. So I'd use orchestrator-workers. The orchestrator plans on a frontier model, and the workers read pages on a cheaper model. Every handoff is a contract: a scoped task, a small tool menu, a budget, and a report schema with evidence pointers. Task state lives in a store the orchestrator owns, so a crashed worker can be retried. Budgets are hierarchical, and a worker that runs out reports partial results. I'd expect a bill several times that of one agent, in exchange for a much shorter wait, and I'd measure the real multiple."

Likely follow-ups:

  1. "Why not one agent for the whole comparison?" One agent would research the five competitors one after another. Its context would fill with all five companies' pages. That takes longer and makes mix-ups more likely. If the request covered one competitor, I would use one agent.
  2. "Why not let the workers talk to each other to fill gaps?" Open chat between agents has no stopping rule, so its cost has no upper bound. A worker that finds a gap reports the gap. The orchestrator then decides whether to send out a new, scoped subtask.
  3. "A worker crashes halfway through. What happens?" Its progress and saved notes are in the task state store, not in the worker. The orchestrator starts a fresh worker with the same contract and the saved artifacts. Its tools change nothing outside the task's store, so the retry is safe. Workers with write tools would also need idempotency keys.

Common Mistakes

Mistake 1: Starting With a Team of Agents

Five agents drawn before any reason is given looks like habit, not design. Start with one agent, and add a second only for context isolation, parallelism, or specialization by configuration, and say which one.

Mistake 2: Accepting Free-Prose Reports

Prose hides conditions and doubts, and the orchestrator then misreads them. Give every worker a report schema with findings, evidence pointers, confidence, and artifacts.

Mistake 3: Keeping State Inside the Agents

If progress lives only in a worker's context, a crash loses it. Keep task progress, artifacts, and spent budgets in a store that the orchestrator owns.

Mistake 4: Forgetting the Integration Budget

All the tokens go to the workers, and nothing is left to combine their reports. Split one top-level budget downward, and include the integration step in the orchestrator's share.

Mistake 5: Letting Agents Chat Freely

Debate and open negotiation have no fixed number of rounds, so their cost has no upper bound. Use fixed handoffs, and allow direct talk only in a producer-reviewer pair with a round limit.

Mistake 6: Assuming Parallel Means Cheap

Parallel workers can save time, but they rarely save tokens. Each one reads its own instructions, tools, and pages. Expect the bill to grow, and check that it buys real wall-clock time or real context freshness.

FAQs

Q: Is a multi-agent system smarter than a single agent?

No. The workers often run the same model a single agent would use. A multi-agent design helps in other ways. It gives each subtask a clean context, runs independent work at the same time, or fits the settings to each subtask.

Q: Must the workers run on a different model from the orchestrator?

No. Specialization by configuration allows it, and it often saves money. But a worker can run on the same model with a different prompt and tool menu. Choose each tier by measuring quality on that subtask.

Q: Should a worker that runs out of budget take unused budget from another worker?

No. It reports back partial results and stops, and the orchestrator decides whether to spend the reserve on a new, scoped subtask.

Q: Can the two shapes appear in one design?

Yes. For example, one stage of a pipeline could fan out to several workers and then fan their reports back in. Each part still needs contracts, budgets, and state in a store.

Q: Is a producer-reviewer pair the same as agent debate?

No. A producer-reviewer pair has fixed roles and a fixed round limit, and code decides when it stops. A debate has no fixed end, so its cost and its result are hard to predict.

Key Takeaways

  • Default to one competent agent. Give it good tools and a bounded context. Every added agent multiplies cost, latency, and failure surface.
  • Three cases earn a second agent. They are context isolation, parallelism, and specialization by configuration. Context isolation is the strongest of the three.
  • Two shapes work in production. They are orchestrator-workers and a pipeline with agentic stages. Most real systems are sequential handoffs, not agents that debate.
  • Handoffs are contracts. Each one carries a task, scoped context, tools, a budget, and a report schema with evidence pointers.
  • State and budgets live outside the agents. A task state store makes a crashed worker retryable. Hierarchical budgets end in partial reports, not silent failures.
  • Errors compound one level up. A bad report becomes a false premise for the orchestrator, so verify the integration step.
  • In a system design interview, start from one agent and say what a second one would buy. If a case is earned, name it, pick the shape, and describe the handoff contract, the budget split, and the cost multiple.

The next lesson, Agent Memory and Context, looks at one agent on a long task. It shows how an agent keeps its context small and its task state durable.

Check Your Understanding

1. A team proposes three agents that debate every support reply until they agree. What should you propose instead?

Show answer

A bounded producer-reviewer pair, or a single agent. Free-form debate has no fixed number of rounds, so its cost has no upper bound. A drafting agent and a reviewing agent with a limit of two rounds gives a review step with a known cost.

2. Every worker report was correct, but the final report states a wrong conclusion. Where is the defect, and what fixes it?

Show answer

In the integration step, at the handoff. Tighten the report schemas so every claim carries an evidence pointer and its conditions. Add a verification pass on the integration step. Then check whether two workers covered the same thing and reported different values.

3. A worker uses its whole budget before it finishes its subtask. What should it do?

Show answer

Stop and report back partial results. Its report should list what it found and mark the rest as gaps. It should not keep running, borrow another worker's budget, or fail without a report. The orchestrator then integrates what it received.

4. A manager asks the research assistant for one competitor's delivery fee. Should the design use several agents?

Show answer

No. The request is one small subtask. There is nothing to run in parallel, the context stays small, and no subtask needs different settings. One agent with good tools does the job for a fraction of the cost.
