Know the Vocabulary

This lesson uses the terms below many times. Read them once now, and come back here when a later section needs one.

  • Large language model (LLM): A model trained on very large amounts of text to write text. Given some text, it predicts what comes next, one small piece at a time.
  • Token: The unit of text an LLM reads and writes. In English, a token is about three-quarters of a word on average, or about four characters.
  • Prompt: All the text sent to the model in one call. It can hold instructions, the conversation so far, and documents.
  • Context window: The largest number of tokens the model can handle in one call. The prompt and the answer must both fit inside it.
  • Context assembly: The step that decides what goes into the prompt for each call. Your application does this work, not the model.
  • Inference: Running a trained model on an input to get an output. For an LLM, one inference call writes a whole answer.
  • Prefill: The first phase of a call. The model reads every token of the prompt, and it can process those tokens together, in parallel.
  • Decode: The second phase of a call. The model writes the answer one token at a time, and each new token depends on the tokens before it.
  • Time to first token (TTFT): The time from sending a request until the first token of the answer arrives.
  • Time per output token (TPOT): The average time the model takes to write each token after the first one.
  • Streaming: Sending the answer to the user piece by piece while the model is still writing it.
  • GPU: A graphics processing unit, a chip that runs many calculations at the same time. Most LLMs are served on GPUs.
  • Weights: The learned numbers inside a model, also called parameters. To serve a model, its weights must be loaded into GPU memory.
  • KV cache: Memory where the model keeps its work on earlier tokens, so each decode step does not repeat that work.
  • Hosted API: A model run by a provider that charges for each token. Self-hosting means running a model on GPUs that you rent or own, paid by the hour.
  • Hallucination: An answer that sounds confident but is false, or is not supported by the sources the model was given.
  • Fine-tuning: Training an existing model further on your own examples, to change how it behaves, such as its tone or format.

Part 1: The Cost Flips Over

In Module 2, the model was the smallest part of the system. The delivery-time model ran in about 1 to 10 milliseconds (ms). Fetching its features often took longer than running it. Much of the cost sat in the data pipelines around the model.

Now take a different feature from the same food-delivery company. The Module 1 capstone scoped a support assistant. It answers questions about order status and refund policies. It writes each answer with a large language model.

Here the picture flips, because one answer can take several seconds to finish. One reply can cost about a cent in model charges, at example prices. The model usually runs on GPUs, which cost much more per hour than ordinary servers.

So the model is no longer the smallest box. It is often the slowest and the most expensive part of the request. This module treats the LLM as a production component, with a speed, a price, and limits.

What Interviewers Expect

Many candidates draw one box labeled "LLM" and move on. Interviewers then ask the questions this module answers. How long will the user wait for the first word? What does one conversation cost, and what does a full day cost? What happens when traffic doubles, or when the provider goes down? How do you know the answers are good?

These questions are not about how the model works inside. They are about the model as a component in a larger system. A software engineer who can reason about its speed, price, and limits can design many LLM features.

This lesson gives you a map of one LLM call and of the module. The seven lessons after it fill in each part of the map.

Part 2: What an LLM Call Is

The Definition

An LLM call is one request that sends a prompt to a model and gets back generated text. From a system designer's view, three facts describe every call.

  1. The input is built fresh for every call. The model's weights do not change while you talk to it, so the model does not remember earlier calls. If the model needs the conversation so far, your application sends it again. Some services can store the history for you, but it is still fed to the model on each call. If the model needs a customer's order status, your application looks it up and adds it. This is context assembly, and you design it.

  2. The work runs in two phases. In prefill, the model reads the whole prompt. It can process the prompt's tokens together, in parallel. In decode, the model writes the answer one token at a time. It cannot write the 50th token before the 49th, because each token depends on the ones before it. A long prompt mostly makes prefill longer, and a long answer makes decode longer.

  3. Two meters run on every call. The latency meter measures time: TTFT for the start of the answer, and TPOT for each token after that. The cost meter counts tokens: input tokens for the prompt, and output tokens for the answer. With a hosted API, you pay for each token. When you self-host, you pay for GPU hours instead. The number of tokens to process then decides how many GPUs you need.

The diagram below shows one call and its two meters.

Notice that the user sees nothing until prefill ends. After that, streaming shows each token as decode writes it. So the user starts reading long before the answer is complete.

Why Output Tokens Usually Cost More

Example prices in this module are 12 per million output tokens. They are illustrative assumptions, not real quotes from any provider. The gap between the two prices comes partly from the two phases.

Input tokens are read together in one prefill pass. Each output token needs its own decode step, run one after another, so output work takes longer per token. Providers also set prices for business reasons, so the ratio is not a fixed rule.

The design lesson is that short answers save both money and time. A cap on answer length is a real cost control, not only a style choice.

What the GPU Must Hold

A GPU has a fixed amount of memory, and two things compete for it.

The first is the model's weights, and at 16-bit precision each parameter takes 2 bytes. So a model with 70 billion parameters needs about 140 GB for its weights alone. That is more memory than many single GPUs have, so such a model is often split across several GPUs.

The second is the KV cache, which grows with every token of every active conversation. So GPU memory often limits how many conversations one GPU can serve at the same time.

Serving engines run many conversations on one GPU together, which is called batching. Good batching is a main reason a GPU fleet can be cost effective. The lessons ahead show how to size a fleet and when it beats a hosted API.

What an LLM Call Is Not

An LLM call is not a fast function call. A small predictive model answers in milliseconds. An LLM answer often takes seconds, so one latency number is not enough. You need the time to the first token and the time to finish.

An LLM call is not priced per request. Two calls to the same model can differ in cost many times over. The length of the prompt and the length of the answer set the price.

An LLM call is not a database lookup. The model can write a fluent answer that is wrong, which is called a hallucination. It also does not know your private data, such as one customer's order, unless that data is in the prompt.

An LLM call is not repeatable by default. The model picks each token with some randomness, so the same prompt can produce different answers. Settings can reduce this randomness, but tests must still check what an answer means, not its exact words.

Part 3: Follow One Support Message

The fastest way to understand one call is to follow it through the system. The steps below use the food-delivery support assistant. The times, token counts, and prices are illustrative assumptions, not measurements.

Step 1: A message arrives. It is the third turn of a conversation. The customer writes, "My order is 20 minutes late. Where is it?" The clock starts at 0 seconds.

Step 2: The context is assembled. The support service builds the prompt, starting with the system instructions, which are the fixed rules for how the assistant behaves. It looks up this customer's order status in the order service. It adds the late-delivery policy and the two earlier turns. The prompt comes to about 3,000 tokens. This step takes about 0.2 seconds, mostly for the lookups.

Step 3: Prefill reads the prompt. The model server reads all 3,000 tokens, which takes about 0.5 seconds in this example. Waiting in a queue and the network add a little more. The first token reaches the screen at about 0.8 seconds, and that is the TTFT the customer feels.

Step 4: Decode writes the answer. The model writes about 300 tokens, which is roughly 225 words. At an example TPOT of 30 ms, that takes about 9 seconds. Streaming shows each token as it arrives, so the customer reads along. The answer is complete at about 10 seconds.

Step 5: The call is logged and priced. The service records the prompt version, the model version, and the token counts. At the example prices, the input costs 3,000 x 0.009. The output costs 300 x 0.0036. The whole call costs about $0.0126, which is about 1.3 cents.

Step 6: Quality is checked later. That night, an evaluation job samples conversations and checks them in three ways. Code checks the format and the policy rules. A second model grades the answers against a written guide, and people review a smaller sample. The logs also show whether each issue was resolved or passed to a human agent.

Step 7: A change ships safely. Suppose the team wants a smaller, cheaper model to answer order-status questions. First, the new setup runs on a golden set: a fixed set of past conversations, each with the behavior a good answer must show. If it passes, a canary release sends it a small share of live traffic, and then more.

The diagram below shows the same seven steps. In the top row, each time counts from the moment the message arrives.

Notice that the customer waited less than a second for the first word, but about 10 seconds for the whole answer. The two numbers have different causes: a long prompt slows the start, and a long answer slows the finish.

The Module 1 capstone set an example target of about five seconds to finish a short answer, so this answer is too slow. A cap of about 150 tokens would cut decode to about 4.5 seconds. That brings the finish close to the target, and it also cuts the output cost in half.

Notice also what Step 2 sent again: the two earlier turns. The model remembers nothing, so every turn sends the history again. Turn 10 carries far more input tokens than turn 1, unless the system summarizes or trims the history.

From One Turn to One Day

One call costs about a cent, but the design question is what a full day costs. Assume each conversation has 10 turns. Assume each turn averages 3,000 input tokens and 300 output tokens, with the repeated history already counted in that average. One conversation then costs about 10 x 0.126.

The Module 1 capstone estimated about 40,000 support conversations a day for this company. At 5,040 a day in model charges. That figure leaves out retrieval, retries, and monitoring. For a busier support bot with 100,000 conversations a day, the same arithmetic gives $12,600 a day.

Module 1 also assumed that a human-handled ticket costs $4. Do not compare one bot conversation with one human ticket directly. A conversation that still reaches a human pays for both. Compare the total support cost for each issue that is correctly resolved.

Inference Economics works through this arithmetic step by step.

Module 2 built a serving path for a small model, and much of it still applies. The table compares the delivery-time model with the support assistant.

Checking qualityCompare the estimate with the real delivery timeMany good answers exist, so there is no single correct label

The serving discipline carries over. A request still has a latency budget. A slow or unavailable model still needs a fallback, such as a second provider or a smaller model. Every call is still logged with the versions it used. New versions still ship in careful steps, as Model Serving Basics describes.

The units change. Latency moves from milliseconds to seconds, and it splits into two numbers. Cost moves from a small amount per request to a token bill that grows with every token in and out.

Three new design questions appear. What goes into the prompt? Which model answers, and does it run on a hosted API or on your own GPUs? How do you test answers that have no single correct label? The lessons of this module answer all three.

Part 7: What the Rest of the Course Reuses

Every later lesson that uses an LLM reuses this module. The model call, its two meters, and its tests return again and again.

Retrieval fills the prompt. Retrieval-augmented generation (RAG) looks up relevant passages and places them in the prompt, so every retrieved passage spends input tokens. The RAG Pipeline sets the budget for those passages by cost and latency, not by the size of the context window.

Product designs start from TTFT and cost. Design a ChatGPT-Style Assistant uses TTFT as the number that shows whether a chat feels quick. It also tracks cost per conversation, as this module does.

Safety starts from the shared prompt. Instructions, user messages, and retrieved documents all reach the model as text in one prompt. So text in a message or a document can try to override your instructions. Safety and Guardrails calls this prompt injection and shows how to defend against it.

Agents multiply the calls. An agent calls the model many times to finish one task. So its cost is the sum of every step's tokens, as What an Agent Actually Is explains. The food-delivery assistant returns in Capstone: A Customer-Support Agent, where it can also take actions such as refunds.

Part 8: Common Mistakes This Module Prevents

Mistake 1: Giving One Latency Number

"The model takes two seconds" hides the real behavior. Give the time to the first token and the time to finish, because they have different causes. A long prompt slows the first, and a long answer slows the second.

Mistake 2: Pricing Per Request

An LLM bill is counted in tokens, and output tokens usually cost more. A design that says "one call costs one cent" without token counts cannot be checked. Size one unit in tokens, price it, and then multiply by volume.

Mistake 3: Filling the Context Window Because It Fits

A large context window gives you room, not a plan. Every extra token adds cost and time, and models can also miss important facts in a very long prompt. Decide what goes in, and trim or summarize the rest.

Mistake 4: Fine-Tuning to Add Facts

Facts that change often, or that only some users may see, belong in the prompt through retrieval. Fine-tuning changes how the model behaves, such as its format or tone. It is usually a poor way to keep facts current or private.

Mistake 5: Optimizing Before Pricing

Caching and routing sound good in any design, but compute the bill before any optimization. That number shows where the cost sits, and how much each change could save.

Mistake 6: Shipping a Prompt Change Without Tests

A small change to a prompt can break answers that used to work. Run a golden set on every prompt change and every model change, the way unit tests run on every code change.

FAQs

Q: Do I need to understand how a transformer works inside?

No. This module treats an LLM as a component with tokens in, tokens out, two phases, and a price. You need to know how prompt length and answer length affect time and cost, not how to build the model.

Q: Should I memorize the prices and speeds in these lessons?

No. Prices and speeds change often, and every number here is an illustrative assumption. Learn how the numbers relate to each other. In an interview, say that your numbers are order-of-magnitude estimates and that you would check current prices.

Q: Does streaming make an answer cheaper?

No. The model writes the same tokens either way. Streaming changes how quickly the answer starts to appear, which is the delay users notice most.

Q: Is running your own GPUs always cheaper at high volume?

No. Steady, high volume can favor self-hosting, but the fleet also needs engineers, spare capacity, and monitoring. Compare the total cost at the quality you need. Many teams end with a mix of a hosted API and their own GPUs.

Q: Should I read the lessons in order?

Yes, if you can. Each lesson uses the numbers and terms of the ones before it, and the capstone uses all of them.

Key Takeaways

  • The model is now often the biggest box. A small predictive model takes milliseconds and little money. An LLM answer can take seconds and about a cent per turn, at example prices.
  • Every call runs in two phases. Prefill reads the whole prompt and sets most of the time to the first token. Decode writes the answer one token at a time and sets the time to finish.
  • Two meters run on every call. The latency meter tracks TTFT and TPOT, and the cost meter counts input and output tokens.
  • The model remembers nothing between calls. Context assembly decides what each prompt holds, and repeated history makes later turns cost more.
  • The serving discipline of Module 2 carries over, with new units: seconds instead of milliseconds, and tokens instead of requests.
  • In a system design interview, price one conversation in tokens before you draw anything clever. Then give the TTFT target, the time to finish, the cost per day, and how you will test the answers.

Check Your Understanding

1. A call has a 3,000-token prompt and a 300-token answer. At example prices of 12 per million output tokens, what does it cost?

Show answer

**About 3 / 1,000,000 = 12 / 1,000,000 = $0.0036. The output has one tenth as many tokens, but it still makes up more than a quarter of the total.

2. Users say the first word takes too long, even though the answers are short. Which phase should you look at first?

Show answer

Prefill, plus any waiting before it. The time to the first token depends on reading the prompt, so a prompt that has grown too long is a likely cause. Time spent in a queue, slow lookups, and the network also add to it.

3. Why does turn 10 of a conversation usually cost more than turn 1?

Show answer

Because the history is sent again with every turn. The model remembers nothing between calls. If each prompt holds all earlier turns, the input grows as the conversation grows. Summarizing or trimming the history keeps that growth under control.

4. The assistant forgets the order number that the customer gave two turns ago. Is the model broken?

Show answer

No. The model only sees what the current prompt holds. Context assembly probably dropped that earlier turn, for example when it trimmed the history. The fix belongs in context assembly, such as keeping key facts like the order number in every prompt.
