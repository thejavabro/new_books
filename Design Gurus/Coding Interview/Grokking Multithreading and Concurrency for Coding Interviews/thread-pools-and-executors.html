Know the Vocabulary

This lesson uses the terms below many times. Read them once now, and come back here when a later section needs one.

  • Task: One small piece of work that a program wants done, such as sending one email. People also call it a job.
  • Thread pool: A limited group of threads that stay alive and run many tasks, one after another.
  • Worker thread: One of the threads in a pool, which takes a task, runs it, and then takes the next one.
  • Task queue: The waiting line inside a pool, where tasks wait until a worker is free.
  • Executor: An object that runs the tasks you give it. You say what to run, and the executor decides which thread runs it and when.
  • Submit (verb): To hand a task to an executor.
  • Future: An object that stands for the result of a task that may not be finished yet. You can ask it for the result later.
  • Shutdown: Telling a pool to accept no new tasks and to end its threads once the work is done.
  • Pool size: The number of worker threads in a pool.
  • Core: One part of the processor that runs one thread at a time.
  • CPU-bound task: A task that spends most of its time computing on a core.
  • I/O-bound task: A task that spends most of its time waiting for something outside the program, such as a mail server or a disk. "I/O" means input and output.
  • Stack: The block of memory that each thread keeps for its own function calls.

Part 1: The Confirmation Email Problem

The ticket sale from the Mutex Lock lesson is over, and now every buyer needs a confirmation email. A big sale can end with thousands of orders, so the site has thousands of small jobs to do.

The simplest plan is to start a new thread for each email. The thread builds the email, sends it, and ends. The code is short, and it works well for 10 emails, but not for 10,000.

What One Thread per Email Costs

A thread is not free, and every new thread costs the program in four ways.

  • Time to create and end it. The operating system must set up each new thread and clean it up when it ends. This takes far longer than building one short email.
  • Memory for its stack. Every thread needs its own stack, and on many systems each stack reserves about 1 MB of memory space. Ten thousand threads would reserve about 10 GB, even though each email needs very little memory.
  • Time spent switching. A core runs one thread at a time. With far more threads than cores, the operating system keeps switching the cores between threads. Each switch costs time that does no useful work.
  • No limit. If 50,000 orders arrive, the site starts 50,000 threads. The operating system can refuse to create more threads, or the program can run out of memory and crash.

The emails themselves are cheap, and the threads around them are what cost so much.

What the Site Needs Instead

The site needs a few threads that stay alive. Each thread sends one email and then takes the next one. Emails that arrive while every thread is busy wait in a line. The program creates the threads once and uses them again and again. This plan is called a thread pool.

Part 2: What a Thread Pool Is

The Definition

A thread pool is a limited group of worker threads that run tasks from one shared queue. The program does not create a thread for each task, but submits the task to the pool instead. The task waits in the queue until a worker is free. The worker runs the task and then goes back to the queue for the next one.

The workers stay alive between tasks, so the program pays the cost of creating them only once, no matter how many tasks it runs.

A post office with 4 clerks and one line works the same way. Customers join the line, and whenever a clerk finishes with one customer, the clerk calls the next one. The post office does not hire a new clerk for each customer. In a program, the clerks are the worker threads, and the line is the task queue. Each customer is a task, and hiring a new clerk is creating a new thread.

The diagram below shows the parts of a thread pool and how a task moves through them.

A thread pool follows four rules:

  1. A limited number of workers. The pool creates its workers once and keeps them. It does not create a new thread for each task. Most pools have a fixed size, but some, such as the shared .NET pool, change their size by themselves.

  2. Tasks wait their turn. When every worker is busy, a new task waits in the queue. Submitting a task is quick, because it only puts the task in the queue.

  3. Workers are reused. A worker that finishes a task takes the next one from the queue. If the queue is empty, the worker waits. It is blocked and uses no processor time.

  4. Results come back through futures. Submitting a task usually returns a future at once. The program asks the future for the result when it needs it.

Thread Pools and Executors

An executor is any object that runs tasks for you. The program says what to run, and the executor decides which thread runs it and when. A thread pool is the most common kind of executor, so people often use the two words together.

This split is useful, because the code that creates the emails no longer creates threads and only submits tasks. You can then change the pool size, or swap in a different executor, without changing that code.

What a Thread Pool Is Not

A thread pool does not make tasks safe. Several workers run tasks at the same time. Two tasks that change the same shared data still race, as the seat count did in the mutex lesson. They still need a mutex or another tool from this chapter.

A thread pool does not run every task at once. A pool of 4 workers runs at most 4 tasks at the same time, and every other task waits in the queue.

A thread pool does not make computing faster than the cores allow. A machine with 4 cores runs at most 4 threads at the same moment. A pool of 100 threads that all compute only makes them take turns.

The Code

The second version submits every email to a pool of 4 worker threads and collects each result from a future. In this demo, each email job only builds the email text. That keeps the job tiny, so the cost of the threads is easy to see. The program prints the emails sent, the threads it created, and the time.

Here are two real runs of the Java version on one test machine:

2000 emails, pool of 4 worker threads
One thread per email: emails sent 2000, threads created 2000, 119 ms
Thread pool         : emails sent 2000, threads created 4, 7 ms

2000 emails, pool of 4 worker threads
One thread per email: emails sent 2000, threads created 2000, 112 ms
Thread pool         : emails sent 2000, threads created 4, 6 ms

Both versions sent all 2,000 emails, but the pool created 4 threads instead of 2,000 and finished about 17 times faster.

The pool's time shows where the first version's time went. The pool built all 2,000 emails in about 7 ms. So almost all of the 119 ms went into creating, starting, and ending 2,000 threads. That is about 56 microseconds for each thread on that machine.

The other languages showed the same pattern. Python took 153 to 167 ms with one thread per email and 16 to 34 ms with the pool. C++ took 49 to 50 ms and 2 to 4 ms, and C# took 99 to 102 ms and 3 ms. The C# version uses the shared .NET thread pool, which chooses its own size and added 6 threads in the test.

Notice that the pool version still runs 2,000 tasks, and only the number of threads changed.

Notice also how the results come back. In the first version, each thread writes into its own slot of an array, so threads never share a counter. In the pool version, each task returns its result through its future. Only the main thread adds up the results, so no lock is needed.

What Happens, Step by Step

Picture a smaller pool with 2 workers and 5 emails.

Step 1: The main thread submits five emails. Each submit puts one task in the queue and returns a future at once. Worker 1 takes email 1, and Worker 2 takes email 2. Emails 3, 4, and 5 wait in the queue.

Step 2: The workers take the next emails. Worker 1 finishes email 1 and takes email 3 from the queue. Worker 2 finishes email 2 and takes email 4. No new thread was created, and the main thread waits for the results.

Step 3: The last email leaves the queue. Worker 1 takes email 5, the last task. Worker 2 finds the queue empty, so it waits for a new task. The main thread still waits for the last result.

Part 4: Executors and Futures in Each Language

Java, Python, and C# each have a thread pool in their standard library. C++ does not, so the C++ program builds a small one.

LanguageCreate the poolSubmit a taskWait for the result
JavaExecutors.newFixedThreadPool(4)pool.submit(task) returns a Futurefuture.get()
PythonThreadPoolExecutor(max_workers=4)pool.submit(fn, arg) returns a Futurefuture.result()
C#None needed: one shared pool per programTask.Run(work) returns a Taskawait task or task.Result
C++None built in: the program builds onepool.submit(task) returns a std::futurefuture.get()

A few details matter in each of the four languages.

  • Java. Executor is the simplest executor interface, with only an execute method. ExecutorService adds submit, futures, and shutdown, and the Executors class has methods that create common pools. The demo passes its own thread factory, a small function that creates each thread, so that it can count the threads.
  • Python. ThreadPoolExecutor lives in the concurrent.futures module. If you leave out max_workers, it uses the number of cores plus 4, and at most 32.
  • C#. Task.Run puts work in the queue of the shared .NET thread pool. The runtime decides how many threads that pool has, and it adds threads when tasks wait too long.
  • C++. std::async is not a thread pool. With std::launch::async, the C++ standard says it runs each task as if on a new thread. The demo's pool keeps a queue of tasks, a mutex, and a condition variable. Workers wait on the condition variable until a task arrives. The Condition Variables lesson explains that tool.

Part 5: Choosing the Pool Size

The right pool size depends on what the tasks spend their time doing.

CPU-bound tasks compute the whole time, such as resizing images. A core can run only one thread at a time, so a pool about the size of the core count keeps every core busy. More threads only take turns on the same cores.

I/O-bound tasks spend most of their time waiting, such as sending an email and waiting for the mail server to answer. A waiting thread uses no processor time, so more threads can keep the cores busy while others wait.

A common starting formula for I/O-bound tasks is:

threads = cores x (1 + wait time / compute time)

Suppose each email needs 2 ms of processor time and then waits 18 ms for the mail server. On 4 cores, the formula gives 4 x (1 + 18 / 2) = 40 threads. Treat the result as a starting point, and measure.

A program can ask for the core count: Runtime.getRuntime().availableProcessors() in Java, os.cpu_count() in Python, std::thread::hardware_concurrency() in C++, and Environment.ProcessorCount in C#. On many processors, one physical core can run two threads, and these methods count it as two cores.

Use a pool about the size of the core count when:

  • Each task computes the whole time, such as resizing images.
  • The language runs threads on several cores at once, as Java, C++, and C# do. In standard Python, only one thread runs Python code at a time, so threads do not speed up computing. Use ProcessPoolExecutor there. It uses separate processes, with the same submit and future methods.

Use a larger pool when:

  • Each task mostly waits, such as for a mail server, a database, or a disk.
  • The thing the tasks wait for can handle that many requests at once. If the mail provider accepts only 10 connections at a time, 40 threads do not help. The Semaphore lesson shows how to respect a limit like that.

Part 6: Shutting Down a Pool

In Java, Python, and the C++ demo, a worker waits for the next task forever. So the pool does not end on its own, and the program must shut it down. Shutdown has two steps. First, the pool stops accepting new tasks, and then the workers finish the tasks in the queue and end.

LanguageHow to shut downWhat happens if you forget
Javapool.shutdown(), then pool.awaitTermination(...)With a fixed pool, the program never exits, because the pool's threads keep it running.
PythonUse with ThreadPoolExecutor(...) as pool:, or call pool.shutdown()Python still waits for the pool's tasks before the program ends.
C#Nothing to shut down. The shared pool lasts as long as the program.When Main returns, the program ends, and any unfinished tasks are dropped. Wait for every task first.
C++The pool's destructor in the demoThe destructor finishes the queue and joins every worker. Destroying a std::thread that was never joined ends the program at once.

From Java 19, ExecutorService also has close(), which shuts the pool down and waits for its tasks. So a try (ExecutorService pool = ...) block does both steps for you.

Java also has shutdownNow(), which interrupts the running tasks and returns the tasks that never started. Use it only when the remaining work may be thrown away.

Part 7: Common Mistakes

Mistake 1: Never Checking the Future

When a submitted task throws an error, the pool does not print it, and the future stores the error instead. Asking the future for the result throws the error again, so the caller can handle it. If nobody asks, nobody sees the error.

pool.submit(send_email, order)          # wrong: an error is stored and never seen

future = pool.submit(send_email, order)
future.result()                         # right: raises the error here, if there was one

In Java, get() throws an ExecutionException that holds the error. In C#, task.Result throws an AggregateException, and await throws the error itself, as get() does in C++.

Mistake 2: A Task That Waits for Another Task in the Same Pool

Suppose each email task in a pool of 4 workers submits a second task to the same pool to build a PDF ticket. It then waits for that task's future. If 4 email tasks do this at once, all 4 workers wait. The 4 PDF tasks sit in the queue, but no worker is free to run them. No thread can ever continue, which is a deadlock.

The fix is to never make a task wait for another task in the same fixed pool. Build the PDF inside the email task, or give PDF tasks a pool of their own.

Mistake 3: A Queue With No Limit

The queue in Java's newFixedThreadPool and in Python's ThreadPoolExecutor has no limit. If orders arrive faster than the workers finish them, the queue keeps growing until the program runs out of memory.

A queue with a limit stops that growth. In Java, you can create a ThreadPoolExecutor with an ArrayBlockingQueue of a fixed size. When that queue is full and the pool cannot add more workers, a new task is rejected with an error by default. With CallerRunsPolicy, the submitting thread runs the task itself instead, which slows the submitter down. The Bounded Blocking Queues lesson explains this kind of queue.

Java's newCachedThreadPool has the opposite problem. Its number of threads has no limit, so a burst of slow tasks can create thousands of threads, as in Part 1.

Mistake 4: One Pool for Fast and Slow Tasks

Suppose the same pool of 4 workers sends emails and also builds seat maps. If the mail server is slow one day, 4 email tasks can keep all 4 workers waiting. Every seat map then waits behind them, although the seat maps have nothing to do with email. Give slow, waiting tasks a pool of their own.

FAQs

Q: Is a thread pool always faster than one thread per task?

No. The pool saves the cost of creating threads, which matters most for many short tasks. For a few long tasks, that cost is small next to the work. The pool still helps by putting a limit on the number of threads.

Q: How many tasks can run at the same time in a pool of 4 workers?

At most 4, and the other tasks wait in the queue until a worker is free.

Q: Does an error in one task stop the pool?

No. With submit, the error is stored in the task's future, and the worker goes on to the next task. In Java, a task started with execute instead of submit ends its worker thread when it throws, and the error is printed. The pool then creates a new worker to replace it.

Q: Should I put Java virtual threads in a pool?

No. Virtual threads, added in Java 21, are very cheap to create. Java's advice is to start one for each task, for example with Executors.newVirtualThreadPerTaskExecutor(). To limit how many tasks use something at once, use a semaphore.

Q: What is the difference between a thread pool and a bounded blocking queue?

A bounded blocking queue only holds work, while a thread pool is a queue of tasks plus the workers that take tasks from it. Many pools use a blocking queue inside.

Key Takeaways

  • A thread pool runs many tasks on a few threads that stay alive. Tasks wait in one queue, and each worker takes the next task when it is free.
  • One thread per task wastes time and memory. In the demo, Java took about 119 ms to send 2,000 emails with 2,000 threads, and about 7 ms with a pool of 4.
  • Submit tasks, and read the results from futures. A future also carries any error, so always check it.
  • Size the pool for the work. Use about the core count for CPU-bound tasks, and more threads for I/O-bound tasks.
  • Shut the pool down when the work is done. A forgotten Java pool keeps the program running, and a C# program that ends early drops unfinished tasks.
  • Watch for the common mistakes. They are unchecked futures, tasks that wait for tasks in the same pool, unlimited queues, and one pool for fast and slow work.
  • In a coding interview, say why you use a pool: many short tasks and a limit on threads. Then give the pool size and explain it from the kind of task, and say how the pool shuts down.

Check Your Understanding

1. What are two costs of starting a new thread for each of 10,000 small emails?

Show answer

It costs time and memory. Creating and ending 10,000 threads takes far longer than building the emails. Each thread also needs its own stack, so 10,000 threads reserve a lot of memory. With no limit, the program can even crash.

2. A pool has 4 workers, and 100 tasks are submitted at once. What happens to the tasks that do not get a worker right away?

Show answer

They wait in the pool's task queue. Each worker takes the next task from the queue when it finishes one. All 100 tasks run in the end, at most 4 at a time.

3. Each task in a pool of 4 submits a second task to the same pool and waits for its future. Why can the program stop forever?

Show answer

All 4 workers can end up waiting. The second tasks sit in the queue, but no worker is free to run them. No thread can continue, which is a deadlock.

4. On a machine with 8 cores, a task computes the whole time. About how many workers should the pool have?

Show answer

About 8. Only 8 threads can run at the same moment. More threads that all compute only take turns on the same cores.
