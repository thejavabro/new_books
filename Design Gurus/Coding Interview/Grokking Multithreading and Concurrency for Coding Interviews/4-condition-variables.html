Know the Vocabulary

This lesson uses the terms below many times. Read them once now, and come back here when a later section needs one.

  • Condition: A fact about shared data that a thread waits for, such as "the sale is open." In code, it is a test, such as sale_open == True.
  • Polling: Checking a value again and again, with a short sleep between checks, until it changes.
  • Busy waiting: Polling with no sleep at all, which keeps a CPU core busy while the thread waits. It is also called spinning.
  • Condition variable: A place where threads can sleep until another thread tells them that shared data has changed. It always works together with a mutex.
  • Wait: The call that puts a thread to sleep on a condition variable. It also releases the mutex while the thread sleeps.
  • Notify: The call that wakes one thread that waits on a condition variable. Java's Condition calls it signal, and C# calls it Pulse.
  • Notify all: The call that wakes every thread that waits on a condition variable, also called a broadcast.
  • Wakeup: The moment a sleeping thread is woken and its wait call returns.
  • Lost wakeup: A bug where a notify happens before a thread starts to wait. The thread then sleeps and is never woken.
  • Spurious wakeup: A wakeup that happens even though no thread called notify.

Part 1: The Waiting Room Problem

The concert sale opens at 10:00, and fans who come early do not see the Buy button yet. The site puts them in a waiting room instead. On the server, each fan in the waiting room is one thread.

Each of these threads must wait until the box office opens the sale. Then every waiting fan must start at once. The box office opens the sale by changing one shared value, sale_open, from false to true. The fans' threads need a way to find out that it changed.

The First Idea: Polling

The simplest plan is for each fan's thread to look at sale_open again and again, which is called polling. The code below reads the flag under the mutex and sleeps 50 ms between checks:

while True:
    with lock:
        if sale_open:             # 1. check
            break
    time.sleep(0.050)             # 2. sleep, then check again
start_buying()

The code is correct, and every fan starts buying in the end. The mutex from the Mutex Lock lesson keeps each read safe, but polling has two costs.

What Polling Costs

Wasted checks. Most checks find the sale still closed. A fan who waits 10 minutes and checks every 50 ms looks at the flag 12,000 times. With 1,000 fans, that is 12 million checks. Only 1,000 of them find the sale open.

Delay. The sale can open just after a fan checks. That fan then sleeps for the rest of its 50 ms before it looks again. So a fan can start up to one full sleep late. In a busy sale, a few late milliseconds can mean that a faster fan gets the seat.

Changing the sleep does not fix both costs. A shorter sleep cuts the delay but adds more checks. With no sleep at all, a thread checks the flag millions of times per second. This is busy waiting, and it keeps a CPU core busy doing nothing useful. The box office thread may even have to wait for a free core.

What the fans need is simple: each fan should sleep, use no CPU, and wake up as soon as the sale opens. A condition variable does exactly that.

Part 2: What a Condition Variable Is

The Definition

A condition variable is a place where threads can sleep until shared data changes. A thread that finds its condition false calls wait. It sleeps there and uses no CPU time. Another thread changes the shared data and then calls notify. The sleeping thread wakes up and checks the condition again.

A condition variable does not hold the condition. The condition lives in your own shared data, such as sale_open, and the mutex protects that data. The condition variable only lets threads sleep and wake around it.

What Wait Does

The wait call does three things, in this order:

  1. It releases the mutex. Other threads, such as the box office, can now take the mutex and change the data.

  2. It puts the thread to sleep. The thread uses no CPU time while it sleeps. These first two actions happen as one step, so no notify can come between them.

  3. It takes the mutex back before it returns. After a notify, the thread wakes up, but wait does not return until the thread holds the mutex again.

So a thread always holds the mutex when it checks the condition. This is true before the wait and after the wait.

The Two Sides

Every use of a condition variable has a thread that waits and a thread that notifies, and each side follows four steps:

The waiting thread (a fan)The notifying thread (the box office)
1. Lock the mutex.1. Lock the mutex.
2. While the condition is false, call wait.2. Change the shared data.
3. The condition is now true, so use the shared data.3. Call notify all.
4. Unlock the mutex, then do any slow work.4. Unlock the mutex.

The code below shows both sides in Python, where a Condition holds a mutex inside it. The line with sale_opened: locks that mutex.

# A fan's thread
with sale_opened:                 # lock the mutex
    while not sale_open:          # check the condition
        sale_opened.wait()        # release the mutex and sleep
    # here, sale_open is True and this thread holds the mutex

# The box office thread
with sale_opened:                 # lock the same mutex
    sale_open = True              # change the shared data
    sale_opened.notify_all()      # wake every waiting fan

Notice that the box office changes sale_open while it holds the mutex. Part 7 shows what goes wrong when it does not.

What a Condition Variable Is Not

A condition variable is not a flag, because it does not remember a notify. If the box office calls notify when no fan is waiting, the notify does nothing. A fan that calls wait later sleeps until the next notify, which may never come. This is why a fan checks sale_open first and waits only while it is false.

A condition variable is not a lock, and it cannot protect data by itself. It always works with a mutex, and the mutex protects the data.

A condition variable does not send messages, and a notify carries no data. It only tells the sleeping threads that something may have changed, so they should look again.

Here are two real runs of the Python version on one test machine:

8 fans arrive 20 ms apart, sale opens after 300 ms, polling every 50 ms
Polling a flag    : fans started 8, checks 48, longest delay 41.2 ms
Condition variable: fans started 8, checks 16, longest delay 0.2 ms

8 fans arrive 20 ms apart, sale opens after 300 ms, polling every 50 ms
Polling a flag    : fans started 8, checks 48, longest delay 41.6 ms
Condition variable: fans started 8, checks 16, longest delay 0.2 ms

Both versions started all 8 fans, so the difference is in the work and in the delay.

With polling, the fans checked the flag 48 times. Only 8 of those checks found the sale open, and the other 40 found nothing new. With the condition variable, each fan checked exactly twice. It checked once before it waited and once after it woke, which makes 16 checks.

The delay tells the same story. With polling, the slowest fan started about 41 ms after the sale opened. It had checked just before the opening and then slept through it. With the condition variable, the slowest fan started 0.2 ms after the opening.

The other languages showed the same pattern. With polling, Java, C++, and C# made 40 to 47 checks, and their slowest fan started 34 to 63 ms late. A delay above 50 ms means that a 50 ms sleep lasted longer than asked, which the operating system is allowed to do. With the condition variable, every run in every language made exactly 16 checks. The slowest fan was always less than 1 ms late.

Notice that the 16 checks do not depend on how long the fans wait. Polling adds one check per fan every 50 ms. If the fans waited 10 minutes, each polling fan would check about 12,000 times. Each fan on the condition variable would still check only twice.

Notice also that the fans did not leave the wait at the very same moment. Notify all wakes every fan, but each one must take the mutex back before its wait returns, so they leave one after another. Each fan held the mutex only for a moment, so even the last fan was less than 1 ms late.

What Happens, Step by Step

Follow two fans and the box office through the condition variable version.

Step 1: The fans wait. Fan 1 locks the mutex and sees that sale_open is false. It calls wait, which releases the mutex and puts Fan 1 to sleep. Fan 2 does the same.

Step 2: The box office opens the sale. The mutex is free, so the box office takes it. It sets sale_open to true, calls notify all, and unlocks the mutex. Both fans wake up.

Step 3: Fan 1 goes first. Fan 1 takes the mutex back, and its wait returns. It checks sale_open again, sees true, unlocks the mutex, and starts buying. Fan 2 is awake, but it waits for the mutex.

Step 4: Fan 2 goes next. Fan 2 takes the mutex, and its wait returns. It checks sale_open, sees true, unlocks the mutex, and starts buying.

Part 4: Condition Variables in Each Language

Every language in this course has a condition variable. The names differ, but each one has a wait, a notify, and a notify all.

LanguageCondition variableWaitNotifyNotify all
Javalock.newCondition() on a ReentrantLockawait()signal()signalAll()

C++std::condition_variable with a std::unique_lock<std::mutex>cv.wait(lock)cv.notify_one()cv.notify_all()
C#Built into every object, used inside lock (obj)Monitor.Wait(obj)Monitor.Pulse(obj)Monitor.PulseAll(obj)
Pythonthreading.Conditioncond.wait()cond.notify()cond.notify_all()

A few details matter in each language:

  • Java. Each Condition belongs to one ReentrantLock, and one lock can have several conditions, each with its own name. The synchronized form gives each object exactly one built-in condition. The program uses a ReentrantLock with one Condition named saleOpened.
  • C++. The wait call needs a std::unique_lock, not a std::lock_guard, because wait must unlock the mutex and lock it again. C++ also has cv.wait(lock, test), which runs the while loop for you.
  • C#. C# has no separate condition variable class, but a plain object used with the lock statement also has one built-in wait list. Monitor.Wait and Monitor.PulseAll use that list.
  • Python. A Condition holds a mutex inside it, but you can also pass in a lock you already have, as the program does. Python also has cond.wait_for(test), which runs the while loop for you.

In every language, a thread must hold the mutex when it calls wait. If it does not, Java throws IllegalMonitorStateException, C# throws SynchronizationLockException, and Python raises RuntimeError. In C++, it is undefined behavior. Java, C#, and Python also require the mutex for notify, with the same errors. C++ lets a thread call notify without the mutex. It must still change the shared data while it holds the mutex.

Part 5: Why the Wait Sits Inside a While Loop

Every wait in this lesson sits inside a while loop, not an if. The loop checks the condition again after every wakeup. Three things make that second check necessary.

Another thread got there first. Suppose a fan cancels, and one seat comes back on sale. Three fans are waiting for a returned seat, and the box office calls notify all. All three fans wake up, but they take the mutex one at a time. The first fan takes the seat. When the second fan gets the mutex, the seat is gone. With an if, the second fan would go on and sell a seat that does not exist. With a while, it sees that no seat is left and waits again.

A spurious wakeup. Java and C++ allow a wait to return even when no thread called notify, and their documentation says so. The loop handles it, because the thread checks the condition, finds it still false, and goes back to sleep.

Different conditions on one condition variable. Sometimes threads wait for different things on the same condition variable. A notify all for one thing also wakes the threads that wait for another thing. Each thread must check its own condition.

The first check, before any wait, matters too. A fan who arrives after 10:00 finds sale_open already true, so it never waits at all. Without that first check, the fan would wait for a notify that already happened, which is a lost wakeup.

Part 6: Notify or Notify All?

Notify wakes one waiting thread, and notify all wakes every waiting thread. The right choice depends on how many waiting threads can make progress.

Use notify all when:

  • Every waiting thread can go on, such as when the sale opens for all fans.
  • Threads wait for different conditions on the same condition variable. A plain notify could wake a thread whose condition is still false, while the right thread keeps sleeping.
  • You are not sure. Notify all is the safe choice, and its cost is that some threads wake, check, and go back to sleep.

Use notify only when both of these are true:

  • Only one waiting thread can make progress, such as when one seat comes back.
  • All waiting threads wait for the same condition, so any one of them can use the change.

In the waiting room, a plain notify would be a bug, because only one fan would wake up. The other 7 fans would sleep until something else woke them, and nothing else would.

Part 7: Common Mistakes

Mistake 1: Using If Instead of While

An if checks the condition only once, so after a wakeup the thread goes on without checking again. Part 5 showed three ways that can let a thread go on while its condition is false. The code below shows the mistake in Java and the safe version next to it:

// Unsafe: after a wakeup, the condition is not checked again
if (!saleOpen) {
    saleOpened.await();
}

// Safe: the loop checks again after every wakeup
while (!saleOpen) {
    saleOpened.await();
}

Mistake 2: Waiting Without Checking First

Some code calls wait as soon as it takes the mutex, without looking at the shared data. If the box office has already opened the sale, its notify is gone. A condition variable does not remember it, so the fan sleeps forever. Always check the shared data first, and wait only while the condition is false.

Mistake 3: Changing the Data Without the Mutex

The box office must change sale_open while it holds the mutex, or two things can go wrong. First, a fan can read the flag while another thread changes it, which is a race. Second, in C++, where notify does not need the mutex, a wakeup can be lost.

Here is how the wakeup gets lost, in four steps. First, a fan holds the mutex, sees that sale_open is false, and is about to call wait. Second, the box office sets the flag to true without taking the mutex. Third, it calls notify all, but the fan is not waiting yet, so nobody wakes up. Fourth, the fan calls wait and sleeps forever. The diagram below shows the same four steps.

This can happen even when the flag is a std::atomic<bool>. When the box office takes the mutex to change the flag, it cannot act in that gap. The fan holds the mutex from its check until its wait releases it.

Mistake 4: Using Notify When Every Thread Must Go

As Part 6 showed, a plain notify in the waiting room wakes one fan and leaves the others asleep. Use notify all whenever more than one waiting thread can go on.

Mistake 5: Doing Slow Work While Holding the Mutex

When wait returns, the thread holds the mutex again. Suppose each fan buys its ticket before it unlocks, and buying takes 200 ms. Then the 8 woken fans take the mutex one after another, and the last one starts 1,400 ms late. Unlock the mutex first, and then do the slow work, as the Mutex Lock lesson advised.

FAQs

Q: Is polling ever the right choice?

Yes, sometimes. When the thing you wait for cannot notify you, polling may be the only way. An example is a payment that another company's server finishes. Inside one program, prefer a condition variable.

Q: Does notify all make every waiting thread run at the same moment?

No. It wakes them all, but each one must take the mutex back before its wait returns. They leave the wait one at a time. If each thread unlocks quickly, this takes very little time, as the demo showed.

Q: Do I need to hold the mutex to call notify?

In Java, C#, and Python, yes, and they throw an error if you do not. In C++, no, but you must still change the shared data while you hold the mutex.

Q: Is there a simpler tool for a one-time "start" signal?

Yes. Java has CountDownLatch, C# has ManualResetEventSlim, and Python has threading.Event. Newer versions of C++ have std::latch. Each one remembers that it was set, so a thread that arrives late does not wait. Python's Event is built on a condition variable.

Q: What is the difference between a condition variable and a semaphore?

A semaphore keeps a count, so a release is remembered even if no thread waits yet. A condition variable keeps nothing, and it only wakes threads that are already waiting. The Semaphore lesson covers semaphores.

Key Takeaways

  • A condition variable lets a thread sleep until another thread changes shared data. The thread uses no CPU while it waits, and it wakes when another thread notifies it.
  • Polling wastes checks and adds delay. In the demo, polling made 48 checks and started one fan about 41 ms late. The condition variable made 16 checks, and the slowest fan started 0.2 ms after the opening.
  • Wait releases the mutex, sleeps, and takes the mutex back before it returns. So the thread always holds the mutex when it checks the condition.
  • Always wait inside a while loop that checks the condition. The first check prevents a lost wakeup. The check after each wakeup catches spurious wakeups and changes by other threads.
  • Change the shared data while holding the mutex, then notify. Use notify all when every waiting thread can go on, and notify when only one can.
  • In a coding interview, name the condition, the mutex that guards it, and the thread that notifies. Then write the wait inside a while loop, and say why it is a loop.

A condition variable is the building block behind many other thread tools. A common example is a queue that makes threads wait when it is full or empty. The next lesson, Bounded Blocking Queues, shows that kind of queue.

Check Your Understanding

1. A fan's thread sees that sale_open is false and calls wait. What happens to the mutex while the fan sleeps?

Show answer

Wait releases it. Other threads, such as the box office, can take the mutex and change sale_open. Before wait returns, the fan takes the mutex back.

2. A developer writes if not sale_open: cond.wait() instead of a while loop. Why is that risky?

Show answer

The thread does not check again after it wakes. A spurious wakeup, or another thread that changed the data first, can let it go on while the condition is false.

3. The box office calls notify all at 10:00. A fan arrives at 10:01 and calls wait without checking sale_open first. What happens?

Show answer

The fan sleeps forever. A condition variable does not remember the notify, so nothing wakes the fan, which is a lost wakeup. Checking sale_open first fixes it, because the fan then sees true and never waits.

4. One seat comes back on sale, and 5 fans wait for a returned seat. Should the box office use notify or notify all?

Show answer

Notify is enough, if all 5 fans wait for the same thing. Only one fan can take the seat. Notify all also works, because the loop sends the others back to sleep, but it wakes 4 threads for nothing.
