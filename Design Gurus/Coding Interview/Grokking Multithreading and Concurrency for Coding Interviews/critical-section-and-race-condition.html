Know the Vocabulary

This lesson uses the terms below many times. Read them once now, and come back here when a later section needs one.

  • Thread: One path of work inside a program. A program can run many threads at the same time.
  • Shared data: Data that more than one thread can read or change, such as a count of tickets sold.
  • Race condition: A bug where the result depends on the timing of threads, that is, on which thread happens to reach a step first.
  • Interleaving: The order in which the steps of two or more threads mix together while they run.
  • Read-modify-write: A change made in three steps. A thread reads a value, computes a new value from it, and writes the new value back.
  • Lost update: A change that disappears because another thread wrote over it.
  • Check-then-act: Code that checks a condition and then acts on what it saw, such as "if no report exists yet, create one."
  • Atomic operation: An operation that the hardware finishes in one step, so no other thread can see it half done.
  • Critical section: The part of the code that uses shared data and must run in only one thread at a time.
  • Time slice: The short time a thread may run on a core before the scheduler may switch the core to another thread.
  • Preemption: The operating system stopping a running thread, at any point, so that another thread can use the core.

Part 1: One Small Change

The Fork/Join Model lesson counted the tickets sold after the sale. Each worker thread read its own pages of orders and counted them in its own array. The main thread then joined the workers and added the arrays together, and the answer was always right.

Now a developer makes one small change. Adding up the counts at the end looks like extra work. So every worker now adds each ticket straight to one shared counter:

# Before: each worker keeps its own count
counts[section] += 1

# After: every worker adds to the same counter
report.total_sold += 1

The change saves one step at the end, but it also breaks the program.

The Code

The program below counts the tickets both ways. To keep it short, it leaves out the database and gives one worker to each of the 4 sections. Each section gets 100,000 tickets, so the right total is 400,000. The real sale had only 8,000 tickets. The program uses large numbers because a race needs many updates to show up in a short test.

The first version gives each worker its own count, as before. The second version makes every worker add to one shared counter, and the program runs it 3 times. Each line prints the total and how many tickets were lost.

Before you look at the results, predict what the second version prints.

The first version counted 400,000 tickets in both runs. The shared counter never did, and its totals ranged from 125,062 to 378,499. In the worst try, Java lost 274,938 updates, which is more than two of every three tickets.

Notice three things about these results:

  • No error appeared. Each run finished and printed a number that looked normal.
  • The total changed from try to try. The same code, in the same run, gave a different answer each time.
  • Every wrong total was too low. No ticket was counted twice, and updates only disappeared.

The other languages gave a mixed picture. C++ lost updates in 5 of its 6 tries. C# lost updates in 2 of its 6 tries and printed 400,000 in the other 4. Python printed the right total in all 6 tries. Part 4 explains why Python did, and why that is not safe either.

Notice also how each language declares the shared counter. Java and C# mark it volatile, which makes each read see the latest value that any thread wrote. C++ makes it a std::atomic<int>, because two threads that change a plain int without a lock cause undefined behavior in C++. That means the language makes no promise about what happens. The C++ code then reads the counter and writes it in two separate calls. None of these tools joins the read and the write into one step, so the race stays.

Part 2: How an Update Gets Lost

One Line, Three Steps

The line report.total_sold += 1 looks like one step. To the computer, it is three:

current = report.total_sold   # 1. read the counter
current = current + 1         # 2. add 1 (the modify step)
report.total_sold = current   # 3. write the new value back

This pattern is called read-modify-write. A thread reads a value, computes a new value from it, and writes the new value back. On a plain variable, the count++ operator in Java, C++, and C# works the same way.

Each step is quick, but another thread can run between any two of them. That gap is where the updates go missing.

Two Workers, One Counter

Suppose the counter shows 41. Worker 1 and Worker 2 each count one more ticket at the same moment.

Step 1: Worker 1 reads. Worker 1 reads total_sold and gets 41.

Step 2: Worker 2 reads. Worker 1 has not written yet, so Worker 2 also reads 41.

Step 3: Worker 1 writes. Worker 1 adds 1 to its copy and writes 42.

Step 4: Worker 2 writes. Worker 2 adds 1 to its own copy, which is still 41, and writes 42 too.

Two tickets were counted, but the counter went up by only 1. Worker 2's write replaced Worker 1's change. This is a lost update.

The diagram below shows the same four steps over time. The middle row shows the value of total_sold at each moment.

Notice that each worker did its own steps in the right order. Neither worker made a mistake on its own, and the bug is in how their steps mixed together.

The order in which the steps of different threads mix together is called the interleaving. Some interleavings give the right answer, and others lose updates. The program does not choose which one happens. The scheduler and the hardware do, and they can choose differently on every run. That is why the totals in Part 1 changed from try to try.

Part 3: What a Race Condition Is

The Definition

A race condition is a bug where the result depends on the timing of threads. The threads "race" through the same code, and the result depends on which one reaches each step first.

A race condition needs three things, all at once:

  1. Shared data. Two or more threads use the same data, such as total_sold.

  2. At least one writer. At least one thread changes the data. If every thread only reads, nothing can go wrong.

  3. No control over the order. Nothing stops the steps of the threads from mixing in a bad order.

Take away any one of the three, and the race is gone. The first version of the program took away the first one. Each worker had its own count, so the workers shared no data while they ran. Every fix for a race works by taking away one of these three things.

Why Testing Misses Races

A race loses updates only when the timing goes wrong. In the test runs, C# printed the right total in 4 of its 6 tries. Python printed it in all 6. A developer who ran either one once could easily decide that the code works.

A separate timing test on the same machine showed why C# was right so often. In those tries, each worker finished all of its adds before the next worker even started. The workers never ran at the same time, so their steps never mixed.

Real data makes this worse. A real section has far fewer than 100,000 tickets. With fewer updates, a bad interleaving happens less often. The bug may stay unseen for months and then appear on the busiest day. A test that passes does not prove that code with shared data is safe. You have to find the race by reading the code.

What a Race Condition Is Not

A race condition is not the same as threads running at the same time. Threads that only read shared data, or that each use their own data, are safe together. The trouble starts only when shared data changes.

A race condition is not a crash. It usually gives a wrong result without any error, and that is what makes it dangerous.

A race condition is not the same as a data race, although the names are close. A data race is a narrower idea. It means two threads use the same memory at the same time, at least one of them writes, and nothing orders the two uses. In C++, a data race is undefined behavior. The C++ demo has no data race, because each single read and write of the atomic counter is safe. It still has a race condition, because the read and the write are two separate steps.

A race condition is not fixed by making each single step safe. The volatile counter in Java and C# and the atomic counter in C++ all still lost updates. Safety for each step on its own is not safety for the whole change.

Part 4: Why It Happens Even on One Core

You might think a race needs two cores, with two threads running at the very same moment. It does not.

On one core, threads take turns, and the scheduler gives each thread a short time slice. When the time slice ends, the operating system may stop the thread and let another thread use the core. This is preemption, and it can happen between any two instructions. The Thread Life Cycle and Scheduling lesson explains time slices and preemption.

So a thread can be stopped after it reads the counter and before it writes it back. Here is what that does on one core, starting again with a counter of 41.

Step 1: Worker 1 reads, then stops. Worker 1 reads the counter and gets 41. Right then, its time slice ends, and the scheduler stops it. Worker 1 still holds 41 in its own copy.

Step 2: Worker 2 runs. Worker 2 gets the core and counts 500 tickets, so the counter climbs from 41 to 541.

Step 3: Worker 1 continues. Worker 1 continues where it stopped, adds 1 to its old copy, and writes 42.

One write erased 500 updates, because a stopped thread holds an old value. When it continues, it writes that old value over everything that happened while it was stopped. This is how a race can lose many updates at once, not just one.

On a machine with several cores, both kinds of mixing happen. Threads still take turns on each core. Threads on different cores also run their steps at the very same moment. More cores give more chances for a bad interleaving, but one core is enough.

What About Python?

In the standard Python build, the Global Interpreter Lock (GIL) lets only one thread run Python code at a time. So Python threads behave much like threads that share one core. The Creating, Starting, and Joining Threads lesson introduced the GIL.

Python makes no promise about where it switches threads, and each version picks its own points. In the Python 3.12 runs on the test machine, no switch landed between the read and the write of +=, so no update was lost.

That luck is not safe to rely on. Python's own documentation lists i = i + 1 as an operation that is not atomic. A different Python version may switch threads at other points. The free-threaded Python build runs threads in parallel without the GIL, so its threads can lose updates on any run. The Mutex Lock lesson shows a Python race that appeared in both of its test runs. In that program, each thread waits 20 ms between its check and its update.

Part 5: Check-Then-Act

The Second Kind of Race

A lost counter update is one kind of race. The second common kind is check-then-act. A thread checks a condition and then acts on what it saw. Between the check and the act, another thread can change the condition. The act is then based on old information.

The best-known case is the last seat of a concert, where two buyers both see one seat left and both buy it. The Mutex Lock lesson walks through that case. The counting program can have the same kind of bug in a different place.

Two Reports for One Count

Suppose the workers share one report object. No report exists at first, so the first worker to finish creates it:

if summary.report is None:          # 1. check
    summary.report = Report()       # 2. act
summary.report.add(section, count)

Here is one interleaving of two workers that finish at about the same time.

Step 1: Worker 1 checks. Worker 1 sees that no report exists yet.

Step 2: Worker 2 checks. Worker 1 has not created the report yet, so Worker 2 also sees that none exists.

Step 3: Worker 1 acts. Worker 1 creates Report A and adds its section's count to it.

Step 4: Worker 2 acts. Worker 2 creates Report B, which replaces Report A. Worker 1's count is gone with Report A. Worker 2 then adds its own count to Report B.

The final report shows only one of the two sections. Again, no error appears, and the total is simply too low.

The Two Kinds Side by Side

The table below compares the two kinds of race.

Read-modify-writeCheck-then-act
The stepsRead a value, compute a new one, write it backCheck a condition, then act on it
Exampletotal_sold += 1if report is None: create a report
What goes wrongOne thread's write replaces another thread's writeThe act relies on a check that is no longer true
Typical resultA count that is too lowOne seat sold twice, or two reports made

Many real bugs mix both kinds. Here is a common one:

if section not in totals:     # check-then-act
    totals[section] = 0
totals[section] += count      # read-modify-write

Suppose two workers add counts for the same section. Both can see no entry and set it to 0, and the second 0 can erase a count that the first worker already added. Both can also read the same old total, so one count is lost.

Part 6: The Critical Section

The Definition

A critical section is the part of the code that uses shared data and must run in only one thread at a time. While one thread is inside, no other thread may run a critical section on the same data. To every other thread, the steps then look like one unbroken step.

In the counting program, the critical section is the line report.total_sold += 1. Its read, its add, and its write must happen together. In the report example, the critical section holds the check and the act together. If only the act were protected, two workers could still both pass the check. The call to add also changes the shared report, so it needs protection too.

How to Find a Critical Section

Step 1: Find the shared data. List each piece of data that more than one thread can reach while the threads run. In this lesson, that is total_sold and summary.report.

Step 2: Find every line that touches it. Include the reads, not only the writes. A read that feeds a later write is part of the change.

Step 3: Group the steps that belong together. A read belongs with the write that uses it. A check belongs with the act that depends on it.

Step 4: Leave everything else out. Work on a thread's own data does not belong inside. Every line inside a critical section makes other threads wait longer.

What a Critical Section Is Not

A critical section is not a whole function or a whole thread. It is usually a few lines, and it should stay that small.

A critical section is not code that only touches one thread's own data. In the first version, counts[section] += 1 is not a critical section. Each worker changes only its own slot, so no other thread ever uses that slot while the workers run.

A critical section is not safe just because you have found it. Finding it only tells you which lines need protection. Something in the code must still keep other threads out while one thread is inside.

Three Ways to Make It Safe

There are three common ways to make a critical section safe:

  1. Do not share. Give each worker its own data, and combine the results once at the end. Then no critical section is left while the workers run. The first version of the program did this.

  2. Turn the steps into one step. An atomic operation adds 1 to the counter in one step that no other thread can split.

  3. Let one thread in at a time. A lock makes every other thread wait outside while one thread runs the critical section. This is called mutual exclusion.

The next lesson tries all three on the shared counter and compares them.

FAQs

Q: Is count++ one step in Java, C++, or C#?

No, not on a plain variable. It is a read, an add, and a write, and another thread can run between them. The demo lost updates with ++ in Java and C#. In C++, ++ on a std::atomic<int> is one atomic step, so the C++ demo reads and writes in two separate calls instead. Each language has an atomic way to add 1, which the next lesson shows.

Q: Does Python's GIL make += safe?

No. The GIL lets only one thread run Python code at a time, but Python can still switch threads between the read and the write. The demo printed the right total in Python, but that was the timing of one Python version on one machine. Python's documentation says that i = i + 1 is not atomic.

Q: Does a race condition need more than one core?

No. On one core, the scheduler can stop a thread between its read and its write. Another thread then changes the data, and the first thread writes an old value over it.

Q: Does volatile fix the shared counter?

No. In Java and C#, volatile makes each read see the latest write. It does not join the read and the write into one step. The demo used a volatile counter in Java and C#, and both still lost updates.

Q: Can threads read shared data without any protection?

Yes, if no thread changes the data while they read it. For example, data that is set up before the threads start and never changed after that is safe to read. Once any thread writes the data, every read and write needs protection.

Key Takeaways

  • A race condition is a bug where the result depends on the timing of threads. It needs shared data, at least one writer, and nothing that controls the order of the steps.
  • total_sold += 1 is three steps: read, add, write. Two threads that run these steps at the same time can lose an update. In the demo, Java lost up to 274,938 of 400,000 updates.
  • Races hide from tests. The total changed from try to try. C++ and C# sometimes printed the right answer, and Python always did. A passing test does not prove that shared data is safe.
  • One core is enough for a race. The scheduler can stop a thread between its read and its write, and its later write erases every update made in between.
  • Check-then-act is the second common kind. A thread acts on a check that another thread has already made false.
  • A critical section is the code that must run in only one thread at a time. It must hold every step that belongs together, such as a read with its write, or a check with its act.
  • In a coding interview, point to the shared data and say which lines form the critical section. Name the kind of race, read-modify-write or check-then-act. Then say how you will protect it: avoid sharing, use an atomic operation, or use a lock.

You now know how to find a race and the lines that cause it. The next lesson, Protecting a Critical Section with a Lock, fixes the shared counter three ways and measures each one.

Check Your Understanding

1. Two threads each run total_sold += 1 once. The counter starts at 41. What values can it end with?

Show answer

43 or 42. If one thread writes before the other reads, the counter ends at 43. If both read 41 before either one writes, both write 42, and one update is lost.

2. Several threads add to one shared counter with no lock. A test runs the program 10 times, and it prints the right total every time. Is the code safe?

Show answer

No. A race loses updates only when the timing goes wrong. In the demo, C# printed the right total in 4 of 6 tries and Python in all 6, yet the code still had a race.

3. A program runs on a machine with one core. Can its threads still lose updates to a shared counter?

Show answer

Yes. The scheduler can stop a thread after it reads the counter and before it writes it back. Another thread changes the counter in between, and the first thread then writes an old value over it.

4. A developer protects only the line summary.report = Report(), but not the check if summary.report is None. Is the code safe?

Show answer

No. Two workers can both pass the check before either one creates the report. The check and the act together form the critical section.
