Case Study: A Publicly Trusted CA

How Google built and runs a certificate authority whose mistakes the whole internet would notice: memory-safe code, fuzzing, strict validation and lots of redundancy.

Why Google built its own public CA

Publicly trusted certificate authorities are the trust anchors of TLS: every browser and phone trusts them by default. Running one means yearly audits, browser-vendor rules and zero tolerance for mistakes; one CA went out of business after attackers misused it. Most organizations should never build one. Google did, for three reasons. Tap them, then the reasons to write the software rather than buy it.

2

Three tiers and two trust zones

Issuance is split into three layers of small microservices (request parsing, registration authority logic, signing) across two trust zones: untrusted input is handled in one environment, critical operations in another. An attacker who compromises one component gains only that component's narrow abilities. Send a request through and try to break a stage.

3

Memory-safe code where the untrusted input lands

Parsing DER-encoded certificate requests has a long history of memory-corruption bugs. The CA parses untrusted requests in Go (memory-safe), and uses C++ only where it integrates with core infrastructure, inside the secure zone. For extra safety, a request is parsed by both and the results compared; any disagreement stops processing. Hardened toolchains add W^X, a hardened allocator and SafeStack to the C++.

4

Do less, on purpose

Commercial and open source CAs supported every esoteric extension in the standards, which made them hard to validate. Google's CA supports only what standard web certificates need. Over a decade and three redesigns the team kept simplifying: consolidating microservices that had become too many, and replacing hand-written ACL checks in each RPC with a central check so no new RPC could ship without one.

5

Harden what you didn't write

Even widely used security libraries have bugs. The team reviewed each open source dependency in depth and sent fixes upstream, ran the X.509 parsing library in a container in the untrusted zone, and wrapped the vendor's closed-source hardware security module (HSM) code defensively, sandboxed with nsjail, reporting issues back to the vendor.

6

Test the bad paths too, constantly

Beyond unit and integration tests, the CA generates test issuances every few minutes: good ones that must succeed and egregiously bad ones that must fail and raise the right alarm. Static analysis, sanitizers and fuzzing run on all the code; a company-wide fuzzing "fixit" found a crash bug in Go's then-young X.509 parser. Every real certificate is also linted at several stages before issuance. Try the linter.

7

Protect the keys, and plan to lose them

Theft or misuse of the key material is a CA's worst risk. The root keys are kept offline behind multiple physical layers, each needing two people to open. Day-to-day issuance uses online intermediate keys. Getting a new root trusted in browsers, TVs and phones takes years, so Google pre-distributes alternate roots in advance. Issued certificates go into public Certificate Transparency logs plus several independent internal logs, reconciled entry by entry.
