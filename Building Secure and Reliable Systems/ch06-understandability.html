Design for Understandability

A system you can't reason about is a system you can't trust. Understandable designs let you state what must always be true, and then check that it is.

1

Say what must always be true

An invariant is a property that holds no matter how badly the environment behaves: malicious requests, crashed machines, overloaded backends. Security and reliability goals become concrete once they're written as invariants. If the system can violate one, that is a vulnerability or an outage waiting to happen.

effort vs. confidence

2

When the mental model stops predicting

Engineers reason with simplified mental models, which work fine under normal conditions. Security and reliability problems live in the abnormal conditions. A server that thrashes swap under memory pressure suddenly gets slower as load grows, which contradicts everyone's model. Design so the model keeps working: without swap, the server fails fast with a clear error.

3

Put each requirement in one place

"Every request must be authenticated, authorized and logged" is hard to verify if each of dozens of handlers does it by hand. Find the handler that forgot. Then switch to a framework that enforces the policy for every method.

4

Interfaces that leave little to interpret

Narrow, strongly typed interfaces (gRPC, protocol buffers) are easier to reason about than a free-form shell or an untyped JSON blob. A common object model, like the one Kubernetes uses for every resource, lets one mental model cover many types. And idempotent operations can be retried safely, which matters enormously during an outage. Press the elevator buttons as often as you like.

idempotent: "go to floor N"
not idempotent: "go up one floor"
5

Identities people and machines can understand

Access control, logs and audits all hinge on identities. A good identifier is understandable without a lookup, robust against spoofing, and doesn't get reused. IP addresses fail on all three, yet are often used anyway. Which identifier would you want in an audit log?

6

Shrink the trusted computing base

The trusted computing base (TCB) for a property is every component whose failure could break it. For "card numbers stay confidential" in a monolithic shop, that's all of the code. Split the payment handling into its own service with its own storage and a narrow API, and the TCB shrinks to something a reviewer can actually examine. Toggle the architecture and tap components.

7

Let types carry the guarantee

If URLs travel through a system as plain strings, every function that uses one must trust that some upstream code validated it. Make it a type whose only constructor validates, and the guarantee travels with the value. The same trick gives you types for SQL that can't contain user input, or HTML that is safe to render.

final class HttpsUrl {
  private HttpsUrl(String s) {…}
  // the only way in: validates or fails
  static Optional<HttpsUrl> parse(String s) {
    URI u = URI.create(s);
    if (!"https".equals(u.getScheme()))
      return Optional.empty();
    return Optional.of(new HttpsUrl(s));
  }
}
// downstream code can't receive a bad URL
void fetchAvatar(HttpsUrl url) {…}
Secure by default, and usableGoogle's Tink crypto library is the chapter's example: a small API that makes the right choices (key handling, no nonce reuse) automatically, so developers focus on their feature. If a safe API is awkward, people won't use it.
