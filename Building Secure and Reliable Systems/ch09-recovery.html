Design for Recovery

Things will break. Recovery is a design property: the mechanisms that get you back must themselves be safe, quick, and impossible for an attacker to turn against you.

1

What are we recovering from?

Systems need recovering from four broad kinds of error. Don't spend time classifying edge cases precisely; design so you can recover from all of them. Tap each.

2

Build it fast, then add the brakes

Design your update system to go as fast as you could ever need, then constrain it with a separate, policy-driven rate limit. The emergency push is just the normal push with the limit turned up, so the emergency path is exercised every day. Google learned this when a monthly golden-image rollout policy, baked into its tooling, couldn't keep up with a growing stream of urgent security patches.

Isolate the rate limiterMake the limiter a tiny standalone service that issues short-lived signed tokens saying "this change, approved at this time". It is easy to test, a natural place for change logs, and any code that duplicates it is an obvious red flag.
3

Rollbacks: reliability's friend, an attacker's tool

Reliability wants to roll back to the last good version. Security worries that "last good" might contain a known vulnerability, and that an attacker could walk a device backward one hop at a time ("unzipping") until it reaches one. Pick a strategy, then play both roles. Version v3 has a known exploit; v6 was just released and has a crash bug.

def update_allowed(state, release):
    # state lives outside any single release, so a downgrade can't erase it
    if release.version in state.deny_list: return False
    if release.svn < state.masvn:         return False  # below the floor
    state.masvn = max(state.masvn, release.masvn)        # floor only rises
    return True
4

Wall-clock time is hidden state

Anything that depends on the current time can block recovery: certificates that expired while a system was down, a clock reset to 1970 after a battery dies, an attacker spoofing unauthenticated NTP. Move the device's clock and see what happens to certificate checks.

Prefer rates, manually advanced epoch or version numbers, and explicit validity or revocation lists over wall-clock time. A hard-coded date in code is a time bomb.

5

Have an explicit way to revoke

When an attacker holds valid credentials, you need to switch them off quickly, at scale, without locking yourself out. Each design has a catch. Tap each.

6

Know your intended state, down to the bytes

Recovery means returning to a known good state, which is only possible if you know exactly what that state is. Even "stateless" services have state: their binary, config, credentials, firmware. Compare a host's intended state with what's actually on it.

Nobody cares about backups; they care about restoresBack up persistent data with integrity protection, keep versions so you can go back past silent corruption or an attacker's edits, protect backups from the same credentials that run production, and regularly test restores. Global services such as naming, identity and storage are the hardest to rebuild; plan their bootstrap.
7

Emergency access: the last layer

Recovery depends on responders being able to reach and talk about the system. Emergency access must use the absolute minimum of dependencies, because there's nothing left beneath it. Knock out a dependency and see whether responders can still get in.

Four error typesRandom, accidental, software, malicious: be ready for all.
Speed with brakesOne push system, rate set by policy; emergency = normal turned up.
Safe rollbacksExternal deny lists and a minimum acceptable security version stop "unzipping".

Known stateKnow every byte you intend; test restores, not just backups.
