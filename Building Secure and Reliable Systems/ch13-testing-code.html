Testing Code

Tests are how you find out your code does what you think. This chapter climbs from unit tests to fuzzers and formal analysis, each catching what the last one missed.

A ladder of testing techniques

No single technique finds everything. Each rung trades effort and speed for depth. Tap a rung.

2

Unit tests: pick the inputs that matter

Good unit tests are fast, deterministic and cover the edges, not just the happy path: empty input, boundaries, invalid formats, huge values. Here is a port-number parser with four hidden bugs. Choose test inputs and run them.

def parse_port(s: str) -> int:
    n = int(s)              # what if s is "" or "abc"?
    if n > 65536: raise ValueError   # off by one?
    return n               # negative? whitespace?
Testable code, and when to write testsTests shortly after the code, or first (test-driven), or when fixing a bug (a regression test proving it's gone). To unit test, code needs seams: interfaces you can swap for fakes, mocks or stubs instead of a real database or network.
3

Integration tests: the real thing, safely

A unit test with a mock only checks that your code called the ticket API. An integration test uses a real (test) instance and checks that a ticket was actually filed with the right fields. Keep least privilege in mind: test against hermetic test instances with synthetic data, never production accounts and real user data.

4

Fuzzing: let a machine invent the inputs

A fuzzer throws enormous numbers of generated inputs at a target and watches for crashes, sanitizer reports and hangs. Random bytes rarely get past the first checks of a parser. A coverage-guided fuzzer (libFuzzer, AFL) keeps any input that reaches new code and mutates it further, so it climbs deeper step by step. The target below crashes only on input beginning JPEG.

// a libFuzzer driver: the engine calls this millions of times
extern "C" int LLVMFuzzerTestOneInput(const uint8_t* data, size_t size) {
  Image img;
  DecodeJpeg(data, size, &img);   // crashes + sanitizer errors are findings
  return 0;
}
5

Dynamic analysis: sanitizers

Sanitizers instrument a build to catch bugs as they happen: AddressSanitizer (out-of-bounds, use-after-free), MemorySanitizer (uninitialized reads), ThreadSanitizer (data races), UndefinedBehaviorSanitizer, LeakSanitizer. They slow programs down, so they run in tests and fuzzing rather than production. Pair them with fuzzing: the fuzzer drives the code, the sanitizer notices the subtle corruption that wouldn't crash on its own.

6

Static analysis where developers already look

Static analysis inspects code without running it, from simple linters to abstract interpretation (proving, say, no division by zero in flight-control software) and formal methods. Google's Tricorder runs about 146 analyzers over 30+ languages on roughly 50,000 code reviews a day, and shows findings in the review itself, many with a one-click fix. Its rule: keep the false-positive rate reviewers perceive under 10%. Mark warnings below.
