Chapter 3: one door into production

Suppose an existing system was not designed with least privilege or recovery in mind, and rebuilding it isn't an option. A safe proxy adds controls without touching the system: clients talk to the proxy, the proxy checks and logs, and the targets are configured to accept calls only from the proxy. Toggle between the two worlds.

Zero Touch ProdGoogle's goal that every production change is made by automation, validated by software, or done through an audited breakglass path. Google estimated that roughly 13% of outages it evaluated could have been prevented or reduced this way. Safe proxies are one of the tools that get there.

Walk a command through the Tool Proxy

Engineers run most admin work with command-line tools, and some can turn off servers. Rather than harden every tool, Google wrapped them: the Tool Proxy runs the requested command on the engineer's behalf, but only if a policy allows it. Here is a policy in the same spirit (simplified, illustrative):

# who may run which tool, and who must approve
tool "cluster-ctl" {
  allow            = ["group:oncall"]
  require_approval = ["group:oncall-leads"]   # multi-party authorization
  test { cmd = "status web"  expect = ALLOW }
}

Chapter 4: features vs. emergent properties

Feature requirements map neatly to code and tests: "a signed-in user can edit their profile" becomes a handler, a form and an integration test. Security and reliability don't work that way. They emerge from the whole design, the dependencies, the build and deploy process, even the org chart. Sort these requirements.

Worked tradeoff: who handles the card numbers?

A widget shop must take payments. Card numbers and addresses are sensitive, regulated (PCI DSS) and an attractive target. The best way to protect sensitive data is often not to hold it: let a payment provider take it. That is a tradeoff, not a free win. Move the slider.

Third-party provider

  • Card data may never touch your servers.
  • Their specialists handle fraud, compliance and hardening.
  • Per-transaction fees grow with volume.
  • New dependency: their outage blocks your "user can buy" story. Plan for it (queue and retry later?).
  • You must still authenticate the provider and protect the integration (keys, callbacks).

In-house

  • No per-transaction fee, more control.
  • You hold the most dangerous data you could hold.
  • Compliance scope, audits, specialist staff.
  • A breach can cost user trust, fines, even the business.

5

Initial velocity vs. sustained velocity

"We'll add security once we have customers" buys speed early and costs it later: retrofitting emergent properties is invasive, and invasive late changes introduce new risks. The internet itself is the cautionary tale: its core protocols had reliability designed in but no way to authenticate senders, and decades later secure versions are still being rolled out. Choose when the team starts caring.

Frameworks: the win-winA widely used framework that bakes in authentication, logging, safe output encoding and load shedding makes developers faster, and gives security and SRE experts one place to improve every service at once. Goals that seemed to compete turn out to align.
