Case Study: Chrome Security Team

Chrome was one of the first Google products with its own security team. Its story shows what a security-centric culture looks like inside a fast-moving product.

1

From no security team to a security culture

In 2006 a small team set out to build, in under two years, an open source Windows browser more secure, faster and more stable than the rest. Browsers are as complex as operating systems, Google had little client-side security expertise, and an open source project couldn't lean on corporate security tooling. Chrome launched in 2008. Tap each stage of its security team.

2

Five evergreen focus areas

At a 2013 offsite the team wrote a mission ("provide Chrome users with the most secure platform possible to navigate the web, and generally advance security on the web") and clustered sticky notes into lasting focus areas, each with an accountable lead, while still swarming across areas so no one got siloed.

3

Security is everyone's job: make the safe path the easy one

The security team can never own all of Chrome's security, so it builds security into everyone's habits. Security engineers fix bugs and write code too, which keeps them honest about how hard bug-free code is and avoids "us versus them". Slide the investment and see where bugs get caught.

4

Help users browse safely without being experts

Security shouldn't depend on users' expertise: update silently, default to safe, make the safe choice the easy one. When phishing and confusing warnings remained unsolved, the team hired a research scientist in usable security (a job ladder Chrome had never hired from), then UX designers and researchers, and partnered with the UX team it used to clash with. Experts, they learned, are often blind to what confuses everyone else. Which warning would you heed?

jargon

NET::ERR_CERT_AUTHORITY_INVALID. The server's certificate chain could not be validated against the trust store. Proceed (unsafe)?

human

Your connection is not private. Attackers might be trying to steal your information (for example, passwords or credit cards).
Back to safety is the big, obvious button.

5

Speed matters: ship fixes before attackers can use the bug

Fast, automatic updates are one of Chrome's most important security features. Release technical program managers watch crash rates and roll out carefully, but also push safety fixes out fast. Hacking contests (Pwn2Own, then Chrome's own Pwnium) served as forcing functions to prove a critical fix could reach users in under 24 hours. Compare exposure windows.

6

Sandboxes, then Site Isolation

Bugs will happen, especially in a huge C++ codebase. Chrome launched with sandboxed renderer processes, so a malicious page couldn't take over the computer, the big threat of 2008. As sensitive data moved online, the next target was stealing data across sites from inside a compromised renderer. In 2012 the team began Site Isolation: a process per site. Estimated at a year, it took more than five times that, and survived because the team kept explaining its value. It later turned out to partly mitigate Spectre-style attacks.

7

Be transparent and engage the community

No silent fixes, no downplaying: Chrome publishes how it handles security issues, discloses every fixed vulnerability (found internally or externally) and lists them in release notes. The Vulnerability Reward Program, launched in 2010, brought a flood of reports on the then little-scrutinized WebKit engine; the team often dove in and fixed them itself, shaping it into a hybrid engineering team rather than a group of consultants. Open hiring (interns, conference speakers, an SRE who wanted to learn security) brought in diverse perspectives.
