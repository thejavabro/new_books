Clean Embedded Architecture

Software should last; firmware becomes obsolete with its hardware. A guest chapter by James Grenning shows how to keep embedded code from becoming all firmware.

1

Software lasts; firmware doesn't

This guest chapter is by James Grenning. It starts from a line in an article by Doug Schmidt: software doesn't wear out, but firmware and hardware become obsolete, so they need maintenance. Most textbook definitions say firmware is code in ROM or flash. Grenning proposes a better one: firmware is code that's hard to change because of what it depends on, namely the hardware. By that definition, non-embedded developers write firmware too, every time they scatter SQL or platform calls throughout their code.

The plea: write less firmware and more software. Drag the slider to see how much of a product becomes firmware as hardware knowledge spreads.

A telecom story from the book: a team moving from TDM to VoIP had business logic for call handling so tangled with TDM details that the only "spec" was the existing code. The whole product had become firmware.

2

Passing the App-titude test isn't enough

Kent Beck's sequence: first make it work, then make it right, then make it fast. Fred Brooks: plan to throw one away. Too much embedded code stops at step one, the App-titude test: it works. Grenning shows a real file whose functions, in source order, mix button handling, persistent storage, display, timing and register access, all testable only on the target. Sort a similar jumble into the concerns it should have been separated into.

3

The target-hardware bottleneck

Embedded developers face special constraints: limited memory, real-time deadlines, hardware that's late or buggy. Code structured without clean architecture can only be tested on the target, and the target becomes the bottleneck. A clean embedded architecture is a testable embedded architecture. Layers that keep hardware knowledge in its place

Separate software from hardware with interfaces. The line between software and firmware is the Hardware Abstraction Layer (HAL), and it exists for the software above it: its API should be shaped by the application's needs, not the chip's. If a battery-low LED hangs off GPIO bit 5, the firmware may offer Led_TurnOn(5); the HAL should offer Indicate_LowBattery(). Layers can contain layers: a fractal. Then swap something out.

5

Don't reveal hardware details to HAL users

Vendors often help in ways that tie you down: compiler keywords for I/O registers, or a vendor acmetypes.h header that every file must include. Code using those is no longer C; it won't compile for another processor or run off-target. Prefer standard stdint.h (write your own for the target if needed). Keep register poking in a small set of files behind the HAL or PAL.


  

  
Program to interfaces and substitutability. Use header files as interface definitions; keep data structures and constants out of them unless every user needs them. And don't sprinkle #ifdef BOARD_V2 through the code: that violates DRY and spreads the target's identity everywhere. With a HAL in place, let the linker or a runtime choice pick the implementation instead.
