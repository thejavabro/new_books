Independence

A good architecture supports what the system does and how it runs, while letting teams build and ship parts independently. Decoupling by layer and by use case gets you there.

What a good architecture supports

The previous chapter's four concerns, sharpened. A good architecture must support:

Easy to say, hard to do: we rarely know all the use cases, the operational constraints, the team structure or the deployment needs up front, and all of them change. But some principles are cheap to apply and help balance these concerns even when you don't know them. They all come down to partitioning the system into well-isolated components that leave options open.

2

Decouple by layer, then by use case

Use the SRP and CCP in the context of the system's intent. UIs change for reasons unrelated to business rules. Application-specific rules (like validating input fields) change for different reasons than domain rules (like computing interest). Databases and query languages change for reasons of their own. That gives horizontal layers. But use cases change for their own reasons too: adding an order and deleting an order change at different rates. Each use case is a thin vertical slice through all the layers. Try a change.

3

Decoupled slices can run differently

Once use cases and layers are separated, operations benefit too. A use case needing high throughput can run on many servers while a low-volume one stays on one. But only if the components don't assume they share an address space: they must be able to run as separate processes, or services. That's where service-oriented architecture comes in, and the book is careful: SOA is not the best architecture by default, just sometimes necessary.

4

True versus accidental duplication

Duplication is usually bad. But two pieces of code that look alike and will change at different rates and for different reasons are not true duplicates. Two use cases with similar screens will probably diverge; unifying them now means untangling them later. Likewise, passing a database row straight up to the UI because the view model looks the same today couples layers that should stay apart. Judge each case.

5

Three decoupling modes, and moving between them

Source levelModules in one address space, calling functions. Changes to one don't force recompiling others. A "monolith".
Deployment levelIndependently deployable units: jars, DLLs, gems. Some may run in other processes on the same machine.
Service levelOnly data structures shared, over the network. Fully independent of others' source and binary changes.

Which is best? It's hard to know early, and the answer changes. Defaulting to services is popular, but it's expensive in development time and resources, and it tends to give coarse decoupling anyway. The author's preference: push decoupling to the point where a service could be formed, but keep components in one address space as long as possible. Move along a system's life and watch the mode follow the need, in both directions.

Protect the source code from the modeA good architecture lets a system be born as a monolith in one file, grow into deployable units and then services, and slide back down when needs shrink, while most of the source code never notices.
