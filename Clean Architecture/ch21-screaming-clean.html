Screaming and Clean Architecture

A system's structure should shout what it does, not which framework it uses. The Clean Architecture is the picture that makes that possible: rings of policy with every dependency pointing inward.

What does your architecture scream?

Look at a building's blueprints and you know at once whether it's a house or a library: front door, living room, kitchen... or check-in desk, reading areas, stacks. The plans scream their purpose. Now look at your top-level directories. Do they scream "health care system" and "inventory management"? Or "Rails", "Spring", "ASP"? Guess what each project does.

This system is for...

Frameworks are tools, not ways of lifeFramework authors believe deeply in their frameworks, and their examples show the "all-in" way. Ask how you'd use one while keeping it at arm's length, and how you'd protect the use cases from it. A good test: a new programmer should be able to read the source tree and learn all the use cases without knowing how it's delivered. "Those are details; we'll decide later."
2

A family of architectures with one goal

Hexagonal Architecture (ports and adapters), DCI, and BCE (boundary, control, entity) differ in detail but agree on separation of concerns through layers: at least one for business rules and another for interfaces. Each produces systems that are:

Independent of frameworksFrameworks are tools, not cages.
TestableRules can be tested without UI, database, web server or anything external.
Independent of the UISwap a web UI for a console without touching rules.
Independent of the databaseOracle, SQL Server, Mongo, BigTable, CouchDB: the rules don't care.
Independent of any external agencyThe rules know nothing about the outside world's interfaces.

The Clean Architecture is an attempt to integrate all of them into one picture.

3

The Clean Architecture

Concentric circles. The farther in, the higher-level the software: outer circles are mechanisms, inner circles are policies. Tap a ring.

The Dependency Rule: source code dependencies must point only inward, toward higher-level policies.

Nothing in an inner circle can know anything about something in an outer circle: not a function, class, variable or any named software entity, nor data formats declared outside (especially formats generated by a framework). Four circles is a schematic; you might need more. The rule always applies. Test some arrows.

4

Crossing boundaries: flow out, dependencies in

At runtime control flows from the controller, through the use case, out to the presenter. But the use case must not name the presenter. So the use case calls an interface in the inner circle (an output port) and the presenter, outside, implements it. Same trick everywhere control has to flow outward: dynamic polymorphism makes the source arrow point against the flow.

What crosses? Simple, isolated data structures: plain structs, DTOs, function arguments, hashmaps. Never entity objects or database rows. If a database framework hands you a convenient row object, don't pass it inward: that forces an inner circle to know about an outer one.

The payoffFollowing these simple rules gives you a system that is intrinsically testable. When an external part becomes obsolete, a database or a web framework, you replace it with minimal fuss.
