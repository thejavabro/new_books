Paradigms and Structured Programming

Every programming paradigm removes a freedom. The first one, structured programming, removed the unrestricted jump, and in return made code small enough to test and trust.

Three paradigms, each one a subtraction

Languages have come and gone by the hundred, but paradigms, ways of structuring programs, number just three. They were all discovered in roughly a decade (1958 to 1968), and the striking thing is what they have in common: each takes something away. None gave programmers a new power. Each imposed a discipline. Tap each paradigm to see what it removes from the raw machine.

What the raw machine lets you do

Why there are probably no moreOnce you've removed goto, unsafe pointers to functions and assignment, there is little left to take away. Software, the book concludes, is made of sequence, selection, iteration and indirection, and the rules haven't changed since Turing's first programs. The tools changed; the essence didn't.

Three paradigms, three architectural concerns

This isn't a history lesson for its own sake. Each paradigm lines up with one of the three big concerns of architecture. Pick a concern.

3

Dijkstra's dream: programs you can prove

Dijkstra, the Netherlands' first professional programmer, saw early that programs hold too many details for a human brain. His remedy was mathematics: build a hierarchy of proven pieces, like Euclid's theorems, and assemble programs from them. While trying to prove simple algorithms he found that certain uses of goto made a module impossible to break into smaller provable parts. The harmless uses were exactly if/then/else and loops. And Böhm and Jacopini had just shown that every program can be built from three structures. Step through how each is proven.

Goto considered harmful

Dijkstra's 1968 letter "Go To Statement Considered Harmful" started a decade of angry letters to editors, and then the argument just stopped, because he had won. Today we are all structured programmers whether we like it or not. Compare the two shapes of the same little routine below: can you cut it into blocks that each have one entry and one exit?

Functional decomposition

Because a structured module can be split into smaller structured modules, a big problem statement can be broken down, level by level, into tiny functions. That idea powered structured analysis and design through the 1970s and '80s. Tap a box to decompose it.

6

Software is a science, not mathematics

The proofs never came. Nobody built the Euclidean hierarchy, and few programmers today would formally prove every function. What saved structured programming was a different way of knowing: the scientific method. Science can't prove a law true; it can only fail, again and again, to prove it false. Dijkstra himself put it as: testing shows the presence, not the absence, of bugs.

Below is a function with a hidden defect. Run random tests and watch your confidence grow. It never reaches certainty, and one unlucky input can still prove it wrong.

function daysIn(month, year) {  // month 1..12
  if (month === 2) return isLeap(year) ? 29 : 28;
  return [4,6,9,11].includes(month) ? 30 : 31;
}
function isLeap(y) { return y % 4 === 0 && y % 100 !== 0; }  // hmm...
Falsifiable unitsTests can only falsify a program that is provable in principle. A goto tangle can't be deemed correct no matter how many tests you throw at it. Structured programming gives us small falsifiable units; architects try to make modules, components and services falsifiable (testable) in the same way, using similar restrictive disciplines at a larger scale.
