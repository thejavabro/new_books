Functional Programming

Variables that never vary cannot race, deadlock or clobber each other. Functional discipline is an architectural tool for taming concurrency.

Variables that don't vary

Functional programming predates computers: it comes from Alonzo Church's lambda calculus (1936), the same problem Turing was chasing. Its core idea is immutability: symbols get values but never change them. Compare two ways of printing the first 25 squares.

// imperative: i changes 25 times
for (let i = 0; i < 25; i++)
  print(i * i);
;; functional (Clojure-style)
(println
  (take 25
    (map (fn [x] (* x x))
         (range))))

Read the second one inside-out: range yields an endless list of integers, map squares each, take keeps 25, println prints. The endless lists are lazy, so only 25 elements ever get built. And nothing is ever reassigned. Step it through.

(range)→map square→take 25→println

Every concurrency bug needs a mutable variable

Why should an architect care? Because race conditions, deadlocks and concurrent-update bugs all require something that can be changed. No variable is ever updated, no race. No mutable lock, no deadlock. Below, two threads each add 1 to a shared counter, 5 times. Run the interleaving several times in each mode.

Segregate the mutable from the immutable

Full immutability needs infinite memory and speed. The usual compromise is to split the system: immutable components do pure computation; a small number of mutable components hold state, protected by transactional memory (treating memory like a database treats records: transactions and retries). An atom handles one variable; several dependent variables need heavier machinery. The advice: push as much processing as possible into the immutable side.

4

Event sourcing: store the transactions, not the state

Memory and storage have grown so much that we need mutable state less and less. A bank could stop storing balances and store only transactions; to get a balance, add them up from the beginning of time. That sounds absurd, but we don't need it to work forever, only for the life of the application, and we can take shortcuts such as saving a snapshot every midnight. Nothing is ever updated or deleted: the app is not CRUD, just CR. No updates means no concurrent update problems. If that still sounds strange, remember it's exactly how your version control system works.
