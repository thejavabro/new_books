Services and the Test Boundary

Services are not an architecture in themselves, and tests are not outside the system. Both are judged by the same rule: which way do the dependencies point?

Services ≠ architectureTwo fallaciesThe kitty problemTests in the systemTesting APIQuick check
1

Services are not, by themselves, an architecture

Service-oriented and microservice "architectures" are popular because services seem strongly decoupled and seem to support independent development and deployment. The book's claim: both are only partly true. An architecture is defined by boundaries that separate high-level policy from low-level detail and follow the Dependency Rule. Services that merely split application behavior are little more than expensive function calls across process boundaries. Some services are architecturally significant; being a service doesn't make them so.

2

The decoupling fallacy

Yes, services run in separate processes and can't touch each other's variables. But they're still coupled by the data they share and by agreement on what it means. Add a field to a record that's passed along a chain of services, and every service that handles it must change. Service interfaces are no more formal or rigorous than function interfaces. Try it.

The independent development and deployment fallacy. Services can be owned by separate teams, sure. But history shows large systems can be built just as well from monoliths and component-based systems, and, as you just saw, shared data or behavior forces coordinated changes anyway.

3

The kitty problem

Back to the taxi aggregator, now built from services: UI, finder, selector, dispatcher, supervisor. One day marketing announces kitten delivery: customers can order kittens to their door, drivers who are allergic must never get these rides, and cars that carried kittens shouldn't go to allergic customers. Which services change?

Cross-cutting concernsEvery significant system faces them, and functional decomposition into services is vulnerable to them all. The fix is the same as in a component system: inside each service, design components following the Dependency Rule, with abstract base behavior and features added by plugging in new jars (template method, strategy). Architectural boundaries don't fall between services; they run through them.
4

The test boundary

Tests are part of the system. Architecturally, every kind of test (unit, integration, acceptance, BDD...) is the same thing: the outermost circle. Tests are very concrete, always depend inward on the code they test, and nothing in the system depends on them. They're independently deployable (mostly to test environments) and the most isolated component of all. That isolation tricks people into designing them as an afterthought.

The problem is coupling. Tests strongly coupled to the system break en masse when it changes: the Fragile Tests Problem. Classic case: business rules verified through the GUI. Change the login page and hundreds of tests fall over. Worse, fragile tests make the system rigid, because people stop making changes that would break them.

5

Design for testability: the testing API

The first rule of design applies to tests too: don't depend on volatile things. GUIs are volatile, so tests that drive them are fragile. Give tests their own API: a superset of the interactors and interface adapters the UI uses, with superpowers to skip security, bypass expensive resources and force the system into specific states. It decouples tests from the UI and from the application's structure.

// structurally coupled: mirrors every class
test("OrderValidator rejects...")
test("OrderPricer applies...")
test("OrderRepositoryImpl saves...")
// rename or merge a class: tests break
// through a testing API: behavior only
const t = TestApi.withState({ stock: 3 });
t.placeOrder({ sku: "A", qty: 5 });
expect(t.lastOrder.status).toBe("backordered");
// production can be refactored freely

Structural coupling, one test class per production class, is among the strongest and sneakiest forms. Hide the structure behind the API and the two can evolve apart: tests grow more specific, production code grows more abstract and general. Keep the testing API's superpowers out of production deployments (a separate, independently deployable component works) so they don't become a security risk.

Designed as part of the systemTests that aren't designed in tend to be fragile and expensive, and end up discarded. Design them with the system, and they deliver what they promise: stability and regression safety.
