Component Coupling

How components relate is as important as what's in them. No cycles, depend toward stability, and make stable things abstract. Then measure how far you've drifted.

1

The morning-after syndrome

You get something working, go home, and come back to find it broken, because someone stayed later and changed what you depended on. With a few developers that's an annoyance; with many, weeks can go by without a stable build. One cure tried in industry was the weekly build: code privately all week, integrate on Friday. Slide the team size and watch the integration day eat the week.

The better cure: partition the work into releasable components, each owned by a team, released with version numbers. Others upgrade when they choose. There's no single moment when everyone must integrate. It only works if the dependency structure has no cycles.

2

ADP: allow no cycles

The Acyclic Dependencies Principle: the component dependency graph must be a directed acyclic graph. Tap a component to release a new version of it: the ones that must re-test are those you reach by following the arrows backward. Then add a cycle.

3

Component structure can't be designed top-down

It feels like the component graph should be sketched on day one, like a functional decomposition. It shouldn't, and can't. The component diagram is not a description of what the application does: it's a map of buildability and maintainability. Nothing exists to build or maintain at the start. As classes accumulate, we isolate volatility (CCP), protect high-value components from volatile ones, and later, as reuse appears, the CRP kicks in. Cycles appear and get broken. The structure jitters and grows with the logical design.

4

SDP: depend in the direction of stability

Stability isn't about how often something changes; it's about how much work a change takes. A penny on its edge isn't changing, but it's not stable. A component that many others depend on is hard to change: it's responsible. One that depends on many others but has no dependents is irresponsible and dependent. The metric:

I = Fan-out ÷ (Fan-in + Fan-out)

The Stable Dependencies Principle: the I of a component should be larger than the I of the components it depends on. Draw unstable components above stable ones and any upward arrow is a violation. Here, a developer working in Stable started using a class C in Flexible, a component designed to change easily.

5

SAP: be as abstract as you are stable

If high-level policy lives in stable components, how can it ever change? The OCP answers: make it abstract so it can be extended without modification. The Stable Abstractions Principle: a stable component should consist of interfaces and abstract classes; an unstable component should be concrete. Combined with the SDP, dependencies then run in the direction of abstraction: the DIP for components.

A = Na ÷ Nc

Na = abstract classes and interfaces in the component; Nc = all classes in it. 0 = fully concrete, 1 = fully abstract. (In dynamic languages abstract components barely exist; dependency inversion needs no declared interface there.)

6

The main sequence and its two zones

Plot every component with instability I across and abstractness A up. The ideal corners are (0, 1), stable and abstract, and (1, 0), unstable and concrete. Real components fall in between. Two areas are trouble:

  • Zone of Pain around (0, 0): stable and concrete, so rigid and hard to extend. A database schema is the classic resident, which is why schema changes hurt. Non-volatile things (like a standard string library) are harmless here.
  • Zone of Uselessness around (1, 1): abstract with nobody depending on it. Often leftover abstract classes nobody implemented.

The line between (1, 0) and (0, 1) is the Main Sequence, and the distance from it is D = |A + I − 1|. Build a component and see where it lands.
