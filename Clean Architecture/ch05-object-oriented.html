Object-Oriented Programming

OO did not invent encapsulation or inheritance. What it gave architects is safe polymorphism, and with it the power to point any source code dependency in whichever direction they choose.

So what is OO, really?

Ask around and you hear three stock answers. "Data plus functions" is unsatisfying: o.f() is not fundamentally different from f(o). "Modeling the real world" is too vague to mean anything. The third answer names three magic words, encapsulation, inheritance and polymorphism. The chapter puts each word on trial, asking: did we already have this before OO? Here's the scorecard it arrives at.

Encapsulation0We had it, and betterC's header files hid data perfectly. C++, Java and C# weakened it.
Inheritance½We had a trickData structures could masquerade as each other. OO made it convenient.
Polymorphism1We had it, but dangerouslyPointers to functions. OO made them safe, and that changes everything.
2

Encapsulation: C did it better

In C you could declare a struct in a header without its fields, and declare functions that operate on it. Clients saw names and nothing else. C++ needed to know the size of every object, so the member variables had to move into the header. Clients now know the fields exist, even if private stops them touching them, and renaming a field forces recompiles. Java and C# dropped the header split altogether. Choose a language and see what a client can see.

Inheritance: a masquerade we already knew

  
If a struct starts with exactly the same fields, in the same order, as another, a pointer to it can be cast to the other type and code written for the first works on the second. C programmers did this constantly, and it is roughly how C++ implements single inheritance. Press the button to cast a NamedPoint to a Point.

  

    

    

  

  
OO earns half a point: it made the trick implicit (no explicit cast), and it made multiple inheritance practical, which the manual trick never did well.

Polymorphism is pointers to functions, made safe

  
A classic C copy loop reads with getchar() and writes with putchar(). Which device? Whatever STDIN and STDOUT point to. UNIX asks every driver to supply the same few functions (open, close, read, write, seek), and a file structure holds pointers to them. A virtual function table in C++ is the same idea. Pick any devices: the copy program never changes and never even recompiles.

Why we needed OO for thisFunction pointers work, but by convention only: initialize every pointer, always call through it. Forget once and you get a bug that's miserable to find. So most programmers never used the plugin idea outside operating systems. OO languages removed the conventions, and with them the danger. Now any program can use plugins, anywhere.






  
5
The real prize: dependency inversion

  
Before safe polymorphism, source code dependencies had to follow the flow of control. If main calls a high-level function, main must name its module (#include, import, using). The architect had no say. With an interface in between, the caller depends on the interface, and the callee also depends on it, pointing back up, against the flow of control. Tap any solid arrow to invert it.

Business rules with the UI and database as plugins

  
Use that power to make the UI and the database depend on the business rules rather than the reverse. Now the three can live in separate deployables (jars, DLLs, gems), and a change in one only redeploys that one. That's independent deployability, which in turn allows independent developability by separate teams. Toggle the arrangement, then make a change.

The architect's definitionOO is the ability, through polymorphism, to gain absolute control over every source code dependency in the system. That lets you build a plugin architecture where high-level policy never depends on low-level detail.
