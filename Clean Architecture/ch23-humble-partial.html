The Humble Object pattern

Originally a unit-testing pattern: when something is hard to test, split it in two. One part holds all the behavior that's hard to test, stripped down to the barest essentials: the humble object. The other part holds everything testable that was pulled out of it. GUIs are the classic case: checking pixels on a screen is miserable, but most of a GUI's behavior isn't about pixels at all. Presenters and view models

The Presenter takes data from the application and formats it into a View Model of strings and booleans, so the View only has to copy values onto the screen. A date becomes a formatted string. A currency amount becomes a string with the right symbol and decimals, plus a flag for "show in red". Enabled buttons become booleans. Change the inputs and watch each layer.

Humble objects at other boundaries

A note on "ORMs": there's no such thing as an object-relational mapper, because objects aren't data structures. Objects expose operations and hide data; data structures expose data and have no implied behavior. What ORMs really do is load data structures from relational tables. They belong in the database layer, forming another humble object boundary between gateway interfaces and the database.

4

Partial boundaries: cheaper ways to leave the door open

Full boundaries are expensive: reciprocal polymorphic interfaces, input and output data structures, and the dependency management to compile and deploy each side independently. Agile folks rightly frown on anticipatory work (YAGNI). Yet sometimes you suspect a boundary will be needed. A partial boundary is the compromise. Compare three.

The FitNesse lessonFitNesse's web server was written to be separable, but kept in the same jar for "download and go". Nobody ever used it separately, and over time dependencies began to cross the line the wrong way. Re-separating it later would be a chore. Partial boundaries degrade unless someone keeps watching.

Each option has costs and benefits. Deciding where a boundary might one day exist, and whether to implement it fully, partially or not at all, is part of the architect's job.
