Identity, Access and Security Operations

Who are you, what may you do, and is anything wrong right now? Identity, access control and continuous monitoring answer those three questions.

1

Authentication, authorization, auditing

Controlling access comes down to three questions. Authentication: who are you? In Google Cloud, Cloud Identity answers. Authorization: what may you do? Cloud IAM answers. Auditing: what did you do? Cloud Audit Logs (and the Reports API for Cloud Identity) answer.

2

Cloud Identity: the front door for people

Cloud Identity is Google Cloud's identity provider, the same identity-as-a-service that powers Google Workspace. It manages the user lifecycle, account security and single sign-on. Setting it up is the first step of onboarding an organization:

Note the two kinds of role: Cloud Identity admin roles manage users and groups; IAM roles grant access to cloud resources. Different systems, easy to confuse.

The phishing test

a convincing fake login page captures what you type

If your company already uses another identity provider, such as Azure AD or Okta, you can keep it as the source of truth: sync users and groups into Cloud Identity with Google Cloud Directory Sync (or the IdP's own provisioning), and delegate sign-in to it with SAML SSO. Employees get one login; access is revoked everywhere when they leave.

3

Cloud IAM: who can do what, where

An IAM policy is a set of bindings; each binding grants a role (a bundle of permissions) to principals (users, groups, service accounts, a whole domain) on a resource. Policies are inherited down the hierarchy: organization → folders → projects → resources. A grant on a folder applies to everything beneath it. Try it:

Three kinds of role

Best practices from the bookGrant roles to groups that mirror functions (networking, DevOps), not to individuals. Sync groups from your source of truth so joiners and leavers are handled once. Name groups consistently. Apply policies at as few points as possible, using folders. Use IAM Conditions (time windows, resource name prefixes, tags) for finer scope, and restrict which domains can appear in policies with the iam.allowedPolicyMemberDomains organization policy.
4

Service accounts: identities for software

Applications need identities too. A service account belongs to a project, has no password and can't log in through a browser. It authenticates with a key pair (Google-managed or user-managed) or through workload identity federation, and users or other service accounts can be allowed to impersonate it.

5

BeyondCorp: zero trust, no VPN

The old model trusts anyone inside the corporate network, so one phished laptop on the VPN can roam. In 2011 Google started BeyondCorp: no network is trusted; every request is checked against who the user is, what device they're on and the context, for every app, wherever the user sits. BeyondCorp Enterprise is the product version, built from four pieces: Identity-Aware Proxy (IAP) in front of apps, Endpoint Verification collecting device posture, Access Context Manager defining access levels, and Chrome with built-in threat and data protection.

Since the book: BeyondCorp Enterprise was renamed Chrome Enterprise Premium in 2024. IAP and Access Context Manager work as described.
6

Security Command Center: one view of risk

Security Command Center is Google Cloud's native security and risk dashboard. It discovers assets (via Cloud Asset Inventory), finds misconfigurations and vulnerabilities (Security Health Analytics, Web Security Scanner), detects threats (Event Threat Detection on logs, Container Threat Detection, VM Threat Detection for things like crypto mining), and maps findings to compliance benchmarks such as CIS, PCI DSS, NIST and ISO. Findings come with recommendations and can be exported to Pub/Sub or your SIEM.
