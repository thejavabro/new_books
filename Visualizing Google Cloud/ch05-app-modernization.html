Migrating and Modernizing Apps

Moving an application to the cloud is a set of choices: what to move, how far to change it, and where it will end up running. This page walks through those choices and the tools that support them.

1

Build new, or move what you have?

Application work in the cloud starts with one of two situations. You're either building a cloud-native app (serverless, containers, managed databases, CI/CD from day one), or migrating an existing one. Either way, most modern requirements push toward microservices: modular services you can reuse, release independently and write in different languages, with no single point of failure. A monolith is one unit: any change means rebuilding and redeploying the whole thing.

what has to be redeployed?

Microservices aren't free. They need to talk to each other, need a solid DevOps pipeline for frequent deploys, and need to be monitored and secured. Those needs shape the rest of this chapter.

2

Should this application move to Google Cloud?

The book suggests three gate questions. A "no" doesn't end the journey: replace that component with a cloud service if you can; if not, leave it on-premises for now and move the rest. If staying on-premises isn't an option (the data center is closing), use Bare Metal Solution or a colocation facility next to a cloud region.

3

Five destinations, four speeds

The book names five destinations: Google Cloud managed services, containers on GKE or Anthos, VMs on Compute Engine, VMware Engine, and Bare Metal Solution. How far you change the app on the way decides how quickly you see value and how much of the cloud you get to use.

4

Four common migration plays

Every play starts the same way: connect your data center to Google Cloud (Cloud Interconnect) and build a landing zone (projects, networks, IAM and the target compute such as Compute Engine, GKE, VMware Engine or Anthos). Then they diverge.

    5

    Anthos: one way to run apps everywhere

    Large companies run apps in their own data centers, several public clouds and at the edge, each with its own tooling. Multiply clusters by environments by teams and you get inconsistent security, config drift and no single view. Anthos puts one control layer over all of it: GKE-based clusters anywhere, a fleet you manage from the Google Cloud console, Config Management to sync policy and config from Git, Anthos Service Mesh for traffic, security and telemetry between services, and observability in one place. Developers get the same Kubernetes and serverless (Cloud Run for Anthos) experience in every environment.

    6

    CI/CD: make releases boring

    Continuous integration merges small changes often and verifies each with an automated build and tests, so problems surface early. Continuous delivery extends it: every change is packaged and ready to release, and strategies like blue/green and canary rollouts cut the risk. The landscape makes this harder: hybrid targets, many microservices in many languages, and a mix of VMs, containers and serverless. Google Cloud's answer is a set of tools that run behind the scenes from commit to production.

- name: 'python:3.12'
