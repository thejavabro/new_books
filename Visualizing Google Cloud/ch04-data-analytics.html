Data Analytics

Five steps of a data analytics pipeline

The chapter's frame is a pipeline with five stages: capture data as it is produced, process it into a clean shape, store it somewhere you can query, analyze it, and use it in dashboards, apps and ML. Step through it.

2

Pub/Sub: the front door for events

Pub/Sub is a global, serverless messaging service. Publishers send messages to a topic; each subscription on that topic gets its own copy of every message and delivers it to its subscribers by pull or push. A message stays in the subscription until a subscriber acknowledges it, so a slow or crashed consumer never loses data. Publishers and subscribers don't know about each other: that decoupling is the point. Features include at-least-once delivery (exactly-once is available for pull), ordering keys, filtering, dead-letter topics, replay by seeking to a time, and retention for days.

Cloud IoT Core: devices as publishers

The outline covers Cloud IoT Core: a device manager (registries, per-device credentials and configuration) plus a protocol bridge that let millions of devices speak MQTT or HTTP, with their telemetry landing in Pub/Sub. Its design principles were the usual IoT ones: secure each device with its own key, handle intermittent connections, and hand data to the analytics stack as quickly as possible.

Since the book: Google retired Cloud IoT Core in August 2023. The pattern lives on with partner IoT platforms or your own MQTT broker publishing into Pub/Sub, then the same pipeline as below.
4

Dataflow: one model for batch and streaming

Dataflow runs Apache Beam pipelines, serverless. You write a pipeline once (read, transform, group, write) and run it on a bounded file (batch) or an endless stream. Dataflow provisions workers, autoscales them, rebalances slow work and handles exactly-once processing. For streams the hard question is when to compute a result, which Beam answers with windows, watermarks (how complete is the data up to time t?) and triggers. Templates and SQL let non-programmers start jobs; governance features keep jobs inside your network and encryption keys.

Windowing the same stream three ways

(p | beam.io.ReadFromPubSub(topic=TOPIC)
   | beam.Map(parse_click)
   | beam.WindowInto(beam.window.FixedWindows(60))
   | beam.combiners.Count.PerKey()
   | beam.io.WriteToBigQuery("analytics.clicks_per_minute"))

Dataproc and Dataprep

Dataproc: managed Spark and Hadoop

Bring existing Spark, Hadoop, Hive or Presto jobs and run them on a cluster that starts in about 90 seconds and is billed by the second. The cloud-native habit is ephemeral clusters: keep data in Cloud Storage (not HDFS), spin up a cluster per job, delete it after. Migrating HDFS data usually means copying it to Cloud Storage (DistCp or Storage Transfer Service) and pointing jobs at gs:// paths.

Dataprep: data prep without code

Data preparation is cleaning, structuring and enriching raw data before analysis, often most of an analyst's time. Dataprep (by Trifacta) shows a sample of your data, profiles each column, flags bad values and suggests transformations as you click. The recipe it builds runs at scale as a Dataflow job.

BigQuery: a serverless warehouse

BigQuery is the center of the chapter. It is serverless: no clusters to size, you load data and write SQL. Unique features include separate scaling of storage and compute, streaming inserts, BigQuery ML (models in SQL), BI Engine for fast dashboards, geospatial functions, federated queries over Cloud Storage and other sources, and Omni for data in other clouds.

Columnar storage: pay for the columns you touch

1 TB table · on-demand pricing

BigQuery stores each column separately (its Capacitor format on the Colossus file system). A query reads only the columns it names. Pick columns, and choose whether the table is partitioned by date.

Looker: one definition of every metric

  
Looker is a BI platform with three ideas the outline highlights. In-database architecture: it doesn't copy data into its own store; it writes SQL that runs in BigQuery (or another database), so dashboards are always current. A semantic modeling layer (LookML) defines dimensions and measures once, so "revenue" means the same thing on every dashboard. And it's cloud native, with APIs to embed data in other apps.

  

    

    

    
measure: revenue {
  type: sum
  sql: ${TABLE}.price * ${TABLE}.qty ;;
  value_format_name: usd
