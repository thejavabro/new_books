Security in Layers

Cloud security is a stack of layers, from the silicon up to your data, and responsibility for each one is split between Google and you. This page climbs the stack.

Cloud security is shared fate

Security in the cloud is shared. The provider secures the infrastructure; you secure what you deploy and your data; and, the book stresses, the provider should actively help with best practices, secure defaults, templates and products. Google calls that shared fate rather than just shared responsibility. The split changes with the service model. Pick one:

youGooglegradient = shared

The chapter walks through nine areas: infrastructure, network, application, software supply chain, data, identity and access, endpoint, security monitoring and operations, and governance, risk and compliance. This page covers the first five; the next page covers identity and operations.

Securing the software supply chain

Code passes through many hands on its way to production, and each hop is a chance to tamper with it. The book lists the risks: bad source code (or a coerced developer), a compromised source repo, a build started from unreviewed code, a compromised build platform, a malicious dependency, deploying an artifact that bypassed CI/CD, a compromised package registry, typosquatting, and tampering in transit. Tap a stage to see the threat and the control.

Google's own answer was zero trust, an incident playbook, and Binary Authorization for Borg: production only runs code that was reviewed and built by trusted systems. It shared the ideas as SLSA (Supply-chain Levels for Software Artifacts), an open framework with incremental levels. In Google Cloud, Binary Authorization enforces it: attestations are signed as an artifact passes each check, and the deploy is allowed only if the policy's required attestations are present.

Encryption: at rest, in transit, in use

Google encrypts all data at rest by default: data is cut into chunks, each chunk encrypted with its own data encryption key (DEK), each DEK wrapped with a key encryption key (KEK), and the pieces spread across storage. An attacker with one key or one disk gets almost nothing. All internet traffic to Google Cloud uses TLS in transit. And Confidential Computing (Confidential VMs and GKE nodes) encrypts data in use, in memory, with keys generated in the CPU that Google can't access.

6

Cloud DLP: find it, then hide it

Sensitive data turns up in unexpected places: a card number in a support chat, an email address in a log. Cloud DLP (now part of Sensitive Data Protection) inspects text, images, Cloud Storage, BigQuery and Datastore using 150+ built-in infoType detectors plus your own, classifies what it finds with a likelihood, and de-identifies it. It also measures re-identification risk: on their own, age, job title and zip code look harmless, but together they may single out one person.
