Infrastructure: Where Your Code Runs

Google Cloud offers a ladder of compute options, from raw virtual machines to a single function that wakes up on an event. Each rung hands more of the work to Google and leaves you with less control.

Who builds the house? Cloud service models

The book explains cloud service models with housing. Building a house yourself is on-premises: you own every brick. Hiring a contractor to build to your plan is IaaS. Renting a home with utilities included, but bringing your own furniture, is containers as a service. A furnished rental is PaaS. A hotel room for one night, paid by the stay, is functions as a service. Moving in and paying someone for cleaning and lawn care is SaaS.

Compute Engine: virtual machines you shape

Compute Engine runs virtual machines on Google's infrastructure. You pick a machine family (or a custom size), a boot image (public, custom, a snapshot or a container image) and a zone near your users. Incoming internet traffic is blocked by the firewall until you allow it. When Google patches the host, live migration moves your running VM to another host in the same zone without a reboot.

Managed instance groups and predictive autoscaling

A managed instance group (MIG) stamps out identical VMs from a template, re-creates any VM that fails its health check (auto-healing), and can spread across zones (a regional MIG) so one zone failing doesn't take you down. An autoscaler adds or removes VMs to track CPU, requests per second or another metric. Normal autoscaling reacts after load arrives; predictive autoscaling learns daily and weekly cycles and starts VMs early, which matters when a VM takes minutes to boot.

4

Why containers, and why Kubernetes?

A VM virtualizes hardware, so each one carries a whole guest operating system. A container virtualizes the operating system: it packages your code and its dependencies and shares the host kernel, so it starts in seconds and is small enough to pack many onto one machine. "Works on my laptop" becomes "works anywhere the container runs".

Once you have hundreds of containers, someone has to decide where each runs, restart the ones that crash and roll out new versions. Kubernetes does that. You stop "flying the plane" and program the autopilot: you declare the state you want ("three copies of the web app") and the control plane keeps reality matching it.

GKE: Kubernetes without running Kubernetes

Running Kubernetes "the hard way" means building the control plane, generating certificates, wiring networking and DNS, and patching it all forever. GKE hands the control plane to Google's SREs. In Standard mode you still manage the worker nodes; in Autopilot mode Google manages the nodes as well and you pay per Pod.

Cloud Run: any container, scaled by requests

Cloud Run takes a standard container image and runs it fully managed. It is built on the open Knative API, so the same container can move to GKE or elsewhere. It scales on incoming requests, can scale to zero when idle (you pay nothing), and unlike a function, each instance can serve many requests at once. Triggers include HTTPS, gRPC, WebSockets, Pub/Sub push, Cloud Scheduler, Cloud Tasks and Eventarc events.

App Engine and Cloud Functions

App Engine is the original Google Cloud platform-as-a-service: push code, get a scaled web app with versions and traffic splitting for A/B tests and canaries. Cloud Functions goes smaller: one function, one job, triggered by an HTTP call or an event, billed by invocations, compute time and memory.

Bring what you already run: VMware Engine and Bare Metal

Google Cloud VMware Engine

A dedicated, fully managed VMware stack (vSphere, vCenter, vSAN, NSX) running on Google Cloud hardware. Migrate VMs without refactoring or re-platforming, keep your VMware tools and skills, then plug the VMs into BigQuery, AI services and the rest. Typical uses: retire a data center, burst capacity, disaster recovery, virtual desktops.

Bare Metal Solution

Purpose-built physical servers in regional extensions close to Google Cloud regions, connected with low-latency links. Meant for specialized workloads that cannot be virtualized easily, Oracle databases being the classic case. Google runs the facility, power, hardware and network; you run the OS, database and apps.

9

Choosing where to run your app

The book's advice comes down to four questions: how much abstraction you want, what the workload is, whether you need open-source portability, and how your team is set up. Billing differs too: Compute Engine and GKE Standard bill for provisioned resources (with sustained-use and committed-use discounts); Cloud Run, Cloud Functions and GKE Autopilot bill only for what runs.
