Load Balancing, CDN and the Service Mesh

With the network in place, the next job is getting traffic to the right backend quickly and safely, letting private machines reach out, and seeing problems before your users do.

Cloud Load Balancing: one IP for the whole world

Cloud Load Balancing isn't a box or a VM; it's software running on the same front-end infrastructure that serves Google, handling HTTP(S), HTTP/2 and gRPC, TCP/SSL, UDP and QUIC at over a million queries per second. A global external load balancer gives you a single anycast IP: users anywhere hit the nearest Google edge, and traffic flows to the closest healthy backend with capacity. Adding a region doesn't change the IP or DNS.

Inside a global HTTP(S) load balancer

A load balancer is a chain of small configuration objects. Step through a request to see where each one acts. Internal layer-4 load balancing between tiers is simpler: a forwarding rule on a private (RFC 1918) VIP points straight to a backend service, with no proxy in the middle and the client IP preserved.

Security at the front doorRun TLS everywhere with Google-managed certificates (many certificates can share one IP). The load balancer absorbs layer 3 and 4 floods across Google's edge; Cloud Armor adds layer 7 protection; Identity-Aware Proxy and firewall rules control who reaches the backends.

Cloud CDN: serve it from the edge

Cloud CDN caches content at Google's edge (120+ locations in the book) behind the global HTTP(S) load balancer: tick a box on a backend service or bucket. A request hits the nearest edge; if the content is there under its cache key (usually the URL), it's a hit and the origin never sees it. On a miss, the edge may fill from a nearby cache (cache-to-cache fill) or fetch from the origin. Objects live until their TTL expires or you invalidate them. HTTP/2 and QUIC to the client cut latency on lossy mobile networks; signed URLs and signed cookies give time-limited access to paid content.

Cloud NAT: outbound only, no public IPs

Best practice is to give VMs and GKE nodes no external IP addresses. They still need to fetch updates and call APIs. Cloud NAT lets them reach out while nothing on the internet can reach in. It isn't a proxy VM: it's configuration on a Cloud Router, applied by Andromeda in every host, so there's no bottleneck or single point of failure. It's set per region and can cover all subnets or only chosen ones (and for GKE, the node and Pod ranges). NAT rules pick which NAT IPs are used for which destinations, so partners can allowlist you.

Traffic Director: a managed control plane for service meshes

In a typical Kubernetes service mesh, every Pod gets a sidecar proxy (usually Envoy) that handles traffic between services: routing, retries, mTLS, telemetry. A control plane tells all those proxies what to do. Traffic Director is Google's fully managed, highly available control plane. It works across multiple clusters and regions, for VMs as well as containers, and even with no sidecar at all: proxyless gRPC apps take their config straight from Traffic Director. It spans hybrid and multicloud endpoints too, and can program ingress and gateway proxies at the edge of the mesh.

Service Directory: one phone book for every service

Enterprises have services everywhere: VMs, GKE, Cloud Run, on-premises, other clouds, third-party SaaS. Service Directory is a managed registry where each namespace holds services, each with endpoints (address, port, annotations). Clients look services up over HTTP or gRPC, or through Cloud DNS, which can answer from a Service Directory namespace. Load balancers can register themselves automatically, and IAM controls who can see or change each entry.
