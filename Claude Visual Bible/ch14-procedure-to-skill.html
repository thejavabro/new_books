Turn a Procedure into a Reusable Skill

If you explain the same procedure to Claude every week, write it down once as a skill. Then test it like you would test a new colleague.

1

A skill is a stored procedure, not a stored prompt

A skill is a folder: a SKILL.md file with a name, a description and instructions, plus optional templates, worked examples, reference files and scripts. A prompt tells Claude what to do in this conversation; a skill teaches a capability available in many. Skills need code execution (and file creation) switched on; in organisations an admin may disable them. Explore this invented skill.

A skill has no memory of your projectLong-running context, files and project rules belong in a project. A skill is the reusable procedure you apply across many projects. Keep each skill small enough to explain in one sentence.
2

When is a procedure ready to become a skill?

Skills shine when you repeat the same procedure with different inputs, have rules you are tired of explaining, need consistency across people, have examples that improve results, and can describe the task narrowly. They fit poorly when the work changes every time, you are still discovering the procedure, or it rests mainly on judgment.

3

The description decides when a skill is used

Claude reads the descriptions of enabled skills, picks the relevant ones and only then loads their full instructions (Anthropic calls this progressive disclosure). So a vague description means the skill is missed or misused. You can always name a skill explicitly, or pick it from the / menu.

4

Built-in, directory, shared or uploaded

Start with Anthropic's built-in skills (Word, Excel, PowerPoint and PDF work load automatically when needed). Browse a directory, accept one a colleague shares, or upload a ZIP. Installed skills are view-only: for different behaviour, make your own. Tap a source.

5

Prepare the procedure before you build

Good preparation matters more than the build. Pick a procedure you have done the same way, with good results, several times (a standard operating procedure, or SOP). Then write the inputs, outputs, rules, resources, one worked example, and acceptance criteria written before you build, so you cannot quietly lower the bar after seeing the first result.

6

Test the normal case, then a hard one

Build by conversation: give Claude its skill-creator skill your specification, answer its questions (such as what should trigger the skill), review, save. Then test. A normal input first; then a hard one that targets a rule, such as leaving out the required audience. A passing skill asks one focused question instead of guessing. When a test fails, fix the instruction, not the output, and re-run both tests.

7

Check an output against the criteria

The book's example skill turns a blog post into a social summary with three criteria: exactly three sentences, a call to action at the end, no fact missing from the source. Edit the text; the first two are checked automatically, the third is yours.

A skill is not magicThe author compares it to a known-good procedure handed to a sometimes unreliable worker. Test three or four times with different inputs before real use. For consequential work: procedure → observe execution → check each important stage → detect deviations → verify completion.
