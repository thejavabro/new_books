Connect Trusted Information and Tools with MCP

The Model Context Protocol gives Claude a standard plug for outside tools and data. Treat each connection as a door: know what it opens, and who holds the key.

1

Why one standard plug helps

Before a shared standard, every link between an AI assistant and an outside system needed custom work. The Model Context Protocol gives developers one common way to expose information and actions, so any MCP-capable assistant can reach any MCP server. Host, client, server, tool, resource

You do not need the internals, but five words come up constantly. Tap the parts of the diagram.

Local or remote serverA local server runs on your computer (personal tools and files) and is set up through the desktop app. A remote server is hosted by another organisation (company systems, third-party services). For Chat and Cowork the easiest route is a remote custom connector, which Claude reaches through Anthropic's cloud. Remote servers usually need an account and explicit approval.
3

Connect only what you trust

A server can request wide access. Prefer the server offered by the organisation that owns the system, use your organisation's approved list if it has one, and ask before connecting anything to work data. Credentials and permissions sit inside a security boundary; no tool call should cross it without your approval.

4

Walkthrough: a disposable workspace and an official server

The book demonstrates with Notion's official remote MCP server because it shows a real OAuth permission flow, both read and write tools, and approval boundaries, all against a throwaway workspace holding three fictional tasks. Step through the flow.

5

Set a policy for every tool

After connecting, review the tool permissions. The book's sensible default: read-only tools: always allow; write and delete tools: needs approval, then approve each write with "Allow once" and check the result in the other app. Set policies for these invented tools.

6

Test low-risk first; never retry blindly

Start with a read request. If a server errors, read the message and confirm it is still trusted and available before trying again; repeating a failed write can duplicate or compound it. Keep a short list of connected servers and why, so you can prune them later.
