Enable Fast and Reliable Automated Testing

Without automated tests, more code means more risk. This chapter builds a fast, reliable test suite and the cultural rule that a red build stops the line.

1

Case study: Google's web server (2005)

Without automated tests, Gary Gruver observes, the more code we write, the more time and money it takes to test it, and the less sure we are that it works. In 2005 Google's web server (GWS), the C++ application serving the homepage and many other pages, had become very hard to change; mistakes could make search results wrong or slow for many users. Team lead Bharat Mediratta drew a hard line: no change accepted without automated tests, a continuous build kept passing, test coverage monitored and rising. GWS became one of Google's most productive teams, and new members could contribute quickly. The practice spread. Scale it up to see Google today, per the book.

Eran Messeri notes that large failures still happen occasionally, and then many people swarm them. What makes it work is engineering professionalism and a high-trust culture that assumes everyone wants to do a good job.

2

The deployment pipeline: build once, test everything

Jez Humble and David Farley defined the deployment pipeline: every change checked into version control is built, packaged once, and pushed through ever more realistic tests. The same package flows through every stage, all the way to production. Run a commit through it. Toggle a bug to see where the pipeline stops it.

A dedicated build-and-test process runs regardless of individual habits, exposes every dependency, and produces packages (or containers) that install repeatably. Builds that pass become available on demand for UAT, integration and security environments. The pipeline needs three things to support continuous integration: a reliable automated test suite, a culture that stops the line when it fails, and developers working in small batches on trunk.

3

Why slow, periodic feedback kills

Ten developers each check in daily. If tests only run overnight, a failure the next morning could come from any of ten changes, or from the environment, and more changes keep arriving on top of it. Change how often tests run and see how hard the hunt becomes.

4

The ideal testing pyramid

Tests run from fastest to slowest: unit tests check one function in isolation, usually with the database stubbed out; acceptance tests check the whole application against a user story or API contract; integration tests check it works with real external systems, and are the slowest and most fragile. Martin Fowler's ideal is a pyramid that catches most errors at the bottom. Many organizations have the opposite: an inverted pyramid of manual and integration testing.

Push errors down the pyramidWhenever an acceptance or integration test finds an error, write a unit test that would have caught it faster and cheaper. If unit or acceptance tests are too hard to write, the architecture is probably too tightly coupled. Martin Fowler says a ten-minute build and test is perfectly within reason; teams may also make test coverage visible, or fail the build if, say, under 80% of classes have unit tests, as long as the team already values testing.
5

Keep tests fast: run them in parallel

Design tests to run in parallel across many machines, and run categories side by side, such as performance and security tests after acceptance passes. Every build that passes is immediately available to testers (which includes developers) for exploratory testing. Drag the number of test machines.

6

Write the test before the code

Kent Beck's test-driven development, from Extreme Programming in the late 1990s: write a failing test, write code until it passes, refactor, checking in each time. The tests become a living specification. A study by Microsoft Research, IBM and NC State found TDD teams had 60–90% lower defect density while taking only 15–35% longer. 7
A few trusted tests beat many flaky ones

  
Unreliable tests waste time on reruns, and teach people to ignore failures, so real problems slip through. Gary Gruver at Macys.com went from 1,300 manual tests every ten days to just ten automated tests on every commit, then grew to hundreds of thousands. Adjust flakiness and watch trust erode.

  

    
    
    

    

  

  
Angie Jones adds three ways to fit automation inside a sprint: collaborate with business, testers and developers on what to automate; automate strategically, for example through APIs; and build incrementally with TDD.






  
8
Test performance and non-functional requirements too

  
Performance problems usually appear in integration testing or production, when they're hardest to fix. Automated performance tests across the whole stack catch problems such as a missing database index making a page grow from 100 milliseconds to 30 seconds, or a change that multiplies database calls tenfold. We also test non-functional requirements: availability, scalability, capacity, security. Many depend on environment configuration, so we test the configured stack (applications, interpreters, operating systems, dependencies) with the same frameworks we use for code.

  






  
9
Pull the Andon cord when the pipeline breaks

  
When the build goes red, the whole team is notified and someone fixes it or rolls back within minutes. Nobody checks in on top of a broken build. Later-stage failures (acceptance, performance) mean developers and testers prioritize the fix. Big, visible indicators help. See what happens when nobody pulls the cord.

  

    

    

    

  

  
Good automated tests are reliable (a failure means a real defect), consistent (every commit triggers them), fast and reproducible (ten minutes or less, reproducible locally) and inclusive (everyone tests, not just testers). DORA's 2018 research also supports exploratory and manual testing throughout delivery.

Does better observability mean less testing?

  
No.The second edition addresses a newer misconception: that excellent production observability lets us skip pre-deployment testing. Incidents in production are costly and hard to debug even with great tooling, and in distributed systems testing each service for correctness before deployment matters even more.
