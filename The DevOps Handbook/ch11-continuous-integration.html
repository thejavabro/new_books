Enable and Practice Continuous Integration

The longer a branch lives, the more painful the merge. Continuous integration means everyone merges into trunk at least daily, with automated tests guarding the shared code.

1

The hidden cost of branching

Branches let developers work in parallel without disturbing each other. But the longer they live and the more of them there are, the harder it becomes to merge them back. Integration problems mean rework: conflicting changes merged by hand, merges that break other teams' work, failed tests that are hard to trace. Continuous integration exists to stop this.

2

Case study: HP LaserJet firmware

Gary Gruver ran firmware for HP's LaserJet printers: 400 developers in the US, Brazil and India, two releases a year, and marketing told to pick the two things they wanted in the next six to twelve months. Gruver estimated only 5% of developer time went to new features. Toggle between before and after.

The goal: ten times more time on innovation. The means: continuous integration and trunk-based development, heavy test automation, a hardware simulator so tests ran on virtual printers, reproducing test failures on developer workstations, and a new architecture where one firmware build from trunk served every model, with printer capabilities set at runtime from an XML configuration file instead of at compile time. Gruver's warning: "Without automated testing, continuous integration is the fastest way to get a big pile of junk that never compiles or runs correctly."

3

Optimize for the individual or for the team?

Jeff Atwood places all branching strategies on a spectrum. At one end, everyone works in a private branch and nobody disrupts anyone, but merging becomes a nightmare. At the other, everyone works on one trunk: commits are simple, but each can break the whole project. Merge effort grows far faster than linearly with branch count and age. Try it.

Large merges have one more side effect: if merging is hard, nobody wants to refactor, because a refactor touches code everyone else is changing. That is how technical debt grows, exactly as Ward Cunningham first described it.

4

Adopt trunk-based development

Every developer checks into trunk at least once a day. The whole system is tested on every commit, so a change that breaks some other part is found at once. Some pipelines go further with gated commits: a change is only merged after the pipeline confirms it merges, builds and passes tests; otherwise only its author is told. Daily commits also force work into small chunks while trunk stays releasable. Try a gate.

The new definition of doneAt the end of each development interval we have integrated, tested, working and potentially shippable code, demonstrated in a production-like environment, created from trunk using a one-click process, and validated with automated tests.
5

Case study: continuous integration at Bazaarvoice (2012)

Bazaarvoice ($120 million revenue, preparing for an IPO) ran on Conversations, a monolithic Java application of almost five million lines over 15,000 files, on 1,200 servers across four data centers. After moving to two-week Agile intervals, its first attempt at two-week releases in January 2012 caused chaos: 44 production incidents. Ernest Mueller found three causes: too little test automation, a branching strategy that let developers commit right up to release, and microservice teams releasing independently in ways that broke the monolith's releases.

For six weeks developers stopped feature work to write JUnit unit tests and Selenium regression tests and to build a TeamCity pipeline. They switched to a trunk/branch release model: a release branch every two weeks, with no new commits unless critical. Watch the incidents fall.

Weekly releases came next and were "almost a non-event"; most changes were in customer service and marketing processes. Later they cut test time from over three hours to under one, dropped a staging environment, and moved to one-click deployments.
