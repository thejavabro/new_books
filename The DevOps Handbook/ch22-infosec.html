Information security is everyone's job, every day

A frequent objection to DevOps is "Infosec and compliance won't let us." The chapter turns this round: use DevOps to improve security by building it into everyone's daily work. James Wickett gives the reason. In a typical technology organization, Development, Operations and Infosec engineers come in a ratio of about 100 : 10 : 1. Outnumbered like that, Infosec can only do compliance checking, unless security is automated and part of how Dev and Ops work.

2

Bring Infosec into demos, defect tracking and post-mortems

Invite Infosec to the end-of-iteration product demonstrations, so they see the team's goals and can give guidance while there is still time to change course. At GE Capital, Justin Arbuckle found that blockages at the end of a project cost far more than at the start, and Infosec blockages were among the worst. "Compliance by demonstration" moved that work earlier and greatly reduced their reliance on static checklists. Move the point where Infosec first sees the work.

Illustrative relative cost of a security finding, not data from the book.

Track security issues in the same system Dev and Ops use. At Etsy, Nick Galbreath put them all in JIRA as P1 or P2: fix immediately or by the end of the week, even for internal applications. Every security issue got a post-mortem, because it taught engineers how to prevent the next one.

3

Put security controls in shared repositories and services

Everyone already uses version control, so place security tooling there too: libraries and settings that make it easy to do the right thing. Infosec can also work with a shared services team to run security platforms such as authentication and logging, and train developers to use them. Tap to see what belongs in the shared repository.

Work with Ops on hardened base images and cookbooks. Keep container base images in a registry, stored with a secure hash that is checked whenever the image is used or deployed.

4

Integrate security into the deployment pipeline

The old way was a security review after development finished, with hundreds of pages of findings in a PDF that went unaddressed because the deadline had arrived. Instead, automate as many security tests as possible so they run with every other test. Developers learn within minutes that a commit may be insecure, and the pipeline can show it in tools such as Jenkins.

Happy, sad and bad paths

Developer tests often check the happy path, where everything works. Good QA, Infosec and fraud people also test sad paths, where things go wrong, and security-specific bad paths. The chapter's example is a checkout form that accepts card numbers. Try some inputs.

Case study: static security testing at Twitter (2009)

Between January and March 2009, Twitter grew from 2.5 million to 10 million active users. Its Fail Whale page was famous. Early that year the @BarackObama account was hacked, and in April administrative accounts were compromised by a brute-force dictionary attack. The FTC issued a consent order: put processes in place within sixty days and keep them for twenty years.

6

Ensure security of the software supply chain

Josh Corman points out that developers now mostly assemble software from open source parts. We inherit their vulnerabilities along with their features. GitHub's 2020 Octoverse found open source dependencies most common in JavaScript (94%), Ruby (90%) and .NET (90%). Automated pull requests that patch vulnerable dependencies fixed them 13 days sooner, or 1.4 times faster.

The 2014 Verizon DBIR found that ten known vulnerabilities (CVEs) accounted for almost 97% of exploits in the cardholder data breaches it studied, and eight of those ten were over ten years old. In 2021 the DBIR authors found most organizations' internet-facing vulnerabilities dated from 2010 or earlier.

Direct versus transitive dependencies

Sonatype's 2019 report analysed components in Maven Central. Only 9% had a vulnerability on their own. With all transitive dependencies counted, 47% did. Expand the tree.

Components with at least one known vulnerability9%

The median time to remediate was 326 days. Time to remediate tracked time to update dependencies (TTU): projects that update often also fix faster. That is why Jeremy Long of OWASP Dependency Check recommends staying current on every dependency. The PrimeFaces flaw CVE-2017-1000486 was published in January 2018, and cryptominers then exploited it. The fix had shipped in February 2016, so teams that had already updated were safe. Popularity, measured in stars or downloads, did not predict better security.

7

Ensure security of the environment

Write automated tests that check that environments are hardened: configuration hardening, database security settings, key lengths and so on. Scan them with tools such as Nmap to confirm that only expected ports are open.

8

Case study: 18F automating compliance with Compliance Masonry (2016)

US federal agencies were projected to spend nearly $80 billion on IT in 2016. Getting any system from "dev complete" to "live" required an authority to operate (ATO), governed by more than four thousand pages of laws and policies. Even low-sensitivity systems needed over a hundred controls implemented, documented and tested, and an ATO typically took eight to fourteen months. 18F, inside the General Services Administration, built Cloud.gov, a platform as a service on AWS GovCloud. It handles logging, monitoring, alerting and most compliance controls at the platform level. Slide to see how much is left for each application team.

Compliance Masonry stores system security plan data as machine-readable YAML and turns it into GitBooks and PDFs automatically, and 18F publishes this work as open source in partnership with the OpenControl community.

9

Integrate information security into production telemetry

In 2010 Marcus Sachs observed that most cardholder data breaches were found months or quarters later, usually by a partner or customer noticing fraud rather than by internal monitoring. So put security telemetry in the same tools Dev, QA and Ops already use. Showing how services are being attacked reminds everyone that security is their concern.

In applications, measure logins that succeed and fail, password resets, email address changes and credit card changes. A rising ratio of failed to successful logins can be an early sign of brute-force attacks. Raise the attack rate.

In the environment, watch for changes to the OS, security groups, production configuration and cloud infrastructure, as well as XSS and SQL injection attempts and 4XX and 5XX web errors. Check that logging sends everything to the right place.

10

Case study: instrumenting the environment at Etsy (2010)

Galbreath did not create a separate fraud or security department. He embedded those duties throughout the value stream and put security metrics on the same dashboards as everything else: abnormal process terminations, database syntax errors, and signs of SQL injection. One check was deliberately simple: alert whenever UNION ALL appeared in user input. Try it.

As Galbreath put it, nothing shows developers how hostile the environment is like seeing their own code under attack in real time.

Protect our deployment pipeline

The CI/CD system is an attack surface too. Someone who compromises version control or build credentials can inject changes straight into production. Jonathan Claudius asked where he would hide malicious code, and answered: in the unit tests, which nobody reads and which run on every commit. Pick the countermeasures the chapter lists.

12

Case study: shifting security left at Fannie Mae (2020)

Fannie Mae helps finance about one in four US homes, so safety and soundness are part of its mission. With low risk tolerance, CISO Chris Porter and COO Kimberly Johnson changed two things: the culture, and how security tools reached developers. They made the tools self-service and API-based, connected them to Jira and Jenkins, trained developers, and spoke of "defects" rather than "vulnerabilities". Compare the two routes.

A failing security test stopped the line like an Andon cord. Security moved from protecting developers from themselves to "you build it, you own it". In the year before the talk, deployment frequency rose 25% and the deployment failure rate fell by about as much.
