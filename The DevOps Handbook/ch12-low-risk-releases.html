Automate and Enable Low-Risk Releases

Separate deploying code from releasing features. Then deployments become boring, automated and frequent, while releases become business decisions you can roll back in seconds.

1

If it hurts, do it more often

Chuck Rossi ran release engineering at Facebook for a decade. In the book's account, his day had a rhythm: by early afternoon he switched to "operations mode", developers with changes going out had to be online in the release chat, and the push happened like clockwork. Rossi noticed that Facebook could only handle a fixed number of changes per deployment, so more changes meant more deployments: from weekly to daily to three times a day for the web code, and from six- to four- to two-week cycles for the mobile apps.

Painful deployments tend to get rarer, which makes each one bigger and more painful, another downward spiral. This chapter breaks it by automating deployment and separating it from release.

Case study: daily deployments at CSG International (2013)

CSG, North America's largest SaaS customer care and billing provider (65 million subscribers, Java to mainframe), released twice a year. Development deployed to test environments daily, but Operations did production. Scott Prugh called it a "practice team" that practiced daily in safe test environments, and a "game team" that got two attempts a year, in production, with missing assets like firewalls and load balancers. So they made one team deploy to every environment daily, cross-trained developers on database changes, and made environments match.

4

Enable automated self-service deployments

Often Ops performs deployments as a form of separation of duty. It is better supplemented by automation everyone trusts: anyone can build packages from version control, test by running any suite on their workstation, and deploy to any environment they have access to with the same scripts. DORA's 2019 report found elite performers deploy on demand, with lead times measured in minutes or hours.

Case study · Etsy (2014)

At Etsy anyone can deploy. Engineers join a deploy queue in chat, run tests, then press a button in Deployinator. The 7,000+ trunk tests would take about half an hour in sequence, too long for the 20-minute deployment window, so they were split across a Jenkins cluster. Try it.

5

Decouple deployments from releases

Traditionally, the marketing launch date drives a big-bang deployment the night before. When it goes wrong, the "release" becomes days of firefighting. The fix is to separate two ideas.

DeploymentInstalling a specified version of software into an environment. A technical event, done by the team, frequently and routinely.
ReleaseMaking a feature available to all customers or a segment of them. A business decision, ideally reversible in seconds.

With short deployment lead times, release becomes a choice for the business and product owners, not for engineering. There are two families of release patterns: environment-based (several environments, only one gets live traffic; no code changes) and application-based (the code itself controls what is visible, using feature toggles).

6

Blue-green deployment

Two production environments; only one gets live traffic. Deploy the new version to the idle one, test it there, then switch the router. Rollback is switching back.

Databases complicate it, because both versions may share data. Either run two databases (put blue in read-only mode, back it up, restore to green, switch), or decouple database changes from application changes: make only additive schema changes and write code that doesn't assume which schema version is live (the expand/contract pattern). IMVU used this around 2009 to deploy fifty times a day, some with database changes.

Case study · Dixons Retail (2008)

Dan Terhorst-North and Dave Farley applied blue-green to thousands of point-of-sale tills across hundreds of British stores. Normally clients and server are upgraded together over a weekend, but the network couldn't push all clients at once. So they first upgraded the server to support both old and new clients, then trickled new client installers out for weeks, staged but inactive. Each store manager then chose when to release, and could revert.

7

Canary releases and the cluster immune system

A canary release promotes the new version through ever larger groups: A1 internal employees, A2 a small share of customers, A3 everyone else. The cluster immune system, documented by Eric Ries at IMVU, links production monitoring to the release so that if user-facing metrics deteriorate (conversion rate, say) it rolls back automatically. Run a release; choose whether the new version has a hidden defect.

8

Feature toggles

Application-based releases wrap code in a conditional that checks a toggle at runtime. Toggles let us roll back a bad feature instantly, degrade gracefully under load (turn off expensive features), build against services that aren't ready yet, and run A/B tests. Acceptance tests should run with all toggles on, so we know hidden code works. Flip some toggles.

if (flags.enabled("new-search", user)) {
  return newSearch(query);   // dark until we flip it
}
return oldSearch(query);
9

Dark launches: Facebook Chat (2008)

Toggles make dark launching possible: put a feature in production, invisible to users, and exercise it with real load before anyone sees it. Facebook Chat, with over 70 million daily users in 2008, had to keep everyone aware of friends' online status, the hardest part computationally. For a year the code deployed daily, hidden by Facebook's Gatekeeper toggle service. Every user session secretly ran a test harness that sent invisible chat traffic to the back end. Then launch was two reversible steps. Ramp it up.

"The secret for going from zero to seventy million users overnight is to avoid doing it all in one fell swoop." Eugene Letuchy, Facebook Chat team.

John Allspaw, at Flickr in 2009, said dark launches raise confidence "almost to the point of apathy" about load problems. Chuck Rossi has said all the code for features Facebook planned to launch in the next six months was already on its production servers.

10

Continuous delivery versus continuous deployment

Jez Humble's updated definitions: continuous delivery means everyone works in small batches on trunk (or short-lived branches merged often), trunk is always releasable, and we can release on demand at the push of a button. Continuous deployment adds that good builds actually go to production regularly through self-service. Most teams at Amazon and Google practise continuous delivery; some do continuous deployment. HP LaserJet firmware is continuous delivery. Which describes each team?

11

Case study: a win-win for Dev and Ops at CSG (2016)

Releases at CSG had improved dramatically, yet conflict with Operations continued. The incident data showed why.

Prugh asked whether different organizational goals worked against system goals, whether Dev's lack of Ops knowledge made software hard to run, whether a lack of shared mission reduced empathy, and whether handoffs stretched lead time. The answer was service delivery teams that build and run the software, Dev and Ops on one team. Leaders applied John Shook's model, change behavior to change culture. Developers joined operations engineers to automate reporting and routine jobs with Jenkins, add telemetry, automate deployments with rollback, put configuration in version control, and pull all tickets into one backlog. Erica Morrison's takeaway: change management had been invisible to developers, and change is a key intersection of opposing Dev and Ops goals.
