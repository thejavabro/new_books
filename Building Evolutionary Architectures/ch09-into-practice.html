From ideas to an organization that evolves

The last chapter leaves the code and turns to people, money and strategy: how team structure shapes architecture, how to make the business case, where to start, and when evolutionary architecture is not worth it.

2

Don't fight Conway's Law

In 1968 Melvin Conway argued that organizations end up designing systems that mirror their own communication structures. If teams are split by technical skill (front end, back end, database) and you build microservices anyway, every domain change needs all three teams. The Inverse Conway Maneuver flips it: shape teams like the architecture you want, and that architecture becomes easier to reach. Change the checkout feature under each structure.

3

Cross-functional, product-minded teams

Domain-centric teams tend to be cross-functional: everyone needed to design, build and run the service sits on the team, which removes the friction of waiting on another silo. Roles shift as a result. Where a skill is scarce, it can rotate across several teams. Tap each card.

Avoid excessively large teams

J. Richard Hackman's explanation for why big teams struggle: it's not the people, it's the connections between them, which grow as n(n−1)/2. Keep teams small, keep inter-team connections few, and guard any integration points between teams with fitness functions.

Culture: what gets measured gets done

Architects shape the technical culture as much as the code. Goldratt's line sums up why: tell people how they're measured and you've told them how they'll behave. Teams rewarded only for new features will neglect evolvability unless someone makes it a priority. How does your team do? Tick what's true.

Watch for overengineering tooThe Refactoring book's rule of three: the first time, just do it; the second time, wince and duplicate; the third time, refactor. When a new library is proposed, run a short experiment to see how much coupling it adds.

7

The CFO's view: quanta and cost

Long-range budgets assumed a predictable ecosystem, which no longer exists. The book observes a curve: as the number of architecture quanta rises, cost per quantum falls (cleaner separation, forced automation), until coordination between tiny pieces starts to dominate. Where's the sweet spot? It depends on how fast your market forces you to move.

8

The business case: hypothesis-driven development

To non-technical stakeholders, fitness functions sound like metawork. Talk instead about what an evolvable architecture enables: A/B tests and learning from real users. Facebook, faced with more than a million photos flagged as offensive in one holiday week, experimented with follow-up questions and cut the false positives to a manageable level. mobile.de, with sales sagging under a cluttered UI, built three versions and let users choose. The method: state a hypothesis, run an experiment, decide from data. Try one.

Hypothesis: larger product images on sale items will raise their sales by about 5%.

Side-by-side variants are easy when a service runs many instances: make a few slightly different and route some users there. Run long enough for significance, and prefer silent measures (clicks, completion) over pop-up surveys.

10

Enterprise fitness functions and zero-day exploits

In 2017 a vulnerability in a popular Java web framework led to a major credit agency breach. Patch and warnings came quickly; finding every affected system did not. The book's answer: if every project runs a deployment pipeline, give the security team a slot in each one. Most days it runs mundane checks; on a zero-day, one new check can fail every build that still uses the bad version.

The same mechanism serves enterprise architects generally. PenultimateWidgets' architects drafted a spreadsheet of 62 requirements (including five nines of uptime everywhere) for a new platform. Who would verify them, and did the admin screens really need five nines? They turned the criteria into fitness functions in a pipeline template: critical checks like security built in, service-specific ones (like availability) left for teams to add.

11

Carving a bounded context out of layers

Layered architectures encourage reuse across contexts; DDD's bounded contexts forbid exactly that kind of reach-in. To reconcile them, keep the layers but mark a bounded context that runs through them, then add fitness functions that stop outside code from coupling to its internals. Where do you start?

It depends on the organization. Pick a starting strategy to see its trade-off.

Infrastructure always affects architectureOne consulting client ran roughly 2,500 servers, each supporting only about five users, because the app stuffed huge amounts of data into HTTP session state. Siloed operations and a ban on production debugging meant developers couldn't untangle it. A rough estimate said around 250 servers should suffice. The "cost-saving" setup was the expensive one; developers eventually ran their own guerrilla DevOps group.
