Engineering Incremental Change

Evolution happens in small steps. Continuous Delivery supplies the machinery, and a deployment pipeline is the natural place to run fitness functions every time anything changes.

1

Incremental change in production

PenultimateWidgets, the book's stand-in company, runs a microservices architecture where every service lives in its own container and shares nothing operationally. Many parts of the business (the catalog page, customer service, shipping evaluations) use one shared star rating service. The team builds a version that supports half stars. Step through how it reaches production without forcing anyone to change.

The machinery underneathServices register their location and contract with a service discovery tool when the pipeline deploys them. Callers look up what they need. A proxy at the old endpoint decides which version answers. Operations watches the routes between services, not just the services, and removes ones nobody calls. Tools such as Swabbie automate that clean-up in the cloud.
2

The deployment pipeline runs the fitness functions

Continuous integration gives a team one official build. A deployment pipeline goes further: it splits post-commit work into stages of increasing sophistication, provisions environments from scratch, and verifies production readiness. That makes it the natural home for fitness functions. They run on every change, at whichever stage fits. Push a commit through, optionally with a change that breaks an architecture rule.

3

Fan out to test in parallel

With continuous deployment, a green pipeline means the change goes to production. So the pipeline must check two things: the change works in the future state, and it does not damage the current production state. A fan-out runs those jobs in parallel; a fan-in gathers the results before deploying. Compare the elapsed time.

4

Deploy is not the same as release

Users may not want features trickling in every day; the business may want a big launch. Feature toggles reconcile the two: code ships to production behind a condition and stays dark until someone flips it. The simplest version is an if on a configuration value; richer ones reload at runtime and route by user, IP or access list.

// a minimal toggle (illustrative)
const flags = loadFlags();      // from config or a flag service

function renderRating(item, user) {
  if (flags.enabled("half-stars", user)) {
    return halfStarWidget(item);
  }
  return wholeStarWidget(item);
}

QA in productionA side effect teams often miss: once new work lives behind toggles that only testers can see, exploratory testing can happen in the real production environment.
5

Case study: the invoicing pipeline

The invoicing team wants to replace old libraries without breaking anyone. They care about scalability (availability agreements with resellers), integration (other services call them), security (it is money) and auditability (state rules require an independent accountant to verify tax-code changes). They replace their CI server with a six-stage pipeline, including two manual stages. Set how often the humans are available.

Why model manual steps as stages?Treating the audit as a fitness function puts it in the same picture as every automated check. Its cost becomes visible, and the business can ask a rational question: is faster release cadence worth paying for more frequent audits?
6

Consumer-driven contracts: an engineering safety net

A second case: an accounting API used by many internal and partner consumers. The pipeline lints the OpenAPI spec at design time, deploys it to a sandbox for functional tests, runs integration contract tests (the book mentions Pact), then ships behind a toggle. The contract stage works like this: each consumer writes tests describing exactly what it needs from the provider and hands them over. The provider promises to keep every one of them passing, and is otherwise free to change. Change the provider's response and see whose contract breaks.

Provider response fields. Tap a field to remove or restore it.

Needs a certain maturityContract tests are worthless if the build is red for days at a time; nobody can tell whether integration still works. Using engineering practices to police practices removes manual pain, but only on a team that keeps its builds green.
7

Where the effort goes

People ask when software will get the heavy predictive mathematics of structural engineering. The authors think it largely won't, because the balance between design and manufacturing is different. In a bridge, manufacturing is expensive and unforgiving, so huge effort goes into predicting before building. In software, "manufacturing" is compiling and deploying, and that is automated and nearly free. Almost all the effort is design (which includes coding).

The software engineering answerBecause rebuilding is cheap but the parts are many and changeable, sanity comes from confidence in making changes: incremental change backed by automated verification.
