Fitness Functions

Unit tests protect the domain. Fitness functions protect the architecture: any mechanism that gives an objective verdict on how well some architecture characteristic is holding up.

What a fitness function is

In genetic algorithms, a program mutates a candidate solution a little each generation, and a fitness function scores each variant so the algorithm keeps the better ones. The authors borrow the idea for architecture: an architectural fitness function is any mechanism that gives an objective integrity assessment of some architecture characteristic.

Fitness functionsprotect architecture characteristics as the system changes

There is a catch: you can download a unit-testing library for your language, but no single tool covers architecture. Fitness functions come from all over the toolbox. Open each family.

"Function" does not mean "code"Like an agile acceptance criterion, a fitness function can be a manual procedure (a regulator-required review, a database failover drill). What matters is that it produces an objective result. You cannot compute a single "architecture score of 42," but you can have precise conversations about which checks pass.

A first example: keeping cycles out

A dependency cycle between components is an antipattern: reuse one and you must drag the whole tangle along. Yet the IDE works against you. Reference a class from a package you have not imported and the auto-import prompt appears; developers dismiss it by reflex, and once in a while that creates a cycle. Let the developers below accept a few auto-imports, then switch on a cycle check in the build.

Is it a fitness function?

  
Not every test is a fitness function, and not every metric either. The test checks an architecture concern and produces an objective verdict. A dashboard someone glances at is not one; the same dashboard with an alarm on a threshold is. Sort these.

Atomic checks can all pass while the whole fails

  
Atomic fitness functions check one aspect in isolation. Holistic ones run several together in a shared context, because characteristics interact. The book's example: a scalability check (enough concurrent users within a latency range) and a security check (data must not be too stale). Turn on caching and run the checks.

  

    
    
    

    

    

  

  
You cannot test every combination, so choose the interactions that matter most. That choice is itself useful: it forces a conversation about which characteristics are worth the effort.






  
6
When does it run?

  
Watch a week go by. Triggered functions fire on an event, such as a commit. Continual ones watch all the time, often by sending synthetic transactions through production: real requests tagged with a flag so the final step does not actually commit (a correlation ID helps trace them). Temporal ones fire on the calendar, such as a reminder to upgrade a library once its first patch release ships.

  

    

    

  

  






  
7
Case study: same rule, two implementations

  
An orchestrator owns the state of a workflow; the domain services must talk only to it, never to each other. No off-the-shelf tool knows your topology, so the architect builds one. It can be continuous (services broadcast who they call; a watcher reacts at once) or triggered (the pipeline periodically harvests logs and checks them). Send a rogue call and compare.

8
A threshold that moves with context

  
A static fitness function has a fixed target: pass/fail, a numeric range, membership in a set. A dynamic one adjusts its target using extra context. Here, the architects accept slightly slower responses as concurrent users climb, but only up to a point. The verdict is still objective; the target just depends on load.

  

    
    
    

    

    

  






  
9
Who writes them, and what to focus on

  

    
Who writes them
Architects usually define them, since they decide the objective measures. Architects and developers maintain them and keep them passing. When one breaks, developers need to know why it exists, or governance feels like a burden instead of a useful constraint. Post results somewhere everyone sees them.

    
Where's my framework?
Domain tests have ready-made libraries per platform. Fitness functions rarely do: operational checks need monitors, security checks need scanners, quality checks need metrics tools. Expect to write a little glue code.

    
Outcomes over mechanics
Like a mathematical function, a fitness function takes inputs and returns a verdict. Focus on what is measured and why, not on which tool measures it. Many are written in a different stack from the system they guard.

  

  
Domain-specific fitness functions?Rarely. Fitness functions cover architectural concerns that make sense regardless of domain (elasticity means the same on a game site or a store). Checking a change of address needs domain knowledge, so it belongs with the ordinary tests. That is a handy litmus test for where a check lives.






  
10
The system-wide fitness function

  
Taken together, the individual checks form a system-wide fitness function: a picture of what matters. Nobody computes it as a number. It exists to make trade-offs visible, because characteristics fight each other (stronger encryption costs performance) and every stakeholder believes theirs comes first. Drag the encryption strength and watch the trade-off.

  

    
    

    

  

  
Breeding, not random mutationWe do not want an architecture that flips random bits and waits a few million years. Like dog breeders selecting for traits, architects constrain evolution toward chosen characteristics. Without that guidance, evolutionary architecture becomes merely reactionary.
