Evolvable Architectures: Guidelines

Most architects inherit a mess rather than a blank page. The second half of Chapter 7 is a toolkit of practical moves that add flexibility without rebuilding everything.

1

Flexibility without starting over

Large enterprises grow like a brain: new capabilities layered on top of old ones, with ancient plumbing still doing critical work underneath. No architect, however gifted, can turn a Big Ball of Mud into clean microservices without enormous effort. The good news is that you can add flexibility points to an existing architecture one at a time. This page walks through the book's guidelines.

2

Remove needless variability

Every unplanned difference between environments is a source of surprise. Snowflake servers, hand-built and hand-patched, drift apart over time. Immutable infrastructure, a term from Chad Fowler, defines the whole machine in code and rebuilds rather than modifies it. That sounds like the opposite of evolvability, but it is what makes evolution safe: fewer variables means fewer unexplained failures. The same idea applies to developer machines ("works on my machine").

3

A cautionary tale about one stale server

The book retells a well-known DevOps disaster at a trading firm in 2012. Step through it.

Two lessonsRemove feature toggles as soon as they have served their purpose; never recycle one. And deploying critical software to servers by hand, instead of through automation that guarantees every node is identical, is reckless.
4

Make decisions reversible

Systems that evolve aggressively will sometimes fail in unexpected ways. When they do, you want a quick way back, and then a new fitness function so it can't happen again. Two common mechanisms: blue/green deployment (two identical environments; switch traffic, switch back if needed) and canary releases through feature toggles or service routing.

5

Prefer evolvable over predictable

Projects start with a list of known unknowns, things they know they must learn. They get blindsided by unknown unknowns, which is why big design up front struggles. Mark Richards puts it neatly: all architectures become iterative because of unknown unknowns; agile just admits it sooner. Tap a quadrant.

6

Build anticorruption layers

The Abstraction Distraction antipattern: application code wired so deeply into a library that switching it is a rewrite. DDD's remedy is an anticorruption layer, an interface describing what you need in your own terms. The book's story: a used-car auction site needed asynchronous bulk photo uploads. Instead of buying the fanciest message queue "because we'll need it eventually" (premature complexity is technical debt you purchase), the architect picked a tiny database-backed queue and hid it behind an interface. Play through two years, with and without the interface.

Just-in-time, not everywhereThis is not a license to abstract everything (a factory to get a proxy to a remote interface to a thing). Modern IDEs can extract an interface when you need one. Ask: do I have to decide now? Can I defer safely? What will suffice now and be easy to change later?
7

Build sacrificial architectures

Fred Brooks: plan to throw one away, because you will anyway. Martin Fowler's sacrificial architecture is built expecting to be replaced if the idea succeeds. eBay went from Perl scripts to C++ to Java. Twitter launched on Rails for speed, then rebuilt its back end when the "fail whale" became famous; building the robust version first might have let a competitor reach the market first. Cloud makes cheap first versions even more attractive.

Plan the rebuild: the business must fund it. And beware Brooks's second-system syndrome: small, elegant successes bloating into feature-laden monsters because nothing is ever removed.

8

Mitigate external change

Every project stands on a tower of third-party code. In 2016 one developer unpublished hundreds of small JavaScript packages, including an 11-line string-padding function, and builds across the ecosystem broke until the registry restored it. Chris Ford's verdict: transitive dependency management is our "considered harmful" moment. The authors suggest a pull model: an internal repository of third-party components, where outside changes arrive like pull requests, go through their own pipeline, and get rejected if they destabilize things.

9

Update frameworks aggressively, libraries passively

Your code calls a library; a framework calls your code. Frameworks (UI, ORM, MVC scaffolding) touch everything, so falling behind hurts a lot; libraries are utilities with much lighter coupling. Prefer libraries where you can. Then treat framework upgrades as push (apply soon after a stable release) and library upgrades as pull (when you need a feature). Slide how far you have fallen behind.

10

Version services internally

Two ways to change an endpoint's behavior. Version numbering creates a new endpoint name (/v2/ratings) and callers must pick one. Internal resolution keeps one endpoint that works out which version the caller needs: less coupling to version numbers. Either way, support only two versions, and only temporarily. The star rating service did exactly this: a new column for the half star, and a proxy inside the service returning whichever format was requested.

11

Fitness function-driven architecture

Like test-driven development, but for a make-or-break characteristic: write the fitness function first and let it drive the design. LMAX, a retail trading exchange, needed enormous throughput on the Java platform. The first thing it built was a measurement of transactions per second. Try their designs in order.

Mechanical sympathyA Formula One idea: great drivers understand how the car works underneath them. Measuring every layer showed LMAX that business logic was a tiny fraction of the time; context switches were the rest. The fitness function stayed in place as the rest of the system was built, and redirected the design several times.
