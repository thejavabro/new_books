Evolutionary Data

Databases are often the stickiest coupling in a system. Schemas can evolve as smoothly as code if they are tested, versioned and changed in small steps, with a transition period for everyone who depends on them.

1

Treat schema changes like code

A schema is an abstraction of the real world, just like a class hierarchy. When the world changes, it has to change too, or it slowly drifts out of sync. The key is to evolve the schema alongside the code, applying the same discipline: tested (including checks that an ORM's mappings still match), versioned with the code that uses it, and incremental, through small migration scripts applied automatically by the pipeline. Play with a migration history.


    

    

  

  






  
2
Shared databases and Expand/Contract

  
Teams often default to shared database integration: everyone uses the company database, so why not read each other's tables? Because it fossilizes the schema. Any change by one application can break the others. The standard escape is the Expand/Contract refactoring (a database case of Parallel Change): add the new structure, keep old and new in sync during a transition that may last days or months, then remove the old one when everyone has moved. Example: splitting one address column into street and city.

  

    

    

    

  

  
In the hardest (and most common) case, a trigger keeps both shapes consistent during the transition. Try writing from each side.

  

    

    

    

  

  
The same move inside a servicePenultimateWidgets adds breadcrumb routing. Not every business unit adopts it at once, so the routing service keeps the old route table and a richer new one, linked by triggers, and serves both APIs. When the last caller moves, the old table and trigger go. Code and data evolve together.






  
3
Why data lags behind

  
Data teams often work with tools far more primitive than a developer's IDE: little refactoring support, no out-of-container testing, unit testing, dependency tracking, linting or mocking. Structures are coupled to application code, ETL jobs and reports owned by other teams, so refactoring means cross-team coordination and gets deprioritized. Suboptimal schemas pile up. The authors add a provocative explanation: data specialists' careers are often tied to one database vendor's certification, so tools from outside that vendor's world struggle to catch on. Open source and NoSQL are loosening that grip.






  
4
Transactions: the strong nuclear force

  
Coupling analysis tools find class and package dependencies easily; transactional coupling is invisible to them. Yet transactional boundaries often reveal how business concepts really belong together, and they bind quanta more tightly than anything else. Try splitting a system finer than its transactions allow.

  

    
    

    

  

  
Don't take "micro" literallyWhen migrating, start with a few larger services. In greenfield work, keep service and data contexts small, but each should capture a useful bounded context, not be as tiny as possible. Granularity finer than the business's transactions is a damaging form of metawork.






  
5
Precious schemas become fossils

  
"Applications come and go, but our schemas live forever," some CTOs say. Schemas do change more slowly than code, but they still model a world that changes. A team that refuses to restructure usually extends the schema by bolting on yet another join table. Each one works today; over the years they hide what the entity really is. Advance the years.

  

    
    

    

    

  

  
Old data is a tax tooData that has survived generations of software is inconsistent at best. Keeping every scrap in the main path couples you to the past. Decide with the business what truly has value: keep it, archive the rest for reference, and fix quality early rather than building workarounds forever.






  
6
Replace database guarantees with fitness functions

  
Splitting a single database into one per service (as microservices do) takes away tools data teams trust: foreign keys, shared reference tables, stored procedures. Architects can reassure them by replacing each native guarantee with governance.

  

    

    

    

    

  

  

    
Share the tables
Convenient, but every schema change ripples to every service. Violates the no-shared-database tenet.

    
Make each a service
Clean ownership, but a flood of interservice calls can hurt performance.

    
Owner writes, others cache
One service owns updates; readers cache on startup and refresh periodically. Updates go through the owner, which publishes changes.

  






  
7
Case study: one database becomes several kinds

  
Monoliths usually start with one relational database for good reasons: speed to market, simplicity, uncertainty. It ends up serving catalog, analytics and operational data, sometimes bent into odd shapes. Breaking up the monolith is a chance to choose storage per problem. Match each workload to a store.

  
Best fit?

  
Every split is a trade-off (more stores to run, consistency to manage), so present the trade-offs to the data team rather than decrees.
