Contracts run from strict to loose

The book defines a contract broadly: the format parts of an architecture use to pass information or dependencies. That covers REST and gRPC, but also library dependencies, caches, method signatures, IP addresses and URLs. Contracts sit on a spectrum. Strict ones remove ambiguity but break whenever anything changes; loose ones bend but give up certainty. Slide along it.

strictloose

  

  
Contracts change often and are used by manyThat combination is exactly what causes rippling breakage in an architecture. Use strict contracts only where their certainty pays off; elsewhere, prefer looser ones and replace lost guarantees with fitness functions such as consumer-driven contracts.






  
2
Need to know: avoid stamp coupling

  
A wishlist service only has customer IDs and needs a name to display. It asks a customer profile service. The tempting move is to take the entire profile "in case we need it later." That is stamp coupling: now any change to any profile field can break the wishlist, which doesn't care about those fields. Change the profile and compare the two contracts.

Case study: microservices as an evolutionary architecture

  
A layered architecture partitions by technical concern: UI, business rules, persistence. But most changes are about a domain concept, such as Checkout, and that concept is smeared across every layer. Microservices flip it: partition by domain, and put the technical layers inside each service along with its database and search engine. Pick the same change in both.

  

    

    

    

  

  
Microservices commonly follow seven principles. Tick the ones a system honors and see how evolvable it is likely to be.

  

    

    

  

  
Why not in 2005?Machines were hand-built, operating systems were licensed and costly, and there was little automation. When operations is expensive, architects design around sharing it, as enterprise-service-bus SOA did. Continuous Delivery, cheap open source stacks and automated provisioning shifted the equilibrium toward domain-centric styles.






  
4
Reuse is an organ transplant, not Lego

  
Every company wants reuse, and SOA chased it hard: two contexts both mention a Customer, so consolidate into one shared Customer service. But making code reusable means adding options and hooks for every caller, and each hook makes it harder to use for any single purpose. Microservices take the opposite stance: prefer duplication to coupling. Slide how many consumers a shared component tries to serve.

  

    
    

    

  

  
When reuse worksEffective reuse needs a good abstraction and low volatility. Open source libraries and frameworks are reused successfully all the time; a fast-changing internal domain object shared by five teams is not.






  
5
Sidecars and the service mesh

  
Some capabilities should be consistent everywhere: monitoring, logging, authentication, circuit breakers. Leave each team to implement them and you get chaos, plus no way to upgrade the monitoring tool across the company. The Sidecar pattern (descended from Cockburn's Hexagonal, or Ports and Adapters, architecture) separates domain logic from operational plumbing. Put the plumbing in a sidecar on every service and the sidecars can link into a service mesh. Build it up.

  

    

    

    

  

  
Orthogonal couplingDomains and operations are two concerns at right angles that must still intersect. A sidecar is an orthogonal reuse pattern: it cuts across the domain seams in one consistent layer, a distributed cousin of the Decorator pattern. In polyglot shops it also means building one sidecar per platform rather than one integration per service.






  
6
Data Mesh: orthogonal coupling for analytical data

  
Zhamak Dehghani and others applied the same idea to analytical data (reporting, ML training, insights), which is coupled to operational data but has different needs. Instead of piping everything to a central warehouse or lake, each domain shares its analytical data peer to peer. Open each principle.

  

  
The core architectural element is the data product quantum (DPQ): code plus data, owned by the domain team, sitting next to its service as a cooperative quantum. It is operationally separate (asynchronous, eventually consistent) but tightly contract-coupled to its service, and more loosely coupled to whatever does the analysis. Choose a DPQ type.
