Automating Governance: Code Level

Architects used to govern with review boards and wikis nobody read. This half of Chapter 4 shows how code-level metrics and architecture test libraries turn rules into checks that run on every build.

1

The same lesson, learned three times

Kent Beck's XP team in the 1990s noticed that projects which integrated more often had fewer problems, so they took it to the extreme: continuous integration, everyone committing to the main line at least daily. The old way, coding in isolation for weeks and merging in an "integration phase," let conflicts pile up combinatorially. Slide the gap between merges.

2

Afferent and efferent coupling

Software has little of the predictive mathematics other engineers enjoy, but it has a few code metrics that say something about architecture. From Yourdon and Constantine (1979): afferent coupling (Ca) counts incoming connections to a component; efferent coupling (Ce) counts outgoing ones. Robert Martin later derived instability, I = Ce / (Ce + Ca). Tap a component.

Tools that report these: JDepend, IntelliJ's dependency matrix, SonarQube, NDepend, JArchitect and others for most platforms.

3

Distance from the main sequence

Abstractness A is the share of abstract elements (interfaces, abstract classes) among all elements. Combine it with instability and you get one of the few holistic structural metrics: D = |A + I − 1|. Components near the diagonal "main sequence" balance the two. Too abstract and unstable: the zone of uselessness. Too concrete and stable: the zone of pain, brittle code nobody can change safely.

Presets:

Two usesBefore a migration, measure and pull troubled code back toward the line: extract methods from oversized ones (raising abstractness), then remove the duplication you uncover. Moving code on a shaky foundation is harder. As a fitness function, fail the build when a component drifts too far from the line.
4

Govern the direction of imports

A close cousin of the cycle check: declare which packages may depend on which, and fail the build otherwise. With a metrics library that has an API, this is a few lines inside an ordinary unit test. The authors prefer this to written guidelines and scolding: developers can focus on the domain, and the rule lives as an executable artifact. Try some imports.

// illustrative: declare allowed package edges
rules = DependencyRules()
web         = rules.pkg("shop.web")
persistence = rules.pkg("shop.persistence")
util        = rules.pkg("shop.util")

web.mayDependOn(util)
persistence.mayDependOn(util)

assert analyzer.matches(rules)

Tap an import to try it.

Cyclomatic complexity, and herding teams

Thomas McCabe's 1976 metric counts independent paths through code. For a single function, CC = decision points + 1 (formally E − N + 2 on the control-flow graph). Pick a function.


    

  

  

  
Industry folklore says under 10 is fine; the authors prefer under 5. But a metric cannot tell essential complexity (the problem is hard) from accidental complexity (the code is poorly factored). Test-driven development tends to produce smaller methods as a side effect. And if your codebase already fails a hard limit everywhere, don't give up: herd teams toward it with a threshold that warns first and becomes an error over time.

Case study: did a license change?

  
PenultimateWidgets' lawyers approved every open source license in a project with patented algorithms. Then the awkward question: what if a library quietly changes its license in a routine update? Before writing anything, check whether a tool already exists (today, Black Duck does this). At the time they built a small fitness function. Step through, then simulate an update.

  

  

    

    

  

  
Half automated, half humanNo attempt to interpret the change. Detection is automatic; the reaction (a lawyer reviewing the new text) stays manual. Fitness functions often just announce "something you care about changed."






  
7
Architecture tests: rules as code

  
ArchUnit (Java) and NetArchTest (.NET) let you write structural rules in fluent, readable assertions: package and class dependencies, inheritance, annotations, layers. Principles written in a wiki are aspirational; principles checked in the build are governance. Pick a rule, then try dependencies against it.
