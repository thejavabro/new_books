Control Plane

Above the running system sits the machinery that watches and steers it. How much you need depends on your scale; what you build must respect the fact that development tooling is production too.

1

Production or control plane?

Instances, networks and pools are scattered like spilled building bricks. The control plane puts them in order: all the background software that makes production work. The book's test: if production user data passes through it, it is production software; if its main job is to manage other software, it's control plane. Sort these.

2

How much is right for you?

Every piece is optional if you accept the trade-off (no monitoring means hearing about outages from the CEO). Each piece also costs money and people to run, forever. It's a trade between fixed costs of a platform team and variable costs of slow deployments, recovery and provisioning. Since the first edition (2007), logging, monitoring and provisioning went from six-figure commercial products to excellent open source; now the hard part is choosing. Tick what you'd build and compare the burden with your scale.

3

Mechanical advantage cuts both ways

On 28 February 2017, Amazon S3 in one region went down for about two hours, and much of the internet with it, for many hours more. An authorized engineer, following an established playbook, mistyped one input to a command meant to remove a few servers, and removed many more. Amazon's postmortem explained, apologized and committed to improve, and never said "human error". This was the system failing a human: the tools allowed a small slip to become a huge outage. The fix: remove capacity more slowly and refuse to go below each subsystem's minimum.

Learn from successes tooThe same playbook had run fine before. Why? Who ran it, was there a second pair of eyes, had steps been relaxed, what feedback did the system give? Hold reviews of successful changes and near misses, not just outages. Automation is for repetitive, fast work; humans are for seeing the whole situation.
4

Platform and ecosystem: enable, don't gatekeep

A platform team provides capabilities others use; it doesn't do the work for them. The monitoring team shouldn't write your alerts from a request form; it should build tools that let you define your own (say, a JSON description), like a stable interface with a hidden implementation. Database administrators keep databases healthy while the data model belongs to the application. With shared SQL databases, one team's schema change can hurt another, hence one database per service, or machine-readable migration formats both sides can script checks against. The goal is to take the platform team out of every day-to-day loop.

5

Development is production

Picture a typical dev server: stale files, unversioned scripts, keys from people long gone. QA: stubbed integrations, unrealistic data, one environment for many teams. Yet developers depend on version control, CI, QA and artifact repositories to do their jobs. If the copywriters' content system went down, that would be a severity 2 outage. The tools developers need deserve production-level SLAs, and QA environments should be stamped out on demand by the same automation that builds production, with recent anonymized data.

6

System-wide transparency: two questions

At system level ask: are users getting a good experience? and is the system creating the economic value we want? Not "is everything running?" At scale, partly broken is normal. Measure user experience directly with real-user monitoring (hosted services start fast and look polished but charge by scale; open source costs labor). Whatever you pick, adopt it thoroughly, with no dead zones. For value, watch the top line (drop-off at each step of a business process, errors in revenue paths, queue depth as the first sign of slowdown) and the bottom line (runaway autoscaling, operations toil, heavy runtimes where it matters). Everyone, from marketing to operations, should look at the same underlying data through their own views.

What to expose, and what "normal" means

You can't predict which metric will matter next year, so expose broad categories. A handy definition of nominal: the mean for the same hour of the week, plus or minus two standard deviations.

Logs and stats get collected by push (syslog-style, good for containers) or pull, then indexed for search, trends and alerts. Metrics databases keep fine detail for recent data and roll older data up into coarser aggregates.

7

Configuration, provisioning and deployment services

Configuration services (ZooKeeper, etcd) are distributed databases for settings, orchestration and leader election, still bound by the CAP theorem. They're scalable but not elastic; reads are cheap, writes need consensus. Rules: instances must start without the config service, must keep working when it's unreachable, a partitioned node must not be able to shut down the world, and replicate across regions.

Push deploymentA central server reaches out (often over SSH) and assigns roles. Simple for long-lived machines using commodity tools.
Pull deploymentMachines know their role and fetch their bits from a config service. Suits elastic, ephemeral instances.

Pair either with a repository of blessed binaries built on clean servers, tagged as they pass each stage. Remember the build server is an attack target (the compromised plugin again). Use canary deployments: give a few instances the new build first; if their metrics go bad, stop the rollout. At large scale, a placement service decides where instances run and wires up addresses, balancers and firewall rules.

8

Command and control

If a config change rolled out in milliseconds and instances restarted in a tenth of a second, you'd just replace instances. Live control matters when startup is slow (JVM warm-up, cache loading, VMs). Plan these controls. Two buttons are traps; tap each.

Sending commands to 500 instances

Start with an admin HTTP API on a separate, non-public port (describe it with OpenAPI and you get a GUI for free). Looping over hundreds of instances gets slow and stalls on one dead node; then move to a command queue all instances listen to, with random delay or waves so you don't dogpile yourself.

GUIs demo well and operate badlyOne order system needed several minutes of clicking on each of six servers for a clean shutdown. Within a one-hour change window, nobody did it. Command lines can be scripted, logged and automated.
9

The platform players

Assembling your own control plane keeps options open but costs integration work (getting authentication, roles and monitoring to fit together is a classic slog). A platform (Kubernetes, Mesos, Cloud Foundry, Docker Swarm at the time of writing) is to the data center what an operating system is to a PC, and can run anywhere. It needs care and feeding by a larger group, not a single team. If you adopt one, embrace it fully; don't wrap it at arm's length.
