NICs and names: a machine has many

"Hostname" means two things. The OS hostname (plus search domain, the FQDN) is what a machine calls itself. A DNS name identifies an IP address. Nothing forces them to agree: a box that calls itself spock.example.com may be reached as www and mail. DNS names and IP addresses are many-to-many, and data center servers are multihomed: several network interfaces on separate networks for production, backups and administration. Tap an interface.

3

Listen on the right interface

Libraries make the easy thing (listen on every interface) the default. On a multihomed server that can expose admin functions to the production network or production functions to the backup network. And "get my local host" returns whatever address matches the internal hostname, which may be the wrong one. Bind explicitly to a configured address. Toggle the bind address and see who can connect.

// risky: every interface, including admin and backup
listen("tcp", ":8080")
// better: an address supplied by configuration
listen("tcp", config.bindAddress + ":8080")

Outbound traffic rarely needs a chosen interface; needing one usually means two routes reach the same place. With two NICs bonded into one for redundancy, make sure the default route uses the bonded interface.

Oversubscribed hosts and random slowdowns

VM hosts are usually oversubscribed: a 16-core host might sell 32 virtual cores. Most of the time that's fine. When neighbors get busy at the same moment, everyone slows down at random, and a guest OS can hardly see why. Design so the loss or slowdown of any one host doesn't matter: avoid protocols that need every node to reply, "special" nodes like lock managers that can't fail over, and hidden dependence on ordering.

Don't trust the clock

Programmers assume the clock is monotonic: it may repeat, but never go backward. Not even true on physical machines; much worse on VMs, which can be paused for any length of real time or moved to a host whose clock is skewed. Syncing the guest with the host on wake-up makes the clock jump even more. For human time, use an external source such as a local NTP server; for measuring durations, use a monotonic timer.

Designing for containers

Containers promise VM-like isolation with a developer-friendly build: "never ask again if production matches QA". But each container has a short-lived identity and little local storage, and networking is the hardest part (overlay networks, VLANs and VXLANs managed by software switches, with a scheduler such as Kubernetes, Mesos or Swarm placing containers). What should live inside the image? Sort the items.

In the image, or supplied at start?

Container rules of thumbInject credentials and config at start (look into password vaults). No hostnames or ports baked in. Start in about a second; long cache warm-ups don't belong here. Ship logs and metrics out to a collector, because debugging inside a container is hard.

8

Virtual machines in the cloud

A single cloud VM is less available than a single well-run physical machine: more moving parts, killed or restarted by the provider's control plane, sharing a host. Identity is ephemeral too; the IP address changes on each boot, and fixed addresses are limited. So VMs must volunteer for work: a new instance starts and joins the pool behind a load balancer or as a competing consumer on a queue, instead of a controller handing out work to known machines. Add a second NIC for monitoring and management, and reach servers through a single logged bastion host rather than exposing SSH everywhere.
