Case Study: The Exception That Grounded an Airline

A routine database failover, one unclosed statement in a lookup service, and an airline's check-in kiosks went dark. The story is small; the lesson about how cracks spread is not.

1

A textbook high-availability system

The airline was moving to shared services. Its "core facilities" service (CF) answered flight searches for the self-service check-in kiosks, the phone system (IVR) and the feeds to travel-booking partners. Gate agent and call center apps were scheduled to move onto CF later, which turned out to be lucky. CF was built to be bulletproof: a cluster of app servers behind redundant load balancers, a clustered database with a virtual IP address, redundant everything, even a second site. Tap a box to see its role.

2

A routine change, then darkness

The change itself went perfectly. Two hours after everyone signed off, every kiosk in the country went red, then the phone system. Follow the night.

23:00Planned database failover from DB 1 to DB 2 for maintenance, then back again. Cluster software moves the virtual IP in about a minute.
00:30Monitoring stays green throughout. Change marked "Completed, Success". The engineer goes to bed after a 22-hour shift.
02:30All check-in kiosks go red at once, nationwide. Minutes later, the IVR servers follow. It is 5:30 a.m. on the East Coast: peak check-in.
02:35Severity 1 call. Scripted thread dumps and database snapshots are taken right away (no improvising).
~03:30Monitoring says CF is fine, but it only checks a status page. CF is the one shared dependency, so the team restarts CF servers. IVR recovers. Kiosks stay red.
~05:40On a hunch, the kiosk app servers are restarted too. All green. A little over three hours in total.
Restore service firstInvestigation comes second, unless data can be gathered without lengthening the outage. Pre-built scripts that capture thread dumps and snapshots strike that balance. "Reboot the world" works but is slow; like a doctor, look for the one culprit the symptoms point to.
3

Three hours, a whole day of damage

The outage lasted three hours, but the airline could not check in passengers by hand fast enough. Off-shift agents were called in on overtime and only cleared the backlog by mid-afternoon. Planes could not leave gates, incoming flights were moved to other gates, the delays made national TV, and on-time numbers that feed the regulator's report card (and the CEO's bonus) suffered. 4

Read the thread dumps like a detective

A postmortem is a murder mystery with no body: the servers are back up, so the failed state is gone. What survives are logs, configs and, best of all, thread dumps, which show what every thread was doing. The cluster configuration was textbook. Then the dumps. Tap the line in each that gives the game away.

Pick the most suspicious frame.

Two quiet villainsThe kiosks called CF over a remote-procedure mechanism that offered no timeout, so a hung CF meant hung callers. And CF's health page ran on a separate HTTP thread pool that stayed idle and happy while every worker thread was stuck.
5

The smoking gun: one unhandled exception

The lookup method looked careful: get a connection, create a statement, and close both in a finally block. The flaw: closing a statement is allowed to throw. After a failover, every pooled connection points at a dead TCP socket. The driver still happily creates statements, but closing one throws, so the line that closes the connection never runs. Here is the same shape in sketch form:

// leaky: if stmt.close() throws,
// conn.close() is skipped forever
try {
  conn = pool.get();
  stmt = conn.statement();
  return lookup(stmt);
} finally {
  if (stmt) stmt.close();  // may throw!
  if (conn) conn.close();
}
// safe: each resource closed on its own,
// failures in one don't skip the other
try (var conn = pool.get();
     var stmt = conn.statement()) {
  return lookup(stmt);
}
// or: close each in its own try/catch,
// and log what failed

Now run it. The pool has 40 connections, like CF's. Before the failover, calls borrow and return connections. After it, each call leaks one.

6

An ounce of prevention?

"This must never happen again." But how? A code review would only catch it if a reviewer knew the driver's internals. A stress test reproduced it easily once people knew where to look. The honest answer is that bugs like this will always exist. The better question: how do we stop a bug in one system from taking down everything else? Which of these defenses would have contained it?
