Handling Versions

Every API you publish is a promise. Change it carelessly and you break people you have never met. How to evolve interfaces safely, and how to consume other people's APIs defensively.

1

Your release should not become their project

Once you can deploy easily and often, you can also change your API easily and often, and that is where the trouble starts. Every consuming application has its own team and its own schedule. If a release of yours forces three other teams to scramble, something is wrong. The chapter's stance: absorb the compatibility cost yourself rather than pushing migration work onto everyone downstream. Coordinated releases don't scale; follow the ripple far enough and the whole company has to upgrade on the same night. So most new versions should simply be compatible.

The ripple of a breaking release

2

An API is a stack of agreements

Postel's robustness principle from the TCP spec says, roughly, be "conservative in what you do, be liberal in what you accept". To apply it, first notice that an "API" is many agreements piled up. IP, TCP, UDP and DNS are shared ground (don't expect multicast to cross networks). Above that, in layer 7, consumer and provider must also agree on the items below. Tap a layer.

"We speak HTTP" is not a contract.HTTP/1.1 alone spans five RFCs. How many clients handle 101 Switching Protocols, or know Transfer-Encoding from Content-Encoding? Real services accept a subset: some verbs, some content types, a few status codes, maybe conditional requests, probably broken range requests.
3

Safe changes and breaking changes

With the stack view, a breaking change is any one-sided break from an earlier agreement. The rule is asymmetric: on the way in you may accept more and require less; on the way out you may return more but never less. (Think covariant requests and contravariant responses, or Liskov substitution.) Rich Hickey's framing in sets: it's always safe to require a subset of the required parameters, accept a superset of the accepted ones, return a superset of the returned values, and enforce a subset of the constraints. Classify each change, then check.

The same applies to accidental behaviour: an edge case that happens to work, an empty collection instead of an absent one. You never meant to support it, but once callers depend on it, a new version cannot reject what the old one accepted. Do still publish formats (Swagger/OpenAPI, say): consumers can code to the spec, and generated tests can push at its edges to find two gaps: between the spec and what you think it says, and between the spec and what the code does.

Three kinds of test across a boundary

  
Generative, randomized tests are the tool of choice here. Pick a style to see who owns the test and what it points at.

  

    

    

    

  

  
A story from the chapter. Two teams in different places negotiated a shared data format. The consuming team wrote FIT tests for every case in the spec and ran them against the provider's staging system. Almost all of them failed on the first run, which is when the spec finally got specific. Once they passed, the production rollout was smooth and the integration had no operational failures for a year. The author doubts it would have gone as well if the implementing team had written the tests.






  
6
When a breaking change is unavoidable

  
First, the cheap step: put a version number in the message format itself (not your app's version). Consumers usually speak one version, so it's mainly a debugging aid. Then comes the hard part. The running example is a peer-to-peer lending service with routes such as POST /applications, GET /applications/:id, POST /borrower and PUT /borrower/:id. New requirements arrive: a richer, multi-language, multi-currency loan representation, and the discovery that one legal entity can be both borrower and lender, each in certain countries. So the responses change shape and /borrower needs replacing with something more general. HTTP offers four options, "none are beautiful".

  

    

    

    

  

  
The author usually picks the URL. The URL alone is enough for a client, and caches, proxies and load balancers already route on URL patterns without any error-prone setup. That matters most when v2 also means a new language or framework running on its own cluster.

  
Whatever you choose
    
    
      
  • Run old and new side by side (zero-downtime deploy, of course) so consumers upgrade when they can.
    • 
      
  • Test mixed calls on the same entities: things created through v2 often blow up when read through v1.
    • 
      
  • If the version is in the URL, bump every route together, even if only one changed.

One business core, two API dialects

  
Copying all the v1 code to serve v2 is the wrong move. The preferred place to bridge versions is the controller: v2 handlers call the current business logic directly; v1 handlers convert old request objects up to current ones, and convert current responses back down to the old shape. 8
Handle others' versions: assume nothing

  
You control your outputs; you control nothing about what arrives. Even with a mapping library, about all you can count on is that fields have the right syntactic type, and with raw JSON not even that (the book suggests washing your hands afterwards). Banks now want in on the lending service: better rates for good credit, but only for some loan categories, and one wants to avoid mobile homes in Tornado Alley. So you add creditScore to the requester, collateralCategory to the loan, and a new allowed value in riskAdjustments. Callers may send all, some or none of these. Tick what a request contains.

  

    

      
      
      
    

    

  

  
Providers can change under you too: they may not follow the safety rules above, so a request that worked a second ago can fail now. Stay cynical, and keep the stability patterns between you and them, however reliable they say their deployments are.






  
9
Don't overspecify the call: split the test

  
A common failing: the integration test builds a request, calls the real provider, and asserts on the response based on what it sent. That checks today's round trip but not that you obey the contract, nor that you can handle every response the provider is allowed to send. It's hard to provoke error responses, which leads to "always throw when I pass this" flags that sooner or later leak into production. Compare the two styles.

  

    

    

    

  

  
Wrapping up. Versioning sits where your software meets the outside world, so it stays messy. The recommended attitude is utilitarian: think globally, act locally. The alternative is an organization that grinds to a halt, each release waiting for synchronized upgrades of its clients.
