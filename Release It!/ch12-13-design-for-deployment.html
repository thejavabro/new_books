Design for Deployment

A deployment that takes a whole night and a war room is a design problem. After a painful case study, the chapter shows how to make deployments automated, continuous and invisible to users.

Case study: Waiting for Godot (chapter 12)

1:17 a.m. A war room of twenty people bowed over laptops, twenty more on conference lines from four countries, all following a row-by-row playbook that took days of meetings to update. The playbook's own clock is stuck at 11:50 p.m., because a SQL script failed and a DBA "fixed" it by running it as a different user. Business stakeholders went to bed at 4 p.m. so they could wake for a 1 to 3 a.m. acceptance test. People watch a graph because, years ago in another release, it went the wrong way. There's a playbook row for the "B team" to go home and sleep, because fatigue once caused an operator error.

The author's job was one script: update symlinks, precompile pages, start servers. Napkin math: about forty people for a day at roughly $100 an hour, plus some lost sales, is about $100,000 per deployment, four to six times a year. In the end the release failed acceptance (QA's data didn't match production's, which had extra third-party script content) and was rolled back around 5 a.m., with a second attempt two days later. Years later, the author watched a visiting investor at Etsy push a single button to deploy, and felt both elation and a deep sense of wasted human potential.

The fallacy of planned downtime

Version 1.0 is the start of a system's life, so expect many deployments, not a few. "Planned downtime" is a fiction: nobody tells users the plan, and to them, downtime is downtime. We usually design for the state after a release, as if the system jumps there instantly. But users live through the "during". Treat deployment as a feature, with three concerns: automation, orchestration and zero downtime.

3

Automated deployments: the build funnel

A build pipeline is CI that keeps going all the way to production. Each stage is looking for a reason to reject the build, so it's really a funnel. Don't hunt for the best tool; pick one that's good enough and get good at it. Push builds through.

Convergence ("pets")Scripts compare the machine's current state with a declared desired state and work out the steps, in dependency order. Common with physical hosts and long-lived VMs, roles often assigned by hand. Risk: states the tool can't repair, and settings it never knew about.
Immutable ("cattle")The pipeline builds a complete VM or container image; any extra config is injected at launch. Always start from a known state; replace instead of repair. Pairs with platforms that place "service X, Y replicas" automatically.
4

Continuous deployment: if it hurts, do it more often

Between commit and production, code is pure liability: unfinished inventory with unknown bugs. A vicious cycle makes it worse: longer delay → bigger batch → more risk → more review steps → longer delay. Break it by doing everything continuously. Whether the last step is automatic or a human "go" depends on whether moving slowly or making an error costs more (and someone must be able to press it at 2 a.m.).

Phases of a deployment

Deployment grain ranges from copying a PHP file (instant) to a huge application archive with a long restart, to a whole VM image (slowest). Each machine goes through four timed steps nested inside the overall rollout. Don't plan a 30-minute rolling window if each machine needs 60 minutes. Tap each phase.

Relational schemas: expand, roll out, contract

Schema changes are the classic excuse for downtime. With a migrations framework, split every change into an expansion applied before rollout (things the old code won't notice) and a contraction applied after (things the old code would choke on). Sort these.

Shims bridge old and newSplitting a table? During rollout, old instances write the old table and new ones the new. Triggers ("shims") copy inserts, updates and deletes across in both directions (avoid infinite loops). Half a dozen shims per change is the price of batching changes. And test migrations on copies of real production data, with its decade-old NULLs and forgotten formats, not polite QA data.
7

Schemaless databases still have schemas

The database doesn't care, but your app expects a structure, and old documents can become time bombs it can no longer read. Three strategies: a translation pipeline (v1→v2→v3 readers; thorough but grows forever), a big migration during deployment (fine when small; later it takes hours, and an old instance reading a new document breaks), or trickle, then batch: new code upgrades documents as they're touched, then a batch job converts the stragglers once no old instances remain, then a later release removes the check. Run it.

8

Web assets: cache busting without breaking

Give static assets far-future cache headers, then change the URL when the content changes. Put the version (a commit hash works) in the path, so old and new sit side by side during rollout: /a5019c6f/js/login.js. Rewrite tricks that strip the version assume an instant switchover. If pages and assets come from the same servers, a new page can be balanced onto an old server that lacks the new asset; use session affinity, pre-deploy assets everywhere, or serve assets from a separate cluster.

9

Rollout and cleanup

On long-lived machines, update in batches: stop accepting work (flip the health check), drain, update, wait for green health checks, accept work. The first group is the canary: ramp traffic to it slowly and watch errors, latency and memory before continuing. New instances start with "available" false until truly ready. With immutable infrastructure, start new machines in the existing cluster (needs session stickiness) or in a new cluster and switch the address. Either way, in-memory sessions are lost, so they should only cache data kept elsewhere.

Cleanup: once everything is on the new code and monitoring is quiet, remove the shims (in a new migration), apply contractions, constraints last, delete unused documents, and review feature toggles (new ones should default to off).

Deploy like the prosMake schema changes data, not raw SQL, so the pipeline can enforce rules such as "every foreign key has an index". Have humans define the rules and machines enforce them. Designing for deployment lets you make big changes in small, safe steps.
