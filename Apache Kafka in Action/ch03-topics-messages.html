Topics and Messages

Topics organize data like tables in a database, and messages are the rows. What goes into a message, which kind of message it is, and how it is encoded decide how useful the stream will be.

Reading a topic description

A topic is rarely used only by the person who created it, so everyone needs to read its settings. kafka-topics.sh --describe prints one header line (topic ID, partition count, replication factor, non-default configs) and one line per partition saying which broker is the leader, which brokers hold replicas, which replicas are in sync (ISR), and which are eligible to become leader (ELR). Change the settings and watch both the output and the brokers.

2

Four kinds of message

Kafka does not care what a message means, but you should. In practice four kinds show up, usually mixed in one system: states (the full current picture of an object), deltas (only what changed), events (what happened, with context) and commands (please do this). Sort the messages below.

3

Bytes in, bytes out: choosing a format

Inside Kafka every key and value is just a byte array. Kafka never parses them, which is one reason it is fast. Two consequences: anything can go in (as long as messages stay small; the default limit is 1 MB and Kafka is tuned for very many small messages, not file transfer), and the meaning of those bytes is entirely a contract between producers and consumers.

Consistency beats clevernessThe authors' advice: picking one format for the whole cluster, and documenting it with a schema (Avro schema, Protobuf definition, JSON Schema, XSD), matters more than which format wins. Almost every topic gets read by a human at some point, which is easier with text, but binary formats save a lot of space.

5

Keys keep related messages in order

Kafka only guarantees order inside one partition. Without a key, messages are spread round-robin, so "coffee pads 10" might be read after "coffee pads 11" and the shop would show a stale price. With a key, all messages with the same key land in the same partition and stay in order. Messages for different keys can still interleave, which is usually fine.

One possible read order (consumer reads partitions in parallel)

# producer: treat text before ":" as the key
kafka-console-producer.sh --topic shop.prices.keyed --bootstrap-server localhost:9092 \
  --property parse.key=true --property key.separator=:
> tea:4
# consumer: show keys too (keys are hidden by default)
kafka-console-consumer.sh --topic shop.prices.keyed --from-beginning --bootstrap-server localhost:9092 \
  --property print.key=true --property key.separator=:

Key handling is a client setting. The topic itself knows nothing about keys; any topic can hold keyed or unkeyed messages.

TopicsCreated, described, altered and deleted with kafka-topics.sh. Names with a leading double underscore are reserved for Kafka.
Partitions only growYou can add partitions but never remove them. Changing the replication factor needs a reassignment.
Four message typesStates, deltas, events, commands. Commands couple sender and receiver most.
Bytes and schemasKafka stores byte arrays; pick one format and document it with schemas.
RecordTimestamp, optional key, value, optional headers (technical metadata only).
KeysSame key, same partition, same order.
