The problem Kafka solves

Customers now expect things to happen in real time: the card payment confirmed at once, the parcel tracked live, the fraud alert now rather than tomorrow. Old systems were built for nightly batches, and as companies break monoliths into many services, the number of things that must talk to each other explodes. Wire every system directly to every other and you get a tangle that nobody dares to change.

Kafka's answer is a central nervous system for data: every meaningful event in the company is written once to Kafka, kept there, and any system that cares reads it at its own pace. Drag the slider to see why a hub beats point-to-point links.

What it takes to run it

Kafka runs on ordinary servers. It does not need special appliances or fail-safe hardware because it expects parts to fail and copes. What you do need:

Servers as brokersSeveral machines that each run a broker on a Java runtime (Kafka is written in Java and Scala).
A good networkLow latency and high bandwidth between brokers, because they copy data to each other all the time.
Designed topics and clientsThought-through topics and partitions, plus well-built producers and consumers in Java, Python or any language with a client.
Self-managed or managed?Cloud providers and specialist vendors sell Kafka as a service, and some products speak the Kafka protocol with their own engine underneath. A managed service removes server work, not the need to understand Kafka: the team still has to design topics, clients and data flows well.

Chapter 2: the first produce and consume loop

The book's running example is an online shop. The product system records every price change in a topic called products.prices.changelog. Names follow a common convention: lowercase words separated by dots. Kafka ships with shell scripts for everything here: kafka-topics.sh manages topics, kafka-console-producer.sh writes one message per line typed, and kafka-console-consumer.sh prints what it reads.

Try the loop below. Notice two surprises from the chapter: a fresh consumer shows nothing until you ask for --from-beginning, and a second consumer sees everything again because reading does not remove anything.

# create a topic with one partition and no copies (fine for a laptop)
kafka-topics.sh --create --topic shop.demo --partitions 1 \
  --replication-factor 1 --bootstrap-server localhost:9092
# each line becomes one message
printf 'tea 4\n' | kafka-console-producer.sh --topic shop.demo --bootstrap-server localhost:9092
# read from the start instead of only new messages
kafka-console-consumer.sh --topic shop.demo --from-beginning --bootstrap-server localhost:9092
GUIs are for looking, not for writingTools such as Kafbat UI or Kadeck show topics, partitions, consumer groups and individual messages, which is great for troubleshooting. The authors warn against producing data or changing configuration through a GUI in production: Kafka is for systems talking to systems. People should write to production topics only as admins in an emergency.

Recap and quick check

Persistent logData stays after it is read (7 days by default, or forever), so consumers can replay and new systems can read history.
Producers and consumersProducers write to topics; consumers read independently of each other and of the producers.
Partitions and brokersTopics split into partitions spread over brokers; each partition has a leader and followers.
CoordinationKRaft (formerly ZooKeeper) keeps track of brokers and metadata.
Scale outAdd brokers to grow; it runs on commodity hardware.
Command-line toolskafka-topics.sh, kafka-console-producer.sh, kafka-console-consumer.sh.
