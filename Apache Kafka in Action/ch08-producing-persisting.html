What happens after produce()

Use the official Java client or a librdkafka-based one; other libraries often miss features and optimisations. Whatever the language, calling produce() (or send()) starts the same pipeline, and the library does most of it for you. Step through one record.

from confluent_kafka import Producer
p = Producer({"bootstrap.servers": "localhost:9092", "acks": "all",
              "enable.idempotence": True, "partitioner": "murmur2_random"})
def report(err, msg):
    print("failed:" if err else "stored at", err or f"{msg.partition()}/{msg.offset()}")
p.produce("shop.prices", key="tea", value="4", on_delivery=report)
p.flush()   # wait for outstanding callbacks
2

Five timeouts, one deadline

The producer has several clocks. max.block.ms (60 s) limits how long produce() blocks when the 32 MiB buffer.memory is full. linger.ms waits to fill batches. request.timeout.ms (30 s) waits for each response, then retry.backoff.ms (100 ms) before the retry. Over all of them sits delivery.timeout.ms (2 min): after that the library gives up and raises an error. Simulate a broker outage:

When the exception comes, don't just resendThe cluster is probably in trouble. The library's own retries already preserve order (with idempotence). Handle the failure with a pattern such as a circuit breaker instead of hammering the brokers.

Inside the broker: queues, page cache, purgatory

A broker's job on a produce request sounds small: receive, check permissions, append, wait for followers, answer. Doing it fast takes a pipeline of thread pools.

Segments and the sparse index

A topic splits into partitions, and each partition splits into segments: a .log file of batches plus an .index (offset to byte position) and a .timeindex (timestamp to offset). Each file is named after the first offset in it. A new segment starts when the active one reaches segment.bytes (1 GiB) or segment.ms (7 days). 6

The leader epoch stops zombie leaders

Each partition directory has a leader-epoch-checkpoint. The epoch goes up by one with every leader change and travels with replication traffic. A broker that missed the change still believes it leads, but its stale epoch gives it away.

7

LEO, high watermark and in-sync replicas

Followers fetch every 500 ms (replica.fetch.wait.max.ms) and report their log end offset (LEO). A follower stays in sync if it caught up to the leader's LEO within replica.lag.time.max.ms (30 s) and keeps sending heartbeats. The high watermark is the smallest LEO among the in-sync replicas: everything below it is committed, and only that is visible to consumers. Drive it:
