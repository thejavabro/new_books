Kafka is not the only way to move data. Comparing it with classic message brokers, synchronous REST calls and relational databases shows where each one fits.

1

No cure-alls

When is Kafka the right choice? It depends on the use case, the non-functional requirements, the existing landscape, and above all on the people who must adopt it. The same use case can deserve different answers in different companies. This chapter compares Kafka with classic messaging, REST and relational databases, and ends with the bigger picture: Kafka as the core of a streaming platform.

2

Data on the inside, data on the outside

Pat Helland's paper Data on the Outside vs. Data on the Inside draws a useful line. Inside data belongs to one service: stored in whatever shape suits it, often read and written synchronously by users with strong consistency, and tightly coupled to the service's code. Outside data is what services exchange: service-agnostic, ideally immutable (someone may already have consumed it), loosely coupled, able to evolve separately from internal models, and carried by a system that must be resilient and fast. Smart pipes, dumb pipes

Classic messaging systems and enterprise service buses (SAP PI, Seeburger BIS, BizTalk…) are smart pipes: they route messages across sites and divisions, convert formats (JSON, XML, IDocs), enforce data protection, and push messages to consumers, deleting them once read. Services stay simple. Kafka is a dumb pipe with smart endpoints: it stores data in logs, and the clients decide what to read and when. Governance differs too. An ESB is usually run by a central team that owns all configuration and transformation logic, and changes can take weeks or months. With Kafka, a center of excellence publishes conventions, teams manage their own topics, users and schemas through automated processes (chapter 14), and format mapping is decentralized. Classic messaging still has its place: IBM MQ next to Kafka in large enterprises, MQTT for IoT, or linking core systems such as SAP ERP to production control. Some call it messaging for the "old world", Kafka for the "new", though Kafka keeps moving into old-world territory.

REST and the distributed monolith

HTTP/REST is easy to start with and works everywhere; the same API can serve the frontend and other services. But synchronous calls create temporal coupling: to answer a request, a service needs other services to be up right now, and they need others in turn. That recreates the monolith's entanglement and adds distributed-system failure modes. Fail a service and compare:

Caching other services' data helps only if you learn about changes, which is exactly what events provide. With asynchronous events, services precompute what they need when something happens and answer quickly. The costs: extra infrastructure and expertise, two APIs per service (internal and external), and no central place for ad-hoc SQL (Flink SQL is improving; usually data also flows into a lake or warehouse). For small teams, it may not pay off; for many interacting teams it usually does. Synchronous calls remain right for some real-time cases such as games or trading.

5

"What is?" versus "What was?"

The authors love relational databases (PostgreSQL sits at the center of their own projects). A database answers "What is the current state?" brilliantly, with SQL and strong guarantees: perfect for inside data. Shared by many services without clear ownership, though, it becomes a house of cards nobody dares touch. Kafka answers "What was? How did we get here?": the history, from which every service can derive the state it needs. Replay the log:

    Databases are logs inside too: the commit log records changes before tables, indexes and materialized views are updated, and drives replication and crash recovery. Kafka topics are such logs, turned outward. Martin Kleppmann calls it turning the database inside out: the log is central, and tables, indexes and views are built in a distributed way by the services, with whatever technology fits (OpenSearch for search, Redis for a hot cache, PostgreSQL for ad-hoc queries, or just a Kafka Streams state store). Kafka Connect links existing databases with little configuration.

    Kafka as the core of a streaming platform

    Calling Kafka "a messaging system" or "a distributed log" undersells it. The authors see it as the core of a streaming platform, a central nervous system for data: whenever something happens, an event lands in the log and anyone can react now or later instead of waiting for tomorrow's batch.
