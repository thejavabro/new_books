What goes wrong without governance

Once many teams share a Kafka cluster, three kinds of oversight become necessary. Without schema management, one producer adds or renames a field and consumers downstream break. Without security, anyone on the network can read payment data or write junk into a topic. Without resource limits, one runaway client can starve everyone else. Tap a pillar:

2

Every piece of data has a schema

Even "schemaless" data has a schema: the one consumers silently assume. If the data doesn't match, the best case is a crash; the worst case is wrong numbers computed silently. A schema is the contract between producer (usually the data owner) and consumer. Unlike a relational database, Kafka can't migrate old data atomically: messages linger in topics, several versions coexist, and sometimes several producers write different versions at the same time. Document every topic's schema somewhere central (wiki, Git repo or a dedicated platform), along with its compatibility level.

Compatibility is easiest to reason about from the consumer's side. Evolve the product schema below and see which levels the change still satisfies:

Breaking change needed? Create a new topic, migrate the old data, then move producers and consumers, the same procedure as changing a topic's partition count.

3

Schema registries and Avro

Kafka only sees bytes, so it can't enforce any of this. A schema registry stores and versions schemas, checks new versions against the compatibility rule, and plugs into the client serializers. Its downsides: one more critical component (if it's down, producers and consumers may be stuck), awkward multi-cluster setups, and meaningless sequential IDs that can change when schemas are exported and re-imported elsewhere.

Registries were born for Avro, a binary format whose messages are self-describing: schema plus payload. Great for long-lived topics with several versions, but heavy. In the book's example the binary payload is 35 bytes and the JSON schema 292 bytes. The registry fixes this: send just a reference to the schema.

Validation happens only in the clients, so a buggy or malicious producer could still write non-conforming bytes. Options: let only the owning team write (single producer pattern), broker-side validation (Confluent Server/Cloud only), or a validating proxy (Conduktor, or the open source Kroxylicious). And in production, don't let producers auto-register new versions: register schemas through your deployment pipeline.

Transport encryption and authentication

TLS is close to mandatory today, even on internal networks. Each broker gets a key pair signed by a central CA, stored in a keystore; clients (and brokers, to trust each other) get a truststore holding the CA's public key. A broker can run several listeners side by side, which is what makes a later migration possible. The cost is configuration effort and some CPU; where CPU is not the bottleneck the loss is minimal, otherwise test first.

listeners=PLAINTEXT://$IP:9092,SSL://$IP:9093
listener.security.protocol.map=PLAINTEXT:PLAINTEXT,SSL:SSL
ssl.keystore.location=/certs/broker.ks.p12      # this broker's private key
ssl.truststore.location=/certs/ca.truststore.p12  # whom to trust

Authentication happens once, when the connection is set up, and holds for the whole session; so if a client is compromised, deleting the user isn't enough, revoke its permissions too. Unauthenticated clients appear as User:ANONYMOUS.

Authorization with ACLs

Each ACL reads as a sentence: principal P is Allowed/Denied operation O on resource R (literal name or prefix), from host H. The authorizer checks in a fixed order: super user? then any matching Deny? then any matching Allow? Otherwise the request is refused. Follow least privilege.     Encryption at rest and end to end

    Kafka has no native encryption at rest. Use the disk encryption of the OS, storage or cloud: cheap, and it protects removed disks, but anyone with admin access to the running system still reads everything. So data in Kafka is usually classed as internal/confidential. For highly sensitive data you need end-to-end encryption in the clients.

    Encrypt after you compress? You can't usefully compress after encrypting: good ciphertext looks random. Key management is a whole process of its own; tools like Vault help.

    Securing a cluster that started insecure

    A proof of concept that slid into production is a classic. Thanks to multiple listeners, Kafka can be secured without downtime, but it takes coordination. (On ZooKeeper-based clusters, also secure ZooKeeper: TLS is supported since Kafka 2.5, mutual TLS recommended, and watch its latency.)

    Quotas protect the cluster

    Quotas are about fairness and about protecting everyone from a misconfigured client. Set them per user principal (client IDs can be faked), with a conservative default and overrides. They limit bytes per second for produce or fetch, or the share of broker thread time (request_percentage). Enforcement is per broker, so a client talking to more brokers can move more in total: quotas are guardrails, not billing.

    CPU quota capacity per broker 

    # default for everyone: 1 MB/s produce, 2 MB/s fetch
kafka-configs.sh --bootstrap-server localhost:9092 --alter --entity-type clients --entity-default \
  --add-config 'producer_byte_rate=1048576,consumer_byte_rate=2097152,request_percentage=100'
# the warehouse system gets more
kafka-configs.sh --bootstrap-server localhost:9092 --alter --entity-type users --entity-name warehouse \
  --add-config 'consumer_byte_rate=5242880,request_percentage=200'

    Monitor first. Brokers expose Produce, Fetch and Request throttle-time metrics; they should be zero. Too-tight quotas make send() block once the buffer fills, then time out, and failures cascade. Without monitoring, don't introduce quotas.
