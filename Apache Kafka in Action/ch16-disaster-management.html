Disaster Management

Networks split, disks die and whole data centers go dark. Replication covers most of it; for the rest there are stretched clusters, mirrored clusters and a very careful look at backups.

What could possibly go wrong?

Outages cost money, customers, compliance and reputation. Kafka is distributed, so many things can fail: the network, the machines, the storage, a whole data center, and, very often, people (misconfiguration, botched maintenance, missing procedures). Knowing which failures are likely and which are critical lets you spend effort where it counts. Click a failure point:

Network failures: mostly, wait

Network trouble is near-certain in a distributed system, and Kafka can do little but wait. Because data is persisted and offsets let clients resume, it rarely causes loss. Consumers simply continue afterwards. Producers must decide what to do meanwhile; that's a design choice for the developers. Cut the network and watch:

Inter-broker network problems are nastier: needless leader elections, replicas dropping out of the ISR, controller trouble. Again the main remedy is restoring connectivity, which is why good monitoring, redundant networks and a good relationship with the network team matter.

Storage failures: never let the disk fill up

A full volume is deceptively dangerous. Kafka hands writes to the OS page cache and lets the OS flush them; if the disk is full, data still in memory can be lost. If all brokers are configured alike, they fill up together, and the loss can be permanent. Rule: Kafka must never run out of disk; stopping it beforehand is better (if the data matters). Old admin trick: keep a 10 GB spare file to delete in an emergency.

5

Losing a data center: stretched clusters

First ask whether you need this at all: when a data center burns, Kafka is probably not your biggest problem, and off-site backups plus rebuilding may be acceptable for many companies. If you do need it, the simplest option is a stretched cluster across data centers (availability zones, within 30 ms). A data-center failure then looks like a few broker failures. But the coordination quorum needs a majority. Fail a data center:

Set broker.rack to the data center or zone so new topics spread replicas evenly (use Cruise Control for existing ones). Backing up Kafka is hard

Replication is not a backup. But first ask whether you need one: if the data can be reloaded from a source database, or only lives in Kafka for seconds, probably not ("if we ever have to restore Kafka, we're broke anyway"). Mirroring clusters with MirrorMaker 2

Mirroring copies messages continuously to another cluster, over distances replication can't handle. MirrorMaker 2 runs on Kafka Connect and copies topics, ACLs and consumer offsets with three connectors: MirrorSourceConnector (topics and ACLs), MirrorCheckpointConnector (offsets) and MirrorHeartbeatConnector (connectivity). Confluent Replicator is a proprietary alternative. Mirroring is asynchronous: the newest messages can still be lost. Choose a topology and break something:
