Kafka is more than brokers

What does it take to run Kafka well? Brokers and a coordination cluster are only the core. Around them sit the applications (producers and consumers; non-Java clients must use the same partitioner as Java ones), Kafka Connect for integration without code, stream processing, schema management, plus tools for viewing, automating and balancing. 2

kcat: a quicker command-line client

An alternative to the bundled console scripts is kcat (formerly kafkacat). It is built on the C library librdkafka instead of the JVM, so it starts instantly, which matters in scripts. Its flags are short, it can read and write headers, and it guesses the mode if you omit it. Like the console tools, it's for exploring, not for writing production data.

3

Look with a GUI, change with Git

A GUI is great for exploring: which topics exist, what's in them, the state of Connect and the schema registry. In production it should be read-only (give its user only read permissions), and it never replaces monitoring. Open source favorite: Kafbat Kafka UI (formerly Provectus Kafka UI). Commercial: Kpow, Kadeck, Conduktor Console, plus the providers' own consoles.

Changes, from pre-production on, are automated and declarative. Never create topics by hand in production. The authors prefer GitOps: a Git repository is the source of truth for topics, users and ACLs, and a pipeline applies merged changes. Most companies build their own tooling because approval processes differ; for Connect, kcctl apply -f connector.json (modeled after kubectl) helps.

4

Balancing load with Cruise Control

Brokers should carry similar numbers of partitions and leaders and, more importantly, similar CPU, memory, disk and network load. Balancing by spreadsheet doesn't scale. Cruise Control (from LinkedIn) has a metrics reporter JAR on every broker writing load samples to a topic, an analyzer that turns them plus your goals into a proposal, and an executor that moves partitions. Start manually: monitoring shows imbalance, you run the analyzer, review, execute. Avoid moves when the cluster is already at its limits: they add a lot of load.

Sizing brokers

Start with at least three brokers and grow. Focus on fast, reliable storage and on memory. Several smaller SSDs beat a few big ones; you can start small and add. Skip RAID (replication does that job), and especially avoid RAID 5 and 6. Since Kafka 3.9, tiered storage can offload old segments to cheap object storage. The heap needs 1 GB at least and rarely more than 6 GB; the rest of RAM is page cache, sized by how far consumers may lag without touching the disk:

8

Keep brokers apart, but not too far apart

Kafka doesn't fsync every message, so if several brokers die at once data can be lost. Never put two brokers on the same VM host, Kubernetes node (use anti-affinity) or rack; use rack awareness and spread over availability zones or fire compartments. But keep inter-broker latency under 30 ms: one cluster across cloud regions is a bad idea. For global setups, run independent regional clusters and replicate only what you must (MirrorMaker, next chapters).

The coordination cluster (KRaft controllers or ZooKeeper) is modest: 4–8 GB RAM and a decent CPU, but a good network, since ZooKeeper especially is latency-sensitive. Use an odd count: 3 nodes tolerate one failure, 5 tolerate two.
