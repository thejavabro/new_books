Kafka as a Distributed Log

Underneath everything Kafka is an append-only log. Split it into partitions, copy each partition to several brokers and let groups of consumers share the work, and you get a log that scales and survives failures.

1

A log: append at the end, read from an offset

We meet logs everywhere: system logs, application logs, and the commit log hidden deep inside every database, which records each change before the tables are touched so the database can recover or replicate. All of them answer one question: what happened? Kafka takes that structure and puts it in the middle of the architecture instead of hiding it.

Think of a diary written in pen: entries are ordered by time, new entries go at the end, you read from old to new, and what is written is immutable. A log has exactly two operations: append, and read starting from a position. That position is the offset, a page number with no meaning beyond position. The broker assigns it at write time, and consumers keep their bookmark in the internal __consumer_offsets topic so they survive restarts.

2

Replaying a log rebuilds any past state

Because the log keeps history rather than just the current state, you can rebuild the world as it was at any point by replaying entries from the start up to that point. That is how databases recover, and how a new Kafka consumer can build its own view of the data. Drag the slider through the price log.

But Kafka is not your databaseThe offset is the only way to address data in a log. There is no "give me the row for key X" without scanning. So use Kafka as the hub that moves data between systems, and let each service copy what it needs into the store that suits it: a relational database for ad hoc queries, an in-memory key-value store for fast lookups, a search engine for search.
3

Scale out, and plan for failure

Scaling vertically (a bigger server) is easy and works for a while, but a bigger server fails about as often as a small one. Scaling horizontally (more servers) adds capacity and redundancy, but now the software must coordinate: who handles which request, how to notice a dead server, how to replace it. Kafka runs on cheap commodity machines and treats failure as normal. One public data set the authors cite puts disk failure at about 1% a year. What does that mean for a fleet?

4

Partitions split the log; keys pick the partition

A single log on one server can't keep up forever. Partitioning (sharding) splits it, the way a worldwide taxi platform could keep each city's trips together without caring about order across cities. A Kafka topic is a set of partitions, each its own ordered log. With a key, the producer computes hash(key) % partitions; the Java client uses the murmur2 hash, which this page reproduces. Type keys and change the partition count.

5

Consumer groups share the work

Kafka does not push; consumers pull. A slow consumer is never overloaded, it just falls behind. To scale a service, start more instances with the same group.id. The group divides the partitions so that each partition is read by exactly one member, which keeps per-partition order. Another service uses its own group and reads everything independently.

Group "price-db" has a single consumer and reads all partitions on its own.

6

Replication: one leader, several followers

Backups are cold replication: data is safe but takes time to restore, and Kafka has no built-in backup. Kafka's replication is warm: every partition lives on several running brokers. One replica is the leader and serves all reads and writes; followers fetch from it like consumers and append to their own copy. Coordination cluster, brokers, clients

A Kafka cluster has three kinds of parts. The coordination cluster watches brokers, stores topic metadata and access rights, and picks a controller that assigns partitions and elects leaders.
