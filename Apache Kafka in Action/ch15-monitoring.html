Monitoring and Alerting

Kafka exposes hundreds of metrics. A few of them, like under-replicated partitions and consumer lag, tell you almost everything. Then alerts must lead to action, not noise.

1

Fault tolerant is not invulnerable

Kafka shrugs off a broker failure, but every broker that stays down eats into the remaining fault tolerance. Monitoring is how we notice quickly, and, just as important, how we find the cause, which is often a side effect of some other, healthy-looking system. This chapter walks from hardware up to brokers, clients and frameworks, then to alerts. (Appendix B sets up Prometheus and Grafana so you can try the metrics.)

2

Start with the machines

Without infrastructure metrics you can spend hours hunting a Kafka bug that is really a full disk. Keep disk and network below about 60%: rebalancing partitions needs extra space and bandwidth, and when a broker fails the survivors take over its traffic. Memory spare capacity becomes page cache; CPU spikes are fine, sustained high CPU is not. A single snapshot says little: watch the trend.

4

The broker dashboard

The vital signs: under-replicated partitions (should be 0; persistently above 0 means a broker is down, fluctuating means resource trouble), at-min-ISR and under-min-ISR partition counts (below min ISR, acks=all producers stop), offline replicas, offline log directories (a dead disk), the active controller (summed over brokers it must be exactly 1), fenced brokers, partition and leader counts per broker (balance), and network processor average idle (consistently under 0.3 means near overload). Pick a scenario, then diagnose a mystery one.

5

Producers and consumers

A healthy cluster is useless if clients fall behind. All clients report connection count (frequent changes on consumers often mean frequent rebalances), failed authentications, request rate and byte rates: good for spotting anomalies. Producers add record error rate (should be 0; often a batch larger than the broker's max message size, or a missing key on a compacted topic), requests in flight, produce throttle time (quotas) and request latency. For consumers, the most important figures are lag and lead:

Consumers also expose time between polls and last poll seconds ago. If processing a batch approaches max.poll.interval.ms, the group considers the consumer dead and rebalances. Watch rebalances total, failed rebalances and rebalance latency (with Kafka Streams a rebalance can take minutes; the cooperative sticky assignor lets others keep consuming), and assigned partitions (a consumer with none for a long time hints at a hidden fault).

From metrics to alerts

Not every metric deserves an alert. Binary ones (good/bad) are easy; others need smoothing and a sensible threshold. CPU can hit 100% for a second and nobody should be woken for that. Start conservative, give self-healing systems (like Kubernetes restarts) a moment, then tighten. Too many false alarms cause alert fatigue, and real alerts get ignored. Tune this CPU alert:

Metrics that make poor alerts still earn their dashboard panels. If a consumer-lag alert fires, a "produced records" panel tells you at a glance whether consumers broke or a flood of data simply arrived. What to watch where

Everywhere: watch failed authentications and unauthorized access attempts; they reveal attacks and misconfigurations alike.
