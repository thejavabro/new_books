Stream Processing

Stream processing reacts to events as they arrive: filter, transform, aggregate, join, window. Kafka Streams turns topics into a pipeline that keeps state and scales with partitions.

1

From nightly batches to one event at a time

Kafka began as a feeder for big-data batch systems such as Hadoop. But if the data is already flowing through Kafka in near real time, why wait for a 4 a.m. job? Stream processing handles each event as it arrives. The price of speed is a shift in thinking: a batch produces a final answer for a closed period, while a stream only ever has an intermediate result that may change. Stream processing is eventually consistent.

2

Processors and topologies

Frameworks like Kafka Streams and Flink are functional: you chain small reusable processors into a topology. Stateless ones look at one message at a time: filter keeps matching messages, mapValues changes the value, map changes key and value (and so forces repartitioning: prefer mapValues), split routes each message to the first matching branch, merge unions streams. The same ideas in SQL

Declarative SQL often says in three lines what takes pages of code. Flink SQL follows the SQL standard. The difference from a database: you don't create empty tables but tables backed by a topic (the data stays in Kafka), and a query doesn't return once, it keeps emitting results forever. In production, queries run headless and write back to Kafka or another system. Review their performance before going live.

CREATE TABLE price_changes (product_id INT, product_name STRING, price FLOAT, old_price FLOAT)
WITH ('connector' = 'kafka', 'topic' = 'shop.price-changes',
      'properties.bootstrap.servers' = 'localhost:9092',
      'format' = 'json', 'key.format' = 'json', 'key.fields' = 'product_id',
      'value.fields-include' = 'EXCEPT_KEY');

SELECT * FROM price_changes WHERE price > 100;                 -- a never-ending filter
SELECT product_id, COUNT(*) FROM price_changes GROUP BY product_id; -- an updating count

Streams and tables are two views of one thing

A stream of changes can be folded into a table of current values, and a table's changes can be replayed as a stream (that is what CDC does). Kafka Streams calls them KStream and KTable; Flink has DataStreams and Tables. A table here is a partitioned key-value store, usually RocksDB on local disk, backed up to a compacted changelog topic. Streaming joins are lookups

A database join can build a cross product of two finite tables. Streams are infinite, so a streaming join is a lookup: when a message arrives, find the matching key on the other side. Both sides must be co-partitioned (same partition count, same key). What triggers the join depends on the types. Send events to each side:

Use case: notify every device of a user

The user-devices topic has a message per device change; notifications has messages keyed by user. Aggregate devices into a list per user (initial state: empty list; adder: add active devices, remove inactive ones), join notifications against that table, write to device-notifications.

7

Which time? Which window?

Kafka orders messages by arrival at the leader, not by timestamp. And "the time" can mean four things: event time (when it happened; put it in a field of your data), create time (set by the producer on send, the default message.timestamp.type), log append time (set by the broker, so ascending within a partition), and stream time (when the processor handles it). Frameworks let you pick via a timestamp extractor, and a grace period decides how long to wait for late messages before ignoring them.

8

Scaling Kafka Streams: tasks, threads, instances

One task per input partition: that is the unit of parallelism. Tasks are spread over instances (via the rebalance protocol, as with consumer groups and Connect) and, inside an instance, over num.stream.threads threads, each with its own consumer and producer. Every stateful task has its own state store.
