1

The entrance to the pipeline

The commit stage begins the moment someone checks in to mainline. The CI server checks out the change and, as a set of build-script jobs, compiles it, runs the commit tests against the integrated code, creates binaries that can be deployed to any environment, runs analysis of codebase health, and prepares artifacts like database migrations or test data for later stages. For developers it is the most important feedback loop of all: it runs many times a day and tells them, within minutes, whether their change broke something.

2

Fast, useful feedback

Commit stage failures come from three causes: a syntax error (caught by compilation), a semantic error (caught by tests), or a problem with the application's configuration or environment, including the OS. Errors are cheapest to fix close to when they were made, and frequent small commits keep the search small. But "fail fast" can be overdone. If the stage stops at the first failing test, the developer fixes one thing, waits again, finds the next. Better: compile, and if that works run all the commit tests, then report everything.

3

What should break the commit stage?

Traditionally the stage fails only for compile errors, test failures or environment problems. But a green build with hundreds of warnings, falling coverage and growing duplication is not really healthy. The authors suggest the build can fail when code quality crosses agreed thresholds, and even imagine a graded result instead of pass/fail. Move the sliders and set the thresholds.

4

The artifact repository and a candidate's life

The commit stage's outputs, binaries plus reports and metadata, go into an artifact repository. It is an unusual version control system: it only needs to keep some versions, but each must be traceable back to the revision that built it, and the binaries promoted later must be the very same files. Follow a release candidate as its status accumulates.

5

Shape the suite like a pyramid

Mike Cohn's test automation pyramid: lots of fast unit tests at the base, fewer service or component tests in the middle, and very few UI-driven tests on top. Commit tests are mostly the base. The authors aim to keep the whole commit stage under ten minutes, which they treat as roughly the upper limit, with five or less being even better. Shape your suite.

The Car and Engine: stub versus mock

  
The chapter's running example: a Car receives its Engine by dependency injection, so a test can pass in a double. With a hand-written stub you write a TestEngine that records what happened. With a mocking library you declare expectations and let the tool verify them. Mocks mean far less code; the risk is coupling tests to implementation details.

  

    
// stub: hand-written
class TestEngine implements Engine {
  started = false; stopped = false
  start() { started = true }
  stop()  { stopped = true }
}
engine = new TestEngine()
car = new Car(engine)
car.drive()
assert engine.started && engine.stopped

    
// mock: generated, expectations first
engine = mock(Engine)
inOrder(engine) {
  expect(engine.start()).once()
  expect(engine.stop()).once()
}
car = new Car(engine)
car.drive()
verify(engine)

  

  
Stubbing big subsystemsDave once worked on a trading system that talked, in complex ways, to a messaging-based external system. A stub simulating that live system let the team test interactions on developer machines and in the commit stage, instead of maintaining a fragile web of real distributed systems.
