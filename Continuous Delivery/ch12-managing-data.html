Managing Data

Data outlives code and cannot simply be redeployed. Versioned migrations, decoupled releases and careful test data let databases keep pace with the pipeline.

1

Why data needs its own chapter

When you deploy new code you can throw away the old version. Data doesn't work like that: it is the most valuable part of most systems, it lives far longer than any version of the code, and its schema must evolve as the application does. So the same principles apply (automate everything, keep it in version control, test it) but the mechanics differ. This chapter covers database scripting, incremental migration, rolling back without losing data, and managing test data at each pipeline stage. It focuses on relational databases, though the ideas carry over.

2

Initialize databases from version control

Every change to a database is made by a script in version control, and those scripts run in CI. The simplest case, which you need from day one, is creating a database from scratch: erase what was there, create the structure (instances, schemas, tables), and load the data the application needs to start. Developers, testers and the pipeline should all be able to do this with one command.

3

Version your database

The heart of the chapter. Number each change script. Store the current version in a table in the database. At deploy time a tool (the book mentions DbDeploy, and Rails ActiveRecord migrations) runs the scripts between the current and target versions: forward to upgrade, and through each script's undo section to roll back. Pick a target version.

schema_version table1
-- 0002_add_date_of_birth.sql  (illustrative)
ALTER TABLE customer ADD date_of_birth DATE;

--//@UNDO
ALTER TABLE customer DROP COLUMN date_of_birth;

Roll-back scripts are easy when the change adds structure. When it destroys data (dropping a column), copy the data into a temporary table first so the undo can restore it. The book recommends Ambler and Sadalage's Refactoring Databases for the patterns.

4

Orchestrated changes and technical debt

Many organizations integrate applications through one shared database. Then changing a table can break apps you have never heard of. Mitigations from the chapter: keep a registry of which applications use which database objects (you can generate it from each app's code during the build), test changes against the other applications that depend on the database, and coordinate releases with their teams.

Databases are where technical debt piles up most. Ward Cunningham's metaphor applies: every suboptimal design choice is a loan with interest paid on each later change. Because schemas are hard to change, it is tempting to stop changing them, and the debt grows. Versioned migrations make paying it down practical.

5

Rolling back without losing data

In test environments, roll-back scripts are enough. In production there are two extra requirements: don't lose the data users created since the release, and keep the service up. Simple undo scripts are fine when the change loses no data, or only data the old version doesn't need. They are not enough when rolling back means restoring from temporary tables with integrity concerns, or deleting new transactions you can't afford to lose. Pick a strategy for each situation.

6

Decouple application deployment from database migration

The third approach, and the one the authors recommend as the default. Make each application version work with both the current and the next database version, so the two can be released separately. Deploy the app first; migrate the database later; roll either back on its own. Move the sliders to check which combinations are safe.

Another option: put an abstraction layer, such as views or stored procedures, between applications and tables, so table structure can change behind a stable interface.

7

Managing test data

Two concerns: performance (tests that touch big databases are slow) and isolation (a test must know the state it starts from). For unit tests, don't use a real database at all: put data access behind a repository interface and use an in-memory double. For suites, there are three strategies, and the authors strongly prefer the first.

Isolation with a transaction

Start a transaction, run the test, roll it back. The database ends exactly where it began.

Resist the "coherent story"It is tempting to chain tests into one narrative: create a customer, then the next test places an order for them, and so on. It saves setup, but one failure cascades through everything after it, and you can't run tests in isolation or in parallel. Real users don't follow one story either.
