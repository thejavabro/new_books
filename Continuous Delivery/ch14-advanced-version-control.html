Three good reasons to branch

Version control lets many people work on one codebase. Branching and merging is the most contentious topic in it, because branches defer integration, and continuous integration is about not deferring it. The authors accept exactly three good reasons to branch; everything else needs a strong case.

ReleaseA branch for a released version. Fixes go in there and are applied to mainline; the release branch is never merged back.
SpikeTo try out a feature or refactoring. The branch is thrown away, never merged.
Rare big changeA short-lived branch for a large change that can't be done incrementally or by abstraction. Its only aim is to get back to mainline fast.

Switch off pessimistic locking

Pessimistic systems make you lock a file before editing; nobody else can change it until you check in. Optimistic systems let everyone edit and merge at check-in, which almost always works automatically. Fears that optimistic locking causes chaos are unfounded in practice. Pessimistic locking also pushes teams into owning files by component, and it makes broad refactorings nearly impossible. The only good use is for binary files like images. 4

Branches are easy; merging is hard

Branches are like parallel universes: cheap to create, but bringing them back together is where the pain is. Textual conflicts are the easy part. Semantic conflicts, such as one branch renaming a method while another adds a call to it, slip past the merge tool and break the build, or worse, behaviour. The longer branches live and the more of them there are, the worse it gets. Try it.

Horror story #1A large network infrastructure provider had a branch for every major customer, plus sub-branches for each bugfix and feature, with four-part version numbers to match. A major release took 12 to 24 months. Worse, the tests lived in a separate repository from the code, so nobody could tell which tests applied to which build, which stopped them adding tests at all. Define a policy for every branch: its role, and who may commit to it.

6

Distributed version control

In a DVCS each user has a complete repository. You can start in seconds, commit offline, pull from or push to any other user, reorder and batch commits before sharing, and try ideas locally. History began with the Linux kernel: patches by email, then BitKeeper from 1999 (for kernel work from 2002), then Git and Mercurial when BitKeeper's free licence was withdrawn. Hosts like GitHub turned forking and pull requests into a new way to collaborate.

Corporate worries (no single canonical copy, slippery auditing, Git letting you rewrite history) are manageable by designating a central repository and policies. The catch for CI: until you push to the shared repository, you are not integrating. A DVCS makes it easy to sit on changes. Push often.

7
Stream-based version control

  
ClearCase and AccuRev organise work into streams that inherit from parent streams. A change promoted to a parent flows down to every child stream automatically, which makes it easy to apply a fix to several releases at once or to roll a library upgrade out to many projects. Teams can promote features up through integration and release streams as they mature.

  

    

    

  

  
The catches: promotion happens at the source level, so teams often rebuild from source at each level, breaking "build your binaries once". Complex merges, dependency problems and integration breakages pile up as layers multiply. ClearCase's dynamic views push others' changes into your workspace mid-thought, and the authors found its performance and administration costly. Yet the Linux kernel works in a similar style successfully, with Linus Torvalds being highly selective about what enters his tree.






  
8
When you must maintain parallel releases

  
Horror story #2: on one very large project the team had to maintain several partly overlapping release branches at once. What kept it under control: a clearly described merge strategy (changes always flowed in one direction between branches), a separate CI server for each long-lived branch, and a small, dedicated, rotating merge team. It worked, but the authors stress how much effort it cost. Branching always has a price; usually the better answer is to keep releasable on mainline.

  
Horror story #3 is gentler: a team in India on a slow, unreliable link to the main repository in England got its own local repository and CI server, committed and integrated locally all day, and one person merged to the shared mainline at the end of each day. A pragmatic compromise; a DVCS makes this pattern natural today.
