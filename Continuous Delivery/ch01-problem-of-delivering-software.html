Deploying by hand versus pressing a button

A manual deployment is a long runbook followed by tired people. Every step is a chance to make a mistake, and no two runs are quite the same. An automated deployment runs the same script every time, and the script itself is documentation that cannot go stale. Run both and compare.

3

Every change triggers feedback, fast

The goal the book sets out: every change, to code, configuration, environment or data, should start an automated feedback process. That feedback must arrive as soon as possible, and the team must act on it. The trick to speed is ordering: cheap, fast checks first; slower, more realistic ones later, run only on changes that survived the earlier ones.

The release candidateEvery check-in produces a build that could, in principle, be released. Each stage it passes raises your confidence in it. "Done" no longer means "coded", it means the candidate made it out of the far end.
4

If it hurts, do it more often

Releasing rarely makes each release bigger, and bigger releases carry more change, more surprises and more fear, which makes teams release even more rarely. The book's advice runs the other way: bring the pain forward and practise until it stops hurting. Move the slider and watch batch size and risk per release.

Illustrative numbers for a team making 2,000 changes a year. The point is the shape: smaller batches mean each release is easier to test, diagnose and undo.
