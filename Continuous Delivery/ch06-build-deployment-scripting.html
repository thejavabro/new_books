Build and Deployment Scripting

From make to Maven to Rake, build tools model tasks and their dependencies. The real skill is writing deployment scripts that work the same way everywhere and can be run again safely.

1

From IDE button to deployment system

On a tiny project the IDE can build and test everything. Beyond that you need scripts: a build that runs from the command line, the same way on a developer's machine and on the CI server. Deployment is harder still: configuring middleware, copying files, migrating data, restarting services, across many machines. The chapter warns against stretching a general-purpose build tool into a deployment system for anything but simple cases. Build and deployment scripts are first-class parts of the system, living as long as it does and maintained just as carefully.

2

Every build tool models a dependency network

At heart every build tool lets you declare tasks and the tasks they depend on, then works out what to run and in what order, running each one only once. Tools differ in one important way. Task-oriented tools (Ant, NAnt, MSBuild, Rake) describe the network in terms of tasks and keep no state between runs. Product-oriented tools (Make, SCons) describe it in terms of the files produced, and skip work whose outputs are newer than their inputs. Edit a file and run the build each way.

Ensure the deployment process is idempotent

  
Your deployment should leave the target in the same correct state whatever state it started in. The simplest way: start from a known-good baseline (provisioned automatically or a virtual machine image), then install the full set of artifacts for this version every time, not just the ones that changed. Run each script against a server in different starting states.

6
Deploy and test in layers

  
Deploy from the bottom up: operating system, then middleware and other software your application depends on, then your application and its configuration. After each layer, run a quick smoke test of that layer. If something fails, you know which layer is broken instead of trawling through logs. Deploy a stack and inject a fault.

Project structure for JVM applications

  

    
project/
  pom.xml / build file
  src/
    main/java/      production code, by package
    main/resources/
    test/java/      unit tests mirror packages
    test/resources/
  acceptance/       other test kinds, separate
  lib/              if not using a repo manager
  target/           ALL build output; never commit
    classes/  reports/  app.war

    

      
The book uses the Maven standard directory layout even for non-Maven projects, because a shared convention lets anyone find their way around. Keep source in directories named after packages; never check in generated code or config; keep unit tests apart from other kinds of test; send everything the build produces to one output directory that a clean deletes.

      
Split into multiple JARs to make deployment simpler and to enforce dependencies between components; a build step that checks no forbidden dependencies have crept in helps. Libraries go in an organization repository (Chapter 13).

Recap on one page

  

    
Dependency networksTask-oriented tools keep no state; product-oriented ones skip up-to-date outputs.

    
Choose wellInternal DSLs (Rake, Buildr) are easier to factor than XML; watch Maven's self-updating defaults.

    
One script per stageSame scripts in every environment, versioned with the code, written with ops.

    
Idempotent deploysFrom a known baseline, deploy everything, every time. Use OS packages.

    
LayersOS, middleware, app; smoke-test each one as it goes in.

    
TipsRelative paths, no manual steps, trace binaries to revisions, no build output in VCS, run all tests before failing.
