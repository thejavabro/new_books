Automated Acceptance Testing

Acceptance tests prove the system does what the business needs. Written well, they are executable specifications that survive UI changes and run fast enough to gate every build.

1

Why automated acceptance testing is essential

An acceptance test checks that a story's acceptance criteria are met: that the application does what the customer meant, not just what its programmers think. Unit tests can all pass while the system as a whole fails users. The suite as a whole also catches regressions, verifies behaviour in a production-like environment, and checks some nonfunctional criteria.

Some argue manual testing or unit tests are enough. The authors disagree: manual regression testing is expensive and gets squeezed when deadlines bite; no other kind of test proves the application delivers what users want; and acceptance tests protect you during large-scale changes. The real reason teams avoid them is cost. The rest of the chapter is about making them cheap to maintain.

2

Layer your acceptance tests

The key to maintainable acceptance tests is layering. Acceptance criteria are written in business language. A test implementation expresses them in code using only domain terms. An application driver layer knows how to talk to the application, through its API or UI. When the UI is involved, a window driver for each screen hides the widgets. Change the UI and see what breaks.

A story from the chapterOn one big project, tests recorded against the GUI fell further behind with each release until they were barely run. Introducing the window driver pattern in the third release, so that screen details lived in one place, turned the suite from a liability into an asset.
3

Acceptance criteria as executable specifications

Kick-off meetings at the start of each story bring together analyst, tester and developers to agree acceptance criteria. Written in the Given / When / Then form of behaviour-driven development, they can be executed by tools such as Cucumber, JBehave, Concordion, Twist or FitNesse, so the specification can never drift out of date. Build one and see the test implementation it maps to.

A good application driver layer

  

    

      
A well-designed driver layer becomes an internal domain-specific language. Two habits from the chapter make it robust:

      
Aliases. Tests say "Dave"; the driver quietly maps that to a unique name like dave_8812. Every test makes its own data, so tests are independent and can run in parallel on the same system.

      
Defaults. Registering a user needs a dozen fields, but a test only states the ones it cares about; the driver fills the rest (password, balance, currency, email…). Tests stay short and focused on intent.

State, boundaries and back doors

  
Acceptance tests can't avoid state, but they can control it. Don't load a production dump; keep the minimum coherent set of data. The ideal test is atomic: it creates what it needs, cleans up after itself, and does not care what order it runs in. Shuffle the order of these tests.

  

    

    

    

  

  
Prefer driving tests through the application's real interfaces. If you need a back door into the system just for testing, treat that as a design smell; reserve special test interfaces for stand-ins of external systems.






  
6
Waiting for asynchronous results

  
Has the test failed, or is the result just not here yet? The chapter's example: a system collects files and emails a confirmation. A naive test sleeps for a fixed delay; across hundreds of tests those delays add up. The better pattern is to poll for the result with a short pause, and give up only at a timeout. Run both against a system with variable response time.

  

    
Response time varies from 0.2 s to 6 s.

    

      
Fixed sleep of 5 s

      
Poll every 0.1 s, time out at 10 s

    

  

  
function confirmEmailWasReceived(alias, timeout = 10s) {
  deadline = now() + timeout
  while now() < deadline {
    if mailbox.has(alias) return
    sleep(100ms)           // small pause, don't spin the CPU
  }
  fail("no email for " + alias)
}






  
7
Test doubles for external systems

  
Acceptance tests run in production-like environments, but real external systems are slow, unreliable and hard to put in a known state. Replace them with doubles at the boundary, behind a component that represents the interface to each one. Then write separate, focused integration tests for those integration points, scoped to exactly the interactions your system uses, and run them at a cadence the external system can bear.

  






  
8
Running the acceptance test stage

  

  
Who owns acceptance tests?The authors once used the usual model where a test team owned them. Developers broke swathes of tests, testers spent their time chasing causes, and the suite rotted. Moving ownership to the whole delivery team, developers included, fixed it: whoever breaks a test fixes it.






  
9
Making the suite fast enough

  
Acceptance tests should exercise the system as a user would, so they are slow. The chapter's escalating tactics: refactor common tasks and slow setup; share expensive resources (like browser instances) where it doesn't hurt isolation; run tests in parallel; and spread them across a compute grid or the cloud. In one of Dave's projects, coarse parallel runs halved test time at a stroke, and moving to a cloud grid cut it further.
