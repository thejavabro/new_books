Managing Infrastructure and Environments

Environments are part of the system. Model them in version control, build them automatically, monitor them well, and they stop being fragile works of art.

1

Infrastructure is part of the system

Deploying software has three steps: create and manage the infrastructure, install the right version of the application into it, and configure the application with its data. This chapter is about the first. "Infrastructure" covers everything: servers, OS and middleware, infrastructural software like version control and directory services, external integration points, and the network. Three principles run through it, and the guiding rule is that testing environments should be production-like, and managed the same way.

2

Understand what operations needs

Operations teams are measured on keeping services up and on managing risk; developers are rewarded for change. Development's job is to understand ops' needs and build for them from the start. Four needs stand out.

Service continuity: RPO and RTO

The recovery point objective (how much data you may lose) drives backup strategy. The recovery time objective (how long you may be down) drives the recovery architecture. Set them and see what they imply.

3

Model and control infrastructure in version control

Keep everything that defines your infrastructure in version control: OS install definitions (Debian preseed, Red Hat kickstart), configuration for data-center automation tools like Puppet or CfEngine, DNS zone files and DHCP and SMTP config, firewall rules, and the scripts you use to manage it all. Then control access, make every change through an automated process, and monitor. Walk a change through the process the chapter describes.

Bad configuration management means debugging on release dayOne deployment to production failed mysteriously. It turned out a production server had a different patch level from the test servers, a difference nobody had recorded. With every server managed from version control, that difference could not have existed unseen.
4

Provisioning and managing servers automatically

Three ways to create OS baselines: by hand (not reliable or repeatable), by automated remote installation (PXE boot with preseed or kickstart; Windows Deployment Services), or from virtual machine templates. After the OS is in, a tool like Puppet keeps each server converging on the state described in version control. Watch a rack of servers drift and get corrected.

# illustrative, Puppet-like: desired state, not steps
class mailserver {
  package { "postfix": ensure => "2.7.1" }
  file { "/etc/postfix/main.cf":
    source  => "repo:///mail/main.cf",
    require => Package["postfix"] }
  service { "postfix": ensure => running,
    subscribe => File["/etc/postfix/main.cf"] }
}
node "smtp.example.com" { include mailserver }

Test-driven changes to environments

The chapter suggests treating infrastructure changes like code, test first:

  1. Write a monitoring check for the problem; watch it go red.
  2. Make the configuration change; roll it out to a production-like test environment.
  3. When the check is green there, roll it out to production.
5

Taming middleware configuration

Web servers, application servers and message brokers carry configuration that is as much part of the system as code. If a product only exposes a GUI, you have work to do. Try the chapter's tactics in order on an awkward product.

6

Infrastructure services and multihomed servers

Network problems are maddening to diagnose. The chapter's advice:

  • Version every bit of network config, from DNS zone files to firewall rules.
  • Install a network monitoring system (Nagios, OpenNMS, HP OpenView…).
  • Log at WARNING every time a connection times out or closes unexpectedly.
  • Smoke tests at deploy time should check every connection.
  • Make the integration environment's network topology match production.
  • Have forensic tools ready (Wireshark, tcpdump).

Production servers are often multihomed: separate network interfaces for production traffic, administration, backups and monitoring, each on its own network. Test environments should mirror this, or you'll find routing and firewall surprises on release day.

7

Virtualization and the pipeline

A virtual machine monitor runs many virtual machines on one host. Images can be stored, copied and versioned, which makes baselines cheap: build a template from a clean OS install plus automated configuration, keep it in a library, and stamp out whole environments. That is the "last missing piece" for push-button deployment of entire environments, and it lets you parallelize slow tests. Spin up environments and run the acceptance suite.

When a stage fails, triage among five causesA bug in the code; a bug or wrong expectation in a test; a problem with the application's configuration; a problem with the deployment process; or a problem with the environment. Versioned baselines and identical deploy processes remove the last two as mysteries.
8

Cloud computing

Utility computing: pay for what you use, scale on demand. The chapter distinguishes applications, platforms and infrastructure in the cloud. Choose a model to see who manages what.

The authors' view (in 2010): early days, with lock-in, security and compliance concerns to weigh, though compliance can be met, and data that cannot leave a jurisdiction is a real constraint. Even if production stays in-house, cloud infrastructure is great for elastic test environments. One size doesn't have to fit all: mix services, or build a private, do-it-yourself cloud.

9

Monitoring infrastructure and applications

A monitoring strategy covers four things: instrument applications and infrastructure to collect data; store it for analysis; build dashboards that aggregate it; and notify people of what they care about. Data comes from hardware (out-of-band management), the OS, middleware, and your applications, which should expose hooks for business and technical metrics. SNMP and log aggregation (the chapter mentions Splunk) help. Set conditions and see the tile's colour, using the chapter's red-amber-green rules.

Behavior-driven monitoringMartin Englund's idea: write monitoring checks as executable scenarios, the same way as acceptance tests ("Given a web server, when I request the home page, then the response is 200 within 2 s"), and run them against production continuously.
