Managing Components and Dependencies

How to keep the application always releasable while making big changes, and how to split a large system into components whose builds and versions you can actually manage.

1

Why components and dependencies matter

Large systems are built from components: reasonably large-scale pieces with a well-defined API that could be swapped for another implementation (DLLs, JARs, gems, services). The opposite is a monolith with no clear boundaries. Components bring their own problems: each may have release branches and versions, and finding a set that works together is exactly the integration problem CI exists to solve. The chapter first asks how to keep an application releasable while it changes, then how to manage the components and dependencies of large systems.

2

Four ways to stay releasable without branching

Teams keep adding features and making big changes. Branching until work is done delays integration. Instead the authors offer four strategies: hide new functionality until it is finished; make every change incrementally, each step releasable; use branch by abstraction for large changes; and use components to decouple parts that change at different rates.

Hide unfinished features

Ship the code, but don't link to it from the UI, or switch it off with configuration. On one of Jez's projects a whole new UI was built this way inside the live application, reachable at a separate URL, then switched over once it was complete. The chapter notes that a world-leading search engine works like this too.

if config.feature("new-reports"):
    menu.add("Reports (beta)", NewReports)
Production, release 41

3

Branch by abstraction

For a change too big to do in one go, such as replacing a persistence layer or a UI framework, the pattern named by Paul Hammant lets you work on mainline the whole time. Step through it.

The hardest parts are isolating the entry points to the part you are changing, and managing changes to it while the replacement is underway. It also works for carving a monolith into components.

4

Kinds of dependency, and dependency hell

Two distinctions help. Libraries are packages your team does not control, updated rarely; components are pieces your organization develops, which change often. Build-time dependencies must be present to compile and link; runtime ones only to run. "Dependency hell" happens when an application needs one version of something and another application on the same system needs a different one: DLL hell on early Windows, the classpath on Java. A build-time version of the same problem is the diamond dependency.

Remedies: .NET assemblies carry versions so several can coexist; Linux shared libraries append a version number to the file name; static linking or shipping your own copies of frameworks avoids OS-wide sharing, at the cost of size and coupling.

5

Managing libraries

Two reasonable options: check libraries (and even the toolchain) into version control, which is simple and works for small projects but bloats the repository over time; or declare them and let a tool like Maven or Ivy fetch them from a repository, ideally your organization's own, with exact versions pinned. Manage your own components the same way. If neither tool fits, a small home-grown declarative system can work.

6

When to split out a component

Good reasons, from the chapter: part of the code must be deployed independently; you want a core and plugins; it is an interface to another system; compiling and linking takes too long; opening the project in the IDE takes too long; the codebase is too big for one team. The last three may sound subjective, but they are real signals. Which apply to you?

Don't make teams own componentsFeature teams that cut through all components work better than component teams: requirements for a single component are hard to write and test in isolation, and every feature becomes a cross-team negotiation. And components don't imply an n-tier architecture; the chapter describes an architect who mandated seven layers, most of them adding nothing. Watch Conway's law: systems mirror the communication structure of the organization.
7

Building a dependency graph

The chapter's example: a portfolio management application depends on pricing, settlement and reports engines, which all depend on a framework; the pricing engine also depends on a third-party credit default swap (CDS) pricing library. Each component has its own pipeline; a component's success triggers builds of its downstream dependents. Click a component to change it and watch what rebuilds. Toggle a failure to see the graph protect itself.

One version of the framework, everywhereThe application must never build against a pricing engine built on one framework version and a settlement engine built on another. That is the diamond problem at build time. Your CI tool should enforce consistent versions across the graph, and let you trace upstream and downstream: which versions went into this build, and what was built from this one.
8

When to trigger builds: cautious optimism

Always rebuilding on every upstream change gives fast feedback but a lot of churn and breakage from unstable dependencies. Never rebuilding means you integrate rarely and painfully. Alex Chaffee's cautious optimism marks each dependency as static (ignore new versions), fluid (rebuild on new versions), or guarded (a fluid trigger that broke the build, and now waits until fixed). Update both upstream components and see.

The less control and visibility you have over an upstream component, the more cautious you should be. For components from teams in your own organization, err toward continuous integration. Apache Gump was an early tool that built the whole open-source Java world against the latest of everything.

9

Circular dependencies and the build ladder

The nastiest case: A depends on B and B depends on A. You can build it like a ladder: build A against a previous binary of B, then B against the new A, then A again against the new B. The authors have seen projects survive this, but recommend removing the cycle.

Managing binaries

artifacts/
  portfolio-app/         one dir per pipeline
    412/                 one dir per build number
      portfolio-1.4.412.war
      portfolio-1.4.412.war.sha1
      reports/
      index.json         status per stage
    413/ ...
  pricing-engine/
    207/ ...

Components should depend on each other's binaries, not source. An artifact repository holds them. Its key property: it must hold nothing you can't re-create. Artifacts are big, so you may delete old ones, but always keep their hashes, so you can verify any binary later.

The simplest repository is a directory structure keyed by pipeline and build number, plus an index file recording each stage's result. The pipeline stores binaries in the compile stage, and later stages fetch them, run, and record status. Maven adds dependency declarations, version ranges and SNAPSHOT builds; use ranges and snapshots with care, since they make builds hard to reproduce. Maven's dependencyManagement lets a parent project define versions once, and its analysis tools flag unused or undeclared dependencies.
