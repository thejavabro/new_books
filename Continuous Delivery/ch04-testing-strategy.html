Implementing a Testing Strategy

Quality cannot be inspected in at the end. A testing strategy spreads automated and manual tests across the whole project so the team always knows whether the software works.

1

Stop depending on inspection

Too many projects rely on manual acceptance testing at the end, with automated tests that are out of date or missing. The chapter borrows one of W. Edwards Deming's fourteen points: stop depending on mass inspection, and build quality into the product from the start. Testing becomes a whole-team activity that runs continuously from day one. In the ideal project, testers, developers and users write automated tests together before the code exists, and the CI system runs them on every change. The suite then doubles as the most complete, up-to-date documentation of the system.

Designing a strategy is managing riskDecide what could go wrong for this project, and which tests are worth their cost to reduce each risk. Good tests reduce defects, cut support costs and give the team confidence to change code.

4

Automating acceptance tests

Acceptance tests answer "how do I know when I'm done?" for developers and "did I get what I wanted?" for users. Automating them speeds up feedback, frees testers for exploratory work, and builds a regression suite that protects big codebases as they change.

They can be costly to maintain if written badly, and the book is clear that not everything needs automating. Its litmus test: swap out part of your system for a new implementation. If the acceptance tests pass, how confident are you that it works?

What to write first: the happy path for every story. Then alternate happy paths and sad paths, prioritised by risk. Tests that drive the UI should be thin; put an abstraction layer between tests and UI so most tests talk to business logic (more in Chapter 8).

Five kinds of test double

Replacing part of a system with a simulated version at test time lets you test one piece in isolation. Gerard Meszaros's vocabulary, as the chapter uses it, has five kinds. Pick one to see a tiny example.


  

  
Mocks are easily abusedA test that asserts every internal call a class makes breaks whenever the implementation changes, even when behaviour is still right. Prefer stubs and checks on outcomes; use mocks where the interaction is the behaviour.

8
Integration testing and test harnesses

  
When your application talks to external systems, integration tests check that you speak their protocol correctly. Never hit a real external system from a test environment by accident: firewall it off, and make the endpoint a configuration setting so you can point at a simulator. Toggle the failure modes a good harness should be able to simulate.

  

    

    

    

  

  
Plan integration into the release: will a test service exist and perform, will the provider fix bugs, can you diagnose capacity against production, and who maintains the harness?






  
9
Process, and what to do with bugs

  

    

      
Hold a short meeting at the start of each story: customer, analyst, tester and developers agree the acceptance criteria and write them up as tests. Developers then work against those tests, and testers pair with them as they go, so there is no big handover at the end where work piles up.

      
On defects, one school (the book cites James Shore) says fix every bug as soon as it is found. Where a backlog exists, keep it visible and treat it as risky. Another approach is to treat bugs like features: estimate them and let the customer prioritise them alongside stories.
