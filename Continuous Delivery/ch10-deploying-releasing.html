Deploying and Releasing Applications

Deployment should be a push-button, low-drama event. This chapter covers release planning, promoting builds between environments, zero-downtime releases and how to undo them.

1

Start with a release strategy

Deploying to a test environment and releasing to production should use the same process; the difference is the consequences. The most important part of a release strategy is getting the stakeholders together at the start of the project (devs, ops, testers, DBAs, support) to agree how it will work. The document lists who deploys where, the deployment technology, environments, monitoring, logging, disaster recovery, SLAs, capacity planning, archiving, patching and upgrades. Writing it surfaces requirements early. How many items does your project have covered?

A release plan, part of the strategy, covers the first deploy, smoke tests, back-out, backup and restore, upgrades that keep state, restarts, logs, monitoring, data migrations, and an issue log from past deployments. Products for sale add pricing, licensing, packaging, documentation, installers, and preparing sales and support.

2

The first deployment happens in iteration one

By the end of the first iteration you should have a commit stage, a production-like environment, an automated process that deploys commit-stage binaries into it, and a smoke test that proves it worked. That is easy while the application is tiny, and it grows with the app. A production-like environment runs the same OS and the same software stack as production, and is managed the same way. Use virtualization, and the "0, 1, many" rule: if production has 250 web servers, two are enough to represent the significant process boundaries.

3

Model your release process and promote builds

Draw your process: which stages a build must pass, the gates between them, and who can approve each gate. Then make promotion a matter of choosing a build and pressing a button. Every testing stage follows the same nine-step workflow. Step through it.

4

Rolling back by redeploying

You must be able to roll back. Two constraints: data (a release that migrated the database complicates things) and other systems you are coordinated with. The simplest approach is to redeploy the previous good version, cleaning the environment first. It is the same process you have tested hundreds of times. The downsides: it takes a non-zero time, during which the system is down; it may overwrite evidence you need to debug; and restoring a pre-release database backup loses data written since.

5

Blue-green deployments

"One of the most powerful techniques we know." Keep two identical production environments. Users hit one (green) while you deploy the new version to the other (blue) and smoke-test it at leisure. Releasing is a router switch; rolling back is switching back. Try it.

Data is the hard part: put the app in read-only mode briefly around the switch, or design the app so the database migrates independently of the release (Chapter 12). With a single environment, you can still run blue and green as separate installs on the same hardware. The chapter mentions one very large organization running five parallel production environments.

6

Canary releasing

Roll the new version out to a small subset of production servers and route a fraction of users to it, like a canary in a coal mine. If error rates or response times look bad, stop routing to it. It makes rollback easy, enables A/B testing, and lets you ramp up load gradually on systems too big to replicate for capacity testing. Ramp a release.

Canaries in point-of-sale systemsThe authors used incremental rollout for a retailer's store systems: different groups of stores, grouped by brand, ran different versions at once. Keep as few versions in production as possible, though; every extra version raises the cost of support and of database compatibility.
7

Emergency fixes go through the pipeline too

Under pressure, teams skip the process: they patch production by hand. The fix is untested, and the change is not recorded, so the next deploy wipes it out or the environment drifts. The rule: run every emergency fix through the standard pipeline; that is one more reason to keep the pipeline fast. Sometimes rolling back is better than fixing forward. Decide for each case.

  • Never do them late at night, and always pair.
  • Test your emergency fix process, including in staging.
  • Only bypass the normal process in extreme circumstances.
  • Weigh the cost of the defect against the cost and risk of the fix.
8

Continuous deployment

Taking "if it hurts, do it more often" to its logical end: every change that passes the automated tests goes straight to production. The term was popularized by Timothy Fitz, whose blog post on it caused a stir. It is not for everyone (sometimes the business doesn't want features released yet), but even where you don't adopt it, it forces you to do the right things: automate everything, test thoroughly, make releases small and safe. It combines naturally with canary releasing. Continuous delivery means every change could be released at the push of a button.

9

Continuously releasing user-installed software

Shipping updates to software that runs on users' machines raises new problems: the upgrade experience, migrating binaries, data and configuration, testing upgrades, and crash reports. The authors argue that prompting users is a cop-out born of the team's own fear of a fragile upgrade. Make upgrading bulletproof and silent, able to go from any version to any other, test it in the pipeline, and collect crash reports. Compare the three options.
