Anatomy of the Deployment Pipeline

The deployment pipeline is the book's central idea: an automated path that takes every change from check-in to release, giving fast feedback and a release candidate you can trust.

1

Beyond continuous integration

CI transforms development teams, but its output usually lands in a queue for manual testing and a handover to operations. That is where the waiting is: ops waits for documentation, testers wait for a "good" build, developers get bug reports weeks after they have moved on, and the architecture's capacity problems show up at the end. The answer is an end-to-end, automated view of delivery. Testers and ops pull builds when they want them, and everyone can see where each change is. The authors call this a pull system, and its mechanism is the deployment pipeline.

2

Start with a value stream map

A deployment pipeline is an automated manifestation of your process for getting software from version control into users' hands. Before building one, map the process: walk a customer request through the organization with pencil and paper, noting the time each step really takes (value-adding time) and the time spent waiting between steps. 3

A basic deployment pipeline

Every check-in creates a new instance of the pipeline. The commit stage proves the code works at a technical level and builds the binaries; automated acceptance tests prove it does what the customer wants; then the same binaries are deployed, on demand, to manual testing, capacity testing and finally production. Step through a change.

The trade-off along the pipeline

Early stages are fast and cheap but less realistic; later ones run in environments ever more like production, so they are slower and more expensive. Each stage you pass raises confidence, which justifies spending more on the next. Fast feedback comes from the first; confidence to release from the last.

Two consequences follow. You cannot release a build that has not been fully tested, and because deployment is automated, releasing becomes rapid and repeatable, often just a button press.

5

Only build your binaries once

If each stage rebuilds from source, what you test is not what you release: a different compiler, library version or config file can slip in between. Build in the commit stage, store the binaries (with a hash) in an artifact repository, and have every later stage fetch those exact files. Try both approaches.

A corollary: no environment-specific binariesIf the binary must be rebuilt to run in a new environment, you cannot promote it. Keep configuration separate and supply it at deploy time, using the same deployment mechanism everywhere, from a developer's machine to production.
6

Each change propagates instantly, in batches

The first stage runs on every check-in, and each stage triggers the next as soon as it passes. Later stages are slower, so they cannot run for every commit. A smart CI server takes the newest passing build whenever a stage becomes free, so slow stages naturally test batches. Add commits and watch.

Commit stage ≈ 2 s, acceptance ≈ 7 s (scaled down).
If any part fails, stop the lineA red stage is everyone's problem. Fix it straight away, before more changes pile on top. Manual stages are the exception to auto-triggering: testers pull the build they want.

What each stage does

Why unit tests aren't enoughOn an 80-developer project with about 90% unit test coverage, a build deployed to a test environment would not even start. Stepping back through versions showed it had been broken for weeks. Unit tests had passed every time. A couple of simple automated smoke tests that started the application would have caught it on day one.
8

Preparing to release, and backing out

Every release carries business risk. The mitigation is to treat release as the natural outcome of the pipeline:

  • a release plan maintained by everyone involved, ops included;
  • automate as much as possible, starting with the most error-prone steps;
  • rehearse often in production-like environments;
  • be able to back out; and
  • have a plan for migrating configuration and data, both ways.

The best back-out is to keep the previous version available while the new one goes live. Next best: redeploy the previous good version from scratch. Never have a separate, special process for backing out.

What a candidate has proved by release time

The authors call this building upon success: each stage adds evidence, and any failure stops the candidate.

9

Implementing a pipeline, step by step

The pipeline does not have to be built all at once. Build it incrementally, measure it, and treat it as a living system that evolves with your process.

10

Measure cycle time, then attack the constraint

Optimize globally, not locally. Cycle time, the time from deciding on a change to having it in production, is the global metric. Goldratt's Theory of Constraints then gives five steps: identify the constraint, exploit it, subordinate everything else to it, elevate it, and repeat. Click the step that's limiting this pipeline to invest there.

Useful diagnostics alongside cycle time: test coverage, duplication and complexity, defect counts, velocity, commits per day, builds and build failures per day, and build duration. Make them visible on every check-in.
