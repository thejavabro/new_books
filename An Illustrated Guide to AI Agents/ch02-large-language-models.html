1

The LLM sits between user and environment

In an LLM-backed agent, the model does four jobs: read the user's request, choose an action, read what came back from the environment, and reply. Here is the smallest possible loop, an information-seeking agent with one web search tool.

The chapter has two halves. The first (sections 1 to 4 here) is what an agent builder needs. The second (sections 5 onward) opens the model up, for readers who want to know why agents behave as they do.

2

System prompts, turns and tool calls are all just text

Training a base model on raw text is phase one. Post-training then teaches it a conversation format: a privileged system prompt that the deployer writes and the user cannot override, labelled turns that track who said what, and a special way to emit a tool call that the harness watches for. Everything below gets tokenized into one long sequence.

TinyAgent gets a brain

The book runs two open models side by side: Gemma 3 12B, which knows nothing about reasoning or tool calling, so you build those behaviours with prompts yourself; and Gemma 4 E4B, trained to do both natively. They are reached through the OpenAI-compatible endpoint, the de facto standard request and response shape that most local and hosted servers speak. A call needs a base URL, an API key, a model name and the messages.


  
Every reply is wrapped in a small Response, and every turn is logged as a Step (thought, action, observation, answer, plus token counts) inside a Trajectory. Trajectories become essential for debugging once agents take dozens of steps, and Chapter 7 evaluates them directly.

How an LLM is trained

  
Two phases. Pre-training is language modeling at vast scale: hide the next token, guess, adjust weights, billions of times, producing a base model. Post-training polishes behaviour with much less data, first by imitation, then by reward. Tap each stage.

  

    

    

    

  






  
5
RLVR and GRPO: reward the better half of the group

  
RLVR uses automatic checks instead of human taste. A math example: +0.3 if the answer sits inside <answer> tags, +0.7 if it is correct. GRPO samples a group of answers to the same prompt, scores each, and pushes the model toward the ones that beat the group average. Toggle the outcomes and watch who gets reinforced.

  

    

    

    

  






  
6
Tokenizer, Transformer stack, LM head, then a choice

  
Inside, a Transformer decoder has three parts. The tokenizer maps text to IDs from a fixed vocabulary (say 50,000 entries), each with an embedding vector. A stack of Transformer blocks refines those vectors. The LM head turns the last position's vector into a probability for every token in the vocabulary. Then a decoding strategy picks one. Temperature 0 always takes the top token; higher temperatures flatten the odds.

  

    
    

    

  






  
7
Tracks, context length and the KV cache

  
Each token flows through the stack on its own track, all in parallel. The number of tracks a model supports is its context length, which caps how much you can put in front of it, and is why context engineering matters. Only the last track predicts the next token. Once the prompt is processed, earlier tracks' results can be cached, so each new token needs just one fresh track. For agents with long, growing prompts, keeping that cache valid is a major lever on speed and cost.

8
Inside a block: attention and the feed-forward network

  
A Transformer block has two parts. The feed-forward network processes each position on its own, expanding the vector to a wider hidden size and compressing it back: much of the model's stored knowledge lives here. Self-attention lets the current position pull in information from earlier positions. Each position is projected into a query, a key and a value; query·key gives relevance scores, softmax turns them into weights, and the output is the weighted sum of values. Tap a word to see where it might attend.

  

    

    

  






  
9
Shrinking the KV cache: MHA, GQA, MQA, MLA

  
The cache stores a key and value per token, per head, per layer, and it grows with context. Multi-head attention keeps separate K and V for every head. Grouped-query shares K/V across groups of heads; multi-query shares one K/V across all heads. Both save memory but can cost accuracy. Multi-head latent attention (DeepSeek-V2, popularised by R1) caches a small compressed latent instead, with a separate small key carrying position (RoPE). DeepSeek-V3.2 added sparse attention: a lightweight indexer scores past tokens and only the top-k (2,048 in the paper) get full attention.

  

    

    

    

  






  
10
Mixture of experts: big model, small active slice

  
In a dense block, one feed-forward network handles every token. A mixture-of-experts layer replaces it with many smaller expert networks and a router: a tiny network plus softmax that scores the experts for each token and keeps the top k. All experts must sit in memory (sparse parameters), but only a few run per token (active parameters). Routers need load balancing, through expert capacity limits, a little noise, or an auxiliary loss, so a few experts do not hog the training. Some designs add a shared expert every token uses.
