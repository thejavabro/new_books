Evaluating Agents

An agent is a whole system acting on the world, so a single text score will not do. Judge what it achieved, how it got there, whether it does so every time, and whether it stays safe.

1

From "it seems to work" to evidence

Every earlier chapter added a component. This one asks: how do you know any of it works? Agents act over many steps on a real environment, so judging them is judging a whole system, not just a model. The book uses four lenses.

2

The benchmark landscape

Benchmarks are what you meet first, in model announcements. Coding benchmarks became the gold standard because code is verifiable: tests pass or they do not. On SWE-bench, built from real GitHub issues, top agents went from about 2% in 2023 to over 70% on the curated Verified set by 2026. Tap a category.

A 2026 analysis found benchmarks cluster heavily around programming, while the occupations that employ the most people go almost untested. Expect more real-work evaluations.

3

Reading a benchmark score critically

"Agent X scores 78% on SWE-bench Verified." Before you believe it, ask the questions seasoned researchers ask. Open each card.

4

Outcome evaluation: did it get the right output?

Human evaluation is the gold standard every automated method is measured against. Raters can score one output against criteria, or compare two side by side, which is easier and more reliable ("A is better" beats "A is a 4, B a 3"). Pairwise preferences over a task suite add up to a win rate. Click each task to record which agent a rater preferred.

Humans are slow and costly, so most evals automate. Cheapest first: exact match (multiple choice, a number), programmatic checks (does the code pass its tests, did the email get sent), and for open-ended outputs an LLM as a judge, given the output, the criteria and perhaps a reference answer.

5

Rubrics: split one judgement into many

A rubric breaks quality into named dimensions, each with its own scale (1 = severely lacking, 5 = comprehensive), scored separately by a human or a judge model. That makes scores more consistent and tells you where an agent falls short. Score this research-agent report.

6

Trajectory evaluation: did it get there the right way?

A trajectory is everything the agent did: reasoning, tool calls, arguments, intermediate results. Aggregated across many runs, tool-use statistics reveal style (one model searches heavily first, then executes). Read individually, they catch problems outcomes hide. All three agents below answered correctly. Find each one's flaw.

The three failure modes deserve separate measures: unsound reasoning, inefficiency, unnecessary overhead. A judge given the full trajectory and a rubric can score them; T-Eval, AgentBoard, TRACE and AgentProcessBench formalise this.

7

Reliability: pass@k versus pass^k

Agents are stochastic, so one run can flatter or punish. Run each task n times and count c successes. pass@k estimates the chance that at least one of k attempts succeeds: a capability ceiling, useful when choosing checkpoints to keep training. pass^k (from τ-bench) estimates the chance that all k succeed: reliability, what matters when you ship a model as-is. Two models with equal pass@1 can differ sharply in pass^k.


  






  
8
Safety: who is causing the harm?

  
An agent can send an email, delete a file or drop a database, so safety tests belong in the suite from day one. The cleanest split is by threat model. Misuse: a malicious user asks for harm; measure refusal rate and harm score (AgentHarm). Manipulation: instructions hidden in data the agent reads (prompt injection) or planted in its memory (memory poisoning); measure attack success rate (AgentDojo, Agent Security Bench). Accidents: no adversary, the agent simply errs on a benign task; the least standardised, relying on your own tests and guardrails.

9
Build your own eval suite

  
Public benchmarks rarely match your use case. Write test cases that cover a wide spread of failure modes and edge cases, not just happy paths; score them with whatever fits each case (exact match, programmatic checks, LLM judge, rubric); and run the suite automatically on every meaningful change, like unit tests. Start small: even 5 to 10 cases are eye-opening. The TinyAgent chapter builds exactly this kind of evaluator.
