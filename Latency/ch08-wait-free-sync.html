Wait-Free Synchronization

Locks make threads wait for each other, and waiting is latency. Atomics and careful memory ordering let threads coordinate without ever blocking.

Why synchronize: the lost update

Partitioning (chapter 5) lets threads work on separate data. When they must share, they need synchronization, or updates get lost. Two threads each run counter += 1, which is really load, add, store. Step through an unlucky interleaving, then fix it.

2

What locks cost: four problems

Inefficiency first. The book benchmarks a shared counter behind a lock as the number of threads grows. Uncontended, a lock costs a few nanoseconds; contended, threads mostly wait, sleep and get woken by the OS.

log scale

Priority inversion: a high-priority task waits for a lock held by a low-priority one, and a medium-priority task preempts the holder, so the high-priority task effectively waits for the medium one. Priority inheritance temporarily lends the holder the waiter's priority.

Convoying: the lock holder is delayed (preempted, page fault, long critical section) and everyone queues behind it, cascading into tail latency and idle CPUs. Deadlock: threads wait on each other in a cycle; the classic is ABBA.

3

Atomics: the building blocks

Every lock is built from atomic operations: indivisible steps that other cores see entirely or not at all.

A spinlock is just a loop around one atomic swap: write "locked" and look at what was there before. If it was unlocked, you own it. Unlocking is an atomic store of "unlocked". On x86-64 both compile to an xchg instruction.

struct Spin { locked: AtomicBool }
impl Spin {
    fn lock(&self)   { while self.locked.swap(true, Acquire) { spin_loop(); } }
    fn unlock(&self) { self.locked.store(false, Release); }
}

Memory barriers: forbidding reorders

CPUs (and compilers) reorder memory operations for speed. Single-threaded code can't tell; other threads can. x86-64 is fairly strict (total store order: one core's stores stay in order), ARM64 is relaxed. The book's experiment: thread 1 writes value = 1 then done = true; thread 2 reads done then value. The invariant "if done then value is 1" should always hold. Run it many times.

Simulated: a relaxed run lets either thread's two operations become visible in either order.

What each barrier forbids

A compiler barrier (Rust's compiler_fence) only stops the compiler from reordering; it emits no CPU instruction. Python and JavaScript expose no barriers at all; Java and C# give you volatile.

5

Wait-free synchronization and progress guarantees

A wait-free data structure guarantees every thread finishes each operation in a bounded number of its own steps, whatever other threads do. That brings predictable latency, scaling across cores, immunity to deadlock, tolerance of stalled threads, and much less priority inversion. "Lock-free" is weaker and often confused with it. Tap each level.

A blocking allocator inside a "wait-free" structure quietly breaks the guarantee, so mind memory allocation here too.

Putting it together: a single-producer, single-consumer queue

The hands-on project builds a bounded ring buffer: an array plus two ever-increasing indices, back (written only by the producer) and front (written only by the consumer). Slot = index mod N. Making it wait-free for one producer and one consumer needs only atomics and an acquire/release pair on each index, no locks. Push and pop below.

fn push(&self, v: T) -> Result<(), T> {
    let back  = self.back.load(Relaxed);      // only we write back
    let front = self.front.load(Acquire);    // see consumer's progress
    if back - front == N { return Err(v); }      // full
    self.slot(back % N).write(v);
    self.back.store(back + 1, Release);        // publish: data before index
    Ok(())
}
