Eliminating Work

1

The fastest code is code that does not run

Part 2 organised data for low latency. Part 3 turns to computation, starting with the oldest trick: don't do the work. The hard part is that much of the work is invisible: hidden in your algorithms, in serialization, in the allocator, in the garbage collector, in virtual memory and in the operating system. Profilers find it; knowing where to look helps you avoid writing it in the first place.

2

Algorithmic complexity

Big O describes how the number of steps grows with input size n, ignoring constants. For latency it predicts how response time grows as data grows. Slide n and assume one step costs 1 ns.

Bars use a log scale. A worse class can still win for small, known n, because constants matter there.

Pick a data structure for the hot path

Hash tables are O(1) on average but O(n) if keys collide, and their memory footprint can thrash caches. Binary search trees keep order, which you need for range queries.

Dynamic memory allocation is not deterministic

A heap allocator carves blocks from a big region and tracks free blocks, in the simplest design a linked free list it must walk to find a fit. As blocks are freed in random order, the heap fragments: many small holes, longer walks, and sometimes no hole big enough. Freeing can be slow too, when the allocator coalesces neighbours. Multithreaded heaps add locking. Some languages also allocate behind your back (autoboxing in Java and C#).

Garbage collection: safe, but when?

GC removes leaks, dangling pointers and double frees, but the runtime decides when to collect, and a collection can take milliseconds to seconds. Generational collectors allocate young objects with a bump pointer (no free list: just move a pointer forward) and collect the young region when it fills, copying survivors out. Allocation rate therefore sets how often you pause.

Mitigations: incremental, concurrent or pauseless collectors; tuning heap size, generation ratios and thresholds; and, above all, not allocating in latency-sensitive paths.

6

Virtual memory, demand paging and the TLB

Your program sees a contiguous virtual address space (text, data, BSS, heap growing up, memory-mapped region, stack growing down). The CPU translates virtual pages (usually 4 KiB) to physical ones through the page table, caching recent translations in the TLB. The OS maps physical pages lazily: the first touch of a page triggers a page fault; under memory pressure pages are swapped to disk and fault back in later. Touch some pages.

Large pages cover more memory per TLB entry, easing TLB pressure, but every fault moves more data. Beyond paging, physical placement still matters: fit hot data in caches, walk big datasets in cache-sized batches, and on NUMA bind memory near the cores that use it (for example with mbind, discovering topology with hwloc).

7

Operating system overhead

The OS time-slices threads onto cores. If you have more runnable threads than cores, a ready thread waits: scheduling delay. Each switch saves and restores state, costs microseconds and evicts your data from caches; system calls pay a similar privilege-switch cost. Add background daemons, kernel threads and interrupts landing on your cores.

8

Precomputation: do it before anyone asks

Move expensive work off the request path: compute at build time, at start-up, or periodically, and serve a lookup. The book's example is a storage usage page: usage, quota (depends on plan and discounts) and a forecast of when you will run out can take seconds to compute, but can be refreshed in the background often enough that nobody notices. Incremental precomputation updates the result as data changes; materialized views are the database version.

Putting it together: benchmark, profile, eliminate

The chapter ends by measuring instead of guessing. A Rust microbenchmark (the Criterion library) times three ways to compute the 10th Fibonacci number, and a flame graph shows where the time goes.

The book's measurements: plain recursion is exponential, O(2ⁿ). Memoization makes it O(n) and 3.5× faster. The flame graph then showed the memoized version spending much of its time in calloc and free for the per-call cache. An iterative loop, still O(n) but with no allocation and no recursion, is about 30× faster than the original.

fn fib_iter(n: u64) -> u64 {          // no heap, no recursion
    let (mut a, mut b) = (0, 1);
    for _ in 0..n { (a, b) = (b, a + b); }
    a
}
