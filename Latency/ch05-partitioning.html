Partitioning

Slice data into smaller pieces and each query touches less of it, and work spreads across machines. How you slice, and how requests find the right slice, decides whether it pays off.

1

Why partition: less to coordinate

Replicating everything everywhere gets expensive, and keeping many copies consistent can create the very bottleneck you were trying to avoid. Partitioning slices a logical dataset into smaller physical pieces that can be accessed independently. Each request touches less data, concurrent writes rarely collide, and the pieces can live on different cores or machines.

The key word is synchronization. A shared table, a distributed lock, or a mutex forces concurrent clients to take turns, and taking turns is what builds tail latency. With partitions, each lock is shared by fewer clients, often nearby ones. Drag the number of partitions and watch the waiting.

The bookstore exampleOne big Orders table is touched by shoppers viewing orders, shoppers checking out and the shipping engine, all at once, so the database coordinates every access. Split orders per customer and shoppers never coordinate with each other, only with the order processor. The price: routing logic, a more complex processor, and no transactions across partitions (a bank transfer between two accounts in different partitions becomes hard).
2

Horizontal, vertical, hybrid

Horizontal partitioning (sharding) splits records: rows, documents or key ranges go to different partitions. It suits OLTP, with many short transactions on whole records. Vertical partitioning splits each record by fields, storing columns together. It suits OLAP: aggregates read only the columns they need (less read amplification), similar values sit together and compress well, and SIMD can chew through them. Hybrid does both. Pick a layout, then a query, and see which partitions the query must touch.

Why "shard"?The word probably comes from the 1996 game Ultima Online, which ran several whole copies of its world and explained them in the story as shards of a shattered crystal, each holding a copy of the world. Read "sharding" as "horizontal partitioning".
3

Choosing a partition key: hash or range, high cardinality

Key hash partitioning spreads keys uniformly but scatters neighbours. Key range partitioning keeps ranges together, great for range scans, but follows any lumpiness in the data. And the key needs high cardinality (many distinct values): partition on order status and you get four partitions, one of them huge. Compare the partition sizes.

Logical partitioning: shape data around the workload

Physical layout says how slices are stored; logical (workload) partitioning says what goes together, based on how the application uses the data. The two combine freely.

Partition imbalance: hot partitions and skew

Imbalance wastes the scheme: one partition is swamped, others idle, and latency follows the busiest one. Two causes. Hot partitions: some partitions hold more data, from a poor scheme or uneven value sizes (big images in an object store). Fixing it usually means rebalancing, which is painful on a live system. Skewed workloads: data is even but access is not, such as a popular product, a launch, Black Friday, or time zones.

7

Putting it together: horizontally partitioned REST API

The hands-on project reuses chapter 3's SQLite REST server, adds a node ID (node n listens on port 8080 + n), and teaches the benchmark client to spread requests round-robin across a configurable number of nodes. With five nodes instead of one, the tail of the eCDF pulls in, because concurrent requests no longer queue behind each other. Simulate it:

// next step: route by key instead of round-robin (illustrative)
fn node_for(user_id: u64, nodes: u64) -> u64 {
    hash(user_id) % nodes        // key hash partitioning
}
let port = 8080 + node_for(uid, 5);
