Caching

A cache keeps a copy of data in faster storage. Everything hinges on the hit ratio, on what you evict, and on how stale you are willing to let the copy get.

Why cache, and the vocabulary

A cache keeps a temporary copy of part of the data in faster, closer storage, while the backing store (a database, a service) keeps the primary copy. It sounds like replication, but the trade-offs differ: you give up freshness and some memory to reuse results. The book suggests reaching for caching when the system:

Vocabulary: a lookup by cache key is a hit or a miss. Caches may be in memory or persistent (survive restarts, avoiding a cold start), transactional (isolation guarantees) or not. Negative caching remembers that something does not exist, so an expensive "no results" search is not repeated. A replacement policy decides what to evict when full; a TTL decides when an entry is too old.

2

Four caching strategies

The strategy decides who talks to the backing store, and when. Pick one and an operation to see the message flow and the latency the application waits for (cache 1 ms away, database 20 ms away; illustrative).

Client-side cachingPut the cache inside the application on the user's device and you skip the last mile entirely. Read-through plus write-behind is the fastest combination there, though transactions get hard and memory use grows. For richer needs, the local-first approach from chapter 4 may fit better.
Distributed cachingMany cache instances, partitioned (chapter 5) and often replicated (chapter 4). You inherit all the benefits, and all the problems, of both.
3

Cache coherence, the CPU way

When several caches hold copies of the same data, coherence means they never disagree. CPUs do this in hardware with protocols like MESI, which tracks a state per 64-byte cache line: Modified, Exclusive, Shared, Invalid. Writing to a shared line first invalidates every other copy, which is why writes to shared data cost latency. Drive two cores.

Memory holds:

Application caches are usually incoherent on purpose: no coordination means low latency, at the cost of stale reads. Note also that coherence is not consistency: it says copies agree, not in what order operations appear. Real CPUs add store buffers and invalidation queues, so two cores can briefly see different values (chapter 8).

4

The hit ratio, and the tail it leaves

hit ratio = hits ÷ (hits + misses). Average latency slides linearly from miss latency toward hit latency as the ratio rises. But averages hide the shape: even at 80% hits, one request in five pays the full miss. The tail is the backing store's latency.

5

Replacement policies: LRU, LFU, FIFO, SIEVE

Fast memory is small and pricey (DRAM costs roughly ten times more per gigabyte than SSD), so a full cache must evict. Try the policies by hand on a 3-slot cache, then race them on longer workloads.

6

Time-to-live: freshness by the clock

TTL expires entries after a fixed time, whether or not anything changed. It solves invalidation without the cache knowing about the backing store, which is why DNS uses it (a day for stable records, 30 seconds for load-balanced ones). The dilemma: long TTL means more hits but staler data; short TTL means fresh data and needless misses.

Model: one key read 10 times per second. Miss whenever the entry has expired; stale whenever the store changed since the entry was loaded.

7

Materialized views and memoization

A materialized view stores a query's results inside the database, e.g. all users in London, and is queried like a table. Some databases refresh it on demand; dataflow systems such as Noria keep it updated incrementally as writes arrive (eventually consistent). It's a cache that the database manages, with full SQL in front.

Memoization caches computation: the function's arguments are the key, its result is the value. Every time you cache a REST response on the client, you are memoizing. Watch the call count.

8

Putting it together: in-application caching

The hands-on project wraps chapter 3's PostgreSQL REST server with an in-process cache-aside cache (the Moka library in Rust) whose entries live 5 seconds. Every 5 seconds a request misses and goes to the database; everything else is served from memory. The book's eCDF shows the whole curve shifting left, with a tail still there from those misses.

// cache-aside in a request handler (illustrative)
async fn hello(pool: &Pool, cache: &Cache<String, String>) -> Result<String> {
    if let Some(v) = cache.get(KEY).await { return Ok(v); }   // hit
    let v = query_db(pool).await?;                          // miss: go to Postgres
    cache.insert(KEY.into(), v.clone()).await;               // TTL 5 s set on the cache
    Ok(v)
}
