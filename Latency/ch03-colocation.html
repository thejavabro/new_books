Colocation

The fastest data access is the one that does not travel. Colocation puts data and compute close together, across the globe, inside a machine, and even on the same CPU core.

1

Why colocate: shorten the trip

Picture a web app querying a database 6,000 km away: every query pays about 60 ms of round trip. Move the database into the same data centre and queries drop below 10 ms, a 6× gain from changing nothing but placement. Embed the database inside the process and the network disappears entirely. High-frequency traders learned this long ago and rent rack space next to the exchange.

The book's pattern is colocate compute and data, applied from the outside in: first between machines (internode), then inside a machine (intranode): the network stack, CPU cores, memory banks, caches. A slow placement can swamp every code-level optimization you make.

2

Geographic and last-mile latency

Network latency between nodes has two big parts. Geographic latency is distance: a premium New York to London link advertises about 60 ms round trip (light in vacuum would need 38 ms), London to Cape Town is about 160 ms and London to Sydney about 250 ms. Last-mile latency is the final hop from the ISP's backbone to the device, over broadband, cellular radio and home Wi‑Fi. It is short in distance but can add 10 to 50 ms, and you barely control it.

The author's own lesson: a real-time system that worked in local tests was too slow in production, because it was accidentally running on the wrong side of the Atlantic. Measure your baseline. Try placing a server for a user below.

3

Edge computing and CDNs

Classic cloud deployments are centralised: one region, everyone travels to it. Edge computing decentralises: smaller deployments near users. "Edge" is an overloaded word, so the book separates two kinds.

CDNs were born in the late 1990s when the web got slow under its own success: cache images, scripts and video on servers spread around the world and route each user to the nearest one. Modern programmable CDNs run your own functions (JavaScript or WebAssembly) at the nearest point of presence, so dynamic responses can be close to users too, as long as the data they need is close as well.

4

Inside the node: the packet's path

Within one machine, the outermost source of latency is usually the operating system's network stack: the NIC driver, the protocol code and the socket API. Step a received packet through it, and compare placing protocol processing on a different core from your application versus colocating them.

Two common strategies: isolate interrupt processing on dedicated cores (set IRQ affinity for the NIC and pin application threads elsewhere), or colocate it with the application thread that consumes the data, which needs coordination such as flow steering (more below).

5

TCP, UDP and Nagle's algorithm

UDP wraps your message in a tiny header and sends it; if a router drops it, it is gone. Great inside a reliable data-centre network. TCP guarantees delivery and order with sequence numbers and retransmission, at the cost of more machinery. By default TCP also runs Nagle's algorithm, which holds back small writes while earlier data is unacknowledged so it can send fewer, fuller packets. Good for throughput, bad for a chatty request–reply protocol. Watch three small messages go out.

// Rust: disable Nagle on a socket (illustrative)
let stream = TcpStream::connect(addr)?;
stream.set_nodelay(true)?;   // send small writes immediately

Some latency-sensitive systems use protocols built on UDP that add their own reliability and flow control (Aeron is one example), getting most of TCP's safety without its defaults. Hardware TCP offload can take protocol processing from tens of microseconds to single digits.

6

Kernel-bypass networking

The kernel stack costs system calls, copies, context switches and per-packet allocations. Kernel bypass moves packet processing somewhere cheaper. Pick an approach and see which layers a packet still crosses.

7

Multicore: memory topology and caches

In a UMA machine every core reaches main memory equally fast. In a NUMA machine memory is split into nodes, and a core reaches its own node's memory faster than a remote node's. (Apple's "Unified Memory Architecture" is a different idea: CPU and GPU sharing one memory pool.) The colocation trick is application-level partitioning: split the data across nodes or cores and send each request to the core that owns its data, like a CDN inside one box. NICs can help with flow steering, delivering each flow to the queue of the right core.

At the smallest scale, colocation means keeping the working set inside the CPU caches: L1 is around 1 ns but tiny, the last-level cache is ten times slower but megabytes to tens of megabytes. If your hot data fits in the LLC, you avoid 100 ns trips to DRAM.

Putting it together: embed the database

The hands-on project builds the same tiny REST endpoint twice, in Rust: once querying PostgreSQL on the same machine over a connection pool, once querying an embedded SQLite database inside the server process. The query does no real work, so the difference is almost pure communication cost. Results from the book's runs with a standard HTTP load tool:

log scale

An eCDF of a fixed-interval benchmark (requests every 10 ms, to avoid coordinated omission) told the same story: SQLite's curve is almost a vertical line far to the left, with a tail around 15 ms against PostgreSQL's 60 ms. Even with no geography involved, crossing process boundaries and the local network stack is expensive.
