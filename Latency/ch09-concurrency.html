Exploiting Concurrency

Concurrency is about structuring many tasks at once; parallelism is about running them at once. The model you pick sets the latency and scalability you can reach.

1

Concurrency is not parallelism

Concurrency means making progress on several tasks over the same period, by switching between them. Parallelism means literally running them at the same instant on different cores (or SIMD lanes, or GPU threads). Concurrency hides waiting: while one request waits for the database, another runs. Parallelism shortens computing.

Little's law from chapter 2 still rules: L = C ÷ T. If throughput stays flat as concurrency rises, latency rises with it, because tasks queue for CPU, memory and I/O. A server whose requests take 20 ms and which receives 1,000 per second already has about 20 in flight; the concurrency model must handle that without throughput collapsing.

2

Concurrency models

A concurrency model is the set of abstractions you write concurrent code with. They differ in who schedules (kernel or user space), whether switching is preemptive or cooperative, and how much each switch costs. Tap a model.

Bars are rough relative scales to compare models, not measurements.

3

Coroutines: functions that pause

A coroutine can yield control back to its caller and later be resumed exactly where it left off. Many of them can share one thread. Below, three coroutines each print, yield, then print again and finish. You are the scheduler.

// shape of each coroutine (pseudo-Rust)
|| {
    println!("Yielding from coroutine {i}");
    yield;                    // hand control back; state is saved
    println!("Returning from coroutine {i}");
}
4

Event-driven concurrency and futures

An event loop waits for events (sockets ready, I/O complete, timers) using epoll, io_uring or kqueue, and dispatches each to a handler. Waiting for events may block; handlers must not, or every other connection stalls. Classic code passes callbacks; futures and promises (Rust's async/await on a runtime like Tokio) give the same model with straight-line code.

5

The actor model

Actors own their state and talk only by messages dropped into mailboxes. No shared memory, so no locks: the runtime guarantees an actor handles one message at a time. Good for many independent entities (a shopping cart per user, a game entity per player) and can span machines; the costs are message overhead, harder debugging, and ordering you must not rely on blindly.

6

Data and task parallelism

Data parallelism: the same operation on different slices of data. Summing an array split into k chunks takes about N ÷ k steps plus a combine. It needs balanced, local chunks (chapter 5's partitioning) and still obeys Amdahl's law. SIMD does it inside one core: AVX-512 handles 64 bytes, sixteen 32-bit integers, per instruction; GPUs do thousands per cycle.

Task parallelism: different, independent tasks at once, ideally pinned to cores (processor affinity keeps caches warm and memory NUMA-local). A product page needs specs, inventory, price and reviews: fetch them in parallel and the page waits for the slowest, not the sum.

7

Transactions: isolation costs concurrency

ACID: atomicity (all or nothing), consistency (invariants hold; not the distributed-systems meaning), isolation (concurrent transactions don't interfere) and durability (committed means survives crashes, which needs synchronous writes). Isolation is where latency is traded: the stronger it is, the more transactions wait or abort.

Serializability means the result equals some serial order, but gives no real-time promise; add linearizability and you get strict serializability. Snapshot isolation gives each transaction a frozen snapshot, so readers never block writers, but allows write skew. Watch it.

8

Concurrency control: lock first, or check later

Two-phase locking (pessimistic): a growing phase that only acquires locks, then a shrinking phase that only releases them. Serializable, but conflicting transactions wait. MVCC (optimistic): every write creates a new version; readers use the versions that existed when they started, so they never wait. Conflicting writers abort and retry. The price: extra storage and garbage-collecting old versions.

9

Putting it together: sequential vs. concurrent

The hands-on benchmark runs a 10 ms simulated operation (think I/O or a remote call) ten times: once in a loop, once as ten futures joined together on Tokio. Sequential took about 130 ms; concurrent about 13 ms. When you cannot make an operation faster, overlapping it is the next best thing.

async fn concurrent(n: usize) {
    let tasks = (0..n).map(|_| simulate_work());  // each awaits 10 ms
    join_all(tasks).await;                          // all wait together
}
