Predictive Techniques

The last trick is to guess. Fetch before you are asked, show the result before it is confirmed, compute before you know you need it, and be ready to roll back when the guess is wrong.

1

Predict, then start early

Some operations are slow and cannot be made faster. The last resort is to start them before anyone asks. Every predictive technique follows the same recipe: find the operations whose latency you cannot cut, build a predictor for when their results will be needed, and kick them off ahead of time.

A right guess feels like zero latency. A wrong guess is worse than not guessing: wasted bandwidth and compute, useful cache entries evicted, rollback overhead, and possibly side effects (a mail client that prefetches messages might trigger read receipts for mail nobody read). Try the trade-off.

Illustrative model: the operation takes 100 ms; a correct prediction makes it free, a wrong one still costs the full 100 ms plus the penalty.

Prefetching patterns

Prefetching hides read latency without keeping extra copies the way replication or caching do. Pattern-based prefetchers look only at the physical layout of the data. Pick a strategy and click a cell to "access" it. The blue cells are what gets fetched in advance.

Which prefetcher suits which workload?

hit rate on 400 simulated accesses, prefetch only the predicted next block(s)

A prefetcher matching the access pattern hides nearly all I/O. A mismatched one fetches data nobody reads. With random access, every prefetcher misses.

It is already happening underneath youThe OS readahead fills the page cache ahead of sequential reads. You can steer it with posix_fadvise(): SEQUENTIAL asks it to prefetch harder, RANDOM turns readahead off, and WILLNEED/DONTNEED hint at reuse. CPUs prefetch cache lines in hardware, and they also offer prefetch instructions you can issue yourself, but manual prefetching is easy to get wrong and can pollute the cache.

Optimistic updates: hide write latency

Apply the change locally, show it immediately, and synchronise in the background. Clicking "add to cart" updates the cart at once. Unlike plain async processing, you can keep making local changes on top of ones that have not synced yet. The trick is an optimistic view: a local database (SQLite, or a structure in memory) plus a shadow write queue of pending changes, merged when you read.

        Synchronising: who wins?

        With more than one writer, the queued changes have to be reconciled. Last-writer-wins is simple, but physical clocks drift. Logical clocks fix the ordering. In a Lamport clock, each process keeps a counter. It increments the counter on every event and attaches it to every message it sends. A receiver sets its counter to max(own, received) + 1.         Speculative execution

        Compute something before you know it is needed. If it is needed, the result is already there; if not, throw it away. Prefetching and optimistic concurrency control (chapter 9) are both special cases. In a CPU, spare execution units make speculation nearly free (branch prediction, out-of-order execution, at least until Spectre showed its security cost). In a distributed application, speculative work takes CPU, memory, bandwidth and connections away from real requests, so accuracy matters far more.

        Predictive resource allocation

        A new VM or database can take seconds or minutes to come up. Overprovisioning keeps spare capacity running all the time: it is fast but costs money, and a spike bigger than the reserve still waits. Prewarming provisions just before predicted demand arrives, using daily or seasonal cycles, scheduled events such as a launch or campaign, or live signals.
