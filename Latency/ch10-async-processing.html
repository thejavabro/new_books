Asynchronous Processing

When you cannot make an operation faster, you can stop waiting for it. Asynchronous processing hides latency by overlapping work, but it needs backpressure and good error handling.

1

Hiding latency: stop waiting

Part 4 is about latency you cannot remove: hardware limits, third-party systems, physics. You can still hide it. In synchronous processing each task runs to completion, including its I/O, before the next starts. In asynchronous processing a task starts its I/O and the program moves on, reacting when the result arrives. A backend calling services A and B finishes when both are done, not after the sum.

Async, concurrent, parallelConcurrency is running many tasks over the same period, parallelism is running them at the same instant, and asynchrony is a way of structuring code around operations that take time. Async code can be concurrent on one core or parallel on many; it guarantees neither. And if the I/O cannot actually overlap, async just adds bookkeeping.
2

The event loop

The heart of an async system: poll for events (epoll or io_uring on Linux, kqueue on macOS, IOCP on Windows), process each one, run scheduled tasks, repeat. Polling may block, with a timeout so background work still runs (or busy-poll for the lowest latency). Handlers never block; they register interest in the next event and return. Follow one request.

loop {
    let events = poller.poll(timeout);   // the only place we block
    for ev in events { handle(ev); }       // short, non-blocking
    run_scheduled_tasks();
}
3

Asynchronous I/O techniques

I/O multiplexing lets one thread watch thousands of sockets instead of a thread per connection. On top of it, several tricks hide round trips.

Request batching

100 requests to a database

Batching responses too means a client waits for the whole batch; send responses individually, or tune the batch size, when they are latency-sensitive.

Request hedging

service: usually 10–20 ms, 5% of calls take 300–1000 ms
-p50
-p99
-load on the service

Send identical requests, use the first reply, ignore the rest. Only safe for idempotent operations (reading a profile yes, charging a card no), and only worth it while the extra load does not itself slow the service. Decide what to do when the first reply is an error.

Buffered I/O

writing 1 MB in 100-byte records

Accumulate in memory, issue fewer, bigger system calls; pair with readahead for reads. Memory mapping goes further: the file appears in memory, the OS pages it in on demand and flushes writes in the background. Convenient and often fast, but page faults bring tail latency that is hard to remove, the working set must fit in memory, and a crash can leave writes unflushed.

4

Deferring work: priorities and stealing

Do what the user waits for now; do the rest later. A social network shows your post immediately and updates engagement metrics afterwards; a shop confirms the order and reconciles inventory off-peak. Deferral moves latency spikes elsewhere, so scheduling matters. Priority queues run urgent work first; aging raises a waiting task's priority so low-priority work does not starve.

Work stealing: an idle worker takes tasks from the tail of a busy worker's queue (the tail, to stay out of the owner's way), preferring nearby workers for cache locality. Task size matters: too fine and stealing overhead dominates, too coarse and there's nothing to balance.

5

Resource pools: pay set-up costs once

Creating threads, allocating buffers and opening connections all cost time. Pools pre-create them and lend them out. A fresh connection to a remote database pays DNS, the TCP handshake and TLS before the first query.

6

Backpressure: async without drowning

Async makes it easy to accept work faster than you can finish it. Then queues grow and, by Little's law, so does latency. Backpressure is feedback from consumer to producer. Push the producer past capacity and pick a strategy.

-queue after 10 s
-latency of last request
-requests dropped or refused

7

Errors, timeouts and observability

Async work fails in pieces. Some uploads in a batch succeed and others fail: track each operation's state so you can retry or report precisely. Transient failures want retries with exponential backoff, and retries want idempotent operations (a retried payment must not charge twice). Timeouts stop hung operations from piling up; cancellation stops unwanted ones, and both need robust cleanup.

Tracing follows one request across asynchronous hops by passing a trace ID that every component tags its timing with. Metrics to watch: active tasks, pool utilization, queue depths, work-stealing activity, error rates by category, retry success. Measure queue wait, processing and external wait separately, and keep the instrumentation itself cheap.
