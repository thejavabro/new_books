Modeling and Measuring Latency

Two simple laws tell you what latency to expect. Then the hard truths: latency is a distribution, the tail finds your users, delays compound, and naive benchmarks lie.

1

Little's law: concurrency = throughput × latency

Before measuring anything, ask what latency you can reasonably expect. Little's law, borrowed from queueing theory, links three averages:

C = T × L   so   L = C ÷ T

C is concurrency (requests in the system at once), T is throughput, L is average latency. A service doing 1,000 requests per second at 50 ms average latency has about 50 requests in flight. Turn it around: if you let 200 requests pile up and you can only process 1,000 per second, each waits about 200 ms on average. Halve the queue, or double throughput, and latency halves.

-average latency L = C ÷ T

The same idea as a queue: work arrives at some rate, servers drain it. If arrivals outpace what the servers can complete, the queue, and with it latency, grows without bound.

2 tasks arrive per step, each takes 1 step
Where it breaksLittle's law assumes latency does not depend on load. Real systems slow down as concurrency rises (context switches, lock contention, algorithmic effects), so treat the law as a sizing tool and always measure.
2

Amdahl's law: the serial part wins

Single cores stopped getting much faster, so we parallelize. Amdahl's law says how far that goes for a fixed-size job: if a fraction P can run in parallel on N units,

speedup = 1 ÷ ((1 − P) + P ÷ N)

The ceiling is 1 ÷ (1 − P), no matter how many cores. Half-parallel code never gets more than 2×.

-speedup
-ceiling with infinite cores

The order endpointParse and validate (5 ms), look up shipping and prices (15 ms), calculate and insert the order (30 ms). Only the lookups can fan out, so P = 15/50 = 0.3. Two cores give about 1.2×, eight about 1.35×, and the curve flattens near 1.4×. Set P to 30% above to see it.
3

Latency is a distribution, and the tail finds you

"The request takes 10 ms" is almost always an average, and the average hides the shape. Minimum and maximum mislead too. Look at percentiles: p95, p99, p99.9 are the tail latency. It is tempting to dismiss them as noise, but users hit them more often than intuition says, especially when one request fans out to many servers and must wait for the slowest.

Following Dean and Barroso's "The Tail at Scale": each sub-request is usually 10 ms but occasionally takes 1 s. If a user request fans out to N servers, the chance that at least one is slow is 1 − (1 − p)N.

-of user requests take over 1 s

Latency compounds

A request's latency is built from parts: propagation (distance ÷ signal speed), transmission (packet length ÷ link rate), processing (actually doing the work) and queuing (waiting for a CPU, a lock, a database). How the parts combine depends on structure. Roll five components with random latencies and compare.

each component: usually 5 to 15 ms, sometimes 80 ms

Serial: sum of all. Parallel: the slowest one. Quorum (3 of 5, as in Raft or Paxos): the third fastest, which shrugs off one or two stragglers.

6

Measuring without fooling yourself

First decide what to measure from whose point of view: the user's, or another service calling your API. Then control the environment. The observer effect bites when the load generator shares a machine with the system under test. The sneakier trap is coordinated omission: a benchmark that sends a request, waits for the reply, then sends the next one slows down exactly when the server stalls, so it records one slow request where real users would have seen dozens.

server pauses 200 ms for GC at t = 300 ms
-requests recorded
-recorded as slow (> 20 ms)
-measured p99

Fixes: send at a fixed rate and collect replies asynchronously, or use a tool such as HdrHistogram that can correct for the expected interval.

Plotting a latency distribution

The book's hands-on part pings a host once a second (fixed intervals avoid coordinated omission), stores samples, and only writes the file at the end so disk I/O does not disturb the measurement. Then it plots three ways. Here is a simulated ping run.

# the gist of a fixed-interval sampler (illustrative)
for _ in range(samples):
    rtt = ping(host, timeout=1.0)
    if rtt is None: warn("timeout, outlier lost"); continue
    values.append(rtt)
    sleep(1.0 - rtt)          # keep a steady 1 s cadence
save_csv(values)              # write only after measuring
