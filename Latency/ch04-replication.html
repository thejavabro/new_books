Replication

Copies of your data near every user cut read latency, but every copy has to be kept in step. The consistency model you choose sets the floor for how fast writes can be.

1

Why replicate: copies close to everyone

Colocating with one location raises two questions: what if that location fails, and what if your users are in many places? Replication keeps several copies of the same data in different places and keeps them in step. Reads can go to the nearest copy, which is the latency win. A CDN is replication of web assets.

The price is coordination. The stricter the promise about how copies agree, the more messages a write needs before it can be acknowledged, and messages cost round trips. Replication also costs storage (strongly consistent setups need at least three copies) and overlaps with partitioning (chapter 5) and caching (chapter 6).

Pattern: replicate data for faster accessServe each request from the nearest copy. Then choose a consistency model that your application can live with, because that choice sets the floor for write latency.
2

Availability, fault tolerance and scale

Replication also buys availability, and downtime is just the far end of tail latency. Availability is quoted in "nines". Fault tolerance is a stronger idea: some components fail and nobody notices at all. And replication helps scale out, adding nodes that serve in parallel, rather than scaling up one bigger box.

Consistency models: what a reader may see

The consistency model is the contract that answers: after a write, which copies show it, and when? At one end, strong consistency (linearizability) pretends there is a single copy. At the other, eventual consistency only promises copies converge some day. Play writes into three replicas, then read from a random one.

Linearizability is about single operations on single objects (get and put on one key). Serializability, a database idea, is about groups of operations on many objects; chapter 9 returns to it. Eventual consistency is not automatically faster for reads: if the app must read several replicas to find the newest version, or the store performs read repair, reads get slower. It is clearly faster for writes, which stay local.

Read-your-writesWith asynchronous replication you can write to one replica and immediately read from another that has not heard yet, and your own update "vanishes". Check whether your store promises read-your-writes before relying on it.
Local-firstPush the data and logic all the way onto the user's device, sync later with CRDTs. Network latency disappears from the interaction; the cost is a very relaxed consistency model, since devices can be offline for a long time.
5

Synchronous vs. asynchronous replication

Asynchronous: the primary acknowledges as soon as it has the write, then forwards it in the background. Writes are fast; a crash before forwarding loses data, and replicas lag. Synchronous: the primary waits for replicas to confirm before acknowledging. Safer, slower. Adjust the distance to the replicas and crash the primary.

6

State machine replication and quorums

State machine replication keeps every node executing the same commands in the same order, so all reach the same state: that gives linearizability and fault tolerance. It relies on consensus (Paxos, Raft, Viewstamped Replication) and majority quorums. For crash-type (non-Byzantine) failures, tolerating f failures needs 2f + 1 nodes. Byzantine failures, where nodes lie or corrupt data, need more. Click nodes to fail them.

Cluster size

Bigger clusters survive more failures but cost more, are harder to run, and wait on more acknowledgements spread over a wider area.

7

Case study: Viewstamped Replication

VSR (Oki and Liskov, 1988; revised 2012) is a primary–backup protocol. Time is divided into views; each view has one primary, and a view change picks the next primary deterministically, which is simpler than Raft's elections. TigerBeetle has renewed interest in it. Step through one normal operation and watch where latency compounds.

Putting it together: a primary–replica key–value store

The hands-on project builds an in-memory key–value store and a tiny protocol with three messages: Put (primary pushes each write), Join (a replica asks to be added) and Snapshot (the primary sends everything it has to a new replica). Writes go to the primary only; replicas serve reads locally. Try it.
