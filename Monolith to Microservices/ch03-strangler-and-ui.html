Splitting the Monolith: Strangler Fig and UI Composition

Migration patterns let a new service grow around the old system instead of replacing it in one go. The first and most useful is the strangler fig: intercept calls at the edge and redirect them, one piece at a time.

1

Can you change the monolith? Copy, don't cut

The first question is whether you can (or want to) change the existing system. It may be vendor software, written in a technology nobody knows anymore, too fragile to touch, or busy with other teams. The book recalls a C library the client refused to share the source of for months; years later the sponsor admitted they had lost it. Several patterns work without touching the monolith at all.

Copy the code; don't remove it yetIf the monolith is well factored, copying code into the new service saves time. Leave the original in place for now: it is your rollback point and lets you run both side by side. Remove it once you're happy. If you reimplement instead, keep each rewrite to days or weeks; when timelines stretch to months, rethink.
2

Pattern: strangler fig application

Named by Martin Fowler after figs that seed in a tree's branches, grow roots down around it, and eventually stand on their own. New code wraps the old; old and new coexist; each step can be reversed; you can stop at any point and keep the benefit. Three moves: identify what to migrate, implement it in the new service, reroute calls. Here it is with an HTTP reverse proxy, moving Payroll.

Deployment is not releaseThe new service can sit in production, deployed but not called, until it is ready. That lets you get comfortable running it, test it in place, and only then flip traffic. Strangler fig, parallel run and canary release all rely on this separation.
3

Where the strangler fits, and where it doesn't

It shines when you can map an inbound call to the functionality you want to move. It is ideal for black-box and vendor systems, and avoids getting in the way of other teams in the monolith.

4

Try it: configure the proxy

Routing on URI paths is easy for a dedicated proxy like NGINX (prefer one over a hand-written proxy, which the author found painfully slow). Tick which resources have been migrated, set a canary share, then fire traffic. Routing on a value buried in a POST body is possible but harder.

5

Changing protocols, service meshes, FTP

A proxy could also translate protocols, say SOAP in, gRPC out. The book is wary: logic piles up in a shared layer many teams must edit, a new source of contention. "Keep the pipes dumb, the endpoints smart." Better to let the service speak both protocols for a while.

Service mesh (Square)Each service instance gets its own local proxy, configured and monitored through a control plane. No central smart pipe. Square used Envoy-based proxies to move from a homegrown RPC to gRPC with less per-service change. The idea is sound; the book advises letting the tooling mature before committing.
Not just HTTP (Homegate)A Swiss real estate site let customers keep uploading listings by FTP. It watched the FTP log and passed new files to an adapter that called a new REST listings service, which published ads faster. Both import paths ran side by side for a while.
6

Intercepting messages

If the monolith is driven by a queue, the idea is the same: intercept and redirect. Two options.

Batch file uploads? Intercept the file, pull out the records you've migrated, forward the rest. With creative thinking the strangler fits a surprising range of protocols.

7

Changing behavior while migrating

Rollback is only safe if old and new behave the same. Fix bugs or add features in the new Payroll service and a rollback reintroduces the bugs or removes features from customers. So try to freeze behavior while it moves. The longer the migration, the harder the freeze is to hold.

Illustrative curves: pressure to "just slip this feature in" grows with time, and each change that slips in makes rollback riskier.

8

Pattern: UI composition

The user interface is another place to splice old and new. At The Guardian the plan was page-by-page migration, one vertical (travel, news, culture) at a time, with old links redirected. But the very first release was smaller: one widget listing the top 10 travel destinations, served by the new platform and spliced into the old travel pages with Edge-Side Includes. Orbitz did similar with "modules" (search form, map, booking) owned by different teams. Toggle which widgets come from the new services, then break one.
