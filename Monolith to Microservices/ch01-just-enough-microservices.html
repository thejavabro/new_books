Just Enough Microservices

Before pulling anything apart, get the vocabulary straight. Microservices are independently deployable services modeled around a business domain, and almost everything else in the book follows from those two ideas.

2

Cohesion of technology vs. cohesion of business

Music Corp, the book's fictional CD retailer, wants customers to pick a favorite genre. In a classic three-tier system the UI team, the backend team and the DBA team each change their layer, then deploy in the right order. The layers are cohesive by technology but not by business function, so nearly every feature cuts across all of them. Conway's law explains why the layers exist: we used to group people by skill, so we built systems in the same shape.

The alternative groups code by business capability. A Customer service holds a sliver of UI, logic and storage for customers, so the genre change stays inside one service. Whether that service has internal layers is its own business.

3

A monolith is a unit of deployment

In this book "monolith" doesn't mean "legacy" or "bad". It means that everything has to be deployed together. That covers several shapes, and the modular monolith in particular is a perfectly good destination for many organizations.

What monoliths do wellSimple deployment topology, simpler developer workflow, easier monitoring, troubleshooting and end-to-end testing, and trivial code reuse. A monolith is a valid architectural choice.
Where they hurtDelivery contention: more people working in the same place get in each other's way. Confused ownership, clashing changes, teams wanting to release at different times.
4

Microservices buy you options, at a price

Independent deployment opens up ways to scale, isolate failure, mix technologies and let more people work in parallel. But every one of those comes with distributed-systems costs. Open each card to see the trade.

Size is the least interesting questionLines of code depend on the language. "Size" is contextual: a 100K-line system feels small to its 15-year veteran and huge to a newcomer. Worry instead about how many services you can handle, and where the boundaries go. One useful angle: aim for as small an interface as possible.
Don't buy new tech on day oneKubernetes, containers, a new language: none is required. A migration already brings plenty of new problems. Start with a stack you know and add technology when a specific problem calls for it. And don't forget the UI: leaving it as a monolithic blob limits the gains.
5

Coupling, cohesion and information hiding

Cohesion: the code that changes together, stays together. Coupling: how much changing one thing forces a change in another. Constantine's law says a structure is stable when cohesion is high and coupling is low. Monoliths often manage the opposite of both. The book sorts coupling into four kinds; pick one.

Information hiding (Parnas, 1971)Separate what changes often from what is stable, and hide the volatile part behind a stable boundary. Expose as little as possible: you can always share more later, but once something is in the interface it's hard to take back. Design interfaces "outside-in": actually ask the consumers what they need, as you would for a user interface.

Try it: temporal coupling

The Warehouse service asks Order for order details, and Order synchronously asks Customer. For the request to work, all three must be up at the same moment. Knock services over and see what each design tolerates.

7

Try it: share only what the warehouse needs

Some coupling is unavoidable: to ship a CD, the warehouse must know what to pack and where to send it. That is domain coupling. But we choose how much to share. Sending the whole order leaks prices and payment data to a service that doesn't need them. The book's answer is a new domain concept, a Pick Instruction. Build one.

Order Processing could send the instruction with an API call, or publish an event the Warehouse listens for. The event flips the dependency: Order Processing no longer needs to know the Warehouse exists.

8

Just enough domain-driven design

An aggregate is a real domain concept (an Order, an Invoice) with a life cycle, so it behaves like a state machine. The code that changes its state lives with the state. Others can ask it to change, but the aggregate can say no. Ask this Invoice for transitions:

A bounded context is a larger organizational boundary, such as the warehouse or finance, holding one or more aggregates and hiding internal detail (what forklift trucks the warehouse uses is nobody else's business). Both make good service boundaries. Start with services the size of whole bounded contexts; split along aggregate lines later, and you can even hide that split behind a coarser API.
