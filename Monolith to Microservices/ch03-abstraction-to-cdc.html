Splitting the Monolith: Branch by Abstraction to Change Data Capture

When the functionality you want sits deep inside the monolith, or when you need proof that a new implementation is right, or when you cannot touch the monolith at all, reach for these four patterns.

1

Pattern: branch by abstraction

Notifications are wired deep into the monolith, so a proxy can't intercept them. Reworking them on a long-lived source branch means a painful merge later, against the grain of continuous integration (and the State of DevOps data favoring trunk-based development). Branch by abstraction instead lets old and new implementations live side by side in the same codebase, with only one active. Step through it; the code is a sketch.


  

  
The middle phase can last months: Jez Humble describes GoCD switching its persistence layer from iBatis to Hibernate this way while still shipping to customers twice a week. The new service can be deployed and tested in production throughout, because nothing calls it until the switch.






  
2
Try it: switch implementations, with a fallback

  
The switch should be easy to flip both ways, typically a feature toggle in configuration. Steve Smith's variation, verify branch by abstraction, adds an automatic fallback: if the new implementation fails, call the old one. It is more complex to reason about, and if both are stateful they need shared, consistent data.

  

    

      

      
      
    

    

    

  

  
Clean up after yourselfOnce the new service handles everything: delete the old implementation, delete the toggle (stale flags are a real hazard), and optionally the abstraction too, though a simple interface that improved the code can stay.






  
3
Pattern: parallel run

  
Instead of calling old or new, call both and compare. The old one stays the source of truth until the comparison earns trust. The author used this replacing a bank's credit derivative pricing: both systems priced every trade, a nightly batch reconciled the results into a spreadsheet for the experts, and many differences turned out to be bugs in the old system. After a month the new system became the source of truth. Run your own.

  

    
    
    
    

    

    

  






  
4
Verifying without side effects, and related techniques

  
Compare functional results and non-functional ones: latency, time-outs, failure rate. If the operation has side effects, like sending an email, you mustn't do it twice. Replace the lowest-level sender in the new service with a Spy that records what it would have sent, and verify later (out of band is usually enough). Keep the real network call to the new service, or you stop testing the thing you care about. GitHub's Scientist library does side-by-side comparisons in code. All are forms of progressive delivery (James Governor's term). Parallel run is a lot of work; the author has used it only once or twice, for high-risk changes. A cousin: N-version programming in fly-by-wire aircraft keeps several implementations permanently and votes on the answer.






  
5
Pattern: decorating collaborator

  
Music Corp wants loyalty points on every order, without touching the complicated order code. Let the call pass through to the monolith as normal, then, based on the result, call the new Loyalty service from the proxy. To the outside it looks like the monolith collaborates with the service.

  

    
    

  

  
Keep the proxy simple: the more logic it gains, the more it becomes a technical microservice of its own. If the information you need isn't in the request or response, think hard before using this pattern.






  
6
Pattern: change data capture

  
React to changes in the monolith's database instead of to calls. When a customer enrolls, the monolith's response says little, so a decorator wouldn't have enough to print a loyalty card. Instead, watch for inserts into the LoyaltyAccount table and fire a "loyalty account created" event onto a broker; the printing service batches them. Which application pattern fits?

  
The author's preference order is roughly: strangler first, branch by abstraction when the code is too deep, and decorator or CDC when you can't change the monolith. Answer three questions.

  

    
Can you change the monolith's code?

    
Can the functionality be reached by intercepting calls at the edge?

    
Is it high-risk enough to verify old vs. new on live traffic?

Recap on one page

  

    
Branch by abstractionAbstraction, migrate callers, new impl, toggle, clean up. No long-lived branches.

    
Parallel runCall both, compare, old stays the truth until trusted. Spies stop duplicate side effects.

    
Decorating collaboratorAct on what goes in and out of the monolith. Needs enough information in the call.

    
Change data captureReact to data changes. Prefer log-based tooling; few triggers; batch is laggy.

    
Mix and matchMost migrations use several patterns; none fits every case.
