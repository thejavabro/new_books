Decomposing the Database: Living With Shared Data

Microservices should hide their data. Most monoliths start with one big shared database. These patterns either make the sharing less harmful or move the source of truth safely.

1

Pattern: the shared database

Several services reading and writing one schema is implementation coupling at its worst. You can't tell what is safe to change, because you don't know which parts others use. And who controls the data? If three services can change an order, its state machine is spread across all three, with no guarantee they agree. The book accepts direct sharing in only two cases: read-only static reference data (country codes, postcodes) and a database deliberately published as an endpoint (database-as-a-service interface, below). Rename a column and see who breaks.

"Database" here means a logically isolated schemaOne database engine can host many schemas. This chapter is about logical separation; physical separation comes later. Some NoSQL stores (DynamoDB, for one) only have tables and access rules, which blurs the idea.
2

Pattern: database view

A view projects a limited, stable shape over the real schema: a cheap form of information hiding. At a bank, the author's team found 20-odd unknown applications reading their schema with one shared login; they had to disable the account and wait for complaints to find out who they were. 3

Pattern: database wrapping service

Sometimes the mess is too dangerous to untangle. An Australian bank had 30 years of business-banking "entitlements" logic (who may see and move money in which account) living in stored procedures, and the database was buckling. Splitting it risked locking people out of their money, or worse. The plan: stop it getting worse. Put an Entitlements service in front of the schema, route access through it, and push teams to store their own new data elsewhere.

4

Pattern: database-as-a-service interface

Some consumers really need SQL: reporting tools like Tableau, big ad hoc queries. Give them a dedicated read-only database, separate from the one you use internally, kept up to date by a mapping engine. The internal schema can change freely as long as the mapping keeps the public one stable. (Martin Fowler calls the common case a reporting database.) The public copy always lags; how much depends on the mapping engine. Write something and watch.

More flexible than a view (the public database can even be a different technology) but more work. Start with a view if it meets consumers' needs. The author now favors change data capture tooling over batch jobs that silently fail or overrun. Consider exposing when the copy was last updated.

5

Transferring ownership: expose it or move it

Bandages aside, decide where data should live. If the new service manages an aggregate's life cycle, its data must move with it. If it only needs data the monolith still owns, the monolith should expose it properly.

6

Pattern: synchronize data in application

Trifork helped move a national store of Danish medical records from MySQL to Riak without long downtime and without losing a single record. The application itself kept both databases in sync, in three stages. Step through, and at each stage try failing the new database.

This fits splitting a schema before splitting the code. If the monolith and a new service both try to keep two schemas in sync, it gets very complicated; it's manageable only when exactly one of them is writing at any moment.

7

Pattern: tracer write

Insisting on a single source of truth at all times forces one big switchover. A tracer write tolerates two sources for a while and moves data a slice at a time, along with its consumers. Square split its food-delivery Order (one concept serving customers, restaurants and drivers) by creating a Fulfillments service, back-filling it with a feature-flagged worker that used the new API, writing updates to both systems, and moving consumers over. Whatever the method, it is eventual consistency. Decide what window is acceptable, and run a reconciliation check (even a couple of SQL queries) so drift doesn't go unnoticed.
