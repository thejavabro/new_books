Decomposing the Database: Splitting It Apart

Splitting a schema means deciding what to split first, finding seams in the data, and replacing joins and foreign keys with code. Static reference data gets four options of its own.

1

Logical versus physical separation

Splitting a database here mainly means logical separation: each service gets its own schema. Those schemas may still share one database engine. Logical separation buys independent change and information hiding; physical separation adds robustness and removes resource contention, at a cost (another cluster, licenses). You can only choose physical separation once you've done the logical split.

2

Split the database first, or the code?

An extraction isn't finished until both the code runs in its own service and its data lives in its own schema. Which half goes first?

The author's hot takeIf I can change the monolith and I'm worried about performance or data consistency, split the schema first. Otherwise split the code first and use it to learn about data ownership, but be honest about whether you'll actually finish the data split. Whatever you do, capture every schema change in a version-controlled delta script (the author co-wrote DBDeploy; today he points to Flyway).
3

Patterns along the way

Four smaller patterns help you get from a shared schema to separate ones. Pick one.

4

Pattern: split table

Music Corp's Item table mixes catalog details and stock levels, but Catalog and Warehouse are becoming separate services. Assign each column an owner. (Tip: you might split the table inside the existing schema first, then move it.)

When two parts of the code write one columnCustomer sign-up flips status from NOT_VERIFIED to VERIFIED; finance flips it to SUSPENDED for unpaid bills. Status is part of the customer's state machine, so it belongs to the new Customer service; Finance will have to call it to suspend someone. And with the split you lose the database transaction that used to cover both. Ask whose existing domain concept owns the data.
5

Pattern: move foreign-key relationship to code

The monthly best-sellers report joins Ledger (Finance) to Albums (Catalog) on SKU: "400 copies of Born to Run" instead of "400 of SKU 123". Split the services and the join moves into Finance's code: query the ledger, then ask Catalog about each SKU. It will be slower. How much slower?

Illustrative numbers: ~5 ms per query, ~20 ms per service call. A monthly report can be slow and cached; a hot path can't. Measure actual latency (a distributed tracing tool like Jaeger helps) against what is acceptable.

Data consistency: Catalog wants to delete SKU 683

With one schema, the foreign key stopped you deleting an album the ledger referenced. Now nothing does. Try each policy.

First check you're not splitting an aggregateLedger and Albums are two separate aggregates with a relationship. An Order and its order lines are one aggregate: move them together. A bigger bite of the schema sometimes takes both sides of a foreign key with you.
6

Static reference data: four options

Country codes (249 entries in ISO 3166-1; the last new one was South Sudan, 2011, with months of notice), clothing sizes, postcodes. Small, rarely changing, used everywhere. The book offers four patterns, and then says what the author would pick. Describe your data:

Volume of data
Must every service see exactly the same version at all times?
Do you need to join to it in SQL?
Is spinning up a new service cheap (a day or less)?
