Style Guides and Rules

Rules are a tool for managing a codebase across time and thousands of authors. Good ones optimize for the reader, favor consistency, and are enforced by machines wherever possible.

1

Why have rules?

Most engineering organizations have rules (mandatory) and guidance (recommended practice). At Google they live mostly in a style guide per language. Their purpose isn't tidiness for its own sake; it's to encourage good behavior and discourage bad, so the codebase stays manageable as it grows across time and thousands of authors. Rules are a tool for scale.

2

Guiding principles for creating rules

A rule is worth having only if it serves agreed goals. Google's style guides are built on five principles. Tap each.

Optimize for the reader

Code is read far more often than it is written. Our own examples of the kind of trade the guides make: tedious to type beats hard to read.

3

Be consistent

Consistency lets engineers move between projects without relearning, makes code easier to read ("chunking" familiar patterns, the way chess experts see positions), and lets tools understand and change the code at scale. A comparison the author makes: offices worldwide that share the same layout make it easy to find the restroom. Even when the choice itself barely matters, picking one matters. Mix the styles and see how much a reader has to adjust.

Consistency with the outside world tooGoogle's Python guide once required two-space indents to match its C++ code, since early Python mostly wrapped C++. As Python engineers mostly read other Python, that choice cost effort every time they looked at outside code, and made open-sourcing painful. New guides, like the one for the Starlark build language, use four spaces like the wider community. Consistency at scale includes the world outside your walls.
4

What goes in the style guide

Rules fall into three broad categories: avoiding danger (features that are error-prone or hard to get right), enforcing best practices (ways to write that keep code readable and maintainable), and building in consistency (choices that matter only because everyone should make the same one). Sort these.

Which category?

Not in the guideRules that are self-evident are deliberately left out. The C++ guide has no ban on goto, because C++ programmers already avoid it. If only one or two people get something wrong, adding a rule for everyone doesn't scale. The guide isn't a legal code: not being banned doesn't make something a good idea.
5

Changing the rules

Rules should change when the reasons behind them stop holding. Google's guides record the rationale for each rule so that, later, people can see when the facts have shifted. Step through two real cases.

The style arbitersEach language's guide is owned by a small group of long-time experts who decide changes as engineering trade-offs within the guide's goals, not by personal preference. Anyone can propose a change; the arbiters weigh it against the guide's goals.
Exceptions and guidanceWaivers are possible but not granted lightly; the arbiters decide, for example letting a genuinely global utility macro skip the project-prefix naming rule. Beyond rules, Google publishes guidance: tips, best-practice articles and language "primers" that people should know but that aren't mandatory.
6

Applying the rules: let machines do it

Teaching and code review spread rules, but they don't scale and humans are inconsistent. Wherever possible, encode rules in tools. Error checkers catch dangerous constructs; formatters end arguments about whitespace. Go shipped gofmt from its first release: no options, so all Go code looks the same, and tools can rewrite code without noisy diffs. An informal 2018 survey by Google's C++ library team estimated that roughly 90% of the C++ style rules could be checked automatically. Social rules, like keeping changes small, stay with humans. Try a formatter on a messy snippet.
