Continuous Integration

CI means continuously building and testing every change as it integrates with everything else. At scale it is a system that decides which tests to run, and when.

1

Continuous integration, defined

The classic definition of CI is a development practice where team members integrate their work frequently, each integration checked by an automated build and test. Google's version widens it: CI is the continuous assembly and testing of the entire complex, fast-moving ecosystem, not only your code but your dependencies, configs, data and the services you call, which change on their own schedule. The core goal is to catch problems as early as possible, when they're cheapest.

The core questionsWhat should we test? (Everything that can break.) When should we test it? (As early as is affordable, and again later as the environment shifts.) And how do we make the answers fast and trustworthy enough that engineers act on them?
2

Fast feedback loops

A bug costs more the further "right" it travels: someone unfamiliar with the change must triage it, the author has to reload context, and others (eventually users) are hurt. Each place where a change meets a testing scenario is a feedback loop. Pick where the bug is caught.

Accessible, actionable feedbackResults must be easy to find and understand: which test, which change, a link to logs. Takeout's scenarios below are largely about this.
Experiments and feature flagsFlags and A/B experiments are feedback loops too: they let a change meet real users at small scale, with a fast way to switch it off.
3

Continuous Build and Continuous Delivery

CI automates two things. The Continuous Build (CB) integrates the latest changes at head and runs build and tests; "breaking the build" includes breaking tests. The Continuous Delivery pipeline then picks a green version, creates a release candidate (a cohesive, deployable unit with its configuration), and promotes it through environments toward production. Static configuration belongs in the RC too, tested with the code that uses it: a large share of production bugs are "silly" config problems.

Two headsTrue head is the latest committed change; green head is the latest change the CB has verified. Engineers often sync to green head while coding but must sync to true head before submitting. Most teams cut release candidates at green head. Artifacts shouldn't be rebuilt as an RC moves between environments; containers and Borg help keep it consistent.
4

Continuous testing: presubmit versus post-submit

The rule of thumb: run only fast, reliable tests on presubmit, usually the project's unit tests. Accept some loss of coverage, then catch the rest on post-submit, where longer and less stable tests are fine, as long as you have mechanisms (like rollbacks) to handle what gets through. Unreliable presubmit tests are especially costly: many engineers end up debugging a failure unrelated to their change.

Where should this test run?

Release candidate testingTest the whole RC again, larger tests included, because it's what you'll deploy and the environment may have changed. Run it against prod-like configuration.
Production testingRun the same suite against production too. Bugs that slip into prod are inevitable; prod tests catch those caused by the environment, not your code.
Hermetic testingTalking to live backends is flaky, so larger presubmit tests often use a self-contained environment with no external dependencies. Same inputs, same results, so a failure points at your change. Record/replay systems go further: cache live backend responses once and replay them hermetically.
5

CI is alerting

A sidebar draws the parallel with production monitoring. Both CI and alerts exist to surface problems quickly; CI just sits earlier. So lessons transfer: an alert that fires and doesn't need action is noise, and so is a flaky test. Aim for signals that are actionable. Not every failing test is an emergency, and a 100% passing rate is as unrealistic a target as 100% uptime. A test is better thought of like an alert threshold: tune it so that failure means something.

6

CI at Google: TAP

Google's continuous build, the Test Automation Platform (TAP), sees more than 50,000 unique changes and runs over four billion test cases a day. Teams define a fast presubmit subset; after submit, TAP batches changes together (it can't run every test on every change at more than one change a second), runs the affected tests, and must work out which change broke what. Try it: one change in this batch broke a test. Test a contiguous range by tapping its last change.

Culprit finding

Split and rerunTAP automatically splits a failing batch into individual changes and reruns them in isolation.
Bisect toolsBecause splitting can be slow, engineers also have tools to binary-search a batch.
Roll backThe Build Cop's best tool is the rollback; TAP can now roll back automatically when confident. Tests give confidence to change, rollbacks to undo.
Resource constraintsTAP only runs tests whose build graph depends on the change, and limits presubmit to the affected project. Flaky tests are deliberately excluded or retried, and big, slow suites run less often.

"But I can't afford CI"

Google has more resources than most, but many of its own products grew too fast to build CI early. The book's answer: count what you already pay for problems found in production, the user impact, and the stress and demoralization of constant firefighting. Start small: even a little automated presubmit testing and a post-submit build buys back a lot, and you can grow from there as the cost of escaped bugs becomes visible.
