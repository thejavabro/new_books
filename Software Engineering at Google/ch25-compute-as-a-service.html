Compute as a Service

Running code needs machines, and managing them by hand does not scale. A shared, automated compute service changes how software is written; the Afterword then sums up the book.

Taming the compute environment

Compute as a Service (CaaS) means engineers ask for "resources to run my stuff" and an automated system handles machines. Google's Borg (started in 2003) was a precursor of systems like Kubernetes and Mesos. The story starts with a 2002 complaint from Jeff Dean: running one data-processing task meant a list of 50+ machines, starting and watching a process on each, no automatic migration when a machine died, and a hand-edited "sign-up" file to keep jobs from colliding. Step through how automation removes the toil.

2

Containers, multitenancy and rightsizing

One program per machine wastes resources: there are more job types than machine types, machines take months to arrive (so you over-buy), and old machines linger. The fix: each job declares CPU, RAM and disk, and the scheduler bin-packs containers onto a shared pool. Containers isolate neighbors, the chapter's "my neighbor's dog barks in my RAM" problem, where a leaky job starves others. Borg once hit process-ID exhaustion from a thread-leaking job.

RightsizingAsking humans to guess resource numbers is flawed: guessing costs time and the numbers drift until a spike finds no slack left. Automating it is hard. Google only recently reached the point where rightsizing automation sets more than half of Borg's resource usage, and an even larger share of configurations: "easy things easy, complex things possible".

Serving and batch jobs turn out to be complementary. Serving jobs must keep slack for spikes and outages, so their machines might really be only 30% used. Borg fills the slack with low-priority batch work and takes it back on demand: freezing batch for CPU, killing it for RAM.

Writing software for managed compute: architect for failure

Take a million documents at one second each: about 12 days on one machine, or 100 minutes across 200 workers. Borg may kill and move any worker at any time. If work is statically split, each kill loses up to a worker's whole share; split it into 1,000 chunks handed out dynamically and a kill loses at most one chunk. Run it below (20 workers shown).

PetsNamed, hand-configured, nursed back to health by a panicking human. Maintenance grows linearly or worse with the fleet.
Cattlereplica001 to replica100, stamped out automatically from an image. Failures self-heal without anyone's weekend.

Serving jobs get advance notice before a planned reschedule, so they can stop accepting requests, finish in-flight ones, and let the load balancer route elsewhere. Harder cases are "leaders" holding state, data sharded so each server is the only holder of 1%, and servers known by hostname.

4

Managing state and connecting to services

Treat in-process and local state as transient. Durable state goes to external storage, which is itself cattle: data replicated, usually 3 to 5 times, with consensus for writes. Local state is still fine when it can be re-created: caches (provision the cache for latency, but the core for the total load, so losing the cache slows you but doesn't take you down), warm-up data, batched writes where some loss is OK, and periodic checkpoints.

Clients find you through service discovery, a stable name the scheduler keeps pointing at live replicas, usually with load balancing. A consequence: requests sometimes need retrying, because the server may vanish mid-request. Mutating requests should then be idempotent. Try ordering a pizza on a flaky network.

Retry safely

Two replica072sWhen the scheduler loses touch with a machine, it reschedules its work, and then the machine comes back. Now two processes both think they're replica072. The one the address system doesn't point to should stop, and idempotency handles the duplicate work in between.
5

One-off code

Engineers also need compute for analyses and prototypes. A laptop handles 1 GB of logs in a minute; 1 TB of logs would take about a day, while a few hundred cores do it in minutes. For iterative questions that's the difference between done and not done. Compute is like the whiteboard markers in the book's opening: a thousand core-hours costs far less than a day of an engineer's time. Unlike markers, you can grab a thousand machines by accident, so Google gives engineers nearly unlimited quota for low-priority batch, which runs on spare capacity anyway.

6

CaaS over time and scale

Containers became an abstraction of the compute environment, not just isolation, and Hyrum's Law applies hard: everything on Borg depends on details nobody thought of as API. Tap each story.

Borg also merged separate pools (one for batch, one per serving team) into one per datacenter: "machines are anonymous". That removes n different machine-management practices, and lets batch run in serving's slack, in Google's case usually effectively for free. Configuration should be submitted in a real configuration language under version control, not kept in CLI flags, docs or someone's head, because a service grows across datacenters, environments and helper jobs.

7

Choosing a compute service

Centralization vs customizationOne CaaS for everyone is cheapest to run. But needs diverge: Compute Engine VMs (from 2012) aren't cattle, so Borg avoided killing them at will and Cloud built live migration; a Search job with a huge on-disk index needed to survive disk failures itself. Such bifurcations made Borg's API large and hard to test, prompting cleanups after 2012 and whitelists for power-user features.
Public vs privatePublic cloud outsources management and makes scaling easy, but brings lock-in risk: an early serverless provider, Zimki, shut down in 2007 with three months' notice. Open-source-based offerings like Kubernetes give an exit path, though Hyrum's Law means provider-specific bits creep in. Hybrid and multicloud also hedge.

Serverless goes one step up: teams write handlers and multitenant framework servers load them on demand. It needs truly stateless code and gives up control (the Code Jam team had to fake a traffic spike to warm instances before the contest). Its big win is scaling to zero. Compare cost by traffic:

Google's choiceNot to invest heavily in serverless. Borg already offers most of its benefits; most of Google's footprint is high-traffic, so over-provisioning small services is cheap; and many systems (GCE, Spanner, BigQuery, slow-warming search servers) aren't stateless. For a small team without a shared cluster, a public serverless offering can be the right call, ideally one with a break-out path (like Knative to Kubernetes).
8

Afterword: the book's closing note

The book closes with a short afterword by Asim Husain. Its themes, in our words: software engineering keeps changing, and Google's practices took a kind of resolute agility to develop. Sustainability, being able to adapt as products, platforms and libraries change, is central. The authors can't prove their approach suits everyone, but few organizations have achieved both scale and sustainability, so they share what they learned, including the bumps. And engineers carry a responsibility to build with inclusion, equity and accessibility in mind, since technology that serves only some users isn't really innovation.
