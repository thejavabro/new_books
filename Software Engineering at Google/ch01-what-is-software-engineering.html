What Is Software Engineering?

Programming is writing code. Software engineering is programming integrated over time: keeping that code useful while everything around it changes, at a scale where every manual habit eventually breaks.

1

Programming integrated over time

The book opens with a distinction. Programming is producing code. Software engineering adds everything needed to keep that code useful for as long as it is used: the tools, the policies, the habits of a team. The authors sum this up as "programming integrated over time". Three things separate the two: time and change, scale and growth, and trade-offs and costs.

How long will your code live? Answers range from minutes (a throwaway script) to decades (a search engine's core). That's a spread of roughly a factor of 100,000, so the same advice can't fit both ends. Drag the slider to see how the concerns change.

Sustainable, not frozenCode is sustainable when, for its expected life, you are able to respond to changes in dependencies, technology or requirements. You may choose not to upgrade. What matters is being capable of it. Short-lived code can skip all this; for code that lives longer than about five years, the first forced upgrade is coming.
2

Hyrum's Law: every behavior gets depended on

With enough users of an API, it stops mattering what the contract promises: every observable behavior will be depended on by somebody. That's Hyrum's Law. It's why changes that "shouldn't" break anyone still do. The classic case is hash ordering: a hash set promises no particular iteration order, but code written against one version quietly relies on whatever order it happened to produce.

Upgrade the hash table

Twelve callers iterate the same set of keys. Some assume the order never changes. Ship a new hash function and see who notices.

"It works" versus "it is correct"Code that leans on unpromised behavior works today and breaks on someone else's schedule. Some libraries now randomize hash order on purpose, so nobody can come to depend on it. The book's contrast: code that relies on such details is "clever"; code written to be changed is "clean and maintainable".
3

Policies that scale, and ones that don't

Everything an organization does repeatedly should cost human effort that grows no faster than linearly (better yet, flat) as the organization grows. Watch out when a cost grows with the number of engineers times the size of the codebase. The book's example: making every team do its own migration when infrastructure changes. Slide the organization's size.

4

The 2006 compiler upgrade

Google's most famous upgrade: in 2006, with several thousand engineers, it changed compilers after about five years on one version. Few people had done it before, the code had absorbed every quirk of the old compiler, and there was no reliable CI to show the impact. It hurt. The lesson wasn't "never upgrade" but "upgrade often": the more frequently you change infrastructure, the easier it gets. Step through the factors that made later upgrades cheap.

5

Shifting left: catch it earlier, pay less

Picture the developer workflow as a line from design on the left to production on the right. A problem found on the left (in design, in the editor, in code review) is far cheaper than the same problem found in production. Much of the book's tooling exists to move detection leftward. Tap where a bug gets caught.

6

Trade-offs and costs

Decisions should rest on weighing costs, never on "because I said so". Costs come in more forms than money. Tap each to see what it means.

Example: whiteboard markers

Many offices ration markers. Google leaves unlocked cupboards full of them. Compare the two costs.

Example: distributed builds

When Google moved builds to a distributed system, builds got fast. Then, as people stopped worrying about dependencies, build sizes grew until builds slowed again. Spending more on a resource tends to raise its use.

Good reasons to decideWe do this because we must (legal or customer requirements), or because it's the best option we can see right now, given the evidence. Data is ideal but rarely complete, so most decisions mix data, assumptions, precedent and argument. When the data changes, change your mind. Revisiting a decision is not a failure.
