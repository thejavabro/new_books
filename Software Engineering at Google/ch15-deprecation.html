Deprecation

Code is a liability, not an asset. Retiring old systems is harder than building new ones, so plan for it, pick the right kind of deprecation, and give it an owner.

1

Why deprecate?

Code is a liability, not an asset. Functionality is the asset; the code is what it costs you. Every running system needs upkeep: security patches, dependency upgrades, on-call, people who still understand it. When a newer system does the job, keeping the old one around costs twice. This chapter is about deprecation: the orderly migration away from and eventual removal of obsolete systems. (Not "sunsetting" a product for customers, but retiring the code and infrastructure behind it.)

The cost of keeping both

Evolve in place when you canOnce you count the cost of turning the old system down, evolving it in place is usually cheaper than building a replacement. Deprecation is for when that's truly not possible.
2

Why is deprecation so hard?

Removal is the ultimate change. Every behavior goes away, not just one. Tap the obstacles.

3

Deprecation during design

Other engineering disciplines plan for the end. A nuclear power plant is designed knowing it will be decommissioned, with money set aside for it. Software rarely is: culture rewards launching new things, not retiring them. Questions worth asking at design time:

  • How easy will it be for consumers to migrate to a replacement?
  • Can parts of the system be replaced incrementally?
  • Does the organization have the will and resources to remove it someday?

5

Deprecation warnings

Marking something deprecated helps stop new uses but rarely moves existing ones. Warnings pile up, especially transitively, until people ignore them: "alert fatigue". A useful warning has two properties: it's actionable (an average engineer can actually do something with it) and relevant (it appears when the user can act on it, ideally at the moment they're writing the code). Pick the best warning.

6

Managing the deprecation process

Treat deprecation like any other project: with owners, milestones and tools.

DiscoveryFind every user. Static tools like Code Search and build graphs help; logs and runtime metrics catch dynamic uses.
MigrationLarge-scale change tools (Chapter 22) let the deprecating team do much of the migration itself.
Preventing backslidingAllowlists, build visibility rules and static analysis (like an @deprecated check) stop new uses from creeping back.
