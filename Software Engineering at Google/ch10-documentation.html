Documentation

Documentation pays off over time and scale, yet engineers avoid it. Treat docs like code, know who you are writing for, and keep each document to one purpose.

1

What counts, and why it's needed

Here "documentation" means every supplementary text an engineer writes: standalone docs and code comments alike. Engineers know docs matter but rarely write them, because the benefits arrive later and to other people. Yet a well-documented API answers questions before they're asked, helps the author think through the design, and pays off for anyone who joins later, including the author's future self. "Why" is the hardest question code can't answer by itself.

2

Documentation is like code

Google's biggest lesson: treat documentation like code. It should have rules, be under source control, have clear owners, go through review, have issues tracked as bugs, be checked periodically for freshness, and ideally be measured. Watch what happened when it wasn't.

Case study: GooWiki

The fix: docs live next to the codeGoogle moved engineering docs into source control (in a system called g3doc), rendered as web pages, owned by the teams that own the code, and reviewed with the same tools. Canonical docs, like the C++ style guide owned by its arbiters, had stayed healthy all along because someone cared about them.
3

Know your audience

The most common mistake is writing for yourself. Audiences differ by experience, domain knowledge and purpose. Some readers are seekers, who know what they want and need it fast; others are stumblers, who may not know what they're looking for and need orientation. Some are customers using an API; others are providers maintaining it. Pick an audience and see how the same API changes.

5
Documentation reviews

  
Docs deserve review like code, ideally from three angles.

  

    
1Technical reviewFor accuracy, usually from a subject-matter expert or teammate. Often part of the code review.

    
2Audience reviewFor clarity, from someone unfamiliar with the domain: a new teammate or an API customer.

    
3Writing reviewFor consistency, often from a technical writer or volunteer.

  






  
6
Documentation philosophy

  
Every doc should answer who it's for, what it's for, when it was written and last reviewed, where it lives, and why it exists. It needs a beginning, middle and end. And good docs balance three parameters that pull against each other: completeness, accuracy and clarity. Push one and watch the others.

7
When do you need technical writers?

  
Google once assigned writers to "important" projects so the engineers could move faster. That turned out to be a bad assumption: most teams write fine for themselves. Writers help most where a document crosses audiences, such as API docs for outside users or docs for a team that doesn't share your assumptions.
