Large-Scale Changes

Some changes touch thousands of files across the codebase. Google makes them routine with a small team, good tools, sharded changes and global approvers.

1

What is a large-scale change?

A large-scale change (LSC) is a set of logically related changes that can't practically be submitted as one atomic unit: too many files for the tools, too many merge conflicts, or repositories that can't be committed together. At Google, LSCs are almost always generated by tools, and typically: clean up antipatterns found by codebase-wide analysis, replace deprecated APIs, enable infrastructure improvements like compiler upgrades, or move users from an old system to a new one.

Who does them?Mostly infrastructure teams, the ones who own the thing being changed. They have the domain knowledge; consumer teams would each have to relearn it, which doesn't scale. A central team also learns the handful of error categories and builds a playbook. Asking every team to migrate themselves is an unfunded mandate.

Testing LSCs: riding the TAP train

Every shard must be tested, but running all affected tests separately for thousands of shards would swamp the CI system. Insight: LSC shards are usually pure refactorings that rarely interact, and most pass. So test them together. The TAP train starts fresh every three hours. Step through it.

The LSC process

Four phases with blurry boundaries: authorization, change creation, shard management, cleanup. Authorization means a short doc (why, estimated impact, an FAQ for reviewers), domain review from the API's owners, and approval from a committee of about a dozen people, who often route all shard reviews to a single global approver. Then the change is generated and handed to Rosie, which shards it by project and ownership and pushes each shard through test, mail, review and submit. Run it.

Cattle, not petsTreat shards like cattle: if one fails tests or a reviewer objects, don't nurse it. Drop it, fix the generator, and regenerate. Reviewers check only that the change is right for their code, not the overall design, which the committee already approved.
CleanupThe last shard isn't the end. Remove the old API, add checks so uses don't creep back (backsliding), and celebrate. Rosie caps outstanding shards and runs at low priority so LSCs don't overload shared test infrastructure.
