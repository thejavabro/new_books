Unit Testing

Most of a test suite is unit tests, so their maintainability decides whether testing helps or hurts. Good unit tests break only when behavior really changes, and say clearly what broke.

1

Why maintainability is everything

Google favors unit tests: narrow scope, usually small size. They're fast, deterministic, easy to write, act as documentation, and make up most of the suite (around 80%). So whether they are a joy or a burden depends on how maintainable they are. The chapter's scenario: an engineer writes a couple dozen lines for a simple feature, then spends the rest of the day fixing a screen of test failures. None found a real bug; they just assumed things about the code's internals, and her hacks to fix them make the tests even harder to understand next time. Two culprits: tests that are brittle and tests that are unclear.

2

Strive for unchanging tests

The ideal test is written once and never touched again unless the requirements of the system under test change. Look at the four kinds of change to production code and when tests should need editing.

Pure refactoringInternals change, behavior doesn't.tests should not change
New featureNew behavior added.only new tests
Bug fixBehavior was wrong.add a missing test
Behavior changeRequirements changed.update tests: expected

Refactor a class and watch the suite

You rename a private helper and switch an internal list to a map. No behavior changes.

3

Test via public APIs, and test state not interactions

Call the system the same way its users do. Tests that reach into private methods or internal fields break on refactors that users never notice. ("Use the front door first.") Similarly, check the result (state) rather than which calls were made (interactions): a test that verifies "save() was called on the database" breaks if you batch writes, even though users can't tell the difference.

Brittle: interaction
def test_create_user():
    db = Mock()
    UserService(db).create("ada")
    db.insert.assert_called_once_with(
        "users", {"name": "ada"})
Robust: state
def test_create_user():
    svc = UserService(InMemoryDb())
    svc.create("ada")
    assert svc.exists("ada")
4

Writing clear tests: complete and concise

A test fails either because the system has a problem or because the test is flawed. Either way, the person who sees it fail, maybe years later, must understand it fast. A clear test is complete (everything needed to understand it is in the test body) and concise (nothing distracting). Toggle.


    

  






  
5
Test behaviors, not methods

  
A test per method grows into a tangle as the method gains features. Instead, write a test per behavior: a guarantee about how the system responds to a sequence of inputs in a given state, often expressed as given / when / then. One method may have many behaviors; one behavior may span methods. Step through structuring one.

  

  

    
Name it after the behavior

    
A good name says the action and the expected outcome. Build one.

    

    

  






  
6
Don't put logic in tests

  
Loops, conditionals and even string concatenation in tests make them harder to read, and tests have no tests of their own. Prefer obvious, literal expectations, even if repetitive. Can you spot the bug hiding below? Toggle to see the version that exposes it.

  

    

    

    

  






  
7
Write clear failure messages

  
When a test fails, the message should say what was expected, what happened, and enough context to start debugging without opening the code. Good assertion libraries help.

  

    
Test failed: account is closed

    
Expected an account in state CLOSED, but got account:
  <{name: "my-account", state: "OPEN"}>
after calling close() with an outstanding balance

  






  
8
Sharing code: DAMP, not DRY

  
In production code, Don't Repeat Yourself (DRY) is gospel. In tests, the chapter argues for DAMP: Descriptive And Meaningful Phrases. Some repetition is fine if it makes each test readable on its own. Sharing values, setup and helpers is good only when it doesn't hide what a test depends on. Slide from fully DRY to fully DAMP.

  

    
    

    

  

  
Test infrastructure is differentShared code used across many test suites, like a fake or a test framework, is real infrastructure. It deserves its own tests and careful design, just like production code.
