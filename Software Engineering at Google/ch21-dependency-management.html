Why dependency management is so difficult

Dependency management means handling networks of libraries, packages and services that you don't control, as all of them change over time. The book calls it perhaps the most difficult topic it covers. Its headline advice: prefer source control problems to dependency management problems. If code lives in your repository with tests and CI, you can see every user and fix things directly; if it lives elsewhere, you're negotiating with strangers through version numbers. The classic trap is the diamond dependency. Pick versions.

2

Importing dependencies

Reusing code is almost always cheaper than rewriting it, in the moment. Over time, a dependency is an ongoing relationship. First, what does the provider promise? Compatibility promises vary widely: the C++ standard library aims for nearly indefinite backward compatibility, even for compiled binaries (ABI); Go promises source but not binary compatibility; Google's Abseil, which about 250 million lines of internal C++ depend on, promises no ABI compatibility and reserves the right to change APIs, but ships tools to migrate users; Boost makes no promises between versions and acts as an experimental proving ground. The limitations of SemVer

SemVer (MAJOR.MINOR.PATCH) is a lossy compression of "how risky does a human think this change is?" Package managers then treat those estimates as absolute truth via constraint solvers. That fails two ways.

It can overconstrain

libbase has two functions, Foo and Bar. Both liba and libb use only Foo. The maintainer changes Bar incompatibly, so libbase goes to 2.0.

It can overpromise

A "patch" release changes the order of results in an "unordered" stream, or adds a millisecond of delay, or changes log format. Is that safe?

Minimum Version Selection

liba says it needs libbase ≥ 1.7; versions 1.7, 1.8 and 1.9 exist. Russ Cox's MVS (used by Go modules) picks 1.7: the version liba's author almost certainly tested with.

So does SemVer work?Within limits: it works best when dependencies are few, providers are careful, and nobody depends on details (Hyrum's Law). It gets worse as networks grow and as precision is assumed. The chapter's thought experiment: with infinite compute, providers could run all downstream tests before releasing, which is roughly what Live at Head does at Google.
5

Exporting dependencies

Releasing code creates obligations too, with two risks: reputation damage if it's poorly maintained ("community over code") and an efficiency tax as internal and external versions drift apart. The chapter's example: around 2006 Google open-sourced its C++ command-line flags library, gflags; outside patches could not flow back in, and the code could not be moved internally (no large-scale refactoring tools yet), so it was doomed to be a "throw over the wall" release or a disconnected fork. In another case, App Engine's old Python runtime was tied to internal tool upgrades, which in 2014 created an unexpected dependency between upgrading a C++ compiler and the Python version customers relied on. Before you publish, decide what you promise, for how long, and who will maintain it.
