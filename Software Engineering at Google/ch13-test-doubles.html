Test Doubles

Test doubles make tests fast and deterministic, but overused they make tests brittle and blind. Google's lesson: use the real thing when you can, a fake when you can't, and mocks sparingly.

1

What test doubles are, and what they cost

A test double is an object or function that stands in for a real implementation in a test, like a stunt double. Doubles make tests faster, deterministic and able to simulate rare conditions (a server error, a full disk). But they have costs: tests become less realistic (passing tests, broken production) and can become tightly coupled to implementation details. Google learned this the hard way: mocking frameworks made tests easy to write, and years later teams were drowning in tests that rarely found bugs but constantly needed maintenance. The pendulum has swung toward realism.

2

Seams: making code testable

To swap in a double, the code needs a seam: a way to substitute a dependency without changing the code. The usual seam is dependency injection: pass collaborators in rather than constructing them inside. Toggle.

Three techniques: faking, stubbing, interaction testing

  
Here is one test written three ways, for code that charges a credit card (our own example).

  

    
FakingA lightweight working implementation
fake = FakeCardService()
store = Store(fake)
store.buy("book", card)
assert fake.charged(card) == 20
Behaves like the real thing (e.g. in memory). Often the ideal.

    
StubbingHard-code return values
svc = Mock()
svc.charge.return_value = OK
store = Store(svc)
assert store.buy("book", card).ok
Quick, but you are guessing how the real thing behaves.

    
Interaction testingVerify calls were made
svc = Mock()
Store(svc).buy("book", card)
svc.charge.assert_called_with(
    card, 20)
Checks how, not what. Brittle by default.

  






  
4
Prefer realism over isolation

  
Use the real implementation whenever you can: it gives the most confidence that the system works. Google even built a @DoNotMock annotation so API owners can tell people "don't mock this; use the real thing or the fake". When should you reach for a double? 5
Fakes: fidelity is everything

  
A fake is only as useful as its fidelity: how closely it matches the real implementation's behavior. It needn't match everything (an in-memory database won't hit disk), but it must honor the API contract. The best fakes are written and maintained by the owners of the real code, and are themselves tested against the real implementation with shared contract tests. Adjust fidelity.

  

    
    

    

  

  
When to write oneA fake costs effort and needs an owner. It's worth it when many tests would use it, which is why the owning team usually writes it. If no fake exists, first ask the API owners for one; failing that, wrap the API in your own class and fake that.






  
6
The dangers of overusing stubbing

  
Stubbing is tempting because it's easy. Used heavily, tests become unclear (extra lines of setup to read), brittle (stubs leak implementation details: change which method you call and tests break), and less effective (stubbed behavior may not match reality). Stub when you need a specific value to put the system in a certain state, and keep it to that.

  

    
Refactor: replace two lookups with one batch call

    

      
Heavily stubbed test
users.get.return_value = alice
users.get_prefs.return_value = prefs
...
assert page.greeting == "Hi Alice"
not run

      
Test with a fake
users = FakeUserStore()
users.add("alice", prefs)
...
assert page.greeting == "Hi Alice"
not run

    

  






  
7
Prefer state testing over interaction testing

  
Interaction tests check that calls happened, not that the system works. They're appropriate when state can't be checked (no fake, or the call is the point: sending an email, for instance), or when the number or order of calls matters (a cache that must avoid a second fetch). When you do use them:

  
    
    
  • Only verify state-changing calls (sending, writing), not read-only lookups.
    • 
    
  • Avoid overspecification: verify only the arguments and calls relevant to the behavior under test.

Recap on one page

  

    
Real firstPrefer the real implementation when it's fast, deterministic and easy to build.

    
Then a fakeHigh-fidelity, owned by the API team, verified with contract tests.

    
Stub sparinglyOveruse makes tests unclear and brittle.

    
Interaction tests lastThey expose implementation details; verify only state-changing calls.
