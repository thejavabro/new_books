Build Systems and Build Philosophy

A build system should be fast and correct, and those two goals fight each other. Google's answer is an artifact-based system that knows every dependency and can cache and distribute work.

1

What a build system is for

A build system turns source code into running binaries. It must be fast (a developer types one command and gets a result in seconds) and correct (the same source always yields the same output, on any machine). Those two goals fight: the quickest way to be fast is to skip work, which risks being wrong. Google's build system, Blaze (open-sourced as Bazel), was the fourth most satisfying of 19 internal tools surveyed, with 83% of engineers satisfied.

2

Task-based build systems and their dark side

Most modern build systems (Ant, Maven, Gradle) are task-based: the build file defines tasks, which are arbitrary scripts, and their dependencies. That's powerful, and the power is the problem. Because a task can do anything, the system can't know what it really reads or writes.

// task-based (pseudo-Gradle)
task compileApp(dependsOn: genProto) {
  doLast {
    exec "javac -d out src/**/*.java"
    // also touches ~/.cache? reads env? who knows
  }
}
3

Artifact-based build systems: Bazel

Bazel flips the model. Engineers declare what to build (targets: a library, a binary, a test), their sources and their dependencies. The system decides how, with a fixed set of tools it understands. Like a functional program, every build step is a pure function from declared inputs to outputs, so Bazel can cache, parallelize and rebuild only what changed. Click a source file to change it and see what rebuilds.

# BUILD
java_binary(
    name = "app",
    srcs = ["App.java"],
    deps = [":ui", ":storage"],
)
java_library(
    name = "ui",
    srcs = ["Ui.java"],
    deps = [":util"],
)
java_library(name = "storage", srcs = [...],
             deps = [":util"])
java_library(name = "util", srcs = ["Util.java"])

4

Distributed builds: remote caching and execution

Because every action is a pure function of its inputs, results can be shared. A remote cache stores outputs keyed by a hash of inputs: if anyone (or CI) built it already, download it. Remote execution runs the actions on a farm of machines. Google has done both since 2008: a remote cache called ObjFS (outputs stored in Bigtables, browsed through a local filesystem daemon that downloads files only on demand, which made builds about twice as fast) and a remote execution system called Forge. Simulate a morning.

5

Modules and dependencies

Finer-grained targets mean more parallelism and smaller incremental rebuilds, at the cost of more BUILD files to maintain (tools help). Google follows a 1:1:1 rule for Java: one directory, one package, one BUILD file, typically containing a few small targets. Slide the granularity.

Minimize visibilityTargets declare who may depend on them: public, private to their BUILD file, or an explicit list. At Google, teams make targets public only for widely used libraries. That keeps implementation details from becoming dependencies (Hyrum's Law again) and lets teams change internals safely.
Declare direct dependenciesRelying on something your dependency happens to pull in (transitive) breaks when it stops pulling it in. Blaze allowed this for years; as Google grew, removing one dependency broke distant targets, so it now enforces strict transitive dependencies: list what you use directly.
6

External dependencies

Third-party code is the riskiest input. Bazel requires external dependencies to be declared with an exact version and a cryptographic hash, and Google checks third-party code into its repository under the One-Version Rule. Depending on "latest" is a recipe for unreproducible builds. Click build twice.
