Critique: Google's Code Review Tool

A review tool can't create trust, but it can remove friction. Critique is built around simplicity, trust, communication and tight integration with everything else.

1

Code review tooling principles

Critique is the web tool nearly every Google engineer uses for code review (Chapter 9 covered the practice; this chapter covers the tool). It was shaped by a culture where review is central, and built around four principles. Tap each.

Gerrit, tooCritique is tied to Google's monorepo and internal tools, so it isn't available externally. Open source teams like Chrome and Android use Gerrit, a standalone open source review tool built around Git. Both share the same core goals.
2

The review flow, stage by stage

Step through the six stages a change goes through in Critique.

3

Stage 1: a diff built for understanding

Understanding the change is the core of review, so Critique's diff starts from a standard longest-common-subsequence algorithm and adds syntax highlighting, cross-references, character-level intraline diffs, adjustable whitespace handling, and move detection. Toggle the features on a small change (our own example).

Analysis results and tool integrationUploading a snapshot triggers static analyzers (Tricorder, Chapter 20); results appear as status chips and inline findings, sometimes with one-click fixes. One click opens the change in Cider (the web IDE), Code Search, test coverage (Zapfhahn) or release tools.
4

Whose turn is it? The attention set

With several reviewers, it's easy to lose track of who should act next. Critique keeps an attention set: the people a change is currently waiting on, shown in bold. It updates automatically when someone publishes comments, and users can adjust it. Users soon couldn't imagine life without it. Play out a review.

5

Stage 5: scoring a change

Scoring is simple and always positive: LGTM ("I reviewed it, it meets our standards, okay to commit after addressing comments"), Approval ("as gatekeeper, I allow it", for owners and readability), and the count of unresolved comments. Critique dropped earlier ratings like "Needs More Work" and "LGTM++". Once a change is mostly good, reviewers trust authors with small edits, with no repeat LGTM required. Set the state.

6

Stage 6 and after: commit and history

Critique has a commit button, so no context switch to the command line. After commit, the review lives on: anyone can browse the history of a change, its comments and how it evolved, which is invaluable for "change archaeology" when debugging or auditing. Comments can even be added after commit, and aggregate review data feeds training.
