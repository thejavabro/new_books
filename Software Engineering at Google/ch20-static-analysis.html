Static Analysis

Static analysis only helps if developers act on it. Google learned to measure "effective false positives", show results in code review, and let experts plug in their own checks.

1

Static analysis: finding bugs without running code

Static analysis means programs checking source code for bugs, antipatterns and other issues without running it. It catches problems before they're checked in, and spreads best practice by encoding it in tools. Google analyzes code at huge scale; a standard example is an Error Prone check that flags a common Java mistake. The hard part isn't writing analyses, it's getting developers to act on them.

// A classic bug an analyzer can flag (our own example):
if (name == "admin") { ... }   // Java: compares references, not contents
// Suggested fix:
if (name.equals("admin")) { ... }
2

Characteristics of effective static analysis

ScalabilityAnalyses must keep up with a multibillion-line codebase. Google's are shardable and incremental: they focus on files affected by a pending change and show results for edited lines, directly to the relevant engineers, with no central bottleneck.
UsabilityEvery warning costs developer time, and fixing working code can introduce bugs. So Google focuses on newly introduced warnings, where the author has context, and fixes automatically whatever can be fixed automatically. Old issues in working code are flagged only if important, like security bugs.
3

Lesson 1: focus on developer happiness

Research on static analysis traditionally chased false negatives (missed bugs). In practice, false positives are what make developers abandon a tool. Google measures effective false positives: any result the developer doesn't act on, whether it's technically wrong or just confusing. Perception is what counts. Tune an analyzer.

4

Lesson 2: make it part of the core workflow

Standalone reports get ignored. Google surfaces analysis where developers already are, mainly code review, where reviewers see findings too and social pressure helps. It also integrates at other points. Tap each.

5

Tricorder: Google's analysis platform

After several failed attempts to integrate analysis into the workflow, Google built Tricorder, with a relentless focus on showing only valuable results. It runs analyzers as microservices on every change in Critique and shows findings as gray comments. It analyzes more than 50,000 code review changes a day, across more than 30 languages and 100+ analyzers, most contributed from outside the Tricorder team. Every new check must meet four criteria:

UnderstandableAny engineer can understand the output.
Actionable and easy to fixWith guidance on how to fix it.
Under 10% effective false positivesDevelopers feel it's a real issue at least 90% of the time.
Significant impactWorth deliberately fixing, even if not a correctness bug.

Feedback channelsEvery finding has a "Not useful" button that files a bug against the analyzer. Reviewers can click "Please fix". The Tricorder team watches analyzers with high not-useful rates and disables them if they don't improve. Sometimes the fix is just a clearer message.
6

Lesson 3: empower users to contribute

A central team can't know every domain. Tricorder lets domain experts write checks for their own APIs and languages, and teams can turn on extra analyzers for their projects (per-project customization). That's how it scaled to over a hundred analyzers. The compiler is the strictest home: an Error Prone "ERROR" check breaks the build, so it must have no effective false positives, be easy to fix, concern correctness only, and the whole codebase must be cleaned up before it's turned on.
