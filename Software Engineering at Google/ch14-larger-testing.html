Larger Testing

Unit tests can't see configuration bugs, load problems or misbehaving dependencies. Larger tests trade speed for fidelity, and need care so they don't bog down the workflow.

1

What larger tests are for

Larger tests are anything beyond a unit test: they may be slow, nonhermetic, nondeterministic, and they test more of the system at once. They exist to buy fidelity: how closely the test reflects real behavior. Unit tests sit at the low end; testing in production sits at the top. Slide along the scale.

2

What unit tests can't see

Unit tests check behavior within a narrow slice, often with doubles. Some problems live only between the slices. Tap each gap.

3

Why not have more larger tests?

A developer-friendly test is reliable, fast and scalable. Good unit tests are all three; larger tests often violate all three. They're flakier (more infrastructure), slower (setup and run), harder to run in parallel (they collide), have unclear owners when they span teams, and lack standard frameworks. Google's answer is not to avoid them but to engineer them carefully, and to use the smallest test that will do. When code is expected to live only minutes, manual testing is fine; as lifespan grows, maintaining larger tests becomes the main concern. Starting with manual tests that pile up is one way projects drift into the ice cream cone antipattern.

The smallest possible testEven for integration, prefer the narrowest scope that exercises the risk. A handful of large tests beats one enormous test. For a long user journey, "chain" smaller pairwise integration tests, saving each one's output as the next one's input.
4

The structure of a large test

A large test has four parts: obtain a system under test (SUT), seed it with data, perform actions, and verify behavior. The SUT choice is a trade-off between hermeticity and fidelity. Pick one.

Case: Webdriver TorsoTo check YouTube's video processing, Google uploaded automated test videos to a public channel. The internet found them, a magazine wrote about the mysterious channel, and a blogger traced it back to Google, which came clean with some jokes (including a Rickroll). Testing in production means users may see your test data.
Shrink the SUT at painful boundariesUIs are slow and flaky to test, so test backends through their APIs. Replace heavy dependencies with doubles; for servers, record/replay proxies record real responses in larger tests and replay them in smaller ones, with a check that the recordings still match reality.
Seeded data
State loaded before the test: domain data, a realistic baseline (say, a believable social graph), seeding APIs.
Test traffic
Handcrafted, copied from production, or sampled. Copies need privacy care.
Verification
Manual (a human looks), assertions (like a unit test), or A/B comparison (old vs new).

Types of larger tests

Each type answers a different risk, with its own SUT, data and verification. Tap one.

A/B diff in action

Possibly the most common larger test at Google, used since 2001 for Ads, Search and Maps. Send the same traffic to the old and new versions and flag differences. Hyrum's Law says any difference may matter to someone; a human decides which are intended.
