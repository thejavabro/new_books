Testing Overview

Automated tests are what let software change safely. This chapter covers why to test, how to classify tests by size and scope, and how Google turned testing from a chore into a norm.

Why do we write tests?

The simplest test is a single behavior, a specific input, and an observable output, run in a controlled environment. Tests catch bugs, but their bigger job at Google is to let code change safely. The turning point was the Google Web Server (GWS), which serves Search. Around 2005, releases had become so buggy that at one point more than 80% of production pushes contained user-affecting bugs that had to be rolled back. The tech lead required tests with every change, run continuously. Within a year, emergency pushes halved, even with record numbers of changes.

You can't rely on programmer ability alone

The chapter's thought experiment: even brilliant engineers who each write just one bug a month add up.

2

Write, run, react

Modern products can't be tested by hand: Search alone must work across countless browsers, devices, languages and features, and ships often. Automated tests turn checks into code anyone can run, and the payoff comes when the team reacts to failures instead of ignoring them. Here's a tiny test in that spirit (our own example).

def test_discount_applies_over_100():
    cart = Cart(items=[Item(price=120)])
    assert cart.total() == 108  # 10% off

def test_no_discount_at_or_below_100():
    cart = Cart(items=[Item(price=100)])
    assert cart.total() == 100

Test size: what resources a test may use

Google classifies tests by size, meaning the resources a test is allowed to consume, not by how much code it covers. Small tests run in one process (often one thread), with no sleeping, I/O, network or disk. Medium tests may use multiple processes and network calls, but only to localhost: one machine. Large tests can span machines. Small tests are fast and deterministic by construction. Tick what your test does.

Google enforces sizes where it can: for example, Java small tests run under a security manager that fails them if they open a network connection. (Internally there's also "enormous"; this book's "large" mostly means that.)

Flaky tests are expensive

A flaky test sometimes fails for no reason. Tiny flake rates add up across a large suite, and once engineers stop trusting failures, the suite loses its value. Google's experience: as flakiness approaches about 1%, tests start to lose their value. Google's own rate hovers around 0.15%, which still means thousands of flakes a day, and it invests real engineering time in fixing them. Rerunning failures trades CPU for engineer time, but only delays the root-cause fix.

Test scope and the pyramid

Scope is how much code a test exercises: narrow (unit tests: a class or method), medium (integration: a few components), large (end-to-end, system tests). Google aims for about 80% narrow, 15% medium and 5% end-to-end tests. Compare shapes.

The Beyoncé Rule"If you liked it, then you shoulda put a test on it." Anything you want to keep working, including performance, behavior, accessibility and security, must have a test. Infrastructure teams may change things freely if your tests pass.
Test for failure tooSystems must cope with failures: errors, timeouts, crashed dependencies. Use tests (and fault injection) to check how code behaves when things go wrong.

A note on code coverage

Coverage says which lines ran, not whether anything was checked. And a target like 80% quickly becomes a ceiling: changes land with exactly enough. Better: think about which behaviors are tested. Google recommends measuring coverage from small tests only, to avoid inflation. Toggle the assertion.

Testing at Google scale

  
Google's monorepo holds billions of lines; every change runs the affected tests, millions per day. At that scale, badly written tests hurt: brittle tests that over-specify behavior break on unrelated changes, and slow, flaky suites make people stop running them. Mocks were a notorious source of brittleness. The next three chapters show how to write tests that help instead.

How Google changed its testing culture

  
Mandating tests from the top wouldn't have worked in a culture of independent engineers. Instead, a volunteer "Testing Grouplet" changed minds. Tap each milestone.

  

    

    

  

  
The limits of automationSome things still need people: judging search result quality (human raters), audio and video quality, and creative security hunting. Once a human finds a flaw, it can become an automated test. Exploratory testing complements automation.
