Encoding and Evolution

Data outlives the code that wrote it. Encoding formats and schema rules decide whether old and new versions of your software can still understand each other.

1

Old and new code must live side by side

Applications change, and their data formats change with them. But code cannot change everywhere at once. Servers are upgraded a few nodes at a time (a rolling upgrade), and users update mobile apps whenever they feel like it. So old and new code, and old and new data, coexist. That requires compatibility in both directions:

Backward compatibilityNewer code can read data written by older code. Usually easy: you know the old format.
Forward compatibilityOlder code can read data written by newer code. Harder: old code must ignore additions it has never heard of.

A rolling upgrade, one node at a time

The process of turning in-memory objects into bytes is encoding (also serialization or marshalling); the reverse is decoding. Language-built-in formats such as Java serialization or Python pickle are tempting but tie you to one language, can execute arbitrary code when decoding untrusted input, and neglect versioning and efficiency. Use them only for transient purposes.

2

JSON, XML and their binary variants

JSON, XML and CSV are readable and universal, which makes them the default for data sent between organizations. They have sharp edges: XML and CSV cannot tell a number from a string of digits; JSON cannot tell integers from floats and has no precision. Large integers silently lose precision in languages that parse every number as a 64-bit float, such as JavaScript. Try it, live in your browser:

Text formats also lack binary strings (people Base64-encode bytes, inflating them by a third) and their schema languages (JSON Schema, XML Schema) are powerful but complex. Binary JSON variants such as MessagePack save only a little space, because they still spell out every field name.

4
Schema evolution with field tags

  
In Protocol Buffers, a field's tag number is its identity; names can change freely, tags never. Old code that meets an unknown tag uses the wire type to skip the right number of bytes, so it is forward compatible. New code reading old data simply sees the new field as missing and uses a default, so it is backward compatible. The rules: new fields get new tag numbers; removed fields' tags are never reused; changing a type is risky (a 64-bit value read as 32-bit gets truncated).

5
Avro: writer's schema meets reader's schema

  
Avro decodes with two schemas: the writer's schema that encoded the data and the reader's schema the application expects. Avro resolves them side by side, matching fields by name. A field only the writer has is ignored. A field only the reader has is filled from its default. So you may only add or remove fields that have a default. The reader learns the writer's schema from a file header, a schema-version number pointing into a registry, or a connection handshake. No tags means schemas can be generated automatically, for example from a database's tables.

6
Dataflow through databases: data outlives code

  
Writing to a database is sending a message to your future self. In a database, values written five years ago sit next to values written five seconds ago. A deployment replaces code in minutes, but the old data stays in its old encoding unless you rewrite it: data outlives code. Most databases avoid full rewrites; adding a nullable column just fills in nulls when old rows are read. One subtle trap: old code that reads a record, updates it and writes it back can silently drop fields it did not know about.

  

    

    

    

  






  
7
Dataflow through services: REST and RPC

  
The second mode of dataflow: a client sends a request over the network to a service. Web services commonly follow REST conventions over HTTP and describe their APIs with OpenAPI; others use RPC frameworks like gRPC with Protocol Buffers. Frameworks generate client libraries and documentation from the definition.

  
RPC tries to make a remote call look like a local function call. That abstraction, location transparency, leaks badly:

  
Local call or network call?

  
For evolution, assume servers are upgraded before clients: requests need backward compatibility, responses need forward compatibility. Public APIs often run several versions side by side for years. Requests also need a route to a healthy instance: load balancers, DNS, service discovery registries (etcd, ZooKeeper) with heartbeats, or a service mesh of sidecar proxies.






  
8
Workflows and durable execution

  
A workflow is a graph of tasks, such as: check for fraud, charge the card, deposit to the bank. If the process crashes halfway, you must not charge the card twice. Durable execution frameworks (Temporal, Restate) log every RPC result and state change. After a crash the workflow function is re-run from the top, but calls that already completed are not repeated: their logged results are replayed.

  

    

    

    

  

  
The fine printExternal services still need idempotent APIs with unique request IDs. And because replay expects the same calls in the same order, changing workflow code is brittle: reorder two calls and in-flight workflows may misbehave. Deploy new versions as new workflows.






  
9
Event-driven architectures

  
The third mode: asynchronous messages through a message broker (RabbitMQ, ActiveMQ, Kafka, cloud pub/sub). The sender does not wait for a reply. The broker buffers messages if the recipient is slow or down, redelivers after crashes, fans one message out to many consumers, and decouples sender from recipient. A queue delivers each message to one consumer; a topic delivers it to all subscribers. Brokers do not impose a format, so use an evolvable encoding.

  
Distributed actor frameworks (Akka, Orleans, Erlang/OTP) combine this with an actor model: each actor holds local state and talks only by messages, which may be lost. Location transparency fits better here, since actors never assumed reliable delivery. Rolling upgrades still need forward and backward compatible messages.
