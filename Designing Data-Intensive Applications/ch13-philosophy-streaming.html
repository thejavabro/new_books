1

Data integration: derive everything from one log

There is no single tool that does everything well. Real applications combine an OLTP database, a search index, caches, a warehouse, ML models and notification systems, each a different view of the same data. The book's central recommendation: be explicit about where data is written first (the system of record) and treat every other representation as derived, fed from a log of changes in a single, consistent order. Funnelling all writes through one ordered log removes the dual-write races from chapter 12.

Derived data vs. distributed transactionsBoth keep systems in step. Distributed transactions use locks and atomic commit, giving linearizability but with poor fault tolerance and performance (XA). Log-based derivation is asynchronous, so no read-your-writes by default, but it is far more robust and lets you add new consumers at will.
Limits of total orderingOne leader ordering all events is a throughput ceiling; across regions or with offline clients there is no single leader; microservices own their own logs. Ordering events that are causally related (a user unfriends, then posts) without a global order is still an open area.
2

Batch and stream together: evolving your data

Stream processing keeps derived views fresh; batch processing reprocesses history. Reprocessing is what lets you change your mind: restructure a dataset into a new model without a risky big-bang migration. Build the new view alongside the old one from the same log, shift users over gradually, and keep the ability to go back. (The book compares it to 19th-century railways converting gauges by laying a third rail, so old and new trains could both run.)

The lambda architecture ran batch and stream systems side by side and merged their results, at the cost of maintaining two codebases. Modern engines unify both: the same code can replay history and process live events, with event-time windows and effectively-once semantics in both modes.

3

Unbundling the database

Inside a database, a secondary index is derived data: the database maintains it automatically from the table. CREATE INDEX even does what we have been describing: snapshot the existing data, then apply every subsequent change. Replication, triggers and materialized views are similar. Unbundling takes these features out of the single database and composes them across specialised systems, joined by logs, much as Unix composes small tools with pipes.

There are two ways to make many systems act as one. Federated databases unify reads: one query interface over many stores. Unbundled databases unify writes: synchronise them through asynchronous event logs with idempotent consumers, which is loosely coupled and tolerates one component being down. What is still missing is a high-level language for this, the equivalent of CREATE INDEX across systems.

4

Designing applications around dataflow

A spreadsheet has done this since 1979: change a cell, and every formula that depends on it recomputes. We want the same at the scale of a data system: change a record, and every index, cache and aggregate that depends on it refreshes, reliably and durably. Edit the inputs:

Blue cells are derived. Their "pipelines" are formulas; nobody updates them by hand.

In this style, application code becomes the derivation function, running as a stream processor that turns one state into another. Instead of a service querying another service for, say, the current exchange rate, it subscribes to a stream of rate changes and keeps a local copy. Purchases are then joined against local state: faster, and no failure in the other service can block it. The database becomes the place where state lives; code runs in separate, deployable stream operators.

5

Observing derived state: write path and read path

Data takes a journey. The write path is precomputed eagerly, whether or not anyone looks (updating an index). The read path happens only when someone asks (running the search). The derived dataset is where they meet, and you can move that meeting point.

Push this further and the boundary reaches the user's device. Rich clients and sync engines keep local state and subscribe to changes, so the server pushes updates over a WebSocket rather than waiting for a reload. Even reads can be treated as events: logging every read makes causal dependencies traceable (what did the user see when they decided?).

6

Aiming for correctness: the end-to-end argument

Strong guarantees inside the database do not make the whole application correct. Transactions do not stop application bugs from writing bad data, and immutability helps more there. Duplicates are subtler: a client submits a payment, the connection times out after the server committed, and the user presses the button again. TCP's deduplication and the database's transaction both work per connection, so neither helps. The end-to-end argument says the check must happen at the endpoints: the client generates a unique request ID once, and it travels all the way to the database, where a uniqueness constraint rejects repeats.

7

Enforcing constraints with logs

Uniqueness ("one account per username") needs consensus. The log-based way: route every claim for a username to the log partition chosen by hashing the name. A single-threaded processor reads that partition in order, keeps a set of taken names, and writes accepted or rejected to an output stream. The client waits for its answer. Because the log totally orders claims for each name, the first one wins and it is deterministic. Requests spanning partitions, like a transfer between two accounts, are split into stages linked by events, with the request ID ensuring each stage happens exactly once, no atomic commit required.

8

Timeliness and integrity

"Consistency" mixes up two different requirements. Timeliness means users see an up-to-date state; violating it is temporary, and waiting fixes it (eventual consistency). Integrity means no corruption or loss: no false data, no missing derived entries. Violating it is permanent. In most applications integrity matters far more. A credit card statement that is a day late is fine; one that is wrong is not.

Timeliness or integrity violation?

Loosely interpreted constraintsMany businesses already break "hard" constraints and apologize: airlines overbook, shops oversell and send a voucher, banks allow overdrafts and charge fees. If occasional violations can be fixed with a compensating action, you do not need synchronous coordination for them: validate optimistically and check afterwards. Log-based dataflow keeps integrity without atomic commit and without waiting, coordinating only where it is truly needed.
9

Trust, but verify

System models say some faults "cannot happen". In reality they are just unlikely: bits flip in RAM, disks corrupt silently, software has bugs, even in mature databases. The answer is auditing: continually check integrity end to end, such as reading back backups and comparing replicas. Event-sourced systems make this easier: re-derive state from the log and compare, with hashes to detect tampering (as in Merkle trees and certificate transparency logs).
