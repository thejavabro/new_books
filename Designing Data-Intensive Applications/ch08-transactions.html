Transactions

Transactions let an application pretend that concurrency and crashes do not exist, up to a point. Which race conditions each isolation level prevents, and how serializability is achieved.

What a transaction promises

Lots can go wrong: the database or application crashes mid-operation, the network drops, clients overwrite each other, readers see half-finished updates. A transaction groups several reads and writes into one logical unit that either commits as a whole or aborts, in which case it can safely be retried. Transactions simplify the programming model by letting the database handle a whole class of errors and race conditions. The safety guarantees are summarised as ACID, though the letters mean less than the marketing suggests.

Single-object and multi-object operations

Almost every storage engine makes writes to a single object atomic and isolated, using a log for crash recovery and a per-object lock. Some add atomic increments and compare-and-set. Those are useful, but a "transaction" usually means grouping multiple objects: keeping a foreign key valid, updating denormalized copies together, keeping a secondary index in step with the row. Retrying is not freeAbort-and-retry is the point of transactions, but if the commit succeeded and only the acknowledgement was lost, a retry runs it twice. Retrying an overload error adds load. Side effects outside the database (emails) happen anyway. Apps need deduplication and backoff.
3

Weak isolation: read committed

Full isolation is expensive, so databases offer weaker isolation levels that prevent some race conditions but not others. These cause real bugs and real money losses, so it pays to know exactly which. The most basic level, read committed, guarantees two things: no dirty reads (you only see committed data) and no dirty writes (you only overwrite committed data). Databases prevent dirty writes with row locks held until commit, and dirty reads by remembering the old committed value and serving it to readers until the new one commits.

4

Snapshot isolation and MVCC

Read committed still allows read skew. Alice has €500 in each of two accounts. A transfer of €100 runs while she checks her balances: she reads account 1 before the transfer (€500) and account 2 after it (€400), and sees €900 in total. Reload and it is fine, but a backup or an analytic query that runs for hours would capture a mix of old and new data. Snapshot isolation fixes this: each transaction reads from a consistent snapshot of the database as of its start.

The implementation is multi-version concurrency control (MVCC). Each write creates a new version of the row tagged with the writing transaction's ID; deletes just mark the row. A reader sees a version only if its creator had committed when the reader started, and it was not deleted by a transaction committed by then. Readers never block writers and writers never block readers. Garbage collection removes old versions nobody can see any more.

Naming is a mess: PostgreSQL calls snapshot isolation "repeatable read", Oracle calls it "serializable", and MySQL's "repeatable read" is weaker than both. Check what your database actually does.

Preventing lost updates

Two clients each read a value, modify it and write it back. The second write clobbers the first: a lost update. Incrementing a counter, editing a JSON document, two people editing a wiki page. Play it.


  

  
Some databases (PostgreSQL's repeatable read, Oracle's serializable, SQL Server's snapshot) detect lost updates automatically and abort the offending transaction; MySQL/InnoDB's repeatable read does not. In replicated databases with multi-leader or leaderless replication, locks and compare-and-set do not apply; commutative operations or keeping siblings work better.

Write skew and phantoms

  
The on-call rule: at least one doctor must be on call. Alice and Bob both feel ill and click "go off call" at about the same moment. Each transaction checks that two doctors are on call, then updates its own row. No row is written twice, so this is not a dirty write or lost update. Under snapshot isolation both commit and nobody is on call. This is write skew.

The pattern: a query checks a condition, the app decides, then writes something that changes the condition's result. More examples: booking a meeting room, claiming a username, spending more than your balance, two players moving to the same square. When the check is for the absence of rows, there is nothing to lock; a write that changes a search result elsewhere is a phantom. One workaround, materializing conflicts, creates lock rows (say, one per room and time slot) just to have something to lock. Usually it is better to use serializable isolation.

Distributed transactions and two-phase commit

  
When a transaction writes to several nodes (shards, or different systems), each could commit or fail independently. Two-phase commit (2PC) makes them agree. A coordinator asks every participant to prepare: a participant that votes yes promises it can commit no matter what, even after a crash. If all vote yes, the coordinator writes its decision to its log (the commit point) and tells everyone to commit. Once a participant has voted yes it cannot back out; if the coordinator crashes then, the participant is in doubt and must wait, holding its locks.

  

    

    

    

  

  

  
Exactly-once without distributed transactionsProcessing messages from a broker exactly once does not need XA. Keep a table of processed message IDs in the database. In one database transaction: check the ID (skip if present), insert it, do the work, commit. Only then acknowledge the message. A retry after a crash finds the ID and drops the duplicate.
