Stream Processing

A stream is a batch that never ends. Brokers and logs carry events, change data capture turns a database into a stream, and stream processors reason about time.

1

Transmitting event streams

Batch processing assumes the input is bounded: you know when you have read it all. Real data never stops arriving. Stream processing handles each event, a small immutable record of something that happened at some time, shortly after it occurs. A producer writes an event once; many consumers may process it. Related events are grouped into a topic or stream. Consumers could poll a database for new rows, but polling is wasteful; it is better to be notified.

Producer faster than consumer: what now?

A second question: what happens if a node crashes? Some systems send messages directly from producer to consumer (UDP multicast, brokerless libraries, webhooks), fast but lossy if a party is down. Most use a message broker, a server that buffers messages so producers and consumers can come and go.

Log-based message brokers

Traditional brokers delete messages once delivered, so you cannot replay them, and a new consumer only sees new messages. Log-based brokers (Kafka, Kinesis, Pulsar, Redpanda) store messages in an append-only log on disk, split into partitions. Within a partition, every message has an increasing offset and order is total. Each consumer simply remembers its offset per partition; reading does not delete anything. Partitions are assigned to consumers in a group, so parallelism equals the number of partitions, and one slow message holds up its partition.

Logs make streams feel like batchThe log keeps messages for days or weeks (or forever, with tiered storage on object stores). A consumer that falls behind just has consumer lag, which you can monitor. You can add a new consumer, start it from the beginning, test new code against production traffic, and replay after a bug: the same read-only, repeatable input that makes batch jobs safe.

Change data capture and log compaction

Change data capture (CDC) observes every change written to a database and publishes it as a stream, in the order the database applied it. The database becomes the leader, and caches, indexes and warehouses become followers that consume the stream. Tools such as Debezium read the replication log (PostgreSQL's logical decoding, MySQL's binlog); many cloud databases offer it natively. A new consumer needs an initial snapshot that corresponds to a known log position. Or use log compaction: keep only the latest value for each key, and remove keys whose latest entry is a tombstone. Then the compacted log alone contains a full copy of the database.

CDC and event sourcing both put a log at the centre. The difference: CDC captures low-level row changes from a mutable database, after the fact; event sourcing records high-level application events designed as the source of truth, from which state is derived.

6

State, streams and immutability

Mutable state and an append-only log of immutable events are two sides of one coin. The current state is what you get by applying every change in order: the integral of the stream. The stream of changes is the derivative of the state. Accountants have worked this way for centuries: the ledger is the log, the balance sheet is derived.

cart state at that point

Immutable logs give auditability, easier recovery from bad deployments, and several read-optimised views from one source of truth. The limits: some workloads churn so much that the full history is huge, and sometimes data must really be deleted, for legal reasons. Deleting from immutable logs is hard, with copies in backups and derived systems.

Reasoning about time

"Requests in the last five minutes" sounds simple. But event time (when it happened) and processing time (when the processor sees it) can differ by seconds or hours: queues back up, consumers restart, a phone was offline. Windowing by processing time is simple but produces artefacts; windowing by event time is right but raises a question: when is a window complete? You never know for sure that no straggler is still on its way. Systems use watermarks and then either ignore late events or publish a correction.

Whose clock?A mobile device's clock may be wrong. Log three timestamps: when the event happened (device clock), when it was sent (device clock), and when the server received it (server clock). The difference between the last two estimates the device's offset.

Stream joins

All three need the processor to keep state based on one input and query it on the other, and the order of events matters. If a user's profile changes, does an older event join with the old or the new profile? If the ordering is not deterministic, the join is not either. Data warehouses call this a slowly changing dimension and give each version its own ID.
