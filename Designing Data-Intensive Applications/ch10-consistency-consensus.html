Linearizability: the illusion of one copy

Replicated databases with weak guarantees make developers reason about replication lag. A stronger model, linearizability (also atomic consistency or strong consistency), makes the system look as if there were only one copy of the data and every operation took effect atomically at one instant. It is a recency guarantee: once any read has returned a new value, every later read, from any client, must return that value or a newer one.

Is this history linearizable?

Bars show when each operation started and finished. A write of x = 1 overlaps some reads; reads overlapping it may return 0 or 1, but once one read has seen 1, later ones must too.

Not the same as serializabilitySerializability is about transactions touching many objects: the result equals some serial order. Linearizability is a recency guarantee on single objects. A database can offer both (strict serializability) or either one alone. Snapshot isolation, for instance, is deliberately not linearizable: a snapshot does not include writes newer than itself.

The cost of linearizability

Cut the network between two regions. With a linearizable database, a region that cannot reach the leader (or a majority) must refuse writes and linearizable reads: it is unavailable. A database that is not linearizable can keep both regions working and reconcile later. That is the CAP theorem's trade-off, best read as "either consistent or available when partitioned". Since partitions are faults you cannot opt out of, CAP is a narrow statement; the book advises against framing designs around it.

Partitions are rare, but linearizability is also slow all the time: response times are at least proportional to network delay uncertainty. Even RAM on a multi-core CPU is not linearizable (each core has a cache), purely for performance. Many systems drop linearizability for speed, not for fault tolerance.

ID generators and logical clocks

A single-node autoincrement counter gives compact IDs whose order is the creation order. It is linearizable, but a single point of failure, a cross-region round trip and a bottleneck. Alternatives each give something up:

A logical clock counts events instead of seconds and captures causality. In a Lamport clock, each node keeps a counter, increments it on every event, attaches it to messages, and on receiving a message jumps its counter to max(own, received) + 1. Timestamps are pairs (counter, node ID), so they are unique and totally ordered, and if A caused B then A's timestamp is smaller. A hybrid logical clock starts from physical time and falls back to Lamport-style bumps, so timestamps look like real time.

Why logical clocks are not enough

A linearizable ID generator fixes that: a single node (replicated with consensus for fault tolerance) handing out blocks of IDs, or physical clocks with tightly bounded uncertainty and commit-wait, as Spanner does with TrueTime.

5

Consensus: getting nodes to agree

Consensus means getting several nodes to agree on something, despite faults. It sounds simple and is subtle. Formally: uniform agreement (no two nodes decide differently), integrity (no changing your mind), validity (the decision was proposed by someone), termination (every non-crashed node eventually decides). Termination is a liveness property that needs a majority of nodes to be working. The FLP result shows that no deterministic algorithm can always reach consensus in a fully asynchronous model if a node may crash; real algorithms use timeouts and live with occasional delays.

A surprising insight: many problems are the same problem in disguise. Solve one and you can build the others.

6

Consensus in practice: leaders, terms and quorums

Most consensus systems provide a shared log: Raft, Zab and Multi-Paxos. A leader appends entries; an entry is committed once a majority has stored it. If the leader seems dead, a node starts an election in a new, higher term (epoch) and needs votes from a majority. A node votes only for a candidate whose log is at least as up to date as its own, so a new leader always has every committed entry. Two majorities always overlap, so two leaders in the same term are impossible, and an old leader's messages from an earlier term are rejected. Click nodes to crash or restart them.

The fine printEach decision costs a round of messages to a majority, so consensus is slowish. A fixed membership is easiest; changing it needs care. Leader elections triggered by flaky networks can stall progress. And consensus systems trust their disks: lose stored votes or log entries and safety can break.
7

Coordination services

Few applications run consensus themselves. They lean on a coordination service such as ZooKeeper, etcd or Consul: a small, fully replicated, linearizable key-value store kept in memory, built on consensus. It holds little data that changes slowly, and offers exactly the primitives distributed systems need.
