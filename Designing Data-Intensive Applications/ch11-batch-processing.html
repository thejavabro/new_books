Batch Processing

Take a big pile of input, run a job, write derived output. Batch processing scales the Unix philosophy to thousands of machines and powers ETL, analytics and ML training data.

1

Online, batch and stream

Most of the book so far has been about online systems: a request comes in and a response should come back fast. A batch processing system takes a large, fixed input, runs a job over it, and produces output. Nobody waits on it; it might run for minutes or hours, often on a schedule, and its key metric is throughput. Stream processing (next chapter) sits in between: it consumes inputs shortly after they arrive.

The quiet superpower: immutable inputsA batch job reads its input and writes new output without modifying the input. If the output is wrong because of a bug, fix the code and run it again; the old output can simply be discarded. This human fault tolerance makes experimentation cheap and is a big reason batch processing is so robust.
2

Batch processing with Unix tools

Start small. Given a web server log, which are the five most requested pages? A chain of Unix commands answers it, each one reading text from the previous and writing text to the next. Toggle the stages and watch the data change; it really runs, in your browser, on a tiny log.


  

  
The same job could be a small program keeping a hash map of URL → count. That works while the distinct URLs fit in memory. The sort-based pipeline does not need that: sort spills to disk and merges sorted runs, much like SSTables, so it handles data far larger than RAM and parallelises across cores. The Unix philosophy (small tools, a uniform interface, composition) is exactly what distributed batch frameworks scale up to many machines.

Distributed filesystems and object stores

  
Batch jobs need somewhere to read input and write output. A distributed filesystem such as HDFS splits files into large blocks and stores copies on several machines, or uses erasure coding to survive failures with less overhead than full copies. Today object stores such as S3 are common instead. They look similar but behave differently:

Object stores separate storage from compute, so batch jobs can no longer move computation to the machines holding the data; they rely instead on fast datacenter networks. Table formats such as Iceberg and Delta Lake add transactions and schemas on top of immutable objects.






  
4
Distributed job orchestration

  
On one machine, the OS kernel runs processes, allocates memory and schedules CPU. Across a cluster, an orchestrator does it: Kubernetes or Hadoop YARN. A job request says how many tasks, how much CPU, memory and disk each needs, where the code and input live. A scheduler decides where tasks run, balancing fairness, locality and priority; executors on each node start tasks, report heartbeats and enforce resource limits. When a task fails, or its machine is lost, it is simply run again elsewhere. That only works because task output is not visible until the job succeeds. Click a machine to fail it while the job runs.

  

    

    

    
Spot or preemptible instances are cheap but can be taken away at any time. Batch jobs tolerate that well.

  






  
5
MapReduce and the shuffle

  
MapReduce, popularised by Google and Hadoop, is the textbook model, though now largely superseded. A job has two callbacks. The mapper is called once per input record and emits key-value pairs. The framework then shuffles: it sorts and groups all pairs by key so that every value for a key ends up at the same reducer, even if they came from different machines. The reducer then processes each key with all its values. Despite the name, a shuffle produces sorted order, not randomness. Step through a word count.

  

    

    

  






  
6
Dataflow engines: Spark, Flink and friends

  
Real workflows chain many steps. With MapReduce each step is a separate job that writes its full output to the distributed filesystem before the next can start. Dataflow engines such as Spark and Flink treat the whole workflow as one job, a graph of operators (map, filter, join, group by) with data flowing between them.

  

    

    

    

  






  
7
Joins and grouping at scale

  
Take a huge log of page views (user ID, URL) and a huge users table (user ID, date of birth). Which pages are popular with which age groups? Both sides are sharded, so the shuffle does the work: key both by user ID, and each user's profile and all their events arrive at the same reducer, profile first if you sort it that way (a secondary sort). That is a sort-merge join. If one side is small, skip the shuffle and send a copy of it to every task: a broadcast hash join.

  

    

    

    

  

  
A celebrity user with millions of events would overload one reducer: skew again. Engines detect hot keys and split them across several tasks, replicating the other side of the join to each.






  
8
Query languages and DataFrames

  
Writing raw map and reduce functions is tedious. Batch frameworks now accept SQL, which a query optimizer turns into an efficient dataflow; and data scientists use DataFrame APIs (Spark, Daft, Polars, pandas-like libraries) that look like pandas but run distributed. Batch processing and cloud data warehouses have converged: both use columnar formats, vectorized execution, shuffles and fault-tolerant scheduling.
