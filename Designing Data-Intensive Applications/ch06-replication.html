Replication

Keeping copies of the same data on several machines sounds simple until the data changes. Three families of replication, each with its own way of going wrong.

1

Single-leader replication

Replication means keeping a copy of the same data on several machines: to keep data close to users, to keep working when parts fail, and to scale out reads. If data never changed it would be trivial. All the difficulty is in handling changes. The most common approach: one replica is the leader. Clients send all writes to it; it applies them and streams a replication log to its followers, which apply the changes in the same order. Reads can go to any replica.

The trade-offSynchronous: a follower is guaranteed up to date, but one slow follower blocks every write. Fully synchronous is impractical, so "synchronous" usually means one follower is synchronous (semi-synchronous). Asynchronous: the leader never waits, but a write acknowledged to the client can be lost if the leader dies before followers receive it. Many systems run fully async anyway.
2

Adding followers and handling outages

A new follower cannot simply copy files while writes continue. Instead it takes a consistent snapshot, which is tied to an exact position in the leader's log, then requests every change since that position and catches up. A follower that crashes does the same from the last position it processed. In the cloud, the snapshot may be fetched from object storage.

Leader failure is harder: failover. Detect that the leader is dead (usually with a timeout), choose a new leader (ideally the most up-to-date follower, which is a consensus problem), and reconfigure clients and the old leader. Everything can go wrong.

Problems with replication lag

  
With asynchronous followers, reads from a follower may be stale. Stop writing and the followers eventually catch up: eventual consistency. "Eventually" can mean seconds or minutes under load, and three anomalies show up. Pick one, then switch on the guarantee that prevents it.

  

    

    

    
    

  

  
These guarantees are workarounds layered on top of a weak model. The cleaner answer is a database with transactions or linearizability (chapters 8 and 10), at some cost in performance.






  
5
Multi-leader replication

  
Allow more than one node to accept writes, and each leader replicates to the others. This shines across regions: users write to a nearby leader, a region outage does not stop writes, and slow links between regions are hidden. The price: two leaders can accept conflicting writes to the same data. Multi-leader setups are also often bolted on and interact badly with autoincrement keys, triggers and constraints.

Sync engines and local-first softwareAn offline-capable calendar on your phone, a Figma file open in three browser tabs, a Google Doc: each device is a leader with a local replica, syncing whenever it can. That is multi-leader replication taken to the extreme, with "replication lag" of hours or days. A library that captures local changes, syncs them and merges remote ones is a sync engine. Local-first apps go further: they keep working even if the developer's servers disappear.






  
6
Dealing with conflicting writes

  
Two devices, both offline, edit the same shopping list. When they sync, what should happen? The simplest policy, last write wins (LWW), keeps the version with the latest timestamp and silently discards the other. Better options: avoid conflicts by routing all writes for a record to one leader; record both versions and let the user or app merge them; or use data structures that merge automatically: CRDTs (conflict-free replicated data types) and operational transformation, used in collaborative editors.

7
Leaderless replication and quorums

  
Dynamo-style databases (Cassandra, ScyllaDB, Riak) drop the leader. The client sends each write to all n replicas and treats it as successful once w acknowledge. Reads ask several replicas and wait for r answers, taking the newest version. If w + r > n, the sets of nodes written and read must overlap, so at least one read reply is up to date. Missed writes are repaired by read repair (fix stale replicas you notice during reads), hinted handoff (another node holds writes for a down replica) and background anti-entropy.

Why go leaderless?There is no failover: a slow or dead replica is simply outvoted, which makes these systems resilient to gray failures and lets clients take the fastest replies (request hedging). The costs: bigger quorums wait on more replicas, hinted handoff adds load at bad moments, and quorums do not give linearizability on their own.






  
8
Detecting concurrent writes

  
Without a leader, nodes may receive the same writes in different orders. Two operations are concurrent if neither knew about the other, regardless of wall-clock time. LWW forces an arbitrary order and loses data. To keep both, the server gives each key a version number; a client must send back the version it last read, and the server keeps any values it has not yet seen as siblings. With several replicas, a version vector tracks one counter per replica.
