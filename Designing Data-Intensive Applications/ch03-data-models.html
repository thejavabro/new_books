Data Models and Query Languages

A data model shapes how you think about a problem, not just how you store it. Compare tables, documents, graphs, event logs and arrays, and the query languages that come with them.

1

Data models stack on top of each other

A data model shapes not only how software is written but how we think about the problem. Applications are built in layers, and each layer hides the one below behind a cleaner model. This chapter is about the second layer: the general-purpose models you choose for storing your data.

Models covered: relational (tables), document (JSON trees), graph (vertices and edges), event sourcing (an append-only log of facts) and DataFrames (tables that become matrices). Each makes some things natural and other things awkward. Declarative query languages such as SQL let you say what you want and leave the how to the database's optimizer.

2

Relational versus document

Take a professional profile: a person, a list of jobs, a list of schools, contact links. In a relational database this gets "shredded" into several tables linked by IDs. In a document database it can be one JSON tree, loaded in a single read. The tree matches how application code usually holds the data, which reduces the object-relational mismatch that ORMs try to paper over.

Normalization, denormalization and joins

  
Should a profile store the text "Greater Seattle Area" or a region_id pointing to a regions table? Storing the ID is normalized: the human-meaningful text lives in one place, and the meaningless ID never needs to change. Storing the text everywhere is denormalized: reads are faster (no join), but every copy must be updated when the text changes, and copies can drift apart. Neither is right in general; it depends on how often the data changes and how often it is read.

Many-to-one (many people in one region) and many-to-many relationships (people and the companies they worked at) do not fit neatly inside one document; they push you toward references and joins. The social timeline in chapter 2 was itself denormalization: precomputed copies that make reads fast and writes heavier.






  
4
Stars and snowflakes: schemas for analytics

  
Data warehouses favour a star schema. At the centre is a huge fact table: one row per event, such as each item sold, mostly made of foreign keys and numbers. Around it sit dimension tables describing the who, what, where, when and how. Split the dimensions further into sub-dimensions and you get a snowflake. Go the other way, folding the dimensions into the fact table, and you get one big table, which costs space but can be faster. In analytics that denormalization is harmless: the history does not change.

  

    

    

  






  
5
When to use which model

  
Documents win when data is a self-contained tree loaded all at once, gives locality (one read, no joins) and allows a flexible schema. Relational wins with many-to-one and many-to-many relationships, and when you need to point at nested items directly. On schema, a better framing than "schemaless" is schema-on-read (structure is implicit, interpreted when read, like dynamic typing) versus schema-on-write (explicit and enforced, like static typing). The two models have also converged: relational databases store JSON, and document databases add joins.

Graph-like data models

  
When anything can relate to anything, model the data as a graph. In a property graph, vertices and edges each have a label and key-value properties, and any vertex can connect to any other. A triple store says the same thing as (subject, predicate, object) statements. The power shows in queries that follow a chain of unknown length, such as "born somewhere within the United States": a city within a state within a country.

7
GraphQL: the client asks for exactly the shape it needs

  
Despite the name, GraphQL is not a graph database language. It lets a client, such as a mobile app, describe the exact JSON tree it wants, and the server fills it in. It deliberately avoids arbitrary recursion and heavy queries, since untrusted clients send them, and it accepts some duplication in responses (the sender's name repeated in every message) to keep clients simple.

  

    

    

  






  
8
Event sourcing and CQRS

  
Instead of overwriting rows, record every change as an immutable event in an append-only log, named in the past tense: "seats were booked", "booking was cancelled". The log is the source of truth. From it you derive materialized views tuned for reading, such as seats left, an attendee list or a revenue report. Separating the write-optimized log from read-optimized views is CQRS (command query responsibility segregation). A command is validated first; only once accepted does it become an event, and views must not reject it.

9
DataFrames, matrices and arrays

  
Data scientists often work with DataFrames (pandas, R, Spark): table-like structures with relational-style operations plus easy reshaping. Machine learning usually needs a matrix of numbers, so data is pivoted, scaled and one-hot encoded. The resulting matrix may be wide and sparse, with thousands of columns, which suits array libraries better than a relational database. Array databases specialise in huge multidimensional numeric data such as satellite rasters or telescope images.
