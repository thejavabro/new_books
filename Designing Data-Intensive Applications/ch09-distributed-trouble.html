The Trouble with Distributed Systems

In a distributed system anything that can go wrong will, and you often cannot even tell that it did. Networks drop messages, clocks drift and processes freeze without warning.

1

Faults and partial failures

Software on a single computer is mostly deterministic: it works or it crashes, and a bug usually produces the same result every time. Computers are deliberately designed that way; if a hardware fault would make results wrong, the machine would rather halt. Distributed systems are different. Some parts break while others work fine, in unpredictable ways: a partial failure. It is nondeterministic, and often you do not even know whether something succeeded.

This chapter is deliberately pessimistic. The theme: assume anything that can go wrong will, and build reliable systems out of unreliable components, the way TCP builds reliable delivery on lossy IP, or error-correcting codes recover from noise.

2

Unreliable networks: the silence game

Datacenter networks and the internet are asynchronous packet networks: a message may arrive, arrive late, or never arrive, with no guarantee either way. When you send a request and hear nothing back, you cannot tell why. Try it: send a request, then guess what happened.

The only real tool is a timeout, and it cannot tell you whether the request was processed. Faults are common in practice: misconfigured switches, a shark biting an undersea cable, a NIC that drops inbound packets but sends fine. TCP retransmits and reorders, but cannot help when the connection drops after your data was sent and possibly processed. Networks can also partition, splitting nodes into groups that cannot talk to each other.

3

Timeouts and unbounded delays

How long should you wait? Too short and you declare healthy-but-slow nodes dead, trigger needless failovers and maybe perform an action twice. Too long and users wait for a dead node. If the network guaranteed a maximum delay d and nodes answered within r, then 2d + r would be a perfect timeout. Real networks have unbounded delays, mostly due to queueing: at switches, in the OS, in VM hypervisors, in TCP flow control, and from noisy neighbours on shared hardware.

Better than a fixed constant: measure the distribution and its jitter, and adjust automatically, as the Phi accrual failure detector in Akka and Cassandra does.

Why not a phone network?A phone call reserves a fixed slice of bandwidth along the whole route: a circuit. No queueing, so delay is bounded. Datacenter networks and the internet use packet switching because traffic is bursty; they make the most of the wires, at the price of variable delay. It is a cost/utilisation trade-off.
Detecting faultsSometimes you get explicit feedback: connection refused, a crash notified by the OS, a management interface that can see the power is off. But you cannot count on it. Retry a few times, then declare the node dead.
4

Unreliable clocks

Every machine has its own clock, usually a quartz crystal that drifts (Google assumes up to 200 ppm, about 17 seconds a day if never corrected). NTP nudges clocks toward time servers, but only as well as the network delay allows. Computers have two kinds of clock:

Time-of-day clock (wall-clock time)
Monotonic clock (seconds since some arbitrary point)only ever moves forward

Use the monotonic clock to measure elapsed time (timeouts, response times). The time-of-day clock can jump backward or forward.

5

Relying on synchronized clocks

Clock problems rarely crash anything. They cause silent data loss. Classic case: last-write-wins replication uses timestamps from the writing node. If that node's clock runs behind, its genuinely later write gets an earlier timestamp and is thrown away.

A clock reading is really a range with a confidence interval. Google's TrueTime API in Spanner returns [earliest, latest]. If two intervals do not overlap, the order is certain. Spanner deliberately waits out the uncertainty (around 7 ms with GPS and atomic clocks in each datacenter) before committing, so timestamps reflect causality. Logical clocks (chapter 10) avoid physical time altogether.

6

Process pauses, leases and fencing tokens

A thread can be paused for a long time at any point without noticing: a stop-the-world garbage collection, a VM being suspended and migrated, a laptop lid closed, a context switch, synchronous disk I/O, swapping to disk, a SIGSTOP. Code that checks "do I still hold the lease?" and then acts may act seconds after the lease expired.

The fix is a fencing token: every time the lock service grants a lease, it returns a number that increases. The storage service remembers the highest token it has seen and rejects writes with an older one. The resource itself must check; you cannot rely on the client to be honest about whether it still holds the lease. Consensus-based lock services such as ZooKeeper can supply the token (its zxid).

7

Knowledge, truth and lies

A node cannot trust its own judgement of the situation. A node may believe it is the leader while everyone else has moved on. So decisions are made by a quorum, usually a majority of nodes: if a majority declares a node dead, it is dead, even if it feels fine. Because two majorities always overlap, there can be only one majority decision at a time.

8

System models: what an algorithm may assume

To reason about algorithms, we fix a system model: an abstraction of what can go wrong. Pick one timing model and one node-failure model. The most realistic combination for most systems is partially synchronous with crash-recovery.

Algorithm properties come in two kinds. Safety: nothing bad happens (uniqueness, no lost data); if violated, you can point to the moment it broke and it cannot be undone. Liveness: something good eventually happens (a request eventually gets an answer). Distributed algorithms usually must keep safety in every situation the model allows, while liveness may depend on the network eventually recovering.

Formal methods and randomized testing

The state space of a distributed algorithm is enormous. Model checkers (TLA+, FizzBee and others) systematically explore the states of a specification to check invariants. Fuzzing and property-based testing throw random inputs at real code. Deterministic simulation testing runs the whole system in a simulator where network, clock and scheduling are all driven by a seeded random generator, so any failure found can be replayed exactly. FoundationDB, TigerBeetle and AWS have used these techniques to great effect. Jepsen tests real databases under injected faults.
