Storage and Retrieval

How does a database actually find your data on disk? From a two-line append-only key-value store to LSM-trees, B-trees, column storage and vector indexes.

1

The world's simplest database

A database must do two things: store what you give it and give it back later. The simplest possible key-value store is a text file you append to: setting a key writes a new line at the end, and getting a key scans for the last line with that key. Appending is about as fast as writing can be, and the file is a log: an append-only sequence of records. Reads, however, scan everything, so they get slower as the data grows.

An index is extra structure derived from the data that makes reads faster, at a cost to every write. The hash map above keeps a byte offset for each key, but it must fit in memory, has to be rebuilt on restart, never frees space, and cannot answer range queries such as "all keys from k100 to k199".

2

SSTables and LSM-trees

Keep segment files sorted by key and you get an SSTable. Sorting means a sparse index is enough (the first key of each few-kilobyte block), blocks compress well, and merging segments is a simple merge-sort. To produce sorted files from writes that arrive in any order, buffer them in an in-memory sorted tree, the memtable. When it fills up, write it out as a new SSTable. Reads check the memtable, then segments from newest to oldest. In the background, compaction merges segments and throws away overwritten values. Deletes write a special marker, a tombstone. This design is the log-structured merge-tree (LSM-tree), used by RocksDB, Cassandra, ScyllaDB, HBase and Lucene. A write-ahead log protects the memtable against crashes.

3

Bloom filters: a fast "definitely not here"

Looking up a key that does not exist would mean checking every segment. A Bloom filter per segment avoids that. Each key is hashed to a few bit positions, which are set to 1. To test a key, hash it the same way: if any of its bits is 0, the key is definitely absent. If all are 1, it is probably present, since other keys may have set those bits by coincidence (a false positive).

4

B-trees: fixed pages, updated in place

The B-tree is the standard index in almost every relational database. It splits the data into fixed-size pages (4 to 16 KiB) and arranges them as a tree. Each page holds keys and references to child pages covering a range. A lookup starts at the root and follows references down to a leaf. With a branching factor of several hundred, four levels of 4 KiB pages can address hundreds of terabytes. Updates overwrite a page in place; inserting into a full page splits it in two and updates the parent. Since a crash mid-split could corrupt the tree, B-trees also write a write-ahead log first.

Secondary indexes, covering indexes and in-memory stores

A primary key identifies one row; secondary indexes let you find rows by other columns, where keys need not be unique. An index entry's value can be the row itself (a clustered index), a reference to the row in a heap file, or a copy of a few columns (a covering index, which can answer some queries alone). In-memory databases such as Redis are fast less because they skip disk reads, since the OS caches hot pages anyway, and more because they avoid encoding data structures for disk. They can also offer data structures, like priority queues, that are hard to build on disk.

-- secondary index on a non-unique column
CREATE INDEX by_city ON users (city);

-- covering: the query reads only the index
CREATE INDEX by_city_age
  ON users (city) INCLUDE (age);
Concatenated indexesAn index on (last_name, first_name) is like a phone book: it finds everyone named "Lee", or "Lee, Sam", but it is no help for finding every "Sam". Column order matters.
7

Column-oriented storage for analytics

Analytical queries touch a few columns across billions of rows. Row-oriented storage keeps each row's values together, so a query must read every column of every row it touches. Column-oriented storage keeps each column's values together (in blocks of many rows), so a query reads only the columns it uses. Pick the columns a query needs and watch how much is read.

Compression: bitmaps and run lengths

A column often has few distinct values. Store one bitmap per value (1 where the row has it), then compress runs of zeros. Sorting the table by this column first makes the runs very long. Click a value to see its bitmap.

Writes are batched: new rows go to an in-memory, row-oriented store and are merged into immutable column files in bulk, which suits object storage well. Query engines then speed up the scans with vectorized processing (tight loops over batches of column values) or query compilation (generating machine code for each query). Formats such as Parquet and table formats such as Iceberg bring the same ideas to data lakes.

8

Materialized views and data cubes

A materialized view stores the result of a query and keeps it updated. A data cube is a special case: precomputed aggregates along every dimension. Tap a row or column total. Queries like "sales per store yesterday" become instant; but anything not along a dimension (say, "share of sales over $100") needs the raw data again.

9

Full-text search and vector embeddings

Some queries need more than one sorted key. Multidimensional indexes such as R-trees find points within a latitude and longitude box. Full-text search uses an inverted index: for each term, a postings list of documents that contain it. A multi-word query intersects the lists. Engines like Lucene add stemming, synonyms and fuzzy matching within an edit distance.

Semantic search goes further. An embedding model turns each document into a vector: a point in a space of hundreds of dimensions, placed so that similar meanings land near each other. A query is embedded the same way, and the index finds the nearest vectors by cosine or Euclidean distance. Exact search compares everything (a flat index). Approximate indexes trade some accuracy for speed: IVF clusters vectors around centroids and searches only the nearest clusters; HNSW navigates a layered graph of neighbours.
