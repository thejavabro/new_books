Sharding

When one machine cannot hold or serve all the data, you split it into shards. The hard parts are choosing the split, moving data as you grow and finding things again.

1

Why shard, and what it costs

Sharding (also called partitioning; each piece is a shard, partition, region, tablet or vnode depending on the database) splits a large dataset so that each record lives in exactly one shard, and different shards live on different nodes. It is usually combined with replication: each shard has copies on several nodes, and each node holds several shards. The point is scalability: with fair splitting, ten nodes hold ten times the data and handle ten times the throughput.

If one machine will do, do not shard: it adds real complexity. Queries that do not know the partition key must hit every shard, and a write spanning shards needs a distributed transaction (chapter 8). Multitenant SaaS systems often shard by customer: each tenant, or a group of small ones, gets its own shard. That gives resource isolation, easy per-tenant backup, deletion and data residency, and room for per-tenant schema rollouts. Big tenants, small-tenant overhead and cross-tenant features are the downsides.

2

Sharding by key range

Give each shard a contiguous range of keys, like the volumes of an encyclopedia. Boundaries follow the data, not the alphabet: one volume might be "A–B", another just "T". Keys stay sorted within a shard, so range scans are efficient. The danger is skew: if keys arrive in order, such as timestamps, every new write lands in the same shard, a hot spot. Prefix the key with something else, like a sensor ID, and writes spread out, at the cost of range queries now needing one query per prefix.

Range-sharded systems grow by splitting a shard that becomes too big (HBase defaults to around 10 GB) or too busy, much like a B-tree page split, and they may pre-split an empty database if the key distribution is known. Splitting rewrites data and tends to happen exactly when a shard is under heavy load.

3

Sharding by hash of key

If you do not need nearby keys together, hash the key first. A good hash spreads even skewed keys uniformly. The naive next step, hash(key) mod N, is a trap: change N and almost every key moves. Compare three ways of mapping 1,000 keys when one node is added.

Fixed shards: 120 shards created up front; whole shards move to the new node. Consistent hashing: a ring with 50 virtual points per node. Each counts real keys hashed in your browser.

Fixed number of shards, moved whole

Create many more shards than nodes (say 1,000 for 10 nodes). Adding a node steals a few shards from each existing node; keys never change shard. Used by Citus, Riak, Elasticsearch and Couchbase. Choosing the count is hard if data volume is unpredictable.

Consistent hashing ring

Hash ranges can also be split dynamically (hash-range sharding in DynamoDB, YugabyteDB, MongoDB). Cassandra and ScyllaDB give each node many ranges with random boundaries so imbalances even out. "Consistent" here means keys tend to stay put, nothing to do with replica or ACID consistency.

4

Skewed workloads and hot keys

Hashing spreads keys, not load. If one key is extremely hot (a celebrity's post, a viral product), every request still goes to the one shard that owns it. Some cloud databases detect and isolate hot keys automatically. A manual trick: append a random suffix from 0 to k−1 to the hot key so writes spread over k shards; reads must then fetch all k and combine them, and you must track which keys are split.

5

Automatic versus manual rebalancing

Automatic rebalancing is convenient and enables autoscaling. It is also unpredictable: moving data is expensive, and combined with automatic failure detection it can be dangerous. An overloaded node responds slowly, others decide it is dead, they move its load elsewhere, which overloads them too, and the failure cascades. Keeping a human in the loop is slower but avoids surprises, and allows planned rebalancing before a known traffic surge.

6

Request routing: which node has my key?

Once data is sharded, a client must find the right node, and the answer changes as shards move. Three options. All need someone to know the authoritative shard-to-node mapping, usually a coordination service like ZooKeeper or etcd built on consensus, or a built-in Raft implementation (Kafka, YugabyteDB, TiDB, ScyllaDB). Riak uses gossip instead, which can briefly disagree.

7

Sharding and secondary indexes

A primary key tells you the shard. A secondary index ("all red cars") does not. Two designs:

Local indexesEach shard indexes only its own records. Writes touch one shard. Reads must scatter/gather to all shards, suffering tail latency amplification, and adding shards does not add query throughput. Used by MongoDB, Cassandra, Elasticsearch and others.
Global indexesOne index across all data, itself sharded by the indexed term. Reads go to one index shard. Writes may touch several shards, so the index is often updated asynchronously or needs a distributed transaction. Long postings lists get expensive.
