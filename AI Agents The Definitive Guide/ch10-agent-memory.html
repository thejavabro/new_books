Agent Memory

Without memory every conversation starts from zero. With careless memory an agent hoards noise or gets poisoned. This chapter shows how agents remember well.

1

The amnesiac agent

Agents do not remember anything by themselves. The author told a fresh LangGraph agent her name and that she was writing a chapter on memory. It wished her luck by name. One message later it had no idea what her name was. Memory has to be engineered, and it is more than retrieval-augmented generation: RAG fetches documents, but it gives no continuity or awareness of past interactions. Memory spans conversation state, user preferences, past episodes, intermediate results and learned behavior.

Memory poisoning is its own threatResearch on memory poisoning shows the danger is not only seeing a malicious instruction once; it is untrusted content being written to memory and returning later as trusted context. Agents that write and retrieve aggressively can be easier to exploit, and prompt-injection defenses do not fully cover it, because the attack now lives in persistent state.
2

A three-legged stool: short-term, long-term, procedural

Short-term memory is what is happening now: messages, the checkpointer, the thread ID. Long-term memory persists across sessions in namespaced store keys: semantic facts (what is true), episodic events (what happened), and procedural instructions (how to behave). Remove a leg and the system wobbles: it loses context, lacks knowledge, or behaves inconsistently. Sort these memories into the right long-term bin.

3

Short-term memory and time travel

A checkpointer saves state after every step of a thread, which makes execution a versioned history. You can inspect any earlier checkpoint, fork from it with a modified value, and replay from there. That is superb for debugging reasoning paths, exploring alternatives and auditing decisions. In production, swap the in-memory saver for SQLite or Postgres.

Ghost from the pastTime travel rewinds the conversation state only, not the long-term store. Decide explicitly whether long-term memory should be versioned, rolled back or left alone.
4

Namespaces and a service layer

Beyond one thread, memory is an application concern. Scope every entry by organization, user and memory type, so facts, episodes and instructions never blur into one blob, and shared org memory sits in its own segment. Wrap all reads and writes in a small service layer used both by agent nodes and by your app's API, so users can inspect and delete their memory through one implementation.

5

Remember selectively

Memory that grows without discipline gets noisy, contradictory and expensive to inject. And memory is not neutral: a wrong "fact" stored as truth compounds in every later answer. So validate before persisting. Try the write gate: it rejects oversize text and anything that looks like an SSN, card number, private key, cloud access key or API secret, and it skips duplicates.

Retention policies keep the store lean: time-based pruning (keep the last N days), importance-based retention (keep errors, violations and high-confidence events), and compression (summarize episodes; compact many small facts into one consolidated profile). Updates also apply rules: drop facts below a confidence threshold, replace by category, and remove the older side of a known contradiction.

6

Deciding what to remember has a price

Asking an LLM "should I store this?" on every step is a hidden parallel tax: a five-step ReAct loop becomes ten LLM calls, and nobody notices because it is infrastructure, not reasoning. A tiered approach gets most of the value cheaply: rules for structured data, embeddings for relevance, a small encoder classifier for routine decisions, and an LLM judge only for ambiguous, high-stakes cases.

7

Memory topology in multi-agent systems

Where memory lives decides whether agents behave like one organization or a loose crowd. Local memory per agent keeps contexts clean but lets agents drift apart and duplicate knowledge. Shared memory gives one source of truth but fills every context with other agents' noise and needs careful concurrent writes. Hybrid, the usual production choice, keeps local working memory plus a shared layer for durable facts and coordination artifacts (with summarization when many agents report back).

A separate question: does a specialist remember anything across calls? The book's example has an orchestrator that forwards only the current turn to a billing worker. Only the persistence mode changes.

Test memory like everything elseMemory often seems to work until real multi-turn use: facts fail to retrieve, summaries drop details, stale or contradictory data resurfaces. Test across turns and realistic interaction patterns.
