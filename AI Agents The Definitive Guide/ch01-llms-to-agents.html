From LLMs to Agents

A language model on its own predicts text. Put it in a loop of reasoning, acting and feedback, give it state and tools, and it becomes an agent. This chapter builds the mental model: agents are state machines with an LLM making choices inside them.

1

An agent is an LLM inside a loop

Think about how a developer builds something for a client. They read the request, sketch a plan, then act: look up docs, write a function, run the tests. Failing tests, a reviewer's comment or the client's reaction feed back into the next round of thinking. Nothing is done in one shot.

An LLM agent works the same way. It reasons about what is missing, takes an action by calling a tool, reads what came back from the environment, and adjusts. It repeats until the goal is met or a limit is hit. A plain LLM call is one pass of text generation; an agent is a decision-maker running inside a workflow.

Bounded autonomy is a featureDevelopers work inside coding standards and review processes. Agents work inside the tools, permissions and safeguards you hand them. Those limits are what make either of them safe to rely on.
2

The base paradigm: finite state machines

Frameworks like LangGraph and CrewAI dress it up differently, but every agent workflow needs a control model: track state, choose an action, observe the result, update context, and eventually stop. A finite state machine (FSM) is the oldest and clearest way to describe that. It sits in exactly one state at a time and moves along allowed transitions when events arrive.

Drive the tool-use machine below yourself. Each button is an event; the guard decides whether the transition is allowed and the action says what happens on the way.

Steps used: 0 / 4. The step budget is a guard too: once it runs out, the only allowed move is to wrap up.

FSMs shine when behavior alternates among a few stable modes and when you need to recover: you can checkpoint at each state boundary and resume from the last completed step after a crash. They also make you decompose a fuzzy job. "Write a blog post" becomes ideation, outline, draft, edit and SEO states, each with its own tools and an explicit condition for handing off to the next.

3

When FSMs get crowded: hierarchical state machines

Add planning, reflection, approval gates and retries to a flat FSM and the edges multiply into spaghetti, with the same safety checks copied onto every one. A hierarchical state machine (HSM) lets states contain states. A superstate holds shared rules once; its substates inherit them. A history marker remembers which substate you were in, so you can come back to exactly that point. Parallel regions let children advance independently, which is how fan-out to several tools or agents is modeled.

Picture a research agent. Instead of one monolithic "research" step it becomes a sub-machine: find keywords, gather URLs, scrape, summarize. Each substate could even be its own specialized agent, while the rate limits and safety filters live once on the parent.

4

How the vocabulary maps to LangGraph

LangGraph already speaks this language. The router that picks the next node plays the role of the event handler: it takes the current state plus the model's latest output and decides the next step. Tap each pairing.

Here is the whole idea in a sketch of my own (not the book's listing): a typed state, a model node, a tool node and a router that loops until the model stops asking for tools.

class State(TypedDict):
    messages: Annotated[list, add_messages]   # shared "bus", merged safely

def think(s):  return {"messages": [llm_with_tools.invoke(s["messages"])]}
def route(s):  # the guard
    return "tools" if s["messages"][-1].tool_calls else END

g = StateGraph(State)
g.add_node("think", think); g.add_node("tools", ToolNode(tools))
g.add_edge(START, "think"); g.add_conditional_edges("think", route)
g.add_edge("tools", "think")
app = g.compile(checkpointer=MemorySaver())  # history for free

From static predictor to dynamic agent

An LLM generates the next token from patterns in its training data. That makes it a strong reasoner, but it cannot check a fact, fetch fresh data or touch the world. Agency appears when reasoning is coupled with action, and the coupling needs two things: explicit state (so earlier tool results and decisions carry forward) and control flow (guards that say when to plan, act or stop).

Stateless calls versus stateful threads

A stateless call treats the model as a black box: prompt in, tokens out, nothing remembered. Even a stateless tool loop forgets everything once the run ends. In a stateful workflow every node reads from and writes to shared state, and a checkpointer saves it per thread. "State" here is more than the prompt text: it includes routing info, tool results, checkpoints and branch IDs.

Two small details that matterAlways bound the loop with a step limit so a model that keeps calling tools cannot spin forever. And if the run ends on a tool observation, send one short wrap-up instruction so you still get a final answer in the format you asked for.
7

Deus ex machina? Orchestrated autonomy

Once agents are seen as HSMs, "autonomy" is just how much choice you allow inside a superstate. A router is a one-edge FSM with a single guard. A tool-calling agent is a WORKING superstate looping through plan, act and reflect. A multi-agent system nests subgraphs under a supervisor. Real systems are not a god descending on a crane to solve everything; they are engineered workflows.

Case study: an AI scientistA multi-agent system using tree search, experiment management and vision-language feedback generated hypotheses, ran experiments, wrote code and drafted papers. One of three workshop submissions passed peer review in 2025. Reviewers still found shallow analysis, citation slips and dataset limits. Impressive inside the boundaries of orchestration; not yet a source of new scientific paradigms.
