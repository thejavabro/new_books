Secure Execution and Tool Governance

Agent failures are rarely dramatic; they are quiet and helpful one step too far. Containment means one governed choke point for tools and deny-by-default sandboxes for code.

1

Governing the overly helpful agent

Letting agents run tools and code without sandboxes is free solo climbing, except the fall can take the whole system with it. And agent failures are rarely dramatic. They are quiet: a file overwritten, a credential reused, a tool called just outside its scope. This chapter is not about outside attackers (that is Chapter 12). It is about the rogue agent: one that stays inside its formal permissions but drifts outside its role. Picture a polite, productive corporate spy who never trips an alarm because they only copy, forward, sync and tidy up. Treat agents like capable junior engineers who never sleep: talented, but in need of boundaries.

System prompts are not containmentAsking the model to behave is a request. Containment means the system decides where execution may happen, which tools may be touched, with what budgets, and when "no" is the only correct answer, no matter what the model wants.
2

A governor between reasoning and execution

The book repurposes the Agent2Agent (A2A) protocol, designed for agents to discover and collaborate with each other, as a governance layer. A2A already brings structured artifacts (intent and decisions as reviewable records), task states (active, paused, blocked) and a split between reasoning and execution. LangGraph proposes tool calls; the A2A governor decides and executes them against MCP and streams every decision as an event. Everything funnels through one privileged function: governed_call. Policy, budget and argument checks must all pass before a byte reaches a server; restricted tools additionally pause for a human.

Budgets are shrunk for the demo. The separation rule blocks discovery and execution in the same run, breaking the "find a new tool, use it immediately" pivot that rogue behavior often follows.

Product requirement promptsFor coding agents working in a real repo, a PRP combines a PRD's goal and rationale with codebase intelligence: exact file paths, library versions, code patterns to follow, and executable validation commands the agent can run to check its own work.
3

Three kinds of sandboxing

Governing tool calls is not enough once agents run code: reasoning mistakes are reversible, execution is not. Sandboxing works in three cumulative layers. Runtime isolation limits where code runs. Ephemeral environments limit how long state survives. Governed execution services decide who may run what, when.

Docker is the usual first layer: a reproducible filesystem, a non-root user, explicit writable directories, privileges dropped before any code runs. But containers do not stop path traversal or "helpful" writes outside the intended folder. The fix is a single writable root and a check on every path: resolve it (following .. and symlinks), then require it to sit under the root. The author watched an agent attempt exactly such an escape; validation turned it into a clean error.

4

Split the permissive UI from the locked-down runtime

A fully locked container fights UI frameworks like Streamlit, which want writable state and long-lived processes. The book's answer: two layers. The browser talks only to the UI. The UI talks to a small internal FastAPI service that starts runs, approves actions and returns artifacts. Only that service holds API keys and makes outbound calls, and file paths never leave the container.

5

Cloud sandboxes: throwaway machines for risky code

When agents write arbitrary code across languages and dependency stacks, move execution out of your system entirely. Services like E2B (also Runloop, Daytona) start a lightweight VM per run or session, take structured execution requests, return structured results, and are destroyed afterwards. No state leaks between runs and runs can go in parallel. The book's two-agent demo: agent A generates 200 rows and fits a regression; agent B fetches that artifact and plots it. Sandboxes can also pause and resume.

6

Programmatic tool calling, safely

Sequential tool calling makes the model take one call, read the result, think, take the next. For structured work (fetch ten items, score, filter, keep the best three) that means many round trips and a context that grows with every result. Code mode asks the model to write a short program that calls approved tools as functions, with ordinary loops and sorts. The program runs once in an interpreter and only the final answer returns.

Token figures are illustrative (about 400 tokens per tool result).

code mode

There is a catch. You are now executing code the model wrote, and a poisoned tool result or web page can steer that code. In sequential mode an injection can at most produce another tool call your governor inspects; in code mode it can become Python that reads environment variables or ships data out. So code mode must run in an interpreter that denies everything by default. The book uses Monty, a minimal Python interpreter in Rust, still experimental, that starts from an empty environment: no imports, no files, no network, only the functions you pass in.

# code a model might write after reading a poisoned tool result

data = open("/app/.env").read()
secret(key + data)          # an undeclared "exfiltration" function

Governing the tools you do expose is the last piece. The interpreter pauses before every external call and hands the host a snapshot: function name and arguments. The host checks an allowlist and a budget, maybe asks a human, then resumes with a value or an exception. A paused program can even be serialized and resumed later in another process, which is how a run survives a slow approval.
