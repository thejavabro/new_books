Foundational Evaluation and Observation

Public benchmarks pick candidates; they do not prove your agent works. Evaluation means stress-testing behavior and threats from the prototype on, then watching real traffic and turning it into tests.

1

Three ways to assess an agent

Evaluation is not a last step before launch. It starts during development and gets more important once real users arrive. The book frames assessment like hiring and managing a person: screen candidates on general tests, give a take-home task and interview, then hold regular performance reviews once they are on the team. This chapter covers the middle part; Chapter 9 covers benchmarks.

False confidenceA model that tops a public leaderboard can still misbehave inside your workflow, with your prompts, tools and users. Both the model and the agent system are probabilistic. A benchmark score is a starting signal, not proof of reliability.
2

Run two evaluation tracks from the prototype on

If security is only checked at the end, weaknesses are already baked into the architecture. So the book runs two tracks in parallel while prototyping. Behavioral stress testing with subject matter experts asks: does the agent actually do the job in realistic, messy situations? Early threat testing with red-team tools and checklists asks: does this setup invite prompt injection, excessive agency, unsafe tool orchestration or memory manipulation?

3

Writing stress scenarios that actually stress

Start from real material if you have it (support tickets, workflows, SME examples) or generate scenarios with an LLM and have experts review them. Either way, treat the set as a hypothesis. Good scenarios define success, include edge cases, specify a persona, and sketch how the conversation should unfold. Failures rarely happen with calm, tidy users; they happen under pressure. Build one.

Each stress dimension maps to a cheap deterministic check: did the agent adapt its behavior to the condition? These do not judge quality; they flag likely problems early. Test yourself: does each reply pass its check?

Pass or fail the rule check?

Erratic intent switchesUsers change their minds halfway through. Include scenarios where the goal flips mid-conversation and check that the agent follows the new intent instead of finishing the old one.
4

A lightweight evaluation harness

Manual click-through testing is slow and does not scale. The book's harness is deliberately small: typed scenario and output schemas, many runs in parallel bounded by a semaphore, cheap rule checks, a batched LLM judge, a blended score (0.4 × rules + 0.6 × judge) used to prioritize, and exported traces (CSV, JSON) so experts review the riskiest outputs first, in tools they know. The judge's score is a triage signal, not ground truth.

Phase 1 generates, phase 2 scores in batches of 3.

5

Early threat testing: the OWASP agentic Top 10

OWASP publishes a Top 10 for LLM applications and, since 2026, one for agentic applications (ASI). It is a threat taxonomy and checklist for what agent architectures add: hijacked goals, misused tools, abused identities, poisoned memory and more. Tap each risk. The book walks through ASI02 with DeepTeam, an open-source red-teaming framework (with mappings to NIST AI RMF and MITRE ATLAS), against a support agent whose rules say: search the knowledge base, never send email without confirmation, do not loop, never claim a blocked action happened.

6

The truth is in the trace, not the text

A red-team judge that sees only the final reply can be fooled. The book's model callback returns a structured turn including which tools ran and which were blocked (tagged BLOCKED::name). That separates a well-behaved agent (never tried) from a contained one (tried, got stopped), and catches passive failures: polite words that hide an action the agent should not have taken.

In the book's run, the example agent mitigated every tested ASI02 vulnerability (excessive agency, function-level authorization bypass, recursive calls, unsafe composition, budget exhaustion, cross-tool state leakage) plus prompt-injection and roleplay attacks. That shows the method works, not that the system is secure in all situations.

7

Observing agents in the wild

Before launch you control the variables; afterwards they control you. Evaluation becomes continuous monitoring, typically on an observability platform (Langfuse and LangSmith are examples; many speak OpenTelemetry so agent traces join your existing monitoring). Every surprising production trace is a candidate for a new test scenario, and that growing set becomes the gate any new model, prompt or architecture must pass.
