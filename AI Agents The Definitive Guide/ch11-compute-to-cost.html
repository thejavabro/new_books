From Compute to Cost

Agents multiply LLM calls, so they multiply cost and latency. Knowing where the tokens go lets you cut the bill without cutting quality.

1

Economics breaks agents before accuracy does

Analysts expect a large share of agentic projects to be cancelled. The usual reason is not weak models: the systems get too expensive or never deliver business value. Every reasoning step, tool call and retry adds latency and tokens. Take your weakest agent: if it succeeds 60% of the time and you rely on independent retries to push it toward certainty, the attempts pile up fast.

Assumes independent attempts. Feedback-conditioned retries (Instructor, LangGraph) improve the odds, but each attempt then carries more context and costs more.

So cost is not something you optimize later. It is a design constraint from day one. This chapter covers the main drivers: multi-step amplification, prompt caching, attention kernels, deployment topology and memoization of decisions.

2

Memory movement, not FLOPS

Anyone who has tuned matrix multiplication knows that the real limit is moving data, not arithmetic. In agentic systems the context window plays the role of memory bandwidth, and API or serverless GPU response time is your latency. When you consider hosting your own models, you choose between hyperscalers (managed, integrated, convenient, pricier) and neoclouds (raw GPUs, cheaper for sustained load, but you build the plumbing). Beware cross-provider traffic: a neocloud GPU querying a hyperscaler vector database each step can cost more than the inference.

Partition the graph by sensitivityNot every agent sees the same data. A supervisor that only routes by category can use a managed API, while the retrieval agent that touches PII runs on a small fine-tuned model in your own environment. You avoid putting the whole graph under the strictest (and most expensive) setup.
3

Prefill, decode and the KV cache

Inference has two phases. Prefill processes all prompt tokens in parallel and fills the KV cache, producing no output tokens. Decode then generates one token at a time, reading the whole cache each step. Reuse saves compute, but decode becomes limited by memory bandwidth. Batching many requests into the cache raises throughput, and how many KV tokens fit on your GPUs sets the possible concurrency.

Two architecture features change the math. Hybrid attention changes memory: only some layers keep a classic KV cache that grows with context. Mixture of experts changes compute: only a fraction of parameters is active per token. Estimate from both, not from the total parameter count. A model's Hugging Face config (sometimes nested under text_config) gives you the numbers.

FlashAttention: tiles instead of a giant matrix

Naive attention builds the full N × N score matrix in high-bandwidth memory (HBM), applies softmax and multiplies by V. Traffic grows with N², so long contexts are bandwidth-bound. FlashAttention computes the same result in tiles streamed through fast on-chip SRAM, keeping running softmax statistics, and never stores the full matrix.

Each version targets the bottleneck of its hardware generation. As GPUs gain matrix throughput faster than memory bandwidth and exponential units, the kernel has to compensate. Without the right kernel a faster GPU is just a more expensive one.

For deep-research agents reading huge codebases, memory movement dominates at a million tokens and beyond. A pricier GPU with a matching kernel can lower total cost, though the gain depends on model, batch, sequence length, precision and runtime.

The agentic cost multiplier

One user request becomes routing, retrieval, reasoning, reflection, guardrails and synthesis calls. A step's expected calls per request are its trigger probability times its calls when triggered, minus whatever memoization serves from cache. Prompt caching avoids reprocessing the shared prefix (system prompt, tool definitions, examples) but does not remove the multiplier. Tune the workflow:

Memoize decisions, not just results

Faster execution is no longer the biggest lever; skipping repeated decisions is. Treat the agent as a state machine over facts: the state is the set of facts gathered so far, and the planner maps that state to the next action. Normally the planner (an LLM call) runs every step. With memoization you first look up a canonical form of the state in a cache of past state→action pairs, a constant-time lookup instead of a context-sized model call.

A fact store that knows what changed

Every write is classified. Only added, reinforced and conflict bump the version, so the planner reconsiders only on meaningful change. Keys are normalized so that "Revenue_2024" and "revenue 2024" are the same dimension.

A three-tier cache with context guards

Lookup tries an exact hash of the raw facts, then a normalized hash of canonical facts, then semantic similarity above a threshold. Every tier keys on the full planner context: task, facts, evidence, available tools and stale tools (tools that recently produced nothing new). Leave stale tools out and a cached "DONE" decided under stale pressure can be replayed where no tool is stale, bypassing the anti-looping signal.

A high hit rate is not always goodNinety percent hits that are all stale means the agent is stuck in a loop and failing faster. Track whether cached decisions lead to new state, and force a live call, a different tool or DONE when they do not. Never cache invalid or failed planner output, and add a TTL in fast-moving environments. Spend some of the tokens you saved on a high-quality synthesis step.
