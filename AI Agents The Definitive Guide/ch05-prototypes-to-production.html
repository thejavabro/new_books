From Prototypes to Production

In production, model intelligence is rarely what breaks first. Loose contracts, unvalidated handoffs and ungoverned tools do. This chapter makes agents predictable, recoverable and governable.

1

The brittle chain: Lusser's law

A demo agent works once. In production the limit is rarely model intelligence; it is unconstrained execution. In a multi-agent system one agent's output is the next agent's input, so every loose schema and unvalidated tool call becomes a liability that travels downstream. Reliability engineering has a name for this: Lusser's law. If independent steps run in sequence, the system succeeds only if every step does: P = p1·p2·…·pN.

A validation gate that catches a fraction v of bad outputs (and lets the agent recover) raises each hop to p + (1 − p)·v. Under the same simplifying assumptions, that bends the curve back up.

2

Contracts at the boundary

Contract failures look trivial: a string where an integer belongs, a missing field, a provider that shapes JSON slightly differently. Clean staging tests pass; production breaks. A Pydantic model declares exactly what may enter, and validation happens at the boundary, before bad data spreads. In the book's design the rules come from a central OmegaConf YAML policy with modes such as strict (hard failures) and lenient (controlled feedback), switchable without redeploying. A factory builds the Pydantic contract from whichever policy is active.

# my own sketch of the idea: the contract is built from the active policy
def make_contract(policy):
    class UserRecord(BaseModel):
        user_id: int
        age: int = Field(ge=0, le=policy.max_age)
        note: str = Field(min_length=policy.min_note)
    return UserRecord

Contract = make_contract(pinned_policy)    # built once per run
record = Contract.model_validate(agent_json) # fails fast or coerces "123" → 123

When feeding errors back to the model, translate them into one clear sentence it can act on, not a raw stack trace.

3

Pin the policy, hash it, checkpoint the run

Environments change mid-run. So the policy is pinned at START: the run keeps the rules it began with, and a hash of those rules (plus a hash of the resulting schema) is stored with every database record. That makes "which rules produced this data?" an auditable fact. Edit the live policy and watch the pinned run stay put.

Checkpoints are the other half. A checkpoint should hold the working state, not only messages: intermediate tool results, where execution paused, pending routing, and the model, prompt, tools and policy needed to resume. If the image step fails after an expensive reasoning model wrote the draft, you resume from the last stable node instead of paying for the draft again.

4

Inner loop, outer loop: Instructor and the graph

Pydantic guards the boundary, but the recovery logic still lives in the graph: a fixer node, explicit retry routing. Instructor moves schema enforcement into generation itself. You pass the contract as the response model plus a retry limit; when validation fails, the error is appended and the model asked again, before the output ever leaves the call. Different failures belong to different loops.

Don't overgeneralizeInstructor optimizes retries caused by schema violations. Timeouts, infrastructure errors and side effects remain the graph's job, with bounded retries and checkpoints.
5

MCP: a universal port for tools

The Model Context Protocol standardizes how agents find and call tools, the way USB-C standardized cables. In late 2025 it was contributed, alongside AGENTS.md, to a new Linux Foundation agentic AI foundation. MCP works because the client surface is tiny: list tools, call one. You rarely rewrite your billing API or database; you wrap it in a thin MCP server with typed inputs and outputs and let any agent consume it.

Hard-coding a send_email tool is the old way. With a discovery hub (the book uses Composio; Docker's MCP catalog is another) the agent describes what it wants and receives matching tool definitions at runtime, having executed nothing yet. Try an intent.

6

Deep agents: plan first, delegate, isolate

Unlimited tool access leads to cost, sprawl and cascading failures. Systems like Claude Code and Manus share a recipe: plan before acting, run work in a controlled shell or filesystem, and hand heavy jobs to subagents with their own clean context. LangChain's open-source Deep Agents harness packages that recipe. A subagent may make dozens of tool calls, but only its summary returns to the main agent, so the planner's context stays small.
