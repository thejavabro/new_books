Customized and Advanced Evaluation

Public leaderboards tell you how a model did on somebody else's tasks. Custom benchmarks built from your traces, your repo and your agents' trajectories tell you whether a change helps on yours.

A fully traced system can still leave you guessing

Tracing shows what happened. It does not tell you whether a new model, prompt or orchestration change is better. Until production evidence becomes structured evaluation cases, you depend on spot checks and sparse user feedback. A custom benchmark lets you test alternatives under controlled conditions before redeploying, and it keeps growing from real usage. The chapter covers three complementary perspectives.

1 · system levelTraces → regression suiteReplay real production cases against candidate models and configurations.
2 · verifier basedRepo → executable tasksInject bugs into your own codebase; tests decide if the coding agent fixed them.
3 · trajectoryMultimodal runs → step reviewFor long, visual tasks, judge how the agent got there, not just where it ended.

Users rarely click thumbs down

Explicit feedback is sparse and skewed to the extremes. Users retry, rephrase, correct the agent, abandon, or quietly go do it by hand. Those behaviors, plus system-level signals like repeated tool calls or schema violations, are often your only evidence of failure. Read them carefully; they are indirect.

From production traces to a regression suite

Do not pull every recent trace. Filter to a time window, an evaluation tag, the workflows and agent roles relevant to the release decision, then keep a small representative batch. (Respect retention rules: no tracing for PII or credential flows, separate projects per tenant.) Toggle the filters.

Score each trace with two kinds of checks. Deterministic checks read explicit fields and should do as much work as possible. Judge-based checks handle open-ended quality; keep their written reasons as an audit trail. For pure text quality, group-relative ranking (like RULER in Chapter 3) beats isolated scoring.

Turn your repository into an executable benchmark

  
Production traces reveal business-logic failures, not syntax errors or broken APIs in code an agent writes. For coding agents, flip it: deliberately create bugs. SWE-smith generates task instances from your own repo: a patch that breaks at least one existing test. Only patches that really break tests are kept. A coding agent then has to restore green tests. Correctness is defined by your system's behavior, not by a judge. And because these tasks are fresh, the model cannot have memorized them, unlike public benchmarks that may be contaminated.

6
Long-horizon, visual tasks: judge the trajectory

  
For GUI and multimodal agents, the task is rarely "look and answer". They read an error dialog, open logs, compare screenshots, click through an interface and combine evidence across many steps. The final answer alone hides failures like clicking the wrong element, stopping early, repeating useless actions or losing context. Trajectory evaluation inspects what the agent saw, which tools it called in which order, what each returned, and where it broke. Benchmarks such as SWE-bench Multimodal and AgentVista add screenshots, mockups and diagrams to the mix, since real UI, web and chart bugs live in JavaScript, HTML and CSS, not only Python.
