Revising Microservice Architecture

Domain-driven and process-driven service design each break in their own way. A service can be three things at once: a bounded context, a set of code packages and a set of workloads. Inside it, put the business at the centre.

1

Domain-driven or process-driven?

Two schools dominate service design. The domain-driven one follows domain-driven design: break the system along bounded contexts, so a "product" in the cart is a different model from a "product" in inventory. The process-driven one splits by technical behaviour: whatever needs to scale or run separately becomes its own process, even if several processes share a database. Switch between the two shapes of the same shop.

Real systems mix the two, either for technical reasons (part of a service must run as a singleton) or because teams disagree. A third idea, naming services by verbs ("task-based services" such as RegisterUser), fixes some ambiguity but gives no rule for where to stop splitting. The deeper problem: each school sees only one dimension, business or technical, and bends when reality needs the other.

2

The three-dimensional service

A 3D service is one logical unit seen three ways: a bounded context (first dimension), implemented as one or more code packages (second), and run as one or more workloads (third). Inside, components are white boxes to each other: they may share a data store or file system and know each other's internals. From outside, the whole thing is one black box. The book's example is an access management service. Click any block to trace it across dimensions, and switch the deployment mode.

Access management service

services:
  auth-server:   { image: some-oss/oauth-server }      # external component
  login:         { build: ./components/login }
  permission-api:{ image: permission:local, command: api }
  im-connector:  { image: permission:local, command: connector }
# one image, two entry points: same code, two independently scaled workloads

Own sketch. The key trick is the same image started with different entry points (an argument, an env var, a different main file).

3

Benefits, challenges, and when not to bother

Monorepo as the jarA 3D service works best in its own monorepo (or a module of a project-wide one) holding code, docs, pipelines and tooling for the whole bounded context. Split across many small repos, it becomes a purely logical group that needs meta-packages or a developer portal to hold together. The author suggests challenging the reasons for small repos: they are often historical.

When storage shapes the business

Layers have one blind spot: the direction of dependency. If the business layer depends on the storage layer, storage details creep upward. Picture a user store designed around MySQL: create() returns an auto-increment number and update() is separate, mirroring INSERT and UPDATE. Now move to object storage, where a single "put" overwrites whatever is at a path. Try both interface designs.


      

    

  

  
Not "very good interfaces", just business-driven onesThe fix isn't a cleverer interface. It is an interface defined by the business and implemented by the storage. Storage serves the business; the business is the architectural centre of gravity.

Domain-centric architecture

  
In a domain-centric architecture, the domain defines the abstractions it needs (for example "register a user") and everything else lives outside and depends inward. Onion, Ports and Adapters (Hexagonal) and Clean Architecture all share this core; their differences are minor. Toggle what you consider "outer" and see which way the arrows point.

7
Make the service scream: use cases and invokers

  
A screaming architecture tells readers what the system does, not which framework it uses. One way: put every use case in its own file in a visible use-cases/ folder, and every entry point in an invokers/ folder. Use cases never call each other; shared logic goes to a domain service. Invokers (HTTP handlers, queue listeners, cron, MCP tool handlers, file watchers…) only trigger use cases. Pick an invoker.
