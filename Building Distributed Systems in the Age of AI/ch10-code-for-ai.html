From Code for People to Code for AI

Clean-code advice was written for human readers. Coding agents read differently: they have no memory of last week, they search by name, and they lean hard on types.

1

Code was written for people

"Programs must be written for people to read, and only incidentally for machines to execute." From that idea came almost every style rule: short functions, clear names, blank-line rhythm, comments explaining choices, linters for line length and complexity. The machine never cared. Beneath the practical reasons, the author sees two motives: code is the place engineers spend their days (keep your room tidy), and it is how they express themselves, to an audience of other engineers.

Agents have neither motive. They know every code smell, but nothing smells to them; they'll add to spaghetti and sleep fine. Harnesses rarely tell them to care, and taste is as hard to put into words as music. So expression moves elsewhere: architecture, constraints, rules, specs, reviews. Code becomes the layer that turns intent into instructions, written and read more and more by AI. The principle expands: code must be understandable to humans and to AI tools.

2

A different kind of reader

Many conventions follow from a human limit: roughly seven items in short-term memory. Agents have huge context windows, but their memory is different in kind, not just size. Compare.

Human engineerCoding agent
Working memory~7 items; a function should fit a screenhundreds of thousands of tokens
Between sessionskeeps a mental model of the architecturestarts cold every time, like a new hire
Team knowledgehears syncs, reads PR threadsknows only what is written where it can read
Rememberingautomatican explicit action (writing memory files)
Sees code asa tree of folders and filesa graph of symbols and references

Agents read code in three main ways, often combined: semantic search over embedded chunks, grep-and-follow (regex search, open hits, chase imports), and AST code maps of symbols handed over up front. All treat the codebase as a graph. A name like extract is fine inside one file for a human; to an agent searching globally, it collides everywhere. Which conventions still earn their keep?

The rule of thumb: conventions that exist to ease human working memory are negotiable; conventions that create stable, searchable, unambiguous anchors gain weight. Classify each one.

Negotiable or gaining weight?

Comments: richer, but check themGenerated code carries more comments, perhaps as reasoning written before the code, perhaps as context for future agents. Agents can keep comments in sync cheaply, but can also produce comments that sound right and describe the wrong behaviour. Review them in critical logic, and keep them in sync when you edit by hand.
4

Stable anchors: names and types

Names are the agent's main anchors in the token stream: they show up in search results, attach to signatures and travel through imports. At a call site, processData says nothing, while validateAndNormalizeShippingAddress says almost everything. Types are names with structure. Documentation at zero runtime costIn a structurally typed language such aliases add no safety (they're all still strings), and some linters call them redundant. Their value is meaning for both readers at almost no token cost. In dynamic languages, the same applies to annotating that data is a list of records of a known shape. Revisit lint rules with the new reader in mind.






  
5
Memory files for agents

  
If the agent has no architectural memory, someone has to give it one. Every tool once had its own file; the ecosystem is converging on AGENTS.md, a plain markdown file with no required fields, under version control, optionally one per package. A README is for a human arriving once; AGENTS.md is for an agent returning hundreds of times. Build one: tick lines worth including.
