Your next user may not be a person

Bots already make up around half of measured web traffic, and people increasingly ask an assistant instead of browsing. Those assistants use the same systems we build. Systems that used to stand alone become links in chains orchestrated by agents. So a system needs several doors, each for a different caller. Click one.

2

Make your API agent-friendly

A developer reads the docs once and writes code for every response shape. An agent reads the spec and decides at run time, with no colleague to ask. Everything it knows must be in the spec or the response. Documentation must be exhaustive and discoverable: a /.well-known/api-catalog (separating human docs from machine-readable descriptions) or an /llms.txt markdown file. Then look at what a single field does to an agent.

An MCP server is not a wrapper

  
MCP has three pillars: tools the model calls, resources the runtime injects as context, and prompts offered to the user as ready-made tasks. The first instinct was to wrap REST endpoints as tools. That works technically, but REST is shaped around entities and CRUD, which yields technical tools like "find orders by 20 filters". Design tools around tasks and questions instead. Ask: "What's happening with my order?"

What about just a CLI?Models are superb shell users: they chain, filter and pipe, saving steps and tokens. One personal assistant, sent an unsupported voice note, sniffed the file header, decoded it with a media tool, found an API key in the environment and transcribed it with curl. Impressive, but it needs terminal access (a hard security audit), the task must be known or documented in advance, and chains fail silently on a wrong property name. CLI is a creative fallback, not a discovery mechanism.

    

  






  
4
Keep the UI human, add shortcuts

  
Computer-use agents now rival humans on desktop benchmarks, but every step means perceiving the page (a screenshot runs to thousands of tokens). And the UI's margins, progressive disclosure and multi-step forms exist for good human reasons, so don't redesign it for bots. Add a parallel path: WebMCP exposes the page's actions as tools; the agent still sees the page, but acts in one call. Compare a checkout.

  

    
    
    

    
Rough arithmetic. "UI provides perception, MCP provides action." A short script wrapping a contact form or a booking widget as a tool can be enough, and smaller models get a real chance to succeed.

  






  
5
Exposing your own agents via A2A

  
If your platform already runs agents (multi-turn, clarifying, slow), A2A lets other agents find them through agent cards and hold long conversations: a partner's procurement agent negotiating with your sales agent. Each turn costs an inference on your side, so match the door to the value. Pick a scenario.

  

    
    

  






  
6
Events as a public contract, and going headless

  
Many callers aren't agents at all: workflows, pipelines, iPaaS automations, partner apps. Their question is whether they can react without polling. Webhooks are often thin, undocumented and brittle. A public event catalog (order.created, shipment.dispatched, payment.failed) with documented, versioned schemas and explicit delivery guarantees in the SLA is a different proposition. Publish once; many listen, often with no code on their side. Break something.

  

    

    

    

  

  
The headless thought experimentA headless system has no UI of its own; it delivers value through assistants, messengers, maps listings and social shops. Restaurants on delivery apps and shops on social feeds already work this way. You needn't go all the way, but treating your own UI as one surface among many forces a clean split between capability and presentation. The question flips from "how do users reach our system?" to "how does our system reach the user?"
