Why are we still using human languages?

If models read, write and edit most of the code, why use languages designed for human cognition? A distinction first: a machine can be the executor (compiler, interpreter) or the author and maintainer. This chapter is about the second. The quick answer is that models learned from human code and engineers want output they can review. The author then proposes a thought experiment: what if agents become better coders than people, and the human reviewer disappears? He's honest that there is no clean answer, and marks what is happening, what is research, and what is speculation. Three things move at different speeds:

SpecificationSlowKeywords, syntax, types, semantics. Proposals take 1–3 years.
EcosystemFastTooling, libraries, runtimes, targets. Where the pressure shows.
CultureShiftingWhat people use it for, conventions, what it is combined with.
2

Committees are quiet, the market isn't

Major language roadmaps contain almost nothing motivated by LLMs: free-threading and a JIT, a native compiler port, pattern matching, async refinements, steady small releases. That's not neglect. Committees are slow by design, models move fast, and maybe there is little to add: what helps models (explicit types, unambiguous syntax, deterministic semantics, small surface) is what language design has pursued for decades anyway. The selection happens in the field instead. Explore the clusters, then spin the flywheel.

The training-data flywheel

More code → better generation → more developers → more code. Today's leaders get locked in. Toy dynamics.

Smaller box, fewer mistakes

General-purpose languages consolidate per cluster while domain-specific languages (SQL, GraphQL, HCL…) multiply: small, declarative, well-defined, and a model can learn a new one from docs and a few examples. Illustrative.

The theorists were right?The result looks like the strongly typed, formally specified, often functional languages academia championed for decades (ML, Haskell, OCaml, Lean, Idris, Agda), which industry found too hard to write fluently. That friction disappears when a model writes. But today's models still write Python and TypeScript best, thanks to the flywheel; a new language must first earn a corpus.

Where it ships today: tool orchestration

  
With plain tool calling, every step is a round trip through the model: no chaining, filtering, loops or deterministic error handling without another inference. Let the model write a small program instead and you gain expressiveness, and a trust problem. Compare the approaches on one task: "find the three cheapest flights, then check the weather for each destination."

Two research-grade ideas worth knowingA Lisp-like orchestration language from 2025 adds a natural-language condition (a branch like "is a premium member" is decided by a model call) and automatic parallelization from static dependency analysis. Safety comes from the grammar: if there is no syntax for file I/O, no token sequence can express it.

Keep the formal layer, drop the text

  
Text is a flat projection of a multidimensional program: every call repeats a name, and a rename must touch every copy. Models hold structure internally but must reproduce surrounding characters exactly; many "hallucinations" are right intent, wrong bytes. Alternative: the model emits typed nodes directly, references point at identities, and ill-formed edits are rejected before they apply. Projectional editors have worked this way for years.
