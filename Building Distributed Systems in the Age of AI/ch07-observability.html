Observability in Unpredictable Systems

Logs, metrics and traces assume the code decides what happens. When a model decides, you also need to record why, and the same record serves engineers, auditors and regulators.

The implicit contract, and how agents break it

Picture the fleet platform going wrong: the customer agent credits the wrong person, or the fleet agent sends 40 scooters where nobody rides. Open the code and you find nothing: it called the model with a prompt and tools, exactly as designed. Classic observability rests on an unspoken contract: behaviour is encoded in source code. Logs say what happened, code says why. Audit logs record who did what, and code explains the rules. Toggle the system type.

2

Logs, traces and metrics, re-read

Each classic pillar still works, but its usefulness shifts. Similar requests used to follow similar code paths, so keeping 10% of traces gave a representative picture. Generate traces and see whether a 10% sample tells you much.

3

Capturing the reasoning

Agentic observability captures reasoning, not just code paths. Ideally everything: each prompt, completion, tool call and output, though privacy, security, cost and retention limit that. Log the full input context too; a completion without its context is a return value without its arguments. On top, ask the agent to emit a structured decision record before consequential actions: observations, options considered, why, and confidence. Here is my own example for the fleet agent.

decision_id: fleet-0412-1730
agent: fleet-positioning
action: recommend_reposition
trigger: "event calendar: arena show ends 22:00"
inputs:
  utilisation_arena: 0.86
  forecast_temp_c: 1
considered:
  - option: move_25_from_old_town
    chosen: true
    why: "old town demand low after 20:00"
  - option: no_action
    chosen: false
    why: "forecast exceeds local supply"
confidence: 0.78
needs_human: true
Like structured logging, but in the promptThe format is instructed in the prompt. It costs tokens in both instruction and output, and buys a searchable, auditable record for engineers and auditors alike.
Not a window into the modelA model's stated reasons need not be faithful to how it actually decided; sometimes they contradict the answer. They are still useful context for finding bad data, weak guardrails or broken tools.

Metrics for decisions, not just latency

Agentic workloads are heterogeneous: three tool calls or fifteen documents. Twenty seconds can be fine; three seconds can be suspiciously quick. So add task-aware metrics on top of infrastructure metrics, and outcome-based SLOs. Click the classifications below: is each signal explicit, implicit or outcome-based feedback?

5

Who is accountable?

Humans remain accountable, legally and ethically. But reviewing every decision kills the efficiency. Human in the loop means the agent pauses only for high-stakes steps: large amounts, irreversible changes, sensitive data. Move the threshold. Then consider the catch: as agents grow more capable, humans won't be able to redo the analysis at all. Oversight then shifts from checking the decision to auditing the reasoning.

6

When debug logs become regulatory evidence

In deterministic systems, engineers keep short-lived debug data and compliance keeps long-lived audit logs; the code bridges them. In agentic systems the reasoning trace is the only explanation, so the same artifact serves the engineer and the regulator. Which requirements does it pick up? Toggle the audiences.

The observability store becomes a sensitive systemTraces hold user input, personal data and full model output, and masking free text is hard. Encrypt at rest and in transit, isolate tenants, enforce role-based access. Regulations such as the EU AI Act make picking an observability platform a compliance decision.
