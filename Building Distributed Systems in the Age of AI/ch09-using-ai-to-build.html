1

Seven-league boots

If your first instinct, once a design is clear, is to open the editor and type, you may be falling behind: not because typing is wrong, but because it is no longer the fastest path from understanding to implementation. Coding agents are among the most successful applications of agentic architecture, built and used by the very engineers they might replace. Like the fairy-tale boots that cover seven leagues per step, they are powerful and disorienting: output that looks right but isn't, ignored constraints, changes you didn't ask for. The urge is to take them off. The book says: don't. Learn to adjust them.

UpsideMore productive engineers, cheaper prototypes and trial-and-error, AI code review that finds subtle bugs and security issues on top of human review.
DownsideUnreviewed generated code ships vulnerabilities and bugs; overtrust in automated review that lacks context misses business-logic problems.
2

When barefoot is the right choice

Writing by hand still pays off when the process yields something: understanding, accountability, trust or discovery. Tap each case.

Is the agent worth it for this task?

Figures are yours to set. The book's rough example: about $20 of API calls plus $200 of engineer time versus over $1,000 of engineer time alone. Remember the hidden third cost: context switching and briefing, which can dominate small, well-scoped tasks.

3

Shaping, not writing

Left alone, an agent "free rides": the output works but reflects no design philosophy, convention or architectural intent. You teach it with rules files, skills, project context and custom instructions, the institutional memory of how code is written here. It is pottery on a fast wheel.

Not "prompt better"It is closer to training a junior through example and feedback, except the training persists in files. Over time the rules become an engineering artifact alongside the code, and existing code serves as a strong example, especially when you tell the agent to follow it.
4

Learning to delegate to something without reluctance

Situational leadership describes four development levels of a delegate (D1 enthusiastic beginner to D4 self-reliant expert) and matching styles (S1 directing, S2 coaching, S3 supporting, S4 delegating). Agents have no motivation and never push back, so one axis remains: competence, per domain. And they present D1 and D4 work with the same confidence. Pick a task and a style.

5

The fallacy of intelligence

Do you see a face?

We personify anything with a hint of a face, and a polite, flattering chatbot gets the full treatment. That raises expectations: users trust outputs too much, operators under-review, products imply more authority than the model has. A model predicts tokens, astonishingly well, but alone it is a function, not a mind. Setting the right expectations has to be designed: off-topic refusal, filtering, clear disclosure that it's automated. As consumers of coding agents, engineers must apply the same realism to their own tools.

6

Methods for working with coding agents

Methods appear and vanish; the principles outlast them. They differ in how much structure you give upfront and how tightly you stay in the loop. Click one.

A Ralph Loop, overnight

while :; do cat PROMPT.md | coding-agent; done
# each run: read spec + plan + code, do ONE atomic change, commit, exit

Fresh context each cycle; Git is the long-term memory. "Eventual correctness": some cycles break things, later ones fix them, but only if the agent can verify its work (close the loop).

7

Shifting bottlenecks

The Theory of Constraints says throughput is limited by one constraint at a time. Speed up writing and the queue moves to review and testing. (A burger chain once sped up order-taking and buried its kitchen; things improved only when a cashier called in sick.) Turn the dials.

Tests are the next queueGenerated tests are boring to review, so they get skimmed, and agents happily write green but meaningless ones: happy path only, assertions on internals, mocked-away risk, hard-coded values. Derive tests from specs, not from the code. And the open question remains: who is accountable when generated code fails?
8

Education and hiring

Why learn data structures if AI writes them? Because the job is making good decisions about systems, and those happen before and after the code. Calculators didn't make arithmetic useless: without it you can't spot a wrong answer. Someone who never struggled with SQL won't notice the generated query that scans ten million rows on every keystroke. Meanwhile entry-level work is compressed, and how the industry grows future seniors without it is unsolved. Sort the skills.

Gaining or losing value?

For interviewsPrefer design discussions, reviewing buggy or generated code, pairing with an agent present, and take-homes followed by deep questioning. Advice to candidates: use agents if you like, but never submit anything you can't fully own in a room with a senior engineer asking questions.
