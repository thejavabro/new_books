Agentic Architecture

An agent is a service whose control flow is decided by a language model at run time. That one change ripples through memory, retrieval, security, platforms and how several agents work together.

An old idea with a new brain

Agents are not new. Research from the mid-1990s already called them important, and defined an agent as a system situated in an environment and capable of autonomous action in it to meet its objectives. Classic agent theory talks of beliefs, desires and intentions: an agent pursues its intentions, tracks whether they worked, and tries again. Language models make that practical, because intentions and perceptions no longer need rigid formal structure. The price is nondeterminism (and the bill for inference).

Most agents today are built service-like: a request becomes an intention, and an isolated agent instance runs in a partly shared, partly personal environment. A rarer style has one long-lived intention, such as a health assistant that watches sensors, talks to you daily and books appointments. Compare an LLM agent with the services you know.

The agent loop: observe, reason, act

A model only produces tokens. It can't call an API or run code; the surrounding runtime reads the tokens and acts. In the agent loop, the runtime keeps asking the model for the next step until the model says the goal is done. Here is my own version of the book's HR example: a user types "Take the week around 14 August off."

Tool calling, structured output and MCP

How does the model "ask" the runtime? The runtime sends a list of tools, each with a name, a description and parameters, usually as JSON Schema. Models were fine-tuned to answer with a specially formatted tool call when they need one, and the runtime replies with the result. This rests on structured output: models can emit JSON that matches a schema. Edit the request and see the call.

{ "name": "weekday_of",
  "description": "Weekday for a date. 1 = Monday.",
  "parameters": { "type": "object",
    "properties": {
      "day":   { "type": "integer" },
      "month": { "type": "integer" },
      "year":  { "type": "integer" } },
    "required": ["day","month"] } }

      

    

  

  

    
MCPThe Model Context Protocol standardizes tool calling. A thin client lives in the agent runtime; the server, part of the external system, declares tools, resources and prompt templates. They talk JSON-RPC 2.0 over HTTP or standard I/O.

    
System vs. user promptThe system prompt holds role, boundaries, tool guidance and security policy, and stays stable. The user prompt is the actual request. Models are trained not to let user input override system instructions.

    
Young standardMCP is still maturing and a successor may come. Tool calling is the lasting idea underneath.

Memory: the model forgets, the app remembers

  
Models keep nothing between calls, so the runtime resends history every turn: all of it, a window, or a summary. Providers fine-tuned models on a role-tagged format (system, user, assistant, tool), and the model is trained to pull clean facts out of messy, self-correcting chat. Across conversations, memory has to be built by the application. Compare two ways.

Retrieval-augmented generation

  
Memory is long-term. Sometimes an agent needs information only for this task: a customer's record, or how colleagues handled similar requests. RAG pulls relevant information into the context before or during generation. Looking up a record by ID is easy; finding "similar requests" needs embeddings: an embedding model turns text into a vector of hundreds to thousands of numbers, each a learned feature, and similar meanings land near each other. Prompt injection and its defences

  
A model's input is one undifferentiated sheet of text: system prompt, tools and user data all mixed together. So anything that looks like an instruction may be obeyed. It is SQL in the 1990s again: before parameterized queries, clients escaped strings and hoped. LLMs have no equivalent of a prepared statement yet. The answer is defence in layers. Pick an attack and switch defences on.

Agentic platforms: a greenhouse for agents

  
A hello-world chatbot is a few lines; a production agent is many concerns. You can run agents as ordinary services in Kubernetes, but platforms bundle the specific "climate" they need. A word on naming: in the broad sense an agent is a whole intentional system of many parts; in toolkit language it has shrunk to model + system prompt + tools + memory running one loop. Click a platform component.

  

    

    

  

  

    
Agentic platforms and AI workflow (iPaaS) platforms are converging

    

    
Agentic platforms grew from AI infrastructure and are adding connectors, schedulers and retries. Workflow platforms grew from enterprise integration and are adding loops, dynamic branching and memory. Self-hosted frameworks are the third route: full control and no lock-in, at the cost of running everything yourself.

  






  
8
Many agents: orchestration or choreography

  
Why split work across agents? Parallelism; smaller contexts (every loop step resends history, so irrelevant detail costs tokens and confuses the model); narrower goals and fewer tools, which models handle better; different models per task for quality or cost; and reuse, even of third-party agents. Then decide who leads.

The invisible why

  
Traditional observability (logs, traces, metrics) shows that the calendar tool was called with these dates and failed. It doesn't show why the model picked those dates, or whether it considered time zones and existing blockers. Failures are stochastic: 99 requests go fine, the 100th fails on a subtle phrasing. And a model's own explanation may be a summary shaped by context, much like a person explaining an opinion to a child versus to their boss. Chapter 7 takes this further.

  
The key adaptationTreat nondeterminism as a feature: flexibility inside guardrails. Agentic architecture adds to services, messaging and streams; it doesn't replace them.
