Defining Data Contracts

Brokers never look inside a message, so the contract between producers and consumers lives elsewhere. Good events, a schema format and compatibility rules keep dozens of teams from breaking each other.

What should an event contain?

An event is an immutable fact that something happened, with a timestamp. Brokers do not care what is inside, so producers and consumers need an explicit agreement: a data contract. Designing that contract is the architect's core task, and the first question is how much to put in the event.

Take a UserProfile made of the user, a list of Addresses and a list of SocialAccounts. The user's city changes. A fact event (also called a state event) carries the entire current state; a delta event carries only what changed.


    

    

  

  
Other design choices: should technical attributes (event ID, source, correlation ID, schema version) live in the payload or in headers? Should consumers receive one event per entity or one per use case? Those come next.

3
Thin notifications that make you call back

  
A tempting shortcut: publish only "profile 42 changed" and let consumers call the producer's API for the current state. It keeps events tiny and the producer's model private. Step through what can go wrong.

  

  
The pattern reintroduces synchronous coupling and load on the producer, and the state you fetch may not be the state the event was about. It needs extra coordination to get right.






  
4
Evolving events without breaking anyone

  
Events change. The question is who upgrades first. With backward compatibility, consumers upgrade first: the new consumer must still read old events. With forward compatibility, producers upgrade first: the old consumer must cope with new events. Toggle and step through a rollout.

  

    

    

  

  
When a change cannot be compatible, publish V2 to a new channel and run both, or place a temporary Transform service that reads V2 and writes V1 for consumers that have not moved yet. Retire the old path once everyone is validated.






  
5
Schema formats: JSON, Avro, Protobuf

  
A data contract has three parts: the structure (a schema), the channel (a topic), and the trigger, when and why it is sent, which no schema language captures and must be documented in words. For structure, three formats dominate. Avro and Protobuf keep field names out of the payload, so messages are much smaller than JSON.

  

    

    

    

  

  
Field notes
Northwind's team started with plain JSON, which everyone knows. The lead architect, with a database background, insisted on formal schemas. They pick Avro for its mature tooling and broad library support, design fact events (a natural fit for compacted profile topics), and keep schemas in a central repository owned by the producing team.

How Schema Registry works

  
Schema Registry is a separate clustered service (one primary handles writes) with an HTTP API. It stores schemas, versioned, in a Kafka topic of its own. Clients cache what they fetch, so it is not on the hot path for every message. Step through one message.

  

  
Schemas get there either by automatic registration, on the producer's first send of a new shape, or by explicit registration through the REST API or a build plugin. Auto-registration is convenient in development but risky in production: a typo becomes version 1 for everyone.






  
8
Subjects: what a schema is versioned under

  
Versions and compatibility are tracked per subject. The naming strategy decides which events can share a topic.

  

    

    

    

  






  
9
Compatibility checker

  
The registry rejects a new version that violates the subject's mode. The default is BACKWARD. Choose a mode and a change.

  

    

    

    

  

  
Plain modes check against the previous version only; the _TRANSITIVE variants check against all earlier versions. Setting NONE temporarily to push a breaking change, then switching back, is possible but leaves the breakage for consumers to discover.






  
10
Alternatives and common problems

  
Karapace (open source, Aiven) and Apicurio (Red Hat) are registries largely API-compatible with Confluent's. Some teams skip a central server and ship schemas as a versioned client library, at the cost of message browsers and tools that cannot decode the data. Confluent's commercial platform adds data-contract rules (integrity constraints, field encryption, migration rules).
