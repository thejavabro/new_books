Who keeps the cluster's metadata?

Where do topic configurations live, and who decides which broker leads each partition? In modern Kafka, a quorum of KRaft controllers. They store all metadata (topics, partitions, configs, ACLs, broker registrations, producer IDs) in an internal log, __cluster_metadata, replicated with the Raft consensus protocol. Brokers serve data; controllers serve the control plane.

# controller-only node (illustrative)
process.roles=controller
node.id=1
controller.quorum.voters=1@ctl1:9093,2@ctl2:9093,3@ctl3:9093
listeners=CONTROLLER://ctl1:9093

A node can also run process.roles=broker,controller (combined mode), which is fine for development; production clusters usually isolate controllers.

2

Quorum math: 2N + 1

A metadata change is committed only when a majority of controllers (voters) have it. To survive N failures you need 2N + 1 controllers. Three controllers tolerate one failure, five tolerate two. Four tolerate only one, so even numbers buy nothing. Click controllers to fail them.

ZooKeeper, brieflyOlder clusters keep metadata in an external Apache ZooKeeper ensemble, with one broker elected as controller. KRaft arrived as an experiment in 2.8 and became the default later in the 3.x line; Kafka 4.0 dropped ZooKeeper entirely. Many production systems still run ZooKeeper mode, so migration (via a bridge phase) is a real project.

On-premises, cloud or both?

The book weighs three dimensions: operational complexity (hardware, upgrades, 24/7 skills), scalability (procurement lead times versus elastic capacity, but with provider limits) and security and compliance (data residency, control over keys and networks). Answer for your organization.

Authorization with ACLs

An ACL says: principal P is allowed (or denied) operation O on resource R from host H. Resources are topics, consumer groups, the cluster, transactional IDs and delegation tokens; names can be literal or prefixed. Build one and test a request against it.

Note the granularity: once a principal may read a topic, it reads all of it. There is no per-message or per-field permission, so sensitive data may need separate topics or field-level encryption.






  
7
Protecting data at rest

  
TLS protects data in motion only. Brokers decrypt, store plaintext on disk, and re-encrypt for consumers. For data at rest the options are filesystem or volume encryption (Linux LUKS, encrypted cloud disks), which protects stolen disks but not a curious admin, or end-to-end encryption in clients, where producers encrypt payloads and only authorized consumers can decrypt. End-to-end is stronger but costs key management, defeats broker-side compression, and must leave keys unencrypted or partitioning and compaction break.

  
Field notes
Northwind's plan: SASL over plaintext between controllers and brokers and between brokers, inside a tightly segmented and monitored private network, to avoid TLS overhead; mTLS between clients and brokers, where traffic is exposed. They issue certificates with the infrastructure team, set ACLs for Kafka Connect and Schema Registry, and document every network path and port.
