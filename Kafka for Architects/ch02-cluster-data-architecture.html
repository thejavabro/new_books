Kafka Cluster Data Architecture

A topic is a name; the real unit of work is the partition. How you partition, replicate and retain data decides throughput, ordering, durability and cost.

1

Topics, partitions and parallelism

Three nouns organize all data in Kafka. A topic is a named destination for one kind of event, such as CUSTOMER_PROFILES. Each topic is split into partitions, the units of scale and redundancy. Inside partitions live messages, each with a key, a value and headers.

The partition count you choose when creating a topic sets its maximum parallelism. Inside a consumer group, each partition is read by exactly one consumer instance at a time, so a fourth consumer on a three-partition topic simply sits idle. Move the sliders.

2

Ordering lives inside a partition

Kafka guarantees order only within a partition. Across partitions of the same topic there is no global order. The book's example: a transaction service publishes balance changes for customers to Customer 360. If two updates for the same customer land in different partitions, two consumer instances may apply them in the wrong order and show the customer a stale balance.

The fix is the message key. The producer hashes the key to choose a partition, so every message with the same customer ID goes to the same partition and is read, in order, by the same consumer.

3

Leaders, followers and in-sync replicas

Each partition is copied to several brokers. The replication factor (RF) is set per topic and defaults to 1, which you should override. One copy is the leader; producers write only to it, and the followers fetch from it. Followers that are fully caught up form the in-sync replica set (ISR).

min.insync.replicas says how many replicas, leader included, must be in sync for a write (with acks=all) to be accepted. Below that number, producers get an error rather than silently losing durability. The usual recommendation is RF 3 with min ISR 2: one broker can fail and the topic keeps accepting writes safely. Try killing brokers.

Leaders are spread across brokers on purpose, so the write load is balanced. When a leader's broker dies, the controller promotes an in-sync follower.

4

Anatomy of a message

"Event" is the logical idea; "message" (or record) is its physical form. Tap each part.

Producers do not send messages one at a time: the client groups them into batches, and the batch is the unit sent over the network and written to disk. Each message gets an offset, its position in the partition. A message is uniquely identified by three values: topic, partition, offset.

5

Segments on disk and data retention

Every partition is a directory on the broker's disk, and its log is split into segment files. Only the newest, active segment receives writes. When it reaches a size or age limit it is closed and a new one starts. Retention then works on whole closed segments: once every message in a segment is older than the retention period (7 days by default) or the partition exceeds its size limit, the segment file is deleted, whether or not anyone read it. That is why deletion time is approximate.

6

Choosing the partition count

More partitions mean more parallelism, but each one costs broker memory, file handles and metadata, and lengthens leader elections when a broker fails. And the count is hard to change later: adding partitions remaps keys (breaking per-key order), and you cannot reduce it at all without recreating the topic. So size it up front. A rough formula: n = max(t / p, t / c), where t is target throughput and p and c are what one partition can handle per producer and per consumer.

Rules of thumbBenchmark if you can. Without numbers, 9, 12 or 15 are reasonable starting counts. Avoid prime counts, which divide unevenly across brokers. KRaft removed the old ZooKeeper-era ceiling of roughly 200,000 partitions per cluster, but each partition still has a cost.
7

Compacted topics: the log as a table

Instead of deleting by age, a topic can use cleanup.policy=compact: Kafka keeps at least the latest value for every key. An account-balance topic then behaves like a key-value table: a dashboard that starts up reads it and gets every account's current balance. To delete a key, send a tombstone, a message with that key and a null value; it is eventually removed too.

You cannot trigger compaction by hand. Background cleaner threads rewrite closed segments (never the active one) when the "dirty" share of the log passes min.cleanable.dirty.ratio (0.5 by default), subject to minimum and maximum compaction lag settings. Offsets are preserved, so compacted logs have gaps.

Field notes

Northwind chooses a delete policy for transactions, which are immutable facts. For customer profiles they experiment with compaction, so the topic itself holds the latest profile of every customer, and plan tests with repeated updates and tombstones before committing.

8

Documenting topics with AsyncAPI

REST has OpenAPI; event-driven systems have AsyncAPI. The book uses it to record decisions as they are made: channels (topics), their addresses, partitions, replication, cleanup policy and, later, message schemas. A sketch in the same spirit:

asyncapi: 3.0.0
info: { title: Customer 360, version: 0.1.0 }
channels:
  customerProfiles:
    address: CUSTOMER_PROFILES
    bindings:
      kafka:
        partitions: 12
        replicas: 3
        topicConfiguration:
          cleanup.policy: [compact]
          min.insync.replicas: 2   # illustrative values
