1

Smart endpoints, dumb pipes

With Kafka, "smart endpoints, dumb pipes" is not a choice but a consequence: brokers never interpret messages, so all logic sits in services. Compare it with the patterns around it.

2

Request-response over Kafka

Kafka is built for pub-sub, but you can emulate request-response: the requester sends a message with a CORRELATION_ID header and a reply topic, the responder echoes the ID in its reply. The hard part is getting the reply back to the same instance that holds the waiting request, because a consumer group spreads the reply topic over all instances.

Every variant must also decide what happens when the requesting instance dies (rebalancing cannot move in-memory waiting requests) and how long to wait before giving up. If you need lots of synchronous calls, HTTP or gRPC is usually the better tool.

3

CQRS: one writer, many read models

Command Query Responsibility Segregation splits the service that changes data from the services that answer questions about it. The command side validates and stores changes and publishes events; each query side consumes them into a model shaped for its reads: a search index, a denormalized table, a cache. It pays off when read models differ a lot from the write model or reads vastly outnumber writes. For simple CRUD it is overhead.

4

Event sourcing with snapshots, and tiered storage

In event sourcing the events are the source of truth and state is derived by replaying them, which Kafka supports with long or infinite retention. Replaying everything on every start gets slow, so services take periodic snapshots to a store (MongoDB in the book's example) together with the position <topic, partition, offset> they reflect. On start: load the snapshot, seek to the stored offset, replay only what came after.

Long retention raises the storage bill, yet old ("cold") data is rarely read. Tiered storage keeps recent segments on broker disks and moves closed older segments to object storage such as S3, Azure Blob or Google Cloud Storage. Consumers read both transparently; brokers stay small and fast to rebalance.

5

Kafka in a data mesh

Analytical data traditionally flows into one central warehouse or lake owned by a central team, which becomes a bottleneck. A data mesh decentralizes it with four principles, and Kafka maps onto each.

6

Inside Kafka Connect

Kafka Connect moves data between Kafka and external systems by configuration: install a connector plugin, post a JSON configuration to the REST API, and it runs. It keeps no database of its own; configs, offsets and status live in Kafka topics. Workers form a cluster; each connector is split into tasks that run in parallel across workers (up to tasks.max). Follow one record through a source pipeline.

Source connectors poll external systems and must remember what they already loaded (they store their own source offsets). Sink connectors are ordinary consumers in a group, so partitions spread over tasks and Kafka offsets track progress; with 2 partitions, a third task gets nothing. Sinks can send unprocessable records to a dead-letter topic.

7

Databases: what does each JDBC mode see?

The JDBC source connector polls tables. Its mode decides how it spots new data, and therefore what it misses. Pick a mode and see which database operations reach Kafka. (Log-based change data capture, such as Debezium, reads the transaction log instead and sees everything, including deletes.)

{ "name": "c360-transactions-source",
  "config": {
    "connector.class": "JdbcSource",
    "connection.url": "jdbc:postgresql://db:5432/transactions",
    "table.whitelist": "public.transactions",
    "mode": "incrementing", "incrementing.column.name": "id",
    "topic.prefix": "connect-",
    "value.converter": "io.confluent.connect.avro.AvroConverter",
    "tasks.max": "1" } }   // illustrative

The JDBC sink writes with plain insert or idempotent upsert by primary key, and turns tombstones into deletes.

Field notes

Northwind tries loading TRANSACTIONS straight from the database with a JDBC source instead of writing a TransactionService. The data engineer worries that this exposes the raw table model and bypasses data contracts, so the connector runs on a separate, isolated Connect cluster.

8

Idempotence, transactions and the outbox

Data can be lost before sending, in flight, on the broker or in the consumer; it can also be duplicated by retries. Kafka gives three tools. First, the idempotent producer: each producer gets an ID and numbers its batches per partition. The broker accepts only the next expected number, so a retried batch that already landed is discarded and a gap is refused, which keeps order even with several requests in flight.

Second, transactions make a read-process-write step atomic: an order service reads from ORDERS and writes to SHIPMENTS, BILLING and INVENTORY; the three writes and the consumer offset commit succeed or fail together. That is Kafka's exactly-once semantics, within Kafka. Consumers must set isolation.level=read_committed to hide aborted and still-open transactions.

Third, for anything outside Kafka: Kafka does not join two-phase commit (KIP-939 proposes it), so "update the DB and publish" cannot be one transaction. The transactional outbox fixes it with the database's own transaction.
