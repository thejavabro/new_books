What's Next for Kafka

Kafka keeps absorbing new roles: workflow backbone, edge buffer, object-storage-backed log and the nervous system for machine learning and AI agents.

1

From LinkedIn's crisis to a platform

In the late 2000s LinkedIn's systems produced huge volumes of profile updates, page views and messages, and users expected everything fresh. Batch pipelines were too slow and too tangled to reuse. The answer was a system that handles massive event rates, processes with low latency, and stores events durably so consumers can recover after downtime: a distributed commit log with smart endpoints and dumb pipes. The book closes by asking where that log goes next.

2

Kafka as an orchestration backbone

Most Kafka applications today are handcrafted: every team re-implements consumption, correlation, retries, error handling and schema plumbing. The trend is a higher level of abstraction: low-code and declarative platforms (Nussknacker and Quix build on Kafka; Apache StreamPipes supports several messaging systems) where domain experts model a scenario visually or in YAML, and the platform generates and provisions the topics, schemas and Flink or streaming jobs. Build a scenario and deploy it.

3

WebAssembly, serverless and the edge

WebAssembly runs compiled C, C++ or Rust code in the browser at near-native speed, the idea Java applets never made work. Could a browser talk to Kafka directly? Not with the native protocol: it runs over raw TCP, and browsers only speak HTTP and WebSocket. Compare the routes being explored.

Serverless Kafka means two things. Serverless clusters: you define topics, the platform handles brokers, partitions and scaling, and you pay per use. Behind it, still real Kafka semantics. Serverless processing: functions (AWS Lambda and similar) triggered per event. Compare the bill, then check whether your workload suits functions.

Kafka at the edge: a small cluster in a factory, vehicle, store or gateway, close to devices, on constrained hardware, built to survive unreliable links. It filters, enriches and alerts locally and forwards to the central cluster when connected, using MirrorMaker (consume-and-produce replication) or broker-level Cluster Linking.

4

Diskless Kafka: storage leaves the broker

Classic brokers are stateful: process plus local disks. In the cloud that hurts: fast disks are expensive, and replicating between availability zones costs real money in cross-zone traffic. Object storage is far cheaper. KIP-1150 (under discussion when the book was written) proposes diskless topics whose data lives only in object storage, with the client API unchanged. Compare the producer paths.

Early limitations in the proposal: no log compaction and no transactional writes on diskless topics, expected to be lifted later. The price is higher read latency, acceptable for many cloud workloads where cost and elasticity matter more.

5

Kafka in the AI and ML world

Batch-trained models served with static features suit decisions that can be hours old. Fraud detection, recommendations and anomaly monitoring cannot wait. Kafka becomes the backbone for three patterns.

Incremental learning, live

A tiny online model estimates the average transaction amount from small batches. Halfway through, behaviour shifts (concept drift). A batch model trained once would stay stuck on the old value.
