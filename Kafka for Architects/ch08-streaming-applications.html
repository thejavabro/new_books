Designing Streaming Applications

Stream processing turns the overnight batch into a continuous calculation. Kafka Streams makes it a library: topics in, topics out, with local state backed by changelog topics.

1

From ETL to stream processing

A streaming application consumes events, transforms them and emits new events continuously, for example an OrderEnrichmentService that adds customer details to each order. It helps to place it next to the older paradigms. ETL extracts data, transforms it in a staging area, then loads it. ELT loads raw data into the target (a warehouse) and transforms it there. Stream processing does the transformation event by event as data arrives. It is less a rival to ETL than ETL without the waiting.

2

Kafka Streams: a library, not a cluster

Kafka Streams applications are ordinary Java services (often Spring Boot) that read input topics and write output topics. There is no processing cluster to run: you deploy more instances, and they share the work as members of one consumer group. Why not just write a consumer and a producer by hand? Open the cards.

Field notes

Northwind's first design had Customer360Service aggregate everything into a relational database behind a REST API. The streaming redesign adds a CustomerJoinService that joins profiles and transactions in real time and writes ready-to-use records to a compacted Customer360-enriched topic, keyed by customer ID, so the latest view of every customer is always in Kafka.

Stateless operations: build a topology

An application is defined as a topology: source topics, a chain of operations, sink topics. Stateless operations look at one record at a time: filter, map / mapValues, flatMap, branch, selectKey. Toggle operations and watch the output topic change.

Stateful operations and fault tolerance

  
Stateful operations (count, aggregate, reduce, join) need memory of earlier records. Kafka Streams keeps it in local state stores, key-value stores backed by RocksDB on disk, and mirrors every change to a compacted changelog topic in Kafka. Lose the instance, and a new one rebuilds the store from the changelog. Count orders per region, then crash it.

5
Tasks, threads and instances

  
Parallelism comes from input partitions. Kafka Streams creates one task per partition (per sub-topology); a task owns its partitions and its slice of the state, and that mapping is fixed. Tasks are spread over the threads of all running instances, and redistributed when instances come or go. Each record goes through the whole graph before the task takes the next one.

  

    

      
      
      
    

    

    

  






  
6
Windowing: aggregating over time

  
"Orders per region" over all time is rarely the question; "orders per region per five minutes" is. Windows group records by their timestamps. Pick a type and slide the size.

  

    

    

    

    

  






  
7
Joining streams

  
Enrichment means joining: an order with its payment, a transaction with the customer profile. A join only works if matching records meet in the same task, which means the inputs must be co-partitioned: same key, same number of partitions, same partitioner. If keys differ, the app must first re-key, which writes through an internal repartition topic. And since two events rarely arrive at the same moment, stream-stream joins are always windowed: each side waits a bounded time for its partner.

  

  

  
Interactive queries: since results already sit in state stores, instances can expose them directly (for example via REST). Each instance knows, from metadata, which instance holds which key, and forwards the query if needed. Useful, but you then own an API built on a sharded, rebalancing store.

Late data and other streaming pitfalls

  
Time in streams is messy. Records can sit in a partition out of timestamp order (several producers, retries, clock skew), and some arrive long after their window should have closed. A window accepts late records only during its grace period; after that they are dropped, often silently. Drag the delay.
