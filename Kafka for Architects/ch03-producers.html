Kafka Clients and Message Production

A producer is a small machine of buffers, batches and retries. Its settings decide where each record lands, how fast it travels and whether it can ever be lost or duplicated.

What happens when you call send()

At Northwind, when a customer profile is created or changed, a profile service validates it, saves it locally and must also publish it to Kafka. Calling send() looks instant, but the client library runs a small pipeline behind it. Step through it.

Kafka speaks its own binary protocol over TCP, and official or community client libraries exist for most languages. They hide batching, retries and leader discovery, which means behaviour is driven almost entirely by configuration. Good practice: keep that configuration outside the code, so the same build behaves predictably in every environment.

2

Listeners: one cluster, several doors

Brokers carry two kinds of traffic: client requests and replication between brokers. Both use the same mechanism, listeners, each with its own name, host, port and security setting. The book's example uses three. Tap one.


    
Clients start from a short bootstrap.servers list, ask any broker for metadata, and receive the addresses in advertised.listeners. If those are addresses the client cannot reach (an internal IP behind a load balancer, say), the first connection works and every later one fails: a classic setup bug.

Serializers: both sides must agree

  
Brokers only move bytes. The producer's serializer turns an object into bytes and the consumer's deserializer turns them back. Keys and values have separate serializers. Nothing in the broker checks that they match, so the contract lives in configuration and, later, in a schema registry (chapter 6).

Quotas: sharing the cluster fairly

  
A shared cluster needs guard rails. Quotas cap produce and fetch byte rates and the share of broker request threads a client may use. A client over its quota is not rejected; the broker delays its responses (throttling) until its average rate falls back under the limit.

  

    

      
      
      

    

  

  
Quotas are attached to a user principal (preferred, since it comes from authentication) or to a client.id (any string, easy to fake or auto-generate). Even without quotas, give every producer a meaningful client.id prefix: it makes monitoring readable.






  
5
Choosing a partition

  
Which partition gets each record? By default, a record with a key goes to hash(key) mod partitions, so the same key always lands in the same place. A record without a key uses the sticky partitioner: fill a batch for one partition, then switch, which gives big efficient batches but no per-key order. You can instead configure a round-robin partitioner, pass a partition explicitly, or write a custom one for skewed keys, at the cost of per-key ordering.

  

    

    

    

  

  
Field notes
The Customer 360 team keys CUSTOMER_PROFILES by customer ID because the order of updates matters, and keys transactions by their own identifiers. Entity IDs as keys become their default rule.






  
6
acks: latency versus durability

  
What counts as "delivered" is the producer's choice, set per producer with acks. Pick a failure and see what each setting does with it.

  

    

    

  

  
acks=all is only as strong as min.insync.replicas"All" means all in-sync replicas, and the leader counts as one. With the default min ISR of 1, a lone leader can acknowledge on its own, which behaves like acks=1. For critical data set min ISR to RF minus one. Since Kafka 3.0, acks=all with idempotence is the default.

  
Field notes
Customer data is business critical and a few extra milliseconds are acceptable, so Northwind uses acks=all for the ODS producers.






  
7
Batching, linger and retries

  
Batches are built per partition in client memory (buffer.memory) and sent by a background thread. A batch goes when it reaches batch.size (16 KB default) or when linger.ms expires (0 by default, so "as soon as the sender is free"). The broker acknowledges a whole batch; if no acknowledgment comes, the whole batch is retried. A few milliseconds of linger often buys much larger batches and far fewer requests.
