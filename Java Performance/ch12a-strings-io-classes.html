Java SE API Tips: Strings to Classes

Small API choices made millions of times add up: compact strings and interning, buffered streams, faster startup with class data sharing, and the true cost of exceptions and logging.

Strings: compact storage and deduplication

Strings are often the biggest consumer of heap. Since JDK 9, compact strings (-XX:+CompactStrings, on by default) store a string whose characters all fit in Latin-1 as one byte per character instead of two. Type a string:

JDK 8: char[] (2 bytes each)
JDK 11: byte[] (1 byte each if Latin-1)

Duplicate strings (the same text in many separate objects) are another waste. Three fixes: canonicalize them yourself (chapter 7); intern() them; or let G1 do it with -XX:+UseStringDeduplication, which makes duplicate strings share one backing array in the background (it costs some GC time, and the String objects themselves remain).

2

Interning and the string table

intern() returns a canonical copy from a JVM-wide hash table held in native memory. The table has a fixed number of buckets (-XX:StringTableSize; 60,013 in JDK 8 and 65,536 in JDK 11). If you intern far more strings than buckets, the chains get long and every intern slows down. Check with -XX:+PrintStringTableStatistics or jcmd <pid> VM.stringtable.

String concatenation

A single expression like "a" + b + "c" is compiled efficiently, and JDK 11 compiles it even better (with invokedynamic, so recompiling old code helps, especially when numbers are mixed in). The trap is concatenation in a loop: each += builds a whole new string.

// O(n²): copies the growing string every time
String s = "";
for (Trade t : trades) s += t.id() + ",";
// O(n): one buffer, appended in place
StringBuilder sb = new StringBuilder(trades.size() * 8);
for (Trade t : trades) sb.append(t.id()).append(',');
4

Buffered I/O

FileInputStream.read() and its friends go to the operating system on every call. Reading a file one byte at a time means one system call per byte. Wrap streams in BufferedInputStream/BufferedOutputStream (or readers/writers) and the JVM moves data in chunks. The same applies inside the JVM: GZIPOutputStream, ObjectOutputStream and character encoders should sit on top of a buffer, and a ByteArrayOutputStream or socket stream benefits too.

Startup: class loading and CDS

Big applications load tens of thousands of classes at startup, and each one is read, parsed and verified. Class data sharing stores that work in an archive the JVM maps into memory at startup (and can share between JVMs). JDK 11 ships an archive for core JDK classes; application CDS adds your own classes. No code changes, often a sizable cut in startup time.


  

  
-Xshare:auto vs. onThe default, auto, silently runs without the archive if it can't be used (for example, the JAR changed since the dump). Use -Xshare:on in testing so you find out. Parallel class loading and making classloaders "parallel capable" also help apps that load many classes from several threads.

JNI is not a speedup

  
Calling native code to "go faster" usually backfires. The JIT already produces excellent machine code, and crossing the Java–native boundary costs time in both directions; native code can't be inlined or optimized with the caller. If you must use JNI, make few calls that each do a lot, and be careful with arrays and strings: native code that pins a Java array (Get…Critical) can block the garbage collector until it lets go.

  

    
    

  






  
8
Exceptions: cost depends on the stack

  
Throwing isn't inherently slow; creating the stack trace is, and it grows with stack depth. Use exceptions for exceptional conditions, not control flow. For hot system exceptions (a NullPointerException thrown over and over), the JIT eventually substitutes a preallocated exception with no stack trace (-XX:+OmitStackTraceInFastThrow, on by default). Your own exception classes can skip the trace by overriding fillInStackTrace(), at the cost of debuggability.

Logging

  
Log generously, but keep detailed logging off by default, and make sure disabled log statements cost nothing. Check the level first (or use a supplier lambda) when building the message needs method calls or allocation. Use a framework with buffered, asynchronous appenders, and be wary of costly formatting such as printing the caller's class and line number, which captures a stack trace per line.

  

    
// arguments evaluated even when DEBUG is off
log.debug("book: " + book.describe());

    
// nothing evaluated unless enabled
if (log.isDebugEnabled()) log.debug("book: {}", book.describe());
logger.fine(() -> "book: " + book.describe()); // JUL supplier
