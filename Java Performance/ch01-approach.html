An Approach to Performance

Tuning flags won't rescue a bad algorithm, and a benchmark that measures the wrong thing will send you chasing ghosts. These first two chapters set out how to think about Java performance and how to test it honestly.

Performance is part art, part science

The book covers two things. First, the JVM itself: how flags for the compiler and garbage collector change what your program does. Second, the platform: how you use threads, strings, collections, JDBC and the rest. The JVM side is mostly tuning flags; the platform side is mostly coding practice. Good performance engineers know both, and what looks like "art" from outside is really deep knowledge applied with experience.

The JVM is still only one part of the story. Before you touch a single flag, the book lists the outside influences that matter at least as much. Tap each card.

Death by a thousand cuts

Every small feature is "too small to matter". Each one adds code to compile, objects to collect and classes to load. Release after release the slowdowns compound, and hardware upgrades hide it. Drag the sliders to see how quickly small regressions pile up.

"Premature optimization" is not a licence to write slow codeKnuth's warning is about complicated algorithmic tricks before profiling shows they are needed. It is not about avoiding constructs known to be slow. If two simple ways of writing something exist, pick the faster one. The classic case is a debug log line that builds a string and calls methods even when the level is off:
// builds the string and calls calcX(), calcY()
// even when FINE is disabled
log.log(Level.FINE, "x=" + calcX() + " y=" + calcY());
if (log.isLoggable(Level.FINE)) {
  log.log(Level.FINE, "x={0} y={1}",
          new Object[]{calcX(), calcY()});
}

Hardware, containers and flags

The book targets the HotSpot JVM in JDK 8 and 11 (long-term support releases). Flags come in two shapes: booleans, -XX:+Flag to enable and -XX:-Flag to disable, and valued ones, -XX:Flag=value. Many defaults are chosen by ergonomics: the JVM looks at the machine and picks values. That is where hardware and containers come in.

5
The whole system sets the speed

  
Think of an application as a chain of steps. Data leaves each box only as fast as that box can process it, so the slowest box sets the rate for everything. Make the business calculation twice as fast and nothing changes if the database load can only do 100 requests per second. Set each module's capacity (requests per second when tested alone) and watch the flow.

  

    

    

    

  

  
The trap of speeding up the wrong boxIf the database is already overloaded, making the Java side more efficient sends it even more load and the whole system can get slower. The wrong conclusion is "that JVM improvement is bad". Also remember several JVMs on one machine compete: one GC can use 100% of every CPU for a moment, which looks like 40% on an average.

Principle 2: throughput, batch time and response time

  
Three ways to measure, all related. Elapsed time runs a fixed job and times it, warm-up included (users do feel the slow start). Throughput clients send the next request the instant they get an answer (no think time) and count operations per second. Response-time clients pause between requests like a real user, which fixes the load, so what you measure is how quickly the server answers.

A throughput test also reports average response time, but that only matters when throughput is equal: 500 ops/s at 0.5 s beats 400 ops/s at 0.3 s. And check that the load generator itself isn't the bottleneck; a starved client measures the client.






  
7
Principle 3: understand variability

  
Run the same test twice and you get two answers. To decide whether a code change (the specimen) really differs from the old code (the baseline), compare the runs with Student's t-test. Its p-value is the probability you'd see a gap this big if the two were really the same. The book's example: three runs each, the specimen 25% faster on average, yet p is about 0.43. Add runs and watch the confidence change while the averages stay put.

Significant is not the same as importantA steady 1% regression can be highly significant (p = 0.01). A noisy 10% regression with p = 0.2 is "inconclusive", yet it deserves your time first. Inconclusive means get more data, not "no change". Choosing the α cut-off (0.1, 0.05, 0.01) is a judgment call: that is the art.

Microbenchmarks done right with jmh

  
The Java Microbenchmark Harness handles the mechanics you'd otherwise get wrong: warm-up, forked JVMs, consuming results and confidence intervals. You still have to think about what you are measuring. Here is the shape of a benchmark (an original sketch):

  
@State(Scope.Benchmark)
public class InternBench {
  @Param({"1", "10000"}) int n;
  String[] words;
  @Setup(Level.Trial)            // build inputs outside the timed region
  public void init() { words = makeWords(n); }
  @Benchmark
  public void intern(Blackhole bh) {
    for (String w : words) bh.consume(w.intern()); // results are used
  }
}

  

    
How one jmh run is spent
defaults: -f 5 -wi 5 -i 5 -r 10s

    

    
    

  

  
The book's own lesson from this benchmark: a hand-rolled map looked faster than intern(), but the map was never cleared, so it had a 100% hit rate while the intern table (weakly referenced) kept dropping and re-adding entries. Pre-creating the strings in a static array in a @Setup method fixes both the input range and the hit rate. Use Level.Invocation setup rarely: per-call setup confuses the averaging.

Recap on one page

  

    
Algorithms firstNo flag fixes a linear search that should be a hash lookup. Smaller code runs faster.

    
Find the real bottleneckThe slowest box sets throughput; it is often the database.

    
Test the real thingMicrobenchmarks mislead; mesobenchmarks help; the full app is the truth.

    
Pick the right metricBatch time, throughput or response time. Report a percentile and the average.

    
Respect varianceUse a t-test; inconclusive means gather more data.

    
Automate and measure everythingCPU, GC logs, JFR, stacks, database stats, on the target hardware.
