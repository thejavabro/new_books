Database Performance Best Practices

The database is usually the bottleneck, and the Java code that talks to it decides how much it hurts. Pool connections, batch statements, fetch wisely and keep transactions short.

1

JDBC drivers: where does the work happen?

Everything starts with the driver. A thin driver does little in Java and leaves the work to the database; a thick driver does more on the application side (caching, processing). Which is better depends on where you have spare CPU. Driver types are a separate axis: type 1 bridges to ODBC (avoid), type 2 calls native libraries, type 3 uses a middleware server, type 4 is pure Java and talks the wire protocol. Neither type 2 nor 4 always wins: test the drivers in your deployment.

2

Connection pools

Opening a database connection takes a network round trip, authentication and session setup, so connections are pooled, in the driver, the app server, or the JPA layer. A pool's size is a throttle on the database, not just your app: one connection per thread that needs one, and no more than the database can handle. Like any pool, connections are long-lived objects that sit in the old generation with their buffers.

The database can process about 30 queries in parallel before it saturates (illustrative).

3

Prepared statements and statement pooling

A PreparedStatement is parsed and planned once and executed many times with new bind values, and it closes the door on SQL injection. But the reuse only pays if the statement object survives: it belongs to a connection, so pooling has to be per connection. Most drivers and frameworks do it for you once you set a statement cache size. The cost: each cached statement holds memory, so cache roughly the number of distinct SQL statements the app actually runs, per connection.

Transactions: commit cost vs. lock time

  
Transactions cost in two opposite ways. Each commit is expensive (it forces a durable write), so many tiny transactions are slow. But every lock a transaction takes is held until commit, so huge transactions block other users. JDBC defaults to autocommit: every statement is its own transaction. Find the balance:

con.setAutoCommit(false);
try (PreparedStatement ps = con.prepareStatement("INSERT INTO price VALUES (?,?,?)")) {
  for (Price p : prices) {
    ps.setString(1, p.sym()); ps.setDate(2, p.day()); ps.setBigDecimal(3, p.close());
    ps.addBatch();                       // sent in one round trip
    if (++n % 500 == 0) { ps.executeBatch(); con.commit(); }
  }
  ps.executeBatch(); con.commit();
}

Result sets and fetch size

  
A query's rows come back in chunks of the fetch size. Each chunk is a round trip; each row held is heap. Defaults differ per driver (some fetch 10 rows at a time, others try to fetch everything). If next() is occasionally slow, that's a round trip: raise the fetch size with setFetchSize(). If a big query blows up the heap, lower it.

JPA: same rules, more layers

  
JPA sits on JDBC, so everything above still applies: pooled connections, cached statements, batched writes, short transactions. Some JPA providers also need bytecode enhancement (weaving) to track changes and load fields lazily; make sure it is on. Then JPA adds its own knobs:

The JPA L2 cache

  
Each EntityManager has its own (L1) cache for a transaction. The L2 cache is shared across the application and keeps entities between transactions. The trap: it holds entities loaded by find() or by navigating relationships, but not results of queries. A clever JOIN query can be faster on the first call and slower forever after, because it always goes to the database.

Size the L2 cache like any cache: big enough for the hot set, with an eviction policy, or with soft references so it yields to memory pressure. Some providers offer a query cache too, which caches IDs; entities still come from the L2 cache. Spring Data and other frameworks layered on JPA inherit all of this.
