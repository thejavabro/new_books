Native Memory Best Practices

The heap is only part of a Java process. Thread stacks, the code cache, metaspace, direct buffers and the GC itself all live in native memory, and they count against your container limit.

1

The whole process, not just the heap

To the operating system the Java heap is just one block of native memory. The process also holds thread stacks, the code cache, metaspace, GC bookkeeping, direct byte buffers, symbol tables, and whatever native libraries allocate. Together that is the footprint. If it exceeds physical memory the machine swaps; in a container, it gets the process killed. Measure footprint as routinely as throughput.

2

Reserved vs. committed memory

With -Xms256m -Xmx4g, the JVM asks the OS to reserve 4 GB of address space up front (a promise, not memory) and commits only what the heap actually uses, growing as it resizes. Only committed memory costs RAM, so over-reserving never hurts performance by itself. On Unix, the process's resident set size (RSS) approximates the committed memory; an RSS below committed can mean the OS is struggling to keep the JVM in RAM. A 32-bit or tightly limited process is the exception, where reservations themselves can run out.

3

Native Memory Tracking

Start the JVM with -XX:NativeMemoryTracking=summary (or detail) and ask it what it is using. Overhead is small for summary mode. NMT sees everything the JVM itself allocates, but not native libraries.

java -XX:NativeMemoryTracking=summary ...
jcmd <pid> VM.native_memory summary
jcmd <pid> VM.native_memory baseline          # mark now
jcmd <pid> VM.native_memory summary.diff      # what changed since

OS tunings: large pages

The CPU caches virtual-to-physical address translations in the TLB (translation lookaside buffer; nothing to do with the TLABs of chapter 6). With 4 KB pages, a multi-gigabyte heap needs millions of entries and the TLB misses constantly. Large pages (2 MB, or 1 GB on some systems) cover the same heap with far fewer entries. They usually give a measurable speedup.
