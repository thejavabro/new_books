Working with the JIT Compiler

Java starts out interpreted and gets faster as it runs. The just-in-time compiler watches which code is hot and turns it into optimized machine code, in tiers.

1

From bytecode to machine code

A CPU runs only its own instructions. C++ compiles to those ahead of time, one binary per platform; scripting languages interpret source as they go. Java does both: javac produces portable bytecode, the JVM starts by interpreting it, and the just-in-time (JIT) compiler turns the hot parts into native code while the program runs. The original HotSpot name says it: compile the hot spots, not everything.

Why not compile everything at once? Compiling costs time, and code that runs once is cheaper to interpret. Code that runs a lot is worth compiling, and the longer it runs, the more the compiler learns (which types really show up, which branches are taken) and the better it can optimize, for example keeping a value in a register instead of reloading it from memory.

Tiered compilation: two compilers, five levels

HotSpot has two JIT compilers. C1 (once called the client compiler) compiles early and quickly. C2 (the server compiler) waits longer, gathers a profile, and produces faster code. Tiered compilation, the default since Java 8, uses both: C1 first for a quick win, C2 later for the hot code. Step through a method's life.

3

The code cache can fill up

Compiled code lives in the code cache, which has a fixed maximum (240 MB by default with tiered compilation; initial size about 2.5 MB). When it fills, the JVM prints a warning that the code cache is full and the compiler has been disabled; everything not yet compiled stays interpreted. Java 11 splits it into three segments (non-method, profiled and non-profiled code) but the total is still set with -XX:ReservedCodeCacheSize=N. Space is only reserved virtual memory until used, so a generous size costs little.

Deoptimization: not entrant and zombie

The compiler optimizes for what it has seen. If an assumption breaks, compiled code is thrown away. Code is made not entrant (no new calls may enter it) when a type assumption fails, or simply when tiered compilation replaces level-3 code with level-4 code. Later, when nothing is still running it, it is made zombie and its space in the code cache is reclaimed.

A call site that changes its mind

Neither kind is usually a concern: tiered compilation produces lots of "not entrant" lines by design, and a type change costs a short dip while the method is recompiled.

6

Thresholds, OSR and compiler threads

Each method has two counters: invocations and back-edges (loop iterations that jump back). When their sum crosses a threshold the method is queued for compilation. A long loop inside a method that is called once can still be compiled mid-loop: on-stack replacement (OSR) swaps the running frame onto compiled code. Counters decay over time, so rarely used methods may never reach C2.

Climb the thresholds

Don't tune the thresholdsWithout tiering, people lowered -XX:CompileThreshold (10,000 for C2) to compile sooner. With tiering this brings little; if you must, the knobs are Tier3InvocationThreshold (200) and Tier4InvocationThreshold (5,000). The queue is not FIFO: hotter methods jump ahead.

Compiler threads by CPU count

defaults with tiered compilation

Change with -XX:CICompilerCount=N. On a single CPU, one compiler thread can help early on (the book saw about 10% faster initial work) because compilation competes less with the application. In older Java 8 builds inside Docker, these were sized for the host's CPUs. -Xbatch turns off background compilation, mainly useful for testing.

7

Inlining: the biggest win

Well-encapsulated code calls tiny getters and setters all the time. A real call means saving registers and jumping; the getter's work is one load. Inlining copies the callee's body into the caller, and then other optimizations can see across the boundary. Turning inlining off slowed the book's stock test by more than half.

// what you write
int total = order.getQty() * order.getPrice();
// what the compiled code effectively does
int total = order.qty * order.price;

Will it be inlined?

the two-size rule

Raising MaxInlineSize lets bigger methods inline on their first calls, which may shorten warm-up but rarely changes a long-running app. Hot methods already get the larger 325-byte limit (MaxFreqInlineSize).

8

Escape analysis

If C2 can prove an object never leaves a method (it doesn't "escape"), it can skip the lock on its synchronized methods, keep its fields in registers, and often not allocate it at all. On by default (-XX:+DoEscapeAnalysis). It is also a big reason naive microbenchmarks measure nothing.

Tiering, AOT and GraalVM

  
Tiered compilation compiles far more code. In the book's NetBeans startup test, turning it off compiled about a quarter as many classes and used about a quarter of the code cache, but started 18 seconds slower. After warm-up, long-running servers perform about the same either way, so -XX:-TieredCompilation or -XX:TieredStopAtLevel=1 (C1 only) can make sense only when memory is very tight.
