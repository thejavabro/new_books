Threading and Synchronization

More threads help until they don't. Size thread pools for the work, understand what a lock really costs, and avoid the cache-line traps that make parallel code slow.

How many threads?

Threads are expensive to create, so servers keep them in pools; and a pool is also a throttle on how much work runs at once. The right size depends on what the tasks do. CPU-bound tasks: about one thread per CPU, since extra threads just queue for cores (remember hyper-threads only add ~30%). Tasks that wait on something: more threads keep the CPU busy, unless the thing they wait on is the bottleneck. Then extra threads pile more load onto it and everything gets slower.

ThreadPoolExecutor: core, max and the queue

A ThreadPoolExecutor has a core size, a maximum size and a task queue, and the rules for when it adds threads surprise people: it starts a thread beyond the core size only when the queue is full. Choose a queue type and feed it tasks.

core = 4, max = 8. Each task takes a while.

Keep it simpleThe book's advice: make core equal to max (the predictable choice), and bound the queue so a flood of requests is rejected instead of quietly eating the heap. Executors.newFixedThreadPool() uses an unbounded queue; build your own executor with an ArrayBlockingQueue when that matters. Idle threads above core retire after the keep-alive time.
3

ForkJoinPool and work stealing

A ForkJoinPool suits divide-and-conquer: a task splits itself into subtasks and waits for them without blocking a thread (the waiting thread runs other tasks). Each thread has its own deque, and an idle thread steals work from the back of a busy thread's deque. That shines when tasks are uneven. It is also what parallel streams and CompletableFuture use by default: the common pool, sized to CPUs − 1 (set -Djava.util.concurrent.ForkJoinPool.common.parallelism=N; it honours container CPU limits in recent JDKs).

For small, even tasks a plain loop or ThreadPoolExecutor can beat ForkJoin: splitting into many tiny subtasks costs objects and bookkeeping. Parallel streams help when the per-element work is large and CPUs are idle; on a busy server they just compete with other requests.

4

What synchronization costs

Two costs. First, scalability: by Amdahl's law, any part that must run serially caps the speedup no matter how many CPUs you add. Second, the lock itself: uncontended locks are cheap; contended ones mean spinning, then parking threads in the OS. And every synchronized block, volatile write or CAS also forces values out of registers to memory, which matters in tight loops.

False sharing

CPUs cache memory in 64-byte lines. If two threads each write their own variable but those variables sit in the same line, every write invalidates the other core's copy. The data isn't shared; the cache line is. It is worst with volatile fields or values written inside synchronized blocks, since those writes must reach memory. Standard profilers don't show it; you find it by reading code (or with CPU-vendor tools).
