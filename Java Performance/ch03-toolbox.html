1

CPU: the goal is to drive it up

Analysis starts with the operating system's own tools (vmstat, iostat, typeperf on Windows), captured from the command line so tests can be automated and graphed later. CPU time splits into user time (your code) and system time (the kernel doing I/O and other work for you).

The surprising rule: for a fixed job you want CPU usage as high as possible for as short a time as possible. A batch job at 50% CPU is idle half the time; remove the stalls and it finishes in half the time at 100%. A server, though, works in bursts: a 1-second request rate with 450 ms of work per request reports 45%. Try it.

2

The run queue

The run queue counts threads that could run if a CPU were free. If it stays above the CPU count, the machine is overloaded: move work elsewhere or make the code cheaper. Careful: Unix counts running threads too; Windows' processor queue does not.

3

Disk and network: too little or too much

I/O can be a bottleneck two opposite ways: writing inefficiently (lots of tiny unbuffered writes; low throughput but lots of kernel time) or writing too much (the device is saturated). Pick a reading and decide what it says.

Looking inside the JVM: the JDK tools

The JDK ships a set of tools that overlap in what they show. Tap a tool to see which kinds of visibility it gives. Install the full JDK in your Docker images: sooner or later you'll need these in production, and the command-line ones run fine through docker exec.

Which flags are really in effect?

# defaults this JVM would choose on this machine (add your other flags too)
java -XX:+PrintFlagsFinal -version | grep -E 'MaxHeapSize|UseG1GC'
# flags of a running process; -all lists every one
jcmd <pid> VM.flags
jcmd <pid> VM.command_line
# read one flag; change it only if it is "manageable"
jinfo -flag PrintGCDetails <pid>

5

Sampling profilers and safepoint bias

Profilers are the most important tool you have. A sampling profiler wakes up on a timer, looks at what each thread is running, and charges the whole interval to that method. Cheap, but it can be fooled. Older Java profilers can only grab a stack when a thread reaches a safepoint (blocked on a lock or I/O, parked, in JNI, or at a check the JIT inserts at loop and method boundaries). Async profilers (built on AsyncGetCallTrace) can sample anywhere.

6

Reading a profile: flame graphs and call trees

A flame graph stacks callers below callees; width is CPU time. A call tree shows the same thing top-down. The lesson: the hottest leaf is often JDK code you can't change. It points to the area to fix. If serialization dominates, make serialization cheaper or rarer; don't try to speed up writeObject0(). Tap a frame to zoom (illustrative data for a REST call that returns a serialized object).

8

Java Flight Recorder

JFR is built into the JVM. It records events (a thread blocked on a monitor, a slow socket read, a GC phase, a compilation) into a circular buffer, which you inspect in Java Mission Control (jmc). Because the data comes from the JVM itself, it sees things no outside tool can. In JDK 11 it is open source; in Oracle's JDK 8 it needs -XX:+UnlockCommercialFeatures.

Pick a template

# reactive: keep a rolling buffer, dump it when something goes wrong
java -XX:StartFlightRecording=maxage=30m,maxsize=250M ...   # JDK 11
jcmd <pid> JFR.start name=load duration=60s filename=load.jfr  # proactive, fixed length
jcmd <pid> JFR.check
jcmd <pid> JFR.dump name=1 filename=now.jfr
jcmd <pid> JFR.stop name=load
