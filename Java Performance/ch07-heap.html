Heap Memory Best Practices

The cheapest garbage is the garbage you never make. Learn to read a heap histogram, diagnose an out-of-memory error, shrink objects, and decide when reuse or weak references pay off.

Find out what is using the heap

Before you optimize memory, find out which objects take it. Start cheap with a histogram: a count and total size per class, from jcmd <pid> GC.class_histogram or jmap -histo (add :live to force a full GC first and count only live objects). If one of your classes has suspiciously many instances, you have a lead. For the full story take a heap dump (jcmd <pid> GC.heap_dump file) and open it in a tool such as Eclipse MAT or jvisualvm.

Shallow, retained and deep sizes

tap an object

Objects with large retained sizes are the heap's dominators. Often the top ones are classloaders, which tell you little. A leak can also hide when the leaking data is referenced from two places, because shared objects are counted in no one's retained size. Then you walk references from a suspicious object back toward the GC roots.

Using less memory: object size

Smaller objects mean less GC work: fewer collections, less to copy. Objects are bigger than their fields suggest. On a 64-bit JVM with compressed references, each object has a 12-byte header, each reference takes 4 bytes, and the total is padded up to a multiple of 8. Arrays have a 16-byte header. Lazy initialization

If most instances never use a field, don't create its value until someone asks. That only pays when the common path leaves it untouched; otherwise you add a check to every access for nothing. With threads involved, use the double-checked pattern with a volatile field and a local variable, so the common path reads the volatile only once:

private volatile Map<String,Rate> rates;   // usually never needed
Map<String,Rate> rates() {
  Map<String,Rate> r = rates;              // one volatile read
  if (r == null) {
    synchronized (this) {
      r = rates;
      if (r == null) rates = r = loadRates();
    }
  }
  return r;
}

Does lazy pay?

The reverse trick, eager deinitialization (setting a field to null so GC can take it), is almost never needed: objects go away when their owner does. It makes sense mainly inside long-lived collections, as ArrayList.remove() does with the freed slot.

Immutable and canonical objects

Immutable objects can be shared freely, so you need only one copy of each distinct value: a canonical version, like Boolean.TRUE. Interning strings is the JDK's built-in version (chapter 12). For your own immutable types, keep a map from value to its canonical instance; with weak keys so unused values can still be collected.

Object reuse: pools and thread-locals

Reusing objects fights the generational collector: a pooled object lives long, gets promoted, and makes old-generation collections slower. Only reuse objects that are expensive to create and few in number: threads, JDBC connections, big buffers, XML parsers, SecureRandom. Two ways to keep them:

Object poolShared among threads, so access is synchronized and can be contended. Size is controlled: good when the pooled thing is externally limited (database connections). Must handle "pool empty".
ThreadLocalOne object per thread, no locking. Simple when objects map one-to-one to threads (a per-thread formatter). The count is tied to the thread count; with thread pools that is usually fine.

Compressed oops and the 32 GB cliff

A 64-bit JVM could use 8-byte references, but with heaps under 32 GB it stores them as 32-bit offsets scaled by 8 (objects are 8-byte aligned anyway). That's compressed oops, on by default below 32 GB. Cross the line and every reference doubles. Since references can be ~20% of a heap, a 33 GB heap may hold less than a 31 GB one.
