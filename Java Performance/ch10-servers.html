Java Servers

A Java server spends its life waiting on sockets. Nonblocking I/O, asynchronous request handling and a sensible approach to JSON keep threads busy doing real work.

1

One thread per connection, or a selector?

Classic Java servers gave each client connection its own thread, which sat blocked in read() waiting for the next request. Thousands of mostly idle keep-alive connections meant thousands of threads. Nonblocking I/O (NIO) flips this: a few selector threads watch all sockets and hand a connection to a worker thread only when it actually has a request to process. Worker pools are then sized for simultaneous requests, not connections.

Server frameworks (Netty, Grizzly, Tomcat's NIO connector, and the Java EE / Jakarta servers built on them) set this up for you. Your tunings are the worker pool size (enough for the requests the box can handle at once) and, sometimes, the number of selector threads (one or two per CPU is typical, but the defaults are usually fine).

2

Asynchronous responses

Suppose a request takes 100 ms of CPU work and 900 ms waiting on a backend. A worker thread holding the request throughout is idle 90% of the time. JAX-RS and servlets let the worker suspend the request, hand it to another pool, and go back to accept more. The response is written later from that other thread. It doesn't make one request faster; it frees workers and lets you throttle the slow part separately, rejecting work early when the async pool is full.

@GET @Path("/quote")
public void quote(@QueryParam("sym") String sym, @Suspended AsyncResponse ar) {
  if (!slowPool.hasCapacity()) { ar.resume(Response.status(503).build()); return; }
  slowPool.submit(() -> ar.resume(lookUp(sym)));   // worker thread returns at once
}

Outbound calls: concurrency and client pools

Many REST handlers call other services. If one request needs three independent calls, making them concurrently with an async HTTP client cuts the wait to the slowest call instead of the sum. Two practical rules: reuse client objects (they hold connection pools), and size the client's connection pool; many default to only a couple of connections per host, which silently serializes your calls.

Async databases and reactive codeJDBC is blocking, so a "truly asynchronous" relational call needs a different driver model; usually you just run blocking JDBC in its own sized pool. Reactive frameworks push the async style through the whole stack; the performance gains come from the same place: fewer idle threads and more concurrency.

Processing JSON

JSON is everywhere and easy to make slow. There are three ways to handle a document, and what matters most is how many objects you create and how much of the document you actually need.
