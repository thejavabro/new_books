An Introduction to Garbage Collection

The JVM frees memory for you, but someone pays for it. This chapter explains how a generational heap works, which collector to pick, and the handful of settings that matter for all of them.

What a garbage collector does

Java has no free(). The collector finds objects nothing can reach any more and reclaims their memory. It starts from GC roots (local variables on thread stacks, static fields, JNI references), follows every reference, and marks what it reaches. Everything unmarked is garbage, even a cycle of objects that point to each other. Step through one collection.

Freeing alone leaves holes. If a 1,000-byte array and a 24-byte array alternate and the small ones die, the heap is half empty yet cannot fit a 25-byte object. So collectors also compact: slide live objects together, which means moving them and fixing every reference. Moving objects that application threads are using is why most collectors must, at least briefly, stop the world.

Generational collection

Most objects die young: a temporary string, an iterator, a BigDecimal from one step of a calculation. So the heap is split. New objects go into eden. When eden fills, a quick minor GC copies the few survivors into a survivor space and wipes eden in one go; copying also compacts for free. Objects that survive several minor GCs are promoted (tenured) to the old generation, which is collected less often. Play the allocator.

Two kinds of pauseYoung collections always stop the world but are short: their cost depends on how many objects survive, not how many were allocated. The old generation is the hard part. A collector either stops everything and compacts it (simple, long pauses) or does most of the work concurrently while the application runs (short pauses, more CPU, more complexity).

Choosing a collector

Start from "G1 unless there's a reason not to". The reasons are about spare CPU: G1's background threads need cycles. With one CPU, or a batch job that keeps every CPU busy, its concurrent work competes with your code. Answer three questions.

Sizing the heap

Too small and the program spends its time collecting. Too big and each pause is longer, and worse, the heap may not fit in physical memory. The OS will swap part of it to disk, and a full GC touches every page, so pauses become an order of magnitude longer. Move the slider.

The JVM grows the heap from -Xms toward -Xmx when it thinks it is collecting too often. For many apps you don't need to set a size at all: set the collector's goals (next chapter) instead. If you know what the app needs, setting -Xms equal to -Xmx saves the sizing work. Rule of thumb: about 30% occupied after a full GC. Remember containers: before 8u192 the defaults came from the host's memory.

6

Sizing the generations

A bigger young generation means fewer minor GCs and fewer objects promoted too early, but a smaller old generation that fills sooner. By default NewRatio=2: young = heap / (1 + NewRatio), a third of the heap. NewSize/MaxNewSize or -Xmn set it directly. Adaptive sizing then moves the boundaries within those limits based on recent GCs; leave it on unless you've tuned everything by hand (-XX:-UseAdaptiveSizePolicy, throughput collector).

MetaspaceClass metadata (not the Class objects themselves, which live in the heap) goes in metaspace, which replaced Java 7's permgen. It lives in native memory and is unlimited by default. Filling it triggers a full GC that unloads unused classes, common with app servers that redeploy often. Setting -XX:MetaspaceSize to what the app uses after startup avoids a few early full GCs; capping MaxMetaspaceSize trades growth for an OutOfMemoryError.
7

How many GC threads?

Stop-the-world phases use ParallelGCThreads threads: one per CPU up to 8, then 5 more for every 8 extra CPUs. Each runs a CPU flat out, which is why GC can spike CPU to 100%. Fine for one JVM per machine; with several JVMs, their GC threads collide. Concurrent collectors also run ConcGCThreads background threads, by default about a quarter of the parallel count.
