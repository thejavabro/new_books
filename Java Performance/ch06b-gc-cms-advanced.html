CMS, Advanced Tunings and New Collectors

The concurrent mark-sweep collector, the knobs shared by all collectors (tenuring, TLABs, humongous objects), and the experimental low-pause collectors that point to the future.

1

CMS: concurrent, but never compacting

The Concurrent Mark-Sweep collector was the first to clean the old generation while the application ran. Young collections still stop the world (logged as ParNew). For the old generation it runs a background cycle with two short pauses. The catch: it sweeps dead objects into free lists but never moves the live ones. Over time the old generation fragments, and when nothing fits, CMS falls back to a long single-threaded full GC. That, plus G1 doing the same job better, is why it is deprecated in JDK 11.

When does CMS start?

-XX:CMSInitiatingOccupancyFraction=N -XX:+UseCMSInitiatingOccupancyOnly

Other CMS facts: its background thread count is (3 + ParallelGCThreads) / 4; on a single CPU the background thread competes with the app (the old "incremental CMS" mode for that case is gone). By default it does not clean metaspace: -XX:+CMSClassUnloadingEnabled (default true in JDK 8) and -XX:+CMSPermGenSweepingEnabled control that.

2

Survivor spaces and the tenuring threshold

Survivor spaces give young objects a few more chances to die before they are promoted. Each object carries an age (minor GCs survived). It is promoted when its age reaches the tenuring threshold, or immediately if the survivor space overflows. The JVM adapts the threshold between 1 and MaxTenuringThreshold (15 for throughput and G1, 6 for CMS), starting at InitialTenuringThreshold (7), aiming to keep survivor spaces about half full (TargetSurvivorRatio=50). Each survivor space starts at young / (InitialSurvivorRatio + 2): 10% of the young generation by default.

Watch it in logs with -Xlog:gc+age=debug (JDK 11) or -XX:+PrintTenuringDistribution (JDK 8). -XX:+AlwaysTenure (threshold 0) and -XX:+NeverTenure exist for special cases; rarely useful.

3

Thread-local allocation buffers

Allocating in eden is fast because each thread owns a slice of it, a TLAB, and bumps a pointer inside it with no locking. When an object doesn't fit in what's left of the TLAB, the JVM must choose: retire the TLAB (wasting the leftover) and grab a new one, or allocate this one object directly in shared eden (slower, synchronized). You rarely tune TLABs. JFR's TLAB events show allocations outside TLABs; if many large objects land there, prefer smaller objects. Otherwise -XX:TLABSize=N sets an initial size, -XX:-ResizeTLAB stops resizing, -XX:MinTLABSize (2 KB) sets the floor.

4

Humongous objects and G1 region size

In G1, an object of half a region or more is humongous: it is placed straight into the old generation in its own set of contiguous regions, skipping the young-generation life cycle. Lots of short-lived humongous arrays mean wasted space, early marking cycles, and possibly a full GC when no contiguous run is free. The fix is bigger regions. The region size is fixed at startup from the initial heap: the smallest power of two from 1 MB to 32 MB that gives about 2,048 regions.

5

AggressiveHeap and the default heap calculation

-XX:+AggressiveHeap is a legacy shortcut for "one JVM owns a big machine": it picks the throughput collector, a heap of up to half of physical memory with Xms=Xmx, a young generation of 3/8 of that, large pages, and fixed 256 KB TLABs. Those values were never updated as the JVM improved, so treat it with suspicion and test before relying on it.

Default heap sizes come from physical memory (or the container limit), adjusted by flags such as -XX:MaxRAM, -XX:MaxRAMFraction/-XX:MaxRAMPercentage and -XX:InitialRAMFraction. The arithmetic is simple on normal machines and gets intricate at the edges (tiny memory, compressed-oops limits); when in doubt, check PrintFlagsFinal.

6

Experimental collectors

Even G1 and CMS stop the world to move objects, because updating references is easy only when nothing else is running. ZGC and Shenandoah compact concurrently: application threads pass through a barrier when they load a reference, and if that object is mid-move they wait briefly (or help). Without long compaction pauses, the heap no longer needs generations. Pauses stay around 10 ms or less whatever the heap size, at some cost in throughput and CPU. Enable them with -XX:+UnlockExperimentalVMOptions -XX:+UseZGC or -XX:+UseShenandoahGC (Shenandoah is in AdoptOpenJDK builds, not Oracle's).

Data reported in the book for an allocation-heavy request. Throughput GC's full GCs dominate the tail; G1 removes those but keeps young pauses; the concurrent compactors flatten it.

Epsilon: the collector that never collects

For a short program that allocates 4,096 half-megabyte arrays and exits, skipping GC entirely was about 30% faster. When the heap fills, Epsilon simply fails with OutOfMemoryError, so it suits very short-lived jobs, programs that never allocate after startup, and testing.
