Automate, Version, Standardize

When infrastructure becomes software, it should be treated like software: automated, versioned and tested. And good standards, like A4 paper, constrain only the edges so creativity can thrive inside.

1

Never send a human to do a machine's job

Agent Smith in The Matrix had a point: never send a human to do a machine's job. There's irony in corporate IT, which built its reputation automating business processes, being so manual itself. A good strategy fits on a sticker: automate everything, and make whatever you can't automate self-service.

A common objection: automating a rare task doesn't pay. That treats automation purely as efficiency, the way you might wrongly think test-driven development is only about testing. Automation is mostly about repeatability, confidence and resilience. Compare the two views.

Repeatability grows confidenceOnce a task is scripted, you can run it again any time without hesitation, so you run it more often and catch problems earlier. Disaster recovery is the extreme case: you hope it's rare, but when it happens, the cost of a slow manual restore is the lost business, not the labor.
2

Self-service, and beyond

Once a procedure is automated, users can trigger it themselves. That doesn't mean a free-for-all: a self-service restaurant still has a cashier. Approvals remain, but nobody retypes a spreadsheet. A good self-service interface also forces infrastructure teams to give users a clear mental model of what they're ordering. Climb the ladder.

3

Software developers don't undo, they re-create

When infrastructure becomes software-defined, from virtual machines to containers to serverless, provisioning turns into a software problem. That calls for a software developer's mindset. Asked for a way to revert infrastructure to a known good state, one vendor answered that it would need an explicit undo script for every action. A developer would instead rebuild the previous version from source. Try both on a small fleet.

Melt the snowflakes"This server has been up for three years" is not bragging rights but a risk: who could rebuild this pet if it died? Software-defined infrastructure means servers are re-created from code in minutes, so nobody fears touching them.
4

Treat configuration like production code

A large internet company once routed all incoming traffic with a version-controlled file of hundreds of regular expressions. Despite code reviews, someone eventually checked in a bad entry and most services went down until the previous version was restored. The response was not to forbid changes, which would slow everyone, but to add automated checks before deploy. Edit a routing rule and run the pipeline.

New rule for

Think like a developer all the way: make infrastructure part of a fast but disciplined software life cycle, or you'll end up with software-defined chaos. And if software eats the world, there will be two kinds of people: those who tell machines what to do, and those for whom it's the other way round.

5

A4 paper doesn't stifle creativity

IT has to cut cost through harmonization while also innovating faster. Do standards kill creativity? Look at paper. The A series isn't arbitrary: every sheet has sides in the ratio 1 : √2, so cutting one in half gives two sheets of exactly the next size down. A0 is one square meter, so 16 sheets of A4 make up A0. Change the ratio and halve the sheet.

The standard fixes the edges and leaves the surface blank. You can draw on A4 with pencil, ink, chalk or watercolor. Envelopes, folders, drawers and copiers all fit, so nobody has to think about them. That's the model for an IT platform.

6

Product standards restrict, interface standards enable

Most IT harmonization standardizes products: one database, one application server. That buys purchasing power but locks choices. Interface standards like HTTP let anyone build a faster web server without replacing every browser. Platform standards combine both: standardize the lower layers that don't differentiate, and leave the upper layer free. Car makers do this with shared chassis and engines under very different-looking models.

7

Don't build the skipping stones

In a notorious Japanese game show, contestants cross a murky pond on stepping stones; some look solid and give way. Some IT platforms play the same trick: components get deprecated, interfaces are inconsistent, parts are poorly integrated. Cross the pond: pick one stone per row. Use the hints.

Start at the bottom row.
How to build a solid platformPick a useful level of abstraction, like paper rather than pens. Keep fine-tuning as technology moves. Keep versions current: one platform succeeded precisely because it updated regularly instead of waiting for every application owner to agree. And make it real: standards that exist only on paper get ignored, ready-to-use tools get adopted.
