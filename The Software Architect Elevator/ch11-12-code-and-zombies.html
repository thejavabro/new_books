Code and Zombies

Moving logic out of code into configuration rarely makes it simpler, only harder to test. And organizations that never switch anything off end up spending their budgets keeping the undead alive.

1

Code fear not: the dark side of configuration

Fear leads to anger, anger to hate, hate to suffering. Corporate IT's fear of code, and its love of configuration, leads down a similar path. Code is seen as where the bugs live, written by expensive outsiders who've left by the time problems appear. Some IT departments even refuse operations support for shared app servers once you deploy code on them, like voiding a car's warranty the moment you start the engine.

The fear grows out of a sound rule: buy before you build. Buying lets someone else handle updates and patches, and configuring a package sounds safer than coding. There are two catches. You depend on the vendor having anticipated your need, which means perfect up-front design. And "configuring" complex behavior often turns out to be programming in a poorly designed language with no tool support.

2

Simple things simple, complex things possible

Raising abstraction is how software gets easier: almost nobody writes assembler or puts raw packets on the wire any more. But an abstraction that removes too much becomes a cage, and one that removes too little isn't worth having. Good ones, like MapReduce for distributed data processing, hide the hard plumbing yet leave room for your own logic. Slide the level of abstraction and watch what your users can still do.

3

When are we configuring, anyway?

"Configuration" usually mixes up three separate questions. None of them, alone, decides whether something is really code.

RepresentationPictures or text? A drag-and-drop GUI changes how a model looks, not how complex it is. A complex workflow drawn as boxes is still a complex workflow.
Data or instructions?XML, JSON or YAML syntax doesn't make something data. Anyone who has written XSLT knows XML can be a full programming language.
Before or after deploy?Configuration can change at runtime, which mattered when code deployments were slow. With a fast toolchain, that advantage shrinks.

Higher-level programming hiding in config files

Distributed systems often connect components through named message channels. Two components talk when they name the same channel, and those names usually sit in local configuration files. That looks harmless, but together the files are the program that defines the system's structure, with no compiler to check it. Rename one channel and see what happens.

Treat it like codeConfiguration is useful, for runtime parameters in distributed programs or for setting up cloud infrastructure. Interestingly, the latter often runs under the label "infrastructure as code," as if "code" sounds more serious. Whatever you call it, give it version control, testing and tooling. And when a vendor touts its configuration suite, ask it to speed up its software delivery instead.
5

If you never kill anything, you live among zombies

Legacy systems run on outdated technology, are poorly documented, and nobody knows exactly what they do, yet they often make lots of money, which is why they're still alive. They also eat IT's brains: manual operations, constant care, expensive hardware, trial-and-error troubleshooting. Each year you add systems. Do you retire any?

Run versus changeMany IT departments split "run" from "change," encoding the idea that running software means not changing it. That structure guarantees systems age into legacy. The Managed Evolution approach argues the opposite: the goal is to keep systems agile. A system nobody dares touch has zero agility.
6

Hope for the best, or prepare for the worst

Organizations without good monitoring or fast deployment try to test every scenario up front, then run "blind" and hope. That optimizes MTBF, mean time between failures. Modern teams also minimize MTTR, mean time to recovery, using transparency, version control and automation. Compare a year of incidents.

7

Version upgrades and the cascade

Zombies aren't only mainframes. Upgrades of JDKs, app servers, browsers or operating systems get deferred until vendor support ends, then the firm pays for extended support. Meanwhile the dependencies lock together. Step through a typical cascade.

8

If it hurts, do it more often

Deferring a painful task makes it disproportionately more painful. Builds you haven't run in months won't go smoothly; an app server three versions behind means the migration from hell. Doing it often forces you to automate, and turns problems into routine, which is why emergency crews drill regularly.
