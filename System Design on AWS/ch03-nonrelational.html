Nonrelational Stores

When a fixed schema or a single machine becomes the bottleneck, NoSQL stores trade some guarantees for flexibility and scale. Four families, each shaped by its data model.

Same data, four shapes

Nonrelational ("NoSQL") stores drop the fixed table schema. Each family is built around one data model, chosen to make a particular access pattern cheap, and most are designed from day one to spread across many machines. Here is the same tiny social app stored four ways.


  






  
2
BASE instead of ACID

  
Distributed NoSQL stores usually pick availability over strict consistency (the A side of CAP). The resulting promise is BASE: Basically Available (always answer, perhaps with partial or stale data), Soft state (the state may change even without new input, as replicas sync), Eventually consistent (given time without writes, all copies agree). Many modern stores also offer ACID transactions or strong reads as an option, at a cost.

  

    
Relational (ACID)
  • Fixed schema, enforced on write
  • Joins and ad hoc queries are natural
  • Strong consistency by default
  • Usually scales up; scaling out takes work
  • Best for: transactions, reporting, integrity

    
Nonrelational (BASE)
  • Flexible schema, items can differ
  • Model data around known queries; joins are costly
  • Eventual consistency by default, often tunable
  • Scales out horizontally by design
  • Best for: huge volume, low latency, evolving shape

Key-value stores: partition and sort keys

  
A key-value store is a giant distributed hash map. The partition key decides which node holds an item. An optional sort key orders items that share a partition key, so you can fetch a slice. Together they form the primary key. Operations are simple: GetItem, PutItem, UpdateItem, DeleteItem, plus Query within one partition. Try it.

  

    

    

    

    

  






  
4
Consistent hashing

  
With hash(key) mod N, adding one server changes N and moves almost every key. Consistent hashing places servers and keys on a ring; each key belongs to the next server clockwise. Adding or removing a server only moves the keys in one arc. Virtual nodes (many points per server) smooth out the load.

  

    

    

    

  






  
5
Leaderless replication and quorums

  
Dynamo-style stores have no leader: any replica accepts writes and clients (or a coordinator) talk to several at once. Each item lives on N replicas. A write succeeds when W replicas confirm; a read asks R and takes the newest. If W + R > N, every read set overlaps every write set, so a read always sees the latest acknowledged write. Lower values buy speed and availability.

  

    

      
      
      
    

    

    

  

  






  
6
Document stores

  
A document store keeps self-contained JSON-like documents grouped into collections. Nested fields and arrays mean one read fetches a whole entity, and secondary indexes let you query any field. A typical cluster has a primary that takes writes and secondaries that replicate it and take over by election. MongoDB is the best-known example; Amazon DocumentDB is compatible with its API.

  

    

    

  

  
The flip side of no schemaNothing stops two documents from spelling a field differently. Validation moves into the application, and data duplicated across documents must be kept in step by you.






  
7
Wide-column stores and the write path

  
Wide-column stores such as Apache Cassandra group columns into families and rows into partitions (by partition key), sorted inside by a clustering key. They are built for very fast writes: nothing is updated in place. Step through a write and a read.

  

  






  
8
Graph databases

  
When the relationships are the data (friends, fraud rings, recommendations), store them directly. Nodes and edges both carry properties, and queries traverse edges instead of joining tables, so cost depends on the neighbourhood you touch, not the size of the database. Click a person to see "friends of friends you don't yet follow".
