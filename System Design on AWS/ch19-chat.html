Designing a Chat Application

Billions of messages a day delivered in order, in real time, to phones that keep dropping off the network.

1

A WhatsApp-sized brief

One-to-one, group and broadcast messages; text, images, video and documents; sent, delivered and read receipts; online and last-seen status; push notifications for offline users; and messages kept on the server only until delivered. Nonfunctional: near-real-time delivery, high availability, messages never lost and delivered in order per chat, end-to-end encryption. The book scales it like WhatsApp.

Of 100 billion messages a day, about 90 billion are text, 8 billion images and 2 billion videos. Direct chats read about once per write; groups skew to roughly 90 reads per 10 writes.

2

Keep the line open

Messages must flow both ways instantly, so the client keeps a persistent bidirectional connection (WebSocket, or MQTT or XMPP over it) instead of polling. Payload size matters too: compact binary formats (protobuf, or WhatsApp's tokenized XMPP) beat verbose JSON on mobile networks. Compare a user idle for a minute who then receives one message.

3

Delivering one message

Each online device holds a connection to some chat server. A session store (DynamoDB or Redis) maps user → server ID plus online and last-seen status. To send, A's server looks up B's server and forwards; B's device acknowledges, and the acknowledgment flows back to A as a tick. If B is offline, the message waits in an offline store and a push notification goes out.

4

Millions of open connections

Every connection is a long-lived piece of state. OS threads are too heavy for that, so chat servers use lightweight concurrency, the actor model: Erlang processes, goroutines, Kotlin coroutines, Java virtual threads. Heartbeats detect dead links without flapping presence on a jittery network. When a server dies, its clients reconnect to another one, which updates the session store.

5

Groups, storage and media

Media goes through a separate media service: upload once, get a reference URL, send the URL in the message, and serve downloads through a CDN. Viral forwards on big days would store the same file millions of times, so the service hashes content and keeps one copy. Try forwarding.

6

Just enough engineering

WhatsApp served billions of users with a small team on Erlang (BEAM VM, an ejabberd/XMPP heritage): millions of cheap processes per box, supervision trees that restart failed processes, hot code loading. Its databases (Mnesia and in-memory ETS) run beside the app, grouped into islands: small sets of nodes that replicate each other, so a failure stays local. Offline messages live in append-only files that are deleted once delivered.

7

Day 0: let AppSync hold the sockets

AWS AppSync manages serverless WebSocket subscriptions, so there is no connection fleet to run. Cognito handles accounts (phone OTP sign-up needs a custom auth flow), DynamoDB stores users, chats, messages and media metadata in separate tables, S3 holds media, Lambda handles groups, contacts and notifications, and ElastiCache can hold presence. 8

When the system is overloaded

Better to serve some requests than none. Graceful degradation sheds load (rate limits with AWS WAF, a friendly error page), and clients are told whether retrying is worthwhile. Backoff alone does not stop a retry storm; a retry budget does: allow, say, one retry per ten successful requests. Push the failure rate up and compare.

9

Day N architecture

At WhatsApp scale, own the connection tier: chat servers on EC2 or EKS behind NLBs, a session manager in ElastiCache, and the services below. Across regions, store each user's data in a home region (plus one for redundancy) and route messages between regions over the AWS backbone. Click a component.
