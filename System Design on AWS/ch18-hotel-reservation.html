Designing a Hotel Reservation System

Search is read-heavy and forgiving; booking is write-critical and must never double-sell a room. One product, several very different subsystems.

1

Two kinds of users, one hard rule

Property owners onboard, list properties and rooms, set prices and availability, confirm bookings and get paid out. Customers search by location and dates, filter, book, pay, cancel and review. The nonnegotiable nonfunctional requirement: no double bookings and no double charges, while search stays fast and highly available. The book's assumptions:

Per property: 500 B details + 100 rooms × 500 B + 50 reviews × 500 B ≈ 75 KB. The read side (search) is ten times the write side (booking), so they are designed and scaled separately.

2

Four subsystems

Like the crawler and search engine of Chapter 15, the platform is really several systems: onboarding writes property data, search reads a denormalized copy of it, booking owns strongly consistent availability and payments, and reviews hang off completed stays. Click one.

A single-table DynamoDB design for onboarding: one query on the property ID with a sort-key prefix fetches the property, its rooms or its images. Aurora works too; onboarding writes are rare.

3

Search: Elasticsearch plus an availability check

Search runs in two steps: (1) Elasticsearch (OpenSearch) finds properties matching location, filters and text, kept fresh from the database via change data capture; (2) a strongly consistent store confirms which of those have rooms free for the dates. Results are cached. Getting the shard count right matters more than node count.

Shards = (source + growth) × (1 + 10% indexing overhead) ÷ target size. Aim for 10–30 GB per shard for latency-sensitive search, up to ~50 GB for logs. Too many tiny shards waste heap and coordination; one huge shard is slow to query and to rebalance.

To show properties near a point of interest, encode latitude and longitude as a geohash: the world is split into a grid, each cell split again, and each split appends a character. Longer hash means smaller cell; a shared prefix means nearby. To widen a search, drop the last character, or check the 8 neighbor cells too (a place just across a cell edge has a different prefix). A quadtree does the same adaptively: dense cities split into smaller cells, oceans do not.

Tap a cell to search from it.

4

A booking is a state machine

A booking moves through explicit states, persisted with history so support can see what happened and so retries resume from the right place. Some properties confirm instantly; others confirm only after payment or a human check.

Store choice: bookings need strong consistency, so a relational database (Aurora) fits. Most traffic touches current bookings, so partition the bookings table by time (PARTITION BY RANGE(created_at)) and archive old partitions; drop whole partitions rather than deleting rows.

Booking is read-then-write: check availability, then decrement it. Two requests interleaving between those steps both see "1 left." Compare the options.

Real platforms also accept some ambiguity: the same room can be sold on several platforms, so the owner's confirmation is the final word, and some hotels deliberately overbook based on cancellation history.

6

Charge exactly once

A payment orchestrator handles pay-in (the guest pays through gateways such as cards, PayPal or UPI) and pay-out (the owner is paid minus commission), plus a wallet and a ledger. Networks fail mid-call, so each payment is split into three phases around an idempotency key: pre-RPC records the intent and key, RPC calls the gateway, post-RPC records the result. A retry with the same key returns the stored result instead of charging again.
