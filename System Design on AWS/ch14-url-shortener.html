Designing a URL Shortener

Part III works through real designs. The first is small enough to hold in your head: turn a long URL into a short one and redirect billions of clicks fast.

Start with requirements

Every Part III design follows the same rhythm: clarify the problem, split functional requirements (what it does) from nonfunctional ones (how well), estimate the scale, sketch a design, then launch a Day 0 version and grow it to Day N. Make it work, make it right, make it fast. For a URL shortener:

Functional

  • Given a long URL, return a unique short URL
  • Visiting the short URL redirects to the long one
  • Optional custom alias and expiry time
  • Later: analytics on clicks, APIs for third parties, custom domains

Nonfunctional

  • Highly available: a dead link breaks someone's page
  • Redirects in a few milliseconds
  • Short links must not be guessable in sequence
  • Scales to billions of links; multitenant later
2

Back-of-the-envelope numbers

The book assumes 1,000 new short URLs per second, 20,000 redirects per second, links kept for a year and about 1 KB per record. Change the assumptions; the shortest safe key length uses base62 (0–9, a–z, A–Z).

3

How to make the short code

Hashing the long URL (MD5, SHA) and keeping 7 characters needs a database check for collisions on every write, and the same URL always maps to the same code. A counter encoded in base62 never collides, but one counter is a bottleneck and single point of failure, and sequential codes are guessable. The book's answer is a key generation service (KGS) that hands out unique IDs in batches. Type a URL.

4

Unique IDs at scale

The KGS can be backed by two ticket servers: databases whose auto-increment step is 2, one starting at 1 and one at 2, so they never clash and either can fail. The URL service grabs a block of IDs (say 10,000) to keep in memory, so the KGS is not called per request; a crash just wastes the rest of a block.

Ticket server Aincrement=2, offset=1
Ticket server Bincrement=2, offset=2

Across regions, a different trick avoids any coordination: Snowflake-style 64-bit IDs built from a timestamp, a machine number and a per-millisecond sequence, giving 4,096 IDs per millisecond per machine.

APIs, redirects and the table

POST /v1/urls
{ "longUrl": "https://…/chapter-14",
  "customAlias": "sd-aws",      // optional
  "expiresAt": "2026-12-31" }  // optional
→ 201 { "shortUrl": "https://sho.rt/sd-aws" }
→ 409 { "error": "alias taken" }

GET /sd-aws
→ 302 Location: https://…/chapter-14
→ 404 { "error": "not found" }

Access is almost always "get long URL by short code", so a key-value store fits: DynamoDB with the short code as partition key. Custom aliases need a conditional write (attribute_not_exists(pk)) so a second user cannot silently overwrite the first; DynamoDB's TTL attribute removes expired links (eventually, not to the second). A GSI on user ID can serve "my links". For multitenant use, add the tenant to the key, or go further with a cell-based architecture: identical, isolated stacks each serving a slice of tenants, limiting the blast radius.

From Day 0 to millions of users

Do not build for 10 million users on day one. Slide through the stages the book walks.

Will Lambda keep up?

Concurrency ≈ requests per second × duration in seconds. Each region has a default concurrency quota (1,000, raisable), and bursts scale up at a limited rate.
