Designing a Social Network and Newsfeed

Hundreds of millions of people post and scroll. The core puzzle is building each person's feed fast when some accounts have millions of followers.

1

Requirements and scale

Scope: users create posts (text, photos, video), follow others, see a timeline of followed users' posts, like and comment, and search by keyword or hashtag. Timelines must load fast and stay available; seeing a post a few seconds late is fine. The book's assumptions are below. The number that shapes everything is how many timelines one post touches.

2

Fan-out on write, on read, or both

Push (fan-out on write): when someone posts, insert the post ID into every follower's precomputed timeline in a memory cache. Reads are instant, but a celebrity with 200 million followers triggers 200 million writes. Pull (fan-out on read): build the timeline at read time by querying everyone you follow. Writes are cheap, reads are slow. The hybrid: push for normal users, and merge celebrity posts in at read time.

3

Storing posts, likes and comments

A post's structured data (ID, author, text, media references) goes to a database; media goes to S3, deduplicated by content hash. The access patterns are simple key lookups, so either sharded PostgreSQL or DynamoDB works. A DynamoDB single-table design, with time-sortable post IDs (Snowflake style) so "latest posts" is a range read:

A viral post makes its like counter a hot key: one partition can absorb only so many writes per second. Spread the counter over N sub-keys and sum them on read, or buffer likes in a stream and apply them in batches.

4

Timeline, graph and search services

The post workflow orchestrator runs after a post is saved: validation (spam, hate speech, sanitisation), media processing and fan-out. The timeline service reads the user's list of post IDs from Redis (only the most recent few hundred per user), merges in celebrity posts, then hydrates IDs into full posts with batched cache reads (MGET or a pipeline, not one call per post), and may rank and insert ads. Click a component.

5

Live comments, consistency and authentication

Comments are read far more than written and can be eventually consistent, so serve them paginated from cache. One exception: read-your-writes. The author must see their own comment immediately, so for a short while route their reads to the leader (or use a strongly consistent read). To push new comments to everyone viewing a post, keep a WebSocket per viewer and publish comment events per post to the gateways that hold those viewers.

Whichever you choose, avoid re-authenticating on every call: issue short-lived signed tokens (JWTs) the services can verify locally, with refresh tokens for sessions.

6

Moving from Day 0 to Day N safely

Big platforms eventually replace components (X built FlockDB for its graph and Gizzard for sharding). The safe way: shadow traffic first (the old system serves users and also forwards a copy of each request to the new one; a pipeline compares responses), then a gradual rollout by percentage, then keep the old system for a couple of weeks before switching it off. Databases move with a backfill plus a change stream, dual reads to verify, then cut over.

7

Surviving a region failure

The Day N design runs two fully independent regions (no shared dependencies), each able to serve users, with asynchronous data replication. Critical (tier 1) services get the most redundancy. If a region fails, DNS shifts traffic to the survivor. If the survivor cannot carry everything at once, load shedding drops a share of low-priority requests: serving some users beats serving none.
