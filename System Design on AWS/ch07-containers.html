Containerization, Orchestration and Deployment

Containers package an app with everything it needs; orchestrators run thousands of them; deployment strategies and pipelines get new versions out without drama.

1

From servers to VMs to containers

First, one app per physical server: wasteful and slow to provision. Then virtual machines: a hypervisor slices a server into VMs, each with a full guest OS. Then containers: apps share the host kernel and are isolated by OS features (namespaces, cgroups), so they start in seconds, weigh megabytes and run the same on a laptop or in production.

Dockerfiles, images and layer caching

A Dockerfile is a recipe; building it produces an image, a stack of read-only layers (base OS, runtime, dependencies, your code). Layers are cached and shared, so a rebuild only redoes the layers from the first changed instruction upward. Click the line you changed.

Ordering tipCopy the dependency list and install packages before copying source code. Code changes daily, dependencies rarely, so most builds reuse the slow install layer.
3

Registry, engine and container lifecycle

Images live in a registry (Docker Hub, or a private one such as Amazon ECR) organised by repository and tag. The Docker CLI talks to the daemon, which pulls images and asks the runtime (containerd, runc) to create containers: a thin writable layer on top of the image plus isolated process, network and filesystem. Drive one through its lifecycle.

Kubernetes architecture

  
One host is easy; a thousand containers across a hundred hosts need an orchestrator. Kubernetes runs a control plane that holds the desired state and worker nodes that run the work. Click a component.

Declare it, and Kubernetes keeps it true

  
You never say "start three containers". You declare "I want three replicas" and controllers keep comparing reality with that wish, fixing any drift. Change the replica count or kill a pod.

  

    

    

    

  

  






  
6
Rolling out a new version

  
A rolling update replaces pods a few at a time; maxSurge allows extra pods during the rollout and maxUnavailable caps how many may be missing. Readiness probes keep traffic away from pods that are not ready yet; liveness probes restart stuck ones. Blue-green runs a full second environment and flips traffic at once, with instant rollback. StatefulSets roll pods one at a time in order, each keeping a stable name and its own volume, for databases and similar.

  

    

    

    

  






  
7
Gitflow and the CI/CD pipeline

  
Gitflow organises branches: main holds released code, develop integrates finished features, feature/* branches hold work in progress, release/* branches stabilise a version and hotfix/* branches patch production. Every change flows through continuous integration (build, test, scan on each push) and continuous deployment (test, staging, production), with infrastructure defined as code. Follow one feature.

  

  
After deploy: watch itMetrics, logs and traces with alerts on what users feel (error rate, latency), clear on-call ownership, runbooks and blameless post-incident reviews close the loop.
