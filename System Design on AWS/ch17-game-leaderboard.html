Designing an Online Game Leaderboard

Millions of score updates a minute and every player wants to see their rank right now. Sorted sets, smart partitioning and a careful cost model.

1

Requirements and scale

Players submit scores; leaderboards (global, regional, per mode, daily or weekly) update in near real time; players see the top N and their own rank. Nonfunctional targets: writes visible in under a second, reads in well under that, high availability during tournaments, protection against cheating. The book sizes it for 10 million players.

2

Why Redis sorted sets

A relational ORDER BY score DESC LIMIT 10 with an index works for thousands of players, but "what is my rank among 10 million?" needs counting everything above you, and constant score updates churn the index. A Redis sorted set keeps members ordered by score in a skip list plus hash: add or update in O(log n), rank in O(log n), top N in O(log n + N). Play a round.


  






  
3
When one sorted set is not enough

  
One sorted set of hundreds of millions of entries strains one node's memory and CPU. Options: separate leaderboards per game mode or season (natural keys), per region (lower latency, data residency), or shards by player ID hash. Hash shards spread load evenly, but a global top 10 then needs scatter-gather: ask every shard for its top 10 and merge. Exact global rank for one player needs a count from every shard.

  

    

    

    
Another trick for approximate ranks: shard by score range and keep a count per range. Your rank ≈ players in higher ranges + your position in your range.

Day 0 architecture on AWS

  
API Gateway in front of three Lambda functions, DynamoDB as the source of truth, ElastiCache for Redis for ranking, SQS to decouple writes from ranking, and SNS for "you were overtaken" notifications. Step through a score submission and a leaderboard read.

5
Stop polling the leaderboard

  
On Day 0 clients keep requesting the leaderboard, most of the time getting the same answer. At millions of players that is pure waste. Day N pushes changes instead: AppSync subscriptions or API Gateway WebSockets notify clients only when a board they watch changes.
