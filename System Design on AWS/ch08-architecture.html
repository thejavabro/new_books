Architectural Designs and Patterns

The building blocks come together into architectures. This chapter tours how services coordinate, how events flow, and the patterns that keep distributed systems standing.

1

Change data capture

CDC streams every insert, update and delete from a source database to other systems (search indexes, caches, warehouses, other services) as it happens, instead of copying whole tables in nightly batches. Only the changes move, so it is cheaper and fresher. How the changes are detected matters.

2

Brokers, queues and topics

A message broker sits between producers and consumers so neither needs to know about the other, or even be online at the same time. Two delivery shapes: a queue hands each message to exactly one of the competing consumers (work distribution); a topic in publish/subscribe delivers a copy to every subscriber (fan-out). Protocols such as AMQP standardise this. Publish a few messages.

3

Choreography or orchestration

An order must reserve stock, take payment and book a courier. In choreography each service reacts to events and emits its own; nobody is in charge. Loosely coupled and resilient, but the overall flow is implicit and hard to trace. In orchestration a central coordinator (a workflow engine such as AWS Step Functions, Conductor or Temporal) calls each step and tracks state. Clear and observable, but the orchestrator is a dependency and a coupling point.

State-oriented versus event sourcing

A state-oriented system stores only the current balance. Event sourcing stores every change as an immutable event and derives the state by replaying them. You get a full audit trail, can rebuild any past state, and can project the same events into new read models later. The costs: replays need snapshots to stay fast, schemas of old events must stay readable, and reads are usually eventually consistent. Drag through time.

Derived balance

A CDC stream is different: it reports row changes after the fact. Event sourcing makes the events themselves the source of truth.

7

CQRS and the saga pattern

CQRS (command query responsibility segregation) splits writes and reads into separate models, often separate stores: a normalized write model and denormalized read views updated by events. Each side scales and is optimized on its own. A saga replaces a distributed transaction with a chain of local transactions, each with a compensating action that undoes it if a later step fails. Make a step fail.

Failure-tolerant patterns

Three patterns keep one sick dependency from taking down everything. A circuit breaker counts failures; past a threshold it opens and fails fast without calling, after a cool-down it goes half-open and lets a trial request through. Click to send calls while the dependency is healthy or failing.

9

HDFS: big files on cheap machines

HDFS splits files into large blocks (128 MB by default) and stores each block on several DataNodes (replication factor 3). A NameNode holds only metadata: the namespace and which nodes hold which blocks. DataNodes send heartbeats; when one goes silent, the NameNode re-replicates its blocks elsewhere. The secondary NameNode merges edit logs into checkpoints; it is not a hot standby. Store a 640 MB file, then lose a node.

10

Kafka: a distributed commit log

Kafka stores streams of records in topics, split into partitions spread across brokers and replicated. Each partition is an append-only log, ordered, with consumers tracking their own offset, so data can be re-read. Records with the same key go to the same partition, which preserves per-key order. Within a consumer group, each partition is read by exactly one consumer, so partitions cap parallelism.
