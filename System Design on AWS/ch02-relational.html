Three ways to store bytes

Hardware changes; applications should not care. Storage systems hide disks behind one of three abstractions. Pick one to see how data is addressed, what it suits, and which AWS service provides it (Chapter 10 goes deeper).

Tables, keys and relationships

A relational database stores data in tables of rows and typed columns. A primary key identifies each row; a foreign key points at a row in another table, which is how relationships are expressed. Around that core sit indexes (fast lookup), constraints (rules such as NOT NULL or UNIQUE), views (saved queries) and transactions. Click an order to follow its keys.


  

  
SQL splits into sublanguages: DDL defines structure (CREATE, ALTER), DML changes data (INSERT, UPDATE, DELETE), DQL reads it (SELECT), DCL controls access (GRANT, REVOKE) and TCL manages transactions (COMMIT, ROLLBACK).






  
3
ACID transactions

  
A transaction groups statements into one unit. Atomicity: all or nothing. Consistency: the database moves only between valid states, respecting constraints. Isolation: concurrent transactions do not see each other's half-done work. Durability: once committed, it survives a crash, thanks to the write-ahead log. Transfer $100 from Alice to Bob, and pull the plug halfway.

Normalization and its opposite

  
Repeating a customer's email on every order wastes space and invites contradictions: change one copy and the others are wrong. Normalization moves repeated facts into their own table and links them by key. The opposite, denormalization, deliberately copies data back to avoid joins, because reads often outnumber writes 100:1 or more.

Indexes and the B+ tree

  
Without an index, finding one phone number means reading every row. A B+ tree index keeps keys sorted in a short, wide, balanced tree; leaves hold pointers to rows and are linked so range scans are cheap. Each level divides the search space by the fan-out, so depth grows with the logarithm of the table size.

  

    
    
    

    

    
The trade: every index costs storage and slows writes, since each insert must update it. Index the columns you filter and join on, not everything.

  

  






  
7
Partitioning and sharding

  
Vertical partitioning splits a table by columns. Horizontal partitioning splits it by rows, either by range (A–F here, G–M there) or by hash of a key. Put partitions on different servers and you have shards. Insert some customers and compare.

  

    

    

    

  

  
Sharding has a billCross-shard joins and transactions get hard, a popular key can create a hot shard, and adding a server forces data to move. Consistent hashing (Chapter 3) keeps that movement small.






  
8
Synchronous or asynchronous replication

  
Replicas give read scale and disaster recovery. The question is when the leader says "committed". Synchronous: after the replica confirms, so a failover loses nothing but every write waits. Asynchronous: immediately, so writes are fast but a replica may lag, and if the leader dies, the tail of recent writes can vanish.
