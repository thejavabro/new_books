Caching Policies and Strategies

The fastest request is the one you never make. Caches keep hot data close, but you must decide what to keep, when to throw it away and how writes reach the source of truth.

1

Why caches work

A cache keeps a copy of hot data somewhere faster and closer than its source. Most workloads are skewed: a small set of items gets most of the reads, so even a small cache catches a large share. The payoff is lower latency, less load on the database, cheaper bandwidth and smoother handling of spikes. Slide the hit ratio and watch the average.

Amdahl's law, appliedSpeeding up one part only helps as much as that part's share of the total time. Caching a lookup that is 5% of the request barely matters; caching the database call that is 80% of it changes everything. Measure first.
2

Eviction policies, raced

When the cache is full, something must go. Queue-based: FIFO evicts the oldest arrival, LIFO the newest. Recency-based: LRU evicts what was used longest ago, MRU what was used most recently (handy for scans). Frequency-based: LFU evicts the least-used. Belady's optimal algorithm evicts the item needed farthest in the future; it needs a crystal ball, so it is only a benchmark. Step through the same request stream under each policy.

An allowlist policy adds business rules on top: items on a priority list (for example, the home page assets) are never evicted.

3

Keeping the cache honest

A cache that serves outdated data is worse than none. Options: invalidate on write (delete or update the entry when the source changes), on read (check a version, for example an HTTP ETag, and refetch if it changed), or let entries expire after a TTL. TTL is the simplest: you trade freshness for hit ratio. A price changes at minute 10; when do users see it?

Content delivery networks

  
A CDN is a cache spread across hundreds of edge locations so content is served from near the user. A pull CDN fetches from the origin on the first request and caches it; a push CDN has content uploaded ahead of time. Send requests from different cities.

Memcached and Redis

  

    
Memcached
A lean, multithreaded, distributed key-value cache of strings. Memory is carved into slabs of fixed-size chunks to avoid fragmentation; LRU eviction. Clients hash keys across servers. No persistence, no replication: pure cache, very fast, easy to scale out.

    
Redis
An in-memory data structure server: strings, hashes, lists, sets, sorted sets, streams, plus pub/sub, Lua scripts and transactions. Single-threaded command loop, optional persistence and replication, several eviction policies including LRU, LFU and TTL-based.
