Concurrency

Concurrency questions are mostly about vocabulary and failure modes: name the state a thread is in, explain how two threads can corrupt or block each other, and know which java.util.concurrent tool fixes it.

1

Thread life cycle states

A Java thread is always in one of the Thread.State values. NEW until start(); then RUNNABLE (running, or ready and waiting for the scheduler). BLOCKED while waiting to enter a synchronized block another thread holds. WAITING with no timeout (wait(), join(), LockSupport.park()), TIMED_WAITING with one (sleep(ms), wait(ms), join(ms)). TERMINATED when run() ends. Drive a thread through its life.

2

Race conditions: the lost update

count++ looks atomic but is three steps: read, add, write. If two threads interleave those steps, one update vanishes. That is a race condition: the result depends on timing. Fix it by making the steps indivisible with synchronized, a Lock, or an AtomicInteger.

T1
T2
class Counter {
    private int count;
    private final AtomicInteger atomic = new AtomicInteger();

    void unsafeInc()              { count++; }               // read, add, write: can interleave
    synchronized void safeInc()   { count++; }               // one thread at a time
    void atomicInc()              { atomic.incrementAndGet(); } // lock-free compare-and-set
}
3

Deadlocks, livelocks and starvation

A deadlock happens when threads wait for each other forever: T1 holds lock A and wants B, while T2 holds B and wants A. The standard cure is a global lock ordering: every thread acquires A before B, so the cycle cannot form. (Or use tryLock with a timeout.)

4

Executor, ExecutorService and thread pools

Creating a thread per task is expensive and unbounded. An ExecutorService keeps a pool of worker threads and a queue of tasks. Executor is the tiny interface (execute(Runnable)); ExecutorService adds lifecycle (shutdown) and submit, which returns a Future. Submit a batch and change the pool size.

Task queue
Workers
ExecutorService pool = Executors.newFixedThreadPool(2);

Future<Integer> f = pool.submit(() -> expensiveSum());   // Callable: returns a value, may throw
pool.execute(() -> log("fire and forget"));               // Runnable: no result

Integer result = f.get();      // blocks until done; exceptions arrive wrapped in ExecutionException
pool.shutdown();               // stop accepting tasks, finish the queued ones
5

CountDownLatch versus CyclicBarrier

A CountDownLatch lets one or more threads wait until a count reaches zero; anyone can count down, and it cannot be reset. A CyclicBarrier makes a fixed number of threads wait for each other; when the last arrives, all proceed, and the barrier resets for the next round.

6

Producer-Consumer

Producers add items to a bounded buffer and must wait when it is full; consumers take items and must wait when it is empty. A BlockingQueue does the waiting for you. Set the speeds and watch the buffer fill, drain and block.

producer
consumer
BlockingQueue<Integer> q = new ArrayBlockingQueue<>(5);

Runnable producer = () -> {
    for (int i = 0; ; i++) q.put(i);      // blocks while full
};
Runnable consumer = () -> {
    while (true) process(q.take());       // blocks while empty
};
// the same with wait()/notify(), by hand
synchronized void put(int x) throws InterruptedException {
    while (queue.size() == CAP) wait();  // always in a loop
    queue.add(x);
    notifyAll();
}
synchronized int take() throws InterruptedException {
    while (queue.isEmpty()) wait();
    int x = queue.poll();
    notifyAll();
    return x;
}
