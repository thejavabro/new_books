System Scalability

Scalability is the ability of a system to cope with more load by adding resources. Interviews test the vocabulary first, then ask you to sketch a system such as a URL shortener or a chat service.

1

Scalability in a nutshell: up or out

Scalability is a system's ability to cope with growing load by adding resources. Vertical scaling (scale up) buys a bigger machine: simple, no code changes, but expensive at the top end, capped by the largest machine, and still a single point of failure. Horizontal scaling (scale out) adds more machines behind a load balancer: nearly unlimited and fault-tolerant, but the application must be stateless or share state carefully. Raise the load.

2

Latency, bandwidth and throughput

Picture a pipe. Latency is how long one drop takes to travel its length. Bandwidth is how wide it is: the most it could carry per second. Throughput is how much actually flows, which can be lower than bandwidth because of congestion, protocol overhead or a slow consumer. Adjust the pipe.

3

Load balancing, sticky sessions and failover

A load balancer spreads requests across servers. Round robin takes turns. Least connections picks the least busy server. Sticky sessions (for example by client IP hash) always send a user to the same server, which keeps in-memory sessions working but loads servers unevenly, and a server failure loses those sessions unless they are replicated or kept in a shared store. Click a server to take it down and watch failover.

4

Sharding, and why consistent hashing exists

Sharding splits one big dataset across several databases (shards), each holding a slice, so reads and writes scale out. The shard key decides where a row lives. With a naive hash(key) % N, adding one shard changes N and moves most keys. Consistent hashing places shards and keys on a ring so that adding a shard only moves the keys between it and its neighbor. Add a shard in each mode and compare how many keys move (orange).

Shared-nothingEach node owns its CPU, memory and disk and shares nothing with the others; nodes coordinate only over the network. It is the architecture that lets you add nodes without a shared bottleneck, and it is why sharding and stateless services go together.
5

The CAP theorem

A distributed data store can guarantee at most two of Consistency (every read sees the latest write), Availability (every request gets a non-error answer) and Partition tolerance (it keeps working when the network splits nodes apart). Since partitions happen in real networks, the practical choice is what to give up during a partition: consistency or availability. Simulate a split.

6

Shortest path between two people

A social network is a huge graph: people are nodes, friendships are edges. The path from Tom to Kelly is a BFS. But BFS from one side explores roughly kd people for k friends each and distance d. Searching from both ends at once and stopping when the frontiers meet explores about 2·kd/2. With real data spread across machines, each lookup of a person's friends becomes a remote call, so batch them and cache popular profiles.

Practice prompts: design a…

The chapter ends with classic design prompts to practise. For each, pick one and talk through the checklist: requirements and scale estimates, API, data model, high-level components, then bottlenecks (caching, sharding, replication, queues). Below, the URL shortener's core trick: turn an auto-increment id into a short base-62 code.

static final String ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ";

String encode(long id) {
    if (id == 0) return "0";
    StringBuilder sb = new StringBuilder();
    while (id > 0) { sb.append(ALPHABET.charAt((int) (id % 62))); id /= 62; }
    return sb.reverse().toString();     // 7 chars cover 62^7 ≈ 3.5 trillion URLs
}
