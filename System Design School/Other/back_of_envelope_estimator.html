Back-of-the-envelope Resource Estimation

Resource estimation turns load parameters, like daily active users (DAU), into concrete compute and storage needs. Doing it early shows where the bottlenecks will be and what the design has to scale for.

Key load parameters

  • Daily Active Users (DAU): the starting point. You convert it into requests per second.

  • Requests per second (RPS): drives how big the database and cache need to be.

  • Read/write ratio: shapes the read path and the write path, and so your choices of caching, replication and data store.

  • Concurrent connections: matters for things like chat, where you hold open WebSocket connections.

Estimating storage and performance

Design considerations based on load

  • Read-heavy (high read:write): add caching and read replicas.
  • Write-heavy (high write:read): pick high-throughput write stores and accept eventual consistency.

Throughput and latency

  • Throughput: how much data or how many transactions the system handles per unit of time.
  • Latency: how long a request takes to travel to the receiver and back. Critical for real-time apps.

Response time

  • Latency plus server processing time. This is what the user actually feels.

Example: online content platform

  • DAU: 500,000
  • Reads/writes per user: 5 reads and 1 write per day (ratio 5:1)
  • Average blog post size: 50 KB
  • Data retention: 10 years (120 months)

Requests per second: reads ≈ 25/s, writes ≈ 5/s

Daily storage: ≈ 25 GB/day

10-year storage: ≈ 93 TB

How the estimator calculates

  • Write RPS = DAU × writes per user ÷ seconds per day
  • Read RPS = Write RPS × (read ÷ write)
  • Storage per day = DAU × writes per user × data per write
  • Storage per month = storage per day × 31
  • Total = storage per month × retention months

Precision Mode is off by default. Off, it uses 100,000 seconds per day and 1000-byte units, which is what you'd do on a whiteboard. On, it uses the exact 86,400 seconds per day and 1024-byte units.
