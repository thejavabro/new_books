State, Memory, and Decision Persistence

Agents that forget lose work; agents that remember everything become a liability. This chapter sorts state into tiers and keeps a defensible record of every decision.

1

When persistence stops being optional

Not every agent needs state. A classifier that reads a document and returns a label is fine stateless. Persistence becomes mandatory the moment work has continuity: multi-turn refinement, records a regulator requires you to keep, or processes that span days. Default to stateless and promote to stateful only when a requirement demands it. MREP runs both side by side: single price lookups are stateless; the multi-day thesis workflow is not.

Stateless or stateful?

Data foundations do not have to take years: the book cites an insurer that rebuilt its core data platform in ten months. Persistence done well compounds; done ad hoc, it sprawls.

2

The four-tier memory hierarchy

A computer has registers, RAM and disk. An agent has tiers of memory that trade speed for durability in the same way. Data starts in working memory and is promoted upwards only if it must outlive the moment. Tap a tier.

3

Binding tiers to services

ADK separates what state to keep from where it lives. SessionService handles Tier 2 and can be backed by memory (development only), a document database, the managed agent runtime or your own store; custom session IDs can match your CRM case numbers so agent state and system of record share an identifier. MemoryService handles Tier 3: it ingests sessions, consolidates new facts into existing memories rather than appending duplicates, and supports reactive recall (the agent searches when it needs to) and proactive recall (relevant snippets preloaded). In production, each agent action writes to several tiers at once. The discipline is knowing which writes block the user.

4

The Day 2 Survival Pattern: schema migration

The most common Day 2 outage is a code-state mismatch. You deploy version 2.0 of the agent, which expects a new risk_score field, but thousands of live sessions were written by version 1.x. The first returning client hydrates an old session and the app crashes. The pattern: a typed state object (not a loose dictionary), schema_version on every state from day one, a migration registry mapping each version step to a function, lazy migration on load, and migrations tested in CI against real snapshots.

5

Decision persistence and replay

Tier 4 is the one you cannot retrofit: anything not captured at decision time is gone. When a client disputes a thesis or a model upgrade behaves oddly, you need to replay the decision. Replay is not rerunning the agent; it is reconstructing the exact conditions closely enough that any remaining argument is about the model's judgement, not your record-keeping. Build a replayable record.

Capture the audit event asynchronously so it does not slow the user, but never skip the reasoning trace: without it, correct outputs and hallucinations look identical in the record.

6

Long-running work: dehydrate, wait, rehydrate

A thesis is requested on day one, reviewed by compliance on day two and approved by the client on day three. Holding compute for idle workflows is indefensible and instances recycle anyway. So the agent becomes a state machine: it dehydrates its state at a wait point and rehydrates when the workflow resumes. The hardest case is version skew: a session that waited three weeks while the code was redeployed five times.

7

Graceful amnesia: forgetting on purpose

An agent that remembers everything eventually retrieves too much: 200 "relevant" memories and the model spends more tokens chewing on memory than producing work. Graceful amnesia prunes low-value memories (brief interactions, superseded preferences, abandoned engagements), and lets the agent admit what it cannot recall rather than confabulate. Forgetting also has a legal side. A client invokes the right to erasure; GDPR gives you 30 days. Run the deletion.

8

From reading the record to changing it

An agent that only answers questions about the business is a research tool; one that acts on the live record is operational, and that is where most of the value and most of the risk sit. Each rung changes less about what the agent can do and more about who is liable when it acts.

One memory, two ownersA programme runs two memories. The delivery harness's memory (context repo, decision logs, codified ways of working) is development-time IP that needs weeding every couple of days, or it resurrects decisions you killed weeks ago; the first symptom is a colleague quietly giving up on the tool. The platform's memory (sessions, long-term memory, audit) belongs to the product and needs both a platform owner and a business owner. The seam between them is where accountability falls through.
