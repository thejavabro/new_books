Single-Agent and Multi-Agent Systems

Multi-agent diagrams look impressive, but every extra agent adds coordination cost and new ways to fail. The real skill is knowing when not to split.

1

Multi-agent systems are seductive

The pitch writes itself: one agent to search, one to analyse, one to write, one to check. The diagram has lots of boxes and arrows. Then a real workflow hits it. The research agent returns data the analyst cannot parse; the analyst guesses; the writer polishes the guess. Every agent boundary adds a Context Management Overhead: more latency, more cost, more coordination and some information lost at each handoff.

The 120-message argumentThe author watched an Analyst agent and a Reviewer agent enter a refinement loop. The analyst fixed formatting but changed one word, so the reviewer re-reviewed the whole thing. By the time a person intervened they had exchanged about 120 messages. Neither agent was wrong; nobody had bounded the loop.

There is an organizational lesson too. If your human teams lack clear ownership, five agents mirroring them will not create it. More often, it automates the ambiguity.

2

How many agents do you actually need?

Start with one agent: a coherent role, the right tools, enough context. Exhaust that design before splitting. A single agent comfortably handles fewer than a dozen focused tools, active context under about 32K tokens, one coherent persona and linear or branching (not heavily parallel) work. Tick what applies to your use case.

A workflow with stages is not automatically multi-agent. If the path is fixed and each stage is predictable, a structured workflow may be the honest design. Calling every stage an agent is agent washing with an architecture diagram.

3

What each handoff costs

Context rarely crosses a boundary intact: it gets summarized, normalized or trimmed. Each downstream agent re-reads what came before, so tokens grow faster than agent count. Add agents in a sequential pipeline and watch fidelity, tokens and the humans' ability to follow.

The AI Squad modelThe author's sweet spot: one accountable human expert overseeing roughly three to five well-scoped agents. It is a heuristic about human cognitive load, not a hard limit. Keep the number of distinct decision-making roles small; several agents can share one role when scale demands it. One human can govern only as much agentic complexity as they can understand and own.

Research on scaling agent teams points the same way: beyond a threshold, adding agents made results worse, and errors amplified far more in peer-to-peer topologies than under a supervisor.

4

Design agents like job specs

If you do split, split by role, not by task. Each agent needs five things written down: a clear name, a responsibility, its capabilities (tools), its boundaries (what it explicitly does not do) and its interface (how it receives and returns work). Clear roles make debugging, permission scoping, cost attribution and scaling per role possible. Tap the agents in the book's running example, the MREP Research Committee, asked for a semiconductor-sector thesis.

In ADK the supervisor routes by reading each sub-agent's description, so the description is the contract. Ambiguity there becomes ambiguity in production.

5

Five ways agents talk to each other

Communication is architecture. Start with the least complicated pattern that meets the need, and make everything else earn its place.

Sequential vs parallel: same three branches

Sequential waits for the sum; fan-out waits for the slowest branch plus aggregation. Parallelism does not remove the work of reconciling conflicting results.

6

Orchestration maturity: earn each stage

Organizations progress through orchestration stages rather than picking one. Each stage adds operational burden the previous one did not need. Teams that jump from one agent to a five-agent team usually spend the next months building the tracing they skipped.

ADK also offers Skills: reusable bundles of instructions, scripts and resources that load progressively (metadata first, full instructions when triggered). They sit between a single tool and a full sub-agent, a useful middle ground near the Default-to-Delegation boundary. The author warns against hand-rolled orchestration: one custom framework he built was obsolete within two weeks as the ecosystem moved under it.

7

What breaks when agents work together

Multi-agent failures are emergent: they come from interactions, not from one broken agent. Tap each failure for its prevention, then try the classic one below.

The delegation merry-go-round

Agent A is told to delegate specialized queries to B. B is told the same about A.

Most of these are invisible without purpose-built observability. Distributed tracing shows the spans; trajectory evaluation checks the sequence of tool calls and delegations, answering "why did the system do that?" rather than only "was the final answer right?"

8

Inside your walls and beyond them

Inside your system

ADK sub-agents for description-driven delegation, plus SequentialAgent, ParallelAgent and LoopAgent, and newer graph-based workflows. These coordinate agents you build and operate.

Across organizations

A2A (Agent-to-Agent) is an open protocol, now under the Linux Foundation, built on HTTP, SSE and JSON-RPC, so your agent can call an agent you do not own. Inside, coordination is a design choice; across boundaries it is a contract.

One line to rememberMCP standardizes how agents talk to tools. A2A standardizes how agents talk to each other.
