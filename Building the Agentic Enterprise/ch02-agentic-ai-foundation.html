1

The word “agent” has lost its meaning

Two 2024 cases frame the chapter. A city launched a "chatbot" for small businesses that, speaking with official authority, gave advice that would have broken the law. An airline was held liable after its support bot invented a refund policy. Neither was an agent, yet both influenced real decisions without governance. Meanwhile, almost anything with an LLM now gets called an agent, and the label risks becoming the strategy.

LLM application

Responds to prompts. Prompt and response, RAG, fixed chains of calls, classification and extraction. Stateless between calls, produces text, holds no goal across turns. Often extremely useful.

Agentic system

Pursues a goal. Reasons about how to get there, uses tools to act, observes results and adapts its plan. Usually has a defined role. It is a governed system component, not a coworker with discretion.

Prompt chain or agent? The tell

A prompt chain splits a task into fixed steps that the developer orders in advance. Every step runs regardless of what the previous one produced. An agent uses each observation to choose the next action. The tell is simple: can it change its plan based on a tool result? Both are valid; they need different operations. Run the same earnings-call job both ways.

Press Run. Step 2 will come back with a low-confidence summary.

Determinism is a feature, tooA CI/CD pipeline is valuable because it does the same thing every time. Agents can help debug or analyse failures, but they should not own it. Use agency where adaptation adds value, keep determinism where predictability is the requirement. There is no prize for agentifying what is not broken.
3

The loop: reason, act, observe

Reason: what do I know, what do I still need, what is the best next step? Act: call a tool, query data, run code, delegate. Observe: fold the result into context and check the goal. The loop ends when the goal is met or an external stop fires: an iteration cap, a budget or a timeout. Closing the loop brings four new concerns: non-determinism compounds, failures become emergent (loops, oscillation, five sensible steps adding up to nonsense), state becomes first class, and actions persist.

Goal needs 3 successful steps. Each pass costs about 5k tokens.
Bad text vs bad outcomesAn LLM app can give you a bad answer. An agent can give you a bad business outcome, sometimes irreversible. That is why every production agent needs an autonomy boundary, and why accountability lands on the organization, never on the model.
4

Tools make agents agents

The model supplies intelligence; tools supply capability. To the model a tool is a contract with four parts: a name that signals purpose, a description that says when to use it, a typed schema that constrains arguments, and a return type that says what comes back. The model never runs the function; it only requests it. The runtime executes it, and that boundary is where calls are validated, permissioned and logged.

The author's favourite fix: a team complained their agent picked tools "randomly". It had three tools called roughly search_data, query_data and fetch_data. Renaming them, describing when to use each, and reducing overlap took selection accuracy from about 60% to over 90%. Which tool definition is better?

Tool design: A or B?

MCP, the Model Context Protocol, standardizes how tools describe themselves so one tool can serve many agents and frameworks. Tool schemas are API contracts: version them, register them, and know who approved each change.

Lifecycles and who owns what

An agent is a managed system actor, not a throwaway function call. It moves through five phases, each with its own failure mode. Short-lived agents finish a bounded task and end; long-lived ones keep state across sessions and bring drift, memory and access-control problems with them.

ADK, Gemini and the layered stack

The book uses Google's open-source Agent Development Kit as its scaffold: multi-language, model-agnostic, with built-in MCP and A2A support. Its six primitives are Agent, Tool, Runner, Session, State and Memory. Keep the layers separate: the framework, the reasoning model and the runtime platform are three decisions, and collapsing them into one forces you to reopen the whole architecture each time one changes.

A minimal agent reads like a set of design decisions. This sketch is illustrative, not from the book:

def lookup_rate(series: str, region: str = "US") -> dict:
    """Use when the user asks for a macro indicator
    (inflation, jobs, rates) for a date range."""
    return rates_service.fetch(series, region)

analyst = Agent(
    name="RatesAnalyst",          # identity and routing signal
    model="fast-tier-model",      # rightsized, not the biggest
    instruction="Answer with sourced figures. "
                "If the series is ambiguous, ask once.",
    tools=[lookup_rate],          # one tool until it earns more
)
The context taxTeams reach for sub-agents and hand-offs before one agent can reliably pick the right tool. Every hand-off makes context travel with the work. Decompose by role, not by task, and earn complexity with production evidence. ADK is a scaffold; it does not give you an operating model, a runtime or governance by itself. Decide who will operate the system first, then pick technology they can run.

Rightsizing models and thinking levels

Defaulting every agent to the most capable model is like putting your most expensive analyst on data entry. Match capability to work: fast tiers and low thinking for routing and extraction, medium for most agent tasks, deep reasoning only where a wrong answer is costly. In an agent, cost is tokens × steps × tool calls × retries, so cost by the interaction graph of one request, not by the number of users. Prices below are illustrative.

Five Day 2 challenges and the governance gates

Building the pieces is not where initiatives stall; operating them is. Five questions return in every production review. Tap each for its monitorable signal.

The fix is not more approvals at the end but gates built into an Agent Development Lifecycle: architecture review shapes agent boundaries, security review shapes identity, DevSecOps shapes pipelines and eval gates, compliance shapes constraints and evidence. Because behaviour shifts whenever the model, instructions, tools or data change, the gates have to run continuously. That is AgentOps and EvalOps.

The 40 repair crewsA utility's leak-detection agent saw a huge pressure drop, which was a sensor glitch, and dispatched forty crews to one street. A human approval step for large dispatches now sits in the loop.
