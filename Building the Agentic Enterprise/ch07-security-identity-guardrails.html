Security, Identity, and Guardrails

An agent that can act needs an identity, a fence and a set of brakes. This chapter builds zero trust for software that makes its own decisions.

1

The trust barrier

An agent can work perfectly and still never ship, because the enterprise lacks the evidence, control and accountability to trust it with real data, tools and consequences. Security review is one of the main places projects die, not because the technology fails but because nobody can answer the security architect's questions. Context is the moat; security is the wall around it. An unprotected context store is an exfiltration route; memory without identity scoping is a cross-tenant leak; a tool list without boundaries is privilege escalation.

The zero-cost exfiltrationIn 2023, engineers at a large electronics firm separately pasted proprietary code and a confidential meeting transcript into a public chatbot, each trying to be productive. No attacker needed. The firm banned the tools and later built internal alternatives. Without controls at the AI boundary, the most mundane workflow becomes the leak.

The chapter answers six questions in order: who is this agent (identity), what can it reach (perimeter), what may it do (access), what stops it exceeding authority (guardrails), how is security made non-optional (review gate), and how do you respond at machine speed (agentic SOC).

2

Identity is the gate

Traditional identity is simple: a user logs in and their session acts for them. An agent is not a proxy but an actor. When it calls an API, is the caller the user, the agent, the platform or the tool? The Agent Identity Stack climbs from maximum to minimum blast radius. Most teams start at the bottom and climb only after their first incident.

Newer platforms add a dedicated agent identity type (SPIFFE-based) separate from service accounts, so audit logs can say which of 500 running instances, on which version, made a call. Why it matters: a misconfigured microservice permission sits there; a misconfigured agent permission gets explored, because the agent reasons about which tools reach its goal. And an agent misusing normal access looks like normal behaviour to insider-threat analytics; intent is not visible on the network.

3

Workload Identity Federation: visitor badges, not master keys

A long-lived service-account key is a permanent badge that opens every door and never expires. Federation replaces it with something like a visitor pass: prove you are running in the expected environment, receive a short-lived token scoped to what you need. Agents authenticate to the platform, not to each other; the platform mediates every boundary. Slide the token lifetime to see the exposure window if one leaks.

Extra conditions can bind tokens to attributes (environment, workload) and a tool gateway can add time-of-day policy, so possessing a token is not enough on its own. For agents that must act on a user's behalf in a third-party system, OAuth with PKCE lets the user authorize the agent without handing over their own credentials. The recurring gap: prototypes quietly use the developer's own access, and nobody notices until production.

4

The network perimeter: assume the model can be tricked

Identity says who; the perimeter says what can be reached. Service perimeters wrap cloud resources so data cannot leave to anything outside, and per-agent egress allowlists list exactly which external APIs each agent may call. The principle: do not rely on the model to enforce security. Models can be manipulated; infrastructure sits outside the reasoning loop. Inject a malicious instruction and see.

Defense in depth is drawn as concentric rings. Tap from the outside in.

5

Tool availability is permission

If a tool is in an agent's list, the agent can and will use it whenever its reasoning says so. So tool-level access control is an overlay on top of IAM: each MREP agent has an explicit list of available tools and an explicit list of exclusions. The director has only delegation tools and cannot read data; analysts have no write tools; the thesis writer cannot publish and must route through compliance.

Data sovereignty adds a new vector: once a client's personal data enters the context window, it can travel to the model endpoint (possibly across regions), into session state and memory, and into traces and logs. Redact before the model sees it, pin processing regions, and control the keys.

6

Guardrails in three layers

No single layer is enough. Input guardrails screen and sanitize requests before reasoning (injection, jailbreaks, sensitive data). Action guardrails constrain execution: iteration caps, cost ceilings, write-back controls, kill switches. Output guardrails validate what reaches the user. You may not know which layer saved you until you read the audit log after an incident. Pick a threat and see which layer is meant to catch it.

Which layer catches it first?

Compliance is architectureImmutable audit trails, decision lineage and mapping to regulations must exist from day 0, because accountability is the constant. Retrofitted security is estimated to cost around ten times more, and sometimes cannot be retrofitted at all.

Defense at machine speed

Threat reporting cited in the book puts the median time from initial access to hand-off to a follow-on attacker at about 22 seconds, down from over eight hours a few years earlier. A human analyst reading an alert, checking logs and filing a ticket cannot win that race. The answer to agentic attacks is agentic defense: triage, malware analysis, detection-engineering and threat-hunting agents that compress half an hour of first-line triage into about a minute, with people supervising.

Securing MCP tool surfaces

MCP's strengths (dynamic discovery, structured calls) are also its attack surface. Threats include tool poisoning, the confused deputy (an agent tricked into using its legitimate authority for someone else), token passthrough, parameter injection, scope inflation, misconfigured servers, shadow MCP servers stood up for convenience, and malicious tool sources. The protocol itself does not enforce permissions, so the book's answer is a centralized MCP proxy that every agent-to-tool call passes through, now available as a managed agent gateway. Step through what it does on every call.

The proxy is a single enforcement point and therefore a single point of failure: architect it as a load-bearing wall. Pair it with a tool registry so unapproved tools cannot appear, and treat agent-framework dependencies as production dependencies with the same vulnerability scanning.

10

The OWASP agentic top 10 and Least Agency

OWASP's Top 10 for agentic applications makes a ready security-review checklist. The first five risks live inside a single agent; the last five emerge from multi-agent systems, persistent state and human trust. Tap each.

Least Agency, beside Least PrivilegeLeast Privilege limits what an agent can access. Least Agency limits what it may decide. The thesis writer can technically reach the publishing step, but deciding to publish is not its call: it drafts and submits. When the director receives an unrecognized request (say, salary benchmarks), Least Agency says decline or escalate, even if it has the permissions to try. Privilege violations show up in logs; agency violations look like competent work outside the brief.
