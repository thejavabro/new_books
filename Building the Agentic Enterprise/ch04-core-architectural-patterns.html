Core Architectural Patterns for Agentic Systems

A small set of recurring patterns covers most agent designs. Learn to name them, and you can reason about cost, control and failure before you write code.

1

Before any pattern: the readiness gate

Patterns are powerful only in organizations that can run them. "AI-ready" (everyone has copilots) has become a baseline, like having a cloud account a decade ago; the differentiator is operating discipline. Few organizations report agents ready for production while many projects are forecast to be cancelled. So the chapter starts with five honest questions. Two or more "not ready" answers mean: pause pattern selection and build foundations first.

The pressure to skip this gate is itself diagnostic: it shows exactly where governance is missing. And readiness does not mean preserving today's process. Agents change processes, people and sometimes org structures; architecture should follow the redesigned process, not freeze the old one.

2

Planner-Executor: what versus how

The Planner works at the strategic level: decompose the goal, order sub-tasks by dependency, estimate cost honestly, and adapt the plan from what comes back. It never touches a tool. The Executor works at the tactical level: parse the plan, run only the tools it names, handle routine retries itself, and report results, including partial failures. Separating them lets you tell a bad plan from a bad execution, and lets a human approve the plan before anything happens.

When the pattern is ceremonyOne team added a Planner to an investment Q&A assistant. Every plan was the same single step: "retrieve the data and answer". The Planner added latency and cost and solved nothing. Use the pattern when a wrong action costs more than an extra planning call: complex multi-step goals, plans that need human review, high-stakes actions, adaptive workflows.
3

Controller-Worker: one owner, many specialists

A Controller routes tasks against a capability inventory, monitors progress (including workers that go quiet), aggregates outputs and escalates. It owns the outcome but never does the work. Workers stay inside their capability, report honestly (especially failures), respect boundaries and ask for help rather than guess. A worker that quietly widens its scope breaks the controller's model of the system.

Patterns compose: a Planner can hand its plan to a Controller that distributes the steps to Workers. MREP's research pipeline does exactly that.

4

Reactive, deliberative, and the hybrid in between

Reactive agents respond to a trigger: fast, little state, predictable, shallow reasoning. Deliberative agents keep a model of the task, plan and adapt: strategic, stateful, slower, less predictable. Most production agents sit between the poles, and the choice can differ per layer. ReAct, the reason-and-act loop, is the canonical hybrid.

Reflection, and the production trifecta

Reflection generates fast, then checks slowly: generate, critique, refine, accept or loop, always with a cap. It typically costs two to three times the tokens and latency. Self-reflection is fine for syntax and completeness. For consequential judgement (compliance, facts, safety) the book prefers a trifecta: a Planner defines what good looks like, a Generator produces, and a structurally separate Evaluator, with its own context and ideally a different model, decides whether it passes.

Each draft has a 25% chance of containing a real compliance problem. Watch which problems slip through.

6

Routing: send each request to the right handler

A router classifies intent and dispatches to one specialist, which keeps every handler focused on its own tools. Routing earns its keep for multi-domain systems, load distribution, permission-sensitive requests and cost (cheap models for easy requests). The book's inbox example: a fast reactive router at the gate, deliberative handlers behind it. Be the router.

Routing versus mixture of expertsRouting is one-to-one: one path, one audit trail. A mixture-of-experts pattern is one-to-many: several specialists each judge whether the request is theirs and their answers are combined. Use the second only for the ambiguous tail ("my payment failed and I want to cancel"), because you pay for every parallel evaluation.
7

Separate who decides from who does

Control logic decides what should happen and must be explainable. Execution logic performs the side effects and must be auditable. They change for different reasons: control moves with the business (strategy, regulation), execution moves with technology (APIs, endpoints). Entangle them and each change breaks the other.

Anti-pattern: the smart toolA tool that quietly decides things ("if the amount is large, also notify finance") hides a decision from the trace. You see the side effect but not the reasoning. Keep tools dumb, keep agents smart.

The wider layer around the model, instructions, tools, context, evaluation and workflow, is the harness. Benchmarks and delivery experience both show the same model performing very differently in different harnesses. The model is what competitors can buy; the harness is yours.

Where should this action execute?

Client-side: the model proposes, trusted middleware validates, policy checks run, then deterministic code executes. Agent-side: the agent platform calls the integration directly. Faster, for low-risk work.

8

Safety as an architectural pattern

Four enforcement surfaces form the minimum viable guardrail set: input validation, output filtering, action restrictions and scope constraints. Leave one out and a whole class of failure goes unguarded. Each guardrail also needs an explicit failure path: reject, or escalate to a human. Send requests through the pipeline.

A useful review question from the author: if this decision went wrong and landed in a post-mortem, would you be comfortable saying the model made it? If not, a human or deterministic control should own it.
