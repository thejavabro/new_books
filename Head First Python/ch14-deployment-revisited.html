1

From a file to a database server

SQLite is perfect for learning and for one process at a time. A webapp in the cloud, with several workers and a Coach adding sessions every week, is better served by a database server. The book switches to MariaDB (a community fork of MySQL), which PythonAnywhere offers as MySQL. There's very little new Python in this chapter. Most of the work is in the details around your code.

SQLiteA library inside your process, reading one file. Nothing to install, nothing to log in to.
MariaDB / MySQLA separate program you connect to with a host, user, password and database name. Built for many simultaneous users.
2

Same SQL, different dialect

Both engines speak SQL, each with its own accent. The schema file needs three small edits, the placeholders change from ? to %s, and the "what tables do I have?" commands differ. Pick a pair to compare.

One codebase, two databases

  
DBcm already accepts either a filename (SQLite) or a dictionary of connection details (MySQL/MariaDB). So the only code change is which one you pass. The book's approach: look at where the code is running and pick the matching credentials, so the same data_utils.py works on your laptop and in the cloud without edits.

  
import platform

if "aws" in platform.uname().release:          # PythonAnywhere runs on AWS
    db_details = {"host": "you.mysql.pythonanywhere-services.com",
                  "user": "you", "password": "…", "database": "you$swimDB"}
else:
    db_details = {"host": "localhost", "user": "swimuser",
                  "password": "…", "database": "swimDB"}

with DBcm.UseDatabase(db_details) as db:
    ...

  

    

    

  

  
Keep passwords out of version controlHard-coded passwords are fine for a learning project. In real projects, read them from environment variables or a config file that never gets committed.






  
4
Moving the data and the app

  
Here is the whole move, end to end. Locally you rebuild the schema in MariaDB, copy the data across and check it; then in the cloud you create a database, upload the code, load the data and reload the webapp.

  






  
5
Code never lives in isolation

  
The point of this last chapter: your Python interacts with its environment. The database engine, the host, the OS and the deployment process all shape what "working code" means. Because the database access sat behind DBcm and a handful of query functions, swapping engines touched only the SQL text and the credentials. The Coach now has a system that copes with any number of swimmers and sessions.

  

    
Isolate the databasePut all SQL in one module of query functions; the webapp calls functions, not SQL.

    
Expect dialectsSame SQL language, different details: auto-increment, placeholders, catalogue commands, types.

    
Choose config by environmentOne codebase, credentials chosen at run time.

    
Test before you deployRun it locally against the same kind of database first.
