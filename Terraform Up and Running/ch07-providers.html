Working with Multiple Providers

A provider is a plugin that teaches Terraform one platform's API. Real systems need several: more than one region, more than one account, even more than one kind of platform, such as AWS plus Kubernetes.

1

What a provider really is

Until now, providers just worked. Underneath, Terraform is split in two: Terraform core, the terraform binary with the language, graph and state logic, and providers, separate plugin binaries that each know one platform's API. Core talks to each plugin over RPC; the plugin talks to AWS, Azure, Kubernetes or whatever it wraps.

terraform init finds and downloads the plugins. Every provider has a source address with three parts. Tap each part.

//
terraform {
  required_providers {
    aws = {                       # local name
      source  = "hashicorp/aws"
      version = "~> 4.0"
    }
  }
}
provider "aws" {
  region = "us-east-2"
}
Always include required_providersWithout it, Terraform guesses the source from the name and grabs the latest version, which can break your code when a new major release ships. Pin a source and a version constraint, and commit the .terraform.lock.hcl file that init writes.
2

Several copies of one provider: regions

A provider block configures one region. To use two, add a second block with an alias, and tell each resource or data source which one to use with provider = aws.<alias>. The book's example deploys a MySQL primary in one region and a read replica in another. Step through.

provider "aws" { region = "us-east-2", alias = "primary" }
provider "aws" { region = "us-west-1", alias = "replica" }

module "mysql_replica" {
  source    = "../../modules/data-stores/mysql"
  providers = { aws = aws.replica }
  replicate_source_db = module.mysql_primary.arn
}
3

Several copies of one provider: accounts

Production systems usually span several AWS accounts (stage, prod, shared services, security) so a mistake or a breach in one can't touch the others. With AWS Organizations you create child accounts from a parent; each gets an OrganizationAccountAccessRole the parent can assume. A provider block can assume that role.

provider "aws" {
  region = "us-east-2"
  alias  = "child"
  assume_role {
    role_arn = "arn:aws:iam::222222222222:role/OrganizationAccountAccessRole"
  }
}
data "aws_caller_identity" "child" { provider = aws.child }  # prove it worked
Cross-account roles are double opt-inThe role's trust policy in the child account must allow the parent, and the user in the parent account must be allowed sts:AssumeRole. Organizations sets up both for its default role; for your own roles you must do it yourself.
4

Reusable modules that need several providers

Provider blocks inside a reusable module are a trap: callers can't change them, and the module can't be used with count or for_each. Instead, the module declares the provider slots it needs with configuration_aliases, and the root module plugs real providers into them.

# modules/multi-account/main.tf
terraform {
  required_providers {
    aws = {
      source = "hashicorp/aws"
      configuration_aliases = [
        aws.parent, aws.child ]
    }
  }
}
# root module
module "multi_account" {
  source = "../../modules/multi-account"
  providers = {
    aws.parent = aws.parent
    aws.child  = aws.child
  }
}
5

Different providers together: Docker and Kubernetes

The chapter's last example mixes two kinds of provider. First a crash course: a Docker image is a self-contained snapshot of an app and its OS libraries; docker run starts a container from it, isolated from the host. Kubernetes runs containers across a cluster: a control plane schedules work, worker nodes run it. You describe what you want with objects such as a Deployment (keep N copies of this container running) and a Service (give them one stable network endpoint and load-balance across them). Try it.

The control plane keeps actual state matching desired state, much as Terraform does for infrastructure.

With Terraform, the book wraps this in two modules: eks-cluster, which uses the AWS provider to create a managed Kubernetes cluster (EKS) with a managed node group, and k8s-app, which uses the Kubernetes provider to create the Deployment and Service. The Kubernetes provider is configured from the cluster's own outputs:

provider "kubernetes" {
  host                   = module.eks_cluster.cluster_endpoint
  cluster_ca_certificate = base64decode(module.eks_cluster.cluster_certificate_authority[0].data)
  token                  = data.aws_eks_cluster_auth.cluster.token
}
6

So, how many providers per module?

Usually oneYou can now deploy to many regions, many accounts and many platforms from one module. The chapter's conclusion is that in production you usually shouldn't: keep each region, account and cloud in its own module, so they stay isolated and a single apply has a limited blast radius. Aliases are for resources that genuinely belong together, such as a replica that must live in a second region.
