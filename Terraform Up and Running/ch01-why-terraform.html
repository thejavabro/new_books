Software isn't done until it ships

For decades, companies split the work in two. Devs wrote the code; Ops racked servers, wired networks and kept everything running. The code was "thrown over the wall" and each side blamed the other when releases broke. As the cloud replaced hardware with API calls, Ops started writing code too, and the wall began to come down. That shift is what people mean by DevOps: not a team or a job title, but a set of practices for making software delivery efficient.

The movement's four core values are often summed up as CAMS: culture, automation, measurement and sharing. The book focuses on just one, automation, and especially on managing infrastructure through code rather than by clicking around a console.

Five kinds of infrastructure-as-code tool

Infrastructure as code means you write and run code to define, deploy, update and destroy infrastructure. The tools fall into five broad families. They overlap, but each is aimed at a different layer of the stack. Pick one to see what it touches and what its code looks like.

Server templating: VMs and containers

  
Server templating tools such as Packer, Docker and Vagrant don't configure live servers. They bake a snapshot of the OS, software and files into an image, then you launch identical servers from it. That image comes in two shapes, and the difference is where isolation happens.

  

    

    

    

  

  
Immutable infrastructureOnce an image is deployed, you never change it in place. Need a new version? Build a new image and replace the servers. Like immutable variables in functional programming, this makes it far easier to reason about what is actually running.

How Terraform works

  
Terraform is an open source tool from HashiCorp, written in Go and shipped as a single binary called terraform. There are no servers to install. When you run it, the binary reads your .tf files and makes API calls on your behalf to providers such as AWS, Azure, Google Cloud or Kubernetes. Step through one run.

  

    

    

  

  
Portable tooling, not portable codeTerraform can't take the same file and deploy it to AWS one day and Azure the next: their servers, networks and load balancers differ too much. What carries over is the language, CLI and workflow. Learn them once and you can manage almost any platform.

Procedural versus declarative

  
Here is the classic experiment. You have 10 servers and want 15. A procedural tool (Ansible, Chef) runs steps: "add 5 servers". A declarative tool (Terraform, CloudFormation, Puppet) states an end result: "there should be 15". Now run each version twice, as you would on the next deploy.

Procedural code only makes sense if you know its history: which scripts already ran, and in what order. Declarative code always describes the current desired state, so it stays small and readable, and reusing it is safe. The price is less control: there are no real loops or branches, though Chapter 5 shows the workarounds.
