Reusable Infrastructure with Modules

Copy-pasting staging into production is how environments drift apart. Modules are Terraform's functions: write the cluster once, call it with different inputs, and pin each environment to a tested version.

BasicsInputsLocalsOutputsGotchasVersioningQuick check
1

A module is just a folder

You now have staging working and need production. Copy-pasting the code works until the copies drift apart. Terraform's answer is the module: any folder of .tf files. Everything you've written so far was a root module, one you run apply in directly. Move the web cluster into modules/services/webserver-cluster and call it from each environment, the way you'd call a function.

module "webserver_cluster" {
  source = "../../../modules/services/webserver-cluster"
  # inputs go here
}
# after adding or changing a module's source: terraform init

One rule to start with: put provider blocks only in root modules, never inside reusable ones. Chapter 7 explains why.

2

Inputs make it configurable

Hardcoded names would make staging and production collide, both trying to create a security group with the same name. So the module declares input variables, and each caller passes its own values. Edit the inputs and watch both the call and the result change.


      

    

  






  
3
Locals: named values that aren't inputs

  
Some values should be named but not configurable. The load balancer's port 80, the "any port" value 0, the CIDR 0.0.0.0/0: repeating them is error-prone, yet exposing them as inputs invites callers to break things. Locals are for this. Define them once in a locals block and read them as local.<name>, only inside the module.

  


locals {
  http_port    = 80
  any_port     = 0
  any_protocol = "-1"
  tcp_protocol = "tcp"
  all_ips      = ["0.0.0.0/0"]
}

ingress {
  from_port   = local.http_port
  to_port     = local.http_port
  protocol    = local.tcp_protocol
  cidr_blocks = local.all_ips
}

4
Outputs: give the caller handles

  
Production should scale out during business hours. That's done with aws_autoscaling_schedule resources, but only in the prod root module, not in the shared module. They need the ASG's name, so the module exposes it as an output and prod reads module.webserver_cluster.asg_name. Drag the clock.

  

    
    

    

  


# modules/services/webserver-cluster/outputs.tf
output "asg_name" { value = aws_autoscaling_group.example.name }

# live/prod/services/webserver-cluster/main.tf
resource "aws_autoscaling_schedule" "scale_out" {
  scheduled_action_name  = "scale-out-during-business-hours"
  min_size = 2, max_size = 10, desired_capacity = 10
  recurrence             = "0 9 * * *"
  autoscaling_group_name = module.webserver_cluster.asg_name
}






  
5
Two module gotchas

  
1. File paths

  
Terraform resolves relative paths from the directory where you run it, which for a module is the caller's folder. To load user-data.sh that sits next to the module's own code, use a path reference. Pick one and see where it points.

  

    

    

    

  

  
2. Inline blocks versus separate resources

  
Many resources can be configured either with inline blocks (an ingress block inside a security group) or with separate resources (aws_security_group_rule). Mixing the two for the same thing makes them overwrite each other. Inside modules, prefer separate resources, because callers can then add their own rules from outside.

  

    

    

  






  
6
Versioned modules

  
If staging and production both point at the same local folder, every edit hits both on the next deploy. Better: keep modules in their own Git repo, tag releases, and have each environment pin a ?ref=. Then you test a new version in staging while production keeps running the old one.
