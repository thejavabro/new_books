Managing Secrets with Terraform

Rule one: never store secrets in plain text. Terraform touches secrets in three places, when it logs in to providers, when it passes values to resources, and in the state it writes down. Each needs its own answer.

The first rule of secrets

Database passwords, API keys, TLS certificates, SSH and GPG keys: sooner or later your infrastructure code handles all of them. The chapter starts with one rule, and repeats it in its conclusion:

Do not store secrets in plain text.

A password committed to Git doesn't stay in one place. Press the button and follow where a hardcoded secret ends up.

resource "aws_db_instance" "example" {
  username = "admin"
  password = "hunter2-do-not-do-this"   # plain text in code
}

Secret #1: logging in to providers

The first secret Terraform needs is its own credentials. Never put access keys in the provider block. For human users, use environment variables, ideally fed from a password manager or a tool like aws-vault that keeps keys in the OS keychain and hands out short-lived session credentials. For machine users such as a CI server there's no human to type anything, and the book compares three options. Pick one.

Secret #3: state and plan files

  
Here is what catches people out. Whichever technique you use, every secret passed to a resource or data source ends up in plain text in the state file. Marking a variable sensitive hides it from plan output and logs, not from state. Saved plan files (terraform plan -out=plan.tfplan) contain them too. Flip the protections.

Takeaways

  

    
No plain text, anywhereNot in code, not in Git, not pasted into a CI config file by hand if you can avoid it.

    
ProvidersHumans: env vars from a password manager or aws-vault. Machines: prefer IAM roles or OIDC over long-lived stored keys.

    
ResourcesEnv vars to start; encrypted files when you want secrets versioned with code; a secret store when you need rotation, audit and standardization.

    
State and plansTreat them as secrets themselves: encrypted backend, tight access, careful with plan files.
