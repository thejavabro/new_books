How to Test Terraform Code

Infrastructure code without tests is broken, you just do not know where yet. There is no localhost for a load balancer, so tests deploy real resources, check them and tear them down.

1

Manual testing: there is no localhost

DevOps runs on fear: of downtime, of data loss, of breaches. Automated tests are how you turn fear into confidence. With a Ruby web server you'd test on localhost with curl. With Terraform you can't deploy an ASG or ALB to your laptop, which leads to the chapter's first takeaway.

The equivalent of localhost is a sandbox environment, ideally a whole AWS account per developer so nobody steps on anybody else. You deploy an example with terraform apply and poke it with curl. Sandboxes cost money, so they need cleaning. Drag the days to see clutter build up, then switch on a nightly nuke.

2

Unit tests deploy real infrastructure

In Terraform, the closest thing to a "unit" is a single reusable module, such as alb. But a module is mostly calls to AWS, so you can't test it without AWS: there is no pure unit test (takeaway #3). Instead, a unit test deploys the module's example into a real account, checks it, and tears it down. The book uses Terratest, a Go library. Step through one test.

func TestAlbExample(t *testing.T) {
  opts := &terraform.Options{
    TerraformDir: "../examples/alb",
  }
  defer terraform.Destroy(t, opts)
  terraform.InitAndApply(t, opts)
  url := "http://" +
    terraform.OutputRequired(t, opts, "alb_dns_name")
  http_helper.HttpGetWithRetry(t, url, nil,
    404, "404: page not found", 10, 10*time.Second)
}

Run it with go test -v -timeout 30m: Go's default 10-minute timeout is too short for real infrastructure. Pin the Terratest version too; it's pre-1.0, and the book's examples target v0.39.0.

3

Dependency injection

hello-world-app reads the database address from the MySQL module's remote state. That's an external dependency: a unit test would need a real database first. The fix is the same as in app code, dependency injection. Expose an optional mysql_config input; when set, use it instead of the remote state.

variable "mysql_config" {
  type    = object({ address = string, port = number })
  default = null
}
data "terraform_remote_state" "db" {
  count = var.mysql_config == null ? 1 : 0     # only if not injected
}
locals {
  mysql_config = var.mysql_config == null ? data.terraform_remote_state.db[0].outputs : var.mysql_config
}
4

Running tests in parallel

A suite of 5-minute tests run one after another takes hours. Add t.Parallel() and Go runs them at the same time. But two copies of the same test now try to create resources with identical names. Takeaway #4: namespace everything. Make every name configurable and give each test a unique ID. Also copy the example folder per test (test_structure.CopyTerraformFolderToTemp) so they don't share a .terraform folder or state.

5

Integration tests and test stages

An integration test checks that several modules work together: deploy mysql, deploy hello-world-app pointed at it, check the response contains "Hello, World", tear down. It takes 10 to 15 minutes. While iterating on just the app, redeploying the database every run is pure overhead. Test stages fix this: each stage can be skipped with a SKIP_<stage> environment variable, and stages save state to disk so later runs can pick up. Choose which to skip.

Retries for flaky infrastructureReal clouds have transient failures: an instance that won't launch, an eventual-consistency error, a TLS hiccup talking to S3. Terratest's terraform.Options accepts RetryableTerraformErrors, a map of known error patterns, plus MaxRetries and TimeBetweenRetries, so known-transient errors trigger a retry instead of a red build.
6

End-to-end tests and the test pyramid

The higher up the pyramid, the slower, costlier and more brittle the tests get, so you want many unit tests, fewer integration tests and only a handful of end-to-end tests. Takeaway #5: smaller modules are easier and faster to test. Tap a layer.

7

Static analysis, plan testing, server testing

Apply-and-destroy tests are the gold standard, but three cheaper families catch many problems first. Select a column to compare it with the others, following the book's summary table (more bars is better).

Use a mixEach type has strengths and blind spots, so combine them, weighted toward the bottom of the pyramid. Start with whatever gives the best return, even if that's only static analysis, and build up. Infrastructure code without automated tests is broken; it just hasn't shown you yet.
