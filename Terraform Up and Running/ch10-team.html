How to Use Terraform as a Team

Tools are the easy part. Getting a team to adopt IaC, review it, test it and deploy it the same way every time is the real work, and infrastructure code needs a slightly different workflow from app code.

1

Convincing your boss

A familiar story: a developer discovers Terraform, shows it around full of excitement, and the boss says no. That isn't stupidity. From the boss's side, adopting IaC has real costs. Open each card, then try two different pitches.

2

Work incrementally, for real

Most large software projects fail. The book cites figures showing about 3 out of 4 small IT projects (under $1 million) succeed, while only 1 in 10 large ones (over $10 million) finish on time and on budget, and more than a third are never finished at all. So adopt IaC in pieces, and make sure each piece delivers value on its own. The trap is false incrementalism: small steps that pay off only once the last one ships. Cancel the project at any point and compare.

Give the team time to learnIf people don't know the new tools, the next outage gets fixed by hand in the console. Now the code no longer matches reality, the next apply is scary, more fixes happen by hand, and soon everyone has quietly gone back to ClickOps. Budget real time for docs, training and practice.

      4

      Deployment strategies for apps

      Five copies of v1 are running; ship v2. App deployments can be done in several safe ways, each with its own trade-offs. Pick a strategy and play it.

      Infrastructure changes mostly don't get these luxuries: there's no blue-green deployment for a VPC and no feature toggle for a database. terraform apply either works or it doesn't, and it doesn't roll back. So plan for failure: retry known transient errors, know that a failed state write leaves an errored.tfstate to push back with terraform state push, and use terraform force-unlock if a crashed run leaves a lock behind.

      5

      The Golden Rule of Terraform

      A quick health check: go to your live repo, pick a few folders at random, run terraform plan. If it always says "no changes", great. Small diffs and excuses ("someone tweaked that by hand") mean trouble ahead. The goal is:

      The main branch of the live repository should be a 1:1 representation of what's actually deployed in production.

      That rules out two things. Out-of-band changes: once you use Terraform, all changes go through Terraform. And long-lived branches deployed to shared environments: there's one environment, so there should be one branch. Watch what happens when two branches both apply to staging.

      6

      Deploying infrastructure code safely

      Infrastructure changes should be applied by a CI server, never from a laptop. But applying arbitrary Terraform needs admin permissions, and CI servers are hard to secure, reachable by every developer and built to run arbitrary code. Toggle the book's mitigations and watch the attack surface shrink.

      The rest mirrors app code: run terraform plan on every pull request and show the output in the review (Atlantis does this automatically), tag releases with Git, and promote the same immutable, versioned artifact from dev to stage to prod. Because a failed apply can't be rolled back, test each change in pre-production before production.

      7

      Keeping the live repo DRY with Terragrunt

      With modules, each environment folder still repeats a provider block, a backend block and a module call. Across many regions and accounts that adds up. Terragrunt, a thin open source wrapper, lets the live repo hold only small terragrunt.hcl files: the backend is defined once in a root file and included everywhere, with the state key filled in from the folder path.

      # live/terragrunt.hcl (root, defined once)
remote_state {
  backend = "s3"
  generate = { path = "backend.tf", if_exists = "overwrite" }
  config = {
    bucket = "my-org-terraform-state"
    key    = "${path_relative_to_include()}/terraform.tfstate"
    region = "us-east-2"
    encrypt = true
    dynamodb_table = "terraform-locks"
  }
}
      # live/stage/data-stores/mysql/terragrunt.hcl
terraform {
  source = "github.com/acme/modules//data-stores/mysql?ref=v0.0.7"
}
include {
  path = find_in_parent_folders()
}
inputs = {
  db_name     = "example_stage"
  db_username = "admin"
}
# $ terragrunt apply

      Quick check

      Where the book leaves youWrite the code, test it, review it, package it into versioned, immutable artifacts, and promote them from environment to environment. Do that for both apps and infrastructure, and Terraform becomes a team sport rather than one person's magic.
