How to Manage Terraform State

Terraform remembers what it built in a state file. Once more than one person touches the code, where that file lives, who can lock it and how it is split up decides whether a typo takes down staging or production.

What Terraform state is

Every run, Terraform records what it created in a state file, terraform.tfstate, a JSON map from each resource in your code to the real object in the cloud (an EC2 instance ID, for instance). On the next plan, Terraform refreshes that object from the API and diffs three things: your code, the state, and reality. Try the events below.

3
A remote backend on S3

  
A backend decides where state is loaded from and saved to. Remote backends (Amazon S3, Azure Storage, Google Cloud Storage, Terraform Cloud) fix all three problems: Terraform loads and saves state automatically, most support locking, and most encrypt in transit and at rest. On AWS the book's recipe is an S3 bucket plus a DynamoDB table for locks.

  


resource "aws_s3_bucket" "state" {
  bucket = "my-org-terraform-state"
  lifecycle { prevent_destroy = true }
}
# + bucket versioning (every revision kept)
# + server-side encryption
# + block all public access

resource "aws_dynamodb_table" "locks" {
  name         = "terraform-locks"
  billing_mode = "PAY_PER_REQUEST"
  hash_key     = "LockID"
  attribute { name = "LockID", type = "S" }
}


terraform {
  backend "s3" {
    bucket         = "my-org-terraform-state"
    key            = "global/s3/terraform.tfstate"
    region         = "us-east-2"
    dynamodb_table = "terraform-locks"
    encrypt        = true
  }
}

4
No variables in the backend block

  
The second limitation hurts more: a backend block can't use variables or references, because it is read before anything else. That leads to copy-pasting bucket names and regions into every module, and the key must be unique per module or two modules will overwrite each other's state. The workaround is partial configuration: keep the shared settings in a file and pass it to init.

  


# backend.hcl (shared)
bucket         = "my-org-terraform-state"
region         = "us-east-2"
dynamodb_table = "terraform-locks"
encrypt        = true


# main.tf (only what's unique)
terraform {
  backend "s3" {
    key = "stage/data-stores/mysql/terraform.tfstate"
  }
}
$ terraform init -backend-config=backend.hcl

  

  
Terragrunt, covered in Chapter 10, goes further and fills in the backend settings, including the key, for you.






  
5
Limit the blast radius

  
Put every environment in one configuration and a single mistake in a staging change can break production. As the book puts it, the whole point of separate environments is that they are isolated. Choose a layout, then make a bad change and see how far the damage spreads.

  

    

    

    

    

  

  






  
6
The recommended file layout

  
Full isolation means a separate folder, and therefore separate state, for each environment, and inside each environment a separate folder for each component. You can also give each environment its own backend with its own credentials, or even its own AWS account. Tap any folder or file.

  

    

      

      

    

  

  
The trade-offs: you can no longer bring up a whole environment with one apply (Terragrunt's run-all helps), the layout invites copy-paste (Chapter 4's modules fix that), and resources in different folders can't reference each other directly. That last one has its own fix.






  
7
Reading another component's state

  
The terraform_remote_state data source reads the outputs of another configuration's state file, read-only. The web cluster can learn the database's address and port without anyone copying values around.

  

    

    

  


data "terraform_remote_state" "db" {
  backend = "s3"
  config = {
    bucket = "my-org-terraform-state"
    key    = "stage/data-stores/mysql/terraform.tfstate"
    region = "us-east-2"
  }
}

user_data = templatefile("user-data.sh", {
  db_address = data.terraform_remote_state.db.outputs.address
  db_port    = data.terraform_remote_state.db.outputs.port
})

  
The same example introduces two more ideas. Database passwords should never be hardcoded: mark the variables sensitive and pass them through TF_VAR_db_password (Chapter 6 goes deeper). And long inline Bash belongs in its own file, rendered with the built-in templatefile function. You can try any built-in function in terraform console, a read-only REPL.






  
8
Quick check

  
Why so much fuss?Bugs in app code usually break one feature. Bugs in infrastructure code can take down every app, every database and every server at once. Isolation, locking and careful state handling are how you make those bugs smaller.
