Why and How to Build Agents

A single LLM call cannot check today's weather, do reliable math or update a database. An agentic system breaks the job into steps and hands some of them to tools.

1

What one LLM call cannot do

A model trained on data up to October 2024 cannot know who won the World Chess Championship that began in November 2024. Nor can it reliably do arithmetic, follow a long plan, or change anything in the world. The book defines an agent as software that uses GenAI to automate one step of a multistep application, and calls the whole application agentic. Tap each limitation to see the agentic workaround.

2

Breaking a request into small tasks

An agentic system turns a request such as "I need to make an appointment with Dr. Smith" into small instructions. Some are native GenAI skills (summarize, extract an address); some need grounding in documents (RAG); some call an external system's API and ground the answer in what it returns; some generate code such as SQL that makes lasting changes. If a call fails, the agent can change its input and retry.

3

Copilots: macros you write in plain language

SaaS products now ship agent interfaces, often called copilots. Like macros, they automate tasks; unlike macros, you describe the automation in natural language, not Visual Basic. Salesforce's Agentforce was an early example. Imagine an account rep typing into its Agent Builder: "Find customers with balances over $10,000 unpaid for six months; email each one the amount owed, a payment-plan offer, a link to book a meeting with me, and a survey link."

Once a multiweek engineering project that rarely got built, so companies fell back on hard-coded rules. The promise is that nontechnical users automate their own drudgery. At the time of writing, low-code agent builders were still very limited, which is why the rest of the chapter builds agents in code.

4

Building a weather agent in AutoGen

"Is it raining in Chicago?" cannot be answered from memorized text. The free US National Weather Service API can answer it, but only for a latitude and longitude. So the agent must: (1) coordinate the steps, (2) pull the place name out of the question (an LLM job: "Orca Island" is not just the last word), (3) geocode it with a maps API, (4) call the NWS API, (5) pick the forecast for the right time, and (6) answer. Microsoft's AutoGen treats this as a conversation between a user proxy (which can run code in a sandbox and stops when it sees TERMINATE) and an assistant backed by an LLM.

def geocoder(location: str) -> tuple[float, float]:
    """Finds the latitude and longitude of a place or landmark."""
    ...  # call a maps geocoding API

autogen.register_function(geocoder,
    caller=assistant,      # the LLM may propose calls
    executor=user_proxy,   # the proxy actually runs them
    description="Finds the latitude and longitude of a location")

Each version of the system prompt carries a one-shot worked example ("Kalamazoo, Michigan → step 1… step 2… answer"), extended as tools are added. Setting AutoGen's next-speaker selection to manual puts a human in the loop to choose which agent speaks next.

Conversation or graph?

LangGraph models the same workflow as a graph, the way data pipelines have long been drawn. Nodes share a state of messages; an edge from the assistant is conditional: if the last message asks for a tool, go to the tools node, otherwise end. Tool output always flows back to the assistant.
