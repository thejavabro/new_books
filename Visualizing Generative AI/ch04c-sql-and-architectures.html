Tables need SQL, not chunks. And once you have tools, there are four classic ways to arrange an agent, plus two emerging protocols for wiring agents to tools and to each other.

Tables need SQL, not chunks

Chunking a table into cells destroys meaning: a cell only makes sense with its row and column headers, and questions about tables usually mean counting or summing rows. The fix is old technology. Keep the data in a relational table with a schema and let the model write SQL. A bonus: whatever query runs, its numbers come from the real data, so the result itself is never hallucinated. Watch LangChain's SQL agent answer a question about US baby-name data (name, gender, count, year).

When valid SQL gives the wrong answer

Syntax errors announce themselves. Logic errors do not. Ask for "the most popular male name in the 1950s" and the agent sorts single-year rows, returning the name with the biggest one-year count, not the biggest decade total. Two fixes. Describe the schema: column comments or a clearer name such as num_babies_with_name_in_year. Helpful, but not enough here. Few-shot examples: show correct queries for single years and for year ranges (deliberately not decades) and the agent generalizes to SUM(count) over the 1950s, answering James. Log intermediate queries and user feedback to keep adding examples; when they outgrow the context window, pick the most relevant ones per question with a semantic-similarity selector, which is RAG for examples.

Four agentic design patterns

  
Andrew Ng sorts agent designs into four patterns. Use the static ones (reflection, tool use) whenever you can fix the steps in advance; dynamic planning and multi-agent collaboration are more flexible and less reliable.

  

  






  
4
Model Context Protocol: a USB port for tools

  
In production, every agent needs data and tools, and custom integrations multiply. The Model Context Protocol (MCP) is an open standard for how agents connect to systems outside the LLM: implement it once per system, and every MCP-aware agent can use it. It is transport-agnostic (HTTP, WebSockets, even stdio in-process), and agents can discover new servers without code changes.

Agent-to-agent: from orchestra to potluck

  
Multi-agent systems usually have a central coordinator. Agent-to-agent (A2A) communication decentralizes: agents advertise capabilities in a registry, message each other directly (often over queues or pub/sub), and negotiate terms such as data needed, deadlines and compute cost. MCP lets you cook with everything in your own kitchen; A2A lets friends organize a potluck, each with their own kitchen.

  

    

    

    

  

  
The catchDistributed agent interactions are hard to debug and can behave in emergent, unpredictable ways. As agents get smarter, the hard question shifts from "how do we make agents smart enough?" to "how do we make their collaboration scalable and reliable?"
