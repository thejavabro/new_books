Application Security, Identity, and Compliance

In the cloud, security is a shared job. AWS secures the infrastructure; you secure what you put on it, using identity, detection, network protection and encryption services.

1

The shared responsibility model

AWS is responsible for security of the cloud: facilities, hardware, the global network and the virtualization layer. You are responsible for security in the cloud: your data, identities, configuration and code. The more managed the service, the more AWS takes on. Nothing stops you from creating an unencrypted, public S3 bucket, and that would be your share of the model failing, not AWS's. Choose a service.

2

IAM: users, groups, roles and policies

IAM secures every other service. A user is a person or app with long-term credentials; a group bundles users that need the same permissions (Admins, Developers, Test); a role is an identity anyone trusted can assume to get temporary credentials from STS, with no long-term keys to leak. Permissions come from JSON policies: who (principal) may do what (action) to which resource (ARN), under what conditions. Follow least privilege. And never use the root user day to day.

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:GetObject", "s3:ListBucket"],
    "Resource": [
      "arn:aws:s3:::reports-bucket",
      "arn:aws:s3:::reports-bucket/*"
    ],
    "Condition": {"Bool": {"aws:MultiFactorAuthPresent": "true"}}
  }]
}

An identity-based policy (like this one) attaches to a user, group or role. A resource-based policy attaches to the resource, such as an S3 bucket policy or a KMS key policy, and names the principals allowed. Both use the same grammar and are evaluated together.

Roles over keysAn EC2 instance or Lambda function gets an IAM role, and the SDK fetches rotating temporary credentials automatically. Cross-account access works the same way: assume a role in the other account.
3

How AWS decides: allow or deny?

Every request starts as denied. An explicit Allow is needed to permit it, and any explicit Deny anywhere wins over every Allow. Organization guardrails (SCPs) and permission boundaries don't grant anything; they only cap what other policies can allow. Flip the switches for a developer trying s3:DeleteBucket.

Many accounts: Organizations, Identity Center, Control Tower

Large estates use many AWS accounts to isolate teams, environments and blast radius. AWS Organizations groups them into organizational units (OUs) under one management account, with consolidated billing and service control policies inherited down the tree. Tap an account to see which SCPs apply.

How KMS encrypts your data

KMS keeps master keys inside FIPS 140-2 validated hardware security modules, where they never leave in plain text. To encrypt large data it uses envelope encryption. Step through it.

CloudHSM gives you dedicated single-tenant HSMs under your exclusive control (PKCS#11, JCE, CNG interfaces) when compliance requires it. Certificate Manager issues and renews TLS certificates for free on integrated services. Secrets Manager stores and rotates database passwords and API keys.
