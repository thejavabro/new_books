From one database to many

For decades the answer to "where do we keep data?" was one big relational database. Then the internet, mobile and IoT multiplied the volume, speed and variety of data, and new kinds of database appeared. (Carlo Strozzi coined "NoSQL" in 1998.) The same customer looks very different in each model.

Consistency models: ACID and BASE

  
ACID (atomicity, consistency, isolation, durability) is the relational promise: a transaction happens completely or not at all. Try a transfer and pull the plug halfway.

BASE (basically available, soft state, eventually consistent) is the trade many NoSQL systems make: stay available and fast, and let replicas catch up a moment later. Write a value, then read from a replica straight away.

Two ways to use data: OLTP and OLAP

  
OLTP (online transaction processing) handles many small, fast reads and writes, such as placing an order, usually on normalized tables (third normal form). OLAP (online analytical processing) runs fewer, heavier queries that scan and aggregate history, usually on denormalized or columnar data in a warehouse. Sort these.

Relational on AWS: RDS and Aurora

  
Amazon RDS runs MySQL, PostgreSQL, MariaDB, Oracle and SQL Server for you: provisioning, patching, daily automated backups with point-in-time restore, and EBS-backed storage. Two features look alike but do different jobs. Toggle them, then fail the primary.

DynamoDB: keys and indexes

  
DynamoDB is a serverless key-value and document database with single-digit-millisecond latency at any scale, global tables (multi-Region, multi-active) and on-demand backups. Design starts with the access pattern. Items are found by partition key (and optionally a sort key); anything else needs an index or a slow, costly scan. In-memory: ElastiCache and the cache-aside pattern

  
When single-digit milliseconds is still too slow, keep hot data in memory. With cache-aside, the app asks the cache first and goes to the database only on a miss, then stores the answer with a time-to-live. ElastiCache offers Memcached (simple, multithreaded, no persistence) and Redis (rich data types, replication, persistence, pub/sub; MemoryDB adds full durability).

Why managed, and how to migrate

  

  
To leave a legacy commercial database, the Schema Conversion Tool converts schemas and code (for example Oracle to Aurora PostgreSQL), and the Database Migration Service copies data with continuous replication, so the cut-over needs only a short outage. Move gradually, workload by workload.
