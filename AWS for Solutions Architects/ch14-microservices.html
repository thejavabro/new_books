Microservice Architectures in AWS

Microservices split an application into small, independent pieces. This chapter compares layered and event-driven designs, lists practical rules, and shows how Domain-Driven Design draws the boundaries.

From monolith to microservices

A microservice is a small, independently deployable service built around one business capability, owning its data and talking to others over the network through APIs. Martin Fowler's description includes componentization via services, organization around business capabilities, decentralized data and governance, and design for failure. On AWS a typical setup is API Gateway routing each path to its own Lambda function or container service. Compare: ship a change to Payments, then break it.

2

Layered architecture

Layers separate concerns: each tier does one job, can be secured on its own (only the presentation tier faces the internet) and can be swapped without touching the others. In a microservice world each layer can itself be a separately deployed, separately scaled service. Tap a layer to see typical AWS services.

3

Event-driven architecture

An event is a fact that something happened: an order placed, a stock price changed. Producers emit events without knowing who listens; consumers react. The book describes two models. In event streaming (message queuing), each message is processed by exactly one consumer. In publish/subscribe, every subscriber gets its own copy. Publish a few order events and watch where they land.

Domain-Driven Design

How do you decide where one microservice ends and the next begins? Domain-Driven Design (Eric Evans) models software on the business domain, the subject area the app serves, using a ubiquitous language shared by developers and domain experts. It builds on object-oriented ideas such as encapsulation. Its key strategic tool is the bounded context: a boundary within which a term has one exact meaning. "Customer" means different things in different contexts. Tap a context.
