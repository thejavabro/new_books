Refactoring: A First Example

A 44-line function that prints a bill for a theater company. Before adding an HTML version and new kinds of play, it gets taken apart in tiny, tested steps: first into named functions, then into two phases, then into a polymorphic calculator.

1

The starting point: one function prints the bill

A company of actors performs plays for customers. Each bill charges per performance, based on the kind of play (tragedy or comedy) and the audience size, and awards "volume credits" as a loyalty bonus. The program that prints the bill is a single function of a few dozen lines: a loop over performances, with a switch on play type in the middle, accumulating totals and text as it goes. Play with an invoice to see the rules it implements.

Invoice for BigCo

Statement

Tragedy: $400 base, plus $10 per seat over 30. Comedy: $300 base, plus $100 and $5 per seat over 20, plus $3 per seat. Credits: one per seat over 30, plus a bonus of one per five seats for comedies.

The program works. Is the design worth worrying about? The compiler doesn't care if code is ugly, but people changing it do. Two changes are coming: the users want an HTML statement (try the toggle above: in the original, that means copying the whole function or wrapping every line in a condition), and they want new kinds of play with their own charging and credit rules, which will keep changing. Fowler's rule of thumb:

Make the change easy, then make the easy changeWhen you have to add a feature and the code isn't structured to make it easy, first refactor so that it is, then add the feature. If the code works and never needs to change, leave it alone.
2

First step: a solid, self-checking test suite

Before touching the code, Fowler builds tests: several invoices, each printed and compared with a hand-checked reference string. They report just green or red. Then comes the rhythm that runs through the whole chapter: make a tiny change, compile, test, commit. A failure means only the last small step can be at fault. The simulation shows why step size matters. Each block is a batch of edits between test runs; a red block means a mistake slipped in and has to be found.

Model: 30 edits, each with a 6% chance of a mistake. Finding a mistake costs time proportional to how many edits you have to search. Green = edits that passed, amber = time spent debugging.

3

Decomposing the statement function

The first chunk that stands out is the switch: it works out the charge for one performance. That insight is in Fowler's head, "a notoriously volatile form of storage" as Ward Cunningham puts it, so he moves it into the code by extracting a function named amountFor. Then he renames inside it (a return value is always result; a parameter is named after its type, such as aPerformance) and removes the play temp by computing it on demand. Temps that hold computed values make extraction harder, so they go early.

Next, the volume credits. The total is built up inside the loop that also does everything else, so he takes four tiny steps, each followed by compile-test-commit: Split Loop, Slide Statements to put the declaration next to the loop, Extract Function, and Inline Variable. The same sequence then removes totalAmount.

"But now the loop runs three times!"Fowler's advice: most of the time, ignore it. The effect is usually negligible, programmers are poor judges of where time goes, and well-factored code is much easier to tune if a real hot spot appears. If a refactoring does slow things down, finish refactoring first, then tune.
4

Splitting calculation from formatting

Now the top-level function is seven lines that lay out the text, and all the calculations are small nested functions. To add HTML without copying them, Fowler uses Split Phase: the first phase calculates an intermediate data structure (customer, performances enriched with play, amount and credits, totals); the second phase only renders it. The calculation code moves to its own file, and a new HTML renderer is a few lines that reuse it. The program is now longer (70 lines versus 44), but every part has a clear job. As he puts it, clarity, not brevity, is what keeps software evolvable.

The camping ruleAlways leave the code base healthier than you found it. It will never be perfect, but it should be better.
5

Reorganizing the calculations by type

For the second change, new play types, the conditional logic on type will only grow. Fowler creates a performance calculator class to host the amount and credit functions, gives it a factory that returns a tragedy or comedy subclass, and then applies Replace Conditional with Polymorphism: each leg of the switch moves into its subclass. Adding a new genre now means adding a subclass, and the two kinds of variation (charging and credits) live together per type.
