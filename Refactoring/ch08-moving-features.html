Moving Features

Context matters as much as structure. These refactorings move code to the place where it belongs: between modules, into or out of functions, up and down a sequence, and out of loops.

1

Moving code to where it belongs

The first chapters of the catalog create, remove and rename elements. This one changes their context: which module a function lives in, which record holds a field, whether a statement sits inside a function or at its call sites, and where a statement sits in a sequence. Loops get special attention, because a loop doing two things is hard to move or extract.

2

Move Function and Move Field

Good modularity means you can change something while understanding only a small part of the system. As understanding grows, you find functions that talk more to another module than to their own (Feature Envy, in chapter 3), and fields that are always passed around together with another record. Moving them is how the design catches up with what you have learned. Moving data is usually harder than moving behavior, so encapsulate first.

3

Moving statements into and out of functions

Function boundaries drift. If every caller runs the same line right after a call, that line belongs inside. If one caller now needs different behavior for part of a function, that part moves out to the callers. And when you see inline code that does what an existing function does, call the function.

4

Slide Statements

Related code is easier to read when it sits together. Sliding is often a preparatory step before extracting a function. The one thing to check: a statement cannot slide past another that writes something it reads, reads something it writes, or writes the same thing. Side effects (like I/O) cannot swap order either.

5

Split Loop and Replace Loop with Pipeline

A loop that does two things forces anyone who touches it to understand both. Split it, even though it now runs twice; measure later if you think speed matters, and usually it won't. Once each loop does one thing, it can often become a collection pipeline: a chain of operations like filter and map that reads top to bottom as the steps of the job.

A pipeline, one stage at a time

6

Remove Dead Code

Unused code costs nothing at run time but plenty in understanding: readers wonder why it is there and are afraid to touch it. Version control remembers it, so delete it. Commented-out code is no better; it was a habit from before version control was common.
