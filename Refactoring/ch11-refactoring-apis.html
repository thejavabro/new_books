Refactoring APIs

Functions are the joints of a program. These ten refactorings make interfaces easier to understand and use: separate reads from writes, tune parameter lists, and choose between functions and command objects.

1

Functions are the joints

Modules and functions are the building blocks; their interfaces are the joints. Good joints are easy to understand and hard to misuse. This chapter covers separating reads from writes, making parameter lists say just what varies, controlling mutation, and two ways to package a computation: a plain function or a command object.

2

Separate Query from Modifier

A function that returns a value and has no observable side effects can be called anywhere, any number of times, moved freely and tested easily. So keep that kind of function distinct from ones that change things. The rule of thumb, known as command-query separation: any function that returns a value should not have observable side effects. (Caching a value internally is fine; nobody can observe it.)

Shaping parameter lists

A parameter list should summarize what varies about a function. Four refactorings tune it: merge near-duplicates by adding a parameter, split a function that branches on a flag, pass a whole record instead of values pulled out of it, and move a value between being a parameter and being looked up inside.

4

Parameter or query? Who does the work

Replace Parameter with Query and its inverse shift a responsibility between caller and function. Passing a value the function could find itself is duplication. But a function that reaches into a global or an awkward dependency loses referential transparency: given the same arguments, it no longer always gives the same answer, which makes it harder to test and to reason about. Pick the side that keeps the function honest.

5

Setters and constructors

A setting method announces that a field may change. If it should not, remove the setter and set the value in the constructor. Constructors themselves have awkward limits in many languages: fixed name, must return a new instance of exactly that class, need a special operator. A factory function has none of those limits.

6

Function or command object?

A command is an object built around one method: you create it, then execute it. Because it is an object it can hold state across sub-steps, support undo, be built up in stages, or be customized through inheritance. That flexibility costs complexity, so Fowler reaches for a command only when a plain function cannot do the job, and turns it back into a function once it no longer needs to be an object.
