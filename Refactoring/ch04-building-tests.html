Why self-testing code comes first

Fowler noticed that most of his programming time went not into writing code but into debugging it: finding what broke. The fix that changed his habits was making every class carry its own tests, run often, that check themselves and report only pass or fail. A suite like that is a powerful bug detector: a failure points straight at what you just changed. That is also exactly what refactoring needs, because every small step is followed by "run the tests".

3

Will a test catch it?

A test suite earns trust by failing when something is wrong. Fowler's habit when he writes a test: briefly break the code on purpose to see the test fail, so he knows it is really checking something. Plant a bug below and see which tests notice. Some bugs are caught only by tests at the boundaries: no producers, zero or negative demand.

Probing the boundariesHappy-path tests check normal use. Boundary tests ask: what if the collection is empty? What if a number is zero or negative? What if the input field is blank? The chapter discovers that a blank demand makes shortfall and profit come out as NaN, and asks whether that is acceptable. A good test can raise a question as well as answer one.
4

Fresh fixture for every test

It is tempting to build the sample province once and share it between tests. Don't: the moment one test changes it, other tests start depending on run order, and failures become intermittent and baffling. Build a fresh fixture for each test (in Mocha, a beforeEach block). Toggle the setup and reorder the tests.

Run them oftenEvery few minutes when programming; at least daily for the whole suite.
Bug report? Test firstWrite a test that exposes the bug before fixing it.
Aim at riskTest where things could go wrong, not every accessor. Imperfect tests that run beat perfect ones never written.
Coverage is a hintIt shows untested code, not how good the tests are. The real measure: are you confident a change that breaks something will be caught?

Chapter 5: how a catalog entry is built

The rest of the book is a catalog that started as Fowler's own notes. Every entry follows the same five-part format, which is also the format of the cards on the catalog pages of this companion. Tap a part.

The catalog is not complete. Fowler chose refactorings he felt were worth writing up; some that are too simple, or too rarely useful, were left out, and others live on his website. The mechanics he gives are the safe, small-step version. With practice you will take bigger steps, and drop back to smaller ones when something breaks.
