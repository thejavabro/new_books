What refactoring means, precisely

As a noun, a refactoring is a change to the internal structure of software that makes it easier to understand and cheaper to modify, without changing its observable behavior. As a verb, to refactor is to restructure software by applying a series of those small changes. The key word is small: each step keeps the code working, so you can stop at any moment. If someone says their code was "broken for a couple of days while refactoring", they were not refactoring. "Restructuring" is the general term; refactoring is one disciplined kind of it.

"Observable behavior" is deliberately loose. The call stack may differ and interfaces may change, but nothing a user cares about should. Performance optimization is similar in mechanics but different in purpose: it aims for speed and may make code harder to work with.

The two hats

Kent Beck's metaphor: when developing, you wear one of two hats and swap them often, sometimes every few minutes. You should always know which one you have on, because each comes with its own rules.

Adding function

  • Add new capabilities
  • Don't change existing structure
  • Measure progress by adding tests and making them pass

Refactoring

  • Restructure, don't add behavior
  • Don't add tests (unless you find a case you missed)
  • Change tests only when an interface changes

3

Why refactor? Because it makes you faster

Refactoring improves the design (without it, code decays as people make short-term changes), makes software easier to understand (for the next programmer, often yourself), helps find bugs (clarifying the structure exposes assumptions), and so helps you program faster. That last claim sounds backwards, so Fowler draws it as a pseudograph, the Design Stamina Hypothesis: teams with poor internal quality start fast and slow down; good internal design lets you keep adding features quickly. He calls it a hypothesis because it can't be proven, but it matches his experience and that of many others.

An illustrative curve, not measured data. Fowler's experience is that the lines cross within weeks, not months.

When should you refactor?

Fowler refactors every hour he programs. The guideline from Don Roberts is the rule of three: the first time you do something, just do it; the second time, wince at the duplication but do it anyway; the third time, refactor. More generally, refactoring fits into the work in several ways. Tap each.

Architecture, Yagni and the wider process

Refactoring changes how architecture is done. Instead of trying to predict every future need up front, and adding flexibility mechanisms (parameters, hooks) that often turn out wrong, you build the simplest thing that works for today's needs and refactor as understanding grows. That is Yagni ("you aren't going to need it"). It is not the end of architectural thinking: some things are expensive to change later, and are still worth thinking about early. But with refactoring, far fewer decisions are irreversible.

Refactoring came out of Extreme Programming, where it is one of a set of practices that support each other. Three form a core: self-testing code makes refactoring safe, continuous integration keeps everyone's refactorings from colliding, and refactoring keeps the code easy to change, which makes the other two practical.

7

Refactoring and performance

Refactoring can make code slower. But it also makes it easier to tune. Fowler describes three approaches to fast software: time budgeting (for hard real-time systems), constant attention (every programmer optimizes everything, all the time, which mostly makes code harder to work with), and the one he prefers: build well-factored code, then measure with a profiler and tune the few hot spots, because most programs spend most of their time in a small fraction of the code. Where it came from, and why tools help

The ideas grew in the Smalltalk community in the 1980s, especially with Ward Cunningham and Kent Beck. Bill Opdyke wrote a PhD thesis on refactoring at the University of Illinois, and John Brant and Don Roberts built the first automated tool, the Smalltalk Refactoring Browser. Today most IDEs automate common refactorings. They work on the code's syntax tree, not its text, which is why an automated rename is reliable where search-and-replace is not.
