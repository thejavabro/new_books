Deciding what to hide

The most important question in modular design is what each module keeps secret. Encapsulation means other code needs to know less, so when something changes, fewer places need to be told. Chapter 7 gathers the refactorings that put data behind walls (records, collections, primitives), turn temporary variables into reusable queries, and move the walls themselves (classes and delegates).

2

Records and collections

A plain record is convenient, but it forces you to expose what is stored versus what is computed. A class can hide that: callers ask for a value and do not care which kind it is. Collections are the classic trap. You wrap a list in a getter and feel safe, but the getter hands out the list itself, and anyone can change it without the owner knowing.

Primitives and temps

Simple data rarely stays simple. A phone number starts as a string, then needs formatting, then area codes. A priority starts as a string, then needs comparing. Giving it its own small class creates a home for that behavior. Likewise, a temporary variable that holds a computed value is only usable inside one function; turning it into a query (a function or getter) makes the value available to everyone and removes a local name that blocks extraction.

4

Extract Class and Inline Class

Classes grow a field here, a method there, until one class carries two jobs. Signs: a subset of data and methods that change together, or data that depend on each other. Ask "what if I removed this piece of data, would the others still make sense?" When an extracted class ends up with too little to do, fold it back in.

Hide Delegate and Remove Middle Man

If a client calls person.department.manager, it knows about departments: change how departments work and the client may break. Hiding the delegate behind person.manager cuts that link. But each feature you hide needs a forwarding method, and if most of a class becomes forwarding, it is a middle man. There is no fixed answer; adjust as the code changes.

6

Substitute Algorithm

Sometimes the way to simplify is not to rearrange the existing code but to replace it with a clearer method, perhaps a library function. Decompose first so the piece you swap is small, and make sure the tests cover it, because this one is a rewrite: you compare old and new results to be sure they agree.
