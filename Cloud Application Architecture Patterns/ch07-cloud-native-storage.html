Cloud-Native Storage: Data Placement

Stateless applications push their state into databases, so the databases have to be as scalable and reliable as the cloud itself. The first half of the chapter covers how data is hosted and owned.

If the app is stateless, where does the state go?

Chapter 3 asked applications to be stateless and replicable. Most applications still have state, so it moves to databases, and those databases now have to be as available, scalable and quick to provision as the applications themselves. The chapter asks three questions: how to represent the data when each microservice manages its own; how the database helps meet availability, redundancy and consistency goals for a replicated app; and how to host and manage all those databases. This page covers hosting and quality of service; the next page covers choosing database types.

How database topologies evolved

To see why cloud databases look the way they do, the authors walk through five topologies. Each fixes a weakness of the one before. Pick one, then click a server to fail it.

3

CAP: what gives when the network splits

Once data is copied across machines, the CAP theorem applies: when a network partition separates the copies, a database must choose between staying consistent (refuse some requests) and staying available (answer, possibly with stale data). The book groups databases as CA (classic relational, synchronous replication), AP (CouchDB, Cassandra, ScyllaDB: eventual or tunable consistency) and CP (MongoDB, Redis: consistent, may refuse during a split). Most products let you tune this, so choose the database type by data shape first, then its topology and settings. Cut the network and try it.

4

Root pattern: Cloud Database

ProblemHow should a cloud-native application store data persistently in a cloud environment?
SolutionPersist it in a Cloud Database: one that scales horizontally the way cloud applications do and gives the application flexibility in how it stores and accesses data.

Traditional enterprise databases were designed around assumptions that made sense on one big, expensive box. Flip between the two to see how each concern is handled.

Cloud Databases come in two broad categories, each its own pattern below: Configuration Databases for small, critical, shared platform state and Application Databases for an application's domain data. Every major cloud offers both, from etcd under Kubernetes to managed document, key-value, graph and relational services.

5

Replicated Database

ProblemHow can a Cloud Database give the same availability, scalability and performance as the cloud-native application using it?
SolutionUse a Replicated Database: many active server processes, each with its own storage, holding several copies of the same data and applying updates consistently across them.

Data is split into partitions (shards) and each partition is stored on several nodes. Any node can serve requests for the partitions it holds, so throughput grows with the cluster, and losing a node loses no data as long as another copy survives. MongoDB, Redis Cluster and Apache CouchDB work this way. Set the replication factor and start failing nodes.

Click nodes to fail or restore them.

6

Configuration Database

ProblemHow can a cloud service store its service state so that every node of the service can share and access it?
SolutionStore it in a Configuration Database: a replicated database that is reliably consistent and notifies all nodes whenever data changes.

Think etcd (the brain of Kubernetes), Apache ZooKeeper and HashiCorp Consul. They do what other replicated databases avoid: every write is a coordinated transaction that is not complete until a majority of nodes have it, so every read anywhere sees the latest value, and clients can watch keys for changes. The trade-offs: in a partition they become read-only or unavailable rather than inconsistent, and they are built for small amounts of data such as configuration, leader election and service discovery, not for your orders table.

Click nodes to fail them.

7

Application Database

ProblemHow should a cloud-native application store its data so it can run as a stateless application?
SolutionUse an Application Database that, like the application, is highly available, holds large amounts of data, scales to many concurrent users and makes data access simple.

Application databases tend to be replicated and come in three families. Tap each.

Within those families sit the five database types the book treats as patterns of their own: relational, document, key-value, graph and columnar. They are explored on the next page.

8

Database-as-a-Service

ProblemHow does an application get access to an Application Database?
SolutionCreate it with a Database-as-a-Service: a cloud service that does most of the work of installing and managing the database.

A DBaaS can be built into the platform (RDS, Cosmos DB, Bigtable, Cloudant), installed from a marketplace as a Kubernetes operator, or hosted remotely by the vendor. Each DBaaS serves one product, so an app using PostgreSQL and MongoDB uses two. Developers rarely have DBA skills, so the book suggests a shared team of DBAs who no longer spend time installing and patching and can focus on tuning: normalization and indexes, document granularity, partitioning policies.
