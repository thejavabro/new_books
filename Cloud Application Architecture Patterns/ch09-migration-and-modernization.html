Application Migration and Modernization

Most cloud apps start life as traditional ones. You can move them as-is, repackage them, or rework them, and the organization has to change along with the code.

1

Build new, or modernize what you have?

Cloud applications are often not born; they are migrated. The first question is whether you have an existing application that fits today's requirements, and how much technical debt it carries. Answer the two questions.

Are the user requirements novel, or well established?
How much technical debt does the existing app have?
Debt travelsMoving an application to the cloud as-is does not fix its technical debt; the debt moves with it. To really benefit from the cloud, the debt still has to be repaid, sometimes by rewriting much of the code.
2

The six Rs of cloud migration

Gartner's five Rs (2010) were reshaped by Stephen Orban in 2016 into six strategies. Only three of them actually move and improve an application in the cloud: rehost, replatform and refactor. Tap each.

3

Platform, architecture, packaging

The book describes any application along three independent aspects. Migration moves the platform (traditional IT → cloud); modernization improves the architecture (mud → modules → distributed) or the packaging (bare metal → virtual server → container). Each pattern in this chapter changes a different combination. Pick a pattern to see which cells it moves.

4

Lift and Shift

ProblemWhat is the simplest possible way to move an existing application to the cloud?
SolutionCreate cloud servers that match the machines the app runs on today, and reinstall it there.

This is rehosting, the first R. Nothing about the app improves, but it often costs less to run than private data-center capacity, gets the team experience with the cloud, and makes later rearchitecting easier because the app is already there. Many teams also swap in a managed database at this point (replatforming). What it cannot do is make the app elastic, resilient or cheap to scale: a monolith built for one big box stays one big box.

5

Virtualize the Application, Containerize the Application

Virtualize: problemWhat is the simplest way to package an app so it deploys easily to traditional IT or the cloud?
SolutionPackage it as a virtual server image that runs on a hypervisor, which can be in the cloud.
Containerize: problemHow can an app be packaged for greater deployment density and platform portability?
SolutionPackage it as a container image, run by a container engine under an orchestrator in the cloud.

In both cases the application itself does not change; only how it is installed. Virtual servers have three drawbacks: they run for a long time and get patched in place, which causes drift (patching is an anti-pattern under twelve-factor's build-release-run); images are proprietary and hard to move between hypervisors; and each carries a full operating system's overhead. Containers share the host kernel and are built from a base image that holds the OS layer and middleware. Fill a host and compare.

# illustrative container recipe
FROM eclipse-temurin:21-jre      # base image: OS layer + runtime
COPY build/quote-service.jar /app/
ENV  LOG_LEVEL=info               # defaults; real values injected per environment
CMD  ["java", "-jar", "/app/quote-service.jar"]
6

Refactor the Monolith

ProblemHow can I make an existing app easier for several teams to maintain, and able to run well across many computers?
SolutionRefactor it from an unstructured blob into modules that can run distributed across computers.

Refactoring is a behaviour-preserving transformation, though it always involves some rewriting. The book frames it as a short series of decisions. Walk through them for your app.

1. Can the existing code be kept at all?An unsupported language or framework, or no one left who knows it, may force a full rewrite. Rewrites are expensive and slow.
2. Do parts of the app have different scaling needs?If everything scales together, a modular monolith may be enough, at least at first.

The book's airline example and published case studies follow the same arc: lift and shift first to learn the platform, adopt cloud databases and backend services, then refactor step by step.

7

Start Small

ProblemHow do we begin adopting the cloud, moving apps or writing new ones, when only a few developers have the skills and drive?
SolutionTake baby steps: deploy one small new function, or rehost or refactor one small existing app, and learn from it.

A small first success builds skills and confidence and shows everyone else that it can be done. A big-bang programme that tries to move everything at once multiplies the unknowns. Pick a first project.

8

Pave the Road

ProblemHow do we get teams onto the cloud without each one going its own way and repeating the same mistakes?
SolutionCreate shared platforms, environments and building blocks that make the basic tasks of building or migrating cloud apps easy.

Usually the work of one or more platform teams (in the Team Topologies sense): a working DevOps pipeline, a containerized environment with a sample app deployed, templates and examples, standard practices, documentation. The book's examples include a financial system and IBM's common CI/CD pipeline for its internal teams.
