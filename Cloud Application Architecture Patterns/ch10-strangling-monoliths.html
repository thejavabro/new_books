Strangling Monoliths

Rewriting a running system in one big bang is a gamble. Strangling it lets new microservices grow around the old monolith until it can be switched off, one slice at a time.

1

Why strangle instead of rewrite?

A big-bang rewrite of a running system is a gamble: years without new value, a moving target, and a single risky cut-over. Martin Fowler named the alternative after the strangler fig, a vine that grows around a tree until it can stand on its own. New microservices grow around the monolith, a routing layer sends more and more traffic their way, and one day the old core can be switched off. Drag the timeline.

2

Root pattern: Strangle the Monolith

ProblemHow can we replace a monolithic architecture with microservices while reducing overall risk?
SolutionGradually replace the monolith by iteratively moving existing functionality into microservices and building every new feature as a microservice, deployed independently. Repeat until the monolith is gone, or small enough to leave.

A supporting pattern, Wrap the Monolith, puts a facade (or proxy) between existing clients and the monolith. At first it passes everything through untouched; as pieces move to microservices it converts old clients' protocols into the new services' APIs, so old clients never have to change. The book cites Uber, Netflix, Amazon and PagSeguro (from a talk at Agile Brazil) as organizations that strangled their way off monoliths. The rest of the chapter is the toolkit, starting with stopping the bleeding.

New Features as MicroservicesProblem: while strangling, how do you avoid adding functionality to the monolith that will just have to be modernized later? Solution: make it a rule that every new feature is built as a microservice, called from the monolith or the router if needed. The monolith stops growing on day one.
3

Transform Monolith into Microservices: find the Hairline Cracks

Transform: problemHow do you keep the monolith working while you substitute pieces of it with microservices over time?
SolutionIteratively find places to split it, then extract, refactor or replace those pieces as domain-modeled components.
Hairline Cracks: problemHow do you identify candidate microservice boundaries inside a monolith?
SolutionLook for hairline cracks: places where the monolith will break apart most easily.

The easiest cracks, in order: existing REST or asynchronous services already inside the monolith; older distributed services such as CORBA, SOAP or EJB, which already have an interface; and simple web interfaces with a thin slice behind them. Tools such as IBM's Mono2Micro analyse runtime traces to suggest partitions. Tap the components of this ecommerce monolith to inspect them, then decide which one to pull out first.

4

Three ways to get a piece out

Once you have picked a piece, the book offers three moves, in rising order of effort. Choose the situation to see which one fits.

Macro ServiceIf the piece that comes out is still big and entangled inside, extract it as a larger Macro Service first and split it into proper microservices once you have learned more. It is easier to split a big service later than to merge small ones.
5

Monolith to Microservice Proxy

ProblemHow can code still inside the monolith use functionality that has moved to a microservice?
SolutionKeep the old component in the monolith but rewrite its insides as a proxy that forwards calls to the new microservice.

Callers inside the monolith keep calling the same interface and do not change at all. Only the implementation behind it becomes a remote call. The book's examples include a payment system and a major retailer.

// before: logic lives in the monolith
class PaymentService {
  Receipt charge(Order o) {
    // 900 lines of card handling...
  }
}
// after: same interface, now a proxy
class PaymentService {
  Receipt charge(Order o) {
    return http.post("https://payments/v1/charges",
                     toJson(o), Receipt.class);
  }
}
6

Playback Testing

ProblemHow do you make sure the new microservices behave like the old monolith, when nobody fully remembers what the old system does end to end?
SolutionCapture real inputs and actions on the old system, replay them against the new one, and compare the results.

The old system becomes the specification. The book's examples are an invoicing system and a US financial institution. Replay a day's captured invoices against the new Invoicing microservice.

The book in one page

The book's conclusion frames the whole pattern language as a set of decisions. There is no single right cloud architecture; there are choices that make an application work better or worse in the cloud. Tap a decision to recall the answer and the chapter to revisit.

And what comes next, beyond the book's scope: application deployment (package, register and configure the platform), build automation (CI/CD so deployment is one reliable command), and continuous delivery (release each approved improvement as soon as it is ready, so users and the business benefit right away). As the authors close: welcome to the cloud, you may as well get comfortable.
