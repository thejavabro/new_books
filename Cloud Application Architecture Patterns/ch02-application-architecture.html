Application Architecture

Before the cloud, there were three basic ways to shape an application. Knowing them, and when each is the right trade-off, sets up everything that follows.

Every architecture is a set of trade-offs

Architecture is the art of balancing competing drivers: performance, availability, security, maintainability, time to market, the skills of the team. Two trade-offs show up on day one of almost every project. Do you build fast now and clean up later, or think hard and try to get it right first time? And how much technical debt, the future cost of keeping today's shortcuts working, are you willing to take on?

2

Module, service, program, workload, application

The book uses five words precisely, and the rest of it leans on them. They nest inside one another. Tap each layer.

An architecture is then a strategy for decomposing functionality into modules and services that collaborate. One application can mix several: a cloud-native core, some microservices and an event-driven corner. Architectures are independent of programming language, though some languages make some architectures easier.

3

Mud, modules, processes

Most applications follow one of three basic shapes, and over their lifetime they tend to evolve along this line, like bicycles evolving from the hobby horse to the modern frame. The same ten pieces of code, three ways.

Evolution is not automaticMoving right is not always an improvement: a distributed architecture is genuinely harder to build, and a modular monolith is often the right answer. And without continued investment, even a well-modularized or distributed system decays back into mud. The authors have seen plenty of distributed balls of mud.
4

Big Ball of Mud: the lack-of-architecture architecture

ProblemWhat is the simplest architecture that gets something working quickly, so you can get the feedback you need?
SolutionFocus on features before architecture. Build the system by any means available: simple, expedient, disposable code that solves just the problem at hand.

The book is honest that this is the most common architecture in the world, and sometimes the right one. A minimum viable product is almost guaranteed to be a little muddy, because only success earns you a second release. The trap is the loop of "just enough" that follows, where debt piles up release after release. The telltale sign is that everything talks to everything, with circular dependencies.

Modular Monolith: one executable, real boundaries

ProblemHow can I architect my application to make it easier to maintain and evolve quickly?
SolutionBuild a single executable composed of separate, encapsulated modules with limited dependencies between them.

A module does one thing: high cohesion inside, loose coupling outside, the idea Larry Constantine described in the 1970s and that objects and APIs later formalized. Interfaces limit how far a change can travel, so small teams can work on different modules without stepping on each other. Yet it is still one codebase, one build, one process: easy to run, test, debug and secure, and calls between modules are cheap in-memory calls.

Real-world examples the book cites: Java's module system, the Eclipse IDE's plug-in architecture and Firefox's component model, each a single program with enforced internal boundaries.

6

Distributed Architecture: each module its own process

ProblemHow can I architect my application so that parts of it can be developed, deployed and run independently?
SolutionMake a composite application: a collection of modules, each designed to run separately in its own process and invoked remotely through an API.

The usual path is to take a modular monolith and give each module a remote API (REST, gRPC or messaging) and its own runtime. The count of components does not change; what changes is that each can be deployed, scaled and can fail on its own. Even on one multicore machine, separate processes use cores better and limit the blast radius of memory bugs. Crash a component below and compare.

You gainIndependent development and deployment; scaling only the bottleneck; failure isolation; better use of multicore CPUs; freedom to put parts on different machines.
You payNetwork latency and serialization (so keep APIs coarse-grained); concurrency and partial failure; harder security, logging, debugging and testing; and above all data: a shared database becomes a bottleneck, while split databases need synchronization and bring eventual consistency.
