1

Meet users where they are

Cloud applications run in the cloud; their users do not. The same person may use a phone on the bus, a laptop at work and a script at night. An architecture that supports many modes of interaction must keep the business logic in one place and treat each kind of user interface as an adapter around it, the idea behind Alistair Cockburn's Ports and Adapters (hexagonal) architecture. Tap an adapter.

Four principles run through the chapter: separate presentation logic from business logic; give users a consistent view of the application however they reach it; meet users where they are, in the form that suits each interaction; and let one team own an end-to-end business process, front end and back end together.

2

Root pattern: Client Application

ProblemHow can an end user take advantage of the services of an application running in the cloud?
SolutionDevelop a Client Application that implements a user interface, runs on the user's own computer or device, and connects to the cloud application over a network.

Client/server solved this long ago; the cloud adds many more kinds of client. The patterns in this chapter form a small family tree. Tap a node.

3

Browser Application

ProblemWhat is the easiest, most universal client for any user, with no assumptions about their hardware or software?
SolutionA Browser Application that runs in any HTML web browser.

The name is slightly misleading: in its simplest form nothing runs in the browser at all; it is a dynamic website the browser merely displays. How much runs where has swung back and forth over thirty years. Step through it.

4

Web Form Application versus Single-Page Application

Web Form: problemHow do you give basic functionality to the widest range of users and devices?
SolutionServe HTML pages from the server and take input through HTML forms (GET to fetch, POST to submit).
SPA: problemHow do you get the best mix of client responsiveness and server efficiency?
SolutionKeep all interaction inside one logical page, with a JavaScript program in the browser calling JSON APIs.

Web forms remain the right default for small, simple or rarely used apps and for users on weak hardware. SPAs bring speed after the first load, a richer experience, decoupling of front and back end, and local state, at the cost of complexity, a slower initial load, broken back-button and history unless handled, and new security pitfalls. Add three items to a cart both ways.

5

Micro Frontend

ProblemHow do you avoid a monolithic single-page app that gathers too much functionality in one shared front end?
SolutionSplit the SPA into several Micro Frontends aligned to business features, each its own small SPA loaded into a region of the page.

Microservices on the back end and one giant SPA on the front end recreate the monolith one layer up. With micro frontends, the team that owns a business capability owns its slice of the page too, giving smaller deployables and independent releases. The risks are added complexity and an inconsistent look unless teams share a design system. Ship a change from the Reviews team.

6

Mobile Application

ProblemHow do you give the best experience on a mobile device and use what makes mobile computing unique?
SolutionBuild a native Mobile Application with the platform's own tools.

Phones differ from browsers on a desk: small, varied screens; touch and voice input; sensors such as GPS and camera; fast-moving platforms; unreliable networks, which make local caching essential; and a coveted spot on the home screen. Native apps gain a specialized UI, app-store discoverability and some lock-in, and cost more effort, duplicated work across iOS and Android, and specialized skills. Go offline and keep using the app.

7

Command-Line Interface

ProblemHow can a user automate bulk loads, bulk changes or scheduled jobs against a cloud application?
SolutionBuild a CLI that invokes the application's APIs from a shell.

Command lines go back to Multics, and every hyperscaler ships one today. Their strengths: simplicity, low resource use, easy testing and, above all, composition: pipe one command into another and schedule the lot. Their weaknesses: installation, user-friendliness and discoverability. Try it; type help.

8

Public API

ProblemHow do you best let third-party applications interact programmatically with a cloud application?
SolutionBuild a separate service with an externally facing Public API for third parties.

A public API opens new business opportunities and an ecosystem of developers who will use it in ways you never imagined, sometimes so much that unplanned uses dominate. Do not do it lightly. Versioning: publish the version (URL or header) and decide how many versions you can afford to run at once. Security: authentication, injection attacks, rate limits. Play the API provider.

9

Interaction Model

ProblemHow do you avoid mixing business and presentation logic inside your client?
SolutionEncapsulate the client's interactions with the cloud application, and the state of the user interaction, in an Interaction Model.

It is the mirror image of a Dispatcher: the dispatcher keeps the back end from knowing about screens; the interaction model keeps the screens from knowing about services. You gain testability, a clean model–view split and independence from front-end frameworks that come and go, for some extra code to maintain.

// tangled: view code calls services
button.onclick = async () => {
  const r = await fetch("/api/fares?from=" + from.value);
  const f = await r.json();
  if (f.total > 500 && user.tier !== "gold")
    warn.style.display = "block";
  price.textContent = "$" + f.total;
};
// interaction model: no DOM, easy to test
class FareSearch {
  constructor(api) { this.api = api; this.state = {}; }
  async search(from, user) {
    const f = await this.api.fares(from);
    this.state = { total: f.total,
      needsApproval: f.total > 500 && user.tier !== "gold" };
    return this.state;
  }
}
// the view only renders model.state
