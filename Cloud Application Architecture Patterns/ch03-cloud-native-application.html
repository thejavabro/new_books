Cloud-Native Application

A cloud-native application keeps its own custom logic small and portable, and leans on the platform for everything reusable. Six patterns describe how.

What the industry means by cloud

The chapter opens with the NIST vocabulary. Five essential characteristics make something a cloud: on-demand self-service, broad network access, resource pooling, rapid elasticity and measured service (you pay for what you use). Clouds are then offered as one of three service models, which differ in how much of the stack you still manage yourself.

And four deployment models: private (one organization), community (a group with shared concerns), public (anyone), and hybrid (a mix, bound together so apps can move between them).

Cloud native is more than code

"Cloud native" means designed to work the way the cloud works, rather than merely running there. The authors stress that the architecture is only one dimension. The CNCF Cloud Native Maturity Model looks at five; an organization that modernizes only its technology stalls on the others. Tap each.

The Twelve-Factor App, mapped to patterns

Heroku's Twelve-Factor App is the best-known checklist for cloud-native apps, and many of this chapter's patterns are its factors written up as patterns. Tap a factor to see which pattern in this book carries it.

4

Root pattern: Cloud-Native Architecture

ProblemHow can I architect an application to take maximum advantage of the cloud platform it will run on?
SolutionImplement the custom domain logic in an application kept separate from the reusable services it uses from the platform's catalog.

Your team writes only what is specific to your business. Databases, messaging, identity and the like come ready-made, managed by the platform: you buy rather than build, and outsource running them. Because the app no longer needs middleware installed next to it, it is small, runs on a plain server and can move around independently of its services. The remaining patterns in the chapter each supply one of the qualities the cloud needs. Tap a part of the drawing.

The costsNew skills for developers used to application servers. Less deployment simplicity: you bind to and authenticate against remote services instead of calling built-ins. Cost that creeps, because every VM and service is metered. And less fine-grained control over hypervisors, operating systems and database tuning.
5

Application Package

ProblemWhat features of a language ecosystem are needed to implement a Cloud Application?
SolutionUse a language and toolset that bundles the program with every dependency it needs to run into one Application Package.

The ecosystem needs two things: a runtime environment that runs the program the same way anywhere, and a package manager that pulls in exactly the declared library versions. Java (with a lightweight server such as Open Liberty), Node.js and Go all qualify. Build the package once; it then becomes the unit you virtualize or containerize.

// a made-up manifest, Node-style
{
  "name": "quote-service",
  "version": "2.4.1",
  "main": "server.js",
  "engines": { "node": "20.x" },
  "dependencies": {
    "http-router": "^3.2.0",
    "db-client":   "^7.1.4"
  }
}

Service API

ProblemHow should an application expose its functionality to clients that want to use it?
SolutionExpose a Service API: a set of tasks the application can perform, implemented as a web service.

The API is a contract. Consumers depend on the tasks it promises; the provider can change everything behind it as long as the contract holds. The book builds the solution up through four forces, each solved by an idea from before the cloud. Step through them.

// the task, as a language interface
interface PriceConverter {
  Money convert(Money amount, String toCurrency);
}
# the same task as a web service
GET /convert?amount=25.00&from=EUR&to=USD
200 OK
{ "amount": "27.10", "currency": "USD" }

The book's examples express the same task as a Java interface, a JAX-RS resource, a Go interface and an OpenAPI document: the contract stays the same while the technology changes.

Stateless Application

ProblemHow can an application handle concurrent requests efficiently and recover from failures without losing data?
SolutionKeep domain state in databases and have each client hold its own session state, passed in as request parameters.

Stateless does not mean no state; it means the state lives somewhere else. Within one request the app may cache freely, but between requests it forgets everything. That wins five things: better performance (no cache to fill), scalability (no duplicated data in memory), consistency (nothing to drift from the database), graceful shutdown (always ready between transactions) and recoverability (a crash loses only in-flight work). Try it.

8

Replicable Application

ProblemHow can an application run reliably on an unreliable platform and scale the way the platform scales?
SolutionDesign it to run as many redundant replicas that all provide the same function without interfering with one another.

Vertical scaling hits a maximum size and leaves a single point of failure. A replicable app lets the platform's deployer stamp out new instances from the Application Package and a load balancer spread requests over them, as Kubernetes ReplicaSets, VM auto-scaling groups and serverless functions all do. Being stateless is a prerequisite. So is avoiding Singletons: each replica would get its own copy, which defeats the point, and sharing one across replicas is fragile. Drive the load and watch an autoscaler respond.

External Configuration

ProblemHow can I build my application once and deploy it to differently configured environments?
SolutionKeep settings outside the code, typically in environment variables, so they change without rebuilding.

The same package goes from dev to test to production; only the values injected around it change. Platforms provide this as container environment variables, Kubernetes ConfigMaps for ordinary settings and Secrets for credentials. Note that a Kubernetes Secret is merely base64-encoded, not encrypted, so sensitive values belong in a secrets manager that encrypts them.

Backend Service

ProblemHow can multiple applications share the same reusable functionality?
SolutionConnect to it remotely as a Backend Service: stateful if need be, reused by many apps, and managed by the cloud platform.

The obvious answer, a shared library, falls short in six ways. Toggle to compare.

The book separates application services, which provide domain-facing functions such as databases and integration, from platform services, such as security and observability, which every app needs whether it knows it or not.
