From orchestration to events

The chapter opens with onboarding a new hire. Many things must happen: an email address, payroll, a welcome package, a laptop, building access. Policies change often and differ by country and division, so no single process really knows the whole list. An orchestrator would have to know every service, call each one, and could not run unless all were up. What if hiring someone simply announced the fact, and each interested component reacted on its own?

2

Why not just make the calls asynchronous?

Putting requests on a queue does not by itself decouple anything. If the caller blocks waiting for the reply, the call is only pseudosynchronous: it still ties up a thread, splits one transaction into several and has to match replies to requests. Truly asynchronous invocation listens for replies on another thread, which scales better, but it still needs exactly-once delivery of both request and reply, which is hard on replicated cloud messaging. Event notification changes the semantics instead: a one-way announcement with no reply expected. Compare where the caller's time goes.

3

The four parts of an event-driven system

Every event-driven architecture has the same cast. The event describes a change. An event emitter detects changes and sends events out. An event listener receives them and decides whether and how to react. An event channel connects emitters to interested listeners. Two characteristics set this apart from calls: transmission is one-way, and an event is a change notification that carries no intent, so two listeners may react to the same event in completely different ways. That makes the family easy to extend: add a listener, add an emitter, or refine a channel, without touching the others.

The chapter's own namesIn pattern form the emitter becomes the Event Notifier, the listener the Reactive Component, the channel the Event Backbone with a topic per event type, and the published set of events and topics is the Event API.
4

Root pattern: Event Choreography

ProblemWhen a change occurs in one component, how can a variable number of other components react accordingly?
SolutionCoordinate components through Event Choreography: when one changes, the others react at their own pace and in their own way, with no central conductor.

The book's example: a flight is running late. The aircraft's next flight may be late too, crews may miss connections, passengers need telling, gates and catering need rescheduling. Publish one event and watch who reacts. Then take a component down and publish again.

StrengthsPublishers and subscribers are independent; new behaviour is just a new subscriber. Notifiers never block waiting for answers, and many subscribers work in parallel. A failing service affects others less because the backbone sits in between.
ChallengesDelivery is best-effort: the backbone can lose an event, nobody may be listening, or a listener can fail mid-processing with no transaction to roll back. Error handling is harder, and the overall flow is visible nowhere in the code.
5

Event: what goes in one?

ProblemHow do you represent a change in one component so it can be communicated to others?
SolutionCapture the minimal description of each change as an Event and send it out.

Events come from database updates, workflow state changes, devices, clicks. At a minimum say what type of change it was and what caused it, and which component it came from. Small data, such as a new temperature reading, can ride along. For a big document, send just its key and let interested parties fetch it (the Claim Check idea). Note that the event format is still a contract: you are coupled through events and topics instead of through APIs. Build an event and watch the trade-off.

Event Notifier and Reactive Component

  

    

      
Event Notifier: problemHow and when should a component announce changes to other components?

      
SolutionDesign each component to announce its most important changes as events. The domain events found in Event Storming are the natural candidates.

    

    

      
Reactive Component: problemHow can you build an application that reacts to events?

      
SolutionBuild it from components that listen for specific sets of events and decide how to react, which may be to do nothing.

    

  

  
The payoff is in branching logic. One onboarding handler with an if for every country, division and job type gets fragile fast. Instead, each option becomes a separate reactive component listening to the same Employee Hired event, each with its own filter. Reactive programming libraries help but are not required.

  

    
// one handler, many branches (fragile)
onHired(e) {
  if (e.country === "DE") { ... }
  else if (e.division === "Labs") { ... }
  if (e.role === "Engineer") { ... }
  // grows with every new policy
}

    
// many small reactive components
on("EmployeeHired", e => e.country === "DE"
    && works_council.notify(e.id));
on("EmployeeHired", e => e.role === "Engineer"
    && laptops.order(e.id, "dev"));
on("EmployeeHired", e => payroll.enrol(e.id));

Event API

  
ProblemHow can reactive components know what events to expect?

  
SolutionDefine an Event API that lists the topics notifiers publish on and the events and formats on each.

  
The Event API is the contract of an event-driven system, just as the Service API is for calls. A good start is the Event Storming wall: each pivotal domain event becomes a candidate topic and message. The AsyncAPI specification is a standard way to write it down, much as OpenAPI is for REST. Tap a channel.

Event Backbone and delivery

  
ProblemHow can reactive components get the events they care about without being coupled directly to the notifiers?

  
SolutionConnect them through an Event Backbone with a separate publish-subscribe topic for each type of event.

  
Event-style systems such as Apache Kafka replicate their logs across machines, which suits the cloud: no single point of failure and no distributed transactions. The price is delivery semantics. Exactly-once is very hard on a replicated log, so you usually choose at-most-once (may lose) or at-least-once (may duplicate). MQ-style queue managers can do exactly-once by using distributed transactions, which fit the cloud poorly. Send ten payments over a flaky network.

Event Sourcing

  
ProblemAs state changes constantly and unpredictably, how can you audit the history that produced the current state?

  
SolutionLog the ordered history of events each component receives, so its current state can be explained and rebuilt by replaying them.

  
The book's illustration is a grade book. The reported grade is not stored; it is derived from the list of graded assignments. Correct a mis-graded quiz and the history, not a overwritten number, explains the change. Banking ledgers work the same way: a disputed charge is reversed by a new credit entry, never by deleting the old line. (In this toy, quizzes count double.)
