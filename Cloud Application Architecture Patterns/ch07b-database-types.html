Cloud-Native Storage: Choosing Databases

There is no one right database. Relational, document, key-value, columnar and graph stores each fit a different shape of data, and a cloud app may use several.

Five shapes of data, five kinds of database

An Application Database (previous page) comes in many types, and the chapter gives each of the five main ones its own pattern. Each is the best answer to a different question about your data. Pick a type to see the same small shop data stored its way, and what it is best at.


    

  






  
2
Relational Database

  
ProblemHow can an application store well-structured data that it needs to query dynamically?

  
SolutionUse a Relational Database, hosted in the cloud: a schema of tables, rows and columns queried with SQL, with views to present the same data differently.

  
Relational is still the right answer when the structure is known, queries are not, and transactions and referential integrity matter. The book distinguishes enterprise SQL (Db2, Oracle, SQL Server), small SQL (PostgreSQL, MySQL) and NewSQL (distributed, horizontally scalable SQL). In the shop, order fulfilment, with many small updates to parts of an order as items ship and return separately, is a natural fit.






  
3
Document Database

  
ProblemHow can an application store and retrieve data efficiently when its future structure is not well known?

  
SolutionUse a Document Database, which structures data the way the application does.

  
Schemaless: store each record as a JSON-like document, nested as the app sees it, and different documents can have different fields. A product catalog is the classic example: a car has far more attributes than a screwdriver. MongoDB, CouchDB, Couchbase, and cloud services such as Cloudant, DynamoDB, DocumentDB, Cosmos DB and Firestore. The design skill is choosing document granularity: what belongs in one document and what is referenced.

4
Key-Value Database

  
ProblemHow can an application store and retrieve independent entities that are always looked up by the same key?

  
SolutionUse a Key-Value Database, optimized to work like a giant hash map.

  
Often the most scalable database of all, because there is nothing to join or search: hash the key, go to the node, fetch the value. Memcached, Redis, Riak KV, Ehcache, DynamoDB, Bigtable. Its signature use is session data, which is how a stateless application can still offer a multi-screen checkout: the session lives in the key-value store, keyed by a session ID the client carries. Look up a key and see which node it lands on.

  

    

    

    

  






  
5
Graph Database

  
ProblemHow can an application store and retrieve interrelated entities by navigating their relationships?

  
SolutionUse a Graph Database: entities are nodes, relationships are edges, and queries walk the graph.

  
Three jobs where graphs shine: navigating deep hierarchies (the book mentions a research family tree of 27 million people), finding hidden connections between distant items (a rerouting around a washed-out bridge), and investigating interrelationships such as fraud rings or recommendations. JanusGraph, Neo4j, Apache TinkerPop, Cosmos DB, Neptune. Ask for recommendations for Ana.

  

    

    

    
// illustrative graph query
MATCH (ana:Customer {name:"Ana"})-[:BOUGHT]->(p)<-[:BOUGHT]-(peer)-[:BOUGHT]->(rec)
WHERE NOT (ana)-[:BOUGHT]->(rec)
RETURN rec, count(peer) ORDER BY count(peer) DESC

    

  






  
6
Columnar Database

  
ProblemHow can an application store data most efficiently for analytics, as in a data warehouse?

  
SolutionUse a Columnar Database, optimized to find records quickly even in semi-structured data.

  
Still tables, but stored by column (or as wide, sparse column families) rather than row by row. An analytic query that sums one column over millions of rows reads only that column, compresses well and skips the rest. HBase, Cassandra, ScyllaDB, Db2 Warehouse, Bigtable, Redshift, Keyspaces. See how much data the same query touches.

  

    

    

    

  






  
7
Data Module

  
ProblemHow can I align my data model with my application model so both are easy to maintain and evolve?

  
SolutionDivide all the data into Data Modules, sets with few dependencies between them, and store each in its own database or schema.

  
Data Module is to data what Modular Monolith is to code. Most references stay inside a module; few cross. Each application module connects only to the data modules it uses, ideally exactly one, which in microservices becomes the self-managed data store. Several modules can still share one database server for efficiency, each in its own schema (PostgreSQL), collection (MongoDB), keyspace (Cassandra) or key prefix (Redis). Polyglot Persistence

  
ProblemHow can an application store each data module in the type of database that suits its structure and access pattern?

  
SolutionUse Polyglot Persistence: choose the best database type per data module.

  
The data version of Polyglot Development. Modules may happen to share a type, but because it fits each of them, not because one was mandated. The cost is more kinds of servers and skills, which DBaaS eases. Choose a database for each of the shop's modules and compare with the book's reasoning.

9
Command Query Responsibility Segregation

  
ProblemHow do you optimize throughput for queries and updates by many clients that need many cross-cutting views of the data?

  
SolutionKeep two copies of the data: a write database that clients update through a command API, and a read database they query through a separate retrieve API.

  
Writes arrive as commands, optionally queued on a command bus, and a (replicable, stateless) write model applies them one transaction at a time to the database of record, then publishes an update event. An event processor applies each event to the read database, whose schema can be shaped for the queries, and the read model returns DTOs. The wins: serialized concurrent updates, complex aggregates kept valid, separate scaling for read and write workloads, schemas optimized for each side, and an update history if you log the events. The cost: complexity, and reads that lag writes slightly. Implementations range from one service with two databases to two separate services. Step through one update.
