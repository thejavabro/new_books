Microservices Architecture

One big application is hard for many teams to change and clumsy to scale. Microservices break it into small, independently deployable pieces, each owned by one team.

1

Small apps, small teams

The chapter borrows a widely used definition: microservices are highly maintainable and testable, loosely coupled, independently deployable, organized around business capabilities and owned by a small team. The last trait is the one people forget. The main reason to adopt them is to let many small teams deliver a large application faster, because each team coordinates mainly with itself.

Why small teams go faster

communication paths grow as n(n−1)/2

Gains over a monolithEach service scales on its own and fails on its own. Redundant copies and rolling replacement give zero-downtime releases. Teams build, test and deploy when they are ready, not when the whole department is.
The billMore interfaces to design and agree on. A build pipeline per service. Distributed transactions. Harder end-to-end testing, tracing and log aggregation, and many small things for operations to watch. Every interface is, though, a handy place to test and monitor.

Microservices are an extension of the cloud-native architecture from Chapter 3: each one is a stateless, replicable Application Package with a Service API, External Configuration and Backend Services. They do not need a cloud, but a cloud makes running dozens of them far easier.

2

Root pattern: Microservice

ProblemHow do you architect an application as a set of interconnected modules that can be developed independently?
SolutionMake each module a Microservice: an independent business capability with its own data, developed by a separate team and deployed in a separate process. Together they provide the application's full functionality.

The book draws a typical microservices application in four tiers. Tap each tier of the airline example.

Netflix is the book's real-world case. Running out of data-center capacity, it moved to AWS from 2009 and spent seven years, to 2016, turning one giant Java WAR into fine-grained REST services: each owned by a small group, each with its own database, each run as at least three replicas across availability zones. Billing, stateful and transactional, went last. The tools it built (Eureka, Zuul, Ribbon) later inspired the service-mesh ideas found in Kubernetes and Istio.

3

Domain Microservice: how big is one?

ProblemHow should a set of microservices provide the business functionality for an application?
SolutionBuild each business capability as a Domain Microservice that offers a Service API for that capability and encapsulates all the functionality behind it.

Two sizing rules keep services from being too small. A service should be broad enough to complete a whole business transaction using only its own data, avoiding chains of calls where one part succeeds and another fails. And it should avoid tight coupling: if one service only ever produces data that another processes, merge them. Move the slider to slice the same airline capabilities finer and coarser.

Adapter Microservice

ProblemHow can the application use existing functionality without abandoning the microservices approach?
SolutionWrap the existing system in an Adapter Microservice: a Service API like any other microservice, implemented by delegating to the old system.

The rest of the application cannot tell the adapter from a domain microservice. Behind it can be a mainframe transaction, a packaged product or a SaaS API with an awkward protocol. A sensible first cut when wrapping existing systems is one adapter per system of record, even if that is not a perfect business capability. Later, the implementation behind the adapter can be replaced without touching its clients, which sets up the strangler work in Chapter 10.

The adapter speaks JSON to callers and a legacy protocol behind.

Dispatcher (Backend for Frontend)

ProblemHow can a client use a channel-specific interface when the business functions are spread across an evolving set of domain APIs?
SolutionBuild a Dispatcher, also known as a Backend for Frontend (BFF): one API per client type, implemented by delegating to the microservices.

A dispatcher does three things: orchestration (several service calls for one user action), translation (reshaping results for the channel) and filtering (dropping what this client does not need). Compare the same "my trip" screen for two clients.

Polyglot Development

  
ProblemWhat language or languages should be used for implementing microservices?

  
SolutionLet each team pick the language for its microservice. They do not have to differ, but they can.

  
Historically, four forces pushed a department toward one language: monolithic applications are one process and so one language; interoperability was easier within one language (think COBOL copybooks or CORBA); platforms and frameworks dictated languages (Java EE meant Java); and staffing was simpler if everyone knew the same one. Microservices talk over language-neutral web APIs and run in containers that host anything, so the first three forces mostly vanish. The staffing force remains, which is why sensible organizations offer a short menu of supported languages rather than a free-for-all.

Self-Managed Data Store

  
ProblemHow does a microservice store its state?

  
SolutionGive each stateful microservice its own data store, accessed only by that microservice. Replicas of the same service share it; different services never do.

  
A shared database is a hidden API: change a column and someone else's service breaks, and two teams can no longer deploy independently. Toggle the design and then try to change the Customer schema.

Service Orchestrator: complex tasks

  
ProblemHow does a microservice perform a complex task made of multiple steps?

  
SolutionMake it a Service Orchestrator that coordinates the tasks of several simpler microservices.

  
There are three ways to build one. An orchestration microservice simply calls the others; it is safe only if every step is read-only or idempotent, because on failure it just starts again. A consolidated microservice merges the steps and their data into one service with one local transaction, which is right when the services were sliced too thin in the first place. A business process runs in a workflow (BPM) engine that remembers which steps finished, resumes after a crash, and undoes finished steps with compensating transactions. Run a checkout and make the payment step fail.
