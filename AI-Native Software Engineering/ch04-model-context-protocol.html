Model Context Protocol

Without it, you are the copy-paste bridge between your agent and every other tool. MCP is one shared plug that lets any AI tool reach any service, and with that reach comes cost and risk you need to manage.

From N × M integrations to one protocol

Before MCP, every AI tool needed its own integration for every service. With MCP, each service ships one server and each AI tool speaks one protocol, the way the Language Server Protocol unified editors and languages. Change the numbers and flip the switch.

The real change: you stop being the retrieval layer. Ask about a performance regression and the agent queries the traces itself, correlates them with code and proposes a hypothesis. You direct and verify.

Hosts, clients, servers

The host is your AI app; it manages connections, approval prompts and security policy. It creates one client per server, each an isolated 1:1 link. Each server offers three kinds of thing. Tap a server.

🛠️ Tools

Actions the agent can call: list_issues, create_pull_request.

📄 Resources

Data to read: files, query results, API responses.

🧩 Prompts

Reusable templates that standardize common workflows.

What a session really costs

Three costs stack up. Description overhead: every connected server's tool schemas ride along on every request, used or not. Call tokens: each call is output, its result is input. Result size: one search can return 8,000 tokens. Build your setup.

8

Four principles, and a golden path

Least privilege

Minimum scope that still does the job. Every extra permission is blast radius.

Isolation

Each server is an untrusted third party. Its credentials reach only its purpose.

Auditing

Keep and review tool-call logs, especially after reading outside content.

Secure defaults

Start with zero servers; add each one on purpose. Treat it like a contractor: access for this project, removed after.

For teams: keep a short registry of reviewed servers with recommended configs and scoped credentials, and make the approved path easier than going off-road. Bring security and AI governance in early.

9

More tools, worse agent

GitHub exposes 15–20 tools, Playwright 20+, AWS 50+. A few common servers can eat over 20% of the window before any work, and the model picks tools less reliably from a crowd ("tool-space interference"). Pick a task and load a matching profile.

How: separate config files per profile, custom agents with a tools: allow-list (Copilot supports server/tool entries), or deferred tool loading so descriptions load only when selected.

10

Building your own server

Build one for internal tools, to slim down a sprawling public server, or as a building block for automation. The SDKs (TypeScript, Python, FastMCP) make it a few dozen lines. The part that matters is the description: what it does, when to use it, what it returns. Test with the MCP Inspector before going live.

MCP in unattended pipelines

  
With no human watching, nobody catches the wrong call. Use service-account tokens with the narrowest scope, and let pipeline agents retrieve and analyze rather than write, push or deploy. Sort these jobs.

  






  
12
Often, a skill + CLI is enough

  
Mature CLIs (gh, aws, kubectl, docker) already handle auth, pagination and output. A skill file that documents them, or your scripts/ folder, gives the agent the same power with no server process and no schema tokens. Heuristic: if you'd type a command, write a skill; if you'd write code against an API, consider MCP.
