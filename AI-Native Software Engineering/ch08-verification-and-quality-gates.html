Verification and Quality Gates

Earlier chapters steered the agent before it writes code. This one is about what happens after: a pull request is ready, twenty more are waiting behind it, and you need to know the code is right without reading every line.

The bottleneck moved

Writing code used to be the slow step, and review came last. Now an agent produces a pull request in minutes while the team reviewing it is the same size as before. The Theory of Constraints says a system moves only as fast as its one bottleneck, and today that bottleneck is human review. Increase the PR volume and watch what happens to quality.

Exploit the constraint first. Make sure everything that reaches a reviewer has already passed every check a machine can run. Only then work on widening the bottleneck. (Numbers here are illustrative: 4 reviewer-hours a day, one hour per careful review.)
2

Five layers of filters

The early layers are cheap and fast, and they catch most of the problems. The later layers are slow and expensive, and they're there for what only a person or live traffic can show. Each layer depends on the ones before it. Switch layers off and drop 100 problems through the stack.

3

The agent as its own first reviewer

The gates that protect you also give the agent feedback. A good harness runs the whole local gate set before any push: lint, types, tests, build. A failure is information the agent can act on: it reads it, fixes the code and reruns. With a headless browser it can even click through the app it just built.

Start today: put every command you'd run to convince yourself a change is safe into one script. That script is the seed of an agent harness.
4

Layer 1: a menu, not a checklist

Deterministic gates give a hard yes or no, cost almost nothing, and leave nothing to argue about, so run them on every PR before any person or model looks. You don't need all of them. Start where it hurts. Pick a project type to see which gates matter first, and tap a gate to see why AI makes it more important.

5

Mutation testing: catching tests that lie

When the same agent writes the code and the tests, "all green" counts for less. The tests can run every line and still check almost nothing, so coverage says 95% while nothing is verified. Mutation testing breaks the code on purpose, one small change at a time. A good test goes red. If the suite stays green, that mutant survived.

function canRent(age, hasLicense) {
  return age >= 21 && hasLicense;

Property-based testing: state the law

  
An example test checks one input. A property states a rule that must hold for every input, and the tool throws hundreds of random inputs at it to break that rule. Agents get the obvious cases right and then fail on the ones you didn't mention: the empty list, the negative number, the exact boundary.

  

    
property: transfer(a, b, amount) conserves money → a + b is unchanged

    

    

    
The agent's version handles the examples in the ticket: 10, 50 and 100.

  






  
7
Layer 2: LLM-based review

  
Deterministic gates can tell you the code is well-formed. They can't tell you it's the right code. An LLM reviewer reads the diff along with the spec and the surrounding code, and gives an opinion. Who reviews makes a big difference: the session that wrote the code mostly agrees with itself.

Tune the reviewer to your codebase

  
Generic instructions get you generic comments: textbook advice, style nits your formatter already handles, the same five suggestions every time. Give it your conventions, your past incidents and a do-not-review list, and it starts to sound like a senior teammate. Build up the prompt and review the same payments diff.

9
Layer 3: the deploy is a safety layer

  
Some bugs only exist in production: real concurrency, the full dataset, the live third-party API. At 25 PRs a day more of them get through, so a deploy becomes a controlled experiment with a small blast radius and a fast undo. The baseline is a feature flag, off by default, which separates deploying from releasing. Run a canary rollout.

10
State can't be flipped back

  
Flags, canaries and blue-green all assume that rolling back means switching to the old code. State breaks that assumption. No flag can bring back a dropped column, unsend a duplicate email or refund a double charge. Agents see the code, not the 500-million-row table, so stateful changes need more human attention and an explicit plan.

  

    

    

    

  

  

    
    
    
    
  






  
11
Layer 4: runtime safety and AI ops

  
Logs, metrics and traces are the raw material. An AI ops agent is only as good as the signals it can read, and OpenTelemetry lets one agent read all three together. A fixed threshold can't tell a strange 3 a.m. Sunday from a normal Monday peak. Anomaly detection learns the usual rhythm. Compare the two.

  

    

    

    

  

  

    
Error budget

    

    

    

    

  

  
Alert fatigue is how an outage goes unnoticed for an hour. Alert on symptoms ("checkout is failing"), not causes ("CPU at 80%"). Use burn-rate alerts, and pair a fast window with a slow one. If a page isn't worth waking someone for, it belongs on a dashboard.






  
12
Detect, analyze, triage, fix, and back through the gates

  
An agent spots a regression after a deploy, gathers traces and recent deploys, opens a ticket and hands it to a coding agent. The draft fix gets no shortcuts: it goes back through every layer and a person approves it. It also brings a test that reproduces the bug, so every escape becomes a new guardrail.

  

    
Regression tests added: 0

    

    
Maturity today: anomaly detection is mature, root-cause drafts and fix PRs are shipping in products, and running the whole loop with no human at the gate is still something to aim for.

  






  
13
Layer 5: which changes need a human?

  
This is one approach that works, not settled doctrine. It uses two mechanisms. A deterministic path gate means anything under payments, auth, migrations, infra or CI always gets a person. An AI risk scorer handles the uncertain middle. The scorer can only add a human, never overrule the gate, and when it's unsure it must fail safe.

Human review

    

  

  
Route to the right human. Someone who has never touched payments, reviewing a payments change, will just check the syntax. CODEOWNERS (or the scorer's reviewer_domain) picks who reviews. The reviewer's job changes too: stop hunting for the missing null check and judge intent and fit. Is this the right thing to build?






  
14
One change, end to end

  
Cheap checks run first on everything and catch the most. Human attention, the most expensive resource, comes near the end and only where it's needed. The staged rollout takes time on purpose, because that time is when production can show you a problem while the blast radius is still small.

  

    

    

    

  

  
Adopt from the bottom up. 1) Tests, strict types, a linter and secrets scanning as one blocking gate, about a week of work. 2) A single checklist reviewer. 3) Risk scoring and routing. 4) AI ops last. Wiring up AI ops before you have flags and tests is like fitting a smoke detector to a house with no walls.






  
15
Measure the system itself

  
Five numbers that pull against each other: cycle time, escape rate, revert rate, false-positive rate and human minutes per PR. You can game any one of them. A healthy system brings cycle time and human time down while escapes and reverts stay flat. Move the dials.

The trust ladder

  
Authority is earned with evidence, one reversible step at a time. Each rung is unlocked by the numbers from the rung below, and you step back down the moment the numbers say so. Collect evidence and climb.
