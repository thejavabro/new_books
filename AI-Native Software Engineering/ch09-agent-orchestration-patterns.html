Agent Orchestration Patterns

At some point one agent isn't enough: the context window fills up, independent jobs wait in line, or you're paying top prices for easy work. Orchestration is a set of patterns, each with a cost. This chapter covers when to use each one, and when to leave it alone.

1

Where one agent hits its ceiling

A single agent is the right default: simple, cheap and easy to follow. Four signals tell you it has reached its limit. Tap each one.

The outcomes spread widely

One published evaluation found a lead-plus-workers setup beat a strong single agent by 90.2%, with parallel work cutting time on complex queries by up to 90%. A study of seven popular multi-agent frameworks found failure rates between 41% and 86.7%. What makes the difference is judgment, not tooling.

2

More agents aren't free

Agents use about 4× the tokens of a chat, and multi-agent systems about 15×. Each handoff is also a chance to lock in an error. Pass a number down a chain of agents and see what happens.

Source document: "Q3 revenue was 10.5K."

Token cost (relative)

Other costs: context poisoning through shared workspaces, merge conflicts, and the work of splitting, tracking and merging. Practitioners suggest teams of 3 to 5 agents with clear ownership of separate files.

3

One agent, bigger jobs: compaction vs a scratchpad

Compaction summarizes the old chat when the window is nearly full. It's automatic, but it decides on its own what to keep. Run it twice and you get a summary of a summary. A scratchpad puts the same memory in a file you can read and fix, and the next window starts clean. Make the session longer.

4

SDD is already an orchestration pattern

Spec, plan and tasks are named scratchpads. Once more than one agent reads and writes them, they become the coordination artifact, sometimes called a blackboard. Agents don't message each other. They align to the spec and update the shared plan. The spec also survives a full window, a crash or a night off. Tap an agent to see what it reads and writes.

5

A different model for each phase

The phases aren't equally hard. Specify and Plan need deep reasoning. Execution is mostly mechanical. Verification is careful reading. Because the handoff is a written artifact rather than a shared chat, you can swap the model behind each phase. Pick a model for each phase.

6

Generator-critic: one makes, one checks, you filter

A model checking its own work is the worst judge, because it already believes the code is right. A fresh critic, ideally on another model, casts a wide net. Its findings mix real problems with false alarms. The step that makes this useful is filtering, by you or by the lead agent. Keep the real ones, drop the noise, then run another pass.

Rules: stop after 2 or 3 passes, and decide in advance what counts as a pass (for example tests green and no high-severity findings).

7

The goal loop: a separate judge decides when to stop

Instead of typing "continue" over and over, set a finish line once. After every turn a cheaper, separate model checks whether the goal is met, and its reason becomes the hint for the next turn. The goal has to be something the agent can show, and you need a turn cap.

8

The Ralph loop: same prompt, fresh window, memory on disk

The most stubborn version: run the same prompt in a loop. Each run starts with an empty context, reads PLAN.md, does one task, runs the tests, commits and exits. It never has a long session, only many short ones. Two guardrails are not optional: a run cap and a finish signal.

for i in $(seq 1 30); do
  out=$(cat PROMPT.md | agent)          # fresh context every run
  git add -A && git commit -m "ralph: run $i"
  echo "$out" | grep -q ALL_DONE && break
done

Running agents in parallel: three levels of isolation

Two things can collide: context (what each agent knows) and files (what's on disk). Use the lightest isolation that keeps the agents out of each other's way. Pick a situation.

git worktree add ../fix-login -b fix-login   # new folder, new branch, shared history
git worktree remove ../fix-login             # after the merge (.env is not copied!)
10

Subagents keep the lead's window clean

The main agent starts a helper, gives it one job, and gets back only the answer. The files it read, the tool output and the false starts stay in the helper's window. That's the quiet superpower here. Answer five questions that each need ten files read.

11

Four ways to arrange subagents

The building block is the same in each, and in all four there's one agent in charge with workers reporting back to it. Tap through the shapes.

Which shape fits?

Sideways coordination, only when it's really needed: a shared blackboard file that every worker reads and writes, or direct messages between agents (small JSON payloads). Messages are more direct but harder to follow and debug.
12

The advisor: pay for brilliance only on the hard slice

A cheap model runs the loop. When it gets stuck it packages the hard question and asks a subagent running your strongest model. This saves money only when hard steps are rare.

13

Workflows: orchestration as code

A script holds the steps, the loops and the order, and calls a headless agent for each piece. Intermediate results live in variables, not in a growing context window. Watch a deep-research workflow: split the question, research each angle in parallel, then merge.

Fixed script or let the agent orchestrate?

14

The dark factory, and your attention budget

Put every pattern together: a spec goes in, agents plan, write and test in a loop, and a pull request comes out. It's called a dark factory because nobody needs the lights on. It works only with two inputs: a clear, testable spec, and automated checks that can tell right from wrong. Otherwise use interactive mode and work out what you want.
