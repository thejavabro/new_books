Spec-Driven Development

Agents don't ask for clarification. They resolve ambiguity silently, with training-data averages, and keep building. A spec is how you make the important decisions yourself, before the code exists.

2

Speed without friction compounds

Two properties make ambiguity worse with agents: velocity (500 lines where a human writes 50) and silence (no "wait, what do you mean?"). An early wrong assumption becomes the foundation for everything after it. Build both towers.

Agent from a vague prompt

Agent from a spec

A spec stops compounding at the source: intent decisions are fixed by a human up front; the agent only makes implementation decisions, which are smaller and easier to correct.

3

You already write specs

SDD isn't new; the audience is. These documents all exist because ambiguity is expensive. SDD writes them for humans and agents, so they need more precision and a format an agent can parse.

No ADRs? Then your codebase is full of unexplained decisions. Code says what, rarely why. An agent may "consolidate" two auth paths kept separate for compliance, or make a deliberately async call synchronous.
4

Writing a spec is how you find the questions

The meeting agreed to "add authentication to the admin panel." Everyone nodded. Start writing the spec, section by section, and watch the unanswered questions appear, and whose they are.

Open questions

Asking the product manager now costs minutes. Discovering the disagreement in review costs hours; in production, much more. A human would stop and ask mid-implementation. An agent picks an answer and keeps going.

5

Visible cost vs. invisible cost

A spec's cost is up front and visible. Skipping it costs are spread out and feel like "normal friction": redoing the first attempt, reconstructing intent in review, clarifying with product, production bugs, the endless "make it a bit better" loop. Adjust to your reality.

And there's a leverage bonus the bars don't show: the spec keeps paying every time someone extends, debugs or onboards to that feature. Scale the investment with the stakes.

6

When SDD is the wrong tool

SDD is an execution tool, not a discovery tool. If you can't write acceptance criteria yet, you are still exploring, and that's fine. Spike first with a prompt or Plan Mode; then turn what you learned into a spec.

The danger is skipping the middle box: going from spike straight to production gives you prototype-quality systems with no record of what they were meant to do.

7

Code is perishable; intent is durable

Tools change every few months. Code gets regenerated, refactored, replaced. A plain-text spec.md in the repo is readable by any future tool, agent or engineer. Play the years forward.

launch

Tool migration

A new tool reads the same spec; code alone is a lossy record of intent.

Onboarding

Code says what; specs say why, which constraints, which alternatives were rejected.

Evolution

Stops intent eroding change by change. Specs turn tacit knowledge in people's heads into something agents can read.

8

SDD gives HITL its checkpoints

Without a spec, reviewing AI output means reconstructing intent from code. With one, review becomes verification against criteria, and you finally have an exit condition for "done". Tap a checkpoint.

9

Why engineers resist, and the counter

A spec isn't documentation you write after you understand something. It's the thinking you do to understand it.
10

Plan Mode: the on-ramp

Between vibe coding and full SDD sits one cheap habit: ask the agent how it would do it before it does anything. Here's a plan for "add cursor pagination to /api/orders". Review it like you would: is something missing?

What Plan Mode gives you

Catches misunderstandings for the price of a sentence. Trains your eye for mismatched intent.

What it doesn't

The plan vanishes with the session, and it answers how, not what. It won't raise the dozen auth questions a spec would.
