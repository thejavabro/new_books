The SDD Workflow

Writing a spec is the start. This chapter is the operating loop around it: six named phases, files that outlive the chat, human checkpoints at the seams, and a way to bring all of it into a codebase that was never specified.

Six phases, one loop

Specify, Plan, Execute, Verify, Integrate, Learn. It isn't a waterfall: a bug fix can go round the loop in twenty minutes, and a big feature can go round it several times over a few days. The order stays the same. What changes is how long each phase takes. Tap a phase to see the file it leaves behind.

2

Humans sit at the seams

The agent can work alone between four checkpoints that a person always owns: spec review, plan review, diff review and deployment review. The point isn't micromanagement. It's catching a whole category of mistake while it's still cheap to fix. Plant a mistake, switch checkpoints off, and see where it finally gets caught.

Stop conditions and escalation

Leave an agent stuck in a failing loop without guidance and it tends to try new versions of the same wrong idea instead of asking for help. A stop condition says when it must stop. An escalation rule says who to tell and what to tell them. You need both. Pick a situation and switch rules on to see what the agent does.

Add rules for your own domain. Payments, auth logic and database migrations are good places for a "stop and ask" rule, even when the code looks correct.
4

Sometimes you can't write the spec yet

A spec can only hold what you already know. When you're unsure of the direction, and not just the details, build a throwaway prototype first and write the spec from what it teaches you. With an agent, a two-day spike takes about two hours, so prototyping should be your first response to real uncertainty. Four kinds of uncertainty justify one. Sort the situations.

The core artifact set

Everything is plain text under version control. The convention is one folder per spec, so every artifact for that piece of work, and the agent, has one obvious home. spec.md covers what and why, plan.md covers how, and tasks.md lists small steps that each have a done check. The other three files are optional.

What makes a criterion production-grade

  
Acceptance criteria carry the most weight in the spec. Each one should point at a test that proves it true or false. Four patterns separate a checklist from a production-grade spec: what happens on failure, under concurrency, how it's observed in production, and how it's rolled back. Choose a risk level and cover the patterns.

8
Let the agent interview you

  
Don't dictate the spec and hope the agent fills the gaps well. Turn the conversation around: "Ask me as many questions as you need, then write the spec." If it doesn't ask, it fills every silence with a sensible average, and that average rarely fits your system. If product, design and engineering answer together, the spec belongs to everyone.

Review the plan like a pull request

  
The agent reads the spec and the code and writes plan.md, with no implementation code at that stage. Reviewing it takes about ten minutes. Check four things: does the approach fit your patterns, are the trade-offs real choices or excuses, does the order respect the dependencies, and is anything missing? Tap the lines you would flag. Three of them have problems.

  

    

    
Corrections made before approval: 0

  

  
A spec gap found during plan review is a good outcome. Fix the spec first, then carry on. That's the cheapest correction in the whole cycle: words on a page, before any code.

Tasks: done checks and a dependency graph

  
Each task needs a done check you can verify without reading the rest of the plan, ideally a passing test. Order tasks by their real dependencies and mark which ones can run in parallel. Then the task list works as a queue that several agents can pull from at once.

Execution: the narrowest slice

  
The context is already prepared, so the prompt can be short: read the three files, do the tasks in dependency order, tick each one off, and stop and report if blocked. Some self-correction is healthy. Three failures in a row for the same reason is not.

implementation_notes.md is the agent's working memory, written to disk: surprises, decisions the plan didn't cover, assumptions. 12
Verification is hard rails

  
The gates are pass or fail, objective, and not up for negotiation. Nothing reaches integration until every gate is green. Agents ship code faster than anyone can review it, so you surround the reviewer with checks: deterministic ones like linters, types and tests, plus checks run by a model, such as review agents and spec-conformance checks. Plant a bug and run CI.

Integration: the PR links the spec and maps each acceptance criterion to its tests. Reviewers read the criteria first and then the code. "Does this satisfy what we agreed?" gives a different answer from "Does this look right?" more often than you'd expect. After the deploy, watch the signals the criteria name.






  
13
Learn: the phase everyone skips

  
Ten minutes after the merge, answer five questions. Each answer goes into a lasting file, so the next cycle starts from a better harness. The model doesn't change, but its environment does. Slide through the cycles.

The two-tier spec lifecycle

  
Most teams work spec-first: write a spec for each task, use it, then leave it alone. On its own that scatters intent across dozens of old files. The practical middle ground is a small strategic tier of living documents on top, with tactical per-task specs underneath that get archived once they ship. Tap a change to see what it touches.

  

    

    

    

  






  
15
Brownfield: Spec Islands

  
The intent behind an old codebase lives in people's heads, in commit messages and in contradictory comments. That is knowledge debt. Don't try to spec everything after the fact. Spec a module just before you change it. Each spec becomes an island, the islands spread into the busy areas, and stable code can stay unspecified.

Reverse-engineering intent: ask the agent to describe what a feature's files appear to do, without suggesting improvements. Then have a second, fresh session check that description. Treat the result as a first draft, because it can confidently describe a bug as if it were the design.
