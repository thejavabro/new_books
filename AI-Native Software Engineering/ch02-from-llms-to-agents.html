From LLMs to Agents

Two ideas carry this whole chapter. An LLM is a statistical engine that predicts the next token. An agent is that engine inside a loop with tools. Get those two right and most agent behavior stops being mysterious.

One token at a time

A model doesn't store its training text; it stores patterns of what tends to follow what. When it answers, it predicts a probability for every possible next token, picks one, appends it and repeats. There is no global planner, so an early wrong turn compounds. Temperature reshapes the odds: low makes it nearly greedy, high gives unlikely tokens a real chance.

Run it a few times at 0.8, then at 0. Same prompt, different outputs: that is why you test behavior, not exact strings.

Tokens and the working-memory budget

Models read tokens, chunks of roughly three to four English characters. Code symbols and unusual names cost more. Everything in a call, input and output, has to fit in the context window. Type something to see a rough split (real tokenizers differ per model).

3

In-weights vs. in-context knowledge

In-weights knowledge was baked in at training: free, instant, frozen at the cutoff and sometimes wrong. In-context knowledge is whatever you put in the window: authoritative because you control it, but it costs tokens and vanishes after the session. Putting the right facts in context is called grounding; RAG is grounding done systematically.

4

Lost in the middle

Raw window size is not usable size. Research found a U-shaped pattern: models attend most reliably to the start and end of the context and less to the middle. Modern models find a single "needle" well, but harder tasks (reasoning across scattered facts) still degrade long before the limit. Drag your key requirement through a long context.

Use it today: lead with the acceptance criteria and the relevant code, not with five paragraphs of background.
5

Why LLMs are good at code

Code is over-represented in training data, strictly structured (it runs or it doesn't), full of repeated patterns, and often appears next to its docs. After pre-training, post-training makes the model useful. Two reward styles matter. Compare them.

Reasoning models

They spend extra "thinking" tokens before answering. More compute per answer, better on tangled multi-constraint problems, but slower and costlier (hidden reasoning tokens are usually billed). Most expose an effort knob.

6

Choosing where a model lives

"Open source" is used loosely. Fully open releases weights, data and training code. Open weights lets you self-host and fine-tune but keeps data private. Closed models run on a provider's cloud, sometimes inside your own VPC. Tick your hard constraints, then optimize inside the tier that remains.

Fully open

Max auditability; lower ceiling.

Open weights

Self-host, fine-tune, control latency.

Closed

Highest ceiling; VPC options; no bare metal.

Small language models (under ~10B parameters) can match large ones on narrow, well-specified tasks like classification, extraction or boilerplate, at a fraction of the cost. Decide with an evaluation set, not a hunch. And treat benchmarks as a rough tier signal: once a measure becomes a target, it stops being a good measure.
7

Where they excel, where they fail

Strong: pattern-finding, summarizing, first drafts of well-specified code, explaining unfamiliar code, translating between formats, applying many constraints consistently. The failures matter more because they hide. Tap each for the countermeasure.

8

The API is stateless

The model remembers nothing between calls. A "conversation" is your app resending the whole messages array (system, user, assistant, tool results) every time. So each turn costs more than the last. The system message is read first on every call, which makes it your highest-leverage input.

9

What makes an agent

An agent is an LLM plus tools plus context plus a loop, pursuing a goal across steps without a human at every step. The model never runs anything itself: it emits a structured tool call, your code executes it and appends the result. Underneath every framework, it is a while loop.

# the whole agent
messages = [user(goal)]
while True:
    r = llm.generate(messages, tools)
    if not r.tool_calls:
        return r.content   # done
    messages.append(r)
    for call in r.tool_calls:
        out = execute(call)  # your code runs it
        messages.append(tool_result(call, out))
10

ReAct, live: tests as observations

The loop's research name is ReAct: interleave a thought, an action and an observation. For coding agents the best observation is a failing test with a clear message. Watch an agent replace a deprecated function, break a test, read the failure and fix itself. Then try it with a vague test message.

11

Every loop needs an exit

A naive loop can spin forever on a vague goal: runaway spend, no signal. Give it a vague task and choose which brakes to install.

A well-specified task usually finishes in 5 to 15 iterations; a vague one can run past 50. Every iteration is a full model call that resends the growing history, so cost and latency grow with the loop.

12

The description is the interface

The model chooses tools from their names and descriptions alone. Write them like docs for a capable but very literal junior who has never seen your code, including when not to use the tool. One team found that requiring absolute paths wiped out a whole class of errors.

Task: "Show me the retry settings in config/payments.yaml."

13

Memory, and how it rots

In-context

The message history. Fast and complete, but bounded and attended unevenly.

Files

spec.md, plan.md, tasks.md. Survive resets, reviewable, version-controlled.

RAG

Hybrid keyword + vector search with a reranker. Great for docs and tickets; coding agents often prefer grep.

Agent notes

The agent writes a handoff log for its future self, like you do before leaving for the day.

Context rot

Long sessions pile up failed attempts, old decisions and contradictions. Symptoms: repeating mistakes, breaking an agreed constraint, forgetting the goal. Add turns, then apply a countermeasure.

14

HITL is a dial

Review at artifact boundaries: plan, code, test results, final diff. Not every tool call. Each correction becomes new context. Better still, let the agent decide when it needs you ("ask rather than guess"). Turn the dial by how costly a mistake would be.

The tool landscape, without the hype

Products will change; the categories are steady. Tap a category, then use the six questions to judge any new entrant.

FitTry it on 2–3 real backlog tasks. Would you merge it?
Context controlCan it load your conventions and code?
Latency & costA fast "good enough" often beats slow and brilliant.
PrivacyOften the deciding factor in regulated work.
AuditabilityCan you see tool calls, reasoning and diffs?
PortabilityDo rules, specs and MCP configs live in your repo?
The assistant is interchangeable; your harness (rules, specs, skills, tests, MCP servers) is the durable part. Pick a credible tool, invest in the harness, switch later if needed.
