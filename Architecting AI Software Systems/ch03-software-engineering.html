Software Engineering and Architecture

AI software is non-deterministic, built on code you did not write, and judged by decisions no one can fully test. Architecture is how a team tames that complexity before it tames the team.

1

Where AI software gets its complexity

Traditional software follows deterministic rules. AI-enabled software imitates human judgment through heuristic algorithms, which makes it non-deterministic and multidimensionally complex. The book cites a Gartner estimate that through 2022, 85% of AI projects would deliver erroneous outcomes because of bias in data, algorithms or the teams managing them. It also points to Linux, over 30 million lines of code, as proof that huge systems can work when a stable, modular architecture frames them. The book names five kinds of complexity. 2

A lifecycle that puts architecture early

The book's development lifecycle moves from concept to requirements to architecture before design and code, then through integration, unit and system testing to deployment. The authors say the same sequence applies whether you work in waterfall or Agile; what matters is that architectural questions are answered early.

3

Verification: which test finds the problem?

AI outputs are probabilistic and depend on training data, initial parameters and randomness. Unit tests help, but integration testing catches failures they miss, and adversarial testing catches failures nobody thought of. The book's example is pedestrian detection in a self-driving car. Architecting is a small-team function

Nobody masters every technology and domain, so architecting is spread across a small team under the chief architect, alongside specialty engineers (data engineers, data scientists, UI and full-stack developers, DevOps, security, operations, compliance and project control analysts). 6

Artifacts that tame complexity

Even the smallest project should write a Concept of Operations (CONOPS, see IEEE 1362): why the system exists, how users will use its AI features, how AI results are presented, how users can influence them, which actors and external systems are involved. Alongside it, a tailored set of UML/SysML diagrams that must cover the whole AI cycle (decision logic, error handling, retraining, human control, data cleansing and quality checks), and the non-functional requirements that drive the architecture. 7

Integration: where small changes ripple

Integration is usually the first time non-functional requirements are actually tested, and late architectural changes cascade. The architect guides four activities: design adequacy, non-functional evaluation, metrics measurement and interface verification. The book's example: a database query gets slower and an AI component starts deciding on out-of-sync data. Make the change and watch the ripple.

CI/CD helpsContinuous integration runs predefined integration tests whenever code is merged into the pre-production baseline, shows which change broke things, and lets you roll back a bad production release.
8

The architect in project management

The architect should not be the project manager, but contributes to all five PMBOK phases: initiation (objectives, statement of work, work breakdown, milestones, method), planning (milestone evidence, team mix, effort, configuration control, room for iterative model work), execution (resolving technical conflicts, balancing accuracy, cost and explainability), monitoring and control (quality reviews, tracking model metrics, data quality and drift) and closing (testing, certification, handing over model-maintenance know-how).

9

Agile, waterfall, and keeping the architecture coherent

The book's case study: a fraud-detection project planned waterfall-style ignored how iterative model building is and how hard integration with transaction systems would be. Re-planned as three-week sprints with early integration tests on synthetic data, models and interfaces were built in parallel and the system cut fraud losses by 37% (a figure from the book's example). The authors still credit waterfall with strong requirements work and project control, and warn that Agile can lose architectural coherence when parallel teams make conflicting design decisions. Their position: Agile plus architecting.
