Fundamentals of AI System Architecture

An AI system is only useful if people trust what it infers. This chapter tours the building blocks (data, algorithms, models, infrastructure) and the architectural choices that keep them fast, scalable, reliable and safe.

1

It all comes down to trust

An AI system makes inferences: it classifies, predicts, recommends. Those results are only worth something if the people relying on them can trust them, and keep trusting them as data shifts and models age. The authors argue that trust is not a model property; it is architected, by designing how the technology is used, watched, corrected and redeployed. They call these supporting mechanisms guard rails, and which ones you need depends on the domain.

Why it matters for the rest of the bookAlmost every later chapter (conceptual design, pipelines, testing, the generative AI case study) can be read as a way of making an AI system trustworthy enough to be used.

Four key components: data, algorithms, models, infrastructure

Data is the raw material the system learns from; its quality, quantity and relevance decide how well the system generalises. Algorithms are the engines (traditional ML such as random forests and gradient boosting, deep learning such as CNNs, RNNs and transformers, and reinforcement learning). Models are what the algorithms produce: the learned patterns used to predict on new data. Infrastructure supplies the compute, storage, networking and frameworks. Microservices: a conversational AI example

As AI systems grow, a monolith becomes hard to change. Splitting it into small services that talk through APIs lets teams deploy and scale pieces independently and keeps failures local, at the price of more moving parts, network hops and harder data consistency. The book's example is a chatbot built from four services behind an API gateway. Step through one conversation turn.

Sync vs asyncThe reply path is synchronous; logging to analytics is asynchronous so it never slows the conversation.
Stateful vs statelessOnly dialog management keeps session state; language understanding stays stateless and scales easily.
Data isolationEach service owns its data. Sensitive user data stays in the dialog state store.
6

Scalability, performance and reliability

Growth arrives as more data, bigger models and more users. You can scale horizontally (more machines or containers, orchestrated by something like Kubernetes), vertically (a bigger machine: more GPU, RAM, faster disks) or spread the work with distributed computing (Spark, Hadoop). Try serving a rising request load. The numbers are made up; the shape is the point.

7

Data lakes, data warehouses, catalogs and ontologies

A data lake keeps raw data of any shape in its native format and applies a schema only when someone reads it (schema-on-read): cheap, flexible, ideal for exploration. A data warehouse holds cleaned, curated, structured data with a schema enforced on the way in (schema-on-write): consistent and fast to query for reporting. Many AI architectures use both: land raw data in the lake, refine it, then load it into the warehouse. Catalogs index what data exists, where, with what lineage and quality; ontologies describe what the data means and how elements relate.

Raw clickstream, images and records land in the lake as-is.

Lake or warehouse?

8

Cloud-native AI versus lift-and-shift

Cloud-native AI is built from containers (Docker), orchestration (Kubernetes), microservices, serverless functions for event-driven work, and managed ML platforms such as Vertex AI, SageMaker, Bedrock (foundation models through an API) and Azure ML. The contrast is lift-and-shift: moving an on-premises system to rented servers without redesign. Compare how each pays for a day of uneven demand (illustrative).
