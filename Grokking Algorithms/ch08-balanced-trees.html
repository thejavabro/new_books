Balanced Trees

Sorted arrays search fast but insert slowly; linked lists do the opposite. A balanced binary search tree does both in O(log n), as long as it keeps itself short.

1

Fast search and fast insert

Binary search on a sorted array finds things in O(log n), but inserting a new value means shifting everything after it: O(n). A linked list inserts by changing a pointer, but searching it is O(n). We want both fast. The answer is a tree: specifically a balanced binary search tree.

2

Binary search trees

A binary search tree (BST) is a binary tree with one extra rule: everything in a node's left subtree is smaller than the node, and everything in its right subtree is bigger. To search, start at the root and go left or right at each node, just like binary search. If you fall off the tree, the value isn't there, and that empty spot is exactly where it would be inserted.

3

Shorter trees are faster

Search time depends on the height of the tree: the most steps from the root to any node. The same values can make a bushy tree or a straggly one. Insert values in sorted order into a plain BST and every node goes to the right: the tree is really a linked list, height O(n). A well-shaped tree has height O(log n). Watch it happen:

AVL trees balance themselves by rotating

An AVL tree is a self-balancing BST. Every node stores its height, or equivalently a balance factor: the height of its right subtree minus its left (the sign convention varies between sources). A balance factor of −1, 0 or 1 is fine; AVL trees don't demand perfection, just that the two sides differ by at most one. After an insert you walk back up through the new node's ancestors updating these numbers. When one hits ±2, the tree performs a rotation.

A rotation rearranges a few pointers while keeping the BST order: in a left rotation the right child moves up to become the parent and the old parent becomes its left child. There are four rotation cases (left, right, and two double rotations); you'll rarely implement them yourself. An insert needs at most one rebalancing, so inserts stay O(log n): search for the spot, then link the node in, much like a linked list.

5

Splay trees: recently used = near the top

A splay tree takes another approach. Every time you look up a node, it is rotated all the way up to become the root, so looking it up again is instant, and recently used items cluster near the top. Like a zip-code lookup that remembers the code you just asked for. The catch: the tree isn't guaranteed to be balanced, so a single lookup can take up to O(n). But any sequence of n lookups takes O(n log n) in total, so they average O(log n) each.

6

B-trees: fewer trips to the store

A B-tree generalizes a BST: a node can hold many keys and have many children (always one more child than keys). The order rule still holds: keys to the left of a key are smaller, keys to the right are bigger. Why bother? Because reading from storage has a physical cost called seek time, like driving to the grocery store. Driving once per item is silly; once you're there, buy everything you need. A B-tree node is a whole cart-load of keys read in one seek, so the tree is much shorter and needs far fewer seeks. That's why databases love them.
