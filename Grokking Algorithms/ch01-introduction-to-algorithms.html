The guessing game

An algorithm is just a set of instructions for getting something done. The book picks algorithms that are either fast, solve an interesting problem, or both. The first one is easiest to feel as a game: I am thinking of a number from 1 to 100, and after each guess you only hear "too high" or "too low".

Play it yourself

Guesses: 0

Each bar is one number. Bars that have been ruled out fade away.

If you guess 1, 2, 3 and so on (simple search), you might need 100 tries. If you always guess the middle of what's left, each answer throws away half the numbers. 100 becomes 50, 25, 13, 7, 4, 2, 1: seven guesses at most. That is binary search. It only works when the list is sorted.

2

Binary search, step by step

In code you keep two markers, low and high, around the part of the list that could still hold the answer. Check the middle; if it's too small, move low past it; if it's too big, move high below it. Stop when you find it, or when the markers cross.

Logarithms: how many halvings?

  
A logarithm is the flip side of an exponent. 23 = 8, so log2 8 = 3: you can halve 8 three times before you hit 1. In this book "log" always means log base 2. For a list of n items, binary search needs about log2 n guesses in the worst case.

Big O: how run time grows

  
Picture a programmer timing both searches on a small list to choose one for a moon landing that must be computed in 10 seconds. Say each check costs 1 ms. On 100 items simple search takes 100 ms and binary search 7 ms, so binary looks "about 15 times faster". The trap is assuming that ratio holds. It doesn't, because the two run times grow at different rates.

  

    

    

    

  

  
Big O notation counts operations, not seconds, and describes how that count grows with the input size n. Simple search is O(n); binary search is O(log n). Big O normally describes the worst case: simple search might get lucky on the first try, but O(n) promises it will never be slower than n steps.






  
5
Drawing a grid two ways

  
A hands-on way to feel the difference: you need a grid of 16 boxes on a sheet of paper. Draw them one by one, and it's 16 operations, O(n). Or fold the paper in half, then again, and again: every fold doubles the boxes, so 4 folds make 16. That's O(log n).

7
The traveling salesperson

  
Here's a problem with a truly awful run time. A salesperson must visit several cities and wants the shortest round trip. The obvious method is to try every possible order and keep the shortest. With 5 cities that's 120 orders; with 10 it's over 3.6 million. For n cities it's n! (n factorial), so the run time is O(n!). Nobody knows a fast exact algorithm, and many think none exists. Chapter 10 shows how to get a good-enough answer quickly.
