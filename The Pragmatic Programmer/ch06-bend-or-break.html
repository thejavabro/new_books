Bend, or Break

Code that bends with change survives. Loosen the joints: fewer chains of calls, less global state, data that flows through transformations, and behaviour you can configure.

Code that bends instead of breaking

Bridges should be rigid: every link locks the others in place. Software should be the opposite. We want it to bend with change, and the thing that makes code rigid is coupling, links that force one part to change when another does. This chapter is about loosening the joints.

In a truss, pushing one joint moves everything. In a chain, each link can move on its own.

Train wrecks: tell, don't ask

Code that reaches through object after object (customer, then orders, then find, then totals, then fields) knows a lot about how other things are built. All of that knowledge has to stay true for the code to work. Now the business says no discount may exceed 40%. Where does that rule go? If any code anywhere can poke at the totals' fields, you can never be sure you enforced it.


  
Tip 45Tell, Don't Ask
Tip 46Don't Chain Method Calls

  
The one-dot rule has a big exception: chains over things that are really, really unlikely to change, like the language's standard collections. Treat everything in your own app, and especially third-party libraries, as likely to change. And a pipeline of functions passing data along is not a train wreck: it couples only on data formats, not on hidden internals.

  
The older Law of Demeter said a method should call only its own class's methods, its parameters, objects it creates, and globals. The authors now drop the global clause and summarise the rest as: one dot.

The evils of globalization

  
Every piece of global data acts as if it were an extra parameter on every function in the system. Change it and anything might break; read it and you've coupled to everything that writes it. Singletons with getters are still globals. So are external resources like a database everybody hits directly.

Transforming programming

  
Every program transforms data: input in, output out. Yet we rarely design that way, thinking instead in classes and modules. Thinking in transformations gives a cleaner picture. The Unix shell has done it for decades: to list the five longest files in a directory, pipe find into word-count into sort into tail.

  
find . -type f | xargs wc -l | sort -n | tail -5

  
Tip 49Programming Is About Code, But Programs Are About Data

one transformation at a time

    

    

  

  
Find transformations by starting with the requirement as one big box (input to output), then splitting it into steps. Repeat inside each step until the pieces are obvious. Language lacks a pipe operator? Chain function calls through intermediate variables. It reads fine.

  

    
# each step wraps results
# {:ok, value} or {:error, why}
read_file(name)
|> and_then(find_lines)
|> and_then(truncate)
# an error skips the rest

    
Error handling. Choose a representation that carries either a value or an error. Then either have each transformation pass errors through untouched, or build an and_then helper into the pipeline that only calls the next step on success. The happy path stays readable.

    
Why it's good. Data is no longer squirrelled inside objects that hoard it; it flows. That cuts coupling: any function can be used wherever its input matches.

Inheritance tax

  
Inheritance arrived with Simula 67 as a way to share code and to build type hierarchies. Both uses cause trouble. Subclass to reuse code and you're coupled to your parent, its parent, and every implementation detail they choose to change. Build type taxonomies and you soon need a class for every combination, and the tree turns into a wall-sized diagram.

Configuration

  
When code depends on values that may change after release, keep them outside the app: credentials for external services, logging levels, ports and hostnames, environment-specific validation limits, tax rates, site-specific formatting, licence keys. Then you can adapt without a rebuild.

  
Tip 55Parameterize Your App Using External Configuration

Static config files (YAML, JSON) are common, usually wrapped behind a thin API so the rest of the code doesn't care where values come from. The authors prefer configuration as a service behind an API: many apps share it, it can have access control and history, and values can change while the app runs. Code that can't adapt goes the way of the dodo.

  
Don't overdo itOne client made every field configurable: some 40,000 settings, weeks for the smallest change. And don't push a decision into configuration just to avoid making it. Try it one way and get feedback.
