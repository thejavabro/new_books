Nobody writes perfect code, including you. So code defensively against yourself: state contracts, crash early, assert the impossible, release what you take and take small steps.

You can't write perfect software

Nobody in the history of computing has written perfect software, and you won't be first. Accept it and turn it into an advantage. Good drivers drive defensively because they assume everyone else is reckless. Pragmatic programmers go further: they don't trust themselves either, and build defences against their own mistakes.

Tip 36You Can't Write Perfect Software
2

Design by contract

Bertrand Meyer's idea, from the language Eiffel: every routine has a contract that spells out the rights and responsibilities of the caller and the routine. If the caller meets the preconditions, the routine guarantees the postconditions and preserves the invariants. If either side breaks the contract, a remedy (usually an exception or termination) is invoked. Never a silent "best effort".

PreconditionWhat the caller must guaranteeThe routine's requirements. It's the caller's job to pass good data, never the routine's to cope with anything.
→ routine →
PostconditionWhat the routine guaranteesThe state of the world on exit: a sort routine returns a sorted array. No infinite loops allowed.
Class invariantA condition that is always true from the caller's point of view. It may be broken briefly inside a method, but must hold again by the time control returns.

Contract checker: withdraw(account, amount)

try calls that break each part
def withdraw(acct, amount):
    require amount > 0 and amount <= acct.balance     # pre
    old = acct.balance
    acct.balance -= amount 
    ensure acct.balance == old - amount              # post
    invariant acct.balance >= 0                     # class
Tip 37Design with Contracts

Write "lazy" code: be strict in what you accept before you begin, and promise as little as possible in return. A contract that accepts anything and promises the world means a lot of code. Some languages let you encode preconditions directly: function clauses or guards that simply can't be called with out-of-range values.

Contracts vs testsYou need both. Contracts need no setup or mocks, describe success and failure for all cases rather than one example, and run forever: in design, development, deployment and maintenance, not just at test time.
Semantic invariantsRequirements so central they are laws, not policies. The authors' debit-card switch had one: never apply the same transaction twice. "Err in favour of the consumer." Write such laws where everyone can see them.
3

Dead programs tell no lies

It's tempting to think "that can't happen" and move on. When something does go wrong, the worst outcome is a program that keeps running with corrupted state: writing bad data to the database, charging the wrong amount, telling lies. Usually a dead program does far less damage than a crippled one.

Catch and release is for fish

# Let exceptions travel up to code

Catching an exception only to log and re-raise adds noise and couples this code to everything its callees might throw. Erlang and Elixir push the idea all the way: let processes fail, and let a supervisor restart them cleanly.

4

Assertive programming

"This code won't be used 30 years from now." "This app will never run abroad." "This count can't be negative." Every programmer has thought these. Whenever you catch yourself thinking "but of course that could never happen," add code to check it. An assertion is the cheapest way.

Tip 39Use Assertions to Prevent the Impossible

Which assertions are sound?

  • Not a substitute for error handling. Assertions check things that should never happen. A user typing a bad date isn't one of them.
  • No side effects. An assertion that changes state (calling iter.next() inside it, say) creates a bug that appears or vanishes depending on whether assertions are on: a "Heisenbug".
  • Leave them on in production. "Turn them off for speed" assumes testing found all the bugs and that production is gentler than test. Production is the harshest environment there is. If a particular assertion is genuinely too slow, disable just that one.
5

How to balance resources

Memory, files, locks, transactions, connections: all follow a pattern. Allocate, use, release. Most problems come from forgetting the last step or doing it in the wrong place.

Tip 40Finish What You Start

The routine (or object) that allocates a resource should release it. In the book's example, one function opens a customer file and stores the handle; a different function writes and closes it. A later change adds a branch that skips the write, and the file is never closed. The fix: one routine opens, calls helpers, then closes.

If allocation itself throws, the left version tries to release something that was never allocated. Allocate first, then guard. Better still, use scoped constructs (with, RAII, Rust ownership) that tie the release to the scope. Can't balance it neatly, as with long-lived data structures? Give each structure a clear owner, and build wrappers that track allocations so tests can check the books balance.

6

Don't outrun your headlights

Low-beam headlights light up about 160 feet. Stopping from 40 mph takes about 189 feet, and from 70 mph about 464 feet. It's easy to drive faster than you can see. In software, our headlights are feedback, and its range is short.

lit: 160 ft

Tip 42Take Small Steps, Always

The rate of feedback is your speed limit. REPL results confirm your understanding of an API, unit tests confirm your last change, demos confirm a feature. A task is too big when it needs fortune-telling: estimating dates months out, designing for imagined future extensions, guessing users' future needs or which technology will be around.

Within the headlights, or fortune-telling?

Tip 43Avoid Fortune-Telling

Black swans (rare, unpredictable, high-impact events) dominate history. Around the first edition, people argued over which desktop GUI toolkit would win. Neither did; the browser took over. Instead of designing for a future you can't see, make code replaceable.
