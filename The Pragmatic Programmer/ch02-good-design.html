The Essence of Good Design

One value sits under almost every design rule: make things Easier To Change. Four topics show what that means for knowledge, coupling and decisions.

1

Good design is easier to change

Design advice comes in endless acronyms and lists. The authors boil it down to one value: a thing is well designed if it adapts to the people who use it, and for code that means it can change. ETC: Easier To Change. Nearly every design principle you know is a special case of it.

Tip 14Good Design Is Easier to Change Than Bad Design

Every principle reduces to ETC

tap a principle

ETC is a value, not a rule: something that nudges you when choosing between paths. Train it deliberately for a while: every time you save a file, write a test or fix a bug, ask "did I just make the system easier or harder to change?" (One suggested trick: have your editor pop up ETC? on save.)

What if you can't tell which path is easier to change?

1 · Make it replaceableIf you don't know what form change will take, make this chunk easy to swap out. That's just decoupling and cohesion, which you should be doing anyway.
2 · Grow your instinctsWrite the fork in your engineering daybook and leave a tag in the code. When the change finally comes, look back and grade your guess.
2

DRY: the evils of duplication

Programmers are always in maintenance mode: requirements shift, regulations change, our understanding grows day by day. When knowledge changes, we have to find every place it lives. If it lives in five places, sooner or later we will update four.

DRY is about knowledge, not textEvery piece of knowledge must have a single, unambiguous, authoritative representation within a system. The test: when one facet of the code must change, do you find yourself making that change in several places, in several formats (code, docs, schema, tests)?

Where duplication hides

Same code is not always the same knowledge

Two functions with identical bodies are not automatically a DRY violation. If they validate different things that happen to share rules today, merging them couples two ideas that will diverge. That's coincidence, not duplication. Sort these:

Duplication or coincidence?

class Line:
    def __init__(self, start, end):
        self.start, self.end = start, end
        self.length = start.dist(end)  # stored copy
# Caller changes .start, .length is now a lie
class Line:
    def __init__(self, start, end):
        self.start, self.end = start, end
    @property
    def length(self):   # derived
        return self.start.dist(self.end)

Length is knowledge already held by the two points. Derive it. If you must cache it for speed, keep the cache private so only the class has to keep it straight, and expose everything through accessors (Meyer's Uniform Access principle: callers can't tell stored from computed).

Tip 16Make It Easy to Reuse

Interdeveloper duplication, two people unknowingly writing the same thing, is the hardest kind to spot. The cure is social: a culture where it's easier to find and reuse than to rewrite. Talk often, keep a forum or channel for questions, appoint someone as a librarian of shared code, and read each other's code.

Orthogonality

Two lines are orthogonal if moving along one doesn't move you along the other. In software: changing one thing doesn't affect unrelated things. A database layer shouldn't care about the UI; changing the UI shouldn't touch the database.

A real helicopter's four controls are anything but independent: change one and you must correct the other three. Nonorthogonal software is the same: every change ripples, and every fix needs another fix.

Tip 17Eliminate Effects Between Unrelated Things

The orthogonality test

pick a requirement that changes

"If I dramatically change the requirements behind one function, how many modules are affected?" In an orthogonal system the answer is one.

Why bother

Productivity: changes are localized, so development and testing time drop. Small self-contained parts get designed, coded, tested and then forgotten. And they combine: if A does M things and B does N, together they can do M×N.

Less risk: sick code is quarantined. A fix in one module doesn't spread symptoms. Tests are easier, and you're less tied to one vendor.

How, day to day

  • Design in layers, each using only the abstractions below it.
  • Toolkits: prefer libraries that don't force you to change your code (persistence should be transparent).
  • Keep code decoupled: shy modules that reveal nothing unnecessary.
  • Avoid global data: pass context explicitly.
  • Avoid similar functions: shared structure hints at a missing abstraction.
  • Testing is a check: a unit test that drags in half the system is a symptom.
  • Bug fixes: does the fix touch one module or many?

DRY and orthogonality are a pair: DRY minimises duplication within the system, orthogonality reduces the interdependency among its parts.

4

Reversibility: there are no final decisions

Engineers like singular answers, and so do spreadsheets. But every critical decision commits you to a smaller target: a narrower slice of reality with fewer options. Make enough irreversible choices and when the target shifts, you miss by a mile. "But you said we'd use database XYZ! We're 85% done!"

Flexible architecture, too

Server-side "best practice" has swung from big iron, to federations of big iron, to clusters of commodity boxes, to cloud VMs, to services, to containers, to serverless, and partly back again. You can't predict the next swing. You can make it cheap to follow: hide third-party APIs behind your own layers, and break code into components even if you deploy them together. Splitting a monolith later is much harder.
