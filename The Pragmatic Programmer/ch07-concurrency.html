Concurrency

Time is a hidden dependency. Find what can happen at once, stop sharing mutable state, and let independent actors or a shared blackboard do the coordinating.

1

Concurrency and parallelism

Two terms first. Concurrency is when pieces of code act as if they run at the same time: a software mechanism (fibers, threads, processes). Parallelism is when they really do run at the same time: a hardware matter (several cores, several machines). Everything worth doing today needs some of both, because the world is asynchronous: users, networks, sensors and timers all happen at once.

Temporal couplingCode that assumes A always happens before B, when nothing actually requires it. Breaking those false orderings is the first topic.
Shared stateTwo pieces of code referencing the same mutable data. That's where the hard bugs live, and the second topic.
2

Breaking temporal coupling

Requirements are often written as a list of steps, so code follows them one by one. But a list implies an order that may not exist. An activity diagram shows what really depends on what: rounded boxes for actions, arrows for "must finish before", and a bar where several actions must all complete.

Tip 56Analyze Workflow to Improve Concurrency

The robotic piña colada

Diagrams show where concurrency is possible, not whether it's worth it. A bartender would need five hands to start everything at once. The real win is spotting activities that take time but not time in your code: the one-minute liquefying, a database query, a call to an external service, waiting for the user. While those run, do something useful.

The authors' own book build is an example: each processor in the text pipeline runs concurrently, and slow equation conversions (up to half a second each) run in parallel processes, one per formula.

3

Shared state is incorrect state

A diner. Two customers ask two waiters if there's any apple pie. Both waiters glance at the display case, see one slice, and promise it. One customer is going to be disappointed. In code, "look at the count, then take a slice" is two steps, and another process can run in between.

Tip 57Shared State Is Incorrect State

Step through the race

pie in case: 1

Multiple resources

The diner adds ice cream. Pie à la mode needs both, so the waiter takes a slice, then finds no ice cream, and has to put the pie back. Two separate atomic operations don't make one atomic operation. The book's fix is to model the combination as its own resource that grabs both or neither.

It isn't only memory. Files, databases, external services, even a printer can be shared state. And because the timing changes between runs, these bugs look random.

Tip 58Random Failures Are Often Concurrency Issues
4

Actors and processes

An actor is an independent virtual processor with its own private state and a mailbox. It sleeps until a message arrives, handles it (maybe changing its state, creating actors or sending messages), then waits again. A process is a more general version, often with OS support. Nothing is in charge, nothing is shared, and the only state is in messages and each actor's local data.

Tip 59Use Actors For Concurrency Without Shared State

The diner as actors

only the pie case actor touches the pie count
slices: 3

Because the pie case handles one message at a time, it can never double-promise. No locks, no explicit concurrency in the code at all. The same actors can run on one core or many machines. Erlang (and Elixir on the same runtime) built a whole platform on this idea, with lightweight processes and supervisors that restart failed ones.

5

Blackboards

Picture detectives on a murder case, posting clues on a shared blackboard. No detective needs to know the others exist; they watch the board and add what they find. Different experts come and go, on different shifts, and anything can go on the board. Gradually the facts add up to a conclusion. It's laissez-faire concurrency.

Tip 60Use Blackboards to Coordinate Workflow

A loan application blackboard

facts arrive in any order
Agents post facts. Rules watch the board and post conclusions when their inputs appear.

In a loan workflow, credit checks are slow, names are instant, some data is gathered by people in other offices, and the law changes by region. Hard-coding that flow is a nightmare. With a blackboard, each new fact triggers whichever rules care about it, and new rules can be added without touching the others. Modern messaging systems (Kafka-style event logs, pub/sub buses) can act like blackboards: persistent, ordered, queryable. The cost: it's harder to reason about, so log everything and keep a common message format.
