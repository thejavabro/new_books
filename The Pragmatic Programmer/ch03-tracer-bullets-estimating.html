Tracer Bullets, Prototypes and Estimates

How do you aim when the target keeps moving? Build a thin working path end to end, throw away experiments on purpose, speak the domain, and estimate in honest ranges.

Tracer bullets: find the target in the dark

There are two ways to fire a machine gun at night. You can compute everything up front (range, wind, elevation, ammunition) and then fire blind and hope. Or you can load tracer rounds that glow along their path, watch where they land, and adjust. In software, the first is the big specification followed by a big build. The second is tracer code.

Tip 20Use Tracer Bullets to Find the Target

Tracer code is a thin, real path through every layer of the system: UI to logic to storage and back. It is lean but complete, and it's production code with error checks, structure and tests. You don't throw it away; you flesh it out.

Tracers don't always hit. That's the point: when one misses, you adjust. A small, working skeleton is cheap to correct and shows you how close you are.

2

Prototypes and Post-it notes

Car makers build clay models, wind-tunnel models and sometimes just a wooden mock-up of a dashboard. Each answers one question cheaply. Software prototypes do the same: explore a specific risk, then get thrown away. You can prototype with code, but also with Post-it notes on a whiteboard, a drawing tool or an interface builder.

Tip 21Prototype to Learn

Good things to prototype

  • Architecture
  • New functionality in an existing system
  • Structure or contents of external data
  • Third-party tools or components
  • Performance issues
  • User interface design

Things you can ignore

  • Correctness: dummy data is fine
  • Completeness: one input, one path
  • Robustness: it may crash off the happy path
  • Style: little documentation, if any

For architecture, you can skip code entirely: arrange Post-it notes for components and ask whether responsibilities are well defined, collaborations clear, coupling minimal, and duplication absent. Every module should have an access path to the data it needs, exactly when it needs it.

The trapMake sure everyone knows the prototype is disposable. Polished demos look finished, and somebody will try to ship them. If that risk is real, use tracer code instead, or prototype in a language or medium that can't be shipped.

Domain languages: program close to the problem

The limits of a language shape how you think. Sometimes the best code reads in the vocabulary of the users: test specs that read like sentences, routes that read like a map, infrastructure as a declarative recipe.

Tip 22Program Close to the Problem Domain

A toy domain language for a greenhouse

edit the rules, move the sensors

This is an external language: its own syntax, read by a small parser (about 15 lines of JavaScript on this page). Try breaking a rule to see the parser complain.

Don't spend more effort than you savePrefer off-the-shelf external formats (YAML, JSON, CSV). If they don't fit, try an internal language. Build your own external language mainly when the application's users will write it. And there's a cheap internal option: just write well-named functions so calls read like the domain, as test frameworks such as RSpec do.

Estimating

Estimating is a skill you can learn, and it helps everywhere: will this fit in memory? Is this design fast enough? How long will this take? The aim isn't precision, it's avoiding surprises.

Tip 23Estimate to Avoid Surprises

Your units say how sure you are

slide the duration
"about 2 weeks"

"130 working days" sounds accurate to within a day. "About six months" says plus or minus a month or so. Choose units that match the accuracy you mean to convey. Roughly: up to 15 days, quote days; 3 to 6 weeks, weeks; 8 to 20 weeks, months; beyond that, think hard before quoting at all.

Painting the missile: ranges, not single numbers

Ask a painter how long the house will take and you'll hear a range: maybe 10 hours if all goes well, more like 18, up to 30 if it rains. The PERT method, created for the Polaris submarine project, formalises this with optimistic, most likely and pessimistic values. The authors like the honesty of ranges but warn against wall-sized PERT charts that feel accurate just because a formula produced them.

PERT expected (O + 4M + P) ÷ 618.7 h

Eating the elephant: iterate the schedule

Often the only way to know the timetable of a project is to gain experience on that project. Work in thin slices (check requirements, analyse risk with the riskiest first, design-implement-integrate, validate with users) and refine the estimate after each iteration.
