The Basic Tools

Tools amplify talent. A small kit you know deeply, built around plain text, beats a drawer full of gadgets you half understand.

1

Every craftsperson starts with tools

A woodworker begins with a small set of good, basic tools and adds new ones only when a real need appears. Over time the tools become extensions of their hands. Programmers are the same: tools amplify talent, and the better you know them, the more productive you are. This chapter's kit is deliberately basic and centred on one theme: plain text, because everything else can work with it.

2

The power of plain text

Our base material is knowledge, and the best format for storing it durably is plain text: printable characters people can read and understand directly. Structured is fine (HTML, JSON, YAML); obscure is not. Binary formats divorce the data from its meaning, so when the program that understood them dies, the data dies with it.

Plain text is also the lowest common denominator between systems built in different languages on different platforms: the Unix philosophy of small tools joined by text streams.






  
3
Shell games

  
For a programmer working with text, the command shell is the workbench. GUIs are great until you want to do something the designer didn't anticipate: what you see is all you get. In a shell you combine small tools into pipelines that answer questions nobody built a button for.

  
Tip 26Use the Power of Command Shells

  

    
Build a pipeline
"which endpoints fail most?"

    

    

    

    
Toggle stages on and off. Each one reads text and writes text, so any of them can follow any other.

  

  
Make the shell your own: colour themes, a prompt that shows the branch, aliases and shell functions for chores you repeat, and command completion. Every bit of friction you remove is time back.






  
4
Power editing

  
Pick one editor and become fluent: so fluent you don't think about editing at all. The authors' point isn't the keystrokes saved; it's that once the mechanics disappear, your mind stays on the problem. Fluency also means growing the editor: when you notice yourself doing something repetitive, find or write an extension.

  
Tip 27Achieve Editor Fluency

To get there: watch yourself. Every time you repeat something tedious, look up the better way, then deliberately use it until it's muscle memory. A couple of new moves a week adds up.






  
5
Version control: a giant undo key

  
Version control is a project-wide time machine. It lets you go back to last week's working code, see who changed what and why, build any past release, and work on parallel branches. A shared network directory is not version control: people clobber each other's changes and nothing is recoverable.

  
Tip 28Always Use Version Control

  

    
Thought experiment: tea over the laptop
what lives in version control?

    
Tap everything you keep in a repository. Then spill.

    

    

    

  

  
The authors keep everything under version control, including dotfiles, editor config, the list of installed software and machine setup scripts, so a new machine is a clone and a script away. And the repository can be the project's hub: pushes trigger builds, tests and deployments (more in Chapter 9).






  
6
Debugging

  
Debugging is just problem solving. Start with the right mindset: nobody wrote perfect software, so it's no surprise there's a bug. Don't blame; don't panic. Turn off your ego, think, and keep the user-visible symptom separate from the cause.

  
Tip 29Fix the Problem, Not the Blame
Tip 30Don't Panic

Release 1 (commit 0) worked. Release 2 (commit 63) is broken. Tap commits to test them. Linear search could take 63 tests; halving needs about 6.

    

    

  

  
Binary chop works on more than commits: halve the stack trace, halve the input data, halve the steps that reproduce the crash. Tools like git bisect automate the commit version.

7
Text manipulation

  
Shell tools are the router; a text-manipulation language like Python, Ruby or Perl is the lathe. Learn one well enough to knock out a script in minutes, and a whole class of chores becomes cheap: generating code, converting data, building docs. The authors build their own books this way: scripts pull code samples into the text, highlight them, update the website and build the index.

Engineering daybooks

  
Keep a paper notebook beside you. Write down what you did, what you learned, sketches of ideas, readings from meters, phone numbers. Paper, not a wiki: the act of writing by hand is different from typing.
