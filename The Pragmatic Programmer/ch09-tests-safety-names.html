Test to code

A bold claim to start: testing is not about finding bugs. The big benefits arrive when you think about and write tests, not when you run them. Writing a test forces you to ask how the code will be used, what it depends on, and how you'll know it works. That's design feedback.

Tip 67A Test Is the First User of Your Code

Hard to test? That's the design talking

try writing a test for each version
def load_report():
    rows = Database().query(...)   # hidden dependency
    today = datetime.now()         # hidden clock
    return format(rows, today)
def load_report(rows, today):
    return format(rows, today)

# test: no database, no clock
assert load_report(FAKE_ROWS, DAY) == EXPECTED

To test the left version you'd need a live database and a frozen clock. The test pushed us to pass dependencies in, which also made the code less coupled.

Test-driven development, without the dogma

Write a failing testSee only it failSmallest code to passRefactor, still green

The cycle should take minutes. It guarantees you always have tests. But the authors warn against becoming a TDD slave: chasing 100% coverage, writing redundant tests (a test that only references a class name), and designs that grow bottom-up without knowing where they're heading. Remember the tale of the developer who TDD'd a sudoku solver and never solved a sudoku: TDD needs you to know where you're going.

Tip 68Build End-to-End, Not Top-Down or Bottom Up

Unit tests against the contract

A unit test exercises a module in isolation, and its natural checklist is the module's contract. For a square-root function: negative arguments are rejected, zero and the maximum value work, values in between give a result whose square is close to the input. Then test modules that use it, once its own tests pass.

Build a test windowEven well-tested code meets surprises in production. Design in ways to look inside: log files in a regular format, a hot-key diagnostic view, a status page. Ad hoc poking around is fine too, but capture anything you learn as a new test.
A culture of testingYou can test first, test during, or test never. "Test later" is test never. Treat test code with the same care as production code: decoupled, clean, robust, not reliant on unreliable things.

Property-based testing

When you write both the code and its tests, your assumptions appear in both. The tests then confirm what you already believed. Property-based testing breaks the loop: you state a property (an invariant that must always hold, like a contract) and let the computer throw hundreds of generated inputs at it. When one fails, the framework shrinks it to the smallest failing example.

Naming things

  
Names are how code tells readers what it means. And readers trust them: your brain treats written words with great respect. Try it.

  

    
The Stroop effect

    

    
Round 1: tap the word as written. Round 2: tap the ink colour.

    

    

  

  
Reading wins over seeing. So a misleading name actively fights the reader. Name things for their role and intent, not their type or mechanics.

  
Pick the better name

  

    
Honor the culturei, j, k are fine loop counters in C, odd in Clojure. Use camelCase or snake_case as the community does.

    
Be consistentEvery project has jargon. Keep a project glossary (a wiki page or index cards) and pair often so the vocabulary spreads.

  

  
Renaming is even harder than naming. Meanings drift; a routine called getData ends up writing to an archive. Misleading names are worse than meaningless ones. When you spot one, fix it now; if you can't, that's an ETC problem to fix first. (Project code names are the exception: clever, obscure names are a fine tradition there.)
