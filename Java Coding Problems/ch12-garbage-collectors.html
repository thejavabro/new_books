Garbage Collectors and Dynamic CDS Archives

The garbage collector decides how long your program pauses and how much memory it uses. Learn the stages, the generational idea, how G1 and ZGC differ, and how CDS archives speed up start-up.

What a garbage collector actually does

The GC's goal is to reclaim memory from objects no one can reach, without the program noticing too much (P243). Most collectors combine three stages (P244): mark everything reachable from the roots (stack variables, static fields), sweep the rest, and compact the survivors so free space is one block and allocation is a pointer bump. Step through a tiny heap.

2

The generational idea: most objects die young

The weak generational hypothesis: most objects die soon after they are created, and the few that survive tend to live long. So the heap is split. New objects go to eden; a cheap, frequent minor GC copies the survivors of eden and one survivor space into the other survivor space and ages them; objects that survive enough minor GCs (the tenuring threshold) are promoted to the old generation, which is collected rarely (P246). 3

Choosing and categorizing collectors

Every collector trades throughput (share of time doing your work), latency (pause length) and footprint (memory overhead); you cannot max all three (P247–P248). Say what matters and see the usual recommendation.

4

G1: garbage first, region by region

G1 (the default since JDK 9) cuts the heap into equal regions (1–32 MB), each currently playing eden, survivor, old or humongous (one object bigger than half a region) (P249). It tracks how much garbage each old region holds, and in a mixed collection it evacuates the regions with the most garbage first, as many as fit the pause target -XX:MaxGCPauseMillis (default 200 ms). Recent JDKs improved its throughput, latency and footprint (P250–P252). Red fill shows garbage.

5

ZGC: colored pointers and load barriers

ZGC (production-ready in JDK 15, generational in JDK 21) does almost everything concurrently, so pauses stay under a millisecond regardless of heap size (P253). Two tricks make that possible. Colored pointers: each 64-bit reference uses some bits for the address and a few for metadata (marked0, marked1, remapped, finalizable). Load barriers: a few instructions the JIT inserts wherever the app loads a reference, which check the color and, if the object has moved, fix the pointer on the spot. Step through a relocation.

Blue: 44 address bits (16 TB). Orange: the 4 metadata bits. Grey: unused, reserved (the book's figure shows the original non-generational layout).

6

Monitoring, logging and tuning

Measure before tuning (P254): jstat -gc <pid>, JDK Mission Control, or GC logs. Since JDK 9 all logging goes through unified logging, -Xlog (P255). Build a logging flag, then look at the main knobs per collector (P256).

7

Class Data Sharing: a faster start

At startup the JVM loads, parses and verifies thousands of classes. Class Data Sharing stores that work in an archive that is memory-mapped on the next run, and shared between JVMs on the same machine. The JDK ships an archive for its own classes; AppCDS adds yours (P257). Compare start-up.
