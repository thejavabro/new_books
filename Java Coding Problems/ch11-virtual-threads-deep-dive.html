Continuations: the engine under virtual threads

A virtual thread is a continuation plus a scheduler (P225). A continuation is a piece of code that can suspend itself with yield, saving its stack, and later resume exactly where it stopped when someone calls run again. The JDK's class is internal (jdk.internal.vm.Continuation, reachable with --add-exports), but stepping through it shows the whole trick.

Virtual thread states and transitions

  
Internally a virtual thread has more states than Thread.State shows (P226). The interesting fork is after PARKING: if the stack can be moved to the heap, the thread is PARKED and its carrier is free; if not, it is PINNED and the carrier waits with it. Extending and assembling StructuredTaskScope

  
ShutdownOnSuccess and ShutdownOnFailure are final, but StructuredTaskScope itself can be extended by overriding handleComplete(Subtask), which runs as each subtask finishes (P227). Scopes can also be nested and assembled: an outer scope forks subtasks that open their own inner scopes (P228), and joinUntil(deadline) adds a timeout (P229).

  
class BestPriceScope extends StructuredTaskScope<Offer> {
    private final Queue<Offer> offers = new ConcurrentLinkedQueue<>();
    @Override protected void handleComplete(Subtask<? extends Offer> s) {
        if (s.state() == Subtask.State.SUCCESS) offers.add(s.get());
    }
    Offer best() { return offers.stream().min(comparing(Offer::price)).orElseThrow(); }
}
try (var scope = new BestPriceScope()) {
    sellers.forEach(id -> scope.fork(() -> fetchOffer(id)));
    scope.joinUntil(Instant.now().plusMillis(500));   // TimeoutException if too slow
    return scope.best();
}

ThreadLocal vs ScopedValue

  
ThreadLocal gives each thread its own mutable copy, forever, unless you remember to remove(); InheritableThreadLocal copies the whole map into every child thread. With millions of virtual threads that is a lot of memory and a lot of leaks (P230). ScopedValue (preview in JDK 21) binds an immutable value for the duration of a call, visible to everything that call runs, then it is gone (P231). Bindings can be nested to rebind (P233), and are inherited by subtasks forked in a StructuredTaskScope (P234). Step through.

  

    
static final ScopedValue<String> USER = ScopedValue.newInstance();

ScopedValue.where(USER, "ana").run(() -> {
    handle();                              // USER.get() == "ana"
    ScopedValue.where(USER, "admin").run(() -> {
        audit();                           // "admin" (rebinding)
    });
    try (var scope = new StructuredTaskScope<>()) {
        scope.fork(() -> report());        // forked: still "ana"
        scope.join();
    }
});
USER.isBound();                            // false: binding gone

    

  

  

  
P232: scoped values are not inherited by tasks submitted to an ordinary ExecutorService; bind the value inside the task, or use a structured scope.

Limit concurrency with a Semaphore, not a pool

  
With platform threads, a fixed pool doubled as a limit on how many tasks hit the database at once. Virtual threads should not be pooled, so express the limit directly: a Semaphore with N permits (P235). Launch 12 virtual threads against a database that tolerates a few connections.

Pinning: when a virtual thread can't let go

  
In JDK 21 a virtual thread that blocks inside a synchronized block (or a native call) cannot unmount: the monitor is tied to the carrier. It is pinned, and the carrier is blocked with it. With few carriers, a handful of pinned threads can stall everything. The book's fix is to use a ReentrantLock, which parks properly (P236). Run 8 tasks that each hold a lock while waiting on I/O for 3 ticks, on 4 carriers.

P237–P239 solve the producer-consumer problem with a BlockingQueue and virtual threads, then control it: a Semaphore caps active consumers, and a monitor adds or removes consumers as the queue grows or shrinks. Tune the rates and watch the queue.
