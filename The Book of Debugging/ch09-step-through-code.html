Step Through the Code

The debugger lets you watch the program think. To get the most out of it you need to know what optimisation does to your view, which kind of breakpoint to use, and how to read stacks, variables and even assembly.

Debug builds, release builds, and what optimisation hides

Examining starts with the debugger: run the program, stop near the entry point, and watch. To see clearly, use a debug build. The editor's unit is the line, but the CPU executes instructions, and an optimising compiler rearranges, merges, hoists and deletes them. In an optimised build the execution pointer jumps around, breakpoints silently move to another line, and variables show as "optimised away". Compare the same function both ways.

Locals

Builds can also behave differently on purpose: compile-time switches swap implementations, add checks or change memory layout, so a bug may show only in one configuration. Default to debug builds; if a bug only lives in release, use a release build with debug info, or switch optimisation off just around the code you need (for example with a pragma in Visual Studio).

Step over, step into, step out

Once paused somewhere relevant, move carefully: step over runs the current line, step into enters the function it calls, step out finishes the current function and returns to the caller. Run to cursor (or a breakpoint further down) skips ahead. Watch the call stack and the locals as you go. Find the bug in this small program: the total should be 50 (orders of 50 or more ship free).

4

Read the call stack like a story

When the program pauses, the highlighted line says where you are; the call stack says how you got there. Each frame is a decision that was taken: if ApplyDiscount sits above Checkout, then whatever if guards that call must have been true. Look at the other threads' stacks too, especially when work is spread over several.

Stacks can be corrupted, typically by a stack overflow from infinite recursion, or by a buffer overrun on the stack. Then the frames are garbage and you work from other evidence.

Conditional breakpoints pause only when a condition holds, which is handy for code that runs thousands of times. But condition editors are fiddly, lack code completion and can be slow. The book's preference: write the if in code with a plain breakpoint inside, and delete it before committing.

Examine the data, by lifetime

Data drives control flow, so at every pause look at what the code references. Different kinds of variables live for different spans, which tells you who else could have changed them.

6

Who wrote to this memory?

A data breakpoint stops execution the moment the bytes at an address change, which answers "who is overwriting my value?" directly. Addresses change between runs, so you set them up again each time, typically by first breaking where the variable is created. Watch windows evaluate expressions; visualisers (such as Natvis files) make your own types readable; you can even move the execution pointer to re-run a line, though that does not undo side effects.

Drop down to the assembly view

One innocent line can be many instructions (a declaration such as SomeClass obj; runs constructors for the class and every member), and any of them can be the one that fails. The assembly view lets you step instruction by instruction. You do not need to be fluent; a handful of x86 mnemonics covers most of what you will read. Tap an instruction.

8
Make sure you are debugging the right program

  

    

      
The program you launch is not always the one doing the work. Launchers check for updates and then start another executable, build systems call compilers with long generated command lines, and the arguments that matter may never be visible to you. Let the launcher run, then find the real process and its command line with the OS tools (ps on Unix-like systems, a tool such as Process Explorer on Windows), and launch or attach to that one directly.

      
Attaching after the fact is also a cure for bugs that hide from debuggers: one remote program behaved differently with a debugger attached because the log was routed differently. Reproduce first, attach second, and examine the fallout.
