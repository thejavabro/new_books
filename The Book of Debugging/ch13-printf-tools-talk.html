Debug with printf, Use Off-the-Shelf Tools, Talk It Through

Print statements are crude but run everywhere. Specialist tools see what you cannot, from memory errors to network packets. And explaining the bug out loud, even to a duck, often solves it mid-sentence.

1

printf debugging: crude, universal, useful

Printing text works almost everywhere, needs no debugger, and shows how data evolves over time. It is not the default tool, because every new question means editing code, rebuilding and rerunning, and printing changes timing, which can hide the very bug you are chasing. But it shines in three cases: when no usable debugger exists for the language, framework or device; when the debugger changes the bug's behaviour; and when you want to see a complex structure or a value's history that a debugger cannot show well.

"One more step away"A project with C++ logic and a Lua GUI debugged the GUI with prints for most of its life because setting up a Lua debugger looked expensive. When someone finally integrated one, it took less time than feared and helped with some bugs, yet prints stayed the everyday tool because the debugger was always one extra step away. Convenience wins; decide deliberately.
2

Write messages you can use

Since each build-deploy-run cycle is expensive and a print line is cheap, add prints generously around the suspect code, then fill in the gaps after each run. Make every message specific: a unique searchable tag, concrete values, where it came from, and how serious it is. Build one.

3

Sixty lines a second

Printing once per frame floods the output with 60 or more lines a second. The fix is the same as in production logging: severities, tags and filters. Logging libraries (spdlog, Quill or Boost.Log for C++; Serilog, NLog or log4net for C#; the standard logging module, Loguru or structlog for Python) add metadata, formatting, routing and filtering for you.

In compiled languages a macro can make low-severity logs cost nothing at all in optimised builds:

#define LOG(sev, ...) \
  if (sev >= kMinSeverity) printf(__VA_ARGS__)
// kMinSeverity is a compile-time constant:
// filtered calls generate no instructions

4

Logs in production, and cleaning up

Shipped builds usually log too, at a less detailed level, so the logs are there when a user hits a problem. Protect privacy: filter out passwords and personal data, or never record them in the first place, since laws may treat even IP addresses as personal data. Log services can store and search logs for server-heavy projects.

When the bug is fixed, review every print you added. Keep messages that help in an error case (concrete data, a clear severity) and remove noise, so unusual output still stands out. Then test again: removing prints is a code change too.

5

The specialist toolbox

The debugger is the most versatile tool, but specialists see what it cannot. Some are free, some cheap but needing approval, some enterprise-priced. A specialised tool does more of the interpretation for you than a general one, and many SDKs and frameworks ship their own tools, which you should check first. Match each problem to a tool.

A diff tool sees what you cannot

Two setting names look identical, yet one lookup fails. A good diff tool, or a hex view, shows the invisible: a trailing space, a non-breaking space, a zero-width character pasted from a web page. The book's own example of raw-data inspection: lighting on a new rendering backend was slightly off; dumping the normal-map texture data from memory into a file and opening it in a texture viewer showed the new platform had skipped a processing step.

7

Talk it through, even to a duck

Explaining a bug in detail exposes gaps in your knowledge and connections you had not noticed, the way the Feynman technique works for learning. Your goal is new leads: missing information and unseen correlations. This is different from asking for help; often the other side barely says a word.

8

Prepare the conversation

Logistics

Book real time without distractions. Pick a place that has what you need (sources, notes, a whiteboard) without killing focus; a video call limits you, so prepare screen sharing.

Content

Start with symptoms and reproduction, like a great bug report. Then what you know, what you ruled out, and your hypotheses. Notes and diagrams help.

During

Take questions any time, not at the end. Rephrase what you hear to check you understood. Write down points, even as comments in the code.

If you are the listenerUnderstand the symptoms, the reproduction and what has been ruled out. Listen actively, ask many questions, and make sure gaps get filled rather than glossed over.
