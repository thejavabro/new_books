Automate the Reproduction

A rare bug might need hundreds of attempts. A computer does not get bored, so let it do the repeating: script the steps, replay recorded input, or test the one function in isolation.

1

Is automation worth it?

If automating takes little effort, do it. Beyond that it is a judgment call, but the cases where it pays off are clear: many or slow steps, rare bugs that need dozens of attempts, steps that need precise timing or positioning, and any bug you will need to re-test after every attempted fix. A computer starts each step the instant it can, never misclicks, does not mind the hundredth try, and scales to a whole room of machines over a weekend. Play with the trade-off.

2

Leave it running overnight, but make it tell you

The big advantage is scale: one spare machine overnight, or many machines at once. The big caveat is easy to forget. The automation must notify you when the bug happens and leave you something to inspect: a debugger attached, logs, or a crash dump. A reproduction you cannot look into gains you nothing.

Ways to automate, from simple to thorough

MethodWhat it doesWatch out for
Start-up settingsCommand-line arguments or config files open the right screen, menu or component at launch.Gets you to the place, not through the interactive steps.
Hard-coded stepsCall the functions user input would trigger, or inject fake input, from inside the program. Full access, nothing in between."Paint 4,000 brush strokes" is easy for a person to describe and tedious to program. Each change needs a rebuild.
External scriptDrives the program from outside. Faster turnaround than hard-coding.Everything must be exposed to the script, and the extra layer can change whether the bug appears.
Record and replay inputCapture real input once, play it back on demand.Needs a deterministic program; any UI change can invalidate recordings.
Target the functionOnce the bug is isolated, call the faulty code directly with chosen arguments, as early as possible.Set up only the dependencies it truly needs.
Saved stateSerialize the program just before the bug, reload it every time.A state that was itself broken by an older bug can mislead you.
Reuse what you haveOne game team repurposed its enemy AI as an automated player: give it an ideal path through the level and a few triggers, and it could fight, solve simple puzzles and walk through missions. Not smart, but good enough to reproduce bugs without a human at the controls.
4

Record and replay, and how recordings break

Recording can live inside the program's input system, where you control it fully but must replicate input exactly, or at the operating-system level, where it works for any program and the program cannot tell replayed events from real ones.

Input is messier than it looks. Buttons are on or off, but analogue axes come in different ranges per device (one gamepad reports a trigger as 0 to 255, another as 0.0 to 1.0), devices connect and disconnect mid-session, and several events can arrive in the same instant. A recording that ignores any of this may fail to reproduce the bug.

5

Call the suspect function directly

When you have narrowed the bug to one function, skip the user entirely: call it at the very start of main() with chosen inputs, or loop over a range of inputs to find the bad ones. If it fails randomly, call it in a loop until it does; if timing is involved, call it at different moments. Here is a deliberately buggy path joiner, the kind of "simple" function that hides edge cases.

function joinPath(a, b) {
  if (a.endsWith('/')) return a + b;
  return a + '/' + b;
}
// call early, with many inputs
for (const [a, b] of cases)
  check(joinPath(a, b));

6

Jump in with saved state

Most bugs need the program in a particular state when a particular action happens. If you can save that state and reload it, every attempt starts one step before the bug. Programs that already serialize projects or progress are halfway there. Ask reporters for their saved state, or save one yourself the first time you get there.

Two real examples from the book: a tool whose first executable wrote a parameters file for the second, so saving that file gave an instant repro; and a game bug that needed a store unlocked and money earned, solved by saving right after reaching that point once.

If you cannot automate itThat is information too. It suggests a human factor such as specific timing or movement. And if a shortcut prevents the bug, the actions you skipped are the important ones; keep them in mind when looking for the fix.
