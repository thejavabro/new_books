Try Shortcuts and Search the Internet

Probing is about covering a lot of ground fast. Experience points you at likely culprits, and the rest of the world has probably met your error message before, if you know how to ask a search engine.

1

Shortcuts: jump, or rule out

Probing starts with the cheapest moves. Once you know where to look, your editor gets you there in a second; the hard part is knowing. Shortcuts use your experience to guess the right area, or to rule out large areas you do not need to look at. Either outcome narrows the search.

The trapShortcuts are seductive because they promise to skip the hard work. They fail when you keep trying one guess after another, or fixate on one lead. A colleague once spent days inside a mature, highly optimised networking library, convinced the HTTP bug was there. It was in how the project called the library. Well-tested code is rarely the culprit.

Time-box the guessing

Rule of thumb from the book: no more than about an hour on shortcuts, and switch strategy after two or three, or as soon as your guesses start to feel desperate.

2

Where educated guesses come from

Experience comes in layers, from the very specific to the very general. Even without programming experience you can treat the program as a black box and watch which inputs cause which problems. Tap a layer.

3

Experience in action: missed input

Some symptoms map to a short list of causes. Missing user input comes from low-level input handling, which works in one of two ways. A program that polls the key state each update misses presses that start and end between two polls. A program that listens to events often handles only one per button per tick and drops the rest. Knowing this leaves exactly two places to look.

Other pattern-matches from the book: a box or blank instead of a character means a non-ASCII character plus a font or decoder that does not support it; a freeze suggests a deadlock or an infinite loop; a file that cannot be written suggests a full disk or a read-only file.

4

Know your foundational APIs

Programs in the same domain call the same operating system, standard library, database and graphics APIs, so they fall into the same traps. One platform's audio call took a pointer, a length and a bit depth. The author passed the length in bytes; the API wanted the number of samples. With 16-bit samples that is twice the real data, so the sound was fine for a while, then turned into noise read from memory past the buffer.

void play_samples(void* data, size_t length, size_t sample_bits);

5

Suspicious systems, irrelevant systems

Poorly understood

Vague pre- and post-conditions invite improvisation, and such systems often sit between others (a threaded data processor feeding a GUI).

Complex

Networking: many preconditions, asynchronous results, latency. Hard to get right, easy to break.

Foundational

A task scheduler is used by everything, in every possible way, so it sees every edge case.

Two more signals: code with unusually heavy comments or internal docs (its author felt it needed explaining), and systems with a history of bugs, since fixes layered on top of a design you do not fully understand tend to breed more. In the other direction, systems with unrelated responsibilities usually do not talk to each other, so you can set them aside, starting your search with the relevant ones and only working outward if needed.

Rule systems in and out

Tap once to look here, twice to ignore, three times to reset. Then check.

6

Surprising dependencies

Systems you ruled out can still be involved. Memory corruption from one system scribbles random values into another, linking two parts of the program that have nothing to do with each other, and behaving differently from run to run. Shared foundational features do the same more quietly: task schedulers, threading primitives, file access, and random number generators.

C's rand() keeps one hidden global state. If physics and loot both draw from it, an extra call in physics changes every loot drop. Give each system its own generator.

7

Search the internet, precisely

For widely used technology, someone has probably hit your problem before. One example from the book: a one-header HTTP library produced a type-redefinition compile error for a socket struct. It looked like an afternoon of following headers; a search showed in a minute that one Windows socket header must be included before the other. Paste the error, but first strip what is unique to your machine: paths, addresses, counts and timestamps will never match anyone else's post.

Build a query

Your error: Failed to open C:\Users\sam\proj\cache\0x7ffd2a.bin: The process cannot access the file because it is being used by another process. (code 32)

8

Beyond the general search engine

General engines index social media poorly or not at all, so search those sites directly. Most technologies also have their own corners of the web; your intranet deserves a look too, since anything found there is about your exact code, and its author may still be down the hall. Source code is hard for search engines (they drop the special characters), so use a code-search service instead.
