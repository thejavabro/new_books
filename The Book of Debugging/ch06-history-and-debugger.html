Check Version Histories and Attach the Debugger

If it worked last week, the answer is in the history: find the change that broke it. And if you always run under a debugger, the moment the bug strikes you are already there to look.

1

Did it ever work? Then the answer is in the history

When a feature that used to work is now broken, some change in between broke it. Find a working version, compare it with the broken one, and the significant difference points straight at the related sources, sometimes at the fix itself. Start by asking the reporter, QA or other users when it last worked; it is worth adding "when did you last see this working?" to the bug report form. A freshly reported bug was probably introduced recently, so start with recent changes.

A story from the bookA report complained about poor performance across the board, right after a round of optimisations. The profiler showed no hot spot, just everything slower. The history revealed a colleague's commit that had accidentally included local debugging changes: optimisations disabled on several functions with a compiler attribute, so they could be stepped through in a release build.
2

Binary search through the commits

With no idea when it broke, use binary search: test the commit in the middle, keep the half that contains the change, repeat. git bisect automates the bookkeeping. Testing cost matters too: an existing binary build (from CI, milestones or QA) takes minutes, a source build much longer. Use binaries to narrow the range, then build from source for the last few steps. Find the commit that introduced the bug.

500 commits, oldest on the left. Blue underline = binary build exists.
$ git bisect start
$ git bisect bad HEAD      # commit 500 is broken
$ git bisect good v1.0     # commit 1 worked
3

Pin down the offending part of the commit

Commits rarely contain just one change. Once you have the guilty commit, find which part of it causes the bug and undo only that, keeping the improvements the author intended. Talk to the author if you can; they know why they made each change and may already suspect which one was risky.

4

Look into the future, and sideways

Somebody may already have fixed it: a later commit, a release branch, a feature branch nobody merged yet, or a fork of an open-source project. On big teams this happens more often than it should. With third-party products it is very likely, because others hit the same bugs. Read changelogs, ask for roadmaps or public trackers, and if you have the source, read the commits themselves.

The book's advice: always push for a source code licence. Without it, a bug in a closed blob means waiting for the vendor, and if the vendor disappears you are stuck for good.

Always run under the debugger

Make launching through the debugger your default. When something goes wrong you are already there: crashes stop at the faulting line with a call stack, exceptions can break the moment they are thrown, and breakpoints are a click away. The deeper reason is that code is only a template; execution fills it with actual values and decisions, and those are not always what you assume. Where to put your first breakpoints

  

    

      
Most bugs do not stop the debugger by themselves, so you place breakpoints in code you suspect. Start with a few functions close to where you think the bug is, at the very top of each function so early returns cannot skip them. Too many generic breakpoints high in the stack fire constantly and tell you little. If none hit, move up the call stack until one does, then step down into the functionality.

7
When the debugger is hard to get, or gets in the way

  

    
No debugger?
Worth real effort to get one: look for third-party tools, ask the platform vendor and community, report the gap to them, and only for long projects consider writing your own.

    
It hides the bug
A debugger can change timing and mask a race, or the program may detect it. Reproduce first, then attach and work backwards from the values you find.

    
It causes a crash
Do not work around it. Find out why the program fails under the debugger and fix that first; it will keep costing you otherwise.

  

  
Break on exceptionsManaged and scripted languages can break whenever a certain exception type is thrown, even if something catches it later. In native Windows code, structured exception handling exposes hardware faults such as access violations and division by zero. Stopping at the throw beats reading a stack that has already unwound.
