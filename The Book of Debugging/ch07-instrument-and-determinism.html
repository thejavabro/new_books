Instrument the Program and Remove Randomness

Make the program tell on itself with assertions and checked errors. Then hunt down the sources of randomness (time, threads, random numbers, input, network) so a one-in-fifty bug happens every time.

1

Assertions: fail where the assumption breaks

Instrumenting means changing the program, before you know what is wrong, so it reports problems itself. The cheapest instrument is an assertion: a check that a condition holds, which stops the program if it does not. Code is full of unstated assumptions (inputs are valid, a container has one element after a push, a sum of squares is not negative). Writing them down as asserts turns silent corruption into a loud stop. The trick is placement: assert as early as possible, so the program fails where the assumption is first violated, not three systems later.

A value goes bad in step 2

Tick asserts in any step, then run. Without them, the crash appears far from the cause.

// break into the debugger instead of exiting
#define ASSERT(cond, msg)            \
  if (!(cond)) {                      \
    printf("Assert: %s\n", msg);    \
    __debugbreak();                   \
  }

// checked at compile time
static_assert(sizeof(Header) == 16,
              "Header layout changed");

A good assertion reports the condition, file, line and ideally the values involved. Better still, under a debugger it should break like a breakpoint, so you can inspect the state right there and sometimes even continue to learn more. Static assertions check conditions at compile time in languages compiled ahead of time (C, C++, Rust, D).

2

Assert, or handle the error?

Asserts are for things that should never happen; error handling is for things that can happen in normal use. A caller passing a null filename is a programming mistake: assert. A file that cannot be opened is a fact of life: handle it, and signal the failure to the caller with an error code, enum, result type, optional or exception. Often you want both: an assert to catch it during development, graceful handling in the shipped build. And always check return values, even from the standard library. One environment-setup tool chased pending-reboot states with checks between every step, until the team noticed installers already report "reboot required" through exit code 3010.

Fill memory with patterns you will recognise

Fill data with obvious magic values and you can see at a glance whether code has run, what it changed, and whether something wrote past its boundary (use guard values, or fences, at the edges). Zero is a poor choice because it looks normal. Good magic values are odd (so they fault when used as addresses), make code that uses them behave strangely, and are invalid as instructions. Visual Studio's debug runtime is the familiar example: 0xCD for freshly allocated memory, 0xDD for freed memory, 0xFD for the guard bytes around each allocation. Set your debugger and logs to show hex so the patterns pop out.

Instrumentation can hide the bug

Every change you add to learn about the bug can change the bug. A log line shifts timing and can make a race disappear; extra code moves data in memory and can dodge a corruption. One team before a big launch had a bug that vanished under the debugger and vanished again when they added logging. Out of time, they shipped with the log statements in place as the "fix".

That worked by luck. Any later change could bring the bug back at a worse moment. Change as little as possible and confirm the bug still reproduces after every modification.

Keep it, but switch it off

Do not delete good instrumentation once the bug is fixed; bugs come back. Put it behind switches that are off by default in user builds (it costs performance and can leak internals), with per-system flags and one master flag.

#if INSTRUMENT_AUDIO || INSTRUMENT_ALL
  ASSERT(voices <= MAX_VOICES, "mixer overflow");
  LOG("voices=%d", voices);
#endif

A random bug has a non-random cause

Computers are deterministic, so a bug that seems random must depend on something that supplies varying values. Find that source and either disable it to make the bug reproduce every time, or follow it to the cause. Watch for patterns first: after a set number of minutes? Only with three keys held? Concurrency: the same program, different results

Two threads each add 1 to a shared counter many times. counter++ is really read, add, write; if both threads read the same old value, one increment is lost. The result changes from run to run, which is exactly what makes threading bugs feel random. Search for thread and lock primitives to find entry points, and if your task system allows it, force everything onto one thread while debugging. Expect slower runs and functions that wait on parallel work.

Fix the seed, fix the clock

A renderer bug only appeared in rain, and the weather was chosen at random on start-up and changed later. Forcing rain and disabling the change made it reproduce on every launch.

Pseudo-random generators are deterministic given their seed; seeding from the clock is what makes each run differ. Use a fixed seed, or return a constant, while debugging. If the program depends on random numbers for real features, own the algorithm: one procedural world generator produced different landscapes on different platforms because each platform's library implemented its PRNG differently.

Time itself is a source: array[time(0) % 11] = 0 writes out of bounds only some seconds. Pin the clock to a value, or start from the same instant, and use a fixed delta time (such as 16.6 ms) instead of a measured one.

Why fixed time steps matter: float addition is not associative

Same numbers, different order, different result. A variable time step changes the operations every run, so floating-point results drift apart; fast-math compiler options make it worse across platforms.

8

Put determinism to work

Follow it

If the bug comes and goes, its cause is linked to the randomness. Trace the data and logic dependencies from the source you found.

Trust the fix

With randomness disabled, "cannot reproduce" really means fixed, not "got lucky this time".

Compare runs

Now you can make a good run and a bad run on purpose and diff their logs or step through both.

You rarely need determinism everywhere, which is hard (every system, compiler, library, OS scheduler and float operation must cooperate). Make the area around the bug deterministic. And yes, very rarely the randomness is real: cosmic-ray bit flips, failing components, unstable power. Consider hardware only after everything else.
