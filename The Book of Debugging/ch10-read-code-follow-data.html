Read the Code and Follow the Data

Sometimes the fastest debugger is your head: read the code and run it mentally. And when the code is fine, the data probably is not, so trace where good data turns bad.

1

Read the code: become the virtual machine

Reading code shows you the bigger picture the debugger hides: surrounding systems, paths that were not taken this time, assumptions that could break. Read it as if you were executing it. Remember each assignment, enter each call, do each calculation (or at least estimate it), and keep a scratchpad of values as you go. Skim first for obvious problems, then go line by line where it matters. Predict which iteration crashes, then run your brain VM.

Bugs that cross languagesA C++ client calling a server written in another language, or a C++ engine with a GUI in Lua: you have to read and debug both sides. If one side is too costly to follow, mock it with a response you have actually observed, not an invented one, so you are still investigating a case that can really happen.






  
2
Readable code hides fewer bugs

  

    

      
The easier code is to read, the easier it is to execute mentally, and the less room a bug has to hide. Two principles: avoid surprises (look and behave like the rest of the project, keep it simple) and choose descriptive names. Readability fades even for the author, which is why code reviews matter. Code is written once and read for years.

      
Type information helps too. auto it = map.find(k); is quick to write; when reading it you have to work out what it->second actually is.

Know your language's trapdoors

  
Features that run code without an obvious call are where reading goes wrong: implicit conversions, exceptions, polymorphism, operator overloading; in C++ also constructors and destructors, temporaries' lifetimes, pointer and string comparisons, arrays decaying to pointers, undefined behaviour, macros and shadowing; in C# properties, value versus reference types, boxing and string comparison; in Python mutable defaults, scoping, late-binding closures and 2-versus-3 division. 4
Follow the data to where it turns bad

  
Code is only half the story. Data (inputs, outputs, assets, configuration) rarely sits still: the program transforms it, losslessly (format conversion) or lossily (compression, rounding). Bugs live in transformations, so follow the data through each one and find the first step where it is wrong. Start from the pristine original, keep good and bad samples side by side, and work forward or backward. Here a user's profile photo ends up with a garbled caption. Inspect stages, as few as possible.

5
Values that should make you suspicious

  
Wrong-but-plausible data points to a logic or specification problem. Corrupt data always means an implementation bug in some transformation, and it often has a recognisable look. Tap each value: suspicious or fine?

  

    

    

  

  
A ported programAfter a move from 32-bit to 64-bit, a low-level C++ program mostly worked but crashed now and then. The tell: many pointers had their upper four bytes all zero. Somewhere, pointers were stashed in 32-bit integers and converted back, cutting off the top half of every address that needed it.






  
6
Compare good and bad data

  

    

      
Putting a good sample beside a bad one often reveals a systematic difference: every accented letter turns into two odd characters, XML arrives where JSON was expected, text where binary should be. Diff tools work for text; images, meshes and audio need their own viewers, and custom formats may need a small converter you write (see the next chapters).

      
A classic: UTF-8 bytes read as if they were a single-byte Western encoding. Type something with accents and watch it break exactly the same way every time.
