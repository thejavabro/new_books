Just Fix It, Share What You Learned, Search for Related Problems

A good fix removes the root cause, can be reverted, and is verified. Then the job widens: document it, guard against it coming back, and find the same mistake everywhere else it was copied.

1

What makes a great bug fix

Part IV starts with a reality check: time pressure, limited control over the affected systems, the need for sweeping changes, missing expertise, or hardware limits can all rule out the perfect fix. Then a stopgap is fine, as long as the real fix is planned. But first aim for the ideal. A great fix is minimal, complete, permanent, clear, tested and timely, and timeliness is the one that most often fights the rest. Compare three candidate fixes for a crash when a user's display name is empty.

2

Make it revertible, then prove it

A clean, minimal change is easy to undo, which matters for three reasons: fixes that do not work must come out, fixes with bad side effects must come out, and undoing a fix is how you prove it worked. Run the repro several times with the fix, revert it and watch the bug return, then reapply. Commit the fix on its own, without your other local experiments. If the bug had several causes (say, code that breaks an asset), untangle them one at a time.

Then test for side effects: other code may rely on the old behaviour. Ask QA to test the area, and if a toggle is impossible, run old and new side by side.

The bug used to reproduce about 40% of the time. One clean run proves nothing.

3

Change the original sources, the right ones

Fix the sources, never generated artifacts that the next build will overwrite. The change might be one character or a redesign; it might be code, an asset that breaks the rules, the rules themselves, the architecture, or a shared protocol spec that several programs follow. Be sure before you commit: a wrong fix leaves the root cause in place or makes things worse.

Tiny

Other programs rejected a library's files. Days of investigation, then a one-word fix: the format spec required mimeType, the library wrote mime_type.

Not a bug

A setup tool "hung" installing software that was already installed in another version. Unblock the colleague, then schedule a proper feature: detect existing installs. Watch for features filed as bugs to jump the queue.

Too big

To fight float precision over huge distances, a team divided every size and distance by 100, code and assets alike. Months later, that tiny scale clashed with every tool's defaults and had to be reverted. Be confident before sweeping changes.

For large fixes, bring in the people who own the affected areas, split the work only if it truly splits, and ask for a second opinion on the approach. If your team's workflow made the mistake easy, change the workflow too.

4

Share what you learned

You paid for this knowledge; spread it. Write a commit message that explains root cause, symptoms and solution (it will help the next person bisecting). Put the same in the bug tracker for a different audience. Write a document for big fixes, a code comment linking the bug where code is fragile, and tell the team. The author runs a recurring "Bug of the Fortnight" slot in the programmers' meeting: the most interesting fix of the last two weeks, mistakes welcome, sometimes with everyone guessing the cause first.

Find out how the bug got in

  
Assume nobody adds bugs on purpose. Causes fall into ignorance (did not know, or was told wrong), oversight (knew, but forgot, was rushed or distracted) and the occasional deliberate shortcut under deadline. Each needs a different remedy. Look at the commit, its documentation, and the calendar (was it the night before a milestone?), then talk to the people involved, respectfully; personal circumstances can play a part and some questions are off limits at work. Search for the same mistake elsewhere

  
A bug rarely exists once. It was copied and pasted, or the same misunderstanding was applied in several places, or a hard API invited everyone to make the same slip, or a dependency changed underneath many callers. Fixing the siblings now, while you understand the problem, is far cheaper than rediscovering each one later. Search with a fragment that captures the pattern without concrete data. Try three searches on this codebase.

  

    

    

    

    

  

  

    

      
Other places to look

      
The commit that introduced the bug (its other hunks, its message, its author's nearby work); other call sites of the same function (IDE "find all references"); the rest of the system where the bug lived; duplicated files; references to the same host, asset or path; platform-specific branches (one port needed every #ifdef block updated in one go).

    

    

      
Let the compiler help

      
Changes to shared code should break the build where callers are wrong. The dangerous ones compile silently: a parameter whose meaning changes but type does not, or a type that changes to something still implicitly compatible. Give assets and protocol messages version numbers so outdated ones fail loudly.

    

  

  
Bulk changes, with cautionSpeculative fixes skip most of the debugging workflow, so be sure the pattern really is the same, try to reproduce each potential bug, and tell QA which areas you touched. Expect the occasional "how did this ever work?": often the code simply never ran, or people saw the problem and never reported it.
