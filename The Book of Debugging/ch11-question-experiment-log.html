Question Everything, Experiment, Keep a Log

The bug lives where you are sure it cannot be. Question every assumption, turn hunches into testable hypotheses, and write down what you tried so you never repeat yourself.

1

Question everything, layer by layer

If the cause is hard to find, it is probably hiding where you are not looking, which usually means somewhere you assumed was fine. A cause must exist, in the program or its environment. You cannot search everywhere, so intuition and experience still pick the order, but nothing is exempt: not old code, not famous libraries, not drivers. Tap the layers to mark what you have verified rather than assumed.

Assumptions verified
Cause and effect can be far apartA released game crashed inside its third-party physics engine, all over the world map. The link nobody would have guessed: it only happened when the player jumped on one particular object, which appeared in many places. Its collision shape was set up wrong.

Do not get lost, though: dig deep only along leads that matter. And verify, do not just suspect: debug the component if you have source, run hardware diagnostics, read the docs' known-issues sections, and test the suspect in isolation with a minimal repro.

2

Experiment with hypotheses

Experimenting is like varying the reproduction steps, but in the code. Start loosely (change things, force conditions, see what moves the bug), then get structured. For each experiment, answer three questions:

1What is the hypothesis?
2How will you test it, as cheaply as possible?
3What will you learn either way?

3
Cheap ways to test a hypothesis

  
Speed matters more than polish here. Take shortcuts and ignore best practices, as long as you can undo it all.

  

  
The hackiest fix proves the pointMeshes rendered wrongly. Hypothesis: the loader reads the wrong vertex count, three times too small compared with the authoring tool. Multiplying the count by 3 in the renderer fixed it, which confirmed the theory. Then a hard-coded correct count in the loader confirmed the problem was in the file itself. Only then did the real fix go where it belonged: the exporter, which mixed up triangles and vertices.






  
4
When the options are few, try them all

  

    

      
Sometimes semi-random changes are the fastest route. Matrix multiplication order is the classic graphics example: order matters, and with two matrices there are only two orders, with three only six. If iteration is quick, just try each one.

5
Keep every experiment revertible

  

    

      
Experimental code is not meant to ship. Two ways to keep it undoable: version control (reliable, but your other local changes get mixed in) or unique comment markers you can search for. Markers also let you share an experiment through version control and run several in parallel, reverting one while keeping the others.

      
When an experiment fixes the bug, keep the dirty version around while you write the clean one, and compare: the clean fix must be at least as good.

    

    
// EXP-17 begin: force LOD 0 to test streaming theory

6
Keep a debugging log

  
Write down everything you try, the places you ruled out, and every idea that pops up, so you never repeat work, never lose your place, and can answer "where are we?" with facts. New ideas mid-investigation are distractions; capture them and keep going. Then prioritise by effort and probability, and always keep the next good lead lined up (the author makes sure to have one ready on Friday for Monday morning). Try it; this log stays in your browser only.

  

    

    

    
Score = chance it leads somewhere ÷ effort. Highest first; finished leads sink, with their conclusion kept.

  

  

  
Document known issuesAfter an update, an online platform kept freezing until a user pointed out it happened when opening the knowledge base. The team had seen it during development: a circular dependency between entries caused an infinite loop, cured by a database command after each deployment. Nobody had written it down. Afterwards they did, symptoms and command included.






  
7
Where to keep your notes

  
FormatStrengthsWeaknesses

    
Plain text / MarkdownOpens anywhere, easy to diff and version.No embedded images or video (Markdown can link them).

    
Documents (.docx, .odt, OneNote)Embed screenshots, videos and data directly.Harder to diff and merge; tied to an application.

    
Wiki or online toolEasy to share, collaborative, with history.Depends on the service and access to it.

    
Team chatWhere answers often appear anyway; searchable.Scattered: copy conclusions into the bug report.

  

  
Whatever you choose, link the notes from the bug report and archive them centrally. The same bugs come back.
