Shorten the Feedback Loop

Each attempt at a bug costs a build, a deploy, a launch and a walk to the right place. Shrink every one of those and you get many more tries per hour, which is the real speed of debugging.

1

Four slices of every attempt

Debugging is a loop of change, try, look. The time between making a change and seeing whether the bug still happens splits into four slices: build the code and assets, deploy them to the device, start the program, and navigate to the place where the bug appears. Each slice can be attacked separately, and every second saved is multiplied by every attempt you make. Switch on techniques below and watch the cycle shrink.

Build faster: code

For compiled languages the setup of the project and the build tools matter most. The book lists a family of techniques:

Incremental builds of one or two changed source files are fast these days. The slow case is touching a header that many files include: one small edit can rebuild half the codebase. Click a file below to see how far a change ripples.

click a file

With pointer-to-implementation, the header only forward-declares a hidden Impl class, so changing private members or function bodies touches only one .cpp. Changing the public interface still rebuilds every includer.

// Widget.h: public face only
class Widget {
public:
  Widget(); ~Widget();
  void Draw();
private:
  struct Impl;   // defined in Widget.cpp
  Impl* impl;
};

Hacks are fine while hunting

While iterating on a fix, it is acceptable to dodge header edits: declare a function locally in the one .cpp that calls it, or poke a quick global variable to try something. Just mark every such shortcut with a comment that does not appear anywhere else in the codebase, so you can search for it and clean up before you commit.

extern int g_forceSlowPath; // HACK-JK: remove
3

Build faster: assets

Assets (window layouts, images, templates, databases, textures, meshes, levels, shaders) often need preprocessing. Profile the asset pipeline first, then apply the same tricks as for code: distribute, cache, and only build what you need. Some programs can process assets on demand at runtime instead of up front, trading runtime speed for less waiting.

Two classic bottlenecks: texture compression (use lower resolution and cheaper compression in development builds) and shader permutations, where hard-coding features multiplies the count into the thousands. Good dependency tracking lets you build only the shaders for one scene, and switching off unrelated rendering features shrinks the set further.

256shader variants to compile

Each on/off feature doubles the count; a scene that only needs a few variants is much faster to iterate on.

4

Deploy less, deploy faster

On a development PC, deployment may not exist. On consoles, phones, dev kits or remote servers it can dominate the cycle, especially when gigabytes of content are involved. Options, roughly from best to worst:

Best

Files on demand

Some device tooling lets the program read files straight from your PC. If it does not, a custom file system layer that fetches over the network and caches locally does the same job.

Good

Copy only the delta

Small, atomically replaced files copy quickly. One giant multi-gigabyte archive that must be rebuilt and resent for each change does not.

Also

Better pipes, smaller packages

Fastest cable and port, wired network instead of Wi-Fi, and a package cut down to the one level or character you are debugging.

Do not remove the bug along with the bulkTrimming the package changes the environment. If the bug depends on timing, shorter load times may make it vanish. After every such change, confirm the bug still reproduces the same way.
5

Hot reloading skips three slices at once

Loading new code or assets into the running program avoids redeploying, restarting and navigating back. Scripted languages make this easy; native programs usually reload a dynamic library (.dll/.so) or patch the executable, and may need code to fix up data whose layout changed.

Two warnings. Hot reloading is a development-only feature and often poorly tested, so it can produce bugs of its own and send you chasing ghosts. And dependents need to hear about reloaded assets: a texture is easy to swap, but code that inspects that texture, or samplers and materials built from it, must be notified and rebuilt.

6

Cut the start-up and the waiting

Everything between launch and the first reproduction step is overhead. Splash and legal screens, preloading that your bug does not need, menus that demand clicks. The hidden cost is the switching: every time you go from waiting to doing, you lose a moment finding the right button, and long waits invite you to read something else and lose the thread entirely.

Also shorten the individual steps: repeat an action 5 times instead of 10, wait less than the report says, start from a prefilled template. After each tweak, check the bug still reproduces just as it did with the original instructions.

The last slice, getting to the right screen, level or record, is best handled by automation (the next strategy) or by tools built into the program that jump straight there.

7

Make loading itself faster

Loading usually breaks down into five stages: read from disk, decompress, find and load dependencies, process the data for use, and (for graphics) upload to video memory. Faster drives, one big read instead of many small ones, asynchronous IO and memory mapping help with the first. Compression is the surprising one: reading less data almost always beats the CPU time spent decompressing it, especially with a fast codec on spare cores.

Simplified model: reading and decompression overlap, so the slower of the two sets the pace.
