Start Over, Find a Creative Solution, and the Conclusion

When the old code cannot be saved, rewrite it carefully and compare. When it cannot be fixed at all, call it a feature, cut it, disable it, or let it be, and say so out loud. Then a look back at the whole workflow.

1

Start over: rewrite the offending part

For a particularly mean bug, or a system with recurring problems, it can be easier to reimplement the functionality than to keep hunting. A rewrite written at a different time, under different assumptions and ideally by a different person, is unlikely to contain the same mistake. Once it works, comparing old and new pinpoints where the original went wrong.

Rewrite for real: don't refactor or shuffle pieces around inside the old structure. Choose the plainest approach you trust (no clever threading, raw pointers or direct memory access), cover it with unit and integration tests, and if possible develop it outside the main program behind the same interface, so it plugs straight back in.

Before you commit to a rewrite

Old systems hide small real-world tweaks that nobody wrote down. Tap to uncover what the "simple" function actually does.


      

      

    

  






  
2
Clean room or dirty room

  
How do you know what the rewrite must do? In a clean room you never look at the original; you work only from a specification. In a dirty room you study the original first and translate its purpose, not its lines. Switch between them.

  

    

    

  

  
From the fieldThe author once wrote a bespoke HTTP server that passed every test but stumbled over some headers in production. Unable to pin down which, he rewrote the request parsing straight from the HTTP specification, which worked far better. Today he would start from an existing, well-tested server instead.






  
3
Run both, compare, and let the differences talk

  

    

      
With both versions working, feed them the same inputs and compare outputs. Make switching easy: a runtime switch is best, a start-up flag or config setting is next, a compile-time switch is the last resort. For many inputs and rare differences, let the program compare automatically and shout (log, breakpoint, on-screen message) the moment they diverge.

      
The diverging inputs point at the root cause. Here an old DaysInFebruary and its rewrite run over 220 years.

      
// original
return (y % 4 == 0) ? 29 : 28;
// rewrite, straight from the calendar rules
bool leap = (y % 4 == 0 && y % 100 != 0) || y % 400 == 0;
return leap ? 29 : 28;

      
Watch for hidden shared state: if the first implementation modifies its input in place, copy the data before running it, or the second version is compared on the wrong input. If both versions agree but are both wrong, the bug may not be in this functionality at all.

Stub first, grow laterShort of a full rewrite, write a stub that returns known-correct outputs for a handful of inputs (worked out by hand or with another tool) and refuses anything else. Extend it gradually: either the bug reappears along the way, or you end up with a reference implementation. Afterwards keep it; an automated comparison can live on in the test suite.

From the fieldA Vulkan renderer had thousands of pipeline state objects that were slow to create, so the team cached them on disk. Loading that cache sometimes crashed the program at start-up, and long debugging found no answer. Because the cache was only an optimisation, they simply disabled it; no user-facing feature went missing.

Disable, don't delete

  
A removal is usually temporary. Code that stays in the codebase is quicker to bring back than an old commit, and it documents what existed. Three ways to switch it off, each with a different trade-off:

  

    

    

  

  

    
Disable selectively and let testers opt in

    
Instead of removing a broken feature for everyone, turn it off by default and let QA or volunteers switch it on to keep debugging it. Who sees the PSO cache?

    

    

  






  
6
Talk, write it down, track the debt

  

    
Get consent
Changing the feature set, even temporarily, needs every stakeholder on board: tech lead, marketing, directors. The bigger the impact, the more options they will want to weigh, from shipping late to shipping without it.

    
Document the decision
What, why, how, who decided, and when it should be revisited. Link it from the code, so nobody "fixes" a bug that became a feature or re-enables a disabled one by accident.

    
Tell users
If they must change how they work, brief them and say when you expect the feature back. A little about the cause helps; too much detail invites armchair debugging. Minor bugs you let be still belong in the known-issues list.

  

  

    
Technical debt list

    
Every creative fix is debt. Keep one shared list: what it is, where it lives, how to pay it off. Remove an entry only once the real fix lands.

The same loop works outside code

  
Reproduce, probe, examine, fix also helps when verifying your own changes, chasing performance with a profiler, getting to know a new project, or when the house goes dark. Returning from a holiday, the author found the power out, but only in his house. The earth-leakage breaker tripped again every time he reset it. With all circuits off it held, so he turned them back on one at a time. Your turn: find the faulty circuit in as few resets as you can.
