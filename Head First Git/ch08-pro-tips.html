Configuring Git: global and local

Back in chapter 1 you ran git config --global user.name. The --global flag writes to a .gitconfig file in your home folder, which applies to every repository on your machine. Run git config inside a repository without --global (or with --local) and the setting goes into .git/config for that one repository. Git reads global first, then local; when both set the same key, local wins.

Handy commands: git config --list shows everything Git sees (global entries first), --show-origin adds which file each came from, and git config --local --unset user.email removes a local override. Git doesn't validate keys: a typo like user.nme is stored happily and does nothing.

Aliases: your personal shortcuts

  
An alias is a configuration entry that expands a short name into a longer Git command. git config --global alias.loga "log --oneline --graph --all" lets you type git loga. Anything you type after the alias is passed along, so git c -m "msg" works if c means commit. What an alias can't do is un-include a flag it already contains, so keep them general.

Telling Git what to ignore

  
Build output, logs, editor settings and OS junk like .DS_Store shouldn't be committed. List them in a .gitignore file at the top of the project (and commit that file). Ignored files no longer show up as untracked in git status, and git add . won't pick them up. One pattern per line; # starts a comment; * is a wildcard; a trailing / means "a folder"; a leading ! re-includes something. .gitignore only affects untracked files. Something already committed stays tracked until you remove it from the index. Don't write one from scratch: templates for most languages and editors exist (GitHub publishes a collection), and you can trim from there.






  
4
Commit early, commit often, and say why

  
Commit whenever you reach a good place. Each commit is a save point you can diff, revert or branch from. Think scope, not size: fixing inconsistent verb tenses across a chapter is one commit; the unrelated typos you spotted along the way are another. Tidy is nice, but don't let the perfect be the enemy of the good.

  
Write messages like an email: a short header, then optionally a blank line and a body. git log --oneline and GitHub show only the header, so make it count. The book's header recipe: a type, a colon and space, a lowercase description in the imperative mood ("add", not "added"), and the ticket number in parentheses. Focus on why more than what.

5
Helpful branch names

  
Slashes are allowed in branch names, so use them to build names from parts. The book suggests your initials (so git branch -a shows who owns what), the ticket number (it then appears in every git status, right when you're about to commit), and a short description taken from the ticket title (a bookmark for your brain when you come back to it).

  

    

    

    
Renaming later is easy: git branch -m old new (chapter 4).

  






  
6
Bring in a graphical interface

  
Every Git GUI runs Git commands under the hood, so it can't do anything the command line can't. What it does well is show: the commit graph, diffs side by side, blame inline, all at a glance. The book's suggestion is to use both: type commands to understand what's happening, keep a GUI open to see the result.
