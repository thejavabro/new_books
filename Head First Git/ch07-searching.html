Searching Git Repositories

When the history gets long you need search tools: who wrote this line, where does this text live, when did it appear, and which commit broke things.

1

Who changed this line? git blame

Trinity and Armstrong are back, now planning Gitanjali and Aref's wedding. The repository has grown, and the questions change from "what did I just do?" to "who wrote this, when, and why?". git blame file answers the first two for every line: it prints the file with the commit ID, author and date of the commit that last touched each line. Tap a line.

GitHub, GitLab and Bitbucket all have a "Blame" view on any file, with links straight to each commit. Editor plugins such as GitLens show the same information inline.

2

Searching the files: git grep

git grep "text" searches every file Git tracks and prints each matching line prefixed with its file name, files in alphabetical order. Because it only searches tracked files, an untracked new file won't show up until you add it. Toggle the useful flags:

-i (--ignore-case): Cheese, CHEESE and cheese all match. -n (--line-number): show where in the file. -l: just list the files, each once. The book's favourite combo is git grep -i -n.

3

Searching history: the pickaxe

git grep searches the files as they are now, and git blame only knows the last change to each line. To ask "when did this text appear or vanish?" across all of history, git log has two "pickaxe" flags. Take a one-line file changed in three commits:

-S: count changedLists commits where the number of occurrences of the text went up or down: it was added or removed.
-G: appears in the diffLists commits where any added or removed line contains the text (a regular expression, in fact), even if the count didn't change. Good for "every time the line with this function name changed".

Add -p (--patch) to see each listed commit's diff, and the usual --oneline/--graph/--all still apply. To search commit messages instead of content, use git log --grep "first draft" (add -i to ignore case).

4

Checking out a commit: detached HEAD

Want to see the project exactly as it was at some commit? git checkout <commit-id> rewrites your working directory to that snapshot. HEAD now points straight at a commit instead of at a branch, and Git warns you that you are in detached HEAD state. Looking around is perfectly safe. The catch is committing:

The moralCommits made while detached belong to no branch. Switch away and nothing points at them; they're effectively lost (and eventually cleaned up). If you might want to keep experimental work, create a branch first: branches are cheap.
5

Finding the bad commit: git bisect

Trinity spots that "blinis" is misspelled on the menu, and it was right once. When you don't even know what text to search for, the pickaxe can't help. But you can test any commit. git bisect runs a binary search: you mark one bad commit and one good one, Git checks out the commit halfway between, you test and say good or bad, and each answer halves what's left. Sixteen commits take at most four tests.

git bisect startBegin a session.
git bisect bad [id]This commit (default HEAD) has the bug.
git bisect good <id>This one didn't. Git checks out the midpoint.
git bisect resetFinished: return HEAD to where you started.
