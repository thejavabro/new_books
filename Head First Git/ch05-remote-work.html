Collaborating with Git, Part I: Remote Work

1

From one repository to a shared one

So far every repository started with git init on your own machine. Most real projects are shared: a copy of the repository lives somewhere everyone can reach, and people exchange commits with it. That shared copy is a remote. Its history becomes a shared history.

The book uses GitHub as the host (GitLab and Bitbucket work much the same). Two words get mixed up early on:

Fork: a GitHub featureCopies someone else's repository into your GitHub account, so you can push to it. You fork the book's working-with-remotes repo because you can't write to the author's copy.
Clone: a Git commandCopies a repository from anywhere down to your computer. git clone <url>, using the HTTPS or SSH address GitHub's green Code button shows you.

Pushing to GitHub over HTTPS asks for a username and "password"; the password it wants is a personal access token you generate in GitHub settings. An operating-system credential helper can remember it for you.

3

Git is distributed

A clone isn't a checkout of some files. It is the entire repository: every commit, every branch. Nothing makes the copy on GitHub special except that the team agrees to treat it as the source of truth. Lose it and any full clone can stand in.

So why use GitHub at all? It is easy to find and share, handles access control, and adds collaboration tools such as pull requests on top of plain Git.

4

Pushing, and why public commits are different

git push sends your new commits to the remote and moves the remote's branch to match. Until then your commits are private, like a draft post: you can amend, reset or reshape them freely. Once pushed they are public: other people may build on those exact commit IDs. If you rewrite a commit you have already pushed, its ID changes, the two histories no longer line up, and Git rejects your next push.

Sharing is caringRewrite private commits all you like. Treat pushed ones as permanent: to undo a public commit, use git revert (chapter 4), which adds history instead of changing it.
5

Pushing branches and merging them

Nothing about branches changes with a remote: you still do each task on its own branch. The first push of a new branch needs one extra hint, because the remote has never heard of it. git push --set-upstream origin feat-a (short form -u) creates the branch on the remote and records that your local feat-a belongs with origin/feat-a. After that, plain git push knows where to go.

When the work is done, there are two ways to get it into the integration branch:

Option 1: merge locallygit switch master, git merge feat-a, then git push so the remote's master gets the result. Quick, but nobody reviews it.
Option 2: pull requestPush the branch, then ask on GitHub to merge it into master. Teammates can read the diff, comment, and approve before GitHub performs the merge. GitLab calls the same thing a merge request.
6

The life of a pull request

A merged pull request changes the remote's master, not yours. Your local master is now behind; catching up is the subject of chapter 6.
