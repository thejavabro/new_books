Leftovers: Five More Topics

Five useful tools that did not fit in the main chapters: landmarks, copying commits, parking unfinished work, the safety net, and the other way to merge.

1

#1 Tags: landmarks that never move

Like a branch, a tag is a name for a commit. Unlike a branch, it never moves. Use tags for landmarks: a release (v1.0.0, the "v" prefix is a common convention), or the commit that finally fixed a nasty bug. git tag v1.0.0 tags the commit HEAD points to; add an ID to tag another one. git tag -l lists them. Tags are shared by pushing and fetching with --tags. A tagged commit stays reachable even with no branch on it.

2

#2 Cherry-pick: copy one commit

On your feature branch you fix a bug that production needs now, but the feature isn't ready to merge. git cherry-pick <id>, run on the integration branch, replays that single commit's changes there as a new commit (same change, new ID). It can conflict like any merge. Use it sparingly: copies of the same change scattered across branches make history harder to read. Keeping different kinds of work in separate commits (and separate branches) is what makes it possible at all.

3

#3 Stash: park unfinished work

You start editing and realise you're on the wrong branch, and switching would clash with your changes. git stash tucks your uncommitted changes (working directory and index) away and leaves you clean. Switch, then git stash pop puts them back and removes the stash. Stashes form a stack, like pancakes: the last one in is the first one out. They are local only and never pushed.

More options: a message (git stash push -m "…"), git stash apply stash@{2} to apply without removing, and flags to include untracked files or only part of your changes. Don't use stashes as long-term storage: that's what branches are for.

4

#4 Reflog: the safety net

Git keeps a private diary, the reflog, with an entry every time HEAD moves: commits, switches, merges, resets. git reflog prints it newest first, each line naming a position like HEAD@{2}. So when a git reset --hard seems to have destroyed commits, they're only unreferenced; the reflog still knows their IDs. Like stashes, the reflog is local to your clone and is not shared.

Tap a reflog line to reset back to it.

5

#5 Rebase: another way to combine

When master and rg/feat-a have diverged, merging makes a merge commit. Rebasing makes it look as if you had started your feature from master's latest commit: from rg/feat-a, git rebase master replays each feature commit on top of master, one by one, as new commits (C′, D′), then moves the feature branch to the last of them. History becomes a straight line, and merging the feature into master afterwards is a fast-forward.

Same files, different historyBoth end with the same content. But rebasing rewrites commits, so their IDs change. Never rebase commits that are already public. The book's advice while learning: merge. Pick up rebasing once you know your team's workflow.
