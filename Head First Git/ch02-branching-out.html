Branching Out

Branches let you work on several unrelated things in the same project without tangling them. A branch turns out to be nothing more than a movable name for a commit.

1

Why branches: Norm's tangled bug fix

Norm is halfway through a big feature, committing as he goes, when a production bug lands on his desk. He fixes it and commits. The trouble: every commit is built on the one before it, so his fix sits on top of his half-finished feature. Shipping the fix ships the unfinished work too. Untangling it by hand means stashing changes in his head and hoping he misses nothing.

Branches solve this. Each line of work gets its own track, starting from a known-good commit, and the tracks don't see each other until you decide to merge them.

2

Creating and switching branches

Every repository starts with one branch. Git calls it master by default (many teams rename it main; nothing about the name is special). Three commands do most of the work:

git branchList branches; the current one has a *. Safe: it never changes anything. Add -v to see each branch's latest commit.
git branch add-fall-menuCreate a branch at the current commit. It does not move you onto it.
git switch add-fall-menuMove onto a branch. git switch -c name creates and switches in one go. (Older tutorials use git checkout; switch is the newer, clearer command.)

Rules of thumb: no spaces (use hyphens), forward slashes are fine and handy for grouping (rg/fix/typo), and creating a name that already exists is an error, so list branches first. Need the docs? git branch -h gives the short version; git branch --help opens the full manual (press q to quit the pager).

3

A branch is just a sticky note on a commit

Say it slowly: a branch is a reference to a commit. Each commit records the ID of its parent, so commits form a chain. A branch is a sticky note with a name and one commit ID. When you commit on a branch, Git writes the new commit with the old tip as its parent, then peels the sticky note off and moves it to the new commit. HEAD marks which sticky note is "current".

Switching rewrites your folderA commit is a snapshot of every staged file. When you switch branches, Git replaces the contents of your working directory with the snapshot of that branch's tip commit. Files that exist only on the other branch disappear from disk (they are safe in the repository) and come back when you switch back. If you have a file open in your editor, reload it after switching.

5

Two kinds of merge

Merging takes two branches: the one you are on (it receives the work) and the one you name (it is mixed in). Picture icing being folded into a cake: you stand at the cake and pull the icing in. At the '80s Diner, the fall menu and the Thursday menu each grew on their own branch off master. Step through what happens when both come home.

Fast-forwardIf the receiving branch has had no new commits since the other branch split off, everything it has is already contained in the other branch. Git just slides the sticky note forward. No new commit.
Merge commitIf both sides have new commits, the histories have diverged. Git writes a new commit with two parents: the first is the tip of the branch you are on, the second is the tip of the branch you merged in. Git asks you for its message (it opens your configured editor with a sensible default).

Direction matters. Merging master into add-fall-menu when master hasn't moved just reports "Already up to date": the feature branch already contains everything master has. The files are the same either way; the history is not.

6

When both sides change the same lines

Usually Git combines the two sides on its own. When both branches changed the same lines of the same file, it can't choose for you. It stops, writes both versions into the file between markers, and waits. You edit the file into the version you want, git add it, and git commit to finish the merge.

The markers are plain text that Git inserted. <<<<<<< HEAD starts your side, ======= divides, >>>>>>> branch ends their side. Delete all three marker lines when you resolve.

7

Deleting branches, and a typical workflow

Once a feature branch is merged, its sticky note is clutter: the commits are reachable from the integration branch. git branch -d name deletes it. If the branch holds commits that are not merged anywhere, -d refuses, protecting you. -D (capital) forces it when you really mean to throw that work away. You can't delete the branch you are standing on.

Integration vs. feature branchesPick one long-lived integration branch (master or main) where finished work comes together. Do everything else on short-lived feature branches, one task each, created from the integration branch, merged back, then deleted. Keep feature branches specific to the one thing they do.
