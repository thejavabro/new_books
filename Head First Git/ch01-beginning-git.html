1

Why version control: a save button for your work

Long video games let you save before the boss fight, so a bad run costs you minutes, not the whole game. Version control does the same for a project. You work a while, take a snapshot of every file you care about, and keep going. Wreck something later and you reload the snapshot. Like what you did and you take another.

Git adds two more jobs on top of that: it remembers who changed what and when (credit or blame), and it lets several people change the same files without trampling each other. Memory bank, safety net, collaboration platform.

Just enough command line

The book drives Git from a terminal (Terminal on macOS, Git Bash on Windows), so the first stop is four commands. Almost everything at the command line is relative to the folder you are in, so the habit to build is checking where that is.

Folders with a dot in front are hidden. ls skips them; ls -A shows them.

Spaces split argumentsThe shell uses whitespace to separate a command from its arguments, so mkdir my projects makes two folders. Quote the name (mkdir "my projects") or, easier, never use spaces: my-projects. Single or double quotes both work as long as they match; use double quotes when the name itself contains an apostrophe.
3

Creating a repository with git init

A repository is a folder that Git manages. You make one by running git init in the top folder of a project. Git answers by creating a hidden .git folder and stocking it with configuration and a place to keep snapshots. That folder is the repository: every commit and branch lives inside it.

Run it twice?Harmless. Git says it is reinitializing and nothing is lost.
No server?None needed to start. Sharing comes later (chapter 5).

4

What exactly is a commit?

Committing is two steps: git add Checklist.md picks what goes in, then git commit -m "message" takes the snapshot. Git stores a commit object inside .git and gives it a 40-character ID computed from its contents. Change anything about the commit, even one character of the message or the time, and the ID changes completely. The chance of two different commits sharing an ID is vanishingly small.

5

The three places a file lives

Why two commands? Because the repository has two parts. git add copies a file from your working directory into the index (the staging area). git commit copies everything in the index into the object database and records a commit. Your files are never moved, only copied, so the same file can exist in up to three versions at once.

The book's cooking image fits: the index is your mise en place. You chop everything on the board, but only gather the ingredients for this dish on the counter. Fixed a typo in the docs while building a feature? Stage the feature files, commit; then stage the docs, commit again. Two tidy commits from one messy session.

6

The life of a file, by comparison

Git works out a file's state by comparing its three copies. No copy in the index or database means untracked: Git sees it but ignores it until you add it. Once added, it is tracked for good, and then one of these holds:

Working dir vs indexIndex vs object databasegit status calls it
samesameunmodified (clean)
differentsamemodified, not staged
samedifferentstaged (changes to be committed)
differentdifferentboth at once: staged and modified

That last row surprises people. It is what you get when you add a file, keep typing, and don't add again.

7

The index is a scratch pad

Adding the same file again simply overwrites its copy in the index with the latest version. There is no "empty the index" step: after a commit the index still holds every tracked file, matching the commit exactly. New adds replace or join what is there.
