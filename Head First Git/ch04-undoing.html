Undoing

Every kind of mistake has a matching undo in Git. The trick is knowing which of the three areas the mistake lives in, and whether anyone else has seen it yet.

git restore: copying backwards

git add copies forward, from folder to index. git restore copies backward. With just a file name, it overwrites your working copy with the copy in the index, discarding unstaged edits. With --staged, it overwrites the index copy with the one from the last commit, un-staging the file while leaving your folder alone. It never touches commits.

3

Deleting and renaming tracked files

The couple swaps the gift registry for a home fund, so gift-registry.md has to go. git rm deletes a tracked file from both the working directory and the index. git status then lists it as deleted under "Changes to be committed", and the next commit records the deletion. Earlier commits still contain the file: history is never rewritten by rm. Changed your mind before committing? git restore --staged then git restore brings it back.

git mv old new does the same for renames and moves: it renames the file on disk and in the index in one step, ready to commit. Untracked files don't need either command; just delete or rename them normally.

Fixing the last commit, renaming a branch

Typo in a commit message? git commit --amend -m "better message" replaces the latest commit on the branch. It is not an edit in place: Git builds a brand-new commit from the old one's parent, the current index and the new message, and moves the branch to it. New content means a new ID. The old commit lingers unreferenced until Git cleans it up.

Only the tip can be amended. Amend as many times as you like.

Clean working directory firstAmend takes whatever is in the index. If you have other changes staged, they quietly join the amended commit. Run git status before amending.

Bad branch name? git branch -m old-name new-name (-m for move) renames the sticky note; the commits are untouched.

5

Pointing at commits relative to HEAD

HEAD marks where you are: normally it points at a branch, which points at a commit. To name commits behind it without copying IDs, Git gives two operators. Tilde ~n walks back n generations, always taking the first parent. Caret ^n picks the nth parent of a merge commit. You can chain them, and use them after commit IDs too.

For a merge commit, HEAD~1 and HEAD^1 are the same thing (the first parent). HEAD~ alone means HEAD~1.

git reset: three ways to un-commit

The party theme in the latest commit is a dud. git reset HEAD~1 moves the current branch (and HEAD) back one commit, so the bad commit drops out of the branch's history. The only question is what happens to the changes that commit contained. That is what the mode decides:

git revert: undo by adding

git revert HEAD undoes a commit without erasing it. Git works out the exact opposite of that commit's changes and records them as a new commit (it opens your editor with a message like Revert "add games"). History only grows, so it is safe even after others have the original commit.

reset
  • Moves the branch backward; the commit leaves the history.
  • Three modes, one of which (--hard) destroys work.
  • Clean history, but only for commits nobody else has.
revert
  • Adds an "anti-commit"; nothing leaves the history.
  • One mode, nothing lost.
  • The right choice once a commit is shared (chapter 5).
