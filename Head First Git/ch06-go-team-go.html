1

Two people, one remote

This chapter is a two-player game. Addison (Player One) and Sangita (Player Two) each clone the same GitHub repository and work on it at the same time. (Playing alone? Make two clones in two folders and switch hats.) Working in parallel is easy; the interesting part is what happens when both of them have new commits and need to see each other's.

The key fact: your clone never talks to the remote unless you run a command that does. git push sends; git fetch (and git pull) receive. Everything else is local. So how does your clone keep track of what the remote looks like? With a third kind of branch.

2

The middlemen: remote tracking branches

When you clone, Git creates a remote tracking branch for each branch on the remote, named remote/branch: origin/master and so on. Think of it as a bookmark that says "this is where master was on origin the last time I checked". You can't switch to them, commit on them, create or delete them: Git moves them, and only when you push or fetch. git branch -a lists them; git branch -vv shows which one each local branch is linked to.

3

Collaboration simulator

One GitHub repository, two clones, one branch. Teal tags are remote tracking branches. Each clone's status chip is what git status would say comparing master with origin/master. Try: Addison commits and pushes; Sangita commits and tries to push.

Hint: fetch is always safe. A push is only accepted if it fast-forwards the remote.
4

git pull is git fetch + git merge

git pull=git fetch+git merge origin/master

git pull fetches, then immediately merges the remote tracking branch into your current branch. Convenient, but it does two things at once, one of which changes your branch. The book's advice: prefer fetch, then merge, at least while you are learning.

Fetch never touches your branchesIt only updates remote tracking branches, so you can run it any time, as often as you like.
Fetch gives you a moment to thinkAfter fetching, git status says ahead, behind or diverged, and git diff master origin/master shows exactly what is incoming. Then you decide when to merge. Pull gives no such pause.
5

The ideal: only one side ever moves

Merging diverged branches means merge commits and possible conflicts. They only happen when both your local branch and the remote's branch gained commits. If only one side moves, every merge is a fast-forward:

How to stay in scenarios 1 and 2? Give every task its own feature branch that only you push to. Then the remote copy of your branch only ever contains your own commits, and catching up is never a real merge. If two people must share a branch, fine: just always fetch and merge before you push.

6

A typical team workflow

Merge locally or open a pull request?Either works. Merging locally adds commits to your local master that you then push. A pull request lets GitHub do the merge after review. Most teams use pull requests for integration branches.
7

Cleaning up remote branches

Leave the campground cleaner than you found it. After a feature is merged there are three things to delete: the branch on the remote, your remote tracking branch, and your local branch.

WhatCommandNotes
Branch on the remotegit push -d origin feat-aYou push a deletion. Git also removes your origin/feat-a. Or use GitHub's "Delete branch" button after the PR merges.
Stale remote tracking branchesgit fetch -p--prune: fetch as usual and delete tracking branches whose remote branch is gone (say, deleted on GitHub, or by a teammate).
Local branchgit branch -d feat-aSame as chapter 2. Switch off it first.

If git push -d says "failed to push some refs", the branch probably doesn't exist on the remote (check the name, or whether someone already deleted it).
